# T1797 - ghoztty CLI commands open windows and panes in the background on Windows; --focus opts in

## Summary

Mac commit 3081022ec (merged as 6e3c35c9b, 2026-10-08) flipped the default
for every `ghoztty +...` command that creates or finds a surface:

- The default is BACKGROUND: the app is not activated, the window is not made
  key, and the caret stays where the user had it. `--focus` (also
  `--focus=true|false`) restores the old raise-and-focus behaviour.
  `--no-activate` is still accepted, as a no-op.
- Covered: `+new-window` (terminal, `--view`, `--split`, `--from-focused`),
  `+split` (every anchor, terminal and viewer), `+new-remote-window`, and the
  idempotent `--target`/`--name` hits (an existing named window is raised
  only with `--focus`). A failed remote dial still alerts.
- A background window is ordered directly behind Ghoztty's frontmost window,
  not to the bottom of the z-order.
- Inserting a split must not leave keyboard focus on the window itself
  (Mac: `keepingFirstResponder`), so typing keeps going to the pane the user
  was in.
- Surfaces the user opens (keybinds, menu, palette, File Open) and the
  `ghoztty://focus` scheme are unchanged.

Windows today has the OLD contract: `src/apprt/win32/IpcHandlers.zig` calls
`SetForegroundWindow` unless `--no-activate` (`focusTarget` on a `--target`
hit, ~line 336/356; `+new-window` ~line 481-489), and even the no-activate
path relies on the window having been created focused and then re-shown with
`SW_SHOWNOACTIVATE`.

Windows-native translation: show the window with `SW_SHOWNOACTIVATE` and
never call `SetForegroundWindow`/`SetActiveWindow`/`SetFocus` on it by
default. Place it with `SetWindowPos(hwnd, <Ghoztty's topmost window>, ...,
SWP_NOACTIVATE)` so it sits just behind Ghoztty's frontmost window and never
above another app. A new split in a background window must not move Win32
keyboard focus to the new pane's child HWND, and when the caller's window IS
foreground the focused pane stays focused. `--focus` keeps today's
`SetForegroundWindow` path (with the existing T86 foreground-lock handling).
The `src/cli/*.zig` flag parse is shared: adopt main's text from 3081022ec
verbatim (`ParsedArguments.focus`) so T1796's merge resolves trivially.

## Validation criteria

- [ ] With another application in the foreground, `ghoztty +new-window`,
      `+new-window --view=<file>`, `+split --target=<pane>`,
      `+split --view=<url>`, `+new-remote-window` and a repeated
      `+new-window --name=<existing>` each leave `GetForegroundWindow()` on
      that application with its keyboard focus unchanged, and the new Ghoztty
      window is not above it in the z-order.
- [ ] The same commands with `--focus` raise and focus the Ghoztty
      window/pane (positive control in the same script).
- [ ] `--no-activate` is accepted and behaves like the default.
- [ ] A `+split` into the window the user is typing in keeps keystrokes
      going to the previously focused pane.
- [ ] `ghoztty://focus/<target>` and user keybinds still focus as before.
- [ ] The acceptance script itself never takes the foreground from the user:
      it runs on the background test desktop (`lib/TestDesktop.ps1`), adds
      no `@input-desktop-exception`, and `foreground-audit.ps1` stays at zero.
- [ ] `docs/claude/cli.md` and the bundled ghoztty skill describe `--focus`
      the same way on both platforms; `ipc-p1/p2/p3` ALL PASS.
