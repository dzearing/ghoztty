# T1507 - A remote machine on a skewed protocol version is back to reading as unreachable (arm 4b of ipc-remote is red)

## Summary

The app classifies a proto-version skew as DialFailed, so the CLI says 'failed to reach' - T628's wrong answer, back

## In plain terms

When the machine you are connecting to runs a different version of Ghoztty, the
error tells you the machine could not be reached. So you go and check the box,
the network and whether its agent is running - all four of which are fine - when
the only thing that can fix it is updating one side. T628 removed exactly this
answer; it is back.

## Goals

- [ ] `+new-remote-window` against an agent on an incompatible protocol version
      says `incompatible Ghoztty version on <host>:<port>` again
- [ ] It does NOT say `failed to reach`
- [ ] Arm 4b of `test\win32\ipc-remote.ps1` is green, and is demonstrated to go
      red on the broken build

## Details

### Measured 2026-09-12, Debug build, `test\win32\ipc-remote.ps1`

```
== 4b: a PROTOCOL SKEW says so, instead of reading as unreachable (T628)
  PASS skewed agent is running
  PASS skewed dial exits nonzero
  FAIL error names an incompatible version
  PASS error names the endpoint
  FAIL error does NOT blame reachability
    skew error was: failed to reach 127.0.0.1:54663: the agent is not running
                    or not reachable
```

Reproduced twice in a row. **Not caused by the T704 change** that was in the
tree at the time: that touches only the agent's per-shell wsl argv
(`windowsCommandArgs` in `src\remote\agent\pty_child.zig`) and nothing on the
handshake or classification path.

The skewed agent really is reachable, so the misclassification is not the
harness failing to produce the state: a second agent started with
`GHOZTTY_AGENT_INSTANCE` forked and `GHOZTTY_AGENT_PROTO_VERSION=0` while
sharing the first's `GHOSTTY_AGENT_LOCK` was measured ALIVE and accepting TCP
on its port (both ports answered `Connect`), so the app dialed a live listener
and still answered `failed to reach`.

### Where to look

`IpcHandlers.zig:620` asks `dial_failure.classify(err) == .incompatible`, and
`classify` only answers that for `error.ProtocolIncompatible`. That error is
minted in exactly one place - `tcp_dial.classifyHandshakeError` - and only when
BOTH halves hold:

```zig
error.Incompatible => if (peer_proto != null) error.ProtocolIncompatible
                      else error.HandshakeFailed,
```

So one of two things is true and the first job is to say which:

1. `waitHandshakeTicking` is no longer returning `error.Incompatible` for a
   version mismatch (it returns a timeout or a generic failure first), or
2. `conn.peerProtoVersion()` is null at that point - the peer's HELLO facts are
   read AFTER `shutdown()`/`joinPump()` precisely so they are available, and
   something on that path stopped recording them.

`log.warn("IPC new-remote-window: dial failed ... err={}")` in `IpcHandlers` has
the answer; on a Debug build it is in the app's log sink
(`%LOCALAPPDATA%\ghoztty[-debug]\ghoztty.log`). Get that error name first,
then fix, then teeth-check by reverting the fix and watching arm 4b go red.
