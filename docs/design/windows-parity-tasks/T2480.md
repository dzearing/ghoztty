# T2480 - Composition glides start about 2 refreshes (17-25 ms) after they are declared: measure click-to-first-motion on the composition path and decide whether to pre-commit or start the animation from the input handler

## Summary

The T2464 live spike run (T2360 "Live cadence report") found composition glides
advance on every refresh once they start, but the first frame lands about two
refreshes (17-25 ms at 120 Hz) after the glide is declared: 34 new frames in a
300 ms / 36-refresh glide, with every inter-frame gap exactly one refresh, so the
shortfall sits at the glide's start. In the spike the glide is declared from a
timer; in the app it will be declared from a click or a key, and this latency
adds directly to input-to-motion time.

Once the app animates on the compositor (T2469), measure click-to-first-motion
(input timestamp to first captured frame that moved) for a blade collapse and a
divider snap, next to today's gdi path, and decide whether anything should
change: start the animation from the input handler itself rather than a posted
message, commit the batch immediately, or accept it if it matches what macOS
Core Animation shows for the same gesture (one commit + one render pass).

## Validation criteria

- [ ] Click-to-first-motion measured on the composition path and on today's path, at 120 Hz, with the method named.
- [ ] Either p95 <= 2 refreshes, or a change lands that brings it there, or a recorded reason it cannot (with the Mac number for the same gesture).
