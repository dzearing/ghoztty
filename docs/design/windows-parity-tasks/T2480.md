# T2480 - Composition glides start about 2 refreshes (17-25 ms) after they are declared: measure click-to-first-motion on the composition path and decide whether to pre-commit or start the animation from the input handler

## Summary

The T2464 live spike run (T2360 "Live cadence report") found composition glides
advance on every refresh once they start, but the first frame lands about two
refreshes (17-25 ms at 120 Hz) after the glide is declared: 34 new frames in a
300 ms / 36-refresh glide, with every inter-frame gap exactly one refresh, so the
shortfall sits at the glide's start. In the spike the glide is declared from a
timer; in the app it will be declared from a click or a key, and this latency
adds directly to input-to-motion time.

Once the app animates on the compositor (T2469), measure click-to-first-motion
(input timestamp to first captured frame that moved) for a blade collapse and a
divider snap, next to today's gdi path, and decide whether anything should
change: start the animation from the input handler itself rather than a posted
message, commit the batch immediately, or accept it if it matches what macOS
Core Animation shows for the same gesture (one commit + one render pass).

## In plain terms

When you click a folded pane's strip, the panes should start sliding the
instant you let go. This measured how long they actually wait: about 30-44 ms
in today's build (four to five screen refreshes), 21-26 ms on the newer
compositor path. Both are longer than the two-refresh target, for two
different reasons, so each now has its own fix filed.

## Goals

- [x] A repeatable click-to-first-motion measurement on the real screen, without taking the user's focus
- [x] Numbers for today's path and the compositor path, with where the time goes
- [x] A decision, with the follow-up work filed

## Method

`scripts\comp-glide-hold-onscreen.ps1 -Clicks <n>` (new in this task): the
app runs as the off-focus ghost window, the strip click is posted and its
button-up stamped on QPC (100 ns units, the clock WGC stamps a frame's
`SystemRelativeTime` on), and each glide is filmed by
`ghoztty-comp-spike.exe --film-hwnd`. Click-to-first-motion is the first
filmed frame after the stamp in which any pane block moved, against the frame
on screen at the click. The app's debug log adds three stamps on the same
clock - `stack glide armed`, `stack glide first tick`, and `stack glide
declared commit` (the commit carrying a declared pane path) - so the wait
splits into its parts. Refreshes use the display's own rate (120 Hz on both
monitors here; the frame clock read 4 ms, because two unsynced 120 Hz
monitors interleave DWM's frames).

## Results (2026-11-26, 8 clicks per arm, -SlideMs 400)

| path | p50 | p95 | where the time goes |
|---|---|---|---|
| `on` - composition present, stepped (what ships) | 30.2 ms / 3.6 refr. | 38-44 ms / 4.6-5.3 | armed +1-4 ms; first tick 14-20 ms after arming, behind the click pass's follow-on work |
| `off` - WGL SwapBuffers | 37.6 ms / 4.5 | 48.9 ms / 5.9 | first tick 15-35 ms after arming |
| `tree` - compositor pane tree, declared (opt-in) | 21 ms / 2.5 | 26 ms / 3.1 | declared commit +1-3 ms; first moved frame 17-25 ms after the commit; first tick 31-44 ms after arming (not on the critical path) |

Decision: neither path meets p95 <= 2 refreshes, and neither has a reason it
cannot - both gaps are ours:
- **T3834** (shipping path): the first stepped tick waits behind the click
  pass's follow-on work; get it in within one refresh.
- **T3835** (tree path): the click's motion is committed almost at once, but
  the compositor's first frame of a declared curve shows its start pose;
  declare a new glide one period in (faces and columns with it).

Not measured here: a divider snap (the task named it beside the blade
collapse). A divider drag already moves on the compositor per input (T2769,
~1 ms); its release snap is a stack glide on the same start path, so T3834
and T3835's oracle covers it once fixed. No Mac number was taken: no Mac seat
on this box, and both gaps are fixable here regardless of where Mac lands.

## Validation criteria

- [x] Click-to-first-motion measured on the composition path and on today's path, at 120 Hz, with the method named. (comp-glide-hold-onscreen.ps1 -Arms tree,on -Clicks 8 -SlideMs 400 and -Arms off; table above, ALL PASS on every run.)
- [x] Either p95 <= 2 refreshes, or a change lands that brings it there, or a recorded reason it cannot (with the Mac number for the same gesture). (Neither: both paths miss and both are fixable, so the changes are filed as T3834 and T3835 with this measurement as their oracle.)
