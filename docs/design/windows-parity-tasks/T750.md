# T750 - The viewer's MIME table has no fonts, wasm or video, so a rendered page's assets arrive as octet-stream

## In plain terms

Open a local web page in a side pane and most of it works, but a page that
ships its own font file, a video, or a WebAssembly module may render without
them. The pane hands those files over labelled "unknown kind of data", and the
browser is entitled to refuse anything it cannot identify.

## Summary

`viewer_content.mimeType` covers exactly what the bundled markdown/code
template asks for: html, css, js, json, the common images, txt, md, woff and
woff2. Everything else is `application/octet-stream`. That was harmless while
the only pages served were ours; T601 made a user's own `.html` file a served
page, and a page brings whatever it likes.

Known gaps, in rough order of how often a real page hits them: `ttf` / `otf`,
`wasm` (which Chromium's streaming compile REQUIRES be `application/wasm` - it
refuses to compile anything else), `mp4` / `webm` / `ogg`, `map` (source maps),
`xml`, `csv`, `avif`, `bmp`, `webmanifest`.

**Why this was not folded into T601.** The table carries a doc comment saying it
is Mac's `ViewerSchemeHandler.mimeType` byte-identical, and it is: two viewers
that disagree about what a file IS is exactly the divergence this project does
not ship. So the row set moves on both seats or on neither, and the Windows seat
cannot land the Swift half.

Also worth deciding while in here: our page host answers whole files only, with
no `Accept-Ranges` and no 206 handling, so a `<video>` element cannot seek. That
is a bigger change than a table and may deserve its own task.

## Validation criteria

- [x] `mimeType` answers the correct type for ttf, otf, wasm, mp4, webm, map,
      xml, csv, avif and webmanifest, asserted in the win32 lane (the file is a
      win32 module, so that is the lane that compiles it) - the new
      `mimeType answers for what a real page brings with it` test, green in
      `floor-lane.ps1 -Lane all`.
- [x] The same rows exist in Mac's `ViewerView.mimeType(forExtension:)` - landed
      as a cross-seat change in the same commit. It needed the ten T1183 image
      rows as well, which the Zig table had carried alone since 2026-09-05; the
      two are byte-identical again, and T1581 is filed for the audit that makes
      that a fact rather than a comment.
- [ ] A local page in `test\win32\viewer-html.ps1` that loads a `.ttf` through
      `@font-face` and a `.wasm` through `WebAssembly.instantiateStreaming`
      gets both served with their real types.
