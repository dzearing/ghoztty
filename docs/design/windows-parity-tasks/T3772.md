# T3772 - When the DEFAULT shell is WSL, a keybind split or new tab of a WSL pane starts at ~ instead of that pane's Linux folder

## Summary

T3754 carries a WSL pane's Linux folder (OSC 7) into a WSL child only on the paths that build the argv themselves (+split --shell=wsl:..., the palette's ... with Shell, Restart Pane with Shell, the + menu). A plain ctrl+d / new tab opens the configured default shell through buildRemoteInherit, which only sets the PROCESS cwd - and T3754 now drops that for a WSL child, since a Linux path is not a Windows cwd. So with command = wsl.exe (or wsl:Ubuntu via Settings) a split of a WSL pane goes to ~. Fix: when Surface.defaultFamily is .wsl and the parent is WSL, build the child's argv with --cd <parent's Linux folder> the way shellPaneOverrides does. Acceptance: extend section F of test/win32/split-inherit-cwd.ps1 with a --command=<stub wsl.exe> app config.

## In plain terms

If WSL is your default shell, splitting a WSL pane or opening a new tab from
it dropped you back in your Linux home folder instead of the folder you were
working in. After this, a new split or tab of a WSL pane starts in that pane's
folder, the way a PowerShell pane's splits already do.

## Goals

- [x] A plain split (ctrl+d, or `+split` with no `--shell`) of a WSL pane on a WSL default shell starts in that pane's Linux folder
- [x] A new tab opened from such a pane does the same
- [x] A `+split --pane=<id>` aimed at a pane in another window asks THAT pane, not the focused one
- [x] A per-shell starting folder (T3770) still applies when there is no folder to inherit, and stands down when there is
