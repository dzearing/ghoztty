# T699 - reset-context verifies the handoff by its file NAME, so a truncated sentence passes in production

## Summary

`reset-context.sh` proves the continuation arrived by grepping the pane for
`PROBE="$(basename "$C")"` — the cont file's basename (helper 0.11.0, line 160).
That probe deliberately sits in the MIDDLE of the sentence it is standing in
for, so every truncation at the front is invisible to it: a pane showing
`ead C:/Users/.../cont-ab12cd.txt - it contains your instructions…` passes the
check exactly as an intact one does. T664 found that loss once by eye and fixed
the ACCEPTANCE side (four new whole-delivery arms in
`test\win32\reset-context.ps1`, plus rounds 13-14 of
`send-keys-bracketed.ps1`); production is still checking the basename.

Worth noting what is and is not at stake. A byte lost inside the fixed prose is
survivable — a fresh session handed `ead <path> - it contains your
instructions.` will still read the file. A byte lost inside the PATH is not: the
session cannot read the file, and the loop stalls with nothing saying why. Both
are cheap to catch at the same place.

## Details

The fix belongs in the helper (source: `D:\git\dzearing-claude-marketplace`,
`skills/reset-context/scripts/reset-context.sh`, and the active plugin cache —
D3 of the acceptance suite asserts the two are byte-identical, so a cache-only
edit fails the run).

Design notes for whoever takes it:

- The sentence is ~110 characters and the pane WRAPS it, so a naive
  `grep -F "$SENTENCE"` against `+read` output may not match even on a healthy
  delivery. Decide from measurement whether `+read` re-joins a soft-wrapped
  line before relying on it; if it does not, check the piece that a leading
  truncation destroys — the line must OPEN with `Read ` followed by the path —
  rather than the whole sentence.
- Keep it a separate verdict from the existing motion gate (T562). "The pane is
  moving" and "what it was handed is intact" are different claims, and folding
  them together is how the last two of these went unnoticed.
- Whatever it checks, it must be provable: give it the negative control, the
  way `GHOZTTY_TEST_T664_BREAK=1` gives the acceptance arms theirs.

## In plain terms

When this session finishes a piece of work it hands the next one a single
sentence — "read this file, it has your instructions". If a character of that
sentence is lost on the way, the check that is supposed to confirm delivery
looks at the file's name, which sits in the middle, and says everything is
fine. If the lost character was in the file's path, the next session has
nothing to read and the whole loop quietly stops with nothing saying why. Now
the check looks at the handoff as a whole, so a lost byte is shouted about
immediately instead of being discovered hours later.

## How it was fixed

The pane read is NORMALIZED before comparison — every whitespace byte and
every non-ASCII byte (the composer's box-drawing rules) deleted from both the
screen text and the needle — and the verdict is then whether `Read <full path>`
survives as one contiguous run. That sidesteps the question the design note
left open: it does not matter where the line broke, or whether `+read` re-joins
a soft wrap, because neither a wrap nor a border can survive normalization.
The needle spans the whole path, so a byte lost anywhere in it fails, and it
begins at `Read`, so a leading truncation fails too.

It is a SEPARATE verdict from the motion gate, logged separately: a session
handed a corrupted path repaints exactly like one handed a good one, so
folding "the pane is moving" together with "what it got is intact" would hide
the second behind the first.
