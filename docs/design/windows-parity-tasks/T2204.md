# T2204 - desktop-launch audit misses camelCase exe variables like $testExe, so update-real-msi opened windows on the user's screen unflagged

## Summary

`Test-DesktopLaunchAuditGhozttyRef` (`test\win32\lib\DesktopLaunchAudit.ps1`)
decides whether a variable names the ghoztty exe with
`(?i)(^|[^a-z])exe(path|)$`. Under `(?i)` the character before `exe` must be a
non-letter, so in practice only a bare `$Exe` / `$exePath` / `$script:exe` /
`$my_exe` matches; `$testExe` and `$AppExe` do not (the comment beside the
rule claims `$AppExe` is covered). `test\win32\update-real-msi.ps1` launched the installed
throwaway product three times as `Start-Process -FilePath $testExe` on the
caller's desktop - every run put a terminal window on the user's screen - and
the audit was green with no `@user-desktop-launch` declaration. Found and fixed
for that one script in T1269 (it now launches through `Start-OnTestDesktop`).

Fix the rule rather than the names: treat a camelCase `...Exe` / `...ExePath`
suffix (case-sensitive capital E after a lowercase letter, plus the existing
bare forms) as an exe reference, then re-run the sweep and declare or migrate
whatever it newly finds. Expect hits on `$agentExe` sites (headless - the agent
opens no window, so the rule may need to exclude names that resolve to
`ghoztty-agent.exe`, or those sites get declared) and on non-ghoztty helpers
like `$sleepExe` / `$leakExe` (cmd/timeout - the audit must not call those app
launches; check how the site classifier scores them before widening).

## In plain terms

A check exists to stop tests from opening windows on the user's screen, but it
only recognises a few spellings of "the app's path". One test spelled it
differently and opened windows on every run without the check noticing.

## Goals

- [x] The audit treats camelCase `...Exe` / `...ExePath` / `...Com` names (`$testExe`, `$AppExe`) as the app
- [x] Names a script visibly fills with another program, and the agent, stay out
- [x] The real sweep stays at zero findings, with no new declarations needed

## Validation criteria

- [x] A negative control: a fixture script that launches `Start-Process -FilePath $testExe` is reported `undeclared` by the audit - `-TeethCheck` E0h plants exactly that into the real suite and the sweep finds it; the HEAD analyzer scores the same two lines 0 sites, the new one 1
- [x] The widened rule produces no false findings on headless/non-ghoztty launches (agent, cmd, timeout), or each is declared with a reason - B40-B43 fixtures; the first widened sweep found 12 false sites of three shapes (parameter default naming another exe, `Get-Command` `.Source`, a copy of a foreign `...Exe`), all now classified foreign, none declared
- [x] The desktop-launch sweep is at zero findings after the change - `desktop-launch-audit.ps1` ALL PASS (71), `-TeethCheck` ALL PASS (79)

## Resolution

Re-verified first: `update-real-msi.ps1`'s own `$testExe` is already caught
today, because T1269 made it `Join-Path $installDir 'ghoztty.exe'` and the
T1267 alias rule follows that. The name rule itself was still blind - a
`$testExe` from a parameter, a function result or the registry was invisible -
so the fix is the rule, as the card says.

`Test-DesktopLaunchAuditExeName` gains a case-SENSITIVE camelCase arm,
`[a-z0-9](Exe|Com)(Path)?$`, so `$execute`, `$income` and `$leakEXE` do not
match; a name containing `agent` is excluded (the daemon opens no window).
`Get-DesktopLaunchAuditForeignNames` runs BEFORE the alias passes and marks a
camelCase name foreign when the script fills it only with another program: a
non-ghoztty `.exe`/`.com` (or the agent) as an assignment or a parameter
default (through `Join-Path` and parentheses), or a `Get-Command` result's
`.Source`/`.Path`. A name also given one of our paths stays watched. The bare
forms (`$exe`, `$Com`) keep their pre-T2204 reading.
