# T3609 - Window>Float on Top no longer makes the window topmost: menu-bar.ps1 section I red (5 asserts) in worker and alone runs

## Summary

menu-bar.ps1 section I (T191/T277 behaviour) is red on HEAD 5fcee7673 plus T2017's harness edit, identically in the parallel worker and the alone run (logs C:\Users\David\AppData\Local\Temp\ghoztty-acceptance-parallel\20261123-163800): the row is present, enabled and unchecked, but choosing it (Window, then mnemonic O) leaves WS_EX_TOPMOST clear and the row unchecked. Either the command no longer reaches toggle_float_on_top from the menu, the topmost bit is dropped again (T277's shape), or the keyed path changed. First step: drive it by the palette or a direct click to split menu dispatch from the window-style half. Found in T2017.

## In plain terms

Choosing Window > Float on Top could leave the window exactly where it was:
no "always on top", no checkmark. A hidden part of the window (a pane's
scrollbar, while it was faded out) had wrongly been marked "always on top"
by itself, and Windows quietly refuses to float a window while one of its own
hidden pieces is in that state. Now the app clears that stray mark and the
float takes on the first choice.
