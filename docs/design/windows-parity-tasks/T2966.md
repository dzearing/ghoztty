# T2966 - A user rename of the loop window strips the [go-loop] marker, and the loop's claim does not put it back

## Summary

2026-11-14 06:25: both loop windows were retitled 'go loop: ghoztty 1/2' (and the controller 'ghoztty: manager'). go-loop-health then reports windows=0 / 'no [go-loop]-marked window' while the loop is healthy, and the claim at turn 23 (T2958) did not re-mark. Duplicate resolution keys on that title, so a cosmetic rename silently disables it. Fix: identify the execution window by something a rename cannot remove (pane id on the lock, or a +set-state tag), or have the claim re-mark and report MARK FAILED; never fight a name the user chose.

## In plain terms

When you rename the loop's window to something you like, the loop's own health
check stopped recognising it and reported "no loop window" even though the
loop was running fine, and the claim printed a scary MARK FAILED every turn.
Now the loop recognises its window by the pane it is running in, keeps your
name, and only the label is missing.

## Goals

- [x] health counts a user-renamed loop window (windows=1, not 0)
- [x] the claim keeps the user's title and says so instead of MARK FAILED
- [x] the watchdog re-enters a renamed loop window instead of opening a second one
- [x] a renamed window that is NOT the loop is still never touched

## Validation criteria

- [x] `go-loop-exec.ps1 list` live on the box: the renamed window `go loop: ghoztty 1` reads `EXEC ... (renamed by the user; holds the lock owner's pane)`; the user's `ghoztty: manager` and lane b's renamed window read unmarked.
- [x] `go-loop-health.ps1` live: `HEALTHY ... windows=1` (was windows=0 / 'no [go-loop]-marked window').
- [x] section MR of `test\win32\go-loop-guard.ps1` (MR1-MR13: role by title / by lock pane / case-insensitive / user's other window untouched / no owner / lane b marker / refusal recognition / lock read / wiring of list, claim and watchdog) - ALL PASS (597 assertions); `go-loop-resume.ps1` ALL PASS (41).

## Decision (mechanism, Claude's call)

Identity = the pane id on the lock, not a `+set-state` tag (that verb is the
activity state, idle/busy/needs_input, and would collide with the banner
hooks). Duplicate CLOSING stays title-only on purpose: a window the user
renamed and that does not hold the lock is theirs, and is never closed.
