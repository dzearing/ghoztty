# T1957 - Low-power auto-switch re-loads the config into every pane: per-pane overrides (wait-after-command of +new-remote-window --command) are re-derived when a no-GPU launch or an RDP switch flips the effects

## In plain terms

When Ghoztty switches its visual effects off or on by itself (a PC with no
graphics card at startup, or a Remote Desktop connect/disconnect), it re-reads
its settings into every pane. A pane opened with special one-off settings, such
as a remote window told to stay open after its command ends, could lose those
settings at that moment.

## Goals

- [x] A pane's own `wait-after-command` survives every app-wide config push (low-power flip, hard reload, soft reload)
- [x] The per-pane soft reload (color-scheme conditional) keeps it too
- [x] An acceptance arm that goes red without the fix

## Summary

`App.refreshLowPower` (T1951) re-loads the config and calls
`core_app.updateConfig`, which re-derives every surface from the app config -
the same path as a user's hard reload. The `.reload_config` handler's own
comment records why that is dangerous for per-surface overrides
(`+new-remote-window --command` sets `wait-after-command` on its surface only).
On a no-GPU box this now happens once on every launch, shortly after the first
GL context, so a restored remote window could be affected.

Options: re-apply the per-surface overrides after the push (the surface keeps
them in `pending_surface_overrides` style), or push only the effects keys to
each surface on top of its OWN current config instead of the app config.

## Validation criteria

- [x] An acceptance arm: `+new-remote-window --command` (or a local
      `wait-after-command` override) survives a forced low-power flip
      (`GHOZTTY_TEST_REMOTE_SESSION_FILE` + `WM_WTSSESSION_CHANGE`), and the
      window stays open after its command exits. Verified by section 3c of
      `test/win32/ipc-remote.ps1`: it checks the flip happened (pane gap 14 -> 0),
      then that the window is still listed and shows the finished `ping`. Run
      before the fix: 2 FAILURES (window gone). After: ALL PASS (40 assertions).
- [x] Unit tests for the sticky set (`src/apprt/win32/surface_sticky.zig`, none lane).

## Resolution

The win32 Surface records the values it was opened with that the app config
does not carry (`Surface.sticky`, `surface_sticky.zig`; today only
`wait-after-command`, set by the `--command` remote path). Every app-wide push
now goes through `App.pushConfigToSurfaces`: `core.App.updateConfig` as before,
then each pane carrying sticky values is re-derived once more from the same
config with its own values laid on a shallow copy. The surface-scoped soft
reload (`pushConfigToSurface`) keeps them the same way, which closes the same
hole on a per-pane color-scheme change. Mechanism choice (re-derive vs patch
the core's derived field): re-derive goes through the core's public
`updateConfig`, so nothing here depends on the shape of the core's private
derived config; the extra derive only happens for the few panes that carry a
sticky value. Spawn-time overrides (command/cwd/env) are deliberately not
sticky: they are read once, at spawn.
