# T1641 - A GUI acceptance script cannot say which window a named pane is in

## In plain terms

Nobody sees this one. It is about the tests: when a test wants to click a
button in one particular pane, it has no way to find that pane's window on
screen. The pane has a name in every listing the app prints, and a window
handle on the desktop, and nothing joins the two. So a test either guesses, or
it closes everything else first so there is only one thing left to click.

## Summary

`+list --json` names panes by id; the GUI harness (`test\win32\lib\TestDesktop.ps1`)
enumerates top-level `GhozttyWindow`s and their `GhozttyViewer` /
`GhozttyTerminal` children. Nothing maps between them. A script that wants
"the window holding pane `<id>`" has to infer it — by taking the window that
appeared after a `+new-window`, by assuming there is only one, or by closing
the others.

T817 hit this head on. Its click arm reads the diff pane's nav-bar geometry out
of the pane's own log line (which is per-pane and exact) and then has to aim a
posted click at a bar it cannot prove belongs to that pane. The first version
picked the window that appeared after its `+new-window`; the clicks landed
somewhere else and two assertions failed against a feature that worked. The
shipped version closes every other viewer window first and asserts that exactly
one is left — correct, but it means the arm cannot run beside the scenarios it
follows, and a suite that has to tear down its own world to aim a click will
keep growing that habit.

## Where

- `src/apprt/win32/Window.zig` / `ViewerPane.zig` — the handles, and where an id
  could be published (a window property, a title suffix, or a field on
  `+list --json`'s window record).
- `test/win32/lib/TestDesktop.ps1` — where a `Get-TestWindowForPane` would live.
- `test/win32/viewer-diff.ps1` section 9 — the caller that had to work around it.

## Notes

Whatever carries the mapping has to be readable from ANOTHER process on a
background desktop, which rules out anything that needs the app to answer a
question interactively. Two shapes worth weighing: a window property
(`SetPropW`) the harness reads by handle, or an hwnd in `+list --json` that the
harness matches against its enumeration — the second costs nothing at runtime
and is testable in the `none` lane, but publishes a handle in a CLI payload,
which is a thing to think about before doing.

## Validation criteria

- [ ] A harness helper answers "which window holds pane `<id>`" from a pane id
      alone, with no window bookkeeping by the caller.
- [ ] `test\win32\viewer-diff.ps1` section 9 no longer closes the other viewer
      windows to aim its clicks, and still passes.
- [ ] A negative control: the helper answers nothing (rather than the first
      window) for an id that is not open.
