# T3130 - The ~290 MB of non-heap private memory the first pane open-close cycle leaves behind is unattributed: perf-baseline's region census puts it all in private_rw (Release 290.2 / 293.1 MB, heap only +3-6 MB)

## Summary

Found by T3005. With the cycle phase's new committed-region census (`perf-baseline.ps1 -Phase cycle`, `cycle.regions`), the first open/close cycle of 10 panes over 3 tabs leaves ~405-417 MB of private bytes behind in Release, split:

| class | relA (default) | relB (GHOZTTY_COMP_PRESENT=0) |
|---|---|---|
| private_rw (non-heap MEM_PRIVATE) | +290.2 MB | +293.1 MB |
| writecombine (GPU driver upload pool) | +81.4 | +74.2 |
| stack | +39.1 | +33.7 |
| heap (NT heaps) | +5.7 | +2.6 |

It is not a leak: after 6-7 warm-up cycles the settled slope is +0.64 / +0.95 MB per cycle and nothing is trimmed after 30 s idle. It is RETAINED: memory the first cycle grew that later cycles reuse. Composition (PA-R02) has no measurable share. `private_rw` mixes Zig page_allocator users (terminal PageList pages, renderer buffers), parked pane/thread state (T3000: 9 parked renderer/io/io-reader triples, each with an NVOpenGLPbuffer), and GL driver arenas, so the census cannot say which.

Next step: split private_rw further - an allocation-size histogram of private_rw allocation bases at start vs cycle-1 closed (pages vs big driver arenas), plus an A/B with pane parking off once T3000 lands - and name the owner of the bulk. Then decide whether retaining it is worth it (a fresh second pane reuses it) or it should be released when the last pane of a burst closes.

## Validation criteria

- [ ] the first-cycle private_rw residue is attributed to named owners covering >= 80% of it
- [ ] a decision recorded: keep (and why) or a filed fix to release it
