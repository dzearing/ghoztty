# T3130 - The ~290 MB of non-heap private memory the first pane open-close cycle leaves behind is unattributed: perf-baseline's region census puts it all in private_rw (Release 290.2 / 293.1 MB, heap only +3-6 MB)

## Summary

Found by T3005. With the cycle phase's new committed-region census (`perf-baseline.ps1 -Phase cycle`, `cycle.regions`), the first open/close cycle of 10 panes over 3 tabs leaves ~405-417 MB of private bytes behind in Release, split:

| class | relA (default) | relB (GHOZTTY_COMP_PRESENT=0) |
|---|---|---|
| private_rw (non-heap MEM_PRIVATE) | +290.2 MB | +293.1 MB |
| writecombine (GPU driver upload pool) | +81.4 | +74.2 |
| stack | +39.1 | +33.7 |
| heap (NT heaps) | +5.7 | +2.6 |

It is not a leak: after 6-7 warm-up cycles the settled slope is +0.64 / +0.95 MB per cycle and nothing is trimmed after 30 s idle. It is RETAINED: memory the first cycle grew that later cycles reuse. Composition (PA-R02) has no measurable share. `private_rw` mixes Zig page_allocator users (terminal PageList pages, renderer buffers), parked pane/thread state (T3000: 9 parked renderer/io/io-reader triples, each with an NVOpenGLPbuffer), and GL driver arenas, so the census cannot say which.

Next step: split private_rw further - an allocation-size histogram of private_rw allocation bases at start vs cycle-1 closed (pages vs big driver arenas), plus an A/B with pane parking off once T3000 lands - and name the owner of the bulk. Then decide whether retaining it is worth it (a fresh second pane reuses it) or it should be released when the last pane of a burst closes.

## In plain terms

The first time you open a burst of panes and close them, Ghoztty stays about 200-300 MB bigger than it started, and nobody could say what that memory was. It is now named: almost all of it is the NVIDIA graphics driver's own scratch pool, which grows as each pane sets up its drawing and is kept by the driver (not us) for the next pane. Opening more panes later reuses it instead of growing again.

## Goals

- [x] perf-baseline splits the unexplained memory by allocation, so a residue has a shape (driver pool vs our page allocations vs big malloc blocks)
- [x] the owner of the bulk is named from a real call stack, not inferred
- [x] keep-or-release decided, with the one lever we own filed

## Findings (2026-11-18, Release +3b32838bf, NVIDIA nvoglv64, 10 panes over 3 tabs)

`perf-baseline.ps1 -Build Release -Phase cycle` now writes `cycle.regions.private_rw_allocs`: every private_rw allocation (one VirtualAlloc reservation) by base, kinded `heap_large` (first qword points into an NT heap), `exact` (whole reservation committed: Zig page_allocator shape) or `arena` (part only reserved), diffed start -> cycle 1 closed and start -> 10 panes open.

| first cycle, start -> closed | MB | allocations |
|---|---|---|
| private_rw total grew | 224.0 | |
| arena: one 1 GB reservation (pre-existing, 48 -> 244 MB committed) | **195.9** (87%) | 1 |
| arena: two 32 MB reservations | 19.8 | 2 |
| arena: other | 0.9 | 4 |
| exact (our page_allocator, renderer/terminal) | 7.4 | 46 |
| heap_large (malloc above the heap threshold) | 0.1 | 1 |

With 10 panes OPEN the same census shows what closes cleanly: 18 x 0.56 MB exact (terminal pages) and 9 x 0.88 MB heap_large blocks are there while open and gone after close.

**Owner of the 1 GB arena: the NVIDIA OpenGL driver.** No 1 GB reservation exists anywhere in `src/` (the only VirtualAlloc users are `terminal/page.zig` / `page_pool.zig`, exact-commit). A cdb conditional breakpoint on `ntdll!NtAllocateVirtualMemory` with `*BaseAddress` inside that range, attached to the test-desktop app while 9 panes were split open: **7 of 7 hits** were `KERNELBASE!VirtualAlloc <- nvoglv64!DrvPresentBuffers+0x44a2a` (the driver's own allocator); 64 KB-1.7 MB commits on the driver's worker thread, and one **10.06 MB** commit under `ghoztty!threadEnter -> opengl32!wglMakeCurrent -> nvoglv64!DrvSetContext` - a pane's renderer thread binding its new context. Arena commit over that run went 49.4 -> 69.7 MB. Named-owner coverage: 195.9 / 224.0 = **87%** (the two 32 MB arenas are very likely the same driver but were not traced, so not counted).

## Decision: keep

The memory is the driver's, committed by the driver's allocator and held by it after `wglDeleteContext`; there is no API to make it decommit, and it is reused (settled slope +0.64 MB/cycle in T3005's run). Releasing it is not ours to do. The lever we do own is how many GL contexts the app makes (one per pane today, ~10 MB of driver arena each on bind): filed as **T3232** (measure per-context cost; evaluate fewer contexts per window).

## Validation criteria

- [x] the first-cycle private_rw residue is attributed to named owners covering >= 80% of it - 87% to `nvoglv64` (perf-baseline `private_rw_allocs` census + cdb stacks, 7/7 hits), method above; `perf-baseline.ps1 -SelfTest` PASS after the change
- [x] a decision recorded: keep (and why) or a filed fix to release it - keep (driver-owned, reused); the context-count lever filed as T3232
