# T1740 - A real drag between monitors of different scale has never been watched: the WM_DPICHANGED arm and its suggested-rect resize are only exercised through the debug seam

## Summary

T1579 gave the top-level window a `WM_DPICHANGED` arm (Window.zig) that
adopts the DPI in wparam, forwards it to every pane, and `SetWindowPos`es to
the rect Windows suggests in lparam. `test\win32\dpi-change.ps1` drives the
same `handleDpiChanged` through the debug-only `WM_APP_TEST_DPICHANGED`,
because Windows refuses a `WM_DPICHANGED` sent from another process and both
of this box's monitors run at 120 dpi. So two things have never been seen:
the OS actually delivering the message on a drag, and the window landing at
the suggested size (no jump, no size loop against `WM_GETMINMAXINFO` or the
client-painted caption).

Needs a box (or a temporarily re-scaled second monitor - the user's call, it
is their display setting) with two monitors at different scales. Drag a window
with two panes across, and with the palette closed.

## Validation criteria

- [ ] On a mixed-DPI setup, a drag across the boundary re-sizes the terminal text and tab strip on arrival, with no popup open (debug log: `window dpi changed dpi=<new> panes=<n>`).
- [ ] The window lands at the suggested size, without a visible jump or a resize loop.
