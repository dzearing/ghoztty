# T2232 - The first +list after a click storm under an output flood takes ~30s: focus-defer.ps1 is red on '+list answers within 8s'

## Summary

Found by T1309 (2026-10-24) running test\win32\focus-defer.ps1 against 2e6696241 debug: 17 pass, 2 fail, reproduced beside others and alone. After the 3000-click storm the GUI thread still pumps WM_NULL, but the first +list does not answer within 8s and the latency samples read 30031, 4214, 16, 23, 16 ms (one failed). So the IPC listener stalls for tens of seconds after a storm while the message loop looks alive - the T48 load shape, with a CLI command hanging instead of a deadlock. Find what holds IPC (queued posted clicks drained ahead of the pipe? the flood's render starving the listener?), fix it, and get focus-defer.ps1 ALL PASS so its new guard row (T1309) stamps.

## In plain terms

Clicking quickly between split panes made Ghoztty repaint its whole window
background once per click, even though nothing visible had changed yet. A
burst of clicks therefore left the app busy for tens of seconds, and any
script or agent command sent in that time (`ghoztty +list`) sat waiting or
timed out. After the fix the background is repainted once per burst by the
existing focus-glow animation timer, and commands answer straight away.

## Root cause

cdb stack sampling of the GUI thread during the stall (19 of 20 samples):
`updateDimOverlays -> syncFocusGlow -> repaintPaneDesk -> paintPaneDesk ->
paintCards`, a synchronous full software desk paint (~15 ms in Debug) on every
focus change. The paint was redundant: at the fade's first instant
`fadeLevel(0) == 0`, so it redraws the frame already on screen, and the 16 ms
`FOCUS_GLOW_TIMER_ID` tick paints the fade anyway. WM_TIMER is generated only
once the queue is empty, so it coalesces a burst into one paint.

Debug builds compounded it: the renderer thread's `mailbox message={}` debug
line formatted each `pane_backdrop` message's whole RGBA slice (~200 KB per
message, 624 MB of stderr in one run), so the renderer fell behind, its
64-deep mailbox filled, and the GUI thread blocked in `push(.forever)`.

Not a Mac obligation: the Mac glow is a SwiftUI animation, and the renderer
log fix is in the shared core, so it lands on both platforms.
