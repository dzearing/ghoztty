# T1230 - Nothing checks what else a test run can write into the user's persistent state

## In plain terms

Running the tests is supposed to leave this machine exactly as it found it. One
place where it did not - the list of programs Windows starts at sign-in - was
found by eye, eight days after it started happening. There are half a dozen
other places a test run could change something permanent about the machine, and
nobody has checked any of them.

## Summary

T1168 found the suite writing permanent HKCU Run entries and closed that one hole. The general question is unanswered: the Run key is not the only durable place a run can reach. Scheduled tasks, HKCU\Software\Ghoztty, the DPAPI credential store, the user PATH, the Start Menu and the session-layout manifests are all writable by an acceptance script, and the only one anything sweeps is the Run key. Wanted: an enumeration of the persistent surfaces a run can touch, a before/after snapshot arm that fails when a suite run changes any of them outside its sandbox, and a decision per surface on whether isolation or teardown is the right answer.

## Goals

- [x] every durable place a run can change is named, with its answer
- [x] an acceptance run that leaves any of them changed goes red and names what moved
- [x] the check is shown each kind of change and must see it

## What was done

`test\win32\lib\PersistentState.ps1` snapshots nine surfaces;
`scripts\acceptance-parallel.ps1` (the step-3 runner, `due` and `run`) takes one
snapshot before the first script starts and compares after the last ends. A
difference still there after a 15 s settle re-check prints
`PERSISTENT STATE CHANGED: <surface> ADDED|REMOVED|CHANGED <item>` and turns the
run RED, exit 1. The re-check is for lane B: its suite can have a value planted
and not yet removed at the moment this run looks; a leak does not go away.
`-NoStateCheck` skips it and prints that it did. A clean run costs ~1 s.

| Surface | What is compared | Answer that keeps it unchanged |
|---|---|---|
| run | `HKCU\...\Run` values named *ghoztty* | isolation (T167 lineage names) + teardown (T1168) |
| env | `HKCU\Environment` PATH entries naming ghoztty / zig-out / %TEMP%, `GHOZTTY_*` values | isolation (source-checkout gate on the PATH self-heal, T1151/T1213) |
| classes | `HKCU\Software\Classes\ghoztty*` except `ghoztty-debug*`, every value | isolation (location gate, T1151) |
| hives | `HKCU\Software\*ghoztty*` / `*dzearing*` keys, `HKCU\Software\dzearing\*` | teardown (each fixture hive removes its own) |
| arp | Uninstall entries for Ghoztty + DisplayVersion | isolation (ThrowawayProduct identities) |
| tasks | scheduled task names *ghoztty* | none should be created; names compared, so the loop's re-registrations are stable |
| startmenu | Start Menu\Programs (incl. Startup) entries *ghoztty* | isolation (installer tests use throwaway identities) |
| install | `%LOCALAPPDATA%\Programs\Ghoztty` exe/com/agent size + mtime | the non-negotiable, now measured |
| account | `%LOCALAPPDATA%\ghoztty\account-debug.dat` | isolation (workers get their own LOCALAPPDATA) |

The first live `due` run under the arm went RED on
`classes CHANGED ghoztty-debug\shell\open\command`: lane B's path flipped to
lane A's. Not a leak. A debug build rewrites its own lineage's handler on every
launch by design (`url_scheme.zig`: the last debug launch answers dev links),
so with two lanes that class flips on any run that launches the app. The
`ghoztty-debug*` classes are now left out (B8b proves it), and the release
`ghoztty://` class, which is the user's, is still compared.

Deliberately NOT compared: the `ghoztty-debug*` classes (above), the release `account.dat` and release state dir (the
user's live terminal rewrites them during any run; protected by BuildMode's
debug-only preflight, T350, and `-ReleaseSandbox`) and the debug state dir (the
suite's own working surface, reset by the clean slate on purpose).
