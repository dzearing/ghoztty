# T2702 - A glass viewer re-renders its whole pane's sheet (~420k px) on every edge-drag step - ~1.5 ms ReleaseFast, ~3.8 ms Debug of T2666's burst paint; render it in parallel or only where it shows

## In plain terms

Dragging the edge of a window that shows a document or web page is slower
than dragging one with only terminals, because the frosted background behind
the page is recomputed for every pixel of the pane on every step of the drag.
Doing that work faster, or only where it can be seen, makes the drag as quick
as a terminal-only window's.

## Summary

Found by T2695. On glass, `ViewerPane`'s `WM_PAINT` calls `paintUnderPage`,
which renders `pane_elevation.glassSheetRegion` over the host's WHOLE client
(clip rect ignored) into a fresh DIB section and blits it. Every edge-drag
step changes the desk size, so `setGlassBackdrop` invalidates the whole
sheet each step and nothing can be reused.

Measured with T2695's `resize trace burst-sheet` line
(`edge-drag-rate.ps1 -Burst`, viewer scene, 2026-11-04): 1 paint per step,
419k px, **3.77 ms Debug** and **1.46 ms ReleaseFast** (sandbox,
`zig-out-perf`) - after T2695 made the per-pixel desk 2.5x cheaper on the
shipped x86-64 baseline. `burst-paint -> burst-window-painted` is 6.3 ms in
the viewer scene vs 2.1 ms in row3 (Debug); the sheet is most of the
difference.

Directions, pixels byte-identical in every case (the viewer probes compare
against `glassSheetRegion`):

- render rows in parallel on a small persistent worker pool (the region is a
  pure function per row);
- render only what shows: a page that does NOT draw on glass is opaque, so
  only the host's uncovered strips need the sheet (`drawsOnGlass`);
- keep one DIB section across paints instead of create/destroy per paint.

## Goals

- [x] the sheet's share of a viewer burst step is under 1 ms ReleaseFast (0.72 ms, of which 0.52 ms pixels; was 1.46 ms)
- [x] pixels unchanged (byte-identical by unit test and by the viewer pixel harnesses)

## What landed

`src/apprt/win32/sheet_workers.zig`: `glassSheetRegion` with the rows cut into
bands and shared over a process-wide `std.Thread.Pool` (at most 4 workers,
CPUs-1 on a small box, none on one CPU; only regions of 64k px or more). The
calling thread renders a band of its own and then helps drain the queue
(`waitAndWork`), so it never sits idle. `ViewerPane.paintGlass` calls it. The
`burst-sheet` trace line gains `render_us` (the pixels alone; the rest of `us`
is the DIB create and the blit).

Not done, deliberately: "render only what shows" - the viewer scene's pages
draw on glass, so the whole sheet shows and there is nothing to skip; and a
kept DIB, which would save at most the ~0.2 ms the buffer and blit now cost
and needs reuse across a size that changes every step.
