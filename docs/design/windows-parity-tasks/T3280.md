# T3280 - A click in one viewer never brings a minimized blade beside it out (Mac 084136b2f): verify the Windows blade stays minimized when a link or text in the neighbouring pane is clicked, and fix the click claim if it does not

## Summary

Mac: every viewer's mouse monitor claimed a click by bounds, and a minimized viewer stays mounted full-size under the pane on show, so a click in that pane focused (and expanded) the blade. Mac test BladeStaysMinimizedTests.aLeadingBladeStaysMinimized: two HTML viewers, the left a blade, real clicks in the right. Windows: check whether a minimized viewer HWND/WebView2 under the shown pane, or the focus path, can expand it; add an acceptance arm either way.

## In plain terms

On the Mac, when a web or document pane had been squeezed down into a thin
strip beside another one, clicking a link or some text in the pane you could
see made the squeezed one pop back out. This checks that Windows never does
that, and adds a test that clicks a link and plain text next to a squeezed
pane and confirms nothing pops out.

## Goals

- [x] Find out whether Windows has the Mac defect
- [x] An acceptance script that clicks a link and plain text in the viewer beside a folded viewer, with a negative control

## Finding

Windows never had the defect, and the reason is structural. On Mac a folded
viewer stays mounted at full size under the pane on show, and its mouse
monitor claimed clicks by bounds. On Windows a strip's pane is a hidden child
window: the run measured the folded v1's window at x 191-470, under w3 at
249-762, exactly the Mac overlap, but HIDDEN, so the OS hit-tests the click to
w3's Chromium input window and v1 never sees it. A page focus from the strip
itself is separately refused by `Window.adoptsFocus` (T2127, T3125). No code
change was needed; the deliverable is the test.

## Validation criteria

- [x] A link click and a text click in w3 each land (w3 takes the caret) and P, s2, v1 stay strips for 2 s after: `test\win32\blade-click-neighbour.ps1`, ALL PASS (15 assertions) via `acceptance-parallel.ps1 run -FailFast`, 2026-11-20, stamped
- [x] `-NegativeControl` (claim C inverted) fails: exit 1, 1 failure, 14 passed
- [x] Guard row `blade-click-neighbour` in `scripts\guard-due.ps1`, so a later edit to Window.zig / ViewerPane.zig / pane_stack_state.zig re-runs it
