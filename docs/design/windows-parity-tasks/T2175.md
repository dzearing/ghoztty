# T2175 - next -Claim hands a lane-A-only task to lane b, and setting it back to todo just hands it out again

## Summary

Tasks gain an optional lane: field; next skips a task whose lane is not this worktree's and names it as Skipped for another lane; validate flags a lane that is not one letter.

## In plain terms

Two copies of the work loop run side by side, but only the first one is allowed
to ship builds. The task picker didn't know that. It kept handing a shipping job
to the second loop, which can't do it, and handing the job back just got it
handed out again. Tasks can now say which loop they belong to, and the picker
skips the ones that aren't for it, saying so.

## Goals

- [x] An optional `lane:` field on task files (`lane: "a"`), absent = any lane
- [x] `next` (fresh claim and stale resume) skips another lane's task and names it
- [x] `validate` fails a lane value that is not one letter (`ODD LANE`)
- [x] T2174 (deliver, lane A only) carries `lane: "a"`

## Validation criteria

- [x] Lane b's `next -Claim` skips a `lane: "a"` todo with `Skipped 1 todo(s) for another lane (this lane=b): T1(lane a)` and claims the next one; lane a is handed it; a stale in-progress lane-a task is not RESUMEd by lane b - `test\win32\parity-tasks-lanes.ps1` G1-G3, green via acceptance-parallel.
- [x] Negative control: the same todo without `lane:` goes to lane b (G4).
- [x] `validate` names `ODD LANE: T3 = 'lane-a'` (G5); the label is registered as a gate in `test\win32\gate-negatives.ps1` with G5 as its demonstration.
- [x] On the real tracker in lane b: `next` prints `Skipped 1 todo(s) for another lane (this lane=b): T2174(lane a)` and hands out T1226 instead.
