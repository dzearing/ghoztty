# T1254 - The dev-install upgrade carries the fallback graphics driver too

## Summary

P2: internal only. upgrade-ghoztty-windows.ps1 mirrors share\ into the dev install but not the new bin\gl\ tree (T1252), so the install the loop tests against differs from what a user downloads - which is how a shipped-payload regression stays invisible on this box. Left out of T1252 deliberately: that task's scope named the MSI, the portable zip and deliver-windows-build.ps1, and touching the upgrade script puts three more acceptance harnesses due.

## In plain terms

The test copy of Ghoztty that the automation upgrades and runs against was
missing the backup graphics driver that real downloads carry, so a problem with
that driver could never show up here. Now the upgrade copies it in, the same way
the installer and the portable zip do.

## Goals

- [x] `upgrade-ghoztty-windows.ps1` mirrors `bin\gl\` -> `gl\` into the dev install
- [x] ...and into every extra install location it mirrors to
- [x] the list of trees comes from the one place deliver-windows-build.ps1 reads it

## What changed

- `scripts/upgrade-ghoztty-windows.ps1`: both mirror sites (primary install and
  extra install locations) now loop over `Get-DeliveryTreeSet` (`share`,
  `bin\gl` -> `gl`) instead of naming `share\` alone, `/MIR` as before. The
  primary site now also logs a `WARNING` on a robocopy failure (rc >= 8), which
  it used to report as a plain "mirrored".
- `test/win32/upgrade-staleness.ps1`: new D12c-D12h (dev install gets `gl\`,
  licence beside it, a previous Mesa's leftover purged, nothing beside the exe)
  and D24-D25 (the extra-install mirror gets it too).
- Same file, found on the way: the harness could not run outside lane A at
  all - every upgrade/launch run is refused by the T1984 lane gate (exit 6), 63
  failures from lane B. Its sandbox runner now sets `GHOZTTY_LOOP_LANE=a` for
  the child, the seam `daily-publish.ps1` already uses; every run there targets
  a sandbox install, so the gate protects nothing in it.
