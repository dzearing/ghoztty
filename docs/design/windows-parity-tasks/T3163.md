# T3163 - A pane that moves to another window (or a parked workspace that comes back) keeps its banner's terminal inset: check the win32 banner layout does not reset on reparent and leave the text under the card (Mac 199403483)

## Summary

Mac 199403483 (v1.55.1): the banner card's onDisappear reset its height/inset/reveal whenever the pane left the hierarchy, so a parked workspace or a pane moved to another window came back at the same banner height without re-firing the height preference, and the terminal was laid out under the translucent card. Fix: reset only when the banner is CLEARED. Windows: verify the same on pane drag-to-another-window (pane_drop) today, and on workspace switch once single-window mode (T3136) lands; if win32 BannerOverlay/Surface resets the inset on reparent, key the reset to the banner clear instead. Mac test: SingleWindowModeTests.aBannerStillHoldsTheTerminalBelowItAfterASwitch; doc: docs/reference/banners.md.

## In plain terms

On the Mac, a pane with a status banner that was moved to another window could come back with its text hidden underneath the banner card. This checks that the same thing cannot happen on Windows, and adds a test that would catch it if it ever did.

## Goals

- [x] Confirm whether Windows has the Mac defect when a bannered pane moves to another window
- [x] An acceptance check that a moved pane keeps its banner space, with a negative control that goes red
- [x] Hand the workspace-switch half to the single-window-mode work (T3182), since that path does not exist on Windows yet

## Finding

Windows does not have the defect, by construction. The Mac bug was state: the banner card cleared its remembered height when the pane left the view hierarchy. On Windows nothing is remembered: `Surface.bannerLayoutInset` (src/apprt/win32/Surface.zig) re-derives the band from the live `banner_overlay` on EVERY layout pass, and the overlay is destroyed only when the banner is cleared (`setPaneBanner` with empty text) or the surface is torn down. A pane moved to another window goes through `Window.adoptPane`, which re-parents the pane HWND and moves its back-pointer; the banner overlay is an owned popup / composition layer of the PANE, so it travels untouched, and the destination window's layout pass reserves the same band. So the Mac fix ("reset only when the banner is cleared") is already how Windows behaves; no product change.
