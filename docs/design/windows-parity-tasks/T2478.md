# T2478 - parity-tasks next's idle re-queue (4f366d19d) hands the loop tasks whose live run is an @input-desktop-exception script, which go.md's NEVER PULL FOCUS rule forbids it to run: T2395/T2396 were re-queued at 838s idle and the turn had to re-park them

## Summary

`scripts\parity-tasks.ps1` `next` (lines ~1138-1170, commit 4f366d19d,
2026-10-29) flips any `blocked(needs ... idle|unlocked|away|absent ...)` task
back to `todo` when `Get-UserPresence` reads absent (5 min with no input, no
fullscreen app), with a note saying "Run it NOW". The tasks parked that way
(T2395, T2396) are live runs of `test\win32\frame-lab.ps1 -Live`, which is a
declared `@input-desktop-exception` (`test\win32\lib\TestDesktop.ps1:271`).
go.md's top rule (user, 2026-10-10) says the loop must not run ANY such script
and must record it NOT RUN, and the 2026-10-28 incident (memory
"idle-is-not-absent": the user, reading, saw windows pop and the cursor sweep)
is the evidence that 5 idle minutes is not absence.

So the re-queue hands the loop work it is forbidden to do. On 2026-10-29
11:55 lane b was handed T2395 at 838s idle and had to re-park both tasks with
wording the regex does not match.

Fix: the idle re-queue must not fire for a task whose live part is an
`@input-desktop-exception` script (or the park wording for those tasks must
be distinct and documented), and go.md should say in one place which park
condition means "the loop may run it on its own" versus "the user starts it".
Decision D-filed alongside asks the user whether an idle box should ever
authorise a real-cursor run.

## In plain terms

The task list automatically put the "move the mouse and open windows" test
back on the to-do list whenever the computer looked idle for five minutes,
even though the standing rule is that the loop never runs that test by itself.
When this lands, those tests wait for the user to say go.

- [ ] go.md states which park wording the idle re-queue honours, and that input-desktop-exception runs are never in it.
