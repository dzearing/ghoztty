# T2495 - focus-defer.ps1 is red on HEAD (d5b32e871, green at 76c530ca2): under the click storm + output flood +list does not answer within 8s and the 150000-line flood never runs out - the GUI thread starves under heavy output

## Summary

focus-defer.ps1 went red on '+list answers within 8s' and 'flood had not run out'
after the click storm. GHOZTTY_PERF showed the first `+list` waiting 30 s in the
GUI thread's posted queue (handler 0 ms), and the app log held 385
`termio mailbox full for 50ms, dropping message=focused` warnings: ~19 s of a
GUI thread parked inside the flooding pane's IO mailbox.

## In plain terms

Clicking quickly between split panes while one of them was printing a lot of
output could freeze Ghoztty's window for tens of seconds: every click told the
busy pane "you gained/lost focus", that pane could not keep up, and the window
waited on it each time. Scripts and agents sending `ghoztty +list` meanwhile
timed out. Now only the newest focus state is handed to the pane, without
waiting, so the window and its commands stay responsive.

## Root cause

Each focus change sends a `.focused` message into the pane's bounded (64-deep)
termio mailbox from the GUI thread. Every `focusGained` on the IO thread takes
the terminal lock, which a flooding pane's read thread holds almost constantly
(T2428's c3d1b4312 stopped per-line retitles from burying the GUI thread, so the
flood now runs ~12.5k reads/s instead of ~2.5k lines/s - which is also why the
150000-line flood ran out inside the test). The IO thread fell behind, the queue
filled, and every further change waited the mailbox's 50 ms give-up and was
then dropped. That was 385 x 50 ms on the GUI thread in one run.

## Fix

FOCUS is latest-wins control state, like RESIZE, and now travels the same way:
`src/termio/FocusSlot.zig` holds the newest value, and at most one `.focused`
marker rides the queue, pushed with `Mailbox.trySend` (never waits). The IO
thread applies the slot's newest value when it pops the marker (keeping the
report's order against surrounding writes), and at every drain start for a
marker that could not be queued. The GUI thread never blocks, the final focus
state is never lost, and intermediate states nobody could see are coalesced.
Shared core, so the Mac build gets it too (it is in `src/termio`, which both
seats compile); not a Mac-only behaviour to port.
