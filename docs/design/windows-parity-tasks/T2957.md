# T2957 - Optimize the hell out of the Windows port: Fable 5.2 audit of memory, GPU, CPU and leaks, filed as tasks and re-audited

## Summary

Run a whole-port performance audit with Fable 5.2, turn every finding into a queued task, and re-run the audit periodically to check fixes landed and the tasks are still right.

The user's ask (2026-11-14, paraphrased): the Windows port is in good shape,
but look for any and all chances to make it as light as possible on memory,
graphics, and CPU, with no leaks. Do the analysis with Fable 5.2 first, split
it into queue tasks, and periodically re-check the original analysis against
the code to see whether things are getting fixed and whether the tasks are
wrong or need adjusting.

## In plain terms

Ghoztty on Windows should use as little memory, GPU and CPU as it can, sit
near zero when idle, and never grow over a long day. This task finds every
place where it falls short, puts each fix in the queue, and keeps checking
that the list stays true as fixes land.

## Plan

This is an umbrella. It stays `in-progress` while its children are worked and
closes only when a re-audit comes back with no open P0/P1 finding.

### 1. Baseline (measure before reading code)

Against the `zig-out` Debug build **and** a ReleaseFast build with its own
non-installed endpoints. Never the installed app (see the CLAUDE.md
non-negotiables). Record each number with its method so the re-audits can
repeat it exactly:

- idle CPU % and wakeups/sec: 1 window, 1 pane, shell at a prompt, 60 s
- CPU during heavy output (`cat` of a large file, a fast-scrolling build log)
- private bytes / working set at start, after 10 panes + 3 tabs, after closing
  them all again (the gap after closing is a leak candidate)
- GDI and USER handle counts, kernel handle count, and thread count over the
  same open/close cycle
- GPU dedicated + shared memory and GPU engine % (idle, scrolling, resize)
- the agent (`ghoztty-agent.exe`) on its own: idle CPU, memory per
  hosted session, and handle growth across attach/detach cycles

Put a reusable script at `scripts/perf-baseline.ps1` that emits these as JSON,
so a re-audit is a rerun and a diff, not hand work.

### 2. Audit with Fable 5.2

Spawn the auditors with `model: "fable"` (claude-fable-5-2). Pass the model
explicitly; it is a user requirement for this task, not a default. Fan out by
area (each brief names `docs/claude/build.md` + `docs/claude/testing.md`, plus
the area's own doc):

- **Renderer / GPU**: swap-chain and present cadence, redraw on idle,
  atlas/texture growth, buffer re-uploads, resize churn, occluded/minimized
  windows still rendering
- **win32 apprt** (`src/apprt/win32/`): message-loop wakeups, timers that
  never stop, layered-window/overlay repaint cost, chrome/tab-strip paint,
  per-pane threads, GDI object lifetimes
- **Memory and leaks**: allocator ownership on every pane/tab/window/viewer
  close path, scrollback sizing, caches with no cap, IPC/registry entries
  never removed
- **IPC + agent** (`IpcServer`/`IpcHandlers`/`IpcRegistry`, `src/remote/agent/`):
  pipe instances, polling vs waiting, per-session buffers, ConPTY lifetimes
- **Viewers**: WebView2/markdown/diff panes: process count, memory held after
  close, background tabs still running
- **Shared Zig core paths hot on Windows**: input, parse, and output
  throughput, the main sources of allocation churn

Each finding gets a stable id (`PA-001`…) with: file:line, the cost
(estimated or measured), the fix, its risk, and a P0/P1/P2. Anything an
auditor *claims* is checked by reading the code (claim-verification rule)
before it becomes a task. The audit lands as
`docs/design/perf-audit/audit-1.md` plus the baseline JSON.

### 3. File the work

One parity task per finding, or a few closely tied findings per task. Each
task's frontmatter `deps` includes T2957, its body cites the `PA-` id(s), and
its validation criteria quote the baseline metric it must move. Wins on shared
code that also touch the Mac follow the platform-symmetry rule: file the Mac
half with `seat: mac` when it applies.

### 4. Re-audit periodically

Re-run the baseline plus a Fable 5.2 re-audit **every 7 days, or after 10
child tasks close, whichever comes first**. Each re-audit writes
`docs/design/perf-audit/audit-N.md`, which:

- marks each `PA-` id as fixed (with the metric delta), still open, wrong
  (the task gets closed or rewritten), or changed (the task gets adjusted)
- adds new findings as new tasks
- flags any regression against the previous baseline as a P0 task
- ends by filing the next re-audit as its own task, so the cadence survives
  without anyone remembering it

## Goals

- [ ] `scripts/perf-baseline.ps1` exists and yields a repeatable baseline JSON for the app and the agent
- [ ] audit-1 done by Fable 5.2 auditors, every finding verified against the code
- [ ] every verified finding is a queued task carrying its `PA-` id and target metric
- [ ] the re-audit cadence is running (audit-2 filed with its trigger)
- [ ] closes when a re-audit finds no open P0/P1 item and no regression

## Validation criteria

- [ ] baseline JSON committed under `docs/design/perf-audit/`, with the method for each number
- [ ] audit-1.md lists every finding with file:line, cost, fix, and priority, and notes that Fable 5.2 produced it
- [ ] each `PA-` id maps to a task id (or a recorded reason it was dropped)
- [ ] at least one re-audit has run and reconciled its findings against the task statuses
