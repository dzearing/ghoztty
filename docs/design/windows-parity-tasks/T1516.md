# T1516 - The session-layout cost harness scores a different failure every run, so nobody can tell a real regression from box load

## Summary

test\win32\layout-capture-cost.ps1 is RED at HEAD on this box and red DIFFERENTLY each run: run 1 failed G4 (the forced refresh did not run the bounded pass, mode was not fresh) and G5 (1 of 1 panes advanced, 6 flooded); run 2, minutes later, passed both and failed G3 instead (17.45 ms against a 16.67 ms frame budget). A wall-clock budget measured on a box that is also building and running GUI acceptance scripts cannot separate a real regression from contention, and the G section's mode assertions look load-sensitive the same way. Either the budget needs a headroom factor and a re-measure policy, or the section needs to measure CPU rather than wall time. Found while converting the script for T1511 batch 4; that conversion was written and REVERTED rather than shipped unproven, because a red run cannot re-stamp the guard.

## In plain terms

The test that checks "saving your window layout never freezes the terminal" kept failing on a busy machine, and failing a different way each time, so nobody could tell a real slowdown from the machine just being busy. Now it judges the typical save (which a real slowdown moves) against one frame, tolerates a single save the machine delayed, still fails loudly anywhere near the old one-second freeze, and prints how busy the machine was.

## Goals

- [x] the frame budget is scored so box contention alone cannot turn it red
- [x] the forced-refresh section no longer mistakes the legitimate quiet-path refresh for a missing bounded pass
- [x] the "every busy pane re-recorded" check counts panes recorded for the first time during the window
- [x] the cost assertions are proven able to go red

## Fix (harness only - the app was never wrong)

- **Scoring**: median sample <= one frame (16.67 ms, still read from `layout_cost.zig`), max <= 3 frames (50 ms; the regression guarded against is 991 ms). Every arm prints `median=` and `box_cpu=`.
- **G window**: polls (min 45 s, max 120 s) until a `mode=bounded` sample exists AND every flooded pane is re-recorded; G3/G3b score only bounded samples; quiet-path `mode=fresh` samples are counted and reported, not failed.
- **G5**: a pane with no recorded screen before the window and one after counts as advanced.
- **`-BudgetOverrideUs`**: negative control; never stamps the guard. (First cut named it `-BudgetUs`, which PowerShell treats as the same variable as `$budgetUs` and silently clobbered - the negative control caught it.)

## Validation criteria

- [x] reproduced the failure condition: final runs at 83% and 71% box CPU had forced max 16.76 ms and 16.69 ms (over the 16.67 ms frame - red under the old scoring), green under the new (`layout-capture-cost.ps1` ALL PASS 31, stamped)
- [x] quiet box: 2 runs ALL PASS before the change (forced max 13.0 / 12.9 ms)
- [x] negative control: `-BudgetOverrideUs 1000` exits 1 with 12 failures (G3, G3b and both E rows of every arm)
- [x] scoped harness floor: `floor-lane.ps1 -Lane harness` PASS (stamped)
