# T2644 - A closed window still leaves ~1 MB of private memory behind outside the Zig allocator (native heap), linear per window, after T2500 closed the handle leak

## In plain terms

Closing a window still keeps about a megabyte of memory, every time. One window is nothing, but a session that opens and closes hundreds of windows keeps growing until Ghoztty is restarted.

## Summary

The remainder of T2500 after its handle fix. `test\win32\window-close-memory.ps1 -Report -Cycles 20` (full shape) on the T2500 build: handles now flat (-0.1 a window; the per-type census reads `ALPC Port -2` and nothing else), but private bytes climb **1.08 MB a closed window in a straight line** - 302.1 MB at baseline, 313.3 after 10, 323.7 after 20. A straight line, not a plateau, so it reads as a leak rather than allocator slack. The split-only shape measured ~0.7 MB before T2500; the viewer adds ~0.4 MB.

**It is not in the Zig allocator.** A debug app driven through 3 window cycles and then quit cleanly (`--quit-after-last-window-closed=true`, close the last window) makes the GPA report every live allocation at exit, and it reported exactly four, all process-lifetime singletons: `relay_account.accountPath`, and three from `PaneSidebar.loadRemembered` -> `pane_sidebar_shared.setWindowOrder` (two key dupes + the list). None scales with windows. (Those four are a separate small one-off leak at quit; fix them in passing.)

So the per-window megabyte is native memory: the process heap / CRT, D3D11/DXGI driver allocations per swap chain, DirectWrite, ConPTY plumbing, or the in-process WebView2 controller (viewer share). Next: bisect by `-Shape single` vs `split` vs `viewer`, then attribute with a heap trace (UMDH `gflags +ust` snapshots before/after N cycles, or an ETW heap trace with `wpr`), and free the owner on window/surface destroy.

## Where it stands (2026-11-03)

Attributed, not yet fixed. Established with `window-close-memory.ps1`'s new
`-HeapCensus` / `-HeapCensusRegions` / `-ReleaseSandbox` modes (cdb non-invasive
attach at baseline and end):

- **It is real in the RELEASE build**, not a debug-allocator artefact:
  `zig-out-relmem` (ReleaseFast, sandboxed) reads **1.23 MB a closed window**
  over 20 full-shape cycles, a straight line (301 -> 326 MB). The debug build's
  number is muddied on top by Zig's DebugAllocator, which never reuses a freed
  slot and keeps a whole 64 KiB bucket alive while any one slot in it lives.
- **It is per TERMINAL pane, ~0.45 MB each** (debug bisect: single 0.60,
  split 0.94, viewer 0.84 MB a window).
- **It is not in any NT heap** (`!heap -s`: process heap flat or shrinking)
  and not in our allocator. It is raw committed memory inside a self-describing
  1 GB reservation whose header points into **`nvoglv64.dll` - the NVIDIA
  OpenGL driver** (`ln` on the header pointer). +6.8 MB of the +8.7 MB a
  10-cycle split run left behind is in that arena.
- **Every `wglDeleteContext` on close succeeds** (Surface.deinit now logs a
  warn when it does not; a 3-cycle debug run logged none).
- **Standalone repro** (zig, 150 lines: window + `SetPixelFormat` + context +
  3 cleared/swapped frames + full teardown, run on the test desktop): with the
  frames drawn on the UI thread, 200 iterations are dead flat (52.7 -> 52.4 MB).
  With the frames drawn on a FRESH THREAD each iteration (ghostty's renderer
  thread shape), it climbs 52.0 -> 77.9 MB, erratically (flat for 100, then
  jumps). So the driver keeps per-thread state for a thread that made a
  context current and then exited.

The repro is `docs/design/t2644-gl-thread-churn.zig` (build beside it:
`zig build-exe t2644-gl-thread-churn.zig -O ReleaseFast -lc -lopengl32 -lgdi32
-luser32 -lpsapi --name glchurn`) and `t2644-gl-thread-churn-run.ps1 -N 200
-Mode 1` runs it on the test desktop (mode 0 UI thread, 1 fresh thread, 2 +
texture churn). The meter commands: `window-close-memory.ps1 -ExePath
<zig-out-relmem\bin\ghoztty.exe> -ReleaseSandbox -Cycles 20 -Report` (with
`GHOZTTY_TEST_ALLOW_RELEASE=1`; build `--prefix zig-out-relmem`), add
`-HeapCensus -HeapCensusRegions` for the region diff.

**Next:** extend the repro to ghostty's exact sequence (UI-thread current at
init -> renderer thread -> UI-thread re-enter for deinit -> delete) and try the
candidate mitigations there first: (a) the renderer thread deleting its own
context before it exits, (b) `wglMakeCurrent(null)` + an explicit
`DllMain`-independent release, (c) a long-lived render-thread pool so threads
are not churned per pane. Then port the winner and re-run the release meter.

### 2026-11-03 afternoon: thread churn is real in the repro, NOT the app's trigger

- The repro grew new modes (header of `t2644-gl-thread-churn.zig`). 800
  iterations: fresh render thread per cycle (mode 1) **109 -> 244 MB,
  unbounded**; deleting the context ON the render thread (3) or never touching
  it from the UI thread (5) grows the same; **one long-lived render thread for
  every cycle (4) is 95.9 MB dead flat**. So on this driver every exited thread
  that made a context current strands ~0.17 MB.
- Mitigation (c) was built and tested in the app: a parked-thread pool for the
  renderer (`src/os/reusable_thread.zig`, 5 unit tests green; renderer
  threadlocals reset in `threadEnter`). **The release meter did not move**:
  full shape 20 cycles 1.27 MB a window (was 1.23), and a split-shape region
  census still shows the nvoglv64 1 GB arena growing +25.8 MB over 10 cycles,
  with A8 GPU memory red too (1.19 MB a window). Not shipped - a shared-core
  change with no measured benefit. Saved whole as
  `docs/design/t2644-renderer-thread-pool.patch` (`git apply` it) in case the
  real trigger turns out to stack with thread churn.
- So the app's arena growth comes from something per terminal pane that the
  repro does not do yet. A8 failing alongside A1 says GPU-side objects survive
  too, i.e. something per pane is not released at all, not just per-thread
  bookkeeping.

**Next (fresh context):** grow the repro toward the pane, one ingredient at a
time, until it leaks with a long-lived thread: (1) a robust context from
`wglCreateContextAttribsARB` exactly as `gl_robust.createContext` asks;
(2) a CHILD window of a long-lived top-level (panes are children; the meter's
top-level dies, but the pane pool parks children - check whether a parked
HWND keeps a drawable); (3) the renderer's GL objects - shaders/programs,
textures, VBO/VAO, `glFenceSync`, an FBO - created and NOT explicitly deleted
before `wglDeleteContext`; (4) swap interval / `wglSwapIntervalEXT`. In the
app, A/B the knobs that exist (`GHOZTTY_PANE_REUSE=0`) with
`window-close-memory.ps1 -Shape single -HeapCensus -HeapCensusRegions` and sum
the arena per 1 GB reservation (the per-region diff is unreadable: the driver
splits and merges regions; summing committed bytes per 1 GB bucket is what
names the arena's growth).
