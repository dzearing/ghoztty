# T1070 - The older copy still cannot start itself: the question offers no way to switch builds for you

## In plain terms

Start a Ghoztty that is a different version from the one already running and it
now asks what you meant: open a window in the one that is running, or open
nothing. If what you actually wanted was to run the copy you double-clicked,
you have to go and quit the other Ghoztty yourself, then start this one again.
The app knows both of those steps; it could just do them.

## Goals

- [x] The question offers a third answer, **Switch**, that quits the running
      Ghoztty and starts the copy the user launched
- [x] The button says what it costs before it is pressed ("your terminals will
      reopen", or "will close" when that app runs without session persistence)
- [x] Against a Ghoztty too old to be asked, the question keeps its two answers
      and says why
- [x] The user's terminals come back after a switch

## What landed

- **Capability handshake.** The `version` reply now carries `handoff_quit: true`
  and `session_persistence`. A build from before this sends neither, and
  `SwitchOffer.fromReply` reads that silence as `.unsupported` - a normal
  outcome, since the other copy is by definition a different build.
- **`handoff-quit`** (IPC action, not a CLI verb - it is one half of the launch
  handoff). `ipc_handoff.refuseHandoffQuit` refuses it without a launch identity
  or from the SAME build, so nothing on the pipe but a launch of another build
  can close the user's app this way. The quit is the ordinary one, deferred
  150 ms on a `msg_hwnd` timer (`msg_timer.handoff_quit`) so the reply reaches
  the launch before teardown starts; with persistence on that detaches every
  pane and flushes the layout.
- **The launch** (`App.handOffOrTakeOver`, `takeOverEndpoint`): `[Switch] [Open
  Window] [Cancel]`, Enter still on Open Window. On Switch it sends the request,
  waits on the old pid (20 s), retries the endpoint bind (5 s) and RETURNS into
  `App.init`, so this process starts as the app and its own launch restore
  re-attaches the sessions. Any failure falls back to the old handoff. The whole
  handoff now allocates from one arena, because the takeover path - unlike the
  forward paths - does not end the process.
- **Mac:** no counterpart owed. The question itself (T1023) is Windows-only:
  macOS has no endpoint handoff to ask about - LaunchServices activates the
  running bundle - so there is no Mac dialog to grow a third button.
- Test seams (debug-only): `GHOZTTY_HANDOFF_PROMPT=switch` answers Switch where
  it is offered (joins where it is not); `GHOZTTY_TEST_PRE_SWITCH=1` makes a
  running app answer like a pre-T1070 build.

## Summary

T1023 built the question (`App.handoffChoice` → `ConfirmDialog`, with
`ipc_handoff.mismatchPrompt` writing the text). It deliberately stopped at two
answers, because the third one needs the running instance to shut down on
request and this one to take the endpoint afterwards, and neither exists yet.

What a third button would take:

- **A way to ask the running app to quit.** There is no `quit` IPC action
  today, and it cannot simply be assumed: the whole point of this path is that
  the other instance is a DIFFERENT build, so it may be one that predates the
  action. The launcher has to handle "it does not understand the question"
  (fall back to today's two answers plus the sentence telling them to quit it
  by hand) as a normal outcome, not an error.
- **A bind retry.** After the other app exits, this process is already alive
  and part-way through `App.init` — it can simply re-run `IpcServer.init`
  instead of relaunching itself. Bounded, with a fallback to handing off if the
  endpoint never frees.
- **An answer to what the user loses.** Terminals survive it: sessions live in
  `ghoztty-agent`, and the layout is persisted continuously, so a quit and a
  restart is the same shape the morning refresh already performs. That should
  be verified rather than assumed, and the button's text should say it ("your
  terminals will reopen").
