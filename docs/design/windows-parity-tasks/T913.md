# T913 - The installer is checked to carry a session agent that matches the app

## Summary

`scripts\morning-refresh.ps1` delivers the **app only, never the agent** (T525),
and go.md records exactly why: *"an agent update ends the loop, which is what
the directive rules out"*. The staged agent then waits for a deliberate,
attended delivery — which on this box is rare — so agent-side fixes reach the
user days after they land.

T907 removes the premise. A delivered `ghoztty-agent.exe` is no longer an
interruption: the running agent notices it, hands its holder-backed sessions to
it, and exits. Nothing closes and nothing asks. So the morning refresh can ship
the agent binary like any other file, drop `-AppOnly`'s `AGENT VERIFY SKIP`, and
let the adoption happen on the agent's own schedule minutes later.

Depends on T912 (with holder-backed spawning off, delivering the agent would
just leave it `draining` forever — which is harmless, but buys nothing).

## What is actually left (2026-09-20)

The vehicle above no longer exists. `scripts\morning-refresh.ps1` was deleted by
49462b527 under D85 — *"the terminal should only ever run something that was
actually published"* — and `test\win32\morning-refresh.ps1` went with it. Nothing
calls `-AppOnly` automatically any more.

The GOAL survives the vehicle, and is already met by the route that replaced it:
an agent fix reaches the user through the daily publish. `build-msi.sh` requires
`ghoztty-agent.exe` in the package and gives it the same strictly-increasing
File-table version as `ghoztty.exe`, so the in-app updater installs an agent from
the same build as the app, unattended, on the user's own schedule.

What was missing was the CHECK. `test\win32\release-artifacts.ps1` asserted both
rules for the portable ZIP and for `ghoztty.com`, and asserted neither for the
agent in the MSI — the comment above A14 claimed "the MSI has enforced this since
T89h" in prose and nothing read it back. Since the MSI is now the only route an
agent fix takes to the user, that is the assertion this task was owed, and it is
the deliverable.

## In plain terms

Fixes to the background session manager reach you when you take an update — the
installer carries the session manager and the app together. Nothing checked that
it stays that way, so a packaging change could have quietly started shipping you
a new terminal beside last release's session manager. Now a test says so.
