# T2754 - drag-perf.ps1 red on lane-b HEAD f945ce5fb (2026-11-06 due sweep): a divider drag now waits 0 times per move at 2 and 8 panes (wait=0us every tick), so the batched-wait claims fail - check whether the drag stopped waiting for its frames (T2724/T2738 frame-clock and budget changes) or the oracle drifted

## In plain terms

The check that measures how smooth dragging a pane divider is now reports
that the drag never waits for the panes to redraw at their new size. Either
the app stopped waiting (which could show panes at the wrong size mid-drag) or
the check is reading the wrong number. This finds out which and fixes it.

Seen in T2748's due sweep (`acceptance-parallel.ps1 due`, 2026-11-06 ~09:40,
lane b, HEAD f945ce5fb + T2748's working tree - which touches only dim/bell
log lines, not the drag). drag-perf.ps1 last stamped green 2026-10-24
(7aec7806a). Now every drag summary reads `wait=0us ... waits/move=0` - at 2
panes as well as 8 - for both the serial and fanout passes, e.g.

```
serial panes=2 ticks=25 mean=7748us ... wait=0us ... resizes/move=2 waits/move=0 timeouts=0
```

and the two batched-wait claims fail:

- "the per-pane wait this replaced multiplied by the pane count: at 8 panes it waited 0 times per move, the batched pass waits 0"
- "...and it got worse with every split, which is the user's report: 0 waits/move at 2 panes, 0 at 8"

Suspects landed since the last green: T2724 (compositor-clock wait / 60 Hz

batched frame wait still run on a drag tick at all (log the awaited count), or
does the summary's `wait` counter just no longer see it?
