# T1278 - A hard-killed agent loses its session records, so the restarted agent reaps live holders as orphans

## Summary

Measured while validating T1276: a 'ghoztty-agent --listen' with one live remote session was killed with Stop-Process. The PTY holder survived (that is its job), but the restarted agent logged 'reaped orphaned holder ...: no session record names it' and swept it away, so the session was GONE and the reconnect ladder correctly went terminal on session_gone. T368 states the opposite contract - 'a restarted agent materializes its sessions as relaunchable tombstones, and the driver ATTACHes those' - so either the session store is only durable across a CLEAN exit, or the --listen lineage writes records somewhere the restart does not read. Either way a remote machine whose agent crashes loses every session it was holding, which is the exact thing holders exist to prevent. Repro: test\win32\remote-reconnect-relay.ps1 with the agent killed instead of the relay.

## In plain terms

When the background service on a remote machine crashes, the terminal you have
open on that machine should pick up exactly where it was - same shell, same
history - once the service restarts. In the test setup it instead came back
empty, because the restarted service threw the still-running shell away. Now a
service that keeps a record of its sessions gets them back after a crash, and a
service that keeps no record no longer leaves invisible shells running forever.

## Goals

- [x] Find why the restarted agent reaped a live holder
- [x] An agent that records nothing stops spawning holders nobody can adopt
- [x] Prove the production shape (a recording agent) keeps a remote session across a hard kill

## Root cause

Not a durability bug in `sessions.json`. The repro's far agent was
`ghoztty-agent --listen` with NO `--sessions-file`, so it recorded nothing -
yet `PtySpawner` still made every session holder-backed (the T909 default).
The holder outlived the kill as designed, the restarted agent had no record
naming it, and the orphan sweep (`holder_adopt.reapOrphans`) correctly reaped
it. A recording agent (the app's own `--listen-pipe --sessions-file` agent,
which also carries the relay uplink in production) was never affected: it
persists the holder pipe on OPEN and re-adopts it on restart (already covered
by agent-recovery.ps1 C5). The defect was holders in agents that can never
re-adopt them: `--listen`/`--relay`/`--stdio` without `--sessions-file` - every
one an orphan by construction, reaped by the next agent on the lineage or, if
none starts, leaked until reboot (the T1127 teardown in remote-reconnect-fresh
was compensating for exactly this).

## Fix

`pty_holder_child.wantedFor(env, recorded)` gates holder spawning on the agent
recording its sessions; `PtySpawner.recorded` is set from `--sessions-file` in
every daemon mode (false for `--relay` and `--stdio`). Unit test:
`wantedFor: no holder for an agent that records nothing...`.

## Validation criteria

- [x] A recording far agent hard-killed under a live relay window: the holder survives, the restarted agent logs `holder sweep: 1 adopted`, reaps nothing, and the window reconnects to the SAME session with the shell answering - `test/win32/remote-reconnect-relay.ps1` new arm E, ALL PASS (20 checks), 2026-10-24.
- [x] Teeth: `-NoSessionsFile` turns E red (window `disconnected`, nothing adopted) and shows the recording-less agent spawned no holder and left none behind - measured 2026-10-24 (5 failures = E's 3 + D's cascade).
- [x] Unit: `wantedFor` truth table in `pty_holder_child.zig` (agent lane).
