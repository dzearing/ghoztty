# T1689 - A user-report close re-files a publish request the release it just triggered already honoured, so the next boundary cuts a release with nothing in it

## Summary

Observed 2026-09-20: daily-publish honoured the T1684 request at 12:34:22 and tagged win-v1.36.33 at 6aaba1724, cleared the request, and twelve seconds later set-status done on T1684 (user-report: true) filed it again - same reason, commit 6aaba1724, the very commit the release carries. It is still pending on 2026-09-23, so the next task-boundary run of step 6.5 will tag win-v1.36.34 over two commits that change nothing in the app (a tracker receipt and the go-loop watchdog), and every user gets an update balloon for nothing. The fix belongs in daily-publish: a request whose recorded commit is an ancestor of (or equal to) the last published commit is already satisfied - log it as such and clear it instead of publishing. Optionally, set-status done can skip filing when HEAD is already published. Validation: an acceptance section in test/win32/daily-publish.ps1 (or its sibling) that writes a request at the published commit and proves the run clears it without calling the publish script, plus the positive control that a request at a newer commit still publishes.

## In plain terms

When a task the user reported is closed, the tracker asks for a release so the
fix reaches them. If that release had already gone out with the fix in it, the
ask was still honoured later, and everyone got an update prompt for a release
that changed nothing they could see. Now an ask whose fix is already in the
latest published release is recognised as answered and dropped.

## Goals

- [x] daily-publish treats a request whose commit the last PUBLISHED release contains as satisfied, and clears it without publishing
- [x] a user-report close records its request at the fix's own commit (`-AtCommit`), not at whatever HEAD has become
- [x] an unresolvable `-AtCommit`, a hand-typed request with no commit, and a release still building (`tagged`) all keep the old behaviour - they publish, the safe direction for someone waiting

## Validation criteria

- [x] A request whose recorded commit the last published commit already contains is logged as satisfied and cleared, and the publish script is NOT called - `test/win32/daily-publish.ps1` J6 (decision) and V1 (live, sentinel publisher), 256/256 PASS 2026-11-21
- [x] Positive control: a request at a commit newer than the last release still publishes - J7 and V2
- [x] The live request on this box - moot: `%LOCALAPPDATA%\ghoztty\daily-publish-request` no longer exists on 2026-11-21 (the T1684 request was consumed by a later publish long ago); the clear path is proven by V1 instead
