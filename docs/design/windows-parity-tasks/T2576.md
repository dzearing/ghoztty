# T2576 - Under GHOZTTY_COMP_NOREDIR every GDI child the main window can show must have a layer of its own or it composes black: audit them all (search bar, pane overlays, banner, in-window dialogs, the agent and update children) and prove each on the ghost film

## Summary

T2548 found the shape on film: with no redirection surface a plain GDI child window (the viewer's nav bar, the pane sidebar) composes as a black rectangle, because child windows sit above the window's own visuals and have no surface of their own. T2548 layers the viewer host, the pane sidebar and the tab-rename box (Window.gdiChildrenLayered, the T1787 composeOpaqueLayer path). Every other WS_CHILD the main window can parent needs the same, or a visual: enumerate them (grep WS_CHILD under src/apprt/win32), open each under the three knobs on a ghost window, and film that none is black. Until this lands the knob stays opt-in.

## In plain terms

There is an experimental drawing mode (off by default) in which any
old-style control inside a terminal window shows as a black box unless it
is given a drawing layer of its own. This task checked every such control
the window can hold, found one way a web/markdown viewer pane could still
arrive without a layer (moving between workspaces in single-window mode,
or being dragged in from another window), fixed it, and added a test that
inspects every control in the window and fails if any is missing its
layer.

## Goals

- [x] enumerate every WS_CHILD the main window can parent and say which need a layer
- [x] close the gaps the enumeration finds
- [x] an automated audit that fails on any unlayered visible child, proven to go red

## The audit (2026-11-26)

Every `CreateWindowExW` under `src/apprt/win32/` read for its style and parent:

- **Owned popups, not children** - own surface, unaffected by the window's
  missing one: the search bar (`GhozttySearchBar`) and command palette
  (`GhozttyCommandPalette`) with their EDIT/STATIC children, the link
  preview, the resize overlay, every pane overlay (dim wash, banner strip
  and `BannerOverlay`, `BannerFreeze`, bell border, drop highlight, hover
  tint, key-state indicator, read-only badge, scrollbar, grab handle, drag
  ghost, strip face, chrome repositioner, fullscreen-exit pill), tooltips,
  the update progress panel, and every dialog (banner, rename, new process,
  host settings, agent integrations, machine chooser, confirm/What's-new,
  activity monitor, settings, shortcut guide). Their WS_CHILD controls are
  children of those dialogs' own top-levels.
- **Direct children of the main window**:
  - `GhozttyTerminal` - presents on the GPU (the knob requires
    `GHOZTTY_COMP_PRESENT`), paints no GDI. No layer needed.
  - `GhozttyPresenter` - DXGI presenter. No layer needed.
  - `GhozttyPaneSidebar` - layered at creation under the knob (T2548).
  - `GhozttyViewer` host - layered at creation (T2548); its nav, find,
    feedback and contents bars and WebView2's windows are its children and
    paint into its layer.
  - the tab-rename EDIT - layered (T2548).
- **The gap**: a viewer is layered only if the window it is BORN in needs
  it. Three paths bring a pane into a window it was not born in:
  `adoptPane` (drag a pane into another window / out into a new one),
  `adoptWindow` (single-window mode: a workspace's panes made while it was
  parked come onto the shared window) and `promoteToOwnWindow`. None
  layered the arriving viewer, so its chrome would compose black.
  `Window.layerArrivingPane` now runs on all three (via `syncTranslucency`
  for `adoptWindow`, whose condition became `gdiChildrenLayered()`).

## Validation criteria

- [x] the window's children all have a layer under the knob: `test\win32\comp-chrome.ps1` E7 enumerates every visible child of the no-redirection window holding a split + viewer (9 checked, 7 on a layer, the rest GPU pane classes) - PASS
- [x] a viewer made in a parked workspace is layered when it goes on show: comp-chrome G0-G5 (single-window mode, `workspaces --op=show`) - PASS; comp-chrome ALL PASS (37)
- [x] the audit can fail: the same harness against a build without the hand-off fix (`zig-out-t2576neg`) FAILs G4 naming `GhozttyViewer`, `GhozttyViewerNav` and three WebView2 windows unlayered
- [x] zig floor lanes green: `floor-lane.ps1 -Lane all` lib/none/win32/agent ALL LANES PASS

Not filmed on screen: the audit reads the property that decides black
(no surface of its own) rather than pixels, which the background desktop
cannot capture (T2463). The `adoptPane` drag path is covered by the same
helper but has no scripted drag; it is the same call as the two tested
paths.
