# T946 - Hover probes outside the banner never ask whether the move changed anything

## Summary

T845 gave `capture-hover` a `changed` field: the app photographs the window
before the move as well and reports whether the move altered a single pixel, so
a capture that silently comes back un-hovered is a named failure instead of a
valid PNG of the wrong instant. Two scripts assert it (hover-capture.ps1,
pane-banner.ps1 6g). The other two consumers do not: split-divider.ps1:582 takes
a hovered capture of the divider and tab-strip.ps1:846-847 take two of the strip
buttons, and all three still infer "the hover took" from comparing pixels
against a separately-taken rest shot - which is exactly the inference T845 was
filed against, since a capture of the wrong moment satisfies it whenever the
control happens to look right. Work: assert `.Changed` on each of those hovered
captures (true where a fill is expected to light, false for a deliberate
dead-space probe), and put the value in the assertion label so a failure says
which of the two things went wrong.

## In plain terms

The tests can now ask the app "did hovering there actually change what the
window looks like?" instead of guessing from two photographs. Two of the four
tests that photograph a hover ask; the other two still guess. This makes them
all ask.
