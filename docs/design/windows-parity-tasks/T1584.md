# T1584 - on the Mac, a restored pane whose session is gone opens in the home directory, because the manifest records no working directory

## Summary

The Mac half of T752, which fixed this on Windows. macos/Sources/Features/Remote/SessionLayoutManifest.swift's Leaf records sessionID, title, ipcName, kind and the viewer locations - and no working directory - so every restore path that OPENs a fresh shell rather than re-ATTACHing to a living session lands the pane in the agent's default directory while its place in the layout, its title and its name all come back. Add a workingDirectory to the Leaf (additive/optional, as every other field there is), capture the pane's pwd into it, and spend it on the OPEN path only: on a live re-attach it would seed the pane's reported pwd with a capture-time path the surviving shell may have left, and a dead-but-relaunchable tombstone gets a fresher answer from the agent itself (ATTACHED.cwd). A stale recorded directory needs no rule of its own - the agent's resolveSpawnCwd already falls back to the user's home. The Windows reader is already waiting for it: src/apprt/win32/mac_layout_blob.zig maps workingDirectory out of a Mac-lineage layout blob today, so a cross-machine Restore All of a Mac window on Windows starts honouring it the moment the Mac side writes it.
