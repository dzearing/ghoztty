# T1317 - A session resumed from another machine gets a fresh pane id, so its still-running shell cannot name itself

## Summary

Resuming one session across machines re-adopts the window name now (T1296) but still mints a NEW pane id for the pane. The far machine's shell is running with the OLD id baked into GHOZTTY_PANE_ID, so anything it emits naming itself - a banner script, a hook, an agent addressing its own pane - points at a pane nobody has. The local arm already re-adopts the recorded id (T113, SessionRoster.persistedPaneIdFor); the remote arm could not, because the roster had no view of the far machine's layout. Since T1296 it does, so this is now a small change: widen persistedPaneIdFor to the same unified layout source and pass the id through App.resumeRelaySession the way the local resume passes it.

## In plain terms

When you pick up a terminal session that is running on another machine, the
window that opens gave its pane a brand-new identity, while the program inside
still believed in the old one. Anything that program did to address itself -
updating its status banner, sending itself keys - went nowhere. Now the
resumed pane keeps the identity it had on the other machine, so those keep
working.
