# T930 - Viewer TOC's active row is a solid accent pill, not the quiet Windows 11 nav treatment

## Summary

Follow-up from T828's consumer audit. The machine chooser's rows and the session roster's keyboard cursor now use the Windows 11 list treatment (neutral subtle fill + a small accent indicator bar at the leading edge, neutral focus rim). The viewer's table-of-contents panel still paints its active row as a SOLID accent pill with contrast-flipped text (ViewerTOCPanel.zig, the emphasized branch), which is the same loudness T828 was reported for, on a surface the user sees far more often than the chooser. Windows 11's own navigation panes (Settings' sidebar) use the quiet fill + accent bar + bold label. Bring the TOC onto chooser_rows' vocabulary (selectionFillFocused / selectionFillUnfocused / selectionIndicator / focusRing) so all three selection surfaces speak one language, keep the emphasized-vs-unemphasized distinction T312 asks for, and hold the 3:1 / 4.5:1 floors in unit tests. Acceptance: test\win32\viewer-panes.ps1 plus the toc unit tests.

## In plain terms

The contents list beside a document in a viewer pane highlights the section you
are reading with a loud, solid colored bar across the whole row. Windows 11's
own sidebars (Settings, File Explorer) mark the current item with a soft gray
highlight and a small colored tick at the left edge. After this change the
viewer's contents list looks like that, the same way the machine picker
already does.

## Design notes

- No focus rim: the contents card never takes keyboard focus, so `focus_visible = false` is passed to `list_selection.rowPaint`. Mac's key-window rule maps onto rowPaint's `focused` input (heavier fill + accent bar when the window is active).
- The summary mentioned a bold label; WinUI's NavigationView does not bold the selected item, and a bold face would change the measured row widths and wrap points, so the selected row keeps the regular face and steps its ink up from secondary to primary instead.
- The accent is floored twice (`accentOn` against the card, then against the fill), so the harness finds the bar by shape rather than by the registry RGB.
