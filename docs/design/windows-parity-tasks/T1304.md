# T1304 - A live WebView2 child blanks the viewer host's own fill in a -Sync capture, and the CAPTURE LIMIT header does not say so

## Summary

Found writing viewer-error-card.ps1 (T381): PrintWindow with no flags on a GhozttyViewer host does NOT return the host's own background fill for the region a live Chromium child occupies - the capture reads black there, not the configured background. A probe that asks a viewer host what colour it painted, while the pane has a working web view, is therefore measuring the child's territory rather than the host's. The card case is safe because a failed pane has no child, but nothing warns the next script. Put it in lib\TestDesktop.ps1's CAPTURE LIMIT header beside the GhozttyTerminal flat-fill limit, and give it the same shape: a named limit with the assertion it invalidates.

## In plain terms

The test harness takes pictures of Ghoztty's windows to check what they drew. For a side pane that is showing a web page, the picture comes back black where the page is, no matter what colour the pane actually painted. A future test that checks the pane's colour there would be measuring nothing. This writes the trap down where test authors look for exactly this kind of limit.

## Goals

- [x] name the limit, and the assertion it invalidates, in the CAPTURE LIMIT header
- [x] correct viewer-error-card.ps1's comment, which said the row reads white
