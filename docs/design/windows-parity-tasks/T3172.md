# T3172 - pane-ingest-ab C1 scores one sample of each arm: the local arm alone varies 5.3-9.8 s run to run on Debug, so the agent/local ratio crosses 1.75x with no code change

## Summary

test\win32\pane-ingest-ab.ps1 scores C1 (agent within 1.75x of local) from ONE run of each arm. T3168's turn (2026-11-16, Debug zig-out at 94f84640c, harness run alone, 12 runs) found the agent arm B steady - 9.3 to 10.4 s warm - while the local arm A ranged 5.3 to 9.8 s. So the same bytes scored 0.99x, 1.04x, 1.27x, 1.48x, 1.72x, and one 2.73x (B 14.7 s, the first run after a fresh build, on a box that had just reclaimed 459 GB of build cache). T3168 was filed as a T3019 regression on two such samples (1.76x, 1.82x against 1.56x), and an A/B of T3019 reverted vs HEAD showed no difference in B (variant mean ~10.1 s, HEAD ~9.8 s).

Fix: make the ratio robust rather than the bound wider. For example, run each arm N times (interleaved A,B,A,B so drift hits both) and score median(B)/median(A), or discard a warm-up run, and print every sample so a red names its spread. Keep the -NegativeControl proof that each arm can go red. Do not widen 1.75x.

## In plain terms

One of the speed checks compares how fast a terminal pane shows a big burst of
output with and without the background session keeper in the way. It timed each
side once, and on this machine one timing swings by almost 2x on its own, so the
check sometimes cried "it got slower" when nothing had changed - and a whole
work session was spent chasing a slowdown that did not exist. Now each side is
timed several times and the typical (middle) time is compared, so one unlucky
run cannot fail it.
