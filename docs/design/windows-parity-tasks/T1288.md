# T1288 - A second strip test can still blame the chord for a confirmation dialog it never looked for

## Summary

tab-strip-autohide.ps1 closes a tab with Ctrl+W (line ~225) without first establishing that the pane's shell is descendant-free, and without reading GhozttyConfirmDialog back. That is the same condition T1284 reproduced in chooser-close-chord.ps1: a busy shell gets the modal instead of a close, and the script reports 'closing back to one tab hides the strip again' as red with no mention of the dialog. Its 8-second retry loop hides most of it, which makes the eventual red rarer and harder to attribute rather than impossible. Use Wait-PanesIdle / Get-CloseConfirmDialog from test\win32\lib\PaneIdle.ps1.

## In plain terms

A check that the tab strip hides again when you close back to one tab was
suspected of the same blind spot as the chooser check: blaming the keystroke
when really a "close anyway?" dialog had popped up. It turns out this check
already turns that dialog off, so the false alarm could not happen - but it
now looks for the dialog anyway and names it if it ever appears.

## Goals

- [x] establish whether the confirmation dialog can intercept this script's ctrl+w at all
- [x] the dialog is read back and named, not inferred from a frozen offset
- [x] the new check is shown to go red when the dialog is forced

## Re-verification (2026-10-24)

The premise does not hold as filed. `Start-Win` has launched with
`--confirm-close-surface=false` since T234 (39f4a8f3d), and
`Surface.closeNeedsConfirm` (src/apprt/win32/Surface.zig) answers `false` for
`.false` regardless of descendants; the Disconnect offer needs a remote
machine. So a still-starting shell cannot turn this ctrl+w into the modal, and
no `Wait-PanesIdle` precondition is owed. What WAS missing is the read-back:
the script now asserts no `GhozttyConfirmDialog` is up after the close, clears
one if it is, and `-ForceConfirm` (`= always`) demonstrates that assertion.
