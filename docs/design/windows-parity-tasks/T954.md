# T954 - A loaded test-binary soak cannot be run from a go-loop turn: the background task is killed inside its first lane run

## Summary

T860 needed the agent lane soaked in build-runner mode under load, and could not get one. Two runs (scripts\test-binary-soak.ps1 -Lane agent -LoadWorkers 8 -LoadKind build, 12 runs then 6) were both killed roughly 3 minutes in, during the FIRST lane run, with an empty output file and only the 'LANE agent run 1/1' line in %TEMP%\ghoztty-soak\t860-ctrl-seam-*.log. A plain floor-lane background run of the same lane completes fine from the same turn, so the difference is something about the soak's shape - most likely its 8 detached Start-Process load workers, each looping a cold zig build. What is needed: find what kills it (harness background-task supervision, a resource guard, or the workers taking the session down with them), then either make the soak survivable from a turn or give it a documented out-of-band way to run - because a validation criterion nothing can execute is a criterion that will keep being written and keep being unmet. Related: T443/T832 both depend on this tool for their rate measurements.

## In plain terms

There is a tool that runs the test suite over and over on a deliberately busy
machine, to catch a rare crash. When the automated work loop tried to run it,
the run vanished a few minutes in without a result, so the evidence it exists
to produce was never collected. When this lands, the loop can either run it to
completion or knows exactly how to run it some other way.

## Goals

- [x] find out what actually ended the killed runs - it does not reproduce: the same command, run from a background task, completes
- [x] make a loaded soak finish from a loop turn, or document the out-of-band way to run it - both: the turn recipe is in docs/claude/testing.md, and the soak daemon (T841) is the out-of-band home for rates

## Validation criteria

- [x] A loaded soak (`-LoadWorkers 8 -LoadKind build`) started from a loop turn reaches its summary line.
      Verified 2026-09-24: `test-binary-soak.ps1 -Lane agent -Runs 1 -LoadWorkers 8 -LoadKind build -NoCatch -Label t954-repro`
      as a background Bash task, stdout to `%TEMP%\t954-soak-out.txt`: lane `PASS in 432s`, summary
      `SOAK t954-repro: ... pass=1 fail=0 crash=0 ... load=8:build load-iters=8 started=16 worker-crash=4`, exit 0,
      about 8 minutes wall clock - well past the ~3 minutes the T860 attempts died at. Worker trees
      torn down afterwards: the only zig processes left were the idle soak daemon's
      (`D:\ghoztty-idle-soak\...` caches), none under this soak's scratch directory.

## Findings

- **Not reproduced.** The T860 transcripts are gone, so what ended those runs cannot be
  read back. The shape it left (killed ~3 min into a single lane run, empty stdout file) fits a
  foreground tool call under its timeout better than anything the soak does; the same command
  as a background task survives. Recorded as INFERRED, not verified.
- **The soak daemon (T841) landed after this was filed** and is now the out-of-band way to
  accumulate rates, which was the second half of what this task asked for.
- **New defect found on the way: T1718.** Every one of the 8 build workers failed its first
  build within 56-82s (`error: OutOfMemory`, clang exit 45/5/66, `failed to parse clang
  diagnostics: FileNotFound`). The summary still says `load=8:build` and counts 4 of those
  failures as `worker-crash`, so a loaded soak's verdict currently overstates both its load and
  its crash count.
