# T776 - A floor-lane run reported agent=FAIL once and passed twice after, with the failure text unrecoverable

## In plain terms

The standing test floor went red once and then green twice in a row on the same
unchanged code, and by the time anyone looked, the reason it went red had
scrolled away. A test suite that fails for reasons nobody can read teaches the
next person to shrug at red, which is the one habit a floor cannot afford.

## Goals

- [x] A red lane's verdict names its log path, so the pointer survives a caller
      that keeps only the last line or two
- [x] The first errors from that lane's log print immediately above the
      verdict, so the reason survives with it
- [x] Every error line on the console says which lane wrote it
- [x] The `--relay url` line is explained and stops appearing in green runs

## Summary

During T271 (a harness-only change - not one line of Zig moved), `scripts\floor-lane.ps1
-Lane all` reported:

```
FLOOR SUMMARY: none#1=PASS win32#1=PASS agent#1=FAIL
FLOOR NOT GREEN
```

Re-running `-Lane agent` alone: PASS (exit 0, no `error:` line). Re-running
`-Lane all`: `none#1=PASS win32#1=PASS agent#1=PASS`, 161s/213s/145s. So the
red was not reproducible and not caused by the change under test.

Two things make this worth a task rather than a shrug:

1. **The failure text is gone.** The turn had piped the run through
   `| Select-Object -Last 1{2}` per the context rule, so the only surviving
   evidence is 12 lines of interleaved tail:

   ```
   error: 'apprt.win32.ViewerPane.test.host floor: a real controller on a real
     window, on this box' failed: ghoztty-agent: --relay url must start with
     https:// or wss:// (http:// / ws:// are loopback-test only)
   ...
   error: while executing test 'benchmark.OscParser.decltest.OscParser', the
     following test command failed:
   ```

   Those two names belong to the **win32** lane, which the same summary line
   scored PASS - so the tail is either interleaved across lanes or the summary
   and the errors disagree. `floor-lane.ps1` writes a per-lane log file and
   names it on the console, but a caller who only keeps the tail loses the
   pointer along with everything else.

2. **The message itself is suspicious.** `--relay url must start with https://
   or wss://` is an agent argument-validation error, and `http://` is documented
   as loopback-test only - so a test that legitimately dials a loopback relay
   would hit exactly this string if the loopback allowance were not in force in
   that binary. Whether that is a real skew (a stale `ghoztty-agent.exe` picked
   up by a live test) or just interleaved noise is unknown.

## Direction

- Make a red lane **self-describing in its own summary**: `floor-lane.ps1`
  should print the failing lane's log path (and the first N `error:` lines from
  THAT lane's log) as part of the FAIL verdict, so a caller keeping only the
  tail still has the pointer. It already does this well for `STALL` and for
  crash diagnostics; a plain test failure deserves the same.
- Establish whether the interleaving is real: if the summary can score a lane
  PASS while that lane's errors appear in the console tail, the console tail is
  not attributable to a lane and should say which lane wrote it.
- Then chase the `--relay url` line specifically: find the test that dials a
  loopback relay and check whether it can ever run against a binary without the
  loopback allowance (a stale agent exe, a lane started while another lane's
  build was replacing it).

## Validation criteria

- [x] A deliberately failed lane (e.g. a test made to fail behind an env knob)
      ends with a verdict that names the lane's log path and its first error
      lines, and a caller keeping only the last few lines can still find them.
      Verified by the last three arms of `test\win32\floor-lane-verdict-detail.ps1`,
      which drive a REAL red run through `floor-lane.ps1 -Command` and then read
      only its last twelve lines - the T776 pipeline exactly. Those twelve lines
      carry `[log: ...log]` on the summary and the failing error text above it.
- [x] Console output attributes each line to the lane that produced it, or the
      summary and the visible errors provably cannot disagree. Both, in the end:
      every line of the `-- errors --` block and of the new failure-detail block
      is prefixed `lane <name>:`, asserted by the "every error line in the block
      says which lane wrote it" arm; and the block is built from THAT lane's own
      log file, so it cannot disagree with that lane's verdict. The T776 evidence
      itself was not interleaving - T860 closed on `benchmark.OscParser` failing
      in the AGENT lane, so the core-looking test names in that tail really were
      the agent lane's.
- [x] The `--relay url` failure is shown to be impossible in a clean run, and
      recorded: it was never a failure. It is stderr from the deliberately
      refusing case of the PASSING unit test `wssBase: https/wss normalize to
      wss; http/ws stay plaintext; others refused`, which `wssBase` printed on
      its way out - so it landed in EVERY agent-lane log, green or red. Measured:
      the three agent-lane logs before this change each carry the line once
      (`floor-lane-agent-20260915-{143548,164647,180852}.log`); the green run
      after it carries zero. The message now belongs to the two CLI call sites,
      so what a real user sees is unchanged.
