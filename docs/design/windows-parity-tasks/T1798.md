# T1798 - Exited shells in session-persistence panes are tombstoned on Windows

## In plain terms

On the Mac, a terminal pane whose shell had ended could be left frozen on its
last output: you could not type into it and it never said the program had
exited. This checks the same thing cannot happen on Windows. It cannot: when
the shell in a kept-alive pane ends, Windows notices within a fraction of a
second, the pane says the process exited, and the session list shows it as
ended. A new on-box test now proves that for PowerShell and cmd, for a delayed
exit, and for an exit while a background program still holds the console.

## Goals

- [x] Confirm how Windows notices a shell exit with no end-of-output signal
- [x] A unit test on a real Windows console that pins it
- [x] An on-box test of the whole pane experience, off the user's screen

## Summary

Mac commit c6619717b (merged 7e58ccbdd, 2026-10-10). On POSIX the agent's only
reap check was the pty reader's EOF nudge, which usually fired before
`waitpid` could collect the child. The session stayed `alive` over a zombie:
the pane showed its last output, rejected input (`pty input write failed:
error.InputOutput`) and never reported the exit. The fix is all in shared
`src/remote/agent/`: the reader waits up to 500ms for the exit to become
reapable before nudging, and the reaper tick sweeps every alive session
(`SessionStore.reapExited`), framing EXIT outside the store lock.

Windows has no zombies, but the agent runs ConPTY children through the same
`session.zig`, and ConPTY's output pipe does not reach EOF when the child
exits (conhost keeps it open until `ClosePseudoConsole`). So the Windows
question is the same one from the other side: does a ConPTY child that exits
always get framed as EXIT? Verify that `reapExited`'s liveness test resolves
to a process-handle check (`WaitForSingleObject(h, 0)` / `GetExitCodeProcess`)
on Windows rather than a POSIX-only `waitpid`, and that the tick covers it.

## Findings

- No code change was owed. Windows exit detection never relied on EOF:
  `PtyChild.tryWaitFn` polls the process handle (`WaitForSingleObject(h, 0)`
  + `GetExitCodeProcess`), the holder's `exitPoller` (`pty_host.zig`) runs it
  every 200 ms and frames EXIT, and `HolderChild.tryWaitFn` answers from that
  frame. The shared `reapExited` sweep T1796 brought in is then a second net.
- Each pane shell on this box carries an inner `cmd.exe` child, so a command
  typed into the pane runs one level below the pid `+sessions` reports. The
  script walks the subtree for that reason.
- The session's kill-on-close job ends a background grandchild when the
  session closes, so "outlives the shell" is checked before the exit, not
  after.
