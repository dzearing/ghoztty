# T2747 - Default composition path: pane-banner.ps1 goes 38-red and overlay-zorder.ps1 cannot find a banner overlay (with GHOZTTY_COMP_PRESENT defaulted on (T2514 run 2026-11-06, debug build) and green with =0 on the same build) - classify each red as a test that assumes the GhozttyBannerOverlay popup vs a real banner defect on the composition path, and fix

## In plain terms

Ghoztty is about to draw pane banners a new way (inside the pane, through the
composition path) by default. Two banner tests went red when that was switched
on. Every one of the reds turned out to be the test looking for the old
floating banner window, which the new path deliberately does not use - not a
banner that looks or behaves wrong. The tests now say which path they test,
and the main banner test also checks the banner on the new path.

## Goals

- [x] classify each pane-banner.ps1 / overlay-zorder.ps1 red
- [x] both harnesses mean the same thing before and after the T2514 default flip
- [x] the composition path's banner has layout coverage in pane-banner.ps1

## Summary

With `GHOZTTY_COMP_PRESENT=1` the banner is a child visual of the pane
(T2559) and the `GhozttyBannerOverlay` popup stays hidden. Classification,
measured 2026-11-06 on a debug build:

- **pane-banner.ps1, 38 red: all harness assumptions.** Every failure traces
  to `Get-Overlay` (or a direct `GhozttyBannerOverlay` lookup) returning
  nothing - "overlay not found", "0 -> 0 px", "no banner overlay for ...".
  No red measured a wrong card.
- **overlay-zorder.ps1 setup fail: harness assumption.** Its subject is popup
  z-order and its probe is the banner popup; on the composition path the
  banner has no popup, so it cannot float over another app at all.

Fix (test-only, no product change):

- Both harnesses pin `GHOZTTY_COMP_PRESENT=0` for their popup sections. The
  popup is still a shipped path - the fallback on machines without GL/D3D
  interop (Mesa, WARP, RDP; comp-present.ps1 L).
- pane-banner.ps1 gains **section 13**: a fresh instance with the knob
  explicitly on, asserting from the app's own log lines (no capture route
  reaches a composition visual off the input desktop): the banner takes the
  visual path and is shown, no popup is visible, 3-line > 1-line, a 12-line
  source caps at the 10-line height, h1 taller than plain, a 4-line table is
  a multi-row card, a split pane's card is a visual and the unfocused pane
  keeps its banner, `--clear` works, no panic / failed upload. Measured
  heights: 83 / 149 / 380 / 380, heading 93, table 145. Skips (named) on a
  machine with no interop.

Not covered on the visual path: the card's pixels (wash, corners, shadow,
checkbox green, link underline) - those probes PrintWindow the popup. Hover
and clicks are comp-present.ps1 K's.
