# T3213 - Collapsed blades must survive the in-app updater's relaunch of SEVERAL windows: prove it with a real-gesture harness (divider drag + pane sidebar minimize; updater quit path; paced background + maximized windows; a term|viewer row) and fix what drops them

## In plain terms

Panes you squeeze to the side as thin "blades" should still be blades after
Ghoztty updates itself and reopens your windows. After the 1.55.3 update they
came back full size. A simple one-window close-and-reopen keeps them, so the
loss is somewhere in what an update does differently: it reopens several
maximized windows one after another, and it quits the app its own way.

## Goals

- [x] a harness that folds panes the way a user does, quits the way the updater does, and relaunches several windows
- [x] replay the exact 1.55.2 -> 1.55.3 pair the user ran (ALL PASS)
- [x] fix whatever drops the blades, or file what is left (nothing drops them in these shapes; the one untested difference in the user's log - an agent handoff during the restore - is T3216)

## Summary

Split out of T3208 (user report, 2026-11-17). T3208's investigation, all on
the test desktop against a debug zig-out at fdfa3cddd:

- A collapse made by a REAL divider drag (`Send-TestMouse` down/move/up, the
  `stack-collapse-drag.ps1` section E shape) IS written to the manifest
  within ~3 s (`pane_stack.rows` gains `{leaves,start,count,shares}`), and a
  Restart-Manager close (`WM_QUERYENDSESSION` + `WM_ENDSESSION` lparam 1,
  as `install-restart.ps1` sends it) plus a relaunch of ONE window brings it
  back - for a term|term|term row and for a term|term|viewer row.
- The user's real update (release log `%LOCALAPPDATA%\ghoztty\ghoztty.log`,
  2026-11-17T03:25Z) differs from that in every untested dimension: the exit
  was the in-app updater's quit (`exit-log.txt` reason=user-quit:
  `applyStagedUpdate` -> `PostQuitMessage` -> `App.terminate` ->
  `syncSessionLayout(.fresh)`), and 1.55.3 restored THREE windows, `main`
  first then `window-1`/`window-2` paced in the background and maximized,
  3 terminals + 1 viewer. The quitting 1.55.2 already contained T3126
  (eaf1693b8 is an ancestor of 0b1373c31), so it should have saved them.

Suspects, in the order to test them:

1. A paced background window: `createWindow(.background = true)` shows the
   window before `restoreTab`/`restoreStacks` run, so layout passes (and
   `noteStackRows`/`noteStacks`) see a partial tree first; and
   `applyRestoreFrame` maximizes AFTER `restoreStacks` (App.zig
   `restoreWindowWhole`).
2. A focus landing on a blade after restore - focusing a minimized pane
   brings it on show (`PaneStackState.noteFocus` / `bringOnShow`), e.g. the
   window's activation focusing its last-created surface.
3. The updater quit's final capture (`App.terminate`).
4. The pane sidebar's minimize as the collapse source - never exercised by
   any harness.

Do: a new acceptance harness (or `session-blades.ps1` section G+) that makes
each collapse the way a user does, quits the way the updater does (find or
add a seam for the `quit_requested` path - not a window close, which marks
sessions closed), relaunches with 2-3 windows where the blades sit in a
paced, maximized one, and asserts via `+list --json` `minimized` (pane HWND
visibility counts were unreliable for viewers in the probe). Then fix what
drops them. Mac reference: a7fe3e9f8, dd77885aa.
