# T2780 - Composition step 5c-5: the rest of a glide's window-thread tick moves to the compositor - the desk's strip and gutter paint and the window regions the cards cut - so the glide tick shrinks to the landing timer T2572 wanted

## Summary

Split of T2640 (its second half: 'also left on the UI tick'). After T2572 and 5c-4a..c no pane or face is placed from the tick, but the tick still repaints the desk (strips on the move, T2417 StripGlide; held strips, T2312; gutters, Slide.shownGutter) and cuts the window regions (slideClip). Under a UI stall those freeze while the declared visuals glide on, so a strip can stand still while the card folding into it moves. Declare the moving strips as desk-layer visuals on the same follower (the desk is already a DComp visual since T2509), and drop the region cuts the tree's clips already make redundant in tree mode. Then the tick is a landing timer that runs endStackSlide. Oracle: comp-glide-hold-onscreen.ps1 -Arms stall scored on a moving strip; stack-fold-slide.ps1 / pane-stack-slide.ps1 ALL PASS with the tree knobs.

## In plain terms

When panes slide around in a stack, Windows now plays most of the slide on its
own, so a busy moment in the app no longer freezes it. A few pieces are still
drawn by the app frame by frame: the thin strips of tucked panes when the whole
grid shifts, the pane sidebar's card beside the grid, and some per-frame window
bookkeeping. This task found those pieces and split them into separate jobs,
each small enough to finish and prove on its own.

## Split (2026-11-08)

Too big for one turn, so it was split into four slices, the way T2640 was. What
forced the split, from reading the code and a baseline film:

- **The moving strip the oracle can see does not move on screen.** Baseline
  `scripts\comp-glide-hold-onscreen.ps1 -Arms stall` on 28cd35639: ALL PASS
  (20). Its layout has exactly one strip that stays a strip and moves (`stack
  strip glide left=91 ... right=150 -> 136`), and the part that moves is tucked
  under the card opening beside it, so a freeze of it is invisible and the stall
  arm cannot score it. A strip moves visibly when the grid's leading edge moves:
  a pane sidebar collapse or expand (T2406/T2417). That needs a new oracle arm,
  and declaring the strip as a face with no content, clipped to its visible part
  (**T2825**).
- **Held strips (T2312) are not part of the problem.** A held strip keeps its
  length for the whole glide and does not move, so a stall cannot freeze
  anything about it.
- **The sidebar's card is a separate window.** `PaneSidebar.gridStepped` resizes
  it with `SetWindowPos` and paints it with `UpdateWindow` on every tick. Once
  T2825 lets the grid edge glide through a stall, the gutter between the two
  opens and closes, so it is its own slice (**T2827**).
- **The region cuts cost time but cause no visible freeze.** In the tree,
  `cutGlideTreeRegion` puts the visual's offset into the region key, so a moving
  pane gets a `SetWindowRgn` on every tick. The window under the visual paints
  nothing, so this is tick cost and not a frozen picture (**T2826**).
- **Turning the tick into a landing timer comes last.** It only works once
  nothing the per-tick live layout pass paints is still changing (**T2828**,
  which depends on the other three).

The gutter bar's `shownGutter` follows a drag only. During a drag the hand
drives the layout from the window's thread anyway, so it stays where it is.
