# T2623 - A window-edge drag keeps each terminal at its pre-drag size (clipped, strips in its background) and resizes it once on a 150 ms pause and at release - the held arm T2609 measured at 33-40% off a step in ReleaseFast, made the default and made flash-free

## In plain terms

Dragging the window's edge feels slow because every few pixels each terminal
is resized and the app waits for it to redraw at the new size. Measured on a
release build, that wait is a third or more of every step. When this lands,
the terminals hold still and are trimmed to their new size during the drag.
Any area they don't cover yet shows their own background. They take the new
size once, when you pause or let go. The edge follows the mouse about 1.5x
faster, and nothing flashes.

## Summary

T2609 step 1 (A/B, `test\win32\edge-drag-rate.ps1 -ContentArms
-ReleaseSandbox`, ReleaseFast `zig-out-perf`, run 20261101-150819) measured a
right-edge drag step in three arms of `GHOZTTY_RESIZE_NO_CONTENT`
(`src/apprt/win32/resize_content.zig`):

| scene/dir    | content (shipped) | held | empty (floor) |
|---|---|---|---|
| row3 grow    | 13.2 ms (wait 4.4) | 8.9 ms | 8.9 ms |
| row3 shrink  | 12.8 ms (wait 5.6) | 7.7 ms | 7.6 ms |
| viewer grow  | 12.8 ms (wait 4.6) | 8.1 ms | 8.7 ms |
| viewer shrink| 11.9 ms (wait 5.0) | 7.4 ms | 7.0 ms |

Held == the empty floor, so the frame wait is ALL of the content's share. The
held arm today is only a diagnostic: it skips the core's `sizeCallback` and
the frame wait while `in_live_resize`, fills uncovered strips (own-layer panes
only) and applies the size at `WM_EXITSIZEMOVE` (`Surface.endLiveResize`).

To make it the shipped behavior:

1. Default it on for the window size loop (keep `GHOZTTY_RESIZE_NO_CONTENT=0`
   as the A/B control that turns it off).
2. Pause debounce: re-arm a `drag_hold.quiet_ms` (150 ms) timer on every
   `WM_SIZE` inside the loop; when it fires, apply every pane's
   `content_pending` (one resize per pause), the way `dragQuietTick` does for
   divider drags (T2459). Apply again at release.
3. Flash-free on grow: the strips a held pane does not cover yet must show
   the pane's own background in the same present as the new rect. That
   covers non-own-layer panes too, which `fillUncoveredStrips` skips today.
   And on the GL child, the default framebuffer grows with the window, so
   check what DWM shows in the grown area before the next SwapBuffers.
4. Shrink: the renderer's last frame is cut by the smaller window. Check that
   the GL viewport origin (bottom-left) does not shift the held picture
   vertically when the height changes, and anchor the picture top-left if it
   does.
5. The window presenter (T2610) already composes a held picture this way:
   `gl_window_presenter.planPane` top-anchors each pane's frame in its rect,
   crops it when the frame is larger and lays background strips when it is
   smaller. So on that path, points 3 and 4 come from the compose plan.
   Build the hold so the two paths share it.
6. Mac reference: AppKit live resize (`inLiveResize`). Check how `macos/`
   reflows on settle before fixing the interval.

## Validation criteria

- [ ] `edge-drag-rate.ps1` (default arm) grow and shrink at or under the held numbers above (+10%), both scenes, ReleaseSandbox run.
- [ ] Resize film: zero blank or desk-coloured frames beside or inside a pane, on grow and shrink. If the film needs the input desktop, mark it NOT RUN.
- [ ] PTY resizes per drag = 1 per pause + 1 at release (`resize-debounce.ps1` C/D style count), and the final grid equals a single resize to the same width.
- [ ] A unit test for the pause/release rule in `resize_content.zig`.
