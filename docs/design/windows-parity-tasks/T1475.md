# T1475 - ipc-p2 failed with zero assertions when run back-to-back after ipc-p1, and did not reproduce

## Summary

During T1458's validation on 2026-09-09, `test\win32\ipc-p2.ps1` reported

```
P2 ACCEPTANCE: 1 FAILURE(S) (0 assertions passed)
```

**Zero assertions passed** is the shape that matters: the script did not fail a
check, it died before running any - so the failure is in preflight (isolation
setup, the sandbox launch, or the endpoint probe), not in any of the eight
sections. A clean run scores 20.

It was running inside a `foreach` over `ipc-p1`, `ipc-p2`, `ipc-p3`,
`resize-flicker`, i.e. immediately after p1's teardown. Re-running p2 alone
passed (20 assertions), and an explicit p1-then-p2 sequence passed too, so it
did not reproduce in two attempts.

**What is NOT known, and the reason this card is thin:** the failing run's output
was piped through `Select-Object -Last 2`, so the failure line itself was never
captured. Nobody can say today whether it was a launch timeout, a stale pipe from
p1's teardown, or something else.

## In plain terms

The test suite that every session runs before committing went red once, then
green twice on the same code with nothing changed. Nothing shipped is known to be
broken - but a suite that occasionally lies is one a person stops trusting, and
then a real failure gets waved past as "that flake again".

## Details

Where to look:

- p2's preflight is `Set-GhozttyTestIsolation` / `Reset-GhozttyTestState` from
  `test\win32\lib\Isolation.ps1` plus the `[isolation]` probes that open the run
  (`endpoint is private (nothing answers before launch)` and `the answering
  instance is ours`). One of those is where a zero-assertion exit comes from.
- The suspect condition is p1's teardown not having fully released the sandbox
  endpoint when p2 probes it. If so, the fix is in the wait, not in p2's body.
- **Make the next occurrence self-explaining before hunting the cause.** A
  preflight failure should print WHICH probe failed on the same line as the
  count, so a truncated log still names it. That is cheap and it is what this
  card was missing.

## What the evidence showed (2026-11-11)

T900 had been preserving red transcripts since before this card was filed, and
two later ipc-p2 reds with the exact `1 FAILURE(S) (0 assertions passed)`
signature were still in `%TEMP%`:

- **2026-10-17 — not a flake at all.** `ipc-floor-setup.ps1` section B runs
  ipc-p2 as a child with `GHOZTTY_IPC_TIMEOUT_MS=1` *on purpose* (its negative
  control), and p2's trailer filed that deliberate red as an ipc-p2 failure
  ("Timed out after 0.0s", 347ms). Every run of that harness planted one, and
  each counted against the keep-limit that prunes the real ones.
- **2026-10-16 — real, and not the suspected race.** The private-endpoint probe
  PASSED, so nothing from p1's teardown was still answering. The app p2
  auto-launched accepted `+new-window --target=p2ide` and then did not answer
  for the full 30s bound — the day lane B first came up, two loops sharing the
  box. One occurrence in two months; no p1-teardown/p2-preflight race exists to
  fix.
- Since T1285 (2026-09-02) the isolation probes throw unscored, so a
  `1 FAILURE / 0 passed` p2 can only be a `Need-*` fixture failure — the
  09-09 one was the same `FAIL SETUP` shape, its block lost to `-Last 2`.

The fix: `FloorFixture.ps1` records a one-line cause and `Complete-TestTranscript`
appends `- setup failed: <cause>` to a red verdict line (all ~40 floor-fixture
harnesses, no per-script edits); a caller's deliberate red sets
`GHOZTTY_TRANSCRIPT_EXPECTED_RED` and is announced, not preserved.

## Goals

- [x] A preflight failure names the probe that failed in the final summary line,
      so a run captured with `Select-Object -Last 2` is still diagnosable.
- [x] Either the p1-teardown/p2-preflight race is demonstrated and fixed, or the
      card is closed naming what the improved output showed instead. (No race:
      see above. The fake reds came from the negative control, now unfiled.)

## Validation criteria

- [x] A deliberately broken preflight (e.g. an endpoint still answering) makes
      `ipc-p2.ps1` print the failing probe's name in its last line. —
      `ipc-floor-setup.ps1` B8 (1ms bound): last line reads `... (0 assertions
      passed) - setup failed: the p2ide fixture window - the app under test
      stopped answering IPC (ghoztty +new-window --target=p2ide: exit 1 after
      372ms)`; B9/B10 prove it is not preserved; `fail-transcript.ps1` H1-H8
      (H8 the control) cover the library, 55/55.
- [x] `test\win32\ipc-p1/p2/p3.ps1` green run back-to-back, five times, with no
      zero-assertion exit. — NOT met as worded, and the miss is the finding:
      14/15 green, and round 3's ipc-p3 went red with the 10-16 shape
      (`+new-window` auto-launch, response not in 30s, lane B idle). Its `-Last 1`
      line named the fixture, verb, exit and 30384ms on its own — the diagnosis
      this card asked for. No p1-teardown race; the real defect is filed as
      T2934.
