# T1838 - A stashed pane comes back on screen after a Windows restart: the session manifest does not record the stash (Mac per-leaf stashIndex)

## Summary

T1827 brought pane stashing to Windows, but the stash is not written to the
session layout manifest, so after an app restart (or a session restore onto the
agent) every stashed pane comes back ON SCREEN. Mac records a per-leaf
`stashIndex` (0 = top of the stash) in `SessionLayoutManifest` and rebuilds the
stash on restore with `withStash(stashedIDs(...))` (main 597a193cc).

Port: add an optional `stash_index` to `session_layout.Leaf` (snake_case like
every other win32 manifest field; additive, absent = not stashed, so an older
app ignores it), write it at capture from `pane_stash.stashIndex`, and on
restore mark the restored leaves in stash order (highest index first, so the
top ends up most recent) then `pane_stash.normalize` the tree. A pane stashed
at launch must still get its real slot size (`Window.placeStashedNode` already
does this on the first layout pass - assert it, that is the c6826b79a case).
Never touch session close intent on the way (Mac PaneStashSessionSafetyTests).

## In plain terms

If you tuck a pane away into the stash and then quit and reopen Ghoztty, the
pane used to come back on screen as if you had never stashed it. Now the app
remembers which panes were stashed, and in what order, so after a restart they
are still tucked away and the "bring back" key returns them in the same order.

## Goals

- [x] the saved session records which panes are stashed, and their order
- [x] a restart (and an agent recovery) brings them back still stashed
- [x] a pane that comes back stashed is already the right size for its slot

## Validation criteria

- [x] capture writes `stash_index` for stashed leaves only - `pane_stash.recordedIndex` unit test + `session_layout` round-trip test (writes the key once, only on the stashed leaf); end to end, claim A of `test/win32/stash-restore.ps1` reads s1=0, s2=1, P absent from the real manifest
- [x] restore re-stashes in the recorded order, top of stash preserved - `pane_stash: a recorded stash round-trips its order` (applied in tree order, which is not stash order); end to end, claim D: the manifest the relaunch rewrites from the restored live state carries the same order
- [x] a restore whose stash would hide every pane leaves one visible (normalize) - `pane_stash: a recorded stash that would hide every pane leaves the top visible`
- [x] a pane stashed at launch is sized to its real slot, not a placeholder - claim C of `test/win32/stash-restore.ps1`: the two hidden HWNDs share the right column's width and their heights add to P's (508 vs 523)
- [x] no session is marked close-on-free by a stash round trip - claim D: all three panes re-attached the session ids recorded before the quit, and the stashed s2 is LIVE (`Test-PaneLive`) after the restart; nothing in the change calls `setSessionCloseIntent`

## Design

- `session_layout.Leaf.stash_index: ?u32` (snake_case, additive; absent = on screen).
- Capture (`App.captureWindow`) writes `pane_stash.recordedIndex` for both leaf kinds.
- Restore: `restoreBuildSubtree` collects `(pane, index)` as it meets leaves
  (`RestoredStash`); once the tab is whole, `Window.applyRecordedStash` marks
  them bottom-first (`pane_stash.applyRecorded`), normalizes, moves the tab's
  active pane off a stashed one, and lays out - `placeStashedNode` sizes the
  hidden panes. Shared by launch restore and the in-place root-rebuild fallback.
- `Window.replaceTabLeaf` (agent in-place recovery) now carries `stash_seq` to
  the replacement pane: before this, recovering the agent un-stashed every
  stashed terminal.
- `mac_layout_blob` decodes Mac's `stashIndex`, so a Mac-lineage layout blob
  keeps its stash too.
