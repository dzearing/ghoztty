# T3291 - The harness floor's membership check reads only a member's own source, so test-reach-audit builds the win32 test lane through a shared library and the check never sees it

## In plain terms

The check that keeps slow, window-opening or compiling scripts out of the quick
"house rules" sweep only reads each script's own text. One member,
`test-reach-audit.ps1`, compiles the Windows test lane through a helper file, so
the check passes it even though it breaks the rule. Today that is a known,
deliberate exception; nothing stops a second one arriving the same way.

## Summary

T1572 made the harness floor's membership rule (no GUI, no app launch, no
`zig build`) a checked property: `Get-HarnessFloorLaunch` in
`scripts\lib\HarnessFloor.ps1`, enforced by section A9 of
`test\win32\harness-floor.ps1`. It reads a member's OWN source.
`test-reach-audit.ps1` calls `Resolve-WinTestBinary` in
`test\win32\lib\TestReachAudit.ps1`, which runs `zig build test
-Dapp-runtime=win32 --verbose` to learn which test binary the lane ran. That
row is `Tier = 'daily'` (T1958) precisely because it is slow, so the breach is
known and priced in - but it is invisible to the check, and the rule text says
"no `zig build`" without naming it.

Decide one of:

1. Make the breach explicit: a row field (e.g. `Builds = '<why>'`, allowed only
   on a `daily` row) that the check honours, and follow dot-sourced
   `test\win32\lib\*.ps1` one level so a lib-reached build is seen and must be
   declared.
2. Move test-reach-audit out of the floor to a guard-due row, as T1572 did for
   caller-anchor.

## Validation criteria

- [ ] A member that reaches `zig build` through a dot-sourced library is caught
      by A9 (planted fixture), unless its row declares it.
- [ ] `test\win32\harness-floor.ps1` ALL PASS, and one failure under
      `-NegativeControl`.
