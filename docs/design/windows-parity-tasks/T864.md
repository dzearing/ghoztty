# T864 - A bare config command naming an UNRECOGNIZED shell (cmd, wsl) still runs nested under the default shell wrapper

## Summary

T514 un-nests a bare `config.command` only when `shell_integration.detectShell`
recognizes the argv0 (bash/zsh/fish/elvish/nu/pwsh/powershell). A bare command
naming a shell OUTSIDE that table — `command = cmd`, `command = wsl`, or any
other interactive program used as a shell — still travels as `OPEN.command`,
so the agent runs it under the default-shell wrapper (`cmd /c wsl`): one extra
hidden process per pane, shell pid in `+list` names the wrapper, and the
wrapper's cwd is what cwd fallback tracking sees.

No integration is lost (cmd cannot integrate, wsl's integration would belong
to the shell inside it), so this is a polish-grade wrapper-process gap, not a
feature gap. Fix directions: extend the bare-shell test to a small allowlist
of known non-integrating shells (cmd, wsl) forwarded as OPEN.shell with no
argv rewrite; or decide the current behavior is correct for wsl (whose flavor
invocation `wsl --` the agent already knows) and only special-case cmd.
Whatever the shape, `test\win32\gui-launch-command.ps1` section F is the place
to pin it.

## In plain terms

If you point the config at a shell the terminal doesn't have integration
scripts for — WSL is the one that still did this — your shell starts inside
an extra hidden helper process. Everything works, but there's one more
process per tab than there needs to be, and "what folder is this pane in"
tracks the helper rather than your shell. Now WSL starts as the pane's shell
directly, the way naming any other shell already does.

## What was actually still broken (2026-09-19)

Half this card was stale. `detectShell` grew a `cmd` row (T512), so a bare
`command = cmd` has unwrapped correctly for some time — the `cmd` half needed
no fix, only the unit coverage it already has. `wsl` was the live half, and it
reproduced exactly as described.

The fix names the real distinction: `detectShell` answers *"which integration
script?"*, which is narrower than the question `bareShellCommand` asks —
*"did the user name their shell?"*. For `wsl` those answers differ. So
`bareShellCommand` now accepts either a `detectShell` hit or a name in a new
`bare_shells_without_integration` allowlist (currently just `wsl`, paired with
the `wsl` row the agent's `windowsCommandArgs` already has). Deliberately an
allowlist and not "any single bare word": `command = htop` is a command, and
silently reinterpreting it as a shell would change what happens when it exits.
