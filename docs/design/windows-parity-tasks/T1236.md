# T1236 - Nothing reads CI's answer back for an advisory guard row unless a turn remembers to

## In plain terms

Nothing a user sees. A check on the Windows installer can only be answered by
the build server, and T1189 added the command that reads that answer back. But
somebody has to run it: the next time the installer script is edited, the check
goes stale again and stays stale until a session remembers. A safety net that
depends on remembering is the shape that decayed the first time.

## Summary

T1189 made `release-artifacts-packaging` advisory and added
`scripts\guard-due.ps1 stamp-ci -Guard <row>`, which stamps a row from a green
run of the CI job it names, after checking that every covered file at that run's
commit is byte for byte what is on disk. That works, and it was used today. What
is not wired is the reading: after the next `build-msi.sh` edit the row goes due
and nothing tries the CI route on its own.

Worth considering, in preference order:

- Have `go-loop-exec.ps1 claim` attempt `stamp-ci` for any due advisory row that
  declares `CiEvidence`, at the point it is already asking the build machine for
  the CI verdict (T1219 makes that call every turn anyway). The content check
  means the attempt either proves the code on disk or does nothing, and the
  claim must stay unable to FAIL over it.
- Or the same attempt from `parity-tasks.ps1 validate` - but validate runs
  before the push, so the run that proves this code does not exist yet, which is
  precisely why the claim, one turn later, is the right place.
- Or leave it manual and make the due line louder. Weakest of the three: the
  line is already printed every turn, and being printed every turn is what it
  was doing while twelve turns passed `-NoGuardDue`.

Whatever lands, the stamp's narrowness is not negotiable: a stamp written from a
run that built other bytes is the lie the whole mechanism exists to prevent
(arms K1-K3 of `test\win32\guard-due.ps1`).

## Goals

- [x] A due advisory row with `CiEvidence` is cleared without a human step, on
      the first turn after the build machine has answered.
- [x] The attempt can never fail a claim, and never stamps without the content
      check.
- [x] Acceptance arms cover both directions: it clears when CI is green over
      this exact code, and it stays due when the run built anything else.

## What landed

- `guard-due.ps1 stamp-ci -DueOnly`: only the CI rows that are due right now,
  silent exit 0 when none are (so a current row costs no `gh` call). It prints
  a `stamp: <path>` line for each stamp it writes.
- `go-loop-exec.ps1 claim` runs it before the guard report and commits (and
  pushes) any stamp it writes through `git-commit-guard.ps1`, so the stamp is
  never stranded work. It never changes the claim's exit code. It passes
  `-IgnoreRunState` because the evidence is the CI run, not the caller.
- **Found on the way (lane b):** `ci-status.ps1` and `stamp-ci` asked GitHub
  about the LOCAL branch name. In lane b that is `lane-b`, which CI never
  builds, so every lane-b claim read `CI UNKNOWN` and validate's CI gate could
  never fire there. Both now ask about the branch this one pushes to (its
  upstream), and fall back to the local name. Live check right after the fix:
  lane b read `CI IN PROGRESS Fork CI still running for 364a617c9`.

## Validation criteria

- [x] A `build-msi.sh` edit, pushed, is followed by a claim that clears the row
      by itself once fork-ci has gone green over it. Proved on a fixture repo by
      S13/S14 of `test\win32\go-loop-guard.ps1`: the real claim, a green run over
      these exact bytes, the stamp written AND committed. The live row was
      already CURRENT this turn, so the real-repo version waits for the next
      `build-msi.sh` edit.
- [x] A claim over a red or mismatched run leaves the row due and still exits 0:
      S11 (green run over other bytes) and S12 (red packaging job) of
      `go-loop-guard.ps1`; S15 shows a current row prints nothing the next turn.
      `stamp-ci -DueOnly` alone: K11-K13 of `test\win32\guard-due.ps1`, K12
      included, which shows it asks about the pushed branch and not the local one.
