# T3016 - PA-I02: every inbound agent frame is parsed, re-encoded, queued and parsed again on an extra thread in the app, and the four buffers on that path keep their largest size (client_mux.zig:209-216)

## Summary

PA-I02 (audit-1, T2962). src/remote/client_mux.zig:209-216 parses each frame from the agent, re-encodes it with protocol.writeFrame into `wire`, writes it to a lane fifo, and connection.zig:4030-4062 (dataReaderLoop) reads the fifo in 16 KiB slices into a second protocol.Reader and parses again. Every win32 dial (local pipe, TCP, relay) goes through tcp_dial.dialConnected, so it is on every agent-backed pane's output path. Cost (estimated): 3 extra memcpys, 1 extra parse and 1 condvar hop per chunk, plus 1 extra thread per connection (16 MB under PA-W01). Buffers: client_mux.zig:291-293 and :209 clearRetainingCapacity, protocol.zig:2315-2317 compact; a relaunch replay is one DATA frame up to the 2 MiB ring (16 MiB max), so ~8 MB (up to ~64 MB) stays held for the app's life on the shared local connection. Fix: dispatch data-lane frames from the pump straight into routeInboundData (drops the data fifo and its reader thread), or at least forward the raw frame slice; shrink past a threshold as inbound_ring.zig:441-442 does. Risk medium: Connection is shared with the Mac build (embedded.zig); wire unchanged. Mac half filed. Findings: docs/design/perf-audit/audit-1/I-findings.md.

## In plain terms

Everything a session prints on its way from the background session keeper to
the window was being unpacked, packed up again, copied into a queue and
unpacked a second time on an extra thread — and a big burst (the screen
history replayed when Ghoztty reopens) left its full size held in memory for
as long as the app ran. After this, output is unpacked once and handed
straight to the pane, the extra thread is gone, and burst-sized buffers are
given back once the burst has passed. Nobody sees a change on screen; the app
does less work per line of output and holds less memory after a restore.

## Goals

- [x] data frames go from the inbound pump straight to the pane, with no re-encode, fifo or second parse
- [x] one fewer thread per agent connection
- [x] buffers on the inbound path stop keeping a burst's size; cobs/base64 readers stop reserving 16 MiB each
- [x] measured against a before build (threads, busy CPU, memory after a relaunch replay)

## Validation criteria

- [x] app thread count with persistence on drops by 1 per agent connection - perf-baseline agent phase (Debug, 5 restored sessions, 3 kill/relaunch cycles), `-ExeDir zig-out-before\bin` (built from e96caadc2) vs zig-out: app threads 107/107/107 -> 106/106/106
- [x] busy-phase app cpu_s for an agent-backed pane drops measurably - new `perf-baseline.ps1 -Phase busy -BusyPersistence` (64 MB `type` through the agent), two alternating runs per build: cpu_s 27.98 / 23.61 before -> 17.23 / 19.48 after (about 30% less), wakeups 73.5k / 73.0k -> 49.7k / 49.1k per s, same ~35 s wall
- [x] after a relaunch replay the app's private bytes return within 5 MB of pre-replay - the same agent phase: app private after each replay 403.8 / 405.8 / 405.1 MB before vs 402.8 / 403.1 / 404.9 after, flat across cycles (these replays are small); the outsized-frame case is the unit test `T3016: a Reader gives an outsized frame's buffers back...` (2 MiB frame, every encoding) plus `Fifo (T3016): a drained burst gives its memory back`
- [x] zig build test (none + win32) and session restore acceptance green - floor-lane all PASS (lib/none/win32/agent; the 4 new tests reached, `-Dtest-filter=T3016` count +4); session-persistence.ps1 green but C3, the standing T2021 red (noted there); session-resume-offset 139/139, agent-relay-session-e2e 28/28, remote-reconnect-relay, ipc-relay, sessions-running-cmd, activity-monitor-dialed ALL PASS
