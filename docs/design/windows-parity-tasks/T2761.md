# T2761 - Composition step 5d-1: the overlay scrollbar's fade in and out is one compositor opacity animation of its pane visual, not a whole-strip pixel re-upload per frame-clock tick

## Summary

On the visual path (T2492) the scrollbar thumb is drawn at its full hover/idle/drag alpha and the overlay fade rides the layer's opacity, declared once to DirectComposition (linear, ~128 ms, the stepped path's 8 x 32 steps); a tree rebuild mid-fade re-declares from the reached value; the popup path is unchanged. Oracle: comp-present-style on-box assertion plus a film with the UI-stall seam and the stepped A/B arm.

## In plain terms

The thin overlay scrollbar on the right of a terminal lights up when output
scrolls and fades away a second later. That fade was redrawn by the app eight
times over, so a busy app made it stutter or freeze. Now the app hands the
whole fade to Windows' compositor once and Windows plays it smoothly at the
screen's own refresh, however busy the app is.

## Goals

- [x] On the composition path the fade is the strip's layer opacity, declared once as a linear ramp (same 128 ms as before)
- [x] The strip's pixels hold still through a fade (no re-upload per frame)
- [x] A fade retargeted mid-way, a rebuilt composition tree, and a switch back to the popup path all carry on from the value reached
- [x] The popup path (composition off) is unchanged
- [x] Debug seams for the on-screen oracle: a UI stall and a stepped A/B arm

## Validation criteria

- [x] Unit: `fadeDurationMs` / `fadeAt` (full ramp 128 ms, a part its share, linear, clamped, a retarget runs at the same rate) - win32 lane via `floor-lane.ps1 -Lane all`
