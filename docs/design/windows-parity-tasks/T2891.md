# T2891 - A GPU driver reset blamed on Ghoztty's GL context (TDR, 'device lost (guilty)') was followed by GL_OUT_OF_MEMORY on the rebuild and an access violation in nvoglv64 that took the installed release down

## Summary

Live case 2026-11-10 07:12 local (installed win-v1.54.8+38d9b9d64, pid 63972). 07:12:05.917 'graphics device lost (guilty); rebuilding this pane's renderer' -> rebuilt OpenGL 4.6 on the RTX 4090 after 1 attempt -> 07:12:05.936 'NVIDIA OpenGL driver has encountered...' + 'GL_OUT_OF_MEMORY ... Failed to allocate memory for buffer object' -> renderer unhealthy -> 07:12:06 APPCRASH in nvoglv64.dll 32.0.16.2114 offset 0xa8e135, c0000005. Windows logged LiveKernelEvent 117 (VIDEO_TDR_TIMEOUT_DETECTED, WATCHDOG-20261110-0712.dmp) at 07:12:11; MicrosoftSecurityApp also crashed in the same second. 'guilty' means the driver blamed OUR context for the GPU hang, so something we submitted ran >2s on the GPU. Dump: %LOCALAPPDATA%\CrashDumps\ghoztty.exe.63972.dmp. Different from T2839 (DrvPresentBuffers worker, no TDR). Earlier LiveKernelEvents 1a8/1b8 on 11-08 15:35/15:59 and 11-09 06:01/06:27 may be related. Work: read the dump with the win-v1.54.8 symbols; find which pane/draw was guilty (log 15:11:59 a 235x197 page-capacity adjust just before); make a post-reset rebuild that hits GL_OUT_OF_MEMORY back off (retry later or drop to a software path) instead of continuing into a driver AV.

## In plain terms

When the graphics card hiccups and Windows resets it, Ghoztty is supposed to
quietly redraw its windows and carry on. On 2026-11-10 it tried to redraw
while the reset was still in progress, the graphics driver ran out of
memory, and the driver crashed the whole app. Now Ghoztty waits for the
reset to finish (up to ten seconds) and, if the driver still is not ready,
throws that attempt away and tries again a moment later instead of drawing
into it.

## Scope note

This task is the CRASH: surviving the reset. WHY the driver blamed our context
for the hang in the first place (something we submitted ran more than 2s on the
GPU) is a separate question, split out to its own follow-up (dump analysis
against the win-v1.54.8 symbols).

## Goals

- [x] the rebuild waits for the driver to report the reset complete (KHR_robustness), with a ceiling
- [x] the same wait on the window presenter's own context
- [x] a rebuild that comes up GL_OUT_OF_MEMORY is discarded and retried, never drawn into
- [x] debug-only seams and an acceptance arm that stage both shapes

## Validation criteria

- [x] the settle policy is unit-tested (`gl_robust.zig` "settle: ..." test) - none + win32 lanes via `floor-lane.ps1 -Lane all`
- [x] a reset still reporting itself is waited out and the rebuild comes after it (`gl-device-lost.ps1` F2-F4, 1500ms simulated; F10 logs once per lost pane)
- [x] an out-of-memory rebuild is discarded and the retry draws the pane's own tint (F5-F9)
- [x] a healthy device never waits or discards (C4 negative control) and arms A-E unchanged - `gl-device-lost.ps1` ALL PASS 63
- [ ] NOT RUN: a real TDR. The loop does not reset the user's GPU on purpose; the next real one is the field check (the log now shows `still resetting` then `reset completed after Nms`).
