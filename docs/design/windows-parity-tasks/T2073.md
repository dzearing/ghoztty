# T2073 - git-commit-guard commit silently drops a staged exec bit on a NEW file: it should refuse (or carry it) when a requested path's index mode differs from what the pathspec commit recorded

## Summary

Seen on T1089 (2026-10-18). A new script was staged with `git add` + `git update-index --chmod=+x`, and the index read 100755. `git-commit-guard.ps1 commit -Paths ...` then committed it as **100644** (651ab1bde) and reported `COMMITTED ... all requested`. The guard's header already says a pathspec commit cannot carry an index-only mode. Nothing ENFORCES that, though, so the bit was lost silently. It surfaced only because the leftover staged mode then blocked the push's `pull --rebase` (exit 6). A workflow that runs the script directly (release.yml) would have died with "Permission denied" at release time. The harness check (D6c of `test\win32\website-windows-download.ps1`) reads the INDEX, so it passed before the commit and could not see the loss.

Fix: after the read-back, compare each requested path's mode in HEAD with its index mode. On a mismatch, either fail loudly with the hold/commit recipe, or carry it (`git update-index --chmod` on the committed tree, then amend inside the held lock). Acceptance: section W of `test\win32\go-loop-guard.ps1`, with a new file staged +x.

## Validation criteria

- [ ] committing a new file staged 100755 through the guard either lands 100755 in HEAD or fails naming the mode loss (never `all requested` over a 100644)
- [ ] go-loop-guard.ps1 section W covers it, with a negative control
