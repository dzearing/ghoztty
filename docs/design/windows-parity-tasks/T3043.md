# T3043 - PA-V11: opening a HEIC or TIFF image holds four or five full copies of its pixels and decodes on the GUI thread (ViewerPane.zig:4935)

## Summary

PA-V11 (audit-1, T2963). transcodeImage (ViewerPane.zig:4935-4941) holds decoded BGRA, the DIBv5 and the BMP file at once; the whole source file is read though WIC needs 32 bytes (:4907); the response copies the BMP into an HGlobal stream (:5126-5129); the comment at :4932-4934 puts a phone photo at a few hundred ms on the UI thread. Cost (computed): 48 MB per copy at 12 MP, ~195 MB transient. Fix: write BMP header and rows straight into the stream; decode on a worker under a deferral. Risk: deferral lifetime vs pane close. Findings: docs/design/perf-audit/audit-1/V-findings.md.

## In plain terms

Opening an iPhone photo (HEIC) or a TIFF scan in an image pane froze the whole
Ghoztty window while the picture decoded, and briefly used four or five times
the picture's size in memory - roughly 200 MB for one 12-megapixel photo. Now
the picture decodes in the background while the window keeps responding, and
it is held in memory once.

## Goals

- [x] the HEIC/TIFF decode runs off the GUI thread, the page's request parked until it is ready
- [x] the decoded picture is written once, straight into the response the page reads
- [x] the source file is no longer read whole on the GUI thread just to sniff 32 bytes
- [x] portrait (EXIF-rotated) photos still show upright

## Validation criteria

- [ ] perf-baseline.ps1 viewer phase (PA-V01) extended with a 12 MP HEIC: peak app private bytes during load drops by >=100 MB - NOT MET AS MEASURED, moved to T3223. Before/after on the same box (12 MP LZW TIFF swapped into an open pane; HEIC cannot decode here, HEVC codec missing): peak +459 MB on both builds, identical to the MB, so another spike on the reload path dominates and hides the ~190 MB of copies this change removed
- [ ] the GUI thread stays responsive during the decode (message-loop latency probe) - the decode itself is now off-thread (`decode_ms=104 parked=true`), and the worst WM_NULL round trip fell from 146/147 ms to 107/119 ms. Something else still blocks ~110 ms; moved to T3223
- [x] viewer-image.ps1 L1: a TIFF is served `parked=true` (decoded on the worker under a deferral) and the body is exactly 14 + 124 + w*h*4 bytes - one copy of the pixels, no padding (2026-11-17, two runs)
- [x] viewer-image.ps1 L1b: a TIFF stored 64x32 with EXIF orientation 6 is drawn upright at 32x64 through the new `orientInto` path (2026-11-17)
- [x] unit: `viewer_image.bmpHeaders` writes a top-down V5 header the clipboard's DIB parser reads back; `image_clipboard.orientInto` matches `orient` and refuses a wrong-size destination (none lane)
