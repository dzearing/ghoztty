# T3178 - A pane drag starts at once with many windows open: only the source and hovered window's sidebar redraws (Mac 343b000e8)

## Summary

Mac 343b000e8: with the all-windows sidebar list every window's sidebar observed the drag session, so drag start redrew windows x panes rows (120-430ms with 19 windows). Now each sidebar sees the drag through its own draggedPane, armed for the source window at begin and for another window on first move over it; finer drag milestone logging. Measure the win32 drag start with many windows and all-windows sidebar on (PaneSidebar.zig, pane_drop.zig, pane_sidebar_cross_drop.zig): if every window's sidebar invalidates at drag begin, scope it the same way. Ref: docs/reference/pane-rearrange.md.

## In plain terms

With lots of Ghoztty windows open and the sidebar showing every window, picking
up a pane to drag it made every window's sidebar redraw at once, so the drag
could hitch before it started moving. Now only the window you drag from gets
ready at the start; another window's sidebar opens its drop spot the moment
the pointer reaches that window, the same as on Mac.

## Goals

- [x] The drag's start arms only the source window's sidebar (Window.setSidebarsDragActive)
- [x] Another window's sidebar joins on the first move over that window, and that same move resolves against its opened drop well (Window.updateRearrangeDrag + armSidebarUnder)
- [x] Every armed sidebar is let go at the drag's end (unarmed ones are a no-op)
