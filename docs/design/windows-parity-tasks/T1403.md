# T1403 - Clear-screen and click-to-move trust ConPTY's prompt marks, which lie mid-command

## Summary

P2: the same ConPTY OSC 133 unreliability T1398 fixed for the close confirmation, in two smaller behaviors. ConPTY brackets a cmd.exe prompt with 133;B and never emits 133;C, so cursorIsAtPrompt() reads TRUE all through a running command. Two other consumers key on it: Termio.clearScreen (src/termio/Termio.zig ~743) sends a form-feed to the shell as if it were at a prompt, and Surface.processMousePressPrompt (src/Surface.zig ~5165) enables cursor-click-to-move mid-command. Neither is destructive, but both are visibly wrong on Windows. Found while root-causing T1398.

## In plain terms

Pressing the clear-screen shortcut while something is running in a pane (a
build, `ping`, Claude Code) used to type an invisible Ctrl+L into that program,
because the terminal believed it was sitting at an empty prompt. Clicking in the
pane during a command could likewise send it arrow keys. Now the terminal checks
whether a command is actually running before doing either, so a running program
is left alone and the screen is simply cleared above the cursor.

## Goals

- [x] Re-verified still real at d13caa868: `Termio.clearScreen` and `Surface.maybePromptClick` both still gate on bare `cursorIsAtPrompt()`
- [x] Clear-screen sends no form-feed into a running command on Windows
- [x] Cursor-click-to-move does not fire mid-command on Windows
- [x] macOS behavior unchanged (the runtime hook is comptime-optional; only win32 declares it)

## Design

The core asks the apprt, via a comptime-optional `commandRunning()` on the
runtime Surface (`Surface.frontendSeesCommandRunning`), whether it can SEE a
command running under the shell. win32 answers from the process table (shell
has a live descendant; remote panes use the agent's pushed `has_descendants`).
"Cannot tell" answers false, so the prompt marks decide exactly as before - the
change only ever overrules a mark when a command is positively seen running.
`Terminal.cursorIsAtPromptUnless(command_running)` is the one place the two
verdicts combine; `clear_screen` carries the flag to the IO thread, and
`maybePromptClick` asks only after its cheap gates pass (so an ordinary mouse
release never takes a process snapshot) and outside the renderer lock.

## Finding: ConPTY's lie depends on the Windows build

The first version of the acceptance section relied on ConPTY's own marks and
PASSED with the fix switched off: on build 26300 (2026-11-10) the marks read
`marks_say_prompt=false` mid-command, whereas T1398 measured them lying on
2026-09-06. So the reader now writes the bare `133;B` itself, which reproduces
the lie on every build; the fix still matters for builds where ConPTY lies.
