# T1663 - A relaunch no longer restores the previous run's window, so session persistence silently does nothing

## In plain terms

Close Ghoztty with a couple of panes open and start it again. It is supposed to
bring those panes back - that is what session persistence is for, and it is the
feature the whole `ghoztty-agent` exists to provide. Right now nothing comes
back: you get a fresh empty window, your panes are gone, and the app says
nothing about it. Turning persistence explicitly OFF produces the same result,
so from where a user stands the setting does nothing at all.

## Summary

`test\win32\persistence-flag.ps1` section C2 is red:

```
PASS  C1c the fixture window has 2 panes (got 2)
FAIL  C2a a launch with no persistence flag RESTORES the previous run's
      window (2 panes, got -1)
FAIL  C2b the restored pane is LIVE: input reaches its child and output returns
PASS  C3a --session-persistence=false restores nothing (got -1 pane(s))
PASS  C3b the non-persistent launch comes up with exactly its own window (got 1)
```

`-1` is "no such window at all". C1 builds the fixture fine (a two-pane
`t158-pair` window under `--session-persistence=true`), so the failure is in
the RESTORE, not in the setup. C3 passes vacuously: it asserts that nothing
comes back, and nothing does either way, which is exactly the shape that lets a
restore regression hide behind a green-looking "persistence off" assertion.

Section A - the source sweep that T1491 is filed against - is **green** in these
runs (`A1 no launch leaves persistence unstated (undeclared: 0 of 309)`), so
this is a different defect from that card and T1491 may itself be already
fixed; see the note below.

## What is already established

- **Not load, not isolation.** `suite-run`'s confirm pass re-ran it ALONE on a
  quiet box and it **REPRODUCED** (`[ 2/3] REPRODUCED 2m 19s
  persistence-flag.ps1 2 FAILURE(S) (26 passed)`). That distinguishes it from
  T1572's known false red, which has always gone green alone.
- **Not a stale `zig-out`.** `zig build -Dapp-runtime=win32 -Doptimize=Debug`
  was run immediately before both failing runs, which is the explanation T1571
  offers for this script going red and it does not apply here.
- **Not the T1645 edit.** Ruled out directly: `src\apprt\win32\ViewerWorktreeProbe.zig`
  was stashed, the app rebuilt Debug from a clean `ab37eccf9`, and
  `persistence-flag.ps1` failed with the identical two assertions. So the red
  belongs to the branch head, not to whatever is in flight.
- **It was green at `7ff8ecb6a`** (stamp generated 2026-09-18T23:13:31). The
  only commits between that and `ab37eccf9` are `9876331b5` (T861) and
  `ab37eccf9` itself, and **both are tracker/PowerShell only - neither touches
  product code.** That is the most interesting fact on this card: a pure-docs
  range cannot have caused a product regression.

## The hypothesis that fits

**The box rebooted at 2026-09-19T01:39**, between the green stamp and the first
red run (the claim's BOOT OUTAGE line names it). Session restore depends on
`ghoztty-agent` holding the previous run's ConPTYs and on state under
`LOCALAPPDATA`, and the fixture repoints `LOCALAPPDATA` at a tmp dir and
supplies its own agent via `GHOSTTY_LOCAL_AGENT_BIN`. So the first thing to
establish is whether this is a PRODUCT regression at all or a post-reboot
environment/state failure that the fixture inherits - and if it is the latter,
the script is asserting something it cannot own, which is its own defect.

Answer that before looking for a code change, because the commit range says
there is no code change to find.
