# T1622 - Tab tooltip shows the raw path and the ~ form on two lines, and tab-tooltip.ps1 has been red since it was last edited

## Summary

Found while running the DUE tab-tooltip guard for T796's commit (the harness was already DUE at that turn's claim, i.e. a previous turn edited test\win32\tab-tooltip.ps1 and never ran it green). Two assertions fail on this box: 'A: the home prefix reads as ~' and 'E: a title that fits keeps the tip cwd-only'. Both print a tooltip whose text is the FULL path, a newline, then the ~-collapsed path - e.g. 'C:\Users\David\AppData\Local\Temp\ghoztty-tabtip-40148\tipA268\n~\AppData\Local\Temp\...\tipA268' - where the assertion expects the ~ form alone. Decide which side is wrong before changing anything: either the product started emitting title+tip in one string (a real regression a user sees as a two-line tooltip) or the harness's oracle was left reading the pre-edit shape. The debug line 'tab tooltip tab=0 text=...' in the app log is the evidence; sections A and E of test\win32\tab-tooltip.ps1 are the harness half.

## In plain terms

Hovering a terminal tab is meant to tell you which folder that tab is in,
written the short friendly way (`~\git\ghoztty`). On most tabs it was saying it
TWICE - the full raw path on one line, and the same path in the short form on
the line below. That is because a tab the shell never named is named after its
folder, so the tooltip's "here is the full tab name that did not fit on the
tab" line was just the folder again, spelled the long way. Now a tab name that
only restates the folder is left off and the tooltip is one clean line; a tab
with a real name still gets that name on top.
