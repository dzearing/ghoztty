# T3378 - Debug builds: any stderr write that fails with an unmapped Win32 error recurses through std's unexpectedError until the main stack overflows

## Summary

T3376's crash had two halves. T3376 fixed the trigger (the console probe left stderr naming a reused handle). The amplifier is still there: std.os.windows.WriteFile maps only a handful of errors, and in Debug builds unexpectedError prints a diagnostic to stderr with std.debug.print and dumps a stack trace - so if stderr itself fails with an unmapped error (536 ERROR_PIPE_LISTENING, 109 ERROR_BROKEN_PIPE when the reader of an inherited pipe exits, 233 ERROR_PIPE_NOT_CONNECTED), the print recurses until the 16 MB stack is gone. Any debug app or CLI whose stderr is a pipe the other side closed can hit it. Look at making main_ghostty.logFn's stderr leg write with kernel32.WriteFile directly and stop on any error (and drop stderr for the rest of the process after the first failure), then check whether unexpectedError's own print can still be reached with a broken stderr from other call sites; a unit test can drive the leg with a closed pipe handle.
