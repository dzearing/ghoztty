# T3383 - An exited command's pane reads back blank: +read of a wait-after-command pane shows neither the 'Process exited' notice nor the abnormal-exit diagnostic

## Summary

ipc-child-exited.ps1 (T65) is red on HEAD 9a40d1d10+, alone and beside others, 3 runs on 2026-11-22: with wait-after-command=true and --session-persistence=false, a pane running 'cmd /c exit 0' stays open and a real key closes it (arm 4 green), but +read --name=<pane> returns EMPTY output even at --lines=200, so arm 1 (Process exited notice) and arm 2 (failed to launch / command / Runtime: diagnostic for exit 3) fail. Either the core child-exited text (src/Surface.zig ~2117) is no longer printed on Windows, or +read of a pane whose child has exited reads an empty screen. Suspects in recent history: T3133/T3155 (just-opened shell close rules), T3061 (renderer wake batching). First step: screenshot/pixel-check the pane to tell the two apart. Logs: %TEMP%\ghoztty-acceptance-parallel\20261122-024924\00-ipc-child-exited.log (the harness now prints the +read text on failure).

## In plain terms

When a command run in its own pane finished very quickly (for example a command that fails straight away), the pane went blank instead of saying "Process exited" or showing why the command failed. The message WAS written, but a moment later Windows' console layer drew its first (empty) screen over it. Now the pane waits for that first screen before writing the message, so the message stays.

## Root cause

Traced with temporary pty-byte logging on 2026-11-22: for `cmd /c exit 0` conhost sends only its 16-byte mode preamble (`CSI ?9001h CSI ?1004h`) before the child exits; the T65 quiet-gate (one quiet 50 ms tick) fired at +50 ms, the notice was printed, and conhost's FIRST paint (`CSI ?25l CSI 2J ...`, erase + blank frame) arrived ~50 ms later and erased it. `+read` was right: the screen really was blank. Not a T3361 (shared +read) regression - that body is byte-for-byte the old dump.
