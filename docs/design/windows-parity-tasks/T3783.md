# T3783 - On WSLg the Linux window shows nothing when the app falls back to X11: find WSLg's Wayland socket, and assert real on-screen pixels

## Summary

User report 2026-11-25: "linux build doesn't render?" - scripts\linux\open.ps1 put a window on the screen that showed NOTHING (see-through: the Windows desktop behind it showed through, only the CSD shadow outline visible), while the app was alive and its own render was correct.

### Evidence (captured 2026-11-25 ~19:45, lane-l build of 19:03)
- Screen capture of the WSLg RAIL_WINDOW ('~ (Ubuntu)', 864x664, CopyFromScreen): only the windows behind it. PrintWindow on a RAIL window returns solid black, so it is not a usable oracle.
- The app's own render (debug `capture-pane --window` over /run/user/0/ghostty-debug-0.sock): correct 800x600 window - header bar, debug banner, sidebar, `root@MaximusHome:~#`.
- Log: `windowing protocol=x11`, `loaded OpenGL 4.6 renderer="D3D12 (NVIDIA GeForce RTX 4090)"`, `libEGL warning: DRI3 error: Could not get DRI3 device`, and 95 x `MESA: error: Failed to attach to x11 shm`.
- Cause: the app runs as root; XDG_RUNTIME_DIR=/run/user/0 has no wayland-0 (WSLg's socket is /mnt/wslg/runtime-dir/wayland-0 and is only linked into the default user's /run/user/<uid>). GDK silently fell back to X11 (XWayland :0), where Mesa d3d12's present path needs MIT-SHM, which fails across the WSLg boundary - every frame is dropped.
- Proof: relaunched with WAYLAND_DISPLAY=/mnt/wslg/runtime-dir/wayland-0 -> `windowing protocol=wayland`, shm errors 0, and the screen capture shows the full window drawn.
- The launcher was patched the same day (open.ps1 sets WAYLAND_DISPLAY to the absolute socket when $XDG_RUNTIME_DIR lacks it). That is a workaround in a person's script; the APP must not depend on it.

### Fix (app)
At startup on WSLg (the same place that sets GALLIUM_DRIVER=d3d12, /dev/dxg present): when WAYLAND_DISPLAY is unset or does not resolve under XDG_RUNTIME_DIR, and /mnt/wslg/runtime-dir/wayland-0 is a socket, use it (absolute WAYLAND_DISPLAY, or point XDG_RUNTIME_DIR at /mnt/wslg/runtime-dir if that is safer for the IPC socket path - decide, record why). Do not leak the override to child shells unless WSLg itself would have given it to them. If the app does end up on X11 with d3d12 and sees the shm failure, it must log ONE loud warning naming the cause and the remedy, never 95 silent Mesa lines and a see-through window (consider falling back to llvmpipe there rather than drawing nothing).

## In plain terms

Opening the Linux version of Ghoztty on this PC put an empty, see-through
window on the screen: the program was running and drawing, but none of it
reached the display. The program now finds the right display connection by
itself, and if it ever ends up on the older connection that cannot show its
picture, it switches to a slower drawing mode that does show, and says why.
