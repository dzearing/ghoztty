# T1685 - A pane died mid-run with no panic text while ctrl+right-click link selections were copied back to back

## In plain terms

A terminal window disappeared on its own. There was no error, no crash box,
nothing written anywhere that says why - the process was simply gone. It
happened while the same gesture (ctrl+right-click on a link, then copy) was
being repeated quickly, about a dozen times in a row.

## Summary

Seen on 2026-09-20 in the first run of `test\win32\terminal-link-paths.ps1`
after T916 changed its fill, and NOT reproduced by the two runs after it (one
plain, one `-NegativeControl`), so it is a real observation rather than a
reliable repro.

What the harness recorded:

```
GUI POSTMORTEM ghoztty.exe pid 18912
  verdict : CRASHED - 0xFFFFFFFF unnamed NTSTATUS
  WER     : no Application Error record found for it
  dump    : none (WER LocalDumps is not armed on this box)
  stderr  : the file ends on a complete line, so it died between writes
    | debug(surface): key event binding flags=... action={ .{ .copy_to_clipboard = .mixed } }
    | debug(io_thread): mailbox message=write_small
```

The app died between the fourth and fifth probe of section 0's walk - a
ctrl+right-press that runs `linkAtPos` -> `setSelection`, a `WM_CANCELMODE` to
close the context menu, then a `copy_to_clipboard` binding, repeated as fast
as the harness posts them. `0xFFFFFFFF` is not a structured exception code and
no panic line was written, which is what makes it worth a card: a Zig panic
aborts with `0xC0000409` and prints, so whatever ended this process did
neither.

T916 did not introduce the gesture, only its density: before that change most
probes landed on a blank or prompt row and only some of the twelve reached the
link path. That is a plausible reason this surfaced now, and also the reason
the script is now a better place to catch it again.

## Where to look

- `src/apprt/win32/Surface.zig` - the right-press path (`linkAtPos`,
  `setSelection`) and the clipboard binding.
- Whether `WM_CANCELMODE` arriving while the context menu's modal loop owns
  the GUI thread can unwind through something that is still borrowed.
- Arm WER LocalDumps (`docs/claude/build.md`) before hunting, or run under
  `scripts\crash-catch.ps1`, which catches first-chance with all-thread stacks.

## Validation criteria

- [ ] The death is reproduced deliberately (a loop of ctrl+right-click +
      copy over a screen of links) or the search is recorded as exhausted
      with what was ruled out
- [ ] If reproduced: the cause is named from a stack, not inferred
- [ ] Whatever ends the process writes SOMETHING first - a panic line or a
      logged reason - so the next occurrence is diagnosable
- [ ] `test\win32\terminal-link-paths.ps1` stays ALL PASS
