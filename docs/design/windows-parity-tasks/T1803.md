# T1803 - Viewer pane keybinding fallback from the core action classification

## Summary

Mac commit 1d513083a (merged 8adc45de4, 2026-10-03). From a focused viewer,
only chords that were also menu key equivalents used to work. Now a chord
that nothing in the pane claimed is forwarded; the page, text fields and the
composer get first claim. The shared core classifies every action
exhaustively (`Action.requires`: app/window/pane/terminal, in
`src/input/Binding.zig`), and terminal actions are never forwarded. Dispatch
goes to the menu item for the action, or else to
`ghostty_app_key_binding_perform` (`src/App.zig`, `src/apprt/embedded.zig`),
which never sends a key to a terminal. Text fields keep typing and text
navigation. Cmd-C in an image pane copies the image.

Windows today: `src/apprt/win32/viewer_accel.zig` `forwardsTag` is a
hand-kept allowlist, consulted from WebView2's `AcceleratorKeyPressed`, which
fires before the page sees the key. Translation: once T1796 brings in
`Action.requires`, replace the allowlist with "forward anything that does not
require a terminal". Keep the comptime check that
`Window.performViewerBindingAction` handles every forwarded tag, and keep the
page's first claim on chords it uses (Ctrl+C/V/A/F/Z in an editable field).
Add Ctrl+C copying the image in an image viewer pane if that is not already
there.

## In plain terms

When you click into a markdown, web or diff pane, most of Ghoztty's keyboard
shortcuts kept working only if somebody had remembered to put them on a
list; a shortcut you set up yourself, or one nobody listed, did nothing. Now
every shortcut that does not need a terminal works from those panes too,
while the page keeps its own copy, paste, select-all and undo keys.

## Validation criteria

- [x] `viewer_accel` decisions are derived from `Action.requires`
      (`viewer_accel.route`), with unit tests asserting that no
      terminal-class action is ever routed (exhaustive over the action space,
      with/without a host terminal, performable or not), that every app/window
      action the core can perform is routed, and that every native tag is a
      non-terminal action. The comptime check that
      `Window.performViewerBindingAction` handles exactly `nativeTag` is kept.
      Verified: `floor-lane.ps1 -Lane all` (none + win32 lanes).
- [x] From a focused viewer, a CUSTOM binding to a window action the old list
      never named acts: `viewer-window-chords.ps1` S3
      (`ctrl+shift+f9=toggle_background_opacity` turns the translucent window
      opaque and back, and the page never sees the F9). Ctrl+1..9, tab
      navigation and rearrange mode were already native and stay so (S1/S2 and
      the controls still pass; rearrange-mode-action and tab-overview-action
      re-run).
- [x] The page keeps its own editing chords: S4 binds `ctrl+a` to
      `toggle_maximize`; from a focused viewer the window stays restored and
      the page logs the ctrl+a. Address-bar typing is a native EDIT, not on
      this path (viewer-nav-pin / viewer-panes re-run).
- [ ] Ctrl+C in an image pane puts the image on the clipboard — split to
      T1872 (needs WIC decoding, not chord routing).
- [x] The tests post keys to the background test desktop and take no
      foreground (the harness's foreground watcher asserts it).
      `-NegativeControl` fails 6 inverted arms, S3 and S4 included.
