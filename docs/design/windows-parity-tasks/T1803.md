# T1803 - Viewer pane keybinding fallback from the core action classification

## Summary

Mac commit 1d513083a (merged 8adc45de4, 2026-10-03). From a focused viewer,
only chords that were also menu key equivalents used to work. Now a chord
that nothing in the pane claimed is forwarded; the page, text fields and the
composer get first claim. The shared core classifies every action
exhaustively (`Action.requires`: app/window/pane/terminal, in
`src/input/Binding.zig`), and terminal actions are never forwarded. Dispatch
goes to the menu item for the action, or else to
`ghostty_app_key_binding_perform` (`src/App.zig`, `src/apprt/embedded.zig`),
which never sends a key to a terminal. Text fields keep typing and text
navigation. Cmd-C in an image pane copies the image.

Windows today: `src/apprt/win32/viewer_accel.zig` `forwardsTag` is a
hand-kept allowlist, consulted from WebView2's `AcceleratorKeyPressed`, which
fires before the page sees the key. Translation: once T1796 brings in
`Action.requires`, replace the allowlist with "forward anything that does not
require a terminal". Keep the comptime check that
`Window.performViewerBindingAction` handles every forwarded tag, and keep the
page's first claim on chords it uses (Ctrl+C/V/A/F/Z in an editable field).
Add Ctrl+C copying the image in an image viewer pane if that is not already
there.

## Validation criteria

- [ ] After T1796: `viewer_accel` decisions are derived from
      `Action.requires`, with a unit test asserting that no terminal-class
      action is forwarded and that every forwarded tag is dispatched.
- [ ] From a focused viewer, Ctrl+1..9 (goto_tab), tab navigation,
      rearrange mode and a CUSTOM user binding all act, and typing in the
      address bar and the composer is unaffected.
- [ ] Ctrl+C in an image pane puts the image on the clipboard.
- [ ] The tests post keys to the background test desktop and take no
      foreground.
