# T1141 - A synthetic click on any window's drag band can freeze the next click in an acceptance script

## Summary

Harness-wide, not menu-bar's: Send-TestMouse routes a click the way Windows does, so a point the app hit-tests as HTCAPTION is posted as WM_NCLBUTTONDOWN, and DefWindowProc answers that with its modal SC_MOVE loop. That loop pumps its own messages and eats whatever is queued behind it; a real user ends it by lifting a real button, but a POSTED WM_NCLBUTTONUP does not reliably do so. Any of the 141 scripts that clicks a caption, a drag band, or a resize edge and then clicks something else can lose the second click - and the losing script usually reports the CONSEQUENCE (nothing happened, wrong state) rather than the lost click, which is exactly how T1110 filed a menu-state defect against a menu that was correct. T1110 cleared it locally with WM_CANCELMODE in menu-bar.ps1; the general fix belongs in Send-TestMouse's click path, where the hit code is already known: after an action=click whose hit code induces a modal loop (HTCAPTION and the sizing codes, never HTSYSMENU or the min/max/close buttons), cancel the mode before returning. Guard against breaking a deliberate caption DRAG, which is a separate down/move/up sequence and must keep its loop.

## In plain terms

Nothing a user of the terminal can see. This is about the automated checks: when
one of them clicks the part of the window title area you would grab to drag the
window, Windows puts the app into "I am being dragged" mode, and the very next
thing the check clicks can be thrown away. The check then reports whatever it
found afterwards as a bug in the app, when the app never got the click at all.

## What was actually going on (measured 2026-10-22)

The summary's mechanism was half right. Measured with GUITHREADINFO's
`GUI_INMOVESIZE` bit (new `Test-TestInMoveSize`):

- A posted caption down starts DefWindowProc's move loop ONLY when the app's
  key state says the left button is held. Posted messages never set that bit,
  so on a clean key state the loop never starts - which is why T1110 could not
  reproduce its lost click on an idle box (0/10).
- With the bit set (a stale one; `GHOZTTY_TEST_MOUSE_STALE_LBUTTON=1`
  constructs it), the loop starts on every caption down, about one double-click
  interval AFTER it (433ms on a 500ms setting), and the posted up does NOT end
  it. The next click is then eaten - the negative control lost the maximize
  click behind half of its drag-band clicks.
- The loop does not begin while the harness thread's input is still attached
  to the app's, so a watch inside the attach never sees it.

The fix (`lib\TestDesktop.ps1`): a whole click or doubleclick clears any stale
held mouse-button bit before posting, so the loop cannot start; if the bit is
still held, `EndModalLoop` watches - after the detach, for a double-click
interval plus 500ms - and SENDS `WM_CANCELMODE` to the hwnd GUITHREADINFO names
as moving, only while the loop is running (a blind cancel would release the
app's own hover capture). A bare `-Action down` is untouched.
`GHOZTTY_TEST_MOUSE_KEEP_MODAL=1` restores the old click.

## Where

- `test/win32/lib/TestDesktop.ps1` - `MouseEvent`, the `action == click` path
- every script that clicks a caption, a drag band or a resize edge and then
  clicks something else
