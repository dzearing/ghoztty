# T2049 - An enrolled Windows machine keeps hosting while the app is signed in to a DIFFERENT account; an enrolled Mac stops (main 6dfb31232's owner != signed-in rule)

## Summary

Mac's MachineHostingVerdict stops the relay agent when relay.env's credential (whoami) belongs to another account than the one signed in: the app is a guest and it is not its enrollment to serve. On Windows the uplink rides the session agent, which never learns the signed-in account, so sharing.decide hosts on credential alone. Bring the rule across: the app (which knows the account and can ask /v1/agent/whoami) should write the verdict the agent acts on, e.g. an owner-mismatch veto file beside relay.env in the shape of pending-revoke.json, with 'relay unreachable = no change' and 'nobody signed in = leave as is' preserved. Acceptance: agent-sharing-uplink.ps1 gains a mismatch section; unit-test the pure verdict.

## In plain terms

If someone signs in to Ghoztty on your Windows PC with their own account, but
the PC was set up for sharing under YOUR account, the PC kept serving your
account: your other devices could still reach it while someone else was using
it. A Mac in the same spot stops sharing. After this lands the Windows PC
stops too, its "Share this machine" box reads unticked, and it picks sharing
back up as soon as you sign in again.

## Goals

- [x] The app decides "this PC's sharing credential belongs to another account" and tells the background agent
- [x] The agent stops sharing while that holds, and resumes once it no longer does
- [x] An unreachable relay or nobody signed in changes nothing (Mac's rule)
- [x] The Share this machine box reads unticked while the PC is not this account's to share
