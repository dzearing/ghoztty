# T1573 - zig's -Dtest-filter does not match the test name the runner prints, and nobody knows its real rule

## In plain terms

There is a shortcut for running one test instead of all of them, and the obvious
way to use it — copy the test's name out of the failure message — quietly selects
nothing at all for some files. Nothing breaks: the build now says so out loud
instead of pretending everything is fine. But whoever reaches for the shortcut
still has to guess what to type, and a shortcut you have to guess at is one
people stop using.

## Summary

Measured under T733 on zig 0.15.2, win32 lane, using the name dump T733 added
(`GHOZTTY_TEST_FILTER_DUMP=1`, which prints every test the built binaries
actually contain):

| `-Dtest-filter=` | named tests compiled in |
|---|---|
| `translate_policy` | 10 (the 9 in `src\apprt\win32\translate_policy.zig`, plus the App.zig test whose *title* contains the word) |
| `.translate_policy` | 10 |
| `win32.translate_policy` | 0 |
| `translate_policy.test` | 0 |
| `T64:` | 0 |
| `VK_PACKET` | 0 |
| `apprt.win32.translate_policy.test.T64: VK_PACKET is translated even on a terminal surface` | 0 |
| `viewer_bridge`, `win32.viewer_bridge`, `viewer_bridge.test`, `T641: the blob`, `the blob does NOT hide` | all match |

So for `viewer_bridge.zig` the documented rule holds exactly — a filter is a
substring of the fully-qualified name. For `translate_policy.zig` only a bare
`translate_policy` works, and every longer substring of the SAME printed name
selects nothing. Both files sit in `src\apprt\win32\`; the printed names have
identical shape (`apprt.win32.<file>.test.<title>`). The difference is not
explained.

One candidate worth testing first: `src\apprt\win32.zig`'s `test { _ = @import(…) }`
aggregator, whose own comments say "THIS LIST is what pulls a file's tests into
the lane". `viewer_bridge.zig` is reachable through that list; `translate_policy.zig`
is not — it is imported as a file-scope `const` by `App.zig` and `Surface.zig`.
That would make the observed behaviour "a file reached only by an ordinary import
contributes its tests only when the filter names the file", which is testable by
adding one line to the aggregator and re-running the table above.

## Details

Why it matters even though nothing is silently green any more: T631's guard
turns a bad filter into a fast, loud failure, so the cost is a wasted minute
rather than a false certification (T733 verified that on this exact case). What
is left is usability — the cheap way to prove a new test runs is
`-Dtest-filter=<something>`, and "copy the name from the failure" is what
everyone will try first. Knowing the rule also decides whether this is ours to
fix (our build wiring / the aggregator list) or a zig issue to report upstream
to ziglang, which is a different remote from either of ours.

Landmarks: `src\build\TestFilterGuard.zig` (the guard and the dump),
`test\win32\test-filter-guard.ps1` section F (the invariant),
`docs\claude\testing.md` (the empirical rule as it stands).

## Validation criteria

- [ ] The rule is stated from evidence: given a test and a filter, what the
      compiler keeps, verified against at least three files with different
      import shapes (aggregator-listed, file-scope import only, root-adjacent).
- [ ] The aggregator hypothesis is settled one way or the other — add
      `translate_policy.zig` to `src\apprt\win32.zig`'s test block and re-measure
      the table above.
- [ ] Whichever it turns out to be: either our wiring is fixed so a printed name
      is a usable filter, or the limitation is recorded as zig's with a version
      and a link, in `docs\claude\testing.md`.
- [ ] `test\win32\test-filter-guard.ps1` section F still holds, and says which
      world we are in.
