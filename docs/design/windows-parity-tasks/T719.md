# T719 - Four acceptance launch sites never declared their session persistence

## Summary

T158's rule is that **every launch in an acceptance script states what it wants
session persistence to do** — by passing the flag, by passing something built
from it, or by a `# persistence: <reason>` marker where neither fits. Four sites
state nothing. Measured 2026-08-10 while validating T179:

```
. test\win32\lib\PersistenceSweep.ps1
Get-GhozttyLaunchSites -Root test\win32 | Where-Object { -not $_.Declared }
```

- `test\win32\url-scheme.ps1:359`, `:368`, `:381` — the three section-E
  activations (`ghoztty-debug://open/urlwin`). These are the forward-and-exit
  second-instance case the marker was invented for, so the fix is a marker, not
  a flag.
- `test\win32\agent-attach-refused.ps1:276` — section C's control launch, which
  restores a manifest and therefore genuinely WANTS persistence on. The fixture
  is correct; what is missing is it saying so.

Nothing is currently mis-behaving because of this — each site happens to want
what it gets. The defect is that a reader (and the sweep) cannot tell these
apart from a launch that never considered the question, which is exactly the
distinction T158 exists to preserve. Persistence is on by default, so an
undeclared launch is one edit away from restoring somebody else's panes into
its own setup assertions (T131, then T155, both of which read as product
regressions in whatever change was in flight).

Fix: declare all four. Then decide whether the sweep should be enforced by
`persistence-flag.ps1` rather than merely available — a lint nobody runs is how
four sites drifted.

## In plain terms

Our automated tests each have to say whether they want the terminal to reopen
the windows from the last run. Four of them never say. They currently get lucky,
but the next person editing one has no way to know which answer was intended,
and getting it wrong makes a healthy build look broken.

## Validation criteria

- [x] Each of the four is declared with the form that matches its intent — a

      changes behavior.
- [x] `test\win32\url-scheme.ps1` and `test\win32\agent-attach-refused.ps1`

      re-validating).
- [x] Decide and record whether the sweep becomes a hard gate in
      `test\win32\persistence-flag.ps1`; if yes, that script fails on a
      non-empty undeclared list.

## Resolution (2026-09-14) - already fixed, verified here

All four sites were declared by **87c762ec1** (T744, 2026-08-12), two days
after this card was filed, and nobody closed it. The
`agent-attach-refused.ps1:276` marker came in **d545a15ca** (2026-08-10); the
three `url-scheme.ps1` section-E activations carry
`# persistence: n/a - a URL activation ...` today (the surrounding block moved
with b30d814f6, but the declaration itself is T744's).

The open question at the end of the Summary is answered too, and the answer is
YES: the sweep is a **hard gate**, not a lint nobody runs.
`test\win32\persistence-flag.ps1` section A (landed 854c10cb6) asserts
`undeclared.Count -eq 0` over the whole suite, and `scripts\guard-due.ps1`
carries the `persistence-flag` row (319 covered files) - so touching any
acceptance script makes that harness DUE, and step 6's `validate` fails until it
has been run green. The drift this card described cannot recur silently.

Verified on the box 2026-09-14 against the `zig-out` Debug build:
