# T1973 - Escaping a job by breakaway only reaches the OUTER job when jobs are nested, so an installer-relaunched app, its agent and every session stay inside a kill-on-close job

## Summary

job_spawn.spawnEscapedOnly took an accepted CREATE_BREAKAWAY_FROM_JOB as an escape. With nested jobs Windows moves the child only out of the jobs that allow breakaway and into the first that does not (measured 2026-10-15). Both installer relaunches on MAXIMUSHOME (2026-10-14 23:31 and 2026-10-15 02:57) logged 'respawned ... (breakaway)' then 'STILL inside a kill-on-close job'. The agent, its PTY holders and the agent handoff spawn through the same tier, so an agent started by such an app dies with that job and takes every session with it. Split out of T1970.

## In plain terms

When the installer restarts Ghoztty, Windows can start the new copy inside a
container that kills everything in it when it closes. Ghoztty tries to step
out of that container, but in one common shape it only steps into the next
container out, which kills just the same. Anything it then starts, including
the background process that keeps your terminals alive, is stuck in there
too. When that container closes, every session goes with it. Ghoztty now
checks where it actually landed, and takes the route that really gets out.

## Goals

- [x] An accepted breakaway that leaves the child in a job (from a caller in a
      job) is no longer counted as an escape; the shell-parent and
      jobless-donor hops are tried, and the breakaway child is kept only when
      neither works, labelled `breakaway, OUTER JOB (degraded)`.
- [x] The same check covers every caller: the startup escape, the local agent
      spawn, the agent's PTY holders, the agent handoff, the relaunch guard
      and the update applier.
- [x] An acceptance section that reproduces the field's nested shape, and goes
      red on the old code.

## Root cause

Measured on this box (scratchpad experiment, 2026-10-15): a process in
`[kill-on-close 0x2000] > [breakaway-ok 0x800]` calling CreateProcess with
`CREATE_BREAKAWAY_FROM_JOB` succeeds, and the child is in the 0x2000 job and
not the 0x800 one. With an outer job that also allows breakaway (0x2800) the
child leaves both. Breakaway leaves only the contiguous run of jobs that
allow it, counting from the innermost.

The user's own log shows the shape: both installer relaunches
(2026-10-14 23:31, 2026-10-15 02:57) logged `this process is inside a
kill-on-close job it does not own (flags 0x800 breakaway_ok); respawning`,
then `respawned as pid N (breakaway)`, then from the twin `STILL inside a
kill-on-close job after the respawn (flags 0x2000 kill_on_close); running
jailed`. The live app (pid 32836) reads `IsProcessInJob = true` while
Explorer and the agent read false. On this box the agent predates the app
(started by the Run key at logon), so the sessions survived. On a machine
where the jailed app is the one that spawns the agent, the agent and all its
holders land in that kill-on-close job and die when it closes.

## Fix

`src/apprt/win32/job_spawn.zig`: tier 1 now creates the child SUSPENDED and
asks `IsProcessInJob` of it. `breakawayVerdict` (pure, unit-tested) answers
`try_parent_hop` when the caller was in a job and the child still is. The
suspended child is held in reserve: a successful parent hop terminates it
before it ran an instruction, and if both hops fail it is resumed and
returned as the new `Tier.breakaway_outer`, whose `escaped()` is false, so
the agent spawn and holder spawn log it as jailed.

      "kill-on-close" job it built was flagless, because

      that bug (it assumed the flags query reads the FIRST job joined; it
      reads the innermost) and is corrected. The same defect in two other
      harnesses is T1974.
