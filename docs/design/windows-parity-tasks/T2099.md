# T2099 - Ticking Share this machine while signed in to a different account than the one that enrolled the PC does nothing visible: the box reads unticked again because the owner veto still holds

## Summary

Follow-up to T2049. With owner-mismatch.json naming relay.env's token, ShareMachineRow.isEnabled reads unticked, and a tick only writes sharing.json, so the box springs back. Check what the Mac does when a guest account turns hosting on for a machine another account enrolled (re-enroll as the signed-in account, or refuse with an explanation), and do the same: either re-enroll (new token, which makes the veto inert by construction) or show why the box cannot be ticked. Acceptance: a GUI-free harness section over the row's decision plus a unit test.

## In plain terms

If you sign in to Ghoztty on a PC that somebody else set up for sharing under
their account, the "Share this machine" box is unticked, and clicking it did
nothing you could see: the tick sprang straight back. Now the click is refused
with a sentence that says whose account shares the PC and that signing in as
them is how to change it.

## Goals

- [x] Find what the Mac does for a guest on another account's machine
- [x] A click on that box is refused instead of silently springing back
- [x] The footer names the owning account and the way to change it
- [x] A re-enrolled machine (stale veto) still ticks as usual

## Decision taken

Mac has no Share this machine box at all: enrollment is the only opt-in, a
guest's app stops the relay agent (`MachineHostingVerdict.decide` → `.stop`),
and nothing on the Mac lets a guest take over another account's enrollment.
So Windows refuses rather than re-enrolling as the signed-in account (which
would silently cut the owner's other devices off this PC). Filed for the
user as a decision, since the two options feel different.

## Validation criteria

- [x] Pure decision unit-tested: `ShareMachineRow.enablePlan` (veto → refuse, never write), `notOursHint` (names owner, nameless fallback, no mechanism words), `owner_veto.ownerAt` (owner exactly when the veto holds, null for a corrupt record). floor-lane `none`/`win32` lanes.
- [x] On the real app, a click on another account's enrollment writes no sharing.json, keeps the box unticked and the credential intact, and the footer names the owner and says "Sign in as": `share-machine.ps1` section J (ALL PASS 63 via acceptance-parallel).
- [x] Negative control: the same click with the veto naming a different credential enables sharing with the ordinary sentence (section J).
- [x] No regression in sections A-I of the same harness (same run).
