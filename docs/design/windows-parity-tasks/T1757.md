# T1757 - Resizing a cmd.exe pane while a command is printing may blank that command's earlier output (cmd integration sends 133;A/B but never 133;C, so output is treated as prompt input)

## Summary

Found while fixing T1698. cmd.exe shell integration (T512, src/termio/shell_integration.zig setupCmd) marks prompts with OSC 133;A/133;B only - PROMPT cannot express 133;C/D. Ghostty's Screen.resize, when shell_redraws_prompt is on (default) and cursor.semantic_content != output, clears every row from the start of the current prompt block down so the shell can redraw it. In a cmd pane the cursor is 'input' from 133;B until the NEXT prompt, so every line a running command prints is part of the prompt block: a resize mid-command (drag a divider, un-zoom, maximize while a build scrolls) should blank that command's output above the viewport too, since conhost only repaints its visible rows. ? INFERRED from reading Screen.zig resize + the setupCmd comment; T1698 proved the mechanism for a REPLAYED prompt only. Reproduce first: cmd pane, run a command that prints 100+ lines, resize the pane narrower, check scrollback. Candidate fixes: have the win32 cmd integration mark output (e.g. doskey macro or a 133;C on Enter from the input side), or set 133;A's redraw=0 for cmd (cmd does not redraw prompts, so clearing is never right for it). Mac seat: cmd.exe only runs on Windows agents, but a Mac window can host a remote cmd pane - the fix must live in the shared core or the integration, not win32 apprt.

## In plain terms

In a Command Prompt pane, if you resized the pane while a command was still
running - dragged a divider, opened a split, maximized the window - everything
that command had already printed could vanish, leaving blank space where a
build log used to be. Ghoztty was treating the running command's output as if
it were the text you were typing at the prompt, and cleared it for the shell to
redraw, which Command Prompt never does. Now the output stays put.

## Root cause

Confirmed, not just inferred: the on-box negative control reproduces the loss.
cmd's integration (T512) is carried entirely by `PROMPT`, which can mark where a
prompt starts and where typing starts but has no hook for "a command started".
It ended in OSC 133;B - "input starts here, until the next mark" - and the next
mark was the NEXT prompt, so for a command's whole run the terminal was still
"reading input". A resize in that state clears the prompt region from the prompt
down so the shell can redraw it (`Screen.resize` with `shell_redraws_prompt`),
and conhost only repaints what is on screen, so the output above was gone.

The fix is one mark: the prompt now ends in OSC 133;I - "input starts here and
ends with this line", which the core already implements (`clear_eol`). cmd's
input is one logical line (a soft wrap keeps it input), so the newline the Enter
echoes is exactly where output begins. It lives in the shared integration
(`src/termio/shell_integration.zig`), so a Mac window hosting a remote cmd pane
gets it too; nothing Swift-side. Decided against `redraw=0` on 133;A: it would
also stop the prompt line being cleared on a resize at an idle prompt, where the
clear is right (conhost repaints it), and it would leave the process-table-free
"is a command running" signal (`cursorIsAtPrompt`) wrong for the whole run.
