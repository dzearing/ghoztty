# T1479 - Posted-mouse acceptance scripts may aim at the caption instead of the client area

## In plain terms

Some of the automated UI tests click at a spot worked out from the wrong
rectangle, so the click lands on the title bar instead of inside the window.
The test then goes green having driven nothing at all. Nobody sees a bug
because of this directly — but a check that cannot fail is a check that will
not catch the next regression it was written for.

## Goals

- [ ] Every script that posts mouse input is checked for the trap
- [ ] Each one that drives a gesture asserts the gesture actually happened
- [ ] The idiom is written down once so the next script does not re-invent it

## Summary

Found while fixing T1476. `test/win32/resize-flicker.ps1` section C1 computed
its divider-drag coordinates as `pane.Right - windowRect.Left`, i.e. it treated
the WINDOW rect's origin as the client origin. On a window with a caption and a
border those differ, so the button-down landed above the client area, the
divider was never grabbed, and ten motion ticks then asserted that two panes
which had not moved still tiled. It had been passing that way since it was
written, and it only surfaced because T1476 wanted the drag's summary line and
the app had printed none.

`drag-perf.ps1` records falling into and solving the same trap (T1343): it hands
SCREEN coordinates to `Send-TestMouse`, which does the client conversion per
target, and it asserts the panes actually resized before it believes the sample.

Other scripts that post mouse messages and do rect arithmetic of their own, and
should each be checked against that idiom: `banner-resize-repaint.ps1`,
`focus-defer.ps1`, `mouse-nc-routing.ps1`, `split-dim-viewer.ps1`. Checking is
not the deliverable — the deliverable is that each gesture-driving script has a
positive control saying the gesture landed, the way C1 now does
(`the posted drag actually grabbed the divider`).

`mouse-nc-routing.ps1` is deliberately about non-client hit testing, so window
coordinates there may well be correct; read before changing.

## Validation criteria

- [ ] Each named script either uses `Send-TestMouse` with screen coordinates or
      justifies its own arithmetic in a comment
- [ ] Each gesture-driving script asserts an observable change caused by the
      gesture, so a miss fails instead of passing vacuously
- [ ] Every touched script still passes, and its negative control still fails
