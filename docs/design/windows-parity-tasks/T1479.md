# T1479 - Posted-mouse acceptance scripts may aim at the caption instead of the client area

## In plain terms

Some of the automated UI tests click at a spot worked out from the wrong
rectangle, so the click lands on the title bar instead of inside the window.
The test then goes green having driven nothing at all. Nobody sees a bug
because of this directly — but a check that cannot fail is a check that will
not catch the next regression it was written for.

## Goals

- [x] Every script that posts mouse input is checked for the trap
- [x] Each one that drives a gesture asserts the gesture actually happened
- [x] The idiom is written down once so the next script does not re-invent it

## Summary

Found while fixing T1476. `test/win32/resize-flicker.ps1` section C1 computed
its divider-drag coordinates as `pane.Right - windowRect.Left`, i.e. it treated
the WINDOW rect's origin as the client origin. On a window with a caption and a
border those differ, so the button-down landed above the client area, the
divider was never grabbed, and ten motion ticks then asserted that two panes
which had not moved still tiled. It had been passing that way since it was
written, and it only surfaced because T1476 wanted the drag's summary line and
the app had printed none.

`drag-perf.ps1` records falling into and solving the same trap (T1343): it hands
SCREEN coordinates to `Send-TestMouse`, which does the client conversion per
target, and it asserts the panes actually resized before it believes the sample.

Other scripts that post mouse messages and do rect arithmetic of their own, and
should each be checked against that idiom: `banner-resize-repaint.ps1`,
`focus-defer.ps1`, `mouse-nc-routing.ps1`, `split-dim-viewer.ps1`. Checking is
not the deliverable — the deliverable is that each gesture-driving script has a
positive control saying the gesture landed, the way C1 now does
(`the posted drag actually grabbed the divider`).

`mouse-nc-routing.ps1` is deliberately about non-client hit testing, so window
coordinates there may well be correct; read before changing.

## Validation criteria

- [x] Each named script either uses `Send-TestMouse` with screen coordinates or
      justifies its own arithmetic in a comment — banner-resize-repaint B1
      rewritten to `Send-TestMouse` (read); focus-defer, split-dim-viewer and
      mouse-nc-routing already aim in screen space from `Get-TestWindowRect`
      (read; mouse-nc-routing's window-rect offsets ARE screen points, which is
      what `Send-TestMouse` takes)
- [x] Each gesture-driving script asserts an observable change caused by the
      gesture, so a miss fails instead of passing vacuously — banner-resize-repaint
      gains `the posted shrink/grow drag actually moved the divider` (>=100 px);
      focus-defer asserts focus lands on each clicked pane, split-dim-viewer that
      the dim overlay moves/clears, mouse-nc-routing that the window minimises
- [x] Every touched script still passes, and its negative control still fails —
      banner-resize-repaint ALL PASS 17 (twice, via acceptance-parallel);
      `-NegativeControl` 2 FAILURE(S) as designed; a mutation restoring a
      mis-aimed press made the new positive control FAIL (`moved ... by up to 0
      px`) while the tiling assertion PASSED over the unmoved panes - the exact
      vacuous pass this task is about

## Details

**The defect.** `banner-resize-repaint.ps1` B1 posted its divider drag as raw
`WM_LBUTTONDOWN/MOUSEMOVE/UP` with `x = owner.Left - window.Left`: the window
origin used as the client origin (off by the frame), AND aimed at the banner
owner pane's LEFT edge, which is the window's own edge whenever the banner sits
on the left pane. Its tiling assertion then checked a pane that had not moved.

**Also found: the script was red at its first assertion** (`banner overlay
window exists`) since T2514 made the composition present the default - the
popup it measures stays hidden there. Pinned `GHOZTTY_COMP_PRESENT=0`, the same
T2747 pin `pane-banner.ps1` carries (the popup is still the shipped fallback
path); comp-present.ps1 covers the composition card.

**Sweep beyond the four named scripts.** Twelve more scripts post raw mouse
messages (activity-help-tooltips, activity-truncated, chooser-help-tooltips,
chooser-kill-hover, chooser-link-hover, chooser-resume, chooser-session-cpu,
caption-bar, context-menu-real-input, pane-sidebar-glide, viewer-diff-tree,
resize-flicker): every one aims in CLIENT space derived from
`Get-TestWindowRect -Client` or the app's own client-space geometry log, which
is correct for a raw post. `drag-perf.ps1` and `resize-flicker.ps1` still define
an unused `New-LParam` helper; left alone (removing it would re-arm two
expensive exclusive guards for no behaviour change).

**The idiom** is a new paragraph in `docs/claude/testing.md` beside T1032's
screen-coordinate rule: "A posted gesture proves it landed".
