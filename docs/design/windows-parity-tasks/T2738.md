# T2738 - Switching back to a background tab the window resized under still ends on an old-size frame in 2 of 5 resize-flicker runs: the tabswitch pass reads waits=1 timeouts=1 stale=2..4 of 4 panes under the 8 ms present lag (T2046's guarantee, red again)

## Summary

resize-flicker.ps1 plain, 2026-11-06, 5 runs after T2506 (build at 849a3b176 + T2506): runs 1 and 3 FAIL 'a switch back to a resized tab ends on a frame at the new size' with panes=4 waits=1 timeouts=1 stale=2 and stale=4; runs 2,4,5 pass. The tabswitch pass's single batch wait runs out its one-frame budget with some panes still at the pre-resize size. T2046 fixed the inline draw on .visible in src/renderer/Thread.zig; something since (or box load against a 16 ms budget with an 8 ms lag) brings it back. Check first whether it is a regression (bisect over the renderer/Surface/Window commits since T2046) or a budget race, and whether timeouts=1 always pairs with stale>0. Validation: 5 consecutive resize-flicker.ps1 runs ALL PASS.

## In plain terms

With several panes in a tab, if you resize the window while looking at a
different tab and then switch back, the panes could briefly show at their old
size before snapping to the new one - a visible flash. The app waits for each
pane to draw at its new size before showing the tab, but it only waited one
frame, and switching to a tab that has been sitting idle sometimes takes a bit
longer than that. It now waits up to three frames for a tab switch (a moving
drag still waits just one), so the tab appears already at its new size.

## Goals

- [x] Measure the tab-switch wait (it was a budget race, not a regression)
- [x] Give a tab switch a discrete-relayout wait budget instead of a drag tick's
- [x] resize-flicker.ps1 green 5 runs in a row

## Validation criteria

- [x] Root cause measured, not guessed: the `window resize` line now carries `wait_us=` and `budget_ms=`, and a stale pane logs `frame wait stale pane awaited= presented= spent_us=`. Before the fix (16 ms budget, 8 ms present lag) the 4-pane tabswitch wait ran 1.5-17.5 ms across 5 runs (one at 17458 us, past budget, answered on its last look); every timed-out batch is stale by construction, so `timeouts=1 stale>0` always pair.
- [x] Fix: `drag_perf.discrete_wait_ms` (48 ms = 3 frames) used by `showTabIndex`'s pass via `Window.frame_wait_budget_ms`; motion passes keep 16 ms. Unit test "a discrete relayout's wait outlasts a full present lag plus a frame (T2738)" in drag_perf.zig.
- [x] resize-flicker.ps1, 5 consecutive runs after the fix: ALL PASS (27 assertions) x5, tabswitch `budget_ms=48 stale=0 timeouts=0`, waits 0.2-11.3 ms.
