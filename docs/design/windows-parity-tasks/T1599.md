# T1599 - kb-actions.ps1 is red on box: ctrl+k fires clear_screen but the primary screen still holds the fill marker

## Summary

Found by T782 while re-running the scripts it touched. test\win32\kb-actions.ps1 fails 'T47 primary screen cleared': the ctrl+k keybind IS delivered (the io message 'mailbox message=clear_screen' is in the app log, and the alt-screen fall-through case passes), but the +read that follows still finds KBFILL_MARKER on the primary screen. Reproduced twice against the working tree and once against the PRISTINE HEAD copy of the script, so it is not T782's edit - it is a live red nobody was running. Either the clear is not reaching the screen or the read races it; the next turn should tell those apart before assuming the product is wrong. Related: this script has NO guard row, which is why the red could sit here unseen.

## In plain terms

Pressing ctrl+k in a Ghoztty pane really does clear the screen and the
scrollback - the terminal was fine the whole time. What was broken is the
automated check that watches this behavior: it looked for a marker word it had
just printed on the very last line, and that is the one line the terminal
deliberately keeps when you clear at a prompt (so you can scroll back one screen
and see what you just wiped). The check called that a failure and had been red
for a while, with nothing in the loop obliged to run it. Now the check prints
the marker first and buries it under a flood of output, so it proves both halves
of the clear - the history is gone and the screen is empty - and the script is
wired into the guard table so a future red cannot sit unseen.
