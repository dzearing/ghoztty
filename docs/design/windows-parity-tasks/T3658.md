# T3658 - Linux L14c: an AppImage of the GTK app, with WebKitGTK's helper processes relocated into the AppDir

## In plain terms

Linux Ghoztty could only be installed as a tarball or a Debian package, and
both need GTK 4, libadwaita and WebKit already on the machine. Now there is
also a single AppImage file that carries those libraries, so it runs on a
machine that has none of them, and viewer panes still work. The shells you
open in it see your normal environment, not the AppImage's internals.

## Goals

- [x] `scripts/linux/package-appimage.sh` turns a package tarball into an AppImage, with no network tool beyond a pinned runtime
- [x] WebKit's web and network processes come from the AppImage, with WebKit's own sandbox still on
- [x] it runs and renders viewers where the host's GTK 4 / libadwaita / WebKitGTK are hidden
- [x] a pane's shell gets back exactly the environment the launch had
- [x] the shared /tmp link it relies on can never be someone else's
- [x] follow-ups filed: URL opening env (T3797), agent outliving the mount (T3799), link re-check + multi-user (T3800), media (T3801)

## Summary

T3578 shipped the release tarball (scripts/linux/package.sh) and the .deb (scripts/linux/package-deb.sh), validated by test/linux/package-release.sh. Left: an AppImage built from the same tree. The hard part is WebKitGTK 6: libwebkitgtk-6.0 spawns WebKitWebProcess/WebKitNetworkProcess from a libexec path fixed at its build time (/usr/lib/x86_64-linux-gnu/webkitgtk-6.0), so a bundled copy must be relocated (WEBKIT_EXEC_PATH or a patched path) along with its injected bundle, GStreamer and gio modules; GTK4/libadwaita can come from linuxdeploy's gtk plugin. Validate by running the AppImage with the host's webkit packages hidden (a throwaway root or LD_LIBRARY_PATH-free env) and opening a viewer pane in the headless harness. appimagetool/linuxdeploy are not on the distro; setup-distro.sh would fetch pinned versions.
