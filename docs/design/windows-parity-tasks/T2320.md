# T2320 - Windows release MSI ProductVersion goes backwards within a day

## Summary

User report 2026-10-26: "i click install and restart. NOTHING HAPPENS". Part
one of the chain (T2321, T2322 are the others).

`.github/workflows/release-windows.yml` (~line 177) computes
`BUILD_NUM=$(( (github.run_number - 1) % 99 + 1 ))` and its comment calls it
"the same-day rebuild counter". It is not per-day: it is the workflow's global
run number wrapped at 99. ProductVersion is `yy.m.d<NN>`, so on 2026-10-25
win-v1.45.0 drew NN=99 (`26.10.2599`, registered in HKCU Uninstall) and
win-v1.45.1/2/3 drew 01..03 (`26.10.2501`..`2503`). Windows Installer saw each
as OLDER:

- Application log, MsiInstaller 10005 at 2026-10-25 20:36:11: "A newer version
  of Ghoztty is already installed, so this installer has nothing to add";
  1033 status 1603.
- ghoztty.log: `update apply: msiexec exited 1603; relaunching the build that
  was already here`.

A later day always sorts higher, so 10-26's win-v1.47.x installs again - the
defect bites only same-day releases after a wrap, which with on-demand
publishes (several a day) is now routine.

## In plain terms

When two Windows updates came out on the same day, the second one could carry
a lower internal version number than the first, so Windows refused to install
it and "Install update" quietly did nothing. After this, each update published
later in a day always carries a higher number, so it installs over the earlier
one. Anyone using the in-app updater notices.

## Goals

- [x] the within-day number rises with the time of publish, not a wrapped global counter
- [x] every date-derived field of one build reads one clock (no midnight split)
- [x] the ordering is tested, with a negative control showing the old formula fails it
- [ ] the next real same-day pair of releases installs over each other (T2326)

## Fix (landed)

`build-msi.sh --build-num clock` derives the number from the 2-minute slot of
the day (1..720), and the ProductVersion is now `yy.m.dNNN` (three digits,
zero-padded), so a day's builds sit in `d001..d720` and the last build of day
d sorts below the first of day d+1. Any two-digit-era release (`yy.m.dNN`,
at most `26.10.3199`) sorts below every new one dated 2026-10-26 or later, so
installed releases keep upgrading. One clock, `GHOZTTY_BUILD_EPOCH`, feeds
every date field; `build-release-artifacts.sh` pins it so its two
`build-msi.sh` calls agree. Chosen over counting today's releases through the
GitHub API (deletions and failed runs make a count non-monotonic, and it adds
a network dependency to packaging) and over 15-minute slots in two digits
(two publishes in one window would tie, which is the same refusal).

## Fix direction (as filed)

NN must be strictly increasing within a local date: e.g. count the win-v
releases already published with today's date (gh api) + 1, or derive from the
UTC time of day (minutes/15 fits two digits) - whatever is monotonic per day
and fits the 2-digit field. Also: a same-semver re-publish must still go up.

## Validation criteria

- [x] unit/acceptance over the version derivation: three same-day publishes
      yield strictly increasing ProductVersions, including across a
      run_number that is a multiple of 99 (positive control: the current
      formula fails that case) — section B1b of
      `test\win32\release-artifacts.ps1`, ALL PASS 2026-10-26; its negative
      control runs the same check over the old formula at run numbers 98..100
      (26.10.2598 26.10.2599 26.10.2501) and requires it to fail
- [ ] a real two-releases-in-one-day upgrade on the box installs the second

      Carried by T2326 (read back from the next real same-day publish pair)
- [x] the misleading "same-day rebuild counter" comment is corrected —
      release-windows.yml now says what the number is and why it changed
