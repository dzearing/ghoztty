# T2320 - Windows release MSI ProductVersion goes backwards within a day

## Summary

User report 2026-10-26: "i click install and restart. NOTHING HAPPENS". Part
one of the chain (T2321, T2322 are the others).

`.github/workflows/release-windows.yml` (~line 177) computes
`BUILD_NUM=$(( (github.run_number - 1) % 99 + 1 ))` and its comment calls it
"the same-day rebuild counter". It is not per-day: it is the workflow's global
run number wrapped at 99. ProductVersion is `yy.m.d<NN>`, so on 2026-10-25
win-v1.45.0 drew NN=99 (`26.10.2599`, registered in HKCU Uninstall) and
win-v1.45.1/2/3 drew 01..03 (`26.10.2501`..`2503`). Windows Installer saw each
as OLDER:

- Application log, MsiInstaller 10005 at 2026-10-25 20:36:11: "A newer version
  of Ghoztty is already installed, so this installer has nothing to add";
  1033 status 1603.
- ghoztty.log: `update apply: msiexec exited 1603; relaunching the build that
  was already here`.

A later day always sorts higher, so 10-26's win-v1.47.x installs again - the
defect bites only same-day releases after a wrap, which with on-demand
publishes (several a day) is now routine.

## Fix direction

NN must be strictly increasing within a local date: e.g. count the win-v
releases already published with today's date (gh api) + 1, or derive from the
UTC time of day (minutes/15 fits two digits) - whatever is monotonic per day
and fits the 2-digit field. Also: a same-semver re-publish must still go up.

## Validation criteria

- [ ] unit/acceptance over the version derivation: three same-day publishes
      yield strictly increasing ProductVersions, including across a
      run_number that is a multiple of 99 (positive control: the current
      formula fails that case)
- [ ] a real two-releases-in-one-day upgrade on the box installs the second
      over the first (msiexec exit 0)
- [ ] the misleading "same-day rebuild counter" comment is corrected
