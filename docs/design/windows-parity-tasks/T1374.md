# T1374 - Scrollbars, combo boxes and buttons still get dark-mode chrome on a light dialog

## Summary

T563 made every dialog and panel PAINT from the theme, but the common controls on them are still pinned to dark: 38 SetWindowTheme(..., 'DarkMode_Explorer') calls across ActivityMonitor, MachineChooser, the five small dialogs, Surface's two popups, the viewer bars and Window. On a light theme the surface and its text are light and the scrollbar, the combo drop-down and the edit's own chrome are still dark, which reads as half-themed. The fix is the same shape as T563's palette: derive 'DarkMode_Explorer' vs 'Explorer' from the panel palette the control sits on (a helper beside system_colors.applyPanelChrome), and re-apply it on the theme-flip broadcast.

## In plain terms

On a light theme, Ghoztty's dialogs (rename, banner, About, the machine chooser, the Activity Monitor and the rest) painted a light background and light text, but their buttons, scrollbars, text boxes and drop-downs were still drawn dark. It looked half-finished. Now every one of those controls follows the dialog it sits on, and switching Windows between light and dark moves them along with the dialog.

## Goals

- [x] one place decides a control's light/dark theme from the palette its surface paints from (`system_colors.applyControlTheme` / `applyControlThemeDark`)
- [x] every pinned-dark site in the win32 frontend goes through it (dialogs, panels, popups, the tab-rename box, the main window, tooltips, viewer bars)
- [x] a light/dark flip re-themes an open dialog's frame and controls, not only its painted surface
- [x] a source sweep stops a new surface from pinning its controls dark again

## What changed

- `system_colors.controlSubApp(dark, combo)` is the one decision (pure, unit-tested): `DarkMode_Explorer`/`Explorer`, and the `CFD` pair for a combo box (read off the window class, so callers never say which kind they made). `applyControlTheme(hwnd, palette)` reads light/dark off the palette exactly the way `applyPanelChrome` does for the frame; `applyControlThemeDark(hwnd, dark)` serves the surfaces that already carry a `dark` flag (viewer bars, tooltips, the main window).
- All 45 `DarkMode_*` literals outside `system_colors.zig` are gone. The light half is a NAMED theme (`Explorer`), not "no theme", so the same call flips a control both ways.
- `rethemeControls(parent, palette)` walks a dialog's direct children (common-control classes only: button, edit, combo, list, scrollbar, list/tree view, trackbar, up-down) and is called, with `applyPanelChrome`, from each of the eight dialogs' color-change branch before the repaint.
- The main window's control theme moved into `applyChromeTheme`, so creation, config reload and the OS flip all re-derive it. The tab-rename edit lost a no-op DWM dark-mode attribute (DWM attributes do nothing on a child) and follows the chrome's `isDark`.
- Caught by the harness on the way: the Rename and Banner dialogs theme their controls BEFORE `self.*` is assigned, so `self.pal()` read uninitialized memory and the dialog never opened. Those sites use `panelFor(window.app)`, the same call their frame already used.
