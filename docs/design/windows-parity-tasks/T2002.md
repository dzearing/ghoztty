# T2002 - An app relaunched after its agent was killed and sessions.json removed is sometimes killed from outside with exit code 1 within seconds (exit ledger: start, then unrecorded-exit)

## Summary

Found building T1978's test\win32\restore-dead-sessions.ps1 (2026-10-16). In 3 of 6 runs the section-C app (relaunched after Stop-RepoGhoztty killed app+agent of the run's lineage and sessions.json was deleted) died: once 2s after launch with both windows already rebuilt, once right after an IPC send-keys. GUI postmortem: 'exited with 1', stderr ends mid-stream with no error; exit-log-debug.txt shows 'event=start' then the NEXT launch's 'unrecorded-exit' - so nothing inside the app chose to exit (no recordExit, no posix.exit path in main runs after windows exist). Something terminated it with code 1. Section D (same kill, sessions.json kept) never died in 6 runs. Suspects: the new agent reaping something by a recorded PID that Windows reused for the new app (proc_control.zig:75 kills by pid; pty_holder/holder-adopt state outside sessions.json survives the B kill and orphaned pty-holders keep the old shells); a harness job teardown. Next: re-run restore-dead-sessions.ps1 -KeepState in a loop, log every process start/exit with ParentProcessId around section C (WMI Win32_ProcessStopTrace), and find the TerminateProcess caller. Real users hit this shape when an agent dies with its state file lost.
