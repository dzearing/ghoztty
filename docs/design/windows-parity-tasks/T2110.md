# T2110 - Stacked panes: goto_split, the pane sidebar, ghoztty://focus links and IPC focus bring a minimized pane on show

## Summary

Fourth slice of T2101. Every focus path routes through PaneStackState.noteFocus before the relayout, so a pane tucked into a strip slides into the run. Acceptance: each path, posted on the test desktop, ends with the target pane on show (enumerated rects).

## In plain terms

When a window is too narrow for every pane in a row, some panes tuck away
behind thin strips. Clicking a strip already brought a pane back, but every
other way of moving to a pane - the keyboard's "focus the split to the left",
a row in the pane sidebar, a `ghoztty://focus` link, `ghoztty` from a script -
moved the keyboard into a pane you could not see. Now each of them slides the
pane into view first, as on Mac.

## Goals

- [x] goto_split (previous/next/spatial) into a tucked pane brings it on show
- [x] a click on a pane sidebar row of a tucked pane brings it on show
- [x] a `ghoztty://focus/<name>` link / IPC focus (CLI, palette jump) brings it on show
- [x] an acceptance harness that fails on the old behaviour

## Design

One helper, `Window.showFocusedPane(tab)`: when the tab's focused pane is
tucked (its window hidden in the tab on show - not stashed, not hero, not
zoomed), run the layout. The layout already notes the focused pane into
`PaneStackState` (`stackGridOf` -> `noteFocus`), which is what brings it into
the run; the paths simply never re-laid the row out. Called from
`gotoSplit` (leaf case), `restorePane` (the sidebar's focus/restore path) and
`IpcHandlers.focusTarget` (links, CLI focus, palette jump), each BEFORE the
deferred SetFocus - which is dropped while the window is not foreground, so
the relayout cannot wait for WM_SETFOCUS. A no-op for a pane already on show.
The machine chooser's "session already open, focusing its pane" path calls it
too. goto_split previous/next do not wrap (SplitTree), as on Mac.
