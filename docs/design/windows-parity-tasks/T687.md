# T687 - Get-TestChildWindow matches window classes case-sensitively, unlike win32 itself

## In plain terms

A helper the automated tests use to find a control inside a window only finds
it when the name is spelled with exactly the right capitalisation. Windows
itself does not care about capitalisation here, so a test written the obvious
way finds nothing, reports a failure, and gives no hint that the spelling was
the problem. Making the helper behave like Windows removes a trap that costs a
debugging cycle every time someone hits it.

## Summary

`test/win32/lib/TestDesktop.ps1` compares class names with a case-SENSITIVE
`==`:

- `FirstChild` (line ~496): `if (cls == null || sb.ToString() == cls)`
- `Tops` (line ~476) and `FindTop` have the same compare.

Win32 does not: `FindWindowExW` matches class names case-insensitively, which
is why `Find-TestWindowEx -Class 'BUTTON'` has always worked against the
confirm dialog while `Get-TestChildWindow -Class 'EDIT'` silently returns
`IntPtr::Zero` — the control's registered class is `Edit`.

Found in T157: the natural spelling of the command palette's search-edit lookup
returned nothing, and the failure looked like "the palette has no edit control"
rather than "you typed EDIT and it is Edit". Worked around there by using
`Find-TestWindowEx`; the helper itself is still the trap.

## Details

Make the compare `String.Equals(..., StringComparison.OrdinalIgnoreCase)` in
the three finders, so every class filter in the suite behaves the way win32's
own finders do.

The change is strictly more permissive — it can only turn a missed match into a
match — so the risk to audit is any assertion that a class is ABSENT and passes
today only because of a casing mismatch. Grep the suite for absence assertions
(`-eq [IntPtr]::Zero`) and re-run the scripts that carry them.
