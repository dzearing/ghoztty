# T3646 - The session agent's private memory grows about 40-50 KB for every pane session opened and closed

## Summary

Measured by test/linux/pane-close-memory.sh (T3572) on the Linux debug agent: over 30 split open/close cycles the agent's private memory (smaps_rollup Private_*) climbed 10616 -> 11836 KB, roughly linearly (~40-50 KB per closed session), while its child processes, and the app's threads and fds, all came back. Under the harness's 1 MB per-pane budget, but a linear climb is the shape of retained per-session state (ring, emulator, session table entry, log buffers) rather than allocator warm-up, which flattens. Find what a closed session leaves behind in src/remote/agent (the code is shared, so check the Windows agent the same way, e.g. pane-close-memory.ps1's descendant column) and free it; acceptance: 50+ cycles with the agent's growth flat after warm-up.

## In plain terms

A memory check on Linux showed the background session service growing a
little every time a terminal pane was opened and closed, which looked like it
was holding on to closed panes. It is not: the service gives back everything a
closed pane used. The growth comes from the extra-careful memory bookkeeping
that only developer builds use. The check now measures what the service really
keeps, so a real leak would still be caught.

## Goals

- [x] Find out what a closed session leaves behind in the agent (nothing; see Root cause)
- [x] Give the close-memory harness an oracle that tells a leak from allocator overhead (M6)
- [x] Prove it flat over 50+ cycles

## Root cause

Not a leak. The Debug agent runs on Zig 0.15's `DebugAllocator`
(`std/heap/debug_allocator.zig`): it "never reuses memory addresses" - a freed
small slot is never handed out again - and a bucket page goes back to the OS
only when `freed_count == allocated_count`. One long-lived small allocation
made amid a session's churn pins its whole page, so private memory climbs per
session while every session byte is returned. A release agent runs on
`std.heap.smp_allocator` (T3017), which reuses its freelists.

Evidence: the agent's own count of bytes handed out (`DebugAllocator` with
`enable_memory_limit`, logged by the new `src/remote/agent/heap_stats.zig` on
every session create/free) over 30 split cycles in WSL: 29,110 -> 29,830 B
(~24 B a cycle, two hash-map-growth steps), while the agent's private memory
rose 11,540 -> 12,340 KB (~27 KB a cycle). One open session holds ~10 KB of
live heap (peak 39,360 B), so a session kept in any form would show as 10 KB a
cycle.
