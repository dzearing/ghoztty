# T3440 - Fork CI windows-cross has failed to link since the T3413 WIP range: lld-link undefined glslang_default_resource and spv::Builder::postProcess in the ReleaseFast x86_64-windows-gnu exe

## Summary

Fork CI's windows-cross job (Cross-compile the Windows exe) has been red on every completed run since b04c716e7 (runs for b04c716e7, 37816554e, 0db3224ca; 04583b4d2 was the last green). Error: lld-link: undefined symbol: glslang_default_resource, and spv::Builder::postProcess(bool), linking exe ghoztty ReleaseFast x86_64-windows-gnu. The range 04583b4d2..b04c716e7 holds 7e0e42b38 (T3412), the four T3413 WIP commits (3e8ec9e9d touched src/apprt/ipc/verbs.zig and src/apprt/win32/IpcHandlers.zig) and two T1768 harness-only commits. The local Debug win32 build links fine, so first reproduce with a ReleaseFast cross build, then bisect the range. A red trunk CI blocks the next release run (T1219).

## In plain terms

The build machine that checks every change compiles for Windows had been
failing since this afternoon, even though nothing wrong had been added to the
code. A check that was cut short partway through saved its half-finished work,
and every later check reused it. After this fix, only a check that finished
cleanly can pass its work on, so one interrupted check can no longer turn the
light red for every change after it.

## Goals

- [x] Find why the Windows cross-compile fails to link on CI but not locally
- [x] Stop a cancelled or failed CI run from saving its Zig cache
- [x] Abandon the poisoned cache chain so the next run builds clean
- [x] Lock the shape with a static harness assertion
- [ ] See Fork CI windows-cross go green on the pushed fix
