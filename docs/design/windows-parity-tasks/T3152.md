# T3152 - The IPC server keeps 16 blocked listener threads (one per pipe instance) where one overlapped waiter would do, adding 12 threads to every idle app since T3105

## Summary

Audit-3 (T3101). baseline-3 against baseline-2: debug and release idle.threads 71 -> 83 and cycle.start.threads 75 -> 87, out of the +-11 tolerance (the only worse-than-tolerance thread metrics). Cause, read at d0d874326: T3105 (e4bfd30f5) raised instance_count from 4 to 16 (src/apprt/win32/IpcServer.zig:57), one listener thread per pipe instance. The I/O is already overlapped (src/apprt/win32/ipc_pipe_io.zig), so one thread can wait on all instances' connect events (WaitForMultipleObjects, up to 64) and hand each accepted client to a short-lived worker or a small pool. Not P0 per the audit rule because the regression is an intended trade with no measured cost beyond the thread count: idle wakeups 147.7 -> 146.5/s and private 202.3 -> 204.7 MB, both within tolerance. Validation: baseline idle.threads back to about 71 with ipc-p1..p3 and the T3105 silent-client harness green.
