# T1582 - Fork CI goes red whenever gitlab.gnome.org hiccups, because the msitools build clones it with no retry

## Summary

windows-cross builds msitools 0.106 from source by cloning https://gitlab.gnome.org/GNOME/msitools.git. On 2026-09-15 that host answered 503 and the whole job failed with exit 128, which turned the branch head red and blocked the next turn's validate gate on a defect that is not in our code. The clone is a single unguarded network call to a host we do not run. Wanted: a retry with backoff at minimum, and better a cached or mirrored source (a pinned tarball from a release asset, or the ubuntu package where the version allows) so a third party's bad minute cannot stop the loop. The same shape applies to any other from-source dependency the workflow clones.

## In plain terms

Every push to the Windows branch builds the installer in the cloud, and that
build downloads one of its tools from a GNOME server. When that server had a
bad minute, the whole build went red even though nothing was wrong with our
code, and the loop had to wave the red light through by hand. Now the download
retries, falls back to GNOME's GitHub mirror, and checks it got exactly the
pinned version, so somebody else's outage no longer reads as our breakage.

## Goals

- [x] the msitools clone retries with backoff instead of failing on the first error
- [x] a second source (GNOME's GitHub mirror) is tried when gitlab.gnome.org will not answer
- [x] neither source is used unless the tag resolves to the pinned commit
- [x] the retry/fallback/refusal paths are tested without a network

- [x] install-msitools.sh clones through `clone_pinned_tag` with both sources and a pinned 40-char sha - `test\win32\release-artifacts.ps1` E13/E13b/E13c PASS
