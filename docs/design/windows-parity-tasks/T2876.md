# T2876 - agent-recovery.ps1 surface oracle is stale since T2597's pane-window pool (E7/G9/H6/I read HWND identity), and no guard row covers the harness so nobody re-ran it

## Summary

Found by T2865. `test/win32/agent-recovery.ps1` proves "a rebuild ran" (E7, H6,
the I section's `Wait-SurfacesReplaced`) and "nothing was rebuilt" (G9) by
comparing the set of `GhozttyTerminal` HWNDs before and after. Since T2597
(`src/apprt/win32/pane_pool.zig`, 2026-11-01) a departing pane's window is
parked hidden in its top-level and handed to the next pane, so a correct
rebuild reuses pre-recovery HWNDs and leaves parked spares enumerable: E7 reads
red on a correct rebuild. T2865 fixed the identical oracle in
`agent-recovery-tabs.ps1` by counting the app's `surface closed` log lines
between `in-place recovery: re-dialed` and `in-place recovery: rebuilt`
(each departing surface logs it synchronously from `old_tree.deinit()`).

Run 2026-11-09 13:50 (log ghoztty-acceptance-parallel/20261109-135022): E7 red
for this reason; F4 and every assertion from G onward red too, but that run
overlapped an agent-recovery-tabs run whose cleanup kills repo-built
instances, so those need a clean serial re-run before they mean anything.

The harness also has NO guard-due row (grep `scripts/guard-due.ps1`), which is
why it was never re-run after T2597 touched the code it covers. Add one.

Fix: give E7/H6/I the same log-window oracle (G9: no `surface closed` in the
blip window), add the guard row, run it alone (about 15 minutes).

## In plain terms

The automated test that proves the terminal recovers in place when its
background session helper crashes was reporting a failure even when recovery
worked. It judged "were the panes rebuilt?" by whether the pane windows were
brand new, and a recent change now recycles pane windows. When this lands, the
test asks the app's own log how many panes it rebuilt, and the test is
re-run automatically whenever the recovery code changes.
