# T2598 - Cut the terminal's first frame at a new size during a window-edge drag (~6 ms draw-begin -> present vs ~3 ms same-size): it cannot begin before the pane batch ends, so it is half of T2577's budget on its own

## Summary

T2577 (steps 2-3) stamped the render thread under `GHOZTTY_RESIZE_TRACE`
(`draw-begin` / `target-ready` / `synced` / `finish` / `comp-begin` /
`comp-begun` / `swap-begin` / `present`). The terminal's first present at a
new size lands ~6 ms after its draw begins (synced ~1.3, finish ~1.3,
comp-begin -> comp-begun ~1.9, ResizeBuffers ~1), against ~3.3 ms for a
same-size frame, and the draw cannot begin before the UI's pane batch ends
(~6.7 ms after the frame change). Step 2 already made the GL target and the
interop texture grow-only (target-ready 2.63 -> 0.48 ms) and the net gain was
small because `synced` / `finish` stretched.

Do: (1) split the first-frame stages again with the box idle (the step 2
numbers were taken with a fullscreen app on the GPU) to find which stage
grows with a size change; (2) take ResizeBuffers off the per-step path
(grow-only swap chain in buckets, presenting a sub-rect / source size) if it
is still ~1 ms; (3) look at whether the draw can begin as soon as the
terminal's new grid size is known rather than at the batch's end (the
composition swap chain does not need the HWND at its new size). A/B with
`scripts\resize-sync-onscreen.ps1` (ReleaseSafe, CHROME+PRESENT+NOREDIR),
alternating, bad frames per step.

## In plain terms

When you drag a window edge, the terminal takes about twice as long to draw
its first picture at the new size as it does to draw an ordinary frame. This
task finds where that time goes and cuts it, so the terminal keeps up with
the window's outline.

## Goals

- [x] the first-frame stages at a new size, measured on an idle box
- [x] the stage that grows with a size change taken down (ResizeBuffers done; `synced` split: it is the first GL round-trip, filed as T2601)
- [x] first frame at a new size close to a same-size frame (gap 2.0 -> ~1.1 ms; the rest is T2601)

## Step 1 (2026-11-01 04:00): the swap chain takes a new size without ResizeBuffers

Landed: the composition swap chain's buffers grow in `share_bucket` (256 px)
steps like the shared texture, and a size change inside them is
`IDXGISwapChain2::SetSourceSize` - the swap chain presents only the frame's
top-left `w` x `h`, which the copy writes. A refused source size drops that
presenter to exact `ResizeBuffers` for good (logged).
`GHOZTTY_COMP_RESIZE_BUFFERS=1` restores the per-step resize for A/B.

A/B, ReleaseSafe @2408b5de6+this, CHROME+PRESENT+NOREDIR+RESIZE_TRACE, four
drags (128 steps), alternating, box idle (04:00, nobody at it). Render-thread
stages, medians in ms from the previous stamp, 128 new-size frames per run
(scratch `stages.py` over each run's stderr: a frame is draw-begin -> its
present, NEW when the present's size differs from that pane's last):

| stage | new 1 | old 1 | new 2 | old 2 | same-size (all runs) |
|---|---|---|---|---|---|
| target-ready | 0.34 | 0.35 | 0.35 | 0.34 | 0.27-0.31 |
| synced | 1.02 | 1.14 | 1.13 | 1.14 | 0.38-0.41 |
| comp-begin -> comp-begun (ResizeBuffers) | **0.38** | 1.33 | **0.39** | 1.35 | 0.36-0.40 |
| swap-begin -> present | 0.40 | 0.60 | 0.41 | 0.60 | 0.43-0.60 |
| **draw-begin -> present** | **4.81** | 5.42 | **4.78** | 5.43 | 3.31-3.99 |

Earlier numbers (~6 ms new against ~3.3) were taken on a contended box; idle,
the gap was 2.0 ms and is now 1.5 ms. What is left of it is `synced` (~0.7 ms
more at a new size). The cell buffers are already grow-only (`Buffer.sync`
doubles), so it is not a reallocation; finer stamps between the uploads are
the next step.

Films (bad rs/rg/ls/lg): new 29/43/31/45 = 148, old 34/40/32/36 = 142, new
35/47/35/42 = 159, old 33/40/34/37 = 144. The film reads slightly WORSE, and
all of the difference is one kind: `gap=` frames (terminal and page
disagree) 36/38 new against 29/26 old, mostly on the grow drags, while the
page-against-frame flags (`right=`) are the same in every run (64/63/64/63).
On a grow, `gap=9 right=9` is the page still at its old place under a
terminal that has reached the new width: the terminal now keeps up more often
and the page - the laggard since T2577 step 4 - does not, so they disagree
more. Cutting the terminal further cannot lower the film until the page keeps
up too (T2580 is the same pairing seen from the shrink side). Landed
anyway: it takes ~1 ms of GPU-allocation work off every drag step, and the
fix for the disagreement is the page's latency, not a slower terminal.

## Step 2 (2026-11-01 05:10): `synced` is the frame's first GL round-trip, not an upload

Split `synced` with stamps between each upload (temporary, not landed),
ReleaseSafe @0763d579d, CHROME+PRESENT+NOREDIR+RESIZE_TRACE, idle box, 128
new-size frames per run. Every render-trace stamp costs ~0.25 ms by itself
(the log line), so a stage of ~0.25 is empty.

| stage (ms) | new | same |
|---|---|---|
| uploads (images, bg image, shader uniforms) | 0.27 | 0.31 |
| uniforms.sync | **1.06** | 0.27 |
| cells_bg.sync | 0.23 | 0.26 |
| cells.syncFromArrayLists | 0.34 | 0.30 |
| atlas / rest -> synced | 0.27 | 0.25 |

A `glGetError` probe before the uniform upload took the whole stall over
(probe 1.00/1.12/1.05/1.04 new vs 0.26-0.28 same; uniforms.sync 0.25), so it
is the first synchronous GL call of the frame, whatever it is. A `glFlush` at
draw-begin (four alternating arms, plain/prime/plain/prime) did not move it
(1.00/1.05 plain vs 1.12/1.04 prime) and the films did not change (146/156
plain vs 159/151 prime). By gap since the pane's last present: new-size
frames after 4+ ms stall (n=107, 1.06-1.09), new-size frames under 1 ms do
not (0.34, n=9), same-size frames do not at any gap (n=3 above 16 ms, thin).
Filed as **T2601** (driver-side; needs GPUView or a threaded-optimization
A/B, not more stamps).

Lever (3), beginning the draw before the pane batch ends, is filed as
**T2602** behind T2580: step 1's film already has the terminal ahead of the
viewer page on grow drags, so an earlier terminal cannot lower the film until
the page keeps up. T2577 now waits on T2602 too.

Closing here: the size-dependent costs this task could reach are cut
(ResizeBuffers 1.33 -> 0.38 ms; new-size frame 5.4 -> 4.8 ms), the gap to a
same-size frame is ~1.1 ms (5.37/5.48 vs 4.29/4.28 on the probe build), and
both remaining pieces have their own tasks.
