# T2491 - Composition step 3b: the dim overlay becomes a child visual of the pane visual (T2467's host) instead of a WS_EX_LAYERED popup

## Summary

T2360 step 3, second overlay after T2467's bell border. The unfocused-split
dim wash (`DimOverlay`, T74) is a `WS_EX_LAYERED` popup that every layout,
move, fold and divider drag repositions by hand (`SetWindowPos` /
`DeferWindowPos`), which is how it can lag its pane by a frame. On a pane that
presents through the composition swap chain (`GHOZTTY_COMP_PRESENT=1`,
T2466), it now hangs under the pane's root visual through T2467's
`comp_overlay.Slot` instead.

## In plain terms

When you have two terminals side by side, the one you are not typing in is
greyed out. That grey layer was a separate floating window that had to be
dragged along every time the pane moved or changed size, and it could trail
behind for a frame. On the new drawing path it is part of the pane's own
picture, so it moves and resizes with the pane by itself.

## Goals

- [x] On the composition path the wash is a child visual of the pane - same colour, same alpha - and no dim popup is shown
- [x] A move, resize, fold or divider drag does no work for it at all (one pixel stretched past any pane size, clipped by the pane window)
- [x] A pane with a banner, a viewer pane, and the knob-off path keep the popup exactly as before

## Design (technical, mine per go.md 5b)

- **One pixel, stretched.** `comp_overlay.Layer.cover` uploads a 1x1 opaque
  BGRA surface and gives the visual a 16384x scale with nearest-neighbour
  sampling. The pane window clips it, so it never needs a re-upload, a new
  transform or a commit when the pane changes size - unlike the bell frame,
  whose pixels depend on the size. The alpha is the effect group's opacity,
  the popup's `SourceConstantAlpha`.
- **Who stays a popup.** A pane with a banner band (T2308): the wash must
  reach up over the band, which is outside the pane window, and stack over
  the strip's popup - a visual inside the pane can do neither. A viewer pane
  (WebView2 presents itself; `create` gets a null slot). And any pane on
  SwapBuffers. `DimOverlay.show` decides per call, so a banner coming or
  going, or the renderer publishing/retracting its tree (WM_APP+44, which now
  re-runs `Window.updateDimOverlays`), moves the wash between the two paths.
- `BannerOverlay.shownDim` reads `DimOverlay.shownPopup()` so a glide's
  frozen copy never stacks against a popup that is not the one up; `seatOver`
  is a no-op on the visual path.
- The lab's planted overlay lag (T2383) only exists on the popup path: on the
  visual path there is no move to hold back.
