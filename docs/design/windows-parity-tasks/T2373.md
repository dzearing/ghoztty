# T2373 - Frame-exact resize and animation lab: capture every composed frame (Windows.Graphics.Capture on the input desktop) during scripted window/pane/sidebar resizes and glides, score each frame for bleeding (background, stale-size, stretched, misaligned content) and motion smoothness (refreshes that advanced, stalls, jitter, input-to-photon lag); the app's self-reported decision logs cannot see what the user sees

## Summary

User, 2026-10-27: "please consider how you will measure the smoothness of the
resizing and painting. i specifically do not want to see bleeding during
resize of the window or resizing panes".

### Why the existing harnesses are not enough

`resize-flicker.ps1`, `drag-perf.ps1` and `frame-clock.ps1` judge the app by
what it SAYS it did (`surface erase ... fill=`, `window resize ... sync=`,
`divider drag ... stale=`, frame-clock interval lines). That was deliberate:
on the background test desktop a GL pane cannot be photographed, and
polling the screen from another process at ~10 ms catches a sub-frame flash
almost never (resize-flicker.ps1 header). So those tests can be green while
the user still sees bleeding. They prove our decisions, not our pixels.
This lab adds the missing half: **every frame DWM actually composed,
scored**.

### "Bleeding": the failure classes, each scored per frame

| class | what the user sees | how a frame shows it |
|---|---|---|
| B1 background flash | desk or flat brush where a terminal should be | desk/background-colored pixels inside a pane's card |
| B2 stale size | content too small (gap) or cut off while the card has moved on | the pane's border ring is not flush with its card edges (> 1 px off) |
| B3 stretch | DWM scaling an old frame to the new HWND size | ring thickness or the ID glyph's size differs from the reference |
| B4 chrome/content tear | divider, strip, shadow or sidebar a frame ahead or behind the panes | divider/strip edges and pane rings disagree in the same frame |
| B5 overlay lag | scrollbar, dim, bell border or banner (layered popups) trailing their pane | overlay color patch off its pane's rect |
| B6 garbage | black, uninitialized or torn pixels | colors outside the scene palette, outside AA/shadow bands |

**Deterministic scene** so every pixel is classifiable: each pane runs a test
card (a small script emitting SGR) that fills its grid with a pane-unique
background, a 1-cell border ring in a second unique color, and a large ID
glyph. The theme's chrome colors come from the app's own tokens. Shadow and
rounded-corner bands get a measured tolerance mask, not a blanket exclusion.
Optional second mode: heavy output (scrolling text) inside the ring while
resizing, to catch renderer-busy cases.

### Smoothness metrics (same capture, no second run)

From each frame's timestamp (`SystemRelativeTime`) and the tracked edge
position (divider/card edge located from the rings):

- **Advance rate**: the share of display refreshes during motion that
  showed new motion. 39 fps on 120 Hz reads about 33%; the target is >= 98%.
- **Stalls**: refreshes in a row with no motion while motion is due. Count
  and longest. Target: none longer than 1 refresh.
- **Jitter**: for constant-speed drags, the spread of displacement per
  refresh; for glides, the max deviation from the ease curve sampled at
  display time (px).
- **Input-to-photon lag** for pointer-driven resizes: refreshes between the
  pointer reaching x and the edge reaching x, p50/p95. Target p95 <= 2
  refreshes at 120 Hz.
- **Reversal check**: scripted back-and-forth drags (the user's "janks back
  and forth"). The edge must never move against the pointer's direction.

### Interactions covered

Window frame drag (edges + corner, real modal size loop via SendInput),
maximize/restore/Aero-snap/caption double-click, split divider drag, sidebar
edge drag (T2359), blade collapse/expand glide, banner toggle, hero, tab
switch, new split/close pane. Matrix: 1/4/9 panes; flat/elevated/glass; DPI
100/150/200%; sidebar expanded/rail/hidden; the 50 ms/500 ms UI-stall knob
from T2360; 60 Hz and 120 Hz; a window moved across two monitors at different
refresh rates.

### Capture mechanics (decided; verify in the first step)

- **Windows.Graphics.Capture** monitor capture cropped to the window rect
  (window capture would miss our owned layered popups, which is B5), with a
  free-threaded frame pool sized for 120 Hz. Frames are scored online on a
  worker, and only failing frames plus a sampled 1% are written as PNG, so a
  long run fits in memory.
- **Cross-check frame accounting** with DXGI Desktop Duplication
  (`AccumulatedFrames > 1` = a composed frame the capture skipped). A
  measurement that drops frames must say so, not score fewer frames.
- **Input desktop only.** DWM composes the input desktop, so this lab is
  INTERACTIVE BY DESIGN and declares it under docs/claude/testing.md's
  rules (`Assert-TestDesktopCapability -Interactive`). It runs when the user
  starts it or when the box is idle (GetLastInputInfo), never under the
  user's hands. The background-desktop decision oracles stay the cheap
  per-commit gate. This lab is the truth gate for anything touching
  layout, paint, present or animation.
- Input is SendInput at 1 kHz along scripted paths with a high-resolution
  waitable timer, and every injected point is timestamped on the same clock
  (QPC) as the capture.

### Controls (mandatory, or a green result means nothing)

- **Positive controls**: debug env knobs that (a) erase a pane to magenta for
  one frame mid-drag, (b) present one stale-size frame, (c) hold a layered
  overlay one frame behind. Each must be caught as B1/B2/B5 in 100% of
  runs. A lab that misses a planted one-frame defect is broken.
- **Negative control**: a static window for 10 s gives 0 findings and 0
  stalls.
- **Baseline**: run against today's build first and publish the numbers.
  It should show what the user sees: the sidebar-drag bleed (T2359) and the
  ~39 fps glides (T2365). If it does not, the lab is wrong, not the app.
- **Ground truth, once**: one 240 fps phone video of a divider drag next to
  the lab's verdict for the same run, to confirm the capture shows what the
  eye sees.

### Output

A stamp JSON (pass/fail per interaction x matrix cell, every metric) for
the harness audit, and an HTML report: an advance-rate/stall chart per
interaction, and a filmstrip of the worst frames with the failing pixels
outlined, so a regression is visible at a glance.

### Gates it creates

- T2359 (sidebar drag), T2365 (frame clock) and T2360 (composition) are not
  done until this lab shows 0 bleed frames and meets the smoothness targets
  for their interactions at 120 Hz.
- Any later change to layout/paint/present/animation code reruns the lab.

### Parity

The same metrics on the Mac (ScreenCaptureKit) make "as smooth as Mac" a
number rather than an impression. File that half as a `seat: mac` task.

## Validation criteria

- [ ] Positive controls caught in 100% of 20 runs each (B1, B2, B5); negative control 0 findings.
- [ ] Desktop Duplication cross-check shows the capture missed 0 composed frames during a 120 Hz run, or reports exactly how many.
- [ ] Baseline report against the current build published (HTML + stamp), showing the user-reported sidebar-drag bleed and glide stutter as numbers.
- [ ] Ground-truth video comparison done once and recorded here.
- [ ] Gates wired: T2359/T2360 validation criteria reference this lab's stamp; seat:mac parity task filed.
