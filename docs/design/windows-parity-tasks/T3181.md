# T3181 - Single-window mode: workspaces share one window - the workspace on show owns it, every other is parked off-window with its terminals not drawing and viewers asleep

## Summary

WorkspaceHost for win32: adopt/surrender hand-off (window controller pointer, chrome, title, tab colour, desk, sidebar, fullscreen/maximize state belong to the HWND), parked Window.hwnd=null with controller->window code skipping window work, park host HWND for parked pane children, parked panes report hidden (Surface.setVisible / the T3035 background path; overlays hidden), viewers stop polling, parked content laid out at the window size and re-laid after a resize settles (0.3s) and on a tree change; every path that opens a window (Ctrl+Shift+N, menus, sidebar +, +new-window, drag-out, undo close, restore) makes a workspace (startsParked); focus policy: manual open on show, programmatic stays parked, --focus shows. Child of T3136 (split 2026-11-16). Design (T3136 Details): ONE shared top-level HWND; every workspace keeps its own Window controller; the workspace on show owns the HWND (GWLP_USERDATA, chrome, sidebar), a parked Window has hwnd=null and its pane child HWNDs are reparented (adoptPane-style SetParent, Window.zig:7278) under a hidden park host so they survive the shared HWND closing. Spec: docs/reference/window-modes.md. Acceptance goes in test/win32/single-window-mode.ps1 (one section per child).

Measured on claim: Window.zig is ~23.5k lines with ~284 `.hwnd` reads, so the whole of the summary above is several contexts of work. This task now delivers the POLICY half of Mac `WorkspaceHost` as a pure module, and the mechanism is split into children:

## In plain terms

Before Windows can keep every window inside one, it needs a single answer to "which workspace has the window right now, which ones are waiting, and who takes over when one closes". That answer now exists and is tested; the pieces that actually move the window around come next.
