# T2553 - Composition step 5b: each pane's content visual (swap chain and overlay layers) joins the window's composition tree instead of a target on its own child HWND, so the compositor can move it; the HWND stays only for input

## Summary

Prerequisite for every pane glide in T2469. Today each pane presents into its own DComp target on its own child HWND (T2466), and its overlays hang off that root (T2467), so pane motion is still SetWindowPos on child HWNDs, which no compositor animation can move. Put each pane content visual (swap chain + overlay layers) into the top-level window composition tree (chrome_comp host, above the desk visual), e.g. via DCompositionCreateSurfaceHandle + CreateSwapChainForCompositionSurfaceHandle so the renderer thread keeps presenting while the window device places the visual. The child HWND stays for input/IME/focus at the pane final rect. Oracle: WGC ghost film, pane pixels identical knob on/off at rest and through a split + resize, 0 blank frames.

## In plain terms

Every terminal pane used to be drawn onto its own little window, so the only way to move a pane on screen was to move that window - which is why pane animations stutter. Now (behind a test switch) each pane's picture is a layer of the main window's own picture, which the Windows compositor can slide smoothly. The small window stays behind it, invisible, just to receive typing and clicks.

## Goals

- [x] the renderer presents into a composition surface handle instead of a target on its own child window (`gl_comp_present.zig`, tree mode)
- [x] the window thread wraps that handle in a visual of the top-level window's tree, over the pane child windows (`chrome_comp.Host.paneAdopt`, a topmost=TRUE pane target)
- [x] the visual follows its child window: moved, resized, hidden, shown (`Surface.syncTreeVisual` on `WM_WINDOWPOSCHANGED`; clip = the pane's client size, hidden = empty clip)
- [x] any failure falls back to the old path (`refused` flag -> `compFail`), and a rebuilt window host re-adopts every pane
- [ ] overlays (scrollbar, dim, bell, banner) in the window tree too -> T2562

## Design (mechanism calls, recorded per go.md 5b)

- **Second DComp target, topmost=TRUE, on the chrome host's device.** The chrome host's existing target is topmost=FALSE (under the pane child windows). A pane visual there would be covered by the child window's own pixels, so the pane layer gets its own topmost target on the same device: it composes over the child windows, which then serve input/IME/focus only. A viewer pane (WebView2) is never covered at rest because terminal-pane visuals clip to their own rect.
- **Cross-thread/cross-device via a surface handle**, not by moving the renderer onto the window's device: the renderer keeps its own D3D11 device and keeps presenting on its own thread; only placement is the window's job. `comp_tree.Slot` is the meeting point (same generation scheme as `comp_overlay.Slot`); the window adopts under the slot lock so a retract cannot close the handle mid-adopt.
- **Knob `GHOZTTY_COMP_PANE_TREE=1`**, effective only with `GHOZTTY_COMP_PRESENT=1` and `GHOZTTY_COMP_CHROME=1`; the renderer only makes a handle swap chain when the window says it has a host (`host_ready`), so a handle is never left unadopted.
