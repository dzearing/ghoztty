# T809 - A GUI acceptance script that crashes ghoztty.exe still reports only a dead pipe: nothing reads the first-crash dump Windows wrote for the APP

## In plain terms

When the terminal itself falls over in the middle of an automated test, the
test log used to say almost nothing about it: the next command it tried failed
because the program it was talking to was gone, and that dead connection was
the whole story. Windows had, all along, saved a snapshot of the crash the
moment it happened. Nothing opened it. Now the test prints where it fell over -
the function, the file, the line - right where it reports the failure, so the
first read of the log is the diagnosis instead of the start of an
investigation.

## Summary

`floor-lane.ps1` has post-mortemed a crashed LANE binary out of the dump
Windows already wrote since T460: `Find-WerCrashDump` ->
`Invoke-CrashDumpAnalysis` -> `Write-CrashDumpStack`, about a second, every
thread, source lines, no re-run. The GUI half of the harness never got that.
`test\win32\lib\GuiPostmortem.ps1` carried its own `Get-GuiCrashDump`, which
globbed `%LOCALAPPDATA%\CrashDumps` and printed a PATH - so the block named the
evidence and stopped there.

Two defects, not one:

- **The dump was never read.** A GUI app cannot be re-run into the same fault
  the way a lane binary can, so that dump is the only evidence there will ever
  be of the crash that actually happened, and the harness left it closed.
- **The app is usually not a pid the harness launched.** `+new-window`
  auto-spawns `ghoztty.exe` from inside the CLI process (`performIpc` in
  `src/apprt/win32/App.zig`), so the process that owns the window has no
  handle, no exit code and no launch record here. `Write-TestDesktopPostmortems`
  is structurally blind to it, and what the log shows instead is the next verb
  failing on a closed pipe - the shape this task is named after.

The fix:

- `GuiPostmortem.ps1` dot-sources `scripts\lib\CrashDump.ps1` and uses it.
  `Get-GuiCrashDump` is now `Find-WerCrashDump` (honours a redirected
  `DumpFolder`, and waits for WER to finish the file instead of racing it);
  `Get-GuiDumpAnalysis` reads the dump with symbols taken from the launched
  exe's own directory and never throws, because it runs from `finally` blocks;
  `Write-GuiPostmortem` renders the `-- crash stack --` inside the same block
  as the verdict.
- `Write-GuiUnclaimedCrashDump` covers the other population: a dump one of our
  exes left during this run that no launch record accounts for.
  `Remove-TestDesktop` calls it after the per-pid sweep, excluding what that
  sweep already printed, so every GUI script gets both for free.

## Validation criteria

- [x] A real access violation launched through the harness reports the stack
      out of the dump, not just its path - the frames name the binary and sit
      in the same block as the verdict. (`test\win32\gui-postmortem.ps1`
      C9-C12: `DumpRead`, a parsed crash, `-- crash stack --` and
      `no re-run, no reproduction` in the printed block, and a frame matching
      the crashed exe.)
- [x] A crash of a process the harness never launched is still reported, with
      its stack. (Same script, section I: the crasher is started with a plain
      `Start-Process`, and `Write-GuiUnclaimedCrashDump` prints
      `no launched pid accounts for` plus the frames.)
- [x] The same dump is never printed twice when a per-pid postmortem already
      covered it. (Section I4: `-ExcludePaths` yields 0 blocks and an empty
      last-block buffer.)
- [x] A box with no WER dump and a box with no cdb degrade to a SKIP and a
      named reason, never to a failure or an exception out of teardown.
      (Sections C and I skip on either; `Get-GuiDumpAnalysis` returns a `Why`
      line instead of throwing.)
- [x] `test\win32\gui-postmortem.ps1` is green end to end and the
      `gui-postmortem` guard re-stamps. (ALL PASS, 41 assertions, STAMPED.)
- [x] The standing floor is green over the change.
