# T2599 - Plain (non-layered) terminal panes leak ~3 MB of GPU memory per closed WINDOW that outlives the window's destruction - window-close-memory A8 3.00 MB with GHOZTTY_PANE_LAYER=0, with or without T2597's pane reuse; blocks flipping T2592's default

## In plain terms

With panes drawn the way that avoids the black flicker on big windows
(T2592), every window you close still leaves about 3 MB of graphics memory
behind for as long as Ghoztty runs. Opening and closing windows all day
slowly eats video memory. When this lands, closing a window gives all of it
back.

## Summary

Found while validating T2597 (2026-11-01, debug build on lane-b, RTX 4090,
WGL). `test\win32\window-close-memory.ps1 -Shape split`, 10 cycles:

- `GHOZTTY_PANE_LAYER=0` (plain children), reuse ON: A8 **3.00 MB a closed window**.
- `GHOZTTY_PANE_LAYER=0`, `GHOZTTY_PANE_REUSE=0`: A8 **3.00 MB** - identical, so
  T2597's pool neither causes nor cures it.
- default (layered panes): A8 0.20 MB, ALL PASS 13.
- `-Shape full` plain + reuse: A8 3.00 MB, A1 1.01 MB (A1 is T2500's residual).

T2499's title already named this half ("~3 MB a window outlives the window
close"); the layered child fixed it by accident and T2597 only fixes the
per-PANE half (a closed pane inside a living window). So with plain children
the top-level's own destruction does not free everything its plain WGL
children's presents allocated. T2499's original measurement put it at
`-Shape split`/`full` only (two terminals), `single` flat - so it may be the
SECOND plain child sharing the redirection surface.

**Bisect, 2026-11-01 (lane b, debug, `GHOZTTY_PANE_LAYER=0`, per-step GPU
dedicated probe, `--undo-timeout=0`).** The shape is now exact:

- **Every plain terminal pane beyond a window's first that ever presented
  strands ~3 MB for good** (top-level-sized). One pane: flat (52.7 -> 32.3,
  back to start). Two: +3.0 a window. Three: +6.0. Cycle 1 leaks too, so it
  is not warm-up.
- Closing the extra pane first (`+close` b, reaped while the window lives)
  frees 8 of its 11 MB; the window close then frees exactly what a one-pane
  window costs (20.4) and the 3 MB stays - reuse on or off.

Levers measured and ruled out (each 2-3 cycles, all still +3.0 a window):
resizing the top-level after the extra pane closed (the redirection surface
is reallocated, nothing returns); making another window present afterwards
(resizing the anchor); deleting every pane's GL context only AFTER
`DestroyWindow(top)`; re-binding each context to its DC before the delete;
keeping the closed window's pane HWNDs app-wide (re-parented to a hidden
keeper) and handing them to the next window's panes - a kept HWND that
presents into a NEW top-level allocates again, so the allocation is per
(child, top-level), not per child; `wglShareLists` between a window's pane
contexts (the driver refuses the call, `ok=0`, so untestable this way).
`GHOZTTY_COMP_PRESENT=1` is no escape either: ~48 MB a closed window (filed
separately). The experiment code is reverted; the patch is not kept.

**What is left (best first):**

- **Never destroy the top-level** - park a closed window's HWND (hidden,
  panes reaped into its own T2597 pool) and give it to the next
  `+new-window`. The strand happens only at a top-level's destruction, so a
  reused top-level bounds it by the pool, the way T2597 bounded the per-pane
  half. Cost: a parked top-level holds its own ~20 MB while it waits, and
  the `Window` state has to re-initialise on a live HWND.
- A WPR GPU trace of one split+close, to name the allocation that outlives
  the top-level (a DWM redirection-surface open held by the ICD, or
  something inside it). Only worth it if the first lever fails.
- One GL child per top-level (every pane draws into it) - removes the second
  presenter outright, at the cost of a renderer architecture change.

If none lands, T2592 decides whether to flip with the leak: ~3 MB per extra
pane per closed window at 1000x700, ~20 MB at the user's 3000x1700.

## Validation criteria
