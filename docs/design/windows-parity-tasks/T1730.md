# T1730 - Pressing Cancel on the 'already installed' prompt ends the installer with error 1722 instead of quietly

## In plain terms

If you run the Ghoztty installer for the version you already have, it now
asks "Repair or Cancel?". Pressing Repair works. Pressing **Cancel** makes
Windows show an error - "There is a problem with this Windows Installer
package. A program run as part of the setup did not finish as expected" - and
the installer ends as a failure. Cancel should just close the installer
quietly.

## Summary

Found by T1302, the first run of `test\win32\install-walkthrough.ps1` section D
against a real msiexec (package `Ghoztty-1.36.36-x64.msi`, `win-v1.36.36`).

The app side is right: msiexec's own verbose log records
`CustomAction MaintenancePrompt returned actual error code 1602`. What is wrong
is the premise in `dist\windows-installer\build-msi.sh` (the MaintenancePrompt
comment, point 3) and in `src\apprt\win32\install_maintenance.zig`'s header:
that 1602 from an EXE custom action is "the ONE non-zero code Windows Installer
reads as 'the user said no'". It is not. For an EXE custom action authored
`Return="check"`, Windows Installer treats ANY non-zero exit as a failure:

```
CustomAction MaintenancePrompt returned actual error code 1602
Note: 1: 1722 2: MaintenancePrompt 3: ...\ghoztty.exe 4: --install-maintenance --installed-version=1.36.36
Product: GhozttyT1299Test -- Error 1722. There is a problem with this Windows Installer package. ...
MainEngineThread is returning 1603
```

and at `/qr` the 1722 is a modal error box (the log shows it sitting for two
minutes until the harness killed msiexec).

The user-exit mapping (msiDoActionStatusUserExit -> 1602) exists for DLL and
script custom actions, whose return value IS an action status - not for an
EXE's process exit code.

## Fix direction (mechanism is this seat's call)

- A custom action whose return value msiexec reads as an action status: a small
  DLL custom action (built by zig alongside the app) that runs
  `ghoztty.exe --install-maintenance`, waits, and returns
  `ERROR_INSTALL_USEREXIT` when the exe exits 1602. Most robust; no script
  engine, nothing for AV to flag.
- Or keep the EXE action at `Return="ignore"` and turn the answer into a
  property a later conditioned action acts on - which an EXE cannot set, so
  this needs a side channel (marker file + a DLL/script reader) and is
  strictly worse than the first option.
- Whichever lands, correct the two comments that state the false premise.
