# T1730 - Pressing Cancel on the 'already installed' prompt ends the installer with error 1722 instead of quietly

## In plain terms

If you run the Ghoztty installer for the version you already have, it now
asks "Repair or Cancel?". Pressing Repair works. Pressing **Cancel** makes
Windows show an error - "There is a problem with this Windows Installer
package. A program run as part of the setup did not finish as expected" - and
the installer ends as a failure. Cancel should just close the installer
quietly.

## Summary

Found by T1302, the first run of `test\win32\install-walkthrough.ps1` section D
against a real msiexec (package `Ghoztty-1.36.36-x64.msi`, `win-v1.36.36`).

The app side is right: msiexec's own verbose log records
`CustomAction MaintenancePrompt returned actual error code 1602`. What is wrong
is the premise in `dist\windows-installer\build-msi.sh` (the MaintenancePrompt
comment, point 3) and in `src\apprt\win32\install_maintenance.zig`'s header:
that 1602 from an EXE custom action is "the ONE non-zero code Windows Installer
reads as 'the user said no'". It is not. For an EXE custom action authored
`Return="check"`, Windows Installer treats ANY non-zero exit as a failure:

```
CustomAction MaintenancePrompt returned actual error code 1602
Note: 1: 1722 2: MaintenancePrompt 3: ...\ghoztty.exe 4: --install-maintenance --installed-version=1.36.36
Product: GhozttyT1299Test -- Error 1722. There is a problem with this Windows Installer package. ...
MainEngineThread is returning 1603
```

and at `/qr` the 1722 is a modal error box (the log shows it sitting for two
minutes until the harness killed msiexec).

The user-exit mapping (msiDoActionStatusUserExit -> 1602) exists for DLL and
script custom actions, whose return value IS an action status - not for an
EXE's process exit code.

## Fix direction (mechanism is this seat's call)

- A custom action whose return value msiexec reads as an action status: a small
  DLL custom action (built by zig alongside the app) that runs
  `ghoztty.exe --install-maintenance`, waits, and returns
  `ERROR_INSTALL_USEREXIT` when the exe exits 1602. Most robust; no script
  engine, nothing for AV to flag.
- Or keep the EXE action at `Return="ignore"` and turn the answer into a
  property a later conditioned action acts on - which an EXE cannot set, so
  this needs a side channel (marker file + a DLL/script reader) and is
  strictly worse than the first option.
- Whichever lands, correct the two comments that state the false premise.

## Goals

- [x] Cancel on the "already installed" prompt ends the installer quietly (msiexec 1602, no error box)
- [x] Repair still repairs
- [x] The false "1602 from an exe is a user exit" premise is corrected everywhere it was written down

## What landed

- **`ghoztty-msi-ca.dll`** (`src/apprt/win32/install_ca.zig`, built by
  `src/build/GhosttyMsiCa.zig` beside the exe on Windows targets). Export
  `MaintenancePromptCA`: reads `INSTALLDIR` / `ARPDISPLAYVERSION` via
  `MsiGetPropertyW` (msi.dll resolved at run time, so gnu and msvc builds link
  the same), runs `"<INSTALLDIR>ghoztty.exe" --install-maintenance
  --installed-version=<v>`, waits, and RETURNS `ERROR_INSTALL_USEREXIT` when
  the exe exits 1602, success otherwise. An exe that cannot start proceeds with
  the pre-armed repair rather than failing the install (that is what fixes a
  broken exe, and a failure would put back the 1722 box). It logs one line into
  msiexec's verbose log for each outcome.
- Pure half in `src/apprt/win32/maintenance_ca.zig` (status mapping + command
  line builder) with lane tests, wired through `install_maintenance.zig`.
- **`build-msi.sh`**: `<Binary Id="GhozttyMsiCa">` + a type-1
  `MaintenancePrompt` (`BinaryKey`/`DllEntry`, immediate, check);
  `SetMaintenancePromptCmd` removed. The read-back verifier now demands type 1
  from `GhozttyMsiCa` / `MaintenancePromptCA`, a `Binary` row, and the export in
  the DLL, and names the type-50 shape as the T1730 defect if it ever returns.
- The false premise corrected in `build-msi.sh`, `install_maintenance.zig`
  and `test\win32\install-maintenance.ps1`.

## Evidence

The installer is packaged by wixl, which needs Docker on this box, so the
validation package was the published `Ghoztty-1.36.36-x64.msi` rewritten to
exactly the authoring above (Binary row + type-1 action + the
`SetMaintenancePromptCmd` rows dropped), then walked by the real msiexec.
Finding on the way: patching a wixl package by deleting rows corrupts its
string pool (wixl under-counts shared strings; "Database string pool is
corrupted" at CreateShortcuts, B6 red). Pinning every touched string in a
scratch table first avoids it - the same defect family
`scripts\msi-test-identity.ps1` repairs after the fact.

- Cancel run log: `Invoking remote custom action ... Entrypoint:
  MaintenancePromptCA`, `MaintenancePromptCA: answer=cancel; ending as a user
  exit`, `Action ended: MaintenancePrompt. Return value 2`, `MainEngineThread is
  returning 1602`; no `Error 1722`, no 1603.
- Repair run log: `Return value 1`, `MainEngineThread is returning 0`.
