# T2593 - Film the window-edge drag with each pane in the window's composition tree (GHOZTTY_COMP_PANE_TREE=1), and with it on, skip the terminal's per-step region cut: with the tree off the region clips the visible swap chain, so T2577 could not drop it

## Summary

T2577 step 5 tried to skip the rounded-region `SetWindowRgn` on terminal panes during a window-edge drag (~1.8 ms cut phase per step). It never fired in the filmed configuration (CHROME+PRESENT+NOREDIR): there the terminal's swap chain is the composition target of its OWN child window, which the window region clips, so the region is visually load-bearing. Only with `GHOZTTY_COMP_PANE_TREE=1` (T2553) is the swap chain a visual in the window's tree, where the child HWND is input-only and its region decides nothing on screen.

Do: (1) film `scripts/resize-sync-onscreen.ps1` (ReleaseSafe, CHROME+PRESENT+NOREDIR) with and without `GHOZTTY_COMP_PANE_TREE=1`, alternating, bad frames per step + the `resize trace` phases; (2) with the tree on, defer the terminal's card region to a settle at `WM_EXITSIZEMOVE` (the T2577 step 5 sketch: skip when `noredir and in_size_loop and in_live_layout and surface.tree_visual != null`, leave `card_region_key` stale, `cutCardRegions()` on exit) and A/B that; (3) if the tree wins, say what stands between it and on-by-default.

## In plain terms

Resizing a window by its edge still shows the inside lagging a frame. One way the app draws terminal panes might remove two slow steps from every resize frame; this measures whether it does.

## Goals

- [x] tree on vs off filmed and scored
- [x] region-cut deferral A/B'd with the tree on

## Result (2026-11-01): the tree does not move the resize timing; the deferral lands, gated, as a small gain

Rig: ReleaseSafe @7a7fb8cc9 + this change, `GHOZTTY_COMP_CHROME+PRESENT+NOREDIR+RESIZE_TRACE`,
`scripts

- **The tree alone is neutral.** Every phase is within run-to-run noise of tree off, and
  so is the bad-frame count (146-150 vs 140-150). Its value is that it lets the compositor
  move a pane (T2570-T2573), not that it shortens a resize step.
- **The deferral fires and saves ~0.25 ms a step.** `resize trace region-deferred` logs on
  150 passes a film with the tree on and never with `GHOZTTY_RESIZE_TREE_REGIONS=1`; the cut
  phase goes 1.9 -> 1.6-1.7 and the deferred arms score the fewest bad frames of the tree
  arms in both rounds (144/141 vs 147/146), which is a lean, not a proof.
- **Why so little: the terminal's `SetWindowRgn` was not most of the 1.8 ms.** A one-off
  build stamped each pane inside the cut (stamps since removed). Each `resize trace` stamp
  ITSELF costs ~0.2 ms (a `GetWindowRect` plus a log line): the gaps between back-to-back
  stamps read 0.23-0.27 ms with nothing between them. Net of that, the viewer's region costs
  ~0.5 ms and the deferred terminal close to nothing (its 0.5 ms interval is the
  `region-deferred` line plus the stamp; the banner setters are no-ops without a banner).
  So the cut phase untraced is ~1 ms, not 1.8, and the trace inflates every phase it splits.
  Read the absolute phase numbers in T2577/T2598 with that in mind.
- **Settles correctly:** every arm passes the settled-frame checks and fails the same five
  live-lag checks (`.5` per drag and left-grow's flat strip, T2549), so the deferral breaks
  nothing the film checks.

Landed: `resize_paint.deferRegionCut` (pure, unit-tested) gates `applyCardRegions`: with no
redirection surface, inside the size loop and a live layout pass, a pane whose picture is in
the window's tree keeps its old region (key left stale), and `WM_EXITSIZEMOVE` re-cuts
(`cutCardRegions` when `noredir`). `GHOZTTY_RESIZE_TREE_REGIONS=1` restores the per-step cut.
The tree stays off by default; what stands between it and default is the card shape
(T2570: the tree visual is clipped to a rectangle, so its corners are square over the desk's
rounded edge) and the glide work (T2571, T2573), none of which this measured.
