# T1348 - A banner resize shows undefined pixels for a frame before the repaint lands

## Summary

Split out of T1344. BannerOverlay.updatePosition sets SWP_NOCOPYBITS on every resize, which tells Windows to discard the client contents rather than blit the still-valid bits. The stated reason - 'a frame of stretched, stale card' - does not match what SetWindowPos does: it blits 1:1 at the same client origin and never stretches. Since the class fully invalidates on a size change and updatePosition repaints synchronously right after, keeping the old bits would show the previous frame for that instant instead of undefined content. T1344 deliberately did not touch it because it is a theory with no demonstration on this box; this task is to find one (or rule it out) and then act.

## In plain terms

When the status banner above a pane changes size, Windows is told to throw
away its old picture first. The worry was that this flashes a frame of
garbage. We measured it on this machine: it does not. For the banner the
setting changes nothing you could see, and for the plain text boxes in the
viewer chrome it is the very thing that stops a stale image lingering. So the
setting stays, and two tests now hold that answer.

## Goals

- [x] Act on the answer (keep the flag; correct the comment that claimed a stretch)

## Outcome

Ruled out. Read back with `GetPixel` from a shown, alpha-0 layered popup (the
banner's window shape), growing 200x40 -> 320x64 with no paint in between:

| class style | flag | surviving region before repaint | after `UpdateWindow` |
|---|---|---|---|
| `CS_HREDRAW\|CS_VREDRAW` (banner, bars) | off | previous frame | new frame |
| `CS_HREDRAW\|CS_VREDRAW` | on | previous frame | new frame |
| none (e.g. `EDIT`, class style `0x4088`) | off | previous frame | **previous frame - stale** |
| none | on | previous frame | new frame |

Discarding the bits never clears them from the surface, so the flag cannot
produce undefined pixels in the region it discards; the strip a grow uncovers
is uninitialised with or without it, and `UpdateWindow` covers it in the same
frame. The flag is a no-op where the theory looked (the redraw classes) and is
load-bearing on the classes without redraw bits, which `place()` also moves
(`ViewerTOCPanel` places its filter `EDIT` through it). Kept.

Found on the way: `chrome_reposition.zig`'s tests, T1392's included, were never
compiled into the win32 lane — `-Dtest-filter=chrome_reposition` matched
nothing. It is now listed in `src/apprt/win32.zig`'s test block.
