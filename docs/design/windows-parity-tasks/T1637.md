# T1637 - session-resume-offset cycle A.1 can see the agent head run ahead of the recorded offset

## Summary

test\win32\session-resume-offset.ps1 failed A.1 'requested offset == agent head (527 vs 673)' on the FIRST kill/restore cycle, then passed clean on an immediate re-run (cycles A.2/A.3 were exact in both runs). Either output lands between the manifest's offset snapshot and the kill in the first cycle only, or the first cycle snapshots earlier than the others. The resume itself was honored and unclamped, so the defect is in what the first cycle records, or in the harness asking the question too early. A guard harness that is red one run in N costs the loop a turn each time it fires.

## In plain terms

One of the session-restore tests failed once, back in September, on the first of
its three kill-and-restore rounds, then passed on an immediate re-run. Nobody lost
any output; the question was whether the test or the app has a timing hole. It
no longer reproduces, so the card is closed rather than worked blind.

## Resolution

Not reproducible. Two things changed underneath the original red since it was
filed (2026-09-17). Either could have produced a 146-byte jump in the agent head
for a single cycle, but neither can be named as the cause: T1494/T2005 gave each
run its own agent lineage and state dir, so an agent shared with another suite
no longer feeds the session. The OPEN/ATTACH `req_id` correlation stops a late
reply from binding the wrong session. The harness's settle loop
(`Provoke-ManifestWrite`, T804) is unchanged and holds on every cycle measured.
If A.1 goes red again, reopen this card with the attach line and the run's
`app-A-1.err.txt`. Do not file a new card.
