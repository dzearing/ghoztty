# T3044 - PA-V12: viewer documents and the files a page loads are read whole and synchronously on the GUI thread, then copied again (ViewerPane.zig:5120)

## Summary

PA-V12 (audit-1, T2963). Resources are read whole and copied into an HGlobal stream (ViewerPane.zig:4822-4838, :5019-5037, :5120-5129); media ranges are 8 MB chunks (viewer_range.zig:27); document stats and reads are synchronous (:4528, :2087-2090, :5076). Cost (estimated): 2x resource size per request; a slow or network path stalls every terminal in the process. Fix: file-backed stream (SHCreateStreamOnFileEx), 1-2 MB range chunks, document reads on a worker_pool job. Risk: share modes while an editor saves. Findings: docs/design/perf-audit/audit-1/V-findings.md.

**Scope as landed (2026-11-17):** the copy and the chunk size. The document read and the per-request stat probes moving off the GUI thread split to **T3224**.

## In plain terms

When a viewer pane shows a page, a picture or a video, Ghoztty used to load each file into memory and then copy it a second time before handing it to the page, and fed videos in 8 MB bites. Now each file is loaded once, straight into what the page reads, and videos are fed in 2 MB bites — so viewing big media costs about half the memory and each bite blocks the app for a quarter as long.

## Goals

- [x] page resources, bundled viewer assets and pictures are read once, straight into the response stream (no heap copy)
- [x] media byte ranges are served in 2 MB chunks, not 8 MB
- [x] an editor saving a file the page is reading is never refused (the read keeps std.fs's share-read/write/delete handle)
- [ ] the document read off the GUI thread — split to T3224
