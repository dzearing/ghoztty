# T2097 - Both go-loop lanes sat 2.5 days on an expired Claude login (10-18 06:32 to 10-20 17:37) because the watchdog knows it is BLOCKED(api-error) but only nudges and logs; a block that only the user can clear never reaches the user

## In plain terms

When the loop's Claude sign-in expires, nothing the loop does can fix it:
only you typing `/login` can. It used to keep retrying in silence, and for
2.5 days nobody knew it had stopped. Now it stops retrying and tells you
once. You get a Windows notification, a banner on the loop's own window
saying "type /login here", and a dashboard bar that says it needs you
instead of saying it will clear by itself.

## Goals

- [x] An expired login is recognised as a block only the user can clear
- [x] The watchdog stops retrying at it and tells the user once (again after 12h)
- [x] The user hears about it even with Windows notifications off (pane banner)
- [x] The health line and the dashboard bar say what to do, not "it will lift"

## Summary

Watchdog -Status read 'recovery: 171 re-entry(s) inside one unmoved turn - BLOCKED(api-error): Login expired - Please run /login'. Resolve-LoopBlocker already classifies the blocker; spend-limit blocks clear on their own (ResetsAt) but a login expiry never does. Split the blocker kinds into self-clearing vs needs-the-user; for needs-the-user, stop re-entering (each nudge is wasted) and raise a non-focus-stealing signal the user will actually see once: a Windows toast notification (no focus change) plus the dashboard's loop card and go-loop-health's verdict naming the remedy ('run /login in the [go-loop] window'). Re-arm the toast only when the blocker text changes or after 12h. Acceptance: gate-negatives-style construction of a transcript ending in 'Login expired' proves the watchdog switches to the notify path and does not nudge.
