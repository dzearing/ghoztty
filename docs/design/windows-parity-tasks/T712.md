# T712 - The Windows machine chooser is modal; Mac's New Window picker is modeless

## Summary

win32 MachineChooser.zig disables its owner window (EnableWindow(owner, 0)) while it is up, so the terminal behind it is frozen for as long as the picker is open. Mac made the same picker modeless in 78a21daa8 precisely so a user can keep working while deciding. Relates to T603 (Ctrl+W over the chooser). Found by the T684 sweep.

## In plain terms

Open "New Window" on Windows and the terminal behind the picker went dead: you
could not type in it, close a tab, or watch the session list react to anything
you did, so the list you were choosing from was frozen at the moment you opened
it. Now the picker floats above its window and leaves the terminal alone — work
behind it, and it is still there with a live list when you come back. Mac made
the same picker modeless for exactly this reason.

## Goals

- [x] the window behind the picker stays interactive while it is open
- [x] the picker stays visible above its own window while you work behind it
- [x] the picker still filters, still picks, and still closes on Escape
- [x] an acceptance harness that fails when the picker goes modal again

## Validation criteria

- [x] With the chooser open, `IsWindowEnabled` on the owner terminal window is
      TRUE — verified by `test\win32\chooser-modeless.ps1` arm A, which FAILED
      against the pre-fix build and passes after it.
- [x] The terminal behind the open picker takes activation and acts on a chord
      (ctrl+shift+d really splits it) — arm B of the same script.
- [x] The picker stays visible and directly above its owner with nothing
      sandwiched between after the terminal is activated — arm C
      (`Get-TestOverlaySandwich` = `0:`).
- [x] The picker still works afterwards: the filter narrows and restores the
      list, Escape dismisses it, no panic in the log — arm D.
- [x] The harness discriminates: `-NegativeControl` inverts arm A and fails.
- [x] The neighbouring claim was corrected rather than left lying:
      `test\win32\chooser-close-chord.ps1` asserted the owner was DISABLED; it
      now asserts ENABLED and is ALL PASS (16 assertions).
- [x] Standing floor green: `scripts\floor-lane.ps1 -Lane all`.

## Translation note (my call, not a decision)

Mac's panel is `.floating` - above every window in the app. On Windows the
picker is an OWNED popup, so it floats above the window it was opened from and
travels with it, and activating a DIFFERENT ghoztty window puts that window in
front of it. That is the native behavior for an owned palette here and is what
every other owned dialog in this app already does; an app-global topmost picker
would be the foreign thing. Recorded rather than filed as a decision: it is a
mechanism-level translation, and the difference is only visible with two
ghoztty windows open at once.
