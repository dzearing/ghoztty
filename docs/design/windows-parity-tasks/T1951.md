# T1951 - Low-power rendering when the GPU is software (WARP) or the session is remote: cap presents per pane, never draw hidden windows, and turn off glass, blur, glow and blink

## In plain terms

Over Remote Desktop every pixel Ghoztty changes has to be drawn in software
and sent over the wire. The glass panes, blur, focus glow, blinking cursor
and dimmed panes are the most expensive pixels and the least needed there.
When Ghoztty sees it is running in a Remote Desktop session, it switches
them off by itself, and switches them back on when the session returns to
the local console.

## Rescoped 2026-10-14 21:30 - GitHub #13 update (read this first)

The user's agent measured dzearing1 on 1.39.8 (GitHub #13 comment,
2026-10-15T04:19Z):

- **dzearing1 is a Windows 365 Cloud PC with no GPU.** Ghoztty loads its
  bundled Mesa `opengl32.dll` (26.2.1) on D3D12 "Microsoft Basic Render
  Driver" (WARP). A `cdb` sample showed **32 WARP pool workers in
  `d3d10warp!PixelJITRasterizeTriangleT`**, fed by per-pane renderer
  threads waiting on fences. Load: 11 windows, 12 terminal + 4 viewer
  panes, 12.5-15.7 cores, 2.1 GB, DPI 192 (4x the pixels of 96).
- **Turning the pane effects off made NO measurable difference** (about 14
  cores either way). So effects-off alone, the original scope below, does
  not fix this. The cost is presents/s x pixels, rasterized on the CPU.
- 1.39.8's sidebar fix held (no outline lines), but it was not the CPU.

New scope, in priority order:

1. **Detect a software renderer**, not just RDP: after context creation,
   read `GL_RENDERER` / `GL_VENDOR`. "Microsoft Basic Render Driver",
   "WARP", "llvmpipe" or "softpipe" (or D3D12 adapter flags
   `DXGI_ADAPTER_FLAG_SOFTWARE`) means software. OR it with
   `SM_REMOTESESSION`. Log the decision once. A Cloud PC is detected by
   the renderer, not the session.
2. **In low-power mode, cap presents per pane.** The focused pane runs at
   up to 30 fps. Visible unfocused panes get 4 fps. Hidden ones get 0
   (step 3). Animated cells (Claude Code's spinner) are coalesced to the
   cap, and the 500 ms forced present is dropped for unfocused panes.
3. **Never present a window that cannot be seen** (minimized, DWM-cloaked,
   fully occluded, background tab). Mark it dirty and draw once on reveal.
   This applies in every mode, but matters most here. (Moved up from
   T1950; T1950 keeps measurement and the probe script.)
4. **Viewer panes**: WebView2 also rasterizes in software here. In
   low-power mode, pause rendering of hidden viewers
   (`ICoreWebView2Controller.IsVisible = false`) and check
   `viewer_pane` / `io_remote` log volume (now the top two log sources).
5. Effects off (the original scope below) stays, as a cheaper frame. It is
   no longer expected to be the main win.

Replacement validation (this supersedes the CPU line below):
- [ ] Force the software path on the test box (a seam that selects the
      bundled Mesa with `GALLIUM_DRIVER=d3d12` on WARP, e.g.
      `D3D12_ADAPTER=warp` / the existing T1251 old-driver switch). With
      16 panes (12 terminal, 4 viewer, about 8 animating like Claude Code)
      in 11 windows at DPI 192, idle app CPU is **under 1 core**, against a
      measured baseline with low-power off. Per-thread sample before and
      after, including the WARP pool.
- [ ] The low-power decision is logged with the renderer string. A
      hardware GPU box does not enter it unless remote.
- [ ] Typing echo in the focused pane stays at full rate (measured) while
      the others are capped.

## Summary

User (2026-10-14): "i am wondering if a short term fix is that if we detect
a terminal session, we disable these automatically". This is step 2 of
T1950, split out to ship first. T1950 keeps the hidden-window and
unseen-pane present skip, and the measurement.

Context: the user's Windows remote machine, reached through Windows App,
runs 1.39.8 and uses 15 cores and 2.5 GB with 24 panes in 12 windows.
Locally the same build is fast.

Behavior:

- **Detect**: `GetSystemMetrics(SM_REMOTESESSION) != 0` at startup (the
  check `DimOverlay.zig:158` already uses), and re-check on
  `WM_WTSSESSION_CHANGE` (`WTSRegisterSessionNotification`), because one
  logon moves between the console and RDP.
- **While remote**, the effective values (not the user's file) are:
  `macos-pane-style = flat`, `macos-pane-glass = false`,
  `background-blur = false`, `cursor-style-blink = false`,
  `unfocused-split-opacity = 1`, no focus-glow animation, and no
  sidebar shimmer.
- **Back on the console**, restore the configured values live. No restart.
- **The user can override.** *Assumption (recorded, not asked):* a value
  the user set explicitly in the config file wins even in a remote session.
  Only defaults are swapped, so someone who wants glass over RDP keeps it.
  If the config layer cannot tell "set" from "default", add one key,
  `remote-session-effects = auto|on|off` (default auto), on BOTH platforms
  (Mac: Screen Sharing / `CGSessionCopyCurrentDictionary`), per the
  symmetry rule.
- **Say so**: one notice when it switches ("Remote Desktop: visual effects
  off to keep typing fast"), plus a line in the log.

Ship it the turn it closes: the auto-filed publish request is honoured at
the task boundary. Report the `win-v*` version.
