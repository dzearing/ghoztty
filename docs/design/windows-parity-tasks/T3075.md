# T3075 - The app's short-lived worker threads (update check/download, dial, probe, restore, roster, viewer servers - ~35 std.Thread.spawn(.{}) sites in src/apprt/win32) still commit 16 MB each while alive, and nothing stops a new .{} spawn

## Summary

T2985 moved the pane pools and the long-lived app threads to os/thread_stack.config (64 KB commit, same 16 MB reserve; -547 MB after a pane cycle). The transient workers in src/apprt/win32 (App.zig update threads, MachineConnectionPool/activity_dial/RemoteReconnect dial workers, SessionRoster, RestoreAll*, ViewerPane serve threads, AgentIntegration*, PathInstaller, url_scheme, ArpOrphanSweep, ...) still spawn with .{}, so each holds 16 MB of commit for its lifetime - a burst of dials or a restore fan-out spikes private bytes by 16 MB per thread. Move them to thread_stack.config and add a harness-floor source audit that fails on a new std.Thread.spawn(.{} in non-test app code (src/apprt/win32, src/remote non-agent, src/termio, src/renderer). Agent-image sites are T3015.
