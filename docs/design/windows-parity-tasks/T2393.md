# T2393 - git-commit-guard's push-time pull --rebase leaves an 'autostash' entry on the SHARED stash stack when the rebase conflicts (2026-10-28 lane b, T2366 commit: two autostash entries left behind, holding guard stamps), which a later turn could pop as its own

## In plain terms

The two loop lanes share one git "stash", a shelf where git can set work aside
for a moment. Turns were pulling with an option that shelves everything dirty
and puts it back afterwards. When putting it back clashed, git left the work on
the shelf with no label, and a later turn could pick it up as if it were its
own. Now there is one sanctioned pull that never uses the shelf. The option is
refused before it runs, and every turn is told about anything still sitting
there.

## Goals

- [x] find what actually creates the autostash entries
- [x] give turns a pull that needs no autostash
- [x] refuse the autostash flag before it runs
- [x] report leftover entries at every claim

## Summary

**The title's premise was wrong.** The commit guard never autostashes: it has
pinned `rebase.autoStash=false` / `merge.autoStash=false` since T1057. The
reflogs show the real source. Turns hand-typed `git pull --rebase --autostash`:
66 times in lane A's reflog, at least 10 in lane B's
(`pull -q --rebase --autostash (start)` and similar). They did it because a
bare `pull --rebase` refuses any dirty tracked file. At pull time the tree
always holds one: the task file `next -Claim` has just edited, or a guard stamp
left by a harness run. Autostash puts all of it on `refs/stash`, and every
worktree of the repo shares that stack. When the pop conflicted (a stamp the
pull had also rewritten), git kept the entry "for safety". On 2026-11-05 four
entries were sitting there (2026-10-22, 10-26, 10-29, 11-01), all holding guard
stamps.

The fix has three parts:

1. **`git-commit-guard.ps1 sync`** is the pull. With nothing unpushed it runs
   `pull --ff-only`, which leaves every dirty file the incoming commits do not
   touch exactly as it is. When a dirty file overlaps an incoming change, it
   refuses without touching anything. Dirty guard stamps are parked in memory
   across the pull and put back under the keep-the-newer rule. With local
   commits it runs the same stamp-parked rebase or merge pull as the
   rejected-push path (`Invoke-ParkedPull`, extracted from
   `Invoke-PushWithRebase`). It never uses the stash. It names any autostash
   litter it sees.
2. **`scripts\hooks\deny-git-autostash.ps1`** is a PreToolUse hook on
   `Bash|PowerShell`. It refuses `--autostash`, `-c rebase|merge.autoStash=true`
   and `git config ... autostash true` on any shell segment whose command is
   git, and points at `sync`. `--no-autostash` is allowed, and so is a segment
   that only mentions the flag (grep, a reflog read). It fails open.
3. **The claim reports `STASH LITTER`** (status line, registered in
   gate-negatives) with the count and the oldest entry, so the four existing
   entries and any future ones are visible every turn. Dropping them is
   destructive, so that is left to the user.

go.md step 4 ("pull before starting") now names `sync`.
