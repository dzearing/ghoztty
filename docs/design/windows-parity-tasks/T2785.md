# T2785 - A terminal pane that was resized strands a window-sized GPU allocation about one close in seven on the composition path (0.2-0.45 MB a window on average, never settling)

## In plain terms

Closing a window that holds two terminals and a document viewer still leaves a
little graphics memory behind - well under a megabyte a window on average -
so a long day of opening and closing such windows slowly grows the app. Closing
simpler windows no longer does. Since 2026-11-08 we know the trigger is
resizing: a terminal whose window (or split) changed size leaves the memory
behind about one close in seven; one that never resized does not.

## Goals

- [x] re-measure after T2782's warm-up fix (A8 green, strand still real)
- [x] bisect to the trigger (a resize, composition path only)
- [x] attribute the stranded allocation (the interop shared texture)
- [x] release it (shared-handle interop texture, 2026-11-08 turn 96)

## Summary

Found closing T2606 (2026-11-07, lane b, debug, RTX 4090, composition present
default ON, `GHOZTTY_PANE_LAYER` unset). T2606 fixed the main strand: the
overlay layers' `releaseShared` committed BEFORE releasing the pane's root
visual, so when an overlay outlived its presenter the root and its swap chain
stayed pending on an uncommitted DComp device. After that fix, GPU dedicated MB
per `test\win32\window-close-memory.ps1 -Report` run:

| shape | cycles | baseline -> end | reading |
|---|---|---|---|
| single (`--undo-timeout=0`) | 20 | 73.4 -> 76.4 | one 3 MB step, then flat (was 64.3 -> 106.4 over 40 before) |
| split (COMP_PRESENT=1, PANE_LAYER=0) | 20 | 69.9 -> 77.4 | fills to cycle 8, flat for 12 |
| viewer | 20 | 64.4 -> 70.4 | two 3 MB steps, 0.59 MB/window, passes |
| **full** (default) | 30 | 69.9 -> 89.4 | **still climbing in 1.5 MB steps to cycle 30**: A8 1.06 MB/window, red |
| full (default) | 10 | 69.9 -> 77.4 | A8 2.05 (mostly fill at 10 cycles) |

So the remainder needs the three-pane shape. A 1.5 MB step is about one
half-width pane's swap-chain buffers, which suggests the same kind of
last-holder-without-commit path somewhere T2606 did not cover - candidates:
the presenter's own `releaseCom` when a commit is refused mid-`BeginDraw`
(`bandCommitRetries`-style `DCOMPOSITION` refusal while the window thread is
uploading an overlay), a `Layer` whose owner is never `deinit`ed on window
close in a multi-pane window, or the chrome's `Overlay`/desk visuals.
Method that worked for T2606: bisect by disabling a source (a temporary env
knob that makes `Presenter.overlayTree` return null), 14-20 cycles each.

## Fix (2026-11-08, turn 96, lane a)

The interop shared texture is now created with `D3D11_RESOURCE_MISC_SHARED`
(`createShared` in `src/renderer/gl_comp_present.zig`), falling back to a plain
texture if a driver refuses it; `GHOZTTY_COMP_SHARED_TEXTURE=0` restores the
plain shape for an A/B. Without the flag the GL driver opens the texture's
allocation through an internal alias that, about one close in seven after a
resize, outlived a successful `wglDXUnregisterObjectNV`; with it the driver
opens the resource by its share handle and nothing is left behind. Single
`-Resize` 60 cycles and the default full shape 30 cycles are both dead flat.
A kernel ETW (DxgKrnl) trace was not needed (and is not possible from an
unelevated session).

## What was left (re-measured 2026-11-08, lane a, debug, after T2782)

T2782's adaptive warm-up waits out the driver's upload-pool fill, and with it
the full shape is **green**: A8 0.38 MB/window over 30 cycles, 0.22 over 60.
But the 60-cycle run never settles (74.4 -> 87.9 MB, 1.5 MB steps at 9, 17x2,
28, 37x2, 48, 54, 59), so the strand is real, intermittent (roughly one window
in seven) and below the budget. Bisect, 60 cycles each, GPU dedicated MB:

| arm | result |
|---|---|
| `-Shape single` | **flat** after one 3 MB step at cycle 9 (A8 0.07) |
| `-Shape split` (no viewer) | strands +10.5 (onset cycle 26) - viewer not needed |
| split + `GHOZTTY_PANE_LAYER=0` | strands +13.5 - not the pane layer |
| split + `GHOZTTY_COMP_PRESENT=0` | **flat**, A8 0.00 - composition path only |
| split, overlays kept off the tree (temp knob in `OpenGL.compInit`) | strands +10.5 - not the overlay layers |
| `-Shape single -Resize` (700x500) | strands +15 in 3 MB steps - **a resize is the trigger** |
| single `-Resize` + `GHOZTTY_COMP_RESIZE_BUFFERS=1` | strands +21 - not the swap2 source-size path |
| single `-Resize`, pane context on a hidden 1x1 helper so the pane window has NO pixel format (lane a, 2026-11-08, experiment patch, reverted) | strands 58 -> 70 in 3 MB steps (12, 31, 34, ~42), A8 0.30 - **not the pane window's WGL drawable** |

The last arm rules out the leading candidate below: with the context made on
a hidden helper (the T2615 presenter-path shape) the pane window never had a
pixel format, so the driver had no default framebuffer to re-size on it, and
the strand was unchanged. What a resize still reallocates under the pane HWND
on this path is its DComp target / redirection surface and the swap chain's
own buffers (grow-only, but the shrink arm strands too), so the attribution
trace below is the next step, not another whole-window arm.

**Attributed (2026-11-08, turn 94, lane a): the stranded allocation is the
pane's interop SHARED TEXTURE** (`createShared`/`destroyShared` in
`src/renderer/gl_comp_present.zig`). Evidence: the step is exactly its
bucketed size - 1024x768x4 = 3.0 MiB for a single pane, 512x768x4 = 1.5 MiB
for the split's half pane - and with a temporary knob that sizes it exactly
(recreated on every resize) the steps became ~2.6 MiB and ~1.0 MiB, the
pre-resize (876x673, pitch-padded) and post-resize (576x423) textures. So
mid-life releases strand too, not only the close-time one. Ruled out this turn
(single `-Resize`, all arms reverted):

| arm | result |
|---|---|
| refcount logging in `releaseCom` (40 cycles) | every close identical: commits S_OK, swap -> 0; context 2 / device 19 / dcomp 8 still held by the window thread's overlay/DComp refs - no per-close difference |
| `ID3D11DeviceContext::Flush` after the swap release (D3D11 deferred destruction) | 60 cycles 67.4 -> 82.4 in 5 steps = the unfixed rate; **not it** |
| exact-size shared texture | 50 cycles, 8 steps of ~2.6/~1.0 MiB (+17.8) - the attribution above |
| exact-size + `glFinish` before unlock/unregister in `destroyShared` | 50 cycles, 2 steps (+5.5) - fewer, NOT zero; inconclusive given the run-to-run spread (one 40-cycle flush run also showed 2 steps and the 60 then did not) |
| `glFinish` before unlock/unregister, default bucketed texture (turn 95) | 60 cycles, 5 steps of 3 MB (19, 20, 25, 28, 59; +15), A8 0.35 = the unfixed rate; **glFinish ruled out** |
| close path skips `wglDXUnregisterObjectNV`, relies on `wglDXCloseDeviceNV` (turn 95) | **far worse**: every window strands its whole pane D3D11 device (+54 threads, +215 handles, A8 19.9 MB). Closing the interop device does not drop registrations, so the per-object unregister is required |

What the last arm teaches: a missed unregister strands the entire device
(threads climb), while the 1-in-7 strand keeps only a texture-sized allocation
with threads flat. So the D3D device dies normally and the survivor is an open
of the texture's allocation held on the GL driver's side past a successful
unregister. App log: exactly one presenter per window, no rebuild or fallback.

Next arms (exact-size knob for a faster signal): release the D3D texture
BEFORE `wglDXUnregisterObjectNV` vs after; `glDeleteRenderbuffers` before the
unregister; create the texture with `D3D11_RESOURCE_MISC_SHARED` (the driver
may then open it by handle instead of an internal alias); and a per-allocation
trace (ETW `DxgKrnl` allocation events across one resize-and-close) to name
the owning process/adapter object outright.

Threads stay flat in every arm, so no pane D3D11 device is stranded (a stranded
one keeps ~55 driver threads, T2772), and the app log shows every presenter
created with no composition failure or fallback. A SHRINK allocates nothing new
in the presenter (shared texture and swap buffers are grow-only), yet strands
anyway, and the step is a window-sized 3 MB (the size BEFORE the resize). So the
leftover is most likely not one of the presenter's own D3D objects but what a
resize reallocates under the pane HWND on the composition path, where
`SwapBuffers` never runs: the WGL drawable's default framebuffer, or the
pane's redirection / layered surface (the T2499 shape: a WGL child's
allocation held past its own destruction). Next instrument: per-allocation
attribution (D3DKMT / `GPU Adapter Memory` per-segment, or a PIX/ETW
`DxgKrnl` allocation trace across one resize-and-close), not more 18-minute
whole-window arms. A resize test is `-Shape single -Resize`, the fastest
reproducer.
