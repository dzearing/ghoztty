# T1701 - task-dashboard.ps1 never returns when its output is redirected to a file

## Summary

Observed 2026-09-23 closing T931: 'task-dashboard.ps1 -NoPane *> file' printed 'serving http://localhost:7788/' and then hung until the tool timed out (300s); the server itself was up and answering 200. Likely the detached node server inherits the redirected stdout/stderr handles, so the caller's pipe never closes (same shape as the GUI-inheriting-stdout hang). A turn that restarts the dashboard from a script stalls. Fix: start the server with its own log redirection / no handle inheritance, and add a harness leg that runs the launcher with output redirected under a timeout.

## In plain terms

When a script (or the loop) restarted the task dashboard and captured what
the launcher printed, the launcher said "serving" and then the script sat
frozen until it gave up, even though the dashboard was already up. Now the
launcher hands control straight back and the dashboard keeps running.

## Goals

- [x] the launcher returns to a caller that captures its output
- [x] the server still writes its stdout/stderr logs under `temp\`
- [x] a harness leg catches the hang, and shows it would catch the old code

## Root cause

`Start-Process node -RedirectStandardOutput ... -RedirectStandardError ...`
makes PowerShell call CreateProcess with `bInheritHandles=TRUE`, so node
inherited every inheritable handle in the launcher, including the write end
of the caller's stdout pipe. node holds it for as long as it serves, so the
caller never reads EOF. Clearing HANDLE_FLAG_INHERIT on the launcher's three
std handles was tried and closed only the stderr leak: powershell.exe keeps a
second inheritable copy of a redirected stdout (measured 2026-11-21).

Fix: start a hidden `cmd.exe /d /s /c "node ... 1>log 2>err"` through
Start-Process WITHOUT any -Redirect switch. That path goes through
ShellExecuteEx, which passes no handles, and cmd opens the two log files
itself.
