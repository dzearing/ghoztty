# T2250 - A pane name is still global across windows on Windows: a second window's +split --name=draft reuses (and +close closes) the first window's pane; +split replies before the pane exists (main 71da9a680)

## Summary

Mac 71da9a680: pane names belong to their window (TargetLookup): a name resolves in the caller's window first, then as a window name, then as the single other window's pane; two or more matches is an ambiguity error, never a pick. The CLI sends the caller's pane on every request as an additive caller_pane field (src/apprt/ipc.zig, merged via T2249). +split now waits (bounded) for the pane to exist and be laid out, and replies with its id, its window and whether it is on show, or fails with the reason - including the agent-backed path. A non-focusing split into a row with no room is FEATURED (comes on show; the caller becomes the strip if it must and keeps the caret) instead of being born a strip. Every +split and ambiguous lookup is logged. Port to win32 IpcRegistry/IpcHandlers: resolve with caller_pane scope, the honest bounded reply, the featured-not-strip placement, and acceptance in test/win32 for two windows sharing a name.

**Scope as built (2026-10-25):** everything above except the featured-not-strip placement, which is a stacked-panes layout change of its own and is split out as **T2257** (the reply already says when a new pane came in as a strip). The skill split in the same Mac commit is **T2258**.

What landed:

- `src/apprt/ipc/target_lookup.zig` - the Mac's `TargetLookup` policy and ambiguity wording, pure, with the Mac's tests.
- `IpcRegistry` holds a list, not a map: a window name is global, a pane name is held once per window, and the pane's window is read live from the trees (a name follows a moved pane). `lookup(name, caller)` applies the policy; `holderIn(name, window)` is the split collision's question; `ambiguityError` names the windows.
- `IpcHandlers.dispatch` reads the request's `caller_pane`, resolves its window into `App.ipc_caller_window` for the request (saved/restored, so a nested dispatch is safe), and every `ipcLookup` starts there. Not-found replies become the ambiguity error when that is why (`missingResponse`); `+close` of an ambiguous name fails instead of reporting an idempotent success.
- `+split --name` collides only with a pane in the window it lands in (`split_name_collision` lost `in_anchor_window` and the "not the window this split was for" wording, as on the Mac). A second window gets its own pane of that name.
- `+split` replies `created pane '<n>' (<id>) in window '<w>'[, showing <v>][; it is minimized to a strip ...]` (`args.splitCreatedMessage`, Mac wording), fails when the new surface has no pane, and logs every outcome as `IPC +split: caller=... window=... pane=... outcome=... onShow=...`.
- `+new-window --target=<a pane's name>` fails (Mac). The in-app `ghoztty://` path reports an ambiguous name (`url_scheme.Failure.ambiguous_target`).

Why the win32 split needs no bounded wait of its own: `newSplitAt`/`newViewerSplitAt` create the pane synchronously on the GUI thread (failure is a returned error, not a later log), and the agent-backed path's reply was already held until the session binds (T1612 `ipc_session_await`). On show is read from the stacked-panes grid as laid out at that moment (`paneOnShow`).

## In plain terms

When two terminal windows each ran an agent that opened a side pane with the same name, the second agent's pane quietly "reused" the first window's pane instead of opening its own, and closing it from one window could close the other window's pane. Now each window owns its pane names: the second window gets its own pane, a command from a window means that window's pane, and when a name is genuinely ambiguous the command says so instead of guessing. The reply to opening a pane now names the pane it created.
