# T1182 - Dashboard lists PR review candidates in plain language: what it does, what changed inside, and what to test

## Summary

The user reviews PRs, so the dashboard is where they should see them. Add a review-candidates view listing every open PR with a plain-language summary of what it does (no commit-speak), expandable detail on the content within it, and an explicit what-to-test section so approving is a checklist rather than a diff read. Complements T1059, which puts PR CI health in the daily digest.

## In plain terms

Pull requests waiting for a review used to be visible only on GitHub or as one
line in the morning digest. The dashboard now has a **Reviews** page: one card
per open pull request saying, in plain words, what it does and what to try
before approving it, with the commits and files tucked behind a click. A pull
request whose description never said either is called out instead of left blank.

## Goals

- [x] a Reviews view in the dashboard nav, badged with the open-PR count
- [x] each PR card: status band (needs a turn / in flight / ready), plain "what it does", a "what to test" checklist
- [x] expandable "what's inside" (commits + files with line counts) and the full description, which stay open across the 5-second refresh
- [x] missing summary / missing test steps are SAID, never invented; an unreachable GitHub reads "unknown", never "nothing to review"
- [x] `ship-feature.ps1 pr` notes a description missing either heading, and the ship-workflow doc says to write both

## Design (mechanism calls, recorded per go.md 5b)

- The data is `scripts\pr-health.ps1 -Format json -Detail` - the same script the
  digest uses, so the verdicts, the `--repo` rule and the timeout have one owner.
  `-Detail` adds `Review { Summary, ToTest, Commits, Files, Additions, Deletions, Body }`,
  parsed from the PR body by heading: `## What it does` (or Summary / In plain
  terms / Overview) and `## What to test` (or How to test / Test plan / Testing).
  No named summary falls back to the first prose paragraph; code fences and the
  Claude Code boilerplate line are ignored.
- The detail read caps at 25 PRs: GitHub refused the 100-PR query with
  commits outright ("exceeds the maximum limit of 500,000" nodes) on the first
  live run.
- The server serves it at `/api/prs` from a 3-minute async cache (bootState's
  shape, so the 5-second poll never waits on GitHub - T1660); `/api/data`
  carries only `reviews { open, needs }` for the badge. `GHOZTTY_PRS_JSON` is
  the fixture seam.
