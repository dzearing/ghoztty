# T3217 - perf-baseline's viewer phase never opens a large-patch diff file, so a diff viewer's patch memory (T3039) has no measured baseline

## Summary

`scripts\perf-baseline.ps1`'s viewer phase (T3033) opens `git-status:` on a scratch repo of two tiny files, so the selected file's patch is a few bytes. T3039 removed four transient copies of a diff patch (up to 8 MB each) and the 8 MB the pane kept after pushing it, but no baseline phase can see either cost: the T3039 criterion "app private bytes after opening a large-patch diff file return to within 1 MB of before" had nothing to run against.

Fix: give the viewer phase a large-patch sample - a file in the scratch repo with a multi-megabyte modification, opened with `+split --view=git-status:` (or `git-diff:`) and selected - and record app private bytes before, at peak while the patch is pushed, and after the pane settles. Add the metric to the `-Compare` tolerance table.

T3039's own proof stands without it: a none-lane test asserts the UTF-16 builder equals the widened UTF-8 call and never regrows, and the win32 host-floor test asserts `probe.patch == null` after the push.

## Validation criteria

- [ ] perf-baseline viewer phase reports peak and settled app private bytes around a >= 4 MB patch
- [ ] settled private bytes return to within 1 MB of before the patch was opened
- [ ] `-Compare` covers the new metric with a stated tolerance
