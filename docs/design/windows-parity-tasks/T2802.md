# T2802 - Composition step 5d-5c: the sidebar list transitions (scope slide and fold) run on the compositor - the before picture as a visual whose offset/clip is declared once over the live column - instead of composing three DIBs on every TIMER_XFADE frame

## Summary

paintTransition (PaneSidebar.zig) paints the material, the live frame and composes them with the before picture in software every frame (pane_sidebar_transition.zig composeSlide / composeFold). On T2765's tree, hang the before picture (and, for the slide, the after) as visuals with the slide's offset and the fold's clip animated by DComp, so a UI stall does not freeze the transition. Oracle: film with stall seam + stepped control.

## In plain terms

Switching the sidebar between "this window" and "all windows" slides the
list sideways, and folding a window's group open or shut reveals or covers
its rows. Until now the app drew every frame of those motions itself, so
whenever the app was busy the list froze half-way. Now each motion is drawn
once and handed to Windows, which plays it smoothly however busy the app is.

## Goals

- [x] the scope slide is drawn once and played by the system compositor
- [x] a fold and an unfold are drawn once and played by the compositor
- [x] if the compositor is unavailable or lost mid-way, the old stepped path takes over
- [x] an A/B knob keeps the stepped path reachable, so the oracle can tell who moved it

## Design

`pane_sidebar_transition_comp.zig` (new, pure helpers unit-tested in both
lanes): three layers on the column's own tree (T2765). `base` is the bare
material over the moving band, opaque and still, with a static clip that
cuts its children at the band's edge (Mac's clipped list). Scope slide:
`back` = the list before, `front` = the list after, each masked to where it
differs from the material (`cropMasked`), X offset + opacity animated on
`slideAt`'s end points along the same ease the stepped path uses. Fold:
`front` = the group's own rows in place with an animated clip bottom,
`back` = the short frame from the header down, masked, with an animated Y
offset riding the band edge (`composeFold`'s top-anchored reveal).
`comp_overlay.Layer` gains `animateOffsetX` and a static `setClip`.
`PaneSidebar.paintTransition` declares the layers on the transition's first
frame (painting the after-frame under them) and is the plain frame after
that; TIMER_XFADE only watches for the end. A lost tree drops the layers and
the stepped compose takes the rest from where the clock is.
`GHOZTTY_DEBUG_SIDEBAR_TRANSITION_STEPPED=1` (debug) is the A/B arm.

## Validation criteria

- [x] the scope slide goes on the compositor whole and the UI thread composes none of its frames: `test\win32\sidebar-transition-comp.ps1` comp arm, `transition scope on compositor layers=3` + done `compositor=true ui_steps=0`, both directions
- [x] a fold and an unfold do the same and never land early: same arm, `compositor=true ui_steps=0`, 0 `fold lands`
- [x] one tree serves every transition, built on demand for it: `composition tree up for=list-transition ... build=1`, exactly one
- [x] the stepped knob keeps the old path (A/B): stepped arm, `compositor=false ui_steps=35/28/28/33` and no tree built
- [x] the oracle can fail: `-NegativeControl` exits 1 on exactly the comp arm's `ui_steps=0` row
- [x] the masked layers over the material reproduce the stepped compose, the plans match `slideAt`/`composeFold`: unit tests in `pane_sidebar_transition_comp.zig` (win32 + none lanes)
- [ ] NOT COVERED: the motion's pixels on screen mid-flight - a background desktop cannot be photographed and WM_PRINTCLIENT reads the GDI frame, not the tree; filming it needs the input desktop, which the loop may not take while the user is present (go.md)
