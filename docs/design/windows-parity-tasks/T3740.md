# T3740 - With about 50 windows open the app gets slow: measure what scales with window count and make the 50th window as fast as the 2nd

## Summary

User report 2026-11-25: "when i spawn 50 windows shit gets SLOW". With ~50 top-level Ghoztty windows open, the app gets slow (typing, switching, opening more). Pane-window reuse (T2597, pane_pool.zig) is ON by default and must stay on (user: "i NEED window reuse"), but it only recycles pane HWNDs inside ONE top-level, so it does nothing for many top-levels. MEASURE first, do not guess: open 1, 10, 25, 50 windows (each one pane, then each a 2-way split) on a Debug and a release build and record (a) time to open the next window, (b) keystroke-to-glyph latency in the focused pane, (c) UI-thread message-loop lag, (d) per-window GPU/committed memory and total, (e) renderer threads and their CPU while idle. Suspects: every window's renderer/IO threads ticking while hidden or covered (T2474 frees targets of hidden windows - is that applied to covered top-levels?), per-window broadcast loops (window_broadcast.zig, the sidebars and the session layout rewritten per window per change), the session-layout save cost growing with window count (T1516), the 512-pane sidebar list, per-window timers. Target: opening the 51st window and typing in it feel the same as the 2nd (state budgets from the 1-window baseline). Acceptance: a harness (test desktop) that opens 50 windows and asserts the open-next-window and key-echo budgets against the 1-window baseline, with the breakdown recorded here. Mac half: check whether the Mac app has the same cliff at 50 windows and file seat: mac if so.

## In plain terms

With about fifty Ghoztty windows open, the app got slow. This task measured
why. Fifty quiet windows are fine: a new window opens and typing echoes about
as fast as with two. Fifty windows whose programs keep printing (an agent's
spinner, a build) are not. When the windows are spread out so each one shows
a strip, every one of them redraws all the time, and together they use about
eleven CPU cores. Windows that are completely covered already stop drawing.
The fix for the busy case is its own task (T3761).

## Findings (2026-11-25, `test\win32\window-count-scale.ps1`)

Idle (each window one `cmd` pane, cascaded), Debug:

| N | open-next | echo | UI msg (med/max) | app CPU | private | GPU | threads |
|---|---|---|---|---|---|---|---|
| 2 | 54 ms | 31 ms | 0.68 / 28 ms | 0% | 243 MB | 83 MB | 91 |
| 10 | 71 ms | 30 ms | 0.37 / 1.1 ms | 1.9% | 605 MB | 253 MB | 123 |
| 25 | 67 ms | 29 ms | 0.32 / 1.4 ms | 1.6% | 1382 MB | 579 MB | 181 |
| 50 | 85 ms | 29 ms | 0.51 / 2.2 ms | 5.9% | 2762 MB | 1127 MB | 278 |

Busy (every pane but one printing ~12 lines/s), cascaded, RELEASE build:

| N | open-next | echo | app CPU | descendants CPU |
|---|---|---|---|---|
| 2 | 69 ms | 27 ms | 0% | 0% |
| 10 | 58 ms | 34 ms | 247% | 50% |
| 25 | 118 ms | 40 ms | 589% | 206% |
| 50 | 266 ms | 79 ms | 1128% | 289% |

- **What scales:** CPU per *visible busy* pane. `GHOZTTY_PERF` shows each busy
  pane drawing ~50 fps for ~12 printed lines a second (ConPTY delivers output
  in small chunks and each chunk wakes a frame); the thread census puts ~17% of
  a core in each pane's `renderer` thread and ~20% in an unnamed GPU-driver
  thread per pane (every pane owns a GL context). Debug and release cost the
  same, so it is not debug overhead. -> **T3761** (P1, user report).
- **What does not:** covered windows. Stacked on one rectangle, 50 windows with
  48 printing cost 54% of a core (the occlusion poll, T1951, stops them); the
  same 25 cascaded cost 668% (negative control). Open/echo/UI lag/idle CPU stay
  flat with idle windows.
- **Memory is linear:** ~55 MB private + ~22 MB GPU + ~4 threads per
  single-pane window, the same on release. -> **T3762**.
- **UI thread under covered retitling panes:** 21% of a core with 48 covered
  windows retitling (cmd retitles every command); Mac holds a hidden window's
  title. -> **T3763**.
- **Mac half:** -> **T3764** (`seat: mac`).
