# T2649 - After the display sleeps once, the frame clock never goes back to the compositor's clock: one STATUS_GRAPHICS_PRESENT_OCCLUDED (0xC01E0006) from DCompositionWaitForCompositorClock drops FrameClock onto the hrtimer for the life of the process

## Summary

Found by T2645, 2026-11-02. `src/apprt/win32/FrameClock.zig` `waitTick`: when the compositor-clock wait returns anything but object/timeout it logs `compositor clock wait failed ({x}); falling back to a timer`, sets `self.wait_clock = null` and switches `source` to `.hrtimer` - permanently. Every divider-flicker run started while the display was asleep (07:25-09:33 on 2026-11-02, 22 runs) logged it with `c01e0006` = STATUS_GRAPHICS_PRESENT_OCCLUDED, which is transient: the display wakes and the clock would work again. So an app that was running when the monitor slept steps every later animation (glides, hero slide, stack fold) on the high-resolution timer instead of on DWM's frames until it restarts.

Fix shape: treat OCCLUDED (and the other transient present statuses) as "tick on the timer for now, retry the compositor clock" - retry every few seconds, or on WM_DISPLAYCHANGE / a monitor-on power broadcast - and keep the permanent fallback only for a wait that is genuinely unavailable. Unit-test the classification in the none lane.

## In plain terms

If the screen goes to sleep while Ghoztty is open, its animations afterwards are timed by a plain timer instead of by the display, which can make them a little less smooth until the app restarts. Nobody has reported it yet; it was spotted in a test log.

## Validation criteria

- [ ] an OCCLUDED wait result keeps the compositor clock and retries it (unit test on the classification, none lane)
- [ ] after a monitor sleep and wake the app log shows the compositor clock back in use (on-box check, idle box)
