# T1263 - Something is still writing backslash escapes into task files as control characters - find the writer

## Summary

T1231 repaired fifteen files and added a commit-time guard, but not the SOURCE. Two of the fifteen (T1251, T1252) were filed AFTER T1231 was written and had picked up the same damage, so whatever writes it was still active. The signature is a Windows path written with a backslash escape that some tool interpreted on the way in: 0x07 for a, 0x08 for b, 0x0c for f. The guard now refuses such a commit, so the next occurrence is loud rather than silent - the work here is to catch one, identify the writing path (a printf or echo -e in a shell helper is the likeliest shape, since PowerShell does not interpret those escapes), and fix it there.

## In plain terms

Notes and scripts in this repo kept getting invisible junk characters where a
Windows folder path was written, so a path like `zig-out/bin` silently became
two run-together words that point nowhere. We found what does it: the AI's own
file-writing tool calls, when a single backslash in a path is read as a special
code. Now that write is refused on the spot with a message saying how to fix
it, and the repo-wide check also catches the two forms it used to miss.

## Goals

- [x] identify the writer from evidence, not a guess
- [x] stop the damage where it is written, before it reaches disk
- [x] catch the `\r` and `\t` members of the same family, which the old check missed
- [x] repair what that blind spot let through

## The writer

Not a script. The pre-2026-09-23 transcripts are pruned, but 18 later ones hold
the same damage, and in every one the decoded byte is already in the Edit or
Write tool INPUT, next to correctly doubled backslashes in the same string - e.g.
an Edit whose `new_string` carries `test\\win32\u0007gent-handoff.ps1`, or a
guard-due.ps1 coverage row written as `'test\\win32\remote-effects.stamp.json'`
(the `\r` decoded to a CR). So a single backslash before `a`, `b`, `f`, `r` or
`t` in the tool-call JSON is decoded on the way in. The Summary's guess (a
printf or echo -e in a shell helper) was wrong; no repo code writes it, which is
why it was still happening after T1231.

The fix therefore sits in front of the tool rather than in a script: a
PreToolUse hook on Edit, Write and MultiEdit that refuses new text holding the
damage and tells the author to double the backslash or use forward slashes.
That is the one moment the author still knows what the path was meant to be.
The commit-time scan stays as the net behind it (the other window sharing the
tree, a tool the hook does not cover).

## The blind spot

T1231's scan flagged bytes below 0x20 except tab, LF and CR - so a decoded `\r`
(a CR) and a decoded `\t` (a tab) went through. Both are legitimate on their
own, so they are judged only in the shape the decode leaves: a CR that is not
half of a CRLF, and a tab glued between path segments. The first full scan with
that rule found 10 lone CRs in 8 task files, every one a `test/win32/r...` path
written with a backslash (T1031, T1203, T1212, T1213, T1343 x2, T1517, T1978
x2, T2169). No tab-in-path hits, and no false positives across 5,509 files. A
decoded `\n` is a real line break and cannot be told from one; it is the one
member of the family left to review.

## Validation criteria

- [x] The writer is identified from evidence: the transcripts' Edit/Write tool
      inputs hold the decoded byte (`\u0007` after `test\\win32`, a raw `\r`
      inside a guard-due coverage path), so the channel decodes it before any
      script runs.
- [x] The write is refused at source: `test/win32/deny-escape-damage.ps1` ALL
      PASS (25) - each decoded byte (0x07, 0x08, 0x0c, lone CR, tab-in-path)
      is denied through the real stdin envelope for Write, Edit and MultiEdit;
      a repair edit, a clean write, CRLF, ordinary tabs, an out-of-scope file,
      another tool and garbage input pass silently; the registered command line
      denies when run through Git Bash. `-NegativeControl`: exactly 1 FAILURE.
- [x] The scan sees the `\r` / `\t` members: `test/win32/control-char-scan.ps1`
      ALL PASS (52), new A9-A11 (lone CR and two tab-in-path shapes reported;
      CRLF, leading tab and tab-between-words not; the finding shows the byte
      made visible). `-NegativeControl`: exactly 1 FAILURE.
- [x] The 10 lone CRs are repaired to the path they were meant to hold (C1 rows
      for all eight files), and a full tracked-tree scan is CLEAN (5,509 files).
- [x] One definition: scanner and hook both load `scripts/lib/EscapeDamage.ps1`
      (section D of the hook harness).
