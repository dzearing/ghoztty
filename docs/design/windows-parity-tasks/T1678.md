# T1678 - A preserved test transcript is UTF-16, so grepping the evidence needs a conversion step

## In plain terms

When a test run fails, it now leaves behind a full record of what it did. That
record opens fine in an editor, but it is saved in a format where searching it
from the command line - the first thing anybody actually does with it - comes
back empty unless they know to convert it first. The evidence is all there; it
is just one step further away than it should be.

## Summary

T900 made a red harness run preserve its transcript under a name later runs
cannot clobber (`lib\Transcript.ps1`). The file itself is whatever
`Tee-Object -FilePath` wrote, and on PS 5.1 that is **UTF-16LE**:

```
 P A S S   v i e w e r   p a n e   l i s t e d
 T 3 3 2   A C C E P T A N C E :   A S S E R T E D   N O T H I N G
```

`Get-Content` and `Select-String` cope. `grep`, `rg`, `findstr` and every
non-PowerShell reader do not, and an empty grep over a file that plainly
contains the string is the kind of wrong answer that gets believed.

The fix is one decision about where to convert: `Tee-Object` has no encoding
parameter on 5.1, so either `Save-FailedTranscript` transcodes on the way to the
preserved copy (the live `-last.log` stays as it is), or the harnesses stop
teeing and write through something that takes `-Encoding utf8`. The first is
smaller and keeps the change inside the library the evidence already goes
through.

Note the standing trap while doing it: never whole-file rewrite a repo text file
from PowerShell. This is about a `%TEMP%` artifact, not a tracked file, but the
same `Set-Content` reflex is what causes it.

## Validation criteria

- [ ] A preserved failure transcript is UTF-8 (no BOM, no interleaved NULs) and
      a plain `grep` for an assertion line in it finds that line
- [ ] Its content still matches the live `-last.log` line for line - transcoding
      did not drop or reorder anything
- [ ] `test\win32\fail-transcript.ps1` asserts both, and stays ALL PASS
