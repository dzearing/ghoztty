# T1244 - Give the update download progress panel a way to stop the download

## Summary

T1195 gave the consented download a progress panel. Closing that panel
dismisses the REPORT, not the transfer: the user consented to install, and
silently cancelling behind a close box would be a different promise than the
dialog made. But there is now no way to change your mind either - a large
download on a bad link runs to completion or to failure, and the app then
quits to install it.

Mac's Sparkle panel carries a Cancel. The mechanism on Windows is an
`InternetCloseHandle` on the connection from the GUI thread, which makes the
worker's in-flight `InternetReadFile` fail; the worker already treats a read
failure as a failed download, so the plumbing downstream exists.

## In plain terms

Once you say yes to an update, the download runs to the end no matter what.
If it turns out to be slow, or you realise you are on a metered connection,
there is nothing to click to stop it.

When this lands, the download panel has a Cancel button. Pressing it stops the
download right away (even if the connection has gone quiet), the panel says
"Download cancelled", and the update is still offered for later.

## Goals

- [x] A Cancel button on the download panel
- [x] Cancel works on a stalled link and before the server has answered
- [x] A cancel reads as the user's choice, never as a failure

## Validation criteria

- [x] The progress panel carries a Cancel that actually stops the transfer -
  update-progress.ps1 section 6: a read blocked on a server holding the socket
  for 90s ended 15 ms after Cancel
- [x] A cancelled download stages nothing and never quits the app to install -
  section 6: no `staged` line, empty staging dir, no applier armed, app alive
- [x] Cancelling says so, rather than reading as a failure - section 6: panel
  logged "Download cancelled. Ghoztty will keep the build you have.", no
  failure line, no failure window
- [x] The offer is still there afterwards: the balloon path can start it again -
  section 6: second balloon click raised the dialog and a second panel; a cancel
  during THAT download's connect phase stopped it in 7 ms

## Design

- `update_progress.Abort`: the GUI side sets a flag and swaps out the
  published WinINet handle; the worker publishes the handle it is blocked on
  (the session handle while `InternetOpenUrlW` connects, then the request
  handle for reads) and takes it back on exit. Whoever swaps it out closes it,
  so it is closed exactly once. Seq-cst on both sides, unit-tested both orders.
- New `Outcome.cancelled` and `error.Cancelled`; the worker posts
  `update_cancelled_code` (5), which clears the in-flight flag and records a
  deferral - no failure window.
- The close box is unchanged: it still dismisses the report only. Mac's Sparkle
  panel has the same split (Cancel vs. closing the window).
