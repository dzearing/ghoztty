# T1520 - Harnesses read a job's log file while the job appends to it, so a collision scores a real hit as a missing one

## Summary

T1517 found this scoring a phantom product defect: relay-account.ps1 read the fake relay's hit log with Get-Content while the background job's Add-Content held it, the read threw 'the file is being used by another process', ErrorActionPreference=Continue turned that into an empty string, and the assertion reported 'FAIL signing back in RE-ENROLLED this machine (T1425)' over traffic that WAS in the log. That file is fixed on both sides (the writer retries, the reader opens with FileShare::ReadWrite and retries), but the shape is not unique to it: every harness whose oracle reads a file a background job writes has the same race, including lib\FakeRelay.ps1's Get-FakeRelayLog (plain Get-Content) and its six callers. The failure is worse than a hang because it is PLAUSIBLE - it names a real product behavior and sends the next turn looking for a bug that is not there. Sweep the suite for reads of a job-written log and route them through one shared helper that shares the write handle and retries; consider making it an audit rule the way job-teardown.ps1 section D is, so a new fixture cannot reintroduce it.
