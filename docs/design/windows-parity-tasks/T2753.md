# T2753 - +split --target=<name> issued right after the +split that created <name> splits the focused pane instead (close-overlays: cw, +split c2, +split --target=c2 c3 builds (cw|c3)|c2, seen 2x on the comp path 2026-11-06)

## In plain terms

A test script built a row of three panes and got them in a different order
than it expected. The app was doing what it is documented to do on both Mac
and Windows: naming a pane with `--target` picks that pane's *window*, and the
split lands beside whichever pane in that window is active. The script should
have named the exact pane with `--pane`. The script is fixed; the app is
unchanged.

## Goals

- [x] tell the two readings apart (lookup race vs. insert side) from the code
- [x] confirm the Mac does the same thing with the same three commands
- [x] fix close-overlays.ps1 to split the exact pane, and assert the order

## Summary

Found by T2748's composition section of `test/win32/close-overlays.ps1`. The
script runs, back to back:

```
ghoztty +new-window --target=cw
ghoztty +split --target=cw --direction=right --name=c2
ghoztty +split --target=c2 --direction=right --name=c3
```

and `+list --json` then shows cw's tree as `split(split(cw, c3), c2)` - leaf
order <cw's pane>, c3, c2 - on two consecutive runs (GHOZTTY_COMP_PRESENT=1, debug
build, test desktop). Asked for: cw, c2, c3. So the second split went beside
**cw**, not c2. Two readings, not yet told apart:

- the `--target=c2` lookup raced c2's name registration and fell back to the
  focused pane (cw - CLI splits open in the background since T1797), which
  would be wrong: an unknown target should answer an error, never act on
  another pane; or
- the split did target c2 but the insert/rebalance put the new leaf on the
  wrong side.

The popup-path sections of close-overlays.ps1 have always found c2 by its
banner height ("not a left-to-right guess"), which suggests the order was
already unreliable there and was worked around rather than filed.

Check the Mac CLI on the same three commands: the order should be cw, c2, c3.

## Resolution (2026-11-07)

Neither reading. `+split --target=<pane>` resolves the name to the pane's
WINDOW and splits that window's active pane - `IpcHandlers.zig handleSplit`
(the `args.target` branch takes `window.tab_active_pane[window.active_tab]`),
and the Mac is identical (`IPCServer.swift splitAnchor` -> `windowAnchor`,
the controller's focused surface). Because CLI splits open in the background
(T1797), c2 never became active, so the c3 split went beside cw: exactly the
documented contract (`docs/claude/cli.md`, `+split` `--target`: "A pane name
here resolves to that pane's window and splits the window's active pane, not
the named one"; T2163 hit the same trap). The exact-pane anchor is `--pane`.

Fix: `test/win32/close-overlays.ps1` splits c3 with `--pane=c2` in both the
popup and composition setups, and the composition section now asserts leaf
order `cw,c2,c3`. No product change: changing `--target` would diverge from
the Mac CLI, which the platform-symmetry rule forbids.
