# T1502 - The reset helper's /clear check looks for a prompt glyph no pane ever prints, so it can never fail

## In plain terms

Before this session hands the next one its instructions, it types `/clear` and
then checks that the clear really happened. That check looks for a particular
arrow character that the terminal is supposed to print in front of whatever you
are typing - and that character is simply not there. So the check finds nothing,
concludes the box is empty, and reports success every single time, including
over a session that was never cleared at all. The loop's safety net has no net
in it.

## Summary

`reset-context.sh` verifies the clear with:

```sh
composer_holds_clear(){
  ghoztty +read --name="$P" --lines=40 2>/dev/null     | grep '^U+276F' | tail -1 | grep -qF "/clear"
}
```

(the literal in the file is the heavy right-pointing angle quote, U+276F.)

A 400-line `+read` of a live Claude Code pane on 2026-09-12 contains that
character **zero** times: the composer is drawn inside a box whose rules are
`U+2500` runs, and what the dump carries in front of the typed text is `>`
followed by a non-breaking space, joined onto the end of the box rule. So the
grep matches nothing, `tail -1` gets nothing, and the function is always false -
the gate reports `verified: /clear landed` unconditionally.

Measured the same day by section B of `test\win32\reset-context.ps1`: over a
pane that provably was NEVER cleared (B2 asserts the session never ran the
command), the helper logged `verified: /clear landed (composer is empty after 0
extra Enter press(es))`. B3-B6, which asserted that a failed clear is shouted
about, went red for exactly that reason and were removed by T699 rather than
left asserting a contract the helper no longer has.

## Details

The gate replaced a whole-screen `grep -qF "/clear"` on 2026-08-25 because that
version cried wolf on every healthy run - Claude Code echoes the command it just
ran into the fresh transcript, so "/clear is on screen" is the NORMAL look of a
successful clear. The composer idea is right; the signature is wrong.

Whoever takes this owes a MEASUREMENT first: dump a real pane with `+read` in
both states (composer empty, composer holding unsubmitted text) and find a
signature that separates them. Candidates to weigh rather than assume:

- the composer is the last content line above the status footer, so a bounded
  tail (last N lines) rather than a glyph anchored at column 0;
- `>` + U+00A0, which is what the 2026-09-12 dump actually carried;
- the status footer itself as the anchor, counting back from it.

Whatever it becomes, it ships with the demonstration that it can fail - the
section B arms removed by T699 are the shape, and a pane fixture that holds an
unsubmitted `/clear` is the negative control. Note that the helper lives in
`D:\git\dzearing-claude-marketplace` and the active plugin cache, which D3 of
the acceptance suite requires to be byte-identical.

## Validation criteria

- [ ] The clear verdict is derived from a signature MEASURED in a real Claude
      Code pane dump, in both the empty-composer and held-composer states.
- [ ] A pane holding an unsubmitted `/clear` is detected, gets its Enter, and a
      persistent one is shouted about - demonstrated in
      `test\win32\reset-context.ps1`, not argued for.
- [ ] A healthy clear still passes with no banner (no return of the 2026-08-25
      wolf-crying).
- [ ] Source repo and active plugin cache byte-identical, plugin version bumped.
