# T2029 - close-overlays.ps1 has no move-to-window section: prove a pane moved to another window or tab takes its banner, dim and scrollbar with it in the same pass (T2012 criterion 3)

## In plain terms

When you pop a pane out into its own window, its status banner and
scrollbar should arrive with it at once - never stay floating over the spot
it left, or catch up a moment later. Nothing checked that before; now a test
does.

## Goals

- [x] A close-overlays.ps1 section that moves a pane to another window and checks where its popups are
- [x] Show the check can fail

## Summary

T2012's harness covers close and stash; moving a pane to another window/tab (+rearrange or the drag) re-owns its popups through a different path and is unmeasured. Add the section, with its own negative control.

**Re-verified 2026-11-23.** Still unmeasured: rearrange-window-drop.ps1 D
(T3163/T3202) checks the popped pane's banner band and popup OWNER, never
where the popups sit on screen after the move. Section 7 added here, on the
popup path (GHOZTTY_COMP_PRESENT=0); on the composition path the overlays are
the pane's own visuals and ride the SetParent (section 6 / rearrange-window-
drop D). Mechanism notes (Claude's call, go.md 5b):

- The move is the header pop-out button (rearrange mode, posted click), the
  one cross-window move that needs no drag geometry. A drag drop and a
  move-to-new-tab go through the same `adoptPane` (SetParent + reownPopups +
  the destination's layout re-glue), so this pins that shared path.
- "Same pass" is an IPC round-trip barrier, not a sleep: `+list` runs on the
  GUI thread after the posted release, so a glue deferred to a later message
  or timer would still be pending and fail.
