# T2475 - Glide/slide timers must stop when their pane or window is freed mid-animation, and a viewer split that fails to insert must release its WebView2

## Summary

Mac 1bc34a8d7: PaneStageView / PaneSidebarCardGlide 120Hz glide timers outlived their owner, and newViewerSplit leaked a viewer it failed to insert (web view, watcher, event monitor). Audit the win32 equivalents - pane_stack_slide / sidebar glide / divider glide SetTimer users (KillTimer on WM_DESTROY and on owner free), and the +split --view failure paths in IpcHandlers/Window (ViewerPane deinit, WebView2 controller Close, file watcher). Add a unit or acceptance check for each path that leaks today.

## In plain terms

On the Mac, closing a pane while one of its slide animations was still
running could leave that animation ticking away in the background, and a
viewer pane that failed to open could leave its hidden web browser running.
Windows was checked for both mistakes and does not have either one. A new
automated test now keeps the animation half from coming back.

## Goals

- [x] Audit every win32 glide/slide animation clock for state that outlives the pane or window that owns it
- [x] Audit the `+split --view` failure paths for a viewer (WebView2, file watcher) that is never released
- [x] A regression test for the shared animation clock's "owner freed mid-animation" path

## Audit verdict (2026-11-09)

Nothing leaks today. Why, path by path:

- **Every animation steps on `(hwnd, id)`**, either a plain `SetTimer` or
  the frame clock (`FrameClock.arm`). A `SetTimer` dies with its window
  (DestroyWindow kills it). A frame-clock subscription whose window is gone
  is dropped at the next frame by `FrameClock.dispatch`'s `IsWindow` check,
  never sent to, and the clock stops when nothing live is left. Pinned by the
  new unit test `T2475: a window freed mid-animation ...` in
  `src/apprt/win32/FrameClock.zig`.
- **Every subscriber destroys its window before freeing its struct**
  (BellBorder, HoverTint, DimOverlay, Scrollbar, BannerOverlay,
  ViewerTOCPanel, PaneSidebar, SettingsWindow: `destroy` = DestroyWindow
  then free; most also clear GWLP_USERDATA first). `Window.deinit` and
  `WM_DESTROY` clear GWLP_USERDATA before the window goes, so a late message
  never reaches a freed `Window`.
- **The one clock on a shared window** is the quick terminal's, on
  `App.msg_hwnd`; `QuickTerminal` disarms it unconditionally before it frees
  itself (QuickTerminal.zig, `deinit`).
- **The pane-stack glide** (`Window.stack_slide`, `STACK_SLIDE_TIMER_ID`)
  holds card ids, not pane pointers: each tick re-walks the live tree, so a
  pane closed mid-glide simply is not in it. The sidebar's column / crossfade
  / reorder / motion ticks likewise re-read the roster rather than follow a
  stored `*PaneView` (`Entry.pane` is asked about by address only, T2607).
- **The viewer split**: `newViewerSplitAt` frees the viewer through
  `viewer.deinit` if `PaneView.createViewer` fails; `createViewerPane`'s
  `errdefer` covers every step after `ViewerPane.create`; and
  `insertPaneAsSplit` takes ownership on failure as well as success (its
  single-node tree's `deinit`, or `destroyUnowned` when the tree cannot be
  built). All three end in `ViewerPane.deinit`, which stops the watcher
  thread first, then `Close`s and releases the WebView2 controller, every
  handler and the environment. Same for the tab path (`addViewerTab`).

## Validation criteria
