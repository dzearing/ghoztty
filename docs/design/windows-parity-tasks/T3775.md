# T3775 - Linux: a GTK pane's released frames still hold their memory on Mesa llvmpipe - find what keeps the storage alive and prove the drop

## Summary

T3645 made a hidden or idle GTK pane release its frames on the main thread (frames report 1890KB target + 1280KB atlases -> 4/5 bytes, test/linux/frame-release.sh R1-R7). But measured 2026-11-25 with LIBGL_ALWAYS_SOFTWARE=1 and MALLOC_MMAP_THRESHOLD_=131072 (temp diag: one pane, idle release, 300x90 window), the app's private memory does not drop and no target-sized (3244KB) anonymous mapping goes away, while a CLOSED pane's targets are freed (pane-close-memory.sh). A validating clear of a private 2x1 FBO after the release did not change it. Suspects: Mesa context state (st sampler views / util_blitter views from the present blit, pipe framebuffer state) keeping the old resources referenced until the GLArea context next draws. Needs gdb or an LD_PRELOAD malloc trace in the distro (install is a one-time distro change - say so). Done when a background-tab pane's release shows as a private-memory drop of about its frames' size, as a new R-check in frame-release.sh.

## Validation criteria

The done-criterion moved from the background-tab release to the idle release
(2026-11-28, evidence below). An allocation trace showed the tab-switch release
already frees the target and atlases without the fix. Its private-memory net
cannot show that anyway: the tab that comes forward allocates its own frames
in the same moment.

- [x] What kept the storage alive is named: Mesa rebinds a context's
  framebuffer and sampler state only when a draw validates it, so after an
  idle pane's last frame llvmpipe kept the old target's storage until the
  pane drew again. Found with an `LD_PRELOAD` allocation trace (a `zig cc`
  shim, so no distro install was needed). Recipe in `docs/claude/linux.md`.
- [x] Fix: `OpenGL.dropReleasedFrameRefs` does one draw with the `bg_color`
  pipeline (no samplers) into the new 1x1 target, saving and restoring the
  viewport around it. `generic.releaseFramesNow` calls it before
  `hiddenTargetsReleased`'s `glFinish`.
- [x] `test/linux/frame-release.sh` R5: an idle release lowers the app's
  private memory by at least 3/4 of the target. Fix in: 2576 and 2492 KB
  freed (and 2832-2928 KB in the trace runs) for a 1890 KB target. Fix off
  (temporary knob, A/B, removed before landing): 696-744 KB. `NEGATIVE=1`
  (no idle release): R1, R2 and R5 fail alone, with 628 KB of background drift.
- [x] Full frame-release.sh is ALL PASS, run twice. The first fix attempt
  broke R3/R6 (the 1x1 viewport leaked into the next frame); restoring the
  viewport fixed both.
- [ ] Atlas storage freed at the idle release: not seen in either mode. Filed
  as T3892.

## Progress log

- 2026-11-28 02:12: claimed; work starting.
- 2026-11-28 02:34: root cause (allocation trace via an LD_PRELOAD zig-cc shim, Mesa 25.2.8 llvmpipe): after an IDLE release the target's storage stayed allocated until the pane drew again, because Mesa rebinds framebuffer/sampler state only at draw validation. Fix: OpenGL.dropReleasedFrameRefs, one bg_color draw into the new 1x1 target (viewport saved/restored), called from generic.releaseFramesNow before hiddenTargetsReleased's glFinish. A/B x3: idle release freed 2832-2928 KB with it vs 696-744 KB without (target 1890 KB). The HIDDEN (tab switch) release freed target+atlases in both modes; its private-memory net is confounded by the forward tab re-allocating its own frames, so R5 measures the idle release instead. Atlas storage (1024+256 KB) was not seen freed at the idle release in either mode -> follow-up.
