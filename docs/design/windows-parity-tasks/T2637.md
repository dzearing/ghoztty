# T2637 - Shared GPU memory grows ~2 MB on some minimize/restore cycles of a 4-pane window, with or without the T2474 target release (hidden-window-memory.ps1 table)

## In plain terms

Each time a Ghoztty window with several panes is minimized and brought back,
the graphics memory it holds sometimes grows by about 2 MB and never comes
back. One cycle is nothing; a day of minimizing a terminal adds up.

**Outcome (2026-11-27): it does not add up.** The growth stops after the
first five or so minimizes and stays put after that (measured over 40), so
there is no slow leak to fix. The test now checks that it stays put.

## Goals

- [x] find out whether the growth is per-cycle, per-pane or bounded
- [x] name what causes it
- [x] make the harness catch it if it ever stops being bounded

## Summary

Found by T2474's `test\win32\hidden-window-memory.ps1` (one window, four
default-layered terminal panes, 1400x900, debug build). Its table shows the
process's SHARED GPU usage stepping +2.0 MB on two of four minimize/restore
cycles (39.1 -> 45.1 MB) both on HEAD 7d0135e39 BEFORE the T2474 release
existed and after it, so it is not the release. Dedicated memory is flat
across cycles once T2474 lands. T2599 measured a +3.0 MB DEDICATED re-pay per
minimize/restore for PLAIN panes (`GHOZTTY_PANE_LAYER=0`); this is the default
layered path and the shared heap, so it may be the same redirection-surface
re-creation charged to a different heap, or a separate one. First step: run
the harness with `-Cycles 10` and a never-split window to see whether the step
is per-cycle, per-pane or bounded; then compare against T2599's
`test\zig-repro\t2599-wgl-multichild` repro.

## Finding (2026-11-27, debug, test desktop, 1400x900)

Bounded warm-up, not a leak. Shared GPU per restore, 4 panes, default:

| cycle | 1 | 2 | 4 | 5 | 6 | 10 | 20 | 30 | 40 |
|---|---|---|---|---|---|---|---|---|---|
| shared MB | 49.1 | 55.1 | 61.1 | 73.1 | 73.1 | 72.9 | 73.0 | 75.0 | 75.0 |

Dedicated is flat (110.5-110.6) and private bytes plateau with it.

- **The step:** the driver's system-memory (upload) pool growing to a
  high-water mark under T2474's per-restore re-creation of every pane's
  target and atlas textures. Disabling only that release (local probe,
  reverted) leaves just the original ~2 MB steps (43 -> 51 over 8 cycles).
- **Not ours elsewhere:** the identical curve with `GHOZTTY_COMP_PRESENT=0`,
  with `GHOZTTY_PANE_LAYER=0`, and with no `capture-pane` readbacks.
- **Scales with the targets, not the panes:** one never-split pane goes
  19.3 -> 31 MB and is flat from cycle 5.
- **Driver baseline:** the standalone WGL repro `one` scenario (now prints a
  `sh=` column) is +1 MB over 20 cycles with nothing re-uploaded.

No code fix is owed: the cost is a one-time ~30 MB of system memory, in
exchange for the ~14 MB of dedicated memory the release gives back on every
minimize. `hidden-window-memory.ps1` gains **A6** (runs of `-Cycles 10`+):
shared at the cycle-6 restore vs the last must stay within 3 MB.

## Validation criteria

- [x] shared GPU usage flat (within 1 MB) across 10 minimize/restore cycles of hidden-window-memory.ps1, with the step that caused it named - past the 5-cycle warm-up: `hidden-window-memory.ps1 -Cycles 10` ALL PASS 23, A6 72.9 -> 73.1 MB (cycles 6-10); 40-cycle probe 73.1 -> 75.0 over cycles 5-40; step named above (driver pool warm-up under the T2474 re-creation)
