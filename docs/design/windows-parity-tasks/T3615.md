# T3615 - Linux L11b2: a pane dragged onto the tab bar becomes a new tab, and a 500ms dwell on a tab opens it so the drag can drop into its layout

## Summary

Follow-up of T3564. The GTK drop resolver is fed only the split area today. Give each window candidate its AdwTabBar rect and tab button rects so pane_drop.resolve answers new_tab with an index, move the pane into a new tab of its own at that index (keeping its shell, the SplitTree.moveTo identity rule), and add the 500ms long-hover that selects a tab mid-drag (pane_drop.hoveredTab) so a drop can land in another tab's tree (SplitTree.moveTo/swapWith across tabs). A move that would empty the source tab's window is refused (a drag never closes a window). Extend test/linux/cli-pane-drag.sh through the pane-drag seam.

## In plain terms

On Linux a pane could only be dragged around inside its own tab: the tab bar
ignored it, and there was no way to carry a pane into another tab. Now
dropping a pane on the tab bar gives it a tab of its own at that spot (or, if
it was already alone in its tab, moves that tab there), and holding a dragged
pane over another tab for half a second opens that tab so the pane can be
dropped into its layout. The pane keeps its running shell throughout, and a
window's last pane can never be dragged out of it.

## Goals

- [x] the tab bar is a pane drop target while it is on screen, resolved by the shared resolver (bar + each tab's button)
- [x] a drop on a tab's button moves the pane into a new tab of its own at that index, selected, same shell
- [x] a pane already alone in its tab moves its tab instead, or stays put on the seams either side of it; a window's only pane never leaves
- [x] a 500ms rest on another tab's button selects it; the tab on show arms nothing; leaving the bar stops the clock
- [x] a drop into the tab the dwell opened lands there from the tab the pane left (split, swap, edge, gap), and an emptied tab closes
- [x] a moved pane stops reading as "split" from the tree it left (is-split is pushed per tree, not bound)
