# T1626 - A restored pane can reprint output it already showed when the manifest was captured mid-stream

## Summary

The session manifest's `screen_snapshot_offset` is written from a debounced
layout capture, and the capture takes the pane's position AS IT IS at that
instant. Bytes already handed over by the agent but not yet applied by the
pane's IO thread are therefore not in the number. The next attach resumes from
that lower offset and the agent's gap-fill replays those bytes again - the pane
prints a chunk it has already shown.

Found while measuring T804. Two runs of
`test\win32\session-resume-offset.ps1` recorded a manifest offset 149 bytes
below the agent's head (arm C cycle 3: `requested=2905 head=3054`) and, once,
393 bytes below (arm D cycle 1: `requested=16 head=409`) - each time because
the capture landed while the pane was still draining. The harness now settles
the capture before reading it, which is right for a TEST but leaves the product
behavior exactly as it was: a real quit or crash in that window strands the same
gap.

Direction to investigate: the capture has the information it needs - the
connection's `Pane.stream_pos` is the position the agent has handed over, and
`Remote.appliedOffset()` is the position the terminal has applied. Recording the
APPLIED one is what makes the offset honest, and it already is; the gap is that
the capture does not wait for the ring to drain and cannot know it is mid-flight.
Either the capture defers while a drain is pending, or the replay it causes is
made harmless (the duplicate is bounded by one debounce window).

## In plain terms

If the terminal is closed or killed at the exact moment a background session is
printing, the next time that session is restored it can print the last line or
two a second time. Nothing is lost - it is the safe direction of the same
bookkeeping T739 fixed - but it looks like a glitch.

## Goals

- [x] A kill in the middle of a burst of output restores without reprinting what

- [x] The fix does not reintroduce the opposite error (a recorded position ahead

- [x] (found doing it) The first line printed after the capture no longer comes
      back glued onto the end of the line before it.

## Outcome

The suspected defect does not exist. The snapshot's grid and its offset are read
under one hold of the renderer mutex, and `drainRing` advances `applied_bytes` in
lockstep with the parse, so a manifest offset below the agent's head only ever
means an OLDER picture plus a LONGER gap-fill, and the two meet exactly. A lower
resume offset is not a reprint.

Measuring it found the real defect next door: the repaint put the CURSOR back in
the wrong place, and the gap-fill writes from the cursor. `TerminalFormatter`
with `Extra.all` writes the CUP with the screen extras and only afterwards the
terminal extras, and DECSTBM homes the cursor while the tab-stop restore walks it
to the last stop (column 57 here); and it always drops trailing blank rows while
CUP is viewport-relative, so a cursor on the blank row under the output came back
a row too high. Every restore of a pane that had printed since its last capture
glued the first new line onto the last restored one. Fixed in
`src/termio/session_snapshot.zig` (two-pass format, trimmed rows put back, cursor
written last and origin-mode aware), used by `Surface.sessionSnapshotLocked` -
shared core, so the Mac restore gets the same fix.
