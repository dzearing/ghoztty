# T1136 - Screenshots and the image strip have no end-to-end coverage on the composer surface users actually get

## In plain terms

Attaching a screenshot to a feedback report is checked thoroughly — but only against the old text box, which is not the one the app opens for you any more. The one it does open has no such check for pictures. If screenshots broke there tomorrow, nothing would notice until somebody tried it.

## Summary

T1102 pinned `viewer-feedback-capture.ps1`, `-images.ps1`, `-carousel.ps1` and `-utf16.ps1` to the RichEdit fallback, because window messages cannot drive a Chromium window from the background test desktop (T233). That was the right call for those scripts — but it means the ENTIRE screenshot story is now proven on a surface no user gets. What the default surface has instead:

- `test\win32\viewer-composer.ps1` covers the web composer's structure and lifecycle and contains no image assertion of any kind (`grep -n 'Image #' ` finds nothing in it).
- the `host floor` test in `ViewerPane.zig` drives a REAL WebView2 end to end and does cover a chip — but through a **paste**, not through the region selector, and it asserts the buffer rather than the strip.

So on the web surface nothing asserts: the `+` button's capture reaching a chip, the picture landing in `images/image-N.png`, `report.json` carrying it at the dragged size, the body's markdown image reference, the carousel strip's tiles, or deleting a chip taking its picture out of the report. Every one of those is asserted for the fallback.

This is not hypothetical rot: the four scripts spent an unknown number of days reporting a broken screenshot feature that was working, precisely because nobody was watching the live surface.

## Where

- `test\win32\viewer-composer.ps1` — the web surface's own acceptance, the natural home for the arms that can be driven from a script
- the `host floor` test in `src\apprt\win32\ViewerPane.zig` — the natural home for anything needing a real controller, since it already has one
- `src\apprt\win32\ViewerFeedbackBar.zig` — `attachImage` / `spliceComposer` / `showThumb`, the paths in question
- `test\win32\lib\ComposerSurface.ps1` — T1102's pin/prove helper

## Details

The awkward part is the same one that made T1102 a harness bug: a script on the background test desktop cannot type into or read from the page. So the coverage has to come from the two oracles that DO work there —

- the pane's **stderr**, which already reports every capture begun/finished/cancelled and every `image=#N bytes=… live=…`, and
- the **report folder on disk**, which is the artifact the feature produces —

plus in-process assertions in the host floor test where the page's own DOM has to be inspected. A drag can still be POSTED to the region selector (it reads coordinates out of the message lparam and never asks the OS where the pointer is), so the capture half is drivable from a script even though the composer half is not; what a script cannot do is read the chip back out of the page, and `live=N` from stderr plus `report.json` covers that without touching a pixel.

Worth deciding while doing it: how much of this should instead ride on the host floor test, which can drive both halves. T937 deletes the RichEdit fallback outright, and when it does, the four pinned scripts have to move somewhere anyway — doing this task first means there is somewhere for them to move TO.
