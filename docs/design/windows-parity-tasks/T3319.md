# T3319 - git-commit-guard sync does not clear a stale empty index.lock, so the pull fails with File exists while commit would have cleared it

## In plain terms

When a git command crashes, it can leave a small lock file behind, and every git
command after it refuses to run. The commit helper already spots a left-over lock
and removes it safely. The "pull the latest work" helper does not, so it fails
with git's "another git process seems to be running" message, which tempts a turn
to delete the file by hand.

## Summary

Found in T1616's turn, 2026-11-21. `.git/index.lock` was 0 bytes, written at
01:05:55, and no `git.exe` was running at 01:09:52. `git checkout -- <file>`
failed with `Unable to create ... index.lock: File exists`. Then
`scripts\git-commit-guard.ps1 sync` failed the same way: it fetched
(`Updating 73722359b..6a2e8043b`) but could not move HEAD, and left the lock in
place.

`Clear-StaleIndexLock` (`scripts\git-commit-guard.ps1`, around line 193) is the
safe clearer T1412 built. It only removes a lock that is empty, at least 10s
old, and not owned by any git that started before it was written. It is called
from exactly one place, the `commit` path (around line 877). `sync` reaches
git's index too (the fast-forward and the rebase), so it hits the same wedge and
gives git's bare advice instead of the guard's diagnosis.

The lock was most likely left by a git started from this turn's own
`parity-tasks.ps1 next -Claim` or the claim step. Which one is not known; this
task is about the missing recovery, not that crash.

## Fix

Call `Clear-StaleIndexLock` at the top of `sync`, the same way `commit` does,
and print `Show-IndexLockDiagnosis` under a failed sync git step.
