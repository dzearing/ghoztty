# T2404 - A window title the user typed outranks every script's on Windows, as on Mac: +rename leaves it and fails naming it, +list --json reports title_set_by_user, and the flag persists with the title (Mac 7e2d0a9da)

## Summary

Mac main 7e2d0a9da: each window title records who set it. User = the sidebar rename field, Change Window Title, a sidebar drag into/out of a group; script = +rename, +new-window --title, the sidebar group + naming its new window. While the user's title is up, +rename changes nothing (not even a clear) and fails with an error naming the user's title; once the user clears it scripts may rename again. +list --json gains title_set_by_user per window (layout.md on main documents it in the skill). The flag persists with the title: AppKit restorable state and the session-layout + remote manifests (true or absent; older state decodes as script). Windows: carry a by-user bit on the win32 window title (IpcHandlers rename path, pane_sidebar rename commit, Change Window Title prompt, group drag), refuse +rename with the same error text, emit title_set_by_user in +list --json, persist it in session-layout.json / the remote manifest additively. CLI surface must match Mac exactly. Refs: docs/reference/cli-commands.md and macos/Resources/Ghoztty/skills/ghoztty/layout.md on main; Mac tests UserWindowTitleTests.

## In plain terms

When you rename a window yourself (Change Window Title, or the pane sidebar), a script or agent running in that window could rename it straight back. Now your name sticks: scripts that try to rename it are told no, with a message naming your title, until you clear it yourself. Scripts can also ask whether a title is yours before trying.

## Goals

- [x] Windows remembers whether the user or a script set each window title
- [x] `+rename` refuses (and cannot clear) a user's title, with Mac's exact error
- [x] `+list --json` reports `title_set_by_user` from the real bit
- [x] The bit survives a relaunch (session-layout.json, Mac layout blobs, session resume)

## Decision record

- **Where the bit lives (mechanism, Claude's call):** on the window-wide pin
  (`Window.title_override` + `Window.title_set_by_user`), the thing `+rename`
  writes. A Mac window is a TAB in the Windows sidebar, and a sidebar rename of
  a window with no window-wide pin pins that tab's title (`setTabTitlePin`) -
  `+rename` never writes tab pins, so those were already safe from scripts and
  need no flag. Mac pane titles need no flag either (only the user sets them).
- **Setters:** user = RenameDialog `.window`, `PaneSidebar.pinWindowName`
  (rename field, group rename, regroup drag); script = `+rename`,
  `+new-window --title`, the sidebar's new-window-with-title, remote-window
  `opts.title`. Restore and resume replay the persisted setter.
- No separate remote manifest exists on Windows (remote windows persist in
  session-layout.json), so that half of Mac's persistence is covered by the
  one field.
