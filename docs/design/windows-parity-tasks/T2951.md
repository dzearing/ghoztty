# T2951 - drag-glide's per-tick oracle reads only ~57% of ticks: GHOZTTY_STACK_TRACE=ring overflows at 4K (16384 lines, ~13.8k dropped a drag), so 'ticks over 16.7 ms' from 'stack trace tick' lines misses the slowest ones

## Summary

At 4K a drag-glide run has ~1283 glide ticks but only 739 'stack trace tick' lines survive (ring lines=16384 dropped=13860). Every per-tick count built on those lines (T2946's close: '7394 ticks, 0 over 16.7 ms'; temp\t2946-stats.ps1) is a sample, and on win-v1.54.17 the glide line's own max_us (which sees every tick) reads 17.1 and 17.4 ms where the trace said max 11.5. Fix the oracle, not the reading: have GlideStats count ticks over a frame budget (e.g. over_16_7 and over_period) on the glide line, which costs nothing and sees every tick, and have drag-glide.ps1 report it; and either size the ring for a 4K drag or stop tracing per-card lines when only tick lines are wanted. Gate: a 4K run's tick-over count from the glide line agrees with the max_us it prints.
