# T3103 - Idle visible panes keep three render targets and font-atlas copies for frames they are not drawing on Windows: release them after 3 s without a draw, without blanking the frame on screen (Mac 8b0de569b)

## Summary

Mac 8b0de569b: after 3 s without a real draw the swap-chain frames release their render targets and atlas copies (IOSurface 337 -> 143 MB on 21 idle panes); the frame on screen stays, next draw rebuilds (~1 ms). The generic.zig half arrives with the merge; check whether the OpenGL/D3D-interop path on win32 takes it (Presenter.texture, back buffers, per-frame atlas copies), port the idle release there, and make sure the visible frame is not blanked (DWM keeps presenting the last buffer). Builds on T2975 (background-tab release). Measure before/after with a frame-memory readout equivalent to ghostty_surface_frame_memory. Validation: N idle panes measured before/after, an idle pane still shows its content, first keystroke after idle redraws with no blank frame.

## In plain terms

Every terminal pane keeps some graphics memory for drawing its next picture,
even when nothing in it has changed for minutes. With many panes open that adds
up. Now a pane that has sat still for 3 seconds gives that memory back, and the
picture stays on screen. When something changes, it draws again straight away.
The Mac build already does this.

## Goals

- [x] An idle visible pane releases its render target and font-atlas copies after 3 s (OpenGL on Win32)
- [x] The picture on screen is not touched by the release; the next frame draws in full instead of re-presenting a freed target
- [x] Snapshots (hero mode, capture-pane) still work on a released pane
- [x] A readout of what was released (log line `released idle render targets ... targets=KB atlases=KB`)
- [x] An on-box harness with a negative control

## Design (recorded per go.md 5b - mechanism, not a decision)

- `generic.zig` `releaseFrameResources(.idle)` now runs for OpenGL too, gated
  by the new `OpenGL.releaseIdleTargetsNow` (Win32, device not lost, knob
  `GHOZTTY_IDLE_FRAME_RELEASE` not `0`). It reuses T2474's redraw contract:
  the API forgets `last_target`, the composition path drops its staging
  texture, and `redraw_after_release` makes the first frame back (even a
  no-op one) draw in full. Nothing presents during the release, so the
  window's swap chain / default framebuffer / presenter slot keeps the frame.
- Atlas copies are now released for both reasons (hidden and idle) on OpenGL,
  as on Metal.
- A release finding the frames already released returns early on every API
  (idle-then-hidden frees nothing twice).
- Known cost: a pane that only gets title-only output re-presents on the 500 ms
  safety bound (T1935), and after an idle release that present is a full draw;
  so such a pane cycles release/redraw every ~3.5 s instead of holding its
  target. Bounded, and measured as fine by title-flood.

## Validation criteria

- [x] N idle panes measured before/after: `test\win32\idle-frame-release.ps1`
      A1, 4 panes in a 1400x900 window, dedicated GPU 109 -> 95 MB on every
      still spell (3 cycles); readout line `targets=488KB atlases=1280KB` for a
      631x198 pane
- [x] An idle pane still shows its content: I3 (capture with text after every
      idle release) + H1 (idle, then minimized/restored). The on-screen pixels
      between release and next frame are not readable off-desktop (PrintWindow
      of a GL child is a flat fill) - held by mechanism: the release presents
      nothing
- [x] First keystroke after idle redraws in full: I2
- [x] No release while drawing once a second: N1
- [x] Negative control (`-NegativeControl`, knob off): I1, A1, I2 red
- [x] hidden-window-memory.ps1 still ALL PASS (runs with the idle release off)
