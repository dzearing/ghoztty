# T2197 - Ghoztty-Setup.exe: a small installer front door that runs the MSI and says in our own dialog when another installation is in the way

## Summary

T1247 split, piece 1. A zig win32 bootstrapper (new build step beside GhosttyMsiCa.zig) that embeds the release MSI via a build option path, runs it with MsiInstallProductW under MsiSetExternalUIRecord so Windows Installer's own error box (1500) never appears, and maps the result through update_apply.describeFailure into ConfirmDialog.showStandalone - 1618/1500 says another installation is running, 1602 is quiet, success hands off to the MSI's own LaunchApp. Pure result-mapping unit-tested in the none lane; acceptance on the test desktop drives the collision through a Debug-only code seam like T1206's GHOZTTY_UPDATE_MSI_CODE (a held _MSIExecute mutex does not collide - measured in T1206) and a negative control (success raises no dialog).

## In plain terms

If you start the Ghoztty installer while another installation is still
running on your PC, Windows refuses it, and until now you saw a window flash
up and vanish with no explanation. There is now a small Ghoztty setup program
in front of the installer: it runs the install for you, and when Windows says
no it tells you why in Ghoztty's own dialog - "another installation is
already running, wait for it to finish and run this installer again" - and
leaves that on screen until you have read it. When the install works, it says
nothing and Ghoztty opens as before.

## Goals

- [x] A setup exe that carries the MSI and runs it the way a double-click would
- [x] Windows' own "Error 1500" box is answered by us, so it never appears
- [x] Any refusal is said in Ghoztty's dialog (the same one the updater uses), in installer wording, with the log and the code
- [x] Success and a cancel say nothing
- [x] The exe shares the app's dialog without carrying the terminal (1.2 MB Debug)

## Design notes (2026-11-24)

- **Reusing ConfirmDialog without the app.** The dialog files named `App.zig`
  as a type, which drags in the whole terminal. They now import `App` from
  `src/apprt/win32/dialog_app.zig`, which is the real `App.zig` everywhere
  except in a root that declares `ghoztty_dialog_app_less = true`; there it is
  a never-instantiated stub carrying only what the dialogs name. Zig resolves
  every `@import` path eagerly, so the setup module is rooted at
  `src/setup_main.zig` (a shim) for `App.zig`'s own imports to stay in-module.
- **What is swallowed.** Only INSTALLMESSAGE_ERROR 1500 (an OK-only box, so
  answering IDOK is the answer a person would give). Every other Windows
  Installer question - files in use, retry/cancel - is still theirs.
- **Where the package goes.** `%LOCALAPPDATA%\ghoztty\setup\Ghoztty-<pid>.msi`
  (`setup-debug` for Debug), kept as the install's source for repairs; a good
  install prunes earlier runs' copies. Per-pid so two double-clicks never write
  one file.
- **Build.** `zig build` on Windows installs `zig-out\bin\ghoztty-setup.exe`
  with no package; `-Dsetup-msi=<path>` embeds one (T2198 wires the release).
- **Exit code** is Windows Installer's, so scripts and T2198 can tell outcomes
  apart.
