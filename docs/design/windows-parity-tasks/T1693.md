# T1693 - A window opened after the session manager failed to start is silently not persisted, with no notice

## Summary

When a local-agent resolve FAILS (spawn failed, agent unresponsive past the 2s deadline) every window opened for the next 15s cooldown, and the one that triggered it, opens as a plain local shell. Only a missing agent binary gets a notice (showStartupWarningsIfAny, T1177); the unresponsive/spawn-failed arms are silent, and the windows vanish at the next restart. T976's retry adopts a late agent for the RESTORE, but a window already opened stays unpersisted. Split from T1688, which fixed the in-flight-resolve race only.

## In plain terms

The terminal keeps your windows alive across restarts with the help of a
background session manager. If that manager fails to start, new windows still
open, but they are ordinary windows that will disappear the next time the app
restarts - and nothing told you. Now each such window shows a banner saying it
will not survive a restart, and why.

## Goals

- [x] A window that opens without persistence because the agent failed to start
      says so on its pane, for both the "did not respond" and the "could not be
      started" failures, including windows opened in the cooldown after it
- [x] The notice does not follow the window into the saved layout, so a
      restore onto a healthy agent never repeats a claim that is no longer true
- [x] Healthy windows never show it
- [x] Mac half filed (T1756)

## Where

- `src/apprt/win32/persistence_notice.zig` (new) - the pure rule: which failure
  gets which sentence, and ownership of the literal by text
- `src/apprt/win32/LocalAgent.zig` - `failedStartCause`, gated on
  `last_failure_ms` so a failure a late adoption (T976) already ended is not
  reported
- `src/apprt/win32/App.zig` - `createEmptyWindow` records the owed notice;
  `captureLeaf` leaves it out of the manifest
- `src/apprt/win32/Window.zig` - `pending_persistence_notice`, consumed by the
  first `addTab`

## Design

- **A banner, not a dialog.** It is a fact about one window, it can happen at
  any time rather than only at startup, and it stays true for the window's whole
  life. The pane banner is where T723's agent-unreachable notice already lives.
- **Which failures.** `spawn_failed` and `unresponsive` (the silent arms).
  `agent_binary_missing` keeps its one app-wide startup dialog (T1177) - a
  half-installed app has no persistence for any window, so repeating it on each
  is noise. `protocol_skew` stays with the mandatory-update path (T125). A
  wedged link (T764) is not a failed start and gets nothing here.
- **First terminal pane only, never over an existing banner.** A viewer first
  pane leaves the notice for the next terminal tab; an IPC `--banner` or a
  restored banner is the more specific sentence and wins.
- **Left out of the saved layout** by exact-literal match, the same ownership
  rule T723 uses.
- Retroactively moving an already-running local shell into the agent is not
  possible, so "tell the user" is the whole fix.

## Validation criteria

- [x] A launch whose agent starts but never answers: both the launch window and
      the window asked for in the cooldown after it carry the "Not persisted ...
      did not respond" banner - `test\win32\resolve-window-persist.ps1` C1-C3.
- [x] A launch whose agent cannot be started (not an executable): every window
      carries the "could not be started" banner - same script, D1-D2.
- [x] The notice is not in the saved layout manifest - C4, which was seen RED
      with the `captureLeaf` filter removed (debug rebuild, 12 pass / C4 FAIL).
- [x] Control: a persisted window carries no notice - A4. Sections A/B (T1688)
      still green: ALL PASS (13 assertions).
- [x] The rule is unit-tested (`persistence_notice.zig`: the two arms get their
      sentences, missing/skew/none get nothing, exact-literal ownership) - `none`
      and `win32` lanes via `scripts\floor-lane.ps1 -Lane all`.
