# T2701 - Settings Appearance: clicking 'All N light themes' no longer shows every light theme (settings-window K red since T2683's live preview)

## Summary

settings-window.ps1 section K fails deterministically (parallel and alone, 2026-11-04 14:28 run 20261104-142800/05-settings-window.alone.log): 'K: clicking All N light themes shows them all' - after the click, show_all and/or the tile count do not match light_count. 163 other assertions pass. The harness last stamped before T2683 added the live terminal preview to the Appearance page; suspect the preview moved the All-N link or shrank the tile area so the click lands elsewhere or the grid caps. Reproduce with powershell -NoProfile -File test\win32\settings-window.ps1, read the K block near line 483, fix the app (user-facing: a user clicking All N would see the same symptom) not the assertion.

## In plain terms

After the live preview was added to the top of Settings > Appearance, an
automated test that clicks "All N light themes" started failing. A person
clicking the tile was never affected: the preview pushed the tile half out of
view, and the test was clicking the hidden half. The test's click now lands
on the part of the control you can actually see, the way a mouse would.

## Root cause

`SettingsWindow.clickHit` (the `--op=click` seam) pressed each hit at the
centre of its rect. With the T2683 preview above it, the theme grid's All
tile sat partly below the list's visible edge, so the centre point's `hitAt`
answered something else (or nothing) and the click missed. A real pointer
can only press the visible part, which `onLeftDown` already handled
correctly, so there was no app defect to fix. The fix is `reachablePoint`:
the seam samples a 5x5 grid inside the rect, centre outward, and clicks the
first point where `hitAt` answers that same hit. A hit with no reachable
point is skipped, as a pointer would skip it.
