# T2968 - PA-R02: every terminal pane creates its own D3D11 device and DirectComposition device, about 54 driver threads and tens of MB per pane; share one device across the process

## Summary

PA-R02 (audit-1, T2959). gl_comp_present.zig:499 (D3D11CreateDevice) and :590 (DCompositionCreateDevice) run in Presenter.init once per pane on the default composition path (default_on = true, :82); comp_overlay.zig:879 records the cost as the pane's whole D3D11 device, ~55 driver threads and its GPU memory. Same pattern in child_comp.zig:218 and chrome_comp.zig:643. Measured: threads 76 -> 611 with 10 panes (baseline-1 cycle1.open.threads), private 325 -> 1418 MB, GPU dedicated 52.6 -> 348.8 MB. Fix: one process-wide multithread-protected D3D11 device (and one DComp device per window) shared by every pane swap chain, the sidebar tree and the chrome host; each GL context still opens the shared device with wglDXOpenDeviceNV. Risk medium-high: present/CopyResource from N renderer threads serialize on one immediate context (consider a waitable swap chain or frame-clock-paced Present(0)); device loss becomes process-wide; interop across many GL contexts on one device needs an NVIDIA/AMD/Intel pass. First step: A/B GHOZTTY_COMP_PRESENT=0 and a thread-start-module histogram to confirm the attribution.

## Validation criteria

- [ ] perf-baseline.ps1 -Phase cycle: cycle1.open.threads with 10 panes drops well below 611 (target: under 200), and the per-pane private_mb and gpu_dedicated_mb deltas fall measurably against baseline-1
- [ ] idle phase threads at 1 pane does not rise
- [ ] split/close/tab-switch/drag/glide acceptance harnesses green; a forced device-lost recovery still rebuilds every pane
