# T2548 - Composition step 4e: drop the window's redirection surface (WS_EX_NOREDIRECTIONBITMAP) so the new frame size and every surface reach DWM in one commit; film the resize knob on and say whether the out-of-step frame is gone

## Summary

T2546 filmed GHOZTTY_COMP_CHROME=1 against off (ReleaseSafe, two runs each): the out-of-step frame is NOT removed. With the caption on the compositor the page and its address bar now agree, but the whole client is still one compose behind the window's new size (shrink: gap=9 right=2 on ~1 frame per step), and on grow the strip the window grew into shows the redirection surface's flat fill. What is left is the redirection surface itself: DWM resizes it and shows the new frame at the first compose, whatever the visual tree holds. Remove it (every remaining GDI pixel and the layered children off the window surface first - T2544/T2545), then sequence the visual-tree commit with the size change and re-film with scripts\resize-sync-onscreen.ps1.

## In plain terms

When you drag a window's edge, for a moment the window has its new size but
what is inside it is drawn at the old size. This task builds the window without
the hidden backing picture Windows normally keeps for it, which was the last
suspect left. The window works fine that way, but the film shows the lag is
still there, so the cause is elsewhere (T2575).

## Goals

- [x] a window can be created with no redirection surface, behind its own knob, and still looks complete
- [x] the chrome is painted inside the size message, so it commits with the size change
- [x] film the four edge drags with it on and say whether the out-of-step frame is gone
- [x] file what the film shows is left (T2575) and what the knob still lacks (T2576)

## What landed

- `GHOZTTY_COMP_NOREDIR=1` (`chrome_comp.noredir_knob`): the top-level is
  created with `WS_EX_NOREDIRECTIONBITMAP`, only when the chrome host knob and
  `GHOZTTY_COMP_PRESENT` are on and the window is opaque
  (`chrome_comp.noredirWanted`). A host that cannot be built destroys the
  window and creates it again with the surface, since otherwise it would show
  only what is behind it.
- The **backstop**: the host's target root becomes a base visual whose bottom
  child is one pixel of the configured background scaled 32768x (hard border,
  nearest sampling). The chrome root hangs above it; `deskHide` takes the root
  off the base instead of clearing the target. Re-attached on a device-loss
  rebuild (`create(.., backstop)`).
- `handleResize` runs `UpdateWindow` on a no-redirection window, so the
  caption and desk commit inside the size message.
- GDI children: without a surface under them they compose **black** (first
  film: the viewer's nav bar and the pane sidebar). `gdiChildrenLayered()`
  extends the T1787 layered-child path to the viewer host, the pane sidebar and
  the tab-rename box. The rest of the window's GDI children are T2576.

## Findings (2026-10-31)

`scripts\resize-sync-onscreen.ps1 -Exe zig-out-rsafe\bin\ghoztty.exe`,
ReleaseSafe, `GHOZTTY_COMP_CHROME=1 GHOZTTY_COMP_PRESENT=1`, ghost window.
Bad frames per drag (right-shrink / right-grow / left-shrink / left-grow):

| arm | bad | frames | flat-background |
|---|---|---|---|
| redirected (NOREDIR off) | 41 / 60 / 41 / 65 | 66 / 68 / 65 / 68 | 0 / 46 / 0 / 0 |
| `GHOZTTY_COMP_NOREDIR=1` | 35 / 66 / 42 / 76 | 77 / 81 / 83 / 84 | 0 / 41 / 0 / 46 |

**Verdict: removing the redirection surface does not remove the out-of-step
frame.** What it changes:

- The page and its address bar now always agree (no `pageL/barL` splits), and
  every settled frame scores clean - the window is complete with no surface.
- The lag is now one clean shape: `right=2` on shrink is the whole client
  exactly one 12 px step behind the frame, including the nav bar, a child
  window moved inside the same `WM_SIZE`. DWM shows the new frame size before
  the size message has finished; the surface was not what made it late.
- On grow the strip the window grew into shows the backstop (the window
  background) where it used to show the redirection surface's fill - T2549's
  shape, unchanged in kind.

Next: T2575 (P0, M1) times the size message against the compose and looks for
what holds the frame to the content. T2516 now also waits on T2575.
