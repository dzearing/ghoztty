# T1918 - chrome-theme's hardcoded-RGB sweep (section E) fails on unit-test fixtures: packRgb(30, 30, 30) in desk_palette.zig and pane_elevation.zig tests since T1884/T1885

## Summary

test\win32\chrome-theme.ps1 E 'no file still hardcodes RGB(30, 30, 30)' goes red on desk_palette.zig:146 and pane_elevation.zig:835/844/875/1012/1018/1054 - all inside test blocks (packRgb fixtures), landed by T1884/T1885 on 2026-10-13. The guard row is stuck DUE until it is green. Fix: either the sweep skips test blocks (and proves it with a negative control that a non-test hit still fails), or the fixtures use a value that is not a retired palette literal. Found by T1889's guard run.

## In plain terms

A test that guards the look of Windows dialogs searches the source for the old
hand-picked dark colours. It started failing on unit-test fixtures that use
one of those numbers as an arbitrary sample colour, which paints nothing on
screen. The check now ignores test blocks but still fails if real drawing code
reuses an old colour.

- [x] a retired colour in real code, in either spelling, still fails the sweep

- [x] `floor-lane.ps1 -Lane harness` green for the edited harness (see progress log).

## Root cause

`Select-String -SimpleMatch` is case-insensitive, so the pattern
`RGB(30, 30, 30)` matched the tail of `packRgb(30, 30, 30)`. The
case-insensitivity is kept on purpose (a `packRgb` spelling in paint code is
the same retired fill); the scope narrowed instead, via `Get-RetiredRgbHits`.
