# T1002 - A window only the agent remembers is missed by a launch that could not reach the agent

## Summary

T976 completes the launch restore for the windows it CARRIED, and a carried window is a manifest entry. A crash-orphaned window that exists only in the agent's layout-blob store (T194's adopt path) is never seen by a launch that could not reach the agent, so it is not in the carried set and the deferred pass has no key to name it - the user gets it back only on the next launch. Restoring it late is not just a filter widening: the deferred pass would have to prove such a window is not already on this instance's screen before rebuilding it, or it duplicates a window the user is looking at.

## In plain terms

If Ghoztty crashes, the list of windows it keeps for itself can be lost, but
the background session manager still remembers every window. If the next start
of Ghoztty also can't reach that manager straight away (a busy machine, just
after a reboot), you used to get one empty terminal and your windows came back
only the time after. Now Ghoztty keeps asking for about a minute, and when the
manager answers, those windows come back by themselves, with nothing shown
twice.

## Goals

- [x] A launch that could not reach the agent keeps waiting for it even when
      its own manifest named nothing to restore.
- [x] When the agent arrives, windows only it remembers are rebuilt in the same
      app process.
- [x] Nothing already on screen here is rebuilt a second time.

## What was decided here (no user question filed)

Mechanism-level only, so recorded rather than asked:

- **The duplicate-proof is "on screen HERE", checked two ways.** An agent-held
  window is left alone when its key is a live window's `layout_uuid` (our own
  mirror read back: `pushLayoutBlobs` pushes every live window) or when it names
  a session a live pane of this process is showing (the same shell under another
  key; attaching it would take the shell from the pane the user is looking at,
  T1684). `session_layout.shownHere`, unit-tested.
- **Windows held by ANOTHER running instance** are handled by the existing
  held-session rule: their sessions read as attached, so they have no
  attachable leaf and are skipped.
- **Late windows are never CARRIED.** Carrying keeps a manifest entry alive, and
  these have none; carrying the key would only inflate the "could not give
  back" count.
- **The settle wait looks only at this pass's windows**, so the deferred pass
  never burns its budget waiting on our own panes, which always read as held.

## Validation criteria

- [x] A launch with no agent and an empty manifest arms the deferred pass
      (`restore_retry.shouldArm(0, false, true)`), logging
      `0 window(s) still need the local agent and its own layouts are unread`.
      *Verified: unit tests in `restore_retry.zig`, plus the log of phase E of
      `test\win32\restore-late-agent.ps1`.*
- [x] When the agent arrives, the windows only it remembers come back into the
      SAME app process, live. *Verified: E3/E4/E5 of
      `test\win32\restore-late-agent.ps1`. E0-E2 are the controls: the manifest
      is gone and the agentless launch restored nothing. Before this change
      `shouldArm` was false with nothing carried, so no deferred pass ran and E3
      could not pass.*
- [x] No window is rebuilt twice, and the untouched stand-in is put away.
      *Verified: E6/E7 (exactly the three agent-backed windows, unique names),
      plus `shownHere` and `adoptedWindows` unit tests in `session_layout.zig`.*
- [x] Recovered windows are adopted back into the local manifest. *Verified: E8.*
- [x] Floor stays green. *Verified: `scripts\floor-lane.ps1 -Lane all`, P1-P3.*
