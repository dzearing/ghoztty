# T1553 - relay-account.ps1 scores a false red when the fake relay still holds its hits log

## Summary

Observed 2026-09-13 during T712: section 10 of `test\win32\relay-account.ps1`
scored `FAIL the sign-out revoked this machine (T1421 still holds)`, and the
three lines directly above it were `(could not read ...hits-a.log - held by the
relay job for 1s)`. The very next run of the same script over the same build was
ALL PASS.

So the assertion did not measure the product: it measured whether the fake relay
job had let go of its hits log within the retry window. A red that means "the log
was locked" is indistinguishable in the verdict from a red that means "sign-out
stopped revoking", which is the expensive one this section exists to catch.

## In plain terms

A test of the sign-out flow fails now and then for a reason that has nothing to
do with signing out - it could not read its own scratch file in time. Anyone
reading the result sees a broken feature that is not broken.

## Goals

- [x] a hits-log read that loses the race is reported as an arm that could not be
      measured, not as a failed product assertion (3c6b86a67, T1520: `Get-Hits`
      reads through `Read-SharedLog`, which throws a named harness error; the
      script's catch prints it as `FAIL script terminated: Read-SharedLog ... a
      harness error, not a product result`)
- [x] the race stops happening in practice (3c6b86a67: the fake relay appends
      with `[IO.File]::AppendAllText`, so it never holds the handle between appends)
- [x] the second, different false red the ten-run check turned up is gone:
      section 10's revocation relay is started only after the record and
      relay.env have been read

## Details

The reader already retries and already NAMES the miss, which is why this was
diagnosable at all; what it does not do is refuse to score the assertion that
depends on content it never got. `Write-TestAssertedNothing` is the established
shape in this suite for "this arm could not be measured". Check the writer side
too - `test\win32\lib\FakeRelay.ps1` - if the job keeps the handle open longer
than an append needs.

## Validation criteria

- [x] With the hits log deliberately held open, the read reports a harness
      error rather than an empty log: `job-teardown.ps1` section G holds a log
      with FileShare.None and asserts `Read-SharedLog` THROWS `harness error` in
      bounded time (landed with T1520).
- [x] Ten consecutive runs of `relay-account.ps1` are green: 10/10 ALL PASS
      (168 assertions each) through `acceptance-parallel.ps1 run`, serial,
      2026-11-20 after the section 10 fix. The 9 runs before it scored 7 green
      and 2 red (runs 4 and 8: `the record carries the device credential the
      retry needs`, `the record names the relay`, `relay.env is kept`) - none of
      them the hits-log race; see the progress log. Scoped harness floor PASS.

## Resolution

The defect this card names was fixed in passing by **3c6b86a67 (T1520)**: the
writer stopped holding the hits log and the reader stopped turning a lost read
into an empty log. The ten-run check it was owed then found a different
false red in section 10: the revocation relay was started right after the
click, so the app's immediate first attempt could succeed and SPEND the pending
record (and delete relay.env) while the test was still reading them. The relay
now starts after those reads, so attempt 0 always fails and the 5 s/15 s backoff
retry is what lands - which is what the section claims to test anyway.
