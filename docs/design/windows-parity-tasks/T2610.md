# T2610 - Present every terminal pane of a window through ONE GL child window (per-window presenter, shared contexts) so no top-level ever has two plain WGL presenters - the driver-level cure for T2599/T2499 proven by test\zig-repro\t2599-wgl-multichild

## In plain terms

Today each terminal pane draws into its own little window. When a window
holds two or more panes, the graphics driver leaks a window-sized chunk of
video memory each time the window is minimized and restored, and again each
time a pane closes. When this lands, each Ghoztty window draws all its
panes through one drawing surface. Nothing leaks, and the black-strip
flicker fix (T2592) can ship.

## Summary

**Evidence (2026-11-01, T2599).** `test\zig-repro\t2599-wgl-multichild` is a
standalone Win32 + WGL program with no Ghoztty code. On the RTX 4090 (WGL,
1000x700 top-level) it shows:

- two LIVE plain GL children that have each swapped: **+3.0 MB per hide/show
  and per minimize/restore**, never freed, whether or not anything presents
  after the show;
- destroying a second child that has swapped strands **3 MB once** (T2499's
  per-pane leak; T2597's pane pool only works around it);
- **one GL child with two contexts scissoring into it and swapping once: flat
  across every cycle.** That is this task's architecture, checked before
  building it.

A context that never swaps costs nothing, and neither does a GDI child, so
viewer panes and the chrome are not part of the problem.

**Shape.**

- Each window gets one plain GL **presenter** child covering the pane area,
  with its own context and thread. Pane renderers keep their own contexts
  (created with `wglCreateContextAttribsARB` sharing the presenter's group,
  since `wglShareLists` after the fact is refused, see T2599). They render
  into their offscreen `Target`, which the OpenGL renderer already has (the
  GTK path renders to an FBO). `present` then hands off the texture plus a
  fence instead of blitting and calling `SwapBuffers` on the pane's own
  window.
- The presenter draws every pane's latest texture into its rectangle, fills
  the gaps and any uncovered strip with the background, and swaps once. A
  resize becomes a re-draw of textures it already holds, which may also cure
  the T2592 strip at its root.
- Pane HWNDs stay, for input, IME, focus, drag-drop and the IPC pane
  identity, but they stop presenting: no pixel format and no swap. How they
  stay out of the presenter's way (the presenter beneath without
  `WS_CLIPCHILDREN`, paint-validate-only panes, or windowless hit-testing) is
  the first design step. Spike it in the repro first.
- A knob (`GHOZTTY_WINDOW_PRESENTER`) keeps the old per-pane present path for
  A/B runs until the new path is the default.

**Interactions to carry:** per-pane pacing and vsync (one swap now serves N
renderers), the frame-lab ring trace and planted frames (T2383), hero
thumbnails (T59a, read from the offscreen target, so that should be fine),
lost-device recovery (T1690), the composition present (`gl_comp_present`,
T2466/T2606), translucent windows (`background-opacity` < 1), the
banner-band span (T2566), the pane pool (T2597, retired once this lands),
and `pane_layer` (T2499/T2502, retired too).

**Steps:** (1) extend the repro with two threads, each rendering into a
shared FBO texture, and a presenter composing them; confirm flat. (2) Write a
design note for the pane-HWND question. (3) Implement behind the knob.
(4) Validate. (5) Make it the default, and close T2599 and unblock T2592.

## Validation criteria

- [ ] repro spike: two renderer threads + one presenter child stay flat across hide/show, minimize/restore and pane churn
- [ ] `window-close-memory.ps1 -Shape split` and `-Shape full` A8 <= 1 MB with the presenter on
- [ ] the T2599 step probe (split, close, 3x hide/show and minimize/restore) is flat with the presenter on
- [ ] T2592's near-full fold drag shows 0 black frames in 3 live runs with the presenter on
- [ ] the floor lanes and the pane/resize acceptance harnesses are green with the presenter on by default
