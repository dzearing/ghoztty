# T1552 - A sign-in or sharing result lands on the first open machine chooser, not the one the user used

## Summary

`RelayAccountRow.openChooser` and `ShareMachineRow.openChooser` both return the
FIRST window with an open machine chooser and deliver the result there. With two
windows each holding a chooser, a sign-in completed in window B can therefore
land on window A's chooser: B keeps showing "Sign in with Google" and never
fetches its list, while A's row updates on its own. Same for the per-machine
sharing toggle's result.

This was always reachable - a chooser was only ever modal to its own window -
but T712 made the chooser modeless, so having two open at once is now an easy
thing to do rather than an awkward one. Noted in the comment above both
functions.

## In plain terms

Open the machine picker in two windows, sign in from the second one, and the
first one is what updates - the window you actually used still says you are
signed out. Nothing is lost (reopening the picker shows the truth), but the
window you were looking at appears to have ignored you.

## Goals

- [ ] a sign-in / sharing result reaches EVERY open chooser, not the first one
- [ ] an acceptance arm that opens two choosers and completes a sign-in in the
      second, failing when the first is the one that updates

## Details

The fix is small and the shape is already there - both callers iterate
`app.windows` - so the change is to notify each open chooser rather than return
early, with `onAccountResult` / `onShareResult` staying idempotent per chooser.
The harness to extend is `test\win32\relay-account.ps1`, which already drives a
fake relay through the whole signed-out -> signed-in row.

## Validation criteria

- [ ] With a chooser open in two windows and a sign-in completed from the
      SECOND, both choosers' account rows show the signed-in state.
- [ ] The same for the sharing toggle's result.
- [ ] The new arm fails against the pre-fix build (it is the current behavior,
      so this is a direct before/after).
