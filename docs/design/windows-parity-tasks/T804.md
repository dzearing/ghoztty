# T804 - Measure the repaint labeling where nothing repaints behind it: a cross-machine attach to a POSIX agent

## Summary

T739's on-box arms all ran against the LOCAL Windows agent, where ConPTY paints a fresh screen after every attach - real stream data anchored at the head, which re-states the true position over a miscounted one. That is why arm C (repaint_data suppressed) still recorded requested==head. The case the 0x15 framing actually saves is the one where the injected repaint is the LAST thing on the wire: a peer that does not repaint on attach, i.e. a cross-machine POSIX agent (or any session that produces nothing after the attach). Prove it end to end - attach a window to a POSIX agent (WSL is enough), kill and re-attach twice, and require requested==head with the capability on and an overshoot with GHOSTTY_AGENT_SUPPRESS_CAPS=repaint_data. Today that claim rests on unit tests only.

## In plain terms

When a terminal window reconnects to a session that has been running in the
background, it has to remember how much of that session's output it has already
shown. On Windows that number came out right for a reason that has nothing to do
with the mechanism meant to keep it right: the Windows console redraws the screen
after every reconnect, and that redraw quietly restated the true position. A
session on another machine does not redraw, so there the number was being kept by
nothing at all — and measuring that here is what this task was for. It turned out
the mechanism really was doing nothing, so it was repaired as well as measured;
without the repair, a reconnected pane on a remote machine would replay a chunk
of output it had already shown.

      the measurement this task exists for, and the thing arm C cannot see. —
      arm E (`+ GHOSTTY_AGENT_SUPPRESS_CAPS=repaint_data`): requested 674 against
      head 409 on every cycle after the first, clamp fired on each, `labeled=false`.

Root cause: Connection.advanceStreamPos did 'panes.get(channel) orelse return' - the agent frames ATTACHED on the control lane and the replay+repaint on the data lane, so those frames land before trackPane; their bytes are held by ChannelTable.pending and flushed by register, but the position they imply was dropped and then overwritten by .stream_pos = .init(resume_at). Same drop hit the gap-fill REPLAY, which is real stream data - position forgotten, next attach resumes below it and the agent replays it again. Fix: Connection.early_stream_pos (only for .buffered pushes, so bounded by the channel table's own caps), folded into the pane by trackPane under panes_mutex with @max so a clamped attach is never dragged backwards. After the fix D holds 407 across 3 cycles and E overshoots to 674 with the clamp firing - the label is now load-bearing and measured.
