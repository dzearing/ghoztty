# T678 - The ViewerPane live WebView2 host-floor test times out (untripped point=read) when the win32 lane follows an acceptance run

## Summary

`apprt.win32.ViewerPane.test.host floor: a real controller on a real window,
on this box` failed the win32 lane once during T149's floor run, with
`[tripwire] (warn): untripped point=read` — the tripwire that says a live
WebView2 controller never reached the point the test waits on. Three runs of
the same tree, same command, on 2026-08-09:

| time | how it was run | result |
|---|---|---|
| 19:5x | `zig build test -Dapp-runtime=win32` directly | PASS |
| 20:10 | `floor-lane.ps1 -Lane all`, started right after `pane-banner.ps1` | **FAIL** (325s) |
| 20:2x | `floor-lane.ps1 -Lane win32` alone, box quiet | PASS (341s) |

So it is a timing flake, not a regression, and the middle run is the one that
differs: it began moments after a GUI acceptance script that launches and kills
Ghoztty processes and their WebView2 host trees. `floor-lane` reported `leaked
webview hosts swept: 0`, so nothing was left running by ITS accounting — but a
just-killed WebView2 process tree can still be tearing down its user-data
folder locks while the next `CreateCoreWebView2Environment` asks for one.

This is NOT T443's armed watch: that one's unblock criterion is a bare access
violation or abort (a crash), and this is a clean assertion failure on a
timeout, with the binary exiting normally.

Worth knowing before touching it: go.md already forbids overlapping a lane with
an acceptance script (T401), and this run did not overlap them — it ran them
back to back. If the settle time is the cause, the honest fix is for the LANE to
wait for (or verify) a quiet WebView2 state before the live tests rather than
for every caller to remember a sleep.

## In plain terms

One of the automated tests that drives a real embedded browser occasionally
fails because the browser takes too long to come up, usually right after another
test has just shut a browser down. Nothing about the product is broken when it
happens, but a red test that is not a real failure teaches people to ignore red
tests.

## What the lane could not see

The pre-lane settle T592 added waits for TEST-BINARY browser trees, named by
the private `ghoztty-wv2test-<pid>` profile or by `--webview-exe-name=<test
exe>`. An acceptance script's viewer panes carry NEITHER: they run in a
repo-built debug Ghoztty and use that app's own profile,
`%LOCALAPPDATA%\ghoztty\EBWebView-debug`. So in the one shape the wait exists
for -- an acceptance script, then a lane, back to back -- it reported "nothing
to settle" and the lane started blind. Measured on 2026-09-09: a single
`test\win32\viewer-panes.ps1` run stands up **17** of those browser processes,
and the settle saw zero of them.

The refinement that was written first and thrown out: only waiting for an
ORPHANED tree (one whose app is already gone), so a dev Ghoztty left open would
cost a lane nothing. Sampling at 250ms through a whole viewer-panes run never
observed an orphan -- the app and its entire browser tree disappear inside one
sample, because the kill-on-close job object takes the tree with the app. A
wait keyed on that state would have been a no-op wearing a fix's clothes, so
the shipped rule is the simple one: any debug-profile browser tree is waited
for, bounded by the deadline, and a give-up SAYS what it was waiting on.

The release profile has no `-debug` suffix, which is what keeps the user's own
terminal -- whose viewer panes run out of the same exe -- outside this
entirely.

## Validation criteria

- [x] The failure is reproduced deliberately (e.g. an acceptance script
      immediately followed by the win32 lane, repeated) rather than waited for —
      or, if it cannot be reproduced in N attempts, that number is recorded here
      — **not reproduced in 3 attempts** (pane-banner, then the win32 lane,
      three times on 2026-09-09: PASS 411s / 229s / 406s). What WAS reproduced
      is the mechanism: sampling at 250ms through a `viewer-panes.ps1` run
      showed 17 debug-profile browser processes the settle could not see, and
      showed them leaving with their app inside a single sample
- [x] Whatever the cause turns out to be, the fix is in the LANE or the test's
      own wait, not a sleep every caller has to remember — `Get-WebViewAppDebugHost`
      plus `Wait-WebViewLaneSettle -IncludeAppTeardown`, in floor-lane's
      pre-lane wait; no caller changes and no sleeps
- [x] `scripts\floor-lane.ps1 -Lane win32 -Repeat 3` green immediately after a
      `test\win32\pane-banner.ps1` run — 3/3 PASS, 2026-09-09
- [x] The live-runtime tests still fail loudly on a box with no WebView2 runtime
      (T372's rule: a quiet skip is a test reporting success for work it never
      did) — untouched (no Zig change), and none of the three lane logs carries
      a `SKIPPED live controller` line, so the host floor ran against the live
      runtime rather than quietly standing down
