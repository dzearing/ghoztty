# T1972 - Panes restored after a restart have no user PATH (only a new pane gets it): restored shells skip the T42 user-environment merge

## In plain terms

After a restart, the restored terminals cannot find your tools, because
their PATH is missing your entries. A brand-new pane works. A restored pane
must start with the same environment a new pane gets.

## Summary

User report (2026-10-15), part 2 of the T1970 report: "the environment
variables aren't loaded so path isn't working. I have to open a new pane
for path to be loaded".

`src/os/user_env.zig` (T42) merges the registry `Path` (HKLM then HKCU) and
any missing user variables into every shell the agent spawns. It exists
because the agent's own environment is a snapshot from whatever started it
(an HKCU Run entry, an MSI custom action, a self-update relaunch). New
panes evidently get that merge. Restored or relaunched panes evidently do
not.

Suspects:

- **A restore or relaunch path that spawns without `user_env`.** Candidates:
  the agent relaunching a dead session, the app-side respawn when no agent
  is found (T1970), and the pty-host spec carrying a SAVED environment
  block (`pty_host_spec.zig`, `server.zig:428`) captured before the user's
  PATH changed.
- **The app itself was relaunched by Restart Manager or msiexec**, so its
  own environment lacks the user's PATH. Restored panes inherit from it,
  while new panes go through the merge.

Fix: route every shell spawn, whatever the path, through ONE function that
applies the T42 merge, with a test that fails if a spawn site bypasses it.

## Root cause

Every shell the AGENT spawns goes through `PtySpawner.spawnChild`
(`remote/agent/pty_child.zig`) or `proc_spawn`, and both apply the T42
merge — that includes restore, relaunch, the pty-host holder and remote
opens. The one shell spawn that did NOT was the app's own exec backend:
`apprt/win32/Surface.zig` `defaultTermioEnv` returned the app's raw
environment. A restore uses that backend whenever the local agent cannot be
reached inside its 2s bound (`LocalAgent.zig`: "the caller opens a plain
exec surface for that window instead", plus a failure cooldown) — exactly
the state after an installer or a restart killed the agent (T1970). An app
relaunched by msiexec / Restart Manager carries a PATH without the user's
entries, so every restored pane did too. A pane opened a minute later went
through the now-running agent, which merged the PATH: the reported
"I have to open a new pane for path to be loaded".

## Fix

`defaultTermioEnv` now calls `internal_os.user_env.overlay` (additive, same
rule and same `GHOZTTY_USER_ENV=off` hatch as the agent). The shell spawn
sites are enumerated in `os/user_env.zig` (`shell_spawn_sites`) and a unit
test fails if any of them stops calling `user_env.overlay(`.

## Goals

- [x] Restored panes that fall back to the app-side shell get the user PATH
- [x] Every shell spawn site is enumerated and guarded by a test
- [x] Acceptance with a negative control

## Validation criteria

- [x] Every spawn site (new pane, split, restore, relaunch, remote open,
      agent respawn) goes through the shared environment builder. They are
      enumerated, and a test fails if one bypasses it.
      — agent paths all funnel through `spawnChild`/`proc_spawn`; the app
      path is `defaultTermioEnv`; `user_env.zig` test "every shell spawn site
      applies the user-environment overlay (T1972)" (none/win32/agent lanes
      green via `floor-lane.ps1 -Lane all`).
- [x] Acceptance: `test\win32\exec-user-env.ps1` (new, guard row
      `exec-user-env`): an app launched with its PATH stripped to
      system32+Windows, exec pane, dumps `set > file` — the user's HKCU PATH
      entry is present and system32 stays first (A1-A3); negative control
      with `GHOZTTY_USER_ENV=off` has only 3 entries and no marker (B1-B2).
      ALL PASS (6 assertions). `agent-user-env.ps1` still ALL PASS (20).
      The exec pane is the same construction site the restore fallback uses
      (`Surface.zig` is the only backend construction site); forcing the
      fallback itself needs an agent that will not come up, which is T1970's
      repro.
- [ ] The same check passes for an app relaunched by the T1934 auto-apply
      (msiexec context). NOT RUN: needs a real MSI apply on this box (Docker
      for wixl, user-gated). The fix does not depend on the launching
      context — the merge reads the registry at spawn time — so this is
      covered by construction, and T1970's restart acceptance exercises it.
