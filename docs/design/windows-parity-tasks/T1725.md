# T1725 - The default win+shift+up/down (previous/next pane) is Windows' own stretch-window shortcut, so a real keypress probably never reaches Ghoztty

## Summary

Found by T1149. The shipping defaults include super+shift+arrow_up/down = goto_split previous/next (Config.zig, hero-mode navigation block). On Windows, Win+Shift+Up/Down are reserved by the shell (stretch the window to full height / restore it) and the shell's low-level hook takes them before any app sees WM_KEYDOWN. Posted-message tests cannot see this (T1149 proved super reaches the binding lookup when the key is delivered), so it needs a real-keyboard check (SendInput on the interactive desktop, or by hand) and, if confirmed, a Windows-native default for these two actions plus a list of any other super defaults the shell reserves.

## In plain terms

Ghoztty's shortcut for "go to the previous / next pane" was Windows key +
Shift + Up / Down. Windows already uses that combination to stretch a window
to full height, so on a PC pressing it resized the window instead of moving
between panes, and the menus and command palette were advertising a shortcut
that could never work. On Windows it is now Ctrl + Alt + Page Up / Page Down,
next to Ctrl + Page Up / Page Down, which already switch tabs. Mac is
unchanged.

## Goals

- [x] Confirm the chord really is Windows' own
- [x] Give Windows a previous/next-pane default that reaches the app
- [x] The shortcut shown in menus/palette is the working one
- [x] Audit the other Windows-key defaults for shell collisions

## Findings

**Shell ownership.** Microsoft's Windows keyboard-shortcut reference lists
Win+Shift+Up ("stretch the desktop window to the top and bottom of the
screen") and Win+Shift+Down ("restore/minimize active desktop windows
vertically"), and the RegisterHotKey documentation reserves Windows-key
shortcuts for the operating system. An ad-hoc SendInput probe on the
interactive desktop could not take the foreground on this box (the same
foreground-lock problem that moved the acceptance harness off-desktop), so it
produced no evidence either way and was abandoned rather than scored.

**Other Windows-key defaults** (`+list-keybinds --default` on the win32 build):
`super+ctrl+[`/`]` (previous/next pane), `super+ctrl+shift+arrows`
(resize_split), `super+ctrl+shift+j` (write_screen_file copy). None of them is a
documented Windows shortcut (the documented Win+Ctrl ones are Left/Right for
virtual desktops, D, F4, Enter, Shift+B, none of which we bind), so no other
change is owed. T1149 already drives the first two through the chord route.

**Choice of chord** (mechanism call, recorded here per go.md 5b): ctrl+alt+
page_up/page_down. Ctrl+Shift+Up/Down is swap_split; Ctrl+Alt+Arrows is the
directional goto_split; a ctrl+alt+`[`/`]` mirror of Mac's cmd+`[`/`]` would
fire when an AltGr layout (German, French, ...) TYPES a bracket, because AltGr
arrives as ctrl+alt. Page keys are named keys no layout turns into a
character. Registered after `super+ctrl+[`/`]`, so it is the reverse-lookup
answer the palette and menus display.

## Validation criteria

- [x] On Windows, ctrl+alt+page_up/page_down resolve to goto_split
      previous/next, super+shift+up/down are unbound, and the reverse lookup
      returns the new chord - unit test `default keybinds: windows
      previous/next pane avoids the shell's win+shift+arrows` (none lane),
      negative control (flipped expectation) went red first.
- [x] Mac and Linux keep super+shift+up/down - the edit is gated on
      `os.tag == .windows`; the `lib` lane compiles the shared core.
