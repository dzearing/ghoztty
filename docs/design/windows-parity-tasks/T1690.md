# T1690 - Every Ghoztty window dies when Windows updates or resets the graphics driver

## Summary

On 2026-09-20 Windows Update replaced the NVIDIA display driver under a running app; the renderer logged three 'software processing fallback in framebuffer pipeline' warnings and the whole process died, taking every window with it (the agents kept the sessions). The app must survive a GPU device loss / driver swap: detect the lost OpenGL context and rebuild the renderer (or fall back) instead of dying. Reproduce with a driver reset (e.g. Win+Ctrl+Shift+B, or disabling/enabling the display adapter) against a zig-out build; the T1686 exit ledger names what happened.

## In plain terms

When Windows updated or reset the graphics driver, every Ghoztty window closed
at once. The shells kept running in the background, but the windows were gone.
Now each window notices that its graphics connection went away, builds a new
one, and keeps drawing. At most you see a brief blank frame.

## Goals

- [x] Ask the driver for a context that reports a reset instead of crashing (a robust context), and fall back to a plain one when the driver has no robust option
- [x] Check for a lost device after every frame and rebuild that pane's context and GPU resources in place (shaders, frames, glyph atlas, inline images, background image)
- [x] Keep retrying on a backoff while the driver is still missing (a driver *replacement* can take a minute), without the app exiting
- [x] An acceptance script that proves a rebuilt pane really draws again, from its pixels

## Resolution

**Cause.** Surfaces created their OpenGL context with plain
`wglCreateContext`. A plain context has no contract for a device reset, so
whatever happens next is the driver's choice. During the 2026-09-20 NVIDIA driver
swap the driver ended the process.

**Fix.**
- `src/renderer/gl_robust.zig` (new): creates the context through
  `wglCreateContextAttribsARB` with `WGL_CONTEXT_ROBUST_ACCESS_BIT_ARB` +
  `WGL_LOSE_CONTEXT_ON_RESET_ARB` when `WGL_ARB_create_context_robustness` is
  offered, else a plain context as before. No version or profile is requested,
  so apart from reset handling the context is the same one as before. The pure
  policy (attribute list, whole-token extension match, reset-status mapping,
  retry backoff 0/250/1000/2000 then 5000 ms, and a log rate limit) has unit
  tests in both lanes.
- `src/renderer/OpenGL.zig`: after each `SwapBuffers`, calls
  `glGetGraphicsResetStatus`, resolved per thread. On a loss it drops every
  name that belonged to the dead context. `rebuildContext` deletes the old
  context, creates a new one on the same DC, makes it current and re-runs
  `prepareContext`, which applies the same version floor. That means GDI's 1.1
  on the basic display adapter is refused and retried.
- `src/renderer/generic.zig` `recoverLostContext`: tears down the swap chain,
  shaders, images and background image while the dead context is still current
  (GL calls on a lost robust context are no-ops). It then rebuilds them in the
  new context. `drawFrame` skips drawing while the swap chain is defunct.
  Metal has no `contextLost`, so this is all comptime-off there.
- `src/renderer/image.zig`: `force_kitty_update` re-scans the terminal's image
  storage, because uploaded image pixels are no longer held CPU-side.
- `src/renderer/Thread.zig`: calls recovery after each draw. A retry timer
  brings an idle pane back without waiting for output, and a wakeup after
  success redraws the pane.
- Debug-only seams (never compiled into a release build):
  `GHOZTTY_GL_SIMULATE_RESET_AFTER=<frames>` and
  `GHOZTTY_GL_SIMULATE_REBUILD_FAILURES=<k>` (per pane). Only detection is
  simulated. The rebuild really deletes and recreates the context.

**Not done here.** A REAL driver reset was not triggered. Win+Ctrl+Shift+B
would also hit the user's installed terminal, which runs pre-fix code, so a
real-reset check is filed separately.

## Validation criteria

- [x] Contexts are robust on this box's driver: `test\win32\gl-device-lost.ps1` A1/C2 (`GL context created robust=true`)
- [x] A lost device is rebuilt on the first attempt, the app and window stay up, and the rebuilt pane's own pixels show text over its tint (127 colors, dominant #204080) with no OpenGL errors after the rebuild: A2-A10
- [x] A device that stays unusable is retried and comes back on the 4th attempt, and the pane draws its own tint: B0-B6
- [x] Negative control: with nothing simulated and every frame checked, a healthy device is never reported lost: C0-C3
- [x] Policy unit tests (`gl_robust.zig`) green in the `none` and `win32` lanes, via `scripts\floor-lane.ps1 -Lane all`
