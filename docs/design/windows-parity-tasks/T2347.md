# T2347 - Windows all-windows sidebar lists in background windows still re-read their roster on every pane/title change in any window; Mac defers that to when the window is next activated (PaneRoster catch-up)

## Summary

Found while landing T2336. Mac (9a1f14230, docs/reference/pane-sidebar.md "Shared across windows") redraws a background window's sidebar for another window opening, closing or changing its panes (`PaneRoster`) only when that window next becomes key. Windows still calls `PaneSidebar.refreshScopes` from every `Window.syncPaneSidebarScoped`, so every all-windows list in every window re-reads (and hashes) the whole roster on each layout/focus/title/activity event anywhere. The signature hash makes it cheap and nothing visible is wrong, which is why T2336 left it.

Fix shape: mark background sidebars roster-stale instead of refreshing them (`refreshScopes` skips windows that are not the active one), and refresh in `PaneSidebar.catchUp` (already called from WM_ACTIVATE). Check pane-sidebar-all-windows.ps1 section 6, which asserts A's list follows a rename/close in other windows while A may not be active - it may need an activation step, or the deferral must keep the window that the user is looking at live.

## Validation criteria

- [ ] A background window's all-windows list does not re-read its roster for another window's change (log/counter), and does on activation
- [ ] pane-sidebar-all-windows.ps1 and pane-sidebar-shared.ps1 stay ALL PASS
