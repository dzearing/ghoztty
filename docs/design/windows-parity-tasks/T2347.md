# T2347 - Windows all-windows sidebar lists in background windows still re-read their roster on every pane/title change in any window; Mac defers that to when the window is next activated (PaneRoster catch-up)

## Summary

Found while landing T2336. Mac (9a1f14230, docs/reference/pane-sidebar.md "Shared across windows") redraws a background window's sidebar for another window opening, closing or changing its panes (`PaneRoster`) only when that window next becomes key. Windows still calls `PaneSidebar.refreshScopes` from every `Window.syncPaneSidebarScoped`, so every all-windows list in every window re-reads (and hashes) the whole roster on each layout/focus/title/activity event anywhere. The signature hash makes it cheap and nothing visible is wrong, which is why T2336 left it.

Fix shape: mark background sidebars roster-stale instead of refreshing them (`refreshScopes` skips windows that are not the active one), and refresh in `PaneSidebar.catchUp` (already called from WM_ACTIVATE). Check pane-sidebar-all-windows.ps1 section 6, which asserts A's list follows a rename/close in other windows while A may not be active - it may need an activation step, or the deferral must keep the window that the user is looking at live.

## In plain terms

With the sidebar showing every window, each open window used to redo its whole
list whenever any pane in any window changed its title or its busy state, and
with spinner titles that is ten times a second. Now only the window you are
using keeps up with those as they happen. The others update the moment you
switch to them, which is what the Mac does. Nothing looks different. There is
just less work going on behind every title tick once many windows are open.

## Goals

- [x] Background windows' all-windows lists mark themselves stale on a title/activity change instead of re-reading
- [x] Activation re-reads a stale list (the hash still decides whether it repaints)
- [x] A layout, focus or close change still reaches every list at once (rows hold pane/window pointers)
- [x] The acceptance proves both halves

## Decision (mechanism, recorded per go.md 5b)

The first cut deferred EVERY other-window refresh. It was withdrawn: a list's
rows point at panes and windows, and paint, hover and sheens read through them.
Close-undo parks a pane before freeing it, so a list that deferred at park time
could still name the pane when it is freed. Only the coalesced title/activity
refresh (T1935's `schedulePaneScopes` -> `refreshScopesLive`) defers, which is
the flood. `refreshScopes` (layout, focus, window close, workspace hand-off)
reaches every list as before. Policy: `src/apprt/win32/pane_roster.zig`.

## Validation criteria

- [x] A background window's all-windows list does not re-read its roster for another window's title/activity change (log), and does on activation - pane-sidebar-all-windows.ps1 section 6a (`+set-state c1 busy` with another window in use logs `roster deferred window=A` and no catch-up; activating A logs `roster caught up window=A`; in use, `+set-state c1 idle` defers nothing); unit tests in pane_roster.zig (live/every x activated/stale)
