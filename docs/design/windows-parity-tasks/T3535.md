# T3535 - Windows diff pane: previous change rolling back into the previous file enters it at its TOP, not its last change (ViewerPane.applyDiffPatch drops the probe request's scroll_to)

## Summary

Found porting T3417: diffNavOverflow asks openDiffFile(at, 'last'), requestPatch carries it into the Job, but ViewerDiffProbe.complete() never publishes the job's scroll_to and applyDiffPatch pushes setDiffFile with scroll_to=null. So walking a diff backwards lands on each earlier file's first line instead of its last change (Mac walks in reverse). Linux keeps its own pending_scroll (src/apprt/gtk/ViewerDiff.zig); fix win32 the same way or publish scroll_to from the probe, and add the check to viewer-diff.ps1.
