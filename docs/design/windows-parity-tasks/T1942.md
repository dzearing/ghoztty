# T1942 - Confirm the first win-v release after T1936 carries Ghoztty-symbols-<version>-x64.zip and that fetch-symbols.ps1 MATCHes the installed app once the updater takes it

## Summary

T1936 wired the symbols asset into release-windows.yml and proved the packager, the identity check and cdb resolution on the box, but no release has been cut through CI with it yet (win-v1.39.8 went out minutes before the change). Once the next win-v release exists: gh release view shows three assets; the CI log shows '(match)' for all three pairs; after the in-app updater installs it, scripts\fetch-symbols.ps1 with no arguments prints MATCH and a cdb -z of the installed ghoztty.exe reads (private pdb symbols). Tick T1936's first two validation criteria from the result.

## In plain terms

When Ghoztty crashes or hangs on someone's machine, the stack it leaves behind
is just numbers unless the matching debug symbols exist. The release pipeline
was changed to publish those symbols with every Windows release; this task
checks that a real release actually carries them and that they fit the app
people install.

## Goals

- [x] A real CI-built release carries the symbols download
- [x] The build machine's own identity check passed for every binary
- [x] The symbols fit the exact app bytes the updater installs, and a debugger reads them

## Validation criteria

- [x] `gh release view win-v1.39.17` lists three assets: `Ghoztty-1.39.17-x64.msi`,
  `Ghoztty-portable-1.39.17-x64.zip`, and `Ghoztty-symbols-1.39.17-x64.zip` (67 MB). That is the
  latest published release, and it contains 10b07fc1b (`git merge-base --is-ancestor` = 0).
- [x] The CI log of release run 38849027193 prints `(match)` for all three pairs:
  `ghoztty.exe` and `ghoztty.com` against `ghoztty.pdb 39E1F0883AC9DB4D4C4C44205044422E1`, and
  `ghoztty-agent.exe` against `ghoztty-agent.pdb 1BDD62E5A0B361D14C4C44205044422E1`.
- [x] `scripts\fetch-symbols.ps1 -Exe <exe> -Version 1.39.17` prints MATCH and exits 0 for both
  `ghoztty.exe` and `ghoztty-agent.exe`. Both exes came out of the MSI the updater staged
  (`%LOCALAPPDATA%\ghoztty\updates\Ghoztty-1.39.17-x64.msi`, same size as the release asset). I
  copied the MSI and read its embedded cab through the read-only `WindowsInstaller.Installer`
  COM API plus `expand.exe`, so nothing was installed. An MSI install copies those bytes to disk
  unchanged.
- [x] `cdbX64 -z <msi ghoztty.exe> -y srv*%LOCALAPPDATA%\ghoztty\symbols\1.39.17` (no pdb beside
  the image) shows `ghoztty C (private pdb symbols) ...\symbols\1.39.17\ghoztty.pdb\39E1F088...\ghoztty.pdb`
  and resolves `ghoztty!main`.
- [ ] NOT RUN: `fetch-symbols.ps1` with no arguments against the installed app. The user's
  install is still 1.39.8, which predates T1936, so it correctly answers "release win-v1.39.8
  has no Ghoztty-symbols". The updater has already staged 1.39.17 and is offering it
  (`update-offer.txt`). Applying it would restart the user's terminal, so that stays their
  call. The byte-identical MSI check above covers the same thing; once they take the update,
  the no-argument run only changes which path is passed in as `-Exe`.
