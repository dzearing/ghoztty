# T698 - A reader that returns nothing 60 times running is a broken reader, and the gate logged it as a quiet pane

## Summary

T663's root cause was visible in every delivery log for months, in these words: 'reuse: pane <id> not settled (pane produced no text in 60 read(s)); typing anyway'. That sentence is true and useless - it describes the PANE, when the thing that had produced no text was the READER. Wait-LoopPaneReady cannot tell 'this pane has printed nothing yet' from 'my capture of this pane returns zero bytes every single time', and it degrades both to a warning nobody acts on. Worth distinguishing: a reader that has returned an empty string for every one of N consecutive reads has told you something about itself, not about the pane, and the honest report is 'the pane could not be READ' - which is a different sentence, and one that would have named this defect the first time it happened. Cheap shape: have the readiness result carry whether it ever saw a single non-empty read, and let the caller say so; a pane that printed nothing but answered with an exit code is a different state from a call that captured nothing at all. Keep the typing-anyway behaviour (a genuinely silent pane must not stall a delivery) - change only what is said about it.

## In plain terms

When the app is upgraded, the last thing the delivery does is type a prompt back into the terminal pane it interrupted. Before typing, it waits for that pane to look alive. For months, when the wait ran out, the log said the pane had printed nothing - and that was the wrong suspect: what had printed nothing was the thing doing the reading. Now the run says which of the two happened, so the next person reading the log starts at the right end of the problem.

## Goals

- [x] The readiness result records whether ANY read ever captured text, across the whole run rather than only the last read
- [x] A read that fails is counted separately from a read that succeeds and returns nothing
- [x] When nothing was ever captured, the log names the reader rather than the pane, and says how many reads failed
- [x] The typing-anyway behaviour is unchanged - a genuinely silent pane still must not stall a delivery
- [x] The arrival gate below it, which reads through the same path, says the same thing when it hits the same state
