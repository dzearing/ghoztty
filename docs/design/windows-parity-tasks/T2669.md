# T2669 - Does an idle Ghoztty grow forever on NVIDIA because the GL driver keeps 64 KB for every thread the process ever creates (OS thread-pool workers included)?

## In plain terms

On this NVIDIA machine the graphics driver keeps a little memory for every
thread a program ever starts, and never gives it back. T2644 fixes the
threads that Ghoztty itself starts per window. Windows also starts and stops
helper threads inside the program on its own, so a terminal left open for
days might still creep upward. This task measures whether it does.

## Summary

T2644 named the allocation by stack: `nvoglv64!DllMain` on DLL_THREAD_ATTACH
`VirtualAlloc`s 64 KB for every new thread and never frees it (driver 616.64,
RTX 4090; repro `docs/design/t2644-gl-thread-churn.zig` mode 6 vs control
mode 8; trace `docs/design/t2644-gl-thread-churn-trace.ps1`).
`DisableThreadLibraryCalls` on the DLL returns success and changes nothing.

That cost is not limited to threads we spawn. The NT thread pool (overlapped
I/O completions, RegisterWaitForSingleObject, RPC/COM, WinHTTP, WebView2)
creates and retires worker threads on its own schedule, and each new one pays
the 64 KB.

Measure it: a release-sandbox app with one window and one idle pane, then the
same with a viewer pane, sampled for private bytes and a thread-creation count
(cdb bp `ntdll!NtCreateThreadEx` counter, or ETW thread start events) over an
hour or more. If it grows, name which pool or subsystem keeps creating threads
and decide whether a persistent pool (`SetThreadpoolThreadMinimum` on a
private pool, or keeping those workers alive) is the fix. If it is flat, close
this as measured.

## Validation criteria

- [ ] an hour-long idle sample of a release-sandbox app (private bytes + threads created), with the verdict: flat, or growth attributed to a named thread source
- [ ] if it grows: a fix, and the same sample flat afterwards
