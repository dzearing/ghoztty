# T2452 - A lane's acceptance sweep reports PERSISTENT STATE CHANGED for HKCU writes the OTHER lane's concurrent scripts made (HKCU\Software\dzearing-cleanup-test from ghoztty-cleanup.ps1, not in the sweep)

## Summary

Lane b's due sweep 2026-10-29 02:2x-02:46 ended state-changes=1: hives ADDED Software\dzearing-cleanup-test. Only ghoztty-cleanup.ps1 writes that key, and it was not in the sweep; the key was gone by the time anyone looked. The before/after durable-state diff is box-wide, so with two loop lanes running a sweep blames itself for the other lane's script. Fix: attribute the diff (per-lane sandbox key names, or the sweep ignoring keys a held cross-lane lease names), or serialize HKCU-writing scripts across lanes with a box-wide lease. Then show it can still fail when this lane's own script leaks.

## In plain terms

Two test loops run on this machine at once. After each batch of tests, a loop
checks that nothing permanent on the machine changed - but it was blaming
itself for a scratch registry key the OTHER loop's test had made a moment
earlier, and calling a clean run a failure. Now a test that makes such a key
leaves a note saying "this is mine, and I am still running", and a loop
ignores keys only while another loop's still-running test holds that note.

## Goals

- [x] a box-wide claim ledger tests write before planting a fixture on a snapshotted surface (`test\win32\lib\FixtureClaim.ps1`)
- [x] the acceptance runner names its run and forgives only changes a LIVE claim from ANOTHER run covers (printed as `PERSISTENT STATE CONCURRENT FIXTURE`, never dropped silently)
- [x] the fixture writers claim what they plant: ghoztty-cleanup (its hive), crash-first-chance (the t808 hive), install-walkthrough (the throwaway identity's hive, arp row, Start Menu entry)
- [x] shown it still fails on this run's own leak, a dead claimant, a reused pid, and an uncovered neighbour

## Design

Of the three fixes the summary offered, attribution by claim was chosen over
per-lane key names (a parallel-runner mirror resolves to lane a, so the lane
is not reliably knowable inside a worker, and the other lane's sweep would
still see a lane-b-named key ADDED) and over a box-wide HKCU lease (serializes
two lanes for every fixture script, and does nothing for a script run by
hand). A claim records surface + `-like` pattern + pid + process start time
(pid reuse guard) + `GHOZTTY_ACCEPTANCE_RUN`, which `acceptance-parallel.ps1`
sets (kept when nested) and its workers inherit. The ledger lives under the
user-scope TEMP so every lane and worker reads the same one whatever its
process env. A claim from the sweep's own run never excuses anything; a
claim whose process is gone excuses nothing and its file is pruned after a
minute.

Not in scope, noticed: ghoztty-cleanup.ps1 and crash-first-chance.ps1 use
fixed key names and delete them at start, so the same script running in both
lanes at once would delete the other lane's live fixture - filed as T3832.
