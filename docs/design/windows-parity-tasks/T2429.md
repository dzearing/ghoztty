# T2429 - Set-GhozttyTestIsolation -ReleaseSandbox leaves PATH self-heal on: a sandboxed release-build run adds its own folder to the user's PATH (seen 2026-10-28, T2419 capture)

## Summary

The T2419 capture ran the 1.49.5 portable under Set-GhozttyTestIsolation -ReleaseSandbox; the next acceptance run's durable-state check reported 'env REMOVED path:...scratchpad/rel/Ghoztty (was present)', i.e. the sandboxed release app had written its own folder into HKCU Environment Path (PathInstaller.zig self-heal). The sandbox already disables the other out-of-sandbox write a release build makes (T2196: GHOZTTY_URL_SCHEME=off) but not this one. Fix: in test/win32/lib/Isolation.ps1's ReleaseSandbox branch set GHOZTTY_PATH_SELFHEAL=off when the caller has not (scripts whose subject IS the PATH install set it themselves), add a demonstration that a ReleaseSandbox launch leaves the user Path byte-identical, and run the guards that cover Isolation.ps1. The stray entry is already gone (the 1.49.6 update rewrote Path).

## In plain terms

Some of our tests run a real release build of Ghoztty inside a sandbox so it cannot touch the user's own setup. The sandbox missed one thing: the release app quietly adds its own folder to the user's PATH. One test run left a temporary folder on the user's PATH that way. Now the sandbox turns that off, and a test proves the user's PATH is left exactly as it was.

## Goals

- [x] `-ReleaseSandbox` turns the release build's PATH self-heal off, unless the caller set it on purpose
- [x] a live demonstration that a sandboxed release launch leaves the user's PATH and the release PATH record byte-identical, with a negative control
- [x] the guards that cover Isolation.ps1 run green
