# T2917 - Defender now quarantines the debug ghoztty-agent.exe on this box (Trojan ThreatID 2147737394) and blocks zig build from installing it, so no agent-backed harness can run

## Summary

2026-11-11 03:44: Defender quarantined D:\git\ghoztty\zig-out\bin\ghoztty-agent.exe (ThreatID 2147737394) seconds after flagging the agent-autostart test's sandbox copy (which writes HKCU Run keys). Same detection has hit sandbox agent copies since 2026-11-05 (T2429 sandboxes). After it, zig build -Dapp-runtime=win32 -Doptimize=Debug FAILS with unable to update file ... ghoztty-agent.exe: AntivirusInterference, so every harness needing the agent (agent-recovery, agent-upgrade, pane-stack-strip, registration-sites D, ...) is red for a box reason. Needs the user's call on a Defender exclusion for the repo zig-out / test sandboxes, or a change to what the autostart test writes so the heuristic stops firing. Related: T1293 (release exe flagged on a clean machine).

## In plain terms

Our own tests were registering throwaway copies of the session agent as Windows
startup programs, which is exactly what malware does, so Windows Defender started
deleting the agent - first the test copies, then the freshly built one, after
which the build itself could not finish. Tests now record those startup entries
in a private scratch location that Windows never runs at sign-in, so Defender has
nothing to object to. The real product's startup entry is unchanged.

## Root cause

`Behavior:Win32/Persistence.A!ml` (ThreatID 2147737394, severity 5) is a
behaviour-model detection: an unsigned exe under `%TEMP%` gets a
`HKCU\...\CurrentVersion\Run` value pointed at it and is then launched from that
command. `agent-autostart.ps1` section E does precisely that on purpose (a copy of
the debug build outside the checkout), and `-ReleaseSandbox` runs (T2429) let a
release build under `%TEMP%\ghoztty-sandbox-*\Programs\Ghoztty` write its own.
Defender then blocks the binary's HASH, so the identical zig-out agent and its
`.zig-cache` twin were quarantined and `zig build` failed with
`AntivirusInterference`. A rebuild with a changed agent clears the hash block
(the build went green again at the start of this turn), but the next autostart
run would have re-taught it.

## Fix

- `src/remote/run_key.zig`: `GHOZTTY_RUN_KEY=<token>` moves every Run read and
  write to `HKCU\Software\Ghoztty-test\Run-<token>` (token whitelisted, capped at
  40, composed under a fixed parent so it cannot aim anywhere else). Unset - the
  only production value - is the real key. Used by `LocalAgent.writeAutostart`
  (which creates the redirected key) and `adopt.zig` read/write.
- `test\win32\lib\HarnessLeak.ps1`: `Set-GhozttyTestRunKey` (sets, creates, arms
  exit teardown of the key and the empty parent), `Get-GhozttyRunKeyPath`,
  `Assert-RunKeyRedirected` (throws before a run could plant a real entry).
- `lib\Isolation.ps1` sets it for EVERY isolated run, debug and release.
- `agent-autostart`, `agent-adopt` (incl. its fake MSI uninstall's `reg delete`),
  `agent-instance-lineage`, `registration-sites` call it / read through it; the
  bystander checks keep reading the REAL key and now also assert nothing was
  added there (`A2b`, `P3b`, lineage's "nothing was added").

Not done, deliberately: a Defender exclusion. It needs admin, it is the user's
machine policy, and it would hide the same signal a user's Defender would raise
(T1293 tracks the release exe being flagged on a clean machine).
