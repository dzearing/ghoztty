# T2828 - Composition step 5c-5c: once every glide visual is declared, the glide's window-thread tick still runs a whole live layout pass (layoutSplitsLive, desk paint, batch flush) per frame - shrink it to the landing timer T2572 wanted

## Summary

Split of T2780, its last slice. Window.stackSlideTick steps the Slide, then layoutSplitsLive + treeGlideBatch flush on every frame (Window.zig ~11744-11765). With the panes (T2572), folding/opening faces (T2778/T2779), moving strips (T2825), region cuts (T2826) and the sidebar column (T2827) off the tick, nothing that pass paints changes until the landing. Make the tick, in the composition pane tree with declare on, a timer that waits out the longest declared span and runs endStackSlide + the landing layout; a retarget (drag) still re-lays out. Keep the stepped path for GHOZTTY_GLIDE_DECLARE=0, forced slow frames and the non-tree arms. Oracle: the glide line (drag-perf / frame-clock.ps1 G2) shows the stack glide's per-tick cost near zero with no desk paint per tick, comp-glide-hold-onscreen -Arms tree,stall,unfold ALL PASS, stack-fold-slide.ps1 / pane-stack-slide.ps1 ALL PASS with the tree knobs.

## In plain terms

When panes slide around in a stack, Windows already hands the animation to
the system so it keeps moving while the app is busy. But the app was still
redoing its whole window layout on every animation frame, for nothing: that
work showed up as each frame costing more time than the screen gives it. Now,
once everything moving has been handed over, the app only keeps count of the
slide and does the real layout work when something actually arrives.

## Goals

- [x] A glide tick that lands nothing skips the window's layout pass once every card, face, strip and sidebar column on the move is declared to the compositor
- [x] Every other tick still lays out: a card or strip landing, the whole glide landing, a drag, a resizing glide, a frame still on its way or newly landed, anything stepped
- [x] The stepped path stays for `GHOZTTY_GLIDE_DECLARE=0`, forced slow frames, off the tree, and `GHOZTTY_GLIDE_LANDING_TIMER=0`
- [x] An on-screen oracle that counts the quiet ticks, with a negative control

## Design

Rather than a one-shot timer for the longest declared span, the glide's frame
clock keeps ticking but a "quiet" tick only steps the `Slide` model (pure
math, microseconds). That keeps the model's `drawn` positions exact for a
retarget to start from, keeps per-card landings mid-glide on the frame they
happen (a tick that changes `Slide.caughtUp` lays out), and lands the whole
glide on the same tick as before. The rule is `glide_landing_timer.quiet`
(pure, unit-tested); `Window.glideAllDeclared` is the positive check of what
is up on the compositor (pane `tree_glide_decl`, strip face `decl` with the
frame the card carries now, moving strip `decl`+`still`, sidebar
`columnDeclared`, no `glide_snap == .waiting`). First film run caught the one
case the first cut missed: an opening card's frame landing after its
band-only face was declared - the face must be declared again with the frame,
so a face whose `decl.content` is not the frame the card holds now is not
"declared".
