# T2717 - An idle loop turn waits for background due sweeps that are no longer running, until the 180m backstop (about 1.5-2h lost per stall)

## Summary

Twice in 4 hours a loop lane sat idle for ~1.5-2h inside one turn, held only by the watchdog's 180m backstop. Lane b, T2704, turn 27: idle from before 21:55 until after 22:12 on 2026-11-04. Lane a, T2705, turn 33: idle from about 00:30 until after 02:12 on 2026-11-05.

The two cases look the same:
- The pane shows 4-6 "still running in background" lines for overlapping duplicate due sweeps (several named "Run all due harnesses without fail-fast"), then "Compacted while idle".
- The watchdog logs session=idle bg=1/2, so T1711's background-wait arm keeps it healthy.
- In lane a's case at 02:12, NO harness process existed. Lane a's claude (pid 25104) process tree held only Claude Code's long-lived PowerShell tool hosts: no acceptance-parallel, no guard-due, no test/win32 runner.

So the tasks the transcript counts as pending were not running. Either they had already exited without a notification reaching the idle session, or the count includes tasks the session already consumed. A turn that relaunches the same sweep several times adds to the count and to the box load.

Fix direction:
1. Get-LoopPendingBackgroundTasks (scripts/loop-session.ps1) should confirm a pending task still has a live process (or an output file still growing) before it lets T1711 waive the stall. Otherwise a dead wait counts until the 180m backstop.
2. go.md should tell the loop to run ONE due sweep and wait for it, never to relaunch a sweep that is still running.

Third occurrence, 2026-11-05 12:12 (controller): lane b, T2386, turn 36, idle 2h24m with `bg=1` and the pane footer reading `14 shells`. The "still running in background" list includes tasks from EARLIER turns: `t2326-hfloor.log` (T2326) and "Wait for Fork CI on the fix commit" (T2704's, from 2026-11-04 21:55). So a background task that never delivered its notification survives `/reset-context` and idle compaction. The pending count is cumulative across turns, not this turn's own work, and T1711's waiver trusts it.

Fourth occurrence, 2026-11-05 14:12 (controller): lane a, T2386, turn 42, idle since 13:29 with `bg=3`, waiting on "the scoped harness floor". No `harness-floor` or `acceptance-parallel` process existed on the box. This one did NOT compact (ctx 286k), so idle compaction is not the trigger. The lost notification happens on its own.

## In plain terms

The loop that works the task queue sometimes went quiet for two hours at a time. It was waiting for a "your background job finished" message that had been lost, for a job that had already ended. Its supervisor believed the wait was real and left it alone. Now the supervisor checks whether the job is actually still running. If it isn't, the loop gets its usual nudge within minutes instead of hours.

## Goals

- [x] A background task whose output file nobody is writing any more no longer counts as something the session is waiting on.
- [x] A task that is genuinely still running still holds the wait (no new false nudges).
- [x] The watchdog log says how many tasks it found dead (`bgdead=`), so the change can be audited.
- [x] go.md tells a turn to run one sweep and wait for it, never stack duplicates.

## Design

Claude Code writes each backgrounded command to
`%TEMP%\claude\<project>\<session>\tasks\<id>.output` and holds that file open for
writing until the command ends. Measured 2026-11-07: a 0-byte `sleep 90` read
HELD for its whole life and `dead` the moment it finished. Every finished
task's file (931 on the box) opens deny-write freely, and the files persist.
So `Test-LoopBackgroundTaskLive` (scripts/loop-session.ps1) answers `live`,
`dead` or `unknown`, and `Get-LoopPendingBackgroundTasks` drops only `dead`.
`unknown` (no file, e.g. a background agent) keeps the T1711 waiver as it
was, so the probe can only give a stalled loop back and never take a genuine
wait away. The session dir is the Claude process's first session, not the
transcript's, so the probe searches every session dir. That costs ~10ms.
