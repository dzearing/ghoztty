# T1145 - The morning refresh can finish on the OLD build when a portable copy still owns the endpoint

## Summary

T1120 stopped the different-build handoff prompt from appearing during the unattended 5am refresh by joining the running instance instead of asking. That is the right answer for the prompt, but it leaves the other half open: the delivery kills only the processes under the install dir, so a Desktop-portable or share copy of the same lineage keeps the IPC endpoint, the freshly installed exe joins IT, and the user's terminal is still the build that was not updated - while the run's own POST-SWAP/APP-REFRESH lines can read as a delivery that worked. What is wanted is that the refresh either brings the endpoint over to the new build or says plainly, in the log and the verdict, that it did not.

## In plain terms

After a delivery swapped in a new Ghoztty build, the log could say everything
worked even though the window you were looking at was still the old build: a
second copy of Ghoztty (a portable one) kept running, and the freshly installed
app quietly attached to it instead of taking over. Now the delivery asks the
running app which build it is, and if it is not the one just installed it says
so plainly and ends with a "not running" verdict instead of "OK".

## Goals

- [x] Read which build actually answers the app's endpoint after the relaunch
- [x] A different build there ends the run as `UPGRADE NOT RUNNING` (exit 2), never `UPGRADE OK`, and `APP-REFRESH ELSEWHERE` instead of `APP-REFRESH OK`
- [x] The log line names the process that kept the endpoint, its commit, and what to do about it

## Design

The task allowed either bringing the endpoint over or saying plainly that it
did not. Bringing it over means killing whatever holds the endpoint, and since
D85 the swap target is the dev install while the endpoint holder can be the
user's own installed release or a portable copy - killing those is exactly what
the ownership rule forbids. So the run REPORTS: `Complete-Upgrade` (the single
verdict site) reads `+version`'s `Running Instance` block - the IPC `version`
verb, which reports the serving process's commit, exe and pid - whenever an
instance answered and the post-swap read-back verified. Judged on the commit,
not the path: a portable carrying the delivered commit is the right build and
is reported OK with where it runs from. No answer is UNKNOWN, never OK.

Code: `Get-RunningInstanceFromVersionText`, `Resolve-GhozttyRunningInstance`,
`Get-RunningInstanceVerdict` in `scripts\delivery-version.ps1`; the verdict in
`scripts\upgrade-ghoztty-windows.ps1` `Complete-Upgrade`.
