# T2508 - Composition step 4a: window chrome host - a DirectComposition target on the top-level window (behind the pane children) with a Direct2D device context over a hardware-then-WARP D3D11 device, opt-in GHOZTTY_COMP_CHROME, rebuilt on device loss

## Summary

T2468 split, part a. Infrastructure only: no visual is attached yet (any visual on the top-level target covers the window's GDI chrome, so attaching one is part b). Oracle: knob on = log line naming target_hr, d2d_hr and adapter (hardware/warp) on window create; a forced device loss rebuilds; knob off = nothing created; and a WGC ghost capture (T2463 technique) confirms the topmost=FALSE ordering: a test-fill visual composes above the window's GDI pixels and below its pane children.

## In plain terms

The frame around the terminals - the desk colour, the margins, the strips -
is still drawn the old way, by hand, into the window. Before any of it can move
onto the system compositor (which is what makes resizing and folding smooth),
each window needs a compositor surface of its own sitting in exactly the right
layer: above that hand-drawn frame and below the terminals. This step builds
that layer and proves where it sits. Nothing on screen changes yet.

## Goals

- [x] A composition target on every window, with a Direct2D drawing context, behind an opt-in switch
- [x] A lost graphics device is noticed and the whole thing rebuilt
- [x] Proof on screen that the layer sits above the drawn frame and below the panes

## Validation criteria

- [x] Knob on: every window logs `chrome composition host ready: target_hr=0x00000000 d2d_hr=0x00000000 adapter=hardware rebuilds=0` (adapter=hardware on this box), and the windows keep working through a split and resize - `test\win32\comp-chrome.ps1` section A.
- [x] A forced device loss rebuilds the host (`rebuilds=1`), once per window, never a loop - section B (B3 caught a rebuild loop in the first draft: the rebuilt host re-read the loss seam).
- [x] The Direct2D context draws into a composition surface the target shows (debug test fill) - section C.
- [x] Knob off: nothing created, nothing logged, even with both seams set - section D. Harness ALL PASS (19).
- [x] On-screen ordering (WGC ghost capture, T2463/T2488 technique): `scripts\comp-chrome-onscreen.ps1` ALL PASS (14) - the magenta test fill covers 12.8% of the window (caption band and desk margins: ABOVE the GDI chrome) and the pane's text box shows 0 magenta pixels (BELOW the pane children; the sidebar child is above it too); knob off has 0 magenta. `-NegativeControl` (arms scored against each other's grab) goes red on fill.3 and off.3.

## Result

New module `src/apprt/win32/chrome_comp.zig`: D3D11 device (hardware, then
WARP) -> IDXGIDevice -> `D2D1CreateFactory(ID2D1Factory1)` -> `CreateDevice` ->
`CreateDeviceContext`; `DCompositionCreateDevice` on the same DXGI device;
`CreateTargetForHwnd(hwnd, topmost=FALSE)`. No visual is attached in a normal
run. `Window.chrome_host` is built right after the top-level HWND exists when
`GHOZTTY_COMP_CHROME=1`, polled for loss on every `WM_PAINT`
(`GetDeviceRemovedReason` + `IDCompositionDevice::CheckDeviceState`) and rebuilt
in place, released in `releaseOwnedResources`. Every vtable slot was counted
from the 10.0.26100.0 SDK headers. Debug-only seams:
`GHOZTTY_COMP_CHROME_FORCE_LOSS` (first check reports lost) and
`GHOZTTY_COMP_CHROME_TEST_FILL` (magenta surface drawn through D2D, attached as
the root visual). Guard row `comp-chrome` covers the module and the harness.

What T2509 inherits: the D2D context draws into a DComp surface via
`BeginDraw(IID_IDXGISurface)` + `CreateBitmapFromDxgiSurface`, clipped to the
update offset (the surface may be an atlas) - the fill path is the template.
