# T842 - zig build against a FRESH private global cache is unreliable on this box - one run died 0xC0000005 in 4s, another failed in zig rc

## In plain terms

Building this project in a scratch folder of its own -- nothing shared with the
normal build -- was written down a month ago as something that does not work
reliably on this machine, after two attempts failed two different ways. That
mattered because "just build it somewhere private" is the obvious way to get a
clean answer when you are chasing a bug. Measured properly, it works fine: nine
builds in a row, five of them from a completely empty scratch cache, all passed.
What actually made builds fail was another job using the machine at the same
time -- and that job has now been identified and filed separately.

## Goals

- [x] Reproduce deliberately instead of remembering two ad-hoc runs
- [x] Separate "fresh private cache" from "this box" with a control arm
- [x] Name a cause, or record the conclusion with its evidence

## Summary

Filed from T840, where a load worker was first designed to build with a FULLY
private cache (`--cache-dir` + `--global-cache-dir` + `--prefix` all its own).
Two attempts on 2026-08-14 failed two different ways -- `zig rc exited with code
3` on freetype's `ftver.rc`, and a `0xC0000005` after 4 seconds with an empty
log -- on a box where the same command against the shared global cache built
fine. It was recorded rather than chased, because nothing then needed an
isolated build.

**Measured 2026-09-18: a fresh private global cache is NOT the problem.** Nine
`zig build test -Dapp-runtime=none` runs, one at a time, every one on this box:

| arm | global cache | box | result | seconds |
|---|---|---|---|---|
| a1 | fresh, private | soak daemon running | PASS | 406.7 |
| a2 | fresh, private | soak daemon running | **KILLED** | 275.3 |
| a3 | fresh, private | soak daemon running | **KILLED** | 289.2 |
| a4 | fresh, private | quiet | PASS | 433.9 |
| b1-b4 | fresh, private | quiet | **PASS x4** | 455.1 / 423.9 / 430.8 / 427.1 |
| c1-c3 | shared (`D:\zig-global-cache`) | quiet | **PASS x3** | 376.6 / 380.5 / 376.8 |

**Fresh private cache on a quiet box: 5 for 5.** The control arm says what the
cache costs and it is not reliability -- about 48 s, ~12%, for re-fetching and
rebuilding the third-party dependencies the shared cache already holds. Every
passing run in both arms produced byte-identical output (39,898 / 39,896 bytes
of expected test-path noise), which is not what an unstable toolchain looks
like.

The secondary hypothesis is dead too. All **eight** fresh caches fetched and
extracted their **22 packages whole** -- `Get-TornPackage` (T1436's
half-extraction detector, `scripts\lib\CacheHeal.ps1`) reported **0 suspects**
against every one of them, including the two whose builds failed. So a torn
freetype was never going to explain the original `zig rc` failure here.

### What the two failures actually were

Not cache failures: **a2 and a3 were killed by another process.** Both died
`exited with code 255` with no handler text, no `Segmentation fault` and no
CrashDiag block -- and in two *different* victim tests
(`font.Collection.test.add full`, then
`terminal.PageList.test.PageList eraseRows invalidates viewport offset cache`),
which is the signature of an arbitrary kill rather than a bad test. Each died in
the same second a soak-daemon round yielded, and the leak-sweep dump from that
second names the victim, which is this experiment's own private cache:

```
.dumps\lane-leak-62768-20260918-004904.log  ->  D:\zgc-t842\a2-c\o\c2924f98...
.dumps\lane-leak-60820-20260918-005353.log  ->  D:\zgc-t842\a3-c\o\f0049928...
```

T841's idle soak daemon runs floor lanes concurrently with a turn by design, and
`Invoke-LaneLeakSweep` reaps any process carrying a lane test-binary name that
was not running when its lane started. `scripts\lib\LaneLeak.ps1`'s own header
names this as the one case it cannot separate, and rests on go.md forbidding
overlapping runs -- a premise T841 retired. **Filed as T1648 (P0)**, because
while it stands no red lane on this box is evidence.

### Conclusion to rely on

**Private/fresh global caches ARE usable on this box.** Use one for a clean-room
reproduction, a bisect harness or a second seat; budget ~7 minutes per cold run
and expect ~12% over a shared-cache build. The thing to control for is not the
cache, it is **concurrent build load** -- quiesce the box first
(`scripts\soak-daemon.ps1 pause -Reason "<why>"`, `resume` after). Recorded in
`docs/claude/build.md` so the next person reaching for an isolated build finds
the answer rather than this task.

### What is NOT claimed

The two original 2026-08-14 shapes did not recur in nine attempts, so they are
not *explained* -- only shown to be non-reproducible and not inherent to a
private cache. Both were observed while T840's load-worker design was putting
concurrent builds on this box, which is the same class of condition as a2/a3,
but nothing here proves that was their mechanism. If either shape returns, it
returns with a `crash-catch.ps1` run behind it.

## Details

Harness: `t842-repro.ps1` (session scratchpad) -- N sequential attempts, each
with its own never-before-used `--global-cache-dir` / `--cache-dir` / `--prefix`
under `D:\zgc-t842` (all on the repo drive, short paths), `-Shared` switching
only the global cache to the box's shared one so the two arms differ in exactly
one variable. Artifacts kept: `D:\zgc-t842\summary-{a,b,c}.txt` and one log per
attempt. The caches themselves (~370 MB each, 8 of them) are scratch and can be
deleted whenever the user wants the ~3 GB back; nothing deletes them
automatically, and `build-cache.ps1` reports stale scratch dirs rather than
removing them.

One harness lesson worth carrying: PowerShell 5.1's `Tee-Object -FilePath`
writes **UTF-16**, so a summary file built with it reads as binary to `grep` and
silently matched nothing. Write with `Out-File -Encoding ascii`.
