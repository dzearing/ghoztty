# T2577 - Cut the window-resize pass from frame change to last pane present under one 120 Hz compose (~6 ms; today ~14-16 ms: batch 4, regions 6, paint 1, wait 1-3), so the content can make the compose that shows the new frame

## Summary

T2575 lined the film's compose times up against `GHOZTTY_RESIZE_TRACE` (ReleaseSafe, CHROME+PRESENT+NOREDIR, right-shrink, 120 Hz). With the frame change paced to just after a compose (DwmFlush in WM_NCCALCSIZE, experiment), the new frame is on screen exactly one compose later (+10-15 ms after the change), every step. The content reaches the screen one compose after THAT, every step, because the last pane present lands +12-16 ms after the change and DWM latches about one period (~8 ms) after the compose it just finished. So the content makes the frame's compose only if the whole pass - children moved, regions cut, desk painted, every pane presented at the new size - finishes within ~6-7 ms of the frame change.

Phase costs from the trace, per step (size-begin is ~1 ms after the frame change): pane batch (DeferWindowPos) ~4 ms, batch-end -> cut-end ~2 ms, cut-end -> regions-end ~5-6 ms (clearVacatedPaneStrips + cutCardRegions), overlays + paint ~1 ms, frame wait 0.5-3 ms; then ~5 ms after the wait before WM_SIZE returns (the NOREDIR UpdateWindow), which does not delay the content but delays the next drag step.

Do: profile each phase (`resize trace` already stamps them), take the regions and the batch down first, and move anything that does not change what the new frame shows (the post-wait work) out of the way. Re-film with `scripts\resize-sync-onscreen.ps1` (a pacing knob is ~15 lines: see T2575's findings) and score bad frames per step, not per film - pacing changes the frame count.

## In plain terms

When you drag a window edge, the inside of the window is redrawn one screen refresh after the outline moves. The redraw takes about twice as long as one refresh on a 120 Hz screen; this task makes it fit in one.
