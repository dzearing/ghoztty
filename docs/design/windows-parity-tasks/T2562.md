# T2562 - Composition step 5b-2: in pane-tree mode (GHOZTTY_COMP_PANE_TREE) the scrollbar, dim wash, bell border and banner are popups again; hang them under the pane's visual in the WINDOW's tree on the chrome host's device, so they move with the pane visual

## Summary

Filed by T2553. Under `GHOZTTY_COMP_PANE_TREE=1` a pane's swap chain is a visual in its top-level window's tree (`chrome_comp.Host.paneAdopt`, on the window's DComp device), and `Presenter.overlayTree()` returns null because there is no pane-local visual on the pane's own device to parent overlays to. So the scrollbar, dim wash, bell border and banner fall back to their `WS_EX_LAYERED` popups in that mode, which a compositor glide of the pane visual (T2554) would leave behind.

Fix: publish a `comp_overlay.Shared` from the WINDOW thread instead - `{ dcomp = host.dcomp, context = host.context (window-thread only, so no multithread flag needed), root = the pane's tree visual }` - when `Surface.syncTreeVisual` adopts, and retract it when the visual drops or the host is rebuilt. The overlays then commit the window's device, which is the same thread. Watch the generation rules in `comp_overlay.Slot` (today only the renderer publishes into it).

Validation: `scripts\comp-present-onscreen.ps1 -Arms tree` extended with a dimmed unfocused pane and a scrollbar: the wash and the thumb are on the grab at the pane's spot and NO overlay popup window exists (enumerate the process's top-level windows); the existing arms stay green.
