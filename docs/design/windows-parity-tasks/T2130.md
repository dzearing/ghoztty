# T2130 - A divider drag interrupted by Alt+Tab or a system dialog stays armed: moving the mouse afterwards with no button held keeps resizing the panes until the next click

## Summary

Found while landing T2124 (read, not reproduced by hand). `Window.zig`'s
`WM_CAPTURECHANGED` arm ends only a rearrange drag (T1531). A split-divider
drag (`dragging_split`) has no arm there, so when the capture is taken away
mid-drag (Alt+Tab, a UAC prompt, a menu) there is never a button-up for it:
`dragging_split` stays true, every later `WM_MOUSEMOVE` the window gets goes to
`updateDividerDrag`, and the panes resize under a pointer with no button held
until the next click lands and ends it. T2124 gave its new stack-grip drag that
arm (`endGripDrag` on capture loss); the divider drag needs the same - end the
drag (and its row drag) where it is, as the rearrange drag does.

Fix: in `WM_CAPTURECHANGED`, `if (window.dragging_split) window.endDividerDrag();`
(endDividerDrag's own `ReleaseCapture` re-enters harmlessly once the flag is
cleared). Hero divider drag (`hero_divider_drag`) has the same shape; check it.

Validation: an acceptance step in `test\win32\split-divider.ps1` or
`stack-collapse-drag.ps1` that presses a divider, sends `WM_CANCELMODE` (or
calls ReleaseCapture from a probe) and then posts button-less moves, asserting
the pane edges do not move.

## Validation criteria

- [ ] capture lost mid divider drag: later button-less moves leave the pane edges where they were (acceptance script, posted messages on the test desktop)
- [ ] the same for the hero divider drag
