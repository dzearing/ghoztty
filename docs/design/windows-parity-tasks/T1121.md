# T1121 - msi-upgrade.ps1 compares two different DisplayVersions as if they were equal

## In plain terms

A check on the Windows installer expects the version recorded in Add/Remove Programs to be one number and finds another. Either the installer is writing the wrong version, or the check is comparing against an out-of-date number.

## Summary

`test\win32\msi-upgrade.ps1` scored `1 FAILURE(S) (34 passed)` in the T1094 sweep:

```
FAIL  v2: DisplayVersion 26.7.2002 == 26.7.1902
```

The two values differ in the last component (`2002` vs `1902`), which reads like a version that moved on while the expected value stayed put - but that is a guess, and the alternative (the upgrade genuinely failing to update the recorded version) is the more serious one and must be ruled out rather than assumed.

34 assertions pass, so the MSI upgrade path is broadly working.

Note for whoever picks this up: this box has a registered ghost product from an earlier MSI experiment that must NOT be uninstalled, and per-user MSI ARP entries land under HKLM here. Read the surrounding script comments before touching the registry.

## Resolution

**The script's expectation was stale; the installer is right.** `build-msi.sh`
derives `ProductVersion` as `yy.m.dNN` from the day the MSI is BUILT, not from
the exe's file version (which the T23 recipe pins with
`-Dwindows-file-version=26.7.19.x`). The throwaway MSIs were rebuilt on
2026-07-20, and their Property tables say so:

```
t23-v1.msi ProductVersion=26.7.2001  ARPDISPLAYVERSION=<none>
t23-v2.msi ProductVersion=26.7.2002  ARPDISPLAYVERSION=<none>
```

The installed Apps & Features entry read `26.7.2002`, exactly what v2 declares,
while the script's default still said `26.7.1902`, the July 19 build's number.

The fix (`test/win32/msi-upgrade.ps1`): `-V2ProductVer` defaults to empty and is
read from the v2 MSI (ARPDISPLAYVERSION when a `--semver` build sets one, else
ProductVersion - the same fallback `build-msi.sh` applies), so rebuilding the
fixtures on any day cannot stale it again. Two setup assertions were added: the
v2 package declares a version at all, and v2's ProductVersion compares GREATER
than v1's, since an equal one is the "refuses to install over itself" case and
not a major upgrade.

Lane note: the fixture MSIs lived only in lane A's `zig-out` (and the runner's
mirrors), so a lane-B run was `SETUP FAIL: missing`. They were copied into
`D:\git\ghoztty-b\zig-out` for this run; the T1996 checkout guard correctly
refuses to grade another checkout's files.
