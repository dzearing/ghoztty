# T2842 - Launching the app with --initial-command opened TWO windows sharing one pane id, so the loop's claim could never mark its window (windows=0)

## Summary

2026-11-08 14:22:07. After the T2839 crash, lane a's go-loop-exec recover ran the watchdog launch-app: installed ghoztty.exe --initial-command=%TEMP%\ghoztty-go-loop-resume.cmd. The app came up with TWO new windows. window-1 runs cmd /c ghoztty-go-loop-resume.cmd (pid 72412, created 14:22:07; lane a's claude 36904 is inside it). window-2 holds a bare cmd.exe (pid 46668, created 14:22:08, different parent). +list --json gives BOTH panes id AND name F6AEC833-7923-4048-85E5-7A4D1F2E4EE4, with different session_ids (65b8fc0e... and 3401aa40...). Consequences: (1) every '+rename --target=F6AEC833...' fails 'names a pane in 2 windows ... ambiguous'. (2) go-loop-exec claim calls Set-Mark and DISCARDS its result (Set-Mark ... | Out-Null, line 417), then prints 'marked this window' anyway. So lane a ran unmarked for 1h50m, and both lanes' health read DEGRADED windows=0 (lane b because the app was briefly gone). The controller marked it by hand at 16:13: '+rename --target=window-1'. Two fixes: (a) Ghoztty: a launch with --initial-command must not open a second default window, and a pane id must never be issued twice (find where the id is minted for the initial-command surface vs the default surface); (b) go-loop-exec claim must check the rename's exit code and, on ambiguity, fall back to marking the window that contains this claude's own pane (the session_id / pid match from +list --json), and say MARK FAILED rather than 'marked'.
