# T1015 - The shared test libraries other than TestDesktop have no harness obliged to run when they change

## In plain terms

The automated tests share a handful of helper files, and when someone edits one
of those helpers nothing makes them re-run the tests that prove the helper still
works. So a helper can quietly stop doing its job and the whole suite keeps
reporting green. T303 fixed this for the biggest helper; the rest still have the
hole.

## Summary

T303 added a `guard-due` row (`test-desktop`) over `test\win32\lib\TestDesktop.ps1`
because nothing obliged anyone to run its acceptance after editing it — the file
every GUI acceptance script stands on. The same audit found the hole is general.

`test\win32\lib\*.ps1` IS in two rows' `Covers` today (`verdict-exit`,
`stderr-capture`), but both are **static AST audits** about a script's verdict
line and its stderr handling. Neither runs the library. So for these files there
is no BEHAVIORAL obligation at all:

- `lib\PaneCapture.ps1` — route 0, the app reading back its own renderer. Has a
  dedicated harness (`test\win32\pane-capture.ps1`) and no row pointing at it.
- `lib\ChromeGeometry.ps1` — the client-coordinate math every chrome pixel probe
  indexes its bitmap with. No dedicated harness at all.
- `lib\TestScore.ps1` — `Write-TestVerdict`, the one scorer that owns both the
  wording and the exit code (T271). A silent edit here mis-reports every script
  in the suite; only the static audit would notice, and only for shape.
- `lib\CleanSlate.ps1`, `lib\Isolation.ps1`, `lib\HarnessLeak.ps1`,
  `lib\PersistenceSweep.ps1`, `lib\PipeBridge.ps1`, `lib\ChooserControls.ps1`,
  `lib\ColorMath.ps1`, `lib\PaneLiveness.ps1`, `lib\paint-blocks.ps1` — same
  question, lower blast radius each.

The failure shape is the one T783 exists for and T303 restated: a guard that
stops firing turns the suite green without ever turning it red.

## Fix

- For each shared library, decide which existing harness is its acceptance and
  add (or extend) a `guard-due` row over it — `pane-capture` over
  `lib\PaneCapture.ps1` is the obvious first one.
- Where a library has no acceptance at all (`ChromeGeometry.ps1`,
  `TestScore.ps1`), say so explicitly: either write the harness or record in the
  table's comment why the static audits are sufficient for that file. A
  deliberate "not covered, here is why" is the T783 pattern (see the
  `NativeArgv.ps1` note at the top of the table); an accidental gap is not.
- Keep rows tight to the family each harness is about — a row that demands a
  full GUI run for every shared-library edit is noise, and noise is how a gate
  gets ignored.

## Goals

- [x] every shared test library is either run by some harness when it changes, or has a written reason why it need not be
- [x] the question is asked mechanically from now on, so a NEW library cannot land with the same hole unnoticed
