# T1827 - Panes cannot be stashed out of the grid on Windows: no +stash/+restore, no stash keybinds, and +list never reports a stashed pane

## Summary

Mac 87afbf6ff gives SplitTree an ordered stashed list: stashed leaves stay in the tree (session close intent, IPC targeting, close confirmation, the manifest all still see them) but are pruned from the visible tree that layout and spatial ops (focus nav, swap, resize, equalize, divider drag, zoom) run on. 597a193cc adds +stash / +restore CLI verbs, stash_pane / restore_stashed_pane keybind actions, +list reporting stashed panes (JSON stashed:true, tree [stashed]), focusing or splitting at a stashed pane restores it, and stash persists in the session manifest (per-leaf stashIndex). c6826b79a: a stashed pane keeps its real slot size (stays mounted, invisible, sized as the full layout would size it) so its program never re-renders at a placeholder size - including panes stashed at launch by a session restore. Port all of that to the win32 SplitTree + IpcHandlers + session layout. Never mark a session close-on-free on stash/restore (Mac PaneStashSessionSafetyTests).

**Scope as landed:** everything above except persisting the stash in the
session manifest, which split out to **T1838** (a stashed pane currently comes
back on screen after a restart). The divider-drag compensation edge case with a
stash present is **T1839**. The pane sidebar itself is **T1828**.

## In plain terms

On a Mac you can tuck a pane out of the way - a log tail, a dev server - without
closing it: it keeps running and can be brought back to exactly where it was.
Windows had no way to do that. Now `ghoztty +stash` / `+restore`, Ctrl+Shift+M,
and the restore keybinding do it on Windows too, and `+list` shows which panes
are tucked away.

## Goals

- [x] a pane can leave the grid without closing, and come back to the exact slot it left
- [x] +stash / +restore behave like Mac's, refusals and messages included
- [x] the stash_pane / restore_stashed_pane keybinds work (Ctrl+Shift+M by default)
- [x] +list marks stashed panes (JSON and text tree)
- [x] focus, splitting and closing never land on, or leave behind, an invisible pane
- [x] a stashed terminal stays sized to its real slot while hidden
- [ ] the stash survives a restart (split to T1838)

## Design (win32)

- **The stash lives on the pane** (`PaneView.stash_seq`: 0 = on screen, larger
  = more recently stashed), not in a per-tab list as on Mac. The win32 tab trees
  are parallel arrays on `Window` that shift on every tab insert/close/move; a
  per-tab list beside them would be one more array for every one of those sites
  to forget, and would hold pointers that can dangle. The mark follows the pane
  wherever it goes and the order falls out of the numbers. Pure model and the
  three Mac invariants: `src/apprt/win32/pane_stash.zig` (unit-tested, every lane).
- **Pruning happens in place.** Every geometry walk in `Window.zig` (layout,
  divider paint, divider hit-test, band rect, region rect, rearrange header paint
  and hit-test, pane slots - nine of them) now goes through one helper,
  `splitRects`, which collapses a split whose one side is all stashed panes into
  its visible side. Handles stay the full tree's, so a divider means the same
  split everywhere, and a collapsed split keeps its ratio for the pane that
  comes back.
- **Spatial operations run on a visible clone** (`pane_stash.visibleClone`):
  directional focus and swap answer by view; equalize equalizes the visible
  arrangement and `liftRatios` copies the result back, leaving collapsed splits
  alone. Keyboard resize steps over collapsed splits (`nearestShowingSplit`).
- **Stashed panes are placed hidden at their full-layout slot**
  (`placeStashedNode`), so a window resize resizes them too and a restore is
  instant at the right size (c6826b79a).
- Session close intent is never touched by stash or restore; a real `+close` of
  a stashed pane still closes it, and closing the last visible pane restores the
  top of the stash instead of emptying the tab.
