# T972 - relay-account.ps1 has no guard-due row, so relay sign-in code can change under it unnoticed

## Summary

Found 2026-08-18 finishing T918. relay-account.ps1 is the only harness that proves the machine chooser's account row behaves - signed out, signed in, renew, and (T747) the no-client-id state - and nothing forces it to be RUN when the code it is about changes. scripts\guard-due.ps1 has no row for it, so an edit to src/remote/relay_signin.zig, src/remote/relay_account.zig or src/apprt/win32/RelayAccountRow.zig lands with the harness unrun and validate silent. That is exactly the T783 gap, on a feature that already shipped broken once past a green suite. Work: add a coverage row (harness + those three sources), add the stamping block at the end of the script the other guarded harnesses carry (only on a clean green run), and prove it - guard-due check reports DUE after touching a covered file and CURRENT after a green run. Note the one risk to check first: section 7 needs go + ghoztty-agent, and a run with SKIPs does not stamp, so confirm the harness can go fully green unattended on this box before the row is added (it did on 2026-08-18).

**Re-verified 2026-09-26 — mostly already fixed.** The coverage row and the
stamping block landed with T316 (`9921a9dca`, 2026-08-20). What was LEFT:
`src/remote/relay_account.zig` — the DPAPI `account.dat` store a sign-in writes
and a sign-out removes, plus the legacy reader and the renew-and-rotate seam
that sections 2, 3, 5 and 6 drive end to end — sat in no guard row at all, so
an edit to the account store could still land with the harness unrun.

## In plain terms

Signing in to your account from the machine chooser has one test that proves
it works end to end. The project's "have you re-run the test since you changed
this?" check already watched most of the sign-in code, but not the file that
actually saves your signed-in account on disk. Now it does, so a change to how
the account is stored can no longer ship without that test being run again.
