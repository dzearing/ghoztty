# T1143 - An acceptance marker the shell echoes can score before the command has run

## Summary

T1116's harness typed a unique end marker into a command line and then waited for it to appear in the pane. The shell ECHOES the command line, so the marker was on screen the instant the keys landed - the assertion scored a flood that had not started (and in one run was still printing a minute later). Sweep test/win32 for Wait-PaneHas-style waits whose needle is typed verbatim in the same command, and split the marker across a concatenation the way holder-volume.ps1 now does, so matching it proves the command RAN.

## In plain terms

Some of our automated tests type a command into a terminal and then wait to
see a unique word appear, as proof the command did its job. But a terminal
shows what you type as you type it, so the word can appear before the command
has even started - and the test passes without measuring anything. This adds a
checker that finds every test doing that and makes each one say whether
"it appeared on screen" is really all it needs.

## Goals

- [x] sweep test/win32 for waits whose needle is typed verbatim into the same pane
- [x] decide, site by site, whether the echo can fool what the wait is FOR
- [x] give the class teeth so the next script cannot reintroduce it silently

## Findings (the sweep, 2026-10-22)

An AST sweep (`test\win32\lib\EchoMarkerAudit.ps1`) over all 490 scripts found
58 waits in 24 files whose needle is nothing but text the same script typed.
Every one was read. None gates on a command having RUN or FINISHED: they are
liveness checks ("the shell echoed a typed marker" - the echo IS the proof),
persistence checks (the restored scrollback holds the marker; an echoed line is
as much the pane's content as a printed one), or analyzer over-reach with a
separate oracle (`Wait-MarkerPings` reads process command lines, not the pane;
ipc-command-keepalive's marker arrives via `--command`, and only `ALIVE<marker>`
is typed later). T1116's flood wait was the one site where the echo defeated the
assertion, and it was already split. So no harness needed a code change; what
was missing was anything stopping the NEXT one, which is what landed.

Mechanism choice (mine, not a decision - no user-visible difference): a
ratchet baseline of the reviewed sites rather than `# echo-marker:` comments in
24 harnesses, so recording them did not edit and re-due those harnesses; new
sites must split the marker or carry `# echo-marker: <reason>`.
