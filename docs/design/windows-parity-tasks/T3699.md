# T3699 - Linux L10f4: a pane row dropped among another window's rows in the GTK all-windows sidebar joins that window

## Summary

Split from T3607. Until now a GTK sidebar row let go anywhere landed among its OWN window's rows. On the Mac, a list drag stays inside its own sidebar (`PaneDragSession.isListDrag`). But inside that sidebar, a row let go over ANOTHER window's group in the all-windows list joins that window (`PaneDropResolver.sidebarHit` over `windowGroups` -> `.joinWindow` -> `PaneMoveCoordinator.insertAtTopLevel(side: .right)`; win32 `join_window` / `commitJoinDrop`).

Re-scoped 2026-11-26: the second half of the original title, a grid pane's grab handle (a pane drag, `application/x-ghoztty-pane`) dropped on the sidebar, is the same work as T3756 (the sidebar as a pane drop target: `.stash` / `.sidebar_order`, including another window's pane joining this window's list). It is left there rather than done twice.

## In plain terms

With the sidebar showing all windows, you can now drag one of a window's panes onto another window's group of rows. The pane moves into that window, next to its other panes on the right, with the same shell still running. Before this change the row always went back to its own window, wherever you let go of it.

## Goals

- [x] A pane row let go inside another window's group (its header down to its last row) moves that pane into that window's grid on the right edge, focused there, with the same shell
- [x] A stashed pane joining another window arrives on screen, not stashed
- [x] Let go in its own window's rows it still only reorders or stashes (T3607/T3698 behavior unchanged)
- [x] The tray does not light while the pointer is over another window's rows
