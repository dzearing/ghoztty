# T3793 - Linux quality pass: the window, chrome and motion must read as Mac quality on the real WSLg screen, judged side by side

## Summary

User directive 2026-11-25, after first seeing the Linux build on the real WSLg screen: "really needs to be as high quality as the mac version". So far the Linux port has been validated almost entirely in the private headless Weston on software GL, and the first look on a real screen found a see-through window (T3783), a too-bold title (T3791) and a resize that feels wrong and slow (T3792). Functional parity is not the bar; Mac quality is.

Do a side-by-side quality pass on the real WSLg screen against the Mac (docs/reference/ for the Mac's behavior and values; mac screenshots from the Mac seat where the reference lacks them): window chrome (header bar, buttons, spacing, corner radius, shadow), typography (weights, sizes, title/tab fonts), the pane sidebar and tab strip, splits and dividers, focus/unfocus dimming, open/close/new-tab animations and their timing, scrolling smoothness, selection, cursor, Settings window, command palette, HiDPI/fractional scale, light and dark. For each gap: file a seat: linux task (P1 for anything a user sees in the first minute) with a screenshot pair, or fix inline when trivial. Record the full list here with the task ids.

This is a PERSON-screen pass: it uses scripts\linux\open.ps1 and screen captures of the user's display, so it runs only when the user has the WSLg session up and has asked for it - never from a lane, sweep or floor step (same rule as WSL itself). The automated half is T3783's `open.ps1 -Check` on-screen pixel assertion.
