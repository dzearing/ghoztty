# T894 - ipc-p1 can fail all 21 assertions on a cold start right after the floor lanes, then pass clean on rerun

## In plain terms

The first acceptance script run after a heavy build/test session sometimes
reports everything broken when nothing is. Whoever is watching has to notice
the failure pattern, rerun it, and see it pass — time lost and trust in the
test's word eroded.

## Goals

- [x] a healthy build whose first launch is simply SLOW no longer scores a red
      floor run — and it is not silent about it either: the run prints
      `NOTE SLOW SETUP: <what> answered after <n>ms`, so a box that is slow for
      a real reason still looks different from a fast one
- [x] an app that genuinely never answers still stops the run, with one
      readable failure carrying the CLI's own words
- [x] the same holds for all three floor scripts, not just the one this was
      reported against

## What it turned out to be

Two defects, one layer apart, and the first one is a fix that overshot.

The 21-assertion cascade in the title is **gone**, closed by T1285: the floor's
fixture verbs are checked (`Need-Ghoz` / `Need-Listed`), so an app that never
came up stops `ipc-p1.ps1` at section 1 with a single `FAIL SETUP:` block
instead of blaming `+close` and `+list` for a window nobody built.

But T1285 made "the CLI printed anything unusual" the failure signal, and the
CLI has **two** unusual sentences, which say opposite things
(`src/os/ipc_timeout.zig`):

- `writeTimeout` — *"Timed out after 30000ms trying to ..."*. The CLI gave up.
  The verb did not happen. A failure, whatever the exit code says.
- `writeNotice` — *"Waiting for Ghoztty to answer ... (the app may still be
  starting up)"*. Printed at **5 seconds**, after which the wait **continues**
  to the full 30-second bound and usually succeeds. And
  `ipc_timeout.auto_launch_ms` is 30 seconds *precisely because* a cold
  auto-launch pays for the loader, Defender scanning a freshly built exe,
  config parsing and a session restore.

So a cold P1 straight after `floor-lane.ps1 -Lane all` — the exact scenario
this task was filed against — still went red on a healthy build and green on
the warm re-run. One failure rather than twenty-one, which is progress, but the
same cry-wolf defect the fixture exists to remove, moved one layer down.

The second defect is the `Cannot index into a null array` the report names. It
is not merely noisy: a PowerShell null-index is a statement-level error, so the
`Assert` it kills is **neither a PASS nor a FAIL** and goes unscored entirely —
the verdict under-counts rather than over-counts. `+list --json` is now parsed
through `Need-Parsed` in all three scripts, so an unparseable snapshot is one
setup failure carrying the raw answer.

## Summary

Observed 2026-08-16 (T578 turn): `test\win32\ipc-p1.ps1` run immediately
after `floor-lane.ps1 -Lane all` finished (four lanes, ~18 min of build/test
churn) failed 21 of 23 assertions, with `Cannot index into a null array` at
the `+list --json` shape checks — the app either never came up or never
answered IPC in time, so every downstream assertion cascaded. An immediate
rerun with no changes passed 25/25. Suspicion: cold-start latency (first
launch after cache churn, AV scan of a fresh exe, or the pipe not yet
listening) exceeding the script's launch/connect wait.

Worth doing: make the P1 launch wait tolerant of a slow first start (poll
the endpoint with a generous cold-start budget before the first assertion,
and make assertion 1 fail with "app never answered within Ns" instead of a
null-array cascade), and check whether P2/P3 share the same shape.

## Validation criteria

- [x] The root cause of the null-array cascade is identified from a repro or
      from instrumentation added to the script's launch path. — read out of the
      code, not guessed: `$json.data.windows | Where-Object` over a `$null`
      answer yields `$null`, `$p1ide.tabs[0]` then raises `Cannot index into a
      null array`, and under `$ErrorActionPreference = 'Continue'` that kills
      the statement WITHOUT scoring it. See **What it turned out to be** for the
      second, larger cause behind it.
- [x] A cold start after heavy churn (or a simulated slow launch) no longer
      fails wholesale: either the wait absorbs it or the script reports a
      single clear "app did not answer" failure instead of 21 cascaded ones. —
      the wait absorbs it. `test\win32\ipc-floor-setup.ps1` section C drives
      `Need-Ghoz` over canned CLI answers: `slow` (notice, then exit 0) returns
      and scores nothing, `gaveup` / harness-timeout still stop the run with one
      failure. Negative control: the same probe against a copy of
      `FloorFixture.ps1` carrying the old combined pattern answers
      `OUTCOME: stopped / FAILURES: 1 / the app under test stopped answering IPC`
      at `exit: 0 after 7ms`, so C1–C3 fail against the old code.
- [x] P2/P3 checked for the same launch-wait shape; fixed or noted why not
      applicable. — same shape, and one edit covers all three: the wait lives in
      the shared `test\win32\lib\FloorFixture.ps1`, which P1, P2 and P3 all dot-
      source. `Need-Parsed` was added to `ipc-p2.ps1`'s `Get-IdeJson` and
      `ipc-p3.ps1`'s `Get-P3Json` as well as P1's section 5.
