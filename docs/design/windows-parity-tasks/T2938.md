# T2938 - +close --force on Windows: close with no confirmation and no undo window, and a +close left waiting on a close confirmation fails instead of reporting success (Mac 4b558ab8f)

## Summary

Mac 4b558ab8f (main, 2026-11-12): +close now runs the close before replying, and a close left waiting on a 'Close Terminal?' confirmation FAILS with 'waiting on a close confirmation' instead of answering success (scripted windows piled up off screen). New +close --force dismisses any confirmation, closes with undo disabled, marks every pane's agent session to END and frees each pane's core at once, so the process exits now; a window target closes its whole tab group; older apps ignore the flag. Port both halves to the win32 IPC close handler (close-confirm dialog + close-undo window + agent session end), document --force in src/cli/close.zig + docs/claude/cli.md, and cover it with an acceptance script (close-confirm / close-undo harnesses are the neighbours). Reference: docs/reference/cli-commands.md '+close' on main, macos/Tests/IPC/CloseWindowTests.swift.

## In plain terms

A script that told Ghoztty to close a window could be told "done" while the
window was actually still sitting there behind an unanswered "Close anyway?"
question. Now that close says it could not finish and why, and there is a new
`--force` option for scripts that need the window gone no matter what: it
answers the question for them, skips the "you can undo this" grace period, and
ends the programs inside right away.

## Goals

- [x] `+close` of a pane or window whose window has a confirmation up fails and says "waiting on a close confirmation", closing nothing
- [x] `+close --force` dismisses that confirmation (as Cancel) and closes the target
- [x] `--force` skips the undo window: the shell exits now, a window is destroyed rather than parked, an agent session ends now
- [x] the CLI accepts `--force` (allowlist, help text, docs, bundled skill)
- [x] an acceptance script on the test desktop, with a negative control

## Design (Windows translation)

- Mac's `attachedSheet` has no win32 field, so the win32 counterpart is a
  registry of the dialogs whose modal loops are running
  (`src/apprt/win32/open_dialogs.zig`, pure + unit tested, pushed/popped by
  `ConfirmDialog.run`). `ConfirmDialog.openOver(hwnd)` is the question,
  `dismissOver(hwnd)` the force's answer (the Escape result: Cancel, or OK for an
  OK-only notice). Any ConfirmDialog owned by the window counts, like any sheet
  counts on Mac.
- Plain `+close` refuses BEFORE closing rather than closing and then checking
  (Mac's order): the dialog's modal loop is on the stack below the IPC dispatch,
  so tearing the window down there would free what that loop's caller returns
  to. Same user-visible answer.
- `--force` without a dialog closes synchronously through
  `Window.forceCloseSplitPane` / `Window.forceClose` (CloseUndo `bypass` = Mac's
  `disableUndoRegistration`; `closeNow` for a window). With a dialog it
  dismisses it and queues the close (`App.forceCloseDeferred`,
  `WM_APP_FORCE_CLOSE`), which runs once the dialog has unwound; a 50 ms
  `force_close_retry` timer covers the case where the posted message is
  dispatched by ANOTHER window's dialog nested inside it.
- No win32 tab groups across windows: a window target closes all of its tabs,
  which is the same experience as Mac's "whole tab group".
