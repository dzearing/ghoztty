# T2679 - Sweep the Apps & Features rows earlier updates orphaned: every box that took in-app updates from 1.43.4 to 1.52.10 still lists one dead 'Ghoztty' per release, and T2327's fix only stops new ones

## Summary

T2327 moved RemoveExistingProducts early so an upgrade no longer leaves the replaced release's HKCU Uninstall\{ProductCode} key behind. It does nothing for the rows already there: this box lists 44 (1.43.4..1.52.8), each a listed key whose product Windows Installer no longer knows (no LocalPackage, no hidden registration), and clicking Uninstall on one runs msiexec /x against nothing. Remove them on the user's behalf: an HKCU Uninstall key whose DisplayName is the product name, whose UninstallString is 'MsiExec.exe /X{code}', and whose {code} is not a registered product (MsiQueryProductState unknown) is an orphan of our own writing. Candidates: the MSI (a deferred CA after RemoveExistingProducts), the app at launch beside PathInstaller's self-heal, or ghoztty-cleanup.ps1. Never touch a key whose product is registered. Acceptance: arp-version.ps1 C1 goes green on this box; a throwaway-identity orphan (arp-orphan.ps1 B produces one) is swept by the shipped mechanism.

## In plain terms

Settings > Apps on a Windows box that took Ghoztty's in-app updates lists
dozens of "Ghoztty" entries, one per old version, and clicking Uninstall on
any but the newest does nothing useful. The fix that stops new ones already
shipped; this one makes Ghoztty clear the old dead entries itself the next
time it starts, so the list shows exactly one Ghoztty again.

## Goals

- [x] decide where the sweep lives: the app at launch (every affected box runs the app after its next update; a package custom action would run inside the very transaction that is writing a listed key)
- [x] remove only rows in the package's exact shape whose product Windows Installer has never heard of, and never while an install is running
- [x] prove it against the real registry and Windows Installer with throwaway rows, plus a negative control
- [ ] the user's own box shows one Ghoztty after the release carrying this is installed (arp-version C1 green) - follows the publish, tracked as a follow-up

## Mechanism (2026-11-04)

`src/apprt/win32/ArpOrphanSweep.zig`, started from `App.init` beside the PATH
self-heal, on a background thread. Which keys are dead is
`src/apprt/win32/arp_orphan.zig` (pure, every lane): braced product-code key
name; `DisplayName` exactly the product name and `Publisher` exactly
`dzearing`; `UninstallString` exactly `MsiExec.exe /X{same code}`; no
`WindowsInstaller`=1; and `MsiQueryProductState` = INSTALLSTATE_UNKNOWN. Skipped
entirely while `Global\_MSIExecute` exists (an install writes its listed key
before it registers the product). HKCU only. A Debug build never sweeps;
`GHOZTTY_ARP_SWEEP=force` plus `GHOZTTY_ARP_SWEEP_NAME=<throwaway name>` is the
test seam, and a forced run with no name does nothing. `GHOZTTY_ARP_SWEEP=off`
disables it.

Why not the MSI: the custom action would run inside the install that is
writing its own listed key, would have to tell that key from an old one, and
would only ever run during installs. Why not ghoztty-cleanup.ps1: users never
run it.
