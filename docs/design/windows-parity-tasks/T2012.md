# T2012 - Closing a pane leaves its banner on screen for ~5 s: per-pane overlay popups (banner, dim, bell border, scrollbar) must hide, move and resize with the pane, not wait for Surface.deinit

## In plain terms

With several panes open, each with a banner, closing one leaves its banner
floating on screen for about five seconds. The banner should behave like
part of its pane: it goes away the instant the pane does, and it moves and
resizes in the same frame as the pane.

## Summary

User report (2026-10-16): "when i have multiple panes open each with a
banner, closing one causes its banner to linger for about 5 second before it
disappears. why is the banner not a part of the pane? It should resize,
dispose, all with the pane."

Why it is a separate window: `BannerOverlay.zig` is a `WS_EX_LAYERED`
popup owned by the surface HWND, because DWM composites a layered popup
above the surface's OpenGL content and a plain child window cannot reliably
do that. The dim overlay, bell border, scrollbar and badges follow the same
pattern (T1350 counts five popups per pane).

Why it lingers (? INFERRED; confirm with timestamps): the banner is
destroyed only in `Surface.deinit` (`Surface.zig:1146`). A closing pane
leaves the layout right away, but deinit runs only after teardown
completes (the PTY/agent detach, a close timeout). Until then the
owner-owned popup stays visible at its old screen rectangle, over the
neighbour that took the space.

Fix:

1. **Hide on close, destroy later.** The moment a pane leaves the layout
   (close, stash, move to another window or tab), hide every overlay popup
   it owns with `ShowWindow(SW_HIDE)` or `SetWindowPos(SWP_HIDEWINDOW)` in
   that same pass. `deinit` can still destroy them whenever teardown
   finishes.
2. **Move and resize with the pane in one batch.** Lay out the pane and all
   its overlay popups in ONE `BeginDeferWindowPos`/`EndDeferWindowPos`
   batch (check how `chrome_fanout.zig` does it today), so a resize never
   shows the banner a frame off.
3. **One rule, every overlay:** a single "pane chrome follows pane" helper
   that the banner, dim, bell border, scrollbar, badges and the readonly
   badge all use, with a check that fails if a new overlay type skips it.
   That is the first step toward T1350 (one chrome window per pane).

## Root cause

✓ VERIFIED. `+close` of a split does not tear the pane down: since T1825
it is PARKED for `undo-timeout` (default **5 s** - the user's "about 5
seconds") so ctrl+shift+z can bring it back. `CloseUndo.hidePane` hid the
surface HWND only. The banner, dim wash, bell frame, badges and scrollbar
are separate top-level popups OWNED by that HWND, and hiding an owner does
not hide what it owns. The parked pane is also out of the tab tree, which
is what every overlay pass walks, so nothing revisited them until the undo
expired and `Surface.deinit` destroyed them.

A second hole surfaced in the harness: a pane hidden by a position call
(`SWP_HIDEWINDOW` in a layout batch: stash, zoom, carousel) gets no
`WM_SHOWWINDOW`, which was the scrollbar's only hide hook, so a stashed
pane's scrollbar stayed up.

## Fix

- `Surface.overlay_fields`: ONE list of the pane's popups, walked by both
  the z-order heal and the new `Surface.hideOverlays()`. A comptime test
  ("every pane overlay is listed") fails if a new `?*T` field whose `T`
  has `owner` + `hwnd` is left off it.
- `PaneView.hideOverlays()` (a viewer hides its dim wash), called from
  `CloseUndo.hidePane`, so parking a pane, a tab or a window takes its
  popups off screen in the same pass.
- The terminal surface's `WM_WINDOWPOSCHANGED` arm: `SWP_HIDEWINDOW` hides
  every popup, `SWP_SHOWWINDOW` brings the scrollbar back.
- `Scrollbar.repositionAndResize` follows its owner like the banner does:
  a hidden owner's scrollbar is placed hidden, never `SWP_SHOWWINDOW`.
- `Scrollbar.hide` / `BellBorder.hide`: the uniform name the list calls.
