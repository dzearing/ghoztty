# T1615 - An activity-monitor.ps1 run started right after another one sees eight stray ping rows and refuses to click

## In plain terms

One of our own test scripts scores itself red when it is run twice in a row,
for a reason that has nothing to do with the terminal. Nobody using Ghoztty
sees this, but whoever is reading the test result does: a red that says
"something regressed" when nothing did costs the next turn its context while
somebody chases a defect that is not there.

## Summary

Observed 2026-09-16 while validating T791. Run the harness, then run it again
immediately: the second run fails section M with `shown=8` (it wants 3) and
section O with `shown=9` (it wants 1), and because those are the SAFETY
assertions that gate the by-position clicking, `$safeToClick` goes false and
M1/M2/O's kill arms never run - 164 assertions instead of 210. A third run,
started a couple of minutes later, was ALL PASS (210).

The count is the lead: 8 is exactly the number of `New-PanelSpawn` calls the
previous run makes (H's 1, M's 3, M2's 3, O's 1). The previous run's own O saw
`shown=1`, so those spawns do NOT match the `ping` needle while their own run
is alive - which points at what they become after their app dies rather than at
what they are. Two candidates worth measuring before fixing anything:

- **ppid recycling.** The spawn parents outlive the app (they are killed in the
  `finally`, and the panel's kill only takes the PING.EXE child), and a dead
  app's pid can be handed to the NEXT run's `ghoztty.exe`. The tree walk is by
  ppid, so last run's orphans would then read as this run's children.
- **Teardown racing the next launch.** `Stop-Process` on the extras is fire and
  forget; a run started seconds later can begin enumerating while they are
  still dying.

The fix should make the section's guarantee hold rather than widen the
tolerance: the needle is what makes "every visible row is mine" true, so a
stray that gets past it is the defect, not the assertion.

## Validation criteria

- [ ] The two candidate causes above are distinguished by measurement (the
      stray rows' pids and ppids captured at the moment M fails), and the one
      that is real is named in the progress log.
- [ ] Back-to-back runs of `test\win32\activity-monitor.ps1` are ALL PASS, with
      no gap between them, repeated three times.
- [ ] `-NegativeControl` immediately followed by an ordinary run is ALL PASS on
      the ordinary run - that is the exact pair that produced this.
- [ ] The M/O safety assertions are unchanged in strictness (still `shown -eq 3`
      / `shown -eq 1`); nothing here is fixed by loosening them.
