# T3754 - A new pane inherits a folder only from a pane of the same shell family: a WSL split of a WSL pane starts in its Linux folder, a Windows shell opened from a WSL pane in its own default, and the CLI passes a Linux --working-directory through for a WSL shell (T3735)

## Summary

Child of T3735. Inherit-working-directory: a WSL split of a WSL pane keeps its Linux cwd (from OSC 7, passed as wsl --cd); a Windows-shell split of a WSL pane, or the reverse, falls back to that shell's own starting folder instead of a mangled path. Today (T3749) a WSL pane opened with no folder goes to ~, and a split's inherited Windows cwd is overridden by ~ only when no --working-directory was given.

**Re-scoped 2026-11-25 (this turn):** the card bundled three features. The inheritance rule and the CLI pass-through land here; the Settings > Shell per-shell **Starting folder** field moved to **T3770** (it needs a new config key and a new Settings control, on both platforms); the remote `wsl:<distro>` expansion moved to **T3771**; a WSL *default* shell's keybind split moved to **T3772**.

## In plain terms

If you split or open a tab from a WSL (Linux) pane, Ghoztty used to hand the new PowerShell or cmd pane a Linux folder it could not use, or the Windows folder WSL happened to be launched from. And a new WSL pane opened from a WSL pane always landed in your Linux home instead of the folder you were in. Now a folder only follows into a shell of the same kind: Linux to Linux, Windows to Windows; otherwise the new shell starts in its own default. Typing `ghoztty +new-window --shell=wsl:Ubuntu --working-directory=/home/me/src` also works now instead of failing.

## Notes

- A WSL pane's folder is only known when its shell reports OSC 7. Stock Ubuntu bash does not, and Ghoztty does not inject shell integration into WSL, so a WSL child of an unconfigured WSL pane still starts at `~`. That is the honest fallback, not a bug: the Windows-side process cwd of `wsl.exe` is never the Linux folder.
- The core stores an OSC 7 path on Windows with its slashes flipped (`\home\me`), so `shell_family.toLinuxPath` flips them back.
- Harness trap found on the way: the stub is cmd.exe, which finds `/c` INSIDE a token, so `--cd /home/x/cli` ran `li` and exited 1. The test folders avoid `/c`, `/k`, `/r`.
- Mac half: none owed for the family rule (Mac has no WSL); the per-shell Settings field (T3770) carries its own Mac half.
