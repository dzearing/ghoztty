# T1636 - A pushed stream is never re-established when a connection reconnects in place, so the roster silently stops updating

## Summary

`Connection` re-establishes its transport on its own (`reconnecting` ->
`reattaching` -> `connected`), and nothing re-issues the subscriptions that were
installed on the previous socket. `subscribeSessionCpu` and the pushed roster
(`subscribeSessions`) both write a control frame once, at subscribe time, so
after an in-place reconnect the peer has no record of either and the frames stop
while the handler slots still look installed.

Found while fixing T813, which covers the SYMPTOM for the CPU meter only: its
staleness rule blanks a column that has gone quiet, whatever the cause. The
pushed roster has no such rule - it just holds the last list it was given - and
the fetched path only re-asks on a selection change or a poll the local machine
does not get. So the roster is the surface where this is still silent.

Two candidate shapes: `Connection` re-issues its own live subscriptions as part
of the resync that follows a reattach (one place, covers every future stream), or
each probe observes link state and re-subscribes for itself. The first is the one
to weigh first - a subscription is connection state, and every consumer
re-deriving it is how the next stream inherits the same bug.

## In plain terms

With the machine picker open on another computer, the list of that computer's
sessions stays current by itself. If the network link underneath it dropped,
the list quietly stopped updating and kept showing whatever it last knew, with
nothing on screen saying so. Now the app notices a link that stays down for a
few seconds, reconnects on its own, and the list and the CPU meter pick up again.

## What was actually wrong (re-verified on claim)

The Summary's premise does not hold: `Connection` never re-establishes its own
transport. When a socket drops, the reader thread exits and the link sits in
`reconnecting` for good; `dead` is only entered by a server-sent DETACHED.

- **Local agent:** already covered. T813's `syncLiveStreams` retargets both
  streams to null when the shared link stops carrying requests and back onto the
  replacement, once each.
- **Remote machine (the silent case):** `MachineConnectionPool` acted on `dead`
  alone, so a dropped relay socket left a zombie pooled entry forever. Nothing
  re-dialed it, and the chooser's pushed roster froze with the last list on screen.
- **A latent use-after-free on the T859 path:** `redialNow` freed the condemned
  entry without telling the leases, so when the replacement landed,
  `retarget` → `stop()` unsubscribed through the freed old `Connection`.

Fix (the "subscription is connection state" shape, one level up, because the
pool is what owns a connection's replacement):
`machine_pool.DownWatch` (5s settle, the `agent_recovery.settle_ms` reasoning),
fed by the link edge in `onLink` and by `MachineConnectionPool.sweep` on the
chooser's 5s poll. Both it and `redialNow` go through one `condemn`, which
notifies the leases with a new `Failure.redialing` WHILE the old handle is still
valid (the chooser `stop()`s both probes; the roster paints no error card), frees
the entry, then re-dials. The replacement arrives through `onPoolChange` and
re-subscribes each stream exactly once.

## Goals

- [x] A remote pooled connection whose socket dropped is replaced without anyone clicking
- [x] The pushed roster and the CPU meter come back on the replacement, once each
- [x] Leases let go of a condemned connection before it is freed (closes the T859 use-after-free)

## Validation criteria

- [x] An in-place reconnect (drop the transport without killing the agent) leaves the pushed roster still updating. — `test\win32\chooser-conn-pool.ps1` section H: the relay drops the bridge, nobody touches the chooser, the pool logs `stayed reconnecting for 5000ms ... redialing`, the roster re-subscribes and the agent's subscribe-time push arrives. (A session started by ANOTHER client after the swap is not pushed - that is not this defect, it is the agent pushing only to the originating connection: T1749.)
- [x] The same for the CPU stream: frames resume without waiting for a selection change. — section H: `chooser cpu: subscribed` +1 and new `chooser cpu: frame rows=` lines.
- [x] Whatever re-subscribes does so exactly once per reattach - no duplicate streams and no doubled frame rate. — section H, measured after a further 12s: exactly one condemn, one pool dial, one roster subscription, one CPU subscription.
- [x] An acceptance script on box demonstrates the reconnect, not just a unit test. — section H ALL PASS (38 assertions); **negative control**: the same script against a build with the sweep call removed fails all 9 H assertions. Unit tests: three `DownWatch` tests in `machine_pool.zig`.
