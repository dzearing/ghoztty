# T1636 - A pushed stream is never re-established when a connection reconnects in place, so the roster silently stops updating

## Summary

`Connection` re-establishes its transport on its own (`reconnecting` ->
`reattaching` -> `connected`), and nothing re-issues the subscriptions that were
installed on the previous socket. `subscribeSessionCpu` and the pushed roster
(`subscribeSessions`) both write a control frame once, at subscribe time, so
after an in-place reconnect the peer has no record of either and the frames stop
while the handler slots still look installed.

Found while fixing T813, which covers the SYMPTOM for the CPU meter only: its
staleness rule blanks a column that has gone quiet, whatever the cause. The
pushed roster has no such rule - it just holds the last list it was given - and
the fetched path only re-asks on a selection change or a poll the local machine
does not get. So the roster is the surface where this is still silent.

Two candidate shapes: `Connection` re-issues its own live subscriptions as part
of the resync that follows a reattach (one place, covers every future stream), or
each probe observes link state and re-subscribes for itself. The first is the one
to weigh first - a subscription is connection state, and every consumer
re-deriving it is how the next stream inherits the same bug.

## Validation criteria

- [ ] An in-place reconnect (drop the transport without killing the agent) leaves the pushed roster still updating.
- [ ] The same for the CPU stream: frames resume on the same `Connection` without waiting for a selection change.
- [ ] Whatever re-subscribes does so exactly once per reattach - no duplicate streams and no doubled frame rate.
- [ ] An acceptance script on box demonstrates the reconnect, not just a unit test of the re-subscribe call.
