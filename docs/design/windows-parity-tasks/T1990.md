# T1990 - Panes show a hard white border on Windows: the focused card's rim and glow render as a crisp white outline, not Mac's faint backlight

## In plain terms

A side pane showing a web page with a dark background (the task dashboard in
the user's screenshots) had a bright white line around its rounded border.
That line was not a focus effect: Windows assumed every web page is white and
painted the thin strip around the page white. Now the strip takes the page's
real colour, so a dark page has no white ring.

## Goals

- [x] Find what actually draws the white line
- [x] The strip around a web or `.html` page takes the page's own colour, and follows it when the page changes theme
- [x] An on-screen check that fails on the old behaviour and passes on the new one

## Summary

User reports (screenshots on 2026-10-10 and 2026-10-15): a viewer pane
showing `http://localhost:7788/#activity` has a crisp white rounded outline
on all four sides. The 2026-10-15 report came after five days with no task:
the controller session explained a cause on 2026-10-10 and promised a task,
but never filed it. That is why this was P0 at order 0.

**The cause was not the rim or the glow.** The filing guessed at
`pane_elevation.zig` (rim rounding up to whole pixels, glow peak stacking on
it). Reading the code disproved that guess. The rim is an analytic 0.5 DIP coverage ring at Mac's
alphas, and there is no `rimPx` rounding. The real cause is
`ViewerPane.cardColors`: for `.web`/`.html` modes it returned a hard-coded
white "browser default" as the card's colour. A viewer's child window sits
`childInsetPx` (1-2 px) inside the card the window paints, so a dark page
was ringed by a 1-2 px strip of WHITE card fill on all four sides and round
the corners, which matches the screenshot exactly. Mac clips the web view to
the card, so its page runs to the edge and there is no strip to get wrong.

**Fix**:

- `viewer_bridge.page_background_js` (main frame, in the injected blob) reads the
  computed canvas colour (root element's background, else body's, per the
  CSS propagation rule). It posts `pageBackground` on DOMContentLoaded/load,
  on a `prefers-color-scheme` change, and on a class/style/data-theme change
  of `html`/`body`, and only when the colour changed.
- `ViewerPane.setPageBackground` composites a translucent colour over
  white and stores it in `page_bg`. When the colour moved, it invalidates the
  parent so the card repaints.
- `cardColors` uses `page_bg` for web/html and falls back to white until the page reports.

      (opaque, translucent over white, and no colour falls back to white).
- [x] Focus cue unchanged: the rim and glow code is untouched, and the existing
      pane-elevation glow assertions stay green in the same run.
