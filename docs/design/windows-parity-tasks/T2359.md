# T2359 - Dragging the pane sidebar's edge relays the panes out on the plain (non-live) path, so every mouse move resizes each terminal without waiting for its frame and the grid janks back and forth; window-edge and divider drags take the synchronous-present path, the sidebar drag does not

## Summary

User report (2026-10-27, interactive): "I resize the left nav, it janks back
and forth like its lagging."

Root cause:

- `PaneSidebar.edgeMove` (src/apprt/win32/PaneSidebar.zig, ~L4212) calls
  `Window.setPaneSidebarWidth` on every mouse move.
- `setPaneSidebarWidth` (Window.zig ~L2781) calls the plain `layoutSplits()`,
  not `layoutSplitsLive()`. So `in_live_layout` is false, and no surface has
  `in_live_resize` set (only WM_ENTERSIZEMOVE sets that, Window.zig ~L15689).
  The chrome fan-out z-order suppression (T1345) is also off.
- Result: each tick resizes every pane's GL child HWND and moves its layered
  overlays without waiting for a frame at the new size. DWM shows the old-size
  frame, then the new one, so the grid looks like it lags behind the pointer
  and snaps back. The divider drag (T1031/T1343) and the window-frame drag
  (T1393) were fixed for this; the sidebar edge drag (T1846/T2265) came later
  and never got the live path.

Fix: route the sidebar edge/gutter drag through `layoutSplitsLive()` (and
the same for the expand/collapse glide ticks the drag triggers). Turn on
`drag_perf_on`/`reportDragCost` for this drag too, so it reports the same
per-tick cost line a divider drag does.

## Validation criteria

- [ ] Sidebar edge drag ticks log `sync=N panes=N` (every resized pane on the synchronous path), the way `reportResizePass` does for a frame drag.
- [ ] A drag-cost line for the sidebar drag on a 4-pane window shows mean tick within the frame budget, measured before and after.
- [ ] Acceptance script in test/win32/ drags the sidebar edge and finds no blank/stale-size pane frames (same oracle as the divider-drag flicker test).
