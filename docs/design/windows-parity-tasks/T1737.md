# T1737 - Nothing measures a terminal pane's frame pacing, so a hero-mode stutter can only be reasoned about, not scored

## In plain terms

Whether the terminal you are looking at scrolls and redraws smoothly could
only be argued about here, never measured. This adds a stopwatch to every
terminal pane in development builds, so a test can say how evenly its frames
arrived - and uses it to check the earlier fix that keeps the overview strip's
little previews from stealing frames from the big pane.

## Goals

- [x] Every terminal pane in a debug build records when each of its frames reached the screen
- [x] A test can read and reset that record per pane (`frame-pacing`, debug-only IPC)
- [x] T1423's before/after is taken: hero pane under a gesture, captures paced vs unpaced
- [x] An acceptance harness scores the probe and the A/B, with a negative control


T1423 paced hero-mode thumbnail captures (Mac bc89bb8f3 policy) and scores it by counting capture requests across a gesture, but its first validation criterion - hero-pane frame timing with the carousel open, before and after - could not be taken: this box has no probe for a terminal pane's present intervals (Mac measured rAF intervals inside a WKWebView). Add a debug-build frame-interval histogram per surface (present timestamps from the renderer thread, exposed through a debug IPC action or the debug log), then take T1423's before/after: hero terminal under continuous input with the carousel open, captures paced vs forced every tick.

## Validation criteria

- [x] Pure recorder (`src/apprt/win32/frame_pacing.zig`): 8 unit tests in every app-runtime lane (steady 60 Hz, a single hitch, ring ageing, reset, clock step-back, buckets, percentiles) - `floor-lane.ps1 -Lane all`
- [x] The probe records, tells panes apart and resets - `test\win32\frame-pacing.ps1` ALL PASS (13): flooding hero 512 intervals at median 8.3 ms; hidden one-line-a-second pane 13 frames vs the hero's 659; a read straight after reset held 3 frames
- [x] T1423 before/after taken (same run, background test desktop, 120 Hz cadence): hero frames during a ~3s wheel gesture, unpaced -> paced: p95 8.6 -> 8.5 ms, p99 9.0 -> 8.7 ms, max 16.9 -> 16.7 ms, long 1 -> 1, captures 35 -> 1. The pacing keeps the captures off the hero pane as designed; on this box a tile-sized readback fits inside the 8.3 ms frame budget, so the frame-time difference is within noise
- [x] Negative control: `frame-pacing.ps1 -NegativeControl` (paced arm launched unpaced) FAILS the paced capture assertion (35 captures) - exit 1, 1 FAILURE
- [x] Release builds do not carry it: action and recording both gated on `build_config.is_debug` (`Surface.frame_pacing_enabled`, `ipc_frame_pacing.enabled`, `heroSnapUnpaced`)
