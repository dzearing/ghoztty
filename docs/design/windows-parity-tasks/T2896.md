# T2896 - Every hover-fill assertion is hollow: the +hover IPC path RedrawWindows the whole window itself, so a build whose hover never invalidated still lights up under test

## Summary

Found by T1407's survey. `ipc_hover.zig:192` ends the hover verb with
`RedrawWindow(RDW_INVALIDATE | RDW_UPDATENOW | RDW_ALLCHILDREN)` on the whole
window, so whatever the app's own hover handler does or forgets to invalidate,
the window is repainted before `Get-TestHoverCapture` reads it. Its `Changed`
flag compares two frames that this call forced, so it is no oracle either.

Affected: caption-bar:424/429, tab-strip:1015-1025/1537/1559, hero-mode
845/849/950/956, chooser-kill-hover:255/266, pane-banner:1613, pane-elevation:321,
pane-stack-strip:519/527, split-divider hover rows.

Decide (mechanism, so it is this task's call): either drop the forced redraw
and let the app's own invalidation be what the capture sees (then measure each
hover claim against its deleted invalidate), or keep it and score the
invalidation separately with the paint probe. Whichever, at least one hover
claim must be RUN red against a deleted hover invalidate before this closes.

## Validation criteria

- [ ] Each listed claim marked survives-deletion / goes-red, with the build that showed it.
- [ ] Every survivor gains a probe assertion RUN red against the deletion, or is re-labelled to what it really measures.
- [ ] Touched harnesses green afterwards; guard-due rows cover any probe surface they depend on.
