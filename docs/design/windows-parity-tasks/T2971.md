# T2971 - PA-R05: every drawn frame builds a full viewport string and byte map for link matching even when no link can highlight (Ctrl not held)

## Summary

PA-R05 (audit-1, T2959). link.zig:76-83 renders the viewport into a string plus per-byte coordinate map before the per-link highlight check at :89-101; generic.zig:1591 calls renderCellMap unconditionally. The default link highlights only on hover with Ctrl (config/Config.zig hover_mods), and generic.zig:1557-1563 already computes the exact predicate (`needed`) but only uses it for seams. Cost estimated: cols x rows string and map allocated, grown and freed per frame, up to 120 fps under output and on every blink tick. Fix: skip renderCellMap when !needed. Risk very low. Shared code: Mac half filed with the shared-renderer Mac task.

## In plain terms

To underline web links when you hold Ctrl and hover them, the terminal copied
the whole visible screen into a text buffer and searched it on every frame it
drew - even when Ctrl was not held and nothing could be underlined. That is
wasted work on every redraw while output streams. Now it only does that work
when a link could actually light up; links still underline and open exactly as
before. Shared renderer code, so the Mac build gets the same saving.

## Goals

- [x] one predicate ("can any link highlight with this mouse/modifier state?") shared by the renderer's seam pass and the link matcher
- [x] the link matcher returns before building the screen text when the predicate is false
- [x] a unit test proves nothing is allocated on a no-highlight frame, with a positive control
- [x] busy-output CPU measured before/after on the release build (inconclusive under box noise - see T3080)
- [x] Ctrl-hover link behaviour re-verified by its acceptance harness
