# T2157 - viewer-narrow-pane is red since panes stopped shrinking at 300 DIP: section E can no longer narrow the bar into its overflow form, and section F's card capture comes back blank

## Summary

Two reproducible reds (both the parallel and the alone run, 2026-10-22, HEAD 4b5d9301d): E 'the narrow bar's leading control is the ... overflow' (every band from ratio 72 to 92 measures the same 373px bar, 5 inked slots - the +rearrange ratios hit c49edb033's 300-DIP pane minimum, so the overflow band is never reached) and F 'the contents card paints under WM_PRINTCLIENT' (Get-TestWindowPixels -Sync on GhozttyViewerTOC returns null/uniform; cause not yet read - may be the same minimum keeping the pane out of compact form, or the glass-pane change b2b611998). guard-due still reads viewer-narrow-pane CURRENT because the pane-minimum code is not in its row, which is the second half of the defect: add the split-minimum source to the row. Fix the harness to narrow by window width (or a min-width-aware layout) rather than by split ratio, find F's cause, and land the coverage row.

## In plain terms

The test that checks how a viewer pane looks when it is squeezed narrow had
been failing on every run since panes got a minimum width. It was still trying
to squeeze a pane by dragging the divider, which no longer goes that far, and a
second check was measuring a window that was now just too narrow to show the
contents list. The test now squeezes a whole window instead, so it can again
see the compact "..." toolbar, and it says plainly when its window is too
narrow.
