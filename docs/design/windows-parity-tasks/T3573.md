# T3573 - Linux L11k: window modes on GTK - an opt-in single window of workspaces, switched from the pane sidebar all-windows list

## Summary

Port docs/reference/window-modes.md to GTK. **Rescoped 2026-11-24 to the
launch latch** (the win32 T3180/T3212 slice); the rest of the feature is split
into T3648-T3655, the way win32's T3136 split into T3180-T3187.

This card: `macos-window-mode` (separate default, single opt-in) is read once
when the GTK app starts, through win32's pure `window_mode.zig`; a reload that
now says the other mode does not move it and says so in the log; with
`quit-after-last-window-closed = false` the first window opened while none is
open is the next launch and re-reads it.

## In plain terms

Linux Ghoztty will get the Mac's "All in one window" option. This first step
makes the app read that setting the way the Mac does - once, when it starts -
so changing it mid-session never half-converts the windows you already have.
The one-window behavior itself comes in the follow-up cards.

## Goals

- [x] the GTK app latches the mode at launch (shared latch, no third copy)
- [x] a reload that disagrees leaves it in force and names the next launch
- [x] a resident app with no window re-reads it for the next window
- [x] the hand-off design is decided and split into cards

## Design (mechanism, decided here)

In single mode the physical toplevel is ONE GTK window. Each workspace keeps
its own `Window` GObject (title, tabs, split trees, sidebar, config binding)
- Mac's "every workspace keeps its own controller; only the NSWindow is
shared". Its template content (the `Adw.TabOverview` subtree) moves into the
shared toplevel on show and is held off-window, ref'd, while parked; the
content's template bindings keep pointing at its own `Window`, so titles and
config stay right with no rebinding. Rejected: one GtkWindow per workspace,
hidden while parked - on Wayland a hide/show is an unmap/map, so the window
would flash and land wherever the compositor puts it (WSLg: a new Windows
window each switch), which is not "one window". Consequences carried by
T3648: every widget-to-window lookup (about 24 `getAncestor(Window)` /
`getRoot` sites) goes through one owner-of helper (Mac `owner(of:)`), and the
workspace's `win` action group is inserted on its content root so
accelerators and menus reach the workspace on show. Membership/decisions:
win32's pure `workspace_host.zig` `Host(*Window)`. Parked content is
unmapped, so `window_seen`/`Surface.syncSeen` already stops its terminals
drawing.
