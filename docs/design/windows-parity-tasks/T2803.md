# T2803 - Composition step 5d-5d: sidebar row reorder - rows sliding aside for a dragged pane and the held row settling where it landed - runs on the compositor (per moving row a visual whose offset Y is declared once), instead of TIMER_REORDER repainting the column per frame

## Summary

onReorderTick repaints the whole column each frame while rows shift (reorder.zig tweens, settle_ms) and the tray hot fade runs. On T2765's tree, each shifting row (and the settling held row with its shadow) becomes a visual with animateOffsetY on the reorder curve; the pointer-driven part of the drag stays per input. Oracle: film with stall seam + stepped control.

## In plain terms

When you drag a pane's row up or down the sidebar, the other rows slide
aside to make room. The app used to redraw the whole sidebar every frame
while they slid, so the slide hitched whenever the app was busy. Now Windows
itself plays the slide, and the row you are holding rides along on the same
layer, moved only when the mouse moves.

## Goals

- [x] each row that slides aside is captured once and its slide handed to the compositor - one declared animation per change of target
- [x] the held row is on the same tree, above the sliding rows, moved per pointer input with no per-frame repaint
- [x] the reorder clock no longer runs for the slides (0 frames vs 24 stepped)
- [x] anything that cannot go on the tree - motion off, a transition, a window/group drag, the rail of windows, a failed capture - stays stepped as before
- [ ] the settle after the drop (filed as T2848) and window/group drags + the tray header slide (T2849) - split out

## Design

- `pane_sidebar_reorder_comp.zig`: a box at the scrolling viewport (clipped
  to it, so a row passing under the pinned head is cut as the paint cuts
  it), a rows box on it, and the held row above that. `addRow` uploads a
  row's capture; `follow`/`slide` declare `animateOffsetY` on the shift
  curve (`fitCurve(transition.ease)`, `tailOf` when declared mid-tween) once
  per retarget; `setHeld`/`moveHeld` carry the held row.
- Capture is a two-background matte (`matte`): the row painted over black
  and over white with the column's own `paintRow`/`paintTile` (and, held,
  `paintLiftBacking` with its shadow), coverage = 1 - (white - black)/255,
  so the visual has the row's antialiased edges, glass and soft shadow over
  whatever the column shows. Unit-tested: opaque, clear, half, ClearType
  fringe, and round-trip over three backgrounds.
- `PaneSidebar.composeDrag` runs in the live paint after `applyDragMotion`;
  composed rows are skipped by `paintRows`/`paintMini`, `paintHeld` only
  moves the composed held row. `reorder_comp_all` keeps the shift tweens
  off `reorderMoving`, so `noteDrag` no longer arms the clock for them.
- Mechanism choice (my call, recorded): the held row has to be on the tree
  whenever any row is - the tree is topmost over the GDI window, so a GDI
  held row would pass under composed ones. If the held capture fails the
  whole drag is stepped.
- Trade-off: a row's capture is frozen for the drag (a title change or a
  busy sheen mid-drag is not redrawn on it until the drop). Sheens already
  stay stepped while a drag runs (T2801).
- Seam: `GHOZTTY_DEBUG_SIDEBAR_REORDER_STEPPED=1` keeps the drag stepped
  (the control arm).

## Validation criteria

- [x] the matte and the slide curve: `pane_sidebar_reorder_comp.zig` tests (none lane via unit_tests.zig)
- [x] a held-tile drag up the rail goes on the tree and the clock never steps it: `test\win32\pane-sidebar-drag.ps1` section F - `comp on=1 held=1 slides=1 clock runs=0 frames=0`; captures partly covered, never a solid block (held 1900/22 of 4221 px, row 1985/1950 of 2025); `reorder comp off slides=1` after the drop; 86/86 ALL PASS

- [ ] NOT RUN (input desktop; the user is present): a film of a drag through a UI stall. WM_PRINTCLIENT returns GDI pixels only, so the background desktop cannot photograph the composed rows; frames=0 is the proof the window thread no longer drives the slide
