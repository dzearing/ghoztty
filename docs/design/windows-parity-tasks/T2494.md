# T2494 - Windows leak sweep for the rest of Mac's 2026-10 memory audit: closed split/tab/viewer panes, failed viewer inserts, glide/animation timers and DComp visuals must not outlive their pane or window - measured over N cycles, every leak found fixed

## Summary

User 2026-10-29 20:45: "i just merged some critical memory fixes into the mac
release. It would be good to eval if we have the same bugs on the windows build
and to repair them asap, leaks are really bad"

Mac's memory audit (origin/main 1bc34a8d7 + ef57f03fd, `docs/reference/memory.md`)
found and fixed these defect classes. Windows has a task for some of them: T2473
(closed window keeps its panes), T2489 (closed pane's shell outlives undo-timeout)
and T2474 (hidden windows keep render targets). The merge itself (T2472) only
mapped the commits; **nobody has measured a Windows process for any of them.**
This task covers the remaining classes:

1. **A closed split pane, closed tab, and closed viewer pane** free everything they
   own once their undo window has passed: the Surface (renderer + IO threads, GL
   context, the T2466 composition swap chain if on), the ConPTY + child process or
   the agent session CLOSE, child HWNDs (T681 regression check), and for viewers the
   WebView2 controller **and its msedgewebview2 renderer process**. Mac's known-unfixed
   gap is a closed viewer keeping its WebContent process. Check whether Windows has
   it too.
2. **A failed viewer insert**, where the split/view request fails after the
   WebView2 environment or controller was created, frees what it created.
3. **Timers and animations outlive their owner.** These are the win32 analog of
   Mac's glide timers: `SetTimer` callbacks (about 50 call sites in
   `src/apprt/win32`), blade glide and fold animations, DComp visuals/animations
   and drag-hold state. For each one, closing the pane or window mid-animation
   must stop it and free it. Use no use-after-free and no timer still firing
   against a dead HWND as the oracle.
4. **Cycle growth.** A closure stored on window-owned state that keeps the tree
   alive shows up here as growth that never returns.

Method: an acceptance script (debug build, off-desktop per TestDesktop.ps1)
drives N = 20 cycles of each scenario through the CLI (`+new-window`, `+split`,
`+split --view=`, `+close`, mid-glide close). After each cycle it waits out
`undo-timeout` and samples the app process: private bytes, GPU dedicated and
shared bytes (`\GPU Process Memory(pid_N_*)`), handle, GDI and USER object
counts, thread count, and the descendant process count (conhost, shells,
msedgewebview2). The fit is a slope over the cycles after warm-up: anything
that grows per cycle past a stated tolerance is a leak. Each leak found gets
fixed under this task, or under a P0 task of its own if it is large. Each fix
comes with a red-then-green run.

## Validation criteria

- [ ] Leak acceptance script exists; with a deliberately planted leak (teeth check)
      it goes red on the per-cycle slope
- [ ] Scenario results table (per scenario: per-cycle slope of each metric) recorded
      here for the current build BEFORE any fix
- [ ] Closed split / tab / viewer: flat on every metric; closed viewer's
      msedgewebview2 process exits
- [ ] Failed viewer insert: flat
- [ ] Close mid-glide / mid-fold / mid-drag-hold: no timer fires afterwards, no
      crash, flat
- [ ] Every leak found fixed with a red-then-green run, or filed P0 with its numbers
