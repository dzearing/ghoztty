# T2505 - Folded blades are opaque on Windows: on Mac a blade is glass, semi-transparent, so the window gradient reads through it while it folds and once folded. Make Windows blades the same glass, in the same atomic present as the fold (user 2026-10-30: part of the jank)

## Summary

The user watched the T2485 chain-fold runs and reported that the blades are not
glassy or semi-transparent, so the window gradient does not show through them.
They called this part of the jank: the eye reads an opaque slab arriving as a
hard change. The full quote is in the progress log.

Mac draws a folded blade, and a blade mid-fold, as the pane's glass sheet
(GLASS_TINT over the desk gradient; see T2160/T2281, done for strips at rest).
On Windows the blade, and the fold face that hands over to it, comes out opaque
in the chain-fold. Find which surface is opaque: the UpdateLayeredWindow face,
the strip pass, or the composition visual. Make it alpha-composited over the
live desk gradient, and keep it in the same atomic present as the fold (T2485).
A translucent blade drawn in its own pass would bring back the
background-clear flicker the user also reported.

## In plain terms

When panes fold down into thin blades at the side of a window, Windows drew
each blade as a nearly black slab, while on Mac a blade is a strip of the
same frosted glass as the pane, with the window's colour gradient showing
through it. After this change, a folded blade on Windows is that same glass,
edged with the same faint rim. It looks the same at rest and while it folds.

## Goals

- [x] A folded blade is the pane's own glass, not a dark fill over it
- [x] The face shown while a pane folds is the same glass, so nothing changes colour when the fold lands
- [x] The blade keeps the card's thin rim, so neighbouring blades still read apart
- [x] Still one paint: no extra pass that could bring the background-clear flicker back

## Validation criteria

- [x] A folded blade's pixels track the desk gradient behind it, at rest and on every fold frame - unit tests `T2505: on glass the strip is the card's own sheet` (every pixel == the pane's own glassMix at GLASS_TINT, a teal-to-navy desk step stays >50 levels apart) and `fillGlass` (the fold face shares the same LUT); on box `pane-stack-strip.ps1 -Glass` ALL PASS (36): blades read rgb(33,58,80) over desk rgb(27,68,96) where the old opaque blade read rgb(25,28,33), each predicted to 1 level from the desk over its own column
- [x] The blade is edged with the card's rim and nothing else - unit test `T2505: a glass strip is edged with the card's rim`, plus a pixel-for-pixel check that the edge-only fast path loses nothing
- [x] Frame cost does not meaningfully rise - ReleaseFast bench of four 44x1350 blades: 301 us -> 319 us per frame (+17 us, ~0.1% of a frame); the fold face is one LUT lookup per pixel before and after
- [x] Still one atomic present - the band stays inside PaneDesk's single compose and blit (no new pass, no new window); stack-fold-slide, pane-stack-unfold, pane-stack-slide, blade-shadow, stack-collapse-drag ALL PASS on the due sweep
- [ ] Mac side-by-side at the same theme - NOT RUN (no Mac seat here); the numbers are Mac's own (GLASS_TINT 0.4 sheet, unfocused glass rim white 10% / black 8%, PaneStackTabFace isFilled=false in the card style)
- [ ] Live real-pointer chain-fold capture with no background-clear frame over a blade - NOT RUN (go.md: no windows on the user's desktop while they are present); the paint path is unchanged apart from the band's colour, and the T2485 D13 ordering fix stands
