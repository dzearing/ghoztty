# T2671 - After T2644's thread pools, a full-shape window (split + viewer) still leaves ~0.3 MB a window once the pools are warm

## In plain terms

Closing a window that had a split and a document viewer still keeps roughly a third of a megabyte. That is much less than before T2644, but it still adds up over a very long session.

## Summary

T2644 stopped every per-pane thread exit on Windows. With the NVIDIA GL driver, a thread that exits while any GL context is alive strands driver memory. After that fix, the release meter (`window-close-memory.ps1 -ExePath zig-out-relmem/bin/ghoztty.exe -ReleaseSandbox -Cycles 20 -Report`) reads a flat line for `-Shape single` (0.23 MB). The full shape reads 0.96 MB a window: 415 -> 430 MB over cycles 1-7 while the pools fill, then 430 -> 434 over cycles 7-20, about 0.3 MB a window.

Suspects, in order:
- threads the app does not create that still exit per window (WebView2 controller threads, ntdll pool workers). Each exit costs driver memory while a context lives.
- something the split path churns.

The guard's own verdict (debug build, 2 warm-ups, 5 measured cycles) still reads A1 1.53 MB and A8 1.20 MB a window. Part of that is the new pools filling up, because 2 warm-up cycles do not cover it. Do not raise `-Warmup` to make the guard pass until cycles 7-20 are flat.

Related: T2669 (the same driver cost for OS thread-pool workers) and T2673 (the guard was stamped from a diagnostic run, so `validate` no longer shows this red).

Bisect with `-Shape split` and `-Shape viewer`. Then run a cdb thread census (`-HeapCensusCommands '~*'`) at cycle 7 and at cycle 20 to name the threads that come and go. Repro and method: T2644's `## Where it stands`.

## Goals

- [x] name the threads a window cycle still creates and exits
- [x] stop the ones that are ours from exiting per window
- [x] hand what is left to tasks that own it

## Result (2026-11-07, lane b)

**Thread census.** A poller read every app thread's Win32 start address (`NtQueryInformationThread` class 9) during the release-sandbox meter and resolved it to module + offset, and `cdb -z` on the pdb disassembled the `entryFn`s. Per full-shape window the app exited:

- three threads of its own, all from the viewer pane: the file watcher's `ReadDirectoryChangesW` loop (`viewer_watcher.zig`), the worktree probe worker (`ViewerWorktreeProbe.zig`, three `git_run.capture` calls), and the `git` deadline watchdog that `capture` starts (`git_run.zig`);
- one WebView2 thread (`EmbeddedBrowserWebView.dll`), which is not ours;
- about 110 NVIDIA D3D driver threads (`nvwgf2umx.dll`), 55 per terminal pane, from the D3D11 device each composition-present pane creates. **Not the residue**: with `GHOZTTY_COMP_PRESENT=0` all of them are gone and private bytes behave the same. They also do not seem to pay the 64 KB attach cost.

**Fix.** `src/apprt/win32/worker_pool.zig`: one `reusable_thread` pool (T2644's) for the viewer's workers. The watcher, the worktree probe, the diff probe (same shape) and the `git` deadline now run on parked threads, so no viewer thread of ours exits per window. A re-run census shows only the WebView2 thread and a few ntdll pool workers coming and going.

**Measured (release sandbox, `zig-out-relmem` vs `zig-out-relbase` built from the same HEAD without the change):**

| run | before | after |
|---|---|---|
| viewer shape, 4 warm-ups, 30 cycles: per closed window | 0.42 MB (cycles 5-30 +3.4 MB) | **0.19 MB** (cycles 5-30 -2.1 MB, flat) |
| full shape, 20 cycles: cycles 7-20 slope | 0.05 MB/window | 0.15 and 0.12 MB/window (two runs) |

The full shape's cycles 7-20 slope is at the meter's noise floor (single samples move +-2 MB) in both builds, so it cannot separate a 0.2 MB/window effect. The viewer A/B can. What is left:

- **A8**: GPU dedicated memory grows ~1 MB a closed window after cycle ~6, in both builds, and is flat with `GHOZTTY_COMP_PRESENT=0`. That is the composition present's strand, T2606, re-triaged P1 now that the path is the default.
- **A1 on the 10-cycle debug verdict (1.76 MB)**: almost all of it is a fill over the first ~5 measured cycles that then stops, in every build. Filed as T2782, which now owns the guard's red.
