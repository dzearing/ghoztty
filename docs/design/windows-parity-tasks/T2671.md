# T2671 - After T2644's thread pools, a full-shape window (split + viewer) still leaves ~0.3 MB a window once the pools are warm

## In plain terms

Closing a window that had a split and a document viewer still keeps roughly a third of a megabyte. That is much less than before T2644, but it still adds up over a very long session.

## Summary

T2644 stopped every per-pane thread exit on Windows. With the NVIDIA GL driver, a thread that exits while any GL context is alive strands driver memory. After that fix, the release meter (`window-close-memory.ps1 -ExePath zig-out-relmem/bin/ghoztty.exe -ReleaseSandbox -Cycles 20 -Report`) reads a flat line for `-Shape single` (0.23 MB). The full shape reads 0.96 MB a window: 415 -> 430 MB over cycles 1-7 while the pools fill, then 430 -> 434 over cycles 7-20, about 0.3 MB a window.

Suspects, in order:
- threads the app does not create that still exit per window (WebView2 controller threads, ntdll pool workers). Each exit costs driver memory while a context lives.
- something the split path churns.

The guard's own verdict (debug build, 2 warm-ups, 5 measured cycles) still reads A1 1.53 MB and A8 1.20 MB a window. Part of that is the new pools filling up, because 2 warm-up cycles do not cover it. Do not raise `-Warmup` to make the guard pass until cycles 7-20 are flat.

Related: T2669 (the same driver cost for OS thread-pool workers) and T2673 (the guard was stamped from a diagnostic run, so `validate` no longer shows this red).

Bisect with `-Shape split` and `-Shape viewer`. Then run a cdb thread census (`-HeapCensusCommands '~*'`) at cycle 7 and at cycle 20 to name the threads that come and go. Repro and method: T2644's `## Where it stands`.

## Validation criteria
