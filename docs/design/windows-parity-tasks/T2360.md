# T2360 - Move Windows animation and presentation onto Windows.UI.Composition, the Windows counterpart of Mac's CoreAnimation: compositor-driven animations at the display's refresh (120 Hz here) for every glide, fade and shadow; terminal panes as swap-chain visuals; chrome as composition visuals. The current hand-stepped GDI + per-HWND WGL + layered-popup stack cannot be smooth

## Summary

User, 2026-10-27: "windows has more than win32 gdi apis to paint. we have
directx, opengl, webassembly, winfx... even web ux has standard smooth
animation support. and i think my display is 120mhz". Also: "it doesn't
smoothly glide like a video game smooth 60fps. it stutters and jitters".

The user is right. The jank is not a limit of Windows; it comes from the
stack this port picked.

### What Mac does

Every card is a CALayer. `PaneStage` glides by setting layer frames inside
one `CATransaction`. Settles and fades are `CABasicAnimation`s that the
WindowServer runs on its own clock at the display's refresh. The app's main
thread does not draw the motion.

### What Windows does (checked in src/ on 2026-10-27)

- Terminal panes are child HWNDs, each with its own WGL context and
  `SwapBuffers` (Surface.zig ~L1267). There is no DXGI, DirectComposition,
  Windows.UI.Composition or Direct2D anywhere in src/. WebView2 is used only
  in the viewers.
- Chrome (sidebar, strips, desk, shadows, dividers) is GDI, repainted on
  the UI thread.
- The scrollbar, dim overlay, bell border and banner are separate
  `WS_EX_LAYERED` popups per pane, moved one at a time.
- Every animation is hand-stepped on the UI thread by a 16 ms `SetTimer`.
  Measured on the user's box, that fires at ~39 fps (T2365). DWM reports
  the display at 120.00 Hz (`DwmGetCompositionTimingInfo`; two LG panels).
  So glides update on about one refresh in three, and a busy UI thread
  makes it worse.

There is no atomic commit across HWNDs and no animation the OS runs for us.
Every frame is N presents plus M window moves plus GDI repaints, which is
what T1031/T1343/T1393/T1476 keep patching.

### Decision (technical, recorded per the decisions rule)

Use **Windows.UI.Composition** (the Visual Layer under WinUI/XAML), hosted
in our plain Win32 windows through `ICompositorDesktopInterop` /
`CreateDesktopWindowTarget`, with a `DispatcherQueueController` on the UI
thread. No XAML and no WinUI dependency.

Why this and not the others:
- **Windows.UI.Composition: chosen.** It is the closest match to
  CoreAnimation. The compositor runs keyframe, expression and implicit
  animations off our thread at the panel's refresh (120 Hz here), with easing.
  It has `DropShadow` (blade shadows), clips, opacity and scale, and one
  batch commit across all visuals. Windows Terminal's UI animations sit on
  this layer. It is callable from Zig as raw COM/WinRT vtables, the same way
  `com.zig` already reaches WebView2.
- **DirectComposition only:** the same atomic commit, but its animation
  objects are piecewise cubics with no easing curves, implicit animations or
  shadows. That is the fallback if the WinRT layer is not available.
- **Direct3D/OpenGL alone:** this solves pixels, not motion. We would still
  hand-step every frame. It is needed for terminal content either way.
- **Web UI (WebView2/CSS):** CSS transitions are compositor-driven and smooth,
  but hosting every window's chrome in Chromium costs memory and input
  latency per window, and the terminal is not a web surface. Keep web for
  the viewers.

### Shape of the work (split into tasks after the spike)

1. Spike: one window with a composition target. Make the desk, cards and
   strips SpriteVisuals, and a blade collapse a compositor animation (offset
   + size, ease). Measure frame intervals with `DwmGetCompositionTimingInfo`
   / PresentMon: every interval should be 8.3 ms at 120 Hz, none missed.
2. Terminal content: present each pane into a DXGI flip-model swap chain
   (D3D11, or GL through `WGL_NV_DX_interop2` as a bridge), hosted with
   `ICompositorInterop::CreateCompositionSurfaceForSwapChain`. During a
   glide, the pane's content visual animates while its grid stays held,
   the same as Mac's `paneContentFreeze`, which T2102 already ported.
3. Replace the layered popups (scrollbar, dim, bell border, banner) with child
   visuals of the pane's visual.
4. Chrome painting: Direct2D into `CompositionDrawingSurface`s, or plain
   composition primitives where they fit.
5. Port each hand-stepped animation (T2365's list) onto compositor animations.

Platform symmetry: Mac already has the CoreAnimation model, so this is
Windows-only work to reach parity, and the user-visible behavior stays
identical.
