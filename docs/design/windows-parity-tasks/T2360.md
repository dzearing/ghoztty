# T2360 - Move Windows animation and presentation onto Windows.UI.Composition, the Windows counterpart of Mac's CoreAnimation: compositor-driven animations at the display's refresh (120 Hz here) for every glide, fade and shadow; terminal panes as swap-chain visuals; chrome as composition visuals. The current hand-stepped GDI + per-HWND WGL + layered-popup stack cannot be smooth

## Summary

User, 2026-10-27: "windows has more than win32 gdi apis to paint. we have
directx, opengl, webassembly, winfx... even web ux has standard smooth
animation support. and i think my display is 120mhz". Also: "it doesn't
smoothly glide like a video game smooth 60fps. it stutters and jitters".

The user is right. The jank is not a limit of Windows; it comes from the
stack this port picked.

### What Mac does

Every card is a CALayer. `PaneStage` glides by setting layer frames inside
one `CATransaction`. Settles and fades are `CABasicAnimation`s that the
WindowServer runs on its own clock at the display's refresh. The app's main
thread does not draw the motion.

### What Windows does (checked in src/ on 2026-10-27)

- Terminal panes are child HWNDs, each with its own WGL context and
  `SwapBuffers` (Surface.zig ~L1267). There is no DXGI, DirectComposition,
  Windows.UI.Composition or Direct2D anywhere in src/. WebView2 is used only
  in the viewers.
- Chrome (sidebar, strips, desk, shadows, dividers) is GDI, repainted on
  the UI thread.
- The scrollbar, dim overlay, bell border and banner are separate
  `WS_EX_LAYERED` popups per pane, moved one at a time.
- Every animation is hand-stepped on the UI thread by a 16 ms `SetTimer`.
  Measured on the user's box, that fires at ~39 fps (T2365). DWM reports
  the display at 120.00 Hz (`DwmGetCompositionTimingInfo`; two LG panels).
  So glides update on about one refresh in three, and a busy UI thread
  makes it worse.

There is no atomic commit across HWNDs and no animation the OS runs for us.
Every frame is N presents plus M window moves plus GDI repaints, which is
what T1031/T1343/T1393/T1476 keep patching.

### Decision (technical, recorded per the decisions rule)

Use **Windows.UI.Composition** (the Visual Layer under WinUI/XAML), hosted
in our plain Win32 windows through `ICompositorDesktopInterop` /
`CreateDesktopWindowTarget`, with a `DispatcherQueueController` on the UI
thread. No XAML and no WinUI dependency.

Why this and not the others:
- **Windows.UI.Composition: chosen.** It is the closest match to
  CoreAnimation. The compositor runs keyframe, expression and implicit
  animations off our thread at the panel's refresh (120 Hz here), with easing.
  It has `DropShadow` (blade shadows), clips, opacity and scale, and one
  batch commit across all visuals. Windows Terminal's UI animations sit on
  this layer. It is callable from Zig as raw COM/WinRT vtables, the same way
  `com.zig` already reaches WebView2.
- **DirectComposition only:** the same atomic commit, but its animation
  objects are piecewise cubics with no easing curves, implicit animations or
  shadows. That is the fallback if the WinRT layer is not available.
- **Direct3D/OpenGL alone:** this solves pixels, not motion. We would still
  hand-step every frame. It is needed for terminal content either way.
- **Web UI (WebView2/CSS):** CSS transitions are compositor-driven and smooth,
  but hosting every window's chrome in Chromium costs memory and input
  latency per window, and the terminal is not a web surface. Keep web for
  the viewers.

### Hard constraint: Remote Desktop and no-GPU machines must keep working

User, 2026-10-27: "i do need this to work over terminal server still" / "so
things like directx might not work on low end hardware or no gpu cases".

How it works today (checked in src/): a Remote Desktop session or a VM
without a GPU offers only OpenGL 1.1, so the GL renderer cannot run there
on its own (startup_error.zig, T1224). It survives because we ship Mesa's
`opengl32.dll`, which turns OpenGL into Direct3D 12 drawn by **WARP**, the
CPU rasterizer built into every Windows install (Surface.zig ~L1294, T1251,
T1951). So the no-GPU path already runs on DirectX, through an extra
translation layer.

Requirements for the composition path:
- **D3D11 device: hardware first, then WARP** (`D3D_DRIVER_TYPE_WARP`). Never
  fail to start because there is no GPU. WARP is in the OS, so this drops the
  GL to D3D12 translation from the no-GPU path instead of adding a dependency.
- **Device loss** (`DXGI_ERROR_DEVICE_REMOVED`/`RESET`): recreate the device
  and every swap chain/drawing surface. Remote Desktop connect/disconnect and
  driver updates swap the adapter under a running app. Hook this to the
  `WM_WTSSESSION_CHANGE` handling remote_session.zig already registers.
- **Composition over RDP**: DWM composes in every session since Windows 8.
  Over RDP, visuals and animations are composed on the host and the result is
  encoded, with the frame rate set by the RDP client and link (typically
  30-60). 120 Hz is a local-display property; over RDP the goal is "no worse
  than today and no stutter beyond what the link imposes".
- **Keep T1951's remote motion policy** (in-window motion off while remote,
  unless the user opts in). Re-measure it on the new path; compositor
  animations should be far cheaper over RDP than GDI repaints.
- **Fallback chain**, chosen at runtime and logged:
  1. Windows.UI.Composition (desktop interop needs Win10 1803+)
  2. DirectComposition (Win8+)
  3. today's HWND/WGL path, which stays until 1 and 2 are proven everywhere.
  The Mesa bundle can only be retired once the D3D renderer covers every case
  it covers.

### Requirement: motion never waits on the UI thread

User, 2026-10-27: "we might want to run on an independent animation thread
as well so that painting is not blocked by stutters in the process execution".

Today every glide step is a UI-thread message, so any stall on that thread
(IPC handling, a big layout pass, a GC-like burst, a modal loop) freezes the
motion. T2365's frame clock is still delivered to the UI thread, so it has
the same exposure. The design must cut that link at three levels:

1. **Declared animations run outside our process.** A Windows.UI.Composition
   keyframe or implicit animation, once started, is ticked by DWM. A 200 ms
   stall in Ghoztty does not drop a frame of it. Prefer this for every
   glide, fade, settle and shadow: the UI thread says where things end up,
   not each frame.
2. **Pointer-driven motion (divider/sidebar/drag-to-collapse) goes through
   expression animations bound to a `CompositionPropertySet`.** Input writes
   one property, and the compositor derives every card's offset/size from it
   each frame, so the rest of the frame needs no per-move layout on the UI
   thread.
3. **A dedicated composition/animation thread** owns the Compositor (its own
   `DispatcherQueueController`, `DQTAT_COM_STA`, created by
   `CreateDispatcherQueueController` on that thread), builds and commits the
   visual tree, and receives layout intents from the UI thread through a
   lock-free queue. The UI thread keeps the HWNDs, input and IPC. Verify in the
   spike that a desktop window target can be created by a Compositor living
   on a thread other than the HWND's owner. If it cannot, use DirectComposition
   there instead (its device commits from any thread), or keep the Compositor on
   the UI thread and rely on 1 and 2.

Terminal content already renders on per-surface renderer threads. During a
glide each pane's swap-chain visual is moved and clipped by the compositor
while its grid size is held (T2102), so no renderer has to keep up with the
motion.

### Shape of the work (split into tasks after the spike)

1. Spike: one window with a composition target. Make the desk, cards and
   strips SpriteVisuals, and a blade collapse a compositor animation (offset
   + size, ease). Measure frame intervals with `DwmGetCompositionTimingInfo`
   / PresentMon: every interval should be 8.3 ms at 120 Hz, none missed.
2. Terminal content: present each pane into a DXGI flip-model swap chain
   (D3D11, or GL through `WGL_NV_DX_interop2` as a bridge), hosted with
   `ICompositorInterop::CreateCompositionSurfaceForSwapChain`. During a
   glide, the pane's content visual animates while its grid stays held,
   the same as Mac's `paneContentFreeze`, which T2102 already ported.
3. Replace the layered popups (scrollbar, dim, bell border, banner) with child
   visuals of the pane's visual.
4. Chrome painting: Direct2D into `CompositionDrawingSurface`s, or plain
   composition primitives where they fit.
5. Port each hand-stepped animation (T2365's list) onto compositor animations.

Platform symmetry: Mac already has the CoreAnimation model, so this is
Windows-only work to reach parity, and the user-visible behavior stays
identical.

## In plain terms

Sliding panels and collapsing sidebars on Windows stutter where the Mac
glides, because every frame of motion is drawn by hand by the app itself.
This moves that motion onto the system compositor, the way the Mac does it,
so a glide stays smooth even when the app is busy. Anyone who drags,
collapses or rearranges panes on a high-refresh display notices.

## Spike report (2026-10-29, lane A)

Built: `zig build comp-spike -Dapp-runtime=win32 -Doptimize=Debug` produces
`zig-out\bin\ghoztty-comp-spike.exe` (`src\comp_spike_main.zig`). The WinRT
bindings live where the app will use them, `src\apprt\win32\winrt_comp.zig`;
every vtable slot and IID was checked against the 10.0.22621.0 SDK headers.
Runner: `scripts\comp-spike.ps1` (background test desktop). Unit tests:
`zig test src\comp_spike_main.zig -lc -luser32 -lgdi32`, 9/9 pass.

What the background-desktop runs established:

- **The composition path works on this box.** RoInitialize, DispatcherQueue,
  Compositor, `CreateDesktopWindowTarget`, sprite visuals, and the
  keyframe animations on Size/Offset all succeeded. Every glide was one
  declaration and 0 UI-thread steps.
- **The open design question is answered: yes.** A Compositor on its own
  thread, with its own DispatcherQueue, created a desktop target for an HWND
  owned by the UI thread (`--thread=worker`: target_hr=0x0, ui_tid 33316,
  worker_tid 32016), and its glides started without error. Level 3 of
  "motion never waits on the UI thread" needs no DirectComposition fallback
  for target creation.
- **Today's path is confirmed at 40 fps.** The hand-stepped glide made 12 steps
  in 300 ms, which is one refresh in three at 120 Hz (T2365 measured ~39). With
  a 500 ms UI stall injected halfway through, it made 7 steps: the motion froze
  for the second half, then snapped to the end.
- **NOT MEASURED: frame cadence on screen.** There are two reasons, and both are
  now tasks:
  1. `DwmGetCompositionTimingInfo` is useless as an oracle on this Windows
     build. A raw dump shows `cRefresh` and `cFrame` advance by 1 per *call*,
     with `qpcCompose` equal to the latest vblank, so a poller counts its own
     polls. The spike reads DComp frame statistics instead
     (`DCompositionGetFrameId`/`DCompositionGetStatistics`), which are real:
     120.00 Hz, 8.333 ms.
  2. That clock is system-wide, and the user's desktop composes on every
     refresh. The `idle` mode, with nothing animating, scores advance 1.000,
     the same as gdi and comp. A background desktop is never composed anyway.
     The cadence has to be scored per window, from captured frames (T2463),
     and live on the input desktop when the box is idle (T2464).
- RDP and no-GPU runs: NOT RUN (criterion 3, T2465).
