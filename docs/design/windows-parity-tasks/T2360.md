# T2360 - Spike: present win32 panes through DXGI flip-model swap chains on one DirectComposition tree (Mac: Metal layers in one CoreAnimation transaction) so a relayout commits every pane and overlay atomically, instead of per-HWND WGL/GDI presents plus layered-popup overlays moved one by one

## Summary

User question (2026-10-27): "are we using the wrong graphics tech" / "everything
feels slower than mac even on my maxed out pc".

What we have now (checked in the code 2026-10-27):

- Each terminal pane is its own child HWND with a WGL OpenGL context
  (`PFD_DOUBLEBUFFER | PFD_SUPPORT_COMPOSITION`, Surface.zig ~L1267), presented
  with `SwapBuffers` into a GDI redirection surface. There is no DXGI swap
  chain and no DirectComposition anywhere in src/.
- Chrome (sidebar, tab strip, caption, dividers, desk) is painted with GDI.
- The scrollbar, dim overlay, bell border and banner are separate
  `WS_EX_LAYERED` popups per pane, which every relayout has to move one by one.

Mac: Metal layers inside one CoreAnimation tree, so a resize lands in one
transaction and every pane and overlay moves in the same frame. Windows has
no atomic commit across HWNDs. Every relayout is N independent presents plus
M overlay moves, and the code holds that together with frame waits
(T1031, T1343, T1393, T1476). That is why resizes are fragile and why fast
hardware does not help: the cost is synchronization, not GPU work.

Spike: prototype a single DirectComposition visual tree per window
(`WS_EX_NOREDIRECTIONBITMAP`), with each pane as a DXGI flip-model swap
chain (D3D11, or GL through WGL_NV_DX_interop as a stepping stone) and the
overlays as DComp visuals instead of layered popups. Commit relayouts with
one `IDCompositionDevice::Commit`. Measure divider/sidebar/frame drag tick
cost and stale-frame count against the current path before deciding to
migrate. Note: upstream Ghostty has no D3D renderer, so this is
renderer-backend work in src/renderer, not only apprt.
