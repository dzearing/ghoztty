# T1350 - Each pane owns five separate layered popups; collapse them into one piece of chrome per pane

## In plain terms

Everything the app draws over a pane - the banner strip, the dim wash over
unfocused panes, the scrollbar, the read-only badge, the key-state pill - is a
separate little window. Windows has to move and composite each one every time
the pane moves, so a splitter drag with eight panes is Windows moving nineteen
windows for every twitch of the mouse. The Mac draws all of that into one layer
tree and moves nothing. This is about drawing the same chrome with fewer
windows.

## Where this came from

T1345 counted the fan-out and deleted the redundant half of it: a scrollbar that
repositioned twice per move, a z-order walk per reposition, a layered blit of a
bitmap that had not changed. What it did NOT touch is the design itself, and the
number it left behind is the honest one:

At 8 panes, one mouse move, on this box (`test\win32\drag-perf.ps1`):

- 15.5 ms per move, of which 9.1 ms is pane placement and 2.7 ms is
  repositioning the washes.
- 19 window repositions: 8 panes + 11 chrome popups.
- 0 layered blits, 0 z-order walks - those are gone.

So the remaining bill is the window manager moving windows, and the only lever
left is moving fewer of them.

## The shape to consider

One `WS_EX_LAYERED` popup per pane, owner-painted, carrying every piece of
chrome that pane needs as regions inside it, instead of one popup per piece.
That takes 11 chrome moves at 8 panes down to at most 8, and each survivor
composites once rather than up to five times.

The constraint that produced the current design is real and must survive: a
plain child window cannot reliably sit above the OpenGL surface, which is why
the chrome is layered popups at all. A single popup per pane keeps that
property; it is a consolidation, not a change of mechanism.

Open questions the work has to answer rather than assume:

- The pieces have different alpha models today - the dim wash is uniform
  (`SetLayeredWindowAttributes`), the scrollbar and the badges are per-pixel
  (`UpdateLayeredWindow`). One window means one model, and it has to be the
  per-pixel one, which makes the wash a full-pane bitmap blit instead of a
  free constant. Measure whether that trade is a win before committing to it.
- The banner strip sits ABOVE the pane rect (the layout reserves a band for
  it), so a per-pane chrome window is not the pane rect - it is the pane rect
  plus the band.
- Hit-testing: the scrollbar takes the mouse, the wash is
  `WS_EX_TRANSPARENT`, the banner has links. One window means one `WM_NCHITTEST`
  that has to answer per region.

## Goals

## Outcome (2026-10-24): a measured no

The premise had moved under the task. When it was filed, an 8-pane drag moved
19 windows per mouse move (8 panes + 11 chrome popups). Today the harness drag
resizes 3 panes and moves **4** chrome popups (2 scrollbars, 2 dim washes),
because T1345's placement cache and the layout work since leave everything
else where it was.

The counts said nothing about cost, so this task added a clock to the moves
(`chrome_fanout.startMoveClock`/`stopMoveClock` around every chrome
`SetWindowPos`, plus the `EndDeferWindowPos` that lands the batched washes),
carried as `mean_chrome_move_us` on the drag line and printed by
`drag-perf.ps1` with a new section E.

At 8 panes, batched, on this box (the user had a GPU-heavy game running, so
the absolute numbers run high):

- whole mouse move 41582 us; paint 21702 us; place 8941 us; overlay 6635 us
- chrome moves: 4, costing **3092 us** together
- the green run that stamped the harness: move 30522 us, chrome moves 2970 us
- one popup per pane could still not move fewer than 2 windows (a pane owns
  at most one popup of each kind), so the **most** it could save is about
  1.5 ms: 1485 us of 30522 us, 4.9% of the move (`drag-perf.ps1` section E
  prints this ceiling every run)

And that ceiling is before the cost the design adds: one window means one
alpha model, the per-pixel one, so the dim wash stops being a free constant
(`SetLayeredWindowAttributes`) and becomes a full-pane bitmap blit - on every
tick of a drag, because a resized popup can never skip its blit. Three
pane-sized BGRA blits per move is the same order as the 1.5 ms it would save,
and the change would rewrite five popup modules' z-order, hit-testing and
hero/tab/DPI handling, which is the riskiest code in the chrome.

So the consolidation is not worth doing. What the clock did find is worth
chasing instead: about **770 us per popup move** is far too much for one
window move, and making each move cheap would save most of the 3 ms rather
than half of it. Filed:

- T2239 - why one overlay popup move costs ~770 us (the real lever here)
- T2240 - drag-perf prints the 2-pane row twice and never measures 4 panes
- T2241 - the 8-pane batched drag misses the two-frame budget, with paint at
  ~21 ms; re-measure on an idle box before calling it a regression
