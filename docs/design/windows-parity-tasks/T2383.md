# T2383 - Deterministic scene + positive-control knobs for the T2373 lab: a per-pane test card (pane-unique SGR background, 1-cell border ring, large ID glyph, optional heavy-output mode) and debug env knobs that plant a one-frame magenta erase, one stale-size present, and a layered overlay held one frame behind

## Summary

Split out of T2373 (user-directed 2026-10-27: no bleeding during window/pane resize; smoothness measured). See T2373's Summary for the full design; this card is one piece of it.

## In plain terms

To check by machine whether a resize "bleeds", every pixel on screen has to
be predictable. So each pane in a lab run shows a test card: a solid colour
unique to that pane, a one-cell border in a second colour, and a big ID digit
in a third. A pane showing the wrong size, a flash of background or a stretched
old frame then shows up as pixels in the wrong place. The lab also needs proof
that it notices a defect, so the app can now be told to make three deliberate
one-frame mistakes: a magenta flash, one frame at the old size, and a dimming
overlay that trails its pane for a refresh.

## Goals

- [x] Test card: pane-unique palette (9 cards), 1-cell ring, large fixed-size ID glyph, all drawn as exact cell backgrounds (no antialiasing)
- [x] Busy mode: changing text every tick for a renderer-busy drag, with no pixel outside the palette
- [x] The scorer's region for a card (`New-FrameLabCardRegion`), from the same layout rule the card draws with
- [x] `GHOZTTY_LAB_PLANT=erase@n,stale@n,overlay@n`: magenta frame, stale-size frame, dim wash held one refresh, each logged with a QPC timestamp
- [x] Acceptance harness + guard row

## Design notes

- **Where the plants live.** `src/apprt/win32/lab_plant.zig` (pure parser and
  fire rule, unit tested in every lane; loaded once in `App.init` before any
  renderer thread). `erase`/`stale` count a pane's renderer frames that found
  it at a new size (`Surface.labPlantOnFrame`, renderer thread only), so
  `erase@12` is "this pane's twelfth resize frame" whatever the drag speed.
  `stale` skips the size update in `renderer/generic.zig` for that one frame,
  so the old target is presented into the resized window. `erase` draws the
  frame as usual and `OpenGL.present` clears the window to magenta instead of
  blitting it. `overlay` holds the dim wash's n-th move
  (`DimOverlay.show`) for two frame-clock ticks, so it lags its pane for at
  least one whole refresh, then catches up to wherever the pane is.
- **Every build, not Debug-only** (my call, mechanism-only): the controls are
  only evidence about the binary they ran on, and the lab measures smoothness
  on release builds. Cost with the variable unset: one load of an all-zero
  struct per resize frame and per wash move, the `GHOZTTY_PRESENT_LAG_MS`
  shape.
- **The dim wash, not the scrollbar, is the B5 target**: it is on screen for
  every unfocused pane at default config, where the overlay scrollbar fades
  out after a second idle.
- **Busy text is Bg-on-Bg.** It was ring-coloured first; the real capture
  showed the renderer blends glyph edges in linear light, off the straight
  sRGB line FrameScore's B6 rule accepts (14,039 false garbage pixels). Same
  renderer work, no off-palette pixel. The scorer gap itself is T2388.
