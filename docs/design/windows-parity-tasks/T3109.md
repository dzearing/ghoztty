# T3109 - Closing a window from the CLI can leave it standing on Windows: +close on the last pane must never put up a confirmation, and a closed window must leave +list and name lookup and release its shells (Mac 4bcf59873, be50bda8b)

## Summary

Mac 4bcf59873: closing the last pane with no confirmation fell through to the menu close action, which confirmed on its own terms, so the CLI put up "Close Window?" with nobody to answer it; and a closed window whose controller was still held stayed in the window list, so +list kept reporting it and its shells kept running. Now the window is marked closed at close, listings/name lookup/in-a-window checks leave it out, and be50bda8b releases its terminals if it is still alive 2 s after the undo window expires. On Windows (T2938 ported +close --force): verify +close without --force on a window's LAST pane and on a whole window never shows a confirm dialog when invoked from the CLI, that +list/+split --target by name never resolve a closed (undo-pending) window, and that its shells end once undo expires. Validation: acceptance case closes a one-pane window via +close while the shell runs a child - no dialog, +list omits it at once, the child process is gone after the undo window.

## In plain terms

On the Mac, a script that closed a window's last pane could leave a "Close
Window?" question on screen that nobody was there to answer, and a closed
window could linger in the window list with its programs still running.
This checks the Windows build never does either, and adds a test that would
catch it if it ever started.

## Goals

- [x] Confirm from the code whether Windows has the Mac defect
- [x] An acceptance case for a last-pane close with a command running
- [x] The same for the last window, which closes at once

## Findings

Windows does not have the Mac defect, by construction (read 2026-11-15):
the IPC `+close` handler (`IpcHandlers.handleClose`) calls
`Window.closeSplitPane` / `Window.close` directly. The only confirmation is
`confirmCloseIfNeededOpts`, reached from WM_CLOSE (title-bar X, Alt+F4) and
the `close_window` chord, never from these calls. A last pane goes
`closeTab` -> `closeTabByIndex`: it either parks the whole window for the
undo (`CloseUndo.parkWindow`, which takes it out of `App.windows` and moves
its IPC names out of the registry, so `+list` and name lookup drop it at
once), or - for the last window - removes the slot and posts WM_CLOSE with
`tab_count == 0`, so the confirmation has no pane to ask about. Undo expiry
runs `closeNow`, which ends every session. So the task's deliverable is the
test.
