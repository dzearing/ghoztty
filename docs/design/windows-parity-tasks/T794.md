# T794 - A test script's .Count on a helper's return is vacuous when the helper returns one element (PS 5.1 unrolls it)

## In plain terms

Some of our automated checks compare "how many windows were there before" with
"how many after". When there is exactly one window, PowerShell hands the count
back as nothing at all — so the check compares nothing to nothing, passes, and
would keep passing no matter what the product did. Nobody can see this by
reading the line; it looks like ordinary arithmetic.

## Summary

Found while writing `test\win32\chooser-open-chord.ps1` (T746). The script's

```powershell
function Get-TopWindows($procId) { return @(Get-TestWindows ... ) }
...
$before = (Get-TopWindows $g.Pid).Count
```

printed `( -> )` on both of its "and no plain terminal window was opened
instead" assertions: PowerShell 5.1 **unrolls a one-element array on return**,
so the caller gets a scalar `PSCustomObject`, `.Count` is `$null`, and
`$null -eq $null` passes. The first run of that script scored two assertions
green that could not have gone red. Fixed there by re-wrapping at the call
site (`@(Get-TopWindows …).Count`), which is the only reliable spelling — the
`@()` INSIDE the function does not survive the return.

This is the same family as **T271** (a run that asserted nothing) and **T791**
(a negative control that inverts nothing): an assertion that cannot fail is
indistinguishable from one that passed. What makes this one worth a sweep is
that it is invisible on the page — the line reads like a normal count
comparison, and it only misbehaves for the one-element case, which is
precisely the common case for "how many windows does this app have".

## Details

Scope: every `test\win32\*.ps1` and `scripts\*.ps1` site that reads `.Count`
(or indexes) off the return of a locally-defined helper, rather than off an
`@()`-wrapped expression at the point of use. `Get-TestWindows`,
`Get-TestChildWindows` and their wrappers are the likely population.

Candidate shape for a static analyzer, in the family of `ExitCodeAudit` /
`SkipAudit` / `VerdictExitAudit`: AST-walk for a `MemberExpression` naming
`Count` whose target is a `CommandExpression` invoking a function defined in
the same file whose `return`/output is an array. Report at zero, with the same
`# count-audit: <reason>` stated-intent exemption the sibling audits use.

Cheaper first cut, if the analyzer proves noisy: sweep by hand once, fix the
sites, and add the rule to the harness header where the other traps are
recorded so the next author meets it.

## Goals

- [x] the rule is machine-checked rather than remembered: an analyzer that
      names every unwrapped count in `test\win32\` and `scripts\`
- [x] it is STANDING - a guard row plus a harness-floor member, so a script
      edited today puts it due and `validate` refuses the commit until it is green
- [x] the sites in the harness-floor audits and their libs are fixed
- [x] the rest are frozen by a ratchet and owned by a filed task, not left as
      a number in a commit message

## Validation criteria

- [x] every `.Count`-on-a-helper-return site in `test\win32\` and `scripts\`
      either reads a genuinely-wrapped value, carries a stated-intent marker,
      or is recorded in `unroll-count-audit.baseline.json` where the ratchet
      holds it and T1617 works it down - verified by
      `test\win32\unroll-count-audit.ps1` (C1/C2/D2, 35 assertions ALL PASS
      with `-TeethCheck`)
- [x] a teeth-check plants a real vacuous site and the sweep finds it -
      `-TeethCheck` sections T1-T4: a new file carrying both shapes, and a
      re-wounded copy of a file this run fixed
- [x] no existing green script turns red for a reason other than a real
      assertion that was previously vacuous (each one investigated, not
      silently re-wrapped) - and one DID: the first pass wrapped 84 sites and
      turned four green audits red, because `return , @(...)` does not unroll
      and wrapping such a call breaks it. The analyzer now excludes those; the
      12 fixed files run in `floor-lane.ps1 -Lane harness`, plus
      `window-composite.ps1` for the `lib\WindowComposite.ps1` site
