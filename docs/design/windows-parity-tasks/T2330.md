# T2330 - git-commit-guard commit cannot record a merge: its explicit pathspec makes git refuse a partial commit during a merge, so every main-merge task falls back to a hand hold/commit/release

## Summary

During T2325 (2026-10-27) `git-commit-guard.ps1 commit -Paths ...` on a `git merge --no-commit` of origin/main failed with `fatal: cannot do a partial commit during a merge.` - git refuses `git commit -- <pathspec>` while MERGE_HEAD exists, and the guard always commits with an explicit pathspec. The turn fell back to `hold` -> `$env:GHOZTTY_COMMIT_LOCK_KEY=<key>; git commit -F` -> `release -Key` -> `push`, which loses the guard's read-back check (that the commit holds only the requested paths) - exactly the protection a merge commit, which brings in many paths, needs most.

Fix: when MERGE_HEAD exists, have `commit` verify the index holds exactly the merge's paths plus the requested `-Paths` (nothing else staged, nothing requested left unstaged), commit WITHOUT a pathspec under the hold, then run the usual read-back against the requested set unioned with the merge's own diff, and push. Prove it in section W of `test\win32\go-loop-guard.ps1` with a scratch-repo merge, plus a negative control in which a stray staged path is refused.

## Validation criteria

- [ ] `git-commit-guard.ps1 commit` records a `--no-commit` merge plus extra tracker paths in one commit and pushes it.
- [ ] A stray staged path not in the merge or in -Paths is refused during a merge (negative control).
- [ ] go-loop-guard.ps1 ALL PASS.
