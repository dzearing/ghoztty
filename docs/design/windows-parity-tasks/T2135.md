# T2135 - Mac: PaneLayout records a divider's displayed ratio as a fraction of its frame while the engine reads ratios as shares of the pane sizes, so a tree that adopts it may shift nested boundaries by up to half a gutter

## Summary

Found in T2125 on Windows: pane_stack_layout (a port of PaneLayout.swift) lays a side-by-side row out from share = product of ratios over (extent - all gutters), but layoutChain recorded ratio = (centre - start)/extent. Adopting that tree (Mac: 'A divider drag starts from these') is not a no-op: each nested boundary moves by roughly g/2 - 2g*d/E. Windows fixed it by recording the share (left sizes / total sizes) and pinned it with 'a tree that adopts its displayed ratios lays out unchanged'. Verify on Mac whether a drag start or keyboard resize jumps a nested divider in the elevated style (10pt gap) and port the fix if so.
