# T2466 - Composition step 2: terminal pane content as a DXGI flip-model swap chain hosted in a composition visual (CreateCompositionSurfaceForSwapChain), grid held during glides like Mac paneContentFreeze

## Summary

T2360 step 2. D3D11 renderer or GL via WGL_NV_DX_interop2 as a bridge. Oracle: terminal-render acceptance green on the new path, and per-window capture shows 0 torn/blank frames across a 9-pane glide.

## In plain terms

Every terminal pane today hands its finished picture to Windows the old way,
through the window it lives in, which is part of why panes flash, tear or go
blank while they slide. This builds the new way: each pane draws into its own
GPU surface that the system compositor shows directly, the way the Mac shows
its panes. It is switched off by default until the on-screen checks prove it,
and anything that goes wrong drops the pane back to the old way instead of
breaking it.

## Goals

- [x] A pane can present through a DXGI flip-model composition swap chain (GL drawn into a D3D11 texture shared through WGL_NV_DX_interop2, copied to the back buffer, Present)
- [x] The swap chain is the content of a composition visual on the pane's window
- [x] Any failure (no interop extension, no D3D device, a failed present) falls back to SwapBuffers for that pane and says why in the log
- [x] A lost GL device on the new path rebuilds its chain (T1690's recovery)
- [ ] Proven on screen (right way up, no tear, no blank frame) and through a 9-pane glide, then made the default (T2488)
- [ ] Grid held during glides like Mac's paneContentFreeze, re-measured on this path (T2488)

## Design decision (technical, mine to make per go.md 5b)

**Hosting is DirectComposition on the pane's own window for this step, not
Windows.UI.Composition's `CreateCompositionSurfaceForSwapChain`.** Everything
here runs on the pane's renderer thread, which runs a libxev loop and pumps no
window messages. A WinRT Compositor commits its visual tree implicitly from its
DispatcherQueue's pump, so a tree built on that thread is never committed; a
DComp device commits explicitly from any thread. The swap chain is the
substantial part and is the same object either way: step 5 (T2469) wraps it with
`CreateCompositionSurfaceForSwapChain` when the pane's visual joins the window's
composition tree, and nothing above the hosting changes.

**An intermediate shared texture, copied into the back buffer, rather than
registering the back buffer with GL.** A flip-model chain rotates its buffers
on every Present and an interop registration names one resource for its life;
the copy is correct on every driver for one GPU copy per frame.
