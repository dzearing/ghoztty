# T1616 - The ProcSampler cpu_pct test still goes red on a loaded box, so a floor run can be red with a green codebase

## In plain terms

One of our tests measures how busy a thread is and expects the number to be
believable. It only gets a believable number when the machine has a core to
spare. Run the standing test floor while the box is doing anything else and the
test fails with nothing actually broken — so a red floor stops meaning "you
broke something", which is the one thing it has to mean.

## Summary

Found in T793's turn, running the standing floor. `floor-lane.ps1 -Lane all`
came back `agent#1=FAIL`, one test of 6024:

```
error: 'remote.agent.proc.test.ProcSampler: a genuinely busy thread reports a
        plausible per-core cpu_pct' failed
  D:\git\ghoztty\src\remote\agent\proc.zig:1010
    try testing.expect(mine.? >= expected / 2.0);
Build Summary: 5945/6024 tests passed; 78 skipped; 1 failed
```

It is the FLOOR assert that fell, not the T480 ceiling. Re-running the same
lane alone on a quiet box a few minutes later: `LANE agent PASS in 175s`. So
the codebase is green and the lane result was a function of what else the box
was doing — the T793 turn had just finished a GUI acceptance script, and the
lane's own automatic `alone` retry fires immediately afterwards, while that
teardown is still in flight, which is why the retry reproduced and a genuinely
quiet run did not.

**This is a recurrence, not a new defect.** [T480] closed exactly this
(`b0b2b7a56`, 2026-08-15) by making the assertion proportional: burn a measured
amount of CPU via `selfCpuNs`, then require the sampler to report at least half
of that burn spread over the outer window, on the reasoning that load shrinks
both sides together. It was soaked at the original contention condition —
`-Mode standalone -Runs 32 -Concurrency 32` — and failed 0 of 32. That soak is
the thing this failure contradicts, so the first job is to find the shape of
load the proportional form does NOT cancel out, rather than to widen the
margin.

One candidate worth measuring first: the proportional form cancels load that
scales `burned_ns` and `wall_ns` together, but the sampler's own window is a
different interval from the test's outer window, and the two are only
guaranteed to nest — not to be affected by a descheduling burst in the same
proportion. A burst that lands inside the sampler's window but outside most of
the burn would drag `mine` below the floor while leaving `expected` where it
was.

## Goals

- [ ] Reproduce deliberately, under a named load, rather than waiting for the
      floor to go red again
- [ ] Name which term of the proportional assert is the one load does not
      cancel, from measured numbers
- [ ] Fix it so the assert is load-independent, without weakening what the test
      exists to catch (a sampler reporting zero, negative, or over-reported
      per-core numbers)

## Validation criteria

- [ ] The failure is reproduced on demand under a described load — a
      `test-binary-soak.ps1` concurrency that makes it fail, quoted with its
      rate — so the fix has something to be measured against.
- [ ] The cause is named from numbers: which of `mine`, `burned_ns`, `wall_ns`
      moves under load and which does not.
- [ ] After the fix, the same soak that reproduced it runs 0 failures, AND the
      T480 soak condition (`-Mode standalone -Runs 32 -Concurrency 32`) is
      re-run at 0 failures, so this closure is not the one T480 already made.
- [ ] Negative control: a deliberately broken sampler (zero, and an inverted
      unit conversion) still fails the test — the load-independence must not
      have been bought by making the assert vacuous.
