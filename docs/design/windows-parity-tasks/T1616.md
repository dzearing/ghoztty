# T1616 - The ProcSampler cpu_pct test still goes red on a loaded box, so a floor run can be red with a green codebase

## In plain terms

One of our tests measures how busy a thread is and expects the number to be
believable. It only gets a believable number when the machine has a core to
spare. Run the standing test floor while the box is doing anything else and the
test fails with nothing actually broken — so a red floor stops meaning "you
broke something", which is the one thing it has to mean.

## Summary

Found in T793's turn, running the standing floor. `floor-lane.ps1 -Lane all`
came back `agent#1=FAIL`, one test of 6024:

```
error: 'remote.agent.proc.test.ProcSampler: a genuinely busy thread reports a
        plausible per-core cpu_pct' failed
  D:\git\ghoztty\src\remote\agent\proc.zig:1010
    try testing.expect(mine.? >= expected / 2.0);
Build Summary: 5945/6024 tests passed; 78 skipped; 1 failed
```

It is the FLOOR assert that fell, not the T480 ceiling. Re-running the same
lane alone on a quiet box a few minutes later: `LANE agent PASS in 175s`. So
the codebase is green and the lane result was a function of what else the box
was doing — the T793 turn had just finished a GUI acceptance script, and the
lane's own automatic `alone` retry fires immediately afterwards, while that
teardown is still in flight, which is why the retry reproduced and a genuinely
quiet run did not.

**This is a recurrence, not a new defect.** [T480] closed exactly this
(`b0b2b7a56`, 2026-08-15) by making the assertion proportional: burn a measured
amount of CPU via `selfCpuNs`, then require the sampler to report at least half
of that burn spread over the outer window, on the reasoning that load shrinks
both sides together. It was soaked at the original contention condition —
`-Mode standalone -Runs 32 -Concurrency 32` — and failed 0 of 32. That soak is
the thing this failure contradicts, so the first job is to find the shape of
load the proportional form does NOT cancel out, rather than to widen the
margin.

One candidate worth measuring first: the proportional form cancels load that
scales `burned_ns` and `wall_ns` together, but the sampler's own window is a
different interval from the test's outer window, and the two are only
guaranteed to nest — not to be affected by a descheduling burst in the same
proportion. A burst that lands inside the sampler's window but outside most of
the burn would drag `mine` below the floor while leaving `expected` where it
was.

## Resolution (2026-11-21): already fixed by ea426fdf7 (T1639)

**It was never load.** The red was the process table being cut at 512 rows,
which T1639 fixed the next day (`ea426fdf7`, 2026-09-17). Before that fix,
`sampleWindows` stopped walking the Toolhelp list at `default_limit` (512) in
OS order. This test binary is a new process, so it is listed near the end. On a
box at the edge of 512 processes (T1639 measured 498 visible in `Get-Process`
the next morning), a GUI script's teardown changes the count between the
test's two `sample()` calls. Our pid falls past the cut in the baseline sample
and back inside it in the second. That leaves no baseline, so `cpuForPid`
returns 0 and `mine` is non-null but 0.0. That is exactly the T1616 signature:
`mine != null` passed and the floor assert fell. It also explains why a retry
during the teardown reproduced it and a quiet re-run did not. The next morning
the same cut dropped our pid from BOTH samples, which is T1639's
`mine != null` red. Since `ea426fdf7` the walk runs to `max_enumerate` (8192)
and `selectMostInteresting` always keeps our own pid, so the cut can no longer
reach the baseline.

The proportional assert itself holds up under real CPU load, measured with a
probe print in the test, a standalone `zig test` build of it, and a
128-thread spinner (4x the box's 32 cores, Normal priority):

| condition | runs | fail | worst `mine`/`expected` |
|---|---|---|---|
| quiet | 5 | 0 | 0.98 |
| 64 spinning processes (2x cores) | 10 | 0 | 1.19 |
| 128 spinning threads (4x cores) | 12 | 0 | 1.15 |

Under load each `sample()` call's wall time grows from ~10 ms to 0.3-2.1 s, but
only `wall_ns` grows; `burned_ns` stays at 312-343 ms. The sampler's window
sits inside the outer window, so `mine` only moves AWAY from the floor (the
ratio goes up under load). The task's "a burst inside the sampler window"
candidate is real arithmetic but has the wrong sign. No load shape was found
that pulls `mine` toward `expected/2`, so the test needed no change.

## Goals

- [x] Reproduce deliberately rather than waiting for the floor to go red again.
      Reproduced by mechanism: clearing the sampler's baseline between the two
      samples (the state the pre-T1639 cut produced) gives `mine=0.0` and the
      floor assert at the same line, every run.
- [x] Name which term moves, from measured numbers. Under load only `wall_ns`
      moves, and it moves the safe way. The red came from `mine` collapsing to 0
      when the baseline was missing, not from any term of the proportion.
- [x] Load-independent without weakening the test. Already the case at HEAD;
      negative controls below.

## Validation criteria

- [x] Reproduced on demand. CPU load could not make it fail (0/27 above, so no
      load-based reproduction exists to quote). The real cause was reproduced
      deterministically: a probe build that clears `s.prev` before the second
      `sample()` gives `T1616PROBE mine=0.0`, failing at the floor assert
      (`proc.zig:1153` in the probe build), 1 failed. The same binary without
      the switch passes.
- [x] Cause named from numbers (table above): `burned_ns` stays at 312-343 ms
      under any load, `wall_ns` grows 10x-16x, and `mine` stays at 1.15x+ of
      `expected`. The failing value was `mine = 0`, from the missing baseline.
- [x] T480 soak condition re-run: `scripts\test-binary-soak.ps1 -Lane agent
      -Mode standalone -Runs 32 -Concurrency 32` -> `pass=32 fail=0 crash=0`.
- [x] Negative controls (probe builds of the Windows busy conversion, each run
      once): `*% 0` (zero sampler) -> `mine=0.0`, floor fails; `/ 100`
      (inverted unit) -> `mine=0.0`, floor fails; `*% 10000` (over-report)
      -> `mine=9706.8`, ceiling fails (`proc.zig:1167`). The assert is not
      vacuous.
