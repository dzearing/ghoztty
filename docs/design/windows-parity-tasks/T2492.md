# T2492 - Composition step 3c: the scrollbar becomes a child visual of the pane visual (T2467's host) instead of a WS_EX_LAYERED popup; hit testing stays on the pane HWND

## Summary

T2467's split, third client of the overlay visual host (after the bell border
and the dim wash, T2491). On a pane presenting through the composition swap
chain (`GHOZTTY_COMP_PRESENT=1`) the themed scrollbar is a child visual of the
pane's visual, not a WS_EX_LAYERED popup that every move, fold and divider drag
had to `SetWindowPos` along. Its mouse input now arrives on the pane window,
which offers it to the scrollbar first.

## In plain terms

The thin scrollbar on the right edge of a terminal pane used to be its own
little floating window, dragged along by hand every time the pane moved - so
during a fold or a divider drag it could trail its pane by a frame. On the new
drawing path it is part of the pane's own picture and moves with it for free.
Grabbing and dragging it still works exactly as before.

## Goals

- [x] On the composition path the scrollbar is a child visual at the pane's right edge, with no popup on screen
- [x] A pane move re-places nothing; only a resize moves the strip (one offset)
- [x] Clicks, drags and hover reach it through the pane window, with the same hit area the popup's pixels had (whole track in always-visible mode, only the visible thumb in overlay mode)
- [x] Knob off, or a pane whose chain failed: the popup exactly as before

## Design (technical, mine per go.md 5b)

- `comp_overlay.Layer.setOffset` (IDCompositionVisual SetOffsetX/Y float
  overloads, slots 4/6 - same overload order as SetTransform 7/8) places the
  strip; pixels are the popup's premultiplied rows (`drawBitmap`) uploaded with
  `setPixels`, gated by the same T1345 signature check.
- The popup HWND stays alive and hidden: it hosts the fade/idle timers and is
  the fallback when the tree is retracted (`WM_APP+44` -> `onTreeChanged`).
- Hit testing: `stripHit` reproduces what Windows did with the popup's
  per-pixel alpha (a fully transparent pixel passes the mouse through).
  `routeMouse` takes move/down/up/leave from the pane WndProc; a drag holds
  capture on the pane window, hover ends via TrackMouseEvent on the pane
  (new pane `WM_MOUSELEAVE` arm). Over the strip WM_SETCURSOR gives the arrow
  the popup's class cursor gave. A scrollbar press does not take focus, as the
  WS_EX_NOACTIVATE popup did not.

## Validation criteria

- [x] Unit tests for `stripHit` (strip bounds; always-visible track vs overlay lit thumb vs faded) - `Scrollbar.zig`, floor lanes.
- [x] Knob on: every pane's scrollbar goes up as a visual, no GhozttyScrollbar popup is visible, a window move re-shows nothing - G0-G3 of `test\win32\comp-present.ps1`, background test desktop.
- [x] Hit testing on the pane HWND: a press on the lit thumb posted to the PANE window starts a scrollbar drag that scrolls the view to offset 0; a click in the grid starts none - G4/G5 of `comp-present.ps1`.
- [x] Negative control: knob off, the scrollbar is its popup (visible GhozttyScrollbar windows, no visual line) - D3 of `comp-present.ps1`.
- [ ] NOT RUN: the on-screen pixels and a real-cursor drag. The test desktop is never composed by DWM (T2463) and real-cursor tests are opt-in while the user is present; the picture waits for T2488's input-desktop proof.
