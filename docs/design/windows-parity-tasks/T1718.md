# T1718 - A -LoadKind build soak's workers mostly fail their builds within a minute (OutOfMemory, clang exit 45/5/66), so the 'loaded' soak runs on failed builds rather than compiles

## Summary

T954 re-run 2026-09-24 (soak label t954-repro, D:\ghoztty-soak-load\t954-repro-20260924-014216): 8 build workers on a 32-core box all exited 1 on their first iteration in 56-82s; worker logs hold 4x 'error: OutOfMemory', clang exited with code 45 (14x), 5 (4x), 66 (2x), and 'failed to parse clang diagnostics: FileNotFound'. The summary still reported load=8:build and counted 4 of those failed builds as worker-crash, so a loaded-soak verdict overstates both its load and its crash count. Find the cause (8 unbounded -j32 cold builds contending for memory/temp, a shared TMP for clang diagnostic files, or the shared global cache) and bound it: cap per-worker -j, give each worker a private TMP, and have the summary separate a worker build FAILURE from a worker CRASH and say when the load was degraded.

## In plain terms

There is a tool that runs the test suite over and over while the machine is
kept busy compiling, to catch a rare crash. When it was asked for eight
compiling helpers, the helpers ran the machine out of memory and failed within
a minute - and the report still said "eight compiles of load" and even counted
four of those failures as crashes. After this, each helper is limited to its
share of the processors, and the report says plainly when the helpers' builds
failed instead of pretending they were load or crashes.

## Goals

- [x] find the cause - memory exhaustion: eight uncapped `zig build`s each defaulting to one job per processor (256 concurrent compiles on 32 cores); the logs hold `OutOfMemory`, `LLVM ERROR: out of memory`, `SystemResources` and `unable to update cache: Unexpected`
- [x] cap each worker's `-j` (processors / (workers + 1), `-LoadJobs` to override)
- [x] give each worker a private TMP/TEMP
- [x] report a failed worker build (`worker-fail=N`, `load-degraded`, a DEGRADED line naming each worker) apart from a crash
- [x] stop counting a compiler's exit code (clang 5/66, zig's compile child 9 after an OOM) as a test-binary crash - all four of the 2026-09-24 `worker-crash` hits were exactly that

## Validation criteria

- [x] The four false `worker-crash` hits are gone on the retained 2026-09-24 evidence: replaying `Get-CrashOccurrenceLine` over `Get-CrashCandidateLines` of each `D:\ghoztty-soak-load\t954-repro-20260924-014216\w*\worker.log` gives 0 hits (before: w1 code 9, w2 clang 5, w4/w7 clang 66).
- [x] `test\win32\test-binary-soak.ps1` covers the new behavior (classifier: clang 5 / clang 66 / wrapped code-9 compile are not crashes, a test exe's exit 3 still is, through the file path too; dry run: default `-j` cap and `-LoadJobs`; a failing load reads `worker-crash=0 worker-fail=N load-degraded` with a DEGRADED line per worker and a green measured round; private TMP; a crashed worker is not also degraded) - green via `acceptance-parallel.ps1 run`.
