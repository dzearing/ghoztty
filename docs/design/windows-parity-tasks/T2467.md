# T2467 - Composition step 3: scrollbar, dim overlay, bell border and banner become child visuals of the pane visual instead of WS_EX_LAYERED popups

## Summary

T2360 step 3. Removes the per-frame popup moves. Oracle: the existing overlay acceptance scripts green, and a glide moves no popup HWNDs (count SetWindowPos calls under GHOZTTY_PERF).

**Split 2026-10-29** (four overlay ports plus shared plumbing do not fit one
context): this task is the shared **overlay visual host** plus the **bell
border** as its first client. The dim overlay is T2491, the scrollbar T2492,
the banner T2493 - each depends on this one.

## In plain terms

The little layers drawn over a terminal pane - the yellow "this pane rang its
bell" frame, the dimming of unfocused panes, the scrollbar and the banner - are
each a separate floating window today, and every one of them has to be dragged
along by hand whenever the pane moves. This builds the place those layers can
live instead: inside the pane's own picture, so they move with it for free. The
bell frame moves in first; the others follow in their own tasks.

## Goals

- [x] A pane presenting through the composition swap chain publishes its visual tree, and the window side can hang overlay layers under it (refcounted, survives the renderer rebuilding its chain)
- [x] The bell border draws as a child visual on that path - same pixels, same fade - with no popup window
- [x] On the old path (knob off, or the chain failed) the bell border is the popup exactly as before
- [x] A pane moving with the bell frame up moves no overlay window

## Design (technical, mine per go.md 5b)

- The pane's DComp device is the renderer's (T2466). The window thread adds
  its own child visuals to the renderer's root visual through a mutex-guarded
  slot on the apprt Surface (`comp_overlay.Slot`): the renderer publishes
  AddRef'd device / D3D context / root on init and retracts on deinit, bumping
  a generation; the window side rebuilds its layers on a generation change.
  DirectComposition objects are free-threaded, so the two threads share the
  device; the D3D11 immediate context is not, so the presenter turns on
  `ID3D11Multithread` protection before publishing it.
- A layer's pixels are the same premultiplied BGRA rows the popup path builds,
  uploaded into an `IDCompositionSurface` (BeginDraw -> ID3D11Texture2D ->
  UpdateSubresource); its fade is an `IDCompositionEffectGroup` opacity. The
  layer is pane-local at (0,0), so a pane move is nothing at all to it.
