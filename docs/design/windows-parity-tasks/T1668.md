# T1668 - The GUI postmortem calls a deliberate Stop-Process kill a CRASH, so ALL PASS runs end in three CRASHED blocks

## Summary

ConvertTo-GuiExitVerdict in test\win32\lib\GuiPostmortem.ps1 calls any exit code with the high bit set a crash. Stop-Process -Force terminates with exit code -1 = 0xFFFFFFFF, which has the high bit set, so every script that force-kills its GUI and then runs a postmortem prints 'CRASHED - 0xFFFFFFFF unnamed NTSTATUS'. Observed 2026-09-19 on test\win32\chooser-resume.ps1: three such blocks under an ALL PASS (29 assertions) verdict, for the three app processes the script itself killed. Nothing gates on the verdict today, so this is report-only - but it is the cry-wolf shape: a reader who learns that CRASHED blocks are normal will miss a real one, and the T1511 family is actively teaching GUI scripts to refuse a crashed run as proof, at which point this becomes a false FAIL. Fix: have the launcher record which pids it deliberately terminated (or pass the expected kill code through) so the postmortem reports 'terminated by the harness' instead of a crash - 0xFFFFFFFF specifically is never a real unhandled-exception status.
