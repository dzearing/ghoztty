# T813 - The chooser's CPU meter freezes silently if the local agent's shared connection is replaced while the chooser is open

## Summary

SessionCpuProbe subscribes to whatever connection the selection resolved to and only re-checks on a selection change (or, for a remote machine, a pool notification). The LOCAL agent has neither: if agent recovery retires the shared connection and dials a new one while the chooser is open, the subscription dies with the old one, no further frames arrive, and the probe still reports supported() - so the column stays and the last readings sit there frozen with nothing saying they are stale. Cheapest honest fix is to re-check LocalAgent.sharedConnectionIfWarm() on each roster refetch and retarget when the pointer moved; the alternative is a staleness rule (no frame in N intervals => drop the meter), which also covers a wedged agent.

## In plain terms

Open the machine chooser and each session row shows a little CPU meter that
ticks along live. If the background helper that feeds those numbers gets
restarted or reconnects while you are looking at the list, the numbers stop
updating - but they stay on screen, looking exactly like live readings. You
would sit there reading a measurement that is minutes old and has no way of
telling you so. After this change the meter either moves or disappears: a
column that has gone quiet takes itself away, and comes straight back when
readings resume.

## Goals

- [x] The meter re-attaches on its own when the local agent's connection is replaced while the chooser is open.
- [x] Readings that have gone quiet stop being shown at all, instead of freezing.
- [x] A frame arriving brings the column straight back, with no separate recovery path.
- [x] The rule is stated on silence, so it also covers an in-place reconnect and a wedged agent.
