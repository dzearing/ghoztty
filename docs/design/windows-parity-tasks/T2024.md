# T2024 - Acceptance scripts call Get-CimInstance with no bound (83 scripts + CleanSlate/HarnessLeak/ModalSweep/PaneIdle libs): a WMI provider-host stall holds every running script at once, and their verdicts come late or wrong

## Summary

Found in T2010. On 2026-10-16 the CIMWin32 provider host stalled (WMI-Activity log: host 82848 from 11:17, replaced by 75932 at 11:41:07). Every acceptance script running at the time sat in its own Get-CimInstance call: in that run's timeline, groups of 3-4 finished scripts were all scored at the same instant 50-90 s after their last log line, and session-relaunch-notify - whose red setup assertion ("no session manager or PTY holder survived the reboot shape") counts processes through Get-CimInstance - wrote its last line at 11:41:09, two seconds after the new host came up. T2010 took WMI out of the RUNNER, so the run can no longer wedge. The scripts are still exposed: their verdicts arrive late, and a process lookup that returns nothing or stale results reads as a product failure.

Fix: a shared WMI-free process lookup in test/win32/lib (image path through OpenProcess + QueryFullProcessImageName, the way scripts/lib/AcceptanceParallel.ps1's Get-ApProcessesUnder does it; the command line where one is needed, read with a bounded call), adopted first by CleanSlate/HarnessLeak/ModalSweep/PaneIdle and then by the scripts. Anything that has to stay on WMI gets -OperationTimeoutSec plus a loud 'WMI did not answer' instead of an empty list. An audit (harness-floor member) keeps an unbounded Get-CimInstance from coming back.

## In plain terms

The automated tests ask Windows "which programs are running?" through a
service (WMI) that occasionally freezes for minutes. When it froze, every test
running at that moment froze with it, and some came back with wrong answers
that looked like bugs in the terminal. The shared test helpers now ask the
operating system directly, which cannot freeze that way; the few questions
only WMI can answer now give up after 20 seconds and say so.

## Goals

- [x] a WMI-free process table every test library can use (`lib\ProcessTable.ps1`)
- [x] the shared libraries converted to it, or bounded where WMI is the only source
- [x] an audit that keeps an unbounded call out of the libraries
- [x] the ~100 acceptance scripts' own calls filed as follow-up work (T3611)

## Scope at claim (2026-11-23)

Re-measured: 203 WMI calls across 103 files in `test\win32`, none bounded; 7
in `lib\`. This task does the shared libraries plus the gate; the per-script
conversion (94 scripts, 169 calls on the audit's count) is **T3611**, which
also widens the gate from `lib\` to the whole suite once the count is zero.

Choices (mechanism, so recorded here rather than filed as a decision):
- `Get-OsProcess` rows carry the Win32_Process field names the suite reads, so
  a conversion is a one-word change. The command line comes from
  `NtQueryInformationProcess(ProcessCommandLineInformation)`, which needs only
  PROCESS_QUERY_LIMITED_INFORMATION; on this box it matched WMI on 178 of 178
  processes WMI could read. Image paths come back in the kernel's casing
  (`C:\Windows`, WMI says `C:\WINDOWS`); every converted comparison is
  case-insensitive.
- `ProcessMemory.ps1` stays on WMI (it needs `PrivatePageCount`) through
  `Get-BoundedCimProcess`, which throws `WMI did not answer within 20s` - the
  meter then fails loudly instead of sampling zero children.

## Validation criteria
