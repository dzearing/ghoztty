# T2024 - Acceptance scripts call Get-CimInstance with no bound (83 scripts + CleanSlate/HarnessLeak/ModalSweep/PaneIdle libs): a WMI provider-host stall holds every running script at once, and their verdicts come late or wrong

## Summary

Found in T2010. On 2026-10-16 the CIMWin32 provider host stalled (WMI-Activity log: host 82848 from 11:17, replaced by 75932 at 11:41:07). Every acceptance script running at the time sat in its own Get-CimInstance call: in that run's timeline, groups of 3-4 finished scripts were all scored at the same instant 50-90 s after their last log line, and session-relaunch-notify - whose red setup assertion ("no session manager or PTY holder survived the reboot shape") counts processes through Get-CimInstance - wrote its last line at 11:41:09, two seconds after the new host came up. T2010 took WMI out of the RUNNER, so the run can no longer wedge. The scripts are still exposed: their verdicts arrive late, and a process lookup that returns nothing or stale results reads as a product failure.

Fix: a shared WMI-free process lookup in test/win32/lib (image path through OpenProcess + QueryFullProcessImageName, the way scripts/lib/AcceptanceParallel.ps1's Get-ApProcessesUnder does it; the command line where one is needed, read with a bounded call), adopted first by CleanSlate/HarnessLeak/ModalSweep/PaneIdle and then by the scripts. Anything that has to stay on WMI gets -OperationTimeoutSec plus a loud 'WMI did not answer' instead of an empty list. An audit (harness-floor member) keeps an unbounded Get-CimInstance from coming back.

## Validation criteria

- [ ] the shared libs no longer call WMI unbounded (an audit says so, and goes red on a planted unbounded call)
- [ ] a script whose WMI lookup times out says so in its verdict rather than scoring the product
- [ ] the converted libs' harnesses are re-run green
