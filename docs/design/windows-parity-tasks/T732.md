# T732 - The four harness-rule audits have no single entry point, so a new acceptance script meets them one red run at a time

## In plain terms

The Windows test suite has four house rules about how a test script must report
itself. Each is enforced by its own analyzer and its own separate check, and
none of them runs as part of the normal test floor. So somebody adding a test
script today learns the rules by tripping over them one at a time, weeks apart,
if anyone happens to run the right check. This gathers them behind one command
that runs with everything else.

## Summary

Four harness-rule analyzers now live in `test\win32\lib\`, each with its own
acceptance script and its own stated-intent marker:

| Rule | Analyzer | Acceptance | Marker |
|---|---|---|---|
| Every launch declares its session persistence (T158) | `PersistenceSweep.ps1` | `persistence-flag.ps1` | `# persistence:` |
| No `Start-Process -PassThru` exit code read without caching `.Handle` (T197) | `ExitCodeAudit.ps1` | `harness-exitcode-audit.ps1` | `# exitcode-audit:` |
| A SKIP is named in the verdict line (T219) | `SkipAudit.ps1` | `skip-visibility.ps1` | `# skip-audit:` |
| A script that prints failure exits nonzero (T221) | `VerdictExitAudit.ps1` | `verdict-exit-audit.ps1` | `# verdict-audit:` |

Two problems, both discovered while adding the fourth (T221, 2026-08-11):

1. **No entry point.** The rules are documented as four separate paragraphs of
   CLAUDE.md prose. There is no README in `test\win32\`, and nothing that says
   "these are the rules a script in this directory follows". A new script
   author has to have read all four paragraphs to write a compliant script.
2. **None of them is in the floor.** The standing floor is the three zig lanes
   plus P1-P3. All four of these audits are pure, non-interactive and take a
   few seconds each - and none runs unless somebody remembers it by name. A
   rule whose check nobody runs is a rule only until the next script.

## What was left when this was claimed (2026-09-14)

Problem 2 is gone: **T725** (`bdf71d1bb`) built the aggregator this task asked
for, and built it wider than four rules. `scripts\lib\HarnessFloor.ps1` declares
a set of 23 harness audits - all four named above among them -
`scripts\harness-floor.ps1` runs them and prints one
`HARNESS FLOOR: ALL PASS (N audits)` line, `scripts\floor-lane.ps1 -Lane harness`
is the one command, and the `harness-floor` guard row is what makes it standing:
touch any script under `test\win32\` and `parity-tasks.ps1 validate` refuses the
commit until the floor has been run green. go.md step 3 says all of that.

Problem 1 was still exactly as filed: **there was no `test\win32\README.md`**,
and nothing in the directory said "these are the rules a script here follows".
So the rules were still learned by tripping over them - now over twenty of them
rather than four, which made the missing entry point worse than when it was
filed, not better.

## Details

What this task delivered, therefore, is the entry point and its teeth:

- `test\win32\README.md`: the one command and its narrower forms, the pending
  ratchet, the two conventions every script here follows (verdict-last scoring
  through `lib\TestScore.ps1`; only ever touch ghoztty processes from the `-Exe`
  path), a row per floor rule naming its audit and **the marker that declares an
  exception to it**, and what to do when adding a script or a new rule.
- Section **F** of `test\win32\harness-floor.ps1`: the README is checked against
  the set rather than trusted to agree with it. Every audit in
  `$HARNESS_FLOOR_AUDITS` must be named in the README, and the README must name
  the command, the guard row and the static-sweep membership criterion. A rule
  added to the floor and left undocumented fails the floor's own harness.

Filed on the way: **T1572** - `caller-anchor.ps1` is in the floor set but is a
GUI product acceptance script, which breaks the set's own stated criterion (no
GUI, no app launch) and is why T1571 saw the harness lane go red on a stale app
build. Documenting the set is what surfaced it.
