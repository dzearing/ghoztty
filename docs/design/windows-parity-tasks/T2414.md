# T2414 - Dragging a divider next to a pane's banner, the banner paints over the pink divider (resize bar) for a frame, so a small rectangle flickers on the bar all through the drag

## Summary

User report 2026-10-28 on win-v1.49.1 (after T2400's banner fixes 73d99baca/b6ffb7759, which the user confirms made it better): while dragging a split divider, the banner beside it still 'eats into' the highlighted (pink/accent) divider: a small rectangle of the bar is repainted visibly on each move. Likely the banner popup is moved/sized to its new rect a frame before or after the divider strip is painted at its new position, or the banner's rect overlaps the divider gap by its rounded-corner/shadow inset, so the two surfaces fight over the same pixels. The bar must be painted correctly on every frame: the banner must never cover any divider pixel, and the banner and the divider must move in the same present. Acceptance: WGC capture of a divider drag with a banner on the pane on each side of the divider shows no frame where any divider pixel differs from the divider colour, and the user sees a clean bar while dragging. Related: T2400 (the parent report), T2360.

## In plain terms

While you drag the line between two panes, the line turns pink. If one of
the panes shows a banner, a small block of that pink line flickered on every
step of the drag, because the banner briefly sat over the line. After this,
the banner moves out of the way before the line is drawn, so the line stays
solid the whole drag.

## Goals

- [x] the banner (and every other per-pane popup) moves before the divider is painted, on every layout path

## Root cause

`Window.layoutSplits` placed the panes, painted the divider bands with GetDC,
and only THEN (its trailing `defer`) ran `updateDimOverlays` ->
`updatePaneBanners`. The banner is a popup above the window, so for the
interval between the band paint and its own move, a banner still at its
pre-tick rect covered the band just painted where its pane used to reach:
a banner-high block bitten out of the accent bar, once per tick on the
shrinking side. Fix: every layout path (grid, zoom, both hero shapes) now
calls `placePaneOverlays` after the pane batch lands and BEFORE the band
paint; the `defer` stays only as a fallback for a path that returns before
painting. A popup placed first only ever covers the band's OLD pixels, which
the paint then replaces.

Not done here (left on T2028): the popups still cannot join the panes'
DeferWindowPos batch (a defer batch takes only windows with the same parent,
and the popups are top-level), so a banner and its pane's terminal content
can still land in different compositions.
