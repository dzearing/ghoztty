# T2689 - parity-tasks validate does not catch a split child that depends on its own split parent: next follows skipped(split -> X) to X, so X waits on itself and drops out of the queue silently (T2666 sat a day that way)

## In plain terms

The work queue could quietly lose a task: when a big task was split into
pieces and one piece was marked as waiting on the original, the piece ended up
waiting on itself and was never handed out. Nothing warned about it. Now the
tracker's own check refuses that state and says which link to remove.

## Goals

- [x] `validate` reports a split child (or redirect target) that waits on itself through its parent as a `DEP CYCLE`, naming the skipped link
- [x] rings among closed tasks, which can stall nothing, stop being reported
- [x] any live instance in the tracker repaired

## Summary

`next` resolves a dep on a `skipped(split -> X, Y)` parent to its children and
a dep on `skipped(duplicate of X)` to X (`Get-OpenDeps`). The cycle check
(`Get-DepCycles`, T1133) walked only the literal `deps:` lists, so a child X
with `deps: [P]` where P splits into X has no literal edge back (P's own deps
are empty) and the ring was invisible: X waited on itself forever and `next`
listed it under "unmet deps" like any honest wait. T2666 sat that way for a day.

Fix (`scripts/parity-tasks.ps1`): `Get-ResolvedEdges` gives the walk the same
edges `next` follows - an open task's deps, a skipped task's split children /
redirect target, nothing for a done task - and the `DEP CYCLE` line is followed
by one line per skipped member naming what it resolves to and the remedy.
Side effect, deliberate: a ring among done tasks is no longer reported, since
`next` never follows a closed task's deps.

The new gate found two live instances on its first run: T2769 and T2770 both
depended on their split parent T2556. Both deps dropped (T2556's own deps,
T2553/T2562, are done), so both are back in the queue.
