# T3272 - Hovering a Ghoztty window steals focus from whatever app is active

## In plain terms

You reported that just moving the mouse over a Ghoztty window, without
clicking, pulls it in front of the app you were using. We read every piece of
Ghoztty that reacts to the mouse and found nothing that should do that, and
Windows' own "activate a window by hovering" setting is off. So the next time
it happens, Ghoztty now writes down exactly how the window got activated. That
record is what will find the cause.

## Goals

- [x] Audit every pointer-motion path for a call that activates a window (none found)
- [x] Rule out the Windows "activate on hover" setting (off, both ways)
- [x] Log the cause of every activation (click, keyboard/program, button held)
- [ ] Reproduce it with that log line on a build that carries it
- [ ] Fix the trigger the log names, and prove it with T3275's hover script

## Findings (2026-11-20)

- **Static audit, no hover trigger found.** Every WM_MOUSEMOVE, WM_SETCURSOR,
  WM_NCHITTEST, WM_NCMOUSEMOVE and WM_MOUSELEAVE handler, the run loop's
  pre-dispatch arm, and every hover timer and tooltip was traced. All hover
  popups are `WS_EX_NOACTIVATE`. Every SetWindowPos uses `SWP_NOACTIVATE`. Every
  SetFocus and SetForegroundWindow sits on a click, a right-click menu, a drop,
  an IPC verb, a dialog open or a notification click. `focusFollowsMouse` is
  gated on the foreground window. The WebView2 `GotFocus` handler only relabels
  the tab.
- **OS setting ruled out.** `SPI_GETACTIVEWINDOWTRACKING`=0,
  `HKCU\Control Panel\Mouse\ActiveWindowTracking`=0, and UserPreferencesMask
  bit 0 is clear.
- **Installed log.** Today's activations of the installed app were a sidebar
  press (05:19 local) and two plain switches yesterday evening that the log
  could not attribute. That gap is why the cause line was added.
- **Latent weakener, filed as T3274.** `onInputDesktop()` is cached forever.
  A wrong first answer makes the deferred-focus gate forward asserts while
  another app is in front. It is not shown to cause this.
- **What to look for.** Search the app log for `window activated ...
  cause=program_no_button` at the moment of a steal. That cause means no click
  and no button held: a hover, Alt+Tab or a taskbar click. `input_desktop=false`
  on the user's own desktop means T3274 is in play.

## Summary

User report 2026-11-20: on the installed Windows build, moving the mouse over a Ghoztty window brings it forward / takes keyboard focus without a click. Ruled out by reading: Surface.focusFollowsMouse (Surface.zig:6517) refuses to act unless the parent window is already active; PaneGrabHandle is WS_EX_NOACTIVATE + SWP_NOACTIVATE + MA_NOACTIVATE. Not yet checked: the other hover handlers in the run loop and WndProcs (BannerOverlay, PaneSidebar, Scrollbar, KeyStateIndicator, viewer bars, WebView2 viewer panes taking focus on hover), any ShowWindow/SetWindowPos on hover missing SWP_NOACTIVATE, and deferSetFocus/WM_APP_SETFOCUS firing on an inactive window. Repro first: two apps side by side, focus the other one, hover a Ghoztty pane (terminal, viewer, sidebar, banner, tab strip) and record which surface steals. Acceptance: a background-desktop script proving hover over each surface kind leaves GetActiveWindow/foreground unchanged. Mac parity: hover must never activate there either - verify.
