# T1543 - Resting a dragged pane on another window's tab button opens that tab

## In plain terms

You can now drag a pane into another window, and you can drop it on that
window's tab strip to make it a tab there. What you cannot do is put it into a
tab that window is not currently showing: hovering over one of its tab buttons
does nothing, so the only way to get a pane into a background tab of another
window is to move it twice.

## Summary

T1537 gave the drag a DWELL: resting on a tab button for 500ms switches to that
tab, so the drag continues against the layout you are aiming at. T1538 left it
deliberately scoped to the window the drag started in, because switching a
background WINDOW's tab reorders something the user is not looking at and
nothing had established what that should feel like. The reachable half is
there - a drop on another window's strip makes a tab - so this is the missing
precision rather than a missing capability.

What the work is: `updateRearrangeDrag` already resolves `pane_drop.hoveredTab`
against a candidate SET and passes it only this window's candidate; the dwell
state (`RearrangeDrag.dwell_tab`) would have to name a window as well as an
index, and `onTabDwell` would have to select the tab on that window and keep
the capture here. Mac's counterpart is `PaneDragController`'s hover timer.

## Validation criteria

- [ ] Resting a dragged pane on a BACKGROUND window's tab button for the dwell
      brings that tab up in that window, and the drag continues against it.
- [ ] Releasing then lands in that tab's layout, with the pane's HWND identity
      and session intact.
- [ ] The tab the drag STARTED in is unaffected until the drop commits.
- [ ] `test\win32\rearrange-window-drop.ps1` grows the claim, and the guard row
      still stamps.
