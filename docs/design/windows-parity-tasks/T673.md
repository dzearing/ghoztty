# T673 - No test seam turns the composer's byte-to-UTF-16 conversion off, so its acceptance script can only be teeth-checked by editing source

## In plain terms

We have a test that proves feedback text with accents and emoji in it behaves.
The only way to confirm that test would actually notice a regression is to
hand-edit the source, rebuild, run, undo the edit and rebuild again. That is
enough friction that nobody will do it, and a test nobody re-checks quietly
stops being one.

## Summary

T648 teeth-checked `test\win32\viewer-feedback-utf16.ps1` by stubbing
`ViewerFeedbackBar.charIndex`/`.byteOffset` back to identity — a source edit
plus two full rebuilds. It found a real problem (the first draft of the script
had no teeth at all), which is the argument for making the check cheap enough
to repeat.

The repo already has the pattern: `GHOZTTY_TEST_LIVENESS_BREAK=1` makes every
liveness arm in a restore script go red and nothing else move, which is how
each of those arms was proved (T532/T652). The same idea applies here.

## Details

- Shape: an env var — `GHOZTTY_TEST_BREAK_UTF16=1` or similar — read once at
  composer creation, that makes `charIndex`/`byteOffset` the identity they used
  to be. Empty/off in every real run, like the agent's
  `GHOZTTY_AGENT_MAX_SESSIONS`/`GHOZTTY_AGENT_SUPPRESS_CAPS` seams (T469).
- It must break exactly ONE thing. A seam that also disables something else
  turns a targeted teeth check into a smoke test, and a red arm no longer names
  its cause.
- Prefer one seam over per-site seams: the conversion has a single home
  (`utf16_offset.zig` behind two helpers), so a single switch covers every
  call site, and there is no way to leave half of it converted.
- Acceptance for the seam itself is the shape T652 used: re-running
  `viewer-feedback-utf16.ps1` with the var set turns the four offset arms red
  and moves nothing else; without it, ALL PASS. That is a script arm, not a
  claim in a commit message.
- Worth considering whether the same seam should cover T672's tightened
  chip-deletion arms in the sibling scripts, so one variable teeth-checks every
  composer offset assertion the suite has.

## Goals

- [x] one switch makes the byte/UTF-16 conversion the identity, at every call
      site at once
- [x] a second switch makes a chip's selection range miss, so the ASCII-only
      composer suites can be teeth-checked too (T672's finding)
- [x] both are off by default, debug-only, and read once
- [x] the pair is documented beside the other test seams

## Validation criteria

- [x] An env-var seam makes the composer's byte-to-UTF-16 conversion an
      identity, and is off by default.
      `GHOZTTY_TEST_BREAK_UTF16=1` sets `utf16_offset.break_identity`, which
      both conversions consult, so every call site (the two `CHARRANGE`
      helpers, `caret`, and the page's own span mapping) turns over together.
      Read once in `ViewerFeedbackBar.create` and only in a debug build. Unit
      test in the `none` lane asserts off-by-default and identity-when-on.
- [x] With it set, `viewer-feedback-utf16.ps1` goes red on its offset arms
      (chip position, caret position, whole-chip Backspace, report body) and
      nothing else changes.
      Measured on the box 2026-09-09: `4 FAILURE(S) (26 passed)`, and the four
      are exactly those arms.
- [x] Without it, the same script is ALL PASS.
      Measured the same night: `ALL PASS (30)`.
- [x] The seam is documented where the other agent/test seams are, so the next
      person re-checking these arms finds it instead of editing source.
      `docs/claude/testing.md`, beside `GHOZTTY_TEST_LIVENESS_BREAK`.
- [x] The sibling ASCII-only suites are teeth-checkable too (the task's "worth
      considering" bullet, sharpened by T672's finding that an identity
      conversion is a no-op on ASCII text).
      `GHOZTTY_TEST_BREAK_CHIP_RANGE=1` makes `ViewerFeedbackBar.chipRange`
      stop one unit short — the single home both chip sites now go through.
      Measured: `viewer-feedback-images.ps1` ALL PASS (40) clean and
      `2 FAILURE(S) (38 passed)` under it; `viewer-feedback-carousel.ps1`
      ALL PASS (59) clean and `1 FAILURE(S) (58 passed)` under it. In both
      cases the reds are the whole-chip deletion arms and nothing else.
