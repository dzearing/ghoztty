# T1758 - validate accepts an open task whose Summary is still the TODO scaffold, so a card can sit in the queue with nothing in it

## Summary

Found at the 2026-09-26 triage. T1745, T1746 and T1747 were filed on
2026-09-25 during the T1633 turn (machine chooser tooltips) with nothing but a
title: `parity-tasks.ps1 new` scaffolds `## Summary` as "TODO: describe the
defect or gap, the evidence, the fix, and the validation." and a matching TODO
validation bullet, and nothing afterwards noticed that neither was ever
replaced. `validate` already fails an in-progress task with no progress log;
it has no equivalent for a todo whose body is the scaffold. The triage filled
all three by hand from the Mac source. At that triage seven MORE open tasks
still carried the scaffold Summary: T888, T1242, T1346, T1347, T1363, T1479,
T1480 — so landing the check means writing (or skipping) those seven first.

Fix: `validate` reports any open (todo / in-progress / blocked) task whose
Summary or Validation criteria is still the exact scaffold text. Decide whether
it FAILS or WARNS: failing is the only version that cannot be ignored, but a
turn that files a task mid-work must be able to finish its commit, so the
likely shape is a fail with the filing turn expected to write the summary
before committing (which is what step 5 already asks for). If it becomes a
gate, it needs its demonstration in `test\win32\gate-negatives.ps1` (T1133).

## Validation criteria

- [ ] A todo task whose Summary is still the scaffold makes `validate` report it by id (section in `test\win32\parity-tasks-seat.ps1` or `gate-negatives.ps1`).
- [ ] A task with a real Summary does not trip it (negative control).
- [ ] Every open task on the tree passes the new check at the commit that lands it.
