# T3430 - Linux: a chord a GTK viewer pane does not claim reaches the app's keybindings, minus terminal-only actions

## Summary

T3412 gave GTK viewer panes their own chords (Ctrl+R/L, Alt+D, zoom, Escape in the address) and declines everything else, but nothing then performs a config keybinding from a viewer: GTK dispatches config bindings through the focused TERMINAL's core surface (Surface.keyEvent), and a viewer pane has none. Only the few actions the app mirrors as GtkApplication accelerators (split, new tab, palette, close) can answer. Port Mac ViewerKeyFallback / win32 viewer_accel.route (T1803): a chord the pane and the page leave alone is looked up in the app's binding set; app actions go through the core app, window actions through a terminal in the same window when there is one, pane actions (split, close, zoom, goto_split) act on the viewer itself, terminal-only actions (text:, copy/paste, font size, scroll, search) are never forwarded. Typing stays typing while the address field has the caret (win32 fieldOffers). Also: the command palette must open over a viewer-only window. Acceptance extends test/linux/viewer-nav.sh through its GHOZTTY_TEST_VIEWER_STEPS seam.

## In plain terms

On Linux, when you clicked into a document or web page shown inside Ghoztty,
most of Ghoztty's own shortcuts stopped working: Ctrl+Shift+T for a new tab,
Alt+2 for the second tab, moving between panes, your own custom shortcuts.
Now they work from a document pane exactly as they do from a terminal, except
the ones that only make sense for a terminal (copy, paste, font size), which
stay with the page. Typing in the page's address bar is still just typing.

## Goals

- [x] An unclaimed chord in a viewer pane reaches the app's keybindings
- [x] Split, close, zoom and pane navigation act on the viewer itself
- [x] Terminal-only bindings are never performed from a viewer
- [x] The page and the address/find/filter fields keep their own editing chords
- [x] It all works in a window that holds nothing but viewers, palette included

## How it works

`viewer_chrome.zig` (pure, none lane) carries the decision, in win32's shape:
`offersToApp` (the page keeps `pageOwns`, a field keeps all but
`fieldOffers`), `keyEventFor`, and `route` - win32's `viewer_accel.route`
with GTK's own native set (`nativeTag`, cut to what GTK implements for a
terminal too: no hero, sidebar or stash). `Viewer.handleKey` offers what the
pane does not claim through `on_app_chord`; `Surface.viewerAppChord` builds
the key event the way the terminal path does (physical key from the hardware
code, else from the keyval); `Application.viewerChord` claims it and performs
it one idle hop later, since a close can free the pane whose handler is still
on the stack. Natives run in `Application.performViewerBinding` on the
viewer's own split tree / tab / window (a split is made OFF the viewer, not
whichever pane the tree last saw focused); app actions and window actions go
through the core's `performActionForNonTerminal`, the latter through a
terminal in the same window. A command palette entry picked over a viewer
takes the same route (`Window.performBindingAction` -> `performViewerAction`).
