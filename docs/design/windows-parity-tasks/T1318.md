# T1318 - The LOCAL machine chooser's resume has no on-box proof that it names the window it builds

## Summary

T1296 named a resumed window from the layout record on both arms, and the CROSS-MACHINE half is proven on box (chooser-resume-remote.ps1 C2, demonstrated red first). The LOCAL half is covered only by a unit test, because chooser-resume.ps1's fixture deliberately DELETES the layout manifest to force the degradation it is about (T620) - so there is no record left for a name to come from and the assertion could not be added without rebuilding the fixture. What is needed: a fixture that keeps the manifest but still leaves the agent's sessions unheld (GHOZTTY_RESTORE_SKIP without the manifest deletion, if that seam holds), then the same assertion as C2 - resume an orphaned session, and the window comes back with the name +rename gave it.

## In plain terms

If the app closes while your terminals keep running, you can reopen one of
them from the machine chooser. When the session was on THIS computer, the
window it came back in had lost the name you gave it and just said
"Ghoztty". It now comes back with your name, the same as a session resumed
from another machine already did.

## Goals

- [x] find out whether the local half really names its window (it did not)
- [x] make a local resume find the name where it survives
- [x] an on-box check that a local resume keeps the window's name, shown red without the fix

## Findings (2026-10-24)

The task assumed the gap was only missing proof. Building the proof showed the
feature itself was broken: the local arm read the window name from the on-disk
manifest only, and the launch that leaves an orphan behind (one that rebuilt
nothing) rewrites that manifest with the windows it did open within seconds.
So by the time the chooser opens, the orphan's window is not in the manifest
at all - deleting it in the fixture changes nothing. The record DOES survive:
the dead app pushed its window's layout blob to the agent, and the new app's
reconcile only deletes keys it pushed itself. Fix: the local fetch pulls
`GET_LAYOUTS` too, and the lookup searches the manifest first (this process's
newer record) and then the agent's blobs. The resumed pane's persisted pane id
(T113) comes from the same lookup, so it gains the same fallback.

## Validation criteria

- [x] a local resume of an orphan comes back with the window name `+rename` gave it - `test\win32\chooser-resume.ps1` (new rename fixture + assertion), ALL PASS (48 assertions) via `acceptance-parallel.ps1 run`
- [x] the assertion has teeth - with the local fetch's layout pull backed out, the same run is 1 FAILURE: the window came back titled `Ghoztty [DEBUG]`
- [x] lookup order is pinned by a unit test - `SessionRoster.zig` "a LOCAL orphan the rewritten manifest forgot is named from the agent's blobs (T1318)": blob-only session named from the blob; a session in both takes the manifest's name and pane id
