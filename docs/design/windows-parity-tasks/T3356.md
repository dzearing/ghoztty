# T3356 - a dialed pane opened with --command=cmd.exe never follows the user's cd, because the agent reads the directory of the wrapper shell instead of the one the user types into

## Summary

Found by T1741. +new-remote-window --host=127.0.0.1 --port=<p> --command=cmd.exe, then cd sub: +list --json never moves to sub within 30 s. The only META{cwd} push that arrives names the OPEN directory with a trailing backslash (the spelling change alone counts as a move). Without --command, the same pane follows the cd in 6-10 s. INFERRED, not traced: the command travels as OPEN.command and the agent runs it under its own cmd /c, so shell_pid (what HolderChild.queryCwdFn reads) is the outer cmd, which never changes directory. T512 unwraps a bare shell command on the local path (bareShellCommand), and the dialed path apparently does not. Fix: unwrap a bare shell --command on the dialed path too, or have the agent read the cwd of the interactive descendant. Repro harness: test\win32\remote-cwd-follow.ps1 with --command=cmd.exe added to its +new-remote-window line.
