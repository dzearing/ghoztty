# T1956 - Viewer and remote-IO logging is the top log volume on the Cloud PC: cut viewer_pane / io_remote info lines to debug or rate-limit them

## In plain terms

On the user's Cloud PC, the two chattiest parts of Ghoztty's log are the
viewer panes and the remote-connection code. Every line written is a little
CPU, on a machine that is already short of it. Those messages should be quiet
unless something is actually wrong.

## Summary

T1951's rescope (item 4) asked to check `viewer_pane` / `io_remote` log
volume, which GitHub #13 measured as the top two sources on dzearing1. T1951
landed the rendering half of item 4 (hidden viewers stop rendering through the
same visibility the panes use); the logging half is this task.

Find the per-event `info` lines in `src/apprt/win32/ViewerPane.zig` (and its
helpers) and the remote IO path (`io_remote` scope), move routine per-frame /
per-message lines to `debug`, and rate-limit any that must stay at `info`
(the T1935 pattern for the sidebar). Keep first-occurrence and error lines.

## Goals

- [x] Find what actually fills the log, from a real log rather than a guess
- [x] Viewer worktree line: written when the answer changes, not every poll
- [x] Resume-offset correction line: first and a log-scaled sample at info, rest debug
- [x] File what is louder than both (the CLI startup banner, T1998) and the
      offset oscillation the volume revealed (T1999)

## What the log said (before)

The last 40,000 lines of this box's `%LOCALAPPDATA%\ghoztty\ghoztty.log`
(2026-10-15 08:17Z -> 2026-10-16 09:53Z):

- `info(viewer_pane)`: **6,142** lines, every one of them
  `viewer worktree pane=... feedback=shown worktree=...` - the loopback
  re-resolve poll (T650) re-pushing an UNCHANGED answer every 15 s, i.e. 4
  lines/min per dev-server pane, ~40 per pane per 10 minutes.
- `info(io_remote)`: **626** lines, all `resume offset corrected`, arriving in
  `delta 16` / `delta -16` pairs ~9 ms apart (filed as T1999).
- For scale, out of scope here: each CLI invocation writes a ~9-line startup
  block, 3,363 times (~30k lines, ~75% of the log). Filed as **T1998**.

## The change

- `ViewerPane.pushWorktree` logs only when `(shown, path)` differs from the
  last line it wrote for that pane (`worktreeLogChanged`, a Wyhash per pane).
  The acceptance scripts read the LAST matching line for a pane, so the oracle
  is unchanged: the last line is still the current answer.
- `Remote.adoptStreamPos` counts corrections per pane; the 1st, 2nd, 4th, 8th...
  stay at info with `n=` (20 lines for a million), the rest go to debug.
- Left alone deliberately: `viewer diff` (already change-gated in
  `completeDiff`), and `viewer page/image served` (one per page request, user
  driven, and acceptance oracles - not idle volume).

## Validation criteria

- [x] An idle run with 4 viewers and a remote pane writes a bounded log.
      Scratch measurement (test desktop, debug build, 4 loopback viewers on a
      live listener + an agent-backed terminal running `ping -t`, 4 minutes
      after a 20 s settle): **0** `viewer_pane` info lines and **0**
      `io_remote` info lines in the window; 4 worktree lines for the whole run
      (one per pane). The old code writes 16 per pane in the same window (one
      per 15 s poll, 64 total) - the 6,142 above. The 4-minute window stands
      in for 10: the old rate is a fixed 4/min/pane, the new one is 0 at idle.
- [x] No error or state-change line is lost: a worktree CHANGE is still logged
      (`viewer-worktree-port.ps1` T650 arm, a pane picking up a dev server
      started afterwards, ALL PASS 23); unit tests `worktreeLogChanged` (first
      answer, each change, none<->path, empty path) and `logCorrection` (first
      always, powers of two, 20 in a million, saturation stays quiet). No
      warn/err call was touched.
- [x] `viewer-worktree.ps1` ALL PASS (50), `viewer-worktree-port.ps1` ALL PASS
      (23), `viewer-composer.ps1` ALL PASS (41); `floor-lane -Lane all` ALL
      LANES PASS; both new tests matched by `-Dtest-filter` (T631 guard).
