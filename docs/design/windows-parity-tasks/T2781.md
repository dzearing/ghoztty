# T2781 - A cold +new-window still opens a stray blank window-1 beside the requested one when the local agent is slow to resolve (resolve-window-persist A, GHOZTTY_AGENT_RESOLVE_DELAY_MS=2500)

## Summary

Found by T2688 2026-11-06. With the 2.5s resolve hold, resolve-window-persist.ps1 section A lists rdA AND window-1 after a cold CLI auto-launch, which is the stray window T2162 (bf61f22e8) set out to remove; B (no hold) lists only rdB<n>. Launching zig-out ghoztty.exe --initial-window=false directly with the same hold and then sending +new-window --target=rdA opens ONLY rdA (log: 'IPC: new-window held until the local-agent resolve finishes', restore resolve served the held request, then 'deferring the startup window 5000ms', no fallback line), so the stray comes from the CLI auto-launch path (autoLaunchInstance + its re-send poll) under a slow resolve, not from the grace timer as tested directly. A detached debug app's stderr is lost, so capture it (e.g. a GHOZTTY test hook that names a stderr file for the auto-launched instance) before guessing. When fixed, section A's A3 ('the launch window is persisted too') must change: it currently relies on the stray window existing.

## In plain terms

Asking for a named window when Ghoztty was not running sometimes opened two
windows: the one you asked for and an extra blank one. It only happened when the
background session helper was slow to answer at startup. The fix had already
landed with T2842; this task proved that and changed the test so it now fails if
the extra window ever comes back.

## Goals

- [x] Find out where the stray `window-1` came from, from the auto-launched app's own log

## Root cause and resolution

Read from the auto-launched instance's log, captured with the new debug hook
`GHOZTTY_TEST_STDERR_FILE` (`src/main_ghostty.zig`; documented in
`docs/claude/testing.md`). It was needed because the detached instance's stderr
is lost. On top of that, the CLI-launch probe's `AttachConsole`/`FreeConsole`
round trip points it at the caller's console halfway through startup, so the
hook re-installs its handle before each log line.

The held `+new-window` (T1688) is served by the message pump inside the launch
restore. That window's layout sync mirrors it into the agent's store, and the
restore's pull then offers it back as a crash orphan
(`session-restore: recovered 1 crash-orphaned window(s) from the agent`). Before
d2880af3f (T2842) the launch pass rebuilt it as a second window, the stray
`window-1`, which had rdA's session, so the old A3 passed on it. T2842 made the
launch pass skip windows already on screen, and the same run now logs `1 offered
window(s) are already on screen here ... left alone`. The direct-launch control
in the summary never saw this because there the request was served after the
restore had finished.

Closed against **d2880af3f**, the commit that actually fixed it.
