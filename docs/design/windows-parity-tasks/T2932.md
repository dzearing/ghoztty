# T2932 - A divider drag re-cuts the window region (SetWindowRgn + region build) on each resized pane every frame, and 1-3 of those ~1800 system calls a run stall 2-7 ms off-CPU: keep the per-frame card shape off the window manager while the drag runs

## Summary

T2874 measured the fold-glide region-cut stall (release sandbox, 120 Hz, the
T2732 glide probe, 11 runs, `GHOZTTY_STACK_TRACE=ring`, the `stack trace rgn`
line that T2874 added):

- ~1800 `SetWindowRgn` calls a run (about 1.6 a tick: the panes the drag
  resizes, `kind=card`), mean 140-155 us, p99 0.4-0.55 ms, and that time is
  the UI thread **on CPU** in the kernel (thread cycles / wall = 1.0).
- 0-5 calls a run take 1.5-8.1 ms, and on those the thread ran only
  130-230 us: it is **off-CPU** - blocked, on a 32-thread box at ~6% load -
  inside the call. The pane's own window procedure accounts for 3-20 us of it
  (3 messages: WM_WINDOWPOSCHANGING / WM_NCCALCSIZE / WM_WINDOWPOSCHANGED),
  and no renderer present on that pane overlaps the span, so it is neither
  our message handling nor the T2732 11-07 renderer contention.
- The same off-CPU stall also lands OUTSIDE `SetWindowRgn` but inside the cut
  phase (a 5.4 ms `cards_us` tick with 1.3 ms in the calls; 3.8 ms with
  0.26 ms) - the region build (`createCardRegion`, GDI) and the rest of
  `applyCardRegions` are system calls too.

So the stall belongs to whichever window-manager / GDI call is in flight when
a session-wide lock is held elsewhere (T2931 names the holder). The lever this
side controls is the NUMBER of those calls a drag frame makes: each is a
ticket in that lottery, and a drag makes ~2 a frame for a shape that only
matters at rest.

Direction: give a drag-resized pane its card shape without a per-frame
`SetWindowRgn` - the way T2826 already does for a gliding tree pane
(`glideRegionIdle`: the visual carries the clip, the region is cut once at the
landing) - and cut the region once when the drag ends. The rounded corner must
still show on every frame (Mac draws it throughout), so this is not "square
corners while dragging"; check `stack-fold-slide` F13/F14 and the pane
elevation harnesses still see the cut.

## In plain terms

Dragging the divider between panes occasionally hitches for a few
milliseconds because, on every frame, Ghoztty asks Windows to re-cut each
resized pane's rounded outline, and once in a while Windows makes that call
wait. On the composition drawing path the pane's picture already carries its
own rounded corners, so the outline is now cut once when the drag ends instead
of every frame. On the default drawing path the outline IS what rounds the
corner, so it still has to be cut every frame - that part is filed as T2933.
