# T2769 - Divider, sidebar and drag-to-collapse drags move the pane visuals on the compositor (one DirectComposition offset/clip write + commit per mouse move) ahead of the resize pass, which coalesces behind it - so the card edge tracks the pointer in ~1 ms instead of the ~15.7 ms pane batch (T2556 decision)

## Summary

Build half of T2556 (decision and measurement are in T2556's file). Under `GHOZTTY_COMP_PANE_TREE` + `GHOZTTY_COMP_CHROME`, one divider-drag mouse move costs a mean 15.7 ms (drag-perf.ps1, 2 panes, 2026-11-06), and 14.7 ms of it is the pane batch (`endPaneBatchFilled`: child-window moves and swap-chain resizes); the card/compositor step is about 1 ms. The pointer therefore waits on the resize.

Split the two. On each `updateDividerDrag` (and the sidebar-width and drag-to-collapse equivalents), compute the new pane rects, write each affected pane visual's offset and clip on the window's DirectComposition device (`chrome_comp.Host.panePlace`, the same visual `syncTreeVisual` places), and commit - BEFORE the layout pass. The layout pass (HWND moves + resizes) then runs coalesced: at most one per frame, and skipped while a newer move is already queued. The grid inside a visual is held at its old size until its resize lands (the Mac `paneContentFreeze` shape T2466 already uses for glides), so a lagging resize shows as a clipped or exposed edge of desk, never as a stretched grid.

## In plain terms

When you drag the line between two panes (or the sidebar's edge), the panes
used to follow your mouse only after every terminal had been resized, which
took 15-70 ms a step depending on how many panes there were. Now the panes'
pictures move to follow the mouse straight away, in well under a millisecond,
and the resizing catches up behind them.

## Goals

- [x] a drag move writes every pane's picture where the layout puts it, and shows it, before the resize work
- [x] the resize work runs at most once per screen frame, and not at all for a position the mouse has already left
- [x] the same for the sidebar edge drag and the drag that folds a pane into a strip
- [x] measured on the test desktop, with the old ordering as the control

## How it works

- `comp_drag.zig` (pure, `none` lane): `decide` (run the pass now, leave it
  to the queued move, or leave it to the frame timer - never for longer than
  a frame), `timerDelayMs`, `reshape` (a visual's card shape carried to a
  size its window does not have yet), and the drag's `Stats`.
- `Window.preplaceDragVisuals`: the active tab's grid, each pane on show in
  the tree written at `leafRect` of its slot through
  `Surface.preplaceTreeAt` (the T2571 `tree_glide_at` hook, so `placeLeaf`
  lands it and the cut sets its true shape), all in one host batch = one
  commit. It declines (old path, whole) when a glide owns the visuals, when
  the move shows or hides a pane, or when no pane is in a tree - checked
  before any grid is computed, so a knob-off drag computes nothing extra.
- `Window.compDragMove` from `layoutDragStep` (divider and row/collapse
  drags) and `setPaneSidebarWidth` (sidebar edge, whose panel sync and paint
  ride the coalesced pass); `COMP_DRAG_TIMER_ID` lands a pass the frame
  clock left; the drag's end runs whatever is left.
- `GHOZTTY_COMP_DRAG_SERIAL=1`: the old ordering, the A/B and the control.
- Perf lines (under `GHOZTTY_PERF`): `divider drag comp landed=N off=M` and
  `divider drag comp commits=.. mean_commit_us=.. max_commit_us=.. passes=..
  skipped_queued=.. skipped_frame=.. passes_inside_frame=.. period_us=..`.

## Validation criteria

- [x] drag-perf.ps1 (pane-tree mode) reports a new pointer-to-commit time per move, and its mean is under 2 ms at 2 and 8 panes - section F, 2026-11-07: 200 us at 2 panes, 241 at 4, 339 at 8 (the whole move: 18.6 / 23.5 / 67.8 ms)
- [x] layout passes per drag are at most one per display frame (counted in the drag summary line) - `passes_inside_frame=0` at every count. Caveat: the harness's posted moves are each handled before the next arrives, so `skipped_queued`/`skipped_frame` stayed 0 there; the skip branches are covered by the unit tests only
- [x] the drag ends with every HWND at the visual's final rect (no residual offset), asserted on the test desktop - `landed=2/4/8 off=0`. The swap chain is not asserted by this oracle: it follows its window when the drag hold releases at the drag's end, as before (T2459)
- [x] with the knob off, the drag path is the old one - `preplaceDragVisuals` returns before computing anything when no pane is in a tree; batched (no tree) drag 6.8 ms/move in the same run, as before
- [x] negative control: forcing the old ordering - `treeserial` (`GHOZTTY_COMP_DRAG_SERIAL=1`) writes nothing ahead of its pass, so the pointer waits the whole move (17.0 / 24.5 / 56.8 ms); `-NegativeControl` inverts the 2 ms row
