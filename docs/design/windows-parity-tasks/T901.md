# T901 - Pane-launched GUI pays a double process start: the com shim could spawn ghoztty.exe already-escaped

## In plain terms

Since T675, a Ghoztty window opened by typing `ghoztty` inside a pane starts
three processes instead of two: the console helper, then the app (which
discovers it was born inside the background service's process group), then the
app again outside that group. Nobody sees anything but a few extra tens of
milliseconds; this task removes the middle start so the launch is as direct as
it can be.

## Goals

- [x] `ghoztty` typed in a pane starts the GUI once, not twice
- [x] the GUI it starts is born outside the pane's kill-on-close job
- [x] the startup escape stays armed as the backstop for every other path

## Summary

`App.runComShimGuiRespawn` (T245) spawns the sibling `ghoztty.exe` with a plain
detached `CreateProcessW`, so the GUI child inherits the pane's job chain and
then immediately re-execs itself via T675's startup escape. If the com shim
used `job_spawn.spawnEscapingJob` for the respawn, the GUI would be born
outside the agent's kill-on-close job and the startup escape would find nothing
to do — one spawn instead of two on the most common launch path.

Care needed (why T675 did not just do this):

- The respawn currently passes `create_new_process_group`; `spawnEscapingJob`
  callers must weigh T84 (the flag disables Ctrl-C for every descendant;
  `App.init` clears it, so dropping it may be the better move — decide, and
  test).
- Tier 2 (shell-parent hop) passes the environment explicitly, so T506's
  `GHOZTTY_CLI_LAUNCH` marker must still reach the child (it is set on the
  shim before the spawn, so `GetEnvironmentStringsW` picks it up — verify with
  the working-directory acceptance).
- The startup escape stays as the backstop for every OTHER launch path; this
  only removes the hop where the com shim is the launcher.

## Validation criteria

- [x] `ghoztty` typed in a pane produces a GUI that never logs
      `startup escape: respawning` (born escaped instead) - section D of
      `test\win32\job-escape-startup.ps1`: D7 asserts the pid the twin
      reports spawning IS the pid still running, which is only true when no
      re-exec happened
- [x] `test\win32\job-escape-startup.ps1` still ALL PASS (direct-exe path
      keeps the re-exec backstop) - 21 assertions, A-C unchanged
- [x] `test\win32\auto-launch-cwd.ps1` still ALL PASS (T506 marker survives
      the escaping respawn) - ALL PASS
- [x] Floor green - `scripts\floor-lane.ps1 -Lane all` + P1-P3 + the harness lane
