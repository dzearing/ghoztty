# T862 - A --shell / command-shell value with spaces (C:\Program Files\Git\bin\bash.exe) splits at the space unless the user hand-quotes it, so detection and spawn disagree

## Summary

Follow-up found during T513. A shell-form `config.Command` is parsed with
`std.process.ArgIteratorGeneral` (`src/config/command.zig:114`), so
`--shell=C:\Program Files\Git\bin\bash.exe` — after the invoking shell and
Windows argv parsing have stripped the user's quotes — arrives as the
unquoted string and splits at the space: arg0 becomes `C:\Program`.
Detection then fails (basename `Program`), while the SPAWN side may still
succeed or fail differently (CreateProcess-style probing tries
`C:\Program.exe` first, then longer prefixes), so the pane can open a shell
that detection never saw, or fail outright, depending on the path.

Workarounds that exist today (both proven in T513's turn): embed literal
quotes (`--shell="\"C:\Program Files\Git\bin\bash.exe\""`), or use the 8.3
short path (`C:\PROGRA~1\Git\bin\bash.exe`, what section C of
`test\win32\agent-shell-integration.ps1` does). Neither is the natural
spelling.

Investigate before fixing: where exactly the quotes are lost per entry path
(CLI `--shell=`, config file `command-shell`, `+new-window --shell=`), what
the Mac/Linux behavior is for a space-containing shell path (parity: they
have the same ArgIteratorGeneral parse, but space-free shell paths are the
norm there), and whether the right shape is (a) quote-detection/auto-quoting
when the value names an existing file, (b) documenting that the value is
shell-words and must be quoted, plus making the failure loud (a "shell not
found: C:\Program" toast/log instead of silence), or (c) a direct-form
default for values arriving from `--shell=` since that flag semantically
names ONE executable path, not a command line.

## In plain terms

If you point Ghoztty at a shell whose path has a space in it — and on Windows
that is most of them, because they live under `Program Files` — the pane opens,
but the shell comes up plain. No directory in the tab title, no command marks,
none of the niceties. Nothing says anything went wrong, and the only spellings
that worked were the old DOS short path (`C:\PROGRA~1\...`) or burying extra
quotes inside the value. After this, the path you would naturally write works.
