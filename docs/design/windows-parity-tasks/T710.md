# T710 - The Windows chooser POLLS the session roster; Mac has the agent push it, and shows window renames

## Summary

Mac's bf318f55b replaced roster polling with an agent-pushed stream and made a window rename show up in the roster live. The win32 chooser still refetches on a timer (see T461), so a roster is stale between ticks, a rename never appears, and every fetch costs a round trip. Distinct from T461 (which is about holding one warm connection) and T462 (the session_cpu stream). Found by the T684 sweep.

## In plain terms

Open the machine chooser and look at a machine's session list: it is a
photograph, not a window. Start a session, finish one, or close one somewhere
else and the list keeps showing what was true when you selected the machine —
you have to click away and back to see the truth. And if you rename a window,
the row for its session keeps the old shell-derived name, so the rename looks
like it did nothing here. When this lands the list updates itself the instant
anything changes, and a window you renamed says the name you gave it.

## Goals

- [x] The chooser subscribes to the agent's pushed roster and refreshes rows
      live (create, exit, close, attach, detach) for the local machine and for
      a selected remote one — `SessionRosterProbe.zig`, retargeted beside the
      CPU meter on the same connection
- [x] An agent too old to push degrades silently to what the chooser does today
- [x] A row bound to an open pane shows the WINDOW's pinned title, with the
      pane title as a disambiguator when the window holds several panes
- [x] One decode path: a pushed roster and a `LIST_SESSIONS` reply produce the
      same rows — `remote_connection.decodeSessions`, which `requestSessions`
      now calls
