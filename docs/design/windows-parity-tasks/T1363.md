# T1363 - A clean acceptance run ends by printing CRASHED, because the harness's own force-kill looks like an exception

## Goals

- [x] a clean run no longer prints CRASHED for the app its own teardown killed (already landed in T2058, c8607b32a)
- [x] a process that really exits with 0xFFFFFFFF on its own is still called a crash, and a test proves it

## In plain terms

Every acceptance script closes by killing the app it started. Windows records a
forced kill with the same kind of exit code an actual crash produces, so the
post-run report at the bottom of a perfectly good run says `CRASHED` in capital
letters, complete with a stack-less "no WER record found" note. It is wrong every
single time, on every clean run, which is the worst possible place for a false
alarm: the block it appears in is the only thing that would tell you about a real
crash, and it has already taught everyone to scroll past it.

## Summary

`ConvertTo-GuiExitVerdict` (`test/win32/lib/GuiPostmortem.ps1:86`) classifies an
exit code structurally: high bit set == crash. That is the right default for an
unhandled exception, and it is also true of `0xFFFFFFFF`, which is what
`TerminateProcess` writes — and `Stop-RepoGhoztty`
(`test/win32/lib/CleanSlate.ps1:129`) tears every run down with
`Stop-Process -Force`. So the harness reports its own teardown as a crash.

Observed on the T552 run of `test\win32\sessions-running-cmd.ps1`, which scored
`ALL PASS (16 checks)` and still printed:

```
  GUI POSTMORTEM ghoztty.exe pid 18744
    verdict : CRASHED - 0xFFFFFFFF unnamed NTSTATUS
```

The fix is not to widen the "not a crash" range — `0xFFFFFFFF` really is
indistinguishable from an exception code by value alone. It is to let the killer
say so: the teardown knows it terminated the process, so it should mark that pid
as deliberately killed (a script-scoped set, or a flag on the postmortem call),
and the verdict should read `killed by the harness` for those and stay `CRASHED`
for everybody else. A process that vanished on its own with `0xFFFFFFFF` must
still report as a crash.

## Validation criteria

- [x] A clean run of an acceptance script that force-kills the app prints no
      `CRASHED` verdict for the pid its own teardown killed - the original
      reproducer, `test\win32\sessions-running-cmd.ps1`, re-run 2026-10-25:
      `ALL PASS (16 checks)` and no POSTMORTEM block at all
- [x] A process that exits with `0xFFFFFFFF` WITHOUT the harness having killed it
      still reports `CRASHED` - new section K of `test\win32\gui-postmortem.ps1`
      (K1-K4): a test-desktop child that runs `exit -1` on its own reads
      `verdict : CRASHED - 0xFFFFFFFF unnamed NTSTATUS` and is not marked killed
- [x] `test\win32\gui-postmortem.ps1` covers both directions - F (teardown
      kill) and J (Stop-RepoGhoztty kill) are the silent side, J3 and K the
      reported side; `ALL PASS (50 assertions)` on 2026-10-25

## Resolution

Already fixed at the source by **T2058** (c8607b32a, 2026-10-17):
`Stop-RepoGhoztty` now marks every pid it actually stopped as killed on the
launch record (`Set-GhozttyHarnessLaunchKilled`), and the teardown's own kill
already did since T527 - exactly the "let the killer say so" design this card
asked for. What T1363 still owed was the negative control at the exact
`0xFFFFFFFF` value: T2058's J3 proves an unkilled child is reported, but with
exit 5, which would have stayed green if someone widened the verdict's
not-a-crash range to swallow `0xFFFFFFFF`. Section K closes that.
