# T2952 - 4K fold glide: a GDI blit of near-zero area to the window stalls 20-40 ms in about one run of fourteen (both desk paints of a tick, plus a resize wait timeout), so a whole drag reads 13 frames over 16.7 ms

## Summary

Found while closing T2950. In one 4K drag-glide run of fourteen on the T2950 fix (ReleaseFast, release sandbox, ring trace; `temp\t2950-ab-B4.txt`, dir `%TEMP%\ghoztty-drag-glide\20261113-18*`), 13 ticks ran past 16.7 ms (max 62.8 ms) where the other thirteen runs had none. The new `stack trace bandpaint` line shows the band paint a memo HIT with `upd=0,0,0,0` (nothing invalid - T2950's fix holding) and `area=0`, yet `desk_out` 20-26 ms: one blit of only the light strips / names / a small carry took that long. The same ticks' vacated paint once spent 21 ms in its desk blit, and one tick logged a resize-wait timeout (`wait_us=24166 timeouts=1`). Other-process CPU that run was 1.9 cores, no higher than clean runs. That shape - a tiny GDI blit to the redirected window surface blocking for a frame or more - looks like the window DC waiting on the compositor or the GPU, not app work. Find out what the blit waits on (ETW/GPUView on a reproduction, or a `GdiFlush` timing split), and whether anything the app controls (batch limit, DC caching, flushing before the blit) avoids it.

## In plain terms

Dragging a divider on a 4K screen is almost always smooth now, but every so often a drag hitches for one to four frames. This card asked what that hitch is waiting on. The answer: the app hands Windows a small picture to put in its window, and Windows makes it wait 15-55 ms before taking it. During that wait the app is idle, and so is the rest of the machine. Naming exactly what Windows was busy with takes an administrator trace, which only the user can start.

## Findings (2026-11-13)

Probe: `src/apprt/win32/stall_probe.zig` (+ `compose_gap.zig`), emitting a `stack trace stall` line for every laid glide tick under `GHOZTTY_STACK_TRACE`: tick wall vs the UI thread's own CPU (thread cycles), every desk blit to the window timed alone (count, sum, longest, its CPU, kind `stretch`/`bitblt`/`flush`, area), and DWM's completed-frame id delta and compose age. Analyzer: `temp	2952-stalls.ps1 -Soak <file>`.

- **Soak 1** (`temp	2952-soak1.txt`, `-analysis.txt`; 20 x 4K ReleaseFast runs, release sandbox): the stall shape appeared in 4 runs (13, 15, 16, 17), clustered there with 2-5 per run, and in none of the other 16. In all 10 of its ticks (18-63 ms) the time is ONE window desk blit, 15-54 ms of wall in which the UI thread ran 0.1-0.3 ms of CPU. Tick CPU was 2.5-5 ms of 18-63 ms. Other processes used 0.8-1.9 of 32 cores, so this is not descheduling: the thread is blocked inside GDI's write to the window's redirected surface. Baseline ticks: cpu/wall 0.83, longest blit mean 0.3 ms.
- **Soak 2** (`temp	2952-soak2.txt`): no episode in 20 runs. The episodes are an external, episodic state, not a per-tick cost.
- A blocked write to the redirection surface is GDI waiting on its sync with DWM (or the GPU behind it). The app cannot shorten that wait. It can only stop writing GDI to a redirected window, which is the no-redirection-surface path (`GHOZTTY_COMP_NOREDIR`; T2548/T2575 done, T2576's black-child audit still open).
- The other over-budget shape, CPU-bound and off-CPU time in placement outside the blits, is filed as T2953.
