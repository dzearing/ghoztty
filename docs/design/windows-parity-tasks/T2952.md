# T2952 - 4K fold glide: a GDI blit of near-zero area to the window stalls 20-40 ms in about one run of fourteen (both desk paints of a tick, plus a resize wait timeout), so a whole drag reads 13 frames over 16.7 ms

## Summary

Found while closing T2950. In one 4K drag-glide run of fourteen on the T2950 fix (ReleaseFast, release sandbox, ring trace; `temp\t2950-ab-B4.txt`, dir `%TEMP%\ghoztty-drag-glide\20261113-18*`), 13 ticks ran past 16.7 ms (max 62.8 ms) where the other thirteen runs had none. The new `stack trace bandpaint` line shows the band paint a memo HIT with `upd=0,0,0,0` (nothing invalid - T2950's fix holding) and `area=0`, yet `desk_out` 20-26 ms: one blit of only the light strips / names / a small carry took that long. The same ticks' vacated paint once spent 21 ms in its desk blit, and one tick logged a resize-wait timeout (`wait_us=24166 timeouts=1`). Other-process CPU that run was 1.9 cores, no higher than clean runs. That shape - a tiny GDI blit to the redirected window surface blocking for a frame or more - looks like the window DC waiting on the compositor or the GPU, not app work. Find out what the blit waits on (ETW/GPUView on a reproduction, or a `GdiFlush` timing split), and whether anything the app controls (batch limit, DC caching, flushing before the blit) avoids it.
