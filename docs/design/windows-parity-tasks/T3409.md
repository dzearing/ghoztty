# T3409 - machine-lock.ps1 section I recurses without end when it runs inside another acceptance sweep

## Summary

Inside an acceptance-parallel run (GHOZTTY_TESTRUN_OWNER inherited), section I's own holder Enter-MachineLock -Kind testrun is NESTED and takes no mutex (log: 'TEST RUN LOCK: nested inside pid 42688's run; not taken for harness-testrun-holder'), so the I5 fixture ap-run.ps1 - which clears the owner - finds the scoped lock free and really runs acceptance-parallel run -Scripts machine-lock.ps1, which reaches section I again. 2026-11-22 09:34-09:59 lane b: 57 levels deep, 210 processes, the due sweep wedged 25 min until killed. Fix: clear GHOZTTY_TESTRUN_OWNER in-process (and restore it) around section I's holder acquisitions so the harness really holds the scoped lock, and make ap-run.ps1 refuse to run when it is itself under a machine-lock harness (a depth guard env var) so a regression cannot fork-bomb the box again. Prove it: run machine-lock.ps1 through acceptance-parallel run and assert one level only.

## In plain terms

One of the loop's own self-tests, when run as part of a bigger batch of tests,
accidentally started another copy of the whole batch, which started another
copy, and so on: 57 copies deep and 210 processes before someone killed it,
and the batch sat stuck for 25 minutes. Now the self-test behaves the same
inside a batch as on its own, and if that ever breaks again it stops at the
first copy instead of filling the machine.

## Goals

- [x] Section I really holds its lock even when run inside another sweep
- [x] A copy of the harness started by its own I5 fixture refuses at once (depth guard)
- [x] Proven inside a real acceptance-parallel run: one level only
