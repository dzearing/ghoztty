# T2465 - comp spike draws through a D3D11 device (hardware, then WARP) and recovers a lost device without a restart; the RDP run and the cadence/CPU numbers are split out (T2360 criterion 3)

## Summary

The spike used colour sprites only, so it never needed a D3D device and said
nothing about Remote Desktop or a machine with no GPU. It now paints the blade
into a CompositionDrawingSurface on a D3D11 device (hardware first, then WARP),
and recovers a lost device by swapping a fresh one in under the surface and
redrawing - on `WM_WTSSESSION_CHANGE`, on a 250 ms device check, and on demand
mid-glide (`--rebind-after-glide`).

Originally this task also carried the real RDP run and the WARP cadence/CPU
comparison. Neither can be done this turn: an RDP session has to be originated
from a second machine (**T2735**), and the live per-window oracle stopped
seeing compositor animations on this box on 2026-11-05 (**T2733**), which the
measurement (**T2734**) waits on.

## In plain terms

The new, smoother animation approach has to keep working when you use the
terminal over Remote Desktop or on a computer with no graphics card. This
teaches the test program to draw the way the real app will - through the
graphics layer Windows always has, even with no GPU - and to pick itself back
up when Remote Desktop swaps the graphics hardware out from under it, instead
of going blank. The actual Remote Desktop trial and the speed numbers are
separate follow-ups.

## Goals

- [x] D3D11 device: hardware, then WARP; never fail for lack of a GPU
- [x] Blade drawn into a CompositionDrawingSurface (the content path the app will use)
- [x] Device-loss recovery: new device, `SetRenderingDevice`, redraw - visuals and running animations untouched
- [x] Hooked to `WM_WTSSESSION_CHANGE` plus a timer for losses no message announces
- [x] A way to drive the recovery on purpose mid-glide, and a harness check that scores it
- [ ] Real RDP disconnect/reconnect run -> T2735 (needs a second machine)
- [ ] Frame rate and CPU per glide, WARP vs hardware vs Mesa -> T2734 (waits on T2733)

## Result (2026-11-05, lane A)

New module `src/apprt/win32/comp_surface.zig`: `Device.create(.auto|.hardware|.warp)`
(D3D11CreateDevice, driver order in a unit-tested `driverOrder`),
`Surface.init` (ICompositorInterop::CreateGraphicsDevice slot 5,
ICompositionGraphicsDevice::CreateDrawingSurface slot 6,
ICompositor::CreateSurfaceBrushWithSurface slot 24), `draw` (BeginDraw with
IDXGISurface -> ID3D11Texture2D, UpdateSubresource slot 48 into exactly the
atlas box at the returned offset, EndDraw always), `rebind`
(ICompositionGraphicsDeviceInterop::SetRenderingDevice slot 4 + redraw) and
`recoverIfLost` (GetDeviceRemovedReason slot 39). Every slot read from the
10.0.22621.0 headers.

Spike: `--surface=auto|hardware|warp`, `--rebind-after-glide=N`,
`--rebind-to=`, `--ghost-alpha=`; prints `DEVICE init/rebind/lost/final`,
`SESSION`, `CPU`. Runner: `scripts\comp-spike.ps1 -Surface -RebindAfterGlide
-RebindTo -CheckSurface -X -Y`, plus a `DWMCPU` line (dwm.exe times are not
readable unelevated here, and it says so).

Measured:

| run | device | rebind | draws | notes |
|---|---|---|---|---|
| bg desktop, `-Surface warp -RebindAfterGlide 3 -RebindTo hardware` | WARP -> hardware | ok, 116 ms | 2 | removed_reason 0x0 after |
| live, `-Surface hardware` | hardware | - | 1 | init ok, session_notify=true |
| live, `-Surface warp` | WARP | - | 1 | init ok |
| live, `-Surface warp -RebindAfterGlide 3 -RebindTo warp` | WARP -> WARP | ok, 6 ms | 2 | the redraw produced a captured frame |

CPU per glide (spike process): none 1477 ms, hardware 1434 ms, WARP 1414 ms,
gdi 1416 ms. The surface adds nothing measurable; the number is dominated by
the two sampler threads' polling in every mode, so it is not a cost of either
path (T2734 measures it properly).

Live cadence: NOT MEASURED. Every comp run today, colour sprites included,
captured 1 frame and an edge that never moved, while gdi scored 0.278 as
before - see T2733 for what was ruled out.
