# T2734 - comp spike WARP cadence and CPU: score glides on a WARP drawing surface vs hardware vs today's Mesa/WARP GL path with the per-window oracle (T2360 criterion 3, measurement half)

## Summary

T2465 landed --surface=auto|hardware|warp and -Surface on scripts\comp-spike.ps1, but the live oracle regressed the same day (T2733), so no cadence number exists for the WARP surface. Once T2733 is green: run -Live -Modes comp -Surface warp/hardware -CheckSurface, record advance/holds/max gap, and compare CPU per glide (the spike's process CPU is dominated by its two sampler threads - ~1.4 s per glide in every mode - so measure with the samplers' cost subtracted or sample the UI thread and dwm). Also compare the app's own Mesa/WARP GL path (GHOSTTY forced-Mesa run) for the same glide.

## In plain terms

Before the new animation approach can ship, it has to be shown to work on
computers with no usable graphics card, where Windows draws everything with
its software renderer. This measures exactly that: how smooth the glide is and
how much processor time it costs, next to what such a computer runs today.
Today's answer is that it does not animate at all - the glide is switched off
on a software renderer - and the one jump it does costs about 200 ms of
processor time; the new approach glides at nearly every refresh for a small
fraction of that.

## Goals

- [x] Live cadence for the blade glide on a WARP drawing surface and on a hardware one
- [x] CPU per glide with the oracle's own sampler threads taken out
- [x] DWM's CPU readable without elevation, so the compositor's off-process work is priced too
- [x] Today's app path priced for the same toggle, on Mesa/WARP and on the GPU
- [x] Numbers written down, with what they can and cannot say

## Result (2026-11-07, lane A)

All on this box (RTX 4090, 120 Hz, OS 26300.9818), 24 glides of 300 ms + 450 ms gap.

**Composition spike** (`scripts\comp-spike.ps1`), cadence from the live ghost
(`-Live`), in-process CPU from the background desktop (no WGC oracle there):

| path | advance (live) | max gap | in-process CPU / glide | UI thread / glide |
|---|---|---|---|---|
| comp, WARP drawing surface | 0.943-0.944 | 24-25 ms | <= 0.65 ms (one 15.6 ms tick in 24 glides) | 0.65 ms |
| comp, hardware drawing surface | 0.943 | 25 ms | <= 0.65 ms | 0.65 ms |
| comp, colour sprites | 0.942 | 25 ms | 0.00 ms | 0.00 ms |
| gdi (hand-stepped 16 ms timer, today's shape) | 0.270-0.278 | 55-57 ms | 7.16 ms | 7.16 ms |
| idle | 0 frames | - | 0.00 ms | 0.00 ms |

DWM's CPU over the whole live run (all windows on the box, so noisy), per
glide: idle 302 / 334 ms, gdi 303 / 324 ms, comp-on-WARP 359 / 344 ms. So the
compositor adds roughly 10-57 ms of dwm.exe time per glide, and that bound
INCLUDES the oracle's own WGC captures (815 frames vs gdi's 232), which DWM
also performs.

**Today's app path** (`scripts\comp-gl-baseline.ps1`, background desktop,
sidebar collapse/expand toggle with both motions at 300 ms):

| build | path | what happens | CPU / toggle |
|---|---|---|---|
| Debug | Mesa on WARP (`impl=fallback`, Basic Render Driver) | **snaps: motion is off on a software renderer** (landed=0) | 193-206 ms |
| Debug | GPU OpenGL | glides, 655 frames / 650 steps | 161-162 ms |
| ReleaseFast (sandboxed) | GPU OpenGL | glides, 667 frames / 651 steps | 82-115 ms |
| ReleaseFast | Mesa on WARP | **cannot be produced**: the forcing seam is Debug-only (`OpenGL.zig forcedVersion`), and the script refuses the row | - |

What this says for T2360 criterion 3 (no-GPU half): on a WARP surface the
compositor glides at ~94% of 120 Hz refreshes, while today's Mesa/WARP path
does not glide at all, and it costs well under 1 ms in-process plus tens of ms
in DWM per glide against ~200 ms for today's single snap (Debug app; Mesa and
WARP themselves are release DLLs either way, and the GPU glide halves from
Debug to ReleaseFast, so a release Mesa snap is still on the order of 100 ms).
**No worse than today's Mesa/WARP path: met, by a wide margin**, on this box.

Limits, stated: the DWM device here is still the GPU (only the drawing
surface is WARP); a true no-GPU machine composes on WARP inside DWM too, which
is T2735's (RDP / Cloud PC) to measure. The DWM number is the whole box's and
carries the oracle's captures.

### What changed

- `src/comp_spike_main.zig`: the `CPU` line now also reports `samplers_ms`,
  `work_ms` / `work_per_glide_ms` (process minus both sampler threads) and
  `ui_ms` / `ui_per_glide_ms` (GetThreadTimes on the UI thread), read before
  the samplers are joined.
- `scripts\comp-spike.ps1`: `Get-DwmCpuMs` falls back to
  `Win32_PerfRawData_PerfProc_Process`, so `DWMCPU` has a number for an
  ordinary user (it used to say `unavailable` on every run).
- New `scripts\comp-gl-baseline.ps1`: prices today's app path for the same
  toggle; `-ReleaseSandbox` for an optimized build; refuses a mesa-warp row
  whose software renderer never took (demonstrated: the ReleaseFast run reads
  `FAILED: the software renderer never took`).

## Validation criteria

- [x] WARP and hardware drawing surfaces glide live at >= 0.9: SURFACE PASS 0.943 / 0.943 (24 glides each), 0.944 (8 glides)
- [x] Sampler-subtracted CPU reported: bg runs give comp <= 0.65 ms/glide vs gdi 7.16 ms/glide; live `samplers_ms` accounts for ~99% of process CPU
- [x] DWM CPU read without elevation: `DWMCPU mode=comp run_ms=8,625.0` (was `unavailable`)
- [x] Today's Mesa/WARP path priced with the renderer verified (`impl=fallback`, Basic Render Driver): 193-206 ms per toggle, snap
- [x] The baseline refuses a row on the wrong renderer: ReleaseFast mesa-warp -> FAILED (the seam is Debug-only)
