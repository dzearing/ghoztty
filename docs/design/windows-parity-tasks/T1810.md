# T1810 - +rearrange (and any other verb that calls deferSetFocus) may activate a background Ghoztty window: SetFocus on a child of an inactive top-level activates it

## Summary

Found during T1797. The CLI-create verbs now open in the background, but +rearrange still ends with App.deferSetFocus(focused pane) in IpcHandlers (the post-swap focus restore). When the rearranged window is NOT the active one, SetFocus on its child activates that window within our queue - a smaller cousin of the focus steal T1797 removed. Mac's 3081022ec did not list +rearrange. Measure on the test desktop (rearrange a background window while another is active; read GetGUIThreadInfo), and if it activates, only restore focus when the window was already active. Same audit for +close of a pane in a background window (closeSplitPane focuses the next pane).

## In plain terms

The worry was that when a script rearranges or closes panes in a Ghoztty
window you are not looking at, that window would jump in front of you and
take your typing. It does not: Ghoztty already throws away a "move the
keyboard here" request aimed at a window that is not the one in front. That
had never been measured for these two commands, so it is now, and a future
change that breaks it will turn the test red.

## Goals

- [x] Measure whether `+rearrange` of a background window activates it
- [x] Measure the same for `+close` of a pane in a background window
- [x] Keep both measured from now on, with proof the check can fail

## Outcome: already fixed, at the source

Every call site named here (`IpcHandlers` post-swap restore, `closeSplitPane`)
goes through `App.deferSetFocus`, and every `WM_APP_SETFOCUS` (main loop and
all four modal pumps) is executed by `App.performDeferredFocus`, which drops
the assert unless the target's root window is the foreground window (input
desktop) or the GUI thread's active window (background desktop). That guard is
T105's `beb91b43f` (2026-07-20), extended off the input desktop by T215's
`5e86eab08` (2026-08-10). So no deferred focus can activate a background
window; the task's premise was the pre-T105 behavior. No product change.

## Validation criteria

- [x] `+rearrange` of a background window while typing in another Ghoztty
  window leaves the active window and the focused pane unchanged - arm L of
  `test\win32\cli-focus-policy.ps1` (ALL PASS, 51 assertions, 2026-10-12)
- [x] `+close` of a pane in a background window, same - arm M (same run)
- [x] both, with the user in another app: nothing activated, no pane takes the
  keyboard - arms N and O (same run)
- [x] the arms can fail: a throwaway build with the `performDeferredFocus`
  guard removed (`zig-out-neg1810`) scored 6 FAILURES on L/M/N/O - the
  rearranged window activated and its pane took the keyboard - so the green
  run measures the guard, not an inert oracle
