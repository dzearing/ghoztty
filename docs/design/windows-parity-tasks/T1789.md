# T1789 - a config reload that changes background-opacity does not make open windows translucent (or opaque): only window creation applies it

## Summary

Found by T1787. Window.onConfigChange re-applies background-blur (applyBackgroundBlur) but never background-opacity: setTranslucent runs only at window creation, and composeOpaqueLayer (viewer hosts, tab-rename box) only when a child is created under a translucent config. Mac re-syncs window opacity on reload. Reloading 1.0 -> 0.6 leaves every open window opaque (the renderer's alpha is ignored until setTranslucent(true)); new windows are fine. Fix: on reload, call setTranslucent(opacity < 1 and not toggled-opaque) per window and composeOpaqueLayer on existing viewer hosts; cover with a reload step in test\win32\translucent-window.ps1.

## In plain terms

Changing how see-through the terminal is (`background-opacity`) and reloading
the config did nothing to windows that were already open - only new windows
picked it up, so you had to close and reopen every window to see the change.
Now open windows follow the reload straight away, in both directions, the way
they do on Mac, and a window you had switched to opaque by hand stays opaque.

## Goals

- [x] A config reload makes open windows translucent (or opaque) to match `background-opacity`
- [x] A viewer pane opened while the window was opaque keeps its toolbar visible once the window turns translucent
- [x] The "toggle background opacity" choice on a window survives a reload, as on Mac

## Validation criteria

- [x] 1.0 -> 0.6 reload turns an open window translucent; 0.8 -> 1.0 turns it opaque; 1.0 -> 0.6 again translucent - `test\win32\opacity-reload.ps1` B/D/E (background desktop, `window translucent=` lines counted per step), ALL PASS (20)
- [x] a viewer host created under 1.0 becomes an opaque layer on the reload (and is NOT one before it - the control) - same script, A/B, reading WS_EX_LAYERED cross-process
- [x] toggled-opaque window stays opaque across a 0.6 -> 0.8 reload - same script, C
