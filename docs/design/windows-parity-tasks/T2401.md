# T2401 - Pulling out the Windows pane sidebar (the left pane) snaps it open in one frame instead of sliding it out, as Mac's sidebar glides

## Summary

User report 2026-10-28 (interactive, installed build 1.48.4+a691d5f4d): when the user pulls out the left pane (the pane sidebar), it jumps straight to its open width instead of sliding out. A sidebar column glide exists on Windows (T2365 put it on the vsync frame clock; T2391 fires it in the frame lab), so either the path the user takes skips it, or the glide runs but nothing draws its in-between frames. First find which gesture 'pull out' is: the toggle button, the keybind, dragging the collapsed rail's edge outward, or a hover reveal. Test every one, and make each open AND close slide with Mac's duration and curve (read the Mac sidebar code for the reference and cite it). Every glide frame must be fully painted, with no black or stale areas in the panes it pushes over (same bar as T2400). Acceptance: a WGC capture (T2373 camera) of each gesture shows the sidebar width moving through intermediate values over several refreshes, with no single-frame jump and no unpainted frames; and the user sees it slide in the relaunched installed build.

## In plain terms

When you pull the left sidebar out (drag its edge, or click its toggle), it is
supposed to slide open the way it does on a Mac. On Windows it often looked
like it just jumped open. The slide was running, but the work of laying out the
panes it pushes over used up the first part of the slide before a single frame
of it was shown, and Mac's slide does most of its moving in that first part.
Now the slide starts counting from the first frame you can actually see, so you
see the whole motion.

## Goals

- [x] Find which gesture "pulling out" is, and whether the glide runs on it

- [x] A glide's first frame counts at most one display period, for the column AND the grid's cards, so a slow layout pass cannot spend the motion before it is shown
- [x] Log what each glide put on screen (frames, worst gap, worst paint, first-frame lag) so the user's own log answers "did it slide"

## Findings

- Gestures: the rail's toggle button, the header toggle, the rail's edge drag (the "pull") and a divider drag all flip collapsed/expanded through `Window.setPaneSidebarExpanded` and run the T2291 column glide (240 ms, Mac `PaneSidebarState.columnAnimation` `.timingCurve(0.2, 0.8, 0.2, 1, duration: 0.24)`; duration and curve already matched). Ctrl+Shift+S hide/show does not glide the column on Mac either (`PaneSidebarHost.swift`: the overlay is inserted with no transition; only the grid glides) - Windows matches.
- The user's log (installed 1.48.4, 2026-10-28 00:29Z): the edge-drag glides DID start (`column glide expanded from=78 to=238`) but landed 455 ms later, not 240, while every layout pass (logged by the website viewer's nav tips) came ~32 ms apart: the UI thread was running ~30 fps during the glide. With Mac's ease-out putting 80% of the motion in the first 80 ms, a first frame that arrives after the layout pass that started it shows the column most of the way out: a snap.
- Off-desktop (`glide-probe`, 120 Hz box, with and without an HTML viewer pane): 24-30 painted frames per glide, paint <= 11 ms, first frame 10-14 ms after start. So the app-side glide paints; the starvation is on the real desktop with real composition, which this seat cannot drive while the user is present.
