# T1579 - A monitor move leaves the terminal at the old DPI scale, and a scrollbar-mode change goes unnoticed, unless a popup happens to be open

## Summary

The terminal HWND is a WS_CHILD, so it never receives WM_DPICHANGED or the WM_SETTINGCHANGE broadcast; Window.windowWndProc has no WM_DPICHANGED arm at all and its WM_SETTINGCHANGE arm does not tell the panes' scrollbars. Found doing T742: the only thing that refreshes Surface.scale or re-reads the scrollbar mode today is one of the two POPUPS getting the broadcast, i.e. it works if and only if the palette or search bar was open at the time. Wanted: Window forwards both to every pane (adoptPane already re-reads DPI by hand for the same reason), with pure assertions for the fan-out and an acceptance arm that moves a window between monitors with nothing open.

## In plain terms

Drag a Ghoztty window onto a monitor that uses a different display scale and
the terminal text stayed the size it was on the old monitor - too small or too
big and blurry - unless the command palette or search bar happened to be open
at that moment. The window's own tabs and title stayed at the old size too.
Now the whole window, and every pane in it, re-sizes for the new monitor, and
a change to Windows' "automatically hide scroll bars" setting reaches every
terminal the same way.

## Goals

- [x] the top-level window handles a DPI change: its own scale and chrome fonts, and the size Windows suggests
- [x] every pane in every tab is told the new DPI - terminal and viewer - with nothing open
- [x] the terminal's font actually changes size (the core was never handed the new scale, popup or not)
- [x] a settings broadcast reaches every terminal's scrollbar, not only the one whose popup is open
- [x] pure assertions for the forwarding rule, and an on-box acceptance arm

## Validation criteria

- [x] Forwarding rule unit-tested: `window_broadcast.zig` (none lane) - DPI change rescales both pane kinds, a setting change re-reads a terminal's scrollbar and leaves a viewer alone, every event owes a terminal something, DPI is LOWORD(wparam) and 0 is refused.
- [x] A DPI change with no popup open re-scales every terminal pane, focused and unfocused: `test\win32\dpi-change.ps1` B1-B4 (chrome reports 180 dpi; both panes 56 -> 37 columns, read from inside the shell with `mode con`) and C1-C2 (back to 120 dpi, 56 columns).
- [x] A settings broadcast with no popup open reaches both panes: `dpi-change.ps1` D1 (`window setting change forwarded panes=2`), app and pane still live.
- [x] The oracle can fail: `dpi-change.ps1 -NegativeControl` (message not sent) -> 4 FAILURE(S) on B1-B4.
- [x] Floor: `floor-lane.ps1 -Lane all`, P1-P3, `-Lane harness`.
