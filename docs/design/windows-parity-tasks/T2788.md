# T2788 - A pane the glide resizes takes 1-6 ms (median 3.8) from its resize wake to its swap, and the next tick's pane batch that moves it while it is still drawing costs 3-4 ms instead of 0.5: the slow-tick tail of the fold glide at 120 Hz

## In plain terms

While a divider drag folds panes away, the two panes being resized redraw
themselves after every frame of the glide. That redraw often is not done by
the time the next frame moves the panes again, and moving a pane while it is
still drawing makes that frame several times slower. Those are the frames
that miss the screen's refresh on a 120 Hz display.

## Summary

Split out of T2732 (2026-11-07). `GHOZTTY_STACK_TRACE=ring` stamps added in
T2732 (`stack trace filled ... defer_end= sizes= size_qpc= fill_qpc=`, and
`began=` on each `stack trace present`) break the live pass's pane batch
down. Release sandbox, 120 Hz, the T2732 glide probe (5 panes, a viewer
second, 1875x1125 px @1.25):

- the panes' own `WM_SIZE` work inside `EndDeferWindowPos` (including the
  uncovered-strip fill) is ~0 (under 0.01 ms a batch): the batch's time is
  all the OS;
- `SwapBuffers` itself is short (mean 0.14 ms, p99 0.6 ms) and almost never
  overlaps the batch;
- the batch is slow (over 2.5 ms; 27% of batches) when **no** swap landed in
  the 4 ms before it - i.e. a renderer is mid-draw on the frame the previous
  tick's held resize woke - and fast (0.44-0.6 ms mean, 0-1% slow) when the
  panes swapped 1-4 ms before;
- wake (`filled`, the held resizes applied) to that pane's next swap begin:
  p10 1.2 / p50 3.8 / p90 5.7 ms, against an 8.3 ms period whose batch runs
  ~1-2 ms into the tick.

Refuted in T2732, so not to be retried as the fix: holding a renderer's swap
while a batch runs (bounded futex wait; A/B late 60/92/52 vs 140/54/49, no
win - the collision is the draw, not the swap), and the T2418
`GHOZTTY_PRESENT_RETIRE` RW gate (removes the overlap, the UI then waits on
the in-flight swap+finish: late 57, mean tick up 4.7 -> 4.9 ms).

Directions: (a) why a resized pane's frame takes 3.8 ms to draw when the grid
is held (T2459) - the renderer's work at a new viewport size (target realloc,
full rebuild?) under `GHOZTTY_RESIZE_TRACE`'s frame stages; (b) make the
batch not wait on a drawing surface (move a pane that only moves by its
composition visual, T2732 direction c); (c) wake the renderers earlier in the
tick (before the strip faces / desk fill) so the draw is done by the next
batch.

### Measured 2026-11-08 (lane b)

New stamps on `GHOZTTY_RESIZE_TRACE` (ring) split a resized pane's frame
from the UI's `held-apply` (the held resize applied) through the renderer's
`wake`, `update-begin`, `state-locked`, `critical-done`, `cells-rebuilt`,
then the existing `draw-begin`/`target-ready`/`synced`/`finish-*`/
`swap-begin`:

- wake -> cells rebuilt is ~0.1 ms: the terminal lock, the cell rebuild and
  the target resize are NOT the cost (direction (a)'s "full rebuild" guess is
  refuted).
- the frame's time is GPU-bound: `target-ready -> synced` (buffer uploads,
  p50 0.5 / p90 9.8 ms) and `Frame.complete`'s `glFinish` (p50 3.0 ms).
- **Refuted: ending the frame with `glFlush` instead of `glFinish`.**
  Release sandbox, 120 Hz, alternating A/B x3: finish late 227/248/248, mean
  batch 5.5/5.9/6.1 ms, slow batches 45-49%; flush late 276/286/288, mean
  batch 9.8/9.5/8.6 ms, slow 50-51%. The move then waits on the same pending
  GPU work, longer. Do not retry.
- **Box caveat:** today's box is far slower than 2026-11-07's (yesterday's
  base build `zig-out-t2732base` reads late=277, mean tick 12.1 ms, against
  late=47, 3.9 ms then), so absolute numbers from today are not comparable to
  the Summary's; only alternating A/B verdicts are. Re-take the baseline on a
  quiet GPU before judging the validation criteria.

What is left: the GPU work a resized pane's frame queues (the buffer
uploads at `synced`, then the draw) and the batch moving a window whose
frame is still on the GPU - direction (b), moving a pane that only moves by
its composition visual, stays the lever.

### Fixed 2026-11-08 (lane b): the pane window is no longer a GL drawable

On the composition path (the default since T2514) a pane renders offscreen
and presents through a swap chain, yet its GL context was still made on the
pane's own window, so that window carried a GL pixel format. Moving such a
window (`EndDeferWindowPos` in every glide tick) waits on whatever that pane
still has queued on the GPU. The context now lives on a hidden 1x1 helper
(the T2615 presenter-path shape), so the pane window is a plain child window
the batch moves without the driver. A pane that drops to SwapBuffers (a
failed or unavailable composition present) moves its context back onto its
own window first (`Surface.adoptPaneDrawable`). `GHOZTTY_PANE_GL_HELPER=0`
opts out.

Release sandbox, 120 Hz, the T2732 glide probe, alternating A/B x3 (one
release exe, knob on/off; run on-3 was re-taken after lane A's timing lock
blocked it):

| arm | late | mean tick | slow batches (>2.5 ms) | mean batch |
|---|---|---|---|---|
| helper (new) | 28 / 37 / 28 | 4.1-4.3 ms | 3.9 / 3.9 / 4.1% | 0.75-0.81 ms |
| pane window (old) | 340 / 325 / 357 | 11.0-12.1 ms | 45.0 / 46.4 / 47.5% | 5.85-6.65 ms |
