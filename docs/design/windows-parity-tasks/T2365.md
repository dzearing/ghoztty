# T2365 - Every Windows animation (stack glide, hero, banner, sidebar column/reorder/xfade, fades) is clocked by a 16 ms SetTimer, which this box delivers at 16 or 31 ms about half the time each (mean 25.6 ms, ~39 fps), so glides judder between one and two vsyncs; Mac steps its glide on a 120 Hz timer inside CoreAnimation. Drive them from one vsync-aligned frame clock

## Summary

User report (2026-10-27, interactive): blade collapse works, "but it's JANKY.
it doesn't smoothly glide like a video game smooth 60fps. it stutters and
jitters as if it didn't know what animation meant."

Evidence (measured on the user's box, 2026-10-27): a WinForms timer (which
is `SetTimer`/WM_TIMER) at 16 ms over 60 ticks: mean 25.6 ms, min 15, max 37.
Histogram: 15-16 ms x19, 30-32 ms x35, the rest in between. The display is
**120 Hz** (`DwmGetCompositionTimingInfo` rateRefresh 10000000/83333; WMI's
`CurrentRefreshRate` wrongly says 60), so a glide updates on about one refresh in three.
Windows 10 2004+ keeps timer resolution per process, and nothing in src/
calls `timeBeginPeriod` or uses a high-resolution waitable timer. So a 16 ms
WM_TIMER snaps to the 15.6 ms system tick and often lands one tick late.
WM_TIMER is also the lowest-priority message: it is only made when the
queue is empty, so input and paint traffic during a drag delay it more.

Every animation is on this clock:
- stack glide: `STACK_SLIDE_TICK_MS = 16` (Window.zig ~L323, tick at
  `stackSlideTick` ~L8548)
- hero: `HERO_ANIM_TICK_MS = 16`
- banner: `banner_layout.COLLAPSE_TICK_MS = 16`
- sidebar: `pane_sidebar_transition.frame_ms = 16`; `pane_sidebar_motion.frame_ms = 33`
  (30 fps, on purpose)
- fades: BellBorder, HoverTint, QuickTerminal, ViewerTOCPanel, focus glow

The glide math is already wall-clock based (`dt` from `Instant`), so the
motion is correct. It is sampled at uneven times and shown on whichever vsync
comes next, which is what reads as judder.

Mac: `PaneStage` steps the glide from a 120 Hz `Timer`, and every card moves
inside one `CATransaction` that CoreAnimation presents on the display clock.

Fix:
1. One per-window (or per-app) frame clock aligned to vsync, replacing the
   per-animation SetTimers. For example, a worker thread blocking on
   `DCompositionWaitForCompositorClock` (Win11) or `DwmFlush` that posts one
   coalesced WM_APP_FRAME per vblank while any animation is live. A
   `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` timer waited on in the run loop's
   `MsgWaitForMultipleObjects` is the fallback. Animations subscribe and
   unsubscribe; the clock stops when none is live.
2. Sample each animation at the PREDICTED present time (next vblank), not
   at "now", so positions move by an even step per displayed frame.
3. Make each glide tick a live relayout (`layoutSplitsLive`, like T2359), and
   measure per-tick cost with the T1343 drag-stats line. If a tick does not
   fit in an 8.3 ms frame (120 Hz), fixing the clock will not be enough and T2360
   (DComp) becomes the fix.
4. Lift the sidebar sheen's deliberate 33 ms cadence to the frame clock.

## In plain terms

Every animation in the Windows app - panes gliding, the banner folding, the
sidebar sliding, fades - used to wake up on a cheap Windows timer that fires
"about every 16 ms" but in practice every 16 or 31 ms at random. Motion
sampled that unevenly looks like stutter. Now all of them step together on
the screen's own refresh, once per displayed frame, like a game does.

## Goals

## Design (recorded 2026-10-27)

- `src/apprt/win32/FrameClock.zig`: a worker thread blocks on
  `DCompositionWaitForCompositorClock` (Win11; a high-resolution waitable
  timer at the display period where it is missing) and posts ONE
  `WM_APP_FRAME` to `App.msg_hwnd` per vblank while anything is subscribed.
  The UI thread then `SendMessage`s each subscriber the `WM_TIMER` it already
  handled, so every converted animation only swapped `SetTimer`/`KillTimer`
  for `FrameClock.arm`/`disarm`; handlers are unchanged and all animations
  step in the same frame. `arm` falls back to the old `SetTimer` when no clock
  runs (tests, a window on another thread, a full table).
- Coalescing: one frame in flight. `pending` clears only AFTER the dispatch
  walk, so a dispatch slower than a frame skips the next post instead of
  queueing one: a posted message outranks input in `GetMessage`, and
  back-to-back frame posts would starve the mouse moves a glide follows.
- Item 2 (sample at the predicted present time) was NOT needed: dispatch
  right after the compositor tick lands every frame within ~0.2 ms of the
  period (probe max 16.8 ms at a 16.5 ms period), so `now` already advances
  by an even step per displayed frame.
- Oracle: under `GHOZTTY_PERF` every finished run prints `frame clock
  id=0x.. ticks= intervals= mean_us= max_us= doubled= period_us=
  cost_mean_us= cost_max_us= source=`. `GHOZTTY_FRAME_CLOCK=settimer` drives
  the same dispatch from the old 16 ms WM_TIMER (A/B on one build);
  `GHOZTTY_FRAME_CLOCK_PROBE=<delay>,<duration>` runs a do-nothing subscriber
  that measures the clock apart from any animation's cost.
- The busy light (`busy_light.FRAME_MS`, 33 ms) stays on its own timer: it
  circles for as long as a pane is busy (hours), it was not in this task's
  list, and doubling its whole-desk repaint rate is a CPU cost with no glide
  to smooth.

## Relationship to T2360

This is the STOPGAP: a vsync clock on the UI thread gets hand-stepped glides
to the panel's refresh while the work fits in 8.3 ms. The real fix is T2360
(compositor-driven animation, as Mac does). Do not let this task grow past
the clock and the interval oracle.
