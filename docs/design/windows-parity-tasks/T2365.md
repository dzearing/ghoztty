# T2365 - Every Windows animation (stack glide, hero, banner, sidebar column/reorder/xfade, fades) is clocked by a 16 ms SetTimer, which this box delivers at 16 or 31 ms about half the time each (mean 25.6 ms, ~39 fps), so glides judder between one and two vsyncs; Mac steps its glide on a 120 Hz timer inside CoreAnimation. Drive them from one vsync-aligned frame clock

## Summary

User report (2026-10-27, interactive): blade collapse works, "but it's JANKY.
it doesn't smoothly glide like a video game smooth 60fps. it stutters and
jitters as if it didn't know what animation meant."

Evidence (measured on the user's box, 2026-10-27): a WinForms timer (which
is `SetTimer`/WM_TIMER) at 16 ms over 60 ticks: mean 25.6 ms, min 15, max 37.
Histogram: 15-16 ms x19, 30-32 ms x35, the rest in between. Display is 60 Hz.
Windows 10 2004+ keeps timer resolution per process, and nothing in src/
calls `timeBeginPeriod` or uses a high-resolution waitable timer. So a 16 ms
WM_TIMER snaps to the 15.6 ms system tick and often lands one tick late.
WM_TIMER is also the lowest-priority message: it is only made when the
queue is empty, so input and paint traffic during a drag delay it more.

Every animation is on this clock:
- stack glide: `STACK_SLIDE_TICK_MS = 16` (Window.zig ~L323, tick at
  `stackSlideTick` ~L8548)
- hero: `HERO_ANIM_TICK_MS = 16`
- banner: `banner_layout.COLLAPSE_TICK_MS = 16`
- sidebar: `pane_sidebar_transition.frame_ms = 16`; `pane_sidebar_motion.frame_ms = 33`
  (30 fps, on purpose)
- fades: BellBorder, HoverTint, QuickTerminal, ViewerTOCPanel, focus glow

The glide math is already wall-clock based (`dt` from `Instant`), so the
motion is correct. It is sampled at uneven times and shown on whichever vsync
comes next, which is what reads as judder.

Mac: `PaneStage` steps the glide from a 120 Hz `Timer`, and every card moves
inside one `CATransaction` that CoreAnimation presents on the display clock.

Fix:
1. One per-window (or per-app) frame clock aligned to vsync, replacing the
   per-animation SetTimers. For example, a worker thread blocking on
   `DCompositionWaitForCompositorClock` (Win11) or `DwmFlush` that posts one
   coalesced WM_APP_FRAME per vblank while any animation is live. A
   `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` timer waited on in the run loop's
   `MsgWaitForMultipleObjects` is the fallback. Animations subscribe and
   unsubscribe; the clock stops when none is live.
2. Sample each animation at the PREDICTED present time (next vblank), not
   at "now", so positions move by an even step per displayed frame.
3. Make each glide tick a live relayout (`layoutSplitsLive`, like T2359), and
   measure per-tick cost with the T1343 drag-stats line. If a tick does not
   fit in a 16.7 ms frame, fixing the clock will not be enough and T2360
   (DComp) becomes the fix.
4. Lift the sidebar sheen's deliberate 33 ms cadence to the frame clock.

## Validation criteria

- [ ] A debug log/oracle reports per-animation frame intervals; on the user's 60 Hz box a stack glide shows every interval at 16.7 ms +/- 2 ms (none at 2x) where today about half are ~31 ms.
- [ ] Same for hero, banner and sidebar column glides.
- [ ] Mean glide tick cost (layout + place + paint) measured and recorded, and under the frame budget on a 4-pane window.
- [ ] Unit tests for the frame-clock subscribe/stop logic (none lane); acceptance script in test/win32/ asserts the interval oracle.
- [ ] Mac parity check: the Mac seat confirms there is no equivalent gap there, or files one.
