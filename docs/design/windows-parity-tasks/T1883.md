# T1883 - A pane relaunched after an agent restart may come back without GHOZTTY_WINDOW_NAME on Windows (main 1342e7af5): prove the restore path bakes the window name into each relaunched leaf

## Summary

Main 1342e7af5: a pane RELAUNCHed by the agent after a cold start or reboot
came back with `GHOZTTY_PANE_ID` but no `GHOZTTY_WINDOW_NAME`, because the
restore path never put the window name into the relaunch env; `/wt-delete`'s
`+close --target=$GHOZTTY_WINDOW_NAME` then found no window. Mac now settles
the restored window's name BEFORE building its panes (the persisted target if
still free on a local restore, else a fresh window-N, never a name another live
window holds) and bakes it into each leaf's config; in-place recovery bakes the
controller's current name. The skill's `$GHOZTTY_WINDOW_NAME` row now says it is
a snapshot as of when the pane's process started.

Windows: check `App.zig` restore (`restoreWindow` / `restoreAttachOverride`) -
the window-name env rides the OPEN on fresh spawns (IpcHandlers new-window), so
verify the relaunch/ATTACH path on a tombstoned session carries it too, with the
same never-collide rule. Then carry the skill row's new wording into the live
fork `src/apprt/win32/assets/ghoztty/skills/ghoztty/SKILL.md` (the pristine
upstream mirror was re-vendored to main's blob by T1832's turn, since hook-json
section A requires it).

## In plain terms

After a reboot, the terminals Ghoztty brings back should still know which
window they belong to, so a script running inside one (like closing "this"
window when a worktree is deleted) acts on the right window. On Mac those
panes came back not knowing their window at all. Windows already did this
right; this task proves it with a test and fixes the one leftover difference:
windows restored from ANOTHER machine now get a fresh local name, like Mac.
