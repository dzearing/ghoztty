# T2986 - PA-W02: a resize outside the modal size loop (maximize, snap, restore, SetWindowPos) rebuilds the whole pane desk on every step, about 4 ms each (PaneDesk.zig:1127)

## Summary

PA-W02 (audit-1, T2960). The desk's live-resize canvas is only enabled from WM_ENTERSIZEMOVE (Window.zig:22473, the only non-test liveResize(true) caller); otherwise PaneDesk.zig:1127 returns the exact size and each step takes a new desk: ensureDesk re-renders and upscales the gradient, ensureComp recreates the DIB, and a full compose runs. The repo's own note (PaneDesk.zig:1102-1105) puts that at ~4 ms of a 120 Hz frame. The baseline resize phase is exactly this path (SetWindowPos every 50 ms: 13.8% CPU release, 31.0% debug); ~110 steps x 4 ms over 8 s is roughly 5% of a core (estimated). Fix: arm the canvas on any burst of size changes (a size change within N ms, or from handleResize) and drop it on a quiet timer, with the settle repaint (Window.zig:22497-22503) driven by that timer too. Risk medium: the gradient layout must still settle correctly.

## In plain terms

When a window is resized by something other than dragging its edge - a
maximize, a snap, a script or tiling tool stepping its size - Ghoztty redrew
its whole pane background from scratch on every step, a few milliseconds of
wasted work each time. Now a quick run of size changes reuses one background
canvas the way an edge drag already did, and redraws it once for the final
size when the changes stop.

## Goals

- [x] a run of size changes outside the edge drag paints on the drag's canvas
- [x] a single maximize or restore costs no more than it did (no double layout)
- [x] the background is laid out for the final window size once the run stops

## Validation criteria

- [x] a SetWindowPos resize burst (no WM_ENTERSIZEMOVE) runs on the canvas: no ensureDesk/ensureComp per step (trace or counter) - `test\win32\size-burst-canvas.ps1` C: 29 steps render the desk 3x growing / 0x shrinking, against 29x / 29x under `GHOZTTY_DESK_NO_CANVAS` (the oracle-live control); `-NegativeControl` goes red on C
- [ ] perf-baseline.ps1 -Phase resize: app CPU below baseline-1 (13.76% release / 30.95% debug) by more than the tolerance - Debug run 2026-11-15: 28.3% (baseline-2 32.2%, baseline-1 31.0%), a 12% drop consistent with the ~4-point estimate but INSIDE the script's 50% cpu_pct tolerance, so not proven beyond noise; release arm NOT RUN (no zig-out-release built this turn)
- [x] the settled desk after a burst matches the pre-change desk pixel-for-pixel (acceptance script on the test desktop) - measured as layout equivalence, not a pixel diff: `size-burst-canvas.ps1` D asserts the settle repaint lays the desk out at exactly the window's desk area (1242x691 / 882x691), i.e. the same `ensureDesk(w, h)` call a non-burst resize makes
