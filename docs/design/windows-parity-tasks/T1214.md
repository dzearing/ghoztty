# T1214 - The soak leaves a fifth idle pane nobody counted, in a window it never meant to open

## In plain terms

Every soak run opens one more terminal window than it uses. Nothing looks at
it, nothing closes it deliberately, and its pane quietly joins every number
the run reports - so a reader of the report sees five panes where the harness
says there are four.

## Summary

T1147's per-pane telemetry made this visible for the first time. Both runs on
2026-08-31 report **5 panes**, not 4:

```
  pane 3AE13174-... idle probe  samples 1487  ... fps<=1 share 0.98
  pane A8F91F1A-... other       samples 1486  ... fps<=1 share 1
  pane soak-altscr  LOADED      samples 1675
  pane soak-grow    LOADED      samples 1486
  pane soak-stream  LOADED      samples 1790
```

The `other` pane is idle for the whole run and is not in the soak window: the
`+new-window --target=soak` auto-launch brings the GUI up with its own default
window first, and that window's pane is never closed. `Assert ($leaves.Count
-eq 4)` only walks the window whose target is `soak`, so it passes and says
nothing about the extra one.

Two consequences. It is 1486 of 7924 samples of pure idle noise in every
pooled statistic the report prints - the same defect T1147 fixed for the
assertion but not for the summary line. And a window the harness did not mean
to open is a window whose teardown nobody proved: `+close --target=soak` does
not reach it, and it survives only because `Stop-RepoGhoztty` kills the
process outright.

Decide whether the soak should close it (and assert it is gone) or drive it as
a fifth deliberate pane. Either way the report should stop describing a layout
that is not the one on screen.

## Where

- `test/win32/soak.ps1` - the auto-launch, the `layout: 4 leaves` assertion,
  the teardown
- likely the same shape in `test/win32/profile-latency.ps1`, which
  auto-launches the same way

## Goals

- [x] The soak accounts for every pane its run creates, in the report and in
      the teardown.
- [x] The layout assertion notices an unexpected window instead of ignoring
      it.

## Resolution (2026-10-22)

Decided: CLOSE it, not drive it. The extra window is the app's own startup
window - an auto-launched instance opens it before it takes the
`+new-window --target=soak` (`autoLaunchInstance`, `src/apprt/win32/App.zig`)
- so it is not part of the layout the soak means to measure. Setup now reads
the roster right after the launch, closes every window that is not `soak`,
reads it back and aborts if one survives - before any load starts, so the pane
never reaches the telemetry. The layout check gained a second assertion (the
instance holds only the soak window), the per-pane report asserts every row is
a pane this run created (`NOT OURS` replaces the silent `other` tag), and the
teardown asserts `+close --target=soak` left no window before the kill runs.

Same shape in `test\win32\profile-latency.ps1` filed as T2172 (an
input-desktop run, so not validated here).

## Validation criteria

- [x] a soak run's telemetry breakdown lists exactly the panes the harness
      created, with no `other` row - `soak.ps1 -Minutes 3` (2026-10-22
      18:57, report `%TEMP%\ghoztty-soak\20261022-185717`): rows are the probe
      + the three LOADED panes, `PASS telemetry lists only the panes this run
      created (not ours: none)`; the startup roster line shows the defect was
      live: `closing ... window-1 (1 pane)`.
- [x] the teardown is shown to close what it opened, rather than relying on
      the process kill - same run: `PASS teardown: +close --target=soak leaves
      no window behind (left: none)`, asserted before the kill.
- [x] a deliberately-injected extra window turns the layout assertion red -
      `soak.ps1 -SelfTest` 11/11: a fabricated roster with `window-1` beside
      `soak` comes back as one stray, named, with its pane count.
