# T3694 - upgrade-ghoztty-windows.ps1 relaunches a Debug (console-subsystem) app with a bare Start-Process, so Windows hands its new console to Windows Terminal on the user's desktop

## In plain terms

When the test suite exercises the upgrade script against a debug build, a
console window can open on the user's screen even though the app itself now runs
out of sight on the test desktop. Once this is fixed, a test upgrade leaves
nothing on the user's screen at all.

## Summary

Found by T2201's validation. After T2201 moved every launch that
`test\win32\upgrade-no-fork.ps1` makes onto the test desktop, a watcher
enumerating the user's desktop (`EnumWindows` from the `Default` desktop) saw
**none** of the sandbox app's own windows there, across all ten sandbox
processes of a full run. It did see one `PseudoConsoleWindow`,
`IsWindowVisible` = true, attributed to each app that
`scripts\upgrade-ghoztty-windows.ps1` relaunched (sections B, E, C and D, four
hwnds). The app the CLI auto-launched in B1 had none.

Mechanism (INFERRED from the evidence; not traced to the process that hosts it):
the Debug `ghoztty.exe` is a **console-subsystem** binary (`src\os\cli_launch.zig`
header), and the upgrade script brings the app back with a bare
`Start-Process -FilePath $oldExe -WorkingDirectory ...` (the restart-only, reuse
and relaunch sites, around lines 913, 1005 and 1210). A console-subsystem child
with no `-NoNewWindow` gets a NEW console, and on this box
`HKCU\Console\%%Startup` delegates new consoles to Windows Terminal
(`DelegationConsole {2EACA947-...}`, `DelegationTerminal {E12CFF52-...}`). The
handed-off console's host window is created on the interactive desktop whatever
desktop the client is on. A pane's ConPTY window, by comparison, is
`vis=False` at 18x18. A release `ghoztty.exe` is GUI-subsystem and gets no
console, so production upgrades are not affected. Only Debug runs are, and the
test suite's runs are Debug.

Likely fix: `-NoNewWindow` on those three `Start-Process` calls. A
GUI-subsystem release exe ignores it. A Debug exe then joins the upgrade
script's own console, which is already hidden (a detached hidden powershell in
production, a `CREATE_NO_WINDOW` child on the test desktop). It also matches
the release launch's `cli_launch` answer, since a release exe's parent owns a
console too. The guards that cover the upgrade script (guard-due rows naming
`scripts\upgrade-ghoztty-windows.ps1`) must be re-run green.
