# T2497 - go-loop-guard.ps1 flakes under a loaded box: different GUI-driven assertions fail each run (run 1: L2/L6/L9/L11/L12; run 2: J3/P9; 504 others green) - make its window/pane waits load-tolerant

## Summary

2026-10-29 ~22:45, controller, while both lanes ran zig builds and acceptance
sweeps: `test\win32\go-loop-guard.ps1` was run twice on the same tree, back to back,
over a one-line change to `scripts/go-loop-health.ps1`'s in-progress note. The two
runs failed on different assertions:

- run 1: L2, L6, L9, L11, L12 (duplicate-window title marking and stand-down)
- run 2: J3 (resume prompt typed into the pane) and P9 (`-Status` reports the last tick)

Neither section exercises the changed line, and every assertion that failed in one
run passed in the other. So these are timing assertions that lose their race
under load: title polls, typed-into-pane reads, and watchdog tick waits. The
guard can then never restamp on a busy box, which leaves `go-loop` permanently
DUE on any loop-script edit.

Fix: find each of those assertions' waits and make them poll for the condition
with a load-tolerant deadline, not a fixed sleep or a single read. Prove it with
3 consecutive green runs while a floor-lane build is running.

## In plain terms

The self-test for the work loop's supervisor kept failing on a busy machine for
reasons that had nothing to do with the code: it looked once, or waited a few
seconds, and a slow box answered a moment later. When this lands the test waits
for what it is checking instead of guessing, and the loop's own duplicate-window
handling no longer mistakes one slow answer for "there are no windows".
