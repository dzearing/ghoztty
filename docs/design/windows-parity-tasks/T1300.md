# T1300 - Apps and Features offers no Repair for Ghoztty

## In plain terms

Ghoztty can now repair itself - if you still have the installer file and run it
again, it offers to. But the place people actually go when an app is misbehaving
is Settings > Apps, and there Ghoztty shows only "Uninstall". The repair exists
and is hidden behind having kept a download.

## Where it comes from

The package sets `ARPNOMODIFY=1`, which tells Windows to hide the Modify (and,
depending on the surface, Repair) entry in Apps & Features. That was the right
call when there was nothing to modify and no repair worth offering: a Modify
button that opens a wizard the product does not have is worse than no button.

T1291 changed the premise. The package now arms `REINSTALL=ALL` with
`REINSTALLMODE=amus` and asks Repair / Cancel, so there IS a repair, and it is
the one thing a user in trouble would want from that page.

## What to think about before changing it

- `ARPNOMODIFY` and `ARPNOREPAIR` are separate switches. The wanted end state
  is almost certainly "no Modify, yes Repair" - there are no optional features
  to change - which means dropping `ARPNOMODIFY` is the wrong move on its own.
- Whatever Windows launches from that page runs the CACHED package, not the
  file the user downloaded, and it runs it in the maintenance path T1291
  authored. Check what UILevel it uses: if it is below 4, the Repair / Cancel
  dialog is correctly suppressed and the repair should just happen - which is
  the right behaviour for a button already labelled Repair, but it wants
  confirming rather than assuming.
- Mac has no analog to check against; this is a Windows-convention call.

## Goals

- [x] Settings > Apps leads to the repair instead of offering only Uninstall
- [x] A repair already chosen (Control Panel's Repair, `msiexec /f`) is not
      asked about a second time
- [x] The build refuses a package that hides either road again

## Decision (made on the box, 2026-09-24): Modify stays ON

The "no Modify, yes Repair" end state this card assumed does not exist on
Windows 11. Measured on this box: the installed product's ARP key already has
no `NoRepair` value, so Control Panel's Programs and Features ALREADY offers
Repair - but the Settings page offers a desktop app only Modify and Uninstall,
and has no Repair verb to turn on. With `ARPNOMODIFY=1` Settings therefore
showed Uninstall alone, which is the defect. The only lever that puts the repair
on the page users actually open is Modify.

What Modify now does: Windows Installer writes `ModifyPath = MsiExec.exe
/I{product}` (it wrote `/X` while `NoModify` was set), which runs at full UI into
the T1291 maintenance path - the app's own dark dialog, Repair / Cancel. That is
not "a wizard the product does not have"; it IS the product's maintenance UI.
Control Panel shows Uninstall / Change / Repair; Change asks, Repair just
repairs.

The second-ask guard: Control Panel's Repair (and `msiexec /f`) arrive with
`REINSTALL` set on the command line. `NoteRepairRequested` (seq 985) copies that
into `REPAIRREQUESTED` BEFORE `SetRepairMode` (990) sets `REINSTALL` itself, and
all four maintenance rows now carry `AND NOT REPAIRREQUESTED` - so a repair the
user already chose is never answered with "Repair or Cancel?", whatever UILevel
Windows picks for it, and the requester's own `REINSTALLMODE` is left alone.

Mechanism-only fork with no Mac analog (a Windows-convention call), so recorded
here rather than filed as a decision (go.md 5b).
