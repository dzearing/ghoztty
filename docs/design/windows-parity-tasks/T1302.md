# T1302 - Nothing has yet watched the Repair / Cancel prompt come out of a real msiexec

## In plain terms

When you run the installer for a version you already have, Ghoztty now asks
whether to repair or cancel instead of quietly doing nothing. The dialog itself
is tested; the installer ASKING for it is not - the case exists in the new
installer walkthrough but skipped on its first runs, because the newest
published package was built before that fix.

## Why it skipped

`test\win32\install-walkthrough.ps1` section D drives a real `msiexec /i` at
`/qr` over an install of the same version, waits for the app's
`GhozttyConfirmDialog`, clicks a button and reads msiexec's exit code (1602 for
Cancel, 0 for Repair). It runs only when the package carries the
`MaintenancePrompt` custom action; `win-v1.36.2` (commit `a5c770836`) predates
T1291, so the harness names that and skips rather than asserting the behaviour
of a build that never had it.

The daily publish supplies a package carrying the fix within a day of it
landing, so this is a re-run, not a rewrite.

## What to do

- Once a `win-v*` release built from `65da707e5` or later exists, run:

  ```
  powershell -NoProfile -File test\win32\install-walkthrough.ps1
  ```

- Section D must run rather than skip, and D1-D6 must pass. If the prompt does
  not appear under a real msiexec - the UILevel gate, the sequence position, the
  exit code mapping - that is the defect this case exists to find; file it.
- With D running and F5 unblocked (T1301), the walk has no skips left and stamps
  its guard row, which is what turns `install-walkthrough` from a report into a
  measurement.

## What the real msiexec showed (2026-09-24)

Package: `Ghoztty-1.36.36-x64.msi` (`win-v1.36.36`, built from `867ea0fdf`,
which carries T1291). Section D RAN - no skip.

1. **The first two runs failed D1-D3/D5, and the defect was the harness.** The
   MaintenancePrompt custom action is launched by the Windows Installer
   SERVICE, which puts it on the INTERACTIVE desktop, not the background test
   desktop msiexec was started on. A poller on the input desktop saw the
   dialog both times - class `GhozttyConfirmDialog`, visible, titled "Ghoztty
   is already installed", from the throwaway install's `ghoztty.exe
   --install-maintenance --installed-version=1.36.36` - while the harness looked
   on the test desktop and found nothing. Fixed in the harness: section D binds
   a second handle to the interactive desktop and finds, reads and clicks the
   dialog through it (BM_CLICK is a sent message - no foreground, no injected
   input, the dialog is up for well under a second).
2. **With that fixed, the prompt works end to end except Cancel.** D1 dialog
   appears, D2 buttons read Repair / Cancel, D4 Cancel leaves the install
   untouched, D5 Repair = msiexec exit 0, D6 product still installed.
3. **D3 is a real product defect, filed as T1730 (P1, M1).** The app exits 1602
   on Cancel exactly as designed (`CustomAction MaintenancePrompt returned
   actual error code 1602`), but Windows Installer does not read an EXE custom
   action's exit code as an action status: it raises Error 1722 ("There is a
   problem with this Windows Installer package") and ends at 1603. The premise
   in build-msi.sh and install_maintenance.zig that 1602 is a clean user-exit
   holds for DLL/script actions only. D3 stays a FAIL until T1730 lands - it is
   the measurement of that defect, not a flake.
