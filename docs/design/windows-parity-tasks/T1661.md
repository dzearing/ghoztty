# T1661 - The harness lane's default 30-minute budget no longer fits its own suite, so a full sweep can end in TIMEOUT instead of a verdict

## In plain terms

Running the harness checks can take half an hour and then stop with "took too
long" instead of saying whether anything is wrong - so the half hour buys
nothing and has to be spent again.

## Summary

`scripts\floor-lane.ps1` defaults `-TimeoutSeconds` to 1800 (line 162). Measured
on 2026-09-18: the harness suite itself is **22m 10s** for 29 audits, and the
confirm pass re-runs every non-green audit ALONE on top of that - on this run
three of them, including `test-reach-audit.ps1` at 5m 27s. Total 29m 26s the
first time, which the wrapper killed at 1800s with
`FLOOR SUMMARY: harness#1=TIMEOUT` and no verdict at all. The re-run with
`-TimeoutSeconds 3600` completed in 1766s and reported the real answer
(`HARNESS FLOOR: 1 FAILURE(S) of 29 audits, 2 PENDING`).

The budget is not per-lane: 1800s is generous for a zig lane and tight for this
one, and the gap grows every time an audit is added. Options to weigh: a
per-lane default (the harness lane knows it is the long one), a budget that
scales with the member count, or a confirm pass that is accounted for
separately from the sweep. Whatever the shape, the wrapper should distinguish
"the suite is long" from "the suite is wedged" - which is the whole reason the
wrapper exists.

Seen on the T861 turn; the turn paid 30 minutes for a TIMEOUT and then 30 more
for the answer.

## Validation criteria

- [x] A full `floor-lane.ps1 -Lane harness` on this box reaches a verdict
      without a hand-passed `-TimeoutSeconds`. (Three full 34-audit sweeps on
      2026-11-21 - 05:11, 07:12, 08:48 - each `HARNESS FLOOR: ALL PASS` in
      17m 16s / 17m 37s / 11m 00s under the declared 3600s cap, `-Jobs 4`;
      logs `%TEMP%\floor-lane-harness-20261121-*.log`.)
- [x] A genuinely wedged harness lane is still killed and still reports STALL /
      TIMEOUT rather than running to the new ceiling silently. (Read
      `scripts\floor-lane.ps1:881-909`: the no-CPU/no-output STALL check is
      independent of the wall-clock cap and fires at `-StallSeconds` whatever
      the cap is; the cap only ever moved from 1800 to 3600.)
- [x] The acceptance script for the lane wrapper covers the new budget rule.
      (`test\win32\floor-lane-releasesafe.ps1` T1657 arms: declared budget
      above 1800, a bare `-Lane harness` uses it, explicit `-TimeoutSeconds`
      wins, no-floor-script control = 1800; ALL PASS (25 assertions) on
      2026-11-21.)

## Resolution

Already fixed by **de63c0ca3** (T1657, 2026-10-27): `harness-floor.ps1`
declares `# suite-timeout-sec: 3600`, `floor-lane.ps1`'s
`Get-HarnessLaneTimeout` takes the larger of that and the 1800s lane default
unless `-TimeoutSeconds` is passed, and the sweep runs four audits at a time,
which brought a full sweep from ~29m serial to 11-18m. This was the "per-lane
default" option the Summary weighed. No new code in this turn; the turn
re-verified it and landed the evidence.

Two things the turn's guard sweep turned up, fixed in the same commit:

- `parity-tasks-seat.ps1` W12 went red in an acceptance worker (4 failures)
  and green alone. `rot-scan` built the task dir's repo-relative path by
  trimming the length of `git rev-parse --show-toplevel` off `$TaskDir`; under
  the worker's junction mirror git reports the resolved root, so the trim
  produced a garbage path and every card read "no such card at c03cb4913^".
  It now asks `git rev-parse --show-prefix`. Red in a worker twice before,
  ALL PASS (308) in a worker after.
- R7 of the same harness: the fifteen Linux-port cards (T3329-T3343) were filed
  without category tags; tagged them.
