# T2040 - Restore All from a Mac places windows at the wrong spot on a scaled Windows display: the Mac origin is in points but is applied as pixels

## Summary

Found in T1979. T1979 made a Mac window's SIZE convert from points (96 dpi) to the landing monitor's DPI, but `fitToMonitor` scales only w/h: the ORIGIN from `mac_layout_blob.frameFrom` is still Cocoa points used as win32 virtual-screen pixels. On a single 200% display a Mac window at (1000, 500) pt lands at (1000, 500) px, i.e. half-way toward the top-left of where it sat on the Mac (then clamped into the work area if the doubled size would overrun it).

Fix sketch: convert the origin on the Mac-sourced path only (never the own-manifest path, whose origins are real pixels). Mixed-DPI multi-monitor arrangements have no single scale for the global space, so the rule must be per landing monitor: map the point origin relative to the source primary, then onto the target monitor in its DPI. Pure rule in `window_placement.zig` or `restore_frame.zig` with unit tests; the Mac seat's mirror (reading a win32 blob's pixels as points) may want the same treatment, so check its reader when building this.

## Validation criteria

- [ ] A Mac window at (1000,500) pt on a 2560x1440 pt primary lands at (2000,1000) px on a single 200% display (unit test).
- [ ] Own-manifest (win32) frames are untouched (existing T1971 tests still pass).
- [ ] A mixed-DPI two-monitor case lands on the intended monitor (unit test).
