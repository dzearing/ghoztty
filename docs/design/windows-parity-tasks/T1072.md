# T1072 - A bare git commit can still leave work on this box - close the last bypass at the hook

## Summary

T1057 made the push automatic for commits that go THROUGH scripts\git-commit-guard.ps1 commit, and gave the turn boundary teeth (claim reports unpushed work, validate fails on it). What is still open is the direct path: a plain 'git commit' from either window bypasses the guard entirely, so the work sits local until the NEXT claim or the NEXT validate notices - a whole turn later in the worst case. The pre-commit hook already runs on that path (it is what enforces the advisory lock), so it could also refuse - or at least warn loudly on - a commit made while HEAD is already ahead of its upstream. Weigh it against the wedge risk: on a box with no network a refusal there would block committing entirely, so the shape probably wants to be 'warn on the first, refuse on the second' or an env opt-out that says it was used. Acceptance: an arm in section W of test\win32\go-loop-guard.ps1 that plants an unpushed commit in the fixture repo and scores what a bare git commit does next.

## In plain terms

The loop's own commit tool always pushes, but a plain `git commit` typed in
either window never did, and nothing said so until the next turn - so work
could sit on this one machine, invisible to the Mac seat and lost with the box.
Now git itself says "not pushed" the moment that happens, and refuses the next
commit until the first one has been pushed.

## Goals

- [x] a bare commit that leaves the branch ahead of origin is announced at once
- [x] a second bare commit over unpushed work is refused, with the remedy
- [x] the guard's own commits, a merge being concluded, a rebase and a branch with no upstream are never blocked
- [x] an explicit, self-announcing hatch for amend / no-network

## Validation criteria

- [x] first bare commit lands and post-commit prints NOT PUSHED - W33a, test\win32\go-loop-guard.ps1 (ALL PASS, 463 assertions, 2026-10-17)
- [x] second bare commit REFUSED, HEAD unmoved, unpushed commit + remedy named - W33b/W33c
- [x] negative control: same commit with hooks unwired goes through - W33d
- [x] GHOZTTY_ALLOW_UNPUSHED=1 passes and says it was taken - W33e
- [x] guard commit (lock key) is exempt while ahead - W33f; bare commit allowed again after push - W33g/W33h

## Design

Shape chosen is the task's own "warn on the first, refuse on the second":
`scripts\githooks\post-commit` (new, advisory, always exits 0) warns after a
bare commit leaves HEAD ahead of `@{u}`; `scripts\githooks\pre-commit`
refuses a commit while HEAD is already ahead. Exempt: a commit carrying the
guard's lock key (it pushes itself, and a no-network push failure must not wedge
its next commit), detached HEAD (rebase), no upstream (nowhere to push), and
MERGE_HEAD present (concluding a merge). Amending the unpushed commit cannot be
told apart from a new commit in pre-commit, so it takes the hatch.
