# T3597 - Linux L8d-3: +new-remote-window opens a remote-machine window in the GTK app

## Summary

Split from T3399. GTK answers +new-remote-window with 'not served'. Port win32's ipc_remote_window.zig + ipc_remote_dial.zig (Mac handleNewRemoteWindow validation strings) so the verb opens a window whose panes are hosted by a remote ghoztty-agent over ssh/relay, and +new-window --from-focused inherits a remote parent's machine. The chooser, pill and reconnect UI are T3563. Acceptance test/linux/cli-remote-window.sh against a loopback agent.

## Validation criteria

- [x] `+new-remote-window --host --port` opens a window whose pane is the TCP agent's child, not the app's; keys and `+read` round-trip; `+list` names its `machine` and `connection.state`, and a local window has neither - `test/linux/cli-remote-window.sh` R1-R5, ALL PASS 26/26 in WSL (2026-11-24).
- [x] `--command` reaches the remote OPEN, for the window and for a `+split` of a remote pane (R6, P2); a split rides the same agent (P1, P3).
- [x] `+new-window --from-focused` on a remote window re-dials its machine (F2, F3).
- [x] Refusals byte-match win32/Mac and come before any dial: no host, no port, tokenless relay ("not signed in: ..."), dead port ("failed to reach 127.0.0.1:<p>: ...") (E1-E5).
- [x] `+close` ends the remote shells, the agent keeps running, and the last pane off the link closes the connection (C1-C4).
- [x] The dial runs off the GTK thread (IpcServer `TakeDeferred` hop; E4/E5 answer and the app stays up).
- [x] Negative control: `NEGATIVE=1` (main window dials a dead port) fails R1 and 10 dependents - 11 FAILURES.
- [x] Linux floor (lib, none, agentx, agent) ALL PASS; RemoteLink's unit tests ride the none lane.
- [ ] Relay path end to end (a real relay dial) is NOT exercised on Linux - only its tokenless refusal. Filed in T3668.
