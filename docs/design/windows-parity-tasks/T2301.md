# T2301 - Check by eye that a glass or elevated card folding into its strip hands its fading face over to the strip with no visible jump (T2288 follow-up)

## Summary

T2288 lays the strip face over the pane's card-inner rect, while the desk band at rest fills the whole strip rect; in the elevated and glass styles the two can differ by the card margin and the name can land a few px apart, and off-desktop probes cannot see the composite. Look on the input desktop (user present: NOT RUN by the loop) and fix any jump at the handover.

## In plain terms

When a pane folds into the thin strip at the edge of its stack, the strip's name fades in over it, and when the fold ends the window's own strip takes over. The worry was that in the raised-card styles the name could land a few pixels away from where the strip then draws it, so it would visibly hop at the end. It does not: the name now lands on the same pixel, and a test measures that on every run.

## Goals

- [x] measure where the fading name lands against where the resting strip draws it, without needing eyes on the screen
- [x] confirm no jump in the flat, elevated and glass styles
- [x] keep it measured: the fold harness fails if the name ever lands more than 1 px off
- [x] what eyes are still needed for (the 1 px card-outline ring) is filed on its own (T3794)

## Validation criteria

- [x] the handover offset is computed by one pure function, unit-tested - `strip_face.handoverGap` test (none lane)
- [x] flat style: the name lands 0,0 px from the resting name, band edges 0,0,0,0 - `stack-fold-slide.ps1` F21, ALL PASS (48)
- [x] elevated (= glass, `macos-pane-glass` defaults on): name 0,0 px, band edges 1,1,-1,-1 (the card outline) - `stack-fold-slide.ps1 -PaneStyle elevated` F21, ALL PASS (44)
- [x] composition tree: flat 0,0 / elevated 1,0 px (rounding) - `-Tree` F21 PASS both styles; that mode's F14/F19 reds are the filed T2817, red before this change
