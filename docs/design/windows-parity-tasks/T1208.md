# T1208 - Tell the user their terminal is being closed for the update

## In plain terms

When an update needs to close your open terminal, it now does that and opens it
again by itself. What it never does is say so. For a second or two your windows
vanish with no explanation, which reads like a crash rather than an update.

## Goals

- [x] The relaunched terminal says it was closed and reopened for an update,
      naming the version it moved to, on both the installer and in-app paths
- [x] It says nothing when nothing happened, or when the update failed
- [x] A click on the notice opens What's New

## Where this stands after T1204

The app registers for restart and exits when the Restart Manager asks, so the
mechanism works and needs no user decision. What is missing is the standard
`MsiRMFilesInUse` dialog, which names the applications that must close and
offers to close and restart them. That dialog comes from the package's UI
table, and the package is compiled by wixl (msitools), whose WiX subset does not
carry the standard UI libraries - so this is a real question about how the
installer is built, not a property to set.

## Options to weigh

- Author the minimal UI table by hand (`FilesInUse` / `MsiRMFilesInUse` dialogs)
  and verify it survives wixl, the way T1176's launch actions are read back out
  of the compiled MSI.
- Say it somewhere of ours instead: the in-app updater already owns its own
  dialog and could name what it is about to close, which covers the path most
  upgrades take.
- Decide the silent close is right for a terminal and only make the RETURN
  visible (a first-run line in the reopened window saying what version it is
  now, which pairs with T1205).

## What was chosen, and why

The third option, extended to both update paths: say it AFTER the fact, from
our side, on the tray surface every other update message already uses.

- The process that is about to be closed for an update leaves a one-line
  marker (`%LOCALAPPDATA%\ghoztty\update-reopen[-debug]`: reason, time, the
  version it was running). The Restart Manager close writes `installer`
  (`Window.zig`, `WM_ENDSESSION` + `ENDSESSION_CLOSEAPP`, just before the
  exit T1204 added); the in-app updater's quit writes `updater`
  (`applyStagedUpdate`).
- The next launch consumes it (always deletes it) right after the first window
  exists, and `update_reopen.decide` picks the sentence: version moved →
  **"Ghoztty Was Updated"** naming both versions, click opens What's New;
  installer close with no version change (a repair) → **"Ghoztty Was
  Reopened"**; a failed in-app update (same version, `updater`) → nothing,
  because the applier's T1206 modal already says so and a cheerful second
  message would contradict it; a marker older than 15 minutes → nothing.
- A balloon rather than a dialog: nothing to consent to, and it can never
  block an unattended or silent install.

Why not the MSI Files In Use dialog: the wixl-built package has no UI tables,
and that dialog only ever covers the installer run by hand, never the in-app
updater, which is the path most upgrades take. The in-app path was already
told BEFORE ("Ghoztty will close, install the update and reopen" in the
Install and Restart dialog); this adds the AFTER for both. Authoring the MSI
dialog is filed separately as a follow-up (it needs wixl, so Docker, to
validate).

## Validation criteria

- [x] An upgrade over a running Ghoztty tells the user, before or immediately
      after, that the terminal was closed and reopened for the update.
      `test\win32\install-restart.ps1` section U: a real RM close of the debug
      build pinned at 1.40.0 writes `v1 installer <ms> 1.40.0` (U2); the
      relaunch at 1.40.1 logs `notice shown=… reason=installer from=1.40.0
      to=1.40.1 title="Ghoztty Was Updated"` and deletes the marker (U3/U4).
      Controls: an ordinary launch says nothing (U5), a failed in-app update
      says nothing (U6), a stale marker says nothing and is cleared (U7/U8), a
      same-version installer close says "Reopened" (U9). ALL PASS, 63
      assertions. Pure decisions unit-tested in `update_reopen.zig` (every
      lane).
- [x] Nothing about that message blocks an unattended or silent install: it is
      a tray balloon shown by the RELAUNCHED app, never by the installer, and
      the close path only adds a synchronous one-line file write before the
      exit (U1 asserts the exit is still prompt).
- [x] Whatever surface carries it is read back from the shipped artifact rather
      than asserted from its source: U reads the marker the running build
      wrote and the verdict line the relaunched build logged. The balloon
      itself reports `shown=false` on the harness's background desktop (no
      notification area there); that is the same limit every tray balloon test
      on this box has, and the line records it honestly rather than claiming
      a display.
