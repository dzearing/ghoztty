# T2193 - zig build test-lib-vt (libghostty-vt and its C API, src/terminal/c) runs in no floor lane on this box, so its tests are never executed on Windows

## Summary

Found by T1237's whole-tree sweep. 23 test-bearing modules - `src\lib_vt.zig` and all of
`src\terminal\c\*.zig` (the libghostty-vt C API) - appear in none of the three test binaries
this box's floor runs (`test` win32, `test` none, `test-agent`). Their tests live in
`zig build test-lib-vt` (two `addTest`s over `mod.vt` / `mod.vt_c` in `build.zig`), and
`scripts\floor-lane.ps1` has no lane for that step, so on Windows they are compiled by
nothing and executed by nothing. T1237 declared them as an exemption in
`test\win32\lib\TestReachAudit.ps1` naming this task.

Fix: decide whether `test-lib-vt` builds and passes on Windows at all (measure it), then
either add it as a floor lane (and add its two binaries to the test-reach sweep's lane
set, dropping the exemption - section D5 turns red the moment the exemption is stale), or
record why it cannot run here and which seat does run it.

## In plain terms

A whole family of terminal-core tests (the part of the terminal that other
programs can embed) was never run on Windows, so a Windows-only break there
would go unnoticed. They now run on this box, and changing that code makes
running them mandatory before the change can be committed.

## Goals

- [x] Measure whether those tests build and pass on Windows at all.
- [x] Give them a lane of their own in the floor runner.
- [x] Make them obligatory when their code changes.
- [x] Have the test-reach audit count them, so their exemption can go.

## Design (2026-11-24)

- `floor-lane.ps1 -Lane vt` runs `zig build test-lib-vt` under the floor's watchdog. It is deliberately **not** added to `-Lane all`: `test\win32\harness-floor.ps1` E3 pins `all` to the four zig lanes, and `floor-lane-parallel.ps1` is written around four. What makes it standing instead is a new guard-due row, `lib-vt`, over `src\lib_vt.zig`, `src\terminal\**` (3 levels), `src\unicode\`, `src\simd\` - editing those puts the lane DUE and `validate` refuses until a whole, unfiltered green `-Lane vt` run re-stamps it (floor-lane stamps on its own PASS).
- The step runs two binaries both named `test.exe` (mod.vt and the C-ABI mod.vt_c). `Invoke-LaneTestBuild` gained `-AllMatches` (returns `ExePaths`) and now requires the exe name to be a whole file name, so `test.exe` cannot also match `ghostty-test.exe`. `test-reach-audit.ps1` section D builds the vt lane every run (warm: seconds) and scores both binaries; new assert D1v requires exactly two. The probe showed mod.vt_c carries all 24 formerly exempt modules (`lib_vt` + 23 `terminal.c.*`).
- Not done: crash attribution (`CRASHDIAG_TEST_EXES`) does not name `test.exe` - too generic a name to attribute box-wide; a crash in the vt lane still reads as a red lane with its exit code.
