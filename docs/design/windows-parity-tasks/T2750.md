# T2750 - remote-effects.ps1 is red on HEAD with the composition present off (=0) and on: 'console launch: the unfocused pane is dimmed (saw 0 overlays)' and 'back on the console: ... dimmed again (saw 0 overlays)' - 2 failures, alone and in parallel, 2026-11-06

## In plain terms

A test that checks Ghoztty's "light mode" over Remote Desktop kept failing.
It expected the inactive half of a split to be greyed out on a normal
(non-remote) launch, but since late October the default glass look
deliberately does not grey out inactive panes - the same as on Mac. The app
was right and the test was out of date; the test now checks the current
behavior, and still checks the grey-out where it does exist (glass off).

## Summary

**The app was right; the harness was stale.** `remote-effects.ps1` (T1951,
2026-10-14) asserted one `GhozttyDimOverlay` over the unfocused pane on a
console launch and after a live flip back to the console. T2281
(7f0381f39, 2026-10-25) made glass panes never dim (Mac 9da9618f8), and
`macos-pane-glass` defaults to `true`, so on the console with defaults there
is correctly no wash on EITHER draw path - which is why it was red with
`GHOZTTY_COMP_PRESENT=0` as well as on.

Fix (test only, `test/win32/remote-effects.ps1`):

- Runs 1 and 2 (default glass) now assert NO wash on the console, citing T2281.
- New run 4 covers the dim swap itself with `--macos-pane-glass=false` set by
  name (the remote swap leaves it alone): remote launch flat with no wash,
  live to the console elevated with exactly one wash, live back to remote the
  wash goes.
- Washes are counted on both draw paths: visible popups plus the composition
  path's child-visual washes read from a per-launch `-StdErr` log (T2748's
  oracle), so no assertion changes meaning with the composition default
  (T2514).
