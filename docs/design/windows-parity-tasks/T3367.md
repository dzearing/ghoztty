# T3367 - Linux L7c: +close and +focus work against the GTK app

## Summary

`+close` and the `focus` wire action are served by the GTK frontend with
win32's rules. `+close` closes a pane (and its window, when it was the last
pane) or a whole window with no confirmation, as the Mac's
`withConfirmation: false` does; it is idempotent (a target nothing answers to
succeeds), a name panes in several other windows hold fails rather than
closing one at random (T2250), and a close over an open dialog closes nothing
and says so unless `--force`, which dismisses the dialog first (T2938).

There is deliberately **no `+focus` CLI verb** on any platform (the title's
"+focus" predates reading win32): `focus` is the action the `ghoztty://` URL
launcher sends (T695). It focuses an existing pane or window and never
creates one. Raising a window is `gtk_window_present`, which on Wayland is an
xdg-activation request the compositor may decline; the pane is focused inside
the app either way, and a pane in a background tab gets its tab selected
first (the surface's own present request, win32's T555).

## In plain terms

Scripts and agents can now close the Linux app's panes and windows from the
command line, exactly the way they do on Mac and Windows: closing something
already gone is fine, an ambiguous name is refused instead of closing the
wrong pane, and a window waiting on "Close Window?" is not torn out from under
it unless the script says `--force`. A `ghoztty://` link can also bring an
open pane to the front once the scheme is registered on Linux (T3343).

## Goals

- [x] idempotent, ambiguity-refusing, dialog-aware (`--force`)
- [x] `focus` action focuses a pane (by id or name) or a window, never creates

## Decisions made here (mechanism, not experience)

- A pane close goes through `SplitTree.closeSurfaceNow`, the same removal a
  confirmed keyboard close runs, so the focus hand-off and "last pane closes
  the tab, last tab closes the window" are the keyboard close's, not a copy.
- A window close is `gtk_window_destroy`, skipping the close-request
  confirmation (Mac `closeWindowImmediately`).
- The open-dialog check is libadwaita's visible dialog (1.5+), else any
  visible toplevel transient for the window. GTK dialogs are not modal loops
  on the dispatch stack (win32's are), so `--force` closes at once instead of
  deferring.
- Testing a dialog needs one up, and Wayland gives a test no input to press
  the close shortcut with, so a **debug-only** seam
  (`GHOZTTY_TEST_ASK_TO_CLOSE=<window target>`, compiled out of release
  builds, the win32 `GHOZTTY_TEST_PRE_SWITCH` shape) opens that window with
  its real close confirmation up.
- Weston headless has no seat, so it never makes any window active: the
  window-level raise is reported by the script, not asserted. The pane-level
  focus is asserted both ways.
