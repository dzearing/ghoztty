# T2634 - Pane-tree mode (GHOZTTY_COMP_PANE_TREE): the folding pane is never drawn mid-fold - with the stack slide stretched to 4 s, a WGC grab 1 s in shows s1 already at its end place and no trace of s2's sliding card, although the log has the card mid-glide at content alpha ~200; so no on-screen check of the fold can see the card cut (T2570)

## Summary

Found running T2570's fold arm. scripts\comp-present-onscreen.ps1 -Arms fold (P|s1|s2 flat, GHOZTTY_STACK_SLIDE_MS=4000, divider dragged past the fold, grab at ~+1000 ms): the mid-fold frame shows P wide and s1 filling 920-1390 behind s2's purple strip edge, and nothing of s2, while stderr logs 'stack fold carried content_alpha=2xx card=1073..1174,315..214'. The same frame comes out identical with Surface.setTreeShape disabled (a negative-control build), so fold.26 (no s2 ink over s1) is green for the wrong reason. In the window path stack-fold-slide.ps1 F1/F8 see s2's card on show at 2+ positions and widths. Find where s2's tree visual goes during the carried fold (z-order under s1, hidden with the window, placed off its card, or the carried frame not reaching the visual), make it draw, then make fold.26 discriminating: add a check that s2's card IS on the grab mid-fold, and confirm a setTreeShape-disabled build goes red. Grabs: %TEMP%\ghoztty-comp-onscreen-25004 (shape on) and -6296 (shape off). T2571's film oracle depends on this.

## In plain terms

When a pane folds into its strip, the test that photographs the window halfway
through the fold saw no folding pane at all, so it could not tell a correct
fold from a broken one. The pane WAS on screen; the camera was blind to it,
because mid-fold the card is drawn by a small separate window and the window
photo left separate windows out. The photo now includes them, and the test
now requires the folding card to be in the picture.

## Root cause

Nothing was missing from the screen. Mid-fold (`glide_snap == .ready`), the
fold carries s2's last frame on its STRIP FACE (`StripFace`, a WS_POPUP owned
by the pane) and hides s2's child window; in pane-tree mode a hidden pane's
visual takes an empty clip (`comp_tree.placement`), so the tree visual draws
nothing - by design. The run's log: 266 of 267 `stack fold carried` lines read
`live=0`. Windows.Graphics.Capture of a window omits its secondary windows
(owned popups) unless `IGraphicsCaptureSession6.IncludeSecondaryWindows` is
set, so `--grab-hwnd` never saw the face. That is also why a
`setTreeShape`-disabled build grabbed the same frame: the shape clips a visual
that is already clipped to nothing for the whole carried phase. The shape only
reaches the screen on the fold's single live frame (the 1 `live=1` line), which
one grab at +1 s cannot land on - that is T2571's per-frame film.
