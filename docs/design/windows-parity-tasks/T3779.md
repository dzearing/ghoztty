# T3779 - On Linux the app quits or dies when about twenty split panes are left open in one window

## Summary

test/linux/pane-close-memory.sh NEGATIVE=1 (T3646 run, 2026-11-25) leaves every warm-up and measured split OPEN in one 100x30 window: after ~20 splits the opens started failing (P1 red) and the app was gone by the end of the split scenario (end sample '0 0 0', P2 'the app is still running' FAILED); every later scenario ran against no app. The harness does not keep the app log, so whether it panicked (tiny pane size? split ratio underflow?), was OOM-killed (597 MB private at peak) or exited is unknown. Reproduce with repeated +split on one pane in the headless harness, keep APP_LOG, and fix the crash; NEGATIVE mode should then be able to fail every budget check without the app dying under it.

## In plain terms

Splitting the same pane over and over on the Linux build made the whole app
crash at the sixteenth split. The cause was a debug printout of the pane
layout: the picture it draws scales the smallest pane up to one character,
and that number grew too big to hold. Now the picture is skipped when the
layout is too deep to draw, and the app keeps running. The same code is in
the Windows and Mac builds, so it is fixed there too.

## Root cause

`SplitTree.formatDiagram` (`src/datastruct/split_tree.zig`) scales the whole
layout so the smallest slot is one cell, using `f16`. Sixteen nested halvings
make the smallest slot 2^-16, `1 / min_w` overflows `f16` to infinity, and
`@intFromFloat(@ceil(inf))` panics. The GTK frontend's `newSplitAt` logs the
new tree with `{f}` at debug level on every split, so a Debug app died at its
16th nested split (`+split` on the same pane each time - exactly what
`pane-close-memory.sh NEGATIVE=1` does). Any frontend formatting such a tree
hits the same panic; the GTK `new split` log is the only place under
`src/apprt/` that formats a whole tree on split (macOS keeps its own Swift
tree), so only Linux showed it.
