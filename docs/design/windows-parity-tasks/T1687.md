# T1687 - A pane that had to open a fresh shell because its session was already restored elsewhere says nothing

## In plain terms

When the app restores your windows it sometimes finds the same shell named
twice, and it can only put that shell in one place. The other pane now gets a
new shell of its own instead of stealing it, which is right - but it arrives
looking like an ordinary empty terminal, so the pane you expected your work in
is silently a different one. It should say what happened, the way a pane whose
shell is gone already does.

## Summary

Follow-up to T1684, which made the restore refuse to hand one session to two
panes: the second leaf opens a fresh shell instead of taking the session off the
first. The refusal is currently a log line only
(`src/apprt/win32/App.zig`, "already being restored into another pane"). Every
other reason a restored pane comes up with a shell it did not have before -
a session the agent no longer knows, a relaunched tombstone - already paints the
session-interrupted notice, so the machinery exists and this case simply does
not use it.

## Where to look

- `restoreAttachOverride` in `src/apprt/win32/App.zig` - the claim refusal.
- The session-interrupted notice and `session-relaunch` policy
  (`src/termio/Remote.zig`, T230/T422) - the existing wording and the banner
  slot rules a new notice must respect.

## Goals

- [x] The pane that was refused its session says so, in its banner and its
      scrollback, in words that do not suggest the work was lost
- [x] A pane that brought its own banner back keeps it
- [x] The refused pane is its own pane: it no longer shares a pane id with the
      pane that kept the session

## The fix

- `session_notice.Reason` (`src/termio/session_notice.zig`): a second reason,
  `restored_elsewhere`, with its own sentence in the T424 `Label:` voice -
  "Session restored elsewhere: this pane's session is already open in another
  pane, and a session can only be shown in one place. Nothing was closed; this
  is a fresh shell." No "previous command" line: the command is still running
  in the other pane. `format`/`formatBanner` are unchanged wrappers over the
  new `formatFor`/`formatBannerFor`.
- `restoreAttachOverride` (`src/apprt/win32/App.zig`) marks a leaf the claim
  rule refused with `session_restored_elsewhere`, which rides
  `Surface.Overrides.Remote` -> core `Surface.RemoteBackend` ->
  `termio.Remote.Config`. The OPEN path in `Remote.threadEnter` then sets
  `did_notify` with that reason, so the notice goes through the exact
  session-interrupted machinery: scrollback fold (T423) plus the banner copy
  only when the pane's own banner did not come back (T422).
- **Found on the way:** the refused leaf also ADOPTED the recorded pane id, so
  two panes answered to one id and `+read --name=<id>` / `--target=<id>` reached
  whichever the registry found first (the first run of B8 read the winner's
  scrollback). The refused pane now gets a fresh id; the process baked with the
  recorded one lives in the other pane.
