# T1687 - A pane that had to open a fresh shell because its session was already restored elsewhere says nothing

## In plain terms

When the app restores your windows it sometimes finds the same shell named
twice, and it can only put that shell in one place. The other pane now gets a
new shell of its own instead of stealing it, which is right - but it arrives
looking like an ordinary empty terminal, so the pane you expected your work in
is silently a different one. It should say what happened, the way a pane whose
shell is gone already does.

## Summary

Follow-up to T1684, which made the restore refuse to hand one session to two
panes: the second leaf opens a fresh shell instead of taking the session off the
first. The refusal is currently a log line only
(`src/apprt/win32/App.zig`, "already being restored into another pane"). Every
other reason a restored pane comes up with a shell it did not have before -
a session the agent no longer knows, a relaunched tombstone - already paints the
session-interrupted notice, so the machinery exists and this case simply does
not use it.

## Where to look

- `restoreAttachOverride` in `src/apprt/win32/App.zig` - the claim refusal.
- The session-interrupted notice and `session-relaunch` policy
  (`src/termio/Remote.zig`, T230/T422) - the existing wording and the banner
  slot rules a new notice must respect.

## Validation criteria

- [ ] A restore whose layout names one session twice leaves the second pane
      showing a notice that names what happened, not a bare prompt
- [ ] The notice follows the same banner rules as the session-interrupted one
      (a pane with its own restored banner keeps it - T422)
- [ ] `test/win32/restore-session-dup.ps1` is extended to read the notice back
      rather than a new script being added
