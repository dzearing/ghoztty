# T2933 - On the default drawing path (no GHOZTTY_COMP_CHROME) a divider drag still cuts ~1.6 pane regions a frame (SetWindowRgn on a child whose own swap chain the region clips), and 1-3 of them a run stall 2-7 ms off-CPU: give the default path's card corner a shape that does not need a per-frame region, or retire the path

## Summary

T2932 landed the per-frame region hold for the composition path
(`GHOZTTY_COMP_CHROME=1` + `GHOZTTY_COMP_PANE_TREE=1`): there the pane's
visual carries the card shape and the desk is a visual, so the window region
clips nothing on screen and is cut once at drag end (1734 -> 31 calls a probe
run, worst `cards_us` 1.18 -> 0.53 ms).

The default path - what the release runs today - has no chrome host and each
pane presents through a swap chain on its OWN child window
(`composition swap chain ... tree=false`). There the window region is what
clips that swap chain to the rounded card, and the GDI desk paint
(`WS_CLIPCHILDREN`) fills the corners the region gives back. Holding a stale
region mid-drag would leave a grown pane's new edge clipped (a desk gap) and a
shrunk pane's corners square. The T2932 probe on the default path:
`stack trace rgn-cut-in-drag tree=0 desk_visual=0` on every one of 1612 cuts -
the hold correctly never engages - and the T2874 stall remains (1-3 ticks a
run over 1.5 ms, worst 2.1-3.1 ms).

### Is it worth it? Measured 2026-11-11 (upper bound)

The T2874 probe, release sandbox, 120 Hz, alternating arms, 3 runs each. One
arm held the region on the default path with an UNCOMMITTED knob, which made
the corners wrong but showed what the call count costs:

| arm | region cuts / run | worst `cards_us` | ticks over 8.3 ms | dropped frames (gap > 16.7 ms) |
|---|---|---|---|---|
| baseline | 1676-1727 | 1.5 / 7.3 / 7.8 ms | 3 / 4 / 3 | 3 / 4 / 3 (10) |
| held | 34-36 | 0.8-1.06 ms | 3 / 1 / 3 | 2 / 1 / 0 (3) |

Mean tick 2.58 -> 2.38 ms. In the baseline, 3 of the 10 cards stalls over
1.5 ms were followed by a dropped frame. `cards_us` is a sub-term of `place_us`,
and fewer region calls also seem to calm the moves (the held arm's worst place
dropped in one run). **Worth building: about 2/3 of the drag's dropped frames.**
The remaining drops are window moves (T2838/T2866).

### Chosen design (the second direction is T2360, blocked on T2735's RDP test)

The corner pixels come from the desk under the pane, the way the glass panes'
`desk under panes` blit already works (`Window.zig`, `blitUnder` with a
`DCX_CLIPSIBLINGS`-only DC that excludes the other children):

1. At the first frame of a divider drag on the default path, clear each card
   pane's region (`SetWindowRgn(null)`, once per pane per drag). A stale region
   would clip a growing pane's new edge.
2. Every frame, put the card's rounded shape on the pane's own swap-chain
   visual from the window thread through the presenter's shared overlay tree
   (`gl_comp_present.Presenter.overlayTree`, `comp_overlay.Layer.setRoundClip`
   / `setClip`), with `plan.treeShape(d)`, as `setTreeShape` does for a tree
   pane.
3. Every frame, blit the desk under only the 4 corner squares (d x d) of each
   held pane. They show through the visual's clip.
4. At drag end, cut the real region (the T2932 `drag_region_held` pass) and
   drop the visual clip.

The risk to check first is sync. The region is applied by the same window
manager transaction as the move. The visual clip (a DComp commit) and the
corner blit (GDI) are not. Film a mid-drag frame, or pixel-probe a corner on
every frame, before trusting it. If corners tear for a frame, commit the clip
before the `EndDeferWindowPos`, sized to the union of old and new.

Probe + analysers: `glide-probe.ps1`, `runs.ps1` (A/B arms), `ticks.py` /
`ticks2.py` (per-tick place/cards and dropped frames), in session 483aab19's
scratchpad. Earlier copies are in sessions 97a4449e and 8d80a733.

## In plain terms

Dragging the line between two terminal panes made the app redo each pane's
rounded-corner shape on every frame, and now and then that stalled a frame.
This change lets each pane's own drawing carry the rounded shape while you
drag, so the shape is redone once, when you let go. It is switched off for now
until someone looks at a drag on a real screen and confirms the corners still
look right (T2935).
