# T1925 - Measure the Windows pane sidebar's idle CPU and scroll cost with many busy panes in the all-windows list: Mac found its shimmer and question ring re-ran the whole sidebar every frame (main 321e61d7c)

## Summary

Mac 321e61d7c measured 40 windows / a dozen busy panes: the shimmer and question ring re-ran the whole sidebar update every frame (86-99% of a core idle, 31-50ms a scroll step), fixed by moving both onto Core Animation (<1% idle, ~8ms a step). Also drop-target frames are now reported only during a drag. Windows draws the shimmer/badge in pane_sidebar_motion.zig; measure the same scenario (idle CPU, scroll-step cost) and fix if it repaints the whole list per frame or recomputes drop targets while scrolling.

## In plain terms

While any pane is busy, the sidebar's shimmer redrew the WHOLE sidebar thirty
times a second - every row, every label - to move one shimmering pill. Now each
frame redraws only the pills that are actually shimmering, so a busy pane costs
a sliver of the sidebar instead of all of it. Nobody sees a difference; the
laptop fan and battery do.

## Goals

- [x] Measure what a busy-sheen frame costs (share of the sidebar repainted, process CPU)
- [x] Repaint only the animating pills, not the whole column
- [x] Confirm scrolling does not recompute drop targets (Mac's second fix) - it never did on Windows: `DropGeometry` is only built by the drag code, `scrollTo` just invalidates
- [x] A harness that measures it and can go red

## Validation criteria

- [x] A motion frame repaints only the busy pills: one busy pane of five paints **3%** of the column per frame (was **100%**), four busy panes **12%** (was 100%) - `test\win32\pane-sidebar-motion-cost.ps1` sections 1-2, from the new `motion off ... frames= area=` log line.
- [x] Process CPU with busy panes drops (Debug build, 5 panes, % of one core): one busy 4.7% -> 3.1%, four busy 5.2% -> 3.1%, idle 0% both - same harness, section 3 (informational).
- [x] The harness goes red on the old behaviour: a build with `invalidateMoving` forced to whole-column, run with `-NegativeControl`, measured area=100 and failed section 2.
- [x] The sheen still moves, stops, and tallies as before - `pane-sidebar-activity.ps1` ALL PASS (48) on the fixed build.
- [x] The dirty-rect tally and overlap test are unit-tested (`pane_sidebar_motion.zig`, T1925 tests) - `floor-lane.ps1 -Lane all`.

## How it works

`sheenAt` notes each busy/fading pill's rect into `paint_dirty` as the paint
draws it; `onMotionTick` invalidates those rects alone (`invalidateMoving`),
falling back to the whole column during a glide, list transition or drag, or
when more than 16 pills move. `paintBuffered` now buffers only `rcPaint` (a
viewport-offset DC, so the frame is still laid out in column coordinates and
the pixels are those a whole repaint would draw), and rows/tiles outside the
clip box are tallied (`tallyUnpainted`) but not drawn, so the clock, the next
frame's dirty set and the marks log still see the whole column.
