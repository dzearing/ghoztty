# T1531 - Dragging a pane header moves it within its own window, with a live drop preview

## In plain terms

Rearrange mode gives every pane a bar across its top, but so far the bar is
just decoration — grab it and nothing happens. After this you can pick a pane
up by that bar and put it somewhere else in the window: while you drag, a
coloured patch shows exactly where the pane will land, and letting go moves it
there. Drop it in the middle of another pane and the two trade places; drop it
against one pane's edge and it splits that pane; drop it against the edge of
the window and it stretches all the way across. The pane you moved is the same
pane — whatever was running in it keeps running.

## Summary

The win32-native drag itself: pressing the header grip captures the mouse, the resolved drop target is drawn as a highlight before the button is released, and releasing commits the move through the tree-rearrange operations. Scope is one window's own split tree; other tabs and windows are the next task.

## Goals

- [x] A press on a pane's header band arms a drag; a press that never travels stays a click.
- [x] While the button is down, the drop is previewed over the rect the pane would occupy.
- [x] Releasing commits the move through T1529's tree mutations, and the pane keeps its process, scrollback and session.
- [x] A centre drop swaps two panes; an edge drop splits the pane under the pointer; the window's edge band spans the pane across the whole window.
- [x] Escape and a lost capture cancel the drag without committing anything.
- [x] Scope held to one window's own tree — the drops T1532 owns preview nothing rather than promising something this task cannot deliver.

## The preview is the rect the pane will actually occupy

Not a band near the target, not a wash over the whole pane for a half-pane
split: `drop_highlight.forTarget` derives the highlight from the SAME geometry
the commit uses — a split at `insert_ratio` takes half the pane it splits, a
top-level insert takes half the window's content, a swap takes the whole of the
pane it trades with. One constant (`insert_ratio`) is shared by the preview and
the mutation, so the two cannot drift. A preview is a promise about what the
release will do, and the user only finds out it lied after letting go.

The corollary: the drops this task does not commit — a new tab, a new window,
a target in somebody else's window — resolve to NO preview rather than to a
hopeful one. T1532 lands those.

## Validation criteria

- [x] Unit tests in the `none` lane cover the preview geometry: each drop kind's rect, the four sides of a half, an odd extent never overflowing the rect it halves, case-insensitive pane-id matching, the null cases (no target, another window, the T1532 drops, an unknown pane), and the threshold (exceeded not merely reached, Chebyshev, DPI scaling). 13 tests in `src/apprt/win32/drop_highlight.zig`.
- [x] An acceptance script drives a REAL drag — posted `WM_LBUTTONDOWN` / `WM_MOUSEMOVE` / `WM_LBUTTONUP` at the window, which is the code path the mouse takes — and scores five claims: a press that never travels moves nothing, Escape mid-drag cancels, a centre drop swaps, an edge drop splits below, and a window-edge drop spans the whole window (three panes, so it is distinguishable from a pane split). `test\win32\rearrange-drag.ps1`.
- [x] The acceptance oracle asserts pane IDENTITY, not just geometry: the same pane HWNDs occupy the new slots, so a rearrange that rebuilt the pane fails even though the layout would look right.
- [x] The live preview is asserted as a real window (`GhozttyDropHighlight`) at the expected rect for each drop kind, and asserted ABSENT before the threshold, after a cancel and after the release.
- [x] `-NegativeControl` on that script fails as designed.
- [x] Both zig test lanes, `test-agent` and the `lib` build stay green.
