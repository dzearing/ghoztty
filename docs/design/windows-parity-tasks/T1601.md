# T1601 - A --command= whose argument holds a quoted path does not run: quoting a path for the pane's shell has no working form

## Summary

Found by T782. test\win32\soak.ps1 split a pane with --shell=cmd and --command=powershell ... -File "<path>". Those quotes never reached the app: PowerShell 5.1 stripped them, so the pane ran the UNQUOTED form and the soak passed. Sending them intact (byte-exact argv, via Invoke-NativeExact) makes the pane run nothing at all - the soak reports 'no telemetry from this pane' and its altscr assertion goes red; measured both ways on 2026-09-15. So a --command= value that needs to quote a path for the pane's shell currently has NO form that works, and any asset path containing a space is unrunnable from a script. Establish what +split/+new-window do with a quoted token inside --command= (does the CLI re-split it, or is it handed to cmd whole?), decide the contract, document it beside --command= on both platforms, and give test\win32\soak.ps1 back its quoting. Acceptance: a split whose --command= runs a script from a path with a space in it.

## In plain terms

If you ask the terminal to open a pane that runs something, and the thing you
want it to run lives in a folder with a space in its name, you have to put
quotes around the path — the same way you would if you typed it yourself. Doing
that used to produce a pane that ran nothing at all, with no error anywhere, so
there was simply no way to write that command. Now it runs, and the quoting you
write means what it means at your shell's prompt.

## Goals

- [x] Establish what actually happens to a quoted token inside `--command=`,
      per shell flavor, measured rather than reasoned about
- [x] Decide and write down the contract
- [x] Make a quoted path work under the default shell (`cmd.exe`)
- [x] Document it beside `--command=` for both platforms
- [x] Give `test\win32\soak.ps1` its quoting back

## What was decided

`--command=<string>` is the command line the pane's SHELL runs, quoted the way
you would quote it at that shell's prompt. That was already true on macOS and
for four of the five Windows flavors; only `cmd.exe` — the Windows default —
could not express it, and the fix is confined to that row
(`apprt.ipc.args.cmdShellArgs`). Measured on the box, 2026-09-16: `pwsh
-Command`, `wsl -e /bin/sh -lic`, a posix `-lic` and `nu -e` all round-trip a
quoted spaced path correctly *because* their command line is written and read
by the same CRT rules — and `powershell -Command` specifically BREAKS if handed
a raw tail instead, so that row had to be left exactly as it was.
