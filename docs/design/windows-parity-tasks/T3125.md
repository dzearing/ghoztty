# T3125 - A pane minimized into a blade comes back out when its viewer page focuses itself (autofocus field after a live reload or navigation, a script's focus()) - Mac a7fe3e9f8 refuses page-driven focus while the pane is a blade

## Summary

Mac a7fe3e9f8: WebKit taking first responder for a page-driven focus brought a blade out; Mac now gates makeFirstResponder on ViewerWebView.mayTakeFocus while the pane is a blade, and every app-given viewer focus goes through ViewerView.focusContent. Windows: WebView2's controller GotFocus (ViewerPane.zig ~181/5994, T1809) activates the pane; check whether a page-driven focus on a blade-collapsed viewer brings it out, and refuse it (MoveFocus back to the host / ignore activation) while collapsed, letting only app-given focus through. Mirror BladeStaysMinimizedTests' probe list in an acceptance script.

## In plain terms

On the Mac, a web page in a minimized side pane could pop that pane back open
just by putting the cursor in one of its own text fields (after a reload, say).
On Windows we checked the same thing: a minimized page that keeps grabbing
focus, and reloads with an autofocus field, leaves the pane minimized and the
cursor where the user put it. Nothing needed changing in the app; what lands is
the test that proves it and keeps it that way.

## Goals

- [x] Find out whether a page-driven focus can bring a minimized viewer strip back out on Windows
- [x] An acceptance script that stages it from outside (script focus() loop + live-reload autofocus)
- [x] A negative control that proves the script can go red

## Findings

Already guarded, by two layers, so no app change:

1. A page's own `focus()` / `autofocus` never takes OS keyboard focus away
   from another pane: WebView2 keeps it inside the document. Measured: with the
   app's debug log captured (the viewer's `got-focus handler registered` line
   present), `page got focus` was logged **0** times - on show and folded,
   across a 300 ms `focus()` loop and a live reload.
2. If a `GotFocus` did arrive for a folded strip, `ViewerPane.becomeActivePane`
   runs `Window.adoptsFocus` (T2127, b79dbe0bc), which refuses a strip the tab
   has not chosen and defers the caret back to the pane on show. The layout
   only brings out the tab's chosen pane (`stackGridOfTab` -> `noteFocus`), and
   a fold of the focused pane hands the caret on first (`rowDragStepped`), so
   the chosen pane is never a strip.

Mac's `mayTakeFocus` gate is the WebKit counterpart of layer 1, which WebView2
gives by default.
