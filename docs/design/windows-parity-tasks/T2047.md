# T2047 - The commit guard has no merge-commit path: a main merge (T1902) must be committed bare, and the guard's rejected-push remedy (pull --rebase) replays the whole merge and re-raises its conflicts

## Summary

Found in T1902 (2026-10-17, lane B). `git-commit-guard.ps1 commit` commits by pathspec (`git commit -- <paths>`), and git refuses a partial commit during a merge, so a main merge has to be committed with a bare `git commit` - outside the guard's lock, its read-back, and its push. Then the push was rejected (lane A had pushed T1035), and the remedy go.md gives for a rejected push, `git pull --rebase` (even `--rebase=merges`), REPLAYS the merge commit: `src/remote/agent`/`ws_client.zig` conflicts came back exactly as they were before the resolution. Recovery was `git rebase --abort` + `git merge origin/<branch>` (a second, conflict-free merge). Fix: give the guard a merge mode (detect MERGE_HEAD; commit the whole index after checking it holds only the merge's paths plus the named ones; read the commit back), and make its rejected-push path `git merge` instead of rebase when HEAD is a merge commit. Validation: a section in `test\win32\go-loop-guard.ps1` that builds a merge in a sandbox repo, commits it through the guard, races a remote push, and proves the push lands without re-raising conflicts.

## Validation criteria

- [ ] the guard commits an in-progress merge (MERGE_HEAD) and reads it back
- [ ] a rejected push of a merge commit recovers by merge, not rebase, with no conflict re-raised
- [ ] go-loop-guard.ps1 section proving both, with a negative control
