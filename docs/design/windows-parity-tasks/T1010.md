# T1010 - A skip-visibility violation can sit red at HEAD: the audit has no guard-due row, so nothing makes anyone re-run it

## Summary

Three sibling suite-wide audits (isolation-meta, verdict-exit, stderr-capture) carry guard-due rows covering every test script, so editing any of them makes the audit DUE and step 6 validate refuses to commit until it is green again. skip-visibility.ps1 has no such row, so a script that starts violating the skip rule goes red at HEAD and nothing tells anyone: T995 was found only because an unrelated task happened to run the audit. Add a guard row (script test\win32\skip-visibility.ps1, covering test\win32 scripts plus lib\SkipAudit.ps1) and stamp it, and give the script the -Stamp/-NegativeControl shape its siblings use if it lacks one.

## In plain terms

One of the checks that keeps the test suite honest (does every test say out loud
when it skipped part of itself?) only ran when somebody remembered to run it, so
it could sit broken for weeks. It is now part of a group of checks that is forced
to re-run whenever any test script changes. Nobody outside the loop notices; the
tracker's own gates get stricter.

## Goals

- [x] editing any test script, or the audit's own library, obliges a re-run of the skip-visibility audit
- [x] the audit can be shown to go red, not just green
