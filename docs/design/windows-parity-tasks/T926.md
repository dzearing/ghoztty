# T926 - Viewer: Ctrl and Ctrl-Shift on a link out of a live page should keep it in Ghoztty

## Summary

T825 sends every cross-site click in a live viewer page to the default browser. Mac routes the same click through the banner-link modifier scheme instead - plain click to the system browser, Cmd to a side pane, Cmd-Shift to a surface of its own - so there is one modifier scheme across every link surface. Windows already honors Ctrl on a popup (T163) and needs the same on this path. WebView2's NavigationStarting carries no modifier state, so the modifiers have to come from the page (a capture-phase listener reporting them) or from a key-state read at event time.

## In plain terms

In a website or HTML page open in a Ghoztty side pane, clicking a link that
goes to a different site always opened your browser, whatever keys you held.
On Mac, holding Cmd opens that link in a Ghoztty side pane instead, and
Cmd-Shift opens it in its own Ghoztty window, the same as links in a banner.
After this, Ctrl and Ctrl-Shift do the same on Windows.

## Goals

- [x] Ctrl-click on a link out of a live page opens a side pane
- [x] Ctrl-Shift-click opens a Ghoztty window of its own
- [x] Plain click still opens the browser, and same-site links still walk in place
- [x] The Ctrl-click that Chromium turns into a new-tab request gets the same answer
- [x] A `file://` link out of a page follows the file half of the scheme (reveal / side pane / owning app), as Mac's does

## Design (decided, not filed — mechanism only)

- Modifiers are read off the keyboard at event time (`GetAsyncKeyState`),
  the way T163's popup hatch already does, and only after a user gesture has
  been established — `routesAsLivePageLink` on the navigation path,
  `viewer_popup.modifiedLivePageLink` on the popup path — so a Ctrl held in
  another app cannot reroute anything (T860).
- Chromium delivers a Ctrl-click on a plain link as `NewWindowRequested`
  (new-tab disposition), not `NavigationStarting`, so both handlers route.
  A same-site Ctrl-click keeps T163's popup-window answer.
- Known divergence: a Ctrl-click on a cross-site `target="_blank"` link gets a
  side pane here, where Mac's Cmd on a `_blank` link takes the popup path (a
  window). WebView2 does not tell the two clicks apart; the side pane is the
  answer for the common case (an ordinary link).

## Validation criteria

- [x] `content.livePageLinkAction` maps plain / Shift / Ctrl / Ctrl-Shift for web and file links to the banner scheme — unit test in the none/win32 lanes (`viewer_content.zig`).
- [x] `viewer_popup.modifiedLivePageLink` routes only a gestured Ctrl request that leaves a live page — unit test with each gate negated (`viewer_popup.zig`).
- [x] Live WebView2: a Ctrl click out of the page lands `split:`, Ctrl-Shift lands `window:`, a gestured `window.open` off-site with Ctrl lands `split:`, and the page never navigates — legs 4-6 of the "host floor" test (`-Lane win32 -Filter "host floor"`, PASS 115s).
- [x] T825's own legs (plain click → browser, same-site walks in place, page-driven navigation untouched) still pass, now with the keyboard pinned instead of sampled.
