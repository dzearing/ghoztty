# T1660 - The task dashboard takes about a minute to answer /api/data, so the board loads slowly and polls can never keep up

## In plain terms

Opening the task dashboard leaves you looking at an empty board for close to a
minute before anything appears, and once it is up the numbers are always a
minute behind. The page asks the server for fresh data every five seconds, and
the server needs about sixty seconds to answer, so it is permanently
answering a question that is already stale - and the machine is busy the whole
time.

## Summary

Measured on 2026-09-18 against the real tracker (1600+ task files):
`GET /api/data` returned in **57.9s** (`Invoke-RestMethod ... -TimeoutSec 120`,
server started with no `GHOZTTY_TASK_DIR` override). The page polls it every
5s (`POLL_MS = 5000` in `scripts\task-dashboard.page.html:461`), so requests
overlap continuously.

The suspect is the git history work `buildPayload` does per commit rather than
the task-file read: `statusesFromDir` (`scripts\task-dashboard.js:488`) runs a
`git grep '^status:' <sha> -- docs/design/windows-parity-tasks` for every sha it
needs a bucket snapshot at, and each of those greps now scans 1600+ files.
`git log --name-only` over the same directory (line 935) is the other candidate.
Profile before fixing - the numbers above are the symptom, not the cause.

Shape of the fix to consider: cache the payload (it can only change when the
task dir or HEAD moves - both cheap to stat), and/or replace the per-sha
`git grep` with a single walk that folds statuses forward.

It also cost `test\win32\parity-tasks-seat.ps1` its green run: section O probed
liveness with `/api/data` on a 5s timeout, so a slow payload read as a server
that never came up. T861 changed that probe to `/` (a true liveness oracle) -
which means the harness no longer notices this slowness at all, and this task is
the only thing tracking it.

## Validation criteria

- [ ] `GET /api/data` against the real tracker answers in well under the 5s poll
      interval, measured the same way (stopwatch around `Invoke-RestMethod`).
- [ ] The payload is still correct: the dashboard renders the same counts,
      series and activity feed as before the change.
- [ ] A regression check exists that would fail if the payload time grows back
      past the poll interval.
