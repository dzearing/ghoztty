# T3072 - Perf audit-2: rerun the baseline and a Fable 5.2 re-audit, reconcile every audit-1 PA id against the code and its task, and file audit-3 (T2957)

## Summary

The first periodic re-audit of the Windows performance work (T2957 step 4).
Audit-1 (`docs/design/perf-audit/audit-1.md`, rolled up by T2965) found 102
PA ids across six areas and filed them as tasks. This task checks them
against the code as it stands and against a fresh baseline.

**Trigger:** 7 days after T2965 landed (2026-11-21), or once 10 audit-1 PA
tasks have closed, whichever comes first. It is parked as an event until then;
T3073 makes `next` re-queue it on its own.

**Steps:**

1. Rebuild both builds at HEAD (Debug in `zig-out`, and the ReleaseFast
   staging build in `zig-out-release`, see `docs/design/perf-audit/README.md`)
   and run `scripts\perf-baseline.ps1 -Out docs\design\perf-audit\baseline-2.json`.
   It must include every phase the audit-1 tooling tasks added by then
   (viewer phase T3033, per-thread attribution T2989, busy-phase counters
   T3059, leak slope and heap census T3005). Record which ones exist.
2. `-Compare docs\design\perf-audit\baseline-1.json,docs\design\perf-audit\baseline-2.json`.
   **Any metric worse than baseline-1 beyond tolerance is a regression: file it
   as a P0 task** naming the metric, both values and the commit range.
3. Fable 5.2 re-audit: spawn the auditors with `model: "fable"` (a user
   requirement for T2957, not a default), one per area as audit-1 did
   (R, W, M, I, V, C). Each brief carries its area's
   `docs/design/perf-audit/audit-1/<A>-findings.md` and asks, for every PA id:
   - **fixed**: the code no longer has it; cite the commit and the metric delta
   - **still open**: still true at the cited lines (re-cite them if they moved)
   - **wrong**: it never was true, or the fix is wrong; close or rewrite its task
   - **changed**: true but different in size or shape; adjust its task
   plus any NEW findings, with new PA ids continuing each area's numbering.
   Verify every claim against the code before it becomes a task (the
   claim-verification rule).
4. Write `docs/design/perf-audit/audit-2.md`: the baseline-2 vs baseline-1
   table, every audit-1 PA id with its verdict and task status, the new
   findings with their task ids, and the regressions filed.
5. Apply it to the tracker: close or rewrite the tasks marked wrong, adjust
   the changed ones, file the new findings (deps on this task, never on
   T2957), and add every new task to T2957's deps.
6. File **audit-3** the same way as this task (7 days after this lands, or 10
   more PA closes), and add it to T2957's deps.
7. If audit-2 finds no open P0/P1 PA item and no regression, say so in
   audit-2.md and on T2957: that is the umbrella's close condition.

## In plain terms

A week after the first performance review, or sooner if fixes are landing
quickly, measure Ghoztty again and check every problem the first review
found: is it fixed, still there, or was it wrong? Anything that got worse is
treated as urgent. Then schedule the next check, so the review keeps
happening without anyone having to remember it.
