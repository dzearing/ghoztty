# T2572 - Composition step 5c-3: the stack glide is declared to DirectComposition - each card edge's 45 ms follower approach as cubic pieces on the pane visual's offset and clip - so a stalled UI thread no longer stops a fold mid-motion

## Summary

Split of T2554. After 5c-2 the visuals move but are stepped from the UI thread's frame clock. Declare the follower instead: an edge from x0 to target closes 1 - exp(-t/45ms) and snaps within 0.5 px, so its whole path is known at declaration (end at tau*ln(|d|/0.5)); fit it with comp_overlay.fitCurve (T2551) onto IDCompositionAnimation on OffsetX/OffsetY and the clip rect's edges. A retarget (a drag reshaping the row, Slide.retarget) re-declares every edge from the value its curve has reached now, the way BellBorder's retarget reads the reached opacity. The UI tick shrinks to a landing timer that runs endStackSlide. Debug seam to inject a UI stall at glide start (the GHOZTTY_DEBUG_BELL_FADE_STALL_MS shape). Oracle: per-window WGC capture advance >= 0.98 at 120 Hz with a 500 ms UI stall injected (T2463 / bell-fade-onscreen.ps1 technique), stepped arm freezes; T2485 chain-fold film 0 bad frames. Needs an idle box for the filmed half (T2552's finding).

## In plain terms

When panes slide sideways in a stack, the app used to work out every frame of the slide itself. If the app was busy for a moment (a big paste, a slow redraw), the slide froze mid-way and then jumped. Now, in the new composition mode, the app tells Windows the whole path of the slide once, at the start, and Windows plays it - so the panes keep gliding smoothly even while the app is busy.

## Goals

- [x] Each sliding pane's whole path (where it is, and what of it shows) is handed to the system compositor once, as the same 45 ms follower the frames step
- [x] A drag that moves where a pane is headed re-hands the path from wherever the running one has got to
- [x] The window's thread no longer places a declared pane on its frames; it places it once, when the glide lands
- [x] A debug knob that blocks the window's thread for a while at the glide's start, and an on-screen film that proves the glide moves through it
- [x] `GHOZTTY_GLIDE_DECLARE=0` puts the frames back in charge (the A/B and negative control)

## Decisions made here

- **Strip cards stay on frames.** A card going into or out of its strip has its fade limited per frame (T2442) and its face is drawn from the window's thread (StripFace popup), so a compositor path would part from both. Only cards that glide as cards are declared; in a fold, that is every card beside the folding one.
- **The UI tick still runs.** It also paints the desk, the gutters, the strip faces and the window regions, none of which are on the compositor yet; it no longer places a declared pane, and its landing pass is what ends the glide. Shrinking it to a bare landing timer waits on those moving to the compositor too.
- **One curve per pane.** Offset and clip edges share the follower's time constant, so one 0..1 curve fitted for the pane's farthest-moving value drives them all; the other values snap within the same half pixel.
