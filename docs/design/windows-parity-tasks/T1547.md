# T1547 - A pane released over a SECOND monitor should open its window on that monitor

## Summary

`Window.workAreaAt` already resolves the drop point's monitor
(`MonitorFromPoint` + `GetMonitorInfoW`) and `pane_relocate.newWindowFrame`
clamps into that monitor's work area, so a release over a second monitor should
place the new window there by construction. Nothing has ever measured it: this
box has one monitor, so T1539's acceptance can only prove the single-monitor
case, and a multi-monitor regression here would be invisible until a user
reported it.

What the task owes: a claim that runs when a second monitor exists and SKIPS
with a named reason when it does not - the shape `Write-TestAssertedNothing`
exists for - so the coverage is real on a box that has the hardware and honest
on one that does not.

## In plain terms

On a two-monitor setup, dragging a pane onto the other screen and letting go
should open its window on that screen. Today nothing checks that it does.

## Goals

- [ ] A release over a second monitor opens the window on that monitor.
- [ ] On a single-monitor box the claim skips out loud instead of passing
      vacuously.

## Validation criteria

- [ ] `test\win32\rearrange-desktop-drop.ps1` gains a monitor-aware
      claim, green on this box as a named SKIP.
- [ ] Verified on a two-monitor box, or the task records that it could not be.
