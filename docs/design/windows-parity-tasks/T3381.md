# T3381 - Linux: +new-window and +split --focus follow T1797 on GTK - a new window opens without taking focus unless --focus, and --focus asks the compositor through xdg-activation

## Summary

T3370 left two focus gaps in src/apprt/gtk/IpcHandlers.zig. +new-window always calls gtk.Window.present on the new window (Application.initAndShowWindow), so it activates even without --focus, where win32 and the Mac open it in the background (T1797). And --focus is only grabFocus + present, which a Wayland compositor may ignore without an xdg-activation token. Make the default no-activate and route --focus through xdg-activation, saying so when the compositor declines. Pairs with T3367 (+focus). Acceptance: extend test/linux/cli-windows.sh (the headless harness cannot see focus pixels, so assert on +list focused flags).

## In plain terms

On Linux, when a script or agent opened a new Ghoztty window, that window
jumped in front and took the keyboard away from whatever you were typing in.
Now it opens quietly behind, the way it does on Mac and Windows, and only
comes forward when the command asks with `--focus` - and if the desktop
refuses to bring it forward, the command says so.

## Goals

- [x] `+new-window` without `--focus` opens the window without asking for focus
- [x] `+new-window --focus` presents the window (xdg-activation on Wayland) and the reply warns when the compositor may decline
- [x] any `--focus` raise logs whether the compositor activated or declined
- [x] `+split` without `--focus` keeps the window's focused pane; with it, focus moves to the new pane

## Decisions

- **No token forwarding.** GTK's `present` already IS the xdg-activation
  request on Wayland (it asks for a token with the app's last input serial).
  Forwarding a launcher's `$XDG_ACTIVATION_TOKEN` through the CLI would need
  a new request field on the shared wire for a token that only exists in a
  freshly launched process's environment, so it is left out.
- **Where the decline is "said".** The compositor answers after the reply has
  gone, so the reply can only carry the request-time warning (no window of
  ours is active); the actual outcome is logged a second later. The warning
  is on `+new-window --focus`; `+split --focus` and the idempotent focus of
  an existing target go through the shared verb bodies, so they log only.
- **X11** gets `_NET_WM_USER_TIME = 0` between realize and map; untestable in
  the Wayland-only harness, compile-checked.
