# T1563 - A manual Check for Updates reports none while the updater is actively suppressing one it found

## In plain terms

The user was eleven releases behind, clicked "Check for updates", and was told
there was nothing to update to. There was: the app had already found it, worked
out it was newer, and then decided not to mention it because it had mentioned it
once before. The only way out is to go to the website and run the installer by
hand — which is exactly the path the in-app updater exists to replace.

## Summary

**Reported interactively by the user, 2026-09-14.** Running `1.36.12+82b87b0d2`
(the exe on disk dated 2026-09-05, process started 2026-09-09) against a
published `win-v1.36.23`, the About box's update check answered "none detected".

It is not a fetch failure and not a comparison failure. The app's own log says
so, once an hour, for hours:

```
2026-09-14T10:50:59.289Z 5144 info(win32): update check: win-v1.36.23 already offered; not re-notifying
2026-09-14T11:50:59.277Z 5144 info(win32): update check: win-v1.36.23 already offered; not re-notifying
2026-09-14T12:50:59.441Z 5144 info(win32): update check: win-v1.36.23 already offered; not re-notifying
2026-09-14T13:50:59.327Z 5144 info(win32): update check: win-v1.36.23 already offered; not re-notifying
```

Everything upstream of that line is healthy, and was verified independently:
the releases API returns `win-v1.36.23` as the first `"tag_name":"win-v` needle
(index 1500 of 177,708 bytes, well inside `UPDATE_RESPONSE_MAX` of 1 MB), and
`isNewer(1.36.12, "1.36.23")` is true. The updater found the release and
correctly judged it newer.

**Correction, from the fix turn (2026-09-14).** The paragraph below says the
dedupe "does not distinguish a manual check from the hourly timer". At the line
it names, that is true; one frame up it was not — `startUpdateCheck` passed
`already_offered = null` whenever the trigger was manual (4d858f157, which IS in
the reported build), so the suppression branch was unreachable from a manual
check and `shouldNotify` answered "offer". So the code as it stood already
INTENDED what the user was owed, and the exact mechanism that defeated it in
their session is not recoverable from the log they have: an automatic and a
manual check logged identically, which is itself part of the defect and is fixed
here.

What is unambiguously true, and what the fix is built on, is the SHAPE the
report exposes: a correct behavior resting on a convention in the caller, with
no test anywhere exercising the manual arm, and one early return — the only one
— that answers a user who asked with nothing at all. That is a defect whether or
not it is the one that fired, and it is one an edit to either function could
arm at any time.

**The report's own diagnosis, as filed**, of `App.zig:8360`:

```zig
if (!update_check.shouldNotify(already_offered, release.version)) {
    log.info("update check: win-v{s} already offered; not re-notifying", .{release.version});
    release.deinit(alloc);
    return;
}
```

Two things are wrong on that branch:

- **It ignores `manual`.** Every other early return in `updateCheckThread`
  calls `postUpdateFeedback(app, 0)` (up to date) or `(app, 1)` (check failed).
  This one returns with no feedback at all, so a user who explicitly asked gets
  the UI's default answer — "none" — over a release the same function just
  logged as newer. Suppressing an *unsolicited* balloon for a version the user
  already waved away is right; suppressing the *answer to a direct question* is
  not. A manual check is the user asking, and it must always report what was
  found.
- **The suppression has no floor.** `shouldNotify` only re-speaks when a
  strictly different version appears. Since this project publishes daily, a
  deferred offer is normally re-raised the next day — which is what has masked
  this. But nothing bounds how far behind a user may drift while the app stays
  silent, and if publishing pauses (as it did 2026-09-09..12 under a spend
  limit) the silence is indefinite.

Note how the incident presented, because it is the reason this is P0 rather
than a papercut: from outside, the app looked *current*. The user had no way to
tell "you are up to date" from "you are eleven releases behind and I have
decided not to say". The delivery path is the only way today's work reaches a
user (D85, T1218), so an updater that can answer a direct question with a
confident falsehood breaks the whole chain.

## Goals

- [x] Asking always answers: a manual check reports what it found, whatever the
      automatic check has already said about it
- [x] The rule lives with the rule, not with a caller two functions away
- [x] No exit of the check can be silent for someone who asked
- [x] The automatic quiet spell ends after a day instead of never
- [x] The manual arm has coverage for the first time

## Validation criteria

- [x] A manual "Check for updates" over an already-offered newer release
      reports the update and offers it — never "none". Asking always answers.
      *(`update_check.decideNotify` returns `.offer` for `.manual`
      unconditionally; scenario 7 of `test\win32\update-check.ps1` stages the
      suppression and asserts the balloon FOLLOWS the ask — "asking over an
      already-offered release OFFERS it".)*
- [x] The automatic hourly check still stays quiet for a version the user has
      already been offered and deferred (T1171's behavior is preserved, with
      its own assertion so this fix cannot silently undo it). *(Same scenario
      asserts the two automatic re-checks in front of the manual one suppress;
      `decideNotify` unit tests cover the matrix in the `none` lane.)*
- [x] Every early return in `updateCheckThread` reports something to a manual
      caller; no path can leave a manual check with no feedback. Asserted
      structurally, so a future branch cannot reintroduce a silent return.
      *(The check is now `runUpdateCheck`, which returns an
      `UpdateCheckOutcome` on every path; `updateCheckThread` has ONE exit and
      hands the outcome to `reportManualOutcome`, an exhaustive switch with no
      `else`. A new outcome that nobody answers is a compile error. The two
      outcomes that used to be silent — a suppressed manual check and an
      undeliverable one — now say so.)*
- [x] An acceptance script in `test\win32\` stages the exact state - current
      build older than the feed, that version already recorded as offered - and
      asserts a manual check surfaces it, with a negative control proving the
      assertion goes red against today's code. *(Scenario 7. Two controls: the
      in-script one asserts the manual regexes find nothing in scenario 6's log,
      where nobody asked; and the policy was reverted by hand
      (`decideNotify` suppressing manual again), rebuilt and re-run — the run
      went `2 FAILURE(S) (23 assertions passed)` on exactly "the offer is
      raised again for the user who asked" and "no manual check ended without
      an answer", with the new `manual update check ended suppressed with
      nothing to show` warning in the log. Restored and green after.)*
- [x] The drift floor is decided and recorded: either the dedupe expires, or it
      is bounded by how far behind the running build is, so a user cannot sit
      silently many releases back. *(Decided: **the dedupe expires**, at
      `update_check.offer_expiry_ms` = 24h from the moment the balloon was
      actually shown — `App.update_offered_at_ms`, an atomic written by the GUI
      thread and read by the worker. Expiry rather than a
      how-far-behind bound because the release distance is not a number this
      code has: the feed gives the newest tag, not the count between, so a
      "5 releases behind" rule would have to be inferred from patch arithmetic
      that a minor bump breaks. A day is also the publishing cadence, so the
      floor reads the same from either end: at most one reminder a day, and
      never indefinite silence.)*
