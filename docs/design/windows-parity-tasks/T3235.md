# T3235 - The release session agent idles at about 1% of a core with one session, and its base memory doubled to 17.7 MB (baseline-4, T3151)

## Summary

perf-baseline agent phase, release: idle_cpu_cycle_pct 0.96 (baseline-4) and 0.997 (repeat), with 1 attached session over 30 s; baseline-3 read 0.05 user-time (pre-T3111, so not strictly comparable, but 20x). Debug also reads 1.0. Base private_mb 9.3 -> 17.7 and per-session child private 12.5 -> 17.8 MB in release only (debug unchanged 9.8 / 12.45), which points at 674561478 (T3017: release agents use the fast allocator - smp_allocator retains per-thread). Idle CPU leads: 29ba077ff (T3019, per-session parse off the agent lock), 7040bd7e8 (T3021), 4a66a406e (T3020). Name the thread from agent wakeup attribution, then fix or justify. Also: the repeat run's per_session_child_private_mb read 2671 MB, a bad sample (a transient child counted?) - make the reader robust to it. P1 not P0: controller ordering (T3151).

## In plain terms

Ghoztty's background session keeper runs all day, even when nothing is happening. It was using about 1% of a CPU core while idle, because once a second it asked Windows for a full list of every program running on the machine. That list is now fetched in a cheaper way and shared between the two checks that need it, so the idle cost drops by about 40%. Removing the rest is a follow-up (T3243).

## Goals

- [x] name the thread that wakes at idle (perf-baseline's agent phase now splits idle wakeups and cycles by thread, and can profile the idle span)
- [x] cut the idle cost it found (cheaper process snapshot, one per tick)

## Root cause

Agent wakeup attribution (Debug, 1 session, 30 s): one thread, the store's
`reaperLoop`, at 29.6 of 30.4 attributed Mcycles/s and 2.6 wakes/s. Profiled
with `cpu-sample.ps1 -Mode cycles`: `snapshotParentsWindows`
(`CreateToolhelp32Snapshot` -> `ZwQuerySystemInformation`, section map/unmap,
`Process32NextW`) under both `sampleDescendants` (every second, for
`META{has_descendants}`, T356) and `sweepVanishedChildren` (every 5 s, T1162).
On this box (344 processes) one Toolhelp32 snapshot costs 18.7M cycles; a bare
`NtQuerySystemInformation(SystemProcessInformation)` 10.7M.

That cost is almost all KERNEL time, and baseline-3's reader counted user time
only (T3111), so the "20x since baseline-3" was mostly the measurement being
fixed, not T3019/T3020/T3021. The same reason Debug reads the same 1%: the
cost is the OS enumeration, not our code.

## Fix

- `proc.zig`: `snapshotParentsWindows` makes one `NtQuerySystemInformation`
  call into a buffer sized from the last table, and walks it in place
  (`parentsFromProcessInformation`, unit-tested against a synthetic and a
  malformed table). Same pid / parent pid Toolhelp reported.
- `session.zig`: `sampleProcessTable` answers the descendants sample and the
  vanished-child sweep from ONE snapshot per reaper tick.
- `perf-baseline.ps1`: the agent phase records `idle_wakeup_attribution`, and
  with `-SampleAgent` (no `-BusyPersistence`) profiles a second idle span.
- `ProcessMemory.ps1`: `Get-Descendants` skips a "child" born before the
  process it names as parent (pid reuse) - the probable cause of the 2671 MB
  `per_session_child_private_mb` sample; the walk is now `Select-Descendants`,
  tested in section D of `perf-baseline-reader.ps1`.
