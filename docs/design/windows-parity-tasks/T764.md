# T764 - A new pane opened during an agent WEDGE is handed the stuck shared connection instead of falling back to exec

## In plain terms

The background helper that owns your panes can freeze — still running, but
answering nothing. The app already knows how to cope with a helper it cannot
reach: it opens the new window as an ordinary terminal instead. But while the
helper is *frozen* rather than gone, it did not do that. Every window and split
you opened during the freeze was wired to the stuck helper and came up dead: a
terminal you can type into and that never answers. So one frozen helper spread
to panes that had nothing to do with it. After this, a window opened during a
freeze is an ordinary working terminal, and the panes that were already there
are still repaired the moment the helper comes back.

## Goals

- [x] A window or split opened while the helper is frozen opens as a WORKING
      terminal, not a frozen one
- [x] Opening it stays fast — it must not block waiting for a helper that will
      never answer
- [x] The panes that were already frozen still come back when the helper does
- [x] An acceptance arm that opens a pane mid-freeze and proves it works

## Summary

Found landing T723. LocalAgent.sharedConnection's fast path returns the cached connection whenever its state is not .dead, and a wedged agent's link sits in .reconnecting indefinitely - .dead is only ever reached via a server-sent DETACHED frame. So a window or split opened while the agent is wedged is wired to a connection that answers nothing, rather than taking the documented fallback of a plain exec pane. The exec fallback exists precisely so an unreachable agent cannot take window creation down with it; the liveness test it gates on is the one thing that cannot tell a wedge from health.
