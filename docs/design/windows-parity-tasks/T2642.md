# T2642 - Dragging a divider beside a pane banner bites a block out of the pink bar again: 23-83 bitten frames per drag on the current build (T2414 regression), and the overlays-before-bands order no longer changes the count

## Summary

Found by T2476's committed harness on an idle box, 2026-11-02 (Debug build at 3cdf6d4b8 + T2476). T2414 (P0 user report, closed at ec075eb1a with 0 bitten frames over 864) is back: during a posted divider drag, a banner beside the bar covers 2-4 px of the accent bar on its rows for one frame per drag step.

Measured with `test\win32\divider-flicker.ps1 -Live` (BITTEN = a banner row not accent where the mid row is):

- T2414's own scene (`-NoViewer -Panes 1 -Orientation vertical`, banners on both terminals): 83 bitten frames of 598, on both halves of the drag.
- With an HTML viewer as the far pane (banner on the near side only): 27-38 per drag at 1, 4 and 9 panes, all on the half where the bannered pane SHRINKS - the banner still at its wider old rect over the bar just painted.
- `GHOZTTY_OVERLAYS_AFTER_BANDS=1` (the pre-T2414 popup order, added by T2476): 76 and 39 - no different. So the popups are still placed before the band paint; what moved is WHEN the banner's new rect reaches the screen relative to the GDI bar. Suspects, newest first: the banner pre-render (a9f898177, T2400 2026-10-29: the frame is rendered before the pane batch and presented by UpdateLayeredWindow), the ULW present itself (b6ffb7759), and T2459's drag holds. Bisect with the harness: each run is ~15 s.

**Half of it is fixed (2026-11-02, this task's first commit).** Root cause one: 3e26994eb (T2516, 2026-10-30) made `clearVacatedPaneStrips` paint the whole desk - accent bars included - in the elevated style, and it runs before `placePaneOverlays`: the pre-T2414 order by another route, which is also why the knob changed nothing. The popups now go ahead of that desk fill (`placeOverlaysBeforeBands`). Measured on the idle box, same harness, Debug:

| scene | HEAD 575a88723 | fixed | fixed + `-Control bite` |
|---|---|---|---|
| `-NoViewer -Panes 1 vertical` | 40 | 17, 25 (20 with `GHOZTTY_KEEP_VACATED_GUTTERS=1`) | - |
| viewer layout, `-Panes 1 vertical` | 19 | 8 | 13 |

**What is LEFT** (the rest of this task): 8-25 bitten frames per cell, still on the half where the bannered pane shrinks. Frame 81 of the first fixed run (`temp\divider-flicker\20261102-072546-none\1-vertical\frames`): the bar has stepped 8 px right while the far pane's banner popup is still at its old, wider rect over 3 px of it; the banner catches up one composed frame later. The popup path is in use (no "banner path visual" line, redirection surface present), and its resize is one `UpdateLayeredWindow` with position, size and pixels, now issued BEFORE the GDI desk/band paint - yet the bar still reaches the screen a frame ahead of it. Ruled out: the vacated fill (the keep-gutters knob reads the same), the dim washes (moved in an earlier batch), the drag holds (they freeze content, not window rects), a bar paint ahead of the pass (the drag step calls `layoutSplitsLive` directly). Leading hypothesis: DWM latches a layered window's ULW update later than a GDI write to the redirection surface, so order on the UI thread is not order on screen; T2414's 0 of 864 used its own probe (its tick rate may not have been this harness's 8 ms). Next: run T2414's probe (`temp\t2414\divider-bite-probe.ps1`, if still on disk) against this build, and try `-TickMs 16` to see whether the residual is a two-passes-per-frame effect.

Fix target: the banner's resize and the bar's paint show in the same composed frame, so no banner pixel ever covers the bar. The harness's `Lc` rows are the acceptance, and once they read 0 the bite control must be shown to bite again (`-Control bite` above 0 while the fixed build reads 0) - today it cannot, because both read the same.

## In plain terms

While you drag the line between two panes, a pane's banner covers a small block of the pink line on every step, so the line flickers next to the banner. It was fixed in October and has come back. After this, the line stays solid the whole drag.
