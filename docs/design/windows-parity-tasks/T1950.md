# T1950 - Typing in Ghoztty over a Remote Desktop (Windows App) session is very slow: measure it in a real session, then a lightweight mode whenever SM_REMOTESESSION is set

## In plain terms

On the user's own machine, Ghoztty 1.39.8 types instantly. Reached through
Microsoft's Windows App (a Remote Desktop session), typing is very slow:
every keystroke has to be drawn on the remote machine and then shipped
across the wire as a picture. Make Ghoztty cheap to draw and cheap to ship
when it knows it is running over Remote Desktop.

## Summary

User report (2026-10-14, after the T1935 fix shipped in 1.39.8): "on local
here, this is awesome and fast, but on a microsoft windows app remote
session, typing in ghoztty is so so slow."

What is known (? INFERRED until measured; that is step 1):

- Over RDP without a GPU, the system `opengl32.dll` cannot give GL 4.3, so
  T1251/T1252's fallback loads the shipped Mesa `d3d12` driver. In a session
  with no GPU passthrough, D3D12's adapter is WARP (software), so every frame
  is rendered on the CPU and presented by a blit.
- RDP ships changed pixels. The renderer draws whole frames, and the elevated
  style's translucent glass panes, focus glow, blur and animations change
  many pixels per keystroke. All of that is encoded and sent.
- T1462 (an output burst presents ~500 frames/s) costs far more over RDP
  than locally.
- `DimOverlay.zig:158` already checks `SM_REMOTESESSION` for one case
  (T1295), so the detection exists.
- **Nothing about real RDP use has ever been measured** (T1256 blocked:
  "needs a session"). The user is in one now.

### Step 1 - measure in the user's session (the user runs a script)

Write `scripts\rdp-perf-probe.ps1`, to be run inside the RDP session. It
reports:
- which GL is loaded (system `opengl32` vs `<install>\gl\opengl32.dll`)
  and the D3D12 adapter (WARP or a real GPU)
- `GHOZTTY_PERF=1` fps, `swap_avg_us`, `swap_max_ms`, `wakeups_per_s`
- keystroke-to-present latency in a plain shell pane

Run it with the default config and again with the lightweight settings
below. The difference says which costs matter.

### Step 2 - a remote-session lightweight mode

When `GetSystemMetrics(SM_REMOTESESSION)` is set (re-checked on
WM_WTSSESSION_CHANGE, since the same session can move between console and
RDP), and unless the user's config overrides it:
- flat panes, no glass, no blur, no focus-glow animation, no sidebar
  shimmer, no cursor blink
- `unfocused-split-opacity = 1` (no dim layer to recomposite)
- cap presents at a modest rate and coalesce bursts (fold in T1462)
- the update banner and the connection pill say "Remote Desktop: lightweight
  mode", so it is not mysterious
- Mac half: macOS Screen Sharing is the analog. File a `seat: mac` task only
  if step 1 shows the mode is worth it.

### Step 3 (only if the numbers say so) - draw less per frame

Damage-tracked presents (only changed rows) so RDP encodes a few rows per
keystroke instead of the window. That is a renderer project (WGL has no
partial swap; DXGI `Present1` with dirty rects does), so it is filed
separately if step 2 is not enough.

### Things the user can do today (in the close-out and in docs)

- Config on the remote machine: `macos-pane-style = flat`,
  `macos-pane-glass = false`, `background-blur = false`,
  `cursor-style-blink = false`, `unfocused-split-opacity = 1`.
- On the remote PC (admin, the user's call): group policy "Use hardware
  graphics adapters for all Remote Desktop Services sessions" lets the
  session use the real GPU instead of WARP. "Prioritize H.264/AVC 444
  graphics mode" makes full-frame updates much cheaper to ship.
- Best of all: run Ghoztty locally and open the remote machine with
  `ghoztty +new-remote-window`. Rendering stays local and only terminal
  bytes cross the wire. That is what the remote-machines feature is for.

### Second report: CPU (2026-10-14, same session)

"I have like 11 windows open and cpu is 91% on 32 cores, ghoztty terminal
process is 47% of that, 15 cores and 2.5 gb of memory, drawing 24 panes
across 12 windows." That is T1935's signature (5-15 cores, 2.9 GB, 22
panes). The version on that box is unconfirmed: auto-update (T1934) is
parked, so it may still be 1.39.7. **Record `ghoztty +version` and the loaded
GL modules first.**

If it is 1.39.8, the T1935 fix (f19b12e09: present only changed frames, a
500 ms forced present per pane, title churn coalesced) still leaves:

- **Cell animations draw.** Claude Code animates text cells (the spinner and
  the status line), so about 13 panes still present at ~10 fps each.
- **The 500 ms bound presents every pane** at 2 fps, including panes nobody
  can see.
- **Hidden windows still render.** Nothing skips a minimized, fully covered,
  or (over RDP) undisplayed window. Locally each frame is cheap on the GPU;
  over RDP each one is software-rendered (Mesa d3d12 on WARP) and then
  encoded.

So step 2 gains, for ALL sessions (not just RDP, because it is waste
everywhere):
- **No presents for a window that cannot be seen**: IsIconic, or fully
  covered (DWM cloaked / occlusion), or a background tab. Mark it dirty and
  draw once when it becomes visible.
- **No 500 ms forced present for a pane that is not visible.**
- In remote-session mode, panes other than the focused one animate at
  1-2 fps.

Validation addition:
- [ ] 24 panes across 12 windows, 13 animating like Claude Code: app CPU
      with all but one window minimized or covered is under 0.5 core
      (measured, with a negative control that draws hidden windows).

## What landed

- `scripts\rdp-perf-probe.ps1` (standalone, ASCII, PS 5.1). Part 1 is
  read-only: `SM_REMOTESESSION`, `SESSIONNAME`/`CLIENTNAME`, OS, CPUs, screen
  and DPI, `Win32_VideoController`; per running `ghoztty.exe` the path, CPU in
  cores over `-Seconds`, threads busy at >= 5% (the WARP pool signature), working
  set and private bytes, the GL/D3D modules it loaded labelled `(system)` or
  `(bundled Mesa)`, windows/panes from `+list --json`, and the last
  `loaded OpenGL` / `low-power` lines of `ghoztty.log`. Part 2 (`-Measure`)
  launches a separate instance (pipe suffix, agent instance and LOCALAPPDATA of
  its own, persistence off, `GHOZTTY_PERF=1`) with a spinner window and a
  focused cmd window, once per `-Modes` entry (default `off`, `auto`), and
  records per-pane fps, swap_avg/max, CPU, echo median/p95 over 12 samples,
  and the `+read` round trip that bounds the echo figure's resolution. It
  stops only its own instance and that instance's children, by pid.
  `-TestDesktop` (repo use) runs part 2 on a background desktop.
- `test\win32\rdp-perf-probe.ps1` + guard row `rdp-perf-probe`.
- `docs/claude/build.md`: "Slow over Remote Desktop or on a Cloud PC".
- Mechanism decisions (not filed, per go.md 5b): echo is measured with
  `+send-keys` + `+read` polling rather than real key input, because real input
  needs the input desktop and the probe must be runnable unattended; it is
  reported as the SERVER half of a keystroke, beside its own resolution floor.
