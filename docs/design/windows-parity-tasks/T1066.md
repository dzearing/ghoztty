# T1066 - Nothing proves a live TUI keeps its mouse when you re-attach to a session

## Summary

Fallout of T1055. That task stopped a restored pane re-arming a dead program's "keep sending me mouse reports" agreement, and the whole reason it is a fix rather than a trade is the other half: a program that is STILL RUNNING must get its real mouse tracking back. The mechanism is there and reads correctly — the agent's `GridEmulator.snapshotAlloc` (`src/remote/agent/grid_snapshot.zig`) serializes with `.modes = true` and leaves `input_modes` at its default of true, so the repaint it appends on ATTACH restates the modes the live child actually has, and it lands right after the client's `input_mode_reset`. That ordering is asserted nowhere. Nothing on the box proves a live alt-screen TUI with mouse tracking on comes back through a re-attach still receiving pointer events. Work: an acceptance arm that runs a mouse-tracking program in an agent-backed pane, kills only the app, relaunches, and shows the restored pane's terminal still has the tracking modes set (the manifest snapshot cannot answer this — read the mode state the AGENT's repaint left, e.g. by having the program echo a DECRQM reply, or by asserting the repaint bytes the client applied). Blocked on nothing; T1055 landed the code this guards. See also T1067, which may mean the mouse modes never reach the pane in the first place on Windows.

## In plain terms

If a program that follows your mouse is running in a pane and Ghoztty restarts, the
mouse should still work when the pane comes back. We believe it does — the piece that
restores it is in place and was read line by line — but no test on this machine has
ever actually watched it happen. This is about proving it, so a future change cannot
quietly take your mouse away.

## Goals

- [x] An on-box acceptance arm runs a mouse-tracking program in an agent-backed pane
- [x] It kills only the app, relaunches, and reads back whether tracking is still armed
      (by the strongest oracle there is: a click at the restored pane reaches the SAME,
      still-waiting child as an SGR report)
- [x] It has a negative control that goes RED if the agent's repaint stopped restating modes

## Outcome

The mechanism T1055 relied on works and is now watched. Side finding, fixed in the
harness: section M's arming child left the console in raw VT-input mode on exit, so
the shell after it read the click's trailing press/release and send-keys' bracketed-paste
markers as typed text (`^[[200~...arm-live.cmd^[[201~` -> "cannot find the file"). The
child now drains its input and restores the console mode on exit, as a real TUI does;
the TERMINAL modes are still left armed, which M3 needs.
