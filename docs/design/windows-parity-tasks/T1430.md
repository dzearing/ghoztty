# T1430 - No on-box acceptance for the revocation park in the agent's --relay daemon mode

## In plain terms

The fix that takes a signed-out machine off the network is proven for the way
Ghoztty normally runs its background service. There is a second, hand-started
way to run it, and nothing on this box has ever watched that one do the same
thing. The behaviour is there in the code; what is missing is the check that
would notice if it stopped being there.

## Summary

T1427 gives `ghoztty-agent` a pending-revocation watcher and wires it into both
of the agent's relay paths: the `SharingUplink` reconciler (`--listen-pipe`
with sharing.json enabled, which is how the app runs it) and `runRelay`
(`--relay=<base>`, the explicit daemon mode). Only the first is observed on the
box — section 5 of `test\win32\agent-sharing-uplink.ps1`.

The `--relay` path differs in one way that matters and is therefore worth its
own evidence: it constructs the watcher with `owns_resume = true`, because
nothing else writes the desired link state there, so the RELEASE edge is a
`LinkControl.reconnect` the watcher makes itself rather than one the reconciler
makes on its next tick. That is the branch no harness has ever executed, and
the failure it would hide is a machine that comes back from a sign-out and then
never comes back online.

`test\win32\agent-relay-session-e2e.ps1` already runs a real agent against
`lib\FakeAgentRelay.ps1` (in `--listen-pipe` mode, it turned out, not
`--relay`), so the cheap shape is a section there that starts a `--relay`
daemon against the same fake relay rather than a new harness: arm a record, watch the control link go down, watch the
de-enroll arrive, clear the record, watch the link come back on its own.

## Goals

- [x] A real `ghoztty-agent --relay=<base>` daemon is driven through the whole
      revocation cycle on the box: arm, park, de-enroll, clear, resume
- [x] The resume is proven to come from the watcher itself, with a negative
      control that turns the assertion red when it does not
- [x] Any later edit to the watcher owes this harness a run

## Validation criteria

- [x] A `--relay` agent parks its control link within a tick of a pending
      revocation being armed beside its relay.env. -- section 7 of
      `test\win32\agent-relay-session-e2e.ps1`: the agent prints the park line
      and the fake relay logs a new `CONTROL down` within 15s; no new
      `CONTROL up` arrives over the next 10s (two ticks, past the 3s backoff).
- [x] The de-enroll POST arrives at the fake relay from that agent, with no app
      running. -- same section: `REQ POST /v1/agent/deenroll` in the relay log;
      the record survives the 404.
- [x] Clearing the record brings the control link back up WITHOUT any other
      process reconciling it (the `owns_resume` branch). -- same section: a new
      `CONTROL up auth=Bearer <token>` after the record is removed. Negative
      control: with `runRelay` constructing the watcher `owns_resume = false`
      the run goes 1 FAILURE (27 passed) on exactly that assertion; reverted.
- [x] `scripts\guard-due.ps1` gains the coverage row so the branch cannot go
      unobserved again. -- the `agent-relay-session` row now covers
      `revoke_watch.zig` and `relay_revoke_pending.zig`; the green run stamped
      it (12 files). ALL PASS (28 assertions).
