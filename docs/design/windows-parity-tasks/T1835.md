# T1835 - Dragging a divider on Windows floods the program with resizes and pops a size overlay: Mac now debounces resizes and shows no overlay by default

## Summary

Mac 733b03e58: termio resizes reach the program on a trailing debounce (100ms settle, 350ms cap) instead of every 25ms; a 600ms divider drag went from 35 resizes to about 4 (aDragDoesNotStormTheProgramWithResizes). resize-overlay now defaults to never. Both are shared core (src/termio/Thread.zig, src/config/Config.zig) and land with the merge. Windows owes: (1) prove a win32 divider drag and a window-edge resize deliver a handful of resizes to a ConPTY child, not dozens - and that the final size always arrives; (2) the win32 resize overlay honors the new default; (3) no regression to the T1800 / resize-flicker / drag-perf harnesses.

## In plain terms

When you drag the line between two panes, or resize the window, the program
running in the pane (Claude Code, an editor) used to be told about every
single in-between size and repaint itself for each one, which flickers. The Mac
build now only tells it a few times during a drag, always including the final
size, and no longer pops a "columns x rows" box in the middle of the window.
This task proves the Windows build behaves the same way.

## Goals

- [x] A divider drag reaches the program in the pane as a handful of resizes, not one per mouse move
- [x] A window-edge resize does the same
- [x] The final size always arrives, and it is the true final size
- [x] No size overlay by default; it still appears when asked for
- [x] No regression in the neighbouring resize harnesses (two pre-existing reds traced and filed, not caused here)

## Validation criteria

- [x] Divider drag storm bounded - `test\win32\resize-debounce.ps1` B: 40 posted moves in 3.1s reached the program as 8 resizes (Mac's bound for that duration: 10). Counted BY the program (`lib\count-resizes.ps1`, WINDOW_BUFFER_SIZE_EVENTs from its console input), not by the app.
- [x] Window resize storm bounded - same script C: 40 SetWindowPos steps in 1.9s -> 5 resizes (allowed 7).
- [x] Counter is not blind - A: five resizes 600ms apart arrive as 5.
- [x] Final size is the true size - D: storm end state 71x31 / 53x31 equals the size the same geometry gets from one single move/resize.
- [x] Overlay - E: none seen during B/C with default config; `--resize-overlay=always` shows it to the same probe (Window.showResizeOverlay already honors the config; the default moved to `never` in shared Config.zig).
- [x] Teeth - `-NegativeControl` inverts B and fails (1 FAILURE, 9 passed).
- [x] Guard row `resize-debounce` (covers src\termio\Thread.zig + the harness + fixture), stamped by a clean green run.
- [x] Neighbours: `resize-flicker.ps1` ALL PASS (24). `split-divider.ps1` 1 FAIL = T533 control 22px short, already filed as T1853 (from T1831's geometry change, not this task). `drag-perf.ps1` 1 FAIL = scores every pane count with the 2-pane sample, already filed as T1854 (my re-filings T1857/T1858 closed as its duplicates).
