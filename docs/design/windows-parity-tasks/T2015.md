# T2015 - viewer-restore.ps1: a restored window brings its panes back in the wrong order (viewer,viewer,terminal) and the agentless web viewer is not live (D2, J4, J7)

## Summary

viewer-restore.ps1 3 FAILURE(S) (54 passed): D2 'panes came back in the same order and kinds (got viewer,viewer,terminal)', J4 same shape, J7 'agentless restore web viewer is LIVE (title 5 -> -1)'. Found in T2005 (2026-10-16): red in lane A on HEAD 161784011 with the script byte-identical to HEAD (run serially, -Width 1, alone), so it predates T2005. Logs: scratchpad aplogs3 of that turn.

## In plain terms

When Ghoztty restarted and its background session helper was missing or
broken, every document and web page pane came back blank: the frame was there,
the page never loaded. Now those panes load as they do on any other start. The
test that should have caught this had also been failing for a second, harmless
reason, which hid the real bug: it built its layout in a way that stopped
working when command-line splits stopped stealing focus.

## Goals

- [x] the restore test builds the layout it means to test, and says so if it ever doesn't
- [x] after a restart with no session helper, viewer panes load their pages again
- [x] the test is tied to the code it covers, so the next edit re-runs it

## Root cause

Two unrelated defects behind one red script.

1. **D2/J4 were the fixture, not the restore.** Since T1797 a `+split` without
   `--focus` leaves the tab's active pane where it was. The fixture's second
   split used `--target=vr` (the window's active pane), so it split the doc
   viewer instead of the terminal and built `viewer,viewer,terminal`. Printing
   the pre-restore order proved the restore reproduced exactly what was built.
   T1797 moved seven harnesses to the new contract and missed this one.
2. **J7 was a real product defect.** The app's stderr in the no-agent relaunch
   read `environment creation failed hr=0x800401F0` (`CO_E_NOTINITIALIZED`) for
   every viewer. The UI thread's only COM init was the lazy one in
   `App.taskbarList`; an ordinary start reached it before any viewer existed,
   but a restore with no local agent builds its viewers first. `webview2.zig`'s
   test comment already claimed "the app initializes one at startup" - it did
   not until now.

## Fix

- `App.init` calls the new `App.ensureCom()` right after the struct is built;
  `taskbarList` uses the same helper.
- `test\win32\viewer-restore.ps1`: the second split anchors with
  `--pane=vrterm`; new **D0** setup control asserts the built order; the page
  server reads until the request headers are complete (bounded) instead of one
  50 ms look, and logs an empty connection; J7 prints a diagnostic on failure
  (pane title + what the server saw); the script stamps its new guard row.
- `scripts\guard-due.ps1`: new `viewer-restore` row (script,
  `session_layout.zig`, `webview2.zig`).

A first theory - a late WebView2 `GotFocus` reclaiming the active pane - was
built, tested, shown not to change the result, and reverted.
