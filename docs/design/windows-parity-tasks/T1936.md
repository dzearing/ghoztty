# T1936 - Installed Ghoztty ships no PDBs, so a hot or hung app on a user's box cannot be symbolized: stacks of ghoztty.exe and ghoztty-agent.exe are bare offsets

## In plain terms

When Ghoztty misbehaves on a user's machine (pegged CPU, a hang, typing lag), nobody can see which
code is running, because the installed app has no debug symbols. Every release should publish its
symbols so a stack taken on any box can be read.

## Summary

User report (2026-10-14, box dzearing1), filed while investigating T1935: "also log a bug for no
pdbs".

`%LOCALAPPDATA%\Programs\Ghoztty\` (1.39.7+99590020e) holds `ghoztty.exe`, `ghoztty.com`,
`ghoztty-agent.exe` and `share\`, and no `.pdb`. When T1935 was investigated, the app was burning
5-15 cores across ~30 per-pane threads, and the hot frames could not be named. Without the PDB a
dump or WPR trace of `ghoztty.exe` resolves only Windows frames (ntdll, kernelbase, opengl32), and
every Ghoztty frame is a bare `ghoztty+0x...` offset.

This is deliberate today. The published zip and MSI exclude `.pdb` on purpose (the PDB is ~100 MB
beside a ~48 MB exe; see D64 and the "no .pdb, no .bak" checks in the packaging tasks). The PDBs
only exist in the build box's `.zig-cache\o\` and are not kept per release. So the gap is not "put
the PDB in the installer". It is that **nothing publishes or retains the symbols for a shipped
version**, so a user-box stack can never be resolved after the fact.

## Fix direction

- For every `win-v*` release, publish the matching `ghoztty.pdb` and `ghoztty-agent.pdb` as a
  separate asset (for example `ghoztty-symbols-<version>.zip`), kept as long as the release is.
  Optionally also publish a symbol-server layout (`<name>.pdb/<GUID+age>/<name>.pdb`) so `cdb`/WPA
  can use it with a plain `srv*` path.
- Verify the PDB GUID/age matches the shipped exe (`dumpbin /headers` or `llvm-pdbutil`), so a
  rebuild can never publish mismatched symbols.
- Add a helper, `ghoztty +symbols` or `scripts\fetch-symbols.ps1 <version>`, that pulls the matching
  symbols for the running build into a local cache and prints the `_NT_SYMBOL_PATH` to use.
- Document the triage recipe in HACKING.md: WPR `-start CPU`, or a `.dump /m` with `cdb`, plus the
  symbol path. Name the tool that is actually installable on a user box (cdb/WinDbg are not here
  by default; WPR is).

## Goals

- [x] Every `win-v*` release publishes a third asset, `Ghoztty-symbols-<version>-x64.zip`, laid out
  as a symbol store (`<name>.pdb/<GUID+age>/<name>.pdb`, `<name>.exe/<stamp+size>/<name>.exe`) so
  `srv*<unzipped dir>` is the whole symbol path

- [x] The Mac half is filed (T1941, seat mac), and so is the check on the first real release (T1942)

## Design

- **A symbol store, not loose PDBs.** Debuggers and WPA find a PDB by GUID+age under `srv*`, with
  no renaming and no risk of picking up a same-named PDB from another build. The images go in too,
  because a minidump holds no module memory and x64 unwinding reads the image's `.pdata`.
- **The identity check is the one a debugger applies.** The exe's CodeView (RSDS) record names a
  GUID and age, the PDB's info stream carries the GUID and its DBI stream the age. Pure-stdlib
  Python, so it runs on the Linux release runner and on the box alike. It runs after signing, so
  the stored images are the exact bytes the packages carry. Authenticode changes neither
  TimeDateStamp nor SizeOfImage, so the image key is the same either way.
- **The packages stay PDB-free (D64).** The PDBs ship only in the new asset. The updater picks
  `.msi` by extension, and the website links name the MSI and the portable zip, so a third asset
  is invisible to both.
- **No `+symbols` CLI verb.** A new verb would need a Mac twin (platform-symmetry rule), and the
  job is triage tooling rather than product behavior, so it is a repo script plus a recipe that
  needs no repo (download the asset, unzip, `srv*<dir>`).
- **Size:** 62 MB for a release build (92 MB PDB + 35 MB exe + .com + agent, deflated).
