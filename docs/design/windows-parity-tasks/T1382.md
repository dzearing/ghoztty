# T1382 - next's CHECK FIRST misses a task that names a script by bare filename, which is how T571 read 0-commits-since while its subject had been rewritten twice

## Summary

`Get-TaskCodePaths` (`scripts\parity-tasks.ps1`) extracts the files a task
names with `$StalePathPattern`, which requires a leading directory segment:
`(?:src|scripts|test|macos|dist|include|images)[\/]...`. A task that names a
script the way people actually write it in prose - `pane-banner.ps1`,
`floor-lane.ps1`, `go-loop-exec.ps1` - contributes NO path, so
`Get-StaleSignal` finds nothing to look for and `next` prints
`0 commit(s) since touched its files` and no `CHECK FIRST`.

That is the check failing on exactly the shape it exists for. T571 was filed
2026-08-07 against a permanent `SKIP T209 chevron fill` in `pane-banner.ps1`;
T282 and T845 rewrote that section and removed the SKIP weeks before it was
handed out. Every mention of the file in the card was bare, so on 2026-09-05
`next` handed it over with `0 commit(s) since touched its files` - the exact
reassurance T404 built this signal to withhold. The turn caught it by reading
the script, which is the thing the signal is supposed to make unnecessary.

The fix is to resolve a bare filename too: a `\w[\w.-]*\.(ps1|zig|swift|md|json)`
token that matches exactly ONE tracked file in the repo is that file. One match
only - an ambiguous basename must stay silent rather than pick a side, since a
wrong path produces a confident wrong "CHECK FIRST" and that is worse than none.
Directories stay excluded for T404's original reason.

## In plain terms

When the loop hands itself a job, it tries to warn "careful, somebody has
changed this area since this was written". The warning only works if the job
description spells out a full folder path. Write the filename on its own -
the way anybody normally would - and the warning silently never fires, so
stale jobs get worked as if they were fresh.

## Goals

- [x] A bare `foo.ps1` in a task resolves to the one tracked file with that
      name, and contributes to the stale signal.
- [x] An ambiguous basename resolves to nothing and stays silent.
- [x] T571's own file, re-run through the signal, reports the T282/T845
      commits instead of zero. *(Verified 2026-11-10 by loading the stale

      among them. T845's commit does not name T845 in its subject, so it
      cannot be picked out by id; the count is no longer zero, which is the
      defect.)*
