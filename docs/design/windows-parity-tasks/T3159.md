# T3159 - The session agent and holder burn ~23 s of CPU relaying a 64 MB flood (daemon ~14 s, holder ~9.4 s) - about as much as the app spends rendering it; profile where it goes

## Summary

Measured in T3017 with perf-baseline.ps1 -Build Release -Phase busy -BusyPersistence (64 MB ascii, release build, 2 runs each side): the agent family spends 22.6-23.8 s of CPU over a ~33 s flood whether or not the DebugAllocator and the extra per-chunk copies are there, so allocation is not the cost. Candidates: the emulator parse under the store lock (T3019), ring append, the holder's ConPTY read + pipe relay, the writer's merge/wire copies, per-chunk syscalls. Take a sampled profile (ETW/xperf or wpr CPU sampling, or cdb with symbols) of both the daemon and the holder over the busy phase, name the top stacks, and file the fixes. Agent code is shared: the Mac half owes the same measurement.

## In plain terms

With session persistence on, a pane's output passes through two background
helper processes before it reaches the window. When a program prints a lot
of output, those helpers used about as much CPU as drawing the output did. We
did not know why. This task finds out where that CPU goes and files the
fixes. No user-visible change lands here. The fixes are separate tasks.

## Findings (2026-11-18)

Profile: `perf-baseline.ps1 -Build Release -Phase busy -BusyPersistence -SampleAgent`,
64 MB of ASCII, ReleaseFast with symbols at 7eba59edd, on-CPU mode, ~8,000
samples per process. Raw output: `temp\t3159-prof2.{json,txt,folded}` (not
committed). Agent family CPU over the span was 15.3 s. The sampler perturbs
the run, so this is lower than the unsampled 20.6 s from the same build, which
matches T3017's 22.6-23.8 s.

**The agent's own code is ~3% of it.** VT parse (`feed`, `print`), ring
append, `snapshotRingsWith` and the allocator together are under 0.3 s.
Allocation and parsing are not the cost, which agrees with T3017's A/B.

**The rest is per-message kernel cost.** `agent_feed` counts 23,817 slices/s
at 2,639 KB/s, so ~113 bytes per message: one ConPTY line, carried as its own
message through every hop.

| process | stack (leaf last) | CPU |
|---|---|---|
| holder 7.2 s | ConPTY `ReadFile` → `NtReadFile` | 3.54 s (49%) |
| | `serverWrite` → `WriteFile` (to the daemon) | 1.49 s (21%) |
| | reader→writer condvar handoff (`SleepConditionVariableSRW`) | 1.47 s (20%) |
| | `serverWrite` → `CreateEventExW` + `NtClose` (event per op) | 0.59 s (8%) |
| daemon 8.1 s | `serverRead` → `GetOverlappedResult` → `NtWaitForSingleObject` | 3.57 s (44%) |
| | bridge writer's condvar wait/wake | 3.53 s (44%) |
| | `serverWrite` → `WriteFile` (to the app) | 0.24 s (3%) |
| | `CreateEventExW` + `NtClose` (event per op, both directions) | 0.25 s (3%) |
| | `onChildOutput` → `feed` / `bridgeData` / `enqueueOwned` | ~0.2 s |

A thread found on-CPU inside a wait stub is paying the kernel's block and
wake path once per message. At ~24k messages/s per hop, that is ~4.6 us each.

**Fixes filed:**
- **T3236 (P1)**: coalesce at the holder's ConPTY read so every hop carries
  fewer, bigger messages. `pty_host.zig:182` records T1464 rejecting a
  coalescing wait. That decision was about THROUGHPUT, which the ConPTY read
  rate bounds. This is a CPU fix, judged on `agent_cpu_s` with the busy wall
  and echo latency held.
- **T3026 (P2, existing audit card PA-I12)**: one cached event per stream
  per direction instead of a CreateEvent/CloseHandle pair per op. Measured
  ~0.85 s per flood (note added). T3237 was filed for this, found to be a
  duplicate, and closed.
- **T3238 (seat mac)**: the Mac agent's half of this measurement.

**Method note.** The first profile used cycles mode. It charges each thread's
cycles to wherever the thread is parked when sampled, and read 85% as
"waiting". That is the bias the on-CPU mode exists to remove. Both runs
named the same hot stacks, but only the on-CPU shares are unbiased.
