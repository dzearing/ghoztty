# T2770 - Drag motion survives a UI-thread stall: a composition thread follows GetCursorPos at the compositor clock and writes the dragged visuals' offsets/clips on the window's DirectComposition device, measured with the UI-stall seam (drag lag p95 and advance, both ways)

## Summary

Stall-proof half of T2556. After T2769 the compositor write is cheap but still runs on the window thread, so a UI-thread stall (the seam bell-fade-onscreen used in T2552) freezes the dragged edge. While a drag is live, a composition thread waits on the compositor clock (`DCompositionWaitForCompositorClock`, with a DwmFlush fallback), reads `GetCursorPos`, maps it through the drag snapshot `split_resize.ratioAt`/`replay` already use (pure, so it can run off-thread over a copied snapshot), and writes the dragged visuals' offsets/clips + commits under a lock shared with the window thread's own device use. The window thread still owns capture, the HWND moves and the resizes, and reconciles the visual to its own layout when it catches up. Measure drag lag p95 (cursor sample -> committed frame) and whether the edge advances during a 50 ms and a 500 ms stall, with the composition thread on and off.

## Validation criteria

- [ ] under a 500 ms UI stall the dragged edge keeps advancing every display frame with the thread on, and freezes with it off (negative control)
- [ ] drag lag p95 recorded both ways, no worse with the thread on than T2769's window-thread path when there is no stall
- [ ] no device-use race: the device lock is held for every cross-thread DComp call (a debug assertion, plus a stress run of drag + glide together)
- [ ] the thread exists only for the life of a drag and exits on button-up, capture loss and window close
