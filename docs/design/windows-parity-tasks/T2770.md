# T2770 - Drag motion survives a UI-thread stall: a composition thread follows GetCursorPos at the compositor clock and writes the dragged visuals' offsets/clips on the window's DirectComposition device, measured with the UI-stall seam (drag lag p95 and advance, both ways)

## Summary

Stall-proof half of T2556. After T2769 the compositor write is cheap but still runs on the window thread, so a UI-thread stall (the seam bell-fade-onscreen used in T2552) freezes the dragged edge. While a drag is live, a composition thread waits on the compositor clock (`DCompositionWaitForCompositorClock`, with a DwmFlush fallback), reads `GetCursorPos`, maps it through the drag snapshot `split_resize.ratioAt`/`replay` already use (pure, so it can run off-thread over a copied snapshot), and writes the dragged visuals' offsets/clips + commits under a lock shared with the window thread's own device use. The window thread still owns capture, the HWND moves and the resizes, and reconciles the visual to its own layout when it catches up. Measure drag lag p95 (cursor sample -> committed frame) and whether the edge advances during a 50 ms and a 500 ms stall, with the composition thread on and off.

## In plain terms

When you drag the line between two panes, the panes should follow your mouse
every frame. Until now, if the app got busy for a moment in the middle of the
drag, the edge stopped under your hand and then jumped. Now a separate helper
keeps moving the edge with the mouse while the app catches up.

## Goals

- [x] a composition thread follows the cursor on the compositor clock during a divider drag
- [x] the window thread publishes a model of the drag at every move; the thread extrapolates the dragged gutter from it
- [x] a device lock so neither thread commits half of the other's frame
- [x] an acceptance script that stalls the UI thread mid-drag and counts the frames the edge still moved

## Design (decided this turn)

- **Extrapolate, do not re-run the layout.** A divider drag is a row drag
  (folds, sidebar tucks, focus moves), none of it pure, so the thread cannot
  run `ratioAt`/`replay` + the grid off-thread as the summary imagined. Instead
  every move the window thread lays out publishes each visible pane's pose and
  which of its edges sit on the dragged gutter (`comp_drag.classify` against
  `grid.dividerGutter`); the thread moves those edges one for one with the
  cursor, clamped at the pane minimum (`travelLimits`). Past a minimum (a
  give-way, a fold) the window thread's own pass reconciles when it catches up.
- **The lock is narrow.** The window thread holds it across the preplace
  writes + commit and around each `syncTreeVisual` place, never across the
  whole layout pass - the first cut did, and the thread then waited out the
  pass's frame wait (lag p95 4.5 ms -> 0.7-4.4 ms after). A window-thread place
  invalidates the thread's last write so its next tick re-asserts its pose.
- **References.** The thread AddRefs the device, every pane visual, rounded
  clip and riding shadow it may write, so a pane closed or a host rebuilt
  mid-drag never frees what it writes; shadows it moved get their cached
  offset forgotten at stop.
- Knob `GHOZTTY_COMP_DRAG_THREAD=0` = window thread alone. Debug seams:
  `GHOZTTY_DEBUG_DRAG_STALL_MS` (6th move), `GHOZTTY_DEBUG_DRAG_CURSOR_FILE`
  (the test desktop has no cursor).

## Validation criteria

- [x] under a 500 ms UI stall the dragged edge keeps advancing every display frame with the thread on, and freezes with it off (negative control) - drag-stall.ps1 -StallMs 500: 56/56 frames in the stall wrote; off arm: no thread; still-pointer arm 0/61
- [ ] drag lag p95 recorded both ways, no worse with the thread on than T2769's window-thread path when there is no stall - RECORDED, NOT MET: thread 0.7-4.4 ms p95 (debug) vs 0.15 ms window write; T2814
- [ ] no device-use race: the device lock is held for every cross-thread DComp call (a debug assertion, plus a stress run of drag + glide together) - assertion in publish/invalidate, every pane place takes the lock; the stress run is T2816
- [x] a transient Commit refusal (a chrome surface mid-draw on the window thread) does not kill the thread - drag-stall.ps1 4/4 green with commit_retries 0-2 per run; before the fix 2 of 3 runs died at the first commit (stall skips dead=62)
- [x] the thread exists only for the life of a drag and exits on button-up, capture loss and window close - one start and one line per drag in every arm (button-up); capture loss and close route through endDividerDrag/deinit (code), their arms are T2816
