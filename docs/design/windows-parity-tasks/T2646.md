# T2646 - stack-fold-slide.ps1 F13 read a black fold face (000000) when run four-wide beside other scripts; green alone

## Summary

stack-fold-slide F13 photographs the fold's strip face (an UpdateLayeredWindow popup) with PrintWindow, and the system intermittently hands back its own untouched black bitmap. T2752/T2836 (b6f5c01058) added up to 5 retakes, but the 2026-11-15 four-wide sweep (20261115-142444) still exhausted all 5 and scored 000000; on 2026-11-27 a black photo turned up even running alone. The black is a measurement gap, not a defect: the photo is a copy of the bytes the app handed UpdateLayeredWindow.

Fix (2026-11-27): the debug build now logs `strip face pixels top=RRGGBB permille=N` after every popup commit (`strip_face.topColor`, a 32x32 grid over the committed frame, card cut included; `Window.zig` beside the commit). When F13's photo is still blind after the retakes (or none landed), it scores the mid-fold commit's line instead of failing: its commonest colour must be a logged band, covering 60%+. A face that draws nothing reads 000000 there and still fails (unit test). `-BlindFacePhoto` forces the fallback so it can be exercised. T2501 (the underlying PrintWindow-vs-ULW question, P1, blocked on T2485) is unchanged; this closes only the flake.

## In plain terms

One of the fold-animation tests takes a snapshot of the folding card, and Windows sometimes hands back a blank black picture instead, which made the test fail for no real reason. Now, when the snapshot comes back blank, the test checks the picture the app actually drew instead, so it only fails when the card really is wrong. Nobody using the terminal sees a difference.

- [x] F13 falls back to that report when the screenshot comes back blank
- [x] the fallback is shown to pass on a real fold and to read black for a face that drew nothing
