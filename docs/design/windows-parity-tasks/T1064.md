# T1064 - A commit message file written with a BOM puts a stray character at the front of the activity feed headline

## Summary

`scripts\git-commit-guard.ps1 commit -MessageFile <path>` passes the file
straight to `git commit -F`, and git does not strip a UTF-8 BOM. PowerShell
5.1's `Set-Content -Encoding utf8` writes one by default, so a message file
made that way produces a commit whose subject begins with U+FEFF. Observed on
commit `6d555b3e3` (2026-08-21): `gh run list` renders it as
`﻿chore(tracker): close T1052`.

## In plain terms

One invisible character sneaks onto the front of a commit's headline and stays
there forever - in the history, in the dashboard's activity feed, and in every
tool that lists the commit. Nothing warns about it, and the most obvious way to
write the message file on Windows is the way that causes it.

## Details

The guard already reads the commit back and fails on paths that were not asked
for; a BOM in the subject is the same class of "the commit is not what you
meant" and the same place can catch it. Options: strip a leading U+FEFF from
the message file before `-F` (silent and always right), or refuse with the
remedy named (louder, teaches the caller). Stripping is probably right - there
is no case where a caller wants a BOM in a subject line.

Related trap already recorded for scripts: PS 5.1 writes UTF-8 with a BOM from
`Set-Content -Encoding utf8` and `Out-File`, which is also why acceptance
scripts are held to ASCII.
