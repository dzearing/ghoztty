# T2239 - One overlay popup move costs about 770us of UI-thread time during a splitter drag; find out what the move is doing

## Summary

T1350 clocked the chrome moves that are left after T1345: at 8 panes, 4 SetWindowPos calls on layered popups (2 scrollbars, 2 dim washes) cost 3092us of a 41582us mouse move - about 770us each, which is far more than a plain window move should cost. Collapsing popups could save at most 2 of those 4; making each move cheap would save most of all 4. Measured while a GPU-heavy game was running on the box, so re-measure on an idle box first, then find what the move synchronously triggers (WM_WINDOWPOSCHANGED handlers, a DWM sync, a repaint) with drag-perf.ps1's mean_chrome_move_us as the oracle.

**What the re-measure found (2026-11-25, idle box).** The 770us popup moves
T1350 clocked are no longer what a drag pays:

- With the default config a divider drag moves **no** popups at all. Glass
  panes are the default and never dim (T2281), and an empty pane shows no
  scrollbar, so drag-perf's chrome and overlay numbers were reading the empty case.
- With glass off, the unfocused-pane washes ride the pane's **composition
  visual** in both pane styles (log: `dim overlay path visual=true`), not
  the popup. Yet on the default elevated cards the overlay term was
  **7.0-8.1 ms per mouse move at 8 panes** (flat cards: 0.06 ms), which is
  about 1 ms per dimmed pane. The cause: `DimOverlay.matchOwnerRegion`
  re-cut the hidden popup's window region (`GetWindowRgn` plus a redrawing
  `SetWindowRgn`) whenever the card's rounded region changed, and an elevated
  card's region changes on every resize.
- The real popup moves that remain are on folded strips: a 28-pane run moved
  6 scrollbars + 6 strip faces per mouse move at about 1.6 ms each. That is
  T3727's question now.

**The fix.** While the wash is a visual, a region change is *owed*, not
paid. The popup path pays an owed cut once, when it next shows the popup
(`dim_math.regionStep` / `popupRegionDue`). After it the overlay term is
0.21-0.31 ms at 8 panes in every drag shape, and the batched mouse move went
from 22.4 ms to 14.9-16.4 ms.

## In plain terms

Dragging the line between panes got slower with every dimmed pane: on
rounded cards each faded-out pane cost about a millisecond per mouse move,
spent re-cutting the outline of a window that was not even on screen. That
work is now skipped until it is needed, so a drag over 8 panes spends about
a quarter of a millisecond on the fading instead of seven or eight.
