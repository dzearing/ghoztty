# T1596 - The --relay url refusal tells the user the wrong rule: http:// and ws:// are accepted but the message says they are not

## In plain terms

If you start the agent with a relay address it cannot use, it tells you the
address must begin with `https://` or `wss://`. That is not the rule it
actually enforces: plain `http://` and `ws://` are accepted too (for a
loopback test relay). Somebody who typed a loopback address and hit an
unrelated problem would read this line and go fix the one thing that was
already fine.

## Summary

`wssBase` in `src/remote/agent/main.zig` maps four prefixes - `https://`
and `wss://` to `wss`, `http://` and `ws://` to plaintext `ws` - and
refuses anything else (a bare host, a typo, a `file://`). The refusal message
names only two of the four it accepts. The parenthetical does say http/ws are
"loopback-test only", but the leading clause states a rule the code does not
hold, and the leading clause is what gets read.

Surfaced by T776, which moved this print out of `wssBase` to its two CLI call
sites so a passing unit test would stop planting it in every agent-lane log.
The wording was left exactly as it was in that change, deliberately: it is a
user-facing string and changing it is its own decision, not a side effect of a
test-output cleanup.

## Validation criteria

- [ ] The message states what is actually accepted, and what a bare host or an
      unknown scheme should look like instead.
- [ ] A unit test asserts the refusal message against the four accepted
      prefixes, so the text and the rule cannot drift apart again.
