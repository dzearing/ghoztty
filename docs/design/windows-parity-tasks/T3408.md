# T3408 - agent-pipe.ps1 section 3: +sessions lists a session the scratch client still holds as detached (attached=false)

## Summary

Seen in lane l's due sweep 2026-11-22 (HEAD a9a6632cf) and reproduced by hand: remote-test-client --pipe --hold=12 OPENs a session and holds it, yet +sessions --json shows attached=false and unattached_since set while the client is connected. The stamp last passed at f81eb427a. T3337 touched no Windows agent or client code; bisect the src/remote and test-client changes since then.

## In plain terms

A test tool that opens a terminal session and holds onto it was being reported
as "not attached" by `ghoztty +sessions`, so the session-listing test failed.
The listing was right: the tool's own connection was quietly letting go of the
session a few milliseconds after opening it. Now the tool opens sessions the
same way the app does, and a held session lists as attached.

## Root cause

Not the agent and not `+sessions`. `remote-test-client` sent OPEN as a raw
control frame and caught OPENED in its own control handler. Since T3254
(41d1705af) `Connection.deliverRpcReply` treats an OPENED that no RPC slot
claims as a stray and answers it with a DETACH (`strayNeedsDetachLocked`), so
every session the tool opened was unbound ~6 ms later (`unattached_since` ==
`created_at` + 6 ms in a hand repro). The fix routes `Session.openFull`
through `Connection.openChannel`, which tags the OPEN with a `req_id` and parks
the slot its reply lands in; `deinit`/`dropLocal` become
`closeChannel`/`detachChannel` on the pane. The app was never affected: every
app OPEN already goes through `openChannel`.
