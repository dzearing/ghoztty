# T1287 - A capture guard that is supposed to refuse a window painting nothing hands back a black picture instead

## Summary

The synchronous window capture prefills its bitmap with a sentinel colour and is documented to FAIL when the window leaves it untouched. Found while fixing T1283: a window purpose-built to answer WM_PRINTCLIENT with nothing (own class, null background brush, DefWindowProcW) captured as solid BLACK, not sentinel, so the guard never fired. Either something wipes the prefill before the window is asked to draw, or the sentinel is being overwritten by PrintWindow itself. Until this is settled, the guard's promise is unproven and the uniform heuristic cannot be handed off to it.

## In plain terms

The test suite's screenshot helper promised to refuse a picture of a window
that drew nothing. That refusal could never happen. The same dead promise sat in
the app's own hover-screenshot code. Both are gone now, and the check that
actually catches a blank window is demonstrated against a real blank window.

## Goals

- [x] say which of the two hypotheses is true, from a measurement
- [x] remove the guard that cannot fire, in the test library AND the app's hover capture
- [x] demonstrate what DOES catch a blank synchronous capture

## Root cause: PrintWindow itself overwrites the sentinel

It was the second hypothesis, and only half of it. `PrintWindow(hwnd, dc, 0)`
never sends `WM_PRINT` or `WM_PRINTCLIENT`. It re-runs the window's
`WM_PAINT` into a surface PrintWindow owns, then copies that whole surface
over the caller's DC. Whatever the caller pre-filled is gone, and whatever the
window did not paint comes back as PrintWindow's own blank: black for a popup,
and white in the client of a captioned overlapped window.

Measured with a scratch probe on a private background desktop. The probe used
four WndProcs (DefWindowProc, a `WM_PRINTCLIENT` that paints nothing, a
`WM_PAINT`-only red fill, and a `WM_PRINTCLIENT`-only green fill) across
visible popup, layered popup, child and overlapped windows. In every case the
magenta prefill read `0xff00ff` before the call and was gone after it. The
message log showed `PAINT ERASE` inside the call and never `WM_PRINT` or
`WM_PRINTCLIENT`. The red fill captured red, and the green fill never
appeared. So the sentinel branch in `CaptureWindowSync` (TestDesktop.ps1) and
`error.DrewNothing` in `ipc_hover.zig` could never fire.

The fix removes both branches and corrects the comments that described a
`WM_PRINTCLIENT` path, in TestDesktop.ps1, ipc_hover.zig and docs/claude/testing.md.
It also removes `hover_capture.fillSentinel/allSentinel` and their two unit tests.
The capture is still synchronous, because the repaint runs inside the call, so
T835's reason for `-Sync` stands. A blank capture is caught by the UNIFORM guard,
which confirms that T1283 was right not to exempt `-Sync` from it.

Follow-up filed: **T2216**. `printclient-audit.ps1` enforces `WM_PRINTCLIENT`
arms that this capture never calls, and `dark-menus.ps1` takes the torn capture
on the same false premise.
