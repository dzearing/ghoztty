# T2772 - Every closed window leaks ~110 threads and ~52 MB (private and GPU): window-close-memory A1/A2/A4/A5/A8 red on clean HEAD 910a71f05, green at b485cb0f8 (2026-11-03) - bisect the close path (suspects 087055a50 composition present default, 2a09f262c glass workers)

## Summary

Found by T2600's due sweep (2026-11-06). `window-close-memory.ps1` per closed
window left behind, on a clean Debug build of HEAD `910a71f05` (scratch worktree,
no T2600 change; log `%TEMP%\ghoztty-acceptance-parallel\20261106-180729`):

| | left per closed window | budget |
|---|---|---|
| A1 private | 51.91 MB | 1 MB |
| A2 handles | 448.1 (Semaphore/Timer/Thread +~1100 over 10 cycles, Event +922) | 5 |
| A4 USER | 6.1 | 1 |
| A5 threads | 109.6 | 0.5 |
| A8 GPU | 52.10 MB | 1 MB |

One open window costs ~111 threads, so essentially NONE of a closed window's
threads are joined: the renderer/IO/pane threads (and their swap chains) are
outliving the window. Descendant processes do exit (A6/A7 pass), so the ptys
close; it is the in-process side. The guard was stamped green at `b485cb0f8`
(T2644, 2026-11-03); T2611's filed regression was 1.02 MB, a different size
entirely. The same numbers reproduce with T2600's change on top.

**Window narrowed to one product commit.** T2611's log has the T2541 turn's
sweep (tree `6061ea336`, 2026-11-06 13:30) at 1.59 MB per closed window. The only
`src/` commits between that and `910a71f05` are `087055a50` (terminal panes
present through the composition swap chain BY DEFAULT, T2514), `0bfbf951a`
(viewer nav bar back buffer, T2550) and `24c267593` (a test). So the prime
suspect is the composition present path not releasing a pane's swap chain /
presenter thread when its window closes. First check: run the harness on
`910a71f05` with the composition present forced off (its env/constant, see
T2514) - if the numbers drop to ~1.6 MB that is the confirmation; otherwise build
`087055a50^` in a scratch worktree (`git worktree add --detach`) and run
`acceptance-parallel.ps1 run -Scripts window-close-memory.ps1 -NoRebuild` from it.

## In plain terms

Closing a Ghoztty window no longer gives its memory back: each one keeps about
50 MB and a hundred background threads alive until the app quits. Someone who
opens and closes windows all day sees the app grow without limit.
