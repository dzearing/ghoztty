# T3710 - The session agent serves a per-session IPC proxy endpoint and points the child's GHOZTTY_IPC_SOCKET at it (app_ipc, Windows + shared)

## Summary

Second slice of T2217 (docs/design/remote-viewer-tunnel.md decision 2). T2217 landed the wire (capability.app_ipc, APP_REQUEST 0x80 / APP_RESPONSE 0x81, AppRequest/AppResponse in src/remote/protocol.zig) and the shared policy (src/apprt/ipc/remote_origin.zig); nothing advertises app_ipc yet. Build in the agent: when a connection negotiates app_ipc, host one owner-only endpoint per session on the agent's machine (Windows: named pipe with the agent pipe's owner-only DACL, win_acl.zig; POSIX: AF_UNIX 0600), rewrite the child's GHOZTTY_IPC_SOCKET in OPEN.env to it (replacing the app's baked local value), read the length-prefixed IPC request the CLI writes (same framing as os/ipc_client.zig, max_app_ipc_bytes), send APP_REQUEST{session_id, req_id, request} to the viewer bound to that session, park on APP_RESPONSE by req_id, and write the reply back. No viewer bound, or no answer within the CLI's timeout policy: an IPC error reply with a sentence, never a hang. Against an older app (no app_ipc) host nothing and leave the env alone. Advertise capability.app_ipc from the agent only when this is done. Also fix the stale comment near src/remote/agent/pty_child.zig:1449 (quoted as :1283 in T2217) about remote panes' IPC. Unit tests in the agent lane for the env rewrite and the proxy's timeout/unbound replies.
