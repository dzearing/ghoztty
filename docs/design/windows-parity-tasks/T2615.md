# T2615 - T2610 step 3c: pane renderers hand frames to the window presenter (slot textures in the presenter's share group, fence + SlotPair publish, no SwapBuffers; pane HWNDs lose their pixel format and contexts go current on a hidden helper window)

## Summary

Builds on 3a/3b. OpenGL.present gets a third answer from the compBegin seam: blit the target into the acquired slot texture via a renderer-owned FBO; drawFrameEnd fences, flushes and SlotPair.publish()es instead of swapping, deleting the replaced fence; back-pressure via acquire()==null waits on the presenter's signal. Planted lab frames (T2383) clear the slot. Surface.zig: no setupPixelFormat for terminal panes on this path; context created with gl_robust.createSharedContext on a hidden WS_POPUP helper owned by the surface. Pane pool (T2597) and pane_layer (T2499) forced off on this path.

## In plain terms

Each Ghoztty window is moving to one shared "screen painter" instead of every
pane painting its own little window, because the per-pane painting leaks video
memory every time a window is hidden or minimized. Until now the shared
painter only drew each pane's background color. With this change, behind an
opt-in switch, the terminal text itself goes through it: every pane draws its
frame off screen and hands it over, and the window paints all of them at once.
Nobody notices yet unless they turn the switch on; the switch becomes the
default in a later step.

## Goals

- [x] A pane on the presenter path draws into a slot texture and publishes it instead of swapping
- [x] The presenter blits every visible pane's newest frame and swaps once
- [x] Pane windows on that path have no pixel format; contexts are current on a hidden helper
- [x] Closed panes on that path are never parked for reuse
- [x] The acceptance proves a renderer-drawn frame reaches the presenter's back buffer

## What landed

- `src/apprt/win32/WindowPresenter.zig`: `PaneLink` (per pane: SlotPair, two
  slot texture names, release fences, a signal), `link`/`unlink`/`freeLink`,
  `createHelper` (hidden `WS_POPUP`), `createSharedContext` with the share
  handshake, and a compose that takes each pane's frame, `glWaitSync`s a fresh
  one, blits it per `planPane`, swaps, then fences each slot it let go of and
  wakes that pane's renderer. Debug-only `GHOZTTY_PRESENTER_PROBE=1` reads
  back each pane's center pixel; the debug self-check also counts pane windows
  that carry a pixel format.
- **The surprise**: `wglCreateContextAttribsARB` refused to share with the
  presenter's context for every pane (`shared context failed` in both arms),
  because that context is current on the presenter thread for life. The T2599
  spike never hit it: its presenter context was current only while it
  presented. Fix: the presenter thread releases its context for the moment a
  pane's context is created (`share_req` / `share_paused` / `share_done`,
  bounded both ways). The same applies to a lost-device rebuild, noted on T2616.
- `src/renderer/OpenGL.zig`: `presToSlot` (acquire with back-pressure, wait
  and delete the slot's release fence, grow-only slot texture, blit or the
  planted magenta clear), `presPublish` at the swap site (fence, flush,
  publish, delete the replaced fence, notify), `presRetire` in `threadExit`.
  `presentLastTarget` is a no-op once the presenter holds a frame. The size
  queries (`surfaceSize`, `frameOutlivedItsWindow`) read the pane window, not
  the DC's window, since the DC is now the helper's.
- `src/apprt/win32/Surface.zig`: `initPresenterContext` / `dropPresenterContext`;
  no pixel format on the pane window on this path; `parkWindow` refuses when
  the window has a presenter. Any failure falls back to the per-pane present.
- `src/renderer/gl_window_presenter.zig`: `SlotPair.Take.released`, the slot a
  fresh take stopped holding (unit-tested).
