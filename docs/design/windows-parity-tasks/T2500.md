# T2500 - A closed window still leaves ~0.7 MB of private memory and ~4 kernel handles behind (1.1 MB with a viewer pane), linear per window, after T2498 freed its desk

## In plain terms

Closing a window still keeps a little under a megabyte of memory and a few system handles, every time. One window is nothing, but a session that opens and closes hundreds of windows keeps growing until Ghoztty is restarted.

## Summary

Measured by `test\win32\window-close-memory.ps1` on HEAD 18ca34685 + the T2498 fix (desk, pane stacks, fonts and chrome freed on the user-close path; GDI is now 0.0 a window):

- `-Shape full` (two terminals + a markdown viewer), 10 cycles: **+1.12 MB private and +3.9 kernel handles per closed window**, linear (baseline 298.3 MB / 468 handles, after 5: 304.5 / 486, end 309.5 / 507). A1 (<= 1 MB) is red on this alone. An earlier T2473 run measured 1.07 MB.
- `-Shape split -CloseSplitFirst`, 8 cycles, three runs: 0.66 / 0.74 / 0.77 MB and 3.6-3.9 handles a window. So about 0.7 MB and 4 handles are not the viewer; the viewer adds ~0.4 MB.
- GDI, USER, threads and child processes are flat. GPU is T2499, a separate defect.

Next: find what the 4 handles are (handle type census before/after with `handle.exe -s -p` or NtQuerySystemInformation by type, from the harness), then the private bytes. Candidates to rule out first: per-window events/timers/waitable handles in `Window.init` that `onDestroy` never closes (it is the same drift T2498 fixed for GDI), the WebView2 environment per viewer, and allocator slack (a plateau over 20+ cycles would say slack, a straight line says leak).

## Validation criteria

- [ ] `window-close-memory.ps1` (verdict shape, 10 cycles) A1 <= 1 MB and A2 handles well under budget, with growth flat across a 20-cycle `-Report` run
