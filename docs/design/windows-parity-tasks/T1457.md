# T1457 - The skill doc Windows ships tells an agent to press Cmd-F and talks about Ghoztty.app

## In plain terms

The instruction sheet an AI agent reads to learn how to drive this terminal is
the same file on both platforms, and it is written for a Mac. It tells the
agent that Cmd-F searches a viewer pane, that a remote window is the
Cmd-Shift-N menu action, and that the app it launches is `Ghoztty.app`. On
Windows those are Ctrl-F, Ctrl-Shift-N and `ghoztty.exe`, so an agent that
relays what the document says hands the user a keystroke that does nothing.

## Summary

T660 forked the shipped `ghoztty` skill document so it describes THIS branch's
CLI. It did not touch the other half of the same problem: the parts of that
document that are true only on macOS. Found while doing T660, in the copy that
`src/apprt/win32/assets/ghoztty/skills/ghoztty/SKILL.md` now carries verbatim:

- **`Cmd-F`** as the viewer pane's find key (line ~134).
- **`Cmd-Shift-N` "New Remote Window"** as the menu equivalent of
  `+new-remote-window` (line ~706).
- **`Cmd` / `Cmd-Shift` modifiers** on banner links (line ~830).
- **`AXWindowActivityState` and `requestUserAttention`** as what `+set-state`
  drives (line ~603) - macOS accessibility API names, meaningless here, and not
  what the win32 build does.
- **`Ghoztty.app`** as what `+new-window` auto-launches (line ~858).

The awkward part, and the reason this is not a find-and-replace: T660's rule is
that the Windows live copy stays **byte-identical to the Mac bundle resource**,
because two platforms handing an agent different instructions is the divergence
`CLAUDE.md` calls the defect (section A of `test\win32\hook-json.ps1` asserts
it). So the fix is almost certainly ONE document that marks platform-specific
text rather than two documents that drift - e.g. "Cmd-F (Ctrl-F on Windows)",
and an activity-state paragraph that names the observable behavior (title
suffix, taskbar attention) instead of one platform's API. Splitting the file
per platform would trade this defect for the drift T1325 exists to catch.

## Resolution (2026-11-10)

**Mostly already fixed, by T1327 (293a34142).** The shared asset stays a
byte-copy of the Mac file on purpose; the Windows app rewrites each Mac-only
phrase as it INSTALLS the skill (`src/apprt/win32/skill_rewrite.zig`), with
two tests as the gate: every rewrite row must still match the shared text, and
no phrase in `mac_only_phrases` may survive the rewrite. That covers Cmd-F,
Cmd-Shift-N, the Cmd banner-link modifiers, LaunchServices and `Ghoztty.app` -
every item this task listed but one.

**What was left, and landed here:** the `+set-state` sentence
(`AXWindowActivityState` / `requestUserAttention`) had no rewrite row and its
API names were not in `mac_only_phrases`, so the Windows install still shipped
it. Added the row (Windows text: the title suffix, which is all the win32
build does) and added `AXWindow` / `requestUserAttention` to the gate.

This turn first edited the shared doc in place (paired "macOS / Windows"
wording), which the none lane rejected because it broke T1327's rewrite
anchors. That approach was reverted: it contradicts T1327's
copy-not-fork design.
