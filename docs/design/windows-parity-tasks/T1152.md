# T1152 - The contents card's chrome pin is gated on a cursor sample, so no acceptance script can ever see the nav bar

## In plain terms

When a viewer pane is narrow, its table-of-contents card can only be opened from
a button in the little toolbar at the top of the pane - so that toolbar is
supposed to stay put instead of sliding away the way it normally does. It does,
but only because the mouse pointer happens to exist. Nothing about "the card is
in its compact form" actually holds the toolbar open; the rule is buried inside
the code that samples where the pointer is, and that code gives up first on any
machine where the pointer cannot be read.

## Summary

`ViewerPane.navHoverTick` is a cursor sample. Its opening guards return early
when there is no pane, no bar, or no readable cursor:

```zig
if (w32.GetCursorPos_(&pt) == 0) return;
if (w32.ScreenToClient(h, &pt) == 0) return;
```

The compact-TOC pin - `const toc_pinned = self.toc_mode == .compact or
self.feedback_open;` followed by `setNavVisible(true)` - sits BELOW those
guards. It is a STATE rule (Mac's `updateChromePin` / `setChromeVisible(true)`
on entering compact), not a hover rule, and it should not need a cursor to hold.

Measured consequence: on the background test desktop `GetCursorPos` fails, so
the pin never runs. A compact viewer pane there shows its contents card with no
opener at all and `GhozttyViewerNav` sized 0x0. That is why
`viewer-narrow-pane.ps1` (T1130) can assert containment for the card but not for
the nav bar's button strip, whose narrow-width contract is covered only by the
pure-layout tests in `viewer_nav_layout.zig`.

The fix is to raise the pin out of the hover tick to wherever `toc_mode` and
`feedback_open` are SET, so entering compact shows the bar directly and the
hover tick is left doing only what it is named for.
