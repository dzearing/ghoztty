# T3572 - Linux L11j: closing a GTK pane, tab or window gives back everything it held - measured

## Summary

Port docs/reference/memory.md: closing a pane or window releases its renderer, swap-chain targets, cell buffers and any closure stored on window-owned state (the teardown invariants), and a pane that is not drawing (hidden, stashed, minimized strip, background window) gives back its frames. Measure on GTK with a scripted open/close scenario (RSS plus GL memory where Mesa reports it) like the 2026-10 Mac audit and the win32 pane-close-memory.ps1 harness, and fix the leaks found. Builds on the background-window card (what counts as not drawing).

**Split 2026-11-24.** This card is the teardown half, measured. The other
half - a pane that is not drawing gives back its frames - is **T3645**: on
GTK the shared release never runs (`OpenGL.releaseHiddenTargetsNow` /
`releaseIdleTargetsNow` answer false off win32), and GTK's GL lives on the
main thread, so it is its own piece of work. The measurement also turned up
**T3646** (the agent's private memory climbs ~40-50 KB per closed session).

## In plain terms

On Linux, nobody had checked that closing a pane, a tab or a window really
hands back what it used - its threads, its shell, its open files and its
memory, the picture it drew included. A scripted test now opens and closes
each kind dozens of times and measures: everything comes back, with nothing
left over that grows with use.

## Goals

- [x] a repeatable open/close measurement for terminal splits, splits closed mid-start, tabs, windows and viewer panes
- [x] GL memory counted (the app runs on Mesa's software rasterizer there, so textures are the app's own memory)
- [x] a negative control that proves the meter can see a retained pane
- [x] fix what it finds - nothing in the app's teardown leaked; the agent's small per-session climb is filed (T3646)
- [x] the frames-of-a-hidden-pane half split to T3645

## Validation criteria

- [x] Closing a terminal split, a split closed at once (mid-start), a tab, a window, and a viewer pane leaves, per cycle after warm-up: private memory <= 1 MB, threads <= 0.5 (renderer + IO threads joined - on GTK the core surface is freed in the GObject's finalize, so a leaked reference would show here), fds <= 0.5, child processes <= 0.2 (shell under the agent, WebKit web processes under the app) and their memory <= 1 MB - `test/linux/pane-close-memory.sh` ALL PASS (32 checks), WSL headless Weston, 8 warm-up + 12 measured cycles each. Measured per closed pane: split 565 KB / 0 threads / 0 fds / 0 procs; rapid 63 KB; tab -152 KB; window 344 KB; viewer 12 KB (6 web processes opened, all gone). One open pane costs ~2.7-5.6 MB, 2 threads, 9 fds, 1 process.
- [x] GL memory is in the measurement: P0d asserts the app runs on llvmpipe with no d3d12 driver mapped (`LIBGL_ALWAYS_SOFTWARE=1`; the app logs `wslg: GPU driver left to the environment`).
- [x] Not a leak, a warm-up: 30 split cycles - the app's private memory climbs ~15 MB over the first ten and then sits within noise (the last eight moved +0.3 MB), where a retained pane would add ~6.5 MB every cycle; hence 8 warm-up cycles.
- [x] Negative control: `NEGATIVE=1` (every measured pane left open) fails all 15 budget checks of split, window and viewer (split: 40 MB, 2 threads, 9 fds, 1 process left per cycle).
- [x] Hidden panes giving back their frames: NOT done here - split to T3645 (code-verified: `releaseHiddenTargetsNow` and `releaseIdleTargetsNow` in `src/renderer/OpenGL.zig` return false unless the runtime is win32).
- [x] No product code changed, so no floor lane is owed; the harness runs only in WSL through `scripts\linux\wsl-run.ps1`.
