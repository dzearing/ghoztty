# T1410 - A +reload aimed at a pane id that no longer names any pane reported success

## In plain terms

After a restart, a pane that came back with a NEW id still answered to its OLD
one, so a script pointing at a pane that no longer existed was told its command
worked. Now an old id that no pane carries any more is refused, the same way a
made-up id always was, and a pane's id is never saved as if it were a name
somebody gave it.

## Summary

Observed while proving T591's acceptance section M can fail. With the T591 fix reverted, the restored viewers came back under NEW pane ids, yet 'ghoztty +reload --target=<the pane id that pane had before the restart>' exited 0 - see the M3 line in the negative-control log. In the same script on the same build, '+reload --target=00000000-0000-4000-8000-000000000000' is correctly refused with exit 1 and 'target ... not found in registry' (section M4), so the refusal path itself works and something is resolving a DEAD id to a live pane. Suspects: IpcRegistry.prune not dropping an entry whose pane died with the app, a restore path registering a recorded id as a name, or the CLI not surfacing the server's failure. Consequence: a script cannot tell a reload that happened from one that found nothing, which is the exact failure mode T591 exists to prevent. Reproduce by reverting the 'viewer.adoptPaneId(open.pane_id)' line in Window.createViewerPane, rebuilding, and running test\win32\viewer-restore.ps1.

## Root cause

The second suspect. `+list` registers every UNNAMED pane under its own pane id
as a fallback name (`IpcHandlers.buildNode` / the `--pid` path), so the value
it prints is immediately a usable target. The session-layout capture
(`App.captureLeaf` / `captureViewerLeaf`) recorded `ipcNameOf(pane)` as the
leaf's `ipc_name` - which, for any pane `+list` had ever been run against, was
that fallback id. The restore (`restoreBuildSubtree`, and the in-place recovery
path) then re-registered the recorded string as a NAME on whatever pane came
back in that slot. When the pane kept its id that was harmless duplication;
when it took a fresh one (a viewer before T591, a terminal whose session went
to another pane under T1687) the dead id still resolved through the name table.

## Fix

`session_layout.paneNameToRecord(name, pane_id)` drops a name equal to the
pane's own id; `leafAdoptableName(leaf, local)` applies it on the restore side
on top of T1883's `adoptableName`. Used at both capture sites and both restore
registration sites, so manifests written before this fix are cleaned on read
too. The id needs no name to stay addressable: `IpcRegistry.lookup` falls back
to matching live pane ids.
