# T3664 - The Settings window takes several seconds to appear on Windows; it should open at once, as on the Mac

## Summary

User report 2026-11-24: "on windows, the settings pane takes quite a few seconds to pop open. should be opened rather instantly". Mac opens it at once.

SettingsWindow.open (src/apprt/win32/SettingsWindow.zig:321) does ALL of its work before the first ShowWindow: create() builds SettingsCatalog.defaults (the whole config schema), resolves the default file paths, opens ConfigFileStore, then reloadData(); open() then refresh()es every row before SW_SHOW. Nothing is on screen until the last of it finishes. Suspects to MEASURE first (do not guess): SettingsCatalog.defaults, reloadData (config parse / per-line validation on a scratch config?), ThemeCatalog.shared (hundreds of theme files read and parsed for the tile grid and live preview - does the first open load them eagerly even when the Appearance page is not showing?), the Sessions & Agent / Remote Machines live sections (T2686/T2687 say read without blocking - confirm they do), and the first layout/text measuring pass.

Target: the window is on screen within ~100 ms of Ctrl+, (first open, cold), and a re-open of an existing window is immediate. Approach: time each phase with the log (the 'settings: opened' line exists - add per-phase ms), then show the window first and defer or cache what is slow (theme catalog lazily on the Appearance page or on a worker, schema catalog cached across opens). Acceptance: a harness that opens Settings via the open_config action on the test desktop and asserts the window exists within a latency budget on first and second open, plus a log-timed phase breakdown recorded in this file.

## In plain terms

Opening Settings (Ctrl+, or the menu) used to leave you staring at nothing
for a second or more, because the window would not appear until it had read
every one of the ~500 colour themes it offers. Now the window appears at
once and the theme picker fills in a moment later, showing "Loading themes..."
until it does.

## Goals

- [x] measure where the open time goes, per phase, instead of guessing
- [x] the window is on screen before the theme catalog is read
- [x] the theme picker fills in by itself when the read lands, with a notice meanwhile
- [x] a harness that would catch the window waiting again

## Measurements (2026-11-24, this box)

Per-phase log line added to the open (`settings: opened ... open_ms create_ms
refresh_ms paint_ms`), debug build, test config: catalog of the schema 3 ms,
file/sources/effective reload 2 ms, setup 0 ms, refresh 26-30 ms of which the
theme catalog read was 25-29 ms, first paint 8-31 ms. Total ~70 ms - on the
dev drive (D:), the whole open is fast.

The user's installed build is different: its themes live under
`%LOCALAPPDATA%\Programs\Ghoztty\share\ghostty\themes` (502 files, replaced
by every update). A read-only pass over them took **1329 ms cold** and 23 ms
warm; the same pass over `zig-out\share\ghostty\themes` on the dev drive
took 17 ms. The window opens on Appearance, whose theme picker read that
whole catalog synchronously inside `refresh()` before the first
`ShowWindow`, so the first open after an update blocked for the cold read
(the user's own config is a one-liner; schema, sources, backups and the live
agent probe are all single-digit ms). Settings code is unchanged between the
user's 1.56.19 and HEAD, so the repo build carried the same wait.

## Fix

`SettingsWindow.open` starts the catalog read on a worker thread
(`startThemeLoad`/`themeWorker`) before the first layout; `themeCatalog()`
returns an empty stand-in while it runs, Appearance shows "Loading
themes..." instead of the "No themes were found" warning, and the worker's
`WM_APP_THEMES_LOADED` hands the catalog over (`finishThemes`, the join is
the hand-off) and refreshes. A theme pick or the light/dark mode switch waits
for the read first (`waitThemes`), as does every `settings` IPC op so tests
read the real catalog; window destruction joins an in-flight read. Debug seam
`GHOZTTY_SETTINGS_THEME_DELAY_MS` stretches the worker read to reproduce the
cold folder on a dev drive. The `settings` state carries `opened` {open_ms,
before_themes, themes_ms}.
