# T771 - The job-object probe asks membership, but what kills us is handle ownership - measure the question that predicts death

## In plain terms

Before Ghoztty shuts its background helper down, it writes a line in the log
saying whether doing so is safe. That line asked the wrong question and answered
it confidently — it said "safe" at the exact moment the terminal was being
destroyed. Nobody sees this line but the next person debugging a disappearance,
and it is the first thing they will trust.

## Summary

T268 proved the app is killed by the agent's kill-on-close job because the agent
**owns that job's last handle**. `job_object.probe` measures only whether the
agent is a **member** of our job — which it is not, and never will be, since a
process is not a member of a job it merely holds a handle to. So the diagnostic
printed `SHARED_JOB=no` while the app was being destroyed by exactly that job,
and the `no` read as an exoneration. The module's own doc comment says
"everything here degrades to unknown rather than to a guess"; the failure here is
subtler and worse than a guess — a correct answer to a question that does not
predict the outcome.

Handle holders are not enumerable without a driver (`NtQuerySystemInformation`'s
handle table is undocumented, unstable and not something a refresh path should
depend on). But the fatal relation has an answerable proxy, using code that is
already in this file: **does OUR job contain the agent's own children?** The
agent assigns every PTY child to its process-global job (`pty_child.zig`), so if
`ownJobContains(<a pid the agent parented>)` is true, our job IS the agent's job,
the agent owns its handle by construction, and killing it kills us.

## Where to start

- `src/apprt/win32/job_object.zig` — `Facts` gains a field for the new question;
  `describe` gains a term. Keep the tri-state discipline (`?` when unmeasurable)
  and keep both functions pure so they stay asserted.
- The pid to test against: the app knows the agent's pid and can enumerate its
  children cheaply (`CreateToolhelp32Snapshot`, parent pid match), or the agent
  can report one over IPC. Prefer the local enumeration — this runs on a path
  where the connection is about to be retired.
- `LocalAgent.terminateAgent` should then have a reason to **refuse**: killing a
  process that owns the job we are standing in is not a refresh, it is a
  suicide. Refusing loudly (and letting the caller pick another path) is better
  than the current silent death — though the real repair is T675, so scope the
  refusal as a backstop, not a fix.
