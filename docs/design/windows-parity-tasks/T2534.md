# T2534 - Chain-fold drag on the composition present (GHOZTTY_COMP_PRESENT=1) shows more black columns than the default path: run43/run45 black on 7 and 31 frames, including a 12 px black band trailing a moving pane edge for ~60 frames (run45 f224-f285); the default arm (run44/run46) had none

## Summary

Found by the T2485 D18 A/B on 2026-10-30 (release +71c6c2c25, ring trace, real pointer, normal window). D18 was expected to be fixed by composition present (T2514's default flip); the A/B says the opposite: the comp arm is worse. T2514 must not flip the default while this holds. Evidence: temp\t2485\run43..46 on lane A, blackcols.py and Invoke-ChainFoldOracle numbers in T2485's progress log. Close when two comp-arm chain-fold runs score zero black/novel/rim frames with tools\blackcols.py and the chainfold oracle.

## Re-verified 2026-10-31: the A/B predates the D18 fill

Both A/Bs (lane A run43-46, lane B run43-46) were recorded on release
+71c6c2c25, at 20:26 and 21:25 on 2026-10-30. The D18 fix, `29a4c9fee`
(`Surface.handleResize` -> `fillUncoveredStrips`, which paints background over
the part of a grown pane its last frame does not cover), landed after both:
committed at 22:46 the same night. That fill is gated on `own_layer` and a live pass. It is NOT gated on
the present path, so it runs for composition-present panes too. On the comp
path it paints the pane's GDI layer, which sits UNDER the swap-chain visual
(`gl_comp_present.zig`: the target is created topmost). The strip past the
swap chain's old size therefore shows that layer: background with the fix,
pure black without it. That is exactly the shape lane B described ("the grown
pane's new strip black on nearly every grow tick").

So the comp arm was never measured with the fill, and the defect may already
be fixed. **What is left is the measurement**: two comp-arm chain-fold runs on
a build at or after `29a4c9fee`, scored with `tools\blackcols.py` and the
chain-fold oracle. Code changes only if those runs are still red. If they
are, these are the comp-specific suspects to read first (none of them
measured yet):

- `Presenter.begin` calls `ResizeBuffers` before the frame is drawn, and a
  T2418-dropped frame (`end(false)`) never presents. So a resized swap chain
  can sit unpresented while `signalFrameDrawn` claims the new size, and the
  next tick's fill skips that span.
- The 12 px band in run45 f224-f285 stayed for about 60 frames, which is not a
  one-frame race. Check that it is inside a grown pane's rect and not the strip
  a moved pane vacates (D17 class), using the ring trace's
  `stack trace present` lines.
- Fallback from the task's first note: under comp, make `shouldFillBackground`
  fill on erase as well. The visual covers the layer, so the T1031 flash
  cannot happen.

## In plain terms

There is a newer way of drawing terminal panes that is about to become the
default. In a test, dragging a divider with it switched on made the edge of
the widening pane flash black. A fix for that same black edge landed shortly
after the test was run, and it covers the newer drawing path too. The test
has to be run again before anyone can say whether the flashing is gone.
