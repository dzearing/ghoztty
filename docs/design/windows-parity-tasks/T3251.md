# T3251 - Relaunch after a full quit shows "error starting IO thread: ConnectionClosed / Timeout" in panes; the local agent has also been stuck on a stale build for two days (self-replacement never completes)

## In plain terms

Ghoztty updated itself four times in two days, but the background process that
keeps your terminal sessions alive never picked up any of those updates - it
kept running a build from before all of them while the app said it was
"updating itself". After this fix, an update installed from inside the app is
adopted by that background process within about a minute, without closing any
session. The pane errors seen after a relaunch are tracked separately in T3252.

## Goals

- [x] Find why the session manager never replaces itself after an in-app update
- [x] Make it see the update and hand over to it, with no session lost
- [x] An acceptance test in the shape real updates produce, proven to fail on the old code
- [x] Split the relaunch IO-thread errors (T3252) and the app's endless "standing down" (T3253) into their own tasks

## Summary (as filed)

User report 2026-11-19 ~04:55: after closing Ghoztty completely and reopening it, panes show `error starting IO thread: error.ConnectionClosed` and `error.Timeout` instead of a shell/restored session.

Not reproduced from logs on this box: the installed app (pid 40096, 1.55.7) has run unbroken since the 22:33 auto-update, and no log under %LOCALAPPDATA%\ghoztty carries the IO-thread text - the message is rendered into the pane, not logged. FIRST STEP: make the IO-thread start failure log its error, the session id, and the agent pid/build it dialed, so the next occurrence is diagnosable.

Strong lead - the local agent never upgrades: the running agent is pid 39896, build 20261116-1d7b2e7ba, alive since 2026-11-17 08:24. Every launch since (1.55.4..1.55.7) logs `agent upgrade check: stale, but the agent is replacing itself without losing any session (standing down)` with handoff-capable=true and 3 live sessions - and it never actually replaces itself; the bundled agent is now 20261118-010fed901. So the app has been talking to a two-day-old agent across four releases, and the "replacing itself" branch has no completion check or timeout. A relaunch racing that never-finishing handoff (or a protocol skew the HELLO handshake does not cover) is the likeliest source of ConnectionClosed on attach and Timeout on open. See docs/claude/sessions.md (the app<->agent compatibility contract).

Acceptance: test/win32 script - (1) a stale agent with live sessions plus an app relaunch either completes the self-replacement within a bound or falls back (and logs which), never stands down indefinitely; (2) full quit + relaunch with live agent sessions attaches every pane with no IO-thread error; (3) relaunch while an agent handoff is in flight attaches or retries rather than surfacing ConnectionClosed/Timeout in the pane.
