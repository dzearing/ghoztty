# T2503 - Layered terminal panes (GHOZTTY_PANE_LAYER=1) fall behind a window-edge drag: resize-flicker.ps1 reads 12-15 stale frame waits of 11 vs 1-12 without the knob, 3-4 woken vs 5-7, and the panes' erase handler never runs on a window resize

## In plain terms

The fix for the graphics-memory leak (each pane drawing into its own surface) makes resizing the window by its edge measurably less smooth: more of the frames shown mid-drag are still drawn at the old size. Until that is fixed, the leak fix cannot be turned on for everyone.

## Goals

- [x] find why layered panes read worse in resize-flicker: the harness's simulated 8 ms present lag was really 12-27 ms (`Sleep` granularity), and timer phase decided the result
- [x] make the simulated lag exact (high-resolution waitable timer)
- [x] give layered panes an honest erase oracle

## Summary

Measured 2026-10-30 by T2502 (debug build at db2584174, same box, alternating knob/plain runs of `test\win32\resize-flicker.ps1`, off-desktop):

| run | knob=1 stale / woken | plain stale / woken |
|---|---|---|
| 1 | 15 / 3 | 8 / 7 |
| 2 | 13 / ? | 12 / ? |
| 3 | 14 / ? | 1 / ? |
| 4 | 13 / 3 | 11 / 5 |
| 5 | 12 / 4 | 3 / 7 |

(stale = drag frame waits that came back on a frame drawn at the OLD size, of 11 waits; woken = waits a presented frame actually woke). Means 13.4 vs 7.0. Plain HEAD is already red on the stale assertion (T2477), but the knob is consistently worse.

Second, deterministic difference (5 of 5 knob runs, 0 of 5 plain): `window resizes actually reached the erase handler (0 new decision(s))` fails - a WS_EX_LAYERED child pane gets no WM_ERASEBKGND on a top-level resize, so the `surface erase ...` decision log never fires and the "no pane blanks itself across window resizes" assertion is vacuous for layered panes.

On-screen look at 60 ms after a SetWindowPos resize showed no black or stale region (single sample, T2502 scratch photos), so the defect is frame-sync timing rather than a visible blank in a still - but it is the exact thing resize-flicker exists to hold.

Where to look: `src\apprt\win32\resize_paint.zig` (frame-drawn signal / wait), `Surface.zig` layered init (`Window.composeOpaqueLayer`), whether a layered child's present reaches the same `signalFrameDrawn` path, and whether the redirected layer surface needs the resize synchronised differently (DWM commits a layered child's new size on its own present).

## Validation criteria

- [x] resize-flicker.ps1 with GHOZTTY_PANE_LAYER=1: stale/woken counts no worse than plain over 5 alternating runs each. With the lag fix, 5 knob + 5 plain alternating runs all read drag `stale=0 woken=11` of 11 (before: knob 12-15 stale, plain 1-12)
- [x] the harness gains a layered-aware oracle: when every visible pane is an opaque layer (WS_EX_LAYERED read off the live window AND layered alpha 255), section C2 asserts that a window resize takes NO erase (nothing there can blank a pane); otherwise it still asserts the resize reached the handler. An RDW_INVALIDATE|RDW_ERASE|RDW_ERASENOW raised on a layered pane from the test process produced no erase either. Knob run: ALL PASS (27)
- [x] none + win32 lanes green: `floor-lane.ps1 -Lane all` ALL LANES PASS (lib, none, win32, agent); harness floor scoped sweep green after the unroll-count fix + baseline (33 -> 28)
- [ ] plain resize-flicker fully green: NOT met. The whole-window `woken` assertion is now a race (T2506, guard ack moved there)

- 2026-10-30 06:50: root cause (instrumented wake/start/swap/signal on one QPC clock, knob vs plain): render 1-4 ms and SwapBuffers ~20 us are IDENTICAL with and without the layer; the renderer starts 0.2 ms after the wake in both. Every signal lands on a ~15.6 ms grid (12 or 26-27 ms after the wake, both panes at the same instant): the harness's GHOZTTY_PRESENT_LAG_MS=8 used std.Thread.sleep, which Windows rounds up to the system timer tick, so the 8 ms lag was 12 or 27 ms by timer phase and the 16 ms budget failed on that phase. The layer's extra ~0.6 ms of pane placement (mean_place_us 1499 vs 882) shifts the phase, hence consistently 'worse'. Fix: Surface.presentLagSleep on a CREATE_WAITABLE_TIMER_HIGH_RESOLUTION timer. Same mechanism is a strong suspect for T2477 (plain red).
