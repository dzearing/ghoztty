# T1412 - a stale .git/index.lock wedges the loop's commit and nothing recovers it

## In plain terms

The loop shares one checkout with a second Claude window. When one of them
leaves a leftover git lock file behind, every later attempt to save work fails
with "another git process seems to be running" and stays failed — there is no
process to wait for and nothing clears it, so the turn just stops being able to
commit until somebody deletes the file by hand.

## Summary

On 2026-09-07 the T595 commit was refused with
`fatal: Unable to create 'D:/git/ghoztty/.git/index.lock': File exists`. The
lock was zero bytes, eighteen minutes old, nothing was staged, and
`git-commit-guard.ps1 status` reported `free` — a leftover from a git that died
around 23:56:57, not a commit in flight. The turn recovered by removing it by
hand.

`git-commit-guard.ps1` already owns the "two windows, one index" problem, but
only through its own advisory hold. It has no answer for git's NATIVE lock: it
runs `git add`, gets exit 128, and reports the failure verbatim. That is the
right default for a lock a live process holds and the wrong one for a stale
file, and the two are trivially distinguishable — an advisory hold that is free,
an empty index.lock older than the hold's ttl, and no git process with the repo
open.

## Details

Give the guard the same staleness rule it already applies to its own hold (a
hold older than its ttl is cleared rather than obeyed). Concretely, before the
`git add`: if `.git/index.lock` exists, the advisory hold is free, the file is
older than the ttl and empty, clear it and say loudly in the output that it did
— a silent removal is worse than the wedge. If any of those is false, fail with
today's message plus the age and holder so the report is actionable rather than
git's generic advice.

Whatever leaves the lock behind is worth one look while there — a killed
`git` in a script that does not trap, most likely — but the recovery is the
deliverable; the loop must not depend on nobody ever dying mid-`git add`.

## Goals

- [x] An ownerless stale lock is cleared, loudly (landed in 5da381781,
      2026-11-02, under a different turn that never named this card)
- [x] When the guard keeps a lock, its refusal says why: size, age, and the
      still-running git that may own it

## Validation criteria

- [x] A stale empty `.git/index.lock` with a free advisory hold is cleared by
      `git-commit-guard.ps1 commit`, which says so in its output, and the commit
      goes through — W17b (5da381781), W17e
- [x] A lock a LIVE holder owns is still refused, with the holder and the age
      named — W17d (a `git cat-file --batch` kept alive across an 11s-old lock;
      the refusal names its pid). The holder of a native index.lock is a git
      process, not the advisory hold: the guard's own hold is always held by the
      committing process at that point, so it is not what gets named.
- [x] A fresh lock (younger than the floor) is still refused — W17c, and W17c2
      asserts the refusal names its age and the floor
- [x] Section W of `test\win32\go-loop-guard.ps1` carries all three, negative
      controls included (W17e is W17d's negative control)

## Resolution

The recovery itself shipped in 5da381781 (`Clear-StaleIndexLock`): an empty
lock at least 10s old with no git.exe that started before it still alive is
removed and reported. The rule is the T1412 shape with one deliberate change:
the floor is 10s rather than the hold's ttl, because "a git that predates the
lock is still alive" is the real liveness test and the age only guards the
instant between a git creating the file and the process query seeing it.

What this card added is the other half of its Details: a kept lock no longer
passes git's bare "remove the file manually" advice through. `git add` and
`git commit` failures now print `index.lock: <bytes>, written <t> (<n>s ago) -
<why it was left alone>`, from the same `Get-IndexLockState` verdict the
clearer uses, so the report and the recovery cannot disagree.
