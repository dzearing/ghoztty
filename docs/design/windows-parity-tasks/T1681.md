# T1681 - isolation-meta does not check the third isolation knob: a sandbox LOCALAPPDATA root can be pinned

## In plain terms

Each automated test gets its own private copy of the terminal. Two of the three
switches that make that copy private are now checked automatically, so nobody
can quietly pin one back to a shared name. The third one — the folder the test
copy keeps its files in — is not checked, so it could be pinned without anyone
noticing.

## Summary

Filed 2026-09-20 from T903. `isolation-meta.ps1` section C asks "is this claim
unique to the RUN?" of `GHOZTTY_PIPE_SUFFIX` (C1, T352) and, since T903, of
`GHOZTTY_AGENT_INSTANCE` (C2). The third knob `Set-GhozttyTestIsolation
-ReleaseSandbox` turns is `LOCALAPPDATA`, and nothing judges it.

The tree is clean today — every sandbox root in `test\win32` is built with
`Join-Path $env:TEMP "...-$PID"` — so this is a guard gap rather than a live
defect, which is why it is P3. It is also a weaker class than the other two: a
leftover directory holds stale FILES, where a leftover pipe has a live process
answering on it. The failure it would catch is two runs sharing one state dir
and reading each other's session/layout state.

The work is small: `Get-PinnedEnvViolation` is already generic over the
variable, so C3 is a third call plus the synthetic controls that prove it can
go red. The one wrinkle is that a `LOCALAPPDATA` assignment is usually a
`Join-Path` expression rather than a quoted literal, so the literal test has to
judge the composed path (or the check has to require `$PID` somewhere on the
line) instead of skipping every expression as "chosen elsewhere".

## Validation criteria

- [ ] `isolation-meta.ps1` grows a C3 that fails a pinned sandbox

- [ ] The rule tolerates the forms already in the tree (`Join-Path $env:TEMP

- [ ] `isolation-meta.ps1` ALL PASS on the real tree with C3 armed
