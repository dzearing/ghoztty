# T3042 - PA-V10: the viewer find card deletes its bitmap while it is still selected, which likely leaks a bitmap on every card resize (ViewerFindBar.zig:764)

## Summary

PA-V10 (audit-1, T2963). releaseCardSurface (ViewerFindBar.zig:764-768) calls DeleteObject on card_bmp while it is still selected into card_dc (selected at :745, original never saved), then deletes the DC. Deleting a selected bitmap fails, so each resize, scale or theme change likely leaks one card-sized DIB (inferred, not observed). Fix: delete the DC first, as ViewerTOCPanel.zig:1552-1553 does, or restore the original bitmap. Risk: none. Findings: docs/design/perf-audit/audit-1/V-findings.md.

## In plain terms

An audit suspected the find bar in document viewers threw away a small image
the wrong way every time it was resized, slowly leaking memory. Measured on
the box, Windows forgives that order and nothing leaked. The cleanup now runs
in the order Windows documents anyway, and a test proves that resizing the
find bar fifty times leaves nothing behind.

## Goals

- [x] Measure whether the old delete order really leaks (it does not on Win11)
- [x] Release the card DC before its bitmap, the documented order
- [x] A unit test that goes red if a card rebuild strands its bitmap

## Validation criteria

- [x] GDI object count is flat across 50 find-card resizes - unit test `viewer find card: 50 rebuilds leave the GDI object count flat` (win32 lane): green with the fix; ALSO flat (1 -> 1) with the pre-fix order, so the leak was not real; proven able to fail by removing the DeleteObject (2 -> 52)
- [x] grep for the same delete-while-selected shape elsewhere in src/apprt/win32 - every DeleteObject near a DeleteDC read: no other production site; four BannerOverlay unit tests delete a selected bitmap via defer order, harmless per the measurement above, left as is (not filed)
