# T2151 - A background test run a turn leaves behind outlives /reset-context and runs beside the next turn's acceptance in the same tree

## Summary

2026-10-21: the T2139 turn started harness-floor.ps1 -Scoped in the background at 21:02 and reset; the T2104 turn claimed at 21:14 with it still running (suite-run.ps1, member audits) in D:\git\ghoztty-b. Meanwhile three of that turn's acceptance runs saw ghoztty.exe exit 1 at launch / mid-test with no panic; once the sweep ended, the same scripts ran green. Cause not proven, but nothing at claim time reports a live test run of this lane's tree, and go.md forbids overlapping lanes/acceptance. Owed: claim lists (and offers to wait for) live harness/acceptance processes whose cwd/script path is this lane's tree.

## In plain terms

When the automated loop starts a long batch of test checks and then wipes its memory to start the next job, the batch can keep running unseen while the next job's own tests run on top of it. Tests that were fine then fail for no real reason. T1658 fixed this for the two main test runners. This change covers the last two ways a batch can start: the harness sweep run directly, and a single test script run by hand.

## Goals

- [x] a direct `harness-floor.ps1` run holds this worktree's test-run lock, so the claim names it (`TEST RUN IN FLIGHT`) and the runners wait for it
- [x] the same run inside floor-lane is nested and never waits
- [x] a hand-run acceptance script beside a live run prints `WARNING TEST RUN IN FLIGHT` naming the holder. It warns and does not wait.
- [x] documented in go.md step 3, docs/claude/testing.md and the MachineLock.ps1 header

## Decision (mechanism, Claude's call)

A hand-run script **warns** and does not wait. A wait of up to 60 minutes on every script run by hand would be a worse cost than the overlap it reports. The sweep runners already refuse to overlap, so the only thing left uncovered is a person or a turn deliberately running one script, and for that case the warning is the useful signal.
