# T3380 - ipc-relay.ps1 1c expects the relay window's machine to be the far agent's hostname, but T1736 (19b223307) made an explicit --name= pin the machine label, and the test opens with --name=relwin, so +list correctly says machine=relwin; update the assertion to T1736's rule (and add a no --name case that still expects the hostname)

## Summary

Defect (in the test, not the product): test/win32/ipc-relay.ps1 section 1c asserts that the relay window it opened reports `machine` = `[System.Net.Dns]::GetHostName()`, the far agent's HELLO hostname. But the window is opened with `+new-remote-window --relay=... --name=relwin` (line 312), and T1736 (19b223307, "A scripted relay window keeps the machine name its script gave it") deliberately made an explicit `--name=` pin the machine label (IpcHandlers `name_pinned`, matching Mac IPCServer `namePinned: name != nil`). So `+list --json` correctly reports `machine = 'relwin'`.

Evidence: 2026-11-22 due sweep (T3361, lane l) and a rerun on a fresh build: `FAIL the relay window reports machine = the far agent's hostname (MaximusHome)` / `machine = 'relwin'`, 40 other assertions pass. The ipc-relay stamp was last green at 19b39814e (2026-11-20), before T1736 landed.

Fix: assert machine = the `--name` the script passed for `relwin`, and add a relay window opened WITHOUT `--name=` that still expects the HELLO hostname (the path the old assertion meant to cover). Keep the human `[machine: ...]` tag checks.
