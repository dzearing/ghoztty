# T2075 - ghoztty-cleanup.ps1 D5 is red: after 'keep' records the last advisory item, the verdict still exits 1 instead of CLEAN (found 2026-10-18 in lane b at 56189ad8b; was already GUARD DUE at claim)

## In plain terms

The test for the "clean up old Ghoztty installs" tool fails one check. When you
mark the last leftover item as deliberately kept, the tool should report the box
clean. In this run it still reported something unaccounted. Either the tool's
verdict is wrong or the test's sandbox is picking up something real from this
box. Nobody knows which yet.

## Summary

`test\win32\ghoztty-cleanup.ps1` was already `GUARD DUE` at T1092's claim
(2026-10-18, lane b, HEAD 56189ad8b; the script was last edited by T2056,
5a620987a). Run as an exclusive script under `acceptance-parallel.ps1 due`, it
scored `GHOZTTY-CLEANUP: 1 FAILURE(S) / 47 passed`. Everything up to D4 passes
(the dirty sandbox is UNACCOUNTED, removal works, the advisory `arp-<code>` item
remains, `keep` exits 0). Then `D5 a deliberately kept item makes the verdict
CLEAN` fails with `verdict -NoProcessScan` exiting 1.

Log: `%TEMP%\ghoztty-acceptance-parallel\20261018-024706\00-ghoztty-cleanup.log`
The previous lane-b turn (T1091, 3ee999ceb, same morning) logged
ghoztty-cleanup as PASS, so this may be intermittent or depend on what is on the
box at the time. Either way, the verdict text is the evidence that is missing.
(The assertion does not print the verdict text, so the log cannot say WHAT was
still unaccounted). First step: make D5 print `$d3.Text` on failure, re-run,
and read which item the verdict still counts. Suspects: a lane-B-specific
location (this worktree's dev install or agent state) leaking into the sandboxed
inventory, or the keep record being written somewhere the verdict does not read.
