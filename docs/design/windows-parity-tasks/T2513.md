# T2513 - Composition step 2b-iii: confirm the grid holds during a glide on the composition path like Mac paneContentFreeze (the visual stretches the last frame instead of a stale redirection bitmap)

## Summary

Split out of T2488. T2102 ported Mac's paneContentFreeze. On the composition path the DComp visual stretches the last presented frame rather than the window showing a stale redirection bitmap, so whether the held grid reads right during a glide needs its own on-screen look, using the T2488 oracle (`scripts\comp-present-onscreen.ps1`).

## In plain terms

When you click a tucked pane's strip, the panes in that row slide to their new
places. Ghoztty has a new, smoother way of drawing terminal pixels on screen
that is still switched off by default. This films that slide on the real
screen, with the new drawing on and off, and checks that every pane's picture
travels with its card, whole and at its own size: never blank, stretched or
torn, and gliding rather than jumping. Nothing pops up while it runs and the
mouse never moves.

## Goals

- [x] An on-screen film of a pane-stack glide that scores each pane's picture frame by frame
- [x] Run with the composition present on, and off for comparison
- [x] A negative control that proves the glide check can fail

## What landed

`scripts\comp-glide-hold-onscreen.ps1`. Same ghost shape as T2488's oracle
(`GHOZTTY_DEBUG_GHOST=bottom`, `GHOZTTY_TEST_NO_OCCLUSION=1`) and the
`ghoztty-comp-spike --film-hwnd` frame stream. Four panes in one row, each
painted with a solid block in its own colour (palette 1/2/4/5 forced to pure
primaries), the window narrowed to 760 DIP (two on show, two tucked), then a
POSTED click on the furthest strip - no SetCursorPos, no input attachment, so
the user's pointer never moves. The glide is stretched to 1.5 s. Per frame
and per colour: rows present, each row's left and right edge. Checks: glide
(2+ positions on the way), whole (a card live at both ends is on screen every
frame at >= 90% of its height), held (never larger than its rest size + 2 px),
untorn (all rows share one left and one right edge within 2 px).

## Findings

1. **Both paths hold the picture through the glide.** The card that travels
   317 px is seen at 28 (on) / 29 (off) distinct positions, in every frame,
   at its rest size 192x208, never stretched, never torn.
2. **This glide resizes no pane**: the debug log's `stack unfold carried ...
   resizes=0` on every step, so the "stretched last frame" the card worried
   about does not arise on a strip click; T2102's S2 (pane-stack-slide.ps1)
   still owns the at-most-once rule.
3. **The film cannot see the opening card's content.** A card coming out of
   its strip is drawn by its face (`StripFace.zig`), a layered popup and so
   its own top-level window, which a window capture never contains - it reads
   as an empty card until it lands live, identically on both paths. The log
   says the face is there (`frame=1`, content_alpha 0 -> 255). The script
   reports that card and does not score it.

## Validation criteria

- [x] grid hold observed on screen during a glide with the composition present on - `scripts\comp-glide-hold-onscreen.ps1`, arm on: `blue ... rest=192x208 seen=111/111 travel=317 positions_on_the_way=28`, .5-.8 PASS
- [x] the same glide knob off, for comparison - arm off: `seen=113/113 travel=317 positions_on_the_way=29`, .5-.8 PASS; whole run ALL PASS (26), the ghost never took the foreground
- [x] negative control - `-NegativeControl -Arms on` (0 ms slide): `positions_on_the_way=0`, on.5 FAIL as required
