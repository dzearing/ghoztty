# T848 - crash-stacks.ps1 goes red on floor-lane's stall self-test when the box is still busy from its own dump captures

## Summary

Found under **T478**. `test\win32\crash-stacks.ps1`'s last section runs
`scripts\floor-lane.ps1 -SelfTest`, which proves the lane wrapper can tell a
wedged command from a slow one. Two runs apart, on an unchanged tree:

```
FAIL floor-lane self-test still passes with the catcher wired in
     tail: FAIL selftest-wedge: wanted STALL, got TIMEOUT
```

then, run standalone seconds later, `LANE selftest-wedge STALL in 21s` and
`ALL PASS`, then crash-stacks itself ALL PASS on the retry.

The self-test decides STALL by sampling CPU for `-StallSeconds` (15) and
concluding nobody is working; `TIMEOUT` means it never reached that verdict
before the 120s cap. crash-stacks reaches it having just written two ~100 MB
`/ma` minidumps, so the box is still flushing them — the sampler sees CPU that
is not the debuggee's and holds off, and the assertion goes red for a reason
that has nothing to do with what either script is about.

## In plain terms

One of the self-checks in the crash-tooling test sometimes fails for no real
reason: it asks "is this command stuck?" right after the test wrote a couple of
hundred megabytes to disk, and the disk activity makes a stuck command look
busy. The test then reports a failure that disappears when you run it again —
the kind of red that teaches people to re-run rather than read.

## Goals

- [x] `crash-stacks.ps1` passes repeatedly (say 5 runs in a row) with no retry
- [x] Whatever the fix is, a genuinely broken stall detector still turns the
      assertion red — the fix must not be "stop asking"

## What it actually was

Not the box being busy. A probe held a wedged `waitfor` tree under four
spinning jobs for a minute and its CPU never moved a tick, so load was never
reaching the signal — the SAMPLE was. The watchdog read any *change* in tree CPU
as progress, and `Get-CimInstance Win32_Process` comes back empty or short on a
loaded box: a sample that flapped empty and back reset the no-progress clock
every single time, so the wedge case ran to the 120s wall-clock cap and reported
TIMEOUT where it had just proved STALL. The minidumps in the title were a
coincidence of timing, not a cause.

Three rules now, in `scripts\floor-lane.ps1`:

- `Get-TreeCpu -State` keeps a **per-pid high-water mark**, so the number is
  cumulative and monotonic. A process leaving the tree no longer takes its CPU
  with it, and a short sample no longer subtracts what it missed.
- Progress means **greater**, not different. Both inputs (that CPU sum, and a
  log that is only appended to) are monotonic, so a drop is a measurement
  artifact and reading it as progress is the whole defect.
- A sample that **saw nothing is not a sample**: it buys no progress, the
  seconds it covers are not charged as stall time either, and no wedge verdict
  is declared off one. The wall-clock cap still is, so a box that can never be
  sampled cannot hold a lane open forever.

## Details

- Candidate shapes, in the order they look right: give the self-test a moment of
  quiet before it starts (the sampler's premise is that nothing else is running);
  have crash-stacks run the self-test FIRST, before its own captures; or teach
  the sampler to attribute CPU to the process tree it is watching rather than the
  box. The last is the only one that fixes the flake for every caller, and
  `floor-lane` is called on already-bad days when the box is busy for real.
- Do not simply drop the assertion: it is the only place that proves the wrapper
  can name a wedge, which is the reason the wrapper exists (T430).
