# T3671 - Linux L8d-5: relay remote windows come back at relaunch (GTK SessionLayout records them)

## Summary

Split from T3668 part 1. SessionLayout.zig skips remote windows today, so a +new-remote-window --relay window is gone after a relaunch, while the Mac and win32 (T3352 relay_manifest + recordRelayWindow) bring it back on the same machine. Record relay windows (base, device, name - never the token; resolve the token from the account store at restore) and re-dial them at launch; a direct --host window follows whatever win32 does for it. Acceptance: extend test/linux/cli-remote-window.sh or session-restore.sh with a relaunch that brings the window back on its agent.

## In plain terms

On Linux, a window opened on another machine through the relay used to vanish
when Ghoztty was quit and started again, even though the shell on that machine
was still running. Now the window comes back on its own at the next launch,
reconnected to the very same shell, under the same name and title - the way it
already does on the Mac and Windows. A window you closed on purpose stays closed.

## Goals

- [x] Record every open relay window (relay, device, name, title, its first pane's session; never a token) in `remote-windows[-debug].json` beside the session layout
- [x] A quit or crash keeps the record; a deliberate close (`+close`, the user's, the shell exiting) drops the entry
- [x] At launch, re-dial each recorded machine off the GTK thread, probe the session, and reopen the live ones re-ATTACHed (dead sessions dropped, unreachable ones kept for later)
- [x] A direct `--host` window is not recorded (win32 and the Mac do not record one either)

## Design (recorded 2026-11-24)

- The record is win32's `relay_manifest.Manifest` (std-only), imported as the
  other GTK ports import win32's pure files; only the path is Linux's
  (`session_layout_rules.relayWindowsPathFrom`, under the config root).
- `src/apprt/gtk/RelayWindows.zig` owns it: `record` (from
  `ipc_remote_window.openWith`, so `+new-remote-window --relay`,
  `--from-focused` off a relay window and the restore all register),
  `windowDisposed` (window `dispose`; removes unless `Application.isQuitting`),
  `syncForQuit` (session + pinned title refresh in `quitNow`), a 500 ms x 60
  session-id capture poll, and `start`/`settle`/`adopt` (worker thread resolves
  the token via `ipc_remote_window.resolveToken`, dials, `probeSessionTimeout`;
  `glib.idleAdd` back to reopen).
- `RemoteLink.Open.session_id` carries the session; the surface's
  `remoteBackend` passes it as the ATTACH id.
- Owned by the instance serving the IPC socket, NOT gated on
  `session-persistence` (the sessions are the far agent's).
- The IPC name recorded is the one the window was opened under (`--name`); a
  name GTK mints later (`window-3`) is not recorded (win32 rule).
- Sign-out/sign-in replay and chooser hooks are noted on T3575 and T3563.
