# T1428 - A machine whose re-enrollment failed while offline does not come back until the app is restarted

## Summary

Follow-up to T1425. The suspended-enrollment restore runs at sign-in and at every launch, so a user who signs back in while the relay is unreachable gets their own machine back only after quitting and reopening Ghoztty - which nobody thinks to do. The pending REVOCATION beside it already has a capped backoff for exactly this reason (relay_revoke_pending.backoffMs) and the restore has none; the Mac seat retries on a network-came-back transition. Give relay_suspend the same cadence, and prove it the way section 9 does: a relay that is DEAD when the restore first runs and answers afterwards.

## In plain terms

When you sign out of Ghoztty and back in, your computer is put back on your
account so your other devices can see it again. If the internet (or the relay)
happened to be down at the moment you signed back in, that step failed and your
computer stayed missing from the list until you quit and reopened Ghoztty -
which nobody would think to do. Now Ghoztty keeps quietly trying in the
background and puts the machine back within a minute or so of the connection
returning.

## Goals

- [x] A restore that could not reach the relay is retried in the running app, on the same capped cadence the pending revocation uses (5s, 15s, 1m, 5m, then every 15m)
- [x] Signing in while the relay is unreachable starts that retry (not only app launch)
- [x] The retry stops on its own once the machine is back, the record is dropped, or the user signs out (so it never races the sign-out revocation retry)

## Design

`relay_suspend.restoreAsync` now runs a loop (`restoreLoop`) instead of one
pass. `retryOwed(outcome)` is the pure rule: `enroll_failed` and `still_armed`
(a pending revocation whose relay could not be asked) retry; `idle`, `kept`,
`dropped`, `restored` end it. Every pass re-reads the account and both records,
so a sign-out reads `idle` and ends the loop at its next tick. The cadence IS
`relay_revoke_pending.backoffMs` - both loops wait on the same thing, the relay
becoming reachable, which no local Windows event reports (the Mac seat retries on a
network-came-back transition; a backoff is the Windows translation the revocation retry
already chose). `signIn` keeps its inline restore and, when that pass is owed a
retry, calls `retryLaterAsync`, which starts the loop at attempt 1 so the relay
that just refused is not re-asked in the same breath. The `still_armed` retry
is a whoami PROBE only - never the de-enroll - so it cannot revoke the machine
the user just signed back in on.
