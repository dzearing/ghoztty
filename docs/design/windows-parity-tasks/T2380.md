# T2380 - viewer-narrow-pane.ps1 is red on HEAD 8fc584ad9 (alone, with and without T2365's frame clock): A sees the wide TOC card at 450px not ~300px, and E[90] finds no control painted in the narrow nav bar's leading slot; it was green at a50ce35ae (2026-10-26), so something in between (T2342's maximize default is the first suspect) broke it

## Summary

Found by T2365's due run (2026-10-27). `test\win32\viewer-narrow-pane.ps1`
fails 3 of 70 on its own, and it fails the same way against a debug build of
HEAD 8fc584ad9 (before T2365), so the frame clock did not cause it:

- `FAIL A: the wide card is at the preferred width (want ~300px, got 450px)`
- `FAIL E[90]: a control is painted in the leading slot (0 ink rows)`
- `FAIL E: both the widest and the narrowest leading slot carry ink`

Its stamp was last written green at a50ce35ae (2026-10-26 08:08). Between
there and 8fc584ad9 come T2342 (new windows open maximized; the harness
launch is pinned to `--maximize=false`, but `+new-window` windows it opens
should be checked), the pane-sidebar intake, and the T2283/T2284 pane-size
changes. Bisect with `-ExePath` against worktree builds.

## In plain terms

The test that checks a squeezed viewer pane keeps its contents list and its
nav button inside the pane had gone red. The viewer itself was fine: the test
was reading leftovers from earlier dev runs on this machine - a contents-list
width someone had dragged wider, and a pane sidebar that a newer feature puts
in every window and that the test never asked to be hidden. The test now runs
with a clean slate of preferences and the sidebar off, so it measures the
viewer again.

## Goals

- [x] Find why section A saw a 450px card and section E lost the "..." control
- [x] Make the harness independent of persisted dev preferences
- [x] Green again, with the negative control still failing exactly five ways

## Root cause

Not a code regression in the viewer - two pieces of state leaked into the run:

- **A (450px card):** the harness ran on the user's real `LOCALAPPDATA`, where
  the debug build keeps `ghoztty\viewer_sidepanel_width-debug`. It read `360`
  (written 2026-10-27 20:42, after the last green stamp at a50ce35ae on
  2026-10-26), and 360 DIP x 1.25 = 450px. No commit caused this; it is box
  state any viewer run that drags the card can leave behind.
- **E[90] (no control in the leading slot):** T2336 (3c124c0db, 2026-10-27,
  "one sidebar for every window") put the pane sidebar in section E's
  single-pane window, restored from the debug `pane_sidebar-debug` state by the
  `remember` default. A rail eats about 100 DIP, so the 90 DIP window gave a
  42px bar; `viewer_nav_layout.Layout.init` drops even the "..." below one
  padded slot (pad + target + pad = 45px), by design. The section's premise -
  "the pane is the window" - had stopped being true.

Fix (harness only): `test\win32\viewer-narrow-pane.ps1` now runs with a
private `LOCALAPPDATA` (restored in `finally`) and launches with
`--macos-pane-sidebar=hidden`. Narrowest bar is back to 120px; card 300px.
