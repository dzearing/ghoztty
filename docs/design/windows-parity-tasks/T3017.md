# T3017 - PA-I03: the agent and holder run on DebugAllocator in release builds, and the agent's output path makes two large allocations and up to four copies per chunk (main.zig:168, server.zig:870, :814)

## Summary

PA-I03 (audit-1, T2962). src/remote/agent/main.zig:168 `var gpa: std.heap.GeneralPurposeAllocator(.{}) = .{};` is DebugAllocator in every build mode (Zig 0.15.2 heap.zig alias), so release agents and holders take its mutex per call, and anything over the 16 KB largest bucket is a direct VirtualAlloc/VirtualFree plus a locked hashmap insert. server.zig:870-874 allocates the DATA payload, then enqueue (:814) dupes it: two allocations, two frees and 3-4 copies (payload, dupe, merged, wire) per chunk; flood chunks reach 64 KB, so each chunk costs two VirtualAlloc/VirtualFree pairs and ~32 soft faults. The attach grid snapshot goes through the same path and peaks near 4x its size (a 4 MB scrollback snapshot ~16 MB transient per session at restore). Fix: std.heap.smp_allocator outside Debug (keep the leak-checking allocator in Debug); an owning enqueue so sendDataFramed hands its buffer over. Risk low; no wire change. Shared agent code: Mac half filed. Findings: docs/design/perf-audit/audit-1/I-findings.md.

## In plain terms

The background process that keeps your terminal sessions alive was built to
use a slow, debugging-only memory manager even in the released app, and it
copied every chunk of output a couple more times than it needed to. It now uses
the fast memory manager in releases and copies output once. Measured on a big
flood of output, this did not make the background process noticeably cheaper;
where its time really goes is now its own task (T3159).

## Goals

- [x] release agents and holders use `std.heap.smp_allocator`; Debug keeps the leak-checking allocator
- [x] DATA and control frames are handed to the write queue instead of duplicated
- [x] attach replay, relaunch replay and FLOW catch-up slice the ring straight into the frame they send (PA-I20)
- [x] perf-baseline can measure the agent under a flood (`-BusyPersistence`)

## Validation criteria

- [x] a release agent under a 64 MB flood (perf-baseline busy phase on an agent-backed pane) is MEASURED before and after - verified with `perf-baseline.ps1 -Build Release -Phase busy -BusyPersistence`, two runs a side, same app exe with the HEAD agent vs the changed one: agent family CPU 22.6 / 23.5 s before, 23.5 / 23.8 s after. **Not lower**: the card's estimate of the allocation cost did not hold, so the expected win is absent; no regression either. The real cost is filed as T3159.
- [x] zig build test-agent green in Debug (leak checks still on) - verified; the release agent ran session persistence in all four A/B runs (the busy pane's 64 MB arrived through it and its marker landed)
