# T1840 - floor-lane's win32 lane goes red on the user's own Spotify window: the lane process-tree walk adopts unrelated processes through a reused parent pid

## Summary

2026-10-11 06:50, T1827 turn: `scripts\floor-lane.ps1 -Lane all` reported
`LANE win32 SHOWED 1 WINDOW(S) ON THE USER'S DESKTOP (T1813)` for
`hwnd=0x90F09DA pid=39000 class=Chrome_WidgetWin_1` and scored the lane FAIL.
pid 39000 is the user's own **Spotify.exe** (WindowsApps), created 2026-10-03,
parent pid 26328 - a process that no longer exists. Nothing in the lane
launched it; it reached `Get-LaneInputDesktopWindow -ProcessId @($tree ...)`
because the tree walk collects children by `ParentProcessId`, and Windows
reuses pids: when a lane process was handed pid 26328, Spotify (whose real
parent died days ago) looked like that process's child.

Fix: in the tree walk (`Get-TreeCpu`'s tree source / whatever builds `$tree`),
only adopt a child whose `CreationDate` is AFTER its claimed parent's - the
standard guard for parent-pid walks on Windows. The CPU-progress signal reads
the same tree, so an adopted stranger's CPU can also be counted as lane
progress (masking a wedge); the same guard fixes both.

## Validation criteria

- [ ] a process whose parent pid is reused by a lane process is NOT in the lane tree (unit-level test on the walk with synthetic rows: child older than parent is dropped)
- [ ] the T1813 check still catches a window the lane's own tree shows (`test\win32\floor-lane-desktop.ps1` stays green)
- [ ] the CPU-progress signal ignores the adopted stranger
