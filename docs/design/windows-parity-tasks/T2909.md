# T2909 - Background windows hold still on Windows too: the busy border and the sidebar busy sheen move only in the window in use (port of Mac 68a8344f0; titles, polling/GIF and the new-pane/measure parts split to T2912-T2914)

## Summary

Port of Mac 68a8344f0 (perf(macos): stop background windows doing work nobody can see; 16 background windows ~21% -> ~4.7% CPU on Mac), the window-in-use half. Mac's `WindowInUse.animates` - the key window, on screen - gates the busy border (`BusyBorderView.updateSpinning`: elsewhere it holds still at the top) and the sidebar busy sheen (`PaneSidebarTileSheenLayer`: elsewhere the glint is off, drift and rim still). State never pauses.

Already on Windows before this task: hidden panes skip frame building (T2910 merged the shared `renderer/Thread.zig` change, and win32's occlusion poll already reports covered/cloaked/minimized windows as not visible).

Split out (2026-11-11, one task per context): held titles while hidden -> T2912; git-status polling + GIF pause -> T2913; a pane added to a hidden window starts hidden, the exactly-behind coverage check and the 16-window CPU measurement -> T2914.

## In plain terms

A pane that is busy shows a light circling its border, and its row in the sidebar shimmers. Until now every window kept animating those even when it was in the background or covered, which costs CPU and GPU time for motion nobody can see. Now only the window you are working in animates; the others show the same busy state, held still, and start moving again the moment you switch back to them.

## Goals

- [x] the busy light circles only in the window in use, held at the top elsewhere
- [x] the sidebar busy sheen moves only in the window in use, still elsewhere
- [x] switching windows (or apps) starts and stills both at once
- [x] the remaining parts of the Mac port filed as their own tasks (T2912, T2913, T2914)
