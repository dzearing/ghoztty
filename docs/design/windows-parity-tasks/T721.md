# T721 - Sweep the remaining owned popups (search bar, command palette) for the T142 z-order heal

## Summary

T180 closed the last popup T142 named as skipped (the hovered-URL bubble) and,
while doing it, enumerated every `WS_POPUP` in `src/apprt/win32`. Two owned
popups still never call `w32.healOverlayZOrder` and were left alone because they
differ in KIND, not because they were checked:

- `Surface.ensureSearchBar` (`Surface.zig` ~2007) — the find bar.
- `Surface.ensureCommandPalette` (`Surface.zig` ~2282) — the command palette.

Both are ACTIVATABLE popups: they take keyboard focus when shown, so Windows
orders them against activation in a way the passive `WS_EX_NOACTIVATE` overlays
are not. That may well make the heal unnecessary — or actively wrong, since the
heal reseats a popup directly above its owner and an activated popup is meant to
be above everything the user is looking at. Decide it with a measurement, the
way T180 did, and write the answer down either way.

Also worth one line of verdict each: the tooltips (`ViewerNavBar.zig` ~412,
`Window.zig` ~6062) are system `TOOLTIPS_CLASS` windows the OS places itself,
and the modal dialogs (`ConfirmDialog`, `RenameDialog`, `MachineChooser`,
`HostSettingsDialog`, `NewProcessDialog`, `BannerDialog`) are activated
top-levels — neither is an overlay, but saying so in a comment costs nothing and
stops the next sweep re-asking.

## In plain terms

Ghoztty draws several small floating panels. Most of them now fix their own
stacking so they can never end up hovering over another application; two — the
find bar and the command palette — still don't, and nobody has checked whether
they need to. This is that check.

## Verdict (measured 2026-09-14)

**Neither popup is healed, and neither should be.** Both are ACTIVATABLE
popups - no `WS_EX_NOACTIVATE`, `SW_SHOW` activates them, focus goes into their
own EDIT child - and both DISMISS THEMSELVES the instant activation leaves
them: the palette on `WM_ACTIVATE`/`WA_INACTIVE`, the find bar on
`EN_KILLFOCUS` of its edit (both in `App.zig`). A popup that cannot be visible
while its owner is in the background cannot reach either T142 case, so
`healOverlayZOrder` on these would be dead code rather than a fix.

Measured as section I of `test/win32/overlay-zorder.ps1` (ALL PASS, 55
assertions), three arms per popup:

- **I1** the healthy baseline - owned by its window, not topmost, seated above
  its own window (popup=1 < oz4=3 for both).
- **I2** the teeth - asserted VISIBLE while its window is active (positive
  control), then activation moved to another window of the same app and
  asserted GONE. If the dismiss ever regresses, this pair goes red, and that is
  the day these two would start needing the heal.
- **I3** the harder half - section B's stray `WS_EX_TOPMOST` injected on the
  popup, which SURVIVES a close and reopen (nothing on the open path clears it,
  asserted as a positive control) and the popup dismisses anyway. So even the
  T142 case-1 bit only ever sits on a window nobody can see.

Side measurement worth keeping: `SetWindowPos(HWND_TOPMOST)` will not change
the band of either popup while it is the ACTIVE window on the test desktop -
four attempts each, the T277 shape - but takes first time while it is hidden.

The other popups named in the Summary, and the ones the sweep turned up that it
did not name, carry their verdicts in `overlay_zorder.zig`'s module doc: the
tooltips are system `TOOLTIPS_CLASS` windows, the modal dialogs (eight of them,
not six - `AgentIntegrationsDialog` and `UpdateProgress` too) are activated
top-levels, `RegionSelector` is topmost ON PURPOSE, and the remaining `WS_POPUP`
hits are in-file test fixtures.
