# T2861 - Prove a shipping build comes back after a crash: crash an installed release that has run 60+ seconds and watch Windows relaunch it with every session re-attached (T2839's live half)

## Summary

T2839 registers shipping builds for Windows' crash relaunch (RegisterApplicationRestart without RESTART_NO_CRASH). The pure flags are unit-tested and install-restart.ps1 L3 proves the debug build still opts out, but the relaunch itself can only be seen on the user's own desktop: Windows Error Reporting relaunches the app there, not on a test desktop, and only for a non-sandboxed release build. Validate once on a release that carries T2839: run it 60+ s, crash it (crash:main binding or a fault injection), confirm a new process starts with no arguments and re-attaches the agent's sessions, and that a second crash within 60 s is NOT relaunched.

## Validation criteria

- [ ] a shipping build run 60+ s and crashed is relaunched by Windows with no arguments, and its sessions re-attach
- [ ] a second crash within 60 s of that relaunch is NOT relaunched (the crash-loop guard)
- [ ] the relaunched app shows the "Ghoztty closed unexpectedly" balloon once (T2862), and clicking it opens the crash report folder in Explorer; the next launch shows nothing
