# T2914 - A pane added to a hidden window starts hidden on Windows, and the background-window CPU cut is measured with 16 background windows (port of Mac 68a8344f0, split from T2909)

## Summary

Part (4) plus the measurement of the Mac 68a8344f0 port, split from T2909. (4) Mac: a terminal added to a hidden window starts hidden (surfaceTreeDidChange -> updateSeen), so it never allocates render targets it will not draw into. Windows: check that +split / +new-window --target into an occluded window leaves the new pane not visible until the window is revealed (applyOcclusion re-asserts on every poll, so at worst one poll interval - decide whether that gap matters and close it if so). Measure: N background windows (Mac's mix: busy panes with a circling border, spinning titles, an animated viewer, a git-status viewer, idle shells) covered by a foreground window, ghoztty CPU before/after T2909/T2912/T2913. Also confirm occlusion.zig counts a window behind another of exactly its frame as covered (Mac's AppKit pitfall; ours unions cover rects, so it should).

## In plain terms

When a script adds a pane to a Ghoztty window that is hidden behind other
windows, the window used to briefly wake up and draw every pane nobody could
see, then go back to sleep. Now a hidden window stays asleep - the new pane
starts hidden and draws the moment the window is shown - and we measured what
background windows cost with all the hidden-window savings on versus off.

## Goals

- [x] a pane split into a covered or minimized window draws nothing until the window shows
- [x] the existing panes of that window are not woken by the split
- [x] a window raised, restored or brought back by undo draws at once, not at the next visibility poll
- [x] a window behind one of exactly its frame counts as covered
- [x] CPU of 16 background windows measured before/after

## Validation criteria

- [x] split into a covered window redraws no pane and the new pane draws on reveal - `test/win32/hidden-new-pane.ps1` B1-B4 green; with the hold disabled B1/B2 red (2 redraws, 3 releases)
- [x] split into a minimized window holds the same - A1-A4 green (a guard: held before too)
- [x] exact-frame cover reads as covered - B0 green, plus unit test "a window behind one of exactly its frame is covered" (occlusion.zig)
- [x] the hold rule - unit test "a layout pass shows a pane only in a window someone can see"
- [x] zig floor lanes green - `floor-lane.ps1 -Lane all`: lib/none/win32/agent PASS (2026-11-11)
- [x] 16-background-window CPU measured - `scripts/hidden-windows-cpu.ps1` (2026-11-11, debug build, 20 s): **83.8% of one core before, 4.9% after, 17x less**. Mix per 8 windows: 3 busy (a line every 50 ms), 2 spinning titles (every 100 ms), 1 git-status viewer, 2 idle shells; all 16 covered by one work-area-sized foreground window. "Before" is `GHOZTTY_TEST_NO_OCCLUSION=1`, which turns off the whole hidden-window skip (T1951's presents plus everything T2909/T2912/T2913/T2914 key on it), so the number is the combined saving, not T2914's alone. 17 'window hidden' log lines after (16 + the launch window), 0 before.
