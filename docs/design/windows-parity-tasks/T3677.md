# T3677 - Linux: a close confirmation answered with Cancel stays in the window's dialog stack in the headless harness, and the window's next close request is spent dismissing it

## Summary

Found by T3563's test/linux/cli-remote-disconnect.sh: after close-dialog --op=window then --answer=cancel, the close-dialog seam still reads the dialog as open 15 s later, and the window's next gtk.Window.close() never reaches windowCloseRequest (libadwaita spends it on the stale dialog). An answer that changes the window (Disconnect, Close) leaves cleanly, so the working guess is a frame-clock stall in the headless Weston: nothing redraws, so AdwDialog's close never finishes. Disabling animations via the harness settings.ini did NOT help, so the guess is unproven. Establish whether a real WSLg window shows it (a person pressing Escape/Cancel then the window x), and either fix it or make the harness tick frames; then move cli-remote-disconnect.sh's W1 back onto rdp before W2. Related: +close --force already loops dismissOpenDialog because a dialog 'may still read as visible while it animates out'.
