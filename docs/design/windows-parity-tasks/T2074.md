# T2074 - activity-help-tooltips.ps1 assertion E goes red when run beside other scripts (suite-run -Jobs 4) and green serially: a late tooltip log line from an earlier hover lands inside its 500 ms 'no new tooltip' window

## In plain terms

One of the checks for the Activity Monitor's hover tips fails when other checks
run at the same time, and passes when it runs alone. The app is probably fine.
The check itself is likely too strict about timing. Until it is fixed, a
side-by-side sweep reports a false failure.

## Summary

Found by T1092's first real side-by-side sweep (2026-10-18,
`suite-run.ps1 -Set gui -Limit 12 -NoConfirm`, at `-Jobs 4` and then `-Jobs 1`).
At `-Jobs 4` the script scored `1 FAILURE(S) (25 assertions passed)`, and the
failure was `E the empty badge slot and the table derive no tooltip`. At
`-Jobs 1` the same script at the same commit was ALL PASS (26).

Assertion E counts `activity help tooltip target=` log lines, moves the pointer
over the empty badge slot and then the table, sleeps a fixed 500 ms, and
expects the count unchanged. Hypothesis (unverified): the derivation from the
previous hover (section C/D, Kill or New Process) is still in flight when
`$before` is taken. Under box load it lands inside E's window and is counted as
E's. The sleep is a fixed timing budget, so load can push it over.

Fix direction: score E on the TARGET named in the new lines (none should name
the badge slot or the table), not on the raw count. Or wait for the log to go
quiet before taking `$before`. Do NOT just mark the script `# @parallel-unsafe`:
the same race can happen on a slow box run serially.

- [ ] after the fix: green beside the same load 3 runs in a row, and still green alone
