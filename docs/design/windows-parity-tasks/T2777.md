# T2777 - Composition step 5c-4a: in the composition pane tree, a folding card's face - the strip's band and name with the pane's carried frame over it - is a picture in the window's own composition tree, not a layered popup over it, still stepped from the window's thread

## Summary

Split of T2640. Today a card folding into its strip (and one opening out of it) is drawn by StripFace, a layered top-level popup that paintStripFace repaints on the CPU every glide frame (band + name + the carried frame at content_alpha) and commits with UpdateLayeredWindow. Nothing about it can be declared to the compositor while it is a separate window, and a window capture never contains it (T2561). With GHOZTTY_COMP_PANE_TREE on, give chrome_comp.Host a face visual in the pane layer (pane_root, above the pane visuals, the hero-slide shape: a container clipped to the card, holding a band+name picture and the carried-frame picture whose opacity is content_alpha), fed from the same pixels paintStripFace builds today, placed per frame from the window's thread. The popup stays the path off the tree and when the host cannot take it. Oracle: stack-fold-slide.ps1 and pane-stack-unfold.ps1 ALL PASS with the tree knobs, and a WGC window capture of a fold now contains the face (the T2561 blind spot, in tree mode). GHOZTTY_FACE_COMP=0 keeps the popup (A/B, negative control).
