# T1985 - Two loop lanes stop colliding on the shared session log

## Summary

Split from T1937 item 5. Both lanes append to windows-parity-log.md and conflict on every concurrent push. Per-lane log fragments merged at read time, or an append done only right after pull --rebase, with a test that two concurrent appends both survive.

## In plain terms

When two copies of the loop work at once, both write a note into the same
history file and push. This makes sure neither loop's note is ever lost or
blocks the other loop's push. It turned out git was already set up to keep
both notes; what was missing was a test that proves it in the exact way the
two loops collide.

## Goals

- [x] Confirm whether two lanes' concurrent log appends actually conflict today
- [x] A test that two concurrent appends both survive the lane's `pull --rebase`
- [x] The test proves it has teeth: the same race without the merge setting conflicts
- [x] go.md and .gitattributes say the log needs nothing more for two lanes

## Finding

The premise was partly stale. `docs/design/windows-parity-log.md` has been
under git's built-in `merge=union` driver since T957, and T1025's
`scripts/ledger-dupes.ps1` catches the doubled entry union can leave. A real
two-worktree experiment (lane b on a local branch, rebasing onto the shared
branch after lane a pushed) rebased with exit 0 and kept both entries. The one
cost is cosmetic: union keeps one copy of the blank line both appends open
with, so the later heading follows the earlier entry's last line directly.
Markdown still reads it as a heading and the scanner still splits there. No
per-lane fragments needed.
