# T1683 - Check the PUBLISHED Windows artifact's baked sign-in credential, not just the workflow that passes it

## Summary

T915 landed `test\win32\relay-signin-live.ps1`, which reads the baked client id
out of every delivered build ON THIS BOX and proves Google accepts it. Every one
of those three locations is built here. The binaries a USER downloads are not:
`release-windows.yml` passes `secrets.GOOGLE_CLIENT_ID` into
`build-release-artifacts.sh`, which bakes it on a GitHub runner, and nothing
afterwards reads the id back out of the MSI or the portable zip.

`test\win32\release-artifacts.ps1` section F (T795) checks that the workflow
PASSES the flag and only when it is non-empty. That is a claim about the YAML,
not about the artifact: a secret that is empty at run time, rotated, deleted, or
holding a Web-application client id instead of a Desktop one would all produce a
published build whose sign-in button cannot work, while every check on this box
stayed green - because this box bakes from its own `google-client-id.txt` and
never sees the secret at all.

The fix is to close the loop on the artifact: extract `ghoztty.exe` from the
published zip (or the MSI), read its `relay sign-in :` line the way
`Get-BakedClientId` already does, and put that id through the same Google
acceptance probe `relay-signin-live.ps1` section B uses. The probe is
unauthenticated and needs nobody signed in, so it can run wherever the artifact
can be fetched.

## In plain terms

Every Windows copy we publish has a credential stamped into it that the sign-in
button needs. We now check that credential on the builds made on this machine,
but the ones people actually download are built elsewhere, and nobody has ever
looked at what ended up inside them. If that credential were wrong, the download
would look completely normal and sign-in would simply fail for everyone.

## Goals

- [ ] read the baked client id out of a PUBLISHED artifact, not a local build
- [ ] put that id through the same Google acceptance check
- [ ] fail the release check when the published artifact cannot sign in

## Validation criteria

- [ ] the baked id is extracted from a published Windows artifact (portable zip
      and/or MSI) rather than from anything built on this box
- [ ] that id is put through the live Google acceptance probe, and the check is
      demonstrated able to fail (a doctored/absent id scores red)
- [ ] a published artifact that reports `not configured` is a failure with a
      message naming the repository secret
- [ ] the standing floor.
