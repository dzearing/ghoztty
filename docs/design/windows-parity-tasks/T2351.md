# T2351 - The win32 floor lane goes red on its clipboard tests (clipboard_open round trip, ViewerPane host floor's copy) whenever the workstation is locked - OpenClipboard is ACCESS_DENIED while LogonUI owns the input desktop; the lane should name that box state (SKIP with reason) instead of reporting a code failure

## In plain terms

When nobody is at the computer and the screen is locked, Windows refuses every
program access to the clipboard. The automated checks that test copy and paste
used to report that as a Ghoztty bug. Now they say "the workstation is locked"
and step aside, so a locked screen no longer reads as broken code.

## Goals

- [x] a clipboard test that fails because the screen is locked SKIPs instead of failing (landed with T2346, bd894bfb06)
- [x] the skip names the lock, not a phantom "another process" holding the clipboard
- [x] the rule that decides "locked" is unit-tested without locking the box

## Summary

**Re-verified 2026-11-26 - partly fixed.** T2346 (bd894bfb06, 2026-11-05)
already made both clipboard oracles SKIP on this card's exact shape:
`OpenClipboard` -> 5 with `GetOpenClipboardWindow` NULL classifies as
`held_unnamed`, a box condition. So the floor no longer goes red on a locked
screen. What was LEFT is the "name that box state" half: the skip text read
"clipboard held by another process", which on a lock sends the reader hunting
for a process that does not exist.

Fix: `clipboard_open.Holder.Kind.desktop_locked`. `holder()` asks, only on a
refusal (err 5), whether the input desktop is the secure `Winlogon` desktop
(`inputDesktopLocked()`: `OpenInputDesktop` refused with 5, or opened and
named `Winlogon`). `classifyWindowless(open_ok, err, input_locked)` is pure and
returns `desktop_locked` for a refusal on a locked box, `held_unnamed`
otherwise; any non-5 failure stays `unknown` (unexcused) even when locked.
`Holder.boxConditionText()` gives the skip its words, used by both skip sites
(`clipboard_open` round trip, `ViewerPane` host-floor copy oracle).
