# T2168 - Apps & Features still shows 26.10.2290 instead of the release number

## In plain terms

Open Windows Settings > Apps and look at Ghoztty: it says 26.10.2290, a
number that appears on no release page. The release the user installed is
1.43.3. An earlier fix (T1205) asked the installer to show the release number,
and every check said it had - but Windows never actually did what it was asked.
When this lands, Settings shows 1.43.3 for a 1.43.3 install.

## Summary

T1205 put `ARPDISPLAYVERSION` (the release semver) into the MSI's Property
table, next to the load-bearing `ProductVersion` (`yy.m.dNN`). Windows
Installer does not recognise `ARPDISPLAYVERSION`: it is not one of the ARP*
properties `RegisterProduct` reads (ARPCOMMENTS, ARPCONTACT, ARPHELPLINK,
ARPNOMODIFY, ARPPRODUCTICON, ...). `DisplayVersion` is always written from
`ProductVersion`.

Evidence (2026-10-22, T1210, read-only):

```
powershell -NoProfile -File scripts\arp-version-check.ps1
  registry: HKLM:\Software\Microsoft\Windows\CurrentVersion\Uninstall\{38E146D2-...}
  package : C:\WINDOWS\Installer\82974b4.msi
  FAIL  display: Apps & Features shows '26.10.2290' (registry DisplayVersion), but ARPDISPLAYVERSION in the package is '1.43.3'
  OK    sequencing: Windows registered ProductVersion 26.10.2290 (registry Version), the package's own 26.10.2290
```

The installed product is win-v1.43.3. The property is still useful in one place:
`build-msi.sh` passes `--installed-version=[ARPDISPLAYVERSION]` to
`--install-restart`, which reads it as an ordinary MSI property and works.

## Where

- `dist/windows-installer/build-msi.sh` (the ARP registration).
- Things that currently CLAIM the display works and must be corrected along
  with the fix: `scripts\verify-release-assets.ps1` ~line 342 ("msi: Apps &
  Features will show $version" checks only the Property row);
  `test\win32\release-artifacts.ps1` A20-A22; the comment in
  `test\win32\update-real-msi.ps1` ~line 284.

## Fix direction (mechanism is ours to pick; record the choice here)

Windows Installer owns the `DisplayVersion` value of the entry it writes, so the
number has to be put there by something other than a Property row. Candidates:

1. `ARPSYSTEMCOMPONENT=1` to hide the MSI's own entry, plus our own Uninstall
   key (DisplayName, DisplayVersion=semver, Publisher, DisplayIcon,
   InstallLocation, EstimatedSize, UninstallString/ModifyPath =
   `msiexec /x|/i [ProductCode]`, so T1300's Settings > Apps -> repair still
   works). The common WiX-world answer. Has to keep `ghoztty-cleanup.ps1
   inventory`, the in-app updater and every harness that finds the product by
   its ARP entry working - check each before choosing.
2. A deferred custom action after `RegisterProduct` that rewrites
   `DisplayVersion` in the entry Windows wrote. Fragile: a repair re-registers
   and puts the yy.m.dNN back.

Whatever lands, `ProductVersion` stays the sequencing number (`sequencing` and
`unfused` lines of the check must stay OK).
