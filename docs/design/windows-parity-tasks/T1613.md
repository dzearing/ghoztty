# T1613 - tab-tooltip.ps1 assumes the default tab title is short, so a deep TEMP path fails two of its arms

## In plain terms

A test of the tab hover-tooltip fails on this box, and the product is fine - the
test simply assumed the tab would be captioned with something short. It is
captioned with the folder the test itself created under %TEMP%, and that path is
long enough for the tab strip to shorten it, which correctly makes the tooltip
show two lines instead of one. Nothing a user sees is wrong; a harness that goes
red for a reason unrelated to its subject is what needs fixing.

## Summary

`test/win32/tab-tooltip.ps1` fails 2 of 20 on this box:

- `A: the home prefix reads as ~` - asserts the probe text `StartsWith('~')`
- `E: a title that fits keeps the tip cwd-only` - asserts the tip has no newline

Both assume the tab's default title is short enough NOT to be elided. The run's
own scratch dir is `%TEMP%\ghoztty-tabtip-<pid>\tipA<n>`, and cmd.exe captions
the tab with that full path, so at a 1200px window (a tab capped at 50%) the
strip ellipsizes it and T556's two-line tip fires - title line, then the
`~`-abbreviated cwd. Observed 2026-09-16, with the escaped newline the oracle
logs shown as `\n`:

```
C:\Users\David\AppData\Local\Temp\ghoztty-tabtip-15532\tipA577\n~\AppData\Local\Temp\ghoztty-tabtip-15532\tipA577
```

The three T556 arms that DO expect elision all pass, which is the tell: the
product is doing exactly what it claims, and only the two arms whose premise is
"the title fits" are wrong. That premise is an accident of how deep the box's
`%TEMP%` sits, so the same script passes on a shallower path and fails here.

The fix is to make the premise explicit rather than incidental: set a short tab
title before the A and E-negative arms (or read the cwd line out of the probe
instead of asserting over the whole tip), so the assertion measures the `~`
abbreviation and the fits-title case rather than the length of the harness's own
scratch path. Found while running the guard for T789.
