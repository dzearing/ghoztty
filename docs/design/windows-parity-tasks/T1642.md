# T1642 - The diff pane's next-change acceptance assertion fails about one run in two

## In plain terms

Nothing is wrong with the terminal here: stepping through a diff change by
change works. What is unreliable is the automated check that proves it — it
says "failed" on some runs and "passed" on the very next one, over the same
bytes. A check that cries wolf is worse than no check, because the next person
to see it red will assume it is lying and ship the thing it was catching.

## Goals

- [ ] The assertion passes on ten consecutive runs, or it is rewritten to wait
      for the state it is asserting rather than for a fixed interval
- [ ] Whatever the race turns out to be is named in the script, so the next
      reader knows what the wait is for

## Summary

`test\win32\viewer-diff.ps1` section 9 (added by T817, 2026-09-17) fails its
`next-change walks off the end of a file into the next one (from 'staged.txt')`
assertion intermittently. Observed 2026-09-17 during the T818 turn: FAIL with
64 assertions passing, then ALL PASS (65 assertions) on an immediate re-run of
the same script against the same build, no rebuild between them.

## Details

The section drives real posted clicks at the nav bar and then reads the pane's
own log line for which file the selection landed on. The shape — post input,
sleep, read state — is the shape every such race has: the second file's listing
has to have been pushed and the selection re-anchored before the read, and
nothing in the assertion waits for that, it waits for a duration.

The fix is the one the rest of this harness uses: wait for the OBSERVABLE
(a listing line naming the next file) with a bounded poll, and fail on the
timeout with what it saw instead. `waitFor`-style helpers already exist in
`test\win32\lib\`.

Worth checking while in there: whether the neighbouring assertions in section 9
share the same fixed sleep and are merely luckier.

## Validation criteria

- [ ] Ten consecutive `test\win32\viewer-diff.ps1` runs, all ALL PASS
- [ ] The assertion fails LOUDLY and quickly when the walk genuinely does not
      happen (a negative control: break `adjacentFile` and watch it go red with
      a message naming what it saw)
