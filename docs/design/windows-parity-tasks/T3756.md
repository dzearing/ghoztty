# T3756 - Linux: the GTK pane sidebar takes pane drops - a pane header or a strip dragged onto the sidebar stashes it or places it in the list (Mac .stash / .sidebarOrder)

## Summary

Found in T3629. GTK's pane sidebar accepts only its own row drags (application/x-ghoztty-sidebar-row, PaneSidebar.dropRowAt); a pane drag (application/x-ghoztty-pane, from a rearrange header or a strip face) has no target there, so the stash-by-drag and sidebar-order drops Mac and win32 have (pane_drop .stash / .sidebar_order via the resolver's sidebarHit, T1844/T2303 on win32) do not exist on Linux. Give the sidebar a PaneDrag drop target, feed its list/tray rects into the resolver's Candidate (sidebar rects), and apply .stash and .sidebar_order through the existing GTK stash (T3596) and sidebar-order code. Acceptance: a cli-sidebar-drag.sh or cli-stash.sh section driving pane-drag (and pane-drag --blade) drops on the sidebar.

## In plain terms

On Linux you could drag a pane's own row around the pane sidebar, but
dragging the pane itself - by its header, its grab handle or its folded strip -
onto the sidebar did nothing. Now it does what it does on the Mac: let go in
the list, the pane takes that place in the list; let go in the "Stashed" tray,
it is tucked away there. A pane from another window works too: it moves into
this window first, keeping its running shell.

## Goals

- [x] the sidebar list takes pane drags (header, grab handle, strip) as well as its own rows
- [x] this window's pane: a place in the list, or stashed at a place in the tray
- [x] another window's (or tab's) pane: arrives on this grid's right edge, then placed in the list or stashed in the tray
- [x] in the all-windows outline, over another window's rows it joins that window
- [x] the tray lights while a held pane drag would stash

## Design note

Not through `pane_drop.resolve`'s sidebar rects, as the Summary first
suggested: on GTK the sidebar is its own widget, outside the split area the
resolver's Candidate is read from, and its row drop (T3607/T3698/T3699)
already applies `sidebarHit`'s exact rules (the tray-top split, the gap index
from the rows' middles, the join over another window's group) over the rows
as laid out. So the list carries a second drop target for the pane mime type
and `rows.paneDrop` plans the release: a pane drawn here is its row's drop, any
other pane arrives (`joinWindow`) and then takes its place (`moveRow` /
`stashRowAt`). One code path for rows and panes, so they cannot disagree. A
strip drag (`--blade`) shares the same target and code; the sidebar has no
blade-specific rule on Mac either (`resolveBlade` -> `sidebarHit`).
