# T2010 - acceptance-parallel run wedges with no workers left: four scripts started 11:34, two finished at 11:41 (logs end in their verdict), the runner never recorded them and sat idle 30+ min with no child processes

## Summary

Found in T2005 on 2026-10-16: a 103-script 'acceptance-parallel.ps1 run' (width 4) stopped emitting rows at 11:34. 81-session-reboot-tui.log ends 'ALL PASS (58)' at 11:35, 82-session-relaunch-notify.log ends '1 FAILURE(S)' at 11:41, 83/84 logs stop at 11:35; at 12:08 the runner pid had NO child processes and had written nothing for 34 min. The per-script timeout (1800s) never fired either. Likely the result-collection path waits on a job/handle that already exited. Repro: the same 103-script list (in T2005's log). Fix + a fixture that kills a worker mid-run and asserts the runner records it or times it out.

## In plain terms

The tool that runs the test suite four scripts at a time could freeze for good
partway through. The scripts kept finishing, but nobody wrote down their results,
and the run sat silent for half an hour until a person noticed. Now the runner
never waits on the part of Windows that froze, so a stall there can slow a run
down but can no longer stop it.

## Root cause

Not a lost process handle. The runner scores every job, and enforces every
per-script timeout, on one thread, and after each worker job it swept that
worker's leftover processes with `Get-CimInstance Win32_Process`, a WMI call with
no bound. The WMI-Activity log shows the CIMWin32 provider host (pid 82848, up
since 11:17) replaced by a new one (75932) at 11:41:07. The wedged run's own
timeline shows the stall building up first: groups of finished scripts were
scored 50-93 s after their last log line, all at the same instant (11:30:15,
11:34:16). After 11:35 the runner's sweep never returned. That is why no row
was written and the timeout never fired, and why the runner had no children (a
WMI query runs in WmiPrvSE, not under the caller). The scripts were caught too:
82-session-relaunch-notify, which counts processes through WMI, wrote its last
line at 11:41:09, two seconds after the new host started.

Fix: `Stop-ApWorkerProcess` lists processes with `Process.GetProcesses()` plus
`OpenProcess`/`QueryFullProcessImageName` (`Get-ApProcessesUnder`), which are
kernel calls that cannot wait on another process. No runner file calls WMI any
more, and section H of the harness keeps it that way. The scripts' own unbounded
WMI calls are filed as T2024.
