# T3581 - Pasting a file copied in Explorer (or from an image pane) into a terminal pane pastes nothing; Mac pastes the file's path

## Summary

Nothing in src/apprt/win32 reads CF_HDROP (grep, 2026-11-23), so a terminal paste of a clipboard that holds only files - Explorer's ctrl+C, and now an image pane's ctrl+C beside its picture (T1909) - pastes no text. Mac's terminal pastes a copied file URL as its path. Windows shape: when CF_UNICODETEXT is absent and CF_HDROP is present, paste the path(s), quoted per the pane's shell flavor, space-separated. Reader: image_clipboard.dropFilesPaths. Validation: unit tests for the quoting per flavor, plus an acceptance row that puts a CF_HDROP on the clipboard, pastes into a pane and reads the path back with +read.

## In plain terms

When you copy a file in Explorer (or press Ctrl+C on a picture in an image
pane) and paste into a terminal pane, nothing happens today. On the Mac the
file's path is pasted. After this, the path is pasted, in quotes when it has
a space, the same way dragging the file onto the pane already types it.

## Goals

- [x] A clipboard holding files and no text pastes the file paths.
- [x] Pasted and dragged files arrive in exactly the same form (one shared rule).
- [x] A picture copied with its file still goes to Claude Code as a picture, as before.

## Decision (mechanism, not filed)

The card asked for quoting "per the pane's shell flavor". The paste uses the
rule drag-and-drop already used instead - space-joined, double-quoted when a
path holds whitespace - now one pure function (`path_paste.zig`) both routes
call. Double quotes are the one quoting cmd, PowerShell and a Windows argv
parser all read as one argument, and a Windows path cannot contain `"`, so
nothing per-flavor is needed for those shells; keeping one rule means a
dragged file and a pasted one can never differ. Text on the clipboard still
wins over files (the card's shape; Mac prefers file URLs, but on Windows an
app that writes both formats meant its text, and Explorer never writes text).
The one shell where the Windows path itself is wrong is a WSL pane - filed
as T3660.
