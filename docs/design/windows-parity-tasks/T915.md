# T915 - Observe a real Google sign-in completing in a delivered Windows build

## Summary

**What is LEFT (rewritten 2026-09-20, after the work below landed):** one
consent click by the user, and one command. Everything else this task was
waiting on is done or was never actually blocked.

Both conditions the triage reason named are gone: the user's
`google-client-id.txt` is at the repo root and all three delivered locations
(the repo build, the Desktop portable and the user's installed release) bake the
same real id, and the relay at the baked default base is live with brokered
sign-in configured. And the part this seat was said to be unable to prove - "is
the credential the RIGHT credential" - turned out not to need consent at all:
Google's authorization endpoint validates a client id on an unauthenticated GET,
so `test\win32\relay-signin-live.ps1` now asks it every run. A dead, revoked or
wrong-application-type credential is refused there, which is the failure this
task existed to catch.

What genuinely needs a person is the consent screen: that is the user's Google
account, and a turn must not click it. So the script does not drive a browser -
it reads the result back with `-Observe` and closes the loop the one way that
cannot be faked by writing a file, by calling the real relay with the stored
token and requiring 200 where an anonymous call gets 401. See `unblock:`.

## In plain terms

Signing in to a remote machine needs a credential stamped into the terminal when
it is built, and until now nobody had ever checked that the one we ship is a
credential Google still recognises. If it had been deleted or created as the
wrong kind, every Windows build would offer a sign-in button that fails, and
nothing in the repo would have noticed until a user hit it. Now a test asks
Google directly, every time, and asks the sign-in server whether it is really
running - no account needed, nobody signed in. The last piece is the part only a
person can do: actually sign in once, so we have seen the whole thing work
end to end. That takes about a minute and the test records the result.

## Validation criteria

- [x] every delivered Windows build carries the same real baked client id -
      measured on the box by `test\win32\relay-signin-live.ps1` section A,
      reading `+version` from the repo build, the Desktop portable and the
      user's installed release: all three report
      `309808407086-...apps.googleusercontent.com`.
- [x] Google ACCEPTS that credential with the loopback redirect the app builds -
      section B. The exact URL `authorizationURL` (src\remote\google_oauth.zig)
      constructs gets a 302 to Google's `/v3/signin/identifier` page with no
      `error=`. This is the "is it the RIGHT credential" question T795 recorded
      as unanswerable from this seat.
- [x] and that check has been OBSERVED saying no, so it is a gate rather than a
      decoration - section C, every run: a never-issued client id is refused
      with `invalid_client`, and the real id asked for a non-loopback redirect
      is refused with `redirect_uri_mismatch` (the shape a Web-application
      client id would produce). `-NegativeControl` additionally inverts B and
      scores 1 FAILURE(S) at exit 1 - measured.
- [x] the relay a shipped build dials is a live BROKER - section D: the baked
      `default_base` answers, `POST /oauth/exchange` 400 (exists and validates
      its body), `/oauth/renew` 401, `GET /v1/client/devices` 401, and a
      nonsense path still 404s so those codes are the routes answering rather
      than a catch-all.
- [x] a green run stamps the covered files so an edit to the URL builder or the
      default relay base re-opens the question - guard row `relay-signin-live`
      in `scripts\guard-due.ps1`, ADVISORY because the subject is the network
      and a third party, so an offline box can never refuse a commit.
      `guard-due.ps1 check` reports `GUARD CURRENT relay-signin-live`.
- [x] the standing floor - `scripts\floor-lane.ps1 -Lane all` and
      `-Lane harness`.
- [x] the `-Observe` path is EXERCISED rather than shipped unrun - measured
      against a seeded store under `GHOSTTY_ACCOUNT_STORE` (the product's own
      override, so the script resolves the path the way `relay_account.zig`
      does): E1-E5 pass, and E6 scores the fabricated token RED with the real
      relay answering 401. That is also the demonstration that E6 cannot be
      satisfied by writing a file - only a token the relay actually minted gets
      200 - and no receipt was written, because the store was an override.
- [ ] **the observation itself**: a real sign-in completing in a delivered
      build, asserted by `relay-signin-live.ps1 -Observe` (E1-E6, ending in the
      real relay honouring the minted token with 200 where D5 got 401) and
      recorded in `test\win32\relay-signin-live.observed.json`. Needs the user's
      consent click - see `unblock:`.
