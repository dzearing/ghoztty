# T2184 - +split --name silently exits 0 when the name belongs to a different pane: report a reuse, fail a mismatch, name where a new pane went (main c2057a810)

## Summary

Mac c2057a810 (SplitNameCollision.swift): a +split --name whose name is held by a matching pane (terminal again, or a viewer showing/opened with that --view) is reused and stdout says so and names its window; a non-matching holder (another --view, kind mismatch, or a WINDOW of that name) fails exit 1 naming the pane, its window and what it shows; a created pane prints where it went; a --target naming nothing fails instead of exiting 0. The line rides a new additive 'message' field on the IPC response that src/cli/split.zig prints (shared core, arrives with the next origin/main merge). Windows today: IpcHandlers.handleSplit (src/apprt/win32/IpcHandlers.zig:842) returns bare {success:true} for ANY live pane under the name and falls through on a window name - exactly the silent no-op the Mac fixed. Port the pure policy as a tested Zig module, emit 'message', and cover it in an acceptance script.
