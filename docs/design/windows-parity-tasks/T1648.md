# T1648 - The idle soak daemon's leak sweep kills a turn's own test binary, so any lane a turn runs can go red with a bare exit 255

## In plain terms

A background job that uses the machine's idle time to hunt a rare crash has
started killing the work the main job is doing. When it happens, the main job's
tests report a failure that looks exactly like broken code — no crash message,
no explanation, just a dead test — so whoever is watching spends the next hour
debugging a change that was never wrong. It has already happened twice in the
twenty minutes after the background job was switched on.

## Goals

- [ ] A soak round can never reap a process it did not start
- [ ] The soak's yield path is proven not to touch a concurrently running lane
- [ ] A negative control demonstrates the new scoping actually refuses the kill

## Summary

T841's soak daemon runs floor lanes in the box's idle time. Every lane run ends
with `Invoke-LaneLeakSweep`, which reaps "leaked" test binaries — and its notion
of a leak is *a process carrying one of the lane's test-binary names that was
not running when this lane started*. `scripts\lib\LaneLeak.ps1` says so in its
own header, and names the one case the rule cannot separate:

> The one case this cannot separate is a SECOND floor run overlapping this one,
> which the house rules already forbid (go.md step 3: lanes and acceptance
> scripts run sequentially, never overlapped).

**That premise stopped being true when T841 landed.** The soak daemon overlaps a
turn by design — it exists to use the idle time *while a turn is running* — so
the one case the sweep admits it cannot handle is now scheduled to happen every
few minutes.

The name list makes it worse than lane-vs-same-lane. `TEST_EXE_NAMES` is seeded
from `$script:CRASHDIAG_TEST_EXES` (`scripts\lib\CrashDiag.ps1:61`), which is
**`ghostty-test.exe` + `ghoztty-agent-test.exe` for every lane**. So a soak
**agent** round sweeps up a turn's **none**-lane `ghostty-test.exe`.

### Measured, twice, 2026-09-18 (T842's turn)

Two `zig build test -Dapp-runtime=none` runs died at
`error: while executing test 'font.Collection.test.add full', the following
command exited with code 255` — no handler text, no `Segmentation fault`, no
CrashDiag block, 5405/5423 other tests passing. Both were killed in the same
second a soak round yielded:

| repro attempt | test binary killed at | soak ledger row |
|---|---|---|
| `a2` | `.dumps\lane-leak-62768-20260918-004904.log` | `00:49:07 agent yielded 39s  foreground work: pid 47980 zig.exe build` |
| `a3` | `.dumps\lane-leak-60820-20260918-005353.log` | `00:53:57 agent yielded 57s  foreground work: pid 52636 zig.exe build` |

Each dump's own path-validation line names the victim, and it is the repro's
private cache, not the soak's:

```
OK   D:\zgc-t842\a2-c\o\c2924f9888012ad139432df4b9642245
OK   D:\zgc-t842\a3-c\o\f0049928ae834aa6e1d0b41154470c67
```

So the sweep took a non-invasive `cdb` stack of a healthy, running test binary
belonging to somebody else and then killed it. Exit 255 with nothing printed is
the signature of exactly that, which is the same reading the 2026-09-07 data
point in T443 arrived at for the lane's own binary.

### Why this is P0

While it stands, **no red lane on this box is evidence**. A turn that runs the
floor and sees a lane die in `font.Collection.test.add full` cannot tell a real
regression from the soak reaping its binary — and the failure wears the costume
of T443, the P0 crash hunt, so it will be mis-filed as a data point in the very
investigation the soak daemon was built to feed. That is the failure mode with
teeth: the instrument manufacturing its own signal.

It also breaks T841's own stated non-negotiable, quoted from
`scripts\soak-daemon.ps1`:

> IT MUST NEVER BE THE THING THAT WEDGES A TURN.

The YIELD mechanism it relies on does not help here. Yield fires on the way
*out* of a round, and the sweep runs after the lane reports — so yielding is
precisely when the kill happens, not something that prevents it.

## The daemon is PAUSED until this lands — do not resume it

Paused 2026-09-18 00:57 with

```
powershell -NoProfile -File scripts\soak-daemon.ps1 pause ^
    -Reason "T842 measurement needs the box quiet; T1648 filed for the cross-kill"
```

and it should stay that way until the fix here is green. This is not tidiness:
while it runs, a turn cannot tell a real regression from a reaped binary, so
every lane result the loop produces is uninterpretable — and the daemon exists to
feed T443, which is the one investigation that a manufactured signal would
corrupt worst. `soak-daemon.ps1 resume` is the last step of fixing this, not
something to do first.

With it paused, this turn's floor was clean: all four lanes PASS, P1/P2/P3
ALL PASS, `leaked test binaries: 0` on every lane.

## Details

Where to fix it, in preference order:

1. **Scope the sweep to the round's own tree**, not to a name plus a
   before/after baseline. The soak already marks every descendant it spawns
   (`soak-daemon.ps1`'s marker appears in child arguments and in the zig cache
   paths underneath its scratch dir — that is how the yield rule avoids
   mistaking itself for a turn). The sweep should use the same marker: a
   candidate whose command line or image path does not sit under this round's
   scratch directory is not this round's leak, whatever its name.
2. **Make the baseline rule honest about overlap.** `Get-LeakedLaneProcess`'s
   "was not running when this lane started" test should additionally require the
   candidate's image path to live under *this* run's cache/prefix. Two builds on
   one box produce test binaries at different `o\<hash>` paths, so this
   separates them exactly.
3. **Have the soak pass `-NoLeakSweep`** (or run its lanes with the sweep
   disabled) as an interim guard, since a soak round's leaks are its own problem
   and it can reap them from its process tree on the way out.

Related: **T1432** is the other half and stays separate — it makes a
sweep-killed binary *diagnosable* (today it reads as a bare red lane). This task
stops the wrong binary being killed at all. Fixing either alone leaves the
other's symptom.

## Validation criteria

- [ ] A negative control reproduces the cross-kill against the CURRENT code: a

- [ ] After the fix, the same control leaves that binary alive and the lane
