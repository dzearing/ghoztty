# T3223 - Swapping a 12 MP TIFF into an open image pane still raises the app's peak private bytes by ~459 MB and blocks the GUI thread ~110 ms, identically before and after T3043's decode fix - find what else spikes

## Summary

Measured 2026-11-17 (T3043) with scratch script t3043-measure.ps1 logic: test desktop, --macos-window-mode=separate, a 64x64 TIFF open in a viewer, then a 4000x3000 LZW TIFF copied over it so the watcher reloads. HEAD 389d8f7ad and T3043 both: private before 270 MB, PeakPagefileUsage after 730 MB (+459 MB, identical to the MB across two runs each), worst WM_NULL round trip 146/147 ms before vs 107/119 ms after. T3043 removed ~4 x 48 MB of copies and moved the 100 ms decode to a worker (decode_ms=104 parked=true), so the dominant spike and the remaining ~110 ms GUI block are elsewhere on the reload/serve path - suspects: the reload render, the pane sidebar tile, the WebView2 response stream hand-off, or the image page's message traffic. Profile one reload (ETW VirtualAlloc stacks / heap snapshot) and fix the largest. Carries T3043's two perf validation criteria (>=100 MB peak drop, GUI responsive during load).

## In plain terms

A big picture in an image pane briefly used ~460 MB of extra memory and froze
the window for ~0.1 s even after T3043 made the decode cheap. This task found
out why. The cost is in how the embedded browser takes a big response from
the app, not in the decode, so it hits every large picture. The fix is T3241.
