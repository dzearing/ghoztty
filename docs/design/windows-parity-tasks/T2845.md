# T2845 - A fold glide's slowest frame is one EndDeferWindowPos of 20-48 ms (4-7 a probe run) that is not our code, not the fold capture, not the viewer and not the box: suspect the per-pane DirectComposition target on each terminal's child window, which keeps a 60 Hz glide from ever reading late=0

## In plain terms

A few times in every divider drag that folds panes away, a single frame of
the glide takes 20 to 48 ms instead of about 3, so the glide visibly hitches
once or twice per drag even on a 60 Hz screen. All of that time is Windows
moving our pane windows, and the usual suspects have been ruled out one by
one; what is left points at how each terminal pane hands its picture to the
compositor.

## Summary

Split from T2732 (2026-11-08 night, lane b). Release sandbox, 120 Hz, the
T2732 glide probe (5 panes in a row, a viewer, the first divider dragged 720
DIP out and back twice, 1875x1125 @1.25 on the background test desktop).

- **What it is.** The run's worst tick is always `owner=tick` with
  `place_us` 20-48 ms, and the ring trace puts all of it in the live pass's
  pane batch: `EndDeferWindowPos` itself (batch begin -> `defer_end`), on
  4-7 batches of ~1300 a run, 19-31 ms each. Every other batch takes 0.5-5
  ms.
- **Not our code.** A temporary wrapper timing every message the terminal
  and viewer pane window procedures handle inside the batch: in a 28.5 ms
  batch they spent **0.15 ms** in total (14 messages). The time is the OS's.
- **Not the fold's frame capture** (the renderer's synchronous
  `glReadPixels` readback for the carried card). With the capture switched
  off by a temporary knob, alternating A/B x3: worst tick 26.8 / 16.0 / 28.3
  ms against 26.6 / 32.8 / 32.4 with it, `late` unchanged.
- **Not the box or DWM in general.** An independent WinForms process
  moving and resizing 5 child panels with `Begin/EndDeferWindowPos` every 8
  ms on the same test desktop, DURING the glide: max 2.6 / 3.4 ms over ~760
  batches, never over 12 ms, while ghoztty's batches in the same runs
  stalled 34 and 48 ms. Idle (no glide), the same bench maxes 1.5 ms.
- **Not the viewer's WebView2** (a cross-process child window). The same
  row with five terminals and no viewer, x3: worst tick 40.4 / 44.1 / 34.0
  ms.
- **No layout feature marks the slow batches.** Diffing each pass against
  the one before (z-order change, show/hide, tuck, card or rect size, face,
  carry): the slow ones change nothing that hundreds of fast ones do not.
- `GHOZTTY_COMP_PRESENT=0` (SwapBuffers on each pane's own window) is far
  worse overall (`late` 640-810, mean tick 9-14 ms), so it cannot isolate
  the cause.

What is left, by elimination: each terminal pane presents through a
DirectComposition target on its OWN child window (`gl_comp_present`, T2466),
created on the renderer thread's device. Moving a window that carries a
composition target from another thread's device appears to wait on that
target's outstanding commit or present. That fits T2788's earlier finding
that a batch is slow when a moved pane's frame is still in flight, at a
larger scale.

Directions:

1. Prove it: build with a stamp of which pane's move is slow (split the
   batch per window, or `SetWindowPos` the panes one at a time under a
   trace knob), then check the slow pane's present/commit state at that
   moment.
2. The structural fix already exists behind a knob: `GHOZTTY_COMP_PANE_TREE`
   (T2553) makes each pane's swap chain a visual in the top-level window's
   own tree, so the child window carries no composition target and is moved
   for input only. It needs `GHOZTTY_COMP_CHROME`, which is 3x slower on this
   probe today (**T2843**). Measure PANE_TREE's batch on its own once T2843
   moves.

Probe and instrumentation: `glide-probe.ps1`, `glide-probe-nov.ps1` (no
viewer), `glide-probe-mb.ps1` + `movebench.cs` (the independent-process
bench), `diffp.py` and `t2732tmp-instrument.patch` (the window-procedure
timer, reverted) in session eac5b6eb's scratchpad.
