# T2028 - A pane's banner and overlays are placed AFTER its layout batch, not inside it: a divider drag can show a banner one frame off its pane (T2012 criterion 2)

## In plain terms

When you drag the line between two panes, a pane's status banner should move
and resize in the same frame as the pane, never trailing it. On the normal
drawing path the banner is now drawn as part of the pane itself, so it cannot
trail; this task proves that with a sampled drag instead of assuming it.

## Goals

- [x] Find out whether the banner can still lag its pane during a divider drag on the default drawing path
- [x] Prove the answer with a sampled drag, and show the check can fail
- [x] Record why the fallback (popup) path cannot join the panes' batch

## Summary

T2012 made a pane's popups hide with it; they were still re-glued by
updatePaneBanners/updateDimOverlays after the pane's DeferWindowPos batch
ended, so a resize could show them a frame behind. Fold the overlay placement
into the same batch, or prove with a sampled drag that it never lags.

**Re-verified 2026-11-23: partly overtaken.** Since T2559 (banner as a child
visual of the pane's composition tree) and T2514 (composition present on by
default), the banner on the DEFAULT path is not a popup at all: the pane's
own window carries and clips it, so a pane move cannot leave it behind, and a
width change re-renders it in the same layout pass. What is LEFT is the proof
(this task) and the popup fallback (no GL/D3D interop: WARP, Mesa, Remote
Desktop), where joining the panes' batch is not possible:

- `DeferWindowPos` requires every window in one batch to share a parent; the
  panes are children of the frame, the popups are top-level (owned) windows.
- A RESIZED banner popup is presented with `UpdateLayeredWindow` at its new
  size (T2400, to avoid a black frame), which cannot be deferred at all.

So the fallback stays "re-glued synchronously in the same UI-thread pass",
which banner-resize-repaint.ps1 sections B/C sample at every drag step.
Decision (mechanism, Claude's call per go.md 5b): no further work on the
popup fallback here; the one-chrome-window direction is T1350.
