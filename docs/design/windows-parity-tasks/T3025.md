# T3025 - PA-I11: a CLI client that stops mid-request parks an IPC listener forever; four of them and the app answers no running instance (ipc_client.zig:147)

## Summary

PA-I11 (audit-1, T2962). src/os/ipc_client.zig:147 `if (!self.owned) return windows.ReadFile(self.handle, buffer, null);` is the server side's read (IpcServer.serveOne :427, :442), synchronous with no timeout; writeFramed (:542) blocks the same way if the client stops reading a reply over the 64 KiB pipe buffer. There are 4 listener instances (IpcServer.zig:48). Cost: each stalled or killed-mid-write client holds one listener; four and the CLI reports 'No running Ghoztty instance found' until restart, and deinit (:298) cannot wake a thread stuck in ReadFile. Fix: create server instances FILE_FLAG_OVERLAPPED and bound reads/writes with the existing overlappedIo path. Risk low-medium. Findings: docs/design/perf-audit/audit-1/I-findings.md.

## Validation criteria

- [ ] an acceptance script opens 5 raw pipe clients that send a partial frame and stall; a real +list still answers within the IPC timeout
- [ ] app exit with a stalled client completes (no hang in deinit)
