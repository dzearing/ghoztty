# T2321 - After a failed install the applier never exits and locks every later update

## Summary

User report 2026-10-26: "i click install and restart. NOTHING HAPPENS". Part
two of the chain (T2320 caused the failed install; T2322 is the silence).

Evidence (`%LOCALAPPDATA%\ghoztty\ghoztty.log`):

- 2026-10-26T03:36:02Z app 48324 ARMED applier pid 18088 for 1.45.3.
- 03:36:11Z applier 18088: `msiexec exited 1603; relaunching the build that
  was already here` -> relaunched pid 35516 -> `Ghoztty could not finish
  updating...`. **And then 18088 never exited**: it was still alive on
  2026-10-27 04:4x (26 hours later), image
  `%LOCALAPPDATA%\ghoztty\updates\ghoztty-updater.exe`.
- Every later arm in 35516 (06:06, 18:46, the 01:58 auto-install, and the
  user's two clicks at 04:40/04:41Z) logged `update apply: NOT armed
  err=error.AccessDenied`: `armImpl` (`update_install.zig` ~380) does
  `deleteFile(applier) catch {}` then `copyFileAbsolute(exe, applier)`, and the
  copy over the running image is refused.

Unblocked by hand on 2026-10-26 21:4x local: Stop-Process on 18088 by exact
ExecutablePath.

## Fix direction

1. Find why the applier stays alive after the relaunch-on-failure path in
   `update_install.run` (a full app init? a wait on the relaunched child? a
   message loop?) - it must return and exit on every path.
2. Make arming robust to a live leftover anyway: copy to a unique name
   (`ghoztty-updater-<pid>.exe`) or detect a live applier, and let sweep()
   clean the old ones.

## In plain terms

When an update failed to install, the small helper that runs the install
put up an error box and then waited for someone to click it. Nobody saw the
box, so the helper never went away - and while it was still running, every
later "Install and Restart" click quietly did nothing. Now the helper always
leaves (the box closes itself after ten minutes), and even if an old helper
is somehow still around, the next update uses a fresh copy and goes ahead.

## Goals

- [x] the applier exits on every path, including an unanswered failure dialog
- [x] a leftover applier still running cannot block the next Install Update

## Root cause

`update_install.run` relaunches the app and then calls `report()`, a modal
`ConfirmDialog.showStandalone` with no timeout. The log line
`Ghoztty could not finish updating...` at 03:36:11.278 is `report()`'s own
log just before the modal; the dialog was never dismissed (T2322 is why
nobody saw it), so pid 18088 sat in the modal loop for 26 hours.

## Validation criteria

- [x] acceptance: force msiexec to fail and assert the applier process exits
      on its own after relaunching the app - `update-failure-visible.ps1`
      section F (1603 via the Debug code seam, report timeout shortened to 4 s
      via `GHOZTTY_UPDATE_REPORT_TIMEOUT_MS`; dialog seen, applier exits with
      it unanswered, log says it timed out, relaunch still first; A9/A10 are
      the control that without the seam the dialog persists). 35/35 ALL PASS.
- [x] acceptance: with a leftover applier RUNNING from
      `ghoztty-updater.exe`, Install Update still arms - `update-auto-apply.ps1`
      section I (a real copy of the build parked as an applier on a live pid;
      the app's idle install arms `ghoztty-updater-<pid>.exe`, exits, and is
      reopened). The positive control is in-run: the log line
      `ghoztty-updater.exe could not be replaced (...)` proves the usual path
      was blocked, which is exactly where the old code returned
      `NOT armed err=error.AccessDenied`. 39/39 ALL PASS.
- [x] unit: `applierName` (usual vs per-pid, never prunable) and the
      timeout bound, in `update_apply.zig` (none lane).
