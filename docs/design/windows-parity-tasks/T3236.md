# T3236 - Every ~113-byte ConPTY line crosses the holder, daemon and app as its own message (~23,800/s in a flood); the per-message kernel wait/wake and I/O is ~90% of the agent family's CPU - coalesce at the holder's ConPTY read and measure CPU, not throughput

## Summary

Profiled in T3159 (scripts\cpu-sample.ps1 via perf-baseline.ps1 -Build Release -Phase busy -BusyPersistence -SampleAgent, on-CPU mode): of the agent family's ~15-20 s over a 64 MB ascii flood, the agent's own code (VT parse, ring append, snapshot) is ~3%. The rest is kernel time paid once per MESSAGE, and the flood arrives as ~23,800 messages/s of ~113 bytes (one ConPTY line each, agent_feed slices_per_s) through every hop. Holder (7.2 s): ConPTY ReadFile 3.5 s, pipe WriteFile 1.5 s, condvar handoff reader->writer 1.5 s, per-op CreateEvent/CloseHandle 0.6 s. Daemon (8.1 s): serverRead's blocking overlapped wait 3.6 s, the bridge writer's condvar wake 3.5 s, WriteFile to the app 0.25 s. Fix: cut the message count at the SOURCE (src/remote/agent/pty_host.zig) so every hop downstream gets fewer, bigger messages - e.g. when a ConPTY read comes back small and the last one was under a millisecond ago (a flood, not typing), let the next read wait briefly so conhost's pipe buffer fills (~2.6 KB/ms at this rate), with keystroke echo kept immediate. NOTE pty_host.zig:182: T1464 measured a 1 ms writer-side coalescing wait and rejected it because THROUGHPUT did not move (the ConPTY read rate is the ceiling). This is a CPU fix, not a throughput fix: measure agent_cpu_s and the busy wall (must not regress) and echo latency, and update that comment with the CPU number. Shared agent code: the Mac half measures its own relay (see the T3159 mac follow-up).

## In plain terms

When a program in a saved (persistent) session prints a lot of output fast,
the background session process was passing it along one line at a time,
paying a fixed cost for every line. Now it waits a fraction of a millisecond
during a flood and passes the output along in larger batches, so the same
output costs noticeably less CPU. Typing still echoes immediately.

## Goals

- [x] The holder's ConPTY reader batches a flood instead of forwarding each conhost line
- [x] A keystroke echo after a pause is never delayed (the policy only waits when the read barely blocked)
- [x] Agent CPU measured A/B over the busy flood, wall time held

## Re-verification (2026-11-19)

Partly fixed since filing: the app-side `agent_feed` no longer shows 23,800
slices/s of 113 bytes - it reads ~3,580/s of ~900 bytes on both sides of
this A/B (the daemon→app leg already batches). What was left was the
holder's ConPTY read → holder → daemon leg, still one message per conhost
write (180 bytes per sink delivery measured below). That is what this fixes.

## Fix

`PtyChild.readerLoop` (src/remote/agent/pty_child.zig) now applies the T3060
`termio/read_coalesce.zig` policy the local pane reader already uses: when
the blocking ConPTY `ReadFile` returned in under 2 ms (a stream, not a
keystroke), it waits on a high-resolution waitable timer in two 0.5 ms
slices, draining whatever conhost wrote meanwhile (PeekNamedPipe + ReadFile),
up to 16 KiB. No timer, or any peek/read failure, delivers what is in hand.
The `pty_host.zig` T1464 comment now records the CPU number.

**Batch cap (found by `test\win32\pty-host.ps1`).** The first version made
the smoke's unreleased-drop scenario red (A18 "owner saw no gap", plus the
smoke verdict A1/A2): that scenario runs the holder with a 4 KiB replay ring,
and a 16 KiB batch appended whole overwrote its own head before the writer
could take it. `PtyChild.max_batch` now bounds every delivery - the blocking
read included, since after a wait conhost can have more than a batch pending -
and the holder sets it to `replay_bytes / 16` (floor 256). The 1 MiB default
ring keeps the full 16 KiB. A/B against a debug agent with the coalescing
short-circuited: base ALL PASS (28); fixed build 3 of 3 runs ALL PASS (28).
An earlier C0/C1 red (idle holder got SHUTDOWN within 3 s) and the
session-shell-exit red coincided with another worktree's debug agent
(`D:\git\ghoztty-t3239`) owning the shared debug agent pipe; both were green
once it was gone.
