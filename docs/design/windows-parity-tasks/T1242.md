# T1242 - Drive the update balloon click and the Install-and-Restart dialog, so the consent path is tested too

## Summary

Re-verified 2026-10-23 as PARTLY covered: `update-progress.ps1` (T1195)
already posts the balloon click and OKs the dialog, but only on the
`auto-update = check` path and by posting `IDOK` - so the default staged path
(click -> dialog -> `applyStagedUpdate` -> arm), the dialog's wording and
button labels, and "Later" were never driven. That gap is what landed.

New harness `test\win32\update-consent.ps1`, entirely off the user's screen:
the app runs on the background test desktop out of an `ApplierSandbox` copy
of the build, the balloon click is the shell's tray callback posted into the
message-only window, the dialog's buttons are BM_CLICKed by their labels, and
`GHOZTTY_UPDATE_MSI_CODE=0` (the Debug-only seam) stands in for msiexec, so
nothing installs and no failure dialog is raised. `-NegativeControl` presses
"Later" where the consent belongs and goes red. New guard-due row
`update-consent` (update_install, tray_notify, ConfirmDialog, the script and
`ApplierSandbox.ps1`).

The issue text's "needs real input on a real desktop" was not taken: real
input would pull focus (go.md forbids it), and the posted callback proves the
handler and everything after it - the same T240 caveat `update-progress.ps1`
and `notification-click-focus.ps1` carry.

## Validation criteria

- [x] A staged update installs nothing and shows no dialog until clicked - `update-consent.ps1` section A (Debug build, auto-apply not opted in).
- [x] The click raises "Update Ghoztty", naming the offered version, saying the terminal closes and sessions are kept, with "Install and Restart" / "Later" - section B, read from the dialog's own STATIC/BUTTON controls.
- [x] "Later" closes it, logs a deferral, arms nothing, leaves the app up and the package staged - section C.
- [x] A second click offers again; "Install and Restart" arms the applier, the app quits, the applier consumes the package and reopens the terminal from the install dir - section D.
- [x] The repo build is untouched and nothing reached the interactive desktop - section E + the foreground watch.
- [x] `-NegativeControl` goes red (5 failures, exit 1).
- [x] Full run: ALL PASS (32 assertions), stamped `update-consent`.

## Goals

- [x] drive the click and both dialog answers on the default (staged) path
- [x] prove "Later" is a refusal and "Install and Restart" is the only consent
- [x] keep it off the user's desktop and away from the repo build

## In plain terms

When Ghoztty finds a new version it shows a notification; clicking it asks
"Install and Restart?" and only then does the update actually run. Everything
after that question is now tested against a real published release (T1194),
and everything before it is tested against a canned one (T1178) - but the two
clicks in the middle have never been driven by a test. If that button stopped
working, nothing would notice until somebody tried to update by hand.

## Details

`App.zig`'s `offerUpdate` is reached from a tray-balloon click and puts up
Ghoztty's own `ConfirmDialog`; `applyStagedUpdate` runs only on OK. A test for
it needs to click a shell tray balloon and then a dialog button, which is real
input on a real desktop - so it belongs with the other input-driven harnesses
rather than in the background-desktop suite (see
`test\win32\lib\TestDesktop.ps1` and the interactive-by-design exceptions).

Worth pairing with T1194's harness: that one already gets a real package
staged and a real product installed, so the consent path could be driven
there instead of `arm()` being simulated.
