# T2449 - A grid pane dropped on another window's tile in the collapsed all-windows rail joins that window (Mac 9e2e2902a); today the Windows rail of window tiles reads as the stash tray only

## Summary

Split from T2445. Mac 9e2e2902a: "A grid pane dropped on a tile still joins that window." T2445 made the collapsed all-windows rail one tile per window, and `PaneSidebar.dropGeometry` now presents that rail as the tray alone (`Layout.windowTiles`: no list rows, no stash rows), so a pane dropped anywhere on it stashes into the sidebar's OWN window. Windows' pane-drop model resolves a sidebar only for its own window (`pane_drop.sidebarHit` -> `.sidebar_order` / `.stash` on `c.window`), so a tile that stands for ANOTHER window needs a new target: per-tile rects in `DropGeometry` carrying the tile's window, and a `pane_drop` target that moves the dragged pane into that window (the cross-window move the expanded list already does through the target window's own sidebar).

Where: `src/apprt/win32/PaneSidebar.zig` (`dropGeometry`, `tileGroup`), `src/apprt/win32/pane_drop.zig` (`sidebarHit`), acceptance in `test/win32/pane-sidebar-all-windows.ps1` section 7.

## In plain terms

With the sidebar collapsed to its narrow rail and showing all windows, each window is one small tile. Dragging a pane onto another window's tile did nothing useful: the pane just got tucked away in this window's stash. Now the tile you are over lights up with an accent ring, and letting go moves the pane, still running, into that window, the same as on Mac.

## Goals

- [x] A pane dropped on another window's tile moves into that window (its grid, on the right)
- [x] The tile it would join lights with an accent ring while it is the target, and only then
- [x] This window's own tile, and the rest of the rail, keep stashing as before

## Design

Mac's `.joinWindow` target, ported: `pane_drop.Target.join_window` (window, tab key, host sidebar, tile rect) and `Candidate.window_tiles`; `sidebarHit` checks tiles that stand for OTHER window tabs first (Mac: `group.window != candidate.window`), so this window's own tile falls through to the tray exactly as Mac's does. `PaneSidebar.dropGeometry` lists those tiles for a rail of windows (own tile left out). A Windows sidebar group is a window TAB (Mac's tab is a window), so the target carries the tab's key; the commit (`Window.commitJoinDrop`) brings that tab up and makes Mac's move - `insertAtTopLevel(side: .right)` - through the existing cross-window / cross-tab paths. Joining the tab the pane is already in is no move (Mac `allows(.joinWindow)` false), so it neither lights nor commits. The ring is the tile's own (Mac `isDropTarget`, 2pt accent stroke), like the empty tray's T2358 light: `drop_highlight.forTarget` answers null for it. The tile's window is looked up among all windows (`App.windowByDropRef`), not the drop candidates, so a minimized window still joins.

Note on criterion 2 as first filed ("own tile stays put"): Mac's resolver gives a drop on the sidebar's own window tile to the tray, so it stashes there; "no move" is the case of the dragged pane's OWN tab's tile. Both are implemented as Mac has them.
