# T2766 - Composition step 5d-6: the quick terminal's slide in/out runs on the compositor instead of a SetWindowPos of its top-level window per ANIM_TIMER_ID tick - decide between animating the window's root visual offset inside a fixed window rect and keeping a DWM-driven move

## Summary

QuickTerminal.zig moves a top-level HWND per FrameClock tick; DirectComposition cannot move a top-level window, so the slide has to become a visual offset/clip within a window already at its final rect (input stays off until it lands). Oracle: film with stall seam and stepped control.

## In plain terms

The quick terminal (the drop-down terminal on a hotkey) slides in from the
screen edge. It used to be moved a step at a time by the app's main thread,
so whenever the app was busy the slide stuck halfway and then jumped. Now
Windows' own compositor carries the slide on a helper thread: it keeps
moving smoothly through a busy moment, it shows the live terminal while it
moves, and the terminal only starts taking keys once it has landed.

## Decision (mechanism - this seat's call, go.md 5b)

The task offered two shapes. **Animating the window's root visual offset
inside a fixed window rect is not viable today**: every terminal pane presents
through its OWN DirectComposition target on its own child window
(`renderer/gl_comp_present.zig`), so an offset on the top-level's tree would
move the chrome layer and leave the panes behind. It needs the panes' visuals
on the window's tree first (the T2516 line).

Chosen: **a DWM-driven slide off the UI thread.**

- The quick terminal sits at its FINAL rect, cloaked (`DWMWA_CLOAK`: DWM
  still composes it, it is not drawn and takes no input).
- A slider thread (`QuickTerminalSlider.zig`) owns a host window
  (`GhozttyQuickSlide`: topmost, non-activating, click-through, no
  redirection bitmap) over the travel area clipped to the monitor, holding a
  live DWM thumbnail of the quick terminal.
- Each composition (`DwmFlush`) the thread moves the thumbnail to where the
  window would be on the same ease as before
  (`quick_terminal_slide.slideRect`). Nothing per frame goes through the UI
  thread.
- In: the UI thread uncloaks on the slider's answer, then the slider takes
  the host down after one composition. Out: the slider cloaks the window
  once its thumbnail is up, and the UI hides it on the answer.
- A toggle mid-slide re-declares it with a new generation, so a stale answer
  is dropped. Any failure (host, thumbnail, cloak) steps the rest on the
  frame clock from the same start; three failures and it stops asking.
  `GHOZTTY_COMP_PRESENT=0` and `GHOZTTY_DEBUG_QT_SLIDE_STEPPED=1` keep the
  stepped path; `GHOZTTY_DEBUG_QT_SLIDE_STALL_MS` is the stall seam.

Side effect, deliberate: the slide no longer overhangs onto a neighbouring
monitor (the host is clipped to `rcMonitor`; the stepped window simply hung
over the edge).

  stepped lerp reproduced at every frame, host clip incl. bottom/centred/
  negative-coordinate monitors, reversal continuity to 1e-9, the packed
  45-byte `DWM_THUMBNAIL_PROPERTIES` at dwmapi.h's offsets) - `zig test`
  alone and in the `none` lane.
- [x] under a 900 ms UI stall a 300 ms slide lands in ~300 ms measured on
  the slider thread (306 ms, 36 frames) - `test\win32\quick-terminal-slide.ps1`
  [dwm], 47/47 green; `-NegativeControl` red on that row (324 ms vs 900).
- [x] landed in: shown at the work-area top, `DWMWA_CLOAKED=0`, host down;
  landed out: hidden, uncloaked, host down - same harness.
- [x] mid-slide the host is up and the window cloaked (=1); a second toggle
  turns it round (`reversed dir=out`) and only the out slide lands - [reverse].
- [x] stepped arm: no slide handed over, no host window, same landing place -
  [stepped].
- [x] the host lives on the app's desktop, never the interactive one - a
  probe enumerated both desktops mid-slide.
