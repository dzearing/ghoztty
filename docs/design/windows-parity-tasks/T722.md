# T722 - The install-unlock guard covers only the default Windows install steps, not the auxiliary test exes

## In plain terms

A rebuild no longer breaks when Ghoztty's background helper is still running.
The same protection has not been extended to a handful of small programs only
developers build by name, so those can still stop a rebuild with a confusing
error. Nobody using Ghoztty is affected; it is a paper cut for whoever is
working on it.

## Summary

T192 wired `InstallUnlock` (`src/build/install_unlock_main.zig`) ahead of the
install steps in build.zig's `config.emit_exe` + Windows branch — `ghoztty.exe`,
`ghoztty.com`, `ghoztty-agent.exe`, `ghoztty-agent-ca.dll`. The auxiliary exes
that also install into `zig-out\bin` are NOT guarded:

- `remote-test-client.exe` (`zig build remote-test-client`) — the one most
  likely to be caught, because acceptance scripts run it with `--hold=<n>` and
  `agent-pipe.ps1` explicitly kills lingerers, so a lingering one is a state the
  suite already expects;
- `ghoztty-conpty-smoke-x86_64.exe` (`zig build conpty-smoke`);
- the WP4 e2e harnesses (`zig build wp4-e2e`, `remote-backend-e2e`);
- the bench exes, if they are ever installed on Windows.

Each is its own named step, so the trap only fires for a developer who builds
that step by name while an instance of it is still up — which is why this is P2
and not part of T192.

## Details

The wiring is three lines per artifact and the helper is already generic
(`guardArtifact` takes any `*Step.InstallArtifact`). The open question is
whether to keep creating one `InstallUnlock` per branch or hoist a single one
into build.zig for every Windows install step, which would also cover anything
added later by default. Prefer the latter: T192's failure mode was precisely a
guard that covered some artifacts and not the one that mattered.

## Validation criteria

- [x] every Windows install step in build.zig routes through `InstallUnlock` —
      one hoisted instance guards the app, its `.com` twin and fallback GL, the
      agent and its CA dll, `remote-test-client`, `wp4-e2e`,
      `remote-backend-e2e`, `conpty-smoke`, the `-Demit-test-exe` binary, the
      bench tools and the libghostty dll. Installed DATA (terminfo, shell
      integration, themes, docs, headers) is deliberately not guarded: a
      running process holds its image open, not the files beside it.
- [x] an arm in `test\win32\build-locked-artifact.ps1` proves it for
      `remote-test-client.exe` the way arm 3 does for the agent — arms 5–8, run
      2026-09-14: ALL PASS. There is no `-Dagent-version` for the client, so
      the copy is forced by backdating the installed file instead of re-linking
      it, and that timestamp is the oracle for which binary is where.
- [x] the teeth arm (`GHOZTTY_INSTALL_UNLOCK=0`) still reproduces the failure
      for that artifact too — arm 6 fails the build with `AccessDenied` on
      `remote-test-client.exe`, which is the state arm 7 then builds through.

## What the guard may NOT do

Each guarded pair gets its OWN run of the tool. A single shared run takes every
guarded artifact's SOURCE as an input and its dependents wait for all of it, so
the first cut of this change made a plain `zig build` compile every on-demand
harness — including `wp4-e2e`, which does not build for this target at all, so
the default build went red. A guard must never decide what gets built.
