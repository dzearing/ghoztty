# T2724 - The frame clock drops to a fixed 60 Hz timer for the rest of the process after one occluded compositor-clock wait (0xC01E0006, measured on the test desktop): on the user's 120 Hz panel every glide would then step at half rate until relaunch. Retry the compositor clock, and give the timer fallback the display's real period (DwmGetCompositionTimingInfo) instead of default_period_ns

## In plain terms

Ghoztty times its animations (glides, fades, the banner collapse) to the
screen's refresh. If that timing source hiccups even once - which happens
whenever the desktop is hidden, e.g. the screen is locked - the app used to
switch to a backup timer stuck at 60 frames a second and never switch back.
On a 120 Hz monitor every animation after that ran at half smoothness until
the app was restarted. Now the backup timer runs at the monitor's real rate,
and the app keeps trying to go back to the screen's own timing.

## Goals

- [x] the backup timer steps at the display's real refresh period, not a fixed 60 Hz
- [x] a failed compositor-clock wait is retried (backing off while it keeps failing), not given up for the life of the process
- [x] while on the timer, the clock's period is the timer's own, so on-time ticks are not counted as skipped frames
- [ ] T2372's third criterion: measure the clock on the user's 120 Hz panel on the input desktop

## Summary

`FrameClock.waitTick` set `wait_clock = null` for good on the first failed
`DCompositionWaitForCompositorClock` (0xC01E0006, STATUS_GRAPHICS_PRESENT_OCCLUDED
on the hidden test desktop or a locked session), and the hrtimer schedule
used `frame_clock.default_period_ns` (60 Hz) whatever the display.

Fix (src/apprt/win32/FrameClock.zig, frame_clock.zig, win32.zig):
- the compositor entry point is kept after a failure; `frame_clock.CompositorRetry`
  tries it again after 250 ms, doubling to an 8 s cap while it keeps failing,
  reset by any successful wait. The first failure warns; repeats log at debug.
- the timer fallback steps at `DwmGetCompositionTimingInfo`'s `rateRefresh`
  period (`frame_clock.periodFromRate`; the struct is pshpack1, so it is read as
  292 raw bytes), else the period the compositor measured before it failed.
  A forced `GHOZTTY_FRAME_CLOCK=hrtimer` uses the DWM period too.
- `stepping` (atomic) is what the worker is on right now; the perf report's
  `source=` reads it. On the timer, `period_ns` is the timer period rather
  than the shortest jittered wakeup (which read 7.9 ms against 8.33).

## Validation criteria

- [x] unit (none lane, `zig test src/apprt/win32/frame_clock.zig` 9/9): `periodFromRate` maps 120/1 -> 8.33 ms, 60000/1001 -> 16.68 ms, rejects 0 and implausible rates; `CompositorRetry` schedules, backs off to the cap, fires once per attempt, resets on success
- [x] `test/win32/frame-clock.ps1` H1 (2026-11-06, acceptance-parallel, ALL PASS 20): on the occluded test desktop the fallback stepped at period_us=8333 against DWM's 8333 read independently by the harness - this box's panel is 120 Hz; before the fix every run read ~16.1 ms
- [x] H2: 6 compositor failures and 5 retries in the probe window - the compositor is tried again rather than abandoned
- [x] B on the fallback: 0/479 probe intervals skipped, mean 8332us against an 8333us period
- [ ] input-desktop measurement on the user's panel (compositor source, expect ~8.3 ms): NOT RUN - it needs the input desktop and the user is present (go.md focus rule)
