# T1643 - The test-reach audit's lane check fails about four times in five, and the log it blames is deleted before anyone can read it

## In plain terms

Nothing a user sees. One of the checks that guards the test suite keeps crying
wolf: four times out of five it reports that the Windows test build failed, when
running exactly the same build by hand a minute earlier succeeds. Worse, the
check points at a log file to explain itself and then deletes that file
immediately, so nobody can find out what actually went wrong. Until it is
trustworthy, every turn that touches a test script has to decide whether to
believe it.

## Goals

- [ ] `test-reach-audit.ps1` B1 gives the same verdict as the command it runs
- [ ] A red run leaves behind enough to diagnose it (done: the temp dir is kept)
- [ ] The lane's own output is readable without wading through `--verbose`

## Summary

On 2026-09-17 (T819's turn) `test-reach-audit.ps1` scored `FAIL B1 the win32
test lane builds and passes -- zig build test exited 1` on FOUR consecutive
runs - twice inside `harness-floor`, twice alone - and then passed on the
fifth, against an unchanged tree. In the same window:

* `scripts\floor-lane.ps1 -Lane win32` was green (13:42).
* The audit's EXACT command, `cmd /c "zig build test -Dapp-runtime=win32
  -Doptimize=Debug"` with `ZIG_GLOBAL_CACHE_DIR` on the repo drive, read back
  through `$LASTEXITCODE` the way `Resolve-WinTestBinary` reads it, exited **0**
  (15:01).

So the audit's own oracle disagrees with the command it runs, and it is the only
member of the harness floor that builds and RUNS the whole win32 lane - a
five-minute step whose failure mode is a bare exit code with no test name.

Two things made it near-undiagnosable, one of which is already fixed:

1. **It deleted the evidence it named.** `Remove-Item -Recurse -Force $tmp` ran
   unconditionally at the end, so the `lane.log` quoted in the failure message
   was gone milliseconds later. Four reds were investigated by racing a file
   copier against that line, which never won cleanly. **Fixed in this commit**:
   a run with failures keeps its temp dir and prints `kept for diagnosis: <path>`.
2. **`--verbose` buries the answer.** The lane is invoked with `--verbose`, so
   the log is ~50KB of zig command lines and the interesting few lines at the end
   are easy to miss entirely. Consider dropping it, or teeing the last N lines
   into the failure message.

A candidate mechanism for the flake itself, not yet confirmed: two zig builds
sharing `.zig-cache` (the audit builds the same lane the floor's win32 lane
builds, and the harness floor runs inside the same repo), or a transient failure
in one of the tests the lane runs. The stack traces for
`claude_plugin_migration.zig` readLink (`error.Unexpected NTSTATUS=0xc0000275`,
STATUS_NOT_A_REPARSE_POINT) that appear in the lane log are NOT it - they are
Zig's `unexpectedStatus` diagnostic printing, and `scriptIsPluginOwned` swallows
that error deliberately (the comment above line 128 names this exact case).

The next turn to hit this should start from the kept temp dir.

## Validation criteria

- [ ] Ten consecutive `test-reach-audit.ps1` runs on an unchanged tree give the

      failing test - demonstrated, not assumed
