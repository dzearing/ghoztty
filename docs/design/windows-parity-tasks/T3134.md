# T3134 - Windows pane sidebar: windows that share a name (every new shell tab is '~') must list in the order they opened, so rapid new-window does not make the selection hop (Mac 5558742c6); verify pane_sidebar_outline placedLess's index tie-break is open order, not tab-strip position

## Summary

Mac 5558742c6 broke name ties in the all-windows list by random window id; it now ties by open order (restore keeps the saved order). Windows pane_sidebar_outline.zig placedLess ties on a.index, the tab's position in the tab list, which is open order only if new tabs always append and a drag in the tab strip does not reorder the sidebar. Measure: open 5 '~' tabs, reorder the strip, open another, check the sidebar order and that the selection stays on the new one; and that restore keeps the saved order. Fix with a monotonic open sequence per tab if it does not hold.

## In plain terms

Every new shell tab is called `~`, so the all-windows list has to decide
which of several `~` entries comes first. It went by where each tab sat in
its tab strip, so dragging a tab along the strip shuffled the list, and the
selection jumped. Now namesakes are listed in the order they were opened, and
a new one always lands at the end of them.

## Goals

- [x] Each tab remembers when it opened, and keeps it through every tab move
- [x] The all-windows list (and the window-to-window chord that walks it) breaks name ties by that
- [x] A restore reopens tabs in the saved order, so the order survives a relaunch
