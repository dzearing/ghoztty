# T2925 - Stacked panes: a background split (agent +split, side pane) off a pane the user minimized in a collapsed row pulls the strips back out - anchor it beside the pane on show nearest it (Mac 251a1a1dc backgroundSplitAnchor)

## In plain terms

If you squeeze a row of panes so some fold into thin strips, and an agent
running in one of those strips opens a side pane, every strip you folded used
to spring back open. Now the side pane opens beside the panes you can see, and
the strips you folded stay folded.

## Goals

- [x] a background split anchored at a pane the user minimized goes in beside the pane on show nearest it
- [x] a split that takes focus keeps its anchor (the user asking for it)
- [x] an acceptance harness that reproduces the defect without the fix

## Summary

Mac 251a1a1dc: a split that leaves the caret where it is, anchored at a pane the user minimized in a collapsed row, now goes in beside the pane on show nearest that anchor (BaseTerminalController.backgroundSplitAnchor = paneOnShow); a focusing split keeps its anchor. Windows features a background split's new pane the same way (Window.zig ~16177, T2257) and has paneOnShowAfter (~11302), so it very likely pulls the strip back out too. Port: anchor background splits via paneOnShow; Mac test aSidePaneFromAMinimizedPaneLeavesTheStripsMinimized; docs/reference/stacked-panes.md.

## Fix

`Window.backgroundSplitAnchor` (new, beside `paneOnShowAfter`): resolve the
anchor handle's pane, ask `PaneStackState.paneOnShow` over the unchanged rows,
and split at that pane's handle when it differs. `insertPaneAsSplit` calls it
only while `split_background` is set, so a focusing split (and every keybind
split) keeps its anchor, exactly as Mac's `focus ? oldPane :
backgroundSplitAnchor(oldPane)`. Both the terminal (`newSplitAt`) and viewer
(`newViewerSplitAt`) paths share `insertPaneAsSplit`, so both are covered, as
Mac covers `newSplit` and `newViewerSplit`.

Scope, same as Mac: `paneOnShow` is pin-based, so this covers a row the USER
collapsed (a divider drag). A row folded only because the window is too narrow
is not pinned, and a featured side pane off one of its strips still reshapes
the run - also Mac's behaviour, so no parity gap (observed while writing the
harness: a side pane off a width-folded edge strip brought it out and folded the
caller instead).
