# T2931 - Name the lock a fold-glide region cut waits on: an elevated kernel trace (WPR CPU + context switch) over the T2874 probe, since the UI thread sits off-CPU 2-7 ms inside SetWindowRgn on an idle box

## Summary

T2874 (2026-11-11) found the fold-glide region-cut stall is the UI thread
**off-CPU** inside system calls: a 6.8 ms `SetWindowRgn` ran 173 us of thread
cycles, the pane's window procedure took 5 us of it, and no present on that
pane overlapped. The box was idle (32 logical CPUs, ~6% load), so the likely
shape is a wait on a lock shared across the desktop session (win32k's user
lock, GDI, or a DWM sync) held by another thread or process - but which one
cannot be named without context-switch ETW, and the kernel providers need
elevation this loop does not have.

What a trace would decide: if the holder is one of OUR threads (a renderer in
win32k, the agent's console host), there is a fix on this side beyond calling
less (T2932); if it is another process or DWM, calling less is the whole
answer.

The `stack trace rgn` line (`qpc`, `end`, `proc_qpc`, `msgs`, `cycles`) gives
the QPC spans to line the trace up against.

## Validation criteria

- [ ] an elevated .etl of the probe, with the UI thread's wait on 2+ slow `stack trace rgn` spans attributed to a named readying thread / lock
- [ ] the finding recorded here and in T2932 (whether anything other than fewer calls can help)
