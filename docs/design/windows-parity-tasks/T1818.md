# T1818 - Measure what Claude Code's fullscreen renderer does on a Windows pane resize, against T1763's clear-and-repaint

## Summary

T1801 turned on `CLAUDE_CODE_NO_FLICKER=1` in Windows panes by default (the
Mac's `claude-code-fullscreen`). The Mac commit's claim is that Claude's
fullscreen renderer re-lays out its own conversation on resize instead of
writing pre-wrapped rows into scrollback, which should also remove the
clear-and-repaint frames T1763 measured on the classic renderer (one Ink frame
leaves conhost as `?2026h 2J 3J ?2026l` followed by an unbracketed paint;
T1763 fixed it with the ConPTY sync hold).

Nobody has measured that on Windows. Do it: run Claude Code in a Debug pane on
the test desktop with and without the variable, resize it, and record the
ConPTY output stream per resize (the T1763 scratch probe shape) - count frames
that close a sync bracket on an empty screen, and whether the T1763 hold still
fires. If fullscreen makes the hold unnecessary for Claude, say so; do not
remove the hold (other TUIs still need it).

## In plain terms

When you resize a pane running Claude Code, the screen used to blink empty for
a moment. A fix in September hid that blink. Since then Windows panes run
Claude Code in its newer "fullscreen" mode, and nobody had checked whether that
mode still needs the fix. It does: in fullscreen mode Claude Code blanks the
screen on every single resize, and the fix is what keeps you from seeing it.

## Goals

- [x] Capture what Claude Code actually sends on a resize, old mode vs fullscreen
- [x] See whether the blink fix still kicks in, and whether you would see a blink without it
- [x] Do it all without touching the user's screen

## Findings (2026-11-22, Claude Code 2.1.330, Windows 11 in-box conhost)

**Raw ConPTY stream** (scratch C# probe: Claude Code under
`CreatePseudoConsole(100x40, flags 0)`, no window and no desktop; six
`ResizePseudoConsole` width changes 2s apart; std handles as
`CommandCore.zig` sets them - `STARTF_USESTDHANDLES` with null handles, or
Node sees a non-TTY stdin and falls into `--print`):

| renderer | history | per resize | erasing brackets |
|---|---|---|---|
| fullscreen (`NO_FLICKER=1`, alt screen `?1049h`) | short | conhost in-place repaint, then `ESC[?2026h ESC[?25l ESC[2J ESC[?2026l`, then an unbracketed paint ~9ms later | 6 of 6 |
| fullscreen | 90+ lines | same | 6 of 6 |
| classic (`NO_FLICKER=0`) | short | conhost repaint, `ESC[?2026h ESC[?2026l` (empty, no erase), repaint | 0 of 6 |
| classic | taller than the screen | same | 0 of 6 |

~2.3-3.9 KB per resize in every mode. History came from three bash-mode
(`!seq ...`) commands, so no model call was made. Fullscreen is exactly the
T1763 shape (the erase closes its bracket before conhost's paint) minus the
`ESC[3J`, since the alt screen has no scrollback. Classic 2.1.330 no longer
erases on resize at all - it differs from what T1763 captured in September.

**In the app** (Debug `zig-out`, test desktop, `--session-persistence=false`,
window widths 1000 -> 1100/900/1200/850/1050/950, the T1763 oracle line
`conpty sync shown how= text_rows= held_ms=`):

| run | erasing redraws | held | shown blank |
|---|---|---|---|
| fullscreen, hold on | 6 | 6 (`idle`, 21-24ms) | 0 |
| fullscreen, `GHOZTTY_CONPTY_SYNC_HOLD=0` | 6 | 0 (`close`) | **6** (`text_rows=0`) |
| classic, hold on | 0 | - | 0 |

**Verdict:** fullscreen does NOT make the hold unnecessary for Claude - it
makes it load-bearing: every resize of every Claude pane (the T1801 default,
and the user's own `settings.json` `tui: fullscreen`) goes through it, and
without it every one would blink. The hold stays. Its harness drives only the
classic shape, so T3547 adds the fullscreen shape to it.
