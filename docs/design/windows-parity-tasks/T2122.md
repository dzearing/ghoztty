# T2122 - Stacked panes: a tucked pane's strip is a screen-reader button named 'Tucked pane: <name>' that brings the pane forward on Invoke

## Summary

Mac's PaneStackTabView is an accessibility button (label 'Tucked pane: <displayLabel>', help 'Brings the pane forward', accessibilityPerformPress activates). T2109's win32 strips are owner-painted pixels with no UIA presence; expose them (a UIA fragment per strip, Invoke -> Window.bringForward).

## In plain terms

When a row has more panes than fit, the extra ones fold into thin strips at
the edge. A sighted user can click a strip to get the pane back, but a
screen-reader user could not find the strips at all - they were just painted
pixels. Now Narrator (or NVDA, JAWS) finds each strip as a button called
"Tucked pane: <its name>", with the hint "Brings the pane forward", and
pressing it brings that pane back, the same as on the Mac.

## Goals

- [x] Each tucked strip appears in the window's accessibility tree as a
      button named `Tucked pane: <name>` (the name the strip shows)
- [x] It carries Mac's help text `Brings the pane forward`
- [x] Pressing it (UIA Invoke) brings the pane on show and focuses it
- [x] The window's existing tree (sidebar, panes, title bar) is unchanged

## Design

- **UI Automation, root only.** `Window.zig`'s `WM_GETOBJECT` keeps the T48
  `OBJID_CLIENT` opt-out (no oleacc proxy for the top-level) and answers only
  `UiaRootObjectId` with `strip_uia_provider.Root`, a fragment root whose
  host provider is the HWND's - so the window's name, frame and child windows
  still come from UIA's HWND proxy, and the strips are added as children.
  Mechanism call, not filed as a decision (no user-visible difference
  between MSAA and UIA here; UIA leaves the deadlock opt-out untouched).
- **Strips are re-resolved on every call** (`Window.uiaStrips`): by pane
  address, compared never dereferenced, in reading order (top-to-bottom,
  left-to-right; `strip_uia.readsBefore`). A strip that has gone answers
  `UIA_E_ELEMENTNOTAVAILABLE`; a gliding card is not a strip yet.
- **Invoke posts** `WM_APP_STRIP_INVOKE` and returns; the message loop
  re-checks the pane is still a strip, then `bringForward` - the click path.
- **Lifetime:** `WM_DESTROY` calls `UiaReturnRawElementProvider(hwnd,0,0,0)`,
  `UiaDisconnectProvider`, and detaches, so a reader holding the objects gets
  "element not available" instead of a freed window.
- Pure half (`strip_uia.zig`, unit-tested in the none lane): name with
  UTF-8-safe cut, reading order, navigation, hit test, runtime id.
