# T1806 - Shift-clicking a remote window's close button closes it without the Disconnect/Close confirmation

## In plain terms

Closing a remote window always asks whether to Disconnect or Close. Holding
Shift while clicking the window's X should skip that question and just close
the window. It does what the dialog's default button would do, so nothing is
lost.

## Summary

User request (2026-10-10): "when im in the new remote window and i hit the X
button, there's a confirm dialog. If i hold shift clicking it, please no
confirm, just close it."

The confirmation is the T1390 remote-close dialog
(`src/apprt/win32/ConfirmDialog.zig`, row `[Disconnect] [Close]`, default
Disconnect; message from `session_disconnect.zig`).

**Assumption (recorded, not asked, per the no-questions directive):** Shift+X
performs the dialog's DEFAULT answer, **Disconnect**. The window closes and
the remote session keeps running, so it can be re-attached later. This is the
non-destructive reading of "just close it". If the user wants Shift+X to end
the remote session, that is a one-line change of which answer the shortcut
picks; flag it in the close-out so they can say so.

Scope:

- The caption X button. Read the Shift state at click time
  (`GetKeyState(VK_SHIFT) < 0` on WM_NCLBUTTONUP/SC_CLOSE). Do not read it
  later, when the user may have released it.
- Ctrl+Shift+W, tab close buttons and Alt+F4 are out of scope unless they show
  the same dialog. If they do, apply the same rule and list them.
- Local (non-remote) windows are unchanged in this task. Whether Shift should
  skip their close confirmation too is noted for the user, not assumed.
- Mac mirror: T1807 (Option-click is the Mac idiom for "skip the prompt";
  decide there whether Mac uses Shift for symmetry or Option for platform
  idiom, and record it).

## Goals

- [x] Shift + click on a remote window's X closes it with no dialog
- [x] The remote session keeps running (Disconnect, the dialog's default)
- [x] A plain click still asks; a busy LOCAL window still asks even with Shift

## What landed

- `session_disconnect.closeStep` (pure): `.disconnect` when Shift was down and
  there are disconnectable panes; the local "processes are still running"
  question is never skipped. Four tests in the win32 lane, where the module's
  other tests already live (the task text said `none` lane; the module is
  registered in `src/apprt/win32.zig`, so that is where it runs).
- `Window.handleNcLButtonUp` reads `GetKeyState(VK_SHIFT)` at the release that
  fires the close and posts `WM_APP_SHIFT_CLOSE` (WM_APP+40) instead of
  SC_CLOSE. Its handler raises `skip_disconnect_prompt` and sends the ordinary
  SC_CLOSE; WM_CLOSE reads and lowers the flag first, so it applies to that one
  close only.
- Scope: only the caption X. Ctrl+Shift+W, tab close buttons and Alt+F4 are
  unchanged (Alt+F4 already holds no Shift meaning; Ctrl+Shift+W IS a Shift
  chord, so reading Shift there would make every Ctrl+Shift+W skip the prompt).
