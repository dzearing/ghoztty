# T1021 - the machine chooser's shape has no guard-due row - chooser_layout.zig can change with nothing obliged to re-run ipc-machine-chooser.ps1

## In plain terms

The "New Remote Window" picker has one test that checks it actually looks
right — the fixed 840x540 dialog, the machine column, the detail pane, the
wrapping status strip. Nothing currently connects that test to the code that
decides those sizes, so somebody can change the dialog's shape and no check
anywhere notices until a human happens to run the right script by hand.

## Summary

`scripts\guard-due.ps1` answers "has anybody run harness X against the code as
it now stands?" and step 6's `validate` fails while an answer is no. Its
coverage table has rows for `chooser-session-sort`, `chooser-resume`,
`chooser-selection` and the chooser's text field — but **none for
`test\win32\ipc-machine-chooser.ps1`**, and `src\apprt\win32\chooser_layout.zig`
appears in no row at all.

That is the harness that owns the chooser's SHAPE (T175): the fixed 840x540
client, the 260 master column and its wash, the hairline rule, the detail pane
following the selection, Cancel alone in the footer, and the status strip that
must wrap without clipping. `chooser_layout.zig` is where every one of those
numbers is decided, and it is unguarded.

Found while doing T314, whose whole subject was the same shape of hole one
level up: a defect class nothing was obliged to look for.

## What to build

Add a row to `scripts\guard-due.ps1`:

```
Name   = 'machine-chooser'
Script = 'test\win32\ipc-machine-chooser.ps1'
Stamp  = 'test\win32\ipc-machine-chooser.stamp.json'
Covers = @(
    'src\apprt\win32\chooser_layout.zig',
    'src\apprt\win32\chooser_rows.zig',
    'test\win32\ipc-machine-chooser.ps1'
)
```

Follow the `chooser-resume` row's precedent on `MachineChooser.zig`: it is
deliberately excluded there because it hosts sixteen chooser features and moves
constantly, which would make the row due on nearly every turn. Decide the same
way here and write the reason into the row's comment either way — the
`chooser-selection` row DOES include it, and says why (the defect lived in the
painter), so the table already carries both precedents and the choice must be
argued, not defaulted.

Note the run cost when deciding: the script is a full GUI acceptance run on the
test desktop (77 assertions, roughly a minute), which is the same order as
`chooser-selection`'s.
