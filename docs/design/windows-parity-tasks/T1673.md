# T1673 - An update the user missed the first balloon for is never offered again, so the terminal sits stale for weeks

## Summary

USER-OBSERVED 2026-09-19: the box's installed Ghoztty is 1.36.12 (binary 2026-09-05) while win-v1.36.30 shipped the same evening - 18 releases and 14 days behind. The updater is healthy up to the last step: it checks hourly, and BOTH Ghoztty-1.36.29-x64.msi and Ghoztty-1.36.30-x64.msi are already staged in %LOCALAPPDATA%\ghoztty\updates. What never happens is the apply. The log names the cause: after the single balloon for a version, every subsequent hourly check logs 'update check: win-v1.36.X already offered; not re-notifying' - one notification per version, for the life of that version. A balloon missed (away from the desk, notifications quiet, a full-screen app) means the offer is gone until a NEWER release appears, which gets exactly one balloon of its own. Nothing escalates, nothing persists, and nothing in the window itself says an update is waiting. Fix direction: an offer that is STAGED and unapplied should stay visible in the app (a persistent affordance - title bar / menu / chooser row - not only a transient balloon), and re-notification should escalate with staleness rather than being suppressed by 'already offered'. Evidence: %LOCALAPPDATA%\ghoztty\ghoztty.log 2026-09-19T19:00 through 2026-09-20T05:00.

## In plain terms

Right now the only way Ghoztty ever tells you an update is waiting is a
notification balloon, and a balloon only appears once. If you were away from
your desk, or in a full-screen app, or had notifications quiet, the offer is
simply gone - and nothing anywhere in the window says a thing. That is how this
box ended up running a build eighteen releases and two weeks old with the
installers already downloaded and sitting on disk.

After this, the menu button in the window chrome wears a small coloured dot for
as long as an update is waiting, and opening that menu shows an "Install
Update 1.36.30" row at the top. The dot starts green, goes amber after two days
and red after a week, so being a long way behind looks different from having
just been told. It survives closing and reopening the terminal, and it goes
away when - and only when - the update is actually installed.

## Goals

- [x] a persistent, always-visible affordance that an update is waiting, not just a balloon
- [x] it escalates with staleness rather than being suppressed by "already offered"
- [x] the offer and its age survive a restart, so a staged package is visible with no network check
- [x] the affordance retires exactly when the running build catches up
- [x] the colour is never the only signal (the row says it in words)
