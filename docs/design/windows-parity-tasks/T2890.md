# T2890 - promote the T1404 child-read warning to a refusal once the acceptance suite runs warning-free

## Summary

T1404 made `Get-TestPixel` (and `Get-TestBrightness`, for a rect a child covers
a quarter of) WARN when a read lands inside a child window of the capture,
because a child control's paint is missing from roughly one `-Sync` capture of
its parent in four to ten. It is a warning, not a refusal, because
`Get-TestPixel` has 161 call sites in 35 scripts and nobody has yet counted
how many read inside children.

A warning in a run log is easy to scroll past. Once the suite is known to be
warning-free, the same check should throw (with `-ChildOk` the opt-out), so a
new probe cannot reintroduce the T1400 shape quietly.

1. Run the full acceptance suite (`acceptance-parallel.ps1 run` over every
   script that dot-sources `TestDesktop.ps1`) and collect every
   `WARNING: ... inside CHILD window` line from the per-script logs.
2. Fix each hit the T1400 way (measure through the rect, bound the scan with
   `Get-TestCaptureChild`), or mark it `-ChildOk` with a comment where the
   read is genuinely about the child and tolerant of its absence.
3. Turn `Write-TestChildReadWarning` into a throw; update section P2 of
   `test\win32\test-desktop-harness.ps1` to assert the refusal.

Hand-rolled `$shot.Bitmap.GetPixel` scans (80 uses, 28 files) are not covered
by either form; consider a harness-floor audit that flags a raw scan over a
shot whose `.Children` is non-empty.

## Validation criteria

- [ ] A suite-wide run lists zero child-read warnings (log grep, numbers in the
      progress log).
- [ ] `Get-TestPixel` inside a child throws; P2 asserts it, `-NegativeControl`
      turns it red.
