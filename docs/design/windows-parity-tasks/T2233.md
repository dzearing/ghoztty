# T2233 - Mac: resuming one session from the chooser mints a fresh pane id, so the still-running shell cannot name itself

## Summary

The Mac half of T113/T1317. The chooser's single-session resume - local
(`AppDelegate.resumeSession`, local arm) and remote
(`AppDelegate.resumeRemoteSession` -> `presentRemoteWindow`) - builds a
`SurfaceConfiguration` with `remoteSessionId` but never sets the pane id, so the
resumed surface mints a fresh one. The shell being ATTACHed to is still running
with the OLD id in `$GHOZTTY_PANE_ID`, so a banner script, a hook, or
`ghoztty +send-keys --target=$GHOZTTY_PANE_ID` from inside it addresses a pane
that no longer exists.

Windows adopts the recorded id on both arms: local from this box's manifest
(T113), remote from the FAR machine's layout view (`GET_LAYOUTS`, T1296/T1317,
`SessionRoster.persistedPaneIdFor`). Mac's full-layout restore
(`SessionLayoutRestore.swift` ~491) already re-adopts ids; only the
single-session path is missing it. Fix: look the session id up in
`SessionLayoutManifest` (local) / the far machine's pulled layout blobs
(remote), and set the surface's pane id from the matching leaf.

## Validation criteria

- [ ] Resuming a local orphan session from the chooser: `echo $GHOZTTY_PANE_ID` in the pane equals the pane's id in `ghoztty +list --json`.
- [ ] Same for a session resumed from a relay machine.
- [ ] A session whose layout recorded no pane id still opens, with a fresh id.
