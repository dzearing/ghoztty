# T2014 - One-tab window shows 14 px of extra chrome: tab-strip-autohide.ps1 reads the pane at offset 54 under a 40 px caption, and the merged strip row at 64 px instead of 50

## Summary

tab-strip-autohide.ps1 5 FAILURE(S) (10 passed): 'no strip - the pane starts right under the caption (offset 54, capH 40)', 'total chrome is bar_h (64 px, expected 50)'. 14 px of chrome appeared somewhere above the pane. Found in T2005 (2026-10-16): red in lane A on HEAD 161784011 with the script byte-identical to HEAD (run serially, -Width 1, alone), so it predates T2005. Logs: scratchpad aplogs3 of that turn.

## In plain terms

A one-tab window looked like it had grown a sliver of extra space above the
terminal. It had not: since panes became raised rounded cards by default, the
cards sit a small margin in from the window edge, and the test was counting
that margin as title-bar chrome. The test now measures the title bar alone, so
it goes back to checking what it was written to check.

## Goals

- [x] Find where the 14 px came from
- [x] Make the test measure caption chrome only, without weakening it

## Root cause

Not an app defect. The 14 px is the elevated pane style's grid margin plus its
rim inset (`pane_elevation.marginPx` + `childInsetPx` at 1.25x), which T1831
(2026-10-11) made the default. `Pane-Offset` reads the first terminal child's
top against the client top, so it took in the margin as well. The fix pins
`--macos-pane-style=flat` in `Start-Win`. `chrome-merged-row.ps1` already does
this for the same reason, and `pane-elevation.ps1` scores the margin itself.
