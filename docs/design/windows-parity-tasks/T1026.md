# T1026 - The merge stages have no pre-flight gate: upstream-remote.ps1 check is never run by anything

## Summary

T957's 'check' verb is the assertion that every sha docs/design/windows-parity-upstream-pull-plan.md pins still resolves and is reachable from upstream/main, and today nothing calls it except its own acceptance script. The claim runs 'ensure' (which repairs and fetches, and is deliberately never fatal so an offline box cannot wedge the loop), and parity-tasks.ps1 validate does not know about it at all - correctly, since a turn that touches no merge machinery should not fail because GitHub is unreachable. The gap is the moment it DOES matter: the start of S1..S6. Give the stages a pre-flight - a script or a documented step that runs upstream-remote.ps1 check, floor-lane -Lane all and guard-due check before a stage branch is cut - so a stage cannot begin against a plan whose shas have gone missing. Depends on T957; wanted before S1 is attempted.

## In plain terms

Pulling the original Ghostty project's changes into this fork is planned as six
steps. There was a safety check that the plan's reference points still exist,
but nothing ever ran it, and nothing else checked the starting point before a
step began. Now one command says whether a step may start, and refuses with the
reason when it may not. It never starts a step itself.

## Goals

- [x] One command, `scripts\upstream-stage.ps1 preflight -Stage S<n>`, that runs `upstream-remote.ps1 check`, `fork-identity check`, `guard-due check` and `floor-lane -Lane all` before a stage branch is cut
- [x] It also refuses a dirty tree, an unpushed base, a stage taken out of order or taken twice, and a stage table that does not join up
- [x] The plan doc's stage sequence names it
- [x] An acceptance harness proves every check can refuse, plus a guard-due row tying the script to it
