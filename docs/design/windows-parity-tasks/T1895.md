# T1895 - pane-banner.ps1 is red at HEAD (bef18f02d): after the T165 Ctrl+click section, +close of the viewer pane does not take, so every later section's +set-banner --target=bw hits the viewer ('bw is a viewer pane, not a terminal') - 17 failures

## Summary

Found by T1850. Its `banner_card.zig` edit made the `pane-banner` guard due,
and the harness went red. The same 17 assertions fail on a clean build of
HEAD `bef18f02d` without T1850's change (built in a detached worktree at
`D:\git\ghoztty-t1850-base`, run with `-ExePath`), so the regression is
older. It was stamped green at 86ae8c657 (2026-10-12). Since then, commits
in files the row does not cover (`Window.zig`, viewer close/stash, T1838-T1849)
moved something.

Shape: section 6 (T165) Ctrl+clicks a banner link, which splits a viewer
pane, then puts the window back to one pane with
`+close --target=<viewer leaf id>` from `+list --json`. From the next section
on, `+set-banner --target=bw` answers `bw is a viewer pane, not a terminal`.
The window target resolves to the focused pane, and that is still the viewer.
So the close never happened (or focus stayed on a closed pane), and T539,
T758, the pane-target, window-target and OSC 7778 sections all fail
downstream of it.

Start by bisecting 86ae8c657..bef18f02d with `pane-banner.ps1 -ExePath`, then
check whether `+close` of a viewer by leaf id still works (`viewer-close.ps1`
is green, so look at the id form the script uses). Also consider adding
`Window.zig` (or the close/focus path) to the `pane-banner` guard row, since
that is how this went unnoticed for a day.
