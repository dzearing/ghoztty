# T1895 - pane-banner.ps1 is red at HEAD (bef18f02d): after the T165 Ctrl+click section, +close of the viewer pane does not take, so every later section's +set-banner --target=bw hits the viewer ('bw is a viewer pane, not a terminal') - 17 failures

## Summary

Found by T1850. Its `banner_card.zig` edit made the `pane-banner` guard due,
and the harness went red. The same 17 assertions fail on a clean build of
HEAD `bef18f02d` without T1850's change (built in a detached worktree at
`D:\git\ghoztty-t1850-base`, run with `-ExePath`), so the regression is
older. It was stamped green at 86ae8c657 (2026-10-12). Since then, commits
in files the row does not cover (`Window.zig`, viewer close/stash, T1838-T1849)
moved something.

Shape: section 6 (T165) Ctrl+clicks a banner link, which splits a viewer
pane, then puts the window back to one pane with
`+close --target=<viewer leaf id>` from `+list --json`. From the next section
on, `+set-banner --target=bw` answers `bw is a viewer pane, not a terminal`.
The window target resolves to the focused pane, and that is still the viewer.
So the close never happened (or focus stayed on a closed pane), and T539,
T758, the pane-target, window-target and OSC 7778 sections all fail
downstream of it.

Start by bisecting 86ae8c657..bef18f02d with `pane-banner.ps1 -ExePath`, then
check whether `+close` of a viewer by leaf id still works (`viewer-close.ps1`
is green, so look at the id form the script uses). Also consider adding
`Window.zig` (or the close/focus path) to the `pane-banner` guard row, since
that is how this went unnoticed for a day.

## In plain terms

After you Ctrl+clicked a link into a side viewer and then closed that viewer,
Ghoztty could still treat the closed viewer as the window's current pane.
Anything a script aimed at the window, such as setting its banner, then failed
with "is a viewer pane, not a terminal". Now the closed viewer can no longer
take that role back, so commands go to the pane you can actually see.

## Goals

- [x] find why the window target resolves to a closed viewer
- [x] fix it at the source
- [x] make the harness that caught it run when the code that broke it changes

## Root cause and fix

A viewer page's "got focus" notice (T1809) reaches the pane as a POSTED
message. When the viewer is closed it is parked for undo (T1825): still alive,
but in no tab's tree. A notice that lands after the close ran
`ViewerPane.becomeActivePane`, which wrote the parked pane back into
`tab_active_pane[active_tab]`. `targetPane` resolves a window target through
that slot, so every window-targeted verb then hit the hidden viewer.
`becomeActivePane` now requires the pane to be in a tab's tree
(`tabIndexOfPane`) and uses that tab rather than the active one, as the
terminal arm in App.zig already did (T249).

Also tried, and dropped: a window-target check in `viewer-close.ps1` section D
(`+split --view --focus`, then `+close`, then `+set-banner --target=<window>`).
It passed on the UNFIXED build, so a CLI split does not reproduce the late
focus notice, and a check that cannot fail was not kept. The Ctrl+click path in
`pane-banner.ps1` is the reproduction, so `ViewerPane.zig` now sits in that
harness's guard row, and the T165 section asserts the close took.
