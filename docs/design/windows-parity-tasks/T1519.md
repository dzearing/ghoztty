# T1519 - The shared fake relay is still stopped with a bare Stop-Job, and its bridge can block mid-frame where that stop cannot reach it

## Summary

test\win32\lib\FakeRelay.ps1's Stop-FakeRelay calls Stop-Job then Remove-Job -Force. Today that is bounded because its accept loop polls Pending() - the property T1517's job-teardown.ps1 section D now enforces - but its WebSocket bridge reads through Read-Exact, which sits in a synchronous stream.Read until the peer finishes a frame it already committed to. A peer that stalls mid-frame (a killed agent, a dropped bridge) parks the job exactly where Stop-Job cannot reach it: the T1517 wedge with a different blocking call. Six harnesses tear down through this helper (activity-monitor-dialed, chooser-conn-pool, chooser-restore-all-remote, chooser-resume-remote, chooser-sessions-remote, remote-reconnect-relay), so one stalled bridge costs all six their verdict, with no exit code and the per-user pipe held against whatever is queued behind them. Fix: record the job's pid as its first statement and tear down through Stop-JobBounded (test\win32\lib\JobTeardown.ps1), the way relay-account.ps1 and share-machine.ps1 now do. Latent, not observed - this is hardening the second blocking call before it bites.
