# T2244 - A panic in a release build leaves no crash report on Windows - Zig's abort exits with code 3 and never reaches the crash filter

## In plain terms

Since T1355 a Ghoztty that crashes on Windows leaves a report behind. One
kind of crash still does not: when the app itself detects something
impossible and stops on purpose (a "panic"), the version users run quits
silently, and the report folder stays empty.

## Summary

T1355 installed an unhandled-exception filter (`src/crash/windows.zig`) that
writes `<stamp>-<pid>.txt` + `.dmp` into the crash dir. A Zig panic does not
raise an exception in a shipping build: `std.debug.defaultPanic` prints the
message and calls `std.posix.abort()`, which on Windows is `@breakpoint()`
only in Debug and then `ExitProcess(3)`. So in ReleaseFast a panic exits
with code 3, no filter runs, and only the NEXT launch's exit ledger notices
(`unrecorded-exit`). On macOS the same panic ends in SIGABRT, which the Sentry
handler catches and reports - so this is a platform-symmetry gap.

Fix shape: give the root a panic handler (`pub const panic` in
`src/main_ghostty.zig`, or wrap the default) that, on Windows, writes the
report with the panic message as an extra `message=` line and a minidump of
the current context (`RtlCaptureContext` into a synthesized
`EXCEPTION_POINTERS`, or `RaiseException` with a Ghoztty-specific code so
the existing filter path handles it), then continues to the default panic.
The renderer and IO threads panic through the same path (`crash:render`,
`crash:io`), so all three must be covered.

## Validation criteria

- [ ] A ReleaseFast build (endpoint-isolated per `Set-GhozttyTestIsolation
      -ReleaseSandbox`) crashed with `crash:main` leaves a `.txt` naming the
      panic message and a `.dmp`
- [ ] Same for `crash:render` and `crash:io`, each naming its own thread
- [ ] `test\win32\crash-report.ps1` grows the release case and stays ALL PASS
