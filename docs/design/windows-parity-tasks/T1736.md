# T1736 - win32 +new-remote-window --name= does not pin the relay pill's machine name the way Mac's namePinned does

## Summary

Mac's IPCServer passes an explicit --name to openRemoteWindow as the Machine's display name with namePinned=true, so the pill says the caller's label and an account rename never overwrites it (AppDelegate: fallbackName ?? reportedHostname ?? device; namePinned && fallbackName != nil; restored windows re-pin via RemoteSessionManifest.Entry.namePinned). On win32 --name is only the IPC registry name: after T1418 the pill shows the directory name (or HELLO hostname) and adoptRelayNames renames it on the next listing regardless. Fix: carry a pinned name on RemoteMachine.relay (a flag beside T1418's name), set it from the verb's --name, skip pinned machines in adoptRelayNames, and persist the pin through session-layout restore. Extend test\win32\remote-pill-relay-name.ps1 with an arm: --name=X shows X and survives a listing.

## In plain terms

When a script opens a window on another machine and gives it a name
(`+new-remote-window --relay=... --device=... --name=build-box`), the Mac shows
"build-box" in the window's machine badge and keeps it there. Windows showed the
machine's directory name instead, and renamed the badge whenever the account's
machine list refreshed. Now Windows shows the name the script asked for and
keeps it.

## Goals

- [x] `--name=X` on a relay `+new-remote-window` makes X the machine's label (pill, tooltip, close confirmation, `+list` machine field)
- [x] a later directory listing never renames a pinned window, and says so in the log
- [x] a window opened WITHOUT `--name` still takes the directory / HELLO name and follows renames (T1418 unchanged)
- [x] New Window on a pinned window inherits the pin (T68 copies the machine record)
- [ ] the pin survives an app relaunch - not possible yet: win32 does not restore relay windows at launch at all; filed as T3352, which carries the pin

## Design / decisions

- `RemoteMachine.relay` gains `name_pinned` beside T1418's `name`; `setRemoteMachine`
  keeps it only when a name came with it (Mac `namePinned && fallbackName != nil`).
- The rename rule is the pure `Window.relayRename(pinned, current, listed)`
  (`keep` / `pinned` / `rename`), so it is unit-tested without an app.
- Restore: the Summary asked to "persist the pin through session-layout restore",
  but the local capture skips every remote window (`App.zig`, `captureLayout`:
  `if (win.remote_dialed != null) continue`), and cross-machine Resume / Restore
  All rebuild from the far agent's blobs, which name the far machine's
  namespace. There is nothing local to persist into, so that half is T3352.
- The TCP path has the same divergence on Mac's side (`name ?? known ?? host`)
  and was out of this task's scope: T3353 (P3).
