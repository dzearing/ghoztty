# T1500 - A script that deletes a tree it did not write still uses the delete a filename can defeat

## Summary

T1499 found that Remove-Item -Recurse -Force cannot delete a directory holding a file named '._.' - the Win32 path parser resolves that leaf to the directory it is standing in, so the delete reports it missing and then refuses the non-empty parent - and gave the cache heal and the whole-cache clear a Remove-TreeHard (scripts/lib/HardDelete.ps1) that survives it. Every other place that deletes a tree whose CONTENTS came from somewhere else - an extracted archive, a fetched package, a downloaded release, a harness sandbox that plants such fixtures - carries the same hazard, and its failure mode is the one that cost 2026-09-12: the delete throws or half-finishes, the caller reads it as a locked file, and the state it was meant to clear stays behind. Sweep the ~298 Remove-Item -Recurse sites under scripts/ and test/win32/, decide per site whether the tree can hold content this box did not write, and route those through Remove-TreeHard. Sites that only ever delete trees we created ourselves can stay as they are - say so per site rather than converting blindly. Worth an audit row afterwards so a new site cannot reintroduce it.
