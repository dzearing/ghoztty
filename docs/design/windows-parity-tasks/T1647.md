# T1647 - The Deadline self-test times its own 8ms sleeps against a 20ms budget, so a loaded box fails the win32 lane

## Summary

T831 landed `Deadline` — a wall-clock budget for a test that waits — and with it
a self-test that proves `progress()` resets the budget:

```zig
var d = Deadline.startWith("...", 20 * std.time.ns_per_ms);
for (0..4) |_| {
    std.Thread.sleep(8 * std.time.ns_per_ms);
    try std.testing.expect(!d.expired());
    d.progress();
}
```

Eight milliseconds against a twenty millisecond budget is 2.5x of headroom, and
that is well inside what Windows' timer slack costs on a busy box: an 8 ms sleep
lands at 20 ms and more whenever anything else is compiling. So the assertion
was measuring the SCHEDULER, not `Deadline`, and it took the lane with it.

Observed the same day it landed, four times: `test-reach-audit.ps1`'s lane arm
(`zig build test -Dapp-runtime=win32`) failed at
`src\remote\test_util.zig:249` in the 13:24, 14:24, 18:24 and 22:51 harness-floor
sweeps, and passed in the 22:24 one — the difference being what else was on the
box. The failure reads as a red win32 lane with no crash and no diagnosis, which
is the most expensive shape of red there is: it makes every OTHER lane result
that morning unusable as evidence.

## The fix

Size the numbers against the scheduler instead of for brevity, and keep the
property: `step` far enough under `budget` that ordinary overshoot cannot reach
it (3x: 100 ms steps against a 300 ms budget), and `steps * step` over the
budget (5 x 100 ms = 500 ms), so a `progress()` that reset nothing would still
fail the loop. The no-progress half then sleeps `budget + step`. The test costs
about 900 ms, which is the price of it meaning something.
