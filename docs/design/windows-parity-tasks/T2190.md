# T2190 - The commit guard pushes a push-rebase that pulled in another lane's source changes without compiling the merged tree first - a broken build reached the trunk

## Summary

2026-10-23: T2187's commit (0c047d1e2) was built and fully tested on a tree
without lane b's T2186 (1de51f746). `git-commit-guard.ps1 commit` hit a
rejected push, pulled with rebase - which brought in T2186's change to the same
module (`pane_stack_slide.at` gained a `resize` argument) - and pushed the
rebased commit straight away. Git merged textually without a conflict, and the
result did not compile; it sat on the trunk until 8b9ce1a89. Nothing between
the rebase and the push looks at whether the pull brought in code.

Fix shape: when the push-rebase pulls in commits touching `src/` or `build.zig`
AND this commit touches `src/`, compile the merged tree (the Debug win32
`zig build`, plus the `lib` lane's build, which is the quick one) before the
push; on failure leave the commit local with a loud `REBASE BROKE THE BUILD`
naming the pulled commits, so the turn fixes it instead of shipping it.
`-NoBuildCheck` hatch for a box with no zig. Acceptance in section W of
`test\win32\go-loop-guard.ps1` with a constructed conflicting-but-textually-
clean pair and a negative control.

## Validation criteria

- [ ] a push-rebase that pulls source changes compiles the merged tree before pushing
- [ ] a merged tree that does not compile is not pushed, and the output names the pulled commits
- [ ] a pull with no source changes pushes with no build (no cost on the common path)
- [ ] negative control: with the check disabled, the constructed broken pair is pushed
