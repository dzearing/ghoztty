# T2673 - window-close-memory.ps1 stamps its guard from a non-default run (-ReleaseSandbox / -Shape / -Report / -Cycles) while the default verdict is red

## In plain terms

The memory test can mark itself "passed" after a special diagnostic run, even while the normal check it guards is failing. Nobody is then told to look.

## Summary

On 2026-11-03 two turns stamped the `window-close-memory` guard green. The runs that stamped it were `-ReleaseSandbox -Report` runs against a ReleaseFast `-ExePath` (lane A at 15:29, commit 7d7a08798; lane B at 17:03). At the same code, the default verdict through `acceptance-parallel.ps1 run -Scripts window-close-memory.ps1` (debug build, 2 warm-ups, 5 cycles) was red: A1 1.53 MB, A8 1.20 MB. The stamp also removed the open guard-ack, so `validate` stopped reporting the red at all.

Fix: stamp only from the default verdict shape, which means no `-ExePath` outside this checkout's `zig-out`, and no `-ReleaseSandbox`, `-Shape`, `-Cycles`, `-Warmup`, `-Report`, `-HeapCensus*` or `-NegativeControl`. A diagnostic run prints `NOT STAMPED (diagnostic run)`. Check the other memory harnesses (`hidden-window-memory.ps1`) for the same shape. Then re-run the default verdict, and hand its red to T2671 with `guard-ack`.

## Validation criteria

- [ ] a `-ReleaseSandbox -Report` green run leaves `window-close-memory.stamp.json` unchanged and prints why
- [ ] the default verdict still stamps on a clean green
- [ ] the guard's current red is acked to T2671
