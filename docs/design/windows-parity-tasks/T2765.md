# T2765 - Composition step 5d-5a: the pane sidebar (a GDI child window) gets a composition tree of its own - a DirectComposition target on its window, built when a motion first asks, rebuilt on device loss - that the sheen, transition, reorder and column-glide visuals (T2801-T2804) hang on

## Summary

Split on claim (the summary asked for it): the four motions are T2801 (sheen),
T2802 (list transitions), T2803 (row reorder) and T2804 (column glide), each
depending on this one. What is left HERE is the thing all four need first.

The sidebar is a `WS_CHILD` that paints with GDI. Every compositor animation
so far hangs on a pane's own tree (`comp_overlay.Slot`, published by the pane
presenter) or on the window's chrome host (opt-in); the sidebar has neither.
Give it one: `child_comp.zig`, a D3D11 device (hardware, then WARP), a
DirectComposition device, a TOPMOST target on the sidebar's window and an
empty root visual, published into a `comp_overlay.Slot` the sidebar owns - so
the motions use `comp_overlay.Layer` exactly as the hover tint and the
scrollbar do. Built lazily (a sidebar that never animates pays nothing),
backed off after a failed build, and rebuilt on device loss with the layers
re-syncing onto the new generation.

Oracle: debug seams `GHOZTTY_DEBUG_SIDEBAR_COMP_FILL` (hang a cover layer on
the tree at placement) and `GHOZTTY_DEBUG_SIDEBAR_COMP_LOSS` (report the
device lost once), read by `test\win32\sidebar-comp.ps1` from the log.

## In plain terms

The pane sidebar's animations (the shimmer on a busy row, rows sliding, the
column opening and closing) are drawn by the app one frame at a time, so they
stutter whenever the app is busy. This step gives the sidebar its own layer
that Windows itself can animate. Nothing changes on screen yet; the next four
tasks move each animation onto it.

## Goals

- [x] the sidebar can build its own composition tree, on demand
- [x] a layer hung on it joins the tree and uploads (on-screen look: the motions' films)
- [x] a lost graphics device rebuilds the tree and the layer comes back
- [x] a sidebar that never asks builds nothing

## Validation criteria

- [x] a sidebar on show that nothing animates builds NO tree (lazy): `test\win32\sidebar-comp.ps1` plain arm, 0 trees and 0 build attempts logged
- [x] the tree builds on demand on the sidebar's own window and a `comp_overlay.Layer` joins it and uploads: fill arm, `composition tree up for=debug-fill adapter=hardware build=1 generation=1` + `composition fill attached build=1 generation=1`, exactly one tree after a re-placement
- [x] a lost device drops the tree, the next ask rebuilds it, and the layer comes back on the NEW generation: loss arm, `tree lost: simulated`, `build=2 generation=3`, fill re-attached at generation 3 (was 1), exactly two trees (no rebuild loop)
- [x] the build back-off (1 s, 5 s, 30 s, then give up; a good build forgives) is unit-tested: `child_comp.zig` `Policy` tests, win32 lane
- [x] the oracle can fail: `-NegativeControl` (expects a tree in the plain arm) exits 1 on exactly that row
- [ ] NOT COVERED here: the layer's pixels on screen (a background desktop cannot be photographed; WM_PRINTCLIENT reads the GDI pixels, not the tree) - the motions' own films carry it (T2801-T2804)
