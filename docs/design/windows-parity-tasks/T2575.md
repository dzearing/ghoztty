# T2575 - With no redirection surface (GHOZTTY_COMP_NOREDIR) the whole client still lands one drag step after the frame: time the size message from the frame change to its last commit against the film, and find what puts the new size and the content in one compose

## Summary

T2548 filmed GHOZTTY_COMP_CHROME+PRESENT with and without NOREDIR (ReleaseSafe): redirected 41/60/41/65 bad of 65-68 frames, no-redirection 35/66/42/76 of 77-84. Without the surface the page and its address bar always agree and the shape is pure lag: right=2 on shrink is the whole client exactly one 12 px step behind the frame, even the layered nav-bar child moved inside the same WM_SIZE. So DWM shows the new frame before the size message finishes. Measure (GHOZTTY_RESIZE_TRACE QPC vs frames.txt compose times) when the frame change lands against the last commit of the pass, then try what can hold the frame to the content: a size message short enough to fit before the next compose, DwmFlush/compositor-clock pacing now that the chrome is one commit, or presenting the panes and the tree at the new size before the window takes it. Re-film with scripts\resize-sync-onscreen.ps1.

## In plain terms

When you drag a window's edge, the outline moves first and the inside follows
one screen refresh later. This task timed exactly why: redrawing the inside
takes about two refreshes on a 120 Hz screen, and the outline is shown after
one. Two fixes follow from it (T2577, T2578).

## Goals

- [x] time each step of the size message against the film's compose times
- [x] find what decides whether the content makes the frame's compose
- [x] try pacing the frame change to the compositor clock

## Findings (2026-10-31)

ReleaseSafe `zig-out-rsafe`, `GHOZTTY_COMP_CHROME=1 GHOZTTY_COMP_PRESENT=1
GHOZTTY_COMP_NOREDIR=1 GHOZTTY_RESIZE_TRACE=1`, `scripts\resize-sync-onscreen.ps1
-KeepFrames`, right-shrink, 12 px steps, a 120 Hz display (composes 8.33 ms
apart). Per frame the page, terminal and nav-bar edges were read off the film
and joined to the trace by QPC (frames.txt and the trace share the 100 ns clock).

Unpaced (as shipped), per step, from the frame change (`WM_NCPAINT` at the new
width, right after `WM_NCCALCSIZE`):

| phase | ms after the frame change |
|---|---|
| WM_SIZE starts | ~1 |
| pane batch ends (children moved) | ~5 |
| regions cut | ~13 |
| desk/bands painted | ~14 |
| frame wait ends (every pane presented) | ~15-16 |
| WM_SIZE returns | ~21 |
| **new frame on screen** | 8.5-22 |
| **new content on screen** | 21-34 (always one compose after the frame) |

The whole client (terminal edge, page, nav bar) moves on screen together and
always one compose after the frame - no frame shows a pane at one size and its
neighbour at another, only all of them a step behind.

**Paced** (experiment, reverted: `DwmFlush()` in `WM_NCCALCSIZE` while inside
the size loop, so the frame change starts ~1 ms after a compose): the noise
goes and the rule shows. The new frame is on screen at +10-15 ms (the compose
after next, every step); the frame wait ends +12-16 ms; the content is on
screen one compose after the frame, every step. Bad frames per step unchanged
(43 of 123 shrink, 51/127 grow, 50/125, 50/122 vs 41/66 ... unpaced, ~1.4 per
step either way). So DWM latches about one period after the compose
`DwmFlush` returned on: a frame change or a present made within ~6-7 ms of the
frame change goes up together, and the pass takes twice that.

**What puts the size and the content in one compose**, from that rule: the
content has to be presented within the same latch period as the frame change.
Two ways there:

- make the pass from frame change to last present fit in ~6 ms (today ~14-16):
  T2577 (P0, M1);
- present the content at the new size BEFORE the frame changes
  (`WM_WINDOWPOSCHANGING`), so the frame change follows the last present by
  ~1 ms: T2578 (P0, M1).

Pacing by itself is not a fix (the pass is longer than the latch period), but it
is the instrument that makes either one measurable step by step. T2516 now also
waits on T2577 and T2578.
