# T1462 - A short output burst presents 500 frames a second nobody can see

## Summary

Measured 2026-09-08 (T1458). On a SHORT output burst the loaded pane presented at
**421-514 fps**, with `wakeups_per_s` tracking it one for one - every wakeup
became a present.

**Re-measured on an OPTIMIZED build the same day (T1463): 2,905-4,192 fps**,
`swap_avg_us` 56-62, `swap_max_ms` 0-1. The 421-514 figure was off a Debug build
and understated this by roughly 8x - the faster the rest of the pipeline gets,
the more frames the uncoalesced path produces for nobody. Use the optimized
number as the baseline; the Debug one is kept only because it is what the first
capture said. No display on this box can show more than a small fraction of
that, so the great majority of those frames are drawn, uploaded and swapped for
nobody.

Under a SUSTAINED stream the same pane settles to 12 fps, so this is not the
cause of T1458's lag and is deliberately not filed as part of it. It is filed
because it is waste on its own terms, and it is worse than ordinary waste on the
kind of desktop this box runs: a streamed session re-captures and re-encodes the
window every time it changes, so 500 presents a second is 500 capture-and-encode
cycles a second for a screen the viewer sees at 60.

P2, not P0: nothing is broken, nobody reported it, and the sustained path - which
is what T1458 is about - does not go through it.

## In plain terms

When a command prints a short burst, the terminal redraws hundreds of times a
second even though a screen can only show a fraction of that. Nobody can see the
difference, but the machine does the work anyway - and on a streamed desktop it
also makes the streamer re-send the window each time. Capping it costs nothing
visible and saves all of it.

## Details

`renderer/Thread.zig` already distinguishes `wakeup` (which coalesces) from
`draw_now` (which does not) - see the comment at `renderer/Thread.zig:66`. The
question this task answers is why a burst of small agent-fed chunks produces a
present per wakeup rather than riding the coalescing path, and whether the frame
rate should simply be bounded to the display's refresh.

Take the measurement with T1458's workload: the 4,000-chunk run is the one that
shows the burst regime, and the 400,000-chunk run settles and hides it.

## Goals

- [ ] A burst no longer presents materially faster than the display can show.
- [ ] Sustained behaviour is unchanged - this must not cost latency at 12 fps,
      which is the regime T1458/T1461 care about.

## Attempt 1 (2026-11-10, lane b) - a timer cap, measured and NOT shipped

The obvious fix was tried and backed out because it made the sustained case worse.

**What it did.** In `renderer/Thread.zig` `wakeupCallback`, an output wakeup
that lands inside the display period behind the last `updateFrame` armed
`render_h` for the rest of that period instead of rendering immediately.
The pure rule lived in a new `renderer/present_cap.zig`. The first frame after
a quiet spell and any forced frame went straight through. Win32 opted in with
`App.presentPeriodNs()`, the DWM refresh period cached for 1 s, plus a
`GHOZTTY_PRESENT_CAP=off` seam. Mac was not touched: Metal paces itself on
its CVDisplayLink (`hasVsync()`).

**What it measured** with an acceptance draft (`burst-present-cap.ps1`:
GHOZTTY_PERF per-pane `fps=` + `wakeups_per_s=`, test desktop, full
ReleaseSandbox), on a 120 Hz box:

| build / path / workload | uncapped fps (wakeups/s) | capped fps (wakeups/s) |
|---|---|---|
| Debug, local pane, scrolling 200-write bursts | 29-40 (30-40) | 24-27 (250-700) |
| ReleaseFast, local pane, scrolling | 41-53 (42-53) | 24-27 (900-1,300) |
| ReleaseFast, local pane, CR repaint (no scroll) | 16-18 (16-18) | 16-18 (16-18) |
| ReleaseFast, agent-backed pane, scrolling | no samples (run broke) | 35-58 (830-1,200) |

What that table shows:

1. **The thousands-of-fps regime did not reproduce** on any of these workloads.
   Uncapped presents tracked wakeups 1:1 at under 60 fps. On a local pane each
   scrolling frame costs ~20 ms, and the async wakeup coalesces everything that
   arrives during it. On a CR-repaint stream, ConPTY coalesces to ~17 updates/s
   before the app sees anything. The 2,905-4,192 fps figure came from T1458's
   agent-backed Claude-shaped workload (lost with that session's scratchpad),
   from before many renderer changes (T1935 present-only-what-changed, T1951,
   T2232). Reproduce it first, or close this as no longer reproducible.
2. **The timer cap HALVED the sustained local frame rate** (41-53 -> 24-27 fps),
   while wakeups rose 20x. On a ~20 ms frame an 8.3 ms cap should never even
   engage. The likely reading: once the renderer stops queueing on the
   terminal mutex every wakeup, the IO thread takes it in many more short
   holds (1,100 processed wakeups/s), and `updateFrame` waits longer behind
   them. A second factor is that xev timers on Windows tick at the default
   ~15.6 ms resolution, so a held tail frame can wait a whole tick for an 8 ms
   request. That is a visible smoothness loss, which goal 2 forbids.

**For the next attempt:**

- Reproduce the regime first, on the agent-backed path (`--session-persistence=true`
  under `Set-GhozttyTestIsolation -ReleaseSandbox`), with a Claude-shaped
  workload: streamed tokens, a spinner, and a CR status repaint every 7th
  write. If it does not reproduce, close with that evidence.
- If it does: do not hold frames on an xev timer. Instead, skip the PRESENT
  (not the build) inside the period and let the next wakeup or a vblank
  carry it. Or make it moot via T2610's window presenter, which paces presents
  to compose (`GHOZTTY_WINDOW_PRESENTER`, still off by default). Any version
  must keep the sustained local-pane fps from the table above.
- The draft harness and full patch were kept out of the tree; the design is
  above. The lab draft's control arm (cap off must exceed the bound) is the part
  worth keeping, because it is what caught this.
