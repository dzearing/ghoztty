# T2625 - Pane-tree mode (GHOZTTY_COMP_PANE_TREE): after a split the left pane's visual shows its text stretched to about twice its width, so comp-present-onscreen.ps1 -Arms tree is red on tree.split-left.8, tree.10 and tree.14

## Summary

Found by T2570 on 2026-11-01 (lane b, HEAD 4972a07b7 plus T2570's clip change, and the same with that change disabled - identical numbers, so it predates T2570). `scripts\comp-present-onscreen.ps1 -Arms tree` (GHOZTTY_COMP_PRESENT=1, COMP_CHROME=1, COMP_PANE_TREE=1): the single pane matches capture-pane 1.000, but after `+split --direction=right` the LEFT pane (471 px wide) shows its text at roughly double width on the WGC grab - "D:\git\ghoztty-b>fo" fills the pane - so it scores match 0.129 at +245 instead of +93, tree.10 (right pane sits right of left) and tree.14 (dim wash on one pane only) go red with it. The right, newly adopted pane is fine (0.906). The T2562 run of the same arm was ALL PASS 30, so something between T2562 and 4972a07b7 broke it; the window-presenter (T2614/T2615) and resize-content (358c4e890) commits are the first suspects to bisect. Shape of the picture: the old swap chain's buffer is shown scaled into the shrunk visual, or the renderer drew a half-width grid scaled up - read the presenter's ResizeBuffers / SetMatrixTransform on the tree path first.

## In plain terms

In a test-only drawing mode that is meant to become the default, splitting a terminal in two makes the left half show its text stretched sideways. Nobody uses that mode yet, but it has to be right before it can be switched on.

## Root cause

Not the presenter's window path: T2598 (d3310641b) made the composition swap
chain grow in 256 px buckets and present each frame as an
`IDXGISwapChain2::SetSourceSize` rectangle. A composition chain can only use
`DXGI_SCALING_STRETCH`, so it stretches that source rectangle over the whole
buffer. The split shrank the left pane from ~950 to 471 px while its buffer
stayed 950 wide, so the frame showed at ~2x; the newly made right pane's buffer
was exact and looked fine. Every bucketed grow (a window-edge drag) was
stretched by up to a bucket as well. `GHOZTTY_COMP_RESIZE_BUFFERS=1` (exact
resizes) turned the arm ALL PASS 33 before any code change.

Fix: with every source size, `SetMatrixTransform` scales by source/buffer
(`gl_comp_present.sourceTransform`), the documented pairing; a chain that
refuses either call is reset to identity and drops to exact resizes.
