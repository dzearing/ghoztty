# T3554 - Linux: a subframe on a GTK viewer page can post a quote, headings or a find count on the viewerTOC bridge; win32 accepts only linkMenu from a subframe

## Summary

links.js is injected into ALL frames (Viewer.zig installLinkScript), so every iframe - an ad on a website - has window.webkit.messageHandlers.viewerTOC, and WebKitGTK's script-message-received carries no frame. Viewer.onScriptMessage therefore acts on a subframe's quote (T3545: opens the composer and files the passage into the report), headings, active and find exactly as on the top frame's. win32 bounds this natively (ViewerPane.onFrameMessage acts on a subframe's linkMenu and nothing else; viewer_bridge subframe_js). Fix: give subframes their own handler name (register a second handler, inject links.js into subframes with a guard that posts there, keep the top-frame scripts on viewerTOC) or use webkit_user_content_manager_register_script_message_handler with a world and check the frame, so only linkMenu is accepted from a subframe. Test: a website fixture with an iframe that posts {type:quote} must leave the composer closed and quoted=0.

## In plain terms

On Linux, a web page shown in a viewer pane could contain an embedded frame
(an ad, a widget) from another site, and that frame could pretend to be the
page: drop a passage into your feedback report, rewrite the page's table of
contents, change the find count, or ask Ghoztty to open a local file. Now an
embedded frame can only do what it can on Windows - get the right-click link
menu on its own links - and everything else it sends is ignored.

## Goals

- [x] Page messages are told apart by the frame that sent them, without the frame being able to lie about it
- [x] A subframe's quote, headings, active heading, find count and file link are dropped (and logged)
- [x] A subframe's link still gets the link menu
- [x] The top page's messages work exactly as before

## Design

WebKitGTK's UI-process API has no frame on a script message (`WebKitFrame` is
web-process-extension only, checked in the 2.52 headers), so the frame check
cannot be made on the message. Instead the native handlers moved into a
private script world (`ghoztty`) that no page script can see, and two user
scripts bridge to them: a page-world shim in every frame (document start)
that defines `window.webkit.messageHandlers.{viewerTOC,ghozttyFileLink}` and
fires a DOM event on its own document, and a private-world relay in every
frame that forwards that event on `ghozttyTop` or `ghozttySubframe` by
`window.top === window`. A cross-origin frame cannot reach the top document,
so its road ends at the subframe handler, which takes only `linkMenu`. The
shared page scripts (`links.js`, `find.js`, `selection.js`, `viewer.js`) are
unchanged. Rejected: moving our scripts into the private world (the template's
own `viewer.js` and every `evaluate_javascript` call run in the page world),
and a shared-secret token (a same-world shim cannot keep it from a frame that
shares the top's origin any better than this, and it needs every poster
changed). Code: `src/apprt/gtk/viewer_frames.zig` (none lane), `Viewer.zig`
`installFrameRelay` / `onTopMessage` / `onSubframeMessage`.
