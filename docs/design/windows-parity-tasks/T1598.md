# T1598 - The sibling harness audits still sweep the top level only, so lib\ can hide a violation from each of them

## Summary

T780 widened the input-desktop audit to test\win32\lib\ because a harness helper can make every script that calls it input-desktop-only while the sweep reads none of them. The scope argument is not specific to that rule: DesktopLaunchAudit enumerates $Root\*.ps1 alone, and the harness-floor family around it (exit codes, skips, verdicts, isolation, capture, body-complete, asserted-nothing) each sweeps the same top level. Ask of each one whether a lib\ helper could carry the defect it looks for - a helper that launches on the user's desktop is the obvious yes - and widen the ones where it could, with the same per-file stated-intent marker rather than a directory exclusion. Where the answer is genuinely no, say so in the header, measured, so the next reader does not have to re-derive it.

## In plain terms

The test suite has automated checkers that read every test script looking for
known mistakes, like a test that opens a window on the user's screen. Most of
them read the shared helper folder too, but a few read only the top level, so
a mistake inside a shared helper (used by dozens of tests) could slip past.
This closes the gap for the one where it mattered and writes down, with
measurements, why the rest are safe.

## Goals

- [x] Ask every harness-floor audit whether a `lib\` helper could carry its defect (inventory below)
- [x] Widen the desktop-launch audit (the clear yes) to `lib\`, with a per-file stated-intent marker
- [x] Say so, measured, in the header of each audit that stays top-level
- [x] File the one remaining "could, but not yet widened" case (T3296)

Top level only, and correctly so: verdict-exit, asserted-nothing,
body-complete. Their rule is about a run's own verdict, and the five `exit`
statements in `lib\` are three skip exits that print SKIP first, the scorer's
own verdict exit, and a pane fixture. Header: `lib\VerdictExitAudit.ps1`.
isolation-meta: isolation is the script's process environment, and a helper
inherits it. build-mode-guard section I: a release subject is named by a
script's own `param()` default, and helpers have none.

Widened: **desktop-launch**. Before the widening, `lib\` held two flagged
sites, both false: BuildMode's agent `--build-mode` probe (the parameter was
named like the app, now `-AgentBinary` with an `-Exe` alias) and
FrameLabDriver's `& $Exe @Arguments` wrapper, whose calls pass only `+split` /
`+rearrange`. The analyzer now scores a splatted-parameter wrapper at its calls.

Could, not yet widened: persistence-flag / stderr-launch-capture
(PersistenceSweep). Two `lib\` launch sites today, both fine, but widening
needs TestDesktop's argv-forwarding shape recognised first: T3296.
