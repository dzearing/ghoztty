# T2580 - On a right-edge shrink the terminal trails the viewer page by one drag step (gap=9 on most filmed frames, with or without T2578's pre-layout): find why the terminal's present misses the compose the page makes, then retry pre-layout for shrinking drags

## Summary

T2578 filmed `scripts/resize-sync-onscreen.ps1` (ReleaseSafe, CHROME+PRESENT+NOREDIR) on one build with the pre-layout on and off (`GHOZTTY_RESIZE_NOPRELAYOUT`). On right-shrink the off run lists `gap=9 right=2` on nearly every bad frame: the page is a step behind the frame and the terminal a step behind the page. With the pre-layout on, `right=` mostly went away but `gap=9` stayed, and the bad-frame count per step did not drop (1.2 -> 1.5). So the terminal's present (OpenGL swapchain) misses a compose that the viewer's page makes, even when both are presented before the frame changes. A shrink pre-layout also needs the desk under the strip the panes leave: `deskRect` now covers the old client while `pending_client` is set, which took the flat frames from 13 to 0.

Do: time the terminal's present against the page's (`GHOZTTY_RESIZE_TRACE`, `wait-end`, frames.txt QPC) on a right-shrink, find why it is one compose later, fix that, then drop the `dw < 0 or dh < 0` gate in `resize_prelayout.pendingClient` and re-film. Films: `%TEMP%\t2578-film-off`, `-on`, `-on2`, `-final`.

## In plain terms

Dragging the window's right edge narrower with a terminal beside a web page,
the panes briefly disagree about where the divider is. This task set out to
find why the terminal is late. The answer: the terminal is not late relative to
the page's address bar; the page is EARLY, landing with the window frame while
the terminal and the bar arrive one refresh later. The fix moves to T2659.

## Findings (2026-11-02)

The film's `right=` measures the viewer's **bar**, and `gap=` is measured off
the **page**, so "terminal trails the page" was a reading of the scorer, not of
the frames. With the bar as the reference, every bad right-shrink frame is the
page at the new geometry beside a terminal and bar at the old one (baseline
28/49, `%TEMP%	2580-base`). A/Bs on one ReleaseSafe build, right-shrink:

| arm | bad | shape |
|---|---|---|
| baseline | 28/49 | page new; bar + terminal one step old |
| page bounds set at the END of the pass | 30/43 | unchanged |
| terminal Present sync interval 0 | 28/46 | unchanged |
| shrink pre-layout (`GHOZTTY_RESIZE_PRELAYOUT_SHRINK=1`) | 31/51 | all content a step AHEAD of the frame (`right=26`), page further ahead (`gap=9`) |
| shrink pre-layout + interval 0 | 36/51 | same |

Trace (`GHOZTTY_RESIZE_TRACE`): a shrink pre-layout runs 12.3 ms (viewer bounds
+2 ms, terminal present +8 ms, bar paint +11.5 ms, frame change +14 ms) - longer
than a 120 Hz compose, so each surface lands in its own compose. The terminal
and bar always land together, a compose behind the frame and the page,
whatever their timing in the pass: the lag is in how child-window content
reaches DWM, not in the present. Split to **T2659**. The shrink gate stays;
`GHOZTTY_RESIZE_PRELAYOUT_SHRINK` is kept as the A/B knob for re-filming it.
