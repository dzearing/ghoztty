# T2580 - On a right-edge shrink the terminal trails the viewer page by one drag step (gap=9 on most filmed frames, with or without T2578's pre-layout): find why the terminal's present misses the compose the page makes, then retry pre-layout for shrinking drags

## Summary

T2578 filmed `scripts/resize-sync-onscreen.ps1` (ReleaseSafe, CHROME+PRESENT+NOREDIR) on one build with the pre-layout on and off (`GHOZTTY_RESIZE_NOPRELAYOUT`). On right-shrink the off run lists `gap=9 right=2` on nearly every bad frame: the page is a step behind the frame and the terminal a step behind the page. With the pre-layout on, `right=` mostly went away but `gap=9` stayed, and the bad-frame count per step did not drop (1.2 -> 1.5). So the terminal's present (OpenGL swapchain) misses a compose that the viewer's page makes, even when both are presented before the frame changes. A shrink pre-layout also needs the desk under the strip the panes leave: `deskRect` now covers the old client while `pending_client` is set, which took the flat frames from 13 to 0.

Do: time the terminal's present against the page's (`GHOZTTY_RESIZE_TRACE`, `wait-end`, frames.txt QPC) on a right-shrink, find why it is one compose later, fix that, then drop the `dw < 0 or dh < 0` gate in `resize_prelayout.pendingClient` and re-film. Films: `%TEMP%\t2578-film-off`, `-on`, `-on2`, `-final`.

## Validation criteria

- [ ] right-shrink film shows no `gap=` frames (terminal and page agree) on the pre-layout path
- [ ] with the shrink gate removed, right-shrink bad frames per step drop below the T2578 baseline (36/78), flat_background stays 0
- [ ] the floor lanes and comp-chrome.ps1 stay green
