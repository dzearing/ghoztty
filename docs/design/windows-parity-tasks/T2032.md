# T2032 - Audit acceptance fixtures that chain +split --target=<window> and assume the new pane became active (T1797 made a no---focus split keep the active pane; viewer-restore.ps1 was missed)

## Summary

Since T1797 (2026-10-10) a `+split` without `--focus` leaves the tab's active pane where it was. T1797 moved seven harnesses to `--focus`; viewer-restore.ps1 was missed and sat red for weeks with a layout it never meant to build (T2015). Sweep `test\win32\` for fixtures that issue a second `+split --target=<window>` (or a window-targeted verb) after a split and expect it to land on the NEW pane. Fix each by anchoring with `--pane=<name>` (preferred: no focus side effect) and add a setup control that asserts the built layout, the way viewer-restore.ps1 D0 does.

## In plain terms

Several automated tests build a multi-pane layout by saying "split the pane I
just made". Since October the app no longer moves focus to a new pane, so those
requests quietly split the original pane instead and the tests measured a
layout they never meant to build. This points each one at the exact pane it
means. Nobody using the terminal sees a difference; the tests become honest.

## Goals

- [x] find every fixture that splits off a pane an earlier unfocused split created
- [x] anchor each one on the exact pane (`--pane=`)
- [x] every touched harness green (pane-hwnd-reap's B1/B2 red is T2921's leak, guard-acked; its setup passes)

## Audit result

Scanner shape: a `+split --target=<X>` where `<X>` was `--name`d by an earlier
`+split` in the same file without `--focus`. `--target` resolves a pane name to
its window and splits that window's *active* pane, which since T1797 stays the
original one. 14 lines in 10 harnesses, all converted to `--pane=<X>`:

| Harness | Line(s) | Did the wrong layout matter? |
|---|---|---|
| comp-chrome | 251 | no (composition checks, any layout) |
| drag-glide | 224, 225 | no (a `+rearrange` sets the row afterwards; the row is asserted) |
| focus-glow-comp | 134 | no (glow moves by name) |
| font-inherit | 138 | by luck no (the original pane is also full width) |
| hidden-window-memory | 173 | no (memory numbers over 4 panes) |
| idle-frame-release | 167 | no (frame release over 4 panes) |
| pane-hwnd-reap | 126 | no (counts child windows) |
| pane-sidebar-motion-cost | 143, 145, 147 | yes - the stack it measures was a different shape; 5 visible panes asserted |
| relaunch-attach | 263, 264 | yes - the restored layout was not the one the comment describes |
| session-persistence | 456 | yes - `P0 \| (spA / spB)` was really `(P0 / spB) \| spA` |

Not flagged and why: every other second split targets a window name or a
window's first pane (still the active one), uses `--pane`/`--focus` already, or
is a CLI-parse test that never builds a layout. viewer-restore was T2015.
