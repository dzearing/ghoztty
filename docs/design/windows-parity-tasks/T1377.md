# T1377 - Activity Monitor acceptance: M1's ctrl-click sometimes does not land, so the batch-kill section flakes

## Summary

Seen once in three consecutive runs on 2026-09-05 while validating T567: 'M1 ctrl-click ADDS row 2 to the selection (selected=1, want 3)'. The runs either side were ALL PASS over the same binary, so the posted ctrl-click is being dropped (or arriving before the row it names is painted) rather than the selection code being wrong. A flake in an acceptance script is a guard that sometimes lies, so the fix is to make M1 wait for the state it expects instead of sleeping - the same shape Wait-PanelShown gave the row counts.

## In plain terms

One of the Activity Monitor's automated checks sometimes failed even though
the app was fine: it ctrl-clicks rows to build up a multi-row selection, and
once in three runs the count came out wrong. The real cause was that the rows
were sorted by CPU usage, which changes every second and a half, so a click
could land on a row that had already been selected and deselect it. A fix
three hours later sorted the rows by process id, which never changes. This
task confirms that fix holds.
