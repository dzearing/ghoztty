# T1935 - Typing lags badly in every pane: with 20 Claude panes open the app burns 5-15 cores (every pane's background threads ~50% busy) and the pane sidebar re-lays out all 14 windows ~6 times a second

## In plain terms

Typing in any Ghoztty pane lags badly: keystrokes show up late in every window, including plain
shells. The app itself is the busy process. With 14 windows and 20 terminal panes open (most of
them Claude Code sessions with an animated title spinner), Ghoztty used 5 to 15 of the machine's
32 cores for hours, and nothing in those panes was producing much output.

## Summary

User report (2026-10-14, ~16:20 local, box dzearing1): "there seems to be a bug in ghoztty
causing massive lag in typing".

Build: `ghoztty +version` -> `1.39.7+99590020e` (ReleaseFast, OpenGL renderer, libxev iocp),
installed at `%LOCALAPPDATA%\Programs\Ghoztty`. App pid 37564, started 13:50:33.

### Evidence (all from the live process, no debugger)

1. **The app burns many cores continuously.** `TotalProcessorTime` was 130,950 CPU-s after
   ~2.4 h of wall time, which averages about 15 cores. Live 5 s samples read **13.1 cores**, and
   later 3 s samples **4.9 cores**. The box has 32 logical cores, so this is not CPU starvation
   of the whole machine. The lag is inside Ghoztty.
2. **The cost is spread over the per-pane background threads, not the UI thread.** 108 threads.
   In a 5 s sample about 30 threads were each 30-57% busy (1.5-2.9 s of CPU per 5 s); in a 3 s
   sample 12 threads were >20% busy and 21 were >5%. Most hot threads started at 13:50:34 (the
   restored session's panes). The rest started in pairs at the moments panes were opened later
   (two at 15:58:32, one each at 15:55:15, 15:17:38, 14:23:23, 16:13:13), which is the shape
   of one renderer thread plus one IO thread per surface. Each of the original threads had
   ~3,900-4,000 CPU-s, so each one had been about 45% busy since launch. The main/UI thread
   (tid 44568) had only 630 CPU-s total and was ~11% busy in the sample, so it is not pegged.
   It does share the terminal locks with those threads, though, so contention is the likely
   path from "background threads busy" to "keystrokes late".
3. **The pane sidebar re-runs its whole all-windows layout ~6 times a second while idle.**
   `%LOCALAPPDATA%\ghoztty\ghoztty.log` was ~3.9 MB and rotated within minutes. Its last ~6
   minutes held 2,396 `info(pane_sidebar): pane sidebar outline mode=expanded ...` lines and
   2,396 `pane sidebar all-windows groups=14 panes=22 lines=12 ... order=<every window title>`
   lines, plus ~370 `pane sidebar rows ...` lines per window. Each line is several KB because
   it serializes every window title and pane GUID. That is about 6.6 full sidebar recomputes a
   second, each logged at `info`, with nobody touching the UI. The likely trigger is title churn:
   Claude Code animates its title (`◐ ◑ ✳ ...`) several times a second in all ~13 Claude panes,
   and each OSC title change appears to recompute the sidebar for all 14 windows
   (O(windows x panes) per spinner tick). The `info`-level formatting and log writes are a
   second, avoidable cost on top.
4. **Memory is high**: private bytes 2,869 MB / working set 2,895 MB, 1,303 handles, for 22 panes.
   Worth a heap check once (1)-(3) are fixed. It may be scrollback, or growth.
5. **Side note: an orphaned agent.** `ghoztty-agent` pid 23868 (started 2026-10-09 03:06, 79 MB,
   34 threads) had used 45,267 CPU-s, about 12.5 CPU-hours, though it was idle (~0.06 cores)
   at sample time. The other 21 agents (one per pane) were 2-40 CPU-s each. If it is not the
   persistent session host, it is a leak from an earlier app instance.

No stacks: there is no `cdb`/WinDbg on the box, and the installed build has no PDB (T1936), so
the hot frames could not be symbolized. That is the first thing to get on a repro.

### Likely causes to confirm (in order)

- **Per-surface renderer/IO threads redrawing or waking on every title/OSC change**, or on a
  continuously running animation (spinner title, the progress glow from main fd30385fd, bell
  border, dim overlay), instead of only when cells change. A surface that is not visible, in a
  background window, should not redraw at all.
- **The sidebar recompute per title tick** (point 3). Mac found the same class of bug and fixed it
  in main 321e61d7c (shimmer and question ring re-ran the whole sidebar every frame). T1925 is
  the "measure it on Windows" task, and this report is the measurement: it is hot.
- **The info-level sidebar logging**: several-KB lines at ~13/s, so the log rotates every few
  minutes and buries everything else in it.

## Repro

1. Open ~14 windows / ~20 panes, most running `claude` (its title spinner animates while it
   works) and a few idle shells, with the pane sidebar in all-windows mode.
2. Leave it for a few minutes and watch `Get-Process ghoztty` CPU and the per-thread deltas
   (`$p.Threads | % TotalProcessorTime` sampled twice). Expect several cores and ~half-busy
   per-pane threads.
3. Type in any pane: echo is visibly late.
4. `ghoztty.log`: count `pane sidebar outline` lines per second.

## Fix direction

- Capture a symbolized CPU profile first: WPR `-start CPU` or a build with PDBs (T1936), then
  name the hot frames before changing code.
- Coalesce title-change -> sidebar work: one recompute per frame at most, only for windows
  whose sidebar is visible, and only if the displayed text actually changed.
- Do not redraw surfaces whose cells did not change, and never for occluded or background
  windows. A title change must not wake the renderer.
- Drop the per-recompute sidebar lines to `debug`, or log only on structural change.

## Goals

- [x] Find the hot path with real stacks before changing code
- [x] A pane whose only output is a title change draws no frames
- [x] Real output still draws at full speed
- [x] Title changes no longer rebuild every pane sidebar on each tick
- [x] The sidebar's per-rebuild log lines are gone from the release log

## What the profile found (2026-10-14)

A debug build on the test desktop: 6 windows, 12 panes, each running a script
that only changes its title (OSC 0) every 100 ms, the way Claude Code animates.
Perf telemetry (`GHOZTTY_PERF=1`) and cdb stack samples with the PDB.

- **Every pane drew 10 frames a second from its title alone.** Each output
  chunk wakes the renderer, and the renderer presented a full frame even when
  no cell had changed. The busiest threads in the stack samples were
  `nvoglv64` (the NVIDIA OpenGL driver), one per pane. This matches the
  report's "per-pane background threads ~50% busy".
- **Every title change rebuilt the pane sidebar right away**, from two places
  (`onPaneTitleChanged` and `updateWindowTitle`). Each rebuild also refreshed
  every all-windows list and wrote several KB of `info` log.
- With session persistence on, the same setup cost about twice as much (0.46
  against 0.21 cores, same sandbox).

## Validation criteria

- [x] Idle CPU drops by a large factor in a title-churn scenario, measured with a
  per-thread sample before and after. *Measured on a debug build, 6 windows and 12
  panes, each pane changing its title every 100 ms (sandboxed config, no
  persistence): **0.21 -> 0.04 cores**, using `repro` samples recorded in the
  progress log. **Not measured here:** the user's exact load (14 windows, 20
  panes, real Claude Code sessions). That needs Claude running in the panes,
  which a test may not do. Re-measure on the user's box once the release is
  installed.*
- [x] No per-pane thread above ~2% busy while its pane prints nothing. *Same repro
  after the fix: the busiest thread was 0.6%, against up to 5.6% before.*
- [x] `pane sidebar outline` / `all-windows` lines appear only on structural changes,
  and the log no longer rotates within minutes. *The per-rebuild geometry lines
  (`rows`, `outline`, `all-windows`, `tips`) are now `debug`, so a release build
  writes none of them. A title-driven rebuild is coalesced to at most one per 250 ms
  per window, plus one app-wide all-windows pass: `title-churn-redraw.ps1` D, 167
  rebuilds for 921 title changes, against one per change before.*
- [ ] Keystroke echo latency in a plain shell pane under that load matches a single-window
  baseline. **NOT RUN:** a measured echo test needs real keyboard input, which the
  test desktop cannot deliver, and the user is present. The cause it measures (the UI
  thread rebuilding sidebars and formatting KB log lines on every spinner frame) is
  removed and measured above.
- [x] A symbolized profile of the before state names the hot path. *cdb stack samples
  with the debug PDB (6 samples, `!runaway` plus all-thread stacks): the hottest
  threads sat in `nvoglv64` (the NVIDIA GL driver), one per pane. `GHOZTTY_PERF=1`
  showed every pane presenting 10 fps from title changes alone. The UI-thread
  half: `onPaneTitleChanged` and `updateWindowTitle` each called `syncPaneSidebar`
