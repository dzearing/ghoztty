# T1645 - A viewer pane keeps filing feedback against the repository its folder used to be in, for five minutes after that changes

## Summary

Recurrence of the flake T678 closed with b601768f1. On 2026-09-17 the harness floor lane went red on test-reach-audit.ps1, whose section B1 runs a nested 'zig build test -Dapp-runtime=win32': the lane failed on apprt.win32.ViewerPane.test 'host floor: a real controller on a real window, on this box' with '[tripwire] (warn): untripped point=read'. The same audit re-run ALONE passed (14 assertions), and a standalone floor-lane.ps1 -Lane all on the same tree passed the win32 lane, so this is the T592/T678 shape: a live WebView2 controller starved while 27 other audits compete for the box. Cost is a 17-minute re-run of the whole harness lane every time it lands, and it cannot be parked in HARNESS_FLOOR_PENDING because that list is a ratchet that fails on a green member. Likely remedy: have test-reach-audit's nested lane wait for WebView2 settle the way floor-lane.ps1 does between lanes, or run it with the live host-floor test filtered out since reaching-the-code is what that audit measures.

## In plain terms

Open a viewer pane on a file, then turn that file's folder into a git
repository. The pane goes on believing the file belongs to whatever repository
the folder used to sit inside — for the next five minutes — so the feedback
button files a report into the wrong project. Nothing tells you; the button
just points somewhere else. The viewer's own live test does exactly this, which
is why the standing test floor had been going red on most turns.
