# T2892 - Windows' relaunch after a crash forwards its new-window to the still-dying crashed instance's IPC pipe and exits, so no window comes back (42 minutes with no Ghoztty on 2026-11-10)

## Summary

Live case 2026-11-10: the installed release crashed at 07:12:06 (see the GPU task filed beside this). T2839's fix worked as far as it went: Windows relaunched ghoztty.exe at 07:12:22 (pid 2516). But that process logged 'another instance owns the IPC pipe; forwarding new-window' and exited, 11 log lines in all. The owner it forwarded to was the CRASHED instance (63972), still alive while WER wrote its dump (CrashDumps\ghoztty.exe.63972.dmp is stamped 07:12:22). The forward went nowhere and no Ghoztty window existed until the go-loop watchdog launched one at 07:54:48: 42 minutes with no terminal on screen. Sessions survived in ghoztty-agent throughout. Fix direction: a forwarding launch must confirm the pipe owner answered the forward (or that GetNamedPipeServerProcessId's process is not terminating/under WER) and otherwise wait for it to exit and take over as the primary instance. A restart-manager relaunch (the registered restart command line) should always take over rather than forward. Test: an acceptance arm that holds a fake pipe owner which accepts the connection but never replies (or is suspended) and asserts the new launch becomes primary within N seconds.

## In plain terms

When Ghoztty crashed, Windows started it again - but the new copy saw the old,
still-dying copy and handed its window to it, then quit. The dying copy could
never open it, so the user was left with no terminal at all until something
else launched one. Now the new copy notices nobody answered, waits for the old
one to finish dying, and starts up properly itself, bringing the sessions back.

## Goals

- [x] A launch tells "the running copy said no" apart from "nobody answered"
- [x] On no answer, it waits for the endpoint to come free and starts as the app
- [x] A copy that is hung (never exits) is not waited on forever
- [x] Ordinary second launches against a healthy app behave exactly as before

## Validation criteria

- [x] Refusal vs no-answer classification is unit-tested - `orphan_endpoint.zig` tests, win32 lane (`floor-lane.ps1 -Lane all`).
- [x] Behind a dying owner the launch becomes the app with its own window and answers `+list` - `test\win32\orphan-endpoint.ps1` O1 (17/17 green, stamped).
- [x] The log names the owner's real pid, read off the pipe - O1.
- [x] Behind a hung owner the launch gives up, logs it, and the ledger says `forward-unanswered` - O2.
- [x] A healthy owner still gets the forward; ledger `forwarded`, no takeover attempted - O3.
- [x] The arm can fail: `-NegativeControl` (zero wait = pre-fix give-up) scores O1 red, 4 failures.

## Notes

- **Live evidence**: `exit-log.txt` shows pid 2516 start 15:12:22.815Z and
  `reason=forward-failed` at 15:12:22.900Z - the forward failed in 85 ms (a
  transport failure, not a timeout), against crashed pid 63972 still holding
  the pipe under WER.
- **Restart-manager relaunch "always take over"** (the Summary's second
  suggestion) was not done: the registered restart command line is null, so a
  WER relaunch is indistinguishable from a user launch, and the
  no-answer path already covers it without changing what an update restart
  replays. Nothing is lost by the general fix.
- **Mac parity**: no Mac counterpart is owed. The defect is in the Windows
  single-instance forward plus Windows' own crash relaunch (T2839); on macOS
  LaunchServices owns single-instance activation and the "Reopen" prompt starts
  a fresh app after the crashed process is gone.
