# T1156 - P3 acceptance scored two failures once and then passed twice with nothing changed

## In plain terms

One of the checks that has to pass before any change ships reported a problem
once, then reported none twice in a row with nothing altered in between. A check
that answers differently to the same question is a check nobody will believe the
next time it says something is broken.

## Summary

Observed 2026-08-23 during T1131's turn, on the debug build at 155ac6b27 plus
T1131's viewer changes (which touch no IPC path P3 exercises):

```
run 1: P3 ACCEPTANCE: 2 FAILURE(S) (14 assertions passed)
run 2: P3 ACCEPTANCE: ALL PASS (16 assertions)
run 3: P3 ACCEPTANCE: ALL PASS (16 assertions)
```

Run 1 was started immediately after `ipc-p2.ps1` finished, and its output was
piped to `tail -3`, so WHICH two assertions failed was not captured - that is
the first thing this task has to recover, and the reason it is filed rather
than dismissed. The 14-vs-16 count says the run got all the way to the end and
two named assertions went red, not that it aborted early.

The leading hypothesis is teardown overlap: P2 kills agents and takes the
per-user pipe, and P3 launched about a second behind it. `go.md` already warns
that a concurrent lane starves test waits badly enough to wedge one; a
still-settling teardown is the same shape one notch smaller. If that is it, the
fix belongs in the script's own setup (wait for the endpoint to be free rather
than for a fixed sleep), not in the caller's discipline.

**Outcome (2026-09-24): the hypothesis was wrong, and the cause is a fixed
sleep, not a leftover from P2.** See Findings.

## Goals

- [x] Name the two assertions and the cause, with a reproduction on demand
- [x] Replace P3's sleep-then-read pairs with a clock-bounded wait in the shared
      harness library, visible when it absorbs a slow box
- [x] Keep the checks able to fail

## Findings

- **The pair is `OSC busy set` + `OSC idle cleared`.** Section 4 typed a nested
  `powershell -Command "...OSC..."` into the pane and read the title after a
  fixed 6 s. If the nested PowerShell starts slower than that (cold start,
  Defender, a loaded box), the busy read is early (FAIL). The idle command was
  typed while the busy one still ran, so it queues behind it, and the idle read
  six seconds later sees the late busy (FAIL). No other assertion is involved.
  That is exactly `2 FAILURE(S) (14 assertions passed)`. No other single delay
  in the script produces that count: section 1/3 slips score one failure each,
  and the old section-5 null cascade left an arm unscored (13 + 2).
- **Reproduced on demand**: the same script with `[Threading.Thread]::Sleep(7000);`
  prepended to BOTH typed OSC commands scored `2 FAILURE(S) (14 assertions
  passed)`, both OSC arms red. Delaying only the busy one scores 1 (the queued
  idle then lands in time). Trap met on the way: `Start-Sleep 7` typed through
  `+send-keys` inside the quoted command arrives as `Start-Sleep7` and errors,
  so the OSC fires at once and the "slow" run passes. Use a space-free delay.
- **Teardown overlap refuted**: 10x P2 then P3 back-to-back, all ALL PASS (P3
  31 s every time); 5x P3 with 32 CPU busy-loops, all ALL PASS. T1285 had
  already run 18 p1/p2/p3 triples green. The app pipe has been per-run
  (`-Tag`+PID) since 2026-08-04, so P2 and P3 never shared it.
- **Fix**: `Wait-FloorState` in `test\win32\lib\FloorFixture.ps1` polls the
  observable state until a 30 s bound, never throws (a genuinely missing state
  still scores the arm red), and parks `NOTE SLOW STATE: <what> settled after
  Nms (nominal Nms)` when it only arrived past the sleep it replaced, printed by
  `Invoke-FloorBody` on every exit. P3 sections 1, 3, 4 and 5 use it; every
  negative wait follows a positive one. P3 went from 31 s to 12 s.
- **Overlap lesson re-learned mid-task**: a 20x run started alongside the
  harness-floor lane went red 6 times with `No running Ghoztty instance found`.
  `persistence-flag.ps1` launches and resets debug instances, and the lane
  scored IT red for the same collision ("alone: PASS"). The sequential-only
  rule in go.md is load-bearing; the 20x evidence below is from a quiet box.
