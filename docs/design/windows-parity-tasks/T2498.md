# T2498 - A closed window keeps its desk bitmaps (4 GDI objects and ~4-7 MB a window); freeing them in onDestroy crashes the app at the 6th window close in window-close-memory.ps1 -Shape split -CloseSplitFirst

## In plain terms

Every window you close keeps a few megabytes of memory and four drawing handles until Ghoztty exits, so a long session that opens and closes many windows keeps growing. The obvious fix frees them, but it makes the app crash in one close pattern, which means something still reads that memory after the window is gone. That has to be found before the fix can ship.

## Summary

Found by T2473's `test\win32\window-close-memory.ps1`. On HEAD 9a289d01a every closed window leaves **4 GDI objects and ~4-8 MB of private bytes** behind (BEFORE: `-Shape full` 10 cycles = +4.0 GDI, +7.9 MB a window; `-Shape single` = +4.0 GDI, +4.2 MB). Root cause: `Window.onDestroy` (the USER close path - `closeNow` -> DestroyWindow -> WM_DESTROY) frees only the drop preview and the tab/pill fonts, while `Window.deinit` (app quit) also frees `pane_desk`, `pane_stacks`, the row drag and the full-screen exit button. `PaneDesk` keeps up to three `Dib`s (`desk`, `comp`, `out`: a DC + DIB section each), so its two window-sized ones are the 4 GDI objects and the MBs.

**The fix is written and measured, but NOT landed**: a `releaseOwnedResources()` helper called from both `deinit` and both `onDestroy` branches (the patch is in `temp\t2473-desk-free.patch` on the lane-a box: `pane_desk.deinit()`, drop preview, full-screen exit button, tab/pill/rename fonts). With it, `-Shape full` measured **0.0 GDI and 1.07 MB a window**. BUT with it `window-close-memory.ps1 -Shape split -Cycles 8 -CloseSplitFirst` crashed the app twice out of two (exit 0xFFFFFFFF, no panic text, on the 6th window close - once right after `parked closed window for undo`, once after `undo expired`), while the unmodified build (`zig-out-t2473old`) ran the same 10 cycles clean. Bisect: dropping the `pane_stacks`/`endRowDrag` frees did NOT stop the crash, and the full-screen button / rename font are never created in that run, so freeing the DESK is what exposes it. The DIBs are never aliased (`desk`/`comp`/`out` are each `Dib.create`d), and no other window holds a desk pointer (the sidebar reads its own window's `deskBackdrop()`), so the working theory is a LATENT use-after-free of a closed window's desk pixels (or of the Window itself) that the leak has been masking: freed DIB-section memory faults where leaked memory read fine. Under `cdbX64 -p` (attach) the crash did not reproduce in 10 cycles, so it is timing-sensitive.

Next: catch it first-chance (launch the app UNDER cdb from the start, or arm WER LocalDumps - that needs the user's UAC, so ask in the digest rather than prompting), find the reader of the freed desk, fix it, then land the helper and also free `pane_stacks` (heap only) on the close path. `onDestroy` must free everything `deinit` frees; a unit-level guard that the two lists cannot drift again is worth adding.
