# T1478 - A stop/resume cycle leaves the loop down while every recovery command reports success

## Summary

**Observed on 2026-09-09, in a controller session, with the full command trail
below.** A controller stopped the loop to run the floor lanes without two GUI
lanes fighting for the foreground, then resumed it. The loop stayed down for
seven minutes across three recovery attempts, and **every one of them reported
success**. This is the "a step whose failure mode is nothing happens" shape that
T1292 paid for over three days of silent publish skips.

The sequence, with the times:

1. `09:20` The loop's own session behaved **correctly**: after its turn it ran
   `go-loop-exec.ps1 claim`, got exit 4 (STOPPED by request), and per go.md step
   0 refused to pick a task and refused to `/reset-context` (perpetuating the
   loop is exactly what a stop defeats). It unmarked its window, released the
   lock, printed "the loop is parked, not broken", and went idle. Nothing here
   is a defect.
2. `09:41` `go-loop-exec.ps1 resume` -> `RESUMED stop request cleared` /
   `claim will take the loop again on the next turn`. **Exit 0.** But there is no
   next turn: the only session that would claim is idle at its composer and
   nothing re-triggers it. The message states a future that cannot arrive.
3. `09:41:52` `go-loop-watchdog.ps1 -Once -Force` ->
   `re-entering: no live loop pane, opening a new window (state=free)` /
   `new-window exit=0` / `ACTION new-window`. **Exit 0.** No session started.
   `+new-window --target=main` is idempotent by design (CLAUDE.md: named targets
   that already exist are focused, not recreated), and `main` was still occupied
   by the parked-but-idle session from step 1. So the watchdog focused a window
   and called it a re-entry.

Both watchdog log lines are false in that state. There *was* a live loop pane -
it was idle, not absent - and no new window was opened. `new-window exit=0`
reports the window operation, not a loop coming back, so the one number a caller
would gate on is the one number that cannot see the failure. Health kept
answering `DOWN state=free windows=0` while all three commands claimed success.

**What actually fixed it** was sending the go prompt to the parked pane by hand:

```powershell
ghoztty.exe +send-keys --target=main --enter "read go.md and go"
```

after which the next health poll read `HEALTHY uptime=1m turn=1 state=held`.

So the capability is all present; what is missing is that nothing connects
"the stop flag is cleared" to "the idle session in the loop window needs the
prompt typed into it".

Two candidate fixes, and the second is the one that closes the hole:

- `resume` sends the go prompt itself when it can see a marked-or-known loop
  window holding an idle session. Direct, but `resume` currently touches only
  the lock file and gains a dependency on pane state.
- **`go-loop-watchdog.ps1` learns the third case.** It already distinguishes
  "live pane, working" from "no pane at all"; the missing branch is "pane exists,
  session is idle, lock is free" -> send the prompt rather than call
  `+new-window` and declare victory. That is also the branch that makes the
  watchdog's existing re-entry honest, because the same wrong log line would
  print for any idle-occupant case, not just after a stop.

Note the near-miss that makes this worth a test rather than a one-line patch:
the controller's *first* send used `--name=` (which is `+read`'s flag; send-keys
takes `--target=`) and got an **empty exit code** with no visible error, which
looked exactly like the `--when-idle` stall it was not. A fix that shells out to
`+send-keys` and does not assert the pane actually started working will
reproduce this whole failure one level down.

## Validation criteria

- [ ] With the loop parked by a stop and its session idle in the loop window,
      the documented recovery (`resume`, then the watchdog) brings the loop back
      to `state=held` with no hand-typed prompt.
- [ ] The watchdog never logs `no live loop pane` or `opening a new window` when
      the target window exists and holds an idle session; the idle-occupant case
      logs what it actually did.
- [ ] Recovery is gated on the loop reaching `held` (poll `go-loop-health.ps1`),
      not on `+new-window` or `+send-keys` exit codes - a malformed send-keys
      must make the recovery go red rather than silently succeed.
- [ ] An acceptance script in `test\win32\` stages the exact state (stop, let a
      session park and idle, resume) and asserts the loop returns to `held`, with
      a negative control proving it goes red against today's watchdog.
