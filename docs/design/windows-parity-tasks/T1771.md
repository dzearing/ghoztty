# T1771 - A pane whose holder dies under a live session manager comes back as a fresh shell with no interrupted notice

## Summary

Found by T1001's teeth run (`test\win32\agent-handoff.ps1 -BreakHolders`,
2026-09-26): with the handoff complete and the successor manager serving, the
test killed every `--pty-host` holder. Both panes came back on NEW session ids
with fresh shells (the long-running `ping` was gone, the pre-handoff marker was
gone from scrollback) - yet neither the pane banner nor the scrollback carried
the "Session interrupted" notice. Arm A of `session-relaunch-notify.ps1` shows
the notice when the manager AND holders die together (the reboot shape), and
arm M under `-BreakHolders` shows it too; the shape that stays silent is a
holder dying while its manager lives.

Decide from the code which is intended: if a holder that dies under a live
manager is treated as "the shell exited" and respawned, the user's program was
killed and replaced without a word, which is the thing the notice exists to
say. Likely the fix is to raise the same interrupted notice (banner +
scrollback) when a holder-backed session is lost to anything other than the
shell's own exit.

## In plain terms

If the helper process that keeps one of your terminals alive is killed, the
terminal quietly comes back as a brand-new empty shell. Whatever you were
running is gone, and nothing tells you it happened.

## Goals

- [x] Decide from the code whether the silence is intended - it is not
- [x] A holder that dies under a live manager, with no pane attached, leaves an
      interrupted session instead of a finished one
- [x] The pane that re-attaches says so, in its banner and its scrollback
- [x] File the attached-pane shape separately (T1793)

## Root cause and fix

Not deliberate. The two ways a holder can be lost disagreed:

- **Found gone at adoption** (a restart, a reboot): `abandonHolder` leaves a
  relaunchable tombstone, the re-attach takes the `restore` policy path in
  `termio.Remote`, and the pane paints "Session interrupted" + the command.
- **Killed while this agent owned it**: `HolderChild.tryWait` synthesized an
  exit from `lost`, and `onChildOutput` recorded it with `markExited` - a
  finished, non-relaunchable session. The roster then listed it dead, so the
  app's in-place recovery (and a launch restore) left it out of the attach set,
  the leaf OPENed a fresh session, and no notice fires on that path.

Fix (agent only, no wire change): `Child.VTable.lost` lets a child say its
reported exit was its host vanishing; `HolderChild` answers it from a new
`lost_exit` flag set only when the exit was synthesized (an exit the holder
SENT is answered first, so a shell that ran `exit` never reads as lost). An
UNBOUND session whose child was lost becomes `Session.markLost`: relaunchable,
no exit code, holder handle forgotten, restart divider appended - exactly the
adoption-failure tombstone. RELAUNCH now terminates whatever child it replaces,
since a lost holder child is no longer the inert placeholder.

A BOUND pane keeps the plain EXIT: a tombstone nobody claims would linger as a
Resume row for a pane that has already closed. Telling an attached pane needs
an EXIT-side signal and is T1793.

Wording: the notice reads "the background terminal process was restarted" -
the holder IS a background terminal process and it did go away; the app cannot
tell this tombstone from a reboot one without a protocol change, and the
sentence is true of both. Kept as is.
