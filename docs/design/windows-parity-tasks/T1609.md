# T1609 - A --command= pane is no longer agent-backed, so it loses session persistence (keepalive control arm G is red)

## Summary

Control arm G of test\win32\ipc-command-keepalive.ps1 - "the --command pane carries a session_id" - is RED, and measured red on an untouched HEAD build (dd9ec8e6b) on 2026-09-16, so it is not the fault of whatever change is in flight. The arm exists because the T468 defect lived on the agent-backed path only: with session-persistence on (the default) every local pane's shell is spawned by ghoztty-agent, and a +list --json leaf for such a pane carries a session_id. A --command= pane that carries none is on the plain-ConPTY fallback, which means (a) the pane does not survive a restart the way every other pane does, and (b) the whole keepalive suite is exercising the path that was never broken and would still report ALL PASS the day T468 regressed. Find out why the OPEN is not happening (or is failing and falling back) for a --command= pane under the test sandbox, and whether it also happens outside it - if it is sandbox-only the control still has to be repaired, because a control that cannot fail in the harness is not a control.


## In plain terms

The test that is supposed to prove a `--command=` pane really is a persistent
one had been failing on and off, which made it look like those panes had quietly
stopped surviving a restart. They had not. The test was asking the question a
fraction of a second too early: the pane is handed its session a quarter of a
second after the window appears, and the test read the answer before it existed.
Now it waits for the answer - and a second copy of the app, deliberately run
with persistence turned off, proves the test still notices when the answer is
genuinely absent.
