# T1830 - Windows panes have no hover grab handle: a pane can only be dragged in rearrange mode, and viewer panes never at all

## Summary

Mac shows a grab handle centered at a pane's top edge: translucent while the pointer is in the pane's top band, opaque over the handle itself (597a193cc). It stays revealed while the pointer is on the pane's sticky banner (bba09ae7d - the banner reports its own hover; rule is a pure function, SurfaceGrabHandle.revealsHandle). Viewer panes (markdown, HTML, website, image, diff) get the same handle (a235110ff), reported via a tracking area that keeps working over the web view and nav bar. Dragging it uses the same drop resolver as rearrange mode (split, tab, window, and the pane sidebar once it exists). Windows today only exposes the rearrange-mode header (rearrange_header.zig, T1525/T1536).

## In plain terms

On a Mac, hovering near the top of any pane shows a small grip you can drag
to move that pane somewhere else - into another split, onto a tab, out into
its own window, or onto the pane sidebar. On Windows the only way to move a
pane was to switch on a special rearrange mode first, and a document/web
preview pane could not be dragged at all. Now every pane, terminal or
preview, shows the same grip when the pointer is near its top edge.

## Goals

- [x] a grip appears, faint, centered at the top of whichever pane's top fifth holds the pointer
- [x] the grip turns solid while it is pressed or carried
- [x] dragging the grip uses the same drop targets as rearrange mode (split, swap, tab, window, sidebar)
- [x] preview (viewer) panes get the grip too
- [x] no grip while typing hides the pointer, in rearrange mode, on a hero tab, or fullscreen with one pane

## Design notes

- One popup per window (`PaneGrabHandle.zig`) that moves to the hovered pane,
  rather than one per pane: only one band can hold the pointer at a time.
- The pointer is fed from the run loop (`App.routeGrabPointer`: every
  `WM_MOUSEMOVE`/`WM_NCMOUSEMOVE` on any of the window's HWNDs) plus a 50 ms
  sample while the pointer is over the window, because a viewer's page is
  another process's window and raises nothing here. Over terminals the sample
  stops after 0.5 s of stillness. A sample only overrides the message point
  when the real cursor MOVED, which is what lets posted input drive it.
- The press hands the pane to the existing pane-drag machinery
  (`Window.beginGrabHandleDrag` -> `beginRearrangeDrag`), so threshold,
  preview, resolver and commit are the rearrange drag's.
- Sizes moved to the 4 DIP grid (capsule 48x16 DIP vs Mac's 46x14pt) and the
  capsule sits 4 DIP inside the pane top instead of overhanging it by 3pt
  (design system: nothing touches its container's edge). Hit box 80x24 DIP.
- Pointer over the handle is `IDC_SIZEALL`, the same move pointer the
  rearrange header uses (T1536: Windows has no open-hand pointer).
- Windows-only suppressions: rearrange mode (the header already drags; two
  grips on one edge is one too many) and hero tabs. Quick Terminal gets no
  handle (nowhere in it to drag a pane to).
