# T1866 - Audit the other owned win32 tooltips for T1842's z-order lift: a topmost tooltip owned by a background window dragged that window above the user's frontmost one when created

## Summary

Found landing T1842. The pane sidebar created a `WS_EX_TOPMOST` tooltip
OWNED by its window on the window's first layout. For a window opened in the
background (`+new-remote-window`, T1797's contract), that creation lifted the
window above Ghoztty's frontmost window: `cli-focus-policy.ps1` arm R measured
the new window at z=6 over the frontmost at z=9, deterministic over two runs,
green with the tooltip disabled and green again with the tooltip created
UNOWNED (the T1842 fix). Other tooltips are created owned the same way:
`ViewerNavBar.tipEnsure` (owner = the bar), `ViewerFeedbackBar`,
`KeyStateIndicator`, and the tab strip's (`Window.tabTipEnsure`). Measure each
on a window opened in the background (arm R's shape: open, then read
`Get-TestZIndex` against the frontmost window); move any that lifts to the
unowned form, or to lazy creation on first hover.

## In plain terms

Ghoztty's little hover tips (the "what does this button do" boxes) were built
in a way that, at the wrong moment, could drag a window the user was not using
up in front of the one they were using. One of them (the pane sidebar's) was
caught doing it and fixed in T1842; this task checks every other tip and makes
them all safe the same way, with a test that fails if any tip comes back in
the risky form.

## Goals

- [x] every tooltip site found and measured or reasoned about, per site
- [x] all of them created the safe (unowned) way, through one shared constructor
- [x] a test arm that fails if any tooltip is created the risky way again

## Per-site findings

| Site | When the tip is created | Measured |
|---|---|---|
| `PaneSidebar` | first layout of every window | lifted (T1842, arm R) - already unowned |
| `ViewerNavBar` | the viewer bar's first layout | `+split --view` into a BACKGROUND window (arm F, now reading z): window stayed at z=4 under the user's app (0) and Ghoztty's frontmost (1) - no lift, but the tip WAS owned (arm T pre-fix: 3 owned tips, one per viewer) |
| `ViewerFeedbackBar` | the composer band's layout | same eager shape as the nav bar; not reached by this harness |
| `KeyStateIndicator` | when the pill shows (a key table / chord in that pane) | needs key input to that pane, so the window is normally active; not reachable on the test desktop |
| `Window` tab strip | on the hover timer over a tab | needs a real pointer; the test desktop has none (T233) |
| `help_tooltip` (machine chooser, Activity Monitor) | on hover in a dialog / tool window | activated top-levels; same constructor for consistency |

An isolated reproduction (two off-screen popups, an owned topmost
`tooltips_class32` created on the lower one) measured NO lift, owned or not,
hidden or shown - so the lift is timing/state dependent, which is why the fix
is structural (no product tooltip is owned) and the regression arm checks
ownership rather than relying on z-order alone.

## Validation criteria

- [x] each owned tooltip site measured on a background-opened window (z-order vs Ghoztty's frontmost), result recorded per site - table above; `cli-focus-policy.ps1` arms E/F now read the background window's z-order
- [x] any site that lifts its window fixed, and an arm in `cli-focus-policy.ps1` (or a sibling) that would catch a regression - all five remaining sites moved to `tooltip_window.create` (unowned); arm T FAILED pre-fix (`3 owned`) and passes post-fix (`10 total, 0 owned`, 57/57)
