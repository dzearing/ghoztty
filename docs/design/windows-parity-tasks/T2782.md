# T2782 - The window-close guard reads ~15 MB of one-time fill as a leak: private bytes climb over the first ~5 measured window cycles and then stop, past the guard's 2 warm-ups

## In plain terms

The memory test that opens and closes windows over and over still says closing a window leaks more than 1 MB. Most of that is memory the app grows once over the first few windows and then keeps steady, which is not a leak. This task finds out what that memory is, and makes the test stop counting it.

## Summary

Found closing T2671 (2026-11-07, lane b). Every run of `test\win32\window-close-memory.ps1`, release or debug, composition present on or off, climbs ~12-17 MB of private bytes over the first ~5 MEASURED cycles (after the 2 warm-ups) and is then flat:

| run | baseline | after 5 | end |
|---|---|---|---|
| debug verdict, full, 10 cycles | 600.4 | 616.9 | 618.0 (cycle 10) |
| release, full, 20 cycles (T2671 build) | 603.1 | 619.1 | 623.2 (cycle 20) |
| release, full, 20 cycles (pre-T2671) | 557.0 | 574.8 | 576.2 (cycle 20) |
| release, full, COMP_PRESENT=0, 12 cycles | 482.3 | 496.0 | 499.2 (cycle 12) |
| release, viewer, 4 warm-ups, 30 cycles (T2671 build) | 524.9 | 532.6 | 530.5 (cycle 30) |

So A1's "1.76 MB a window" on the 10-cycle debug verdict is mostly that fill spread over 10 cycles. GPU shared memory (`GpuShMB`) fills over the same cycles (26.7 -> 39.6) and then stops too.

Do two things:
1. **Name the fill.** A `-HeapCensus` at cycle 1 and cycle 6 of the release sandbox, summed per region type, tells whether it is the C heap, the NVIDIA arena, WebView2's in-process heap, or thread pools. If it is a bounded cache, write down what bounds it.
2. **Then fix the guard, not the number.** If the fill is bounded, move the guard's baseline past it (more warm-ups, or a baseline taken once the per-cycle slope settles) and keep the 1 MB budget on the slope. If it is not bounded, it is a leak and this becomes its fix.

Not this task: A8 (GPU dedicated ~1 MB a window, composition present only) is T2606.

## Validation criteria

- [ ] the fill is named by a census, with what bounds it
- [ ] the guard's verdict run (`window-close-memory.ps1`, debug, default args) passes A1 without hiding a per-window slope: a `-NegativeControl` run still goes red
