# T1508 - A Debug build leaves no log file behind, so an acceptance failure cannot be diagnosed after the fact

## Summary

`logFn`'s Windows file sink is compiled out of Debug builds, so the app the
acceptance harnesses drive logs only to a stderr nobody captures

## In plain terms

When an acceptance script says the app answered wrongly, there is no record of
what the app thought it was doing - the debug build writes its log to a console
that the harness never opened. So the only way to find out is to rebuild the
scenario by hand and hope it misbehaves again while somebody is watching.

## Goals

- [x] A Debug build writes its info/warn/err lines to a file under
      `%LOCALAPPDATA%\ghoztty\`, under a name that cannot collide with the
      release sink the user's installed app is appending to
- [x] The file is bounded the same way the release sink is (`log_rotate`)
- [x] An acceptance failure can be explained from that file without rebuilding
      the scenario

## Details

`src\main_ghostty.zig` gates the whole `windows_file:` block on
`builtin.mode != .Debug`, with the reasoning that a Debug build uses the console
subsystem and logs to stderr "like every other platform". That is true of a
developer running the exe by hand, and false of every acceptance script: the app
under test is auto-launched by a `+…` CLI verb, so its stderr belongs to a
process nobody is capturing.

T1507 paid for this directly. Its card said "the `err=` the app logs is in the
app's log sink (`%LOCALAPPDATA%\ghoztty[-debug]\ghoztty.log`)" - a file that has
never existed for a Debug build - and diagnosing the failure needed a bespoke
repro harness that pre-launched the app with `-RedirectStandardError` just to
read one `log.warn` line.

The naming is the one real design point: the release sink is `ghoztty.log` and
the user's installed app appends to it continuously, so a debug build must NOT
share it (T350's whole rule). The repo convention for debug-suffixed state in
that directory is a suffixed NAME (`session-layout-debug.json`,
`local-agent-debug`), so `ghoztty-debug.log` fits, which means `log_rotate`'s
`live_name`/`rotated_name` need to be comptime-selected rather than constants.
That touches `src\os\log_rotate.zig`, so the `log-sink` guard
(`test\win32\log-append.ps1`) is due with the change.

## Validation criteria

- [x] `test\win32\log-append.ps1` green (the `log-sink` guard, re-stamped)
- [x] A Debug `zig-out\bin\ghoztty.exe` run produces
      `%LOCALAPPDATA%\ghoztty\ghoztty-debug.log` containing its startup lines
- [x] The user's `ghoztty.log` is byte-unchanged across that run
- [x] `zig build test -Dapp-runtime=win32` and the `none` lane green

## Evidence (2026-11-19, lane b)

- **Fix.** `log_rotate.live_name` is comptime: `ghoztty-debug.log` in Debug,
  `ghoztty.log` otherwise (`rotated_name` = `live_name ++ ".1"`, so the T410
  bound and handle-rename carry over unchanged). `logFn`'s `windows_file:` sink
  is now gated on Windows only and opens `live_name`. `startup_error.log_path`
  is built from `live_name`, so a Debug startup-failure dialog names the file
  that actually exists. The CLI-became-master banner re-log (T1998) now runs
  in Debug too.
- **Found on the way:** every Debug `+verb` also logged three "This is a debug
  build" warnings, which the file sink would keep (warnings pass the T1998
  gate) - thousands of harness CLI calls burying the app's lines. Those three
  lines are now skipped for a Windows CLI call (the app still says them;
  `build optimize=Debug` is in every banner). Asserted by D8.
- **log-append.ps1** (log-sink guard): new D arm, D0-D8 - release never
  writes the Debug sink; a Debug `+validate-config` writes
  `ghoztty-debug.log` with T270-prefixed lines of its own pid, its banner
  (`build optimize=Debug`) and its warnings; a pre-seeded `ghoztty.log` is
  byte-identical afterwards; a plain Debug `+list` writes nothing.
  **LOG-APPEND: ALL PASS (45 assertions)**, STAMPED log-sink, against this
  tree's own `zig-out-release` (ReleaseFast, `-Dstrip=false`).
- **Negative control:** lane A's pre-fix Debug exe, same sandboxed `+list`:
  the `ghoztty` sink dir stays EMPTY (log-append itself refuses to grade
  another checkout's build, T1996, so this was run by hand).
- **Manual:** this tree's Debug `+list` in a sandbox LOCALAPPDATA wrote
  `ghoztty-debug.log` (banner, locale, debug warnings, `executing CLI
  action=.list`); the user's real `%LOCALAPPDATA%\ghoztty\ghoztty.log`
  SHA-256 was identical before and after.
- **startup-failure.ps1:** A7/E7 now require `ghoztty-debug.log` (its subject
  is always Debug - the isolation pre-flight refuses release). ALL PASS (42).
- **Floor:** `floor-lane.ps1 -Lane all` - lib/none/win32/agent ALL PASS.
- **Guards made due by this diff, all green:** window-active, printclient,
  docs-routing, doc-claims, tree-swap, type-ramp, radius-table, test-reach,
  neuter, thread-join, self-spawn, unwired-hook, seam (13/13).
