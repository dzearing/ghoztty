# T1508 - A Debug build leaves no log file behind, so an acceptance failure cannot be diagnosed after the fact

## Summary

`logFn`'s Windows file sink is compiled out of Debug builds, so the app the
acceptance harnesses drive logs only to a stderr nobody captures

## In plain terms

When an acceptance script says the app answered wrongly, there is no record of
what the app thought it was doing - the debug build writes its log to a console
that the harness never opened. So the only way to find out is to rebuild the
scenario by hand and hope it misbehaves again while somebody is watching.

## Goals

- [ ] A Debug build writes its info/warn/err lines to a file under
      `%LOCALAPPDATA%\ghoztty\`, under a name that cannot collide with the
      release sink the user's installed app is appending to
- [ ] The file is bounded the same way the release sink is (`log_rotate`)
- [ ] An acceptance failure can be explained from that file without rebuilding
      the scenario

## Details

`src\main_ghostty.zig` gates the whole `windows_file:` block on
`builtin.mode != .Debug`, with the reasoning that a Debug build uses the console
subsystem and logs to stderr "like every other platform". That is true of a
developer running the exe by hand, and false of every acceptance script: the app
under test is auto-launched by a `+…` CLI verb, so its stderr belongs to a
process nobody is capturing.

T1507 paid for this directly. Its card said "the `err=` the app logs is in the
app's log sink (`%LOCALAPPDATA%\ghoztty[-debug]\ghoztty.log`)" - a file that has
never existed for a Debug build - and diagnosing the failure needed a bespoke
repro harness that pre-launched the app with `-RedirectStandardError` just to
read one `log.warn` line.

The naming is the one real design point: the release sink is `ghoztty.log` and
the user's installed app appends to it continuously, so a debug build must NOT
share it (T350's whole rule). The repo convention for debug-suffixed state in
that directory is a suffixed NAME (`session-layout-debug.json`,
`local-agent-debug`), so `ghoztty-debug.log` fits, which means `log_rotate`'s
`live_name`/`rotated_name` need to be comptime-selected rather than constants.
That touches `src\os\log_rotate.zig`, so the `log-sink` guard
(`test\win32\log-append.ps1`) is due with the change.

## Validation criteria

- [ ] `test\win32\log-append.ps1` green (the `log-sink` guard, re-stamped)
- [ ] A Debug `zig-out\bin\ghoztty.exe` run produces
      `%LOCALAPPDATA%\ghoztty\ghoztty-debug.log` containing its startup lines
- [ ] The user's `ghoztty.log` is byte-unchanged across that run
- [ ] `zig build test -Dapp-runtime=win32` and the `none` lane green
