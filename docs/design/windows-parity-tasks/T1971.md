# T1971 - After a restart, every window comes back small instead of at its saved size and position

## In plain terms

When Ghoztty comes back after a restart, every window is small. Each one
should reopen exactly where it was, at the size it was.

The cause: window sizes were saved as raw screen pixels, with no note of the
display scale they were measured at. Over Remote Desktop the scale changes
with each connection (the user's Cloud PC runs at 200%), so a window saved at
one scale came back at a fraction of its size at another, and a brand-new
window opened at a quarter of its intended area at 200%. Sizes now carry
their scale and are converted to the screen they land on.

## Goals

- [x] A restored window keeps its real size when the display scale changed
      since it was saved.
- [x] A window with no saved size opens at 800x600 at the screen's scale,
      not 800x600 raw pixels.
- [x] The remembered size for new windows converts the same way.
- [x] Moving a restored window onto a screen at another scale no longer
      rescales it a second time.

## Summary

User report (2026-10-15), part 1 of the T1970 report: "the window sizes
are all small and not restored".

Leads (unverified):

- **Placement is saved in physical pixels and restored onto a different
  desktop.** Over RDP and Windows App, every reconnect can change the
  session's resolution and DPI (the user's Cloud PC is at DPI 192). The
  robust shape is to save device-independent geometry plus the monitor,
  then clamp into the current work area. Use `GetWindowPlacement` /
  `SetWindowPlacement` with `rcNormalPosition` in workspace coordinates,
  and keep the maximized state separately.
- **The sessions-lost path (T1970) skips layout restore** and opens fresh
  default-size windows, so the two symptoms may share a cause.
- **Restore runs before the window has its DPI**, so the size is scaled
  twice or not at all.

## Validation criteria

- [x] Acceptance (test desktop): windows at distinct sizes and positions,
      one of them maximized, come back after a restart within 2 DIP of
      their saved geometry, with the maximized state intact.
      `test\win32\restore-dpi-frame.ps1` B (a drag-resized 1137x841 window
      at 60,40 comes back exact, 120 dpi box) and
      `test\win32\session-restore-maximized.ps1` (maximized state + its
      restore-down rect, 22/22).
- [x] Changing the desktop resolution or DPI between save and restore
      (seam) keeps each window inside the work area at its saved DIP size,
      never smaller than saved. The seam is the recorded `frame_dpi`:
      `restore-dpi-frame.ps1` C (saved at 2x scale -> half the pixels, same
      DIP, position unmoved), D (saved at half scale -> doubled, inside the
      work area, never smaller), E (negative control: no recorded scale ->
      replayed verbatim), F (the placement memory converts the same way; a
      pre-T1971 file loads unscaled). 19/19. Unit tests: `fitToMonitor`,
      `scaleDim` (window_placement.zig), the DPI token (window_memory.zig),
      `frame_dpi` round trip (session_layout.zig); floor lanes all PASS.
- [ ] The same holds when the session restore itself fails (T1970's
      negative control): the layout is still applied to the fresh panes.
      NOT met here: a window whose every session is gone is dropped by
      restore by design (T851/T590), and the app opens one fresh window -
      which now opens at the remembered size at the right scale (F above),
      but not as the old layout. Rebuilding dead windows is a behavior
      change filed as its own task (see progress log).
