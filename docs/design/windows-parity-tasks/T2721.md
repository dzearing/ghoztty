# T2721 - Ctrl+V with an image AND text on the clipboard (browser Copy Image) pastes the text into Claude Code instead of attaching the image

## In plain terms

Right-click "Copy image" in some browsers puts the picture on the clipboard
together with some text (its address, or HTML). Pressing Ctrl+V in a Claude
Code pane then pastes that text rather than attaching the picture. Screenshots
work since T2694, because they carry no text.

## Summary

On Windows, Ctrl+V is Ghoztty's paste keybind. T154 passes ^V through to the
program only when the clipboard has no `CF_UNICODETEXT`
(`Surface.clipboardRequest` returns false, `src/apprt/win32/Surface.zig`
~2829), and T2694 binds Chat `ctrl+v` to `chat:imagePaste` in Claude Code's
`~/.claude/keybindings.json`. So with an image-only clipboard Claude gets the
^V and attaches the image; with image + text, Ghoztty pastes the text and
Claude never sees the key.

Constraint from the T2694 report: do NOT rewrite Ctrl+V for arbitrary
programs, since a shell or editor in a pane owns its own ^V and wants the
text. Any fix has to be specific to the pane running Claude Code (Ghoztty
already knows that from the Claude hooks / activity markers), or decide which
format wins by what the clipboard actually holds. First, record exactly which
formats Chrome, Edge and Firefox "Copy image" put on the clipboard. That
answers whether the text is even plain text or only `HTML Format` (which would
not trip the `CF_UNICODETEXT` check at all).

Mac comparison: Cmd+V is paste there and Ctrl+V always reaches Claude, so the
Mac user never hits this.

## Goals

- [x] Ctrl+V over a picture + its web address reaches Claude Code as ^V, so Claude's `chat:imagePaste` attaches the picture.
- [x] Every other program in a pane still gets the address pasted (the T2694 constraint).
- [x] A picture beside REAL text (an Excel or Word copy) still pastes the text, in Claude too.
- [x] A Claude whose Ctrl+V is not bound to image paste keeps today's paste, rather than losing it.

## The fix

`src/apprt/win32/claude_image_paste.zig` holds the rule (pure, unit-tested in
every lane). `Surface.clipboardRequest` returns false (which passes ^V through,
T154) only when ALL hold: it is the user's paste keybind (not an OSC 52 read);
the clipboard holds an image (`clipboard_image.available`); the clipboard text
is empty or a single image address token (`https://`, `http://`,
`data:image/`, `blob:`, `file:`); `claude.exe` runs at or below the pane's
shell (`ProcessTree.claudeRunsUnder`, one Toolhelp32 snapshot, taken only for
this rare clipboard shape); and Chat `ctrl+v` is bound to exactly
`chat:imagePaste` in `%USERPROFILE%\.claude\keybindings.json`
(`ClaudeKeybinding.imagePasteBound`).

Why the text test and not "image always wins in Claude": Excel, Word and
OneNote publish a rendered picture beside the cells/prose the user copied.
Preferring the image there would attach a picture of a spreadsheet when the
user wanted its cells. A browser's companion text is one address; content is
not, so content always wins.

Why the binding test: Claude Code on Windows binds image paste to Alt+V. With
no Ctrl+V binding a passed-through ^V does nothing, which would turn today's
(wrong but visible) address paste into a silent no-op.
