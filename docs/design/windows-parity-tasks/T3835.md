# T3835 - Declared compositor glides show their start pose in the first composed frame, so a click's motion reaches the screen a refresh late: start each new declared glide one display period in, faces and columns with it

## Summary

Measured by T2480 (scripts\comp-glide-hold-onscreen.ps1 -Arms tree -Clicks 8 -SlideMs 400, 120 Hz, 2026-11-26): in the composition pane tree (GHOZTTY_COMP_PANE_TREE=1) the click's own layout pass declares every card's glide and the commit carrying it goes up 1-3 ms after the button-up, yet the first frame that moved is composed 17-25 ms after that commit (click-to-first-motion 21 ms p50 / 26 ms p95 = 2.5 / 3.1 refreshes). A DirectComposition animation starts its timeline when DWM applies the commit, so the first frame that composes it shows the curve's t=0 pose - where the card already was - and the first frame that moves is a refresh later. Core Animation starts its clock at the commit, so its first rendered frame already shows progress (frame_clock.firstFrame's rule, T2401). Fix: declare a NEW glide one display period in - the pane visual's follower is an exponential approach, so starting from reached(period) with t0 backdated one period is the same curve - and shift every other declaration made in the same pass by the same period (the shadow ride shares the pane's segments; the strip faces' enter/knee timelines, the sidebar column and hero glides need the same offset, or the face parts from its pane by one period's travel). The first visible step then carries exactly one period of motion, the bound T2401 set for the stepped path. Oracle: that command's START LATENCY p95 <= 2 refreshes with tree.5-.8 and .18/.19 still green.
