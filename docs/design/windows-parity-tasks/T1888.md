# T1888 - Divider-drag compensation solves with the 2 DIP flat band while the elevated layout uses the pane gap: nested pinned dividers can be off by a pixel or two

## Summary

Found while working T1839, by reading the code; not measured yet.
`split_resize.plan` (and `dividerPos`) compute every sub-range with
`split_geometry.axis(.., scale)`, i.e. the flat 2 DIP band (`bandPx`). The
window lays splits out with `Window.splitRectsFull`, which uses
`pane_elevation.gapPx` as the band when `macos-pane-style = elevated`
(T1831). So in the elevated style the solver's idea of where a nested
region starts and ends is off by about (gap - 2px) / 2 per level, and the
ratio it computes to hold a nested divider can land a pixel or two off the
pixel the user sees.

Fix direction: pass the band the layout actually uses into the solver (a
`band` field on the plan / gesture instead of `scale`), and assert in
`split_resize.zig` tests with an elevated-sized band.

- [ ] after the fix, the nested divider holds within 1px in both pane styles
