# T2597 - Terminal panes as plain (non-layered) child windows without T2499's GPU leak - reuse a closed pane's window and GL context for the next pane, so the plain child that cures T2592's black strip stops costing a window-sized GPU buffer per closed pane

## In plain terms

Panes drawn the way that avoids the black flicker on big windows (T2592)
also keep a chunk of graphics memory every time a pane closes, until the
window closes. When this lands, closing and opening panes keeps graphics
memory flat AND resizing panes shows no black stripe.

## Summary

T2592's experiment B (2026-11-01, release @1dad9fbe6, `GHOZTTY_PANE_LAYER=0`):
a plain WGL child shows **0 black frames** on the chain-fold drag in 3 of 3
live runs (near-full 20261101-021658 and 20261101-022215, normal
20261101-022731), against black frames in every layered near-full run
(20261101-001013, -004809, -014250). A plain child presents into the
top-level's redirection surface, so its resize is a clip change there and the
old pixels stay until the new present; a layered child owns a surface DWM
reallocates at `SetWindowPos`, black beyond the old size, before the present.
No renderer-side fix reaches that (T2592's log), so the plain child is the
structural cure.

But the plain child is exactly what T2499 moved away from: each plain child
that ever ran `SwapBuffers` leaves a TOP-LEVEL-sized GPU allocation that only
the top-level's destruction frees (3 MB a closed pane at the default size, 8
MB at 1800x1100; `test\win32\pane-close-memory.ps1` is the oracle). T2502 made
the layered child the default to stop it.

Fix to try first: **reuse pane windows**. A closed terminal pane's HWND (and
its GL context / pixel format) goes to a per-top-level pool, hidden, instead
of being destroyed; the next terminal pane in that top-level takes it. The
allocations are then bounded by the peak number of panes the window ever held,
not by how many were ever closed. Measure first (a scratch hide-and-reuse run
under pane-close-memory) that a reused child does NOT add a second
allocation; if it does, record that and look at the next lever (one shared GL
drawable per top-level, or the composition present's own leak, T2499 notes it
leaks too). Tab close leaks the same way (T2494's numbers), so the pool must
cover a pane moving out of a closed tab's tree, and a pane moved to another
top-level (tear-off) must not carry a window-sized allocation of the old one
across.

When this lands, T2592 flips `pane_layer` default to off (keeping the knob
as the A/B escape hatch, inverted) and re-runs the chain-fold.

## Goals

- [x] a closed plain pane's window is parked in its top-level and the next pane takes it
- [x] closing and opening plain panes keeps graphics memory flat inside a living window
- [ ] closing a whole window with plain panes gives everything back - NOT this task's: T2599

## What landed

`src/apprt/win32/pane_pool.zig` (pure rules + a 16-slot LIFO, none-lane
tests), `Window.pane_pool`, and in `Surface`: `parkWindow` (deinit hides the
window, clears its userdata and parks it instead of posting the T681 reap) and
`takeParkedWindow` (init revalidates class/userdata/parent, moves it into
place, and skips `SetPixelFormat`, which a window takes once for life). Only
plain children park; a layered pane and any pane whose top-level is closing
(the T681 crash shape) is reaped as before. The GL context is NOT kept: the
next pane creates its own on the same DC. `GHOZTTY_PANE_REUSE=0` turns it
off. The default (layered panes) never reaches the pool, so today it only
changes translucent windows and `GHOZTTY_PANE_LAYER=0` runs.
