# T3402 - win32: an -e argument containing a space splits into several words on the way to the local agent

## Summary

T3396 fixed this for POSIX agents only (`Command.posixShellString`). On Windows
`src/Surface.zig` still forwards `Command.string`, a plain space join, and the
agent runs it through its per-shell convention (`cmd /c`, `pwsh -Command`), so
an `-e` argument holding a space (a path under `Program Files`, a pwsh script
block) arrives as several words. Needs Windows quoting by the
`CommandLineToArgvW` rules, or the T468 `command_argv` route for a verbatim
argv. Related but distinct: T1666 (a `direct:` value in the CONFIG cannot
spell a space at all) - that one is the parser, this one is the hand-off to
the agent.

## In plain terms

Starting a command in a new Ghoztty pane with `-e` broke any argument that
had a space in it: a script under `Program Files`, or a single argument like
`"fix the bug"`, arrived chopped into separate words. After this, those words
arrive exactly as typed, while commands that already worked (`-e claude`,
`-e echo hi`) behave exactly as before.

## Goals

- [x] an `-e` word holding a space reaches the program as one word (app launch, `+new-window -e`, `+split -e`)
- [x] commands with nothing to quote, npm `.cmd` shims and cmd builtins keep today's behavior
- [x] an empty `-e` word is no longer dropped from a Windows command line

## Validation criteria

- [x] `ghoztty -e` with an argument containing a space runs intact in an agent-backed pane (a check in `test/win32/`) - ipc-command-keepalive.ps1 arm L (`+new-window -e` and `+split -e`, session_id asserted), ALL PASS 2026-11-23
- [x] a unit test covers the Windows quoting of argv words with spaces and quotes - CommandCore `windowsCreateCommandLine` round trips through `ArgIteratorWindows` (spaces, quotes, backslashes, empty word) + agent_exec_argv's route decision, none lane
