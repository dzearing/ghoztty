# T2573 - Composition step 5c-4: the hero glide runs as a compositor animation of the pane visuals in pane-tree mode, not a SetWindowPos per HERO_ANIM tick

## Summary

Split of T2554. **Re-verified at claim (2026-11-02): the title's mechanism is wrong.** The hero slide never moves a pane window: `heroStartAnims` hides every hero HWND and `HeroCarousel.paintSlide` GDI-paints the outgoing and incoming panes' snapshots, one strip slot apart, on every 16 ms HERO_ANIM tick (into the desk overlay on the composition path). What the task is for still holds: that paint is stepped from the window's thread, so a busy thread froze the slide mid-way.

Done: in the composition pane tree, with the desk on the compositor, the two snapshots go up once as image layers in a container clipped to the hero rect, over the desk overlay, and their offsetY runs the same easeInOutCubic over HERO_SLIDE_MS (350 ms) as compositor animations (`comp_overlay.fitCurve`, 8 cubics - the ease is cubic on each half and the joint falls on a segment boundary, so the fit is exact to well under a pixel). The tick only lands it (shows the selected pane, takes the layers down). The painted path stays for the knob off (`GHOZTTY_HERO_DECLARE=0`), no desk visual, or any failed step.

## In plain terms

In hero mode, picking another pane slides the old one out and the new one in. The app used to draw every frame of that slide itself, so if it was busy for a moment the slide froze and then jumped. In the new composition mode the app hands Windows the two pictures and the whole slide once, and Windows plays it - so it stays smooth while the app is busy.

## Goals

- [x] The slide's two pictures and their whole path go to the compositor once, with the same ease and distance the painted slide uses
- [x] The window's thread stops painting the slide while the compositor carries it, and lands it when it is over
- [x] A debug knob that blocks the window's thread at the slide's start, and an on-screen film that proves the slide moves through it
- [x] `GHOZTTY_HERO_DECLARE=0` puts the painted slide back (the A/B and negative control)

## Decisions made here

- **Snapshots, not the live pane visuals.** The painted slide shows the panes' snapshots (both HWNDs are hidden for the slide), so the compositor slide uses the same pictures: the film matches the painted arm frame for frame and at the landing. Moving the live tree visuals instead would show content the painted path never did and needs both panes rendered at hero size while hidden.
- **The carousel re-center stays painted.** It is the carousel's own owner-drawn strip (tiles, hover chrome), not a pane picture; it moves on the next T2554 step that puts the carousel on the compositor, if any.
- **No child windows to place at the end.** Nothing moved them during the slide, on either path.
