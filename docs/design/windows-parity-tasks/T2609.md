# T2609 - A growing window-edge step waits longer for the terminal's frame inside T2578's pre-layout than in a plain WM_SIZE pass (viewer 2.8 vs 1.6 ms; renderer draw-begin -> target-ready 1.5 vs 0.9 ms mean, 52 vs 21 steps over 2 ms): find what the renderer thread blocks on while the top-level is inside WM_WINDOWPOSCHANGING and remove it, so the blank-free grow costs no rate

## Summary

T2603 removed the redundant `WM_SIZE` layout after a pre-layout, so a growing
step is now one layout pass plus a desk blit. What is left of the pre-layout's
cost is the frame WAIT: under `GHOZTTY_RESIZE_TRACE` (edge-drag-rate.ps1 run
20261101-073120, Debug, background desktop) the pre-layout pass spends about
the same on placement and paint as a plain pass (row3 13.2 vs 13.4 ms), but
waits longer for the terminal's frame at the new size (viewer 2.8 vs 1.6 ms),
because the renderer thread's `draw-begin -> target-ready` stage is slower
while the top-level is inside `WM_WINDOWPOSCHANGING` (mean 1.5 vs 0.9 ms; 52
vs 21 draws over 2 ms). That stage is `swap_chain.nextFrame()` plus the size
update in `renderer/generic.zig` (before `target-ready`), so suspect the
previous frame's SwapBuffers/fence on a child of a window mid-SetWindowPos.

Find what it blocks on (add a trace stage after `nextFrame()`), remove it,
and `edge-drag-rate.ps1` C should land well under its 125% line (D106 asks
the user whether to keep the pre-layout at all).

## Validation criteria

- [ ] `edge-drag-rate.ps1` C: a growing step with the pre-layout within 110% of one without, both scenes, on a quiet box.
- [ ] The trace names the blocking stage and shows it gone.
