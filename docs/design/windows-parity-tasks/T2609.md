# T2609 - A growing window-edge step waits longer for the terminal's frame inside T2578's pre-layout than in a plain WM_SIZE pass (viewer 2.8 vs 1.6 ms; renderer draw-begin -> target-ready 1.5 vs 0.9 ms mean, 52 vs 21 steps over 2 ms): find what the renderer thread blocks on while the top-level is inside WM_WINDOWPOSCHANGING and remove it, so the blank-free grow costs no rate

## Summary

T2603 removed the redundant `WM_SIZE` layout after a pre-layout, so a growing
step is now one layout pass plus a desk blit. What is left of the pre-layout's
cost is the frame WAIT: under `GHOZTTY_RESIZE_TRACE` (edge-drag-rate.ps1 run
20261101-073120, Debug, background desktop) the pre-layout pass spends about
the same on placement and paint as a plain pass (row3 13.2 vs 13.4 ms), but
waits longer for the terminal's frame at the new size (viewer 2.8 vs 1.6 ms),
because the renderer thread's `draw-begin -> target-ready` stage is slower
while the top-level is inside `WM_WINDOWPOSCHANGING` (mean 1.5 vs 0.9 ms; 52
vs 21 draws over 2 ms). That stage is `swap_chain.nextFrame()` plus the size
update in `renderer/generic.zig` (before `target-ready`), so suspect the
previous frame's SwapBuffers/fence on a child of a window mid-SetWindowPos.

Find what it blocks on (add a trace stage after `nextFrame()`), remove it,
and `edge-drag-rate.ps1` C should land well under its 125% line (D106 asks
the user whether to keep the pre-layout at all).

## In plain terms

Dragging the window's edge felt slow. The user's guess was that the time goes
into resizing the terminals' content on every step. This task measured where
each step's time actually goes, so the fix targets the real cost.

## Step 1 result (2026-11-01): the A/B

`GHOZTTY_RESIZE_NO_CONTENT` (`src/apprt/win32/resize_content.zig`) has three
arms. `content` (unset) is shipped. `held` keeps the terminals at their
pre-drag size, fills the strips and applies the size at release. `empty`
makes a pane's resize do nothing (the floor). The new
`edge-drag-rate.ps1 -ContentArms [-ReleaseSandbox -ExePath ...]` mode prints
each drag's stage breakdown.

ReleaseFast (`zig-out-perf`, run 20261101-150819), ms per step:

| scene/dir     | content: total / wait / place / paint | held | empty |
|---|---|---|---|
| row3 grow     | 13.2 / 4.4 / 6.1 / 1.9 | 8.9 | 8.9 |
| row3 shrink   | 12.8 / 5.6 / 5.3 / 1.0 | 7.7 | 7.6 |
| viewer grow   | 12.8 / 4.6 / 6.0 / 1.4 | 8.1 | 8.7 |
| viewer shrink | 11.9 / 5.0 / 5.4 / 0.6 | 7.4 | 7.0 |

In release the user is right. The wait for each terminal's frame at its new
size takes 33-44% of a step, and holding the content removes all of it: held
equals the empty floor, at 75 -> 112-135 fps. In Debug (runs
20261101-145430/145656) the same wait was only about 1 ms out of 15-17, because
Debug's own pixel loops (the desk compose, about 3 ms) bury it. A Debug-only
bench would have ruled the hypothesis out. That is why `-ReleaseSandbox`
exists.

The original question (why `draw-begin -> target-ready` is slower inside the
pre-layout) no longer matters: the fix removes the frame wait altogether
instead of making it cheaper. Follow-ups:

- **T2623** (P0): make the held arm the default for edge drags, add the
  150 ms pause debounce, and make it flash-free.
- **T2624** (P1): the 7-9 ms floor (window placement and desk paint).
