# T1484 - A blocked loop is only visible to somebody who runs a command; nothing tells the user their account hit its spend limit

## In plain terms

For two and a half days the loop did nothing because the account had run out of
monthly budget. The box knew — or could have known — within a minute, and the
only way to find out was to type a command nobody typed. There is no place a
person glancing at their screen would have seen it. When work stops for a reason
only the user can fix, the screen should say so.

## Summary

T1483 made the reason **legible**: `go-loop-health.ps1` now reports
`blocked=usage-limit` with the message and the instant it clears, and the
watchdog log names it on every decision. That closes the diagnosis gap and
nothing more — both are pull, and during the 2026-09-09..12 outage nobody
pulled for 63.5 hours.

What is missing is a **push**. Candidates, in rough order of how little they
cost the user:

- The **task dashboard** already polls `go-loop-health.ps1 -Json`, which now
  carries `blocked`, `blocked_kind`, `blocked_why`, `blocked_resets_at`. A
  banner across the top — "the loop is blocked: monthly spend limit, clears
  2026-09-12 01:00" — is the cheapest real answer, and it is where the user
  already looks.
- The loop pane's own **sticky banner** (`+set-banner`), so the terminal window
  running the loop says it without a dashboard at all.
- The **daily digest**: a day the loop was blocked for hours must say so in
  Commentary rather than reading as a thin day. Today's digest is the first
  chance to test this.

The bar to clear: on the next quota outage, somebody who walks past the screen
sees it, and the gap between the block starting and a human being able to know
about it is minutes rather than days.

## Validation criteria

- [x] A blocked loop is visible without running any command — at minimum on the
      task dashboard, from the `blocked*` fields `go-loop-health.ps1 -Json`
      already publishes.
- [x] The surface names the reason and when it clears, in the user's words, not
      "turn_age exceeded".
- [x] It clears itself the moment the block lifts; a stale "blocked" banner over
      a working loop is worse than none.
- [x] An acceptance arm stages a blocked health payload and asserts the surface
      appears, with an unblocked payload as the negative control.

## How it was validated

- **Visible with no command** - `test\win32\dashboard-dom.ps1` C31/C34: the
  page, driven in a real browser against a blocked payload, carries a
  `#blockbar.blockbar` across the top of the document with nothing clicked.
- **In the user's words** - C32/C33: the bar reads "The loop is stopped: this
  Claude account has hit its usage limit", quotes the message that caused it,
  and says "It clears 2026-09-12 01:00".
- **It clears itself** - C35 flips the stub's payload to unblocked and lets the
  page's own fetch-and-render path remove the bar; `test\win32\task-dashboard.ps1`
  F3 is the server-side half, where a block recorded against a turn the loop has
  since completed reports nothing.
- **The arm can score red** - the same driver against a copy of the page with
  the `renderBlockBar(d)` call removed scored `T565-DOM-SELFTEST 4 FAIL`.
