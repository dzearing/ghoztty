# T726 - test\win32\persistence-flag.ps1 is red: launch sites declare no session persistence

## In plain terms

The test suite has a rule that every test which opens a terminal window must say
out loud whether it wants the previous run's windows restored on top of it.
Forty-nine places had stopped saying it, so the check that enforces the rule
reported a failure - and a check that is always red is a check nobody reads,
which lets a test quietly inherit another test's windows and fail for reasons
that have nothing to do with what it is testing. All forty-nine say it again,
and the check is green.

**Re-measured 2026-09-03 by T404's already-fixed sweep. The four sites this

`test\win32\persistence-flag.ps1` (T158) enumerates every GUI launch across
`test\win32\` and requires each to DECLARE its session-persistence intent - by
passing `--session-persistence=`, by passing something built from it, by having
every caller of its helper pass it, or by carrying a `# persistence: <reason>`
marker.

What is left, from a run on 6161bc18e:

```
FAIL  A1 no launch leaves persistence unstated (undeclared: 49 of 274)
FAIL  C2a a launch with no persistence flag RESTORES the previous run's window (2 panes, got -1)
FAIL  C2b the restored pane is LIVE: input reaches its child and output returns
3 FAILURE(S) (17 passed)
```

**A1 - the corpus drifted, the enumerator is fine.** The original four
(`agent-attach-refused.ps1:276` and three in `url-scheme.ps1`) all carry
deliberate `# persistence:` markers today and no longer appear. The corpus grew
from 164 launch sites to 274 in the meantime and 49 are undeclared, in three
families:

- **New suites nobody declared**: `startup-failure.ps1` (7 sites),
  `install-restart.ps1`, `install-maintenance.ps1`, `install-walkthrough.ps1`,
  `update-real-msi.ps1`, `update-graceful.ps1`, `session-vanished.ps1`,
  `holder-*.ps1`, `agent-*.ps1`, `rdp-session.ps1`, `restore-late-agent.ps1`,
  `session-layout-preserve.ps1`, `chooser-*.ps1`, `remote-reconnect-relay.ps1`,
  `window-name-env.ps1`. These want the same per-launch judgement T158
  describes.
- **The audits' own fixtures**: `launch-preflight-audit.ps1` (7),
  `desktop-launch-audit.ps1` (4) and `suite-run.ps1` (3) are flagged for their
  OWN violator strings - lines that exist to be found by a sweep. A rule that
  cannot express "this string is a specimen" turns every audit that grows one
  into a new violation, so the enumerator needs a way to say it.
- **Launches of something that is not ghoztty**: `suite-run.ps1`'s `ping`
  decoys, `upgrade-staleness.ps1`'s powershell decoy, `task-dashboard.ps1`'s
  node server. Those cannot restore anything and should not be counted at all.

**C2a/C2b are a different defect, and they are new here.** Sections C2/C3 are
the behavioural half: a relaunch WITHOUT the flag should bring the previous
run's window back. C3 (`--session-persistence=false` restores nothing) passes;
C2 reports `got -1 pane(s)`, meaning no restored window was found at all. That
is either a real restore regression or a fixture that no longer leaves C2 a
manifest to restore from - it needs its own root-cause pass, and it is why the
script is red today rather than merely nagging.
