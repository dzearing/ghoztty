# T2943 - 4K fold glide on the published release: one tick over 16.7 ms in 2 of 5 runs that is NOT the fold-tick shape (why=none partial compose 4-10 ms + a 6 ms window-move batch, beside a 402 ms renderer swap stall) - find what slows that tick

## Summary

win-v1.54.16 (17ffa33d3, carries T2941), release sandbox, drag-glide 3800x2100 travel 2600 step 24, ring trace, 5 runs: per-tick cost p99 11.8-12.4 ms, max 12.7/14.1/15.8 ms on runs 1,2,4 (0 over), but run 3 had ONE tick at 17.5 ms (preceded by a 15.4 ms tick, both with every phase ~2x its neighbours: dc 979 vs ~400 us, desk_in 2271 vs ~1130, compose 4.1 ms, why=none cover=0, waits=0) and run 5 ONE tick at 20.8 ms (batch EndDeferWindowPos 6.0 ms, partial compose 9.6 ms why=none, a strip face carried=true on that tick; the line before is an opengl perf line swap_max_ms=402 swap_avg_us=134398). Published 1.54.14 had 4-5 fold ticks over a run; T2941 removed those. These residual outliers are the last thing between T2462 and its 4K 'no frame over 16.7 ms' clause. Find whether it is box/GPU contention (rerun on a quiet box, count over several runs, correlate with the renderer swap stall) or a real code path (a compose that should have reused the desk; a batch that waited on a hung renderer), and either fix it or re-scope the clause with evidence. Repro: temp\t2462-rel16 + the runner in T2462's progress log.

## In plain terms

Dragging a divider across a 4K window so panes fold into strips now runs at
about 100 frames a second, but roughly once every two drags a single frame
takes 17-18 ms instead of fitting in one 60 Hz refresh. This task found out
why: it is not one broken step, it is the busiest kind of frame (the one that
repaints a wide strip label) running into ordinary Windows housekeeping
delays. Shaving that busiest frame is the fix, and that work now lives in
T2942.

## Findings

Measured on the published win-v1.54.16 exe (temp\t2462-rel16), release
sandbox, ring trace, 4K arm (3800x2100, travel 2600, step 24), 12 more runs on
2026-11-12 23:39-23:47 with a 500 ms CPU sampler of every other process beside
each run (scratch runner: Isolation.ps1 -ReleaseSandbox + drag-glide.ps1 per
run, count `stack trace tick ... cost_us` > 16700, sum other-process CPU%).

1. **Under real load the clause collapses, and the load was the other loop
   lane.** Run a5 had 55 ticks over 16.7 ms (max 68.7 ms, p99 32.9 ms) while
   other processes used up to 46% of the box - zig.exe compiles (lane B
   building T2938, which also landed 23:38 inside the window of the original
   run-3/run-5 captures). The timing lock (MachineLock.ps1) only keeps the
   other lane's TIMING scripts out, not its compiles, so a 4K capture taken
   while lane B builds is not a measurement of the app.
2. **On a quiet box (other CPU 5-10%) the residue is 5 ticks in 11 runs**
   (runs a1-a4,a6 + t1-t6: 0,0,2,0,1 / 0,1,0,0,1,0), each 17.4-18.5 ms, about
   1 tick in 2,000. Per-tick p99 11.9-12.9 ms throughout.
3. **Every quiet-box outlier is a heavy tick plus a tail, never a new code
   path.** Ticks >= 12 ms (14-19 a run) are, 100% of the time, the ticks that
   repaint a carried strip face through its layered popup: face cost 3-8 ms
   (UpdateLayeredWindow of a ~650-700 x 2023 bitmap ~1.3-2 ms, plus fill and
   finish) on top of the window-move batch (2.5-3.6 ms mean on those ticks)
   and the vacated compose (~3 ms). A light tick's face is ~0.6 ms. The
   outliers are those same ticks with ONE window-manager-synchronous call in
   its tail: SetWindowRgn 4.0-4.3 ms (mean 0.2-0.5), EndDeferWindowPos 6-6.5 ms
   (mean ~2, run max ~7 in runs with no outlier), GetDC 1 ms (p50 0.3, p99
   0.7-1.0, run max 1.3-2.5 in every run). The run-3 original: face 6.3 ms +
   batch 3.8 + vacated 5.5; the run-5 original: batch 6.0 + compose 9.6 (the
   2x tail of the iters=2 compose, normally <= 5.2 ms).
4. **The work in those ticks is normal; the wall time is not.** The card
   region calls on the run-3 outlier tick spent 575k/610k/963k cycles, the
   same as the run median (634k); cycles per QPC tick 215-270 against a
   191-300 p10-p90. The thread was not doing more, it was waiting on the
   window manager, which is why each outlier's slow phase is a different call.
5. The 402 ms renderer swap stall in the run-5 original is the end-of-run
   flush of hidden/strip panes (fps=2 panes, logged after the ring), not on
   the UI thread and not on the outlier tick (10 s apart in QPC).
6. A/B with `GHOZTTY_COMP_PANE_TREE=1` (faces on the composition tree, no
   per-tick ULW/SetWindowRgn) was INCONCLUSIVE: the knob did not engage under
   drag-glide.ps1 (every pane still logged `tree=false`, every face `tree=0`),
   so those six runs (t1-t6) are a second popup-path sample, not a tree one.

**Verdict:** the residue is the app's heaviest tick (wide strip face +
batch + compose, ~12-14 ms of synchronous win32k work) leaving ~3-4 ms of
headroom, which an ordinary DWM/win32k sync tail eats about once per 2,000
ticks. It is not outside the app - the app chose to do that much synchronous
window work on one tick - so the clause is NOT re-scoped. The lever is cutting
the heavy tick's placement + face cost, which is T2942's scope; T2942 is raised
to P0/M1 and replaces this task in T2462's deps.
