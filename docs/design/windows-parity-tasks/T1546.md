# T1546 - Popping a pane out of a maximized window gives a full-screen window that is not maximized

## Summary

`Window.newWindowFrameAt` sizes the popped-out window from `GetWindowRect` of
the window the pane is leaving, and `commitPopOutDrop` then forces
`start_maximized = false` so the window honours the previewed rect. That pair is
right for an ordinary window and wrong for a MAXIMIZED one: the rect it copies
is the whole work area, so the pane arrives in a restored-state window that
happens to cover the screen edge to edge. Dragging its caption then does not
un-maximize it (there is nothing to un-maximize), and the window has no smaller
size to fall back to.

Decide what a pop-out out of a maximized window should produce - most likely the
source window's RESTORED rect (`GetWindowPlacement().rcNormalPosition`) placed
against the drop point, which is the size the user last chose by hand - and make
the preview say the same thing, since T1539's acceptance already holds the
preview and the window that arrives to the same rect.

## In plain terms

Maximize a window, drag one of its panes out onto the desktop, and the window
you get fills the whole screen even though it is not maximized - so it cannot be
restored to anything smaller. It should come out at a normal window size.

## Goals

- [ ] A pop-out from a maximized window produces a window at a sensible size,
      not a screen-filling restored one.
- [ ] The preview shows that same rect while the button is down.

## Validation criteria

- [ ] `test\win32\rearrange-desktop-drop.ps1` grows a claim: from a
      MAXIMIZED source window, the window that arrives is smaller than the work
      area and matches its own preview.
