# T1565 - A manual check for updates answers only with a tray balloon, which Windows is free to swallow

## In plain terms

You click "Check for Updates…" and Ghoztty answers in a tray balloon. Windows
decides whether a balloon is shown at all — Focus Assist, notification
settings, a full-screen app, a tray icon the shell refused — and when it
decides not to, you get nothing. Not a wrong answer: no answer. From where you
sit, "there is no update" and "the answer was thrown away" look exactly the
same.

## Summary

Filed from the T1563 turn, which fixed the case where the app *decided* to say
nothing. This is the other half: everything a manual check has to say — "an
update is available", "you are up to date", "the check failed" — is delivered
through `App.showUpdateBalloon` → `showTrayBalloon` → `Shell_NotifyIconW`, and
that call is allowed to fail or be ignored with no recourse.

It is not hypothetical here. `test\win32\update-check.ps1` logs it on this very
box on a routine run:

```
warning(win32): NIM_SETVERSION failed for tray uid=2 (NIM_ADD failed too); balloon clicks will not be delivered
```

and `showTrayBalloon` also returns false silently when the title or body is
too long for `NOTIFYICONDATAW`. Nothing upstream of it distinguishes "shown"
from "dropped", and nothing tells the user.

The distinction that matters is CONSENT: an unsolicited offer belongs in a
balloon, because a balloon is the polite way to interrupt somebody who did not
ask. A manual check is not unsolicited — the user asked a direct question with
a click, they are looking at the app, and the answer should land somewhere they
are already looking. Mac answers a manual check in a window (the About panel's
own update row), not in Notification Center.

Likely shape of the fix: a manual check reports in a small dialog (the T50
`ConfirmDialog` pattern, "Update available / Install and Restart / Later" and
"Ghoztty is up to date"), anchored on the focused window, with the balloon kept
for the AUTOMATIC arm. That also gives the manual path a click target that is
not the tray icon, which is what the `NIM_ADD failed` line above breaks.

Worth checking while in there: whether this is what actually happened to the
user on 2026-09-14. T1563 could not pin the mechanism down — an automatic and
a manual check logged identically at the time — and "the answer was delivered
to a balloon nobody saw" fits their report as well as any other theory.

## Validation criteria

- [ ] A manual check that finds an update reports it in a window, not only a
      balloon, and that window offers Install and Restart / Later.
- [ ] A manual check that finds nothing reports "you are up to date" the same
      way, where the person who clicked is looking.
- [ ] The automatic arm is unchanged: still a balloon, still quiet about a
      version already offered inside `update_check.offer_expiry_ms` (T1171,
      T1563).
- [ ] A tray notification that the shell refuses no longer costs the user the
      answer to a question they asked — demonstrated with the tray path made to
      fail, not argued from the code.
- [ ] Acceptance coverage extends `test\win32\update-check.ps1` scenario 7
      (which already drives a real manual check through
      `GHOZTTY_UPDATE_MANUAL_MS`).
