# T1555 - About box links are never proven to actually open anything

## Summary

T714 gave the win32 About box a row of hyperlinks (Release notes, Commit, Docs,
GitHub) and `test\win32\ipc-version.ps1` proves the controls are there, sized,
visible and carrying the right labels - but nothing proves that ACTIVATING one
reaches the right URL. Both the click and the Enter paths end in
`App.openUrl` -> `ShellExecuteW`, so an acceptance script that exercised them
would launch a browser on the test desktop on every run, which is why T714
stopped at the controls.

`ViewerPane.zig` already solved exactly this: under a test lane a link is
RECORDED as `<kind>:<target>` instead of reaching `ShellExecuteW` (see the
comment at `ViewerPane.zig:3406` and its T594 note). Extending that recording
to `App.openUrl` - or hanging it off the same switch - would make the About
row's destinations assertable on the box: activate each link, read the
recording back, compare it to the URL `about_links` says that build earns.

The two cases worth proving are the conditional ones, because they are the ones
a unit test can get right while the wiring is wrong: a release build's version
link resolving to `.../releases/tag/win-v<version>`, and Enter on a focused
link FOLLOWING it rather than dismissing the dialog (`handleKey` declines the
key for a focused link; nothing on the box checks that it still does).

## In plain terms

The About box now has clickable links. We have checked that they are there and
that they say the right things, but not that clicking one actually goes where
it claims - a test that clicked would pop a web browser open every time it ran.
There is already a trick elsewhere in the app for recording where a link WOULD
have gone instead of going there; this is about reusing it here.

## Goals

- [x] Link activation is recordable under a test lane instead of reaching the shell
- [x] The About row's destinations are asserted on the box, per link
- [x] Enter on a focused link is proven to follow it and leave the dialog open
- [x] A release-shaped build is proven to produce the `win-v` tag URL

## Validation criteria

- [x] An acceptance script activates each About link and reads back the exact
      URL, with no browser launched - `test\win32\about-links.ps1` ALL PASS
      (26 assertions) on the test desktop, 2026-11-20, guard `about-links` stamped
- [x] A negative control proves the assertion can fail (a wrong expected URL
      makes the run red) - `-NegativeControl` scores exactly B 'Docs' and C red
      (2 failures, 24 passed)

## Resolution

The viewer's `LinkSink` (T594) is an in-process unit-test seam, unreachable
from a script, so this adds its out-of-process twin rather than reusing it:
`src/apprt/win32/open_url_seam.zig`, Debug builds only (a release compiles both
reads to null).

- `GHOZTTY_TEST_OPEN_URL_LOG=<file>` makes `App.openUrl` append the URL to the
  file as one line and return before `ShellExecuteW`. Every shell-bound link in
  the app goes through `openUrl`, so the seam is not About-specific.
- `GHOZTTY_TEST_ABOUT_VERSION=X.Y.Z` stands in for the version About builds its
  LINKS from (the provenance text still names the build's own), so a dev build
  shows the row a published release shows and the `win-v` tag link is provable.

`test\win32\about-links.ps1` opens About through the palette on the test
desktop and: A asserts the release-shaped row (Release notes, Commit, Docs,
GitHub, in order); B posts a click at each link and reads back exactly one
line, the exact URL, with the box still open; B1 pins the release link to the
`win-v<version>` tag page; C focuses Docs and posts Enter - one line, the docs
URL, box still open; D is the control that C's "still open" can fail: Enter on
OK closes the box and records nothing. New guard row `about-links`.
