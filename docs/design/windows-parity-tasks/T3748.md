# T3748 - A link clicked in a viewer pane opens its side pane WITH the keyboard on Windows and Linux; the Mac leaves the caret where it was and features the new pane

## Summary

Found in T3628. Mac ViewerView.openViewerSplit -> BaseTerminalController.newViewerSplit never moves focus (moveFocusTo: nil), always features the new pane (paneStackState.feature) and anchors it via backgroundSplitAnchor (docs/reference/stacked-panes.md: 'a banner link's Cmd-click side pane' is a non-focus split). GTK surface.zig openViewerSplit calls newSplitAt with the default focus=true (its comment says 'focused, as the keyboard's split is', which the Mac code does not bear out); win32 sets split_background only from IPC (IpcHandlers.zig), so its viewer-link / banner-link side pane takes focus too. Re-verify the Mac behavior on the Mac build, then pass focus=false on both ports (GTK: .focus = false in openViewerSplit; win32: split_background for the viewer link and banner link side pane) and assert it: test/linux/viewer-links.sh and the win32 viewer-link harness - the source pane keeps the caret and the new pane is on show in a full row. P2: user-visible focus divergence from the Mac on both ports, only for link-opened side panes.
