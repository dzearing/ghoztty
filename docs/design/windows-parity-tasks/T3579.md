# T3579 - Linux: an in-app ghoztty:// link (viewer page, pane banner) that names nothing only logs on GTK; the Mac and the desktop-delivered path show the Can't focus dialog

## Summary

IpcHandlers.focusLink (src/apprt/gtk/IpcHandlers.zig) logs the verbs.focus reply and nothing else, so a viewer or banner link to a closed window does nothing visible - the Mac presents GhozttyURLScheme.Failure, and T3343's url_scheme.openInApp already presents the same wording in a GtkAlertDialog (coalesced). Route focusLink's miss through url_scheme's present (keep the GHOZTTY_TEST_VIEWER_LINKS sink behaviour), and extend test/linux/viewer-links.sh with a missing-target link.

## In plain terms

On Linux, clicking a Ghoztty link inside a document pane or a pane's status
banner that points at a window that is no longer open did nothing at all -
no message, no feedback. On the Mac (and on Linux when the link comes from
outside the app) you get a "Can't focus" message saying nothing has that
name. Now the in-app click shows that same message.

## Goals

- [x] A viewer-page or banner link that names nothing (or names a pane two windows hold) shows the scheme's Can't focus dialog, same wording as the Mac and the desktop path
- [x] A malformed in-app link says "Unsupported Ghoztty link" (win32's handleInApp does the same) instead of being swallowed
- [x] A burst of misses is still one dialog (the same coalescing flag as the desktop path)
- [x] The headless harness proves it
