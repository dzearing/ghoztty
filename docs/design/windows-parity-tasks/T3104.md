# T3104 - Stashed panes and panes behind a zoomed pane keep rendering every frame on Windows: tell them they are hidden, and never draw a hidden surface from any thread (Mac e15077861, 6bd6fe7fb)

## Summary

Mac e15077861: a terminal is visible only if its window is on show, it is not stashed, and nothing is zoomed over it - re-evaluated on occlusion changes and every tree change (covers a pane created while its window is covered). 6bd6fe7fb (shared renderer): a hidden surface draws nothing even when a non-render-thread caller asks. On Windows: verify what +stash and split zoom do to the hidden panes (setVisible/occlusion signal into the renderer), wire them as hidden, and audit any WM_PAINT/resize path that draws a hidden surface directly and would re-take released targets. Validation: zoom a pane over busy siblings and stash a busy pane - the hidden ones stop presenting (frame counter flat) and release targets; unzoom/restore shows current content with no blank frame.

## In plain terms

When you zoom one pane, or stash a pane into the sidebar, the panes you can no
longer see stopped drawing already on Windows - but each one kept several
screen-sized pictures in graphics memory the whole time. Now they hand that
memory back while hidden, the way Mac does since this week, and redraw fresh the
moment you unzoom or restore them.

## Goals

- [x] panes behind a zoom give back their render targets
- [x] a stashed pane gives back its render targets
- [x] unzoom / restore shows current content, drawn in full
- [x] no hidden surface is drawn from any thread (audit - see Design note; no code needed)

## Design note

What Mac fixed, and where Windows already stood (verified 2026-11-15):

- **Hidden panes stop drawing** (e15077861's main point): already true here.
  Zoom (`layoutSplits` zoom branch), stash (both the grid and hero layouts)
  and stack-tucked cards all call `PaneView.setVisible(false)`, and a hidden
  render thread neither builds nor presents (`Thread.renderCallback`). A pane
  created while its window is covered is held hidden by
  `occlusion.paneShows` (T2914).
- **Nothing draws a hidden surface from another thread** (6bd6fe7fb): the
  shared-renderer guard is already in this branch and is Metal-only; on
  Win32 there is no other drawer to guard - `must_draw_from_app_thread` is
  false, no win32 code calls the core `Surface.draw`, and WM_PAINT / IPC
  thumbnail requests only set `force_frame` and wake the render thread, which
  skips while hidden.
- **The gap: targets.** Mac's hidden surface gives back its frames; here only a
  hidden window (T2474) or a background tab (T2975) did. Zoomed-over and
  stashed panes now go through `PaneView.hideReleasing`, which marks them
  release-safe (`Surface.window_hidden`) before hiding them. A stack card its
  strip face carries is left alone on purpose - the face reads its frame.
