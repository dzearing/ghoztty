# T1488 - A day the loop spent blocked reads as a thin day in the morning digest

## In plain terms

When the loop spends most of a day unable to work - the Claude account hit its
usage limit, or its login expired - the morning digest used to read as if
little got done. Now the digest names the block: how long, what share of the
day, and why, so a blocked day and a slow day no longer look the same.

## Goals

- [x] a source that measures, from the watchdog logs, how long each lane was blocked on a given day, and why
- [x] a rule in the digest step: a materially blocked day is said so in Commentary
- [x] acceptance that proves the report can score red

## Summary

go.md step 0.5's Commentary is written from the log and the tracker, both of which are silent about hours the loop spent blocked by a usage limit - so a day that shipped little because the account was out of budget reads exactly like a slow day. The watchdog log and its state file carry the answer. Give the digest step a source and a rule: when the loop was blocked for any material part of the day, Commentary says so, for how long, and what it cost.

## Validation criteria

- [x] A real blocked day is measured: `scripts\loop-blocked-time.ps1 -Date 2026-11-18` against the live watchdog logs reports `LOOP BLOCKED` - lane a 16h41m (03:32-20:13), lane b 16h42m (03:32-20:14), usage-limit, clears 2026-11-21 00:00; 2026-11-16 reports `LOOP NOT BLOCKED`.
- [x] Spans are measured correctly (first-to-last observation; a healthy tick or a gap over 20 min ends one; midnight clipped to each day; under an hour is minor) - `test\win32\loop-blocked-time.ps1` section A.
- [x] No watchdog evidence for the day is `LOOP UNKNOWN`, never "not blocked" - section B.
- [x] The digest sentence names duration, share of day, reason in plain words, and reset - section C; go.md step 0.5 runs it and states the rule - section D.
- [x] The harness can score red: against a mutant subject whose BLOCKED pattern never matches it scored `16 FAILURE(S)`.
