# T2036 - Both loop lanes run lane B's git hooks: core.hooksPath lives in the shared .git/config, and each lane's commit-guard install points it at its OWN tree, so the last lane to claim wins for both

## Summary

2026-10-16 20:45: git config --show-origin core.hooksPath in D:\git\ghoztty reads D:\git\ghoztty-b\scripts\githooks from file:.git/config - the one config every worktree shares. git-commit-guard.ps1 install (run by every claim) sets core.hooksPath to its own tree, so lane A commits through lane B's pre-commit hook (and lane B's lock path) until lane A next claims, then the reverse. A hook edit in one lane silently governs the other, and a lane whose tree is behind runs stale hooks. Fix: set extensions.worktreeConfig=true and write core.hooksPath with git config --worktree, or keep one path both lanes agree on (the main worktree's), and have install read it back. Prove it in go-loop-guard.ps1 section W: after both lanes install, each worktree's effective hooksPath is its own (or the agreed one).

## In plain terms

Two copies of the work loop run side by side, each in its own folder of the
same repository. A safety check that runs before every commit was being
configured in a spot both folders share, so whichever loop started last made
the OTHER loop run its copy of the check. Now each folder gets its own setting,
and each loop runs its own check.
