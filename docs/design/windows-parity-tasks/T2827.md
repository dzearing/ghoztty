# T2827 - The pane sidebar's card following a grid glide (T2406) is resized and repainted from the window thread on every glide tick, so a busy window thread freezes it while the declared grid glides on in the composition pane tree

## Summary

Split of T2780. PaneSidebar.gridStepped (PaneSidebar.zig ~3594) runs from Window.stackSlideTick: it reads paneSidebarFollowLag, SetWindowPos-resizes the sidebar's child window and UpdateWindow-paints it, every tick. Once T2825 declares the strips that the grid's shift moves, the grid's whole leading edge glides on the compositor through a stall and the sidebar column beside it does not, so the gutter between them opens and closes. The sidebar column has to become a declared shape too (its card's edge on the same 45 ms follower as Slide.leadingLag's card), or the column glide has to own the clock. Oracle: the sidebar arm T2825 adds to comp-glide-hold-onscreen.ps1, scoring the gutter between the sidebar card and the grid's leading card through a GHOZTTY_DEBUG_GLIDE_STALL_MS stall (constant within 2 px on every frame), -NoDeclare red.

## Carried over from T2804 (closed as a duplicate of this task, 2026-11-08)

T2804 asked for the same motion ("the column picture as a visual whose
clip/width is declared once, in step with the grid's own glide") but depended
only on T2765, the sidebar's own composition tree. Reading the code on claim
showed why that is not enough, and the findings belong here:

- **The grid's sidebar glide is still a window-thread tick.** The stack slide
  (`Window.stackSlideTick` -> `layoutSplitsLive`) places the pane visuals per
  tick, even in the composition pane tree; nothing about it is declared yet.
  A column declared on the compositor beside an undeclared grid would drift
  from it through a stall - the gutter opening and closing - which is worse
  than both stepping together. So this waits on T2825, as filed.
- **The sidebar's own tree (T2765) is clipped to the sidebar's window.** A
  TOPMOST DirectComposition target on a `WS_CHILD` draws only inside that
  child's client rect. A collapse needs the moving edge to sweep across
  pixels that end up belonging to the grid, so either the sidebar HWND stays
  at `max(from_w, to_w)` for the glide with everything beyond the card's
  declared edge drawn correctly (it would cover the grid's leading cards,
  which are siblings under it - not possible from GDI underneath), or the
  column visual hangs on the WINDOW's tree (`chrome_comp.Host`, topmost over
  the children) for the glide and the HWND is placed once at the landing.
  The second is the shape that works for both directions; it ties this task
  to the chrome host being on.
- **The own-clock case** (`Column.following == false`, `TIMER_COLUMN`): only
  when no grid shift is planned (`Window` sets `stack_slide_column` only on
  a shifted, active slide). An expand on its own clock could ride the
  sidebar's own tree (HWND placed at `to_w` up front, the `under` backdrop
  beyond the clip edge), a collapse cannot (same clip constraint). Rare
  enough to land with this task rather than alone.
