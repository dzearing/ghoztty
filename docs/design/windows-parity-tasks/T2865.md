# T2865 - agent-recovery-tabs D3 is red on HEAD: after in-place agent recovery the two surviving tabs keep 3 old surfaces plus 1 new (count=4 reused=3) instead of two freshly rebuilt ones

## Summary

Found 2026-11-09 by T2842's due sweep. `test/win32/agent-recovery-tabs.ps1` fails one assertion:

    FAIL D3 two freshly rebuilt terminal surfaces (count=4 reused=3)
    [D] before=35652,12196,86788 after=12196,86788

D1/D2/D4/D5 pass: the rebuild runs from the original capture and each survivor
keeps its own session, but the surface set after recovery is 4 (3 of them the
pre-wedge surfaces) where the harness expects exactly the 2 survivors rebuilt
fresh. The closed tab's surface (or a stale one) seems to outlive the rebuild.

It is NOT T2842's change: it reproduces with `src/apprt/win32/App.zig` reset to
HEAD 1e0b4c0d7 (log: ghoztty-acceptance-parallel/20261109-074144). The last
App.zig edits before that were T2828's compositor-glide work (030719623), so
bisect from the guard's last green stamp. Decide whether the code regressed
(a surface leaked through recovery) or the harness's surface oracle went stale
after the pane-stack work.

## In plain terms

A safety test for "the terminal reconnects to its background helper without
losing your tabs" started failing. The feature itself was fine: a recent
memory fix made the app reuse a closed pane's window for the next pane, and the
test was still judging "did the panes get rebuilt?" by whether every window was
brand new. The test now asks the app's own log instead.

## Goals

- [x] name the cause (regression or stale oracle)
- [x] give D3 an oracle that survives window reuse
- [x] agent-recovery-tabs green alone
- [x] file the same defect in the sibling agent-recovery.ps1 (T2876)

## Resolution

Not a code regression. T2597 (`pane_pool.zig`, landed 2026-11-01) parks a
departing pane's HWND hidden in its top-level and hands it to the next pane
built there. The in-place rebuild builds each survivor's fresh pane BEFORE
releasing the old one, so survivor 1 gets a new HWND and parks its old one,
survivor 2 takes that parked HWND, and the spares stay enumerable as hidden
`GhozttyTerminal` children - `count=4 reused=3` on a correct rebuild. The
diagnostic dump showed both survivors' surfaces logging `surface closed`
inside the rebuild and the closed tab parked for undo (T1825).

D3 now counts `surface closed` between `in-place recovery: re-dialed` and
`in-place recovery: rebuilt` (want 2): each departing surface logs it
synchronously from `old_tree.deinit()`, and a recovery that rebuilt nothing
has no `rebuilt` line at all, so it still reads red. On red it dumps every
surface (pre-wedge/new, visible) and the recovery log lines.
