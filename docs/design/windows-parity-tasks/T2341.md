# T2341 - Windows pane sidebar rows no longer stay lit after clicking through to another window: a row covered by another window is not hovered, and hover re-syncs when the window gains or loses focus, as on Mac

## Summary

Mac 8faf92148 (+ the no-hover-while-dragging half of 97afdaf5a, which the reorder task carries). Clicking a row brings its window forward over this one with no mouse-leave, so on Mac hover counts only when this window is frontmost under the pointer (HoverTrackingView.pointerLocation) and re-syncs on key change; before, rows stayed lit and showed so when the window came back. Check the win32 sidebar's hover tracking for the same stale-hover shape (WM_MOUSELEAVE never arrives when another window covers the pointer) and fix it. Mac ref: docs/reference/pane-sidebar.md 'A row covered by another window is not hovered'; tests HoverTrackingViewTests.

## In plain terms

On Mac, clicking a sidebar row that brings another window forward used to leave the row lit up when you came back; that is fixed. Windows likely has the same stuck highlight. After this, a row is only highlighted while your mouse is genuinely over it in the front window.

## Goals

- [x] Reproduce or rule out the stuck hover on Windows after clicking through to another window - the shape is there by code reading (a row press SetCaptures, the click activates on the up, and a window raised over the column under the cursor owes it a WM_MOUSELEAVE that nothing guaranteed); a live repro needs the real cursor on the user's desktop, NOT RUN (the user is present)
- [x] Hover counts only while this window is frontmost under the pointer (`WindowFromPoint` must be the column itself; `pane_sidebar.resyncedHover`)
- [x] Hover re-syncs when the window gains or loses focus (WM_ACTIVATE either way posts `WM_RESYNC_HOVER` to the column)

## Validation criteria

- [x] On-box acceptance: another window raised over this one, then return, no row reads hovered - `test\win32\pane-sidebar-hover-resync.ps1` ALL PASS (17 assertions) via acceptance-parallel; the real-cursor-over-a-row half is NOT RUN (needs the user's desktop)
- [x] -NegativeControl goes red (5 failures: B never activated, so A never re-reads its hover)
- [x] Unit test `pane_sidebar: T2341 a resync drops a hover ...` in every lane

## Resolution

The column now asks its hover again from where the pointer really is whenever
its window is activated or deactivated (posted, so the z-order the click or
switch set up has settled first): off the column - another window in front
there, or no readable cursor - nothing is hovered and the pane tint lets go; a
held item, edge or thumb keeps its hover (T2337). A capture change also drops
the leave-tracking flag so the next move re-arms TrackMouseEvent. Debug oracle:
`pane sidebar hover resync reason=<activate|deactivate> window=<hwnd> was= hover= under=`.
