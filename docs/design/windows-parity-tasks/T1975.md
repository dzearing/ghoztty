# T1975 - The agent never says whether it is running inside a kill-on-close job, so a field log cannot show the one condition that loses every session at once

## Summary

T1970's mechanism (an agent spawned into a nested kill-on-close job dies with it) is invisible in the agent's own log: only the APP probes its job at startup. Have the agent log its job membership and immediate-job flags at startup (and report it in a health or +sessions field), so the next 'restart lost my sessions' report carries the answer instead of needing a repro.

## In plain terms

The background process that keeps your terminals alive can end up inside a
Windows container that kills everything in it when it closes. When that
happens, every terminal can vanish in one go. Until now nothing written down
said whether it was in such a container, so a "restart lost all my sessions"
report could not be explained from the log. Now the log says so on every
connect, with a warning when the container is the dangerous kind.

## Goals

- [x] The agent measures its own job once at startup and publishes it in its
      info file (`port.json`, additive `"job":{"inJob":B,"flags":N}`, nulls for
      unknowns) and on its own stderr.
- [x] The app copies it into ghoztty.log every time it connects to an agent
      (startup resolve, in-place recovery, late adopt), at WARN when the job
      kills on close, and says "not reported" for an agent too old to publish it.
- [x] An acceptance harness proves it against a really-jailed agent.

Decided (mechanism, not experience): no `+sessions` field. A Windows-only
CLI field would be exactly the platform divergence CLAUDE.md forbids, and the
log line is what a field report carries. The Mac has no job objects, so there
is no Mac half owed (a diagnostic for a Windows-only mechanism).

## Validation criteria

- [x] Unit: `formatInfoFile` emits the job field only when given one, with
      nulls for unknowns (agent lane); `parseInfo`/`agentJobPhrase` read it and
      an agent without it (win32 lane); `describeSelf`/`killsOnClose` (win32 lane).
- [x] On box: `test\win32\agent-job-report.ps1` - an app-spawned agent's
      port.json carries the field and the app logs the same pid and facts; an
      agent born inside a kill-on-close job reports `in_job=yes flags=0x2000
      kill_on_close` in port.json and its stderr; the app adopting it logs it
      at WARN; the job's teardown kills that agent (the warning is real).
- [x] Floor: `floor-lane.ps1 -Lane all` green.

Verified 2026-10-16: the unit tests ran in the agent and win32 lanes of
`floor-lane.ps1 -Lane all` (ALL LANES PASS); `agent-job-report.ps1` ALL PASS on
the test desktop and stamped. The jailed agent wrote
`"job":{"inJob":true,"flags":8192}` and the adopting app logged
`warning(win32_local_agent): local agent pid N job: in_job=yes flags=0x2000
kill_on_close - closing that job ends every session it hosts`.
