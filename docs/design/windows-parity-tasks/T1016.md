# T1016 - background-blur still rides the undocumented accent-policy blur; evaluate the documented Win11 acrylic backdrop

## Summary

T306 finding. applyBackgroundBlur (Window.zig) enables blur with SetWindowCompositionAttribute + ACCENT_ENABLE_BLURBEHIND, which has been undocumented since Win10. The documented Win11 route is DWMWA_SYSTEMBACKDROP_TYPE=3 (Acrylic). They are not identical for the user: the legacy accent blur blurs WHATEVER IS BEHIND THE WINDOW (other windows included), while a DWM acrylic backdrop samples the DESKTOP WALLPAPER only. Evaluate which one background-blur should be on Win11 (and what Mac's translucency shows through), measure both, and record the call. T306 rules out a backdrop for the OPAQUE chrome band; this is the separate, still-open question for the translucent case.

## In plain terms

Ghoztty has a "blur what's behind a see-through window" setting. The question
was whether to move it onto the officially supported Windows 11 way of doing
it. Measuring it turned up a bigger answer: today the setting does nothing at
all on Windows - neither the old way nor the new way blurs, because of how the
window is made see-through (which also fades the text, unlike on Mac). That is
now its own fix, and the supported Windows 11 blur is the one to use after it.

## Finding (measured 2026-09-27, Windows 11 26200, transparency effects on)

**Method.** `scripts\blur-backdrop-probe.ps1` parks a debug ghoztty
(`background-opacity=0.6`, `background-blur=true`) topmost over an 8px
red/white checker and applies each mechanism from outside the app - T306's
method, so no experiment code ships. Score `hf` = mean |dG| between horizontal
neighbours in a 300x120 client patch: the checker seen at 40% keeps ~12.7, a
blur drives it toward 0. The same modes are then applied to a positive-control
window built the way DWM materials expect (no `WS_EX_LAYERED`, frame extended
over the client, client alpha 0).

| Mode | ghoztty window (layered, LWA_ALPHA 153) | control window (per-pixel alpha) |
|---|---|---|
| no blur | hf 12.62 | hf 31.56 (sharp) |
| accent blur (shipped) | **hf 12.66** - not blurred, only lightened (R 108->163) | hf 1.13 - blurred |
| acrylic backdrop (3) | hf 12.62 - no effect | **hf 0.00**, smooth pink = the checker, blurred |
| Mica backdrop (2) | hf 12.62 - no effect | hf 0.00, pale wallpaper colour - checker gone |
| accent + acrylic | hf 12.66 | hf 1.13 |

**1. `background-blur` does nothing on Windows today.** The window is made
translucent with whole-window `LWA_ALPHA`, and DWM blurs only under per-pixel
alpha. The accent policy returns success and the view behind stays exactly as
sharp, just brighter. The same whole-window alpha fades glyphs with the
background, where Mac keeps text opaque - one root cause, filed as **T1787**
(P1). The `applyBackgroundBlur` doc comment in `Window.zig` ("the desktop
behind shows blurred") is therefore wrong; it is left for T1787 to rewrite with
the code rather than re-staling every guard over `Window.zig` for a comment.

**2. The task's premise was half right.** Mica samples the wallpaper only;
**acrylic does not** - it blurs whatever is behind the window, other windows
included, which is exactly what Mac's `CGSSetWindowBackgroundBlurRadius`
shows. So acrylic is a faithful translation of `background-blur` and Mica is
not.

**3. The call:** on Windows 11 `background-blur` uses the documented
`DWMWA_SYSTEMBACKDROP_TYPE = 3` (acrylic), with the accent policy kept only as
the fallback where that attribute is refused (pre-22H2). This is a mechanism
choice (both blur the same things) and so this seat's call, per the
2026-08-14 directive. What the user COULD tell apart - acrylic's own tint and
noise against Mac's plain blur, and Mac's configurable radius against
acrylic's fixed one - is carried into **T1788** as a side-by-side check that
files a decision if the look diverges. Neither mechanism can show anything
until T1787 lands, so T1788 depends on it.
