# T720 - toggle_window_float_on_top still will not stick on a ghoztty window, though the quick terminal's setTopmost does

## Summary

**Falsified on 2026-09-14 — everything below is the filing-day reading, kept for
the record.** Section E does not skip any more (T607 landed the fix and the
assertions), the float pins the window the user is on, and the one case that is
still refused is refused identically for an external process. See `## In plain
terms`, the validation criteria and the progress log for the measurement.

Section E of `test/win32/overlay-zorder.ps1` has announced a SKIP since T277:

```
SKIP E: toggle_window_float_on_top left the window non-topmost - float-on-top
is broken (T277), so the "legitimate topmost owner" case cannot be set up
```

Its stated reason is that *the app cannot reach a legitimately-topmost state on
this desktop at all*. **T180 falsified that.** The new section H toggles the
QUICK TERMINAL and measures, on the same run and the same background desktop:

```
PASS  H: the quick terminal is topmost (positive control)
PASS  H: the quick terminal float propagates to its owned popup (positive control)
```

So a ghoztty window CAN hold `WS_EX_TOPMOST` here. Both paths call the same
`w32.setTopmost` (`App.zig` ~5425 for the action, `QuickTerminal.animateIn` for
the quick terminal), and only one of them sticks — which means the remaining
cause is specific to the float-on-top path, not to the harness, the desktop, or
`SetWindowPos`.

## In plain terms

"Float on Top" in the Window menu is supposed to pin a terminal above your other
apps, and this card said it did not. Re-measured on 2026-09-14: **it does.** With
one window or with several, the window you are actually on pins on a single press
and unpins on the next.

There is one case where the pin is refused — a window sitting BEHIND another one,
which on a real desktop nothing can ask for, because the keybind, the palette and
the menu all belong to the window you are focused on. That refusal is Windows'
own: asking for the same thing from a completely different program gets refused
in exactly the same way. So nothing here was ours to fix, and what this task
leaves behind is the test that will notice if that ever stops being true.

## Where to look

- `src/apprt/win32/App.zig` ~5410-5435 — the action: early-returns when the bit
  already matches, then `w32.setTopmost`, then heals the owned popups.
- `src/apprt/win32/QuickTerminal.zig` 112-140 — the path that DOES stick, for
  comparison.
- `w32.healOverlayZOrder` demotes a stray-topmost popup, and Windows drags an
  owner out of the topmost band along with any owned window that is demoted —
  worth ruling in or out as the thing that undoes the float a moment later.
- Section E's own note says an INJECTED `HWND_TOPMOST` on a `GhozttyWindow` did
  not stick either, while the same injection on an overlay popup does (section
  B). That asymmetry is the sharpest clue and should be re-measured first.

- 2026-09-14 05:28: ROOT CAUSE MEASURED (probe, 3 variants, scratchpad float-probe2/3.ps1). With ONE window the float pins on a single press. With a SECOND window up, a press on the window that is NOT at the top of the z-order never pins - 0 of 10 cycles, and setTopmost logs 'topmost band change did not take want=true attempts=3' every time. The distinguishing condition is z-order position, not activation and not our code: an EXTERNAL harness injection of WS_EX_TOPMOST is refused on the same window (A as-is z=4 -> False), accepted the moment the window is raised (A z=2 -> True), and then refused on the window that fell behind (B z=4 -> False). So on a desktop with no foreground window the window manager silently refuses a band change for any window that is not front-most - SetWindowPos returns TRUE with GetLastError 0. The quick terminal path 'works' only because it is always the front-most window when it animates in. Fix: when the band change to topmost is refused, RAISE the window and retry - pinning a window above everything while leaving it behind its siblings is incoherent anyway.
- 2026-09-14 05:35: VERDICT: the card's defect is NOT a product defect any more, and the measurement says why. Two cases with a second window up: (1) the window the user is ON pins on ONE press and unpins on the next - keybind, palette and menu all go to the focused window, so this is every path a person can take; (2) a window BEHIND another, reachable only by an injected keystroke, is refused. Case 2 is the window manager's rule, not ours: an injection of WS_EX_TOPMOST from the HARNESS PROCESS is refused on the same window in the same state (app=False external=False). I built a raise-and-retry into setTopmost for case 2 and REVERTED it - SetWindowPos(HWND_TOP, SWP_NOACTIVATE) is refused on that desktop too, so it fixed nothing and would have shipped as unmeasured code. Landed instead: section C of test/win32/float-on-top.ps1, asserting the real-user path and asserting the app and an external caller get the SAME answer for a background window - an equality, so it stays honest if Windows ever changes its mind.
