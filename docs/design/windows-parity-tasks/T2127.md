# T2127 - Stacked panes: stashing, closing a viewer, killing a pane from the trash and activating the window never put the caret on a folded strip

## Summary

Split from T2084 (Mac 2811a3043). Only closeSplitPane routes through PaneStackState.paneOnShow today; route stash, trash-kill, viewer close (Ctrl+W) and window activation (WM_ACTIVATE focus restore) through the same choice so the focused pane is always on show, and do not read a stale focused terminal as focused. Also: a pane dropped on a strip stays minimized there, and a former strip is a drop target again once on show. Unit tests on the chooser; acceptance by enumerated focus after each operation.

## In plain terms

When some panes of a row are folded into thin strips, hiding the pane you are
in (stash) used to hand the keyboard to the folded pane next to it, and that
pane popped back open, unfolding the row you had folded. Now the keyboard goes
to a pane that is already showing, and the folded strips stay folded. The same
holds when you switch back to the window.

## Goals

- [x] Stash of the focused pane never hands the caret to a strip
- [x] Window activation hands the caret to a pane on show, never a strip
- [x] A stale focus landing on a strip after it folded is not adopted (terminal and viewer)
- [x] Trash-kill and viewer Ctrl+W: verified they already route through `closeSplitPane`'s `paneOnShowAfter` (T2083)
- [x] Drop rules checked (see Details)

## Details

Windows translation of Mac 2811a3043's caret rules:

- **Stash** (`Window.stashPane`): the neighbour a close would pick now goes
  through `paneOnShowAfter` with the rows from before the stash, exactly as
  `closeSplitPane` does.
- **Trash-kill** (`paneSidebarKill`) and **viewer Ctrl+W**
  (`performViewerBindingAction(.close_surface)`) are both `closeSplitPane` on
  Windows, so T2083 already covered them; no change.
- **Window activation** (`Window` `WM_SETFOCUS`): `caretPaneOnShow` runs
  `paneOnShow` over unchanged rows, so a remembered focused pane that is a
  strip gives the caret to the pane on show nearest it.
- **Stale focus** (Mac: "a stale focused terminal is not read as focused";
  `holdsKeyboardFocus`): on Windows the analog is a deferred/posted focus
  landing on a pane after it folded. `Window.adoptsFocus` - called from the
  terminal's `WM_SETFOCUS` (App.zig) and a viewer's `becomeActivePane` -
  refuses a strip that is not the tab's focused pane and hands focus back.
  Every deliberate focus path (strip click, goto_split, sidebar, IPC) sets
  `tab_active_pane` before focusing, so it is never refused.
- **Drops**: Windows' drop slots (`Window` pane-slot enumeration) are rebuilt
  from the live grid and skip only panes tucked NOW, so a former strip is a
  drop target again once on show by construction. A strip is not a swap
  target at all on Windows yet, so "a pane dropped on a strip stays minimized
  there" has no path to apply to; it belongs with the strip drop targets of
  T2128 (noted there).
