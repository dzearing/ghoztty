# T1688 - A window opened while the app is still finding the session manager silently opens without persistence

## Summary

A window created while the app is still resolving its connection to the local
session manager opens as a plain local shell instead of an agent-backed one.
Nothing tells the user, nothing retries, and the window is simply not persisted:
it will not come back after a quit, a crash or an upgrade, and `+list --json`
reports `session_id: null` for its pane forever.

## In plain terms

The terminal keeps your shells alive across restarts by handing them to a
background session manager. Finding that manager takes a moment at startup. A
window opened during that moment misses it - and then never asks again. The
window looks completely normal; the only sign is that it vanishes for good the
next time the app restarts, which is the moment the user was relying on it not
to.

## Evidence

Found on 2026-09-20 while re-running `test/win32/restore-session-dup.ps1`
(T1684): roughly two runs in five, the window the script creates immediately
after launch comes up with `session_id: null` while the launch window has one.
The run log shows the two panes side by side:

```
panes: dupsessA=<none>, window-1=54a7279c15bf931662aa8b424c535395
```

`LocalAgent.sharedConnection` (`src/apprt/win32/LocalAgent.zig:439`) answers
`null` outright when `self.resolving` is set, so `createEmptyWindow`
(`src/apprt/win32/App.zig`) leaves `local_agent_conn` null and every surface in
the window opens as a local ConPTY. The re-entrancy guard itself is correct and
deliberate (T188: `findOrSpawn` pumps IPC while it waits, so an IPC
`+new-window` lands one frame deep inside the resolve and re-entering would
spawn a second agent). What is missing is the other half - the window that got
the truthful "none" is never revisited once the resolve finishes.

## Goals

- [x] A window opened during the resolve still ends up persisted
- [x] Or, if it cannot be, the user is told rather than silently losing the
      window at the next restart - moot for the race: the window now waits for
      the resolve and gets the agent. A resolve that genuinely FAILS (and the
      15s cooldown after it) is a different state, filed as T1693.
- [x] The race is reproducible in a test rather than by running an acceptance
      script five times

## Where

- `src/apprt/win32/LocalAgent.zig` - `sharedConnection`, the `resolving` guard
  and `last_failure_ms` cooldown, both of which answer none without a follow-up
- `src/apprt/win32/App.zig` - `createEmptyWindow`, where a null connection
  quietly becomes a local-only window

## Fix

The nested IPC pump (`App.pumpIpc`, the T188 hook the resolve calls while it
waits) no longer serves a `+new-window` while `LocalAgent.resolving` is set. It
takes the request off the queue, finishes the drain, and posts it back, so the
main loop serves it the moment the resolve returns and `sharedConnection` has a
warm connection to hand it. Every other verb is still answered mid-resolve, so
T188's "startup answers `+list`" is untouched. The rule is pure and unit-tested
in both lanes (`src/apprt/win32/resolve_defer.zig`): `new-window` is the only
IPC verb that resolves the agent - `+split` and new tabs inherit
`Window.local_agent_conn`, `+new-remote-window` dials another machine.

Two debug-only hooks make the race deterministic: `GHOZTTY_AGENT_RESOLVE_DELAY_MS`
holds every resolve open (pumped, exactly like the real spawn poll), and
`GHOZTTY_IPC_NO_RESOLVE_DEFER=1` turns the fix off for the negative control.

      pane edits are never held, an unreadable body is served not parked) -
