# T2231 - The win32 test lane's ViewerPane 'host floor: a real controller on a real window' test crashed the test binary (exit 255) inside test-reach-audit while the daily harness sweep ran beside it; green alone minutes later

## Summary

2026-10-24 06:2x, during T2227: test-reach-audit.ps1 B1/D1 red because zig build test (win32) died in 'apprt.win32.ViewerPane.test.host floor: a real controller on a real window, on this box' with exit code 255 (a crash, not an assertion). WebView2 environment creation had failed twice just before it (hr=0x80004005, then hr=0). The floor lane's win32 run passed 15 min earlier, and test-reach-audit alone passed straight after. The difference was floor-lane -Lane harness -HarnessFull running at the same time. Log kept at %TEMP%\t2227-hostfloor-crash-lane.log. Find why a failed WebView2 environment turns into a process crash rather than a skip or a clean failure: a test that kills the whole binary takes 6900 other tests' verdicts down with it.

**What it actually was (2026-10-29).** The exit-255 crash above happened once
(10-24, right after the test's TOC click) and appears in none of the ~900 win32
lane logs since; it is split out as T2453. Every red after it, including the
"reproduces alone" runs on 10-27 and 10-28, was a different failure in the same
test: the Copy-button oracle (`copy[md]: clipboard=null`, then
`expect(copied != null)`). It fell in one unbroken window, 2026-10-27 08:41 to
2026-10-28 06:55 (47 red win32 lanes on 10-27, then 0 on 10-28 after 06:55),
and in 70 of the 71 red runs `clipboard_open`'s "open then close leaves the
clipboard takeable again" failed too. It never failed in a run where the copy
passed. So some other process on the box held the clipboard open for about 22
hours, and both tests blamed the code.

**Fix.** `clipboard_open.holder()` says who has the clipboard open right now
(free / this process / another process by pid and exe / unknown). When another
process holds it, both tests skip that one check loudly and name the holder.
Our own process holding it, or a holder nobody can name, still fails.

## In plain terms

One of the viewer's big self-tests kept going red, and it looked like the
viewer's Copy button was broken. It wasn't. Some other program on the machine
had kept the Windows clipboard locked for almost a day, so nothing could copy.
The test now notices when another program is holding the clipboard, names it,
and skips just that check. It still fails if the copy is really broken.
