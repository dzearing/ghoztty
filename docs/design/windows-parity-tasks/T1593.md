# T1593 - A release local agent does not answer its pipe for 15-30 seconds, so a cold launch comes up with no sessions

## In plain terms

The background process that keeps your terminal sessions alive takes something
like half a minute to start answering in a shipping build, while Ghoztty itself
waits only two seconds for it. So a Ghoztty that has to start that process from
cold - the first launch after a restart, say - gives up on it and opens your
windows as plain new shells, with the work that was running in them not
reattached. A developer build starts answering in about a second, which is why
this has never shown up in testing.

## How it was measured

On 2026-09-15, in an isolated sandbox (private `LOCALAPPDATA`,
`GHOZTTY_AGENT_INSTANCE`, pipe suffix), a `zig-out-release` agent started by
hand:

| after | `ghoztty.com +sessions` |
|---|---|
| 5s | `could not connect to the local agent: HandshakeTimeout` |
| 15s | `could not connect to the local agent: ConnectionRefused` |
| 30s | `No sessions.` (it answered) |

`port.json` is published within a second in all three cases, so the agent is
running and has bound its pipe long before it will talk. A second run of the
same binary is just as slow, so this is not first-touch disk caching or a virus
scan of a new file. The debug agent under the identical harness answers inside
the app's own 2s window (`test\win32\agent-upgrade.ps1`, arms B-M).

The user-visible consequence in the app's own log:

```
warning(win32_local_agent): local agent did not become dialable within 2000ms
info(win32): session-restore: no local agent; restoring only windows that need none
```

## Where to look

- `src/apprt/win32/LocalAgent.zig` - `findOrSpawn`, `spawn_deadline_ms`.
- `src/remote/agent/main.zig` - `runListenPipe` and everything between binding
  the pipe (which is early - `port.json` proves it) and serving the first HELLO.
  The suspicion is a blocking startup step on that path that a Debug build skips
  or completes quickly; a fixed ~15-30s smells like a network or service
  timeout rather than compute.
- `test\win32\agent-upgrade.ps1` `Start-LineageAgent` works around this
  deliberately (it waits for the agent to actually answer) and names this task;
  that workaround should come out when this is fixed.

## Validation criteria

- [x] The measurement above is reproduced and the blocking step named, not
      guessed - a stack or a log line, on the box. (cdb on the live agent, 4s
      in: `runListenPipe -> holder_adopt.run -> reapOrphans -> shutdownOrphan ->
      pipe_stream.dialHandle -> KERNELBASE!WaitNamedPipeW`, main thread, before
      the accept loop and before the banner.)
- [x] A ReleaseFast agent answers `+sessions` within the app's own spawn
      deadline, measured the same way (the table above, re-run): **0.03s**,
      against 27.4s for the same binary minutes earlier - and 27.4s again for
      the pre-fix binary kept beside it as the positive control.
- [x] A cold release launch that must spawn its own agent restores its sessions:
      no `did not become dialable` line, no `session-restore: no local agent`.
      It logged `shared local-agent connection ready (agent pid 59444)` and came
      up with a live session on a pty holder.
- [x] An acceptance script measures time-to-first-answer for a release agent, so
      a regression of this cannot be silent again:
      `test\win32\agent-first-answer.ps1`. It manufactures the condition rather
      than waiting for it (six busy holder pipes in the agent's namespace) so it
      measures in any build mode, and it reads the threshold out of
      `LocalAgent.zig` rather than copying it. 68ms on the fixed agent, 10364ms
      on a deliberately un-fixed one.

## Summary

Measured under T772 on 2026-09-15. A ReleaseFast ghoztty-agent started in an isolated sandbox publishes port.json within a second but refuses/times out the HELLO handshake for 15-30s (5s: HandshakeTimeout, 15s: ConnectionRefused, 30s: answers). A debug agent answers in about a second. The app's find-or-spawn gives up after spawn_deadline_ms = 2000ms, so a launch that has to spawn its own agent logs 'local agent did not become dialable within 2000ms' and then 'session-restore: no local agent; restoring only windows that need none' - i.e. the user's panes come back as fresh shells. Warm restarts of the same binary are just as slow, so it is not first-touch caching.

## Progress log

- 2026-09-15 14:01: claimed; work starting.
- 2026-09-15 14:09: root cause NAMED with a live stack (cdb, release agent, 4s in): main thread is runListenPipe -> holder_adopt.run -> reapOrphans -> shutdownOrphan -> pipe_stream.dialHandle -> KERNELBASE!WaitNamedPipeW, BEFORE the accept loop and before the 'listening on pipe' banner. dialHandle retries PIPE_BUSY 10 times x WaitNamedPipeW(1000ms) = up to 10s PER probed pipe, serially, on the startup path - which is exactly the 10/20/30s quantization measured. Two contributing defects: (1) shutdownOrphan's own doc comment promises 'an unserved connection must cost the agent two seconds and a skipped reap, never a wedge before it listens' - only the HELLO wait was bounded, the dial was not; (2) the holder pipe namespace 'ghoztty-pty-host[-debug]-<USER>-<sid>' carries NO lineage suffix, so a release agent in an 'isolated' sandbox enumerates the box's REAL live release holders, finds none of them claimed by its empty roster, and probes every one of them as an orphan. Debug is fast only because no debug-lineage holders are lying around.
- 2026-09-15 14:26: fix landed: pipe_stream gains dialHandleWithin(alloc, name, busy_budget_ms) (dialHandle = the same call at the 10s default_busy_budget_ms), holder_adopt's shutdownOrphan dials at orphan_busy_budget_ms = 0 (a busy pipe HAS an owner, so it is by definition not an orphan), and reapOrphans now carries a 2s sweep_budget_ms ceiling so a crowd of connectable-but-silent pipes cannot add up to a wedge before the accept loop. Measured on the same box, same harness, minutes apart: pre-fix ReleaseFast agent 27.4s to first answer, post-fix 0.03s. New acceptance test\win32\agent-first-answer.ps1 manufactures six busy holder pipes in the agent's namespace and times +sessions against the app's own spawn_deadline_ms read out of LocalAgent.zig; it measures 68ms on the fixed debug agent and 10364ms on a deliberately un-fixed one, so it has teeth. Two unit tests in pipe_stream.zig pin the budget's wall clock at 0ms and at 300ms.
- 2026-09-15 14:30: validation criterion 3 confirmed on the box: a COLD release launch (isolated LOCALAPPDATA + GHOZTTY_PIPE_SUFFIX + GHOZTTY_AGENT_INSTANCE, no agent of that lineage running) spawned its own fixed ReleaseFast agent and logged 'shared local-agent connection ready (agent pid 59444)' - no 'did not become dialable', no 'session-restore: no local agent'. It came up with 1 live session and a pty holder. Also updated agent-upgrade.ps1's Start-LineageAgent preamble: the pre-start stays (an upgrade arm needs a SPECIFIC build already serving) but it is no longer described as a workaround for the stall.
