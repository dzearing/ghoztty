# T1920 - tab-tooltip.ps1 reports a hover that missed the tab as 'no debug oracle (release build?)' and SKIPs, so a broken probe passes; detect the build mode directly and fail a debug build that logs nothing

## Summary

`test\win32\tab-tooltip.ps1` decided whether the build could speak by whether
its first hover produced an oracle line. A hover that missed the tab (T1900:
the pane sidebar shifted the strip right and the probe hit the sidebar card)
logs nothing either, so it read as "release build?", printed SKIP, and the run
passed with every tooltip text arm unrun.

Fix: the harness keeps the build mode `Assert-GhozttyIsolatedBuild` reads from
the exe's own `+version` and keys the skip on it. Only a non-Debug build
(log.debug compiled out) may skip; a Debug build whose probe logs nothing is a
FAIL that prints the point it aimed at and the chrome metrics it came from.
`-NegativeControl` aims the hover 200px below the strip on purpose, never
stamps, and must go red.

Re-verified before building: the two commits since filing (T1511, T2005) did
not touch the skip decision, so the defect still stood.

Same pattern in tab-strip / pane-banner / resize-flicker: filed as T3593.

## In plain terms

One of the automatic checks for the tab hover tooltip could quietly give up
and still report success when it pointed the mouse at the wrong spot. It now
knows which kind of build it is testing, so a missed hover is reported as a
failure instead of being excused.

## Goals

- [x] the skip is keyed on the exe's build mode, not on an empty log
- [x] a Debug build whose probe logs nothing fails, naming where it aimed
