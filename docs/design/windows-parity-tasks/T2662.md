# T2662 - After a reboot the loop supervisor starts the user's Ghoztty with the loop script as its default command, so every pane the user opens starts a go-loop

## In plain terms

After the PC restarted, the background helper that keeps the work loop alive
found no Ghoztty running and opened one for you - but it opened it in a way
that made every new pane you opened start the work loop instead of your
normal shell. Now the helper still opens the loop in its own first window,
and every other pane you open is your usual shell again.

## Goals

- [x] the watchdog's app-gone launch runs the loop shim in the first surface only
- [x] the user's later panes, tabs and windows get their own default shell
- [x] a guard assertion that fails if `--command=` ever returns to the launch line

## Summary

**Defect.** `scripts\go-loop-watchdog.ps1`'s app-gone branch (T849) launched the
GUI as `ghoztty.exe --working-directory=<repo> --command=<shim>`. At launch those
are CONFIG keys, not `+new-window` flags, and `command` is the default for every
surface the app ever creates (`src/config/Config.zig`, the `command` doc). The
app it starts is the user's own terminal, so after the 06:43 reboot on
2026-11-03 every pane the user opened ran `ghoztty-go-loop-resume-b.cmd`, and two
of them took lane b's lock at 06:48.

**Fix.** The launch now passes `--initial-command=<shim>`. `initial-command`
applies to the first surface only (core `Surface.init` hands it to
`app.first`), and since T406 win32 `App.run` opens that window BEFORE session
restore, so the shim gets its own window and restored/new panes get the user's
shell. The config key, not `-e`, on purpose: `-e` also forces
`quit-after-last-window-closed=true`, which would make the user's terminal quit
when the loop window closed. When an instance is already up, T487's hand-off
forwards `initial-command` as that one new window's `--command`, so the race
case is per-window as well.

Only that one launch site was affected: every other resume path
(`upgrade-ghoztty-windows.ps1`, `watchdog-ghoztty-windows.ps1`, the
watchdog's own `new-window` branch) goes through `+new-window --command=`,
which is per-window by design. The affected instance (pid 25012) is no longer
running, so nothing on the box still carries the shim as its default.

## Validation criteria

- [x] The app-gone launch line carries `--initial-command=<shim>` - H19 of
  `test\win32\go-loop-guard.ps1` (stand-in exe records its argv; PASS).
- [x] It never carries `--command=` - H20 of the same harness (PASS). Against the
  pre-fix line (`--command=<shim>`) both H19 and H20 evaluate false by
  construction.
- [x] `go-loop-guard.ps1` whole: ALL PASS (513 assertions) via
  `acceptance-parallel.ps1 run -FailFast`, 2026-11-03.
- [x] Harness floor (scoped): PASS, stamped. No Zig source changed, so the zig
  lanes were not re-run.
