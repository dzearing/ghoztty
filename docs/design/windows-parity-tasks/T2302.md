# T2302 - Windows pane sidebar has no list order of its own: port Mac PaneSidebarOrder (arranged/moving/shift), keep a per-tab order the roster is drawn in, and persist it by pane id (manifest + Mac blob paneSidebarOrder) - T2275 part 1

## Summary

Mac e77422577 PaneSidebarOrder: the sidebar list has its own order; the grid never changes; a pane the order has never seen goes after its nearest known tree neighbour, else before the next, else at the end; stashed panes keep their place; closed panes pruned on the next move; empty order = tree order; persisted by stable pane id (session manifest paneSidebarOrder). Windows: per-tab (a Mac window is a Windows tab).

**Design call (mechanism, no experience difference):** ONE order per Windows WINDOW, not per tab. Pane ids are unique across tabs, so a single list serves every tab (each tab's roster reads only its own panes from it) and the per-tab parallel arrays that every tab insert/close/move/drag-out would have to shuffle are avoided. Consequence: a tab dragged to another window arrives in tree order there (its ids are unknown), which matches Mac, where a pane joining from another window goes beside its tree neighbour.

## In plain terms

The pane list in the sidebar always mirrored the grid's order, so there was nothing to keep when you rearranged the list. This gives the list a memory of its own order, which survives a restart. Nothing visible changes yet: dragging rows to reorder (T2303) and the sliding motion (T2304) build on it.
