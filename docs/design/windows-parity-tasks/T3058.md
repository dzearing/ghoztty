# T3058 - PA-C01: with NumLock or CapsLock on, every mouse move and keystroke over a pane forces a full screen rebuild (Surface.modsChanged)

## Summary

PA-C01 (audit-1, T2964). src/Surface.zig:2316-2321 `modsChanged` compares the stored mouse mods against the RAW mods but stores `mods.binding()`, which strips caps/num lock and sides; src/apprt/win32/Surface.zig:7165-7170 sets `caps_lock`/`num_lock` from GetKeyState. With NumLock on (the desktop-keyboard default) the comparison is never equal, so every WM_MOUSEMOVE (cursorPosCallback :5866) and every key press/release (:3814, which also runs getCursorPos + mouseRefreshLinks under the renderer mutex) sets `terminal.flags.dirty.clear = true` and queues a render: a full-viewport rebuild per event. Cost (estimated): 60-125 full rebuilds/s while the pointer moves over a pane, two extra per keystroke; at 2-5 ms per rebuild roughly 10-50% of a core. Fix: compare against `mods.binding()` at both sites. Risk: trivial. Shared code: Mac half T3071. Findings: docs/design/perf-audit/audit-1/C-findings.md.

## In plain terms

With NumLock (or CapsLock) switched on - which is how most desktop keyboards
start - just moving the mouse over a terminal, or typing, made the terminal
redraw its whole screen on every single event. That burned CPU for nothing.
Now it only redraws when a modifier that actually matters (Ctrl, Shift, Alt,
Win) changes.

The test asserts on the comparison, not on dirty.clear: Surface itself has no unit-test seam, and the comparison is the whole of the fix.
- [ ] NOT RUN: on the test desktop with GHOZTTY_PERF=1, a posted WM_MOUSEMOVE sweep with NumLock on. This box's NumLock and CapsLock are both OFF (`[Console]::NumberLock` False), and the win32 surface reads them with GetKeyState, which only follows the real keyboard toggle - turning NumLock on means changing the user's keyboard state on the input desktop, which go.md forbids. With NumLock off the defect does not trigger, so a sweep here would measure nothing. Filed for a box/session with NumLock on (see progress log).
- [x] link hover with ctrl still highlights/detects: test\win32\terminal-link-paths.ps1 (ctrl+right-click link detection) ALL PASS (35 assertions) on this build. Idle CPU cannot regress from this change: it only makes an inequality fire less often.
