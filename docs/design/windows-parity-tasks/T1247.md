# T1247 - A double-clicked installer that collides with another install still shows nothing of ours

## Summary

T1206 made the in-app update path say why an install failed. The raw double-clicked MSI is still Windows Installer's own UI: a transaction that cannot start shows Windows' wording, or nothing, and the user is left guessing. Making that moment ours needs a bootstrapper (or a launcher handed out by the download page) and overlaps T1203's signing work on the same first-contact moment.

## In plain terms

If you double-click the Ghoztty installer while another install is still
running on your PC, it fails and you are told nothing useful. Ghoztty's own
updater already explains this in its own dialog; the installer you download
from the website does not, because that moment belongs to Windows. The fix is
to make the website hand out a small Ghoztty setup program that runs the
installer for you and speaks up when it cannot.

## Design (2026-10-23, settled - recorded here rather than filed as a decision)

- **Why nothing inside the MSI can do it.** The product deliberately has no
  wizard (build-msi.sh, T1291 comment), and every hook it does have - the
  MaintenancePrompt DLL action, LaunchApp - is a custom action. A collision
  (Error 1500 / exit 1618) is refused at transaction START, before
  CostInitialize, so no custom action ever runs on that path. Only something
  that runs *before* msiexec can say anything.
- **So: a bootstrapper, `Ghoztty-Setup-<version>-x64.exe`.** A small zig
  win32 exe that embeds the MSI, runs it through `MsiInstallProductW` with an
  external UI record handler (so Windows' own error box never appears and the
  1500 is OURS to word), and reports through the same
  `update_apply.describeFailure` text and `ConfirmDialog.showStandalone` the
  in-app updater already uses (T1206) - one dark Ghoztty dialog, same words,
  whichever door the user came in by.
- **The MSI stays a release asset**: it is the in-app updater's payload and
  what an IT admin deploys with `msiexec`. The setup exe is the person-facing
  front door.
- **Why this is not a decision for the user** (go.md 5b experience test): the
  Mac has no counterpart failure (a DMG drag has no install transaction), so
  there is no Mac look to translate, and a setup exe in front of an MSI is the
  ordinary Windows convention (VS Code, Chrome). The only visible changes are a
  different filename on the download page and a readable message where there
  was none.
- **Platform symmetry**: no Mac task owed - the failure mode does not exist on
  the Mac's install path.
- **Signing (T1203)**: the setup exe joins the signed set through T1203's
  existing certificate hook; until a certificate exists (T1246/D87) it ships
  unsigned and says so, exactly like the MSI.

## Split

- **T2197** - the bootstrapper itself, its result mapping (unit tests) and a
  test-desktop acceptance with a Debug-only code seam and a negative control.
- **T2198** - release-windows.yml builds, signs and attaches it.
- **T2199** - the download page and release notes point people at it.
