# T2419 - Collapsing panes into blades is still visibly janky on the installed 1.49.4 even with T2415 and T2417 in it; capture a collapse on the release build frame by frame, name every inconsistent frame, and fix until none remain

## Summary

User report 2026-10-28 ~16:50: collapsing panes into blades is still "janky as hell" on the INSTALLED 1.49.4. That build contains both earlier blade fixes: T2415 (4ee3ff0da, no per-frame repaint of the folding pane, no stale flat-style pixels) and T2417 (c5b6ee6da, blades glide with the panes when the sidebar opens or closes). So neither fix removed what the user sees. Those tasks were closed against debug-build tests, not against what the user's eye reports on the release build. This task is not closed by another narrow fix and a green debug harness. (1) Reproduce on the RELEASE build (a portable 1.49.4 zip extracted to temp, never the installed copy) with a frame-by-frame capture of an ordinary blade collapse, and list every bad frame: a frame where the folding pane, its neighbours, the blade strip or the chrome sit at inconsistent positions, are unpainted or black, or jump. (2) Compare against Mac 7e2d0a9da's rules: the grid is never stepped toward a layout it has not been laid out at, strips tween rect to rect, and every surface moves in the same present. (3) Fix the causes found and re-capture with zero bad frames. If the user supplies a screen recording (see the controller note), extract its frames with ffmpeg and use them as the reference repro. Likely root (T2360): the terminal panes, blades and chrome are separate HWND/swapchain surfaces presenting on different clocks; if no in-place fix reaches zero bad frames, say so in the log and say how much T2360 must cover.

## In plain terms

When you drag the line between panes far enough that a pane folds into a
narrow blade, the picture flickers: for a frame or two at a time you see the
panes' old text left behind next to the new text, and the pink divider line
vanishes and comes back. This task is done when a frame-by-frame recording of
that motion on a published build shows every frame clean.

## Capture findings (2026-10-28, release win-v1.49.5)

Setup: portable 1.49.5 extracted to scratch, `Set-GhozttyTestIsolation
-ReleaseSandbox`, user away (idle 52 min), window made topmost without
activation, 3 panes P|s1|s2 at 1500x700 DIP on a 150% monitor, default
(flat) style, WGC monitor capture of the window rect at 120 Hz, every frame
written (1032 frames, 0 queue drops, 0 slot gaps). Root divider dragged right
past the fold point by posted mouse messages (24 steps), held, released; then
dragged back. Tools: `temp\t2419\blade-cap.ps1`, `bars.py` (accent-bar runs
per frame), `edges.py` (column edges per frame); evidence PNGs in
`temp\t2419\frames` (temp is gitignored: on this box only).

Bad-frame classes:

1. **Drag-step ghost (every pointer move, both directions).** On each move
   the pane to the right of the divider is shown at its new place while the
   strip it vacated still holds its old text, and the divider's accent bar
   and P's card edge are missing; the next present (8-17 ms later) repaints
   them. Frames 150-151, 161, ... on the fold drag (strip2.png: "M:Microsoft"
   doubled) and 563, 574, 585, ... every ~10 frames on the drag back
   (strip1.png). 157 of 756 frames in the 0.7-7.0 s window lack exactly one
   accent bar. Same class as T2418 (lane B), which found 0 such frames on a
   2-pane DEBUG build - this capture is 3 panes on RELEASE.
   Mechanism read from the code: `placePane` (Window.zig) moves pane children
   in one DeferWindowPos batch WITHOUT `SWP_NOCOPYBITS`, so Windows blits the
   old pane pixels to the new rect and leaves the vacated strip to the
   parent; `layoutSplits` paints the bands with GetDC right after
   `EndDeferWindowPos`, but the capture shows the move and that paint land in
   different DWM presents.
2. **Fold-glide doubled frames** (T2427): during s2's fold glide, alternate
   frames show the folding pane's and s1's previous text beside the new
   text (frames 231-247, strip3.png); s1's edge moves 93 px in 25 ms
   mid-glide.

Not obtained: the same capture on the debug build (its window stayed under
the user's windows despite HWND_TOPMOST; retry next time the box is idle).
If neither in-place fix reaches zero bad frames, the residue is T2360's
(one composition surface for panes + chrome).
