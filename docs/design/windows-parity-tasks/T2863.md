# T2863 - Hovering a background Ghoztty window sometimes raises it over the window just brought forward from the pane sidebar (hover must never activate)

## Summary

User report 2026-11-09 ~06:20 (installed release): clicking a window's row in the left pane sidebar brought that window to the foreground, but then merely HOVERING the previously-foreground Ghoztty window (now in the background) raised it back over the new one. A minute later it no longer reproduced; the user suspects some state. Windows convention is that hover never raises. Ruled out by reading code: focusFollowsMouse (Surface.zig:6261) gates on windowIsActive(parent) and only defers SetFocus within the active window; BannerOverlay's SetForegroundWindow is on right-click only; PaneSidebar's are on click (search/rename). Suspects: (1) a deferred WM_APP_SETFOCUS queued for the OLD window before the sidebar activation that fires on the next mouse move (shouldForwardFocus off the input desktop returns true when active==0, and SetFocus on another top-level of the same UI thread activates it); (2) the sidebar row activation path leaves GetForegroundWindow on the old window for a beat (foreground-lock refusal + fallback), so the hover guard sees the old window as active; (3) hover/mini-rail reveal of the sidebar in the background window doing an activate. Repro is state-dependent: capture ghoztty.log around a recurrence (search 'deferSetFocus', 'present', 'activate').
