# T3352 - A relay window open when Ghoztty quits does not come back at the next launch (Mac restores it from RemoteSessionManifest)

## Summary

Mac registers every relay window in RemoteSessionManifest (WP-D2) and re-attaches it on relaunch, re-pinning a caller --name via Entry.namePinned. On win32 the local layout capture skips every remote window (App.zig captureLayout: 'if (win.remote_dialed != null) continue'), so a relay window only returns through the chooser's cross-machine Resume / Restore All, which rebuild from the FAR agent's blobs and drop the window's ipc name (session_layout.adoptableName). T22a deferred this as a stretch goal and nothing tracked it. Build the Windows-native equivalent: a local record of open relay windows (base, device, session id, name, name_pinned, ipc name) re-attached at launch off the GUI thread, carrying T1736's RemoteMachine.relay.name_pinned so a pinned label survives the relaunch. Validate with a relaunch arm beside test\win32\remote-pill-relay-name.ps1.

## In plain terms

If you had a window open on another machine (through your account's relay) and
closed Ghoztty, that window was simply gone the next time you started it, even
though the shell on the other machine was still running. On a Mac it comes back.
Now it comes back on Windows too: same session, same name, same title. A window
you closed on purpose stays closed.

## Goals

- [x] remember every open relay window (where to dial, which session, its name, pin and title)
- [x] forget it when the user closes it; keep it through a quit, a crash and a sign-out
- [x] at launch, reopen each one whose session is still alive, without blocking startup
- [x] a caller's `--name` comes back as both the window's target name and the pill's pinned label

## Validation criteria

- [x] Record lifecycle (register, session capture, rename skips pins, mark-don't-drain restore, file round trip, malformed file) - unit tests in `src/apprt/win32/relay_manifest.zig`, none lane green.
- [x] A relay window open when the app goes away is re-attached at the next launch to the same far session, under its pinned name and title, and a window closed with `+close` is not - `test\win32\relay-window-relaunch.ps1` ALL PASS (23 assertions); `-NegativeControl` fails as designed.
- [x] Startup is not blocked: dialing and the liveness probe run on a worker (`RelayWindowRestore.zig`), the GUI thread only reopens.
- [x] Floor: `floor-lane.ps1 -Lane all`.

## Design notes

- Windows-native counterpart of Mac's `RemoteSessionManifest` (UserDefaults): a JSON file beside the session layout, `%LOCALAPPDATA%\ghoztty\remote-windows[-debug][-<lineage>].json`, same debug/release/lineage separation as `session-layout*.json`.
- GUI-thread-only record; the worker reports fates (`restore` / `drop` / `keep`) and never writes it.
- Fates follow Mac: no session id or far agent says `dead` -> dropped; no credential, dial failure or an unanswered probe -> kept for the next launch; alive -> reopened, the new registration superseding the old entry in one write.
- One entry per window, re-attaching its FIRST pane's session (Mac does the same); a multi-pane relay window comes back as that one pane.
- Relay windows the chooser rebuilds (`restoreWindow` with a relay transport) are recorded too, as Mac registers on its restore path.
