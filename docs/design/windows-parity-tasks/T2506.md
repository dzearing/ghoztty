# T2506 - resize-flicker.ps1's whole-window 'a presented frame woke the resize waits' is a race now that the 8 ms present lag is real (T2503): 3 of 10 runs read 0 woken over 8 passes, plain and layered alike, because the pass's own work outlasts the lag and the frame is already there when the batch wait starts

## Summary

Until T2503 the harness's `GHOZTTY_PRESENT_LAG_MS=8` ran through `Sleep`, which Windows rounds up to the ~15.6 ms timer tick, so the "8 ms" lag was really 12-27 ms and every whole-window pass's batch wait found its frame still pending. T2503 put the lag on a high-resolution timer, which made the divider drag read stale=0 woken=11 of 11 in 10 of 10 runs (and cleared T2477). It also exposed this: a whole-window pass (`Window.endFrameWaitBatch`) does enough placement and paint before its wait that, with an accurate 8 ms lag, the new-size frame is sometimes already presented when the wait begins. Then `live == 0` on the first look, the pass logs `waits=1 woken=0 timeouts=0 stale=0`, and in 3 of 10 runs (plain and layered alike) all 8 passes did this. The summed assertion cannot tell that apart from an unwired signal.

Fix direction: make the oracle say whether a wait actually BLOCKED. For example, the pass log gains `blocked=` (the batch went onto WaitForMultipleObjects at least once), and the wiring assertion becomes "of the passes that blocked, a present woke at least one, and none timed out". A run where no pass blocked is then a measured state rather than a red. The drag's section E already carries the SetEvent teeth (woken=0 with the SetEvent removed), so keep the whole-window half honest without making it flaky. Prove the teeth again with the SetEvent removed.
