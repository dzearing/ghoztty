# T1092 - The acceptance suite can only be run one script at a time, so a full sweep costs hours nobody has

## In plain terms

The automated checks that drive the real Windows app can only be run one at a
time, and there are 241 of them. Running the whole set takes hours, so in
practice nobody runs it, and broken checks sit unnoticed. If several could run
side by side the whole set would fit in a coffee break, and it would actually
get run.

## Goals

- [x] the whole-suite sweep can run several scripts at once (`suite-run.ps1 -Jobs N`)
- [x] serial stays the default and behaves exactly as before
- [x] a 4-wide run and a serial run can be compared verdict for verdict
- [x] the speed-up is measured on real scripts, not argued

## What landed (2026-10-18)

Re-verified at claim: **T1960 (6eb1e0938) had already solved the hard half**,
with a different and better shape than "The fix" below. Each worker runs from
its own mirror of the repo (junctions to the real tree, its own hard-linked
`zig-out`, its own `LOCALAPPDATA`, agent lineage and pipe suffix), so every path
a script derives from `$PSScriptRoot` names that worker's copy. No script needs
an injected exe path, so fix step 1 and its meta-check (criterion 1) are moot.
T1960 pointed that engine only at the per-turn DUE set, which left
`suite-run.ps1`, the whole-suite sweep, serial.

This task adds `suite-run.ps1 -Jobs N`. With N > 1 the selection goes to
`Invoke-AcceptanceRun` (scripts\lib\AcceptanceParallel.ps1) and the rows come
back in suite-run's own schema. The summary records `jobs`. Red rows are re-run
alone by suite-run's own confirm pass, so one code path re-runs reds. `compare`
works unchanged across widths. `-MaxTimeoutSec` now passes through to the engine
(new `-MaxTimeoutSec` on `Invoke-AcceptanceRun`). A row the engine refuses in a
foreign checkout scores `error` with lane `refused` and is never re-run. The
one trade-off is the between-script leak and modal sweeps: they run once, at
the end, and a stray dialog found there fails the run as a whole.

**Measured** (lane b, 56189ad8b + this diff, `-Set gui -Limit 12 -NoConfirm`):
`-Jobs 4` took **6m 19s** wall for 10m 03s of script time. `-Jobs 1` took
**10m 11s**. That is 1.6x on this set. The ceiling is the longest single script
(activity-monitor.ps1, 2m 57s) plus the scripts that must run alone, so a
larger set gains more. `compare` showed 11 of 12 identical. The one DIFFER was
activity-help-tooltips.ps1 (fail at 4-wide, pass serial), a load-sensitive
assertion filed as **T2074**.

## Summary (as filed, 2026-08-22)

`scripts\suite-run.ps1` (T361) is serial by design, and the design note in its
header says why: it cannot safely be otherwise today.

Every acceptance script resolves the app under test as
`<repo>\zig-out\bin\ghoztty.exe`. 91 of them compute that path internally and
ignore any `-Exe` a caller passes. `test\win32\lib\CleanSlate.ps1` then kills
the app under test by EXACT ExecutablePath, and every script clears
`%LOCALAPPDATA%\ghoztty\*` at launch. So two workers running out of one
`zig-out` do not merely share state - each one's clean slate kills the other's
app, mid-assertion, with no error either of them can attribute, and the failure
looks like a flaky product rather than a flaky harness.

Measured cost of staying serial: the first real sweep (2026-08-22) averaged
about 45 s per script over its first 15, which puts one full forward pass near
three hours, and T267's forward/forward/reverse check near nine.

## The fix

1. One place decides the exe: an injected path (env var, e.g.
   `GHOZTTY_TEST_EXE`) that `lib\CleanSlate.ps1` / `lib\BuildMode.ps1` resolve
   once, with the `zig-out` default as the fallback. Convert the 91 scripts that
   compute the path inline onto it; add a meta-check in the style of
   `test\win32\isolation-meta.ps1` so a new script cannot go back to a literal.
2. Per-worker sandbox: a copy of `zig-out\bin` per worker plus a throwaway
   `LOCALAPPDATA`. The pipe endpoint is already run-unique
   (`Set-GhozttyTestIsolation` embeds `$PID`), so that half is done.
3. `-Jobs N` in `scripts\suite-run.ps1`, with the serial path kept as the
   default until the meta-check proves every script honors the injection.
