# T729 - Cover the viewer nav hover reveal and the TOC accent pill on the test desktop (both became reachable in T215)

## In plain terms

When you open a document in a viewer pane, the contents card beside it
highlights the section you are on. That highlight is meant to be a coloured
pill while you are working in that window and a quiet grey one the moment you
click over to another window -- the same way the Mac marks the selection in
whichever window is "key". Nothing checks the grey half, so if the card started
shouting its accent from every window in the background nobody would notice.

## Summary

**Rewritten 2026-09-14 on the CHECK FIRST re-verification** (this card was
filed 2026-08-10 and one of its two halves has since gone away).

- **The nav hover reveal half is MOOT.** T729 was filed to cover
  `ViewerPane.navHoverTick`, which T1185 deleted: there is no peek left to
  reveal, the address bar is part of every viewer pane's frame from its first
  layout, and `test\win32\viewer-nav-pin.ps1` asserts that replacement
  contract in all five pane modes. Nothing to cover.
- **The TOC accent pill half is still real, and half-covered.**
  `ViewerTOCPanel.isEmphasized()` (T215) gates the selected row between the
  accent pill and the neutral wash. `chrome-theme.ps1` section F asserts the
  EMPHASIZED arm only -- and asserts it as an accent-*cache* oracle (the pill
  follows a `WM_DWMCOLORIZATIONCOLORCHANGED`), with activation pinned on so
  that it can. No script anywhere asserts the other arm: that the pill drops to
  the unemphasized grey when activation moves to a different window. That is
  precisely the pair the T211 audit warned would be "fixed" by weakening it --
  a build that simply painted accent unconditionally scores green on every
  assertion that exists today.

So what is left is one script asserting the PAIR, on the test desktop, with a
negative control: `test\win32\viewer-toc-emphasis.ps1`.

## Validation criteria

- [x] A `test\win32\` script asserts the selected row is the ACCENT pill while
      the viewer window is the active window, by pixel probe
- [x] The same script asserts it is the DERIVED unemphasized wash -- neutral,
      not accent -- once activation moves to another window, and that the
      selection is still visibly marked rather than gone
- [x] The pair is asserted to be two different colours, so a build that
      collapsed them cannot pass one weight at a time
- [x] Re-activating the window brings the accent back (the state is live, not
      a one-time paint)
- [x] `-NegativeControl` FAILS
- [x] ALL PASS x3
