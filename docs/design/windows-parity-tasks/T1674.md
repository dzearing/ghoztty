# T1674 - The update badge can sit a day behind its own colour on a window nobody touches

## Summary

Found while landing T1673. The pending-update badge's colour is computed at
PAINT time from `now`, so it escalates whenever the chrome repaints - and the
only thing that forces a repaint on its own is `refreshUpdateAffordance`, which
runs when an offer is MADE. An automatic check that finds the same version
again returns at `decideNotify` -> `.suppress`, before `rememberUpdate`, so it
repaints nothing. A window sitting untouched can therefore hold a green dot for
up to a day after the two-day line, and an amber one for up to a day after the
seven-day line.

In practice the chrome repaints constantly (hover, focus, tab switches, the
title spinner), so this is a narrow case: a window nobody looks at is also a
window nobody is misled by. It is filed because the escalation is the part of
T1673 that makes "fourteen days behind" look different from "told yesterday",
and a ladder that can be a day stale is a ladder with a caveat.

Fix direction: have the suppressed arm of the automatic check call
`refreshUpdateAffordance` too - it already knows an offer is outstanding, and a
repaint is the cheapest possible thing to do with that knowledge. Cover it with
an assertion in `test\win32\update-check.ps1` scenario 6, which already runs the
suppressed path on a short cadence.

## In plain terms

The little update dot changes colour as you fall further behind. On a window you
have not touched at all, that colour change can arrive up to a day late. Nothing
is wrong with what it says, only with when it starts saying it.

## Goals

- [x] a suppressed automatic check still repaints the chrome carrying the badge
- [x] a test that would fail if it stopped doing so

## Validation criteria

- [x] the escalation reaches an idle window within one check cadence, demonstrated rather than asserted — `test\win32\update-check.ps1` scenario 14 seeds an offer 9 s short of the two-day line, launches with a 3 s re-check and no input, and reads `update badge painted stale` out of the paint path after the suppressed re-check's refresh. Negative control: the same harness against a build with the refresh disabled (`zig-out-neg1674`) goes 2 FAIL, and that window only ever painted `available`.
- [x] `test\win32\update-check.ps1` stays ALL PASS — 59 assertions, stamped.

## Evidence

Scenario 14 was added as its own scenario rather than folded into 6: scenario 6
publishes a new version mid-run, which would re-offer and repaint through
`rememberUpdate` and hide exactly the path this task is about.
