# T1491 - The persistence sweep's own assertion has gone red and nothing noticed

## In plain terms

There is a check that every Windows test says up front whether it wants the app
to restore its old windows on launch. When a test forgets, it can quietly test
somebody else's leftover layout and fail for a reason that has nothing to do
with the change being tested. That check is currently failing on 52 launches,
and it has been failing long enough that nobody knows when it started — nothing
runs it, so nothing reported it.

## Summary

`test\win32\persistence-flag.ps1` section A asserts that every launch of the app
under test in `test\win32` declares its session-persistence intent (T158). On a
pristine `HEAD` checkout of the suite, swept with `HEAD`'s own
`lib\PersistenceSweep.ps1`, that assertion finds **61 undeclared launches** — so
section A is red and has been for some time.

Found while measuring the launch inventory for T689, which added a second field
to the same sweep. T689's own changes took the number to **52**: it removed 15
phantom rows (a launch spelled inside a quoted string, or named in a `<# #>`
block comment, is no longer scored as a launch) and added none, which is the
only reason the number moved.

Worst-affected files at the time of writing: `startup-failure.ps1` (7),
`gui-postmortem.ps1` (4), `install-restart.ps1` (4), `session-layout-preserve.ps1`
(3), `suite-run.ps1` (3), `launch-preflight-audit.ps1` (3).

Two questions to answer before fixing, in this order:

1. **Did the SCRIPTS decay, or did the SWEEP?** Some of these are certainly real
   (a new script's launch that nobody declared). Some may be analyzer blind
   spots of the same family T689 fixed — a launch built through a shape
   `Test-VarDeclaresPattern` cannot follow. Score each one before editing it;
   declaring a site that was already declared teaches the suite nothing.
2. **Why did nothing report it?** `persistence-flag.ps1` has no row in
   `scripts\guard-due.ps1`, so no turn was ever told it was stale — which is the
   same gap T783 closed for other harnesses and the reason this could sit red.
   The fix is not complete until the harness has a coverage row, because
   otherwise it can go red again the same silent way.

## Details

Reproduce without a build (the sweep is static, about a second):

```powershell
. test\win32\lib\PersistenceSweep.ps1
$s = @(Get-GhozttyLaunchSites -Root test\win32)
@($s | Where-Object { -not $_.Declared }).Count
$s | Where-Object { -not $_.Declared } | Group-Object File | Sort-Object Count -Descending
```

Note that section A also has to be run end-to-end at least once, because its
sections B (teeth) and C (the live control that the flag really stops a restore)
have not been exercised either; a red A means the whole script exits 1 and B/C's
results have not been read by anybody in the meantime.

## Validation criteria

- [ ] Every launch site in `test\win32` declares its persistence intent — the
      sweep reports zero undeclared.
- [ ] Each fix names which of the two causes it was (an undeclared script, or an
      analyzer blind spot), so the 52 are not papered over with markers.
- [ ] `test\win32\persistence-flag.ps1` is ALL PASS on the box, sections B and C
      included.
- [ ] `scripts\guard-due.ps1` carries a coverage row for it, so a future launch
      added without a declaration is reported at the next turn's claim rather
      than discovered a year later.
