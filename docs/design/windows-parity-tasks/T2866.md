# T2866 - Moving a viewer pane's window during a fold glide costs 9.7-12.6 ms once or twice a run (every terminal pane move stays under 2-5 ms): the one pane move left over a 120 Hz period

## Summary

T2845's per-pane move stamp (GHOZTTY_PANE_MOVE_TRACE=1, release, 120 Hz, the T2732 probe) found exactly one move over 8 ms per run with a viewer in the row, and it was the viewer's window both times (9.7 and 12.6 ms, nothing on any terminal renderer in flight). The no-viewer row had none (max 2.0 ms over 6617 moves). Suspect: the viewer window hosts a WebView2 child owned by another process, so moving it waits on cross-process window-position messages. Next: time the viewer's own WM_WINDOWPOSCHANGED / bounds sync inside the move, and try moving the WebView2 controller's bounds rather than its host HWND during a glide.

## In plain terms

When panes fold and slide sideways, a web/markdown viewer pane sliding with
them now and then holds up a frame for 10-13 ms - longer than one refresh on a
120 Hz screen - so the slide visibly hitches once or twice. Terminal panes
never do. After this, the viewer slides as cheaply as a terminal and the hitch
it caused is gone.

## Goals

- [x] name what the viewer's slow move actually is (the OS, its bounds sync, or its WebView2 position refresh): its bounds sync
- [x] ~~stop paying that cost on every glide frame~~ - the cost is the bounds sync, which T2838 owns; the position refresh it was suspected of is ~2 us a tick (tried deferring it, measured, reverted)

## Outcome

The suspect was wrong. The viewer's slow move is not the OS moving a window
that hosts another process's child: that part is 0.8-1.1 ms. It is the
viewer's own `WM_SIZE` - the WebView2 bounds sync - which nothing holds during
a live batch, so it ran inside the move and T2845's trace counted it as OS
time. The trace now splits it out (`viewer_size_us` / `viewer_move_us`, per
slow move and glide-wide), and the remaining cost is T2838's, raised to P1.
T2838 landed on lane a while this was closing (c5a548a40): a viewer's sync
inside a live batch is now held and run after the terminals' resize work, so
the trace times only an unheld sync inside the move (rebase-merged in
`ViewerPane.wndProc`). Re-probing the glide with the hold in place is T2922's.
