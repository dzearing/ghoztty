# T1767 - The OpenGL loader's path log line can overrun its buffer on a long non-ASCII install path

## Summary

src/renderer/gl_loader.zig logPath converts up to max_path (1024) UTF-16 units into a 1024-byte buffer with the unbounded std.unicode.utf16LeToUtf8; an install path over ~341 three-byte characters panics at startup. It is a log line, so truncate via utf16_text.toUtf8Truncating (or size the buffer 3x). Found by T991's sweep; outside src/apprt/win32 and src/remote/agent, which T990/T991 covered.

## In plain terms

When Ghoztty falls back to its bundled OpenGL, it writes the install folder's
path into its log. If that folder's path was long and written in, say,
Chinese or Japanese characters, the conversion wrote past the end of its
scratch space and the app crashed on startup. Now the log line always fits.

## Goals

- [x] the log conversion can hold a full-length path in any script
- [x] anything longer is cut cleanly instead of overrunning
- [x] covered by unit tests in both zig lanes

## Validation criteria

- [x] a 1023-unit path of three-byte characters converts whole into the new buffer - `pathForLog` unit test, `zig test src/renderer/gl_loader.zig` 12/12 and `floor-lane.ps1 -Lane all`
- [x] a 400-unit three-byte path into the OLD 1024-byte buffer is cut to 1023 bytes of valid UTF-8, never overruns - same tests
- [x] a cut that splits a surrogate pair drops the dangling half - same tests
- [x] ASCII is unchanged and malformed UTF-16 still logs without the path - same tests
