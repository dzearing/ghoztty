# T1481 - fork-ci windows-cross fails installing msitools, so every push reads red

## In plain terms

The build machine cannot finish a Windows build any more: it dies while
installing the tool that packages the installer, before it ever compiles
anything. Nothing is wrong with the code, but every push now reports a failure,
which means the one signal that says "the branch builds" says nothing at all.

## Goals

- [x] fork-ci's windows-cross job goes green again
- [x] The packaging step cannot take the whole job down with it when its
      dependency source moves

## Summary

`Fork CI` run 34384937910 (commit `886dc6f1e`, 2026-09-09) failed in
**windows-cross**, at the step **"Build and install msitools 0.106 (wixl,
msiinfo, msibuild)"**, with `Process completed with exit code 100` — the apt
exit code, i.e. the package fetch/build failed on the runner. The compile step
after it ("Build Windows release artifacts") never ran, and `release-parity`
passed, so **no Zig code is implicated**: the job dies before it builds.

This matters beyond one red run. `parity-tasks.ps1 validate` FAILS on a red CI
verdict (T1219) and `go-loop-exec.ps1 claim` reports it, so as long as this step
is broken every turn's close has to reach for `-NoCiCheck` — which is exactly
the hatch that is supposed to be rare and explainable. A permanently-excused
gate is not a gate.

Two things to decide while fixing it: whether msitools should be pinned/cached
(or fetched from a prebuilt artifact) rather than built from source on every
run, and whether the packaging step belongs in the same job as the cross
compile at all — the compile is the signal the loop actually gates on, and it
is currently hostage to a packaging dependency.

## Details

**Root cause.** `install-msitools.sh` opened with a bare `sudo apt-get
update`. That command exits **100** when *any* configured apt index fails to
download — including indexes for repositories we never install a byte from.
The ubuntu-latest runner image ships several such third-party sources, and on
2026-09-09 `dl.google.com/linux/chrome-stable` served a `Packages.gz` whose
hash did not match its own `Release` file. apt exited 100, `set -euo pipefail`
ended the script, and the job died having compiled nothing. Neither the tree
nor msitools nor gitlab was implicated; an unrelated vendor's mirror decided
whether this branch had a build signal.

**Fix, part 1 — the install stops being decided by repos we do not use.**
Before the update, every source list in `/etc/apt/sources.list.d/` except
ubuntu's own is moved to `/tmp/apt-sources-disabled/` (guarded on
`ubuntu.sources` existing, so a future image layout cannot leave apt with no
sources at all). The update itself is retried three times and is **no longer
the gate**: a stubborn failure emits a warning and continues, because
refreshing an index is not what we need — installing the packages is, and the
`apt-get install` below fails loudly and specifically when an index we
actually depend on never arrived.

**Fix, part 2 — the compile verdict stops being hostage to packaging.**
`build-release-artifacts.sh` gains `--build-only`, the mirror image of the
existing `--skip-build`: cross-compile the exe, assert its embedded version
string, stop. fork-ci's `windows-cross` now runs that FIRST, installs msitools
second, and packages third with `--skip-build` over the same `zig-out`. The
build flags still live in exactly one place — this is two invocations of the
same script, not a zig command line pasted into the workflow — and a broken
packaging toolchain now fails a step that has already answered "does the
branch build for Windows?". The two flags are rejected together.

`release-windows.yml` picks up part 1 for free (one shared install script)
and keeps its single packaging step, which is what it is there to do.
