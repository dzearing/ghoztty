# T2627 - T2574 on-screen oracle: film the compositor glow fade (WGC grab of the faded-in glow vs the GDI arm at rest, and the fade still advancing through a 500ms UI stall) on an idle box

## Summary

T2574 landed the focus glow as compositor layers with unit-test pixel equivalence (PaneDesk 'T2574: the glow layer faded to L ...') and off-desktop log proof (test\win32\focus-glow-comp.ps1: fade declared once, 0 desk uploads per fade). Not run: the on-screen half, which needs the input desktop and was NOT RUN because the user was present (a fullscreen app). Build it in the comp-desk-onscreen.ps1 shape: ghost window, split, glow on the focused card; grab the faded-in glow with GHOZTTY_COMP_CHROME=1 and with GHOZTTY_DEBUG_GLOW_STEPPED=1, match within rounding; then add a debug stall seam (like GHOZTTY_DEBUG_BELL_FADE_STALL_MS) at fade start and show the glow's level reaches >= 0.98 through a 500 ms UI stall on the compositor arm and freezes on the stepped arm (negative control).

## In plain terms

When you move between split panes, the lit border around the active pane fades across. An earlier change handed that fade to Windows' compositor so it stays smooth even while the app is busy, but nobody had actually filmed it on a real screen. This films it, and shows it stays smooth through a half-second freeze where the old way stuttered and then jumped. It also fixes a small bug found along the way: focusing a pane from the command line or a link in a window that is not in front left the glow on the old pane.

## Goals
