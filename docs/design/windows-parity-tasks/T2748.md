# T2748 - Default composition path: bell-border.ps1 (6), close-overlays.ps1 (2), split-dim.ps1 (4) and split-dim-viewer.ps1 (4) go red (with GHOZTTY_COMP_PRESENT defaulted on (T2514 run 2026-11-06, debug build) and green with =0 on the same build) - the bell border and unfocused dim are child visuals there, not popups; classify test-assumes-popup vs real defect and fix

## In plain terms

Terminal panes are about to switch to a newer way of drawing by default. Four
automated checks - the bell flash around a pane, the dimming of panes you are
not typing in, and overlays disappearing when a pane closes - failed when that
switch was turned on. This works out whether the app or the checks were wrong,
and makes the checks cover both ways of drawing.

## Goals

- [x] every red classified: all 16 are the test looking for a popup window that the new path draws as part of the pane instead - no app defect
- [x] the four harnesses keep testing the old (popup) path explicitly, since viewers, banner panes, the opt-out and machines without the graphics interop still use it
- [x] each harness also tests the new path for the behaviors only it covered
- [x] the four stay green with the default actually flipped

## Summary

**Classification: test-assumes-popup, all 16 reds; no defect on the
composition path.** With the pane presenting through its composition swap
chain, the bell border (T2467), dim wash (T2491) and banner (T2559) are child
visuals of the pane's own DirectComposition target, so there is no
`GhozttyBellBorder` / `GhozttyDimOverlay` / `GhozttyBannerOverlay` window to
enumerate - which is all the reds were. comp-present.ps1 E/F/J already covered
the visuals' fade, rect and banner fallback; these four harnesses covered
behaviors it did not (which pane carries the wash after a focus flip, zoom,
viewer focus via GotFocus; which pane the bell frames; close hiding a pane's
overlays).

**Fix.**

- `DimOverlay.zig` / `BellBorder.zig`: the visual-path log lines
  (`dim overlay path|shown as visual|hidden visual=true`, `bell border shown as
  visual|hidden`) now end in `pane=<hwnd>`, so a harness can tell WHICH pane
  carries a visual. Appended at the end: every existing matcher is a prefix and
  still matches (checked: comp-present.ps1, comp-present-onscreen.ps1,
  bell-border.ps1).
- Each harness pins `GHOZTTY_COMP_PRESENT=0` on its original launches (the
  popup path keeps its coverage after the flip) and gains a `=1` section:
  - bell-border.ps1 section 5: frame up as a visual on the RIGHT pane's window
    at 3pt, no popup, compositor fade, resize+move re-show nothing, a key hides
    it on that pane.
  - split-dim.ps1 run 4: wash on the unfocused pane alone at alpha 77, no
    popup, focus flip moves it, zoom takes it down, unzoom restores it.
  - split-dim-viewer.ps1 step 6: viewer focused / goto into the viewer / click
    straight into Chromium (GotFocus) each put the wash on the terminal,
    focusing the terminal takes it down, no popup ever.
  - close-overlays.ps1 section 6: three banners as visuals, no overlay popup
    but the banner panes' dim washes (popups by design over a band,
    comp-present F4), `+close c2` hides c2's pane window (and with it its
    visuals) and its wash popup by the time +close answers, `+close cw` takes
    the window.
- Surprise found on the way: `+split --target=c2` right after c2's creation
  split cw (tree `(cw|c3)|c2`), so section 6 maps panes to names from the
  `+list` tree, never by position - filed **T2753**.
