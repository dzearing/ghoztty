# T1868 - floor-lane-stall-sampling's negative control is flaky: the pre-fix rule only goes red when the wedge tree shows nonzero CPU, and cmd+conhost+waitfor can read exactly 0

## Summary

2026-10-11 20:57 (T1840 turn): arm 11 'the pre-fix rule fails the same assertion (teeth)' FAILED; re-run seconds later ALL PASS 18. The grafted pre-fix rule reads progress as any CPU CHANGE, and a blind sample (tree empty) gives cpu=0 - so it only flaps when the non-blind tree sum is nonzero. The selftest-wedge tree (cmd.exe, conhost.exe, waitfor.exe) sometimes accounts exactly 0 ticks (CPU accounting is per-quantum), so the negative copy names the wedge correctly and the teeth check fails. Fix: make the negative's flap independent of the tree's real CPU (e.g. have the wedge fixture burn a measurable sliver of CPU before waiting, or inject a nonzero synthetic CPU through a test-only env var), then prove the teeth assertion over N runs.

## In plain terms

One of the test scripts that guards the build's hang detector has a
"prove this test can fail" step, and that step occasionally failed for no
real reason, so a test run had to be repeated. After this change that step
gives the same answer every time; nothing about the real hang detector changes.
