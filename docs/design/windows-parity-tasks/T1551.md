# T1551 - The commit guard rejects a wildcard pathspec as another session's work, after the commit has already been made

## Summary

`git-commit-guard.ps1 commit -Paths` passes its pathspecs to `git add`, which
expands a wildcard, but the read-back afterwards compares the COMMIT's file list
against the literal strings it was given. So `test/win32/*.stamp.json` stages and
commits 19 stamp files and then every one of them is reported as a path the
caller did not ask for - the T948 "another session's changes landed under this
subject" refusal - with the commit already made and unpushed. Hit on 2026-09-13
closing T711, where all 19 stamps were this turn's own green runs; the remedy was
a soft reset and a re-commit naming each file. Either expand the pathspecs the
same way `git add` does before the read-back, or refuse a wildcard up front with
that reason, so the caller learns before the commit rather than after it.

## In plain terms

When the loop commits a batch of files using a wildcard like `*.stamp.json`,
the safety check that reads the commit back does not understand the wildcard
and accuses the commit of containing somebody else's work. The commit has
already been made by then, so the turn has to undo it and redo it by hand,
listing every file. Nothing is lost, but it costs a turn a detour and it reads
like a real conflict when there is none.

After this, a wildcard either works or is refused before anything is committed.

## Validation criteria

- [ ] A commit through the guard with a wildcard pathspec whose every expansion
      is a requested file exits 0 and PUSHES - no T948 refusal.
- [ ] A commit whose read-back really does contain a path outside the (expanded)
      request is still REFUSED, so the fix does not blunt the guard.
- [ ] Both are sections of `test\win32\go-loop-guard.ps1` (section W), with the
      second one as the negative control.
