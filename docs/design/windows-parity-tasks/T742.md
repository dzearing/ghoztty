# T742 - Positioning the palette or search bar resizes the terminal grid to the popup's size

## In plain terms

Every time you open the command palette or the find bar, the terminal
underneath is told it just became the size of that little popup, and reflows to
match. The next real resize puts it back, so what you see is a flicker or a
scrambled line rather than a lasting wrong size — but the text you were reading
moved for no reason.

## Goals

- [x] Opening the palette or the search bar leaves the terminal's rows and
      cols exactly as they were.
- [x] Neither popup can resize, type into, click on or focus the terminal on
      the strength of a message it received itself.
- [x] Closing a popup does not take the pane's scrollbar down with it.
- [x] Every arm of `surfaceWndProc` either routes by role or says in a comment
      why it is right for all three windows.

## Summary

`App.surfaceWndProc` serves three windows — the terminal child HWND, the
search-bar popup and the command-palette popup — because all three store the
same `*Surface` in their `GWLP_USERDATA`. T613 fixed the `WM_DESTROY` arm of
that confusion (a popup's destroy cleared `Surface.hwnd`, which crashed the
process). The rest of the switch is still unrouted:

- `WM_SIZE` calls `surface.handleResize(w, h)` with **the popup's** dimensions.
  `positionCommandPalette` and `positionSearchBar` both call
  `MoveWindow(popup, …, 1)`, which sends `WM_SIZE` — so this fires on every
  palette open and on every window move while the search bar is up.
- `WM_ENTERSIZEMOVE`/`WM_EXITSIZEMOVE` set `surface.in_live_resize` for a popup
  the user is not resizing.
- `WM_DPICHANGED` runs `surface.handleDpiChange()` off the popup's DPI.
- The key/char arms (`WM_KEYDOWN`, `WM_CHAR`, …) route to the terminal from a
  popup window; the popups normally give keyboard focus to their child EDIT, so
  this may be unreachable in practice — establish that rather than assume it.

## Where

- `src/apprt/win32/App.zig` — `surfaceWndProc`, the `switch (msg)` arms.
- `src/apprt/win32/surface_window_role.zig` — T613's pure role classifier; the
  `role` is already computed at the top of the procedure, so each arm can
  simply ask.
- `src/apprt/win32/Surface.zig` — `positionCommandPalette` (~2367),
  `positionSearchBar` (~2120), the two `MoveWindow` calls.

## Validation criteria

- [x] Opening the palette does not resize the terminal grid: the pane's
      reported rows/cols are unchanged across a palette open/close.
- [x] Same for the search bar, including while the window is moved with the bar
      up.
- [x] Each remaining arm of `surfaceWndProc` either routes by role or carries a
      comment saying why it is correct for all three windows.
- [x] Pure assertions extend `surface_window_role.zig` where a new routing rule
      is added; `zig build test -Dapp-runtime=none` and `-Dapp-runtime=win32`
      green, plus P1-P3.

## What was found and done

`drivesTerminal(role)` in `surface_window_role.zig` is the rule, asserted in
the `none` lane, and every arm that reads or writes terminal state now asks it:
`WM_SIZE`, `WM_MOVE`, `WM_SHOWWINDOW`, `WM_ENTERSIZEMOVE`/`WM_EXITSIZEMOVE`,
all the key / char / IME arms, the mouse buttons, move, wheels, `WM_SETCURSOR`,
`WM_CONTEXTMENU`, `WM_DROPFILES`, `WM_SETFOCUS`/`WM_KILLFOCUS`. `WM_PAINT` no
longer wakes the terminal's renderer for the search popup. `WM_SETTINGCHANGE`
posts its re-flow to `surface.hwnd` BY NAME rather than to `hwnd` — the
broadcast only ever reaches the popups, because the terminal is a `WS_CHILD`.
The remaining arms (`WM_CLOSE`, `WM_DPICHANGED`, `WM_GETOBJECT`, `WM_COMMAND`,
the two `WM_CTLCOLOR*`, `WM_ACTIVATE`) carry a comment saying why they are
right for all three.

Two things the work turned up:

- **The key arms were reachable after all.** Not by typing — a popup's focus
  lives in its child EDIT — but an injected `WM_CHAR` at the palette popup
  typed straight into the terminal, which arm E of the new script measures.
- **`WM_SHOWWINDOW` was the second visible half**: showing or hiding a popup
  ran `setOwnerVisible` for the TERMINAL's scrollbar, so closing the search bar
  hid the pane's scrollbar.
- **`MoveWindow` to a size the popup already has sends no `WM_SIZE`**, so the
  palette-open reflow fires when `Surface.scale` moved between creation and
  positioning rather than on every open. The acceptance script therefore sends
  each popup the exact `WM_SIZE` `DefWindowProc` delivers for its own rect,
  which is the arm under test stated without that dependency.
- T1579 filed: the terminal child never receives `WM_DPICHANGED` or the
  `WM_SETTINGCHANGE` broadcast at all, so a monitor move refreshes its scale
  only if a popup happened to be open.

Acceptance: `test/win32/palette-grid-size.ps1` (new, agent-free). Negative
control on the pre-fix build FAILS four arms — grid 51x16 -> 51x21 for the
palette, -> 31x1 for the search bar, the scrollbar gone dark, the injected
`WM_CHAR` in the terminal — and the fixed build is 13/13.
