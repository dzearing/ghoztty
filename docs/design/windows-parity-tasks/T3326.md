# T3326 - The due sweep spends 80% of its wall clock in a serial tail of exclusive scripts, half of it re-confirming reds already acked to open tasks

## In plain terms

Checking a change before it is committed can take over half an hour, and most
of that time goes to a handful of slow tests that have to run alone. Four of
those slow tests were already known to fail for reasons someone is already
working on, so running them again told nobody anything new. Fixing that means
fixes reach the user sooner. Nothing on screen changes.

## Summary

Measured from `%TEMP%\ghoztty-acceptance-parallel\20261121-054418\summary.json`
(lane A, `acceptance-parallel.ps1 due`, commit bd69f54cb, 45 runs, wall 2024s):

- Every `parallel`-class script was done by **249s**, four at a time.
- Then the `exclusive` class ran one at a time from 249s to 1849s, which is
  **1600s, 79% of the wall clock**: drag-perf 185s, frame-clock 69s,
  pane-close-memory 274s, viewer-image 84s, agent-autostart 17s,
  agent-upgrade 242s, registration-sites 83s, harness-floor 646s.
- **drag-perf, frame-clock, pane-close-memory and viewer-image are GUARD ACKED**
  to open tasks (T1854, T2820, T2692, T3222) and all four came back red as
  expected. That is **612s spent confirming reds the tracker already owns.**
- The six-script `confirm` phase (re-running reds alone) added another 172s,
  again mostly reds already owned by open tasks (fixed-ports T3320,
  overlay-zorder T2300, close-undo/rearrange-undo T2921, test-desktop-harness
  T2884, machine-lock T2905).
- `harness-floor.ps1` alone is 646s as one exclusive row, and it is already a
  4-wide sweep inside itself (T1657).

Two levers, decide by measurement:

1. **Acked guards are not owed by the turn.** `validate` already passes on
   them. A `due` run could skip a guard that is ACKED to an open task (still
   listing it as `ACKED, not run (T<id>)`), with an opt-in to include them
   when the turn is working that task. The skip must not hide a guard that
   went GREEN: if acked rows are skipped, the owning task's turn is the one
   that re-runs them, and `guard-due.ps1` keeps naming them.
2. **The exclusive tail is ordered after the pool and is strictly serial.**
   Check which `exclusive` classifications are still required (agent-upgrade
   and registration-sites touch per-user state; is harness-floor exclusive
   only because it is heavy?) and whether the long exclusive rows can start
   while the pool's short rows are still finishing. Never overlap a
   `@timing-sensitive` script with anything (T401 stands).

Parent: T1651 (closed as superseded). It asked for one shared GUI fixture per
batch; measuring showed a GUI fixture costs about 4s (ipc-target-exists-note.ps1:
2.3s setup, 1.6s teardown, 6.0s total), so sharing it would save about 20s of
wall clock in this sweep while giving up per-script isolation.

## Validation criteria

- [ ] A `due` run over the same guard set as 20261121-054418 reports the same
      verdicts for every script it runs, and names every acked script it did
      not run with its owning task.
- [ ] Measured wall clock for that set is recorded before and after, in the
      progress log.
- [ ] A guard ACKED to the task the turn has claimed IS run (the turn working
      the red needs it), demonstrated in the runner's own acceptance.
- [ ] No `@timing-sensitive` script ever overlaps another (the schedule check
      that exits 3 stays green).
