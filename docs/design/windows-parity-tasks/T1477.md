# T1477 - Two viewer acceptance scripts run back to back have no WebView2 settle between them

## Summary

The same teardown race T592/T678 close for lanes exists in the acceptance-script sequence: each viewer-*.ps1 stands up its own debug Ghoztty browser tree and kills it at the end, and nothing makes the next script wait for that tree to go. Not observed failing yet - filed while the mechanism was measured (17 browser processes per viewer-panes.ps1 run). The wait already exists: Wait-WebViewLaneSettle -IncludeAppTeardown in scripts\lib\WebViewLane.ps1.

## In plain terms

When the automated GUI tests run one after another, each one opens a real
embedded browser and closes it at the end. Nothing makes the next test wait for
the last one's browser to actually be gone, so a test can occasionally fail for
a reason that has nothing to do with the code it is checking — the kind of red
result that teaches people to re-run instead of read.

## Goals

- [x] A viewer acceptance script waits for the previous one's browser tree
      before it stands up its own
- [x] The wait is shared, not copied into each script
- [x] Nothing waits on the user's own terminal (release profile), ever

## Validation criteria

- [x] Two viewer scripts run back to back green, repeatedly, with the wait
      visible in the second one's output when there was something to wait for
      — `acceptance-parallel.ps1 run -Width 1` viewer-find, viewer-html,
      viewer-find, viewer-html: 4 PASS (21s each, unchanged), no settle line
      (nothing to wait for — the normal case), while lane B's viewer-panes.ps1
      ran concurrently in its own worker and did NOT hold these launches.
      The "visible when there was something to wait for" half is arm 29 of the
      settle harness (a real orphan exiting 1.5s in: waited, and the line said so).
- [x] `test\win32\floor-lane-webview-settle.ps1` still ALL PASS — 62
      assertions, 13 new (arms 25-31)
- [x] The wait is bounded and SAYS so when it runs out — arm 28
      (`PROFILE NOT SETTLED ... (T1477)`, 1s deadline honoured)

## Design (2026-11-11)

Hooked into `Start-OnTestDesktop` (test\win32\lib\TestDesktop.ps1), the one
launcher every GUI script goes through, rather than into each viewer script:
before any `ghoztty.exe` GUI launch (never a `+verb` client), it runs
`Wait-WebViewProfileSettle` (scripts\lib\WebViewLane.ps1, next to the lanes'
settle). Three choices, each measured against a way the obvious version breaks:

- **Profile-exact**, `<LOCALAPPDATA>\ghoztty\EBWebView-debug`. Parallel
  acceptance workers each have their own LOCALAPPDATA, so a marker-only match
  (`Get-WebViewAppDebugHost`) would hold every launch in a 4-wide sweep at the
  gate for the full deadline over another worker's live panes.
- **Orphans only** (owning app gone, or its pid reused since). A live owner is
  a script's own first window while it opens a second, or a dev Ghoztty left
  open; WebView2 shares one browser among apps on one profile, so that is not
  the failure shape — the teardown is.
- **Debug only**: `Select-WebViewProfileOrphan` throws on a non-`-debug` root.

Cost when the profile is clear: one name-filtered CIM query per launch.
