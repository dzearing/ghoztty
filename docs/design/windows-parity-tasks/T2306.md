# T2306 - An acceptance run that ASSERTED NOTHING still stamps its guard green and clears the guard's ack: the stamp block is gated on failures -eq 0, and a Tee-Object collision on the fixed %TEMP% transcript name (ghoztty-<tag>-last.log) under parallel workers kills the body with zero scored

## Summary

Seen in the T2276 turn, 2026-10-26 05:11. In
`scripts\acceptance-parallel.ps1 run`, worker w4's `pane-sidebar-scroll.ps1`
printed:

```
  STAMPED pane-sidebar-scroll (4 files) -> test\win32\pane-sidebar-scroll.stamp.json
  ACK CLEARED pane-sidebar-scroll: a green run replaced it

T1878 ACCEPTANCE: ASSERTED NOTHING (0 assertions) - this run proved nothing; it is not a pass
```

The same script, run alone a minute later, was RED (section 4, the open
T2267). So a run that proved nothing wrote a green stamp over code that is
red, and deleted the T2267 ack along with it. The turn caught it in
`git status` and restored both from HEAD. A turn that commits stamps
wholesale would have shipped it. `pane-sidebar-actions` and
`pane-sidebar-all-windows` also stamped from ASSERTED NOTHING worker runs in
the same batch. Their re-runs alone happened to be green, so the stamps held
by luck.

**Two defects:**

1. **The stamp gate.** Each harness ends with
   `Complete-TestBody; if ($script:failures -eq 0 -and -not $NegativeControl) { guard-due.ps1 update ... }`.
   Zero assertions means zero failures, so it stamps. T1039's
   `GHOZTTY_TEST_BODY` check does not catch this: `Complete-TestBody` sits
   after the `& { } | Tee-Object` block, so it reads `complete` even when
   that block died early. Fix centrally, not in ~300 scripts. For example,
   `Complete-TestBody`/TestScore could publish the pass count (or the scorer
   could record the verdict) before the stamp block, and `guard-due.ps1
   update` would refuse while it reads zero passes (`STAMP REFUSED: the
   calling run asserted nothing`).
2. **The cause, this time.** The worker's stderr shows
   `out-file : The process cannot access the file '...\ghoztty-t1878-last.log' because it is being used by another process`
   (`Tee-Object` at `pane-sidebar-scroll.ps1:170`; `Add-Content` at
   `lib\Transcript.ps1:173`). The transcript path is a fixed name in
   `%TEMP%`, shared by every copy of the script on the box: the other
   acceptance workers' mirrors, lane B (`D:\git\ghoztty-b`), and a hand run.
   The runner flagged the other two as `PARALLEL-SENSITIVE`, which is this
   same collision, not a real ordering dependency. Make the transcript name
   unique per run (pid or worker), or have `New-TestTranscript` open it
   shared.

## In plain terms

The test runner keeps a "this test was last run green over this code" receipt
for each test. A test that crashed before checking anything still wrote that
receipt, so a broken feature could look verified. Now a run that checked
nothing is refused the receipt, and two copies of one test running at once no
longer trip over each other's log file (which was what made them check
nothing).

## Goals

- [x] a run that asserted nothing cannot stamp its guard or clear its ack
- [x] concurrent runs of one harness each get their own live transcript

## Fix

- `test\win32\lib\TestScore.ps1`: `Complete-TestBody` now also publishes
  `GHOZTTY_TEST_PASSES`, read from the harness's own `$script:passes` /
  `$script:pass` counter (the first that holds an integer; every scored
  script uses one of those two), so none of the ~340 callers needed an edit.
  `Reset-TestBody` clears it so a parent run's count is never inherited.
- `scripts\guard-due.ps1 update`: refuses (`STAMP REFUSED: the calling run
  asserted nothing`, exit 3) while that reads 0, before touching the stamp or
  the ack. Unset (a hand `update`, a script with another counter name) stamps
  as before; `-IgnoreRunState` overrides, as for the T1039 refusal.
- `test\win32\lib\Transcript.ps1`: the live transcript is
  `ghoztty-<name>-last-<pid>.log`; `New-TestTranscript` sweeps every earlier
  live file of that harness it can delete (a running copy's open file
  survives), including the pre-T2306 fixed name.
