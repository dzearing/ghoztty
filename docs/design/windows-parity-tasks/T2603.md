# T2603 - Window resize feels slower on 1.51.6 than before (user 2026-11-01): measure how fast the window edge follows the pointer (steps per second, pointer-to-edge lag) on 1.51.5 vs 1.51.6 and HEAD, and get it back at or above the old rate without losing T2578's in-sync grow - the resize harness scores frame correctness only, never responsiveness

## In plain terms

Since 1.51.6, dragging the window's edge to make it bigger is noticeably
less smooth: each step of the drag takes the app longer, so the edge keeps
up with the mouse fewer times per second. Making it smaller, and dragging
the line between two panes, cost the same as in 1.51.5 on the test bench.
When this lands, growing the window is at least as quick as before.

## Summary

MEASURED (2026-11-01, Debug, background test desktop, so no compositor
pacing; same box, back to back):

- **Divider drag: no regression.** `drag-perf.ps1 -PaneCounts 2,4`, batched
  2-pane drag: win-v1.51.5 (0fb318146, built in a worktree) 15.5 ms per move,
  HEAD 15.5 ms per move, both ~64 fps. Placement (~9.8 ms) is most of it.
- **Window-edge GROW: regressed by T2578's pre-layout.** New meter (below),
  40 right-edge steps of 10 px:

  | scene | mode | grow | shrink |
  |---|---|---|---|
  | 3 terminals | pre-layout (shipped) | 17.2 ms (58 fps) | 12.8 ms |
  | 3 terminals | `GHOZTTY_RESIZE_NOPRELAYOUT` | 14.6 ms (68 fps) | 13.1 ms |
  | terminal + viewer | pre-layout (shipped) | 16.4 ms (60 fps) | 12.3 ms |
  | terminal + viewer | `GHOZTTY_RESIZE_NOPRELAYOUT` | 12.4 ms (80 fps) | 12.6 ms |

  A growing step pays the pre-layout pass (13.2 ms, MORE than a whole plain
  pass at 11.6 ms) and then the `WM_SIZE` pass anyway (2.5-3.2 ms: it re-places
  every pane, 1.4 ms, and repaints the desk, 1.0 ms).

DONE (2026-11-01, second turn): (1) landed - `Window.finishPrelaidSize`
(rule `resize_prelayout.sizePassNeeded`): a `WM_SIZE` at exactly the rect a
pre-layout laid out only paints the desk; size pass 2.5-3.0 ms -> 1.5-1.7 ms
in every run (`GHOZTTY_RESIZE_PRELAID_FULL` restores the old pass for an A/B).
(2) traced - the pre-layout pass costs the same as a plain pass in placement
and paint; its extra is the frame WAIT, because the terminal renderer's
`draw-begin -> target-ready` is slower inside `WM_WINDOWPOSCHANGING` - filed
as T2609. Pre-layout kept ON: turning it off brings back T2578's 40 flat-
background frames per grow (the user's "blank areas"), and the trade is the
user's to make - D106. edge-drag-rate after the fix, on a loaded box (game +
stray pwsh): C row3 125/107/125%, viewer 107/132/112% (2 of 3 runs green).

ORIGINAL PLAN (kept for the record): make a growing step cost one pass, not one and a
quarter. (1) After a pre-layout at exactly the client rect that landed, the
`WM_SIZE` pass skips placement/cut/overlays (the panes are already there; the
window's origin did not move) and only paints the desk for the newly exposed
strip, which the pre-layout's paint could not reach (clipped to the old
client). (2) Find why the pre-layout pass costs ~1.6 ms more than a plain pass
(`GHOZTTY_RESIZE_TRACE` both modes and diff the stages). Then
`edge-drag-rate.ps1` must go green: grow with the pre-layout within 125% of
grow without it in BOTH scenes, keeping T2578's in-sync grow
(`scripts\resize-sync-onscreen.ps1`, on-screen; NOT RUN while the user is
present). If the pre-layout cannot be brought inside the budget, turn it off
(rate beats a one-compose sync gain the user never asked for).

The meter: under `GHOZTTY_PERF` each edge step is timed from its
`WM_WINDOWPOSCHANGING` (before the pre-layout) to the end of its `WM_SIZE`
(`Window.edgeStepBegin/End`), and `WM_EXITSIZEMOVE` prints
`window drag steps= prelayouts= mean_prelayout_us= mean_size_us= mean_us= fps=`
plus the divider drag's full cost line as `window drag ticks=...`. Harness:
`test\win32\edge-drag-rate.ps1` (guard row `edge-drag-rate`).
