# T3393 - An installed-release updater running from any folder other than the real install can run msiexec over the user's installed product

## Summary

T3388 closed the test-sandbox route with GHOZTTY_AUTO_UPDATE=off, but the app itself still applies an MSI whenever install_location reads its own folder as the installed release, and msiexec product state is per user: any copy of a release build under some LOCALAPPDATA\Programs\Ghoztty (a sandbox, a second profile path, a stale copy) installs over the real product. Decide in the app: before arming the applier, compare the folder the MSI's product is registered at (MsiGetProductInfo InstallLocation for the UpgradeCode's product) with this exe's own folder, and refuse with a logged reason when they differ. Unit-test the comparison; acceptance: a sandboxed release copy with a staged package logs the refusal and runs no msiexec.

## In plain terms

Windows installs an update into wherever Ghoztty is *registered* as installed,
not into the copy that downloaded it. So a copy of Ghoztty running from some
other folder (a test sandbox, a portable unpack) could install an update over
the user's real Ghoztty. Now a copy that is not the installed one refuses to
start the installer and says so in its own window, pointing at the releases
page instead.

## Goals

- [x] Before the installer is started, the app reads the update package's identity and asks Windows Installer where that product's ghoztty.exe is registered
- [x] The install goes ahead only when that is the running exe's own folder; anything else (registered elsewhere, not installed, unreadable package, lookup failure) is refused with a logged reason
- [x] The refusal reaches the user as the existing "could not start the update" dialog, worded to send them to the releases page rather than to retry
- [x] Unit tests for the decision, and an acceptance script that drives the real click in a sandbox copy against the user's real registration

## Validation criteria

- [x] Pure decision unit-tested (`src/apprt/win32/update_target.zig`: same folder / elsewhere / not installed / unresolved / one-of-many / sibling prefix / short|long FileName / seam enforcement / log line) plus the dialog wording test in `update_apply.zig` - floor lanes
- [x] A sandboxed copy with a staged release-identity package logs `update apply: REFUSED - the package's product is registered at C:\Users\David\AppData\Local\Programs\Ghoztty, not at this copy`, shows the refusal dialog, arms nothing and never invokes msiexec - `test\win32\update-target-guard.ps1` ALL PASS (25 assertions)
- [x] The harness can fail: `-NegativeControl` (guard advisory) goes red with 9 failures
- [x] The user's installed product is untouched after both runs (ProductInfo VersionString unchanged at 26.11.22445, agent exe present)

## Design notes

- The task suggested `MsiGetProductInfo(InstallLocation)`; on the box that is EMPTY for the real release (the package never sets ARPINSTALLLOCATION). The guard uses `MsiGetComponentPathW` for the package's own ghoztty.exe component instead - the path msiexec itself resolves.
- The identity (UpgradeCode, ComponentId) is read from the staged package, not compiled in, so a throwaway test identity is judged by its own product.
- Debug seam: with `GHOZTTY_UPDATE_MSI_CODE` set (msiexec never runs) the verdict is advisory, so the canned-package harnesses keep arming; `GHOZTTY_UPDATE_TARGET_ENFORCE=1` restores the teeth. Release builds always enforce.
- Experience change: a portable copy that used to install a second, MSI copy (and then relaunch the old portable) now gets the refusal dialog pointing at the releases page. Filed as a decision for the user to confirm.
