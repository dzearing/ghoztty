# T2460 - Blades: a viewer pane (markdown/HTML/website/diff) folding into its blade carries its last frame through the fold like a terminal does, instead of the live WebView2 under a fading face (T2457 viewers)

## Summary

T2457 carries terminals only: `PaneView.glideSnapRequest` returns false for a viewer, so a folding viewer keeps the old live-window-plus-face mechanism (and its desync). Viewers already have a hero snapshot path (`ICoreWebView2::CapturePreview`, PaneView.heroSnapRequest viewer arm); wire it to glideSnapRequest/glideFrame so a viewer fold is one picture too.

## In plain terms

When you drag a divider far enough that a pane folds away into a thin strip
at the edge, terminals now slide away as one still picture of themselves. A
markdown, web page or diff pane did not: its live page stayed on screen under
a fading cover, the two moving out of step, which reads as jank. Now a viewer
pane folds the same way a terminal does: one picture of the page, sliding and
fading into its strip.

## Goals

- [x] a folding viewer is asked for its page's last frame at its full size
- [x] the fold draws the viewer's card from that frame and hides the live page under it
- [x] an acceptance script proves it on the test desktop, with a negative control

## Validation criteria

- [x] The viewer's frame lands during the fold, at the pane's own size, and is the page rather than a black capture - `test\win32\viewer-fold-carried.ps1` V1/V2 (green 2026-11-01: `kind=viewer 319x826 colors=6` against a 319x826 window)
- [x] The card is carried on 2+ frames, the live viewer window is hidden on every carried frame after the first, and the content's strength only falls - V3 (173 frames, 0 live after the first, largest rise 0)
- [x] At rest the viewer is folded and no face is left on show; dragged back it is a live viewer again - V4/V5
- [x] The harness can fail: `-NegativeControl` (0 ms slide) scores V3 red (3 failures)
- [x] The frame-colour oracle is unit tested: `strip_face.zig` "sampleColors" test in the win32 lane

## Notes

- Mechanism: `ViewerPane.glideSnapRequest` is the hero thumbnail's `CapturePreview` without its pacing; a capture already in flight is taken over (its decode reads `snap_w`/`snap_h` when it lands). `gdiplus_decode.scaleInto` now hands back its bottom-up DIB pixels (after `GdiFlush`), which is what a terminal's frame already is, so `strip_face.blendContent` takes either kind unchanged.
- Out of scope here: a viewer OPENING out of its strip (T2458's unfold path is still terminal-only, `armGlideSnaps` keys it on `view.surface()`); filed as T2635.
