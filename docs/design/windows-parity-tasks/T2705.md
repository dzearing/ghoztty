# T2705 - Pane drop targets that would leave the pane where it is still react on Windows; Mac now shows no target or preview there, and previews swap as a center box with a swap glyph and splits with seams

## In plain terms

On the Mac, while you drag a pane, places where dropping would change nothing
no longer light up, and the highlight now shows more clearly what will happen
(a box with a swap symbol for a swap, lines where the new dividers go for a
split). On Windows a pointless spot still lights up as if dropping there would
do something. After this lands, Windows highlights only real moves and draws
the same clearer previews.

## Goals

- [x] A drop spot that would leave the pane where it is shows no target and does nothing on release
- [x] A swap preview is the pane's center box with a swap glyph
- [x] A split or window-edge preview shows a seam where the new divider runs

## Summary

main intake 2026-11-04, from 30d13ea14 (`PaneMoveCoordinator.wouldLeaveInPlace`,
`SplitTree.hasSameLayout`, `PaneDropFeedbackView.swift`):

- **No-op suppression**: for a split, divider or edge candidate, the session
  makes the move on a copy of the tree and compares layouts (sizes aside, a run
  of same-axis splits read as one row). Equal -> no target, no preview, and a
  release does nothing. In A | B dragging A: B's left triangle, the divider and
  the window's left edge are all quiet. A stashed pane is not on the grid, so
  every place is new to it.
- **Previews**: a split, top-level insert and divider insert fill the landing
  area with seams where new dividers run; a swap fills the center box itself
  with a swap glyph.
- Pane zones are now drawn as four triangles + center box on Mac (the hit
  geometry is unchanged: diagonals, 34% center box floored 44pt, capped 60%).

Windows today: `pane_drop.zig` only treats the dragged pane itself as a no-op.
`DropHighlight.zig` / `drop_highlight.zig` draw the highlight.

## Validation criteria

- [x] Pure `hasSameLayout`-equivalent + would-leave-in-place check with unit tests (A | B cases from the Mac doc; same-axis run read as one row; stashed pane always new) - `src/apprt/win32/pane_layout.zig`, 8 tests, none + win32 lanes
- [x] Acceptance: in A | B dragging A, B's left triangle, the divider and the left window edge show no highlight and a release changes nothing - `test/win32/rearrange-noop-drop.ps1` claims Q/R, ALL PASS (32); `-NegativeControl` fails as it must
- [x] Swap preview is the center box with a swap glyph; split/insert previews show seams (off-desktop capture) - claims S/W of the same harness (WM_PRINTCLIENT pixels: one seam on the inner edge, framed box, 182 glyph pixels); `rearrange-drag.ps1` claim A updated from whole-pane to center box, green; insert seams already covered by `rearrange-divider-drop.ps1`, green

## Decisions made here

- The no-op check builds a ratio-free copy of the visible tree in a fixed buffer (`pane_layout.Shape`) instead of cloning the `SplitTree`: it runs on every mouse move, and a clone would allocate and ref every view. The move is still MADE on the copy and compared, Mac's approach, so it cannot disagree with the commit.
- The overlay is one layered window with a single alpha, so the swap box is drawn at alpha 150 (was 72) for the glyph to read; Mac's per-element opacities have no direct counterpart here.
- Not ported: Mac now draws the pane zones' four triangles (the summary's note). Mac's hover feedback is still only the landing preview - the triangles are the hit geometry, which was already the same here.
