# T2117 - Fork CI windows-cross fails since 2026-10-21 13:31 on a docs-only commit: 'compile lib glslang ReleaseFast x86_64-windows-gnu' dies with 'failed to link with LLD: UnableToWriteArchive' (runner cache/disk, not code)

## Summary

Fork CI's `windows-cross` job is red on every push since run 39615301443
(475a6bebb, 2026-10-21 14:15) and on 39608795825 (d25e3b484, a digest-only
commit that touches no code), so the cause is the runner, not the tree:
`compile lib glslang ReleaseFast x86_64-windows-gnu` -> `error: failed to link
with LLD: UnableToWriteArchive`. Earlier runs that day (39603465814,
39600011534) passed that job. Likely suspects: a poisoned/oversized zig cache
restored by actions/cache, or runner disk exhaustion while writing the glslang
archive. Investigate the cache key and free space in the job log, then fix
(cache bust, disk cleanup step, or a retry) and get the job green.

Separately, `release-parity` has been red since the Mac v1.43.0 release
(e16e44b37, 05:15): `win-v1.43.0` does not exist yet (newest win-v1.42.1).
That one clears when step 6.5's daily publish tags win-v1.43.0 - not part of
this task unless the publish fails to pick the new base.

## In plain terms

The automatic build check that runs on every push said "the Windows build is
broken" six times in a row on 2026-10-21, even for a change that only touched
documentation. Nothing was wrong with the code: the build server was reusing a
damaged leftover from an earlier build. Now the check spots that specific
damage, throws the leftover away and builds again from scratch, so a damaged
leftover can no longer make every push look broken.

## Goals

- [x] Name the cause from the CI logs, not by guess
- [x] Make CI clean a poisoned build cache itself instead of passing it on
- [x] A test that fails if that self-healing step is removed

## Root cause (log evidence)

- Failing `windows-cross` job in run 39630890907 (8ca65f6a5, 16:02Z):
  `Cache hit for restore-key: setup-zig-cache-v2-windows_cross-...--39626119452-1`,
  `Cache Size: ~375 MB`, then `error: failed to link with LLD:
  UnableToWriteArchive` 8 s into the build. The key it restored was saved by
  the previous FAILING run, so the bad artifact was inherited run to run.
- The next run, 39631635990 (4eb6998b5, 16:05Z), restored the cache 39630890907
  saved: `Cache Size: ~0 MB (189 B)` - effectively a cold build - and
  `windows-cross` went green, as has every run since (39641256459 ...
  39693760978). Not disk exhaustion: the failure is seconds into the job.
- So: a poisoned setup-zig cache, healed by accident. Nothing guaranteed the
  accident would recur.

## Fix

`.github/workflows/fork-ci.yml`, step "Cross-compile the Windows exe": tee the
build log; on failure, and ONLY when the log carries `UnableToWriteArchive`,
wipe `$ZIG_GLOBAL_CACHE_DIR` / `$ZIG_LOCAL_CACHE_DIR` / `.zig-cache` and build
once more cold. setup-zig's post step then saves the clean cache, so the next
run inherits a good one. Any other failure stays red on the first attempt.
Assertion E12 in `test\win32\release-artifacts.ps1` pins the shape (signature
match, cache wipe, pipefail, exactly two build invocations); proven to score
red against the pre-change workflow and green against the new one.
