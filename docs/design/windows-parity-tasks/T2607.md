# T2607 - Closing a split pane a second time in a window crashes the debug build (use-after-free): layoutSplits paints the sidebar desk card from a roster that still names the freed pane, and rawLayout calls e.pane.isViewer() on it - since 3e26994eb (1.51.0), on every pane style that paints the desk

## In plain terms

Splitting a window and closing the split, then doing it again, crashed
Ghoztty's development build on the second close. Released builds read the
same freed memory without crashing, which is luck rather than safety. After
this fix, the sidebar never asks a closed pane anything.

## Summary

Found 2026-11-01 while probing T2599 (lane a, debug, 1000x700, RTX 4090):
`+new-window`, then `+split` / `+close` of the split, repeated. The second
close died with `Segmentation fault at address 0x...0708` in
`PaneSidebar.rawLayout` (`e.pane.isViewer()`), called from
`Window.closeSplitPaneOpts -> layoutSplits -> clearVacatedPaneStrips ->
paintMovedBands -> paintPaneDesk -> PaneSidebar.deskCard`. Same crash in the
default layered panes, with `GHOZTTY_PANE_LAYER=0`, and with
`GHOZTTY_PANE_REUSE=0`, so T2597's pool has nothing to do with it.

**Cause.** `clearVacatedPaneStrips` (desk paint since 3e26994eb, 2026-10-30,
in every release from 1.51.0) paints the desk card inside `layoutSplits`,
BEFORE `syncPaneSidebarScoped` re-reads the roster. The card's layout funnel
(`rawLayout`) built its rows from `entries` and asked each row's pane
`isViewer()`, so the row for the pane the close had just freed was a
use-after-free. The debug allocator unmaps freed pages, so it faults there;
a release build reads stale bytes.

**Fix.** `Entry.viewer` is read at refresh, next to every other field the
row carries. `rawLayout` and the rename pencil (`beginRenamePane`, the other
reader) both use it, so no row asks its pane whether it is a viewer.
