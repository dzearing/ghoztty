# T2196 - Release-sandbox harnesses must not register the user's ghoztty:// handler: Set-GhozttyTestIsolation -ReleaseSandbox should turn GHOZTTY_URL_SCHEME off itself

## Summary

update-graceful.ps1 (a -ReleaseSandbox run) re-pointed HKCU\Software\Classes\ghoztty\shell\open\command - the USER'S release scheme - at the GhozttyT1209Test install it then deleted, so ghoztty:// links opened nothing until restored by hand (2026-10-23, caught by acceptance-parallel's state check during T1244). T1244 fixed that one script with GHOZTTY_URL_SCHEME=off; the class of bug lives in Set-GhozttyTestIsolation -ReleaseSandbox, which isolates the pipe, agent and LOCALAPPDATA but not HKCU classes. Make -ReleaseSandbox set GHOZTTY_URL_SCHEME=off (url-scheme.ps1 and registration-sites.ps1, whose subject IS registration, opt back in), sweep the other -ReleaseSandbox callers, and assert the release class is unchanged in the lib's own test. Sibling of T2195 (the dev ghoztty-debug scheme via ApplierSandbox).

## In plain terms

Some of our automated tests run a release-style copy of Ghoztty in a sealed-off
sandbox. The seal missed one thing: that copy re-registered itself as the
program that opens `ghoztty://` links, so after a test your links pointed at a
deleted copy and did nothing. The sandbox now switches that registration off
on its own, so no test can take your links again.
