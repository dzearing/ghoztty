# T2989 - PA-W05: the perf baseline cannot say which threads cause the 160-210 idle context switches a second, or what the ~51 USER objects and +10 handles per cycle are (perf-baseline.ps1:264)

## Summary

PA-W05 (audit-1, T2960). Tooling. perf-baseline.ps1:264 sums context switches across all threads. Reading the code, the apprt explains ~6/s of the measured 164-213/s at idle (4/s visibility poll PA-W06, ~1.7/s blink PA-R04, the rest minute-scale timers; FrameClock, IPC listeners and parked pool threads block). The remaining ~150/s is presumably GL/D3D11/DComp driver and OS pool threads, but no code reading can confirm it. Likewise the cycle phase leaves ~51 USER objects, 12 threads and +10 handles/+5 USER per cycle that no apprt site explains. Fix: have the snapshot keep per-thread deltas grouped by start address/module and thread name (renderer/io/io-reader are already named) and report the top 10; add a handle-type diff (NtQuerySystemInformation handle info or handle.exe -s style) before/after each cycle. Risk none (script only).

## In plain terms

The performance report could say "the app wakes up about 150 times a second
while idle" and "closing panes leaves some objects behind", but not WHO wakes
up or WHAT is left. It now names both: which threads do the waking (ours or
the graphics driver's), and which kinds of handles, windows and threads an
open-and-close round leaves. That turns two mysteries into two concrete leads.

## Goals

- [x] the idle phase splits its wakeups by thread, with each thread's name or start module
- [x] the cycle phase breaks its residue down by handle type, window class and thread group, plus the USER objects that are not windows
- [x] the remaining idle wakeups are attributed (driver threads) and the leads filed

## Findings (Debug, NVIDIA box, 2026-11-15)

- **Idle, 1 pane: 146-149 switches/s.** NVIDIA driver threads ~127/s (87%):
  `nvwgf2umx.dll` (D3D11) 3 threads ~75/s, `nvoglv64.dll` (OpenGL) 2 threads
  ~50/s. Ours: the main (UI) thread ~10/s (`mainCRTStartup`, symbolised with
  cdb), the renderer ~10/s. 86 threads, 55 of them `nvwgf2umx` pool threads.
  Lead filed as T3119.
- **First cycle residue** is mostly the deliberate pools: 9 parked pane
  windows (T3000), 9 parked renderer/io/io-reader thread triples
  (`reusable_thread`), and each parked renderer thread also keeps an
  `NVOpenGLPbuffer` and an `IME` window alive (+18 windows). On top: 44
  non-window USER objects, Event +233, IoCompletion +44, Semaphore +39, Timer +39.
- **Second cycle residue** (per-cycle growth): Event +4, IoCompletion +3,
  USER +3 (none of them windows), no threads. Lead filed as T3120.
