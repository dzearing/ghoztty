# T3108 - A viewer that stops reading can grow the Windows agent outbound queue until it runs out of memory, and an accept failure ends the agent with every session: prove the bounded queue, ring catch-up and accept retry on the named-pipe agent (Mac d5f83c3d4, 6c854957d)

## Summary

d5f83c3d4 (shared src/remote/agent/server.zig): past 4 MiB queued the bridge refuses the chunk (already in the ring), a behind session sends nothing live and the writer catches it up from the ring in 64 KiB pieces; FLOW resume uses the same path. 6c854957d (src/remote/agent/main.zig): the accept loop retries on fd/memory exhaustion instead of returning. Both arrive with the merge; check the Windows named-pipe transport goes through the same bridge/writer path and the same accept loop (the win32 accept may be a separate ConnectNamedPipe path that still returns on error), port where it does not, and add an agent-lane or acceptance test: a viewer that stops reading while a pane floods - agent private bytes stay bounded, the viewer catches up with no gap once it reads again.

## In plain terms

If the Ghoztty window stops reading from the background agent (it is frozen,
suspended, or behind a slow link) while a pane keeps printing, the agent used to
pile up every byte in memory until it ran out and took every session down with
it. The Mac fix caps that pile and replays the missed output from the pane's
own history once the window reads again. This task proves the Windows agent gets
the same protection over its real connection, not just in theory.

## Goals

- [x] Confirm the Windows connection uses the same capped send path as the Mac
- [x] Confirm the Windows agent keeps accepting connections after an accept failure
- [x] A Windows-only test over a real named pipe: a viewer stops reading, a pane floods, memory stays capped, and every byte arrives in order afterwards

## Validation criteria

- [x] Windows pipe connections run the shared `serveOne` -> `Server` bridge/writer
  path (`PipeConnWorker.run`, src/remote/agent/main.zig), and every production
  output source (ConPTY child and holder) reaches it through
  `SessionStore.onChildOutput` (session.zig) - read, so the d5f83c3d4 bound applies
  unchanged; no port needed.
- [x] Windows accept loop never returns on an accept error: `runListenPipe`
  logs, sleeps 100 ms and continues on every `listener.accept()` failure, and
  `PipeListener.accept` re-creates a dropped instance on entry - read; this
  already exceeds 6c854957d (which still ends on a non-listening socket, a state
  a pipe listener has no analog of).
- [x] New agent-lane test `named pipe: a viewer that stops reading while a pane
  floods keeps the queue bounded and catches up with no gap` (server.zig,
  Windows-only, real 64 KiB-buffer named pipe): the viewer stops reading while
  the pane prints 6x the queue limit; peak queued <= limit, `sent_offset` held
  back, then every byte arrives contiguous and byte-identical with no further
  output needed, then live streaming resumes. The connection's limit is lowered
  to 256 KiB in the test (new `Server.data_queue_limit`, defaulting to the shared
  4 MiB constant) because the agent's emulator parses ~120 KB/s in Debug: the
  first 24 MiB version passed but took ~4 min (evidence noted on T3019). Green
  on `floor-lane.ps1 -Lane agent -Filter "pane floods" -Repeat 3` and `-Repeat 2`
  (~15 s each); **negative control**: with the limit set to maxInt/2 the test
  goes red on the bound assertion.
- [x] Floor: `floor-lane.ps1 -Lane all` ALL LANES PASS (lib, none, win32, agent);
  due guards for server.zig re-run green (pane-ingest-ab, agent-relay-session-e2e,
  sessions-running-cmd, thread-join-audit, self-spawn, unwired-hook, seam,
  idle-frame-release, gl-device-lost, title-churn, cursor-blink, prompt-reflow);
  harness floor (scoped) PASS. thread-join-audit caught an unjoined accepter
  thread in the first draft of the test; the test now dials then accepts on one
  thread.
