# T1415 - Nothing tells a turn that an edit to the overlay z-order code owes overlay-zorder.ps1 a run

## Summary

T1413 restored a heal that T1345 removed a week earlier, and the gap between the two is the whole point: test\win32\overlay-zorder.ps1 is NOT a row in scripts\guard-due.ps1's coverage table, so editing src\apprt\win32\win32.zig's heal path (or chrome_fanout.zig, or any of the six overlay types that call it) flags nothing. T1345 was a measured, careful perf change with green floor lanes; the only thing that would have caught it at the boundary is the harness that owns the claim, and nothing asked for it. It surfaced instead a week later, by hand, under T607's sweep. Add an overlay-zorder row covering win32.zig, chrome_fanout.zig, overlay_zorder.zig and the overlay types (BannerOverlay/DimOverlay/Scrollbar/ReadonlyBadge/KeyStateIndicator/Surface link preview), and the matching 'update -Guard overlay-zorder' stamp call at the foot of the script, the way drag-perf.ps1 does it. Note when doing it: overlay-zorder.ps1 can legitimately SKIP section E on a desktop that refuses a band change, and guard-due does not stamp a run with skips - so decide deliberately whether E's skip should block the stamp or whether the row should cover only what always runs.

## In plain terms

When someone changes the code that keeps the terminal's floating chrome (the banner strip, dim wash, scrollbar) layered above the right window, nothing reminded them to re-run the test that proves the chrome still stays in place. One such change shipped a bug that was only found a week later by hand. Now changing that code makes the test show up as owed.
