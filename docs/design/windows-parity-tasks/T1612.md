# T1612 - +list --json reports no session_id for a pane +new-window just created, so a script cannot capture it

## In plain terms

Open a window from a script and then immediately ask which persistent session
that window's shell belongs to, and most of the time the answer comes back
empty - even though it does belong to one, and the same question answered a
quarter of a second later gets the right id. Anything automating Ghoztty that
wants to note down a window's session (to re-attach to it later, or to join it
against `+sessions`) has to know to wait and poll, and nothing says so.

## Summary

Measured on box for T1609, 15 cold starts: `+new-window --command=...` followed
immediately by `+list --json` reported `session_id` absent on 11 of 15, and
present on all 15 when the same query was retried. The id appeared 250-774 ms
after `+new-window` answered.

This is not a persistence failure - the pane really is agent-backed every time
(`shared local-agent connection ready` in the app log on every run). It is
ordering: `+new-window` answers as soon as the window exists, and the agent OPEN
that binds the pane to a session completes afterwards, publishing the id then.
`IpcHandlers.buildNode` reads `surface.core_surface.remoteSessionId()` at query
time and correctly reports null before that.

The question this task has to settle is which contract to hold, since both are
defensible and only one can be true:

- `+new-window` (and `+split`) do not answer until the pane's OPEN has
  completed, so the id is readable the moment the verb returns. Costs a
  round-trip on the reply path, and has to keep the "answer or explain rather
  than block forever" rule - a bounded wait with the existing fallback.
- `+list --json` keeps its current meaning ("what is true right now") and the
  documented answer is that a caller polls. Then `docs/claude/cli.md` has to say
  so beside `session_id`, because today nothing does.

It cost T1609 a whole turn's diagnosis, and `test\win32\ipc-command-keepalive.ps1`
now carries a `Wait-SessionId` poll for exactly this reason - which is the
workaround, not the fix.

Mac side: `T553` is the separate question of whether Mac reports `session_id`
at all; this is about WHEN, and whichever contract wins should hold on both.

## Goals

- [x] `+new-window` answers only once its new pane's session is bound
- [x] `+split` (including `--from-focused` and `+new-window --split`) likewise
- [x] the wait is bounded and never holds the GUI thread
- [x] the contract is documented beside `session_id`

## Decision

The verb waits (option 1 of the Summary). A script should not have to know
about an internal OPEN to address what it just made, and the "answer or
explain" rule is kept by a 3 s budget plus an early exit when the OPEN fails.
The wait runs on the IPC listener thread (one of four pipe instances), polling
readiness through the GUI thread via the same `WM_APP_IPC` message, so every
existing drain path (shutdown, the local-agent resolve pump) serves the polls
too and the GUI keeps pumping. `termio.Remote.bringup_settled` flips as
`threadEnter` returns, after the id is published, so "settled and no id"
means that bring-up failed.

## Validation criteria

- [x] The contract is decided and written into `docs/claude/cli.md` beside
      `session_id`. (cli.md, new paragraph under the `session_id` one.)
- [x] A script that runs `+new-window` and then `+list --json` once, with no
      poll, gets the pane's `session_id`. (`test\win32\ipc-list-session-id.ps1`
      section 4: the launching `+new-window`, a second `+new-window --command`,
      and a `+split`, each read once - ALL PASS, 48 assertions; verbs answered
      in 108-126 ms.)
- [x] The check is exercised over a COLD start (no agent running). (Each of
      section 4's five rounds kills app and agent first. Negative control: the
      same script against a build with the wait disabled scored 20 FAILURES -
      every round red - so the arm measures the fix, not luck.)
