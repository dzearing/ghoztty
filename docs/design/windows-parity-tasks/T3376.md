# T3376 - The debug app can crash 8s after a cold launch inside FormatMessageW on its main thread (access violation)

## Summary

The debug GUI, cold auto-launched by ipc-p1 section 1 at 2026-11-21 14:11:51, died 8s in with 0xC0000005 on its MAIN thread inside KERNELBASE!FormatMessageW (ntdll!RtlFindMessage -> LdrRscIsTypeExist -> LdrLoadAlternateResourceModuleEx), called from ghoztty+0x996bf; 21 threads alive. The CLI saw it as "Failed to read IPC response length" after 7546ms (transcript %TEMP%\ghoztty-ipc-p1-fail-20261121-141200-43972.log). Dump: %LOCALAPPDATA%\CrashDumps\ghoztty.exe.36580.dmp, copied to D:\git\ghoztty-b\.dumps\ghoztty-20261121-141159-0.dmp (+ .log with every thread). Symbols did not match the current zig-out, so the caller frame is unresolved: first step is to resolve 0x996bf against the build of that hour (or catch it live with scripts\crash-catch.ps1), then find which error path formats a Win32 message on the UI thread and why FormatMessageW faults (bad lpSource/flags, or a stack too small for it).

## In plain terms

When Ghoztty was started from a command line without a console of its own (the
way the CLI starts it in the background), a startup check quietly broke the
app's error-output channel so that it pointed at something else the app had
opened - on the day of the crash, its own command pipe. In a debug build the
first log line after that sent it into an endless loop and it crashed a few
seconds after launch. In a release build those log lines would silently go
into the wrong place. After this lands, the check puts everything back the way
it found it.

## Goals

- [x] name the real fault (it was a stack overflow, not a FormatMessageW bug)
- [x] fix the startup check so it leaves the standard handles untouched
- [x] an acceptance check that goes red on the old build and green on the new

## Root cause

The dump's main thread had used all 16 MB of its stack. Symbolised against a
rebuild of a4ea9abf4 (the build of that hour), one ~3.6 KB cycle repeats about
4500 times: `std.debug.print -> lockStderrWriter -> flush -> WriteFile ->
unexpectedError -> std.debug.print`. `!gle` reads 536 (ERROR_PIPE_LISTENING):
stderr was a named-pipe SERVER end - the IPC listener. std's WriteFile does not
map 536, so it calls `unexpectedError`, whose Debug-only diagnostic print writes
to the same stderr and fails the same way.

Why stderr was the listener: `cli_launch.parentOwnsConsole()` probes the
parent's console with `AttachConsole(ATTACH_PARENT_PROCESS)` then
`FreeConsole()`. The attach points all three standard-handle slots at the
parent's console; the free closes those handles but leaves the slots holding
the closed numbers, which the next handles the app creates reuse.

Fix: `src/os/cli_launch.zig` saves the three slots before the attach and
restores them after the free (and after a failed attach).
