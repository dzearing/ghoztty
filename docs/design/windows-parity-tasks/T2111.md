# T2111 - task-dashboard.ps1 goes 10-red in a parallel worker (every /api/data request answers -1 after 220s) and is all-green alone in 33s; nothing marks it, so each due run pays a retry

## Summary

Seen 2026-10-20 during T2097: 'acceptance-parallel.ps1 run -Scripts task-dashboard.ps1' with no other script beside it - w1 FAIL B1-B5, C1-C4, C6 (/api/data and /api/commit got -1), then w0 alone PASS 33/33. The runner printed PARALLEL-SENSITIVE. Find what the worker mirror lacks or shares that makes the payload build time out (git history in the mirror? the live dashboard's port 7788?), fix that, or mark the header @parallel-unsafe with the reason.

## In plain terms

One of the tracker dashboard's own tests failed every time it ran beside the
others and passed when re-run alone, so every test sweep paid for a retry. It
now passes in a worker the first time.

## Goals

- [x] find what the worker run has that the lone run does not
- [x] fix that rather than marking the script parallel-unsafe

## Root cause and fix

Reproduced 2026-11-24 (`acceptance-parallel.ps1 run -Scripts task-dashboard.ps1`):
w1 aborted at section E with `ReadAllText ... being used by another process`
on `task-dashboard-selftest-<pid>.html`, then w0 alone passed. The /api/data -1
timeouts of 2026-10-20 no longer reproduce (the payload has been made fast
since: G1's warm budget). Section E launched headless Edge with **no
`--user-data-dir`**, so Edge used `%LOCALAPPDATA%`'s default profile - the
user's real profile when run alone, and in a worker (private LOCALAPPDATA) a
brand-new one, where first-run setup leaves helper processes alive holding the
redirected stdout after the launcher exits. Fix: a private profile plus
`--no-first-run` (what dashboard-dom.ps1 has always done), and a bounded 20s
wait for the DOM file instead of a throw that aborted every later section.

## Validation criteria

- [x] stays green beside its neighbour - `run -Scripts task-dashboard.ps1,dashboard-dom.ps1` twice: both PASS in workers both times
