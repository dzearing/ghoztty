# T2726 - GUI acceptance harnesses that launch the debug build on the user's real LOCALAPPDATA read and write persisted chrome preferences (viewer_sidepanel_width-debug, pane_sidebar-debug), so one run's drag or toggle changes the next run's design defaults; T2380 was this shape. Audit which harnesses do, and isolate them (private LOCALAPPDATA or pinned config), ideally with a harness-floor audit that fails a new one

## Summary

Found by T2380. The debug build keeps chrome preferences under `%LOCALAPPDATA%\ghoztty\*-debug` (`viewer_sidepanel_width-debug`, `pane_sidebar-debug`, `pane_sidebar_order-debug`, ...). Most GUI harnesses isolate only the IPC pipe (`GHOZTTY_PIPE_SUFFIX`), so they read whatever an earlier run left and write their own: on 2026-11-05 a red `viewer-narrow-pane.ps1` run rewrote `pane_sidebar-debug` at 09:22, and a 360 DIP card width left on 2026-10-27 turned its section A red for nine days. A harness whose numbers depend on a design default is then measuring box history.

Fix: list the GUI harnesses that launch the app without a private `LOCALAPPDATA` (`Set-GhozttyTestIsolation` or the `viewer-popup.ps1` pattern), isolate the ones that read chrome prefs, and add a harness-floor member that fails a new GUI harness without it (or with an explicit exemption line).

## Validation criteria

- [ ] An inventory of GUI harnesses on the shared LOCALAPPDATA, each isolated or exempted with a reason.
- [ ] A harness-floor audit that fails a new GUI harness without isolation, with a -NegativeControl.
- [ ] The user's `*-debug` pref files are not modified by a full `acceptance-parallel.ps1 due` sweep (mtime check before/after).
