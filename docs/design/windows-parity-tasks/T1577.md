# T1577 - tab-strip.ps1's two-tab width assertion can read a shell's transient path title

## Summary

Seen once on 2026-09-14 during a T737_NEUTERED control run: 'two tabs: each is still its own content's width (319 vs 171)' failed because the new tab's title at the instant of measurement was the cmd.exe PATH ('C:\\WINDOWS\\system32\\cmd.exe') rather than the settled cwd title ('C:\\Users\\David'). The same run passed with 171 vs 171 twice either side of it, and the code under test was identical (the neuter restores pre-T737 behaviour), so this is the harness reading a title that is still in flight rather than a defect in the strip. The fix shape is the one section 8 already uses: settle the title deliberately (send a known 'title X' and wait) before measuring, or assert against the title +list --json reports at that moment instead of an expected width.

## In plain terms

Open a second tab with the "+" and it came out noticeably wider than the
first one, even though both showed the same folder name. The new tab was
sized for the longer name its shell shows for an instant while it starts,
and the strip's rule against tabs shrinking on their own kept that width.
Now a tab that nobody has typed into yet settles onto its real name, so two
identical tabs are the same width.

## Root cause

Not the harness: the product. The strip re-fits its ratchet marks when a tab
opens (`tab_sticky_key` changes with the count), and at that instant the new
tab's shell is still titled with its launch command (the cmd.exe path). The
prompt's own title (the cwd) arrives a beat later and is SHORTER, and T249's
grow-only ratchet refuses a shrink - so the tab held 319 px against its
twin's 171 until something else re-fitted the strip. Deterministic since at
least 2026-11-15. The harness's title wait (T756) was already right, which
is why "2 titles agree" printed beside every red.

Fix: `tab_strip_layout.releaseFresh` (called by `Window.zig` just before
`applySticky`) lets a tab whose focused pane has had no user input
(`core_surface.user_input_sent`) follow its title in both directions. The
first keystroke ends it, and T737's pointer freeze still defers the release
while the pointer is in the strip. Negative control: `T1577_NEUTERED`.
