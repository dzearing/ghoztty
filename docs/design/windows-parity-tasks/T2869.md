# T2869 - A moving blade leaves a frozen copy at its start while the app stalls mid-glide: the desk under the compositor's strip face is not repainted before the stall, so comp-glide-hold-onscreen.ps1 -Arms strip .22 reads the old blade still at its rest place for the whole stall

## Summary

Found by T2851's film. Five panes beside the pane sidebar's rail (flat style), the first tucked into a blade; the toggle expands the sidebar with GHOZTTY_DEBUG_GLIDE_STALL_MS=500. The blade's face is declared (`stack strip face declared clip_left=95->330 ... still=330,40,140,866`, still empty) and slides on through the stall - the band trace reads a blade at 145, 154 ... 320 frame by frame - but a SECOND copy of the blade sits at its start (x 101, one tick's step from rest at 96) for the whole stall and leaves only at ~880 ms, when the thread wakes. The leading edge therefore holds still 525 ms (.22 red). The desk that should stop painting the blade (`deskStripTab` -> `StripFace.still`) has not been repainted when the stall lands: the stall comes after the glide's first tick, before the WM_PAINT that would paint the desk without the blade, so DWM keeps composing the old desk under the moving face. A busy UI thread does the same in real use. Likely fix shape: paint the desk synchronously (or in the same commit as the face's declaration) in the pass that declares, so the face and the desk without the blade go up together.

Evidence: `powershell -NoProfile -File scripts\comp-glide-hold-onscreen.ps1 -Arms strip -KeepFrames` (frames f9-f70 of the 2026-11-09 run show both copies). With -StallMs 0 the arm is smooth (57 moves, 17 ms longest still), so it only shows when the thread is busy mid-glide.

## In plain terms

When you open the pane sidebar while the app is briefly busy, the thin folded pane at the edge of the grid appears twice for half a second: one copy slides over with the other panes, and a frozen copy stays behind where it started. It should just slide.
