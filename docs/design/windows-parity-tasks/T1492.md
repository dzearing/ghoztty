# T1492 - A debug agent's own log line makes the delivery read its build stamp as missing

## In plain terms

Before a new build is delivered, the scripts read each binary back and ask it
which build it is, so a copy that silently did not happen cannot be reported as
a success. The background helper now prints one line of debug logging when it
starts, and that line arrives ahead of its answer — so the check reads "this
binary told me nothing" and fails, on a binary that in fact answered correctly.

## Summary

`Get-StampFromAgentVersionText` (`scripts\delivery-version.ps1`) reads the agent's
build stamp out of `ghoztty-agent.exe --version`. It walks the output lines, and
**returns empty the moment the first non-empty line is not `ghoztty-agent
<stamp>`** — deliberate strictness, so junk output cannot be mined for a false
stamp (T281's whole point is that an unread stamp must never read as a match).

A debug-build agent now opens with a `std.log` line before it prints anything
else:

```
debug(os_power): power throttling disabled for this process
ghoztty-agent 20260908-fc2e17ac4
```

so the parser bails on line 1 and reports `no 'ghoztty-agent <stamp>' line in
the output`. Observed on `zig-out\bin\ghoztty-agent.exe` (stamp
`20260908-fc2e17ac4`), which answers correctly when run by hand.

Cost: `test\win32\upgrade-staleness.ps1` is **10 FAILURE(S) (143 passed)** —
B7, B8, E1, E4, E10, E11, E12, E13 and neighbours, all of them the
`AGENT VERIFY` family that exists to catch the 2026-07-20 skipped swap. Its
guard was stamped green on 2026-09-07 and the agent stamp is dated 09-08, so it
has been red since then with nothing reporting it (found while running the
harnesses T689's edits made due).

Scope, confirmed: the agent declares no `std_options`, so it takes Zig's default
log level — `.debug` in Debug builds, and not `.debug` in the ReleaseFast the
delivery actually ships. So a released agent does not emit that line and the
production delivery path was never broken; what was broken is the verification
of DEBUG agents, which is the entire on-box acceptance path. The app's own
`+version` reader (`Get-CommitFromVersionText`) is immune for a different
reason: it matches multiline against the whole payload rather than anchoring on
the first line.

## Details

The fix must keep the strictness that motivated the current shape. Skipping
lines that are recognisably `std.log` output — `debug(scope):`, `info(...)`,
`warning(...)`, `err(...)` — and still bailing on anything else preserves "junk
cannot produce a stamp" while letting the agent talk on its way up.
`Get-CommitFromVersionText` (the APP's `+version` reader) deserves the same
question asked of it.

## Validation criteria

- [x] A stamp is read correctly from output whose first lines are `std.log`
      lines, and still NOT read from output that is merely junk (both directions
      asserted). `upgrade-staleness.ps1` A24a/A24b/A24c — the debug line ahead of
      the banner, every log level, and junk ahead of the banner still yielding
      nothing.
- [x] `test\win32\upgrade-staleness.ps1` is ALL PASS on the box — 156
      assertions, up from 143 passed / 10 failed before the fix, and it
      re-stamped its guard.
- [x] It is stated, from evidence, whether a ReleaseFast agent emits anything
      ahead of its version line. It does not: the agent declares no
      `std_options`, so `.debug` messages are not emitted outside a Debug build.
