# T1822 - test-binary-soak and crash-databreak still run test binaries on the user's desktop: Start-Process -WindowStyle Hidden from the caller's process, so a win32 soak/databreak shows its banner windows on screen

## Summary

T1813/T1815 moved floor-lane, the soak daemon and floor-lane's cdb re-run onto GhozttyLaneDesktop. Three hand-run investigation paths still launch test binaries from the caller's (input) desktop: scripts\test-binary-soak.ps1 (Start-Process cmd /c ... lines ~373 and ~850, plus PsExe children ~508/~599), scripts\crash-databreak.ps1 (zig build via Start-Process ~343) and scripts\lib\DataBreak.ps1 (cdb via Start-Process ~126/~815/~1060). A win32-lane soak or databreak run therefore re-runs the banner tests on the user's screen. Fix: route each through Start-LaneProcess (scripts\lib\LaneDesktop.ps1) with cmd redirection, as CrashCatch.ps1 now does; measure from inside the child (the deskav crasher pattern in test\win32\crash-stacks.ps1 section 4a).

## In plain terms

Two debugging tools we run by hand to chase a rare crash (the soak runner and
the data-breakpoint runner) re-run the Windows test suite many times. Those
tests briefly open small windows, and these tools started them on the user's
own screen, so a soak could flash windows over whatever the user was doing.
After this change every test those tools start runs on a hidden background
desktop, the same one the regular test lanes already use.

## Goals

- [x] the soak runner's direct test runs land on the background desktop
- [x] the soak runner's load workers land there too (a load command can be a test lane)
- [x] the data-breakpoint runner's debugger, and so the test binary under it, lands there
- [x] the data-breakpoint runner's `zig build` lane lands there
- [x] each placement is measured from inside the child, with a control

## Design

One helper, `Start-LaneRedirected` in `scripts\lib\LaneDesktop.ps1`: a program
on the lane desktop with stdout/stderr in files, via `cmd /s /c` redirection
(the shape `CrashCatch.ps1` already used for the T1815 re-run). Six launch
sites moved onto it or onto `Start-LaneProcess`: the soak's standalone run and
its cpu and command load workers; `crash-databreak.ps1`'s `Start-Lane`; and
`DataBreak.ps1`'s probe, page-watch and per-call cdb runs. The timed-out kill
paths now kill the TREE (`Stop-ProcessFamily` in the soak, `taskkill /T` in
DataBreak), because the returned process is cmd, and killing it alone would
leave the binary running on a desktop nobody can see.

The build-runner round deliberately stays where it is. It starts
`floor-lane.ps1`, which opens no window and already places its lane (T1813)
and its cdb re-run (T1815) on the lane desktop. Its window check then
samples the input desktop. Section 7 measures the lane's own process there.

Found in passing: `Start-LaneProcess` read every `CreateProcessW` failure as
"desktop unavailable" and fell back to the input desktop with a false outage
banner, even for a program that does not exist (the soak harness's
no-worker check tripped it four times). File-/path-not-found now throws, the
way `Start-Process` always did.

- [x] a build-runner round's lane and a command load worker both report the lane desktop - same section 7

- [x] `Start-LaneRedirected` lands on the lane desktop, splits or folds stderr, returns the program's exit code; a missing program throws without a false outage line - `test\win32\floor-lane-desktop.ps1` section D (ALL PASS 20)
