# T2630 - Under a held drag (T2623) a pane WITHOUT its own layer (GHOZTTY_PANE_LAYER=0) never gets its revealed strips filled: fillUncoveredStrips is own-layer only, so a grown pane on the escape-hatch path can show stale or desk pixels until its next frame

## In plain terms

When you drag the divider between two panes, the pane that grows briefly shows a
strip of leftover pixels (the old neighbour's text or the desktop colour) along its
new edge until the drag settles. The normal setup already painted that strip with
the terminal background; the fallback setup (panes without their own layer) did not.
Now both do, so the growing edge reads as background on every path.

## Goals

- [x] The uncovered-strip fill runs for any opaque pane that presents into its own window, not only a layered one
- [x] The rule is a pure, unit-tested function
- [x] An on-box harness shows the fill firing on the plain-child path, with a layered positive control, and goes red on the old gate

## Summary

`Surface.handleResize` filled the strips a grown pane's last frame does not cover
(T2485 D18) only when `own_layer` was set. A plain WGL child (`GHOZTTY_PANE_LAYER=0`,
with the composition swap chain off - `GHOZTTY_COMP_PRESENT=0` - since that has been
the default path since T2515) skipped it, so under a held divider drag (T2623) the
grown strip showed the top-level redirection surface's stale pixels until the settle.

Fix: the decision moved into `resize_paint.fillsUncoveredStrips` - fill when a live
pass is running, the pane presents into its own window (no window presenter T2610,
not the composition path), and the window is opaque. A translucent window still
skips it: an opaque GDI fill there would stop the desktop showing through.
`fillUncoveredStrips` now logs `pane strip fill layered=<bool> strips=<n>` as the
oracle (the strip is sub-frame and the GL surface does not PrintWindow off the input
desktop, so the decision is stated rather than photographed - the T1031 shape).
