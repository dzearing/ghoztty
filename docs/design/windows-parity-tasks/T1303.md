# T1303 - The post-update sweep check fails under box load, and reads as a real leak

## Summary

update-real-msi section E waits up to 30s for the app's next launch to sweep what the update left, then FAILS naming the file (ghoztty-updater.exe). On 2026-09-03 it went red on a loaded box and green solo, minutes apart, over the same code - so a real leak and a slow box are indistinguishable. Give the wait a load-aware bound or measure the sweep's completion rather than a fixed window.

## In plain terms

The test that walks a real in-app update ends by checking that the next launch
cleaned up the update's leftover files. It gave the app a flat 30 seconds, so on
a busy machine it reported "a file was leaked" when the app simply had not
finished starting. Now it waits until the app has provably done its cleanup and
only then looks, and "the app never started" is reported as its own failure.

## Goals

- [x] The leftover check waits for proof the cleanup ran, not a fixed clock
- [x] A slow launch and a real leak produce two different failure messages
- [x] A planted leak still fails, naming the file

## Validation criteria

- [x] Section E waits for the relaunched app's first window (`+list --json`
      reports one) - the startup sweep runs in `App.init` before `run` opens
      any window, so a window is proof the sweep finished. Load-aware bound:
      60s base, extended while the app's stderr moves, 240s cap. Verified:
      `acceptance-parallel.ps1 run -Scripts update-real-msi.ps1` ALL PASS (39
      checks), window up after 12s, guard re-stamped.
- [x] A launch that never reaches its window fails as "its sweep ran ... not a
      leak verdict", and the leak assertion is not made. Verified by the
      first (pre-fix-probe) run: the readiness line failed alone, the leak line
      was never asserted.
- [x] Negative control `-PlantLeak` (a held `*.old-1303` image the sweep
      cannot delete): "sweep ran" PASS, "swept everything" FAIL naming
      `ghoztty-agent.exe.old-1303`, 1 FAILURE (38 passed), no stamp.
