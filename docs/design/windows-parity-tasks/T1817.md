# T1817 - Windows port of the --reboot-tui restore scenario

## In plain terms

After the computer restarts (or the background session keeper restarts), a
restored Windows terminal pane should look exactly as it did, with a working
prompt, no stray characters typed into the shell, and nothing going blank when
the pane is resized. The Mac proved this with a scripted scenario; Windows has
the same shared code but nobody has proved it here yet.

## Summary

Split from T1800 (Mac commit 7e78aacf4, merged on this branch by T1796). The
Mac reproduced 14 failures with `scripts/e2e/session-persistence.py
--reboot-tui` and fixed them in shared code: content-only HISTORY replay
(`grid_snapshot` scrollback, `<id>.hist`) instead of the raw ring, client
inbound-ring per-channel overflow plus FLOW resume, `drainRing` yielding on big
replays, panes waiting for their real size instead of the 49x17 placeholder,
`Attached.replay_len` plus the discard-watermark clamp, live-cwd re-sampling,
orphan snapshot sweep, extended VT mode resets, and soft-wrap/OSC 133 kept on
restored rows.

T1800 itself landed the one piece that was explicitly POSIX-only (per-child
input writer threads, now on Windows too). What is left is the Windows proof:
an on-box acceptance script, run on the background test desktop, that kills
and restarts a debug `ghoztty-agent.exe` (by ExecutablePath, never by name)
with a TUI and a pwsh pane mid-session, re-attaches, and asserts the outcomes
below. Any assertion that fails is a defect to fix here (or a new task).

## Validation criteria

All by `test\win32\session-reboot-tui.ps1` (new), run 2026-10-10 on the debug
build of bf1e6a16c (no product code changed in this task): **ALL PASS (56 assertions)**, stamped.

- [x] Restored pane shows the exact pre-restart history (content match) -
      H1: all 120 conversation lines above the notice, once, in order; H2 the
      final prompt-box frame; H3 no stale frames. B5 is the positive control
      (the LIVE pane held the same exact sequence before the kill). The
      full-screen pane's last frame is NOT restored - filed as **T1819**, and
      the harness prints `PENDING H4 ... (T1819)` every run until it lands.
- [x] No terminal query replies are answered into the new shell - Q1 (no
      DA1/DECRQM/XTVERSION/kitty reply text after the notice, both TUI panes)
      and Q2 (no file created in the panes' cwd, which is what a reply typed
      into cmd.exe's `>` redirect would do).
- [x] No keyboard/mouse/bracketed-paste modes left on after restore - M1:
      DECRQM from inside each restored pane reads ?1000/1002/1003/1004/1006/2004
      all reset ('2'). Kitty keyboard flags are reported as information: the
      `CSI ? u` query gets no reply through ConPTY, so it cannot be scored.
- [x] A live prompt answers typed input after restore - L1 (Test-PaneLive)
      on all three panes, R3 again after the resize.
- [x] The restored pane opens at its real size, not 49x17 - S3: no
      "attaching at the placeholder" line in the app log (S2 positive control:
      the log records the attaches); S1: each restored console is the window's
      width exactly and its height less the interrupted-notice banner (measured
      112x30 before, 112x26/27 after; the banner lengths are printed beside it).
- [x] A pane resize after restore does not blank the restored output - R1/R2:
      all 120 lines still present after narrowing and re-widening the windows.
- [x] The script runs on the background test desktop and takes no foreground;
      it has a guard-due row - G1/G2 (foreground watcher sampled, no test pid
      ever foreground) and the new `session-reboot-tui` row in
      `scripts\guard-due.ps1`.
