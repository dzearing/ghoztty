## Summary

T2727 built the scenes for every trigger cell (banner's `pane-top` edge, and
`New-FrameLabCellScene -States` for hero / tab-switch / split-close), proven on
synthetic frames in `test\win32\frame-lab-live-scene.ps1` section H. The live
driver (`test\win32\lib\FrameLabDriver.ps1`) still cannot use them:

  (`Invoke-FrameLabTrigger`, presence-gated like the pointer driver).
- The scene hook must take one still per pane-set state the way it takes the
  maximized still: fire the first step, settle, measure that state's geometry
  and capture its still, fire back. For split-close the new pane has to run a
  test card (index not used by the start), or the state cannot calibrate.
- `Geometry.Target` must name the banner's pane (the trigger plan needs it
  for IPC and the spec for `pane-top`).
- Real-app risks the synthetic world does not cover: the banner's own colour
  equal to the theme padding would stop the `pane-top` scan at the banner's
  top; the left padding may be inside the content rect (calibration refuses).

## In plain terms

The frame lab photographs the terminal while something happens to it - a
banner appearing, a pane going full-screen ("hero"), switching tabs, opening
and closing a split - and checks that no photographed frame is half-drawn.
Its scoring for those six actions existed, but the part that actually PERFORMS
them on the real app did nothing, so every such check said "skipped". Now it
performs them, takes the reference photos each check needs, and scores the
result. Who notices: whoever runs the lab live (`frame-lab.ps1 -Live`).
