# T1580 - A video in a viewer pane cannot be scrubbed, because the page host answers whole files only

## Summary

T750 widened the MIME table so a <video> element in a rendered .html pane finally gets video/mp4 instead of application/octet-stream. Playback is only half of it: servePageResource reads the whole file and answers 200 with no Accept-Ranges header and no handling of a Range request, so the engine cannot seek. A long clip buffers from the start and the scrubber does nothing. The same gap applies to <audio>.

**Correction on re-verification (2026-09-25):** the filing said Mac's ViewerSchemeHandler has the same shape and so this "moves on both seats". It does not: Mac renders a `.html` pane with `webView.loadFileURL(url, allowingReadAccessTo:)` (`macos/Sources/Features/Viewer/ViewerView.swift:2607`), so the page's media loads through WebKit's own `file://` loader, which already seeks. `ViewerSchemeHandler` only serves the bundled template's assets. This is Windows catching up to Mac; there is no Mac half to file.

## In plain terms

A web page opened in a viewer pane could play a video or a sound clip, but dragging the progress bar did nothing. The clip always loaded from the start, and a clip bigger than 32 MB would not load at all. Now the pane serves the part of the file the player asks for, so seeking works and large clips play.

## Goals

- [x] the page host answers a `Range` request with `206 Partial Content` and exactly the bytes asked for
- [x] every answer advertises `Accept-Ranges: bytes`; a range past the end is a `416`; an unparseable or multi-range header is ignored (whole file)
- [x] only the requested slice is read off disk, capped at 8 MiB per answer, so a clip above the 32 MiB whole-file ceiling still plays and seeks
- [x] a real `<audio>` element in a rendered page seeks on the box

## Validation criteria

- [x] Range rules (single range, suffix, open-ended, clipping, the 8 MiB cap, 416 vs ignored, headers) - 8 unit tests in `src/apprt/win32/viewer_range.zig`, `zig test` standalone and in the `none` lane via `src/apprt.zig`.
- [x] COM slot positions for `get_Headers`, `GetHeader`, `Contains` - asserted in `webview2_iface.zig`'s vtable layout tests (win32 lane).
- [x] On the box, section K of `test\win32\viewer-html.ps1` (ALL PASS, 66 assertions): no-Range 200 with Accept-Ranges; `bytes=10-19` a 206 carrying bytes 10..19 (content checked); `bytes=-5` the last five; `bytes=5000-` a 416 with `bytes */1000`; a multi-range header answered whole (negative control); `bytes=0-` on a 40 MiB file capped at 8 MiB; its last bytes reachable past the ceiling while the whole-file fetch is still refused; an `<audio>` seeked to its last second, which the log shows as the engine asking for `range=20971520-21168043/21168044 status=206`.
