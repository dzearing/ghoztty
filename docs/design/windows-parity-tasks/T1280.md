# T1280 - test-desktop-spike.ps1's posted-input assertions flake, so the harness's own regression test can read as a product regression

## In plain terms

The small script that proves the hidden test desktop works fails now and then
for no reason - press a key, nothing arrives, run it again and it is fine. It is
the script everything else about that desktop is trusted on, so a random red
here looks like the app broke when nothing did.

## Summary

Observed on 2026-09-02 while closing [[T1115]]. Three consecutive runs of
`test\win32\test-desktop-spike.ps1` against the same Debug build at the same
commit:

| run | verdict |
|---|---|
| 1 | `2 FAILED / 14 passed` - `posted WM_KEYDOWN reaches the terminal` and `a posted ctrl+shift+t chord fires its keybind (tabs=1, want >=2)` |
| 2 | `ALL PASS (16 assertions)` |
| 3 | `ALL PASS (16 assertions)`, and green again through `suite-run.ps1` |

Both failures are the same event: the posted key never reached the app. The
chord assertion is downstream of the plain post, so one cause produces both
lines. The capture assertions were unaffected in all three runs.

The likely mechanism is a race between the launch and the input, not a
capability gap - the script posts as soon as it has found the window and taken
focus via `AttachThreadInput` + `SetActiveWindow` + `SetFocus`, and a window
that has been created but whose surface/keybind wiring has not finished
initialising will drop the message with no error. There is a fixed
`Thread.Sleep(150)` after the focus dance and a `Thread.Sleep(400)` after the
posts; neither waits on anything observable.

Why it matters more than a normal flake: this script is the certificate for the
background-desktop harness (`lib\TestDesktop.ps1`) that ~50 acceptance scripts
now run on. A red here is read as "the desktop harness regressed", and one that
is red a quarter of the time trains everyone to re-run rather than look - which
is exactly how [[T1115]]'s real, month-old wrong answer survived in the same
file.

## Where

- `test/win32/test-desktop-spike.ps1` - the focus dance and the two posted-input
  assertions
- `test/win32/lib/TestDesktop.ps1` - the shared post/focus helpers the harness
  scripts use, if the fix belongs there instead

## Goals

- [x] Establish the actual cause with a repeat run (e.g. 20 iterations, logging
      the focus/tab state at each step) rather than assuming the race.
- [x] Replace the fixed sleeps on the input path with a wait on something
      observable - focus actually held, or the app answering over IPC - so the
      assertion cannot fire before the app can receive.
- [x] Confirm the fix with a repeat run that is green N-for-N.

## Cause (measured 2026-10-24)

Not the launch race the Summary guessed. A background-desktop-only probe
(scratchpad, no input-desktop contact) measured it:

- **Launch timing is not it.** From a clean slate, posting with ZERO settle
  after the window appears was 6/6 green; the shell prompt is already up and the
  posted keys land in the pane ~20 ms after the post.
- **The spike never reset state.** `Kill-SpikeInstances` is
  `Stop-RepoGhoztty -AppOnly`: the debug session-layout manifest and the
  agent's layout store survived, so every launch RESTORED what the previous
  script or spike left. Over 14 consecutive runs the tab count before the
  chord climbed 2 -> 11, so `tabs >= 2` passed with no chord at all (a false
  green), and earlier runs' `spikeb` was already on screen.
- **The readback was not tied to the window posted to.** It read
  `windows[0].tabs[0]`, while the keys went to the first `GhozttyWindow`
  `EnumWindows` returned. With a restored second window those are
  order-dependent - which is exactly the 2026-09-02 red: no `spikeb` seen and
  `tabs=1` (the OTHER window's count), both from one cause.
- **A second, latent race:** the ctrl/shift key state was cleared on a fixed
  200 ms timer after posting the `T` keydown, whether or not the app had
  dequeued it yet - a busy app reads plain `t`.

## Fix

- `Reset-GhozttyTestState` (full: app + agent, manifest, agent layouts) before
  the launch.
- The window is located in `+list` by its hwnd (`id`), never as `windows[0]`.
- A new clean-slate assertion: one fresh tab and no leftover `spikeb` before
  anything is posted.
- Every fixed sleep on the input path is now a bounded IPC poll: focus held,
  the app listing the window with a non-empty pane, the token appearing, the
  tab count rising. The modifier state is held until the new tab is reported.
- The chord asserts exactly `+1` tab, not `>= 2`.

      only the SendInput call, the SetForegroundWindow call and
      `Assert-UserAbsent` removed ran 20/20 with all four input assertions

      depends on - the 150/800/200/1500 ms sleeps are replaced by IPC polls
      (the 400 ms after the SendInput attempt remains; it only serves the
      SendInput-is-blocked assertion, which reads a return code).
