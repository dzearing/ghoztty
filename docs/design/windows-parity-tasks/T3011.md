# T3011 - PA-M11: the first use of a missing glyph opens every font file in the Windows Fonts folders with FreeType, up to 16 faces per .ttc (font/discovery.zig:1050)

## Summary

DONE in this task's commit: `src/font/WindowsFontIndex.zig` (process-wide family + cmap-coverage index, prewarmed off-thread, folder-stamp invalidation); `src/font/discovery.zig` Windows backend queries it. Original filing:

PA-M11 (audit-1, T2961). src/font/discovery.zig:1050-1085 tryMatch calls Face.initFile on every .ttf/.otf/.ttc (16 faces per .ttc) in the system and user font directories per discovery; SharedGrid caches the answer (negatives included), so it runs once per new codepoint/style/presentation. Estimated tens to hundreds of ms of CPU per first-seen missing codepoint (unmeasured). Fix: build a family + coverage index once per process (or use DirectWrite's fallback). Risk low. Windows-only discovery backend. Baseline: docs/design/perf-audit/baseline-1.json (T2958); findings: docs/design/perf-audit/audit-1/M-findings.md.

## In plain terms

The first time a pane had to draw a character none of its configured fonts
has (a CJK ideograph, a rare symbol, binary noise), Windows Ghoztty opened
every font file installed on the machine to look for one that did, and every
pane sharing those fonts froze while it looked. A burst of unusual output
could freeze the terminal for seconds. Now the installed fonts are catalogued
once, in the background, and the lookup answers from that catalogue.

## Goals

- [x] a missing-glyph lookup no longer opens every installed font
- [x] the answers are exactly what they were (same fonts, same order)
- [x] a font installed while the app runs is still found
- [x] the one-time catalogue build happens off the GUI and render threads

## Validation criteria

- [x] time to first render of a never-seen fallback glyph measured before and after (numbers in the task) - one fallback query (none lane, this box, warm file cache): uncovered U+10FFFC 42.6 ms -> 0.4 ms, U+4E00 19.0 ms -> 0.3 ms, U+0E01 17.8 ms -> 0.2 ms. The one-time index build is 60-75 ms and runs on the `font-index` prewarm thread started when discovery is created.
- [x] font discovery tests green; fallback glyphs still resolve - `windows` discovery test plus three new tests in `src/font/WindowsFontIndex.zig` (range folding; family/codepoint queries + a font added to an indexed folder is found on the next query; every candidate on the real Fonts folders really maps the probe codepoint). Discovery re-opens and re-checks each candidate against the real face, so the index can only skip work, never change an answer. Floor lanes: see the progress log.
- [x] (from T3063, PA-C06) frame time while printing 200 distinct uncovered codepoints, before and after - measured at `CodepointResolver.getIndex` (the call that runs under the grid's exclusive lock): 200 distinct uncovered codepoints 15670.8 ms -> 12.9 ms. Measured through a temporary probe test, with the old `discovery.zig` swapped in for the before figure; the probe was removed afterwards.
- [x] (from T3063, PA-C07) GUI-thread time per ctrl+= zoom step with font-family set, before and after - measured per family discover (`Consolas`): 8.4 ms -> 0.2 ms; a zoom step makes one per style per configured family, so ~34 ms -> ~1 ms of discovery per step with one family (derived from the per-call figure; the step's face loading is unchanged).
- [x] (from T3063) a font installed while the app runs is found after WM_FONTCHANGE - installing or removing a font changes the Fonts folder's last-write time, and the index rebuilds on the next query when either folder's stamp moved; no WM_FONTCHANGE plumbing needed. Unit-tested by adding a font file to an indexed folder. Unchanged by this task: a grid's per-codepoint negative cache still remembers a miss made before the install (that cache dies with the grid).
