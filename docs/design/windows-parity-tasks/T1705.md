# T1705 - An Enter at the end of the web feedback composer puts two line breaks in the pane's text

## Summary

When the caret is at the end of the web composer and the user presses Enter, Chromium's `plaintext-only` box can represent the new, empty last line as a trailing `"\n"` inside the text node (`"hello\n\n"`) instead of a placeholder `<br>`. `walk()` in `src/viewer/composer.js` only recognises the `<br>` form of that placeholder, so the page reports `"hello\n\n"` and the pane's buffer holds one more line break than the user typed.

Evidence (T1702, 2026-09-23, `test\win32\viewer-composer.ps1` section H over the DevTools driver): typing `héllo`, Enter, `world` logged the growth echo `bytes=8 lines=2`. That is `héllo\n\n`, not `héllo\n` (7). After Ctrl+Z the box's `innerHTML` was the plain text `"héllo\n\n"` with no `<br>`.

Fix: in `walk()`, drop a trailing `"\n"` when it is the text-form placeholder. That means the last text node of the box ends in `"\n\n"`, or ends in `"\n"` and the text before it already ends in a break. Mirror the rule in `$script:CdpComposerRead` in `test\win32\lib\WebViewCdp.ps1`. Then tighten section H's Ctrl+Z assertion to the exact `héllo\n`.

Watch out: a document that really does end in a blank line the user typed (two Enters) must still read as one break more than a single Enter. Check that shape with the driver before landing the change.

## Validation criteria

- [ ] viewer-composer.ps1 section H: after `x`, Enter the page reads `x\n`, the reopen echo reports 2 bytes, and Ctrl+Z after further typing reads the exact post-Enter text.
- [ ] Two Enters still read as `x\n\n`.
