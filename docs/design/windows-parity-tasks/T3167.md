# T3167 - +new-remote-window --relay still renews the signed-in relay session token over HTTP on the GUI thread (IpcHandlers resolveAccountToken -> relay_session.renew) when it nears expiry; move token resolution into the T3022 dial worker

## Summary

Found while landing T3022. T3022 moved the `+new-remote-window` DIAL off the GUI
thread, but the relay path's token resolution still runs in the GUI-thread
handler: `IpcHandlers.handleNewRemoteWindow` -> `resolveAccountToken` ->
`relay_account.resolveSessionToken`, which calls `relay_session.renew`
(`src/remote/relay_account.zig` ~:243) — an HTTP round trip to the relay —
when the stored session token nears expiry. A slow or unreachable relay
freezes every window for that request's duration.

Fix: resolve the account tier on the T3022 worker (`IpcHandlers.runRemoteDial`)
instead. The tokenless refusal ("not signed in: ...") must still come back
without any dial, and the token tier order (explicit `--token`, account, env)
must not change; `isSignedIn` is a file check and can stay on the GUI thread to
decide the refusal up front. Same check for the other GUI-thread callers of
`IpcHandlers.resolveToken` (App.zig ~:1245, ~:8389, ~:8609).

## Validation criteria

- [ ] a relay `+new-remote-window` whose account token needs renewal against a relay that stalls leaves `+list` answering in under 1 s (extend ipc-relay.ps1's fake relay with a stalled renew endpoint)
- [ ] the "not signed in" refusal and the tier order are unchanged (ipc-remote.ps1 section 5, ipc-relay.ps1, relay-account.ps1 green)
