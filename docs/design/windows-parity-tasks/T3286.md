# T3286 - activity-help-tooltips.ps1 section C flakes: the ctrl-click meant to add a second row can land on the already-selected row after a %CPU re-sort and toggle it off (1 of 3 runs, 2026-11-20)

## Summary

Seen while validating T1548 on 2026-11-20: one worker run of `test\win32\activity-help-tooltips.ps1` failed `C a ctrl-click adds a second row` and then `C Kill counts two rows (got '<none>')`; the same build passed alone, and a second worker run passed whole (36 assertions). Section C runs with Show all ON, so the table holds the whole box sorted by %CPU descending, and it clicks two fixed client points (`$rowAY`, then `$rowAY + height/12` with MK_CONTROL). A 1.5 s refresh between the two clicks can move the first-selected process under the second point, and a ctrl-click on a selected row toggles it off (selection 0, not 2). The Kill tip then says nothing because nothing is selected. Hypothesis, not proven: the failing run's log did not record the PIDs under each click.

Fix shape: make the second click's target stable - sort by PID first (click the PID header, which `activity-selection.ps1` already finds), or read the PID under the point from the T1548 cell oracle (`activity help tooltip target=name pid=<n>`) and re-click until it names a PID other than the selected one. The test's oracle is otherwise sound.

## Validation criteria

- [ ] `activity-help-tooltips.ps1` passes 5 worker runs in a row through `scripts\acceptance-parallel.ps1 run -Scripts activity-help-tooltips.ps1`.
- [ ] A failing section C names the PIDs under both clicks, so the next red is diagnosable from the log.
