# T2345 - clipboard-paste.ps1 goes red in its own setup: Set-TextClipboard cannot write the clipboard in 10 tries (2s), twice in a row on 2026-10-27, with no process holding it open

## Summary

Found in T2308's due sweep. `clipboard-paste.ps1` fails at line 233,
`Assert (Set-TextClipboard 'ZQTOKEN') 'harness: text clipboard set'`, and then
unwinds, so nothing past it is proven. It failed in the 4-wide sweep
(20261027-075157\18-clipboard-paste.log) and again run alone
(20261027-084829\00-clipboard-paste.log). `GetOpenClipboardWindow()` right after
showed no holder. `Set-TextClipboard` swallows the exception, so the real cause
is not recorded. Possible causes: the script running MTA (WinForms
`Clipboard` needs STA), a clipboard-history or cloud-clipboard listener
racing the write, or a recent harness change. Fix direction: log the
exception text and `[Threading.Thread]::CurrentThread.ApartmentState` on
failure, then fix the cause (fall back to the Win32 Open/EmptyClipboard/
SetClipboardData path if WinForms is the problem). Validation:
clipboard-paste.ps1 ALL PASS twice in a row.

## In plain terms

The test that proves copy and paste work in the terminal sometimes failed
before it tested anything: it could not put its sample text on the clipboard,
and it threw away the reason. It passes again now, and if the clipboard ever
refuses it again, the test says exactly why and who was holding it.

## Goals

- [x] A clipboard setter that gives up names the error, the thread apartment and the clipboard's holder
- [x] clipboard-paste.ps1 green again, twice in a row

## Validation criteria

- [x] The failing Set-TextClipboard records its exception text. All three
  setters (text, image-only, image+text) collect each try's exception and, on
  give-up, print `CLIPBOARD GIVE-UP <setter>: <n> tries, apartment=<STA|MTA>,
  holder=<hwnd pid (name)|none>` plus each distinct error. Demonstrated
  against a real hold: a second powershell holding `OpenClipboard` made
  Set-TextClipboard print `holder=hwnd=0x2070D8E pid=49096 (powershell)` and
  `error: ... "Requested Clipboard operation did not succeed."`, return
  false, then succeed once the holder exited.
- [x] clipboard-paste.ps1 ALL PASS, twice in a row - three times on
  2026-11-26 through `acceptance-parallel.ps1 run` (once before the edit, twice
  after; 53 assertions each, logs 20261126-073524/-073824/-073919). Scoped
  harness floor PASS (240s).

## Outcome

The 2026-10-27 red does not reproduce a month later, so no root cause could
be observed; the MTA theory was already ruled out by the script's up-front STA
check. Rather than add an unproven Win32 fallback, the change makes the next
occurrence diagnosable in one read. If it recurs, the GIVE-UP line names the
holder and the exception - file a new task from that line.
