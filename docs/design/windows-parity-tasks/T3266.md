# T3266 - The site-mirror check compares only index.html, so the mirror's landing/ assets went stale for three weeks unnoticed

## Summary

Found closing T1513. `dist/website/site-mirror.py check` (and section F8 of
`test\win32\website-windows-download.ps1`) compares only
`relay/deploy/ghpages/index.html` against origin/gh-pages. The mirror also
tracks `relay/deploy/ghpages/landing/main.js` and `landing/styles.css`, and
both had been stale since the 2026-10-29 site rebuild (75a845108 on
gh-pages) without any check saying so; T1513 refreshed them by hand. The
mirror also does not hold the rebuilt page's images (`landing/shots/*.webp`,
`favicon-64.png`, `icon-256.webp`), so it cannot render the page it mirrors.

Fix: decide the mirror's scope (my call, mechanism only): either extend
`check`/`sync` to every tracked file under `relay/deploy/ghpages/` (blob-hash
compare against the same path on gh-pages, so a stale asset is MIRROR DRIFT),
or stop tracking the landing copies. Recommended: extend the check to the
tracked text assets, since `publish` already deploys from this tree.

## Validation criteria

- [ ] `site-mirror.py check` reports drift when a tracked `landing/` file differs from gh-pages (negative control: edit the mirror's styles.css, see red).
- [ ] `test\win32\website-windows-download.ps1` ALL PASS with a row covering the asset compare.
