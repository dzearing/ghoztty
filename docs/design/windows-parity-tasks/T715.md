# T715 - Windows exposes no assistive-tech attribute for a remote window's link state (Mac's AXGhosttyLinkState)

## In plain terms

A script that wants to know whether one of your windows has lost its connection
to the other machine should not have to read the screen. On the Mac it asks the
accessibility system. On Windows it asks `ghoztty +list --json`, and the answer
has been there since T609 — this card was filed by a sweep that went looking for
the Mac's name for the feature rather than for the feature. What was missing was
the check that the answer stays right for ORDINARY windows: nothing proved that
a plain local window keeps quiet instead of reporting itself as a dead remote.

## Summary

Mac publishes AXGhosttyLinkState on terminal windows (97530c9ac) so external
tools can read whether a remote window is connected/reconnecting/disconnected
without parsing the title, the same contract AXWindowActivityState has for
activity. win32 tracks the state (connection.LinkState, the T367 pill) but
publishes nothing to UI Automation. Found by the T684 sweep.

## Resolution: already delivered, by T609 (777af5f23)

Re-verified against the code before building (go.md step 1, CHECK FIRST), and
the capability this card asks for is present on Windows in the channel
automation here actually uses:

- `+list --json` carries a per-window `connection` object —
  `state: connected | reconnecting | disconnected`, plus `attempt`,
  `self_healable` and `reason` — sourced from the same reconnect ladder the pill
  paints (`WindowState.listConnection`, `src/apprt/win32/remote_reconnect.zig`).
- It is **absent** for a local window, which is this platform's spelling of the
  literal `"local"` Mac publishes.
- `windows-parity-spec.md` already declares the whole AX attribute family
  Mac-only and out of scope; the mechanism is what is out of scope, not the
  capability, and that file now carries the attribute → Windows-counterpart
  table so the next symbol sweep maps these instead of re-filing them.

So the deliverable here is the validation the card was owed, not a second
implementation. The serializer half was already unit-tested (`list.zig`,
"connection is additive and absent for a local window"); the PRODUCER half —
`if (window.hasRemotePill())` in `handleList` — had no end-to-end coverage at
all, and a regression there would tell every automation tool that the user's
ordinary local windows are disconnected remote ones.

The one row of the table with nothing behind it is the machine NAME
(`AXGhosttyMachine`), now filed as **T1557**.

## Goals

- [x] A script can read a window's link state on Windows without parsing the
      title or screenshotting the pill
- [x] A local window is distinguishable from a remote one, and the distinction
      is pinned by a test against a live window
- [x] The Mac attribute names map to their Windows counterparts in the spec, so
      the sweep that filed this cannot re-file it
- [x] The genuinely-missing half (the machine name) is filed rather than lost

## Validation criteria

- [x] `+list --json` reports the reconnect ladder's state for a cross-machine
      window — covered end-to-end by `test\win32\remote-reconnect-relay.ps1`,
      which polls the `connection` object through a real drop and recovery
- [x] A live LOCAL window publishes no `connection` object — new assertion in
      `test\win32\ipc-p1.ps1` §5, against a real running debug build
- [x] The serialized shape is additive and omits the field entirely for a local
      window — `zig build test -Dapp-runtime=none` ("List: connection is
      additive and absent for a local window (T609)")
- [x] The P1-P3 acceptance floor and all four zig lanes stay green
