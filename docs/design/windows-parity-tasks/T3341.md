# T3341 - Linux L12: secret store on libsecret with a 0600-file fallback, and relay sign-in

## Summary

Keychain -> DPAPI -> libsecret (Secret Service). WSL usually has no keyring daemon, so fall back to a 0600 file under $XDG_DATA_HOME and say so in the UI. Then relay sign-in per docs/claude/remote.md.

**Scope as landed (2026-11-23):** the store and the sign-in flow core. The UI
half - the chooser's account row, where "say so" and the Sign in button live -
needs the GTK chooser (T3563), which does not exist yet, so it moved to
**T3575** (deps T3563). `relay_signin.signIn`/`signOut` are shared code that
already builds and unit-tests on Linux (browser via `xdg-open`); T3575 calls
them from the row.

## In plain terms

When you sign in to your Google account for remote machines, the app has to
keep that sign-in somewhere safe. On a Mac that is the Keychain and on Windows
it is encrypted for your user. On Linux it now goes into the system keyring
when one is running, and when there is none - the normal case in WSL - into a
file only your user can read. The app can tell which, so the sign-in screen
can say so.

## Goals

- [x] Linux keeps the relay account in the Secret Service when a keyring daemon answers
- [x] With no keyring (WSL default) it falls back to a 0600 file under `$XDG_DATA_HOME/ghoztty/`
- [x] The store can say which one holds the sign-in (`relay_account.location`), for the UI
- [x] Debug and release sign-ins stay separate in the keyring too (T1859)
- [x] Unit tests can never touch the person's real keyring
- [ ] The chooser's account row signs in/out and says "private file" - moved to T3575
