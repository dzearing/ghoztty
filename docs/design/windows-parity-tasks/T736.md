# T736 - src/build/wasm_patch_growable_table.zig's tests run in no build step

## In plain terms

There is a file of checks in the build tooling that nobody ever runs. It looks
like it is tested - the checks are written and sitting right next to the code -
but no part of `zig build test` reaches them, so if that code broke tomorrow
every lane would stay green. Wiring them in is a few lines now that there is a
place to wire them into.

## Summary

Found while landing **T243**. The main test binary roots at `src/main.zig` and
therefore reaches **none** of `src/build/`, so a `test` block written next to a
build helper runs in no step at all. T243 added
`src/build/build_test.zig`, an aggregator wired into `test_step` for exactly
this, and put `drive_check.zig` behind it.

`src/build/wasm_patch_growable_table.zig` is still orphaned. Orphaned
assertions are worse than no assertions: they read as coverage in review and
cannot fail.

**Evidence refreshed at HEAD 2026-09-09 (T676 sweep).** When this was filed,
that file was the *one* other file under `src/build/` with `test` blocks.
Today `grep -rln '^test "' src/build/` finds **three** — `drive_check.zig`,
`TestFilterGuard.zig` and `wasm_patch_growable_table.zig`. `TestFilterGuard.zig`
landed after filing and was wired into the aggregator correctly
(`src/build/build_test.zig:13`), so the gap did not widen; but the aggregator
was *remembered* that time rather than enforced, which is the argument for the
sweep the last paragraph below floats.

The likely one-liner is adding `_ = @import("wasm_patch_growable_table.zig");`
to the aggregator. What needs checking first is whether it compiles under the
aggregator's module root and target (`config.baselineTarget()`) - it patches
wasm binaries, so it may pull in imports or assume a wasm target, in which case
it needs its own test artifact rather than a line in the aggregator.

While in there, consider whether the aggregator should be *enforced* rather
than remembered - a sweep that fails when a `src/build/*.zig` carries a `test`
block no step imports would stop the next one rotting the same way. That is the
same shape as the `ExitCodeAudit` / `SkipAudit` / `VerdictExitAudit` analyzers
already in `test\win32\lib\`.

## Validation criteria

- [ ] `zig build test -Dapp-runtime=none --summary all` shows the
      `wasm_patch_growable_table` assertions running (a test count that grows by
      its block count), on both lanes
- [ ] Deliberately breaking one of its assertions turns the lane red (teeth
      check), and reverting it turns it green again
- [ ] No `src/build/*.zig` is left carrying a `test` block that no step
      imports - either wired in, or the gap is named with a reason
