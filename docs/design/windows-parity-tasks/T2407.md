# T2407 - The collapsed Windows pane sidebar rail's + opens a new window (the panel header's +), not a pane in this window (Mac 7e2d0a9da)

## Summary

Mac main 7e2d0a9da: in the rail the header is a + alone (under the expand button) and that + is the panel header's new-window + (exactly Ctrl+Shift+N / Cmd-N), the topmost + in the rail where the panel's new-window + sits when expanded. On Mac clicking it added a pane to this window instead (theRailsPlusOpensAWindow). Windows: check what the rail's topmost + does (T2323/T2324 added the + buttons); make it open a new window and add an acceptance check. Ref docs/reference/pane-sidebar.md on main ('Header +').

## Validation criteria

- [x] In Panes the rail's + adds a pane in this window (T2324 behavior kept) - test\win32\pane-sidebar-this-window.ps1 section 1, ALL PASS 53.
- [x] In All Windows the rail opens with a + above every window, in a window header's slot - unit test `T2407: all windows' rail opens with a + ...` (pane_sidebar.zig) and 7b of test\win32\pane-sidebar-all-windows.ps1.
- [x] Clicking it opens a new window (4 windows logged), not a pane - 7b, ALL PASS 114.
- [x] Its tooltip says New window there, New pane in Panes - `railAdd` unit test (pane_sidebar_add.zig).

## In plain terms

With the sidebar collapsed to its thin rail, the topmost + now does what the list beside it suggests: showing this window's panes, it adds a pane; showing all windows, it opens a new window. Before, the all-windows rail had no + at all.

## Update from the 2026-10-28 evening intake (Mac 6bd2962eb)

Mac refined this the same day: the rail's + now follows the sidebar's scope - in **Panes** mode it adds a pane to this window, in **All Windows** mode it opens a new window. Build to that rule rather than "always a new window".
