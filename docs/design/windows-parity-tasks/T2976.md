# T2976 - PA-R10: closing 10 panes leaves about 50 MB of GPU memory behind (107 MB vs 57.6 MB at start); find the carrier (parked pane windows, per-HWND DComp target or driver cache) and trim it

## Summary

PA-R10 (audit-1, T2959; cause unverified). baseline-1: closed.gpu_dedicated_mb 107.4 vs 57.6 at start, second_cycle_gpu_dedicated_mb 0, so a bounded plateau, not a growing leak. 49.8 MB over 9 closed panes is ~5.5 MB each, close to one 1400x900 BGRA surface. Suspect: pane_pool.zig:28 (capacity 16) parks closed pane HWNDs (Surface.zig:1554-1555) and only window destroy drains it (Window.zig:423-427); but the pool's rationale is SwapBuffers residue and composition panes never SwapBuffers, so the carrier may be the per-HWND topmost DComp target (gl_comp_present.zig:597) or driver caching. Teardown itself is complete (OpenGL.zig:517-521 -> gl_comp_present.zig:875-919). Step 1: A/B GHOZTTY_PANE_REUSE=0, GHOZTTY_COMP_PANE_TREE=1, GHOZTTY_PANE_GL_HELPER=0 with perf-baseline.ps1 -Phase cycle. Step 2: if it follows the HWND, add an idle trim that destroys parked windows after N seconds through reapSurfaceHwnd (T681); if it follows the HWND target, tree mode removes it. Also, private_mb retains ~830 MB after the first cycle (the memory auditor's area, T2961) - cross-reference.

## In plain terms

After you open a lot of panes and close them again, Ghoztty keeps showing about
50 MB more graphics memory than it started with. This task found out who is
holding it: the graphics driver (NVIDIA's OpenGL driver on this box), which
keeps the freed memory and hands it back when you open panes again, so it
never grows past what your busiest moment needed. Nothing in Ghoztty is left
alive, and no switch on our side gives it back.

task), GPU dedicated MB as start / open 1 / closed 1 / open 2 / closed 2:

| run | dedicated MB | residue |

| HEAD, defaults (mixed: 10 panes, 3 tabs) | 57.6 / 189.6 / 107.3 / 209.0 / 107.3 | +49.7 |
| `GHOZTTY_PANE_REUSE=0` (no parked windows) | 57.6 / 189.5 / 107.2 / 208.9 / 107.2 | +49.6 |
| `GHOZTTY_COMP_PANE_TREE=1` (no per-HWND DComp target) | 57.6 / 189.5 / 107.2 / 189.4 / 107.2 | +49.6 |

| `-CycleShape one` (2 panes) | 57.6 / 70.8 / 63.1 / 70.8 / 63.1 | +5.5 |
| `GHOZTTY_COMP_PRESENT=0` (plain WGL, no D3D/DComp at all) | 42.2 / 153.2 / 91.9 / 158.7 / 91.9 | +49.7 |

What that says:

- **None of the card's suspects carry it.** Parked pane windows, the per-HWND
  DComp target and the D3D11 device's deferred destruction / driver trim all
  leave it at 107 MB. Audit-1 saw the same 107.4 MB with per-pane D3D devices,
  so the shared device (T2968) is not it either.
- **It is on the OpenGL side.** With composition off entirely - no D3D11, no
  DXGI, no DComp - the residue is the same 49.7 MB.
- **It is a high-water mark, ~5.5 MB per pane at the PEAK.** 2 panes leave
  5.5 MB, 10 leave 50 whether they were tabs or splits, and the second cycle
  adds 0.0 in every run: the freed memory is reused, so it cannot be live
  objects of ours (those would add another 50 MB per cycle).
- **Every pane's GL context is deleted on close** (`Surface.zig:1409-1415`,
  `wglMakeCurrent(null)` then `wglDeleteContext`) and pane contexts are in no
  share group (the window presenter is off by default), so nothing of ours
  keeps the objects alive.

So the carrier is the GL driver's own per-process allocation pool, which keeps
freed video memory for reuse and never returns it; there is no WGL/GL call that
asks it to. The second validation criterion is therefore not reachable by a
trim, and is recorded as such below rather than met. The lever that remains is
the per-pane GL allocation itself (the pool is sized by peak panes x per-pane
cost), filed as T3110.
