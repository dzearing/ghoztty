# T1999 - Remote panes correct their resume offset in +16/-16 pairs 9ms apart: the counted and stream positions drift and snap back on a busy pane

## Summary

Found while measuring T1956: ghoztty.log carried 313 pairs of 'resume offset corrected: counted=X stream=X-16 (delta 16)' followed ~9ms later by '(delta -16)'. adoptStreamPos's comment calls a correction rare and names only repaint/scrollback-lost injection as the cause; a symmetric 16-byte pair on a live pane says the stream-position anchor and the parsed-byte count are briefly out of step (a 16-byte frame counted before its anchor arrives, or vice versa). Find which 16 bytes, decide whether a resume taken inside the window would replay or drop them, and fix the ordering. T1956 now logs only the 1st/2nd/4th/8th... correction per pane at info with n=, so the evidence is still there.

## In plain terms

A remote or persisted pane keeps a bookmark of how much of the session's
output it has shown, so a restore can resume exactly where it left off. On a
busy pane that bookmark briefly fell a few bytes behind, then jumped back. If
the app saved the session at that moment, the restore would show those few
bytes twice. After this fix the bookmark only moves when it is exact.

## Goals

- [x] Name the 16 bytes and the ordering that produces the +16/-16 pair
- [x] Decide what a resume taken inside the window does (replays the bytes twice; never drops them)
- [x] Fix the ordering so the pane never adopts a position behind what it parsed

## Root cause

The data reader routes a frame in two steps: push the bytes into the pane's
ring, then (only once it knows how many the ring accepted) publish the
frame's stream position. The pane's IO thread could pop and parse the frame,
pop again empty, and adopt the position published BEFORE that frame -
`counted=X stream=X-16 (delta 16)`. The next frame's adoption ~9 ms later
re-corrected by -16. The 16 bytes are simply whatever the last frame of a
burst was (a 16-byte frame is common for cursor/sync-output sequences).
During the window `applied_bytes` sat one frame short, so a manifest written
then would resume 16 bytes early: duplicated output, the safe direction.

Fix: `Pane.route_inflight` counts frames between push and publish
(`beginRoute` under the panes lock before the push, `finishRoute` with the
position). `drainRing` reads `streamSnapshot()` before its pop and adopts
only when it was settled; otherwise `requestAdoptWake()` asks `finishRoute`
to wake the consumer on the publish (or retries at once if it already
happened), so a pane that goes idle after a repaint still adopts.
