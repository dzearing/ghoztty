# T1211 - Nothing watches the stale-build balloon actually appear

## In plain terms

When a newer Ghoztty is installed while you have one open, the app now pops a
notification saying so and offering to restart. Every part of that is tested
except the notification itself: no test has ever seen the balloon appear or
clicked it. If the tray plumbing broke, the tests would stay green and the
user would simply never be told.

## What is and is not covered today (from T1205)

Covered:

- **Whether to notify** — `image_freshness.zig`, unit-tested in every lane
  (started-vs-written, the tolerance edge, unknown timestamps).
- **What a click MEANS** — `tray_notify.classify`, unit-tested, including the
  case that matters most here: a balloon that merely TIMES OUT must not
  restart the user's terminal.
- **The sentence** — `test\win32\ipc-version.ps1` section 2b renames the
  running image aside, puts a fresh file at its path, and asserts `+version`
  says a newer build is installed and names the remedy.

Not covered:

- The `Shell_NotifyIconW` call, its `NIM_SETVERSION` registration, the
  one-per-build dedupe, and the 60-second timer that drives them.
- The About box's "Restart Now / Later" branch.
- `App.restartIntoInstalledBuild` — the spawn-then-quit ordering that must
  leave the terminal alive if the spawn fails.

The obstacle is the harness's own isolation: acceptance scripts run on a
BACKGROUND Win32 desktop (`test\win32\lib\TestDesktop.ps1`) so they never take
the user's foreground, and the notification area does not exist there. T448
hit exactly this for the desktop-notification balloon.

## Possible shapes

- Assert the SIDE EFFECTS instead of the pixels: drive the timer's work
  directly and assert the log line, plus the dedupe (a second tick with the
  same file must not re-notify, a newer file must).
- Cover the About branch through the palette, the way section 3 of
  `ipc-version.ps1` already opens the About box: with a newer file staged, the
  dialog must carry the Restart/Later buttons rather than a bare OK.
- Cover `restartIntoInstalledBuild`'s refusal path (spawn fails -> app keeps
  running), which is the half that can cost the user their terminal and needs
  no tray at all.

## Goals

- [x] Watch the app decide to tell the user about a newer build, and not repeat itself
- [x] Prove the About box turns into the restart offer when a newer build is on disk
- [x] Prove a restart that cannot happen leaves the terminal open and says so

## Validation criteria

- [x] A harness observes the app DECIDING to notify about a newer build on
      disk, not merely the text a CLI would print. (`test/win32/stale-build-notify.ps1`
      S1/S2: three ticks over the launch file decide nothing; a renamed-aside
      image plus a fresh file decides once and logs the shell's answer.)
- [x] The dedupe is asserted: the same on-disk build notifies once, a newer
      one notifies again. (S3: three more ticks, still one; S4: a re-stamped
      file notifies a second time, once.)
- [x] The About box's stale branch is asserted to offer a restart. (S5: its
      buttons are exactly "Restart Now | Later", no bare OK; Later is logged
      and attempts nothing.)
- [x] A failed relaunch leaves the app running, asserted rather than assumed.
      (S6: the relaunch guard's marker path is a directory in a private
      LOCALAPPDATA, so arming fails for real; the app logs NOT quitting, asks
      for the fallback balloon, and the process and window are still there.)
- [x] The harness can fail: `-NegativeControl` (no newer file) scores 10
      failures across S2-S6.

## Notes

- App changes are observability only: a Debug-only cadence seam
  (`GHOZTTY_STALE_BUILD_CHECK_MS`, both first fire and repeat), a debug tick
  line, and log lines for the balloon's outcome, the About choice, and the
  restart fallback. Behaviour for a user is unchanged.
- The app runs from a COPY of `zig-out/bin` under the run's temp dir, so the
  rename-aside never touches the build output.
- The SUCCESSFUL restart is not exercised here on purpose: the relaunch would
  land on the user's desktop. `app-restart.ps1` owns that path.
