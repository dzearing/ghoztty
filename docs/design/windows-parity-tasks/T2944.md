# T2944 - A timing-sensitive perf capture is not protected from the other loop lane's compiles: the timing lock keeps lane B's timing scripts out but not its zig builds, so a 4K drag-glide run under lane B's build read 55 frames over 16.7 ms (max 68.7 ms) against 0-2 on a quiet box

## Summary

Found in T2943 (2026-11-12 23:41): run a5 of a 6-run 4K drag-glide series on win-v1.54.16 had other-process CPU up to 46% (zig.exe compiles from lane B, T2938) and 55 ticks over 16.7 ms (p99 32.9, max 68.7) while the runs around it had 0-2. scripts\lib\MachineLock.ps1's header says the other lane's compile makes a timing measurement read wrong, but only scripts carrying # @timing-sensitive take Global\GhozttyTimingTest, so a build never waits for a timing script and a timing script never knows a build is running. Fix: either have zig builds launched by the loop (floor-lane, acceptance-parallel's rebuild, build scripts) take the timing lock as a shared/reader, or have the timing harness sample other-process CPU during its run and report the run as ASSERTED NOTHING / CONTAMINATED when it exceeds a threshold (the T2943 scratch runner sampled Get-Process CPU every 500 ms; a5 averaged 14.6% vs 5-10% quiet). Acceptance: test\win32\machine-lock.ps1 gains a section that runs a CPU burner beside a timing script and proves the verdict changes.
