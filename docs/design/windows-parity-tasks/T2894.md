# T2894 - Tab-strip and caption live-update claims (pressed caption button, tab color, new tab, title change) are scored by a capture that repaints them - measure each against its deleted invalidate with the window paint probe

## Summary

Found by T1407's survey. Each of these captures the top-level `GhozttyWindow`
chrome after a state change, and the capture (`-Sync` = `WM_PRINTCLIENT`) draws
the new state itself, so none of them can fail if the invalidate is deleted:

- `caption-bar.ps1:389` pressed fill and `:~442` release, `close-glyph-white.ps1:140`
  (`handleNcLButtonDown`/`Up` -> `invalidateCaption`, `Window.zig`)
- `tab-color.ps1` stripe after Tab Color > Red (`invalidateTabBar`)
- `tab-strip.ps1:441/723/668/1192/1352`, `menu-bar.ps1:718` (`addTab`,
  `onPaneTitleChanged` -> `invalidateTabBar`)
- `title-jitter.ps1:330/343` tab chiclet width on a title change
- `remote-pill.ps1:260/264` - `refreshRemotePill` invalidates only when the pill
  WIDTH changed, so a same-width state change may genuinely never repaint
- `hover-capture.ps1:300` mouse-leave unlatches (`handleTabBarMouseLeave`)

The `.window` paint-probe surface already exists (`paint_probe.zig`); it is
quiet outside hero mode (the 150ms carousel timer is the known exception).
For each claim: build with its invalidate deleted, run, record survives/red;
for each survivor add a chrome-theme-G-style count assertion (quiet interval,
then the change, no capture between) and RUN it red against the deletion.
The remote pill's conditional invalidate is the likeliest real bug - measure
it first. T1407's viewer card was exactly that shape: hollow test, real bug.

## Validation criteria

- [ ] Each listed claim marked survives-deletion / goes-red, with the build that showed it.
- [ ] Every survivor gains a probe assertion RUN red against the deletion, or is re-labelled to what it really measures.
- [ ] Touched harnesses green afterwards; guard-due rows cover any probe surface they depend on.
