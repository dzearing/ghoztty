# T2372 - Extend the T2365 frame-clock oracle to the glides themselves: drive a stack glide, hero slide, banner collapse and sidebar column glide in test\win32\frame-clock.ps1, record each one's per-tick cost (frame clock id=0x534C/0x4841/...), and make the stack glide tick a live relayout (layoutSplitsLive) if its cost overruns the frame

## Summary

T2365 put every Windows animation on one vsync frame clock and proved the
clock with a do-nothing probe and the focus glow (`test\win32\frame-clock.ps1`).
It did not drive the glides the user actually complained about: the stack
glide's harnesses cannot form a stack right now (T2355), and the hero, banner
and sidebar column glides were not scripted. Each one reports a
`frame clock id=0x...` line under GHOZTTY_PERF already, so this is harness
work plus whatever the numbers show.

Two open questions to answer with numbers:

- Per-tick cost. If a glide's tick does not fit in one frame (8.3 ms at the
  user's 120 Hz), the clock alone cannot make it smooth: make the stack glide
  tick a live relayout (`layoutSplitsLive`, as T2359 did for the sidebar drag),
  and if that still overruns, T2360 (compositor animations) is the fix.
- Refresh rate. T2365's runs on the hidden test desktop measured a 16.4 ms
  compositor period (60 Hz), but the user's panel is 120 Hz
  (`DwmGetCompositionTimingInfo`). Confirm on the input desktop (or with
  T2373's frame lab) that `DCompositionWaitForCompositorClock` ticks at 8.3 ms
  there; if it does not, the clock needs to wait on the right output.

## Validation criteria

- [ ] `frame-clock.ps1` drives a stack glide, hero slide, banner collapse and sidebar column glide, and reports each one's skipped-frame share and per-tick cost.
- [ ] Every glide's mean tick cost fits in a frame at the panel's rate, or the one that does not has a fix landed or filed.
- [ ] The frame clock's period on the user's 120 Hz panel is measured, not assumed: ~8.3 ms, or a task filed to make it so.
