# T2941 - The tick a pane folds into its strip costs 16.8-19.5 ms (one per drag round): EndDeferWindowPos of the 4 moved panes takes up to 8.7 ms and the desk is composed whole (4.2-5 ms) in the same tick, so a 60 Hz display drops a frame on every fold

## Summary

Split from T2732's 2026-11-12 re-measure (release sandbox, 120 Hz, T2732 glide probe, 3 runs): every run has exactly one tick over 16.7 ms (19.5 / 17.8 / 16.8 ms) and it is the fold's first tick (waits=1, resizes=2, 'plan runs' with a card going strip=true into=true, moved=4). Run 1: batch EndDeferWindowPos 8.67 ms (qpc batch->defer_end), whole desk compose 4.98 ms (vacated ready->composed, hit=false), paint 2.8 ms; run 3: defer 8.2 ms + compose 4.2 ms; run 2: defer 1.7 ms but compose 4.2 ms + a frame wait. T2866 (viewer window move) and T2845 (DComp target) are closed, so the 8.7 ms batch on this tick is unowned. This is T2732's remaining 60 Hz criterion (late=0 at 60 Hz on three runs): owns it from here. Levers: the whole compose at the fold's first frame (T2732 goal 1 stopped it at fold start/end for cards coming and going; this re-lay still composes whole since the dirty area is >3/4), and what the 4-pane move's EndDeferWindowPos waits on.

## In plain terms

When you drag a divider far enough that a pane folds away into its strip,
the moment it folds used to take longer than one screen refresh on a big
(4K) window, so the motion visibly hitched once per fold. The app was
redrawing the whole background behind the panes for that one frame, when only
the thin bands round the moved edges had actually changed. It now redraws only
those bands, and the fold frame fits inside a 60 Hz refresh.
