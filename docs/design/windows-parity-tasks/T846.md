# T846 - Nothing runs the test suite at ReleaseSafe, so build-mode-only defects reappear silently

## Summary

Every lane in the floor — `none`, `win32`, `agent` — builds the tests at
**Debug**. `-Dtest-optimize=ReleaseSafe` exists (T473 added the knob) but
nothing runs it, so a defect that only Debug masks lives in the tree
indefinitely.

T477 is the proof that this is not hypothetical. Two real defects were sitting
in the tree at once, both invisible to 26 consecutive green Debug runs:

- `free()` on an `undefined` slice in `src/renderer/cell.zig` — UB that
  ReleaseSafe compiles to an `int 3`, and which the *shipping* renderer also
  executes on its first `resize()`.
- A test returning a pointer into a dead stack frame in
  `src/apprt/win32/App.zig` — Debug left the memory intact, ReleaseSafe reused
  it and segfaulted 10/10.

Both are the same class: code whose correctness Debug's allocation and frame
behavior accidentally provides. The suite is clean at ReleaseSafe as of T477,
so this is the cheap moment to nail that down — a clean baseline is what makes
a future red run mean something.

## In plain terms

Our tests are only ever compiled one way. Two genuine bugs — one of them in
code that ships to users — hid behind that for weeks, because the way we
compile tests happens to paper over them. Running the same tests compiled the
way real builds are compiled catches that class of bug, and right now nothing
does.

## Goals

- [x] The ReleaseSafe test binary gets built and run somewhere that fails
      loudly — a `floor-lane.ps1` lane, or a scheduled/periodic sweep
- [x] Decide and record whether it belongs in the per-turn floor (it costs a
      full extra build plus ~85s a run) or on a slower cadence
- [x] A red ReleaseSafe run names the victim test, as `test-binary-soak.ps1`
      already does

## What landed

`scripts\floor-lane.ps1` gained two lanes and a group:

```
powershell -NoProfile -File scripts\floor-lane.ps1 -Lane releasesafe
powershell -NoProfile -File scripts\floor-lane.ps1 -Lane win32-releasesafe -Seed 0xa1f74462
powershell -NoProfile -File scripts\floor-lane.ps1 -Lane releasesafe -DryRun
```

- `none-releasesafe` / `win32-releasesafe` are the `none` and `win32` test
  lanes with `-Dtest-optimize=ReleaseSafe`; `releasesafe` runs the pair. They
  get the whole existing wrapper — the watchdog, the cache heal, the compiler
  crash retry, the leak sweep, the solo confirm, and the failure-detail block
  that names the victim test — because they are ordinary lanes, not a new
  runner.
- Every ReleaseSafe run carries a `--seed`, random per run and printed on the
  `LANE ...` line, and `-Seed` replays one. This is not decoration: the first
  red these lanes produced was green on the very next unfiltered run of the same
  code, and the only thing separating them was a seed nobody had recorded.
- `-DryRun` prints the command each selected lane would run and exits, which is
  what makes the lane set assertable in seconds instead of forty minutes.

**Cadence decision: a sweep, not a per-turn gate**, and the idle soak daemon is
where it stands. Measured on this box 2026-09-18, from a cold optimize-mode
cache: `none-releasesafe` 545s, `win32-releasesafe` 695s (193s and 684s when
that cache is warm), against ~3m for the whole Debug floor. A separate optimize
mode is a separate cache, so a turn that touches `src/` pays most of that again
— too much for every turn, and exactly what idle time is for. So
`scripts\soak-daemon.ps1`'s DEFAULT rotation is now
`agent,none,none-releasesafe,win32-releasesafe`: the installed tick task passes
no `-Lanes`, so the default IS the standing cadence. A soak round draws its own
seed and the ledger keeps it, so a red round is replayable as
`floor-lane.ps1 -Lane <lane> -Seed <seed>`.

Acceptance: `test\win32\floor-lane-releasesafe.ps1` (16 assertions, guard row
`lane-releasesafe`, which covers `scripts\floor-lane.ps1` and
`scripts\soak-daemon.ps1` — so a lane that silently loses
`-Dtest-optimize=ReleaseSafe`, or stops naming its seed, is DUE and fails
`validate`).

## Details

- Build knob: `zig build -Dapp-runtime=win32 -Demit-test-exe
  -Dtest-optimize=ReleaseSafe --prefix zig-out-t473\win32-releasesafe`.
- Runner: `scripts\test-binary-soak.ps1 -Exe … -Runs N` already reports
  `pass/fail/crash` and names the victim test on a crash.
- Note the diagnostic gap this class has: these crashes take an `int 3` with
  **no stderr message**, and `crash-catch.ps1` reports them as a clean run
  (T478). A lane that only checks for output would call a crash a pass; gate on
  the exit code (`0x80000003` → exit 3), which is what `test-binary-soak.ps1`
  does.

- [x] The T477 revert was tried as the negative control and no longer
      reproduces: with `Contents.bg_cells` put back to `= undefined`, the
      ReleaseSafe binary runs the `Contents with zero-sized screen` test clean

      in August, so that revert proves nothing today — hence the real red above
      as the demonstration instead. Recorded rather than quietly dropped.
- [x] The floor's wall-clock cost is measured and recorded (see **What
      landed**): 545s / 695s cold, 193s / 684s warm, against ~3m for the whole
      Debug floor. The cadence decision is made on those numbers.
- [x] The lane set itself is guarded: `test\win32\floor-lane-releasesafe.ps1`,
      ALL PASS (16 assertions), and shown to be able to fail — deleting
      `-Dtest-optimize=ReleaseSafe` from one lane scores `1 FAILURE(S)` and
      exits 1.
