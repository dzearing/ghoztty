# T2954 - Under GHOZTTY_COMP_CHROME a 4K fold-glide tick spends 33-42 ms of UI-thread CPU placing the overlays and clearing the vacated strips, so ~90% of its ticks run over 16.7 ms (default path: ~1.7 ms)

## Summary

Found by T2953's placement laps (`stack trace place`, `GHOZTTY_STACK_TRACE=ring`). In an interleaved A/B (`temp\t2953-ab2A.txt`, 6 x 4K ReleaseFast drag-glide runs of `temp\t2953-rel` with `GHOZTTY_COMP_CHROME=1`, release sandbox), 1981 of 2144 laid ticks ran over 16.7 ms: mean tick 30.8 ms against 5.1 ms on the default path, and place_us 28.6 ms against 4.5 ms. The `clear` phase (`placeOverlaysBeforeBands` + `clearVacatedPaneStrips`, Window.zig layout pass) is 33-42 ms of wall with cpu ~= wall (e.g. `clear=41015/39256`), so it is UI-thread work, not a wait. On the default path the same phase is ~1.7 ms. `faces` is also ~4-5 ms there (default ~0.5).

Next: split `clear` into the overlay placement and the vacated-strip fill with the same `stall_probe.placeLap` shape, find which call is CPU-bound under the chrome host (a GDI fill or region op that now runs through the composition chrome, or a per-overlay commit), and remove it.

## In plain terms

An experimental drawing mode for the window frame makes dragging a divider on a 4K screen run at about 30 frames a second instead of 60, because the app does about 35 ms of work per frame tidying up after the moved panes. It is off by default, so nobody sees it today, but it is the mode a planned fix depends on.

## Validation criteria

- [ ] The CPU-bound call inside `clear` under `GHOZTTY_COMP_CHROME=1` is named (wall/cpu per sub-phase).
- [ ] After a fix, a 6+ run 4K release soak under `GHOZTTY_COMP_CHROME=1` has its `clear` phase within 2x of the default path's, measured with `temp\t2953-place.ps1`.
