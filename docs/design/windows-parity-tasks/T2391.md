# T2391 - Frame lab trigger drivers (T2389 split): drive maximize-button, blade collapse/expand glide, banner toggle, hero, tab switch and split/close through IPC or keys with the trigger time stamped on QPC beside the capture, so FrameLabCatalogue's trigger interactions stop reading Blocked

## Summary

Split out of T2389 (2026-10-28). `test\win32\lib\FrameLabCatalogue.ps1`
lists six interactions as `trigger` with `Driver = 'T2391'`, and every matrix
cell of theirs reads `Blocked: no driver yet (T2391)`: maximize-button,
blade-glide (sidebar collapse/expand), banner, hero, tab-switch, split-close.
They are not pointer gestures (or not only), so the input driver cannot play
them.

Build, per trigger: the action that fires it (an IPC verb - `+set-banner`,
`+split`, `+close` - or a key chord through the same SendInput path as
FrameLabInput, or a click on the maximize button located from the chrome's
own geometry), its fire time stamped on QPC beside FrameCapture's frame
slots, and what is tracked (blade-glide: the sidebar edge against the glide's
ease curve - FrameScore's `-Expected`; banner: the pane top; the rest: bleed
only). Then flip `Kind` to something the matrix runs, drop the Blocked
reason, and extend `test\win32\frame-lab-catalogue.ps1` with fake-driver
proofs for each trigger.

## In plain terms

The frame lab that hunts for flicker and stutter could only test things you do
with a mouse drag. Six things the user does with a click, a key or a command -
maximizing, collapsing the sidebar, showing a banner, hero mode, switching tabs,
opening and closing a split - were on its list but marked "can't run yet". Now
each has a scripted way to fire it, with the exact moment it fired recorded on
the same clock as the captured frames, so the lab can test them too and judge
the sidebar's glide against the curve the app is meant to follow.

## Goals

- [x] A plan per trigger, built from the scene's geometry (`Get-FrameLabTrigger`, `test\win32\lib\FrameLabTrigger.ps1`)

## Design notes

- **Fire time.** A click or chord fires when `SendInput` returns (the input is
  queued); an IPC verb fires at its START, because the app can act before the
  CLI process exits - Done-Start is kept as `FireSpreadUs` so a slow CLI is
  visible rather than folded into "app lag".
- **Out and back.** Every trigger is two steps (maximize/restore, collapse/
  expand, banner on/clear, hero in/out, next/previous tab, split/close), so
  the scene ends where it began and the accounting run replays the same thing.
- **The curve cannot drift.** The PS ease is a line-for-line port of
  `pane_sidebar_transition.zig`'s `ease()`, and the harness reads `column_ms`
  and the curve back from the zig source (H1); the zig file is in the guard's
  Covers, so changing it re-runs the harness.
- **Live sink** (`New-FrameLabTriggerSink`): clicks through FrameLabInput's
  `GliSendInputSink`, chords through a keyboard `SendInput`, IPC through the
  scene build's CLI. It is an input-desktop helper and never runs in its own
  harness; the live matrix run is T2392's.
- **Scene contract** for T2392's Launch: Geometry.MaximizeButton, Sidebar
  {EdgeX, OtherEdgeX, Toggle}, Target (pane name), and a second tab open for
  tab-switch.
