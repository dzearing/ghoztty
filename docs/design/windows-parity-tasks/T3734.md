# T3734 - Choosing WSL (or any shell) in Settings > Shell does not change the shell: new windows still open cmd.exe

## Summary

User report 2026-11-25 (laptop with WSL): choosing WSL in Settings > Shell does not change the shell - every new window still opens cmd.exe. The Shell row (settings_pages.zig:307) writes `command` to the config file. Leads, to MEASURE not guess: (1) does the running app reload `command` after the Settings write, or only at launch - a new window must use the value the Settings window just wrote, with no relaunch, as on the Mac; (2) with session-persistence on, every local pane runs through the local agent, and Surface.zig:1102-1130 forwards a configured command only when `command_explicit` is set (T104) - confirm a command that arrived by config RELOAD (not at launch) still counts as explicit, and that the agent's OPEN carries wsl.exe rather than falling back to its cmd.exe default; (3) the agent's windowsCommandArgs flavor table for wsl.exe. Acceptance: a test that sets command = wsl.exe through the Settings window's seam on a running app, opens +new-window, +split and a new tab, and asserts each pane's shell process is wsl.exe (by the pane-shell lookup, not a title), with session-persistence on AND off; plus the same after a relaunch.

**WSL in tests (CLAUDE.md: never start WSL unasked).** Nothing in the Windows floor, sweeps or the go-loop may boot WSL, so every WSL arm of these tests is opt-in (`-Wsl`, skipped with a stated reason otherwise; the precedent is the ipc-command-keepalive WSL arm, T1751). The always-run arms prove the same code path with a non-WSL shell (pwsh / Git Bash), and the WSL arm is run by hand (or by the user) before close; record that run in this file.

## In plain terms

Picking a shell (WSL, PowerShell, anything) in Settings > Shell saved the
choice, but every new window, tab and split kept opening Command Prompt until
Ghoztty was restarted - and with the default settings, not even reliably then
for windows opened after a later settings change. Now the next window, tab or
split opens the shell you picked, straight away, as on the Mac.

## Root cause

Measured, not guessed (debug build, background test desktop, Settings seam
`--op=shell --key=command --value=powershell.exe` on a running app, then read
each new pane's shell process by its leaf pid):

| case | new window | split |
|---|---|---|
| persistence ON (the default), Settings write | cmd.exe | cmd.exe |
| persistence OFF, Settings write | powershell.exe | powershell.exe |
| persistence ON, `command` in the file at LAUNCH | powershell.exe | powershell.exe |

So the reload itself worked; what the reload lost was the "the user asked for
this command" mark. `Config.finalize` records it as `_command-explicit`, and
the agent-backed pane path (`Surface.init`, T104/T514) forwards a configured
shell to the session-persistence agent only when it is set. A hard reload
stores the new config into the app with `Config.clone` (win32 App
`config_change`), and `clone` copies **Key fields only** - `_command-explicit`
is not a Key, so every clone reset it to false and the agent fell back to its
own default, cmd.exe. A launch-time config is never cloned, which is why a
restart appeared to fix it. The exec path (persistence off) never consults the
flag, which is why that arm was the green control.

Fix: `Config.clone` carries `_command-explicit` (src/config/Config.zig). It is
shared core, so the Mac and Linux builds get the same fix; the unit test
`clone: _command-explicit survives a clone` runs in every lane.
