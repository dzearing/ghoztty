# T3734 - Choosing WSL (or any shell) in Settings > Shell does not change the shell: new windows still open cmd.exe

## Summary

User report 2026-11-25 (laptop with WSL): choosing WSL in Settings > Shell does not change the shell - every new window still opens cmd.exe. The Shell row (settings_pages.zig:307) writes `command` to the config file. Leads, to MEASURE not guess: (1) does the running app reload `command` after the Settings write, or only at launch - a new window must use the value the Settings window just wrote, with no relaunch, as on the Mac; (2) with session-persistence on, every local pane runs through the local agent, and Surface.zig:1102-1130 forwards a configured command only when `command_explicit` is set (T104) - confirm a command that arrived by config RELOAD (not at launch) still counts as explicit, and that the agent's OPEN carries wsl.exe rather than falling back to its cmd.exe default; (3) the agent's windowsCommandArgs flavor table for wsl.exe. Acceptance: a test that sets command = wsl.exe through the Settings window's seam on a running app, opens +new-window, +split and a new tab, and asserts each pane's shell process is wsl.exe (by the pane-shell lookup, not a title), with session-persistence on AND off; plus the same after a relaunch.

**WSL in tests (CLAUDE.md: never start WSL unasked).** Nothing in the Windows floor, sweeps or the go-loop may boot WSL, so every WSL arm of these tests is opt-in (`-Wsl`, skipped with a stated reason otherwise; the precedent is the ipc-command-keepalive WSL arm, T1751). The always-run arms prove the same code path with a non-WSL shell (pwsh / Git Bash), and the WSL arm is run by hand (or by the user) before close; record that run in this file.
