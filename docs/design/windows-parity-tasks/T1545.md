# T1545 - A pane drag only offers the first six windows as drop targets

## In plain terms

With a lot of Ghoztty windows open, dragging a pane onto the seventh one does
nothing - the drop lands nowhere and the pane stays put. Nobody with two or
three windows will ever meet this, but somebody who keeps a wall of terminals
will, and "this window refuses drops and that one accepts them" reads as a bug
rather than as a limit.

## Summary

`MAX_DROP_WINDOWS = 6` in `Window.zig` bounds how many candidate windows one
drag resolves against, because the candidate geometry is built on the STACK on
every `WM_MOUSEMOVE` (pane rects and tab rects per window) and an unbounded walk
of `app.windows` there would put tens of kilobytes on it per move. The windows
are taken frontmost-first, so the cap bites the ones furthest back.

Options worth weighing when this is picked up: build the candidate set once per
drag into a heap allocation the drag owns (the z-order is already snapshotted at
the press, so the SET does not change mid-drag - only the geometry does); or
resolve lazily against the one window under the pointer (`WindowFromPoint` plus
a membership check) and keep the pure resolver's set interface for the tests.
The second is less code and makes the cap disappear entirely.

## Validation criteria

- [ ] With more than six windows open, a pane can be dropped into any of them.
- [ ] The drag stays smooth - no per-move allocation on the mouse path, or a
      measurement showing the one it does costs nothing at this scale.
- [ ] `test\win32\rearrange-window-drop.ps1` covers the many-window case.
