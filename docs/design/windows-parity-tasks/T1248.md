# T1248 - update-real-msi's final sweep arm flakes when the applier is still exiting

## Summary

Arm E ('the next launch swept everything the update left') failed once on 2026-09-01 with ghoztty-updater.exe still in the staging directory, and passed on an immediate re-run with the same build. The applier holds its own image until it exits, so the 30x1s poll is racing the applier's exit rather than the sweep. A red that clears on a re-run reads as a broken change to whoever hits it; the arm should wait for the applier pid to be gone before it judges the sweep.

## In plain terms

The test that walks a real in-app update end to end sometimes failed its last
check - "nothing was left behind" - and then passed when run again with nothing
changed. The update itself was fine: the test simply looked too early, while
Windows was still letting go of the updater's file, and the app only cleans up
once per launch. Now the test waits until nothing holds those files before it
launches the app whose clean-up it judges, so a red means a real leak.

## Goals

- [x] the judged launch starts only once every leftover is released (or 60s pass, and the failure then names what was still held)
- [x] the release probe proves it can see a held file (control), so the wait can never be a silent no-op

## Validation criteria

- [x] `update-real-msi.ps1` ALL PASS (32 checks) 4 of 4 consecutive runs through `acceptance-parallel.ps1 run` on 2026-10-23 (the flake hit 2 of 4 on 2026-09-01); no run needed the 60s fallback note
- [x] both probe controls PASS in section E: an open file reads as held, the same file reads as released once closed
