# T2448 - Under a divider drag the fold glide steps at 10-15 fps in the user's own window (release 1.49.6, a viewer pane in the row resized on every pass, passes 60-100 ms apart): measure the per-pass cost with a viewer pane and get glide frames back to the display rate

## Summary

Found working T2442 (2026-10-28). The user's installed release log
(`%LOCALAPPDATA%\ghoztty\ghoztty.log`, 2026-10-29T05:20:19-22Z) shows a
divider drag folding panes in a 5-pane window with a viewer pane in the row:
the viewer's `viewer nav tips` line - written each time a pass resizes it - lands
every 60-100 ms, and every logged fold showed its strip face first at alpha
175-255, i.e. one glide step crossed most of the 120-DIP fade. A 45 ms follower
stepping at 60-100 ms closes 75-90% of the way per frame, so the glide reads as a
jump regardless of how it is drawn. T2442 capped the fade at a third per frame so
the content can no longer pop; this task is the frame rate itself.

What to find out: what a drag pass costs with a WebView2 viewer pane in the row
(controller bounds, the frame wait batch over the other panes, the strip face
DIB), whether the glide's FrameClock ticks are starved by the mouse-move passes
(each move is a full `layoutSplitsLive`), and whether a pass that only moves
cards still resizes the viewer. Related: T2143/T2241 (8-pane drag budget, no
viewer), T2373 (frame lab), T2360 (composition). Measure with `GHOZTTY_PERF`'s
`drag ticks=` line on a row that includes a viewer pane (drag-perf.ps1 has no
viewer variant today), on the release build where possible.

- [ ] the cause of the 60-100 ms passes named and fixed, or split into tasks that each own one term
