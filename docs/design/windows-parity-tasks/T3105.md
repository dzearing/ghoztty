# T3105 - One IPC client that connects and says nothing can hold up every other ghoztty command on Windows: serve clients concurrently with a read/write timeout, serialize only commands that change what exists (Mac 1956f5f55)

## Summary

Mac 1956f5f55: every command ran on one serial queue with an untimed read, so a silent client hung every later +verb and every status/banner hook; a +split waiting on its pane did the same; stop() deadlocked quit. Fix there: each client on a concurrent queue, 5 s read/write timeout, at most 48 at once; mutating commands serialized under a lock, reads and per-pane commands do not wait; remote dial does not hold the lock; listen backlog 5 -> 64. On Windows: IpcServer.zig runs several ConnectNamedPipe listener instances - verify whether a connected-but-silent client, or a handler waiting on the UI thread (+split waiting for its pane, a remote dial), blocks other clients and banner hooks; add the per-client timeout and the read-vs-mutate split where it does. Validation: an acceptance case opens the pipe and sends nothing while +list, +set-banner and +read from other clients still answer inside their normal time; quit is not held up by an in-flight command.

## In plain terms

Any program that opened Ghoztty's command channel and then said nothing (a
status hook that got killed halfway, a script that stalled) could tie it up.
Four of them and every `ghoztty` command and banner update in every pane said
"No running Ghoztty instance found"; one of them and quitting Ghoztty hung. Now
a silent caller is dropped after 5 seconds, sixteen can sit on the channel
while everyone else still gets straight in, and quit never waits for them.

## Goals

- [x] every server read/write on a client is bounded (5 s, the Mac bound)
