# T790 - win32 filter boxes fold ASCII-only where Mac folds Unicode: a non-ASCII machine or process name cannot be filtered for

## Summary

Mac filters both the machine chooser (MachineChooserView.swift:244-245,253) and the Activity Monitor process table (RemoteActivityMonitorView.swift:808) with localizedCaseInsensitiveContains, which is Unicode- and locale-aware. Windows folds ASCII only (text_search.containsIgnoreCase over std.ascii.indexOfIgnoreCase), so typing an accented, Cyrillic or CJK-cased letter into either filter box narrows the list to nothing where the Mac would show hits. Found while hoisting the two private copies of the fold into one module (T288); the hoist is what makes this a one-function change.

## In plain terms

Type into the search box of the machine chooser or the Activity Monitor and it
only understands English letters. Search for a machine called `Munchen` and it
finds `Munchen`; search for `Munchen` spelled with the umlaut in the other case,
or for a program with a Russian or Greek name, and the list goes empty even
though the row is right there. On a Mac the same search finds it. Anyone whose
machines or apps are not named in plain ASCII notices; everyone else never will.

### Deliberate divergence, recorded

The ASCII fast path is not only a speed choice. A linguistic fold is
locale-dependent, and under a Turkish locale `I` and `i` are deliberately NOT
the same letter — so routing ASCII through it would stop `ghoztty` matching
`GHOZTTY` for that user. ASCII folds by ASCII rules; everything else folds
linguistically. That answers what T790 was filed about without introducing a
second, subtler version of it.

### Decision D71 - Should the win32 filter boxes fold Unicode case the way macOS does, and if so with Windows' linguistic search or an in-tree fold table?

Resolved 2026-08-14T18:02:37Z : Use Windows' own linguistic search, FindNLSStringEx with LINGUISTIC_IGNORECASE (Recommended)

Resolved by Claude (user delegated technical calls, 2026-08-14). The experience is settled by parity - the Windows filter must match what the Mac filter matches, including non-ASCII. Among mechanisms, the platform linguistic fold (FindNLSStringEx) tracks Windows own casing rules without vendoring case data; the policy stays pure behind one function as T288 prepared.
