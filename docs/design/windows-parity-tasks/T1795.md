# T1795 - Loop and soak runs pull focus from the user (windows popped over a fullscreen game): nothing a run starts may take the foreground while the user is at the box

## In plain terms

While the user was playing a fullscreen game, windows the automation opened
kept popping up on top of it. Automated runs (the go-loop's tests and the soak
daemon's background rounds) must never take the foreground away from the
person using the machine.

## Summary

User reports: 2026-09-27 ("you're popping windows above my game ... stop the
weird testing") and 2026-10-10 ("continue go loop. Please avoid pulling focus
from me by running tests that do that"). On 2026-09-27 the loop was stopped
(`go-loop-exec.ps1 stop`) and so was the soak daemon (`soak-daemon.ps1 stop`).
The daemon was mid-round in `zig build test -Dapp-runtime=win32` at the time.
**The soak daemon stays stopped until this task lands.**

T211-T218/T272/T276 moved the acceptance suite onto a background desktop, so
the remaining routes to the user's foreground are not covered by
`foreground-audit.ps1`. Suspects, unmeasured (? INFERRED):

1. **The soak daemon's win32 unit lane.** `zig build test -Dapp-runtime=win32`
   runs on the INPUT desktop, outside `TestDesktop.ps1`. Any unit test that
   creates a real top-level HWND (or calls ShowWindow/SetForegroundWindow) shows
   it on the user's screen. The daemon's yield rule (testing.md "INTERRUPTIBLE")
   yields to foreground WORK, not to a foreground USER, so a game counts as an
   idle box.
2. **The six declared `@input-desktop-exception` scripts** in
   `test/win32/lib/TestDesktop.ps1` (context-menu-real-input, profile-latency,
   test-desktop-spike, notification-click-real, translucent-window,
   rdp-session). By declaration they use the real desktop and real input.
3. **The loop's own CLI calls on the user's desktop** (`+new-window`, `+split`,
   reset-context, the dashboard). The Windows CLI still focuses what it
   creates. Mac commit 3081022ec ("CLI-created windows and panes no longer
   steal focus; --focus opts in") is the parity fix for that and is filed
   separately by the 2026-10-10 intake.

### Fix shape

- One shared user-presence predicate, for example
  `test/win32/lib/UserPresence.ps1`: true when the last input
  (`GetLastInputInfo`) is recent, or when the foreground window is fullscreen
  or exclusive (a game). A run must not start anything on the input desktop
  while it is true. Input-desktop exception scripts SKIP with a reason; they
  never wait and never fail.
- Run the soak daemon's `busy`/yield check against the same predicate, so it
  only takes the box when nobody is using it.
- Measure suspect 1 first: list the win32 unit tests that create visible
  windows. Either make them hidden or message-only, or move that lane behind
  the predicate.
- `foreground-audit.ps1` gains the property, so a new input-desktop path
  without the gate is a finding.
