# T1527 - close-confirm-idle flakes on the dialog wait, so its verdict says nothing about the code

## In plain terms

One of the automated checks that runs before a change can land is unreliable:
asked the same question twice about exactly the same build, it gave two
different answers, failing a different part each time. Nobody can tell a real
break from a bad day, and because this check covers a file that changes almost
every day, the noise lands on whoever is working next.

## Summary

Two back-to-back runs over IDENTICAL bytes failed DIFFERENT sections: run 1 failed C/remote (idle remote ctrl+w opened no confirm within the 5s Wait-Dialog budget) and passed D; run 2 passed C and failed both D/always checks (confirm-close-surface=always produced no dialog). A harness that answers differently to the same question cannot stamp, and every turn that touches Window.zig is now blocked behind a coin flip. Find what the dialog wait is racing (key delivery to the surface vs the dialog pump, or a settle the remote arm leaves behind for the next section) and make the oracle deterministic or the wait honest.

## Validation criteria

- [ ] The race is NAMED - what the dialog wait is actually waiting on, and why it
      sometimes is not there yet - rather than the timeout being raised until the
      red goes away.
- [ ] `test\win32\close-confirm-idle.ps1` runs green three times in a row over
      unchanged bytes, and the run is stamped.
- [ ] `-NegativeControl` still fails, so the repaired wait did not become a wait
      that cannot say no.
