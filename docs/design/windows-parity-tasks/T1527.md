# T1527 - close-confirm-idle flakes on the dialog wait, so its verdict says nothing about the code

## In plain terms

One of the automated checks that runs before a change can land is unreliable:
asked the same question twice about exactly the same build, it gave two
different answers, failing a different part each time. Nobody can tell a real
break from a bad day, and because this check covers a file that changes almost
every day, the noise lands on whoever is working next.

## Summary

Two back-to-back runs over IDENTICAL bytes failed DIFFERENT sections: run 1 failed C/remote (idle remote ctrl+w opened no confirm within the 5s Wait-Dialog budget) and passed D; run 2 passed C and failed both D/always checks (confirm-close-surface=always produced no dialog). A harness that answers differently to the same question cannot stamp, and every turn that touches Window.zig is now blocked behind a coin flip. Find what the dialog wait is racing (key delivery to the surface vs the dialog pump, or a settle the remote arm leaves behind for the next section) and make the oracle deterministic or the wait honest.

## Goals

- [x] Re-verify the flake on today's code before changing anything
- [x] Name what each failing wait was racing
- [x] Fix the wait that was genuinely wrong, and make a future miss explain itself

## What was found (2026-11-20)

- **C/remote was already named and fixed by T2470** (5a7e42cbb): the section
  typed `ping` before the remote pane had drawn its prompt, so under load the
  keystrokes landed before the shell was reading. It now waits on the prompt.
- **`Wait-Dialog $false` was inverted.** It kept polling while the dialog was
  ABSENT and returned the handle (a failure) the instant it was still present,
  so every "Escape dismisses" check was one sample racing the dialog's
  teardown, and a clean dismissal cost the full timeout. Fixed: it now polls
  until the dialog is gone.
- **D/always did not reproduce** in four runs over identical bytes on today's
  code. The 2026-09-13 miss printed nothing that could tell its states apart,
  so a confirm miss now prints `dialog miss: <why>`: app exited / window closed
  WITHOUT confirming / a system `#32770` box is up instead (ConfirmDialog's
  silent MessageBoxW fallback, filed as T3277) / window open with no dialog.
