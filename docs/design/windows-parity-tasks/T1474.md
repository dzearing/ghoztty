# T1474 - stale-scan measures card ROT but nothing reads it: a still-real card whose line numbers and counts have gone wrong reads as fresh

## In plain terms

A card in the queue can be completely correct about the problem it describes
and completely wrong about how big it is, because the file it points at has
moved and the count it quotes has grown. Nobody finds out until an agent picks
it up expecting a one-line change and finds thirty-eight. The information that
would have warned them is already collected — it just is not shown to anyone.

## Summary

Found by the **T676** sweep on 2026-09-09. That card went looking for *phantom*
cards — todos a later turn had already fixed, the T122/T422 shape — and found
none. What it found instead, in three of the seven cards it examined, was a
different and commoner failure:

- **T1047** named `hero-nav.ps1:464-465` and called it "the remaining instance
  in the suite". At HEAD the site is `:488-489` and the shape appears in **15
  files, ~38 sites**. The card is planned as a one-liner and is not one.
- **T736** said `wasm_patch_growable_table.zig` was "the one other file under
  `src/build/` with test blocks". There are three today.
- **T1437** said "roughly twenty more sites". There are **55 across 21 files**.

None of these is a phantom, so none is closable, and no existing check looks at
them: `validate` checks structure, `stale-scan` ranks by *a later commit having
named the task* and by *the files the card names having been touched*. That
second signal — the `touched=` column — is exactly the measurement this needs,
and today nothing acts on it. T1047 was sitting there reading `touched=` nonzero
the whole time.

The cost is not a wasted close, it is a **mis-planned turn**: the agent that
claims a card sized "one line in one script" and discovers a 21-file sweep
either does the wrong-sized thing or spends its context re-deriving the scope,
which is the same context T676 existed to stop burning.

## Details

The cheap version is a **report**, not a gate — the same posture T404 took, and
for the same reason: a card whose files moved is a prompt to re-read, never a
verdict that it is wrong.

Shape to consider (pick one, they are not exclusive):

1. **Surface `touched=` where a turn actually reads it.** `next` already prints
   "filed N days ago; M commit(s) since touched its files" and says `CHECK
   FIRST`. That is the right hook and it already fires — what it does not do is
   distinguish "the subject code moved" from "the card's own quoted evidence may
   now be false". A card carrying a `file:line` or a count is the high-risk
   shape; detecting those in the body (a `:\d+` reference, a "N sites" phrase,
   "the only", "the one other", "the remaining") and saying so specifically
   would turn a generic nudge into an actionable one.
2. **Make quoted line numbers checkable.** A `path:line` in a card body can be
   re-resolved: if the line at that path no longer contains what the card says,
   the reference is stale by construction. This is the strongest signal and the
   narrowest to implement.
3. **A periodic sweep**, the way `stale-scan` is run at triage — a `rot-scan`
   listing open cards whose quoted references no longer resolve, for the daily
   triage step to work off.

Deliberately NOT proposed: auto-editing card bodies. The T676 pass rewrote three
Summaries by hand and the judgement in each ("not all 38 are defects —
`focus-defer.ps1` polls on purpose") is not mechanizable.

Prior art in the repo to follow rather than reinvent: `scripts\parity-tasks.ps1
stale-scan` (the ranking and the report format), `scripts\guard-due.ps1` (the
"has anything moved under this since it was last blessed" stamp shape), and
`scripts\parity-sweep.ps1` (enumerate-then-subtract, exit 1 on unmapped).
