# T1234 - An HEIC or AVIF photo may open as an error card where Mac shows the picture

## In plain terms

Opening an iPhone photo (.heic), a scanned .tiff, or a Mac app icon (.icns) in a
Ghoztty image pane on Windows showed "Cannot display this image", while the Mac
build shows the picture. Now Windows decodes those formats itself and shows the
picture too; when a photo genuinely cannot be shown because Windows is missing
the HEIF codec, the card says which Store extension to install instead of a
generic error.

## Goals

- [x] .tif/.tiff opens as a picture (decoded by Windows' own codecs)
- [x] .heic/.heif opens as a picture wherever the HEIF Image Extensions are installed
- [x] .icns opens as a picture (its largest embedded PNG)
- [x] a HEIC with no codec to decode it says "Windows needs the HEIF Image Extensions to show this image"; a merely corrupt one keeps the ordinary card
- [x] any other raster the page cannot draw (e.g. an AVIF on a WebView2 without AV1) gets one retry through the Windows codecs before the card

## Summary

T1183's extension table is Mac's, byte for byte, and includes .avif/.heic/.heif. macOS decodes all three through ImageIO with no extra install. On Windows the decode belongs to whatever codecs the box has: WebView2 decodes AVIF, but HEIC/HEIF need the HEIF Image Extensions from the Store, and .tif/.tiff and .icns are not web image formats at all - so a photo straight off an iPhone can open as 'Cannot display this image' on one machine and as a picture on the next. The card is honest, but it is not parity. Wanted: decide per format whether to decode natively on the host side (GDI+/WIC already ships gdiplus_decode.zig, and WIC covers TIFF and - with the extension - HEIF) and hand the page a PNG, or to say so in the card ('Windows needs the HEIF Image Extensions to show this') rather than the generic message. Either way the answer should be the same on both seats for the same file.

## Decision (mechanism - Claude's call, per go.md 5b)

Both halves of the "either" were taken, per format:

- `viewer_image.Route` decides per extension how the bytes reach the page:
  `.browser` (the file itself), `.wic` (heic/heif/tif/tiff: decoded through
  `image_copy.decodeWhy` - the same WIC decoder ctrl+C uses, EXIF orientation
  included - and served as a BMP of the pixels), `.icns` (the widest PNG the
  icon set embeds, `icnsBestPng`; WIC has no ICNS codec).
- BMP rather than a PNG re-encode: the pixels never leave the process, and the
  hand-written `png_encode.zig` would spend seconds on a 12 MP photo where a
  14-byte header costs nothing. Chromium honours the V5 alpha mask.
- `fallback`: a `.browser` raster the page fails gets ONE retry via WIC (an
  AVIF on a WebView2 without AV1, a misnamed file). SVG never retries.
- The codec card fires only when WIC says NO codec recognised the file
  (`WINCODEC_ERR_COMPONENTNOTFOUND`) AND the content is a real HEIF/AVIF `ftyp`
  container (`missingCodec`); a corrupt HEIC on a box that has the extension
  keeps the ordinary card. AVIF names the AV1 Video Extension.
- Mac needs nothing: ImageIO already shows all of these, so no Mac-seat task.
