# T1937 - Run a second Windows loop seat in its own worktree: cross-worktree task claims, a machine-wide lock for timing-sensitive tests, per-seat log fragments, a watchdog for both seats

## In plain terms

Right now one loop works one task at a time. The user wants a second loop,
in its own copy of the repo, so two Ghoztty issues move at once. The two
loops must never pick the same task, and must take turns only for the tests
where another loop's compiling would skew the result.

## Summary

User request (2026-10-14): "is it possible to create another worktree to
work on 2 ghoztty issues at a time and just coordinate when you're testing".
Sequenced after T1935 (typing lag, then publish) and T1936, at the user's
call.

What already works side by side:

- Separate builds: each worktree has its own `zig-out` and local cache. The
  box has 32 cores.
- Test endpoints: `test/win32/lib/Isolation.ps1` (`GHOZTTY_PIPE_SUFFIX`, T441)
  moves the app pipe and the agent endpoint per run, in 210 of 389 scripts.
  GUI scripts run on the background test desktop.
- `scripts/ship-feature.ps1` already creates a worktree on its own branch
  (T1058).

What collides today, and the fix for each:

1. **Task claims.** `status: in-progress` lives in git, and each worktree
   has its own `temp\go-loop.lock.json`, so two loops can claim the same
   task. Fix: a claim ledger outside both worktrees (for example
   `%LOCALAPPDATA%\ghoztty\loop-claims.json`, written under a named
   mutex). `next` skips tasks the other seat holds, and claims expire with
   the holder's heartbeat.
2. **Timing-sensitive tests.** Perf or latency measurements (T1935's CPU
   check, resize-flicker, `profile-latency`, soak) read wrong while the
   other seat compiles. Fix: a machine-wide `Global\GhozttyTimingTest` mutex.
   Scripts declare `# @timing-sensitive` and take it, as do the end-of-task
   floor runs. Plain builds and isolated functional tests do not take it.
   Waiting is bounded and reported, never silent.
3. **The 179 scripts without Isolation.ps1.** Audit them: any that launches
   the debug app gets isolated, and the rest are proven not to launch it.
   Extend the existing isolation audit so a new script without isolation
   is a finding.
4. **Single-loop machinery.** The watchdog holds
   `Global\GhozttyGoLoopWatchdog` and supervises one pane and one lock.
   Fix: seat-qualified names (`-Seat a|b`), one watchdog per seat, and the
   dashboard and `go-loop-health.ps1` show both. The dev install
   (`%LOCALAPPDATA%\ghoztty\dev-install`) and publishing are single-owner:
   seat A owns them, and seat B never delivers or publishes.
5. **The shared log.** Both seats append to
   `docs/design/windows-parity-log.md`, which conflicts on every concurrent
   push. Fix: per-seat fragments merged when the log is read, or append
   only right before the pull/rebase.
6. **Branches.** Git will not check out the same branch twice. Seat B works
   on a local branch and does pull --rebase, then push
   `HEAD:users/dzearing/windows-amd64` at each task boundary (the same
   contract the Mac seat has).

## Validation criteria

- [ ] Two seats run one task each for a full turn with no shared task, no
      lost commit, and no log conflict. Both close their tasks and push.
- [ ] Claim race test: two `next`+claim calls at the same instant hand out
      two different tasks (scripted, with a negative control that turns the
      ledger off).
- [ ] A `@timing-sensitive` script waits while the other seat holds the
      mutex, and says so. A non-timing script does not wait.
- [ ] Isolation audit: every script that launches the app is isolated, and
      a new one without isolation fails the audit (teeth check).
- [ ] `go-loop-health.ps1` and the dashboard show both seats. Stopping one
      seat does not stop the other.
- [ ] Seat B never publishes and never touches the dev install (asserted).
