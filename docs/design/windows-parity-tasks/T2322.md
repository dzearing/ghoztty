# T2322 - A failed Install Update must tell the user

## Summary

User report 2026-10-26: "i click install and restart. NOTHING HAPPENS". Part
three of the chain (T2320, T2321 are the causes).

Two failure points are invisible:

- Arming fails (`update apply: NOT armed err=...`, `update_install.zig` ~362):
  the app logs and stays up, the menu row stays, and the click visibly does
  nothing.
- msiexec fails in the applier (`exited 1603`): the app is relaunched on the
  old build with only a log line `Ghoztty could not finish updating, so it is
  still running the version you already had.`

Mac parity: Sparkle answers a failed install with an alert window in the app
("Update Error!"), never with a notification alone. The Windows translation is
Ghoztty's own dialog, owned by the window the click came from.

**Re-verified 2026-10-27 and SPLIT.** Both failure points already "said"
something: a failed arm raised a tray balloon (3aa5ef013, 2026-08-30) and a
failed msiexec raised the applier's modal (1be02f7f1, T1206). Neither reached
the user: a balloon is suppressed by Do Not Disturb / notification settings and
answers a click in the window with a toast elsewhere, and the applier's modal
comes from a detached windowless process with no right to the foreground. This
task now covers the CLICK half - a failed arm - plus the menu-row marker both
halves share; the msiexec half (the applier handing its failure to the reopened
app) is **T2344**.

## In plain terms

Clicking "Install and Restart" could fail before anything happened, and the
only answer was a notification that Windows often hides, so the click looked
dead. Now Ghoztty shows its own message in the window: the update did not
install, your terminal is fine, why, and what to try next. The update menu
item also says when the last try failed.

## Goals

- [x] a failed arm after "Install and Restart" shows Ghoztty's own dialog,
      owned by the window, with the reason in plain words and a way forward
      (try again from the menu / open the releases page)
- [x] an automatic install whose arm fails raises nothing, but the menu row
      shows that the last attempt failed
- [x] the menu row reads "Install Update <ver> (last try failed)" after any
      failed attempt this session
- [x] split: the msiexec-failure handoff is T2344

## Validation criteria

- [x] unit tests: the arm-failure wording (cause per error, remedy, error name)
      and the failed menu label (fits label_cap, falls back) - none + win32 lanes
      (`update_apply.zig`, `update_badge.zig`; floor lanes)
- [x] acceptance on the test desktop: a forced arm failure after "Install and
      Restart" raises the dialog in the APP's process with the cause, the
      remedy and the error; the app stays up, the package stays staged, and the
      app logs that the menu row now marks the failure; -NegativeControl (no
      forced failure) goes red - `test/win32/update-arm-failure.ps1` ALL PASS
      25; `-NegativeControl` 13 FAILURE(S)
- [ ] NOT DRIVEN LIVE: the automatic path's failed arm (code path only:
      `maybeAutoApplyUpdate` -> `markInstallFailed`, no dialog); the menu row's
      text is asserted by unit test + the app's log line, not read off a popup
      menu (popups do not open on the background test desktop)
