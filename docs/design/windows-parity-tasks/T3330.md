# T3330 - Linux L1: the GTK debug build compiles and launches in WSLg

## Summary

zig build -Dapp-runtime=gtk -Doptimize=Debug inside WSL Ubuntu via scripts/linux/wsl-run.ps1 (L0). Expected to fail first: src/apprt/gtk has not been taught the apprt actions Ghoztty added since the fork. Make each compile (log-and-ignore is fine for unported ones; list them in this file as the Phase 1-3 backlog). Install the GTK4/libadwaita dev packages and record the exact apt line in docs/claude/linux.md. Acceptance: the window opens in WSLg, a shell runs, glxinfo -B shows the d3d12 (GPU) renderer or the llvmpipe fallback is recorded. Debug endpoints must differ from release (T243/T350 rule).

## In plain terms

Ghoztty had never been built for Linux. Now the Linux version compiles inside
WSL, opens a terminal window, and runs a shell in it. There is a script that
proves it, and it does so without ever putting a window on your screen. Nobody
can use it yet: none of the `ghoztty` commands reach it, and the Ghoztty-only
features are switched off on Linux for now.

## Unported on GTK (the Phase 1-3 backlog this build exposed)

The compile only failed on these. Each one now logs
`ghoztty action not ported to gtk yet` and returns "not handled"
(`src/apprt/gtk/class/application.zig`):

| apprt action | Owner |
|---|---|
| `pane_banner`, `prompt_banner`, `toggle_pane_sidebar`, `activity_state` | T3339 (L10 banners + sidebar) |
| `stash_pane`, `restore_stashed_pane` | T3336 (L7 CLI verbs: `+stash` / `+restore`) |
| `toggle_hero_mode`, `toggle_rearrange_mode` | T3340 (L11 reference intake: window modes) |

And on the CLI side: GTK's `performIpc` used to send only `new_window`, over
upstream's D-Bus. It now sends every verb over the Unix socket, like the Mac
and `none` runtimes. The GTK app does not serve that socket yet, so every verb
answers "no running instance" until T3335 (L6). Starting the app when it is not
running, which win32 does for `+new-window`, is T3336.

Two shared-core fixes were needed. Neither changes Mac or Windows behaviour,
because both are no-ops on a static event-loop backend:
- `src/renderer/generic.zig` imported the raw `xev` (static io_uring on Linux)
  while `renderer.Thread` passes it a `global.xev` (Dynamic) Async.
- `src/termio/Thread.zig` called `loop.update_now()`, which the Dynamic loop
  does not forward. It now goes through `updateLoopNow`.
