# T2042 - cli-focus-policy.ps1 arms F/H (viewer split landed) fail beside other scripts and pass alone: the pane-count wait is too short under parallel load, or the script needs @parallel-unsafe

## In plain terms

One of the automated checks for "commands open panes without stealing your
keyboard" sometimes failed when run alongside other checks, then passed when
run on its own. It was a timing problem in the test, not in Ghoztty: the check
looked for the new pane after a fixed two-second wait, and on a busy machine a
document pane can take longer than that to appear.

## Goals

- [x] the pane-count checks wait for the pane to appear instead of sleeping a fixed time
- [x] the script passes beside other scripts in the parallel runner

## Summary

Re-verified 2026-11-23: the defect is still in the script. Arms E, F, G, H, L
setup, L, M and O each slept a fixed 0.9-2s after the CLI command and then
read the pane count once from `+list --json`. A viewer split has to start
WebView2, so under the parallel runner's load it can land after the 2s sleep
(arms F and H, the viewer splits, are the ones that went red). The arms read
the old count, while the same run alone passed.

Fix: `Wait-PaneCount` in `test/win32/cli-focus-policy.ps1` polls `+list --json`
every 250 ms until the window reports the expected count, for up to 20 s. It
then settles (600 ms by default, 1.5 s after a viewer split) so the focus and
z-order oracles that follow still read the post-layout state, which the fixed
sleep used to cover. Every count-after-sleep site in the script uses it. The
assert messages now name the count the app actually reported. `@parallel-unsafe`
was not needed: the flake was the wait, and the runner's per-worker isolation
already holds for this script.
