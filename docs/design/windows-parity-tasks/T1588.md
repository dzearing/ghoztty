# T1588 - Nothing publishes when the stranded-commit count gets large, so a day's fixes can sit twelve hours behind a release that already went out

## In plain terms

Ghoztty cuts one release a day, in the evening. Anything that lands after it
waits until tomorrow. On a busy day that means a fix can be finished, tested and
pushed by ten in the morning and still not be installable until the following
evening — and on 2026-09-03 exactly that shape had the user download a broken
installer twice and report the same bug twice, because the fix was sitting
behind a release that had already gone out.

## Summary

`scripts\daily-publish.ps1` fires on the first task-boundary push at or after
17:00 local, or on the first push once 24 hours have passed since the last
publish (T1292). Two escape hatches exist:

- `-Request` (hand-run), which makes the next step-6.5 run publish despite the
  day's watermark; and
- the automatic request `set-status ... -Status done` files for a task carrying
  `user-report: true` (T1315).

Both are keyed on somebody having *reported* the problem. Nothing is keyed on
the size of the gap itself. This morning the gap was **37 commits**, the largest
this month; yesterday it was 9.

## Details

The number already exists — `daily-publish.ps1 -Status` prints it, and
`go-loop-health.ps1` reports it as `publish=ok+<n>`. What is missing is a rule
that acts on it.

Proposed: a stranded-commit threshold that files a publish request the same way
a user report does, so the evening cadence stays the floor and a heavy day cuts
a second release rather than banking the work. The threshold wants to be a
named constant with its reasoning beside it, not a magic number, and a publish
it triggers should say in the log that the threshold is what fired it.

Deliberately NOT publish-per-commit: the tag/release pipeline runs on CI for
every publish, and one release per push would be both noisy for the user and
wasteful. The question this task answers is "how big a gap is too big", not
"can we ship continuously".

Relevant history: T1292 (the 24-hour fallback), T1294 (the stranded list and the
`-Request` hatch), T1315 (automatic requests for user reports), D85 (the user's
directive that the installed terminal only ever runs something published).

## Goals

- [x] A heavy day cuts a second release instead of banking the morning's work
- [x] An ordinary day still cuts exactly one

## Resolution

`scripts\daily-publish.ps1` gains `-StrandedThreshold` (default 30: the loop
lands ~50 commits on a working day, a task being a work commit plus a tracker
close, so 30 is about half a day) and a pure `Test-StrandedThreshold`. Before the
due decision, when no request is pending and the last publish is `published`,
a gap at or above the threshold writes an ordinary request file with reason
`stranded threshold: N commits have landed since <tag> (threshold T)`; the
existing request path then honours, consumes or preserves it. `tagged` (CI still
building) and `failed`/`attempting` (the T1369 retry rule's) never fire it.
`-Check` decides out loud and writes nothing. Live `-Check` against the real
watermark on 2026-09-25: `DUE: requested: stranded threshold: 37 commits ...;
publishing win-v1.36.38`. Acceptance: sections P and Q of
`test\win32\daily-publish.ps1`, 188/188, negative control 188 red.

The harness floor's unroll-count audit caught a latent bug on the way:
`Get-StrandedCommits` returned a bare array, so a gap of ZERO unrolled to
`$null` and `-Status` reported it as "unknown". It now returns
`{ Known; Lines }`; baseline lowered 2 -> 0 for the file. Harness floor green.

## Validation criteria

- [x] A stranded count at or above the threshold files a publish request
      automatically at a task boundary, with the threshold named as the reason.
      (P1/P2 pure; Q3 live: `REQUESTED: stranded threshold ...` then
      `DUE: requested: stranded threshold ...`, publisher ran.)
- [x] A stranded count below it changes nothing — an ordinary day still cuts one
      release, proven by an arm that runs a boundary under the threshold and
      shows no request was filed. (P3 pure; Q1 live: exit 0, no request file,
      no publish, threshold never mentioned.)
- [x] The request a threshold files is indistinguishable downstream from one a
      user report files: step 6.5 honours it and the watermark is consumed.
      (Q3: request file consumed, watermark stamped today at HEAD; Q4: a SKIP
      leaves it standing for the next push, like a hand-filed one.)
- [x] The threshold and its reasoning are a named constant, and
      `test\win32\daily-publish.ps1` covers both sides of it.
      (`-StrandedThreshold = 30` with its reasoning in the param block; P9.)
- [x] `go-loop-health.ps1` still reports `publish=ok+<n>` with the same meaning.
      (Untouched; read back `publish=ok+37` after the change.)
