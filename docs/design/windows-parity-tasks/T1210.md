# T1210 - Apps & Features shows the release version, but nothing checks a real install

## In plain terms

The number in Apps & Features used to be one nobody publishes, and T1205 fixed
that. What proves the fix today is the recipe, not the meal: we check that the
installer script asks for the right number and that the built package carries
it. Nobody has installed a real Ghoztty and read the number back off the
machine, so if Windows ever ignored the setting we would not find out from a
test.

## Where the coverage stops today

T1205 wired `ARPDISPLAYVERSION` (the marketing version, e.g. `1.35.0`) beside
the load-bearing `ProductVersion` (the `yy.m.dNN` sequencing number). Three
things check it:

1. `dist/windows-installer/build-msi.sh` reads the property back out of the
   COMPILED package and fails the build if it is missing or wrong.
2. `test\win32\release-artifacts.ps1` A20-A22 assert the wiring statically, so
   it cannot be deleted on a box with no Docker.
3. Nothing else.

(1) only runs where Docker does. Neither proves the LAST hop: that Windows
Installer honours the property and Apps & Features displays it. That hop needs
a real `msiexec /i` of a real package, and installing one here would replace
the user's Ghoztty — this repo's first non-negotiable.

## What would close it

Either of these, not both:

- Fold the check into the clean-machine install walk that already gates the
  cutover: after the user installs a release, read
  `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\*` for the Ghoztty
  product and assert `DisplayVersion` equals the semver in the MSI's file name.
  `scripts\ghoztty-cleanup.ps1 inventory` already enumerates ARP registrations,
  so the reading half exists.
- Or install the TEST-IDENTITY package (`build-msi.sh --test-identity`), which
  has a distinct product name, install dir and UpgradeCode precisely so it
  cannot collide with the user's install, and assert the same registry value
  before uninstalling it. This is the version a harness could run unattended,
  and it depends on Docker being available to build the package (T1189).

## Goals

- [x] Read the number Apps & Features shows off a real install, not off the recipe
- [x] Hold it against the package that installed it, naming both surfaces
- [x] Keep the sequencing number separately asserted
- [x] Stop install-walkthrough asserting the defect as correct (its B4 compared
      DisplayVersion to ProductVersion, which only passed because of the bug)

## What landed (2026-10-22)

The first read answered the question the task was filed to ask, and the answer
was no: the user's installed win-v1.43.3 declares `ARPDISPLAYVERSION=1.43.3` in
its cached package (`C:\WINDOWS\Installer\82974b4.msi`) and Apps & Features
shows **26.10.2290**. Windows Installer does not recognise that property; the
fix T1205 shipped never reached the registry. Filed as **T2168** (P1).

Neither route the task proposed was needed to see it. There is already a real
install on this box, and its registry entry and cached MSI can both be read
without touching it. So:

- `scripts\lib\ArpVersion.ps1` - the verdict (three checks: `display`,
  `sequencing`, `unfused`), each line naming the surface it read, plus
  read-only readers for the Uninstall key and the MSI Property table.
- `scripts\arp-version-check.ps1` - the CLI. Exit 0 agree / 1 mismatch /
  3 not installed. Read-only; safe against the user's install.
- `test\win32\arp-version.ps1` - A pure fixtures, B the CLI against a fixture
  HKCU Uninstall key + a fixture MSI, C the user's real install, read-only.
  Red on C1 only, by design, acked to T2168 (`guard-ack`); new guard row
  `arp-version`.
- `test\win32\install-walkthrough.ps1` - `Get-ArpEntryVersion` now reads the
  REGISTERED ProductVersion (the `Version` DWORD) for every "which build is
  installed" check (B4, C5, D4, D6, E4), and a new **B4b** runs the same
  verdict against the walked package.

## Validation criteria

- [x] A real installed package's `DisplayVersion` is read off the machine and
      asserted to equal the release semver, by a harness or by a documented
      step of the install walk. - `test\win32\arp-version.ps1` C1 against the
      user's installed Ghoztty (read-only), and install-walkthrough B4b against
      the walked package. C1 is RED today, correctly: that is T2168.
- [x] The check names what it read and where, so a failure says which surface
      disagreed rather than "mismatch". - A5/B5 assert the FAIL line carries
      both numbers, the registry key and the package path; live output:
      `FAIL display: Apps & Features shows '26.10.2290' (registry DisplayVersion), but ARPDISPLAYVERSION in the package is '1.43.3'`.
- [x] The `ProductVersion` sequencing number is asserted to be UNCHANGED by
      that check — display and sequencing must not be re-fused into one value.
      - `sequencing` and `unfused` checks; A6/A7 prove each goes red on its own
      shape. Live: sequencing OK (26.10.2290), unfused OK.

Runs: `arp-version.ps1` 18 pass / 1 fail (C1, the defect);
`-NegativeControl` adds exactly its one failure. Harness floor (scoped) green
after re-running `stderr-capture-audit.ps1` (the harness's first shape merged a
native stderr into a file - fixed with Start-Process redirection). argv-hazard,
unroll-count, unwired-hook audits ALL PASS. No zig source changed, so no zig
lane was run. **install-walkthrough NOT RUN**: its act D puts the Windows
Installer's dialog on the user's interactive desktop, which go.md forbids while
the user is present; it is an advisory row, and its B4b will read red until
T2168 ships anyway.
