# T1649 - A floor lane kills a CONCURRENT run's WebView2 hosts, so an overlapping lane can go red for somebody else's sweep

## In plain terms

Two test runs can share this machine at the same time, and one of them tidies up
by killing browser processes it thinks it left behind. It cannot tell its own
from the other run's, so it kills both — and the other run's tests then fail for
a reason that has nothing to do with the code being tested. The same mistake was
just fixed for the test programs themselves; this is the other half of the
cleanup, still unfixed.

## Goals

- [x] A lane's WebView2 sweep can only reach hosts owned by its OWN test binaries
- [x] A negative control shows a concurrent run's host surviving the sweep
- [x] `test\win32\floor-lane-webview-settle.ps1` carries it, so the guard row keeps it standing

## Summary

Sibling of T1648, unfixed by it. Invoke-WebViewLaneSweep kills every msedgewebview2.exe whose command line carries the shared profile prefix ghoztty-wv2test- or --webview-exe-name=<a lane test binary>. Both markers are shared by every concurrent run, so a soak round ending its lane kills the WebView2 hosts a turn's win32 lane is using right now - the same cross-kill T1648 fixed for the test binary itself, on a different resource, with the same symptom (a red lane that is somebody else's sweep). The fix has the same shape: a host counts as this run's only when the test binary that owns it does (profile pid in this run's own set, or image under this run's build roots per Get-LaneBuildRoot). Remove-WebViewLaneProfile is already safe - it skips a directory whose owner pid is alive.
