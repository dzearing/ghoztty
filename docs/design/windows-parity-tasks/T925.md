# T925 - The notice-banner assertions in session-relaunch-notify fail under box load

## Summary

Arm E's E3/E4 read every restored pane's banner immediately after Wait-Leaves returns 3 leaves. The two panes that OWN a banner have theirs back at layout-restore time, but the third pane's notice banner is emitted later, by the restore policy on the pane's IO thread - so under load the read lands in the gap and reports bannerless=1/noticed=0. Failed twice in a row on 2026-08-17 with the box busy, then passed cleanly; a DIAG dump of every leaf's banner was added in the same turn so the three possible stories are distinguishable. Fix: wait for the notice banner (or for a stable read) rather than sampling once.

## In plain terms

A test that checks the "your session was interrupted" notice after a restart
sometimes failed when the computer was busy, even though the feature worked:
it looked before the notice had arrived. It now waits for the notice, so the
test only goes red when the feature is actually broken.

## Goals

- [x] The E arm waits for every restored pane's banner before scoring it
- [x] The script passes on a quiet box and on a fully loaded one

## Resolution

Already fixed in passing by **fedd35a59** (T922), which added
`Wait-BannerSettle` to `test\win32\session-relaunch-notify.ps1`: arm E now waits
until every restored pane holds a banner before E3/E4 count them. The settle
condition asks only that each pane has *a* banner, never which one, so it cannot
mask a real precedence regression. T977 (8a9481d9a) then added E4b, which bounds
the settle time at 15s, so a notice that arrives late is still caught.
No code change in this task. The validation below is what the task was owed.
