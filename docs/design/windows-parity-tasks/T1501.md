# T1501 - A test fixture can plant a filename Windows quietly renames, so the harness proves less than it says

## Summary

Measured on this box during T1499: Set-Content -Path (Join-Path $d '._.') creates a file named '._' - PowerShell strips the trailing dot and reports success - so a fixture that means to plant an AppleDouble root sidecar plants something else and the harness is quietly weaker than it reads. That is exactly what happened to T1436's torn-package fixtures: they reproduced the real package's contents "exactly" apart from the one name that defeats the delete, so every arm stayed green while the real heal could not delete the real package, and the box went red for four lanes. The fix in T1499 was local (write fixtures through an extended '\\?\' path). What is missing is the general guard: a meta-audit over test/win32/ that flags a fixture whose planted filename PowerShell cannot create verbatim - a trailing dot or space, a reserved device name (CON, NUL, AUX, COM1..9), a name differing from its intended form only by characters the parser strips - and says which call site to convert. Same shape as the existing script-wide audits (body-complete, verdict-exit): cheap, non-interactive, and it fails on a planted example of its own.

## In plain terms

Some of our automated tests set up fake files before they run. Windows quietly
renames certain file names (one ending in a dot, for instance, loses the dot),
so a test could think it had set up a tricky file when it had actually set up a
harmless one, and then pass while the real problem went unnoticed. That
happened once and let a real breakage through. Now a standing check reads every
test and flags any that would plant a name Windows will rewrite.

## Goals

- [x] A standing check finds a test that plants a filename Windows rewrites
      (trailing dot or space, reserved device names like CON or NUL)
- [x] It finds the exact shape that bit T1436 - the name two hops from the
      write, through a loop and a helper function - and says which line to fix
- [x] It stays quiet on the remedy (`ConvertTo-ExtendedPath` / `\\?\`), on a
      deliberate `# fixture-name-ok: <why>` line, and on ordinary prose
- [x] It runs on its own as part of the harness floor

## Design

- `test\win32\lib\FixtureNames.ps1` - the scanner. Parses each script, finds
  every call that creates or names a path (New-Item, Set-Content, Out-File,
  Copy/Move/Rename-Item, Join-Path, `[IO.File|Directory|Path]::` writers, `>`
  redirections, and any same-file helper whose parameter flows into one of
  those), and follows the literal through `$x = ...`, `foreach ($x in ...)`
  and helper call sites (named and positional), bounded at depth 4. The
  segment rule and the node walk are a small compiled helper (Add-Type): the
  pure-PowerShell walk took 137 s over the suite, the compiled one ~20 s.
- `test\win32\fixture-name-audit.ps1` - the harness-floor member (row in
  `scripts\lib\HarnessFloor.ps1`).
- Known limit, by design: a name built by `+` from pieces that are each
  harmless (`'._' + '.'`) is not followed, nor is a name from a file read at
  run time. The sweep is for the literal-fixture class that bit T1436.

## Validation criteria

- [x] Ground truth on this box: `Set-Content` of `._.` plants `._`; the same
      write through `\\?\` plants `._.` (A1, A2 of fixture-name-audit.ps1).
- [x] The rule classifies 16 segment shapes the way Windows treats them (A3/A4).
- [x] The T1436 pre-fix fixture is a finding at the line `._.` is written on,
      naming the Join-Path that takes it; a positional helper argument too (B1-B5).
- [x] Each direct write shape (New-Item, WriteAllText, `>`, Out-File, an
      assigned variable, Copy-Item -Destination) is a finding (B6).
- [x] Remedy, `\\?\`, pragma, `-Value` content, prose, wildcards are clean (B7).
- [x] The live suite (628 scripts) is clean, and floor-lane-cache-heal.ps1 is
      clean only because of its remedy: strip it from a copy and the same `._.`
      is a finding (C1-C5).
- [x] Wired into the harness floor, not pending (D1, D2).
- [x] `-NegativeControl`: a `._.` planted in the live lib\VtText.ps1 is caught
      (exactly 1 inverted FAILURE) and the file is restored byte for byte.
