# T2198 - Every Windows release ships a signed Ghoztty-Setup-<version>-x64.exe beside the MSI

## Summary

T1247 split, piece 2. release-windows.yml builds the T2197 bootstrapper AFTER wixl has produced the MSI (it embeds it), signs it through T1203's certificate hook (unsigned-and-says-so when no certificate is configured), and attaches it to the release. The MSI stays a release asset: it is the in-app updater's payload (T1178) and the managed-deployment download. test\win32\release-artifacts.ps1 asserts the new asset and that its embedded MSI is byte-identical to the published one.

## In plain terms

Every Windows release page will now offer Ghoztty-Setup-<version>-x64.exe
beside the MSI. It is the friendlier installer from T2197: it runs the install
itself and, when Windows refuses (another installation still running), says
why in Ghoztty's own dialog instead of flashing a window and vanishing. It
carries exactly the published, signed MSI, so both downloads install the same
bits. The MSI stays for the in-app updater and for managed deployment.

## Goals

- [x] The release build makes the setup exe from the signed MSI and signs it too
- [x] The build refuses to ship a setup that does not carry that exact MSI
- [x] The release publishes it (new release and re-upload) and its notes say which to download
- [x] Building the setup never disturbs the already-signed app files

## Design notes (2026-11-24)

- **Built after the MSI is signed**, in `build-release-artifacts.sh` step 2a,
  so the embedded package is the published one. Shared script, so fork-ci's
  per-commit packaging run builds it too, before any release depends on it.
- **`zig build setup`** (new named step in `build.zig`) installs ONLY the setup
  exe. By then ghoztty.exe, the twin and the agent in zig-out/bin are signed,
  and a full `zig build` would copy the unsigned cached images back over them
  under the portable ZIP and the symbol store. Same flag set as the exe build
  (`ZIG_ARGS`), so target, mode and FILEVERSION match.
- **Embed proof** is `dist/windows-installer/verify-setup-embed.py`: the MSI's
  bytes occur in the exe exactly once. Run before signing the setup and after
  (a signature appends to the image and must not touch the payload).
- **Signing** goes through `sign-artifacts.sh` like every other asset:
  unsigned-with-a-banner while no certificate is configured (T1203).
- Not done here: the setup's PDB is not added to the symbols asset (a crash
  in a 1 MB dialog front door is far less likely than in the terminal); the
  website's download button still points at the MSI - filed as T3703.
- **Found on the way:** `scripts/fetch-symbols.ps1` died under Stop when the
  debug twin, run from a Ghoztty pane, printed its GHOZTTY_IPC_SOCKET note on
  stderr; release-symbols D5 was red for it. Fixed by running that one native
  call under Continue.
