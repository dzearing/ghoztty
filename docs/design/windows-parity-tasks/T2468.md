# T2468 - Composition step 4: chrome (sidebar, strips, desk, shadows, dividers) painted with Direct2D into CompositionDrawingSurfaces or composition primitives, DropShadow for blade shadows

## Summary

T2360 step 4. Oracle: chrome pixel acceptance (Get-TestWindowPixels -Sync analog for visuals) matches today, and the win32 design-system tokens are unchanged.

## In plain terms

The parts of the window around the terminals - the coloured desk, the card
shadows and corners, the dividers and the strips - are still drawn by hand
into the window on every change. This moves them onto the system compositor
the way the terminals themselves moved, so they can glide with the cards
instead of being redrawn behind them. It is too big for one step, so it is
split into four.

## Design and split (2026-10-30, lane A)

Read on claim: steps 2 and 3 (T2466, T2467) put each PANE's content on a
DirectComposition target on the pane's own child window. The chrome lives on
the TOP-LEVEL window and is GDI: `PaneDesk` composes desk + cards + lights
into a DIB and BitBlts it (`Window.paintPaneDesk`), and dividers, stack
strips and names, gutter bar, rearrange headers and the caption are GDI
painters wrapped by `paintAlphaCorrect`. The sidebar and strip faces are
their own child windows and are not in this step.

The fact that shapes the split: a DComp target's visual tree composes ABOVE
the window's own redirected GDI pixels (`topmost=FALSE` only puts it below the
CHILD windows). So the first visual attached to the top-level target hides
every GDI painter under it; the chrome cannot be moved piece by piece in place.
The order that keeps the window whole at every step:

1. **T2508** host: target + D2D context + device loss, no visual attached.
   Proves the ordering on screen with a WGC ghost capture (the T2463
   technique, which works with the user present).
2. **T2509** the desk/cards buffer becomes the bottom visual.
3. **T2510** every remaining GDI painter composes as an overlay visual above
   it, from a persistent buffer with real erase semantics (`paintAlphaCorrect`
   source-overs partial passes, which a replaced layer cannot do).
4. **T2511** shadows become compositor shadows that move with their card,
   which is where this meets step 5 (T2469, now dep on T2508).

Direct2D draws into the surfaces where a painter is ported natively; the
first moves upload the existing CPU-composed pixels (the T2467 pattern), so
the pixels are byte-identical to today while the plumbing is proved.
