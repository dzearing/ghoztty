# T1794 - Input-desktop harnesses run over a user's fullscreen app and steal their keystrokes: Assert-TestDesktopCapability -Interactive must refuse (SKIP) when a fullscreen/foreground app is in use

## In plain terms

Some of the automated screen tests have to draw on the real screen and type real
keys. On 2026-09-27 they did that on top of the user's fullscreen game, so the
game lost keystrokes and the tests measured the game instead of the terminal.
Those tests must see that someone is using the machine and skip themselves.

## Summary

`Assert-TestDesktopCapability -Interactive` (test/win32/lib/TestDesktop.ps1)
lets a declared `@input-desktop-exception` script run on the user's input
desktop whenever that desktop is reachable. It never asks whether a person is
using it. On 2026-09-27 translucent-window.ps1 and the new background-blur.ps1
(T1788) ran over a fullscreen game: the captures were invalid and the test window
took the user's keystrokes.

Fix: the shared user-presence predicate T1795 describes (recent input via
`GetLastInputInfo`, or a foreground window that is fullscreen or not ours), and
`-Interactive` SKIPs with a named reason when it is true. Never wait, never fail.
T1795 depends on this card; this is the harness half of it.

## Goals

- [x] One shared user-presence predicate (`test/win32/lib/UserPresence.ps1`)
      that T1795 can reuse for the soak daemon
- [x] `Assert-TestDesktopCapability -Interactive` skips, with the reason,
      whenever somebody is using the box
- [x] The two declared scripts that do not go through that function
      (`rdp-session`, `test-desktop-spike`) gated too

## What landed

`lib\UserPresence.ps1`: `Resolve-UserPresence` (pure decision),
`Get-UserPresence` (live probe) and `Assert-UserAbsent` (the gate). Present
when ANY of: keyboard/mouse input within `GHOZTTY_TEST_PRESENCE_IDLE_SECONDS`
(default 300); `SHQueryUserNotificationState` says BUSY / D3D fullscreen /
presentation / fullscreen app; or the foreground window covers its monitor and
is not the shell. A foreground window from this repo (a zig-out test build)
does not count for the two fullscreen signals; D3D-exclusive and presentation
mode still do. Decision made here (mechanism, not experience): "foreground not
ours" alone is NOT a presence signal - the user's own terminal is a foreign
window nearly always, so that would be a blanket skip; idle time covers it.

`Assert-TestDesktopCapability -Interactive` calls the gate before its probes
(the real-input probe is an injected event and would read as recent input).
`rdp-session.ps1` (interactive mode only) and `test-desktop-spike.ps1` call
`Assert-UserAbsent` before they stop, create or launch anything. Coverage row:
`UserPresence.ps1` added to guard-due's `test-desktop` row.

## Validation criteria

- [x] With a fullscreen foreign window in the foreground, an `-Interactive`
      script SKIPs and names the reason, without creating a window.
      LIVE, not staged: the user was playing Valheim fullscreen
      (`valheim.exe`, `UnityWndClass`, covers monitor, QUNS=2) during this
      turn. `translucent-window.ps1`, `background-blur.ps1` and
      `test-desktop-spike.ps1` each printed `SKIP ALL: user-absent ... the
      shell reports a fullscreen app in use`, exit 0, zero repo ghoztty
      processes before/after, and the foreground was still valheim afterwards.
      Same case constructed in `test-desktop-harness.ps1` B2 (fullscreen
      foreign window on an idle box reads present).
- [x] With recent user input, the same script SKIPs. B2: `Resolve-UserPresence
      -IdleSeconds 5` reads present; the forced-present child of an
      `-Interactive` script prints SKIP ALL and never reaches its body.
- [x] A negative control (predicate forced false) still runs the script. B2:
      the forced-absent child runs to `REACHED THE END`; idle-with-nothing-
      fullscreen and our-own-fullscreen-window both read absent.
      `test-desktop-harness.ps1` ALL PASS (95), stamped.
