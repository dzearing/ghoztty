# T1844 - Panes cannot be dragged into or out of the Windows pane sidebar: no row drag source, and the sidebar is not a stash drop target

## Summary

Follow-up of T1828 (Mac 597a193cc, design 'Drop resolution'). Rows drag through the existing pane drag machinery (to the grid = restore/move at the drop target, to the stash section = stash at that index / reorder, to another window = move). The sidebar (rail included) is a .stash drop target with precedence tab bar > sidebar > window edge band > pane zones; dropping on the grid section stashes at the top; an empty 'Drop to stash - it keeps running' slot shows during a drag with nothing stashed. Cross-window drop onto another window's sidebar moves and stashes there in one step.

## In plain terms

On a Mac you can grab a pane's row in the sidebar and drag it: down into the
stash to put it away, back onto the grid to bring it out exactly where you drop
it, or onto another window's sidebar to send it there. On Windows the sidebar
only answered clicks. Now its rows and rail tiles drag the same way, the
sidebar is somewhere you can drop a pane, and while you drag with nothing
stashed it shows an empty "Drop to stash - it keeps running" slot so you can
see where to let go.

## Goals

- [x] the sidebar (rail or panel, or the open card) is a drop target that stashes, at the gap between stashed rows nearest the pointer
- [x] the tab strip still wins over the sidebar, and the sidebar wins over the window's edge band and the panes under the open card
- [x] a row or rail tile is a drag source: onto the grid restores the pane there in one step, onto the stash reorders it
- [x] dragging the last pane on screen into the stash is refused, and not previewed
- [x] a pane dropped on ANOTHER window's sidebar moves there and is stashed in one step
- [x] an empty "Drop to stash" slot shows in every sidebar during a drag with nothing stashed
- [x] Escape cancels a drag that started from the sidebar; the open card does not fold away mid-drag

## Design (win32)

- **One resolver, one new target** (`pane_drop.zig`): `Target.stash{window,
  index}`; `Candidate` gains `sidebar_rect` (null while hidden - a sidebar the
  user hid is not a target) and `stash_row_rects`. Precedence after the strip
  and before the edge band, so the open card, which hangs OVER the grid, never
  means a pane. The index counts stashed rows whose vertical midpoint is above
  the pointer: the grid section is 0 (top of the stash), past the last row
  appends.
- **Preview** (`drop_highlight.zig`): `.stash` is a caret across the rows on
  the gap (the new-tab caret's vocabulary); with nothing stashed, `.stash_slot`
  washes the empty slot. Not drawn when the drop would be refused
  (`can_stash`). Shown topmost so it is never under the open card's popup.
- **Order** (`pane_stash.markAt`): the stash order is the pane's `stash_seq`, so
  a drop at a gap renumbers the stash bottom-first; a stashed pane dragged
  within the stash is placed among the others.
- **Source** (`PaneSidebar.zig`): a press on a row or tile that travels past the
  drag threshold hands the pane to `Window.beginSidebarDrag`, which starts the
  existing pane drag live (same capture, preview, dwell and commit). The row
  names its pane explicitly, since a stashed pane has no slot to be found by.
- **Commit** (`Window.zig`): in its own tab, `stashPane` (its focus rules and
  last-pane refusal) then `markAt`. From another tab or window, Mac's one-step
  move-and-stash: inserted at the top level on the right (the slot a restore
  returns it to) and stashed in the same commit, through the existing
  `commitCrossTabDrop` / `commitCrossWindowDrop` relocation (no session close
  intent). Placed anywhere else, a stashed pane is unmarked in the commit that
  places it (Mac's `PaneMoveCoordinator.apply` rule), so restore-by-drag is
  one step. The tab a pane left is normalized (invariant 1) and its active
  pane re-picked from what is on screen.
- **Escape** is caught in App's message loop while a drag is live: the keyboard
  is on whatever pane had it, and a sidebar drag runs outside rearrange mode,
  whose own Escape would not apply.

Not in this task: the all-windows scope's "drop on another window's group in
this sidebar" (that scope is T1829), and a grab handle outside rearrange mode
(T1830). Both use this target unchanged when they land.
