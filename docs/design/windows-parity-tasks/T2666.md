# T2666 - Hand DWM the new frame and the content in the same latch on an edge drag: lay out and draw at the new size in WM_WINDOWPOSCHANGING on every edge, but hold the terminal Present, the viewer page bounds and the bar paint until the end of the message, right before the frame change, and step past a latch that would fall between them

## In plain terms

While you drag the window's edge, the window's outline and what is inside it
reach the screen on different refreshes, so for an instant the terminal, the
page and its address bar sit out of line with each other. This makes them
arrive on the same refresh, so a drag looks like one solid window resizing.

## Goals

- [x] the terminals draw at the new size during the pre-layout but hold their swap until the end of `WM_WINDOWPOSCHANGING` (`Surface.burstHoldBeforeSwap`)
- [x] the viewer's page bounds and its address bar paint go out at that same moment (`ViewerPane.burstHold`/`burstFlush`)
- [x] when DWM's clock says a latch would fall inside the burst, wait past it first (`resize_burst.stepPast`, unit-tested)
- [ ] film it on a lit display and score it against T2659's baseline; make it the default if it wins
- [ ] carry it to the left and top edges (the origin moves there; follow-up once the film says the burst works)

## Summary

T2659 measured why content and frame disagree: DWM takes whatever was submitted by a latch about 3.4 ms before each compose, and anything later waits a whole compose. Post-layout (default) the terminal presents ~9 ms after the frame change and the bar paints in WM_PAINT after the compose, so a latch always falls between them (content one compose late). Pre-layout (GHOZTTY_RESIZE_PRELAYOUT_SHRINK) presents ~4.8 ms BEFORE the frame change, so a latch splits them about 58% of the time (content one compose early, 38/65 bad). Fix: draw early, but submit everything visible in one burst at the end of WM_WINDOWPOSCHANGING (gap ~1 ms), and when DwmGetCompositionTimingInfo says a latch falls inside that burst, wait it out first. Evidence and timelines: T2659 progress log.

## Details

How to read a film against the latch: T2659's scratch timeline joined each
`frames.txt` compose stamp with the trace's `msg=0x85` (frame) and `present`
lines. Measured on 2026-11-03 (120 Hz, composes 8.33 ms apart):

- a frame change 4.9 ms or 3.55 ms before a compose made it; 3.15 ms, 2.3 ms
  and 2.0 ms did not - the latch is ~3.4 ms before the compose stamp;
- a present 6.8 ms before made it, 3.46 ms before did not - same latch;
- the bar paints in WM_PAINT (msg 0xf), which the size loop runs AFTER the
  compose that shows the frame, so the bar must paint inside the pass;
- the page (WebView2 child HWND, solid content) only needs its bounds set
  before the latch, which the batch already does - that is why it "leads".

Also measured: `GHOZTTY_COMP_PRESENT=1` alone (terminal on a DComp target on
its child HWND) is identical to the default (31 bad) - it is not a
redirection-surface effect; COMP_PRESENT+COMP_CHROME+COMP_PANE_TREE puts every
pane one compose behind the frame together (54 bad), the same latch problem
for the window's whole tree.
