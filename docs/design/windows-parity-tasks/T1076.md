# T1076 - Nothing ever reads a published release's assets back, so a broken download is only found by whoever downloads it

## Summary

The release pipeline verifies what it BUILT (dist/windows-installer + test\win32\release-artifacts.ps1) and what it DELIVERED to local install locations (deliver-windows-build.ps1), but nothing asks GitHub what it is actually serving. T1065 had to hand-roll that readback in a scratchpad script to close its own validation criteria: download the win-v tag's MSI + ZIP, assert Ghoztty/ghoztty.com is in the ZIP with PE subsystem 3 beside a subsystem-2 ghoztty.exe, and read the MSI File table through the Windows Installer COM API (New-Object -ComObject WindowsInstaller.Installer -> OpenDatabase -> OpenView 'SELECT FileName, Version FROM File'), which needs no Docker and no msitools. That script should be scripts\verify-release-assets.ps1 with an acceptance harness, run as the last step of every release.

## In plain terms

When a Windows release goes out, nothing ever downloaded it back to check it
works: a broken installer or zip was only discovered by whoever downloaded it.
Now every release is fetched back from GitHub as soon as it is live and
checked file by file. If it is broken, the publish log says so, naming the
problem.

## Goals

- [x] `scripts\verify-release-assets.ps1`: download a win-v release's MSI + portable ZIP and check what GitHub serves (assets present + sizes, ZIP layout + PE subsystems, MSI File/Property tables via the Windows Installer COM API, ZIP/MSI one build, MSI built from the tagged commit)
- [x] run it once per release, from daily-publish's confirmation pass (advisory, beside the T1312 scan)
