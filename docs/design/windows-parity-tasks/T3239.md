# T3239 - Agent-held pane flood ingest is bimodal on Debug since 2026-11-17: pane-ingest-ab B lands at 8-9 s or 20-28 s on a quiet box while local A sits at a steady ~5 s, so median agent/local reads 1.8-4.8x against 1.75x

## Summary

Found by T3172 (2026-11-18, lane b, Debug zig-out at 2b237eb9f + T3172's harness, every run solo). With pane-ingest-ab now scoring the median of 3 interleaved samples per arm, ten runs gave:

- A (local ConPTY): 4670-5642 ms in every one of 30 samples. Steady.
- B (agent-held): bimodal. Either 6.6-9.9 s or 13-28 s, with 2-3 samples of a run often all in the slow mode. Medians 1.18x, 3.72x, 5.09x, 1.52x, 1.42x, 3.96x, 3.14x, 4.83x, 1.77x, 1.79x.
- The box was quiet for the second set (box CPU 4-24% throughout, logged every 5 s), so this is not load from the other lane.

T3168 (2026-11-16 at 94f84640c) measured B steady at 9.3-10.4 s and A at 5.3-9.8 s. What changed in between, all on 2026-11-17: T3060 (09c94632b, the ConPTY reader batches; probably why A is now a steady ~5 s), T3061 (5059acb10, renderer wakes once per frame), T3068 (2b92c79da, a flooded pane yields to keys/repaints between slices). The relay-throughput guard does not cover those files, so none of those turns had to run pane-ingest-ab.

Do next: A/B each of the three commits (revert one at a time on a scratch build, 3+ runs each with the median harness) to find which one introduced B's slow mode, and whether the good mode's ~1.6-1.8x is just A getting faster. Read the relay meters (`-KeepArtifacts`) of a slow-mode sample against a fast one to see which leg stalls. If the slow mode is in termio/Remote or the app's ingest path, add those files to the relay-throughput guard's Covers so the next change to them has to run it.

## Outcome (2026-11-19)

**No commit caused it.** The program in an agent-held pane was running in Windows
efficiency mode (EcoQoS). The holder's own opt-out (T1465, `power.disableThrottling`)
is not inherited: `GetProcessInformation` on a live tree read control=1 on the
holder and control=0 ("system decides") on its conhost, shell and the shell's
children. Whether the classifier clamped the writer varied with box state,
which is why the same code drifted from 9-10 s (T3168) to 11-16 s here.

Bisect (Debug, solo runs, CPU ~4%; B medians): HEAD 14.2/16.1 s; HEAD with T3068's
yield disabled 12.2/14.8 s; before T3060 (ccc103ce7) 13.6/13.4 s; T3168's own
commit 94f84640c 14.7/11.6 s on the current harness and 16.4/14.1/13.9 s on the
old one. Release sandbox, unchanged: 2.17x/2.00x/2.87x. Experiments on that
unchanged release build, done from outside the process: holder tree hard-pinned
to P-cores 0.84x/0.85x; HighQoS on every descendant 0.73x/0.84x; HighQoS on conhost
alone 1.93x; HighQoS on the writer alone 0.98x.

Fix: the PTY job gets a completion port and one thread that opts every process
out as it joins the job (`JOB_OBJECT_MSG_NEW_PROCESS` -> `power.disableThrottlingFor`).
This is event-driven, so it costs nothing while idle, and it does not touch
affinity, so the shell still has the whole machine.

## In plain terms

When a terminal pane is kept alive by the background session keeper (the normal
setup), whatever you ran in it (a build, a log dump, Claude Code) could be run
by Windows in its slow "efficiency mode", because nothing in that pane's process
family owns a window. A big burst of output took two to three times longer than
in a plain pane. Now every program started in such a pane is opted out of that
mode, and the two kinds of pane are equally fast.
