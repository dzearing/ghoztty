# T704 - A REMOTE --shell=wsl.exe --command= pane has T656's defect: the agent still spawns wsl -- <cmd>

## Summary

windowsCommandArg in the agent still answers -- for wsl, so a cross-machine WSL pane gets the whole command line as one quoted word

## In plain terms

The WSL problem T656 just fixed for local panes still exists for a pane running
on ANOTHER machine. Open a remote window with WSL as its shell and a command to
run, and instead of the command's output you get `command not found` naming the
whole command line.

## Goals

- [x] A remote WSL pane runs its `--command=` instead of answering
      `command not found`
- [x] The agent's own convention stays the agent's — this does not import the
      local table

## Details

T656 fixed `wrapShellCommandArgv` (`src/apprt/ipc/args.zig`), which is the
LOCAL table — and since T468 the local-agent path sends that wrapped argv as
`OPEN.argv`, so a local WSL pane is now correct on both paths.

A CROSS-MACHINE agent deliberately applies its OWN convention (CLAUDE.md: "a
cross-machine agent is a different machine and applies its own"), and that
convention is `windowsCommandArg` in `src/remote/agent/pty_child.zig:1133`,
which still answers `--` for wsl:

```zig
if (std.ascii.eqlIgnoreCase(base, "wsl")) return "--";
```

So the agent spawns `{wsl.exe, --, "<the whole command string>"}` — byte for
byte the shape T656 removed locally, with the same outcome: `wsl --` hands the
rest of the WINDOWS command line to the distro's default shell as written, the
quoting Windows applied to a spaced argument survives into the distro, and bash
looks for a program literally named `"echo hi"`.

The comment above it states the reasoning that made this look right — "`-e`
would exec the string as a bare binary with no shell parsing" — which is true of
`-e "<one string>"` and NOT of `-e /bin/sh -c "<cmd>"`. That is the fix shape,
and it needs a signature change: `windowsCommandArg` returns ONE flag, and the
wsl row needs three argv elements. Every other row is genuinely one flag, so
widening that return type for one row is the design content here.

Note the agent's rows do NOT keep the shell alive (`cmd /c` exits with its
command) — so this is `-e /bin/sh -c`, not the local `-lic "…; exec"` form.
Match the agent's existing convention rather than importing the local one.

## What shipped

`windowsCommandArg` returned ONE flag, and every row but wsl genuinely is one
flag — so the fix is the signature: `windowsCommandArgs` returns
`[]const []const u8`, the elements that go between the shell and the command
string. The wsl row is now `-e /bin/sh -c`:

- **`-e` rather than `--`**, because `--` hands the rest of the *Windows*
  command line to the distro's default shell verbatim, so the quoting Windows
  applies to a spaced argument survives into the distro and bash looks for a
  program literally named `"echo hi"`. `-e` execs an argv.
- **`/bin/sh -c` as the inner interpreter**, because `-e "<one string>"` would
  exec the command as a bare binary with no shell parsing — the inner
  `sh -c` is what gives the command string its parsing back. `/bin/sh` is the
  one binary every distro is guaranteed to have.
- **No keep-alive `exec`**, deliberately unlike the local table's
  `-lic "…; exec \"$SHELL\" -li"`. The agent's rows do not keep the shell
  alive (`cmd /c` exits with its command), and the task's instruction was to
  match the agent's existing convention rather than import the local one.

The two tables stay independent — a cross-machine agent applies its own
convention — so `wsl_inner_shell` is a parallel constant in `pty_child.zig`
rather than an import of `apprt.ipc.args.wsl_inner_shell`.

`docs/claude/remote.md` said the `--command` conventions were "POSIX `-lic`, cmd
`/c`, powershell/pwsh `-Command`, wsl `--`"; it now says what the code does, and
names the keep-alive difference from the local table.
