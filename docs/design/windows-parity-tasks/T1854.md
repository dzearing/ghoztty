# T1854 - drag-perf.ps1 scores 4 and 8 panes with the 2-pane sample: the app prints one drag summary per instance, so 'it got worse with every split' reads 2 waits at 2 panes and 2 at 8

## Summary

Seen in the T1831 sweep (2026-10-11). It fails the same way under --macos-pane-style=flat, so it is not T1831's geometry. Only one drag summary is printed per instance; the drags at 4 and 8 panes produce none, and the script reuses the first sample. Make the summary per drag (or the script launch per count) and fail when a sample is missing instead of reusing one.

## In plain terms

The test that measures how smooth dragging a pane divider is was only really
measuring the 2-pane case: with 4 or 8 panes its drag never grabbed the divider,
so it either re-used the 2-pane number or reported nothing. Now every pane count
gets its own real drag, so a slowdown that only shows up with many panes can be
seen.

## Goals

- [x] every shape lays its panes out so none folds under the minimum size (one tall column)
- [x] one fresh app instance per shape and pane count, so no row can borrow another's sample
- [x] a count whose drag prints nothing is missing from its table and fails section A

## Validation criteria

- [x] Every shape (serial, fanout, batched, tree, treeserial) produces its own drag summary at 2, 4 and 8 panes - `acceptance-parallel.ps1 run -Scripts drag-perf.ps1` (exclusive, Debug, run 20261122-221040): 15/15 rows with resizes/move 2/4/8, section A 3/3 in all three asserted shapes.
- [x] No NO SAMPLE rows and no reused sample - same run; the four reds left are real 0-vs-0 numbers against assertions the T2459 grid hold superseded, filed as T3548 (guard-ack moved there).
