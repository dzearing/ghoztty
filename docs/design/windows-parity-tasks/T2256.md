# T2256 - git-commit-guard push answers a rejected push with pull --rebase, which flattens a main-merge commit into replayed main commits (stopped on a conflict at c2057a810 during T2249); a merge at HEAD needs --rebase-merges or a merge pull

## Summary

During T2249 (lane b, 2026-10-25) the merge commit f5690d6ab (origin/main
370050aed into the branch) was pushed with `scripts\git-commit-guard.ps1 push`.
Lane A had pushed two commits in the meantime, so the push was rejected, and
the guard answered with a plain `git pull --rebase`. A plain rebase drops merge
commits and replays every commit they brought in: it began replaying main's 12
commits on top of origin and stopped at c2057a810 with conflicts (exit 6). It
was recovered by `git rebase --abort` + `git merge origin/<branch>` + push.

Had the replay applied cleanly, the branch would have been pushed with main's
commits rewritten as new shas and no merge commit: the merge-base with main
would not move, so the next main intake would re-evaluate (and git would
re-merge) the same commits. Every main-merge task (T2088, T2249, the next one)
runs this path, and two lanes pushing is the ordinary case now.

Fix: when HEAD's history since the upstream contains a merge commit, retry with
`git pull --rebase=merges` (or a merge pull) instead of a plain rebase, and say
which it used. Test: a section in test\win32\go-loop-guard.ps1 that builds a
local bare remote, a merge commit, a racing push, and asserts the pushed head
still has two parents and the merged side as an ancestor.

## In plain terms

When two loops push at the same moment, the commit guard catches up by replaying
its own commits on top of the other loop's. That is fine for ordinary commits,
but a "bring main into this branch" merge gets taken apart by the replay, so the
branch would quietly forget it ever took main's changes. Now a push that holds a
merge catches up by merging instead, and the merge survives untouched.

## Goals

- [x] A raced push holding a merge commit keeps that merge commit exactly.
- [x] Ordinary commits still catch up by rebase, as before.
- [x] The test proves the old way flattens and the new way does not.

## Decision (mechanism, Claude's call)

Merge pull (`pull --no-rebase --no-ff`), not `pull --rebase=merges`: rebase-merges
re-runs the merge and discards its conflict resolutions, so a big main merge would
stop on the same conflicts again. A merge pull keeps the original merge commit's
sha and every resolution in it, at the cost of one extra merge commit in history.
