# T3578 - Linux L14b: .deb and AppImage packages, and a release-mode tarball built and installed end to end

## In plain terms

Linux could only be packaged as a debug build, and a packaged copy quietly
worked only when started from inside the source folder: anywhere else it failed
to start for want of a library. Now a release package installs and runs from
anywhere, a `.deb` can be built from the same files, and an installed release
copy and a developer build can run side by side without links meant for one
reaching the other. The AppImage moved to its own task (T3658).

## Goals

- [x] a ReleaseFast tarball builds, installs without `--dev`, and runs from any directory
- [x] the packaged binary finds its private `libgtk4-layer-shell.so` through `$ORIGIN`, not a build-tree path
- [x] a dev build alongside the installed release app never answers its `ghoztty://` links or its D-Bus name
- [x] a `.deb` from the same tree: `/usr` layout, Exec lines at `/usr/bin/ghoztty`, real Depends, installs and removes cleanly
- [ ] an AppImage - split to T3658 (WebKitGTK's helper processes have to be relocated into the AppDir)

## Summary

T3343 shipped scripts/linux/package.sh (a relocatable tarball) and its install.sh (~/.local, handler registration, manifest uninstall), validated with a DEBUG package only (test/linux/package-install.sh). This task: build and install a ReleaseFast package end to end (release app id com.dzearing.ghoztty, ghoztty:// scheme, release socket - and prove a dev debug build alongside it never answers its links), and a .deb from the same tree. The AppImage is T3658.

What landed:

- **A defect T3343's test could not see.** Zig's link step gives `bin/ghoztty` a RUNPATH of `.zig-cache/o/<hash>` for the from-source `libgtk4-layer-shell.so` - relative to the current directory. An unpacked or installed package started from anywhere but the repo root failed with `libgtk4-layer-shell.so: cannot open shared object file` (observed this turn from `/`); `package-install.sh` I8 passed only because it ran from the repo root. `package.sh` now moves the library to `lib/ghoztty/`, sets RUNPATH `$ORIGIN/../lib/ghoztty` with patchelf, and drops the developer artifacts (`include/`, `libghostty-vt*`, pkg-config). It writes `.package-info` (version, commit, commit count, mode, arch, staging prefix).
- **`scripts/linux/package-deb.sh`**: tarball -> `ghoztty_<ver>+<count>.g<sha>_<arch>.deb` under `/usr`; Exec/TryExec/ExecStart rewritten to `/usr/bin/ghoztty` and refuses if any other file still names the staging prefix; `Depends` from `dpkg-shlibdeps`; Debug tarballs refused (exit 3). No maintainer scripts: the summary's planned postinst `update-desktop-database` is what the dpkg file triggers of desktop-file-utils / hicolor-icon-theme / shared-mime-info already do for `/usr/share/applications` and `/usr/share/icons`, and Debian policy asks packages to rely on those.
- `setup-distro.sh` installs `patchelf` and `dpkg-dev`.
