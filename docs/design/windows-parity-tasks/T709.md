# T709 - Activity Monitor shows no per-core %CPU and never says which pane owns a process

## Summary

Mac's Activity Monitor (ab79f37c4, 2964c8859) reports %CPU normalised per core AND labels each row with the Ghoztty pane that spawned it, with the session's own CPU promoted to its own column and pane labels made distinguishing. The win32 ActivityMonitor.zig has none of that: no per-core figure and no owning-pane column, so a busy process cannot be traced back to the pane a user would go close. Found by the T684 sweep of already-merged Mac history.

## In plain terms

Open the Activity Monitor on Windows today and the %CPU column reads 0.0 for
almost everything, even while a process is pinning a core - the number was being
divided by the core count, so on a many-core machine nothing ever looks busy.
And when you do find the busy process, nothing on screen tells you which
terminal pane it belongs to, so you cannot go and close the right one. After
this, the CPU number reads the way Task Manager's does, and a new "Window /
Pane" column names the pane each process is running in - with a different name
for each pane, not the same string twenty times.

## Goals

- [x] the table's %CPU shows the per-core figure as reported, not divided by the core count
- [x] a "Window / Pane" column between Memory and Path, sortable, with unattributed rows last
- [x] a process anywhere under a pane's shell is traced back to that pane
- [x] two panes in one tab never render the same label
- [x] the spawned-only filter can ride on attribution when the root pid finds nothing

## Validation criteria

- [x] `formatCpu` prints the per-core reading unchanged - unit test
      `formatCpu: the per-core reading is printed as reported, never divided`
      (none lane, green), pinning the exact 18-core case the divide destroyed.
- [x] Attribution seeds on the pane shell pid and propagates down the ppid
      chain, order-independently, and survives a cycle / a missing parent /
      a pane with no shell - six unit tests in `activity_panes.zig`
      (none lane, green).
- [x] Two panes whose titles are identical get positional labels - unit test
      `paneLabel: lone pane, distinguishing title, positional fallback`, and
      live in section C of `test\win32\activity-pane-column.ps1`, which read
      `"t709win > pane 1"` / `"t709win > pane 2"` off two real shells.
- [x] The column sorts, with unattributed rows last in both directions - unit
      test `less: the pane column groups by label and puts unattributed rows
      LAST`; live, section E drove the header cursor onto the column the panel
      names `pane` and Space produced `sort=pane/asc`.
- [x] A process started inside a pane is attributed to it, and stops being so
      when it exits - section D: `attributed 2 -> 3` on a `ping` started with
      `+send-keys`, and `3 -> 2` after `C-c`.
- [x] The label follows the window the user renamed - section B:
      `+rename --title=t709win` and the panel's next pane line read `"t709win"`.
- [x] `test\win32\activity-pane-column.ps1`: ALL PASS (27 assertions);
      `-NegativeControl`, which asserts the 2964c8859 defect (both panes
      rendering the same label), scores 1 FAILURE as it must.
- [x] Floor: `floor-lane.ps1 -Lane all` green.
- [x] The panel's existing harnesses re-run green over the change:
      `activity-monitor.ps1`, `activity-selection.ps1`,
      `activity-monitor-dialed.ps1`.
