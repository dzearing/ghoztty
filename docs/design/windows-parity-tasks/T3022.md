# T3022 - PA-I08: +new-remote-window dials the remote machine on the GUI thread with no connect timeout, freezing every window for up to ~30 s on an unreachable host (IpcHandlers.zig:810)

## Summary

PA-I08 (audit-1, T2962). src/apprt/win32/IpcHandlers.zig:810 `dialed.* = tcp_dial.dial(alloc, host, args.port, .raw)` (and :796 -> App.openRelayWindow -> relay_dial.dial, App.zig ~:7997) runs on the GUI thread, as the comment at :767-770 admits; tcp_dial.zig:180 std.net.tcpConnectToHost has no bound, then HELLO waits up to 10 s (tcp_dial.zig:147). Cost (estimated, not measured): DNS plus the OS connect timeout (~21 s on Windows for a black-holed host) plus up to 10 s with every window frozen and every other IPC verb queued. Fix: dial on a worker and post the result, as MachineConnectionPool.startDial already does, holding the IPC reply the way awaitSessions does. Risk medium: reply ordering, and error strings must stay byte-identical. Findings: docs/design/perf-audit/audit-1/I-findings.md.

## In plain terms

Opening a window on another machine from the command line used to lock up
every Ghoztty window until that machine answered, which for a machine that
is off or unreachable meant up to half a minute of a frozen terminal. Now
the connection is made in the background: your windows keep working, other
commands keep answering, and the remote window appears (or the same error
message comes back) when the connection settles.

## Goals

- [x] the dial runs off the GUI thread for both the direct (host:port) and relay paths
- [x] every refusal and error sentence is unchanged, and the reply still waits for the window
- [x] quitting the app never waits on an in-flight dial
- [x] an acceptance section that is red on the old code and green on the new
