# T970 - A holder that drops output the agent never released says nothing, so recoverable scrollback is lost in silence

## In plain terms

When a pane prints faster than the safety buffer holds, the oldest of it is
thrown away. Nothing anywhere records that this happened. The pane looks
perfect, and the loss only shows up much later as a hole in the history after a
crash — with nothing to say when or why. This adds the count, so the one loss
that can still happen is one we can see.

## Summary

`ReplayBuffer.append` advances `start` when the ring is full — deliberate, since
the pty reader must never stall on a slow or absent owner. Two different drops
hide behind that one line:

1. **Bytes the owner had not taken yet.** Already reported: the owner sees
   `o.offset > expected` on the next OUTPUT frame and logs `holder replay gap:
   N byte(s) lost`.
2. **Bytes the owner HAD taken but had not released** (the T911 case). Invisible
   from both ends. The owner never sees a gap — it already has those bytes in
   its ring — and the holder says nothing. Yet this is precisely the stretch a
   crash was supposed to be able to recover, so dropping it silently converts a
   guarantee into a coin flip.

Fix: count it where it is known. The holder tracks the last ACKed offset
(`state.replay.ackTo`), so a drop below the acked point is case 1 and a drop
above it is case 2. Log the second with a count, keep a running total, and
surface it — the natural home is the HELLO the next adopting agent reads, so an
adoption can say "N bytes were dropped from the recoverable window while you
were away" the same way it already reports a replay gap.

## Goals

- [x] A drop of un-released output is counted and logged by the holder.
- [x] An adopting agent can report the total, so the loss appears at the moment
      it matters instead of never.

## What landed

The Summary's split ("below the acked point is case 1, above it case 2") turned
out to be the wrong axis once read against the code: `ackTo` advances the ring's
`start`, so NOTHING retained is ever below the ACK - every overflow drop is
un-released by construction. The real split is at what the current owner has
been *sent*:

- `ReplayBuffer.delivered` - high-water mark of bytes written to the current
  owner's pipe, published by the writer under the lock it already takes each
  loop (no extra acquisition on the T1464 hot path), reset when the owner
  disconnects (a drop with nobody attached is the next owner's replay gap, which
  it already reports).
- `ReplayBuffer.dropped_unreleased` - running total of bytes dropped from
  `[start, delivered)`: the owner had them, had not released them, and they have
  left the only place a crash could recover them from. Charged inside `append`,
  so every caller counts it.
- The holder logs it (throttled to one line per 5 s, since a pane that outruns
  its owner drops on every read) and sends the total as an additive trailing
  u64 on `HELLO` - an older holder sends none and it decodes as 0, so no
  protocol bump.
- The adopting agent warns with the total when it is non-zero, beside the
  existing "dropped while no agent was running" line.

Caveat found on the way, filed as **T1721**: an app-launched agent and its
holders have no stderr on Windows (`DETACHED_PROCESS`, no std handles, no file
sink), so both log lines are only readable where stderr is captured today. The
HELLO total is the durable half of this change for exactly that reason.
