## In plain terms

When a pane closed, Ghoztty keeps its empty window to hand to the next pane
(window reuse, which stays on). If the fast drawing path then failed in the new
pane, Ghoztty tried to switch it to the slower drawing path. On a reused window
that switch could fail, and the pane showed nothing even though its shell was
running. Now a pane on a reused window is set up so the switch has nothing to
move. If drawing still can't reach the screen, the pane keeps retrying the fast
path instead of staying blank.

## Goals

- [x] A pane on a reused window that already carries a pixel format keeps its GL context on that window (made with that format), never on a composition helper (`pane_pool.contextHome`, Surface.zig init)
- [x] A reused window whose last pane never drew into it gets its pixel format set before a context goes on it (the old `reused == null` guard skipped it)
- [x] A failed move onto the window logs GetLastError and both formats, and puts the context back on its helper
- [x] A pane that is stranded that way retries the composition path with a backoff (250ms, 1s, 4s, 15s, 60s) instead of staying blank (`OpenGL.compLeaveHelper`/`compBegin`)
- [ ] Why the composition present failed on the user's box (the `compFail` stage + hr line from their log; Remote Desktop suspected) - filed as T3746, needs the user's log
- [ ] The user's "closing a WSL pane does not close the shell" hypothesis, checked on a real WSL pane - filed as T3747 (WSL is opt-in, never booted by the loop). Answer so far, from the code: what is reused is the WINDOW (T2597's parked HWND, its `GWLP_USERDATA` cleared), never a shell; a closed pane's shell lives on only for `undo-timeout` (CloseUndo, T1825)

## Notes on the cause

The context a composition pane makes on its helper is made against the
helper's pixel format. A reused window carries the format its previous pane
set, possibly under a different GL implementation or display adapter (an RDP
session's adapter, or the Mesa fallback after `gl_loader.switchToFallback`).
`wglMakeCurrent` refuses a context on a DC whose format does not match it.
That refusal is the `could not move the pane context` line. A fresh window has no format, so
`setupGlPixelFormat` gives it a matching one, which is why the user's second
WSL pane (a new window) drew. The fix stops relying on the match: a window
that already has a format gets a context created ON it.

## Evidence from the user, 2026-11-25 (supersedes the leads above)

The pane was NOT untypeable: the shell inside was running and receiving the keys, but nothing was drawn. The app log said `could not move the pane context onto its window; this pane may not show` (src/renderer/OpenGL.zig:1579), and Claude on the user's box reported the WSL pane "picked up a leftover window". A second WSL pane then built a new window and worked.

What that chain is, read from the code:

1. **The leftover window is T2597's pane-window reuse** (`pane_pool.zig`, `Surface.zig:961` `takeParkedWindow`): a closed plain-WGL pane's bare HWND is parked hidden with its pixel format already set, and the next pane in that top-level takes it. The GL context is not kept.
2. **The composition present failed** on this box - `compFail` (OpenGL.zig:1560) logs `composition present failed (...) at <stage> hr=0x...` just before; get that line from the user's log, it names the stage. The box was reached over Remote Desktop (see T3738), a prime suspect for DirectComposition failing.
3. **The SwapBuffers fallback then failed on the REUSED window**: `compLeaveHelper` -> `Surface.adoptPaneDrawable` (Surface.zig:1693) skips `SetPixelFormat` because `GetPixelFormat(dc) != 0` (the parked window's format is set for life) and `makeCurrent(dc, hglrc)` fails - most likely because the context was created on the helper with a pixel format that does not match the one the parked window was given. It returns false and the pane is never drawn.

**Window reuse STAYS ON - user directive 2026-11-25: "i NEED window reuse".** The fix must make a pane on a reused window draw; it may not turn reuse off, bypass it for some panes, or fall back to destroying the parked HWND and building a fresh one (that is reuse off by another name, and brings back T2499's per-pane GPU allocation). Fix it inside reuse: (a) the context a pane creates must be compatible with the pixel format its reused window already carries - record the parked window's format in `pane_pool` and create the pane's GL context (and the composition helper's) with that same format, so `adoptPaneDrawable`'s `makeCurrent` succeeds on the reused DC; (b) if `adoptPaneDrawable` still fails, log the GetLastError and the two formats, and retry the composition path rather than leaving a blank pane; (c) find out WHY the composition present failed on this box (the `compFail` line names the stage and hr; Remote Desktop is the suspect) and fix that too, so the fallback is rare. Do NOT offer `GHOZTTY_PANE_REUSE=0` as the remedy - it stays an A/B knob for tests only.

**The user's hypothesis, to check and answer in this file:** "closing a wsl pane is not closing the shell; it seems to be reusing it on opening a new pane". The reuse is of the WINDOW, not the shell - but verify the shell side too: close a WSL pane, wait past `undo-timeout` (CloseUndo parks the pane with its shell alive for that long, T1825), and assert its wsl.exe/ConPTY (or agent session) is gone; and confirm a new pane never attaches to a parked pane's session (cf. T1684).

**Acceptance (in addition to the above):** a test that forces the composition path to fail (a debug knob on `compFail`) on a pane that took a parked window, and asserts the pane still paints (pixel probe or the renderer's frame counter), with GHOZTTY_PANE_REUSE on (and asserts the pane really took a parked window, so the test cannot pass by not reusing); plus the close-then-wait shell-teardown check.
