# T3739 - A WSL pane opened from the CLI (Claude asked to open one) cannot be typed into

## Summary

User report 2026-11-25 (laptop with WSL, current release): the user asked Claude Code to open a WSL pane; the pane opened (so via the CLI: +split/+new-window with --shell=wsl.exe and/or --command=wsl), but nothing the user typed reached it. The exact command line is not known - reproduce every form Claude would plausibly use: +split --shell=wsl.exe; +split --command=wsl; +split --command=wsl.exe; +new-window --shell=wsl.exe; each with session-persistence on and off. Leads: (1) args.zig localExecArgv wraps a WSL command as wsl.exe -e /bin/sh -lic "<cmd>; exec ${SHELL:-/bin/sh} -li" (args.zig:610, test at 1309) - check the pane ends on an interactive shell reading the ConPTY, not on a process with no stdin; (2) T1751: ipc-command-keepalive's WSL arm already flakes on "send-keys runs in the pane afterwards" - the same symptom from the automation side, likely the same cause; (3) keyboard focus: does a CLI-opened split take focus so typed keys go to it (the user may be typing into the old pane) - check which pane has focus and whether a click into the WSL pane then works; (4) wsl.exe first-run / distro-boot prompt eating input while the VM starts. Acceptance: a real-keys test (kb-actions style, the T86 harness) that opens a WSL pane by each CLI form and asserts typed text echoes back from inside the distro, plus the same with +send-keys; T1751's arm goes green with it.
