# T2749 - Default composition path: pane-elevation.ps1 (3), frame-lab-card.ps1 (2) and stack-fold-slide.ps1 (5, 1 of them pre-existing T2620) go red (with GHOZTTY_COMP_PRESENT defaulted on (T2514 run 2026-11-06, debug build) and green with =0 on the same build) - classify test-assumes-WGL vs real defect and fix

## In plain terms

Ghoztty is about to draw pane banners and the unfocused-pane dimming a new
way (inside the pane, through the composition path) by default. Three tests
went red when that was switched on. Most of the reds were the tests looking
for the old floating windows, which the new path deliberately does not use.
One was real: when a squeezed pane slid back open out of its strip, its
banner vanished for the whole slide and popped in only when it landed - the
bug the user reported on 2026-11-03, back again on the new path. That is
fixed, and the tests now pass on both paths.

## Goals

- [x] classify every red in pane-elevation.ps1, frame-lab-card.ps1 and stack-fold-slide.ps1
- [x] fix the real defect: the banner comes out with its card on the composition path too
- [x] each harness means the same thing before and after the T2514 default flip

## Summary

Measured 2026-11-06 on a debug build of f458464b1 with
`GHOZTTY_COMP_PRESENT=1` in the caller (same counts as T2514's run):

- **pane-elevation.ps1, 3 red: harness assumption.** `solid bands` /
  `glass bands: the banner strip is up` and `banner: the strip is up` look up
  the `GhozttyBannerOverlay` popup, which the visual path (T2559) keeps
  hidden. Every other assertion (140) passed on the composition path.
- **frame-lab-card.ps1, 2 red (D9, D11): harness assumption.** The lab's
  `overlay` plant holds the dim wash's POPUP back on a move
  (`DimOverlay.zig`); on the composition path the wash is a visual moved
  with its pane in one commit, so there is no popup lag to plant or read.
- **stack-fold-slide.ps1, 5 red: 2 harness, 2 a REAL DEFECT, 1 pre-existing.**
  The F19 precondition and F6 dim-wash precondition counted popups (harness).
  The two F19 unfold reds were real: on the visual path the banner lives in
  the pane's composition tree, and a card opening out of its strip keeps its
  pane window hidden for the whole glide (T2458), so the banner was hidden
  with it and popped in when the glide landed - T2661 (user report
  2026-11-03) regressed on the composition path. F13 is T2620 (red both ways).

Fix:

- **Product** (`banner_layout.wantsVisual`, `BannerOverlay.syncPath`): while
  the owner pane is hidden under an opening card (`openingCarried`), the
  banner takes the popup path, which comes out with the card cut to it
  (T2661's machinery); when the pane shows at landing it goes back into the
  tree. Switching to the popup invalidates it, since it sat hidden while the
  tree drew the card. Unit tests in `banner_layout.zig`.
- **pane-elevation.ps1**: the two sections whose probe IS the popup launch
  through `Start-PopupBannerGui` (`GHOZTTY_COMP_PRESENT=0` for that launch,
  the caller's value restored), so the rest runs on whichever path the
  caller chose.
- **frame-lab-card.ps1**: section D's launch pinned to `=0` (the plant's
  subject is the popup), caller's value restored.
- **stack-fold-slide.ps1**: path-aware. It reads the banner's path from the
  app's `banner path visual=` line; on the visual path the precondition is
  "path=visual, no popup on show", the unfold watch takes any banner popup
  (it is made on first need), and at rest "back to visual, popup down". F6
  counts popup washes plus visual washes (`dim overlay shown as visual` less
  `hidden visual=true`).

Not measurable off the input desktop: the banner VISUAL's pixels at rest
(no capture reaches a composition visual; pane-banner.ps1 section 13 reads
its layout from the log).
