# T1984 - The watchdog, loop lock, health check and dashboard know about two loop lanes, and lane B never publishes or delivers

## Summary

Split from T1937 item 4. Lane-qualified watchdog mutex and lock, one watchdog per lane, go-loop-health.ps1 and the dashboard show both lanes and their current tasks, stopping one lane does not stop the other. Lane A alone owns daily-publish and the dev install; lane B refusing them is asserted.

## In plain terms

The loop's supervisor, its window label and its health report all assumed
there is only ever one loop. A second loop in a second copy of the repo would
have had no supervisor, would have closed the first loop's window as a
"duplicate", and could have published a release on top of the first one. Now
each loop has its own supervisor and label, the health check and dashboard
show both loops and what each is working on, and only the first loop ever
publishes or installs anything.

## Goals

- [x] one watchdog per lane: lane-qualified mutex, Run entry, revive task, log, resume shim and re-entry window (lane a keeps every historical name)
- [x] the claim's window marker is per lane, so a lane never closes the other lane's window
- [x] `go-loop-health.ps1` and the dashboard show every lane, its state and its claimed task
- [x] stopping one lane does not stop the other
- [x] lane b never publishes (daily-publish SKIPs) and never delivers (tag/upgrade/launch/deliver refuse)
- [x] the watchdog heartbeats its lane's ledger claim on healthy ticks; ledger TTL 180 -> 60 min

## Design (recorded; mechanism calls, not decisions)

- `scripts\lib\LoopLane.ps1` decides the lane from where a script lives: the main worktree is `a`, a linked worktree named `...-x` is `x`, any other linked one is `b`, a non-git path is `a`; `GHOZTTY_LOOP_LANE=<letter>` overrides (a longer value is LoopLedger's free-form lane NAME and is ignored here). No configuration is needed to bring lane b up.
- Lane a's names are byte-identical to the old singletons, so nothing already installed on the box had to be re-registered.
- Lane b's marker is `[go-loop b]`, deliberately not prefixed by `[go-loop]`: the duplicate test is a StartsWith.
- daily-publish refuses as a SKIP (exit 0), after `-Request`/`-Status`: the request file is box-wide, so lane b's user-report closes still reach lane a's next publish. Everything that can tag, push or write the watermark is behind the refusal, including the tagged->published reconcile.
- A lane's task in the overview comes from the claim ledger, not task files: lane b's in-progress mark is not in lane a's files until it is pushed and pulled.
- The ledger touch runs on HEALTHY ticks only, so a dead lane's claim still ages out.
