# T2142 - Stacked panes: a pane dragged onto a folded strip swaps with it and stays folded there, as on Mac (strips are not drop targets on Windows yet)

## Summary

Mac 2811a3043 (PaneMoveCoordinator swap + isMinimized): a pane dropped on a
strip trades places with it and stays minimized there, and a pane that was a
strip is a drop target again once on show. On Windows `collectPaneSlots`
skips tucked cards, so a strip is no drop target at all and a release over it
does nothing. Publish strip rects as swap-only candidates (no split quadrants
on a 36-DIP strip) and commit through `PaneStackState.swap`, which exists and
is unused by Window. Raised by T2127's progress note on T2128.

## In plain terms

When a row of panes is too narrow, some panes fold away into thin titled
strips. On Mac you can drag a pane onto one of those strips and the two trade
places: the pane you dragged folds away where the strip was, and the folded
one comes out. On Windows, letting go over a strip did nothing. After this, it
works the way it does on Mac.

## Goals

- [x] A strip is a drop target for a pane drag, built the way Mac builds it:
      the strip's rect is an ordinary pane target (`collectDropSlots`), so its
      middle swaps and its edges split, exactly as Mac's `PaneDragSession`
      puts each `PaneStackTabView` into `paneRects`.
- [x] A swap carries the collapsed rows (`PaneStackState.swap`, noted before
      the swapped tree is installed) in a same-tab, cross-tab and
      cross-window drop.
- [x] Focus follows Mac: in one window the caret goes to the pane that came
      out of the strip; into another tab or window it stays where it was.
- [x] The stacked-pane fuzz test swaps strips too, as Mac's does.

## Design note

The Summary proposed swap-only strip targets (no split quadrants). Mac does
not do that: its strips are plain pane rects, so a drop near a strip's edge
splits it. Platform symmetry wins, so Windows does the same; the strip's swap
zone is the resolver's usual floor-and-cap rectangle.
