# T3019 - PA-I05: one agent-wide mutex is held across ring append, emulator parse and frame build for every session's output, and across the attach grid snapshot (session.zig:1660-1662)

## Summary

PA-I05 (audit-1, T2962). src/remote/agent/session.zig:1660-1662 onChildOutput takes `self.mutex` (the SessionStore lock) and holds it through recordOutput (ring append + feedEmulator VT parse) and bridge_data; handleAttach serialises its grid snapshot under the same lock (server.zig from :1407). Cost (by reading): N noisy panes parse on one lock's worth of a core, and a multi-MB attach snapshot stalls every other session's output. Fix: a per-session lock for ring and emulator, store lock only for table lookup and lifecycle. Risk medium: lock ordering with the bridge, detach and snapshot paths. Shared agent code: Mac half filed. Findings: docs/design/perf-audit/audit-1/I-findings.md.

## In plain terms

When session persistence is on, every pane's output passes through the
background agent, which keeps a copy of each pane's screen. Building that copy
happened while holding one lock shared by every pane, so two panes printing a
lot at once took turns instead of running side by side, and each slowed the
other down. Now each pane builds its own copy on its own, so busy panes no
longer queue up behind each other.

## Goals

- [x] the per-chunk screen-copy work (the VT parse) runs outside the agent-wide lock
- [x] the screen copy still sees every byte in order, so a re-attached pane repaints correctly
- [x] measured: two sessions ingesting at once beat one at a time (2.0x, ReleaseFast)
- [x] the attach snapshot itself moves off the agent-wide lock - split out as T3165

## Validation criteria

- [x] with two sessions flooding at once, combined throughput rises measurably - measured at the agent, not through GUI panes (the GUI renderer would dominate a `type` run): new opt-in bench `GHOZTTY_BENCH_T3019=256 zig build test-agent -Dtest-optimize=ReleaseFast -Dtest-filter=T3019`. One session alone 1.20 MiB/s; two sessions on ONE store 2.43 MiB/s combined (2.0x); control, two sessions on two separate stores (no shared lock at all) 2.40 MiB/s. Same-store = separate-store means the store lock no longer costs the pair anything. No separate run on the pre-fix code: there the parse ran inside the one store lock by construction, so the pair could not exceed the solo rate. Debug: 0.09 vs 0.22 MiB/s (2.3x).
- [x] zig build test-agent green, including the attach/detach and restore tests - `floor-lane.ps1 -Lane all`: lib/none/win32/agent all PASS. New test `SessionStore.onChildOutput: the VT parse runs with the store lock released (T3019)` observes a chunk already in the ring with its parse lock still held while the test thread holds the store lock (a state the old single lock hold made unobservable), and checks the emulator still repaints the last line.
