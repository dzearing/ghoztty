# T1763 - Resizing a pane running Claude Code flickers: the content clears and repaints instead of updating in place

## In plain terms

When you resized a pane running Claude Code, its contents blinked: the
screen went blank for a moment and then filled back in. Programs like Claude
Code ask the terminal to show a full redraw as one finished picture. Windows
split that request so the "clear" arrived before the new content, and the
terminal was showing the empty screen in between. Now the terminal waits for
the new content before it shows anything, so a resize updates in place.

## Goals

- [x] Find out which part of the Windows pipeline produces the blank frame
- [x] Keep the blank frame from ever reaching the screen, for local panes and
      for panes kept alive by the session agent
- [x] Do not slow down ordinary output (typing, spinners) that never clears the
      screen
- [x] An on-box test that can see the blank frame, and proves it is gone

## Summary

User report (2026-09-26, interactive): resizing a pane that runs Claude Code
flickers - "it's like it's repainting by clearing and then repainting". This
is the pane's CONTENT, not the chrome: T1031/T1393 fixed the pane blinking
to the background colour during resize, and that fix is in place
(`resize-flicker.ps1` green, every logged decision `fill=false`).

### Likely cause (leads, not yet measured)

Claude Code (Ink) answers a size change by erasing the screen and redrawing
all of it. A terminal hides that by honouring DEC mode 2026 (synchronized
output): the renderer skips frames while the mode is set
(`src/renderer/generic.zig`, the `synchronized_output` check), so the clear
and the redraw show up as a single frame. On Windows, two things are in the
way:

1. **ConPTY sits between the app and our parser.** `src/pty.zig`
   `WindowsPty.open` calls `CreatePseudoConsole(..., 0, ...)`, with no
   flags. In that mode conhost parses the app's VT into its own buffer and
   then emits ITS OWN VT stream. ? INFERRED: an in-box conhost does not pass
   `CSI ? 2026 h/l` through to us, so the sync bracket never reaches
   `stream_handler.zig`, and we render the half-cleared intermediate state.
   Verify by logging the modes we receive while Claude Code redraws.
2. **ConPTY repaints on resize by itself.** `ResizePseudoConsole` makes
   conhost re-emit the whole screen (see the comment in
   `src/remote/agent/server.zig` around the `quiet_attach` seam, T804). So
   one resize produces two full repaints: conhost's reflow, then the app's
   clear-and-redraw.

### Candidate fixes, to evaluate in order

- `PSEUDOCONSOLE_RESIZE_QUIRK` (0x2, the flag Windows Terminal passes) stops
  conhost from invalidating and re-emitting the whole buffer on resize.
  Check what it means for our reflow, since we then own reflow alone.
- `PSEUDOCONSOLE_PASSTHROUGH_MODE` (0x8), or a bundled newer `conpty.dll` /
  `OpenConsole.exe`, which forwards the app's VT verbatim and so carries
  2026. This is a larger change: it affects every sequence, input, and the
  agent (`src/remote/agent/`, which also creates the ConPTY through
  `pty.zig`). Treat it as a separate task if it is the answer.
- Fallback when 2026 cannot be carried: coalesce the renderer across a
  resize, so we hold the frame for a short, bounded window after a resize
  (or after an ED 2 / ED 3 that follows one) until output goes quiet. This
  is the same idea as the synchronous-present wait T1031 added for chrome.

Sessions attached through `ghoztty-agent` go through the agent's own ConPTY.
Whatever flag is chosen has to apply there as well, and the app<->agent
protocol stays untouched (docs/claude/sessions.md).

Mac seat: nothing to file. There is no ConPTY on the mac path, and 2026
reaches the parser directly, which is the behaviour this task restores.

## Validation criteria

- [x] Evidence of which cause it is: a trace showing whether `?2026`
      arrives while Claude Code (or a stub that emits BSU, ED 2, redraw,
      ESU) repaints after a resize, and how many full repaints one
      `ResizePseudoConsole` produces.
      *Verified with a scratch C# ConPTY probe on in-box conhost (Windows 11
      26200), timestamped per pipe read. `?2026` DOES arrive, but conhost
      re-emits an Ink frame as two writes: `ESC[?2026h ESC[2J ESC[3J
      ESC[?2026l` (n=24), then its own paint `ESC[?25l ESC[H <rows>` outside
      any bracket. One `ResizePseudoConsole` produces one in-place repaint
      (`ESC[8;r;ct ESC[H` + every row + `ESC[K`, no ED2), so lead 2 is not
      the blank. Flags 0x2 (resize quirk) and 0x8 (passthrough) produced
      byte-identical output on this conhost, so neither is a fix here.*
- [x] An on-box acceptance script in `test/win32/` drives a pane resize
      while a stub child does a synchronized clear+redraw, and asserts that
      no presented frame shows the cleared, empty intermediate state. It
      FAILS before the fix and passes after.
      *`test\win32\conpty-sync-hold.ps1`: an Ink-shaped stub redraws on every
      width change and the debug build logs the text rows on screen at the
      moment each erasing bracket's frame becomes showable. `-NegativeControl`
      (hold off via `GHOZTTY_CONPTY_SYNC_HOLD=0`): 6 of 7 frames shown with
      0 rows, both sections, FAIL as expected. With the fix: 0 of 7 blank,
      every frame held (~27ms), ALL PASS (18). The first version of the fix
      (release on 12ms of quiet) was caught by this oracle at 4-5 of 7 blank.*
- [x] Holds for a local pane and for a pane attached through
      `ghoztty-agent`.
      *Sections A (persistence off; the stub's ConPTY owner is ghoztty.exe)
      and B (persistence on; owner ghoztty-agent.exe, the app parsing it as a
      remote pane), both asserted from the process tree.*
- [x] `floor-lane.ps1 -Lane all` and `ipc-p1/p2/p3` green.
      *floor-lane all: lib, none, win32, agent PASS. ipc-p1 26, ipc-p2 20,
      ipc-p3 16, all ALL PASS. Also run because the change made them due:
      kb-actions (44), tab-tooltip (31), guard-due (113), seam-audit and
      persistence-flag (after registering the new env seam and declaring the
      launch's persistence), and the harness floor, which ended PASS.*
