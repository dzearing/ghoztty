# T2346 - The box's clipboard is wedged: OpenClipboard returns ACCESS_DENIED for every process (no GetOpenClipboardWindow holder, so a windowless OpenClipboard(NULL) was never closed), turning the win32 lane's clipboard_open and ViewerPane host-floor tests red

## Summary

Seen 2026-10-27 08:50-09:07 by lane b (T2322 floor run): win32 lane FAIL on 'clipboard_open: open then close leaves the clipboard takeable again' (clipboard_open.zig:184) and 'ViewerPane host floor' (ViewerPane.zig:9711 copied != null), reproduced alone and under -Dtest-filter on the user's desktop. A PowerShell probe: OpenClipboard(NULL) 0/40 and 0/20 a few minutes later, GetLastError 5; GetOpenClipboardWindow and GetClipboardOwner both NULL; input desktop Default (not locked); no job UI limits; WinSta0. No repo test process alive at the time; lane a's acceptance (D:\git\.ghoztty-par\w4) had been running beside it. Find the holder (a process that called OpenClipboard(NULL) and never CloseClipboard - candidates: a hung test binary or app from the parallel mirrors, the installed app, a third-party clipboard tool), and make the harness say 'clipboard held by another process' (SKIP with the probe) instead of a red that reads as a code defect. Also check whether the user's own copy/paste is broken while it lasts.

## In plain terms

clipboard, and the tests that use the clipboard reported that as a bug in
Ghoztty. They now say the clipboard is held by another process and skip
that one check. Ghoztty's own clipboard code is unchanged, and a real defect
in it still fails.

## Findings (2026-11-05, measured on this box)

| holder shape | GetOpenClipboardWindow | others' OpenClipboard |
|---|---|---|
| another process, own window | that window | refused, 5 (already `other_process`, T2231) |
| another process on the TEST desktop, own window | that window (cross-desktop) | refused, 5 -> `other_process` |
| window destroyed while held | NULL | succeeds (destroy releases) |
| test desktop torn down under a live holder | NULL | succeeds (holder is killed) |
| thread B opens with thread A's window, A destroys it | NULL | succeeds |
| `OpenClipboard(NULL)` held | NULL | succeeds (T992) |
| same thread re-opens with NULL while holding with a window | our window | refused, 5 -> `this_process` |

So "refused with 5, no window named" cannot be this process with a live
window (that names the window) or with no window (that excludes nobody). It
is the 10-27 shape, and T2231's probe called it `unknown`, so T2231's fix
would still have failed on the real event. Its negative control used a
holder that owns a window, and that is not what the box saw.

Fix: `clipboard_open.Holder.Kind.held_unnamed` (pure `classifyWindowless`,
unit-tested), `Holder.last_error`, and `isBoxCondition()` (other_process or
held_unnamed). The round-trip test and the ViewerPane copy oracle skip on it
and print kind/pid/image/last_error. `this_process` and `unknown` still fail.
