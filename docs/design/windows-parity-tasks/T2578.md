# T2578 - Lay the panes out and present them at the new size in WM_WINDOWPOSCHANGING, before the size loop applies the frame, so content and frame land in one compose; right/bottom edges first, film it with resize-sync-onscreen.ps1

## Summary

T2575's timing says the frame change is on screen about one compose after it happens, and anything presented within the same latch period goes up with it. Today the window rect changes first (SetWindowPos, before WM_SIZE) and the content follows 12-16 ms later, a full compose behind. The other order: in WM_WINDOWPOSCHANGING (the new rect is known, nothing has moved yet) lay the panes out at the new client size, present them, and only then let the size loop apply the frame - the frame change then follows the last present by ~1 ms and joins its compose most of the time. It needs the layout to take a client rect instead of reading GetClientRect (surfaceRect, deskRect, captionLayout ...), and a left/top edge drag moves the client origin, so start with the right and bottom edges. On shrink a miss shows a desk strip at the trailing edge for one compose (the reverse defect); on grow a miss is clipped by the old frame and invisible. Film all four drags with `scripts\resize-sync-onscreen.ps1` against T2575's numbers (~1.4 bad frames per step).

## In plain terms

When you drag a window edge, the outline moves first and the inside catches up a refresh later. This tries drawing the inside at the new size first, then moving the outline straight after, so both show up together.

## Findings (2026-10-31)

`Window.prelayoutForPos` runs `layoutSplitsLive` from `WM_WINDOWPOSCHANGING` (after DefWindowProc's min/max clamp) with `Window.pending_client` set; every layout reader of the window's client rect goes through `layoutClientRect` (caption layout, surface/desk rect, sidebar mode and sync, chrome invalidation, the fold clip). The rule (inside a size loop, top-left unchanged, growing, not minimized) is `resize_prelayout.zig`, unit tested in the `none` lane. `WM_SIZE` still runs its whole pass after the frame changes; the panes are already at their size, so it re-presents nothing. `GHOZTTY_RESIZE_NOPRELAYOUT=1` turns it off for A/B films.

Films, `resize-sync-onscreen.ps1`, ReleaseSafe `zig-out-rsafe`, CHROME+PRESENT+NOREDIR, one build, bad frames / frames:

| drag | off | on (all sizes) | on + desk covers old client | final (grow only) |
|---|---|---|---|---|
| right-shrink | 36/78, flat 0 | 47/84, flat 13 | 46/102, flat 0 | 37/77, flat 0 |
| right-grow | 75/82, flat 40 | 47/86, flat 0 | 62/87, flat 0 | 64/85, flat 0 |
| left-shrink | 42/79 | 43/78 | 42/78 | 47/79 |
| left-grow | 76/82, flat 41 | 68/78, flat 34 | 68/81, flat 38 | 71/79, flat 33 |

Grow: 2.5 -> 1.5-2.1 bad frames per step, and the flat-background frames are gone. Shrink is not better laid out ahead (1.2 -> 1.5): what is left there is the terminal one step behind the page (`gap=9`), which is on both paths. So the pre-layout is gated to growing drags, and shrink went to T2580. Left drags are untouched and score the same within film noise.
