# T2335 - An unfocused pane's read-only badge, bell frame and search bar can sit above its dim on Windows; Mac's dim covers them (the key-state pill excepted)

## Summary

Found while fixing T2308. Mac's `SurfaceView` ZStack puts the unfocused-split
dim `Rectangle` after the `ReadonlyBadge`, `SurfaceSearchOverlay`,
`BellBorderOverlay` and `HighlightOverlay`, so all of them dim with the pane;
`KeyStateIndicator` carries `.zIndex(1)` and stays above the dim, and
`SurfaceGrabHandle` is deliberately last. On Windows every one of those is a
popup owned by the surface HWND, and two such popups sit in whatever order
last moved them (T2261), so an unfocused pane's badge, bell frame, hover tint
or search bar may or may not be dimmed. T2308 gave `DimOverlay.seatOver(card)`
for the banner strip; extend the same read-then-seat to the badge, the bell
frame, the search bar and the hover tint, and seat the key-state pill above
the dim. First measure the order today (EnumWindows z-order, as
`pane-banner.ps1` 7c does). Validation: a z-order row per popup on an
unfocused pane, with a negative control.

## In plain terms

When a window is split and one pane is not the one you are typing in, that
pane is shaded so the active one stands out. On Windows the little
"READ-ONLY" chip on a shaded pane (and, in some setups, its bell frame or
hover highlight) could stay at full brightness on top of the shade, so it
looked like part of the active pane. Now the shade covers them the way it
does on the Mac, while the key-sequence pill stays bright above it, as on Mac.

## Goals

- [x] the shade covers an unfocused pane's read-only badge (it switches to the popup wash while a badge is up, and stacks over it)
- [x] the shade also stacks over the bell frame and the sidebar-hover tint when those are popups, and is in front of them when all three are drawn inside the pane
- [x] the key-state pill is put back above the shade
- [x] a pane that leaves read-only while unfocused goes back to the in-pane shade
- [x] measured (z-order), with a negative control

## Findings

- The find bar cannot reach this state: it closes itself the moment focus
  leaves its edit box (`overlay_zorder.zig`, the NOT HEALED bucket), so an
  unfocused pane never has one. Nothing to do for it.
- Glass panes (the default) never dim (T2281, Mac 9da9618f8), so the defect
  only showed with `macos-pane-glass = false`.
- With composition present (the default since T2466) the dim, bell frame and
  hover tint are child visuals of the pane, and the badge and pill are
  popups, which always sit above anything inside the pane. So a badge could
  NEVER be dimmed there; the wash now leaves the visual for the popup while a
  badge is up, the same way a banner already sends it there (T2308).
- On the visual path the wash used `Layer.setVisible`, which attaches at the
  BACK (T2771), so a bell that rang before the pane lost focus drew over its
  dim. The wash now attaches at the front. The rest of T2771 (the other
  overlays' places) is still open there.

## Validation criteria

- [x] An unfocused read-only pane's dim is a popup stacked OVER its badge, and still click-through - `readonly-badge.ps1` E2 (z index dim=0 badge=1).
- [x] A pane turned read-only, then unfocused, is dimmed over its badge; clicking that badge (which does not move focus) takes the wash back to the pane's visual - `readonly-badge.ps1` I1-I3.
- [x] Negative control: `DimOverlay.T2335_NEUTERED = true` turns E2 (both rows), I1 and I3 red (4 FAILURE(S), 50 passed), and nothing else.
- [x] The seat order itself (wash over badge and bell, seated one after the other; pill back over the wash; hidden windows untouched; reshow keeps a hidden wash hidden) - DimOverlay unit test "the wash stacks over every chrome popup and under the key-state pill (T2335)", win32 lane.
- [ ] Bell frame / hover tint over the wash on the visual path: not pixel-probed here (the background desktop cannot photograph a composite); the front attach is the code half of T2771, whose comp-present probe covers it.
