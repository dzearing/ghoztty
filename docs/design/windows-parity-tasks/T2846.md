`%TEMP%\ghoztty-t2291-fail-20261108-200248-78408.log`,

The last green stamp is 8a880a392 (2026-11-07 12:58). Since then the sidebar
changed in two commits only: T2765 (afb376f04, the composition tree - lazy,

## In plain terms

A test of the pane sidebar said that dragging the open panel's edge back
in did not tuck it away. It did; the test was reading the wrong moment. It
fires 1300 fake mouse moves for each drag, and on a slow day the app took
longer than the test waited to work through the first drag's moves, so the
second drag was scored on the first one's release. Real mice never pile up
moves like that, so nobody using the app saw anything.

## Goals

- [x] find why section 5 went red
- [x] make the harness wait for the first drag to finish, and say so when it does not

## Root cause

Both red logs have one shape: in the PULL's window the glide lands but no
`edge drag end` arrives inside `Wait-GlideDone`'s 15 s, and the PUSH's
window holds only `edge drag end expanded=true width=222` - the pull's own
late release. The pull's 1300 posted moves (PostMessage moves are never
coalesced, unlike a real mouse's) were still draining when the push
pressed; the push's lines fell after its own 15 s budget too. The app was
slower that evening (pull glide 39-45 steps in its 2 s vs 80 now) - the red
ran during T2801's sweep with its working tree, and four later commits
(T2802/T2826/T2827/T2828) took per-frame layout off the glide path. On HEAD
d6600fe8b the pull drains in 2.2-3.4 s and section 5 is green. Not a
sidebar defect: no bisect owed, since the failure is the harness letting a
second gesture start before the first one ended.

Fix (harness): `Wait-GlideDone` budget 15 s -> 45 s, the drain time is
printed for both drags, and a new assertion requires the pull's
`edge drag end` before the push presses, so a slow drain is named as one
instead of being scored as a push that never tucked.
