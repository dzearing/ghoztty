## In plain terms

record with evidence turned out to be the app itself crashing 8 seconds after a
cold start, and T3376 already fixed that crash. Nothing new was built here; this

## Resolution

**Already fixed by 84a8b868c (T3376).** The 2026-11-21 ipc-p1 failure ("Failed to
read IPC response length" at 7546ms) was a crash of the fixture app, not a slow
start: `%LOCALAPPDATA%\CrashDumps\ghoztty.exe.36580.dmp` (worker
`D:\git\.ghoztty-b-par\w1`, process uptime 8s) and its lane-A twin
`ghoztty.exe.44792.dmp` (18:42, `D:\git\.ghoztty-par\w1`, also 8s). This turn rebuilt
the crash-hour commit 4867de175 in a side worktree and resolved the dump's stack
against it. The cycle repeating through the 64 KB of stack the dump carries is
`unexpectedError -> print -> lockStderrWriter -> flush -> drain -> WriteFile ->
unexpectedError`, with `handleSegfaultWindows` at the bottom: a stderr write failed
with a Win32 code std does not map, and std's Debug diagnostic for it wrote to the
same stderr. That matches T3376's root cause independently. The CLI-launch console
probe's FreeConsole left closed handle numbers in the std slots, and the IPC
listener's pipe reused one (ERROR_PIPE_LISTENING). The std recursion itself is
T3378.

The original 2026-10-16 ipc-p2 symptom was a 30s hang, not a crash. No event-log
or dump evidence of it survives, and it has not recurred in any retained run.
Every P1-P3 failure on record in `%TEMP%\ghoztty-acceptance-parallel` since 10-10 is
the one 11-21 crash above.
