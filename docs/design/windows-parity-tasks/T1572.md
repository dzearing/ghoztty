# T1572 - A GUI acceptance script sits in the harness floor, so the fifteen-minute source-scan lane launches windows and goes red on a stale build

## In plain terms

There is one command that checks the test suite follows its own house rules, and
it is supposed to be pure reading: it scans the text of every test script and
never opens a window. One of the twenty-three things it runs is not like that -
it launches two real terminal windows and drags panes around. So the check needs
a desktop, takes longer than it should, and fails for reasons that have nothing
to do with the rules it is supposed to be checking.

## Summary

`scripts\lib\HarnessFloor.ps1` states its own membership criterion in its header:

> Every member is a STATIC SWEEP over the suite's own source or a pure-logic
> check of a shared gate: no GUI, no app launch, no `zig build`. That is what
> makes the set runnable as one lane in minutes rather than an afternoon, and it
> is the line to hold when adding a row.

`caller-anchor.ps1` breaks it. It is T1079's **product** acceptance script: it
launches two GUI windows, runs `+split` / `+rearrange` against them and asserts
where the pane landed (`Start-Process`, `Run-Cli '+split ...'`, 27 assertions).
It was pulled into the set for a sound reason - T725's note names it as one of
five audits with no `guard-due` coverage row, i.e. running only when somebody
remembered it - but the floor is the wrong mechanism for that: the floor is for
source sweeps, and a coverage row in `scripts\guard-due.ps1` is the mechanism
that makes a *behavior* script standing.

Consequences already observed:

- **The lane needs a desktop and a fresh app build.** T1571 records exactly this
  shape: `-Lane all` never builds `zig-out\bin\ghoztty.exe`, so the next
  `-Lane harness` scores `build-mode-guard`, `persistence-flag` and
  `caller-anchor` red on staleness - ten minutes to learn a rebuild was missing.
  Two of those three are in the set legitimately (they read the build they are
  handed); `caller-anchor` is red because it wanted to launch the app.
- **It makes the floor's colour a property of the box**, which is the exact thing
  the set was shaped to avoid.
- **A5 of `test\win32\harness-floor.ps1` enforces the criterion on one case**
  (the audit that drives a real `zig build` stays out) and nothing enforces it
  generally, which is how this row got in.

## Details

The fix has two halves, and the second is what stops the next one:

1. Drop `caller-anchor.ps1` from `$HARNESS_FLOOR_AUDITS`, and give it a
   `guard-due` coverage row instead, naming the sources whose change should make
   it due (`src\apprt\win32\IpcHandlers.zig` and the CLI's caller-pane seeding -
   T1079's progress log argues the gating would be noise, which was true when
   the alternative was nothing and is not true now that guard-due exists).
2. Make the criterion checkable rather than stated: a section in
   `test\win32\harness-floor.ps1` that fails when a member's source contains a
   GUI launch or a `zig build` - the same text-scan shape
   `launch-preflight-audit.ps1` already uses to find launch sites. Then a row
   that does not belong cannot be added quietly.

Found while finishing T732 (the harness rules' entry point): documenting the set
in `test\win32\README.md` is what surfaced that one row does not match the rule
the README has to state.

## Validation criteria

- [ ] `caller-anchor.ps1` is no longer in the harness floor set, and still runs
      as a standing check through a `guard-due` coverage row that goes DUE when
      the sources it covers change.
- [ ] `powershell -NoProfile -File scripts\floor-lane.ps1 -Lane harness` launches
      no GUI window and needs no app build.
- [ ] `test\win32\harness-floor.ps1` fails when a member of the set launches the
      app or runs `zig build`, demonstrated on a planted row.
- [ ] `test\win32\harness-floor.ps1` and `test\win32\caller-anchor.ps1` both ALL
      PASS, and each scores exactly one failure under `-NegativeControl`.
