# T3792 - Linux window resize feels wrong and slow on the real WSLg screen: match the Mac's live resize

## Summary

User report 2026-11-25, on the Linux build on the real WSLg screen (after T3783's launcher fix): resizing the window "feels weird" and is "slow". The bar is the Mac: "really needs to be as high quality as the mac version".

T3630 paced edge-drag resize and stopped blank prompts, but it was measured only in the headless Weston on Mesa software, never on WSLg's d3d12 GL through the real compositor. Measure THERE first, then fix:
- Is it the build? open.ps1 launches a Debug build ("Performance will be very poor"). Measure Debug AND ReleaseFast side by side (a ReleaseFast GTK build for the measurement only; still never the user's installed app) and report both - a slow-only-in-Debug finding is still a finding, but name it.
- What "weird" is: stretched/stale frames during the drag, content snapping at the end, the grid reflowing every frame vs. at the end, the CSD shadow/frame lagging the content, a resize overlay, the terminal re-centering. Record a frame sequence (or a short capture) of a drag on WSLg and describe exactly what is visibly wrong.
- The Mac's live resize is the reference: content follows the edge every frame, no blank, no stretch, grid reflows smoothly. docs/reference/ has the Mac's resize behavior - follow it.

Suspects to measure, not guess: the per-frame GL resize path (`gl resize` logs per configure), font grid / atlas rebuild per size, PTY resize storms, GtkGLArea on WSLg's RAIL compositor (XWayland vs Wayland - T3783 changes which one we are on, so measure on Wayland after T3783).

## In plain terms

Dragging the edge of the Linux Ghoztty window on the real screen feels slow
and odd. Measured so far: the app itself does very little per frame, about
1.5 thousandths of a second (a frame has 16), in the debug build and in an
optimized one. So the slowness is not the terminal drawing and not the debug
build. It sits between the app and the screen, in the layer WSL uses to show
Linux windows on Windows, and only a drag on the real screen can measure that.
There is now a single command for the person at the keyboard to do it.

## Measurements

Headless seat (`test/linux/resize-frame-cost.sh`, private Weston on WSLg's
d3d12 GL, a bash prompt, 40 window-edge steps through the window-size seam,
2026-11-26):

| Build | draws | draw mean / worst | core resize work mean / worst | frame gap during drag |
|---|---|---|---|---|
| Debug | 30 for 28 resizes | 1.51 / 2.57 ms | 15 / 21 us | 27.2 ms mean (the seam's step pace) |
| ReleaseSafe | 27 for 26 resizes | 1.36 / 3.23 ms | 14 / 20 us | 27.1 ms mean (same) |
| Debug, NEGATIVE=1 (40ms sleep in every draw) | 42 | 42.8 / 50.6 ms | 25 / 225 us | 66.0 ms - F4 fails alone |

Reading: every resize got a frame, the work per frame is under a fifth of a
60 Hz frame in both builds, and the optimized build is not meaningfully
faster. So the app is not the slow part, and it is not a Debug-build artifact.
ReleaseSafe stands in for ReleaseFast because ReleaseFast compiles out the
debug seams that drive and read the drag. The frame gap in the headless run
is the IPC step pace, not a compositor measurement. What is left are the
compositor-side suspects: WSLg's RDP/RAIL presentation (frame callbacks,
how often the Windows-side window is repainted), and the CSD shadow/frame
following the content. Only the real screen can measure them.
`open.ps1 -DrawStats`'s `resize_gaps` there is the frame interval a person
actually saw.
