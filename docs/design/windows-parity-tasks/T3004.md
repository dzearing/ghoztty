# T3004 - PA-M04: clearing scrollback returns no memory until a full reset or pane close, so ten panes that each ran one noisy build keep 100-177 MB (PageList.zig:3473)

## Summary

PA-M04 (audit-1, T2961). destroyNode zeroes the page and puts it on the pool free list (src/terminal/PageList.zig:3470-3476); only reset() on RIS (:716-725) shrinks the arena. A pane that filled its 10 MB scrollback keeps it (17.7 MB committed, PA-M03) after cls/clear, and the memset keeps freed pages in the working set. Fix: when eraseHistory removes all history, or the free list passes a few pages, release the excess (with PA-M03's allocator: decommit freed pages). Risk medium, shared core: tracked pins and the zeroing invariant must survive. Mac half filed separately (seat mac) for validation, since the code is shared. Baseline: docs/design/perf-audit/baseline-1.json (T2958); findings: docs/design/perf-audit/audit-1/M-findings.md.

## In plain terms

A terminal pane that printed a lot (a noisy build, a long log) kept every
megabyte of that history even after you cleared it with Ctrl+K - the memory
only came back when the pane was closed. Ten such panes quietly held 100+ MB.
Now clearing the history hands that memory straight back to Windows.

## Goals

- [x] a destroyed page beyond a one-page reserve is released to the OS, not zeroed and kept
- [x] unit tests pin the release path (pool and PageList)
- [x] an on-box harness measures the drop and was red before the fix

## Fix

`ExactPool` (Windows' page pool since T3003, one allocation per page) gains
`release(ptr)` and `freeCount()`. `destroyNodeExt` keeps at most
`page_free_retain` (1) destroyed standard page on the free list; any further
destroyed page is freed to the page allocator (VirtualFree) without the
memset, so it never re-enters the working set either. One page of reserve
covers destroy-then-create churn (resize/reflow) without a VirtualAlloc round
trip. Scrollback pruning at the limit (`grow`) reuses the oldest page in
place and never goes through this path, so steady-state scrolling is
unchanged. macOS keeps the arena-backed upstream pool, which cannot release
single items; that half is T3013 (note added there).

## Validation criteria

- [x] fill a pane's scrollback, then clear it (ctrl+k = clear_screen on Windows): private_mb drops by >= 8 MB within the settle window (measured) - `test\win32\scrollback-clear-memory.ps1`: fill +19.5 MB, clear -8.4 MB, ALL PASS. A/B with the release disabled (`page_free_retain = maxInt`): clear -0 MB, A2 red. `-NegativeControl` (no ctrl+k): A2 red.
- [x] none and win32 lanes green (floor-lane -Lane all: lib, none, win32, agent PASS); PageList unit tests cover the release path - unit tests `ExactPool release returns the item to the child allocator (T3004)` and `PageList windows: erasing history returns its pages to the OS (T3004)` pass (filtered none lane)
