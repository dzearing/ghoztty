# T3203 - Single-window mode: a workspace born parked takes its terminals' DPI from the hidden park host, not the shared window, so on a second monitor of another scale its grid changes when first shown

## In plain terms

In single-window mode, a workspace you have not looked at yet keeps its
terminals in a hidden holding spot that Windows places on the main monitor.
Those terminals measured their text size from that spot, so on a desk where
the Ghoztty window sits on a second monitor with a different scaling, the
first time you switched to that workspace its text resized and the lines
re-wrapped. After this, a hidden workspace's terminals are sized for the
window they will actually appear in, so switching to it shows them as-is.

## Goals

- [x] A terminal created in a hidden (parked) workspace takes the scale of the shared window, not the hidden holding window's monitor
- [x] A terminal moved into a hidden workspace does the same
- [x] Unit tests for the choice of scale

## Summary

Each terminal pane reads its DPI from its own HWND (`Surface.updateDpiScale`
-> `GetDpiForWindow`). A pane born in a parked workspace (T3191) is a child of
`App.parkHost`, a 1x1 popup at 0,0 on the primary monitor, so on a mixed-DPI
desk its grid was computed at the primary's cell size and reflowed on adopt
(`adoptWindow` -> `refreshPaneDpi`). T3193 already gave a born-parked
controller the shared window's `scale`; the panes ignored it.

Fix: `window_broadcast.initialScale` decides a new pane's scale - a parked
parent's `scale` wins over the HWND's DPI - and `Surface.init` uses it in
place of `updateDpiScale`. `window_broadcast.adoptDpi` does the same for
`Window.adoptPane` into a parked destination, which used to re-read the park
host's DPI via `handleDpiChange(null)`. Covers `+split` in a parked workspace
too (same `Surface.init` path). Viewer panes (WebView2) are out of scope here.
Mac analogue: a parked terminal keeps its window's backing scale
(`SurfaceView.backingSize`).
