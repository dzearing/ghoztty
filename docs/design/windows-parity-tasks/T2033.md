# T2033 - A task finished in one lane is handed to the other lane before the finish is pushed: the shared claim ledger releases at set-status done, while the other worktree still reads the task as todo (T2012 worked twice, 2026-10-16)

## Summary

Lane B claimed T2012 at 18:04 and ran set-status done at 18:59 in D:\git\ghoztty-b; its commit reached origin at 19:00:31. Lane A ran next -Claim at 18:59 and got NEXT: T2012 - the T1981 ledger had released the claim, and lane A's checkout still said todo. Lane A then re-implemented the same fix for a whole turn and only found out when its push rebased onto B's. Fix: the ledger keeps a done task reserved (status=done-unpushed, with the sha) until the finishing lane's commit is on origin, and next -Claim in any lane skips a task the ledger marks done; prove it in loop-lanes.ps1 with a done-but-unpushed task that the other lane's next must not hand out.

## In plain terms

Two copies of the work loop run side by side. When one finished a task, the
other could be handed that same task a moment later, because its copy of the
task list had not caught up yet - and it then spent a whole turn redoing
finished work. Now a finished task stays marked as "done over there" until
the other copy has it, so it is never handed out twice.

## Goals

- [x] closing a task keeps it reserved to the lane that closed it
- [x] the other lane skips a reserved task and says why
- [x] the reservation ends by itself once the close has arrived (or a TTL after the push)

## Validation criteria

- [x] a task marked done in lane B but not yet pushed is NOT handed out by lane A's `next -Claim` - `test\win32\parity-tasks-lanes.ps1` F1/F2/F8 (the ledger's own harness; loop-lanes.ps1 covers lane plumbing, not the claim ledger).
- [x] Once B's commit is on origin, the reservation clears and nothing is left stuck - F9/F10 (pushed -> pushedAt, cleared a TTL later) and F5 (cleared at once when the other lane reads the close).
- [x] Negative control: with the old release-at-done behaviour the section goes red - F11 (`GHOZTTY_LOOP_LEDGER_NO_RESERVE=1` hands the finished task out).

Design note (mechanism call, not a decision): the reservation lives in the
existing claim entry (`closed`, `path`, `pushedAt`) so every reader that
already skips another lane's claim skips it too. Ending it is upkeep that
`next` runs; the "pushed" test reads the task file at `@{u}` in the finishing
worktree and never fetches. Residual: a lane that has not pulled for over an
hour after the push can still be handed the task - the TTL bounds the stuck
case instead.
