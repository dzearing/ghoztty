# T1967 - Bring main 40c63c90b's per-role agent guard to Windows: a takeover never kills the other role's agent, and the agent stops leaking its lock, heartbeat and device-token variables into pane shells

## Summary

Intake 2026-10-15: main 40c63c90b (shared src/remote/agent) makes the daemon single-instance guard per role (relay / listen / listen-unix), lets --force-replace and stale-heartbeat takeover kill only a holder whose role is confirmed equal, stops the agent leaking GHOSTTY_AGENT_LOCK / HEARTBEAT / GHOSTTY_DEVICE_TOKEN into the shells it spawns, and adds --exit-on-revoke. After the merge (T1902) prove each on Windows: the named-mutex/pipe guard is per role; a relay-role takeover can never terminate the session agent owning the user's ConPTYs; a pane shell's environment carries none of those variables (the device token is a credential); --exit-on-revoke exits 0 after two 401 dials. The ConPTY spawn path is Windows-only code, so the env scrub needs its own edit there.

## In plain terms

The background helper that keeps your terminal sessions alive and the one that
connects this machine to your account can now run side by side, and starting
one can never shut down the other. The secret sign-in token the helper holds no
longer shows up inside the shells it opens for you.

## Goals

- [x] Both helpers run at once on Windows; two of the same kind still refuse each other
- [x] A relay launch that inherited the session helper's settings never kills it
- [x] No pane shell sees the helper's private variables or the device token
- [x] `--exit-on-revoke` leaves cleanly after the relay rejects the credential

## Validation criteria

- [x] Session agent and relay agent hold separate guards and run together; a second session agent exits 183 — `test\win32\agent-role-guard.ps1` A1-A5
- [x] `--relay --force-replace` with the session agent's `GHOSTTY_AGENT_HEARTBEAT` yields 183 ("different kind of agent") and both holders survive; without the override it replaces the relay holder (control) — B1-B7
- [x] Pane shell env has none of `agent_private_env` (read from source) on the holder-backed AND in-process (`GHOZTTY_AGENT_PTY_HOLDER=0`) paths; an ordinary var does arrive (control) — C1-C8. Teeth: with `scrubAgentPrivateEnv` commented out the run goes 10 FAILURE(S) (C3/C4/C7/C8)
- [x] `--exit-on-revoke` exits 0 after 2 rejected (401) control dials against a loopback relay; without the flag the agent keeps redialing (3+ rejections, still running) — D1-D6
- [x] Floor: `floor-lane.ps1 -Lane all` ALL LANES PASS; `-Lane harness` (scoped) PASS + stamped; guard row `agent-role-guard` added and stamped

## Findings

No Windows code change was needed: the merge (T1902) already carried the
per-role mutex names, the role-confirmed takeover, and the scrub in
`PtySpawner.init` — which BOTH Windows spawn paths go through (the `--pty-host`
holder builds its own `PtySpawner`, so it scrubs too). The deliverable is the
on-box proof. `--exit-on-revoke` is deliberately not passed by the Windows tray
agent (its Sign-in re-enrolls in place), so it is a flag parity, not a
supervisor change.
