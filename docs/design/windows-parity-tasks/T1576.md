# T1576 - A hovered paint cannot be held across a title change, so the strip freeze has no end-to-end arm

## Summary

T737 froze the tab run's widths while the pointer is in the strip, and the one thing the acceptance suite cannot assert is the pair the freeze exists for: a growth ARRIVING while the pointer is inside. A posted WM_MOUSEMOVE is chased by WM_MOUSELEAVE within a frame on the test desktop (T233), so the pointer state cannot be HELD across a title change coming from a pane; capture-hover (T282) wins the ordering for one paint on one stack, but the title change is asynchronous and lands on a different one. Section 9 of tab-strip.ps1 therefore proves the wiring (a hovered paint runs the frozen path, a pane-hovered one does not) and the unit tests prove the rule. What is missing is a probe that can do both on one stack - e.g. a debug-only capture-hover variant that applies a caller-supplied tab title, or takes the move, and paints, in one handler - which would close the same gap for any future 'state X while the pointer is somewhere' claim.

## In plain terms

When your mouse rests in the tab strip, tabs are not allowed to change width
under it (a background tab's command growing its title would otherwise slide
the tab you were about to click). That rule had no automatic end-to-end check
for the exact moment it exists for: a title growing WHILE the pointer is
there. Now there is one, so a regression is caught by the test suite instead
of by a mis-click.

## Goals

- [x] the debug `capture-hover` probe can apply a pane title change between the move and the paint, on the same stack
- [x] tab-strip.ps1 asserts a growth arriving with the pointer in the strip is held back, and lands once the pointer leaves
- [x] a control proves the same growth is taken at once with the pointer in a pane

## Design

`capture-hover` gained `--retitle-target=<pane>` + `--retitle=<title>`
(both or neither; refused before any message is sent). The title goes through
`Surface.setTitle`, the entry a terminal OSC 0/2 title takes, after the move
and before `RedrawWindow(RDW_UPDATENOW)`, so the captured strip paint has the
pointer inside AND the wider title pending. The oracle is the existing
debug log line `tab strip freeze=F deferred=N`. Chosen over a separate
"hold the hover" product flag for the reason T282 gave: nothing latches.
