# T1576 - A hovered paint cannot be held across a title change, so the strip freeze has no end-to-end arm

## Summary

T737 froze the tab run's widths while the pointer is in the strip, and the one thing the acceptance suite cannot assert is the pair the freeze exists for: a growth ARRIVING while the pointer is inside. A posted WM_MOUSEMOVE is chased by WM_MOUSELEAVE within a frame on the test desktop (T233), so the pointer state cannot be HELD across a title change coming from a pane; capture-hover (T282) wins the ordering for one paint on one stack, but the title change is asynchronous and lands on a different one. Section 9 of tab-strip.ps1 therefore proves the wiring (a hovered paint runs the frozen path, a pane-hovered one does not) and the unit tests prove the rule. What is missing is a probe that can do both on one stack - e.g. a debug-only capture-hover variant that applies a caller-supplied tab title, or takes the move, and paints, in one handler - which would close the same gap for any future 'state X while the pointer is somewhere' claim.
