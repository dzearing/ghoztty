# T814 - unsubscribeMetrics/unsubscribeSessionCpu returning does not actually prove no handler is in flight

## Summary

Both unsubscribe paths clear the handler slot under write_mutex, and every caller in the app treats the return as the guarantee that no further callback can fire against its context (ActivityMonitor.dropProbeLink says so in as many words; SessionCpuProbe.stop and the Mac SessionCPUProbe rely on the same claim). The control dispatch does not support it: it takes write_mutex, READS the handler and the ctx, releases the lock, and only then calls - so a handler already past the unlock runs while unsubscribe returns and its ctx is freed. Never observed, and the window is a few instructions wide, but it is a use-after-free by construction and the comments promise it cannot happen. Shape of a fix: an in-flight counter (or a per-handler rwlock) that unsubscribe drains before returning, in connection.zig so every subscription kind gets it at once.

## In plain terms

When the activity panel or the machine chooser stops watching a remote machine, it tells the connection "stop sending me readings" and then frees the memory those readings were being written into. The connection said that was safe, but it was only almost true: a reading that had already started arriving could still be landing in that memory a moment later. Nobody has seen it crash, but it is the kind of thing that crashes once, at random, on somebody else's machine. After this, "stop sending me readings" waits for the one already in flight to finish, so the promise is real.

## Goals

- [x] Unsubscribing waits for an in-flight callback instead of returning over the top of it
- [x] The same guarantee for all three pushed streams (host metrics, per-session CPU, session roster)
- [x] A callback that unsubscribes itself still works (no deadlock)
- [x] Tests that fail without the fix

- 2026-09-17 06:01: root cause confirmed: handleControlInternal reads the push handler+ctx under write_mutex, unlocks, THEN calls - so unsubscribe could clear the slot and return while a handler was mid-call. Fix in src/remote/connection.zig: per-kind in-flight counter (pushEnter under the same critical section that reads the slot, pushLeave + push_cond broadcast on return) and drainPush() after the slot is nulled in all three unsubscribe paths; the control-reader thread id is latched so a handler that unsubscribes itself does not wait on its own frame. Three unit tests added (none lane), negative control done: commenting out drainPush(.metrics) fails 'T814: unsubscribeMetrics waits for a handler that is already running'.
