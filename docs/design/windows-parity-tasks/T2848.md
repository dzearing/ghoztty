# T2848 - Composition step 5d-5d2: the held sidebar row's settle once let go - the glide to where it landed and the lift fading - runs on the compositor (offset Y animation + backing opacity), instead of the reorder clock repainting the column for 220 ms

## Summary

T2803 put a pane drag's sliding rows and the held row (per input) on the sidebar's tree; once let go the drag drops off the tree and the settle (Settle hold-then-glide, settle_ms, the lift backing fading) is stepped by TIMER_REORDER. Split the held capture into backing+shadow (opacity animation) and the row (animateOffsetY from the drop to the laid top once the layout catches up). Oracle: pane-sidebar-drag.ps1 E/F settle with clock frames=0 vs -ReorderStepped.

## In plain terms

When you let go of a pane's row after dragging it in the sidebar, the row
glides into its new place while its raised "lifted" look fades away. The app
used to redraw the whole sidebar every frame for that quarter second, so the
landing hitched whenever the app was busy. Now Windows itself plays the glide
and the fade, the same way it already played the rows sliding aside.

## Goals

- [x] the held row on the tree is two pictures under one box: its lift (glass + shadow) and the row itself
- [x] let go, the lift's fade is one declared opacity animation and the glide one declared offset animation (re-declared only if the landing place moves)
- [x] the settle's two edges - the end of the hold and the end of the glide - are a one-shot timer, so the reorder clock never runs for it
- [x] anything that leaves the tree mid-settle (a transition, a lost device, a refused declaration) falls back to the stepped settle; a new drag mid-settle drops it
- [x] `GHOZTTY_DEBUG_SIDEBAR_REORDER_STEPPED=1` still steps it all (the control arm)

## Design

- `pane_sidebar_reorder_comp.zig`: `held` is now a pixel-less box with
  `held_back` (the lift, `captureDrag(.lift)`) and `held_row`
  (`captureDrag(.lifted_row)`) on it, same padded size and origin.
  `settle(from, to, elapsed, glide_ms, now)` declares the fade once
  (`animateOpacity` 255 -> 0 on the settle curve, tail from the drop) and the
  glide once per (target, start) (`animateOffsetY` on the box, tail from the
  glide's start) - exactly `reorder.Settle.top`'s formula, which reads
  `from + (to - from) * progress(since glide)`.
- `PaneSidebar`: `endDragMotion` marks `settle_comp` when the held row is on
  the tree and arms `TIMER_SETTLE` for the hold (`settle_hold_ms`); the paint
  that sees the glide begin (the list laid the new place out, or the hold
  ran out) arms it for the glide's end; `onSettleTick` lets the row back into
  the list. `composeDrag` keeps only the held row on the tree while settling
  (`dropRows`). `reorderMoving` answers false for a tree settle, so the clock
  runs only for what is still stepped (tray fade, header).
- Mechanism choice (mine, recorded): a one-shot `SetTimer` at the two edges
  rather than the frame clock - the edges are the only moments the window
  thread has anything to decide.
