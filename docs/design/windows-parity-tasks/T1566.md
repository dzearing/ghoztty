# T1566 - An automatic update offer lives only in a balloon, so a swallowed one means the user never learns there is an update

## In plain terms

When Ghoztty notices an update on its own, it says so once, in a tray balloon.
If you were in a full-screen app, had Focus Assist on, or simply looked away
for ten seconds, that is the end of it - there is nothing anywhere in the app
that still says an update is waiting. The next time you wonder, your only move
is to go and ask.

## Summary

Filed from the T1565 turn, which moved the MANUAL check's answer into a window
precisely because the tray is allowed to swallow it. The automatic arm was
deliberately left on the balloon - an unsolicited offer should interrupt
politely, not throw a modal at somebody mid-sentence - but that leaves the
offer with no durable surface at all. `App.rememberUpdate` already holds
everything needed (`update_latest_ver`, `update_asset_url`,
`update_staged_msi`); nothing renders it.

Mac's answer is the About panel's update row, which is persistent: the offer is
still there tomorrow. The win32 side has `about_links.zig` and an About dialog
but no update state on it, and no other affordance either.

Likely shape: show the pending offer where the user already looks - an About
row that reads "Version X is available / Install and Restart", and/or a mark on
the Help > Check for Updates... command - driven off the state
`rememberUpdate` already stores. No new check, no new network call: this is
rendering a fact the app already knows.

## Goals

- [x] an automatic offer has a durable in-app surface, not only a balloon
      (landed by T1673, commit 654143980: the menu dot + "Install Update" row)
- [x] prove it holds when the balloon is swallowed, which T1673 never tested

## Re-verification (2026-09-25)

`next` flagged CHECK FIRST, and the defect had indeed been fixed at the source
five days after filing: T1673 (654143980) added the persistent menu-button dot,
the "Install Update <ver>" row at the top of the menu popup, and the on-disk
offer record restored at launch. `rememberUpdate` raises all three BEFORE the
balloon is attempted, so a swallowed balloon cannot take them with it. What
T1673 did not land is the demonstration this card asked for - every T1673
scenario ran with a working tray - so this close is the validation it was
owed: scenario 13 of `test\win32\update-check.ps1`, plus an `update affordance
up` log line in `rememberUpdate` so the harness sees the surface go up rather
than inferring it.

## Validation criteria

- [x] After an automatic check finds an update, the offer is still discoverable
      in the app with the balloon never shown - scenario 13 (`autotraydead`)
      of `test\win32\update-check.ps1`: with `GHOZTTY_TRAY_FAIL` set the
      balloon is suppressed, no manual check fires, the affordance line is
      logged, the offer is written to disk, and a fresh launch with no feed
      restores it. Negative control: scenario 3 (up to date) logs no
      affordance line.
- [x] The surface offers the same action the balloon click does - by reading
      the code: Surface.zig's `.install_update` and App.zig's
      `.open_release_page` balloon click both call `offerUpdate()` first; with
      no package the balloon opens the release page and the row runs a manual
      check, whose no-installer answer (`showManualUpdateOffer`) offers that
      same page.
- [x] The surface goes away once the update is installed or the app is
      current - scenario 11 (T1673), still green.
- [x] Acceptance coverage in `test\win32\update-check.ps1`: ALL PASS (54
      assertions, 6 new).
