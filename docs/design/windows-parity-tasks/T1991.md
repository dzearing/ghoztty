# T1991 - task-dashboard.ps1 goes red (9 failures) beside dashboard-dom.ps1 in the acceptance pool and green alone: mark it @parallel-unsafe or stop it sharing whatever they share

## In plain terms

Two of the dashboard's automated checks failed whenever they ran at the same
time and passed when run one by one, so the "run the checks four at a time"
tool could not be trusted with them. They were both grabbing the same network
port for their test servers. Each now asks the operating system for its own
port, so they run side by side and stay green.

## Summary

What they shared was a **TCP port band**. `task-dashboard.ps1` (its G2
fixture server and its section I launcher fixtures) and `dashboard-dom.ps1`
(its stub server) each took "the first free port in 7861-7880" with a
check-then-launch scan. Run side by side, both checks see the same port free
before either binds it, so they pick the same one. The loser's
`task-dashboard.js` hits EADDRINUSE, which the server answers by exiting 0
with "(already serving)" - so the harness carried on and tested the OTHER
script's server. That is the 9-failure red, and why it only appeared in the pool.

The repo already had the remedy (`test\win32\lib\FreePort.ps1`, T694: draw an
OS-assigned port, assert it free, print it), and a sweep that keeps scripts on
it (`fixed-ports.ps1` section C over `lib\FixedPortAudit.ps1`). The sweep missed
these because it knew three shapes - pinned param default, literal assignment,
literal endpoint - and not a range scan.

Fix (no `@parallel-unsafe` - the scripts no longer share anything):

- `task-dashboard.ps1`: all four ports (main server, G2 fixture, I1/I3 launcher
  pair) come from `Resolve-TestPort`; the I pair is redrawn until the two
  differ. Its private `Test-PortFree` and the now-dead "no free port" skips
  are gone.
- `dashboard-dom.ps1`: the stub port comes from `Resolve-TestPort`.
- `lib\FixedPortAudit.ps1`: a fourth violation shape, `guessed-range` - a
  `lo..hi` range whose both ends are port numbers (1024-65535), so `1..60`
  retry loops stay clean. Before the fix it flags exactly the four sites
  above and nothing else in `test\win32`.
