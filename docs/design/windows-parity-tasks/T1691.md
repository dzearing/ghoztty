# T1691 - The exit ledger's crash record is never exercised by a test

## Summary

T1686's unhandled-exception filter writes 'event=crash code=... addr=...' before handing the exception on, but test\win32\exit-reason.ps1 covers only quit, outside kill, second-instance and forwarded launches. Add a debug-only, env-gated crash seam (like startupFailSeam) that faults on purpose, and assert the crash line lands with the right code and that WER/LocalDumps still see the exception.

**Re-verified at claim (2026-11-21): mostly already done by T1355** (3b43d0922, 2026-10-25). `test\win32\crash-report.ps1` crashes the app on purpose through the stock `crash:main` binding - no new seam was needed, because a Debug panic is a 0x80000003 breakpoint that reaches the unhandled-exception filter exactly as an access violation does in a release build. Its section E already asserted the ledger's crash line with the right code, and section B asserts the process exits with the exception code itself, which is only true when the filter returns `EXCEPTION_CONTINUE_SEARCH` and the default handler (the one that reports to WER) runs. What was LEFT: nothing checked the line's address, or that the crashed run is recorded as a crash and not also as something else.

## In plain terms

When Ghoztty crashes it writes one line in a small log saying it crashed and
where. A test already crashed the app on purpose and checked that the line
appeared; it now also checks that the line points at the real place the
crash happened, and that the crash is not also mis-recorded as a normal quit
or as a mysterious disappearance the next time the app opens.

## Goals

- [x] A test crashes the app on purpose and finds the crash line (already true since T1355)
- [x] The line's address is checked against an independent record of the same crash
- [x] The crashed run is recorded as a crash only - not a quit, not a vanished run

## Validation criteria

- [x] The crash line lands with the right code - crash-report.ps1 E (code=0x80000003), ALL PASS 30, acceptance run 20261121-114908
- [x] The crash line names the real faulting address - new E check: ledger addr equals the crash report's address (0x7FF793E3777E both), two filters reading the same ExceptionRecord
- [x] The run reads start -> crash and nothing else - new E check (`start,crash`)
- [x] The next launch does not also accuse the crashed run of an unrecorded exit - new G check (0 lines)
- [x] The exception still reaches Windows' own handling - crash-report.ps1 B: exit code is the exception code (0x80000003). LocalDumps itself is not configured on this box (HKLM, admin) and was not exercised; the exit code is the evidence the default handler ran
- [x] Harness floor (scoped) PASS and stamped
