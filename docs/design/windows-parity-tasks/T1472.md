# T1472 - Nothing makes the composer's three offset suites due when the offset code changes, so the seams that teeth-check them can go unrun

## In plain terms

Three test scripts check that pictures and quotes land in the right place in a
feedback report, including when the text has accents or emoji in it. Nothing
tells anyone to re-run them when the code they check is edited, so the person
who changes that code has to already know they exist.

## Summary

`scripts\guard-due.ps1` has a `viewer-feedback` row covering
`ViewerFeedbackBar.zig`, and that row points at `viewer-feedback.ps1` alone.
The three suites that actually assert OFFSETS —
`test\win32\viewer-feedback-utf16.ps1`, `viewer-feedback-images.ps1` and
`viewer-feedback-carousel.ps1` — are in no row at all, and neither is
`src\apprt\win32\utf16_offset.zig`. So editing the conversion makes nothing
due, and none of the three writes a stamp.

T673 gave those suites their teeth (`GHOZTTY_TEST_BREAK_UTF16=1` and
`GHOZTTY_TEST_BREAK_CHIP_RANGE=1`). This is the other half: the scheduling that
makes somebody use them.

## Details

- Add a guard row — `viewer-feedback-offsets` is the obvious name — covering
  `src\apprt\win32\utf16_offset.zig`, `src\apprt\win32\viewer_feedback_images.zig`
  and the three scripts. Whether the existing `viewer-feedback` row should also
  gain `utf16_offset.zig` is a judgement call: one row per HARNESS is the
  table's shape, so a file covered by two harnesses belongs in both rows.
- A guard row is only half-wired without the stamp: each of the three scripts
  needs the `guard-due.ps1 update -Guard <name>` block that
  `viewer-feedback.ps1` ends with, gated on `$script:fail -eq 0`. A row with no
  stamping harness reads DUE forever, which trains people to reach for
  `-NoGuardDue`.
- Three scripts stamping ONE guard means the guard is only as fresh as the
  last of them; consider a row per script instead, which is what the table does
  elsewhere (`viewer-feedback` vs `viewer-feedback-capture`).

## Validation criteria

- [x] Editing `src\apprt\win32\utf16_offset.zig` makes the offset suite(s)
      report DUE from `scripts\guard-due.ps1 check`. — appended a probe
      comment: all three rows read `GUARD DUE ... has not been run since these
      changed`; bytes restored, all three back to `GUARD CURRENT`.
- [x] A clean green run of each covered script clears its own guard, and a red
      run leaves it due. — `acceptance-parallel.ps1 run`: utf16 32/32, images
      48/48, carousel 59/59, each `STAMPED`. Red: utf16 stamp parked, run with
      `-BreakUtf16` = 5 FAILURE(S), no stamp written, guard still DUE.
- [x] `scripts\go-loop-exec.ps1 claim` and `parity-tasks.ps1 validate` both see
      the new row (the standing two-ended arrangement), demonstrated rather
      than asserted. — both call the same `guard-due.ps1 check` that printed
      the DUE/CURRENT lines above; `validate` run before the commit (see log).

## Decision recorded

One row per script, not one shared row: a shared guard would read current
after the first of three green runs. The existing `viewer-feedback` row did
NOT gain `utf16_offset.zig` — that harness types ASCII only, so a change to
the conversion cannot be observed there; the three new rows own it.
