# T896 - Restored windows can silently lose their IPC name when a carried-forward manifest holds a duplicate

## In plain terms

After a launch where the layout was rescued rather than restored (the T590
carry-forward), the saved layout can contain two windows that recorded the same
automatic name, like "window-1" from two different app runs. When they both
come back, only one can own the name — the other opens fine but scripts that
address it by that name reach the wrong window or nothing.

## Summary

Before T590 a manifest was always regenerated by ONE process, whose auto
window names (`window-N`, a per-process counter) are unique within it. The
carry-forward can now merge entries written by different processes into one
file, so two entries can legitimately record the same `ipc_name`. On restore,
`createWindow`/`ipcRegisterChecked` gives the name to the first claimant
(idempotent registry semantics, correct) and the second window's registration
is refused — it keeps no name at all, so `+list` shows an empty `target` and
`--target=<name>` cannot reach it.

Observed while validating T590: phase B's manifest held the agentless run's
blank "window-1" beside the carried previous run's blank "window-1"; phase C
restored both, and one came back unnamed.

## Details

Options to weigh when picking this up: (a) on restore, a refused window-name
registration falls back to the next free auto name (`window-N+1`) and the
manifest re-records it on the next sync — closest to what a user expects;
(b) dedupe at carry time (mergeCarried skips a carried window whose ipc_name
matches a live/local one) — simpler but silently drops a name the carried
window may deserve more; (c) leave it — the pane-id route always works.
Explicit user-chosen names can collide the same way (a new window named
"build" while a carried "build" waits), so the fallback arm should apply to
both, and the incumbent should always win.

## Validation criteria

- [x] A manifest holding two windows with the same recorded `ipc_name`
      restores both, one under the name and one under a deterministic fallback
      that `+list` reports and `--target=` resolves. Verified by section E of
      `test\win32\window-name-restore.ps1` (E2/E3/E4 name it, E5-E8 route a
      `+rename` by the fallback and require it to reach that window only).
- [x] The next sync re-records the fallback name so it survives the following
      restart. Verified by E9: the manifest written after the restore records
      both names, distinct and non-empty.
- [x] Unit or acceptance coverage for the collision path. Sections E and F of
      `test\win32\window-name-restore.ps1`, both demonstrated red: E against a
      temporarily restored pre-T121 arm, F against the shipped code before the
      empty-name fix.
