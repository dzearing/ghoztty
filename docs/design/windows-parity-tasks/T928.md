# T928 - Viewer: right-clicking a link inside an iframe still gets the browser's menu

## Summary

T826 gave every viewer link Ghoztty's own right-click menu, but only in the page's MAIN frame. Mac runs links.js in subframes too; on Windows a subframe's postMessage is delivered to ICoreWebView2Frame's own WebMessageReceived rather than to the web view's, so a subframe copy would suppress the browser's menu and have nowhere to send the href - a right-click that opens nothing. Add the FrameCreated / ICoreWebView2Frame plumbing, then drop the main-frame guard for links.js.

## In plain terms

Right-clicking a link in a viewer pane offers Ghoztty's own menu (open beside,
open in browser, copy) - except when the link sits inside an embedded frame on
the page, where you got the browser's generic menu instead. After this, a link
inside an embedded frame, or a frame inside a frame, gets the same menu as any
other link on the page.

## Goals

- [x] A right-click on a link inside an iframe shows Ghoztty's link menu
- [x] An iframe nested inside an iframe behaves the same way
- [x] A relative link in a frame resolves to the real file, the same as on the page itself
- [x] An iframe can open the link menu and nothing else - it cannot set the
      table of contents, quote, or feed its selection into a feedback report
- [x] A runtime too old for the frame events keeps the browser's menu (no dead right-click)

## Where it landed

- `src/apprt/win32/webview2_frame_iface.zig` - new: `ICoreWebView2_4`
  (`add_FrameCreated`), `ICoreWebView2Frame` (`IsDestroyed`), `Frame2`
  (`add_WebMessageReceived`), `Frame7` (nested `add_FrameCreated`), the
  created-args, and three handler IIDs; slot offsets asserted.
- `src/apprt/win32/viewer_bridge.zig` - `subframe_js`: inverted guard, shim,
  `links.js`.
- `src/apprt/win32/ViewerPane.zig` - `subscribeFrames` (installs the subframe
  blob only once frames can be heard from), `adoptFrame` / `pruneFrames` (one
  shared handler object per kind, frame references held until the frame is
  destroyed), `onFrameMessage` (link menu only).

## Known limits

- A CROSS-origin iframe is not covered by the live test (the test pages share
  the `ghoztty-page` origin). WebView2 documents frame `postMessage` for any
  origin, so it should behave the same; not proven here. Filed as T1700.
