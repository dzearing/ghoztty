# T1684 - A new window does not open a fresh shell - it attaches to the shell another window is already running

## Summary

Reported by the user on 2026-09-20 while using the installed release: opening a new window did not start a default shell. The pane came up already attached to the same process another open window was running, so two windows are typing into one shell.

## In plain terms

Two windows ended up showing the same shell. A terminal session can only be
displayed in one place, and whoever asks for it last gets it - so the window
that had it is left showing a picture that never updates again, while anything
typed into it still reaches the shell the other window is driving. What the
user saw was a window that never started a shell of its own.

## Goals

- [x] A window can never come up holding a shell another window is running
- [x] The record the app keeps of its windows can no longer name one shell twice
- [x] A pane that would have stolen a shell opens a fresh one instead
- [x] Both halves are pinned by tests, and the new check is seen scoring red

## What was wrong

Two halves, one symptom.

- **Nothing enforced one pane per session on restore.** The session manager
  binds a session to the NEWEST `ATTACH` and never refuses (T703), so if the
  layout the app restores names one session in two windows, it replays both and
  the second takes the shell off the first. `reconcile` already refuses an
  AGENT-recovered window whose session a local window claimed, but the local
  manifest itself was never checked against itself.
- **And the manifest could be written that way.** `mergeCarried` (T590) carries
  a window the launch could not restore forward through the wholesale manifest
  rewrite, and adjudicated it by its window KEY alone. A session that came back
  under a DIFFERENT key - a Restore All, an adoption, a window the user rebuilt
  - left the carried entry in place, so the next sync recorded that session in
  the live window AND in the carried one.

## The fix

- `SessionClaims` in `src/apprt/win32/App.zig`: a restore pass hands each
  session to at most one leaf. A later leaf naming a session the pass already
  gave away is treated exactly like a positively-gone one - it OPENs a fresh
  shell - and says so in the log. Live only between `beginRestoreClaims` and
  `endRestoreClaims`, which wrap the launch/deferred pass and nothing else: the
  in-place recovery walk legitimately re-attaches sessions live panes hold, and
  must see the rule switched off rather than half-applied.
- `session_layout.mergeCarried`: a carried window whose sessions are live under
  another key is adjudicated and dropped, and two carried windows naming one
  session ride along once.

## Validation criteria

- [x] A restore whose manifest names one session in TWO windows attaches it to
      exactly one pane, and the other window comes back with a shell of its own
      - `test/win32/restore-session-dup.ps1` section B, ALL PASS (8 assertions)
- [x] No restored pane is left without a shell by the new refusal, and no two
      panes report one shell pid - same script, B5/B6
- [x] The new check is demonstrated scoring RED against the state it refuses -
      `restore-session-dup.ps1 -NegativeControl` fails B2 and exits 1
- [x] `mergeCarried` can no longer record one session twice - unit tests
      "T1684: ..." in `src/apprt/win32/session_layout.zig`, `none` lane green
- [x] The claim rule is inactive outside a restore pass (every other attach path
      is byte-identical) - unit test "SessionClaims: one pane per session, and
      only while a pass is running", win32 lane
- [x] An ordinary two-window session is unaffected: each new window still opens
      its own shell - measured directly before the fix (three windows, three
      distinct sessions and pids) and again by section A
- [x] Standing floor: `floor-lane.ps1 -Lane all`, and the harness is registered
      as the `restore-session-dup` guard row so an edit to either covered file
      makes it due
