# T1910 - A phone photo copied from an image pane comes out sideways: ctrl+C ignores the EXIF orientation the pane displays

## Summary

T1872's copy decodes the file's first frame with WIC, which hands back the pixels as STORED. A JPEG from a phone stores them rotated and carries an EXIF Orientation tag (274); the pane's browser applies it (image-orientation: from-image) so the user sees it upright, then pastes it sideways. Read /app1/ifd/{ushort=274} through IWICMetadataQueryReader and apply it with IWICBitmapFlipRotator before CopyPixels (src/apprt/win32/image_copy.zig decode). Verify first that the pane really does show such a file upright. Validation: a unit test in image_copy.zig over a generated JPEG with Orientation=6 reads back transposed dimensions, plus a viewer-image.ps1 K arm.

## In plain terms

A photo taken in portrait on a phone shows the right way up in an image pane,
but pressing Ctrl+C put it on the clipboard sideways, so it pasted sideways
into a chat or a document. Now the copy is turned the same way the pane shows
it, so what you paste is what you saw.

## Goals

- [x] Ctrl+C at an image pane copies a phone photo upright, as the pane shows it
- [x] A picture with no orientation tag copies exactly as before

## Validation criteria

- [x] The pane really shows such a file upright: viewer-image.ps1 K5, the page reports natural 400x800 for an 800x400 JPEG tagged Orientation=6.
- [x] Ctrl+C copies it upright: K5, the copy log says `size=400x800` and the clipboard reads back 400x800 (`viewer-image.ps1` ALL PASS, 54 assertions, test desktop).
- [x] Every one of the eight EXIF orientations maps the stored pixels correctly: `image_clipboard.zig` "orient: every EXIF orientation..." (none lane).
- [x] WIC actually reads the tag from a real JPEG: `image_copy.zig` "decode turns a phone photo upright..." asserts `rotate_90` and 16x32 with red on top for tag 6, blue on top for tag 8 (win32 lane, filtered run 88/88).
- [x] Untagged pictures unchanged: same test's plain case; K1-K4 still pass.
