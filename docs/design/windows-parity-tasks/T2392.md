## In plain terms

The frame lab is the tool that will tell us, frame by frame, whether resizing a
window or a pane ever shows the user a flash or a stale picture. Before its
verdicts can be trusted, two things have to be proven on the real screen: the
mouse lands exactly where the script says, and when the screen recorder misses
a frame it says so. This task built the script that proves both. It refuses to
run while anyone is using the machine.

## Re-scope (2026-10-28, at claim)

The task as filed was the whole live driver. Reading the pieces turned up one
it did not account for: FrameScore scores a frame against a FIXED scene, and in
a live resize every card rect moves every frame. So a per-frame scene inference
has to exist before any live cell can be scored, and it must not infer the pane
from the card's own content, or a stale-size frame reads clean. That is a
design task of its own. The box was also LOCKED for the whole turn (LockApp
covers the monitor, so presence reads `present`), so nothing live could run.
Split, so the work that needs no scorer lands now:

- **landed here**: `test\win32\frame-lab.ps1`, a declared input-desktop
  exception, presence-gated with `Assert-UserAbsent`: pure section A (the
  cursor-check sink and the drop-control decision), live B (cursor calibration
  plus a 1 kHz move-only shuttle checked read by read) and live C (the WGC-drop
  positive control), plus the `StallAtFrame`/`StallMs` knob in
  `lib\FrameCapture.ps1` that C needs.
- **T2394**: the live per-frame scene scorer.
- **T2395**: the matrix launcher, Score bridge, results JSON/HTML, and one live
  verdict per pointer interaction (deps T2394).
- **T2396**: the first live run of B/C on an idle, unlocked box.

Mechanism note (for T2394/T2395): FrameLabInput's types compile in memory, so
no later Add-Type can reference their assembly. frame-lab.ps1 therefore
compiles its GflCursorCheckSink WITH `$script:FrameLabInputSource`, before
anything imports it.
