# T1574 - A force-killed GUI fixture is reported as a CRASH in the postmortem

## Summary

A script that tears down its own app with Stop-Process -Force before Remove-TestDesktop leaves the launch unmarked as a deliberate kill, so Write-TestDesktopPostmortems reads its 0xFFFFFFFF exit code and prints 'CRASHED - unnamed NTSTATUS' with a stack-less report. Observed on window-composite.ps1 during T778 (fixed there by letting Remove-TestDesktop do the killing); pane-capture.ps1 has the same shape, and the pattern is easy to copy. Either mark the launch killed from the script's own teardown or teach the postmortem to recognise a harness-issued force kill.

## In plain terms

When a test script shut down its own copy of the app on purpose, the end-of-run report called it a crash. That false alarm made real crashes easy to miss. It was already fixed by an earlier change; this task only confirms that fix.

## Goals

- [x] a test that stops its own app is not reported as a crash, whatever form the stop takes
- [x] an app that really dies on its own is still reported as a crash

## Validation criteria

- [x] A bare `Stop-Process` on a harness launch (by -Id, piped, positional) is not reported: `gui-postmortem.ps1` L2/L3/L5 PASS (acceptance-parallel run 20261120-190119, ALL PASS 57).
- [x] A self-exiting 0xFFFFFFFF child is still CRASHED: L4 PASS; a stop after death does not mark it killed: L6 PASS.
- [x] pane-capture.ps1:249 stops `$app.Pid` (a harness launch record, line 117), so the library's Stop-Process proxy (TestDesktop.ps1:3017) marks it; window-composite.ps1 already defers to Remove-TestDesktop.
