# T927 - Test harness: no way to synthesize a real user input event into a WebView2 page

## Summary

The host-floor viewer test drives pages with ExecuteScript, which carries user activation of its own - so it can stand in for a click but cannot tell a click apart from a page navigating itself. T825 needed exactly that distinction and both DevTools routes tried (Runtime.evaluate with userGesture:true, and Input.dispatchMouseEvent) returned S_OK from CallDevToolsProtocolMethod and had no effect on the page, which cost a context to discover. T825 worked around it with a page that navigates itself at load time. Find out why the CDP input path is inert (session/domain enable? a completion handler the null argument skips?) and give the harness a real press, so the next test that needs one does not re-derive this.

## In plain terms

The automated tests for viewer panes could only "click" a page by running a
script in it, and a page can tell that apart from a person's click. So a test
could not check behavior that depends on whether a real person clicked. The
tests now have a real click they can send to any element on the page.

## Goals

- [x] Find out why the DevTools input route looked inert in T825
- [x] A test helper that sends a real, aimed press to an element
- [x] A live test proving the press is trusted, the script click is not, and a press on a link out of a live page is routed like a user's click
- [x] Document the helper where the next viewer test author will look

## Root cause

The DevTools input path is **not** inert. Measured on this box (hidden parent
window, controller hidden or shown, completion handler or null): both
`Input.dispatchMouseEvent` calls return S_OK with `{}` and the page receives a
click with `isTrusted: true` and `navigator.userActivation.isActive: true`.
The T825 attempt was never committed, so its exact shape is lost; the one
thing it could plausibly have got wrong that this path is sensitive to is
AIM: a press lands on whatever sits at (x, y) in viewport CSS pixels, and a
one-word link is a small target. The helper therefore measures the element's
box first (`getBoundingClientRect`, after `scrollIntoView`) and presses its
centre.

## Validation criteria

- [x] A harness press on a small, off-origin button reaches the page as a trusted click (`click:true`) - `T927: a harness press is a real click, and an ExecuteScript click is not`, win32 lane filtered on `T927`, PASS
