# T2693 - Ctrl+Enter in a Claude Code pane on Windows never fires Claude's send-now (its default chat:sendNow key); Mac delivers it

## In plain terms

In Claude Code on Windows, Ctrl+Enter (send the message now) did nothing
special, and Shift+Enter could not be told apart from Enter. On a Mac both
work. Now Windows hands Claude Code the same keys a Mac does, so Ctrl+Enter
sends now and Shift+Enter reaches it as Shift+Enter.

## Goals

- [x] find what bytes a Claude-Code-style program actually receives for Ctrl+Enter on Windows
- [x] deliver modified Enter/Tab/Backspace/Escape in the form the program asked for (kitty / modifyOtherKeys), like macOS
- [x] leave every other key (text, Ctrl+letter, Ctrl+C, plain Enter) exactly as before
- [x] an on-box acceptance harness that reads the bytes, with a negative control

## Summary

Measured 2026-11-05 with a raw-mode Node reader (libuv, the console read path
Claude Code's Bun runtime uses) that sets up its keys the way Claude Code does
under `TERM_PROGRAM=ghostty` (strings in claude.exe 2.1.318: `ghostty` is in its
extended-keys allowlist, so it writes `CSI < u`, `CSI > 1 u` and `CSI > 4;2 m`).
Ghoztty receives and acknowledges the kitty push (`CSI ? 1 u` comes back), but
ConPTY runs the terminal in Win32 Input Mode, so every key left Ghoztty as a key
record and conhost turned it back into bytes for the program: Ctrl+Enter
arrived as `0a` (same as Ctrl+J), Shift+Enter as `0d` (same as Enter). Writing
`CSI 13;5u` into ConPTY raw does not help: conhost's input parser drops it.

Fix: `src/apprt/win32/kitty_key_bridge.zig` (pure: the decision + the bytes) and
`Surface.sendKittyBridgedKey`. While the program has asked for kitty flags or
modifyOtherKeys 2, a Ctrl/Alt/Shift + Enter, keypad Enter, Tab, Backspace or
Escape is encoded by the core encoder and sent as one win32-input CHAR record
per byte, all in one write; conhost passes char records through verbatim, so
the program reads `CSI 13;5u` (kitty) or `CSI 27;5;13~` (modifyOtherKeys),
the same bytes a macOS Ghoztty writes. Everything else stays a key record, so
console-API programs, Ctrl+C interrupts, dead keys and IME are untouched.

The modifier field carries NumLock (`13;133u` with NumLock on), which is what
the kitty spec and a Linux Ghostty send; Claude Code's parser masks the bits
(`ctrl: (n-1)&4`) and buffers an escape split across reads
(`incompleteEscapeTimer`), so both are harmless to it.

Mac seat: nothing owed - macOS has no ConPTY and already sends these bytes.

## Validation criteria

- [x] Ctrl+Enter / Shift+Enter / Alt+Enter / Ctrl+Backspace reach a kitty-mode reader as CSI <code>;<mods> u with the right modifier bits - `test\win32\kitty-key-bridge.ps1` A, green 16/16 on the test desktop, 2026-11-05
- [x] plain Enter, Ctrl+J and Ctrl+A unchanged in the same session (0d 0a 01) - same harness, B
- [x] with nothing requested Ctrl+Enter / Shift+Enter stay LF / CR - same harness, C
- [x] modifyOtherKeys-only reader gets CSI 27;N;13~ - same harness, D
- [x] negative control: `-NegativeControl` scores red (1 failure) - 2026-11-05
- [x] pure decision/encoding unit tests (`T2693:` in kitty_key_bridge.zig) - win32 lane `-Dtest-filter=T2693` green
- [ ] NOT RUN: a real Claude Code session on screen pressing Ctrl+Enter - it would send a message on the user's account and needs their desktop; the byte oracle plus Claude Code's own parser code stand in
