# T2386 - A lane's split or release of a claimed task is invisible to the other lane until the end-of-turn push, so the other lane re-claims and re-does the same work: set-status/new on a lane-claimed task should commit and push the tracker change at once (or keep the claim held until it is pushed)

## Summary

2026-10-27: lane b claimed T2373 at 20:37, split it locally into T2374-T2379 and set T2373 back to todo (which released this lane's ledger claim), then built the scorer slice for ~1h45 without pushing. Lane A's 22:02 next -Claim saw T2373 as an open todo, split it again (T2381-T2385) and built the same scorer; lane b's push hit add/add conflicts and its work was dropped (kept at tag t2374-alt-scorer). Either set-status on a split / new children should push immediately through the commit guard, or the ledger claim should stay held until the release reaches origin. Acceptance: a two-lane fixture in test\win32\loop-lanes.ps1 where lane 1 splits and lane 2's next does not hand out the parent or its scope.

## In plain terms

Two copies of the work loop run side by side. When one of them broke a big job into smaller pieces and put the big job back on the shelf, the other copy could not see the pieces yet, saw the big job sitting there untouched, and did the same work again. Now the first copy keeps the big job reserved until its pieces have actually reached the other copy, so the work is done once.

## Goals

- [x] `set-status todo` on a task the lane has split (a changed or new task file names it) or edited (deps, summary) keeps it reserved in the ledger instead of releasing it
- [x] the other lane's `next` skips it and says `RELEASED IN OTHER LANE`, until its own copy matches the released one
- [x] the reservation survives a long unpushed turn: the lane's watchdog heartbeat refreshes its own unpushed reservations
- [x] a plain abandonment (claimed, journaled, set back) still releases at once

## Design

Chose "keep the claim held until it is pushed" over "push from set-status": parity-tasks.ps1 never commits, a mid-task push would bypass the commit guard's message/validate discipline, and the T2033 close reservation already has exactly this shape. A release reservation is a ledger claim with `closed: "todo"` plus `sha` (hash of the released file). It is pushed when `@{u}` holds that text (or the lane's current copy) and caught up when the other lane's copy does. Scope detection (`Get-LedgerReleaseScope`): the task text minus `status:` and `## Progress log` differs from `@{u}` (`edited`), the upstream lacks the file (`new`), or a task file changed/untracked vs `@{u}` names the id (`split:<ids>`). No git upstream -> release as before. Acceptance lives in `test\win32\parity-tasks-lanes.ps1` section H (the ledger harness) rather than loop-lanes.ps1, which covers lane plumbing, not the ledger.
