# T1592 - Prove the job-ownership refusal fires: a pane-launched destructive refresh should read AGENT_OWNS_JOB=yes and be refused, not obeyed

## In plain terms

When the terminal offers to restart its background helper, it now checks first
whether doing so would take the terminal down with it, and backs out if it
would. Nobody has watched it back out. Until somebody has, "it would refuse" is
a belief about the code rather than something the product has been seen to do.

## Summary

T771 added `AGENT_OWNS_JOB` to the pre-kill diagnostic and a refusal in
`LocalAgent.terminateAgent` keyed off it. Both are proven in the directions
available on a background test desktop:

- the pure verdict (`jobIsAgentsFrom`) is unit-tested over the exact field shape
  T268 met - agent NOT a member, and yet the job is the agent's;
- `agent-upgrade.ps1` arm J (J22b/J22c) proves the term is on the real line in a
  real destructive refresh, and that it is NOT `yes` there, because that arm's
  app escaped its job at startup.

What is NOT proven is the arm that matters: the T268 shape itself. That needs
an app launched FROM A PANE (so it is auto-assigned to the agent's kill-on-close
PTY job), the startup escape suppressed, and a destructive refresh driven
through it. The expected outcome after T771 is `AGENT_OWNS_JOB=yes` followed by
`REFUSING to terminate pid N` and a **surviving app** - where before T771 the
app simply vanished mid-call with no further log line.

That arm is also the negative control the refusal is owed: a gate that has never
been observed saying anything but "carry on" is indistinguishable from a gate
that cannot say anything else.

### What the run found (2026-11-20)

The premise was half stale. Since T909 the default PTY is **holder-backed**: a
per-session holder process (escaped from the agent's job) creates the named PTY
job and parents the shell. In that shape the agent parents no shell, so
`AGENT_OWNS_JOB` reads `no` - correctly, because killing the agent leaves the
holder holding the job and the pane-launched app lives (R6 measures exactly
that). The T268 shape still exists in the **in-process** child
(`GHOZTTY_AGENT_PTY_HOLDER=0`, and the fallback when a holder will not start),
and there the refusal fires (R5). Both are now arms of
`test\win32\app-restart.ps1`, because that harness already drives the real
destructive kill (the palette's "Restart Ghoztty and Background Sessions"); the
`app-restart` guard row now covers `LocalAgent.zig`, `job_object.zig`,
`pty_holder_child.zig` and `pty_child.zig`.

The app is put in the job the way a user does it: created with the pane's shell
as its parent process (PROC_THREAD_ATTRIBUTE_PARENT_PROCESS), so Windows places
it in the shell's job at birth; the harness holds no job handle by the time
anything destructive runs.

Follow-ups filed: T3294 (after a refused kill the command relaunches anyway and
says the sessions ended when none did), T3295 (under holders the command may end
no session at all).

## Goals

- [x] Build the pane-launched shape for real, on the test desktop
- [x] See the refusal say no where the kill would be fatal
- [x] See it stay quiet where the kill is safe (the holder default)

## Where to start

- `test\win32\job-escape-startup.ps1` already knows how to build the hostile
  shape (it constructs a real kill-on-close job and proves an escaped app
  survives its teardown). The missing arm is the un-escaped app plus a refresh.
- `GHOZTTY_JOB_ESCAPE` is the knob that suppresses the startup escape; check
  `src\apprt\win32\job_escape.zig` for the exact spelling before relying on it.
- Verdict plumbing: `job_object.ownJobIsAgents` / `jobIsAgentsFrom`, and the
  refusal in `LocalAgent.terminateAgent`.
- Wire the new arm into the `job-escape-startup` guard row (it already covers
  `job_object.zig`) rather than minting a new harness.

## Validation criteria

- [x] A pane-launched (job-assigned, escape suppressed) app writes
      `AGENT_OWNS_JOB=yes` on the pre-kill line - app-restart.ps1 R5a, in-process
      PTY shape (`self_job_flags=0x2000 ... SHARED_JOB=no AGENT_OWNS_JOB=yes`)
- [x] ... and the refresh is REFUSED, with the `REFUSING to terminate` line naming
      the pid - R5b
- [x] ... and the app is still alive afterwards, which is the whole point - R5c
      (the app logged `stopped=false`, i.e. the call returned), R5e/R5f (agent
      and shell are the same live processes)
- [x] The arm is a negative control too: it fails if the refusal is removed -
      built once with the `if` compiled out: R5b/c/e/f went red and the log
      stopped dead after the job-facts line with no `terminate returned`, the
      exact T268 field signature; source reverted (`git diff -- src` empty) and
      rebuilt
- [x] The guard row covering it re-stamps green - `app-restart` (84 assertions,
      ALL PASS, on the restored build); the row now covers the refusal's sources
- [x] (added) Under holder-backed PTYs the refusal stays quiet and the app
      survives the kill - R6a-R6e
