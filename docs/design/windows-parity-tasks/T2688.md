## In plain terms

The test that checks "a window the app could not save says so" had gone red.
The app was fine: an earlier fix made a cold `ghoztty +new-window` open only
the window you asked for, and the test was still waiting for the old extra
blank window. The test now asks for a second window itself, so it checks the
same two windows as before.

## Goals

- [x] Find why C1/D2 went red (root cause, not a guess)
- [x] Make the harness match the one-window cold launch without losing the cooldown-window coverage
- [x] File what the investigation found that is not this task's

## Root cause

Not an app regression. T2162 (bf61f22e8, 2026-10-23) made a cold
`+new-window --target=X` pass `--initial-window=false` to the auto-launched
app, so it opens ONLY window X instead of X plus a blank `window-1`. Sections
C and D still expected two panes: C1 required a launch window (`window -ne
rdC`) and D2 required `panes.Count -ge 2`, so both went red with one pane,
while C2 passed vacuously over an empty launch set.

Fix (harness only): `Invoke-FailedLaunch` asks for `$Name`, waits for its
notice (that first window IS the launch window now, and its own resolve is
the one that fails), then asks for `$Name-2`, which lands in the 15s cooldown.
C reads rdC as the launch window and rdC-2 as the cooldown window, so C2 and
C3 each test a real window again.

Found in passing and filed as T2781: section A (2.5s resolve hold) still lists
a stray `window-1` beside rdA through the CLI auto-launch, although a direct
`--initial-window=false` launch with the same hold opens only rdA.
