# T3778 - On Linux the app's own memory keeps climbing about 1 MB per pane split opened and closed once you go past 30 cycles

## Summary

test/linux/pane-close-memory.sh with SCENARIOS=split CYCLES=50 WARMUP=8 (T3646 run, 2026-11-25, Debug GTK app on Mesa llvmpipe via LIBGL_ALWAYS_SOFTWARE=1): M1 FAILED - app private memory 296952 -> 350624 KB over 50 measured cycles, 1073 KB per closed pane, while threads, fds and child processes all came back (M2-M5 green) and the agent's live heap stayed flat. The default 12-cycle run passes at ~135-376 KB per cycle, and the 2026-11-24 note says the app plateaus after ten warm-up cycles, so the climb is not warm-up. Rerun with REPORT=1 to see whether it is linear or stepwise; separate GL/Mesa memory (render targets, atlases freed by T3645) from GTK widget/GObject retention (a closed Surface whose finalize never runs keeps all of it), e.g. by comparing against GDK_DEBUG/G_DEBUG refcount tracing or a CYCLES=100 run.

## In plain terms

A memory check on the Linux build once said the app kept about 1 MB every
time a split pane was opened and closed. Re-measured, it does not: the app
fills its caches over the first ten or so panes and then stays flat. That
one run started measuring before the caches were full. The check now keeps
warming up until memory levels off, so a slow start can no longer read as a
leak, and a real leak still fails it.

## Goals

- [x] Find out whether the climb is real: it is not, it is warm-up
- [x] Make the check wait for the plateau instead of a fixed count
- [x] Record the finding where the next reader of the check will see it

## Root cause

Not a leak. The 2026-11-25 failure does not reproduce: `SCENARIOS=split
CYCLES=50 REPORT=1` passes at 5ac82365f (129 KB a cycle, flat 340.7 MB from
cycle 10 to 50), at 4a2d831378 (112 KB) and at da7a3488b6, the very commit
the failing run was taken on (183 KB). That run's baseline was 297 MB where
every re-run's sits at ~335 MB after the same 8 warm-ups, and it ended at the
same ~345-350 MB plateau; the measured cycles were the tail of warm-up. Glibc
tunables do not move it (`MALLOC_ARENA_MAX=2` 255 KB, `MALLOC_MMAP_THRESHOLD_=131072`
260 KB), and threads, fds, children and the agent's live heap all came back
in every run. So no app commit fixed anything; the fix is the check's
warm-up, which now runs until a 4-cycle block grows by <= 1 MB a cycle (cap
32), in `test/linux/pane-close-memory.sh`.
