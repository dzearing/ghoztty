# T3746 - Find why the composition present failed on the user's Remote Desktop box (the T3739 blank WSL pane): read the compFail stage and hr from their log and fix that failure, so the SwapBuffers fallback stays rare

## Summary

T3739 made a pane on a reused window draw when the composition path fails, and made a stranded pane retry. It did not find out WHY the composition present failed on the user's box in the first place. Their app log has a line 'composition present failed (<err>) at <stage> hr=0x...' (OpenGL.zig compFail) or 'composition present unavailable ... at <stage>' just before 'could not move the pane context'. Get that line (ask the user for %LOCALAPPDATA%\ghoztty logs from 2026-11-25), name the stage, and fix that failure. Remote Desktop is the suspect (see T3738): if DirectComposition or the interop fails over RDP, detect it up front, the way the no-interop path is (comp-present arm L), rather than failing mid-life. Deps: T3739.

## In plain terms

With many terminal panes open at once, every pane after the fifteenth
quietly lost Ghoztty's fast drawing path. On a recycled window that is what
left the user's WSL pane blank. The cause is a graphics-driver limit: one
graphics device accepts at most fifteen panes. Ghoztty now opens another
device when one is full, so the twentieth pane draws the same way as the
first.

## Goals

- [x] Find a failure that reproduces the symptom: on this box the 16th pane open at once fails at `wgl-open-device` every time (seven app runs in the debug log show it; the probe below reproduces it on demand)
- [x] Show it is a limit on panes open at the same time on one D3D11 device, not a leak and not RDP: closing panes frees slots, and with `GHOZTTY_COMP_SHARED_DEVICE=0` (a device per pane) 25 of 25 panes built their chain
- [x] Fix: the process-wide device (T2968) is now a pool of up to 8. A pane that is refused goes to the next pooled device, and every pane tries device 0 first (`DeviceCache.acquireAt`, `nextPoolIndex`, `Presenter.init` opens the interop before building on the device)
- [ ] Confirm against the user's own log line. NOT DONE: the user's `%LOCALAPPDATA%\ghoztty` log is on their laptop, and the loop does not ask. This box shows a deterministic cause that produces their exact chain of failures. A user who keeps many Claude panes open passes 15 easily. If the release carrying this still leaves a pane blank, their `composition present ... at <stage>` line names the next cause

## Validation criteria

- [x] Reproduced before the fix: a scratch probe (debug build, test desktop) opened 20 windows and got `ok=15 unavail=5`, all at `wgl-open-device hr=0x0`. Closing 15 and opening 5 more gave 5 new chains, so the failures track panes open at once. With `GHOZTTY_COMP_SHARED_DEVICE=0` the result was `ok=25 unavail=0`. This is the negative control for arm P
- [x] After the fix, the same probe gave `ok=25 unavail=0` with the default shared device, and the log shows `D3D11 device 0 refused another GL interop open; this pane tries pooled device 1` and `pooled D3D11 device 1 created`
- [x] Unit tests (none lane): "T3746: a pane refused by a pooled device gets the next one, and slot 0 stays first" (references, protection, reuse, deinit drops every slot) and "T3746: the pool is bounded, and a device of its own has nowhere to go". The T2968 cache tests are unchanged and still pass
- [x] `test\win32\comp-present.ps1` new arm P: 20 panes at once all build their chain with none unavailable (P1). On NVIDIA the pool must have grown, so the arm cannot pass without reaching the cap (P2). The 20th pane draws text (P3). After 15 closes a new pane builds on device 0 with no refusal (P4). No GL error (P5). ALL PASS, 140 assertions (`acceptance-parallel run -Scripts comp-present.ps1`)
