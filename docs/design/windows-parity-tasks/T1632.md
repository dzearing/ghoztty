# T1632 - Two Activity Monitor panels on one machine silently steal each other's host-CPU reading

## Summary

A Connection carries exactly ONE metrics_handler slot, so two Activity Monitor panels riding the same link cannot both watch the host CPU stream: the second subscribeMetrics overwrites the first's handler, and the first panel to close unsubscribes the stream out from under the other. Today that is reachable through the BORROWED arm - two windows on the same remote machine, each opening the panel from the palette, both borrow that window's connection. It is also the one thing standing between the Activity Monitor and App.machine_pool: T810 left the panel dialing its own connection deliberately (Mac does too - RemoteActivityMonitor.presentDialing owns its handle), and a shared pooled link would make the clobber the normal case rather than the two-window case. The fix is a multiplexed metrics subscription - a fan-out the connection owns, delivering one pushed frame to every subscriber, with the unsubscribe refcounted - after which pooling the panel becomes a safe, separate call.

## In plain terms

If you open the Activity Monitor from two windows connected to the same remote
machine, the first panel's CPU reading freezes, and closing either panel stops
the live CPU reading in the other. After this fix both panels keep updating,
and closing one leaves the other running.

## Goals

- [x] every panel on one connection receives every pushed CPU sample

- [x] no app-agent protocol change (the agent already treats a repeat subscribe as an interval update)

## Outcome

`Connection` carries a fan-out of up to 16 metrics subscribers keyed by `ctx`,
not one slot. `unsubscribeMetrics(ctx)` removes only that subscriber; METRICS_UNSUB
goes out only when the last one leaves, and otherwise the agent is re-armed at
the smallest interval still wanted. There is no wire change: the agent already
treats a repeat METRICS_SUB as an interval update. Pooling the panel's
connection is NOT filed as a follow-up. T810 kept the panel on its own
connection on purpose, which matches Mac (`RemoteActivityMonitor.presentDialing`
owns its handle), so the change removes a hazard rather than unlocking work
that is owed. Mac: shared core plus the embedded C API (same signature for Swift),
so no Swift change is needed.
