# T2081 - Stacked panes on Windows (epic): panes keep a minimum width, and a row that does not fit keeps what fits on show and minimizes the rest into titled strips

## In plain terms

On Mac, panes no longer get squeezed thinner than 300 points. When a row
holds more panes than fit side by side, it keeps as many on show as fit,
and folds the rest into thin titled strips at the row's edge. Clicking a
strip slides that pane into view like a carousel. Windows should behave the
same way.

## Summary

Epic for the Mac stacked-panes family landed on main between 2026-10-18 and
2026-10-20:

- 86b7e3410 `feat(macos): stacked panes - a 300pt minimum, and rows that don't fit stack` -> **T2082**

- 2811a3043 `fix(macos): harden stacked panes - strips stay put, chain collapse, gutter-only resizers, strip drop targets` -> **T2084**
- f9e99a860 `feat(macos): name stacked strips and sidebar rows by the banner title` -> **T2085**
  (the sidebar half stands alone; the strip half needs T2082)
- 89848fd59 (glass for stacked rows: a tucked card is drawn as its strip alone) -> **T2086**

Mac's design: `PaneLayout.swift` is ONE pure layout function shared by the
grid and the stash slots. `PaneStackState.swift` holds the per-row
collapse ("pin"), keyed by the row's panes. `PaneStackTab.swift` is the
strip. `PaneStage.swift` runs the slide on Core Animation, so no terminal
resizes mid-slide. The Mac CLAUDE.md sections added by these commits are
the spec.

Windows-native translation: the split layout already lives in
`src/apprt/win32/` (SplitTree + `split_resize.zig` + PaneDesk/pane cards).
Port the layout as a pure Zig function (unit-tested in the `none` lane the
way PaneLayoutTests covers it), keep the stack state beside the SplitTree
so undo/stash restore it, draw strips as pane-card chrome, and run the slide
by moving the HWNDs/visuals with ONE resize at the end
(SetWindowPos batch / DeferWindowPos, never a resize per frame).
