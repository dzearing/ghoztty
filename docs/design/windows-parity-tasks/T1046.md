# T1046 - agent-adopt's idle-stop wait is a fixed 60s, so a busy box reports ten failures over an adoption that was merely slow

## Summary

Observed on 2026-08-21 while working T1042. Two runs, back to back, same commit,
same binaries, nothing else changed:

- run 1 (after three other acceptance harnesses in the same sweep): 147 s wall,
  `10 FAILURE(S) (16 assertions passed)`.
- run 2 (quiet box): 25 s wall, `ALL PASS (26 assertions)`.

Every one of the ten is downstream of a single wait. `test\win32\agent-adopt.ps1`
line 155 gives the standalone agent a flat 60 seconds to go idle and stop:

```powershell
# The cmd 'session' drains (~10s), then 3 idle polls at 1s land the stop.
$deadline = (Get-Date).AddSeconds(60)
while ((Get-Date) -lt $deadline -and -not $fake.HasExited) { Start-Sleep -Milliseconds 500 }
Assert 'idle standalone was stopped' $fake.HasExited
```

The comment's budget is ~13 s, so 60 s looks generous - until the box is running
another suite and the drain, the polls and the uninstall hop each stretch. Once
that assert falls the run never recovers: the stop, the uninstall, the shield,
the restore announcement and `adoption.json`'s `done` all describe steps that
simply had not happened yet, and section 3's "no re-adoption after done" then
fails because nothing reached done.

The fix is not a bigger number. The wait should key on the thing it is actually
waiting for (the agent's own `stopping`/`stopped` announcement in `a2.err`, the
same way the four asserts above it already do) with a generous ceiling, so a
slow box costs seconds rather than a red suite. Cascading failures should also
be reported as such: nine of these are noise once the first one is known, and
they make a genuine adoption bug hard to see in the output.

## In plain terms

The test that proves an old-style session manager gets retired cleanly reports
ten failures when the machine is busy, and none when it is quiet - same code
both times. It is waiting a fixed minute for something that usually takes
thirteen seconds, and a loaded machine simply takes longer. Ten red lines that
mean "still working on it" are how people learn to skip the output.

## Goals

- [x] the stop wait ends when the agent says it stopped (or could not), not on a clock
- [x] one real failure reads as one failure, not ten

## Validation criteria

- [x] the idle-stop wait keys on the agent's own announcement rather than on a
      flat clock, with a ceiling generous enough for a loaded box - it waits for
      `idle; stopped it|could not stop the standalone` in `a2.err` (240s ceiling),
      then up to 15s for the process to exit; the two downstream waits went
      30s -> 90s (they return the moment the text lands)
- [x] `test\win32\agent-adopt.ps1` passes under load, ten runs in a row - run
      under a 32-job all-core CPU burner instead of a preceding harness (a harder
      CPU condition, though it does not reproduce I/O/process-start contention):
      10/10 `ALL PASS (35 assertions)`, 29-31s each; plus a green run through
      `acceptance-parallel.ps1 run -Scripts agent-adopt.ps1` (28s)
- [x] a genuine failure to stop still FAILS - new `-NegativeControl` keeps the
      fake standalone's session alive for the whole run (45s ceiling): exit 1,
      `1 FAILURE(S) (22 assertions passed, 12 SKIPPED)`; the control never
      stamps, and its ping child is reaped in the finally
- [x] the asserts downstream of the stop report as blocked-by - `Assert-Gate`
      records the root; the 12 downstream asserts print `BLOCKED <name> (by: idle
      standalone was stopped)` and score as skipped (never as passes); section 4,
      an independent fixture, clears the gate
