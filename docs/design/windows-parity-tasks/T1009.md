# T1009 - The activity monitor shows a focus ring when the row was clicked with the mouse

## Summary

`ActivityMonitor.paintTableFocus` (ActivityMonitor.zig:3472) draws the table's focus ring whenever the panel holds focus and `self.focus == .table`, with no reference to Windows' UI state. Windows keeps focus rectangles hidden until the user navigates by keyboard (`UISF_HIDEFOCUS`) and shows them from then on; the machine chooser honours that (MachineChooser.zig:2227 reads `ODS_NOFOCUSRECT` into `RowState.focus_visible`), and the activity monitor is the only other surface here that paints a focus ring. It cannot read `ODS_NOFOCUSRECT` because it is custom-painted rather than owner-drawn, so it has to ask: `SendMessage(hwnd, WM_QUERYUISTATE, 0, 0) & UISF_HIDEFOCUS`, refreshed on `WM_UPDATEUISTATE`. Visible consequence: click a process row with the mouse and a focus ring appears around it; do the same in the machine chooser and it does not. Measured while fixing T988, where the same bit turned out to be the whole reason two chooser probes were intermittently red - `test\win32\chooser-selection.ps1` section E now shows how to pin it from a test.

## In plain terms

Click a row in the activity monitor with the mouse and an outline appears around
it, the kind Windows only shows once you start using the keyboard. Clicking a
machine in the machine chooser correctly shows no outline. The two panels should
agree, and Windows' own rule is the one to follow.

## Goals

- [x] The table's caret ring and the carousel's card ring honour Windows'
      "hide focus until the keyboard is used" state
- [x] The panel tells Windows when it is driven by keyboard, since its keys are
      consumed before DefWindowProc sees them
- [x] The panel starts in the state a dialog would (UIS_INITIALIZE)

## Validation criteria

- [x] Clicking a process row with the pointer selects it and draws NO focus ring
      — `test\win32\activity-selection.ps1` E2 (row fill emphasized, accent mark,
      0 outline lines, UI-state bit still 0x1)
- [x] Navigating with the keyboard draws the ring again, from that point on —
      E3 (Home posted to the panel clears the bit to 0x0; 6 neutral rim lines)
- [x] The panel repaints on `WM_UPDATEUISTATE` rather than only on the next
      focus change — E1 (bit set with no click or focus change; rim gone)
- [x] An on-box probe pins the UI-state bit both ways — C pins it SHOWN, E pins
      it HIDDEN; activity-selection ALL PASS (91 assertions)

## Resolution

`activity_input.zig` gains `focusRingVisible` (panel focused AND
`!focus_hidden`), `refreshUiState` (WM_QUERYUISTATE) and `noteKeyboardUse`
(WM_CHANGEUISTATE UIS_CLEAR from `handleKey`, because the app loop consumes the
panel's keys before DefWindowProc could notice keyboard navigation).
`ActivityMonitor.zig` sends UIS_INITIALIZE after showing the window and handles
WM_UPDATEUISTATE (DefWindowProc first, then re-read and repaint).
`activity_paint.zig` gates both focus rings — table caret and carousel card —
on `focusRingVisible`; the selection fill's emphasis still follows keyboard
focus alone, since only the rim is a keyboard cue. UI-state constants and
`uiStateWParam` live in `win32.zig`, with unit tests in `activity_input.zig`.
