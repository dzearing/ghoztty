# T1371 - After a rearrange with no surviving focus, focus lands on an arbitrary pane rather than the first one on screen

## Summary

Found while fixing T560. IpcHandlers' rearrange path keeps the focused pane if it survived the new layout, and otherwise falls back to 'the first leaf' - read from SplitTree.iterator(), which is the tree's storage order. That order is an artifact of how the splits were allocated, so the pane that ends up active after a rearrange is effectively arbitrary rather than the top-left one a person would point at. T560 added SplitTree.leafIterator() for exactly this meaning; this site (src/apprt/win32/IpcHandlers.zig, the 'Focus: keep the focused pane if it survived, else the first leaf' block) was left alone because it needs its own acceptance coverage. Sweep the remaining iterator() call sites at the same time and confirm none of the others mean screen order.

## In plain terms

When a script rearranges a window's panes and the pane you were typing in is
not part of the new layout, Ghoztty has to pick which pane gets the cursor.
Mac picks the top-left one. Windows got the same answer only by luck of how it
builds the new layout, so a later change could quietly make it pick some other
pane. Now it picks the top-left pane on purpose, and the same rule is used when
a closed tab waiting for undo loses its active pane.

## Goals

- [x] The rearrange focus fallback picks the first pane on screen (Mac `leftmostLeaf()`), not the first in storage order
- [x] One shared, unit-tested helper (`pane_stash.keepOrFirstVisible`) owns the rule
- [x] Remaining `iterator()` call sites swept for screen-order meaning

## Re-verification (2026-10-25)

The defect as filed does not reproduce today: `buildLayoutNode` writes the
layout preorder, left before right, and `insertAtTopLevel` (the stash carry)
only relocates the root SPLIT node to the end, so the non-stashed leaves come
out of `iterator()` in screen order. That held by accident, not by contract, so
the fix is to say "screen order" explicitly rather than rely on it.

Sweep of the other `iterator()` sites in `src/apprt/win32/`: every one visits
all panes (counting, ref/visibility/overlay passes, id lookup, session-id
collection) except `CloseUndo.zig`'s parked-tab path, where the closed pane was
the tab's active one and its replacement was the first leaf in storage order.
That one now uses the same helper, falling back to the top-left leaf if only
stashed panes remain so `active` never names a freed pane.
