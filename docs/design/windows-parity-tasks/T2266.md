# T2266 - No acceptance check proves a stacked row's grip gutter lights the accent bar on hover and while dragged (T2253 follow-up)

## Summary

T2253 lit stack-grip gutters (hover_grip / grip_drag) as well as split dividers, but its acceptance (split-divider.ps1, pane-elevation.ps1) only drives a divider. Add a grip case to a pane-stack harness (pane-stack-grid.ps1 or pane-stack-unfold.ps1): hover capture over a between-grip shows the half-strength bar, a grip drag shows the full bar on the grip nearest the pointer, and release leaves nothing lit. The debug line is 'gutter bar grip <hover|drag> rgb=r,g,b'.

## In plain terms

When panes are stacked side by side, the thin gap between two of them lights
up in the accent colour when you point at it, brighter while you drag it, and
goes dark when you let go. That already worked, but no automated test checked
it, so it could break without anyone noticing. Now a test does.

## Goals

- [x] an acceptance case hovers, drags and releases a grip between stacked cards
- [x] it can fail (negative control)

## Validation criteria

- [x] Hovering a grip between cards logs `gutter bar grip hover` with a non-black accent rgb - `test\win32\stack-collapse-drag.ps1` H1, green 32/32 (acceptance-parallel run, twice)
- [x] Dragging it logs `gutter bar grip drag` in the same rgb, and it is the last bar state while held - H2, same runs
- [x] Releasing leaves `gutter bar none` - H3, same runs
- [x] The case scores red without the hover - `-NegativeControl` fails H1/H2 (6 failures total)
- [x] Harness floor green over the edit (sleep-handshake-audit re-run green after the fixed sleeps became log polls)
- Not asserted: WHICH grip the drag bar sits on (the oracle names the gutter kind, not its index); a 60 DIP drag replaces no grip, so the nearest grip is the pressed one.
