# T1871 - session-reboot-tui: a TUI pane's stream sometimes never starts, so B3/B4 wait 361s at a bare prompt and the run goes red

## Summary

Seen 2026-10-11 during T1793 validation, run 8th in a sequential batch of acceptance scripts: B3/B4/B5/B8 and the dependent H1/H2/H4/H6/R1/R2 failed because tuiA/tuiB showed only the cmd banner and prompt after 361s - the command that types the stream never ran. Re-run alone minutes later: ALL PASS (58), streams rendered in 8.1s. Find why the stream launch can be lost (send-keys landing before the shell prompt? the --command not executing?) and make the harness wait for/verify the launch instead of timing out at the render wait. Run log copied to temp\t1793-reboot-tui-flake.txt.

## In plain terms

The test that checks "after a reboot, do panes that were running a full-screen app come back with their history" sometimes failed before it reached the reboot. Its two app panes sat at an empty command prompt for six minutes, so the run went red for a reason that had nothing to do with restore. Now the test can see whether each pane actually started its app. A pane that never ran its command fails immediately and says so. An app that died on startup is restarted once and the run notes it.

## Goals

- [x] the stream launch is observable (which half ran: the pane's --command wrapper, the player)
- [x] a pane that never ran its --command fails at once (B3a/B4a) instead of after a 361s render wait
- [x] a player that died before its first line (a box condition) is relaunched once from the pane's shell, with an info line naming the exit code

## Validation criteria

- [x] `-SimulatePlayerDeath` (tuiA's player exits 7 once before its first line) takes the relaunch branch and the run is ALL PASS 61: verified on the box, `session-reboot-tui.ps1 -SimulatePlayerDeath`
- [x] the normal run is ALL PASS 61 (B3a/B4a `started`): `acceptance-parallel.ps1 run -Scripts test\win32\session-reboot-tui.ps1 -FailFast`, 114s
- [x] harness floor (scoped) green after the edit

## Root cause (evidence)

The 2026-10-11 run log (`temp/t1793-reboot-tui-flake.txt`) shows both tuiA and tuiB holding only the `cmd` banner and a prompt in the run's work dir before the reboot. That is what the keep-alive `cmd /K "cmd /c playX.cmd"` prints when the inner command returns without output. The pane ran a shell, and nothing the player writes ever arrived. The harness had no way to tell "the app dropped --command" from "powershell died before its first line" (the shape a desktop-heap or DLL-init failure takes when it is 8th in a sequential batch). The control run reproduces exactly that bare-prompt shape with a player that exits before writing. It could not be reproduced natively. Next time, the launch markers will say which half it was.
