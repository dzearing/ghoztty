# T2839 - The installed release crashed in the NVIDIA OpenGL driver's own worker thread (nvoglv64 DrvPresentBuffers, access violation) and took every window down

## Summary

2026-11-08 13:54:20. The installed release crashed: C:\Users\David\AppData\Local\Programs\Ghoztty\ghoztty.exe, v26.11.8.437, pid 48348. Exception 0xc0000005 in nvoglv64.dll 32.0.16.1664 at offset 0xa71735. WER APPCRASH, report e3455717-0d7a-46d9-822b-cd1f33520a5b. Dump: %LOCALAPPDATA%\CrashDumps\ghoztty.exe.48348.dmp (67 MB). The faulting thread is entirely driver-owned: BaseThreadInitThunk -> nvoglv64 (DllMain, DrvSwapLayerBuffers, DrvValidateVersion) -> nvoglv64!DrvPresentBuffers+0x2f015, with no ghoztty frame on it. That is the shape of the driver's threaded-optimization worker presenting for a context or surface the app had already torn down or resized. Every window disappeared. The sessions survived in ghoztty-agent: both go-loop lanes' claude processes (25104, 12384) kept running, and the health checks then read windows=0 for both lanes. Investigate: (1) the other threads in the dump at the crash, especially whether a ghoztty thread was mid wglMakeCurrent / wglDeleteContext / DestroyWindow / resize; (2) whether NVIDIA threaded optimization (a per-app profile 'Threaded optimization = Off', or __GL_THREADED_OPTIMIZATIONS) avoids it; (3) whether the T48 freeze watchdog should also relaunch the app after a crash, so a GPU-driver fault costs seconds rather than every window until the user notices.

## In plain terms

On 2026-11-08 the installed Ghoztty crashed inside the graphics card's
driver, and every window vanished at once. The programs running in those
windows kept going in the background, but nothing brought the windows back
until somebody noticed. Now a shipping build asks Windows to reopen it after
a crash, and the reopened app picks up every session where it was. That is
the Windows version of the "Reopen" button a Mac shows after a crash.

## Findings (2026-11-09)

**Symbols.** The `ghoztty.pdb` beside the installed exe is a 2026-08-31
leftover and does not match (cdb: `sig MISMATCH`, exe GUID
1CA5AC82-E868-BE1D-4C4C-44205044422E, pdb 9383EE6C-...). The matching store
is the `win-v1.54.4` release's `Ghoztty-symbols-1.54.4-x64.zip` (the crashed
exe is 26.11.8.437 = win-v1.54.4, tagged from 1205154d9). `docs/claude/build.md`
now warns against the stale pdb.

**The threads at the crash** (dump `ghoztty.exe.48348.dmp`, 313 threads):

- Faulting thread #129 (`bcdc.5148`) is the driver's own worker: started by
  `BaseThreadInitThunk` straight into `nvoglv64`, no Ghoztty frame on the
  live part of its stack. Older slots on that stack show it had earlier
  delivered a message to our `glDebugMessageCallback` (OpenGL.zig:217), which
  only formats and logs.
- Renderer #102: drawing, `RenderPass.step` (VertexArray unbind), blocked on
  an SRW lock inside nvoglv64.
- Renderer #127: `checkDevice` -> `glGetGraphicsResetStatus`
  (OpenGL.zig:866), the lost-device poll, waiting inside nvoglv64.
- Renderer #185: `initTarget` -> `Renderbuffer.storage` (OpenGL.zig:1222),
  building a render target (a resize), waiting inside nvoglv64.
- Main thread #0: idle in `GetMessageW` (App.zig:2247). No thread was in
  `wglDeleteContext`, `wglMakeCurrent(null)`, `DestroyWindow` or a window
  resize.

**Verdict:** a fault inside the NVIDIA driver (32.0.16.1664) while three of
our render threads were making ordinary, concurrent GL calls on their own
contexts. No teardown race of ours is visible, so there is nothing in our
code to fix for the fault itself.

**Threaded optimisation (question 2): not pursued.** There is no
reproduction to test a change against, and turning it off means writing an
NVIDIA driver profile (machine-wide driver settings) on the user's PC, which
is not ours to change on a single unexplained crash. Revisit if a second
dump shows the same worker thread.

**Relaunch (question 3): done, by the Windows-native route.** The app
already registered with `RegisterApplicationRestart` for updates (T1204),
but with `RESTART_NO_CRASH`. `restart_manager.restartFlags(mode, sandboxed)`
now drops that flag for shipping builds. Windows Error Reporting then
relaunches the app (no arguments, so session restore re-attaches the agent's
sessions) after our own crash filter has written its report. Windows only
relaunches a process that ran 60+ seconds, which guards against a crash
loop. Debug builds, and any process with `GHOZTTY_PIPE_SUFFIX` or
`GHOZTTY_AGENT_INSTANCE` set (a test sandbox), keep `RESTART_NO_CRASH`, so a
test that crashes the app on purpose never gets a window back on the user's
desktop. The flags in effect: 10 for a shipping build, 11 for debug/sandbox.
`RESTART_NO_HANG` and `RESTART_NO_REBOOT` are unchanged.

**Parity:** macOS answers a crash with the system's "quit unexpectedly -
Reopen" prompt, so the Mac seat owes nothing new. T2862 adds the one-time
"closed unexpectedly and was reopened" note on Windows, which the Mac gets
from that prompt.
