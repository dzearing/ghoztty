# T1640 - The activity panel never says its process list was cut short

## Summary

Filed out of T1639. The process snapshot has always carried a `truncated` flag —
the agent's sampler returns it (`src/remote/agent/proc.zig`), the wire declares it
(`protocol.ProcSnapshot.truncated`), the connection decodes it
(`src/remote/connection.zig:2147`), and the win32 side stores it on the snapshot
(`src/apprt/win32/ActivityMonitor.zig:385`). Nothing ever renders it. Grep for
`truncated` in `src/apprt/win32/ActivityMonitor.zig` finds the field and no reader.

Before T1639 that mattered less because the flag was rarely set on a real box.
It is set routinely now: 512 rows is the default cap and this box is running 521
processes, so every snapshot it takes is a partial one. T1639 made the cut
meaningful (our own lineage first, then the busiest rows), which is exactly what
makes a "showing the top 512 of 640" line honest rather than alarming — the rows
that went are the ones nobody was looking for.

The macOS panel is the reference for what this should look like.

## In plain terms

The panel that lists what a machine is running shows at most a few hundred rows.
On a busy machine that is not everything, and right now the panel does not say
so — it looks like the complete list either way. It should tell you when it is
showing you the top slice rather than the whole table.

## Goals

- [x] the panel says, visibly but quietly, when the list it is showing was cut
      (already true since baf948c9a / T286: "⚠ List truncated" in the warn colour
      beside Show all, Mac's `Label("List truncated")`; tooltip since T1634)
- [x] it says how many rows are shown out of how many exist, if the count is available
      (not available: the wire carries only the flag, and Mac shows no count
      either, so matching Mac is the parity answer - no N-of-M line on either)
- [x] it says nothing at all when the table fit, rather than showing a permanent notice
      (section C of `test\win32\activity-truncated.ps1`)

## Validation criteria

- [x] an acceptance check drives the panel against a snapshot with `truncated`
      set and finds the notice; with it clear, finds no notice.
      `test\win32\activity-truncated.ps1` ALL PASS (14): the debug-only
      `GHOZTTY_TEST_ACTIVITY_ROW_CAP=20` seam makes the real sampler return a
      truncated table; the badge is found by hover with Mac's sentence, and the
      uncapped run (negative control) finds no badge on the same walk.
- [x] the notice reads correctly on a real box over the cap (this one, at 500+
      processes) and is not present on one under it. This box is at ~320 today,
      so "over the cap" is produced by the seam (the real sampler, a lower
      limit) rather than by the box; "under it" is the uncapped run.
- [ ] the win32 lane and `test\win32\activity-monitor.ps1` stay green.
