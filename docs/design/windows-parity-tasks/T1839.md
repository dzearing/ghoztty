# T1839 - Dragging a divider whose nested splits are collapsed by a stash can shift the visible nested dividers: split_resize.plan solves on full-tree geometry

## In plain terms

When you hide (stash) a pane and then drag one of the remaining dividers,
another divider you never touched could slide along with it, and the hidden
pane could come back a different size than it left. After this fix, only the
divider you drag moves, and a restored pane returns to its old slot.

## Goals

- [x] the divider solver understands a split that a stash collapsed
- [x] mouse drags and keyboard resizes both use the stash-aware view
- [x] an on-screen check proves the untouched divider holds and the stashed pane's slot is kept
- [x] a drag that ends on its grab pixel leaves every other divider where it was (found while validating)

## Summary

`split_resize.plan` keeps every OTHER boundary pinned while a divider is
dragged, by re-solving nested split ratios from the tree's geometry. Since
T1827 the window lays out splits with an all-stashed side COLLAPSED, but the
drag snapshot (`Window.snapshotNodes`) still describes the full tree, so the
solver can compute compensation for nested splits that are not on screen and
for regions that are larger on screen than it thinks. The likely symptom: with
a pane stashed inside the dragged split's subtree, the visible nested divider
drifts while you drag instead of holding still.

Fix direction: snapshot the visible arrangement (`pane_stash.visibleClone`),
solve on it, and lift the ratios back (`pane_stash.liftRatios`) - the same
shape equalize uses since T1827. Reproduce first on the test desktop with
`Invoke-TestDragResize`.

## Validation criteria

- [x] reproduce: nested divider drift during a drag with a stashed pane in the subtree - reproduced in pure form by the unit control `stash: the full-tree snapshot is the control` (the full-tree encoding drifts the on-screen divider >50px and re-plans the hidden split); the on-box acceptance additionally caught an 8px jump on the final tick of an out-and-back drag (see Details)
- [x] after the fix every visible boundary other than the dragged one holds within 1px through the drag - `test/win32/stash-divider-drag.ps1` claim B, 16 ticks, max 1px (flat; elevated also 1px); `-NegativeControl` fails as required
- [x] the collapsed split's own ratio is unchanged by the drag (restore lands in the old slot) - claim C, s1's share of the right region 0.498 before and after; unit tests assert no adjustment ever names the collapsed split or its stashed side

## Details (what landed)

- `split_resize.Node` gains `.pass: u16` - a split a stash collapsed, whose
  whole range belongs to its visible child. The walk, `dividerPos`, the
  keyboard gesture's fingerprint and `apply` all treat it as a pass-through
  that is never planned. `Window.snapshotNodes` emits it (via
  `pane_stash.splitShowing`), so the mouse drag AND the keyboard resize get
  the stash-aware solve with the node handles unchanged and no allocation -
  chosen over the `visibleClone` + `liftRatios` direction in the Summary,
  which would have needed a per-drag allocation and a handle map back.
- **Second defect found on the box:** the mouse drag applied `plan` to the
  LIVE tree each tick, and `plan` prunes subtrees whose range did not move.
  Dragging back to the exact grab pixel therefore re-pinned nothing and the
  nested divider kept the previous tick's ratio (8px jump measured). This was
  independent of the stash (any nested layout) and hidden by the existing
  reversibility unit test, which reset the tree to the snapshot every tick.
  New `split_resize.replay` = plan + snapshot ratio for every split the plan
  does not name (the mouse twin of `KeyboardGesture.restoreUnplanned`);
  `updateDividerDrag` uses it.
- New guard row `stash-divider-drag`; follow-up T1888 (suspected band/gap
  mismatch) was filed, measured on the box, and closed as not observable.
