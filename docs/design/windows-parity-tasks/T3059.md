# T3059 - PA-C02: the busy phase of perf-baseline.ps1 records none of the GHOZTTY_PERF reader/renderer counters, so the 70% busy CPU cannot be attributed (perf-baseline.ps1)

## Summary

PA-C02 (audit-1, T2964). scripts/perf-baseline.ps1 has zero GHOZTTY_PERF references, though the counters exist: src/termio/Exec.zig:1548-1633 (reads_per_s, batches_per_s), src/termio/stream_handler.zig:138-166 (queue_render_per_s), src/renderer/Thread.zig:629-656 (wakeups, fps). baseline-1 busy reads ~2 MB/s at 66-72% of a core with ~28.5k context switches/s, and the auditors could only infer that the reader's per-batch syscalls and wakeups explain the switches. Fix: run the busy phase under GHOZTTY_PERF=1, parse the log into busy.perf {reads_per_s, batches_per_s, bytes_per_batch, queue_render_per_s, renderer_wakeups_per_s, fps}, and record per-thread CPU and context switches by thread role (extends PA-W05/its task). Risk: trivial, tooling. PA-C03 and PA-C04 quote these metrics. Findings: docs/design/perf-audit/audit-1/C-findings.md.

## In plain terms

The performance baseline shows the app using about 70% of a CPU core while a
pane prints a lot of text, but it could not say what that CPU was spent on.
Now the baseline turns on the app's built-in counters during that test and
records them: how often the pane reads output, how much each read carries, how
often it asks for a redraw, and which threads use the CPU.
