# T3061 - PA-C04: every output batch posts an IOCP wakeup to the renderer even when one is already pending, from inside the terminal lock and before the parse (queueRender / xev Async on IOCP)

## Summary

PA-C04 (audit-1, T2964). libxev (hash 86vtc4..) src/backend/iocp.zig:850-861 `async_notify` calls PostQueuedCompletionStatus unconditionally, after src/watcher/async.zig:597-606 takes a guard mutex; the loop discards the stale packets (iocp.zig:343-346). Callers: src/termio/stream_handler.zig:171-174 `queueRender`, invoked at src/termio/Termio.zig:1190-1192 inside the terminal mutex and BEFORE the parse ('we can call this first because we have the lock'), and src/termio/Remote.zig:2180-2182 per agent frame. The renderer builds at most a frame per wake, so nearly every post under flood is redundant, and an idle renderer woken before the parse blocks on the mutex the reader still holds (one extra block/wake per isolated chunk). Cost (computed from 19-29k batches/s): the same number of redundant syscalls + dequeued packets per second and longer lock holds. Fix: an app-side atomic `render_pending` flag: queueRender skips notify while it is set; the renderer's wakeup callback clears it BEFORE draining (a lost wakeup is a frozen pane, T40). Move the notify after the parse/unlock. Do not fork libxev. Risk: medium. The flag is shared code; the syscall saving is Windows-specific. Findings: docs/design/perf-audit/audit-1/C-findings.md.

## In plain terms

When a program prints a lot of output quickly, the terminal used to send the
screen-drawing thread a "wake up and redraw" signal for every small piece of
output - tens of thousands a second - even though the screen can only be
redrawn about a hundred times a second. Now it sends one signal and skips the
rest until the drawing thread has woken up, so heavy output costs less CPU and
nothing on screen changes.

## Goals

- [x] output-driven render requests are coalesced behind one atomic flag (src/renderer/wake_coalesce.zig)
- [x] the request is posted after the parse and after the terminal lock is released
- [x] the busy-phase perf numbers confirm fewer wakeups at unchanged fps
- [x] no frozen pane in the repaint-sensitive harnesses
