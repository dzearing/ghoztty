# T2162 - ghoztty +new-window --target=X with no app running opens TWO windows: the named one plus an unnamed default window-1

## Summary

Seen 2026-10-22 during T1160 on +95c284ad8 (release build, fresh sandboxed LOCALAPPDATA, test desktop): after '+new-window --target=rep --shell=cmd' auto-launched the app, +list showed window 'rep' AND a second window 'window-1' with one idle pane - in every run (soak 20261022-103620 and two repros). A user scripting a layout from cold gets a stray extra window. Check what the Mac auto-launch does (does open -na + the queued new_window leave an initial window behind too?) and match it; if Mac yields one window, Windows should suppress the startup default window when the launch was made to serve a +new-window. Also: soak.ps1 telemetry reports that window's pane as 'other'.

## In plain terms

Running a script like `ghoztty +new-window --target=build` when Ghoztty was not open
started the app and then gave you two windows: the one you asked for and an empty
extra one you had to close by hand. Now you get just the one you asked for, the
same as on Mac.

## Goals

- [x] A cold `+new-window` auto-launch leaves exactly one window, the requested one
- [x] `initial-window = false` works on Windows (Mac and Linux already honored it)
- [x] An app started with `initial-window = false` that nobody asks for a window still opens one after a short wait, so it is never running invisibly

## Findings

- Mac: `+new-window` with no app running no longer auto-launches at all (since
  372a8c606 it prints "No running Ghoztty instance found. Launch Ghoztty first."),
  while `docs/claude/cli.md` and the README still promise auto-launch. Where Mac
  does start with a request pending (`hasPendingIpc`), it skips the first window.
  So the one-window result is the parity target; the doc-vs-Mac drift is filed
  as a mac-seat task.
- Windows fix: the auto-launch passes `--initial-window=false`; `run()` honors the
  key through `startup_window.zig` (pure, tested in both lanes). `false` defers the
  blank window by 5s instead of dropping it, because a Windows app with no window
  is the invisible start T1177 refuses; config diagnostics wait for that moment too.

## Validation criteria

- [x] One window after a cold auto-launch - `auto-launch-cwd.ps1` B1/B2 (waits past the grace period, then counts), green via `acceptance-parallel.ps1 run -Scripts auto-launch-cwd.ps1`
- [x] The launched instance carries `--initial-window=false` and the requested directory - B3-B5
- [x] `--initial-window=false` with no request: no window inside the grace period, one after it - section E (E1-E3)
- [x] The pure rule - `startup_window.zig` unit tests, both zig lanes (floor-lane.ps1 -Lane all)
