# T1235 - The narrow-pane strip probe scores a red run about once in three

## In plain terms

Nothing a user of the terminal would ever see. This is one of our own test
scripts crying wolf: it measures the viewer's toolbar by photographing it at
five widths, and every so often one of those five photographs is taken a
fraction too early and comes back showing more buttons than the width could
hold. The run then reports a defect that is not there — and because that
particular script is one of the ones allowed to block a commit, a wolf cry
costs whoever is working at the time a whole detour.

## Summary

`test\win32\viewer-narrow-pane.ps1` section E narrows a viewer pane through
five ratios and asserts the strip only ever SHEDS controls (`E: narrowing
never ADDS ink to the strip`). Observed 2026-09-01 during T1184's floor: two
consecutive runs failed that one assertion, and a third — same build, same
box, nothing changed in between — passed with a clean monotone series:

```
ratio 55 -> bar 351px, edit 176px, inked slot boxes 8
ratio 72 -> bar 217px, edit 122px, inked slot boxes 5
ratio 80 -> bar 155px, edit 100px, inked slot boxes 3
ratio 86 -> bar 108px, edit   0px, inked slot boxes 1
ratio 92 -> bar  77px, edit   0px, inked slot boxes 1
```

So the LAYOUT is right (the same arithmetic is asserted exhaustively without a
window in `viewer_nav_layout.zig`) and the MEASUREMENT is racy: `Measure-NavBar`
captures after a `Set-HtmlRatio`, and a capture that lands before the strip has
repainted at its new width photographs the previous band's controls. The
neighbouring probes in the same script settle first or capture synchronously;
this one does not.

Not T1184's doing — that change touched no strip geometry and no paint. It
surfaced there only because `ViewerNavBar.zig` is in this guard's coverage row,
so an unrelated edit to that file made the harness due and it was re-run.

## Goals

- [x] Section E scores a band only once the bar has stopped changing.
- [x] The negative control proves the slot count still sees a width change.

## Re-verification (2026-10-23)

Since this was filed, T2157 rewrote section E: it now narrows a window whose
single pane is the viewer (700 → 90 DIP) instead of walking split ratios, so
the five ratios named below no longer exist. The old form could not be re-run.
Three runs of the current form before the fix were all green, so the race no
longer reproduces on demand. The criterion it rests on still holds: a fixed
1200 ms sleep, then one capture.

Reading `ViewerNavBar.zig` also changed the diagnosis. The capture is
`WM_PRINTCLIENT` (synchronous), and `place()` / the paint derive the strip
from the bar's current width. A capture that lands "too early" therefore
photographs the strip for the width the bar has now, not the previous band.
The one input that can ADD a control between two bands is state the pane
pushes asynchronously after the page opens (`shown()`: contents, feedback,
diff, reveal). Both readings have the same fix: score a band only when
consecutive captures agree.
