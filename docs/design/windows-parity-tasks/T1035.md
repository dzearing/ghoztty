# T1035 - Nothing proves a resizing pane actually waits for its new frame - the synchronous-present path has no oracle

## Summary

T1031 put the divider drag, the window-edge drag and the banner toggle on the same synchronous-present path and wired the frame signal that path waits on, but its acceptance can only assert the erase decision and the clip styles - 'the pane blocked up to 16ms for a frame at its new size' is a schedule, not a pixel, and resize-flicker.ps1 says so in its own header. So the wiring could be removed again and every test would stay green. Wanted: an oracle with teeth. The likely shape is the GHOZTTY_PERF telemetry already in renderer/OpenGL.zig - have the resize path log the wait outcome (frame arrived vs timed out) in debug builds and assert the arrived case over a scripted drag, the way the erase decision is asserted now.

## In plain terms

When you drag a divider or resize the window, each pane is supposed to hold
still for a moment until it has redrawn at its new size, so you never see the
old picture stretched into the new space. Since T1031 that works, but no test
could tell whether the pane was being told its new picture was ready or just
waiting a fixed 16 ms and hoping. Someone could break that again and every
test would still pass. Now a test checks that the "ready" message really does
end the wait. A deliberately broken build fails it.

## What the measurement found

- The gap was real, and wider than the filing said. Since T1476 the harness
  asserts `waits > 0` and `stale = 0`. A wait whose `SetEvent` is gone still
  passes both: the 16 ms clock ends it, its last look finds the new-size frame
  the renderer drew in the meantime, and nothing is stale.
- On the hidden test desktop the frame signal never decided anything. Presents
  are not vsync-throttled there, so each pane's new-size frame was already on
  screen before the layout pass closed its batch. 11 of 11 drag waits and 9 of
  9 window passes ended `woken=0 timeouts=0`. A "frame arrived vs timed out"
  oracle reads exactly the same on a build with the signal unwired. So the
  oracle needed two parts: a count of waits that were actually *woken*, and a
  way to put the wait into the state the user's desktop is in.
- Under an 8 ms lag the drag wakes 9-10 of its 11 waits and the window passes
  3-4 of 8, with 0 timeouts. A 4 ms lag was not enough for the drag: its
  debug-build layout pass spends ~13 ms painting divider bands before the batch
  closes.

## What landed

- `drag_perf.WaitOutcome { timed_out, woken }`. The batched wait
  (`Window.endFrameWaitBatch`) and the serial one (`Surface.waitForAwaitedFrame`)
  both report it, and `woken` is counted on its own (unit test in
  `drag_perf.zig`). It is not `waits - timeouts`, because "already presented"
  is neither of the two.
- `woken=` on the `divider drag ...` summary (after `stale=`, so existing
  parsers keep working; drag-perf.ps1's full-line regex takes it as optional)
  and at the end of the `window resize cause=...` line.
- `GHOZTTY_PRESENT_LAG_MS`, a measurement knob read once per Surface beside
  `frame_event` and clamped to `drag_perf.present_lag_max_ms` (8, half the
  wait budget). It holds `signalFrameDrawn` back, the way a throttled
  compositor holds `SwapBuffers`. It is a Surface field rather than read
  through `parent_window`, because it runs on the renderer thread and an adopt
  can move `parent_window`.
- `test\win32\resize-flicker.ps1` sets the lag to 8 and asserts `woken > 0` in
  section E (the drag) and section D (summed over the whole-window passes).
  Both assertions are inverted under `-NegativeControl`.

- [x] The resize path states how each frame wait ended (woken / timed out / already there)
- [x] An acceptance assertion that fails on a build with the frame signal removed
- [x] The test desktop reproduces the blocking wait the user's desktop has

- [x] Teeth. With `SetEvent` in `signalFrameDrawn` replaced by a no-op and
      rebuilt, resize-flicker.ps1 reads drag `timeouts=9 stale=0 woken=0` and
      `0 woken over 8 waiting pass(es)`: 2 FAILURES. Restored and rebuilt:
      ALL PASS (26 assertions), twice. `-NegativeControl` on the restored
      build: 5 FAILURES.
- [x] `acceptance-parallel.ps1 run -Scripts resize-flicker.ps1`: PASS (26).
- [x] `floor-lane.ps1 -Lane all`: lib/none/win32/agent ALL LANES PASS.
      Includes the new `drag_perf` stats assertion.
- [x] drag-perf.ps1 still parses every summary row with `woken=` present.
      It is red for the one known T1854 reason (one 2-pane sample reused at 4
      and 8 panes), not for this change.
- [x] `acceptance-parallel.ps1 due` (30 scripts): 26 PASS. drag-perf (T1854)
      and hook-json (T2001) are red for already-tracked reasons. seam-audit C3
      flagged the new knob as an unregistered seam; it is registered in
      `seam-audit.registry.json` (non-default / shipped-elsewhere), and the
      re-run is ALL PASS (27). harness-floor's only non-PENDING red was that
      same seam-audit row, re-run with `-Include`.

      mechanism with no AppKit counterpart (same finding as T1031).
