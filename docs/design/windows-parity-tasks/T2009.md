# T2009 - +validate-config --config-file=<a 2-line file> fails with 'CLI action failed error=error.FileTooBig' instead of reporting the bad keys

## Summary

Found in the T1998 turn: a release ghoztty.com run as '+validate-config --config-file=bad.conf' where bad.conf is 'font-size = banana' + 'not-a-key = 1' (31 bytes) exits 1 and logs 'error: CLI action failed error=error.FileTooBig' - the user never sees which lines are wrong. Check whether --config-file is read with a zero/garbage max size on Windows, compare with the Mac CLI, and fix on both if it is shared. Note test\win32\log-append.ps1 section T uses this call as its source of a CLI error line (it asserts only that SOME warning/error lands), so keep a deterministic failing CLI call available there after the fix.

## In plain terms

When a script or another program captured the output of `ghoztty +validate-config`, the command printed its findings and then failed anyway. A perfectly good config was reported as broken (exit code 1), and the log blamed a "file too big". Run from a terminal it looked fine, which is why it went unnoticed. Now the command gives the same answer however its output is collected.

## Goals

- [x] Find where FileTooBig comes from: it is the stream-finishing call, not the config reader
- [x] A piped `+validate-config` answers 0 for a good config and names the bad lines for a bad one
- [x] The other verb with the same call (`+explain-config`, its usage and unknown-flag errors) is fixed by the same helper
- [x] A test that would have caught it, proven to fail on the old code

## Root cause

`std.fs.File.Writer.end()` (zig 0.15.2) flushes and then TRUNCATES the stream at its position (`setEndPos`), forgiving only `error.NonResizable`. On POSIX a pipe fails ftruncate with EINVAL, which maps to NonResizable. On Windows a pipe passes the writer's positional probe, and `SetFileInformationByHandle` then fails with INVALID_PARAMETER, which std maps to `error.FileTooBig`. `validate_config.run` ended with `try stdout_writer.end()`, so that error replaced the verb's result. It made no difference with a file redirect (truncatable) or a console. In the user's own log, every piped `+validate-config` today carried the line. The T1998 report's 31-byte file was a coincidence: the size never mattered.

Mac: nothing owed. The helper is shared code and builds for both. On macOS `end()` was already harmless on a pipe (NonResizable), and the flush-only finish is identical there.

## Validation criteria

- [x] Unit: `src/cli/stdio.zig` - `finish` on a pipe delivers the text and does not fail, and leaves a regular file whole. - [x] log-append section T still has a deterministic failing CLI call - `log-append.ps1` ALL PASS (36) on a fixed ReleaseFast `zig-out-release`; T2-T5 read 1 warning/error line by default and 1 with the opt-in. That harness captures through a FILE, so it never met FileTooBig: its warning line was always the config loader's, and the fix does not move it.
