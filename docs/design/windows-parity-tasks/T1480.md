# T1480 - A drag tick that misses the frame budget is still called smooth

## In plain terms

When a pane cannot draw its new size fast enough, the drag shows the previous
picture for a frame — a small blink. The drag's own self-assessment does not
count that as a problem: it looks only at how long each tick took, so a drag
that blinked twice still reports itself as smooth. If this starts happening
often on a slower machine, nothing in the app will say so.

## Goals

- [x] A drag that left panes showing the previous size says so in its verdict
- [x] The threshold is stated, not implied, so the line means one thing

## Summary

Follow-up to T1476, which added `stale=N` to the `divider drag ...` summary:
panes whose frame wait ran out the one-frame budget with the renderer's last
present still at the pre-resize size. Each one is a displayed frame of the old
picture in the new window — exactly the defect T1476 was filed for, arriving by
the one route the fix deliberately leaves open, because holding the UI thread
longer would trade a blink for jank.

`drag_perf.Stats.verdict()` decides `smooth` / `steppy` from tick TIMING alone,
so a drag with `stale=2` still reports `verdict=smooth` and `reportDragCost`
logs at `debug` rather than `info`. On this box the fixed shape measured
`stale=0` over six 41-tick drags, so there is nothing to see today; the point is
that if a slower machine or a heavier pane starts missing the budget, the app's
own verdict will call it clean.

Not just a log-level change: decide what rate of stale presents is worth
reporting (one in a 40-tick drag is a blink the user may not notice; five is the
original complaint), and say so where the verdict is defined rather than at the
call site.

## Details

Re-verified 2026-11-12 against HEAD: `Stats.verdict()` still judged on
`meanUs()` alone, so the defect was real (the six commits since filing touched
the drag path, not the verdict).

Fix: `verdict()` gains a fourth answer, `stale`, owned by `drag_perf.zig`.
A drag tolerates one stale present per `stale_ticks_per_tolerated` (20)
ticks, never fewer than `stale_tolerated_min` (1) - so a 40-tick drag reads
`smooth` at two stale presents and `stale` at three, and the original T1476
complaint (five) reads `stale`. Timing still wins when both are true (`steppy`
is the larger defect; `stale=` on the line carries the rest). The log level is
not the lever any more: since T2609 `reportDragCost` always logs at `info`
behind `GHOZTTY_PERF`, so the verdict word is the whole signal.
