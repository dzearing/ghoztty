# T1686 - The installed terminal vanished mid-session with nothing in the event log

## Summary

P1: the user's installed Ghoztty (release, %LOCALAPPDATA%\Programs\Ghoztty) disappeared between 10:05 and 10:40 on 2026-09-20 while a go-loop turn was running in one of its panes. The agents survived and kept the sessions, so nothing was lost, but every window was gone and the loop could not type its own reset. Windows recorded no Application Error for it.

## In plain terms

Every Ghoztty window on the box closed itself. Nothing was asked, nothing was
reported, and Windows has no record of a crash — the app was simply not there
any more. The sessions themselves survived (the background agents kept them),
so reopening the app gets the work back, but from where the user sits the
terminal disappeared out from under them.

## What is known

- Observed 2026-09-20. The app answered `+list` normally at 09:55 and was
  gone by 10:40; `Get-Process ghoztty` returns nothing while four
  `ghoztty-agent.exe` are still up holding the sessions.
- The build that vanished was the installed release
  (`1.36.12+82b87b0d2`, ReleaseFast), not a repo build.
- The acceptance runs going on at the time cannot be the cause:
  `Stop-RepoGhoztty` is path-exact and refuses any exe outside the repo
  (`test\win32\lib\CleanSlate.ps1`), and the only processes it stopped were
  `zig-out` ones.
- No Application Error record in the Windows event log for it, which is the
  same silence T1685 records for a Debug build dying mid-run — the two may be
  the same defect seen from different builds.

## Where to look

- Whatever ends the process writes nothing first. That is the first thing to
  fix whether or not the cause is found: a terminal that can disappear needs
  to leave a reason behind (`docs/claude/build.md` for WER LocalDumps, and
  `scripts\crash-catch.ps1`).
- The T48 watchdog covers a FROZEN app; nothing covers one that exits.
- Cross-reference T1685.

## Validation criteria

- [ ] The exit is reproduced, or the search is recorded as exhausted with what
      was ruled out
- [ ] An app that exits for any reason other than the user closing it writes a
      reason somewhere durable first, and that is asserted by a test
- [ ] If the cause is found, it is named from a stack or a dump, not inferred
- [ ] The relationship to T1685 is settled either way - same defect or not
