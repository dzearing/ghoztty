# T1686 - The installed terminal vanished mid-session with nothing in the event log

## Summary

P1: the user's installed Ghoztty (release, %LOCALAPPDATA%\Programs\Ghoztty) disappeared between 10:05 and 10:40 on 2026-09-20 while a go-loop turn was running in one of its panes. The agents survived and kept the sessions, so nothing was lost, but every window was gone and the loop could not type its own reset. Windows recorded no Application Error for it.

## In plain terms

Every Ghoztty window on the box closed itself. Nothing was asked, nothing was
reported, and Windows has no record of a crash — the app was simply not there
any more. The sessions themselves survived (the background agents kept them),
so reopening the app gets the work back, but from where the user sits the
terminal disappeared out from under them.

## What is known

- Observed 2026-09-20. The app answered `+list` normally at 09:55 and was
  gone by 10:40; `Get-Process ghoztty` returns nothing while four
  `ghoztty-agent.exe` are still up holding the sessions.
- The build that vanished was the installed release
  (`1.36.12+82b87b0d2`, ReleaseFast), not a repo build.
- The acceptance runs going on at the time cannot be the cause:
  `Stop-RepoGhoztty` is path-exact and refuses any exe outside the repo
  (`test\win32\lib\CleanSlate.ps1`), and the only processes it stopped were
  `zig-out` ones.
- No Application Error record in the Windows event log for it, which is the
  same silence T1685 records for a Debug build dying mid-run — the two may be
  the same defect seen from different builds.

## Where to look

- Whatever ends the process writes nothing first. That is the first thing to
  fix whether or not the cause is found: a terminal that can disappear needs
  to leave a reason behind (`docs/claude/build.md` for WER LocalDumps, and
  `scripts\crash-catch.ps1`).
- The T48 watchdog covers a FROZEN app; nothing covers one that exits.
- Cross-reference T1685.

## Resolution

**Cause.** Windows Update replaced the NVIDIA display driver (32.0.15.9186)
under the running app. The System event log shows `nvlddmkm` / NVIDIA Display
Container LS disabled at 10:29:49-56 local (17:29:49-56Z); the app's last log
lines, at 17:29:51.725Z, are the only three `Software processing fallback in
framebuffer pipeline` warnings in its whole 2.8 MB log, and an IPC `+read` at
17:34:27Z got no answer. The agents survived because they touch no GPU. No
dump exists (nothing was configured to write one and the process did not raise
a catchable exception), so the cause is named from those two time-aligned
logs, not from a stack. Surviving the driver swap is T1690.

**The ledger.** `%LOCALAPPDATA%\ghoztty\exit-log[-debug].txt`, one ASCII line
per event, append-only and shared by every process
(`src/apprt/win32/exit_reason.zig`; the pure line format, parse, dangling-run
audit and trim are `src/os/exit_ledger.zig` with unit tests in the `none`
lane). Every GUI launch writes `start`; every deliberate ending writes `exit
reason=` (`user-quit`, `startup-failed`, `forwarded` / `forward-failed` for a
second launch that hands off to the running app, `handoff-cancelled`,
`session-end` at logoff/shutdown, `restart-manager` when an installer closes
it); an unhandled exception writes `crash code= addr=` and is then passed on
untouched to WER/LocalDumps. The one case nothing inside a dying process can
witness - killed from outside, or taken down with a driver as here - is
written by the NEXT launch as `unrecorded-exit prev_pid= prev_start=`, and a
run that is still alive (a second instance) is never accused.

**T1685 is a different event:** its run was ~09:5x local, half an hour before
any driver activity.

Follow-ups: T1690 (survive the driver swap, P1), T1691 (a test that exercises
the crash line), T1692 (the macOS ledger, seat: mac).
