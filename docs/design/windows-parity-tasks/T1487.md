# T1487 - A block is only recorded when the watchdog acts, so the screen learns about it up to an hour late

## Summary

The blocked state the dashboard bar (T1484) reads is written by Add-Ineffective, which only runs when the watchdog takes a recovery action - so the first observation lands after the stall arms fire (45m) plus the rearm hold-off. The classifier is cheap and the watchdog already runs every 5 minutes; stamping the verdict on the observing tick rather than on the action would cut the time between a block starting and the screen saying so from tens of minutes to one poll. Clearing has the same shape: an unblocked tick should clear the record rather than waiting for a turn to complete.

## In plain terms

When the loop gets stuck on something outside the box (a spend limit, an
expired sign-in), the dashboard is supposed to say so. It only learned about it
when the supervisor tried to restart the loop, which happens 45 minutes or more
after the block began, and it kept saying "blocked" after the block lifted. Now
the supervisor writes down what it sees every five minutes, so the screen is at
most one check behind in both directions.

## Goals

- [x] Every watchdog tick that sees a blocker records it, not only a recovery action
- [x] A tick that sees no blocker clears a standing record without waiting for a turn to complete
- [x] Observing never inflates the "re-entries that changed nothing" count
- [x] "Blocked since" survives repeat observations of the same blocker
