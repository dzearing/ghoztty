# T3076 - T3058 live check: with NumLock ON, a WM_MOUSEMOVE sweep over an idle pane shows renderer fps and CPU at the NumLock-off level (needs a session with NumLock on)

## Summary

T3058 fixed `Surface.modsChanged` / the key path comparing raw mods (with
caps/num lock and sides) against stored `binding()` mods, which forced a
full-viewport rebuild on every mouse move and keystroke while NumLock or
CapsLock was on. The comparison is pinned by a none-lane unit test, but the
live measurement could not run on 2026-11-14: the box's NumLock was OFF, the
win32 surface reads it with GetKeyState (real keyboard toggle state only), and
the loop may not change the user's keyboard state on the input desktop.

Build a small harness (pattern: `test\win32\title-churn-redraw.ps1`,
GHOZTTY_PERF=1 `perf pane=... fps=N`): post a WM_MOUSEMOVE sweep (~100/s for
5 s) over an idle pane on the test desktop and read the pane's fps. It should
SKIP (not pass) when `[Console]::NumberLock` is false, since the defect cannot
trigger then.

## Validation criteria

- [ ] with NumLock ON, the idle pane presents at most ~2 fps during the sweep (pre-fix: one frame per move)
- [ ] the harness SKIPs with NumLock off, naming why
