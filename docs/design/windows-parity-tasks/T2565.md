# T2565 - A sidebar edge drag never flickers the sidebar card or a tucking pane strip (Mac bfb31b7ac)

## Summary

Mac bfb31b7ac fixed two one-frame races during a sidebar edge drag, exposed by the heavier All-windows list: (1) the sidebar card took a new width mid-glide before the grid had moved, so its edge sat a drag step past the grid for a frame - now held until the stage origin moves or followWait; (2) a gliding strip's clip stayed at the target layout while its frame was offset, cutting the strip short at its far end for a frame - the clip now moves with the frame. Windows: verify with a sidebar edge drag (filmed, frame by frame) whether pane_sidebar_transition.zig's card glide and pane_stack_slide.zig's strip glide show either artifact; fix the one(s) that do and add a frame-level test. Mac reference: docs/reference/pane-sidebar.md card-glide paragraph, docs/reference/stacked-panes.md strip clip.

## In plain terms

On the Mac, dragging the sidebar's edge while it was still sliding open could
make the sidebar's edge or a folded pane's tab flicker for one frame. This
checked whether Windows does the same. It doesn't, because of how it is built,
and two tests now keep it that way.

## Goals

- [x] Find out whether the Windows sidebar card can run ahead of the grid on an edge-drag step mid-glide
- [x] Find out whether a gliding strip's shown part is cut at its target instead of where it is drawn
- [x] Pin each invariant with a unit test so a later change cannot bring the Mac race in

## Findings

Neither race has a Windows counterpart. These are structural reasons; no frames were filmed (see below).

1. **Card vs grid.** On Mac the stage view takes a new size a beat before its
   frame moves, so a width taken at once was measured against a stale origin.
   On Windows there is no separate stage: one synchronous pass handles an edge
   step (`Window.setPaneSidebarWidth` -> `layoutSplitsLive`). That pass
   retargets the glide (`planStackSlide` -> `Slide.retarget`) and then places
   the sidebar (`syncPaneSidebar` -> `PaneSidebar.place`, which sets
   `column.to_w`). So `followWidth(from, to_new, leadingLag())` is read against
   the retargeted slide, where the lag is `drawn.left - to_new.left`, and the
   card's edge stays exactly a gutter short of the grid as drawn.
2. **Strip clip.** `Window.tuckedStrips` cuts a strip's shown part
   (`visiblePart`) from `shownStripTab`, which is the rect as the glide draws
   it. The desk's exclusion (`ExcludeClipRect` on the same `shownStripTab`)
   uses that rect too. Nothing keeps a clip at the target layout.
