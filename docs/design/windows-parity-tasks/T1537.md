# T1537 - A dragged pane can be dropped on the tab strip to become its own tab

## Summary

Split out of T1532, which bundled four separate drops. This is the SAME-WINDOW
half: in rearrange mode, dragging a pane onto the tab strip previews and then
commits a new tab holding that pane, at the index under the pointer, and
resting the pointer on an existing tab button for 500ms switches to that tab so
the drag can continue into its layout.

The pure resolver already answers both questions — `pane_drop.resolve` returns
`.new_tab{ window, index }` for a point on the strip, and `pane_drop.hoveredTab`
is the dwell result for the timer — and neither has a caller. What is missing is
the Window.zig integration: feeding `tab_bar_rect` / `tab_button_rects` into the
candidate (`stripRegions()` already publishes both in client coordinates), a
preview for the new-tab drop, the commit, and the dwell timer.

No cross-window relocation is involved: every pane in a window's tabs is already
a child of the same HWND, so a new-tab drop is a pure tree edit (remove from the
source tab's tree, seed a new tab's tree with the same `*PaneView`) plus a
refcount that never reaches zero. That is why this half can land before T1538's
`SetParent` machinery.

## In plain terms

Right now rearrange mode lets you move a pane around inside the layout you are
looking at, but there is no way to send it to a tab of its own — you have to
open a new tab and start the work over. After this, dragging a pane up onto the
tab bar makes it its own tab where you dropped it, and hovering over a tab for a
moment opens that tab so you can keep dragging into it.

## The preview and the refusal are the same answer

A pane that is its tab's only pane is ALREADY a tab of its own, so a new-tab
drop has nothing to do and `remove(.root)` would empty the tab out from under
it. That refusal (`canNewTabDrop`) is read in one place and handed to two: it
decides whether the commit happens and whether the caret is drawn. A caret over
a release that does nothing is exactly the lying preview T1531's geometry rule
exists to prevent, and the two could only disagree if each derived the answer
for itself.

## The pane crosses tabs without its shell noticing

Every pane in every tab of a window is already a child of the same HWND, so
none of this re-parents anything - it is tree editing, and the only thing that
has to be right is the reference count. `commitNewTabDrop` builds the
single-leaf tree FIRST, taking a second reference, and only then releases the
source tree's old value, so the count never touches zero. A cross-tab drop
goes through T1529's `moveTo` / `swapWith`, which hand back both trees for the
same reason.

The sharp edge is the tab a dragged pane can EMPTY. `closeTabByIndex` is the
wrong tool there: it marks every session in the tree it closes as ENDING, and
the pane that emptied the tab is still running in the tab next door. So the
slot bookkeeping is split out as `removeTabSlot` and the close path keeps its
intent to itself.

      strip, a strip with no tabs, DPI scaling that never rounds to zero, a tab

      on the strip previews a caret and opens a tab holding the dragged pane; the
      tab lands at the INDEX under the pointer rather than appended; a tab's only
      pane previews nothing and opens nothing; and a 500ms dwell on another tab's
      button switches to it mid-drag so the drop lands in that tab.
      `test\win32\rearrange-tab-drop.ps1`.

      new tab is the same child HWND that was dragged, and after the cross-tab
      drop both panes are the same two windows - a drop that rebuilt the pane
      would leave the tab count right and the user's shell dead.
- [x] The caret is asserted as a real window (`GhozttyDropHighlight`) inside the
      strip band the product itself publishes through `+list --json` (T231),
      never a rect re-derived in PowerShell.
