# T2942 - At 4K the slowest fold-glide frames still spend 11-13 ms placing the moved panes, so a 120 Hz display misses them (60 Hz now fits after T2941)

## Summary

After T2941 the fold tick no longer composes the desk whole, and at 4K no glide tick exceeds 16.7 ms on a release build (max 14.3-15.7 ms, 4 runs). The top ticks are now placement: place_us 11.2-13.4 ms of 12.3-14.3 ms cost (paint 0.6-1.1 ms), on the fold ticks (resizes=1-2). That is the EndDeferWindowPos of the moved panes T2941's title named (up to 8.7 ms in the T2732 re-measure) plus the vacated/desk work around it; no task owns it. Lever: split the tick's place_us with the existing batch/defer_end/cut/filled QPC stamps on the release sandbox and find what the batch waits on. Evidence runs: %TEMP%\ghoztty-drag-glide\20261112-220543-42500 and 20261112-220909-18440 (stderr.log, ring trace).

## In plain terms

On a big 4K window, dragging a divider far enough that panes fold into strips
still stalls for one frame now and then. The slowest frames are the ones that
repaint a wide folding card, and a large slice of that frame is the app asking
Windows to re-cut the card's rounded shape every frame. This change bakes the
shape into the card's own picture instead, so the slowest frames get lighter
and the occasional hitch has room to disappear.

## Goals

- [x] The folding card's face no longer asks Windows to re-cut its window shape on every frame
