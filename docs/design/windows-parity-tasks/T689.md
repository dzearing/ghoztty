# T689 - Acceptance launches that capture no stderr leave a dead GUI undiagnosable

## In plain terms

When the app under test dies during a Windows test, some of those tests throw
away everything it said on the way out. Whoever picks the failure up has a red
line and no explanation, and usually has to re-run the whole thing with a
change just to find out what happened. Capturing the output costs one argument
per launch.

## Summary

`Start-OnTestDesktop -StdErr <path>` and `Start-Process
-RedirectStandardError <path>` both exist and most of the suite uses them, but
a number of scripts launch with neither. `pane-banner.ps1` was the case that
made this concrete (T158's parent note): when its instance disappeared mid-run
there was no log to diagnose from, and the Windows event log had no crash
record either — a debug build writes `std.log` to stderr and nothing else, so
an unredirected launch discards the whole story.

The launch inventory now exists: `lib\PersistenceSweep.ps1`'s
`Get-GhozttyLaunchSites` enumerates every launch of the app under test in
`test/win32` (148 sites as of T158), so the same enumeration answers "which of
these capture stderr" without a fresh grep design.

## Details

Extend the sweep row with a `CapturesStderr` field (`-StdErr` for the test
desktop, `-RedirectStandardError` for `Start-Process`), then give the launches
that lack it a per-run named log. Two rules worth keeping from the scripts that
already do it right: name the file after the script and the section so a
multi-launch script does not overwrite its own evidence, and keep the artifacts
when the script fails (the `if ($script:fail -eq 0) { Remove-Item ... }`
pattern) so a red run leaves something to read.

An arm in `test\win32\persistence-flag.ps1` (or a sibling) can then assert the
inventory stays at zero uncaptured launches, the same way section A asserts
zero undeclared ones.

## Goals

- [x] The sweep answers, per launch site, whether the app's stderr is kept.
- [x] The default is the HELPER's, not each caller's — a launch that names no
      log still gets one.
- [x] The remaining `Start-Process` sites say it themselves, or say why not.
- [x] A static arm fails when a new launch is added without capture.

## Validation criteria

- [x] The sweep reports, per launch site, whether stderr is captured.
      `Get-GhozttyLaunchSites` rows carry `CapturesStderr` / `StderrHow`
      (`literal` / `var:$x` / `callers:<helper>` / `marker` / `helper`);
      section B of `test\win32\stderr-launch-capture.ps1` proves each form.
- [x] Every launch of the app under test in `test/win32` captures stderr, or
      carries a marker saying why it cannot. Section A: **0 uncaptured of 287**
      (was 163 of 301), `literal=152, helper=124, marker=11`.
- [x] A static arm fails when a new launch is added without capture (teeth
      checked against a synthetic fixture, as T158's section B does).
      `stderr-launch-capture.ps1 -TeethCheck` injects an uncaptured
      `Start-Process` into the swept directory and requires section A to find
      exactly it — T1, green.
- [x] The scripts edited to add capture still ALL PASS on the box. See the
      progress log for the per-harness verdicts; `guard-due.ps1 check` drove the
      list, so the set that ran is the set the edits touched rather than a
      sample chosen by hand.
