# T1365 - A Repair tells every open window a newer build is installed when nothing changed

## In plain terms

If you run the installer for the version you already have and choose Repair,
every Ghoztty window you have open starts saying a newer build is installed and
offering to restart. Nothing newer was installed. Restarting gets you the same
build you were already running, and the offer comes back the next time somebody
repairs.

## Goals

- [x] A Repair or same-version reinstall no longer makes open windows offer a restart
- [x] A real upgrade still does, balloon and About both
- [x] The decision is unit-tested and the acceptance scripts prove both paths

## Summary

`image_freshness.isStale` (T1205) compares two runtime facts: when this process
started, and when the file it was launched from was last written. That is the
right comparison for an upgrade - a version string cannot tell two builds of the
same version apart - but it answers "the file changed" rather than "the build
changed", and a Repair rewrites the same bytes with a fresh mtime.

So after a repair:

- the tray balloon fires on every open window,
- About turns into a "Restart Now" offer,

and both are false. T1352's installer-side offer deliberately does not fire on
this path (its condition is `NOT Installed AND OLDERVERSIONFOUND`, the true
upgrade only), which is why this is visible as a difference: the installer says
nothing and the app nags anyway.

## Where

- `src/apprt/win32/image_freshness.zig` - the comparison.
- `src/apprt/win32/provenance.zig` - where the two timestamps are collected.
- `src/apprt/win32/App.zig`, `Surface.zig` - the balloon and the About offer.

## Likely shape

Keep the mtime test as the cheap trigger, and confirm it before speaking: read
the build stamp out of the on-disk exe and compare it against this process's
own. Equal stamps mean the file was rewritten with the same build, which is not
news. That is strictly more information than the mtime alone and does not
reintroduce the version-string weakness the module's header rejects, because a
build stamp is per-build rather than per-release.

## Validation criteria

- [x] A repair or same-version reinstall leaves open windows saying nothing.
      `test\win32\stale-build-notify.ps1` S1b (same bytes, fresh mtime: no
      tick says true, no notice) and S3b (a repair of an already-announced
      newer build is not announced twice); `ipc-version.ps1` 2b's new
      "a repair ... is not called a newer build" assertion. Both ALL PASS.
- [x] A genuine upgrade still raises the balloon and the About offer (the T1205
      behaviour is unchanged). Same scripts, S2/S4/S5/S6 and 2b, now against a
      copy whose PE link stamp was bumped - a different build, not only a
      newer mtime. `-NegativeControl` scores S2-S6 red (12 failures).
- [x] The comparison is unit-tested in the `none` lane, the way the rest of
      `image_freshness.zig` is: `linkStamp` parsing (valid / truncated / no MZ
      / no PE / zero) and `isNewerBuild` (repair quiet, upgrade loud, unknown
      stamp falls back to mtime, older file never news).

## Resolution

The mtime stays the cheap trigger; when it fires, `provenance.collect` reads
the on-disk exe's PE link stamp (`IMAGE_FILE_HEADER.TimeDateStamp`) and
compares it with the one in this process's own mapped header page
(`GetModuleHandleW(null)`), via `image_freshness.isNewerBuild`. Equal stamps =
the build we are running, rewritten = silent. The stamp is per link (link time
in Debug, an output hash in the CI release builds - checked on the box:
installed `0x1679f469`, staging `0xc26de48d`), so this does not bring back the
per-release weakness of a version string; an unreadable or zero stamp falls
back to the T1205 mtime verdict. The tray-balloon dedupe also keys on the
stamp, so a repair of an already-announced newer build does not re-announce it.

The two acceptance scripts used to fake an upgrade by re-stamping identical
bytes - which is precisely the repair case - so they now bump the copy's link
stamp to make a real second build.
