# T2350 - Windows pane sidebar: a '<project>: <name>' window's own Panes list sits under its group's header (count, pencil, + and x; folding it folds the group in every list), as Mac 32bc9a6b5

## Summary

Split from T2340 (the one piece of it that is a new structure rather than
metrics). Mac 32bc9a6b5: in the single "this window" list, a window titled
`<project>: <name>` shows its group's project header above its own window
header (labeled `<name>`): the whole group's window count, and on hover the
pencil (rename the group), + (new window in the group) and x (close every
window in the group). Folding that header folds the group in every list
(the shared `folded_projects` set), and while folded the window header and
its panes go away.

Where: `pane_sidebar.addThisWindowHead` (lay a project head above the window
head when the title splits), `PaneSidebar.zig` single-roster gather (~line 760:
compute the project's window count across every top-level window's tabs, and
the project key/label as the outline gather does ~line 1132), `paintHead` /
the head hit handlers (they already act on a `.project` head through
`g.project_key`). Mac ref: docs/reference/pane-sidebar.md "A window's own
Panes list" bullet.

## In plain terms

On a Mac, a window whose name is "project: worktree" shows the project's
heading above its own pane list, with the same buttons the project heading
has in the all-windows view. Windows shows only the window heading there.

## Goals

- [ ] The project head sits above this window's head in its own list
- [ ] Its count, pencil, + and x act on the whole group
- [ ] Folding it folds the group everywhere and hides the window head and panes

## Validation criteria

- [ ] Unit test: addThisWindowHead lays a project head above the window head for a grouped title, nothing for an ungrouped one, and only the project head when the group is folded
- [ ] On-box: test/win32 sidebar acceptance reads the heads via the debug oracle
