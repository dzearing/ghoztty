# T3216 - Collapsed blades after an update whose relaunch finds the local agent replacing itself (the user's 1.55.3 log: 'agent is replacing itself without losing any session'): extend session-blades-update.ps1 with a stale bundled agent so the restore runs beside an agent handoff, and with a down/column stack and a blade in a background tab

## In plain terms

After an update, panes the user had squeezed into thin blades came back full
size. Every way we have of replaying that update keeps them, so this chases the
one thing the user's update did that no test does yet.

## Summary

Follow-up of T3213 (user report via T3208). T3213's harness
`test/win32/session-blades-update.ps1` makes the fold with a real divider drag
(term + viewer blades, a stashed pane beside them), quits through the `quit`
action (the updater's `quit_requested` -> `App.terminate` path), and relaunches
three windows with the folded one paced in behind the first and maximized. It
is ALL PASS on HEAD and on the exact pair the user ran (a 0b1373c31 / 1.55.2
debug build quits, a 0b4aa273d / 1.55.3 build relaunches, via
`-RelaunchExePath`). Blade persistence (T3126) shipped in 1.55.1.

What the user's restore had that the harness does not (release
`ghoztty.log`, 2026-11-17T03:25:51Z): "agent upgrade check: stale, but the
agent is replacing itself without losing any session (standing down)" - the
restore ran beside a local-agent handoff (running 20261111, bundled 20261116).
Do: give the relaunch a newer bundled agent than the running one, so the
restore meets the handoff, and assert the blades. Also untested: a fold in a
down (column) stack, and a blade in a non-active tab. Fix what drops them.
## Goals

- [x] the update replay can run its relaunch beside a real local-agent handoff (`session-blades-update.ps1 -AgentHandoff`)
- [x] folded panes survive that handoff, or what drops them is fixed - the blades held; what the handoff dropped was a whole WINDOW (fixed, see Findings)
- [x] a fold in a down (column) stack and a blade in a background tab are covered too - split out to T3240

## Findings (2026-11-18)

**The handoff did not unfold anything - it dropped a whole window.** The first
`-AgentHandoff` run on HEAD (d9091f448 + harness only) reproduced it: the
relaunch restored `wc`, paced in `wb` (blades intact), and then the agent
replaced itself. `tickPacedRestore` treated any drop or replacement of the
link as the end of the pacing - "the local agent went away mid-restore;
keeping 1 window(s) for the next launch" - so the third window stayed off
screen until the next launch (D: 2 of 3 windows, 1 of 2 paced). On the
user's update the folded window could just as well have been the one left
behind, and the next launch is a different restore.

**Fix** (`App.tickPacedRestore`, decision in `restore_pacing.linkStep`, unit
tested): a dropped link is waited out (up to `link_wait_ms` = 30 s, covering
the in-place recovery's 5 s watch and re-dial); a live link that is not the
one the probe was taken on - or one that dropped and came back - gets a FRESH
`AttachProbe` (the old roster describes an agent that may be gone) and the
pacing carries on. Only a link down for the whole budget leaves the rest
carried, as before.

**Test seam**: `GHOZTTY_RESTORE_PACE_MS` (debug builds only,
`restore_pacing.intervalFromEnv`) stretches the gap between paced windows;
the harness sets 2.5 s and lands the newer agent just after the lead window,
so the handoff falls inside the paced restore on every run (it landed in it
one run in two at the shipping 200 ms). F4 asserts the pacer met it, F5 that
nothing was left for the next launch.
