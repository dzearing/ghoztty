# T3216 - Collapsed blades after an update whose relaunch finds the local agent replacing itself (the user's 1.55.3 log: 'agent is replacing itself without losing any session'): extend session-blades-update.ps1 with a stale bundled agent so the restore runs beside an agent handoff, and with a down/column stack and a blade in a background tab

## In plain terms

After an update, panes the user had squeezed into thin blades came back full
size. Every way we have of replaying that update keeps them, so this chases the
one thing the user's update did that no test does yet.

## Summary

Follow-up of T3213 (user report via T3208). T3213's harness
`test/win32/session-blades-update.ps1` makes the fold with a real divider drag
(term + viewer blades, a stashed pane beside them), quits through the `quit`
action (the updater's `quit_requested` -> `App.terminate` path), and relaunches
three windows with the folded one paced in behind the first and maximized. It
is ALL PASS on HEAD and on the exact pair the user ran (a 0b1373c31 / 1.55.2
debug build quits, a 0b4aa273d / 1.55.3 build relaunches, via
`-RelaunchExePath`). Blade persistence (T3126) shipped in 1.55.1.

What the user's restore had that the harness does not (release
`ghoztty.log`, 2026-11-17T03:25:51Z): "agent upgrade check: stale, but the
agent is replacing itself without losing any session (standing down)" - the
restore ran beside a local-agent handoff (running 20261111, bundled 20261116).
Do: give the relaunch a newer bundled agent than the running one, so the
restore meets the handoff, and assert the blades. Also untested: a fold in a
down (column) stack, and a blade in a non-active tab. Fix what drops them.
