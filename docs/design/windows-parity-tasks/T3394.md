# T3394 - update-real-msi and update-graceful run a real msiexec under a release sandbox with no check that it cannot reach the user's installed product

## Summary

These two harnesses drive the updater on purpose with their own GHOZTTY_UPDATE_URL feed, which T3388 lets win over the GHOZTTY_AUTO_UPDATE=off sandbox switch, so the T3388 gate does not cover them. Their MSIs carry the product's real UpgradeCode, so a real msiexec can reconfigure or major-upgrade the user's installed Ghoztty exactly as the 2026-11-22 incident did. Add a pre-flight to both that snapshots the user's real product (MsiGetProductInfo version + install location, and the hash of the installed ghoztty.exe/ghoztty-agent.exe) and a post-check that it is byte-identical, failing loudly otherwise; and decide whether the fixture MSI should be built with a test-only UpgradeCode so it cannot touch the real product at all.

**Re-verified at claim (2026-11-22):** the "real UpgradeCode" premise was
wrong for both - they already install a throwaway identity
(`scripts\msi-test-identity.ps1`, a test-only UpgradeCode, so the "decide on a
test-only UpgradeCode" half was settled long ago). What was real: (1) the
identity asserts in section A only SCORED; nothing stopped msiexec running if
the rewrite had not taken, and the package the applier installs is a download
the app staged, never checked at all; (2) "the user's install untouched" was a
file count plus ghoztty.exe's mtime, which reads the 2026-11-22 damage (agent
renamed aside, nothing rewritten, count unchanged) as clean; (3) that check ran
inside the try, so a run that threw half-way, and the cleanup's own
`msiexec /x`, were never measured.

## In plain terms

Two tests install a real copy of Ghoztty under a made-up name to check that
updates work. If that disguise ever failed, nothing stopped them from
installing over the user's real Ghoztty, and their "we didn't touch your
install" check would not have noticed the kind of damage seen this morning.
Now they refuse to install anything that could reach the real product, and
they prove afterwards - file by file - that the user's install is unchanged.

## Goals

- [x] a pre-flight that refuses msiexec on any package able to act on the shipping product (UpgradeCode, Upgrade-table row, installed ProductCode, ProductName), checked on the published pair AND on the staged download
- [x] a before/after snapshot of the user's install: registered product + version + cached package, every file, SHA-256 of the three live images
- [x] the installer's own record: any MsiInstaller event naming the shipping product during the run fails it
- [x] the comparison runs in the finally, after the cleanup uninstall, on every path
- [x] the library is proven against states it must catch (its own harness, with a negative control)
- [x] follow-up filed for the four other real-msiexec harnesses + an audit (T3405)
