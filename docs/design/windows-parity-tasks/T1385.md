# T1385 - +list's human output does not mark a read-only pane

## Summary

T574 put readonly on the JSON wire, but the human-readable +list output still shows a read-only pane exactly like any other - no marker beside the pane, the way viewers get a 'view:' prefix. Somebody reading +list in a terminal to work out why their keystrokes vanish gets no hint. Add a marker to the human formatter (src/cli/list.zig) on both platforms, sourced from the same field, and cover it in the CLI's own tests.

## In plain terms

When you turn on read-only for a pane, everything you type into it is ignored. Running `ghoztty +list` to find out why gave no hint: the read-only pane looked like every other pane. Now it is tagged `[read-only]` in that listing, on Windows and Mac alike.

## Goals

- [x] Plain `+list` tags a read-only pane `[read-only]`
- [x] Nothing is tagged when the mode is off
- [x] Covered by unit tests and by the live read-only harness

## Validation criteria

- [x] A read-only pane's line carries `[read-only]`, before the focus star - unit test `formatTerminal: a read-only pane is tagged [read-only] (T1385)` (none lane, filtered run; negative control went red on the right test) and live: `readonly-badge.ps1` B, which read `... running  [read-only] *` from the real app after the toggle chord.
- [x] No tag when the field is absent or false - unit test `no [read-only] tag when the field is absent or false`; live `readonly-badge.ps1` A and H (0 tagged lines before the toggle and after toggling off).
- [x] Composes with the other tags in a fixed order - unit test `[read-only] composes with the other tags` (exact string).
- [x] Both platforms - the formatter is the shared Zig CLI (`src/cli/list.zig`) and both servers already emit `readonly: true` (win32 `IpcHandlers.zig`, Mac `IPCServer.swift`, T574), so no Mac-side change is owed.
