# T3005 - PA-M05: perf-baseline.ps1 takes its leak delta at cycle 2, inside the known GPU driver upload-pool fill, and cannot split heap from driver memory, so the 29 MB/cycle and the 390 MB first-cycle residue stay unattributed (perf-baseline.ps1:535)

## Summary

PA-M05 (audit-1, T2961). scripts/perf-baseline.ps1:483 runs two cycles and :535 takes second_cycle_private_mb = cycle2.closed - cycle1.closed. T2782's census showed window-close-memory climbs ~12-18 MB over its first cycles (+12 MB PAGE_WRITECOMBINE = GPU driver upload pool, ~6 MB non-heap RW, NT heaps flat) and is then flat; baseline-1's gpu_shared_mb at close rises 14-22 MB cycle1->2 in all four runs. No close path leaks Zig memory (all three M auditors). Fix: adaptive warm-up like window-close-memory.ps1 -MaxWarmup (:250) and a slope over >= 5 settled cycles; the -HeapCensus region split at start / cycle-1 closed / last closed; an A/B with GHOZTTY_COMP_PRESENT=0 to size PA-R02's share of the first-cycle residue; and, if quit returns through main, a Debug GPA leak report after N cycles (src/global.zig:183-187). Distinct from PA-W05 (T2989, per-thread switches + per-type handle/USER diffs). Risk none. Baseline: docs/design/perf-audit/baseline-1.json (T2958); findings: docs/design/perf-audit/audit-1/M-findings.md.
