# T2108 - Stacked panes: the win32 grid places panes through the engine - panes stop at 300 DIP, tucked panes show only their strip, and the divider paint, hit test and drag read the engine's dividers

## Summary

Second slice of T2101. Window.layoutNode/placeStashedNode, paintMovedBands, hitTestDivider and the divider drag go through pane_stack_grid (T2107) instead of splitRects; tucked panes are clipped/hidden to their tab; the stack state notes stacks after each layout. Acceptance on the test desktop: 4 panes in a window narrower than 4x300 DIP keep N on show and the rest tucked (enumerated pane rects).

## In plain terms

Until now a row of split panes on Windows simply divided the space by the
split ratios, so four panes in a normal window could squeeze a terminal down
to a sliver nobody can read. Now a pane never gets narrower than about 35
columns (300 DIP): a row that cannot fit shows as many panes as fit and tucks
the rest behind them, and widening the window brings back exactly the layout
the user had. The tucked panes' title strips are painted next (T2109).

## Goals

- [x] Every geometry walk in the window (placing panes, sizing stashed panes,
      the desk's cards, divider paint, hover, drag and band repaint, the
      rearrange headers) reads one layout, the stacked-panes engine
- [x] No pane is laid out under 300 DIP while the row fits at that minimum
- [x] A row that cannot fit shows a run of panes; the rest are tucked -
      hidden but kept at their slot's size, so bringing one forward is a move
- [x] Shrinking and re-growing the window returns the user's layout
- [x] Nothing changes for a flat-style user whose panes fit: the gutter stays
      today's 2 DIP band until T2084 takes Mac's 6 pt gutter on purpose
