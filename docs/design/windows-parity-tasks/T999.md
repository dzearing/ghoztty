# T999 - Nothing checks the build cache for tearing after an unclean shutdown

## Summary

Both torn-cache incidents (2026-08-05, 2026-08-18) followed a hard reboot: NTFS gives back files whose tail is zeros or missing, and the damage is only discovered when a lane goes red minutes later. The loop already detects a boot outage at claim time (go-loop-boot.ps1). Have that same path sweep the cache for the shapes Test-CacheFileIntact knows (empty / NUL-filled / not newline terminated) across .zig-cache/c and the global cache, and delete what it finds, so the first build after a reboot starts from a cache that has been looked at rather than one that is trusted.

## In plain terms

A crash or power cut can leave a half-written file in the compiler's cache,
and until now nobody looked: the next build failed minutes later with an error
that read as broken code. Now the loop's start-of-turn cache check reads the
compiler's generated files, deletes any that are empty, full of zero bytes or
cut short, and says so, so the first build after a reboot starts clean.

## Goals

- [x] one scan that recognises the torn shapes (empty / NUL bytes / no trailing newline) in the generated-source bucket of both caches
- [x] the start-of-turn cache sweep deletes what it finds and names it; the read-only check only reports
- [x] a file young enough to be a concurrent build mid-write is never judged
- [x] no false positives on the real cache, and cheap enough to run every turn

## Design note

Scoped to every claim rather than to "a reboot was detected": the scan costs
~150ms over the live `c\` bucket (193 files), so tying it to the boot ledger
would only add a way to miss a tear (an unclean shutdown that the boot record
reads as clean, or a crashed zig process with no reboot at all). The race with
another window's build is closed by age instead: a file written in the last two
minutes is skipped, and a tear left by a shutdown always predates the boot.
Only the `c` bucket is scanned - both observed tears were an options.zig there,
every file in it is newline-terminated text, and `o\` holds binaries where NUL
bytes are normal. Fetched packages keep their own report-only alarm (T1436).

## Validation criteria

- [x] the scan names exactly the torn fixtures (empty, 2036 NULs, cut short) and not a whole one - G1-G3 of `test\win32\build-cache.ps1`
- [x] a torn-looking file written just now is left alone, and judged once past the window - G4/G5
- [x] `build-cache.ps1 check` reports without deleting; `sweep` (what the claim runs) deletes only the torn entries, loudly, and a second sweep is quiet - G6-G13
- [x] the live repo cache reads clean (no false positives) - G14, plus a live `build-cache.ps1 sweep` printing only `build cache ok`
- [x] wiring: the sweeper runs the scan and the claim runs the sweeper in sweep mode - G15/G16
- [x] harness ALL PASS (92), `-NegativeControl` goes red on G12 (and C5); floor-lane-cache-heal ALL PASS (85) over the Test-CacheFileIntact refactor
