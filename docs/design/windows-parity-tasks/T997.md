# T997 - Saving scrollback rewrites the whole buffer every time, so a noisy pane writes about twice what it prints

## Summary

T969 made ring snapshots fire on VOLUME as well as on the 30-second timer, which is what gives a busy pane the same crash-recovery guarantee a quiet one has. The cost it inherits is that a snapshot rewrites the WHOLE ring: with the trigger due every half-capacity, a pane that prints N bytes causes about 2N bytes of disk write, and the amplification is set by the ring size rather than by the delta. An append/delta snapshot format (or a two-file scheme where only the tail is rewritten) would make the write proportional to what actually arrived. Nothing is broken - this is the bounded cost of the fix, written down so the next person does not re-derive it.

## In plain terms

Ghoztty keeps a copy of each terminal's recent output on disk so it can bring the scrollback back after a crash or reboot. Until now, every time it saved, it rewrote the whole copy - up to 2 MB per pane (more with a larger scrollback setting) - even when only one new line had appeared. Now each save adds just the new output to the end, and the full copy is rewritten only occasionally, so disk writes track what the terminal actually printed.

## Goals

- [x] a save writes only the output that arrived since the last one
- [x] the full copy is rewritten only once the additions reach about one scrollback's worth (writes stay at most 2x the output, disk use at most two scrollbacks per pane)
- [x] crash recovery still returns everything saved, and a half-written save loses only itself
- [x] an older agent (rollback) still reads the saved scrollback, just without the newest additions

## Design notes

- The `.ring` base keeps its GRS2 layout untouched, so a rolled-back agent still loads it; the journal is a separate `<id>.ringlog` whose header binds it to one exact base (end offset + CRC-32 of the base bytes). A journal next to some other base is ignored rather than spliced on.
- Records carry their stream offset, length, capture geometry and a CRC-32; the writer appends at the length it tracked (`pwrite` + truncate + fsync), so a torn tail from a failed write is overwritten by the next good record instead of stranding it.
- The writer only appends when this process wrote the pair (`Session.snap_disk_end`); after an agent restart, a preload renumbers the ring, so the first pass rewrites the base. Whole passes are serialized by `snapshot_mutex` (reaper, viewer disconnect and shutdown handlers can overlap).
- Before: every pass rewrote the whole ring, so a quiet pane printing one prompt per 30 s rewrote 2 MB for it, and a busy one under the T969 volume trigger wrote ring/threshold = 4x its output at the defaults (32x at a 16 MB ring). After: at most ~2x in steady state.
- Test harnesses read the pair through `test/win32/lib/RingSnapshot.ps1`, which mirrors the loader.
