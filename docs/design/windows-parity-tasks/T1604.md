# T1604 - -AppOnly delivers a new app beside whatever agent a location already had, and never says so

## Summary

scripts\deliver-windows-build.ps1 skips resolving the staged agent stamp entirely under -AppOnly, so the per-location agent read-back (T281) is dead there. The run withholds the portable ZIP for exactly this reason ('AppOnly ships no agent', D12b) - but it leaves the LOCATION in the state it refuses to publish: a new app paired with an agent of unknown age, silently. Proposal: read the staged stamp under -AppOnly too and REPORT a location whose agent does not match it (a warning rather than a failure, since not shipping the agent is the point), with an arm in section H of test\win32\deliver-windows-build.ps1.

## In plain terms

A partial refresh that updates only the terminal app (not its background
session helper) used to leave each install folder with a new app beside an
old helper, and said nothing about it. Now the delivery checks the helper
it left behind and says so on its final line when that helper is from
another build or is missing.

## Goals

- [x] -AppOnly reads the staged agent's stamp (never copies it)
- [x] each location's kept agent is compared against it; a mismatch, an unreadable agent or a missing one is a WARN
- [x] warnings ride onto the DELIVER OK verdict line, and never turn it into a failure

## Validation criteria

- [x] a location holding the staged agent is cleared with no warning - D12e/D12f and H25 of `test\win32\deliver-windows-build.ps1` (ALL PASS, 143 assertions, `acceptance-parallel.ps1 run`, run with `GHOZTTY_LOOP_LANE=a` because lane b's delivery refusal otherwise reds the sandbox sections - filed as T3297)
- [x] a location with no agent still delivers, and the verdict line names it - D12g/D12h
- [x] a location keeping another build's agent (a real debug-tree agent with a different stamp) delivers, the stale bytes stay, and the verdict line names both stamps with `1 warning(s)` - H21-H24 (section H ran, not SKIPped)
