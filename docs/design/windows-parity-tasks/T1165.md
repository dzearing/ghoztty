# T1165 - -NoGuardDue is a blanket hatch: a guard red for a FILED defect should be acked to that task, not waved past

## In plain terms

When one of the automated checks is failing for a reason someone has already
written down and put in the queue, the only way to get a commit through is a
switch that turns off *all* of the checks at once. So a second check that goes
bad on the same day slips out unnoticed. There should be a way to say "this one
check is red, and here is the task that owns it" and leave the rest armed.

## Goals

- [x] One red guard can be handed to the open task that owns it, leaving every other guard armed
- [x] The hand-off expires by itself when that task closes
- [x] The loop's reports tell "red and owned" apart from "nobody ran it"

## Summary

`parity-tasks.ps1 validate` fails when `guard-due.ps1` reports any acceptance
harness that has not been run green against the code as it now stands (T783).
The only way past is `-NoGuardDue`, which disables the check for **every** row
in the table. That is the right hatch for its stated case - "a harness that
genuinely cannot run on this box" - and the wrong one for the case that keeps
occurring: the harness runs fine and is genuinely RED, for a defect already
filed and queued.

Measured, three turns running: 2026-08-23's T1110, T1133 and T1158 commits each
used `-NoGuardDue` naming `fork-identity` (now fixed, T1134) and/or `suite-run`
(T1164, open). Each of those commits also silenced the other ~90 rows for the
duration. That is exactly the failure mode T783 exists to prevent, arriving
through the escape hatch instead of through the gate.

The precedent for the fix already exists in this repo: `ack-stranded <Tid>`
(T847) parks a stranded-work finding against an open task, and the ack holds
only while that task is open. A `guard-ack <guard> <Tid>` would do the same job
for a red harness - it names the guard, names the task that owns the red, and
evaporates the moment that task closes, so the guard cannot stay acked past its
own fix.

## Where

- `scripts/guard-due.ps1` - the check, and where an ack file would be read
- `scripts/parity-tasks.ps1` - `validate`'s guard-due gate and the
  `-NoGuardDue` hatch; `ack-stranded` is the shape to copy
- `scripts/go-loop-exec.ps1` - the claim's guard report, which should show an
  acked guard as acked rather than as plain DUE
- `test/win32/guard-due.ps1`, `test/win32/gate-negatives.ps1` - acceptance

## The work

- `guard-ack <guard> -Task <Tid>` records the ack; it is refused if the task
  does not exist or is already closed.
- `validate` accepts a DUE guard that is acked to an OPEN task, and fails on
  one that is acked to a closed or missing task (the ack must not outlive its
  reason).
- The claim report and `guard-due.ps1 check` print `GUARD ACKED <name> (T1164)`
  rather than `GUARD DUE`, so a watching human can see the difference between
  "nobody ran it" and "it is red and owned".
- `-NoGuardDue` stays, for the case it was written for, and should say in its
  own output that an ack is the narrower tool.
- Per T1133, the new refusals ship with their demonstration: an ack to a closed
  task, and an ack to an id that does not exist, both proved red in
  `test\win32\gate-negatives.ps1`.

## Validation criteria

- [x] `guard-ack` lets `validate` pass with the acked guard still red, while an
      unrelated guard going DUE in the same tree still fails it. Shipped shape
      is `parity-tasks.ps1 guard-ack <Tid> -Guard <name>` (task first, like
      `ack-stranded <Tid>`), backed by `guard-due.ps1 ack -Guard <name> -Task
      <Tid>`. Verified: guard-due.ps1 R3 (check level) and R14/R15 (real
      `validate` against the fixture).
- [x] Closing the acked task makes `validate` fail again on that guard, with a
      message naming the closed task (`ACK EXPIRED: ... acked to T9101, which
      is done`). Verified: R5/R6 (closed, missing) and R16 through `validate`.
- [x] `guard-ack` refuses an unknown id and an already-closed task. The
      demonstrations are in section R of `test\win32\guard-due.ps1` (R7, R8,
      R17); `ACK REFUSED` and `ACK EXPIRED` are registered as gates in
      `test\win32\gate-negatives.ps1`'s registry pointing at them, which is
      how that harness holds every delegated gate (same as `GUARD DUE`).
- [x] The claim report distinguishes ACKED from DUE: claim relays `check`
      verbatim, which prints `GUARD ACKED (T<id>) <name>` plus an `owned by`
      line (R2). `validate` also prints those lines on a pass (R14).
- [x] `test\win32\guard-due.ps1` is ALL PASS (146 assertions, via
      acceptance-parallel).
