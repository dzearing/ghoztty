# T2356 - Check for Updates does nothing

## Summary

User report 2026-10-27 (~17:25 local), on win-v1.48.1 (0ef9c932a, installed
app pid 2880): "i click check for updates. nothing happens." / "no feedback,
hnothing."

`%LOCALAPPDATA%\ghoztty\ghoztty.log` for pid 2880 has ONLY the hourly
`update check (automatic): up to date` lines. A manual check always logs
`update check (manual): ...` (`App.zig` updateCheckThread, ~10433/10446) and
then posts feedback (`postUpdateFeedback`, which T1565 routes to a dialog
rather than the tray balloon). Neither happened, so the click is lost BEFORE
`App.startUpdateCheck(.manual)`.

Path: menu bar `Check for &Updates…` (`menu_bar.zig:259`) / palette row
(`commands.zig:370`) -> `Surface.performCommand` (`Surface.zig:3436`) ->
`.binding` -> `core_surface.performBindingAction(.check_for_updates)` ->
core `App.zig:514` -> `rt_app.performAction(.app, .check_for_updates)` ->
win32 `App.zig:9614`.

Silent drop candidates, in order of suspicion (unverified):

1. `performCommand` starts with `if (!self.core_surface_ready) return;` - no
   log. If the menu's WM_COMMAND is routed to a surface that is not ready (or
   to none: focus in the pane sidebar, a viewer pane, the stash tray), the
   app-scoped action dies there. An app-scoped action should not need a
   terminal surface at all.
2. The WM_COMMAND for the menu bar item is not mapped to `performCommand`
   for this id (check the Window.zig menu handler).

Not yet known: whether the user used the menu bar, the window menu, or the
palette - test all three.

## In plain terms

Picking "Check for Updates…" from the window's menu did nothing at all when
the pane you last clicked was a document/web viewer rather than a terminal -
no check, no message. Now the menu works the same whichever kind of pane has
focus, and the check always answers in a dialog ("up to date", "an update is
available", or "could not check").

## Root cause

`Window.openMenuBarAt` dispatched every menu pick through
`getActiveSurface() orelse return`. `getActiveSurface` is null when the
focused pane is a viewer, so EVERY menu command was dropped silently from a
viewer-focused window - the user's loop window has the task dashboard viewer
beside its terminal. The palette was never affected (T394 hosts it on a
terminal), which is why the scripted manual checks in `update-check.ps1`
(timer-driven, no menu) stayed green over it.

## Fix

`Window.performMenuCommand`: a ready focused terminal performs the command as
before; otherwise a binding command takes the keyboard's T1803 route
(`viewer_accel.menuRoute`: app actions through the core with no terminal
needed, native viewer actions on the focused viewer, window actions through a
host terminal, pane/terminal actions refused rather than sent to another
pane), the app-local kinds run through any terminal in the window (and the
update/help kinds with none at all), and whatever is left logs `menu command
dropped id=<cmd>` instead of vanishing. `Surface.performCommand` logs its own
not-ready drop.

## Goals

- [x] every route to Check for Updates reaches `startUpdateCheck(.manual)`,

- [x] the user always sees an answer via the T1565 dialog - the menu route
