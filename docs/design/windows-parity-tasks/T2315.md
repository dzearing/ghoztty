# T2315 - A background acceptance run started before /reset-context keeps running into the next turn and kills that turn's test apps (two false 0xFFFFFFFF crashes in T2267)

## Summary

Turn 96 (T2267) saw pane-sidebar-scroll die twice mid-setup with exit 0xFFFFFFFF and no WER record; the cause was the previous turn's 'Re-run due harnesses on the merged tree' (acceptance-parallel, run_in_background) still running after the reset and clean-slating repo-built ghoztty by path. Nothing at claim time reports in-flight acceptance runs. Fix shape: go-loop-exec claim (or acceptance-parallel itself) detects a live acceptance run from this tree and either waits or reports it, and the reset path refuses/warns while one is in flight.

## In plain terms

A batch of tests left running in the background when the loop restarted
itself kept going into the next round, and quietly killed that round's test
copies of the app, which then looked like crashes. By the time this card came
up, two later fixes had already made the next round see the leftover run,
wait for it instead of colliding, and warn when a test is started by hand
beside it.

## Goals

- [x] The next turn's claim reports a test run still in flight from this tree (T1658, `TEST RUN IN FLIGHT`)
- [x] The sweep runners wait on it instead of overlapping it (T1658: acceptance-parallel, floor-lane; T2151: harness-floor)
- [x] A hand-run acceptance script beside a live run warns before it starts (T2151, CleanSlate.ps1)

## Validation criteria

- [x] Claim prints TEST RUN IN FLIGHT for a live run - `test\win32\machine-lock.ps1` I10, ALL PASS (45 assertions) 2026-11-26
- [x] acceptance-parallel / floor-lane / harness-floor wait then refuse rather than overlap - machine-lock.ps1 I4-I8, I12-I14
- [x] A hand-run script beside a live run warns, and is silent inside it or with nothing running - machine-lock.ps1 I15-I17
- [x] A dead holder never reads as in flight - machine-lock.ps1 I9

Decision recorded: the "reset refuses while a run is in flight" half of the
original fix shape is deliberately NOT built. T1658 chose that a sweep
outlives a reset and the next turn waits on it; refusing the reset would
re-open the stalled-loop failure (go.md step 7), which costs far more than a
waited-on sweep.
