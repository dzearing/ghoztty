# T2296 - Unticking Share this machine should remove this PC from your account, so other devices stop listing it as offline (D100)

## In plain terms

Today, unticking "Share this machine" on Windows stops the PC serving but
leaves it registered, so your other computers list it as an offline machine
you cannot open. You chose (D100) that unticking should take the PC off your
account entirely, the way signing out does on a Mac, so no dead entry is left
behind.

## Summary

D100 (resolved 2026-10-26T05:59:57Z, option o1 "Untick removes this PC from
your account (Recommended)") overturns what T1965 assumed. T1965 made the
sharing choice tri-state (`sharing.Choice`: absent = follow enrollment,
explicit on/off respected) with `decide(choice, has_credential)` shared by the
agent reconciler and the chooser checkbox; an explicit off keeps the
credential and parks the uplink, which is the listed-but-dark state.

To build: unticking must deregister the machine from the relay account (the
same effect as the sign-out path that deletes `relay.env`), and re-ticking must
re-enroll (which now needs the sign-in step again, the con D100 accepted).
Re-check the D101 guest path (T2099: a non-owner's tick is refused and
explained) still holds, and whether an explicit "off" in sharing.json still has
any meaning once untick == sign-out.

Mac: no counterpart change - Mac has no checkbox; leaving there is signing out.

## Goals

- [x] Unticking takes this PC off the account, so other devices stop listing it.
- [x] Sharing stops at once even when the relay cannot be reached; the removal finishes itself later.
- [x] Ticking again afterwards re-adds the PC through the browser approval.
- [x] Changing your mind before an offline removal lands keeps the PC, without undoing a sign-out.

## What was built (2026-10-29)

- `ShareMachineRow.disable` writes `enabled:false` synchronously (the agent
  parks on its next poll, network or not), then a detached worker calls
  `enroll.deEnrollStatus` - the same `POST /v1/agent/deenroll` sign-out uses
  (`relay_signin.revokeThisMachine`). 204/401 clears relay.env's credential;
  the worker then deletes sharing.json, so the machine is back to "follows
  enrollment" and no explicit off survives to recreate an enrolled-but-dark PC.
- A relay that does not answer arms the T1424 pending revocation
  (`relay_revoke_pending`), with a new additive record field
  `origin: "untick"` (absent = `"sign-out"`, so old records read correctly).
  Footer: "will be removed ... as soon as the relay can be reached".
- A tick while that record is armed for the same credential cancels it
  (`pending_revoke.tickCancels`); a sign-out's record is never cancelled by
  the box.
- No whoami before the de-enroll, unlike sign-out: the box can only read
  ticked on a credential that is not another account's (T2099), and the
  user's intent is "this PC should not be reachable", not "leave my account".
- The busy guard is now direction-aware (`Busy.enrolling` / `.leaving`): one
  flow at a time either way, and only an enrollment shows the box ticked ahead
  of the file. Both workers release the guard BEFORE posting their result.
- **Does an explicit "off" still mean anything?** Only transiently: while an
  offline removal is owed, `off` keeps the uplink parked over the kept
  credential. Once the removal completes in the chooser's worker the file is
  deleted. (A removal completed later by the retry loop leaves `off` behind;
  harmless, since there is no credential, and a re-tick writes `on`.)
