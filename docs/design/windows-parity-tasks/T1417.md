# T1417 - win32 caption band has no tooltip host, so remote_pill.tooltip() is never shown

## In plain terms

Hover the connection chip in a remote window's titlebar and nothing happens.
It should tell you what it is: which machine you are connected to, and — while
the link is dropping — how many times it has tried to get back. That sentence
is already written and correct in the code; there is simply nothing on Windows
that can put a tooltip over the titlebar, so nobody ever reads it.

## Summary

Split out of T610 (2026-09-07), which added the machine name and the click but
left this half, as its Details section allows ("Either add a caption tooltip
host here or file it separately").

`remote_pill.tooltip()` produces the text and is unit-tested; every caller of
it is a test. The caption band has no tooltip control at all — `Window.zig`'s
`tab_tip*` block is a comctl32 track-mode tooltip wired exclusively to the tab
strip's hover tracking, keyed on one tool (`uId = 1`), and positioned under the
strip.

It matters more since D93: the recommended wording there gives the label to the
STATUS while a link is in trouble and moves the machine name into the tooltip,
so the tooltip is the answer to "which of my two reconnecting windows is this".

## Details

The shape to aim for is generalising the existing host rather than adding a
second one: one tooltip control per window, a small enum for what it is
currently describing (a tab, the pill), the text derived by whichever pure
module owns that thing, and the anchor rect supplied by the caller. Two
comctl32 controls in one window would double the theming work
(`tabTipReset` re-creates the control on a theme change) for nothing.

Hover already exists on the caption side: `caption_hover` is maintained by
`handleNcMouseMove` from `WM_NCMOUSEMOVE`, and `WM_NCMOUSELEAVE` clears it. The
delay timer is the same `GetDoubleClickTime` pattern the strip uses.

Note the non-client subtlety: the band's pixels are client but its mouse
messages are non-client, so the pointer position for `TTM_TRACKPOSITION` has to
come from the message rather than from a `WM_MOUSEMOVE` that never arrives.

While in there, check whether the "…" button and the caption slabs want tips
too — Windows names its own caption buttons to assistive tech, and ours are
custom-drawn.

## What changed

- `Window.zig`: `TipSubject` (none/tab/pill) says which region armed the one
  delay timer; `handleNcMouseMove` arms it for the pill, `WM_NCMOUSELEAVE` and a
  pill press drop only a PILL tip, the strip's `WM_MOUSELEAVE` only a TAB tip
  (the two leaves arrive in either order when the pointer crosses between
  regions). The pill tip sits 4 DIP below the capsule, pulled back inside the
  window's right edge, and re-reads its text when the ladder moves.
- **Latent bug fixed in passing:** `tabTipEnsure` zeroes the tool's text buffer
  when it creates the control, and both show paths loaded the text BEFORE
  calling it — so the first tooltip of a window's life, and the first after a
  theme reset (T557), came up as an empty bubble. Caught by 6a's width check
  (14 px of padding); the tab path had the same order and is fixed too.
- `test\win32\lib\TestDesktop.ps1`: `Send-TestRawMessagePair` posts a hover
  and its delay timer from one stack, so the leave TrackMouseEvent queues on a
  cursorless desktop lands behind both instead of between them.
- Follow-up filed: T1733 (the "..." and caption slabs want native-worded tips).
