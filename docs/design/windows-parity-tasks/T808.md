# T808 - Crash dumps are mini, not full: offer an elevated one-time arm that sets DumpType=2 for our test binaries, so a heap-corruption crash yields memory and not only stacks

## In plain terms

When something crashes on this box, Windows keeps a small snapshot of it. That
snapshot is enough to say which line of code fell over, but it throws away the
program's memory - so the crashes that come from memory being scribbled over,
the hardest ones we have, cannot be investigated from it. Windows can keep the
whole thing instead, but only an administrator can turn that on. Right now the
only instruction we give is a raw registry command pasted into a status line.
After this, one command offers to turn it on (a single Windows permission
prompt), one undoes it, and the status line says, per program, whether we are
keeping the small snapshot or the whole thing.

## Summary

WER's `LocalDumps` is armed machine-wide on this box and writes `DumpType=1`
(mini). A mini dump carries every thread's stack, which is what a stack
question needs - but it drops the heap, which is exactly what a corruption
crash (T443's family) needs. Full memory is a per-exe `DumpType=2` value under
`HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\<exe>`;
HKCU is ignored outright, so this needs elevation and is therefore an offered
one-time act rather than something a lane can arrange for itself.

The fix:

- `scripts\lib\CrashDump.ps1` grows the primitives - `Get-WerArmFullPlan`
  (what would be written, per target exe, without writing it),
  `Set-WerFullDumpArm` / `Remove-WerFullDumpArm` (the write and its undo), and
  `Test-IsElevated`. The key root is resolved through
  `Get-WerLocalDumpsKeyRoot`, which honours `GHOZTTY_WER_KEY_ROOT` - a test
  seam in the same spirit as `GHOZTTY_CRASH_NO_WER`, so the write path is
  provable against an HKCU sandbox instead of being asserted about.
- `scripts\crash-catch.ps1 -ArmFull` offers it: already elevated, it writes;
  otherwise it re-launches itself once through UAC and reports what the
  elevated run did. `-NoElevate` prints the exact `reg add` lines and exits 2
  rather than pretending. `-Disarm` removes the per-exe entries again.
- `-Status` now names the dump type per target binary, so "are we keeping full
  memory for ghoztty.exe?" is answerable without reading the registry.

## Validation criteria

- [x] `crash-catch.ps1 -ArmFull -NoElevate` on an unelevated shell prints the
      per-exe reg commands and exits 2 - it never reports success it did not
      achieve. (`test\win32\crash-first-chance.ps1` section 6b: exit 2, "needs
      an administrator", the exact `reg add` line, and no UAC prompt raised.)
- [x] `Set-WerFullDumpArm` against a sandbox key root actually writes
      `DumpType=2` per exe, and `Get-WerLocalDumpConfig` then reads that exe as
      `full` while an unarmed exe still reads `mini`. (Same section, against
      `HKCU:\Software\ghoztty-test-t808` through `GHOZTTY_WER_KEY_ROOT`; also
      checks the entry is per-exe and that folder/retention still come from the
      global key, and that a second arm changes nothing.)
- [x] `Remove-WerFullDumpArm` puts the sandbox back exactly as it was (the
      per-exe subkeys are gone, the global key untouched). (Same section.)
- [x] `-Status` names each target binary and its dump type. (Same section, plus
      by hand: `ghostty-test.exe / ghoztty.exe / ghoztty-agent.exe  mini dumps`.)
- [x] `test\win32\crash-first-chance.ps1` is green end to end and the
      `crash-first-chance` guard re-stamps. (ALL PASS, 69 assertions, STAMPED.)
