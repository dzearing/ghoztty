# T980 - Nothing stops a new self-spawn site from reappearing in a test build

## Summary

T933 found that a test build's selfExePath is the test runner, so any code that spawns 'our own exe' launches a detached copy of the test suite instead of the product - measured as 40+ minutes of dead time per floor run. Four sites were routed through src/os/self_exe.zig productExePath (holder spawn, relaunch guard, auto-launch, the agent's Run-key command), but nothing prevents the fifth. Wanted: a cheap sweep (a lane check or a scripts sweep) that fails when selfExePath/selfExeDirPath feeds a process spawn outside self_exe.zig, plus an audit of the sites that spawn a SIBLING computed from the exe dir (LocalAgent, AgentIntegration, cli/sessions.zig) - in a test build those resolve into .zig-cache and only miss by luck.

## In plain terms

When the test suite runs, some product code that "launches Ghoztty again" can
accidentally launch another copy of the test suite instead, which then runs for
tens of minutes in the background. Four such places were fixed by hand; this
adds a check that fails the moment a new one is written, and fixes the handful
that were still unguarded.

## Goals

- [x] every site that LAUNCHES our own exe (or a sibling beside it) goes through `src/os/self_exe.zig`
- [x] a sweep that fails on any new raw `selfExe*Path` call under `src/` that is not registered as a read
- [x] the sweep is a guard row, so editing `src/` makes it due and `validate` enforces it

## Validation criteria

- [x] `test/win32/self-spawn-audit.ps1 -TeethCheck` ALL PASS (14): fixtures both directions (A), zero findings over the real tree with a site-count floor (B), and a planted T933-shape spawn goes red (C). Verified on the box 2026-09-26; plain run ALL PASS (11) and stamped
- [x] floor lanes green: lib + none PASS; win32 + agent first went red on two LocalAgent composition tests that relied on the test binary's dir (fixed by naming the agent via `GHOSTTY_LOCAL_AGENT_BIN`), then PASS on re-run. Harness floor PASS (2 pending on T1568/T1123). Every harness made due by the touched files ran ALL PASS: url-scheme, registration-sites, rearrange-mode-action/window-drop/restore, pty-host, agent-autostart, resolve-window-persist, agent-handoff, agent-upgrade (147), agent-relay-session, sessions-running-cmd, msg-timer-ids, window-active-audit, restore-late-agent, guard-due
- [x] `self_exe.zig` unit test proves `productExeDirPathAlloc` refuses in a test binary (runs in the none/win32/agent lanes, all PASS)

## Resolution

Audit of the 23 raw `selfExe*Path` sites outside `self_exe.zig`:

- **Launches, now routed** (`productExePath*`, which refuse in a test build):
  `App.restartIntoInstalledBuild` (detached relaunch), `App.runComShimGuiRespawn`
  (the `.com` twin's respawn), `url_scheme.register` (the registered link-handler
  command is a launch the shell performs later), `handoff` supervisor `tick`
  (spawns the on-disk candidate agent), and the three smoke self-spawns in
  `conpty_smoke.zig` / `pty_host_smoke.zig` (product binaries, so the answer is
  unchanged there).
- **Sibling launches, now routed** through the new
  `self_exe.productExeDirPathAlloc`: `LocalAgent.agentBinary` and
  `cli/sessions.zig agentBinaryPath` (both spawn `ghoztty-agent.exe` from our
  dir). In a test build those resolved into `.zig-cache\o\<hash>` and missed only
  because nothing sits there; `GHOSTTY_LOCAL_AGENT_BIN` still overrides first.
- **Reads, registered** (14) in `test/win32/self-spawn-audit.registry.json`,
  each with its why: env exports, location gates, identity/provenance, install
  dirs.

The sweep (`test/win32/lib/SelfSpawnAudit.ps1`) keys sites by file + enclosing
function, reports unregistered sites, a registered read whose function also
launches a process, and stale registry entries. Guard row `self-spawn` covers
all of `src/`.
