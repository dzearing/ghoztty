# T1012 - Fourteen acceptance-script launches still do not say whether they want session persistence

## In plain terms

Test scripts that launch the terminal are supposed to say whether they want
the previous run's windows restored. Fourteen of them do not say either way,
so what they get depends on whatever the last run happened to leave behind —
which is how a test starts failing for a reason that has nothing to do with
the thing it is testing. The check that enforces this is currently failing,
and a failing check that nobody fixes is a check nobody reads.

## Summary

Found while running the standing audits for T297 (the new
`activity-monitor-dialed.ps1` is NOT one of the offenders). `test\win32\persistence-flag.ps1`
is RED on `main`:

```
FAIL  A1 no launch leaves persistence unstated (undeclared: 14 of 219)
```

The fourteen (script:line):

- `agent-handoff.ps1:239`
- `chooser-selection.ps1:135`
- `chooser-session-sort.ps1:96`
- `holder-adopt.ps1:421`
- `holder-durable.ps1:223`
- `holder-volume.ps1:256`
- `restore-late-agent.ps1:176`, `:214`
- `session-layout-preserve.ps1:173`, `:205`, `:243`
- `task-dashboard.ps1:94`
- `upgrade-staleness.ps1:647`
- `window-name-env.ps1:155`

T158's rule is **state which you want**, not "always pass the flag": several of
these (the `holder-*`, `restore-late-agent`, `session-layout-preserve` family)
legitimately WANT persistence on, so the fix for those is a
`# persistence: <reason>` marker, not a flag. Two are not ghoztty launches at
all in spirit — `task-dashboard.ps1:94` starts node and `upgrade-staleness.ps1:647`
starts a decoy powershell against the INSTALLED exe — and want a marker saying
so.

## Details

The sweep is `test\win32\lib\PersistenceSweep.ps1`; the acceptance script that
scores it (and proves the flag really stops a restore) is
`test\win32\persistence-flag.ps1`. Its section B already demonstrates all four
ways a site can declare intent (literal flag, splatted variable, marker,
every-caller-passes), so each of the fourteen has a shape to copy.

Do NOT paper over it by adding `--session-persistence=false` to a script that
wants a restore: that would turn a red audit into a green audit over a test
that no longer tests what it says it does.

## What was actually done (2026-09-13)

By the time this was worked the count was **52 undeclared of 289**, not 14 of
219 - the suite grew and T697 widened the sweep. Three of those 52 were not
work anybody could do, so they were fixed in the SWEEP rather than in the
scripts:

- an image taken from the environment (`-Exe $env:ComSpec`) resolved to a
  variable named `env` and was swept as the terminal: five cmd.exe `ping`
  fixtures were reported as undeclared ghoztty launches, and cmd.exe has no
  session to persist. An env var whose NAME says ghoztty is still ours (B11/B12);
- a tool found on PATH (`$node = Get-Command node`, launched as `$node.Source`)
  carries no `.exe` literal for the image check to read, so the dashboard's node
  server read as an undeclared ghoztty launch (B13);
- a marker written in the script's HEADER - the widest of the three marker
  scopes, and the one `update-graceful.ps1` had already written - counted for
  nothing, so a site whose reasoning was at the top of its own file was reported
  as work nobody had thought about. The same sentence written after the code
  starts still declares nothing (B14/B15).

The other 49 were declared where they stand: markers for the launches that want
a restore (or that run in a throwaway `$env:LOCALAPPDATA`, or that never open a
window), and `--session-persistence=false` for the two that keep the ambient
`$env:LOCALAPPDATA` and would otherwise reopen an earlier debug run's panes
(`chooser-selection.ps1`, `remote-reconnect-relay.ps1`).

And the reason the count could quadruple unnoticed is closed: `persistence-flag`
is now a row in `scripts\guard-due.ps1`, and a clean green run stamps it, so an
edit to any `test\win32\*.ps1` makes the sweep due again.

      from swallowing a real site - sections B11-B15 of `persistence-flag.ps1`.
