# T1394 - The autohide test probes the '...' button where it used to be, and lands on minimize

## Summary

`test\win32\tab-strip-autohide.ps1` fails one assertion:

```
FAIL  the '...' button hit-tests as HTSYSMENU, Windows' own code for the window menu (got 8)
```

8 is `HTMINBUTTON`; the script wanted 3 (`HTSYSMENU`). The button itself is
fine - two assertions later in the SAME script press it and get the window menu
popup, and the maximize/close probes beside it still answer 9 and 20. What is
wrong is where the script looks: it steps leftwards from the right edge by
(square + gap), and T496 made the caption trio full-height zero-gap slabs, so
the accumulated gap carries the leftmost probe one slot too far and it lands on
minimize.

Proven pre-existing by the T584 bisect on 2026-09-06: with `title_font.em`
forced back to the old off-ramp `16.0 * scale`, the same single assertion fails
identically, so it has nothing to do with the tab strip's font size.

## In plain terms

One of our own tests is clicking in the wrong place. The '...' button in the
title bar works - the test even proves it opens the menu a moment later - but an
earlier check asks "what is at this coordinate?" using spacing the window
stopped using, so it points at the minimize button and calls that a failure.

## Details

- The probe geometry lives in the script, near the `HTSYSMENU` assertion; the
  truth it should be measuring against is `caption_layout.zig`, which is where
  T496 put the zero-gap slabs.
- Prefer asking the layout rather than re-deriving it in PowerShell: the whole
  family of caption probes should step by whatever the code says a slab is
  wide, so the next caption change moves the test with it instead of past it.
- While in here, check the sibling scripts that probe the same trio for the
  same drift (`tab-strip.ps1`, `tab-color.ps1` are ALL PASS today, so the drift
  is likely local to this one, but confirm rather than assume).
