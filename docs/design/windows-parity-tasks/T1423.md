# T1423 - Hero-mode thumbnail snapshots steal frames from the hero pane

## In plain terms

Open the overview and the big pane in the middle should keep running smoothly
while the little previews along the strip refresh. Instead the work of
photographing every other pane competes with drawing the one you are actually
looking at, so the hero pane visibly hitches while the carousel is open. Mac
just fixed this by pacing the snapshot work.

## Goals

- [x] Find where the cost lands (see Findings: a synchronous GPU readback on the hero pane's own renderer thread, and a full-page browser paint for a viewer)
- [x] Snapshot capture is paced so it cannot starve the hero pane's paint
- [x] Thumbnails still refresh often enough to look live
- [x] A test that scores the pacing, not a screenshot of the result

## Findings

Where the cost lands on this side (read from the code, 2026-09-24):

- **Terminal leaves.** The carousel's 150ms heartbeat asked EVERY leaf, the
  hero pane included, for a capture. A terminal capture is a blit plus a
  synchronous `glReadPixels` on the pane's own renderer thread, taken after the
  frame is drawn and before it is presented, so the frame it rides on waits for
  the GPU to drain. Typing into the hero terminal paid that seven times a
  second. (The capture was already at tile size, so Mac's resolution fix has
  no terminal counterpart here.)
- **Viewer leaves.** `CapturePreview` makes the browser process paint and
  PNG-encode the whole page (it has no size knob), then GDI+ decodes it on the
  GUI thread. The 2s floor spaced those out but did nothing to keep one off a
  scroll. And the in-flight flag latched forever if the page never painted.

What changed (Mac policy, `bc89bb8f3`):

- `hero_snap_schedule.zig`: pure, clock-injected scheduler. 300ms quiet period,
  10ms jitter slack, per-kind idle cadence (terminal 150ms, viewer 1s - the
  Mac numbers; the viewer's old 2s existed only because nothing kept captures
  off a gesture), 5s stale-capture expiry, resize skips the cadence but never
  the quiet gate.
- Interaction is read off the App message loop for every window inside the
  top-level (keys, wheel, buttons, drags; plain pointer drift excluded, as on
  Mac), so the hero pane's own events count - the Mac bug's crux.
- Input to a WebView2 page never reaches our loop (its windows belong to the
  browser process), so the heartbeat also samples the session's last-input
  tick: it counts when it moved, our window is foreground, and the pointer did
  not move (a wheel/key/click, not drift).
- Viewer: in-flight is a timestamp that expires, and each capture's handler
  carries a generation so a late answer to a superseded capture is dropped.
