# T2946 - At 4K the heaviest fold-glide tick is still 12-14 ms of window-move batch plus vacated-strip compose, leaving too little headroom for a window-manager sync tail (after T2942 took the face's SetWindowRgn out)

## In plain terms

On a 4K screen, folding a pane into its strip while dragging a divider runs
a few heavy frames that take 11-12 ms of the 16.7 ms a smooth frame allows.
That leaves too little slack: when Windows itself is briefly slow on one of
those frames, the frame is late and the glide hitches. This task trims those
heavy frames until a slow Windows call still fits.

## Goals

- [x] Find where the heavy frame's time actually goes (split the batch, the desk paint's tail, and the glass slices)
- [x] Stop a card that only slides from flickering a pixel in size every frame (a needless resize of the viewer page, 1.5-2.3 ms)
- [x] Stop each glass slice paying for fresh memory every frame
- [x] Cut the desk compose on the heavy frames (2.3 ms -> 0.7 ms average: its columns now composed across the sheet workers)
- [x] Cut the folding card's face repaint (wide-face avg 2.38 -> 1.62 ms: its band fill and its finish now shared across the sheet workers)
- [ ] Cut the window-move batch so the heaviest frame is <= ~10 ms (now 9.9-11.3 ms max per run)

## Summary

T2943 found the rare >16.7 ms 4K fold-glide tick (about 1 in 2,000 on a quiet
box) is always one of the 14-19 heavy ticks a run - the ones that repaint a
wide carried strip face - plus one window-manager-synchronous call running 2x
its mean. T2942 took the face's per-tick popup `SetWindowRgn` out (its card cut
now goes into the face's pixels): face rgn_us 0.25 ms mean / up to 6.5 ms ->
8 us, face max 8.7 -> 4.2 ms, ticks >= 12 ms 31 -> 22 in 4 runs. What is left
on those ticks is the window-move batch (EndDeferWindowPos, 2.5-3.6 ms mean on
heavy ticks, 6 ms tail seen) and the vacated-strip compose (~3 ms), plus the
face's UpdateLayeredWindow of a ~700 x 2023 bitmap (~1.3-2 ms) and its fill/finish
(~1.5 ms). Target: the heavy tick <= ~10 ms so a 2x sync tail still fits a
60 Hz frame.

Levers to measure (release sandbox, `GHOZTTY_STACK_TRACE=ring`, drag-glide
4K arm; the A/B runner shape is in T2942's progress log): what the batch waits
on (split place_us with the batch/defer_end/cut/filled QPC stamps), whether the
vacated compose can be cut to the swept strip, and whether the face's repaint
can shrink to what changed (the carried frame is pinned; only the band edge and
the fade move).

- [ ] On a release build: 0 ticks over 16.7 ms across at least 10 consecutive quiet-box 4K runs (other-process CPU recorded per run), closing T2462's 4K frame clause

1. **The batch's tail was the viewer, not the terminal.** New `stack trace
   applied` stamp: the held terminal `applyResize` is ~25 us; the 1.0-2.3 ms
   after it is the viewer's `syncBoundsLive` (nav bar + WebView2 put_Bounds),
   which only runs on WM_SIZE.
2. **That WM_SIZE was spurious on ~80 ticks a run.** A drag glide's pane rect
   rounded each edge on its own (`Edges.round`), so a 281 px card whose eased
   edges sat near a half pixel presented as 282 on some frames (`card ...
   from=2609,53+281 drawn=...+282 to=...+281`). Fix: `Edges.roundSized`
   (round the leading edge and the size) for the resize glide's pane rect.
   The viewer's size changes per run fell 297 -> 217 (the rest are real
   layout resizes).
3. **The desk paint's 1-2 ms tail was the glass slices.** New `stack trace
   vacated tail` line: `syncGlassBackdrops` 1.2-1.6 ms on heavy ticks; each
   moved terminal gets a new desk slice. Per slice ~1.6 us per 4 KB page of
   fresh buffer (page faults) plus a memory-bound crop. Fix:
   `backdrop_pool.zig`, a process-wide recycling allocator the renderer frees
   back into, and whole-texel stores in `cropDeskRegionRgba`. Widest slice
   ~430 -> ~325 us; the rest is reading the 4K desk -> T2947.
4. **The vacated compose is the biggest piece left**: `area`/`rects` on the
   vacated line say ~600k px in 4 rects, 2.5-2.8 ms.
