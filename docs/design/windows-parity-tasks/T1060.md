# T1060 - Adversarial review gate before any PR merges: accuracy, CLAUDE.md compliance, DRY design, real test coverage

## Summary

User directive, 2026-08-21: every PR gets an adversarial review before merge,
enforcing four things - claims are accurate, CLAUDE.md rules were followed, the
code is good and the design is DRY, and it is genuinely tested.

The point of "adversarial" is that the reviewer's job is to REFUTE, not to
approve. A reviewer that starts from "does this look fine" finds nothing; one
that starts from "this claim is false, prove otherwise" finds the class of
defect this project keeps paying for - a validation criterion ticked without
evidence, a test that cannot go red, a second copy of an existing helper.

## In plain terms

The person who wrote the code is the worst person to judge whether it works.
Every proposal should get a second opinion whose job is to try to knock it down:
does it really do what the description says, does it follow the house rules, is
it a duplicate of something we already have, and would the tests actually notice
if it broke. If it survives that, it merges.

## What the gate checks

1. **Accuracy** - every claim in the PR description and every ticked validation
   box is backed by evidence that can be re-run. This project has a standing
   claim-verification rule and a history of exactly this failure; the reviewer
   should assume a tick is unproven until shown otherwise.
2. **CLAUDE.md compliance** - the non-negotiables, notably platform symmetry
   (both seats, or the other half filed), never touching the user's installed
   build, the wire-protocol compatibility boundary, and "everything gets tests".
3. **Quality and DRY** - no second implementation of something that exists;
   check against the existing helpers before accepting a new one.
4. **Tests that can fail** - a teeth-check, not just a green run. A test nobody
   has seen go red is not evidence.

## Goals

- [x] The review is a defined, repeatable step with a written checklist, not an
      ad-hoc read. -> `scripts\pr-review.ps1 check|prompt|record|gate`; the
      checklist sits between markers in the workflow doc and `prompt` prints it.
- [x] It is adversarial by construction - the reviewer is prompted to refute and
      defaults to "not proven" when uncertain, rather than to approve. -> the
      brief's opening and checklist item 5; `record -Verdict pass` REFUSES while
      any mechanical finding is unanswered (fixed, or waived with a recorded why).
- [x] It runs at the PR boundary and its verdict is visible on the PR. ->
      `record -Pr <n>` posts the verdict (with every waiver) as a PR comment,
      through the script's single `--repo`-pinned gh funnel.
- [x] A failing review blocks the merge; overriding it is explicit and recorded.
      -> `ship-feature.ps1 merge` runs the gate on the exact pushed head (a newer
      push reads REVIEW STALE); `-Override -Reason` records an `override` verdict.

## Validation criteria

- [x] Run against a real change and produce findings that a human agrees are
      real. **Verified, by proxy**: no PR exists before the cutover (T1074), so
      the brief `pr-review.ps1 prompt` generated for the real commit c8607b32a
      went to an independent `critic` subagent. It returned VERDICT: FAIL with
      one defect: T2058's "harnesses made due by the library edit ... 7/7"
      tick names two guards whose stamps do not cover the edited libraries. I
      checked that against the stamps and it holds, so it is journaled on T2058.
      The first run against a real PR is T2065.
- [x] Run against a deliberately-bad PR and confirm each planted defect is
      caught. **Verified**: `test\win32\ship-workflow.ps1` section E plants an
      unevidenced tick, a Windows-only feature, a duplicated PowerShell helper,
      a duplicated zig helper, a zig test with nothing that can fail, and a
      harness whose asserts are all `$true` (E1-E7), plus untested code (E12).
      Each is caught by key. Negative control: with the unproven-tick rule
      disabled, E2 went red (1 FAILURE, 60 passed).
- [x] A clean PR passes without invented findings, and the false-positive rate
      is measured, not assumed. **Verified**: E17 (a clean sandbox PR: CLEAN).
      `check` was run over the last 41 real non-chore commits, one at a time.
      The first sweep flagged most of them, and the rules were tightened (wider
      evidence shapes, zig methods and one-word names excluded, a port that
      names the other platform is not one-platform). The final sweep flags 1
      of 41, T1041's "closed without a new code commit" tick, which is
      arguably a real finding.
- [x] The checklist lives with the workflow docs (T1058), so the gate and the
      process cannot drift apart. **Verified**: `<!-- review-checklist:* -->` in
      `windows-parity-ship-workflow.md`. `prompt` reads it from there and
      refuses (exit 2) if the markers are missing. D7 asserts the markers, and
      E10 asserts the brief carries the doc's text.
