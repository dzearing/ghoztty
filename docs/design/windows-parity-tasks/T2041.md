# T2041 - test-reach audit stayed green while mac_layout_blob.zig's tests were in no test binary: find why its binary scan counted a module the lane never ran

## Summary

Found in T1979. `src/apprt/win32/mac_layout_blob.zig` has had `test` blocks since T337, and `layout_blobs.zig` imports it, but nothing referenced it from a test container (`src/apprt.zig` lists `layout_blobs.zig` and not this file). Evidence that its tests did not run: `zig build test -Dapp-runtime=win32 -Dtest-filter=mac_layout_blob` hit the test-filter guard ("matched no tests") before T1979 added `_ = @import("apprt/win32/mac_layout_blob.zig");` to `src/apprt.zig`, and afterwards the same filter ran them and a deliberately broken assertion went red.

Yet `test/win32/test-reach-audit.ps1` (T1191) was stamped green on 2026-10-16. Its rule is exactly this case. Find out why: whether its `Get-WinModulesInTestBinary` string scan matched `apprt.win32.mac_layout_blob.test` in the binary from something other than a compiled test (debug strings, a panic message, the other test binary), whether `Resolve-WinTestBinary` read a different binary than the lane ran, or whether the filter guard misled T1979. Fix the audit so it goes red on this shape, and add the case to its section A fixtures / `-TeethCheck`.

## Validation criteria

- [ ] With the `src/apprt.zig` reference to `mac_layout_blob.zig` removed, the audit's section B goes red naming `mac_layout_blob` (or the investigation shows the tests really ran before, and T1979's log entry is corrected).
- [ ] Restored, the audit is ALL PASS.
