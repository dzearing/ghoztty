# T1651 - Every due GUI acceptance harness stands up its own desktop and app launch, so one small change costs four full fixtures

## In plain terms

Proving a one-line change is safe can take twenty minutes, and almost none of
that time is spent checking anything. Each automated screen test opens its own
private desktop, starts the app from scratch, and tears it all down again, even
when four of them run back to back over the same change. Fixing that would not
change anything on screen — it would mean fixes arrive faster.

## Goals

- [ ] One command runs every GUI harness that is currently due, on a single
      background desktop, with a single app launch where the scripts allow it.
- [ ] A harness run this way reports the same per-script verdicts it reports
      today; batching must not collapse four answers into one.
- [ ] A script that dirties the fixture (kills the app, takes the pipe) is
      declared as such and is given its own fixture inside the batch.

## Summary

`scripts\guard-due.ps1 check` can report several GUI acceptance harnesses due
from a single edit — on 2026-09-17 a one-line change to `MachineChooser.zig`
made four rows due, and running them cost twenty-plus minutes of wall clock.
Each script independently stands up a background desktop via
`test\win32\lib\TestDesktop.ps1`, launches `zig-out\bin\ghoztty.exe`, waits for
the window, runs its assertions, and tears the whole fixture down. The
assertions themselves are seconds; the fixture is the cost, and it is paid once
per script rather than once per change.

The shape to aim for: a batch runner that takes the due set, opens one desktop,
and drives the scripts that can share a fixture in sequence against one app
instance, isolating only the ones that deliberately destroy it (the scripts that
kill agents or take the per-user pipe — `docs/claude/testing.md` names them).
Verdicts stay per-script so a red stays attributable, and the guard stamps are
written per-script exactly as they are today.

Constraints worth respecting: the lanes and acceptance scripts must still run
sequentially, never overlapped (T401); a shared app instance must be proven not
to leak state between scripts, or the batch will trade wall clock for flake;
and a script that cannot share must be able to say so declaratively rather than
by convention.

## Validation criteria

- [ ] Running the batch over a due set of four GUI harnesses produces the same
      four verdicts as running them individually, on the same tree.
- [ ] Measured wall clock for that set is materially lower than the sum of the
      individual runs (record both numbers in the progress log).
- [ ] A script marked as fixture-destroying gets its own fixture, demonstrated
      by including one in the batch and showing the scripts after it still pass.
- [ ] Guard stamps written by a batch run are byte-identical in shape to those
      written by an individual run.
