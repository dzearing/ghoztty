# T3241 - A large picture in an image pane costs ~9.5x its size in app memory and a ~110 ms GUI stall because every WebResourceRequested body is copied inside WebView2's in-process hand-off - serve big pictures without passing their bytes through the app

## In plain terms

Opening or live-reloading a big picture (a 12-megapixel TIFF, a 48 MB PNG) in
an image pane briefly balloons Ghoztty's memory by about 460 MB and freezes
every pane in the window for about a tenth of a second. The cause is not the
picture decode. It is how the picture is handed to the embedded browser. When
this lands, a big picture costs roughly its own size once, and the window
stays responsive while it loads.

## Goals

- [x] find out why the folder-mapped picture never loaded (read over the DevTools protocol)
- [x] serve large pictures from a folder the browser process reads, so their bytes never pass through the app
- [x] keep small pictures, vector art and every failure card on the path they used before
- [x] never leave staged pictures behind: not on close, not after a crash

## Summary

Measured by T3223 (2026-11-18, lane b, debug build, test desktop,
`--macos-window-mode=separate`, a 64x64 picture open, then a 4000x3000 one
copied over it so the watcher reloads; private-bytes timeline sampled every
20 ms, events wall-clock stamped):

- **Route-independent.** The `wic` route (12 MP LZW TIFF -> 48,000,138-byte
  `.bmp`) and the `browser` route (48,054,642-byte noise PNG streamed straight
  from disk by `respondFile`) both show the SAME +459 MB peak and ~110 ms
  worst WM_NULL round trip. So T3043's decode work was never the spike.
- **Where it happens.** Decode on the worker +46 MB (the one body buffer).
  WebView2 then reads the response IStream in 1,466 x 32 KB `Read`s, ~20 ms
  total. Then **+320 MB appears inside WebView2's in-process hand-off within
  ~80 ms after the last `Read`**, and is freed before the page reports
  `loaded`. That is about 9.5x the body.
- **Ruled out:** stream agility. WebView2 QIs the body for `IAgileObject`.
  A non-agile stream is read on the GUI thread, an agile one on a WebView2
  thread, but the peak and the stall were unchanged either way. Also ruled
  out: our own copies (one GlobalAlloc after T3043).

## Approach tried (does NOT work yet) - the WIP patch

`docs/design/perf-audit/T3223-folder-mapping-wip.patch` (applies cleanly to
d303d324e) serves the picture through `SetVirtualHostNameToFolderMapping`
(`ICoreWebView2_3` slots 71/72, added to `webview2_iface.zig` with
`HostResourceAccessKind`; ABI and enum checked against the 1.0.2903.40 SDK
header). On the `browser` route the picture's own folder is mapped. On the
`wic` route the worker spills the `.bmp` to a per-pane `%TEMP%\ghoztty-decoded\<pane>`
folder and frees its buffer. The parked `__image` request is answered with a
`302 Location:` to the mapped URL. It also adds `viewer_content.mappedImageUrl`
plus a unit test.

Result: with the patch the peak drops to +46 MB and the stall to 9-24 ms, BUT
**no picture loads** (no `event=loaded`; the `browser` route logs
`viewer image retry route=wic`). So the low numbers only mean that nothing was
fetched. Variants tried, all still failing:

1. a 302 from the intercepted `__image` request to the mapped host
2. `setImage` pointed DIRECTLY at the mapped URL (`browser` route, mapping set
   after the page had navigated)
3. the decoded host mapped BEFORE the first `Navigate` (`subscribeFileMode`
   time), answered by 302
4. dotted host names (`image.ghoztty.example`) instead of single-label ones

`SetVirtualHostNameToFolderMapping` returned S_OK every time.

## Next steps

- Find out WHY the mapped host serves nothing. The combination not yet tried is
  mapping set before navigation AND a direct `src` with no redirect. Read the
  failure with the DevTools protocol (`Network.loadingFailed`) or a
  `WebResourceResponseReceived` handler, rather than guessing. Suspects: the
  `deny_cors` access kind for a cross-origin `<img>`, a redirect out of an
  intercepted response not being followed, or the mapping only reaching
  navigations.
- If folder mapping cannot serve this page, try the fallback design:
  `ICoreWebView2Environment12::CreateSharedBuffer` +
  `ICoreWebView2_17::PostSharedBufferToScript`. The page builds a Blob/object
  URL from the shared ArrayBuffer, so the app holds the bytes once, in shared
  memory. That needs an `image.js` change; keep the Mac path untouched.
- Re-run the measure (logic in T3223's progress log; it needs a `loaded` check
  added so a failed load can never read as a win).
