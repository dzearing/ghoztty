# T2424 - No hover highlight or pane tint anywhere during a Windows pane-sidebar or pane drag (Mac 6bd2962eb nothing hovers mid-drag)

## Summary

Mac main 6bd2962eb: while any drag is in flight (sidebar item drags AND pane drags) no row shows hover and no pane shows its hover tint. Windows: check the sidebar row hover and the pane hover tint during a sidebar row drag and during a pane drag (PaneDragSession equivalent); suppress both until the drag ends; add an acceptance check. Ref HoverTrackingViewTests.swift / PaneDragSession.swift in 6bd2962eb.

## In plain terms

When you hover a pane's row in the sidebar, that pane lights up in its colour.
If you then grabbed the row and dragged the pane somewhere, nothing stopped
that colour from staying on, or from lighting up again mid-drag. On the Mac
nothing lights up while something is being dragged. Now Windows matches: the
colour comes off when you pick a pane up and comes back, from wherever the
pointer is, once you let go.

## Goals

- [x] Any live pane drag (from a sidebar row, a grab handle, a header or a
  strip) holds every hover: the pane tint comes off and no row gives one
  until the drag ends.
- [x] When the drag ends, every sidebar re-reads the hover from the pointer
  and gives the tint back if a row is still under it.
- [x] Sidebar window/group drags (T2337) already cleared hover and tint and
  re-synced afterwards; checked, nothing needed.

## Design

- `App.hover_held` is Windows' `HoverTrackingView.isHeld`. It is set and
  cleared in `Window.setSidebarsDragActive`, the one place every live pane
  drag goes through (Mac sets it in `PaneDragSession` begin/end). Going on, it
  clears `App.sidebar_hover_pane` (Mac `PaneSidebarHover.shared.clear()`) and
  every window re-lays its tints.
- `pane_sidebar.tintedItem(hover, held)` (pure, unit-tested) is the one
  answer to "which row's pane takes the tint"; `PaneSidebar.syncHoverTint`
  asks it, so every route that changes hover mid-drag (leave, the T2341
  activation re-read) is refused.
- `PaneSidebar.setDragActive(false)` re-reads the hover (`resyncHover
  "pane-drag-end"`), then re-syncs the tint (Mac `heldDidEnd`).
- Row hover LOOK is left as it is during the drag, as on the Mac ("every
  hover stays as it is").
- Window logs `pane hover held=true|false` at each edge, for the harness.

## Validation criteria

- [x] The tint gate is pure logic with a unit test - `pane_sidebar.zig`
  "a pane drag tints no pane (T2424, Mac 6bd2962eb)"; `floor-lane.ps1 -Lane
  all`.
- [x] Hovering a row tints its pane (positive control), a live pane drag
  logs `pane hover held=true`, a hover posted at the row mid-drag tints
  nothing, and the release logs `held=false` - section C of
  `test\win32\pane-sidebar-drag.ps1`, ALL PASS (80 assertions).
- [x] The mid-drag check has teeth: with the gate disabled
  (`tintedItem(.., false)`) and rebuilt, `C: no pane is tinted while it is
  carried, even hovered` went red (1 failure, 79 passed); reverted.
- [ ] Not observable off-desktop: that the tint visibly comes off at the
  pickup. A posted hover does not stay - the app's leave tracking sees the
  real cursor elsewhere and fades it within milliseconds - so the tint is
  already gone by the pickup on the test desktop. The code path is the same
  `syncHoverTint` the mid-drag check proves.
