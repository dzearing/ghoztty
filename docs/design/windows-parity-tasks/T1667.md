# T1667 - The two hand-kept shell tables (bare_shells_without_integration and the agent's windowsCommandArgs) can drift apart with nothing to catch it

## Summary

T864 added `bare_shells_without_integration` to
`src/termio/shell_integration.zig` — the allowlist of programs that are shell
CHOICES even though no integration script exists for them. It currently holds
one row, `wsl`, and the reason `wsl` may be on it is that the agent's
`windowsCommandArgs` (`src/remote/agent/pty_child.zig`) knows how to run `wsl`
as a shell. The two lists are a PAIR, and nothing asserts they agree.

Two drift directions, both silent:

- A row added to `bare_shells_without_integration` that the agent has no
  handling for: the client stops wrapping it, the agent spawns something it
  does not know the command convention for, and a pane with a command
  misbehaves in a way that points at neither file.
- A row added to `windowsCommandArgs` (a new shell the agent learns) that
  nobody adds to the client list: that shell keeps running under the
  `cmd /c` wrapper — T864's defect, re-created for the new shell, with the
  fix for the general case already in the tree and not applied.

`detectShell`'s own table is the third member of the family: `powershell`
appears in all three, `cmd` in two.

## In plain terms

Two lists in two different files have to agree about which programs count as
shells, and right now the only thing keeping them in step is somebody
remembering. If a future change teaches one of them about a new shell and not
the other, a pane running that shell quietly gets an extra hidden process
again — the exact thing that was just fixed.

## Where

- `src/termio/shell_integration.zig` — `bare_shells_without_integration`, `detectShell`
- `src/remote/agent/pty_child.zig` — `windowsCommandArgs`
