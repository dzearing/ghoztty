# T3214 - close-undo.ps1 run alone (w0) reads the user's real config: with macos-window-mode = single there, +new-window becomes a workspace and 16 extra assertions go red

## Summary

Found in the T3206 due sweep (2026-11-17). `test/win32/close-undo.ps1` is green
apart from T2921's one known assertion in a pool worker (93 pass), but run ALONE
in w0 it fails 17. Section 4 reports "its shell is still running" FAIL; 4w reports "setup:
w2's window and pane found" FAIL, and every assertion after those fails too. Both runs were reproduced: logs
`%TEMP%\ghoztty-acceptance-parallel\20261117-084525\05-close-undo.alone.log` and
`%TEMP%\ghoztty-acceptance-parallel\20261117-084953\*close-undo.alone.log`. This morning's T3205 alone run
(05:04) had only the T2921 assertion red.

Cause: the user's real config `%LOCALAPPDATA%\ghostty\config.ghostty` now says
`macos-window-mode = single` (the user's own setting - never touch it). The
alone run does not isolate XDG_CONFIG_HOME, so the debug app launches in
single-window mode. `+new-window w2` becomes a workspace in the shared HWND, and
the close/park/undo shapes the script asserts are the separate-mode ones.

Fix: close-undo.ps1 (and any sibling that launches the app without a temp
config - sweep with the harness floor's isolation audit) launches with a
temp XDG_CONFIG_HOME, or at least pins `macos-window-mode = separate`. The
isolation audit should also flag a launching harness that reads the user's
config.

## Validation criteria

- [ ] close-undo.ps1 run alone (`acceptance-parallel.ps1 run -Scripts close-undo.ps1 -Width 1`) with the user's config in single mode fails only T2921's assertion
- [ ] a harness-floor audit names any app-launching harness that does not isolate the config
