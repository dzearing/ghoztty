# T3214 - close-undo.ps1 run alone (w0) reads the user's real config: with macos-window-mode = single there, +new-window becomes a workspace and 16 extra assertions go red

## Summary

Found in the T3206 due sweep (2026-11-17). `test/win32/close-undo.ps1` is green
apart from T2921's one known assertion in a pool worker (93 pass), but run ALONE
in w0 it fails 17. Section 4 reports "its shell is still running" FAIL; 4w reports "setup:
w2's window and pane found" FAIL, and every assertion after those fails too. Both runs were reproduced: logs
`%TEMP%\ghoztty-acceptance-parallel\20261117-084525\05-close-undo.alone.log` and
`%TEMP%\ghoztty-acceptance-parallel\20261117-084953\*close-undo.alone.log`. This morning's T3205 alone run
(05:04) had only the T2921 assertion red.

Cause: the user's real config `%LOCALAPPDATA%\ghostty\config.ghostty` now says
`macos-window-mode = single` (the user's own setting - never touch it). The
alone run does not isolate XDG_CONFIG_HOME, so the debug app launches in
single-window mode. `+new-window w2` becomes a workspace in the shared HWND, and
the close/park/undo shapes the script asserts are the separate-mode ones.

Fix: close-undo.ps1 (and any sibling that launches the app without a temp
config - sweep with the harness floor's isolation audit) launches with a
temp XDG_CONFIG_HOME, or at least pins `macos-window-mode = separate`. The
isolation audit should also flag a launching harness that reads the user's
config.

## In plain terms

Several test scripts, when run on their own instead of in the parallel pool,
read the user's own Ghoztty settings. The user has single-window mode switched
on, so those tests saw "new window" open a tab-like workspace instead of a
window and failed for a setting that is perfectly fine. Now every test launch
gets a blank settings folder unless the test deliberately picked its own.

## Goals

- [x] an alone/exclusive run never reads the user's real config
- [x] a script that chose its own config (XDG_CONFIG_HOME, or a private LOCALAPPDATA) is untouched
- [x] the residual reds belong to already-filed defects, with the guard acks moved to them

- [x] close-undo.ps1 run alone (`acceptance-parallel.ps1 run -Scripts close-undo.ps1 -Width 1`) with the user's config in single mode fails only T2921's assertion - verified 2026-11-18 02:34 with `macos-window-mode = single` in the user's config: 93 pass, 1 fail ("u1's HWND is destroyed once the 6s undo runs out", T2921); it was 17 red before.
- [x] a harness-floor audit names any app-launching harness that does not isolate the config - the isolation now rides the only two launch helpers (Start-OnTestDesktop, Invoke-OnTestDesktop), and desktop-launch-audit.ps1 (harness floor) already fails any script that launches the app any other way, so "launches without isolating the config" and "launches outside the helper" are the same finding. Z3 of test-desktop-harness.ps1 asserts the decision both ways and what the helper hands a real launch.
