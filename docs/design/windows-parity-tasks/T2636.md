## In plain terms

With the new GPU presentation path turned on, a terminal pane whose size had changed showed its text slightly (sometimes very) stretched sideways and downwards - most visibly right after a pane slid into place, when one pane's text looked 1.6 times too wide. Now the picture is shown at exactly one screen pixel per pixel at every size, so text stays crisp after any resize or slide.

## Root cause

T2598 (2026-11-01) stopped resizing a pane's swap chain on every resize step: the buffers grow in 256 px buckets and each frame is presented as a `SetSourceSize` rectangle of them. On a COMPOSITION swap chain the compositor stretches that source rectangle over the chain's whole buffer size, so every frame was drawn buffer/source too large - the blue card's "rest" size in the film was 234 px against a true 192, and the card that had just come out of its strip was 1.6x wide. The scorer only noticed at the landing, because that is the one moment a card's stretch factor changed mid-film. A/B with `GHOZTTY_COMP_RESIZE_BUFFERS=1` (exact resizes) was ALL PASS, which isolated it.

Fix: `IDXGISwapChain2::SetMatrixTransform` with scale (source / buffer) beside every successful `SetSourceSize`, identity when the chain refuses. This turn built and validated exactly that, and at push time found lane B had landed the same fix minutes earlier as **3fe9df516 (T2625)**, from the split side of the same stretch. The rebase took T2625's code verbatim, so this task closes on that commit, and the film re-run on it is the validation T2625 did not carry.
