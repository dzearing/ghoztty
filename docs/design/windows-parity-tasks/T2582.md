# T2582 - A development build reads and writes its own config file, never the installed release's (Mac ac44094e8)

## Summary

Mac ac44094e8: libghostty's bundle_id is the same in every build, so the debug app loaded and its Settings window WROTE the release app's config; a fork-new key written while testing made the installed release show 'unknown field' errors. Mac now gives dev builds (Debug/ReleaseSafe, build_config.is_dev_build - the debug-IPC rule) their own config folder (build_config.config_bundle_id = <bundle_id>.debug) and preferredDefaultFilePath never returns the shared XDG file for them. Windows: every build resolves %LOCALAPPDATA%\ghostty\config.ghostty (src/os/xdg.zig config(), file_load.preferredDefaultFilePath 'else' arm), so the debug build's Open Config (App.openConfigFile) and +edit-config already open the USER'S release config, and once the Settings window writes config this is a CLAUDE.md non-negotiable breach (never touch the installed Ghoztty). Translate: a dev build's preferred (written) config is a debug-suffixed file beside the per-build prefs pattern (pane_sidebar-debug, the debug pipe), loaded after the shared file the way Mac loads App Support after XDG; release unchanged. Arrives with the T2490 merge (build_config.is_dev_build / config_bundle_id land in shared src/). Mac reference: docs/reference/settings.md 'The debug build has its own config'. Unit test in the none lane: the dev-build preferred path is the debug one on windows.

## In plain terms

A test copy of Ghoztty used to read and write the same settings file as the
copy the user actually uses, so trying out a setting while testing could change
(or break) the user's real terminal. Now a test copy keeps its own settings
file beside the real one: it still picks up the user's settings, but anything
it creates or edits goes into its own file. The installed app is unchanged.

## Goals

- [x] a dev build's "open config" / `+edit-config` path is `config-debug.ghostty`, never `config.ghostty`
- [x] a dev build loads the shared file first, then its own file over it (Mac's XDG -> `.debug` App Support order)
- [x] a dev build only ever creates its template in its own file
- [x] release builds unchanged

## Design

- `file_load.devXdgPath` = `%LOCALAPPDATA%\ghostty\config-debug.ghostty`; `uses_dev_xdg_path` = Windows and `build_config.is_dev_build` (Debug/ReleaseSafe, the same rule Mac and the debug IPC use).
- `preferredDefaultFilePath` (Open Config, `+edit-config`, `+list-themes`) returns it unconditionally on a dev build.
- `Config.loadDefaultFiles` loads it after the XDG file; the template is written there only when neither exists.
- `edit.configPathCandidates` returns only it on a dev build (unused on win32 today; kept coherent for the Settings writer).
- A sibling file rather than a `ghostty-debug\` folder: matches the per-build Windows file naming (`pane_sidebar-debug`, viewer prefs), and keeps the `config-file` relative includes the user's shared config may name resolving from the same folder.
