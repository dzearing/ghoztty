# T774 - ghoztty.log grows without bound - no size cap or rotation

## In plain terms

The log file the Windows build leaves behind used to grow forever, and that was
fixed two weeks ago: it stops at 4 MiB now and keeps one older copy beside it.
What was never actually measured is the awkward part of that fix - the log is
written by the app, the background agent and every one-shot command at the same
time, so several of them can decide to archive it in the same instant. If they
get that wrong, the one thing that can happen is the worst thing: the archive
they were preserving gets replaced by an empty file, and the history a user was
about to send you is gone. Nothing notices, because logging never reports a
failure. This lands the test that proves it does not happen.

## Goals

- [x] Re-verify the cap and rotation the card asked for actually shipped
- [x] Prove the archive survives many writers crossing the threshold at once
- [x] Prove no writer loses a log line across the rotation boundary
- [x] Prove a straggler that renames after somebody else already rotated
      cannot move a fresh, tiny log over the archive

## Summary

**The cap itself shipped in T410** (`53d21cc1d`, 2026-09-03): `src/os/log_rotate.zig`
bounds `%LOCALAPPDATA%\ghoztty\ghoztty.log` at 4 MiB and two generations,
archiving the live file over `ghoztty.log.1` by renaming the HANDLE rather than
the path. Re-verified against the source at claim time; the direction this card
asked for is what was built, including the concurrency answer it asked to be
explicit.

**What was still owed is this card's own Validation line**: a rotation arm under
CONCURRENCY. `test\win32\log-append.ps1` sections R1-R10 all cross the threshold
with one process at a time, which is the half that cannot fail. The claim the
bound actually rests on - N writers crossing in the same millisecond neither
destroying the archive between them nor losing a line across the boundary - was
argued in the module header and never measured. A path-rename build passes
R1-R10.

## Fix

Two arms, at the two layers where the claim lives.

- **`test\win32\log-append.ps1` sections C1-C7** measure it on the real release
  binary: the live log is seeded exactly ON the threshold, then all 24 writers
  are launched at once so each one's first line crosses it. C2/C3 assert the
  archive is still the seeded generation and still 4 MiB (a racer that moved a
  fresh live log over it leaves a few hundred bytes and no seed marker), C4 that
  no third generation appears, and C5/C6 that the union of the two generations
  holds every one of the 9 lines each writer emits - which is "no line lost
  across the boundary" with an exact oracle rather than a spot check.
- **`src/os/log_rotate.zig`** gains the deterministic unit test for the
  straggler: two writers open a rename handle on the oversize log, the first
  rotates, a third writer recreates the live file, and only then does the second
  rename. Renaming by handle moves the file it opened - already the archive - so
  4 MiB of history and the fresh live file both survive. Teeth confirmed by
  swapping in `dir.rename` on a scratch copy: it fails with
  `expected 4194304, found 64`, which is precisely the history-destroying defect.

One false failure came out of building this and is worth recording: C6 reported a
lost line twice before the oracle was right. The seed padded the file to the
threshold mid-line, so the first line written after it was glued onto the pad and
stopped matching the line shape - indistinguishable from a line rotation lost.
The seed ends its line now.
