# T1820 - cli-focus-policy K fails: +new-window --focus=true on an existing target no longer activates it

## Summary

Found during T1806 (2026-10-11). test\win32\cli-focus-policy.ps1 section K fails twice in a row, and also fails with HEAD (a1585e8b4) code with no T1806 change in place: 'K: an existing target with --focus=true is activated (active=<other>, want <w2>)'. The guard was stamped green at acfe7cb72, so the likely cause is in 375846ed6 (T1804 restart: spawned children name the caller's desktop explicitly) or in the harness timing (900ms settle). Bisect between acfe7cb72 and a1585e8b4, then fix and re-stamp the guard.

## In plain terms

Asking Ghoztty from a script to bring an already-open window to the front
(`+new-window --target=<name> --focus`) did nothing at all whenever Windows
decided another app owned the screen. Now the window at least becomes
Ghoztty's own front window, so switching back to Ghoztty lands on it, the way
Mac makes it the key window even when it cannot steal focus.

## Root cause

Not a regression in T1804: a build of acfe7cb72 (the green stamp's commit)
fails K identically today. `focusTarget` raised with `SetForegroundWindow`
only. Windows refuses that call whenever focus-steal prevention is in force -
here the user's foreground was held by another app (an OpenWith dialog, filed
as T1823) and the foreground lock timeout on this box is 2147483647 ms, i.e.
never expires - and a refused call left the existing window not even
Ghoztty's active window. The stamped green run was taken under a foreground
state that happened to grant it. A NEW window (arm J) passed regardless
because showing it activates it within the app's own queue.

Fix: `raiseWindow` in `IpcHandlers.zig` follows `SetForegroundWindow` with
`SetActiveWindow`, unconditionally (a no-op when the raise landed; asking
whether it landed would compare the foreground window, which the T730
window-active-audit forbids because it answers "no" forever off-desktop). That activates within our own queue only - it
never takes the foreground from the user's app and does not raise in a
background queue (so the "never pull focus" contract is intact).
