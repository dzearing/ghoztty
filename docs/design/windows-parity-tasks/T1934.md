# T1934 - Updates download but never install: the offer is shown once and never again, so a long-running Ghoztty sits on a staged MSI for weeks

## In plain terms

Ghoztty downloaded every new release but never installed one. It waited for
a click on an update offer that it showed only once, so the user stayed on a
September build for six weeks. Updates must install by themselves.

## Summary

User report (2026-10-14): "why haven't we updated ghoztty here", then "it IS
NOT UPDATING", then the directive: "you should be rebooting the session and
making sure updates happen automatically".

Evidence (`%LOCALAPPDATA%\ghoztty\ghoztty.log`, app pid 24292, up since
before 2026-10-10, version `1.36.12+82b87b0d2` from the Sep 5 install):

- Every hour: `update available: current=1.36.12... latest=win-v1.39.7`
  followed by `update check: win-v1.39.7 already offered; not re-notifying`.
- `win32_update_install: update download: staged ...` for 1.39.5 (10-13),
  1.39.6 (10-13) and 1.39.7 (10-14). No apply attempt anywhere in the log.
- `%LOCALAPPDATA%\ghoztty\updates\` held about 800 MB of staged MSIs back to
  1.36.37, none of them ever applied or pruned.

So the version check and the download both work. The defect is the policy:
applying requires a click on an offer shown once, and nothing ever asks
again.

Manual recovery this session (2026-10-14 16:31): sidelined the running
`ghoztty-agent.exe` (`.bak-20261014-163100`), then ran
`msiexec /i Ghoztty-1.39.7-x64.msi /qb-! /norestart`. Restart Manager closed
the app (`restart manager asked us to close for an update; exiting`) and
T1204's RegisterApplicationRestart reopened it as 1.39.7 eight seconds
later. Every session survived in the still-running Sep 25 agent. **That is
the proof that an automatic apply costs the user nothing when session
persistence is on.**

### Required behavior (user directive)

1. **Apply automatically.** Once a release is staged and verified
   (`update_apply.looksLikeMsi`), install it without a click. Do it the way
   this session did by hand: sideline the agent image, run msiexec, and let
   Restart Manager close and reopen the app.
2. **Pick the moment so it does not interrupt typing.** *Assumption
   (recorded, not asked):* apply when the user has been idle for a few
   minutes (`GetLastInputInfo`) and the foreground app is not fullscreen
   (T1795's presence predicate), or at the next app launch, whichever comes
   first. Never wait for a click. A hard cap applies (for example 24 h after
   staging): apply at the next idle moment no matter what.
3. **Persistence off.** An apply closes shells, so it still asks, but the
   question comes back every day instead of once, and launch-time apply
   happens before any shell starts.
4. **The agent follows the existing rules** (`docs/claude/sessions.md`). A
   compatible older agent stays running, and is replaced when no sessions are
   live. An incompatible one goes through the mandatory-update dialog.
5. **Prune old staged MSIs:** keep only the newest staged package and the
   one that is installed.
6. **Say what happened.** After an automatic apply, the reopened app shows
   the existing "Ghoztty updated" notice (`update_reopen.zig`).
7. **Mac parity:** Sparkle auto-install on the Mac side. Check whether Mac
   already installs automatically. If it does not, file the `seat: mac`
   half.

## Validation criteria

- [ ] Unit tests (none lane): the apply-timing policy (idle, fullscreen,
      cap, launch, persistence off) as a pure function.
- [ ] On-box script (test desktop, no SendInput, never the user's install):
      a dev install at version N with a staged N+1 and persistence on is
      updated with no click. The app pid changes, the version is N+1, and
      the session ids and scrollback markers are unchanged.
- [ ] Negative control: with the auto-apply switched off, the same run stays
      on N (this is the current behavior, made visible).
- [ ] Persistence off: no silent apply. The prompt reappears on the next
      day's check (time injected).
- [ ] The staged directory is pruned to at most two packages after an apply.
- [ ] `floor-lane.ps1 -Lane all` and `ipc-p1/p2/p3` green.
