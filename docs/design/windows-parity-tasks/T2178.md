# T2178 - Delivery .bak generations grow without bound: 3 GB beside the Desktop portable and 3 GB on the share after 39 deliveries

## Summary

deliver-windows-build.ps1 keeps every .bak-* generation and only OFFERS -PruneBackups (deletion is user-gated). After T2174 the Desktop portable held 39 generations / 3.05 GB and the share 38 / 3.02 GB. Surface the pile somewhere the user reads (digest or dashboard) with the one command that trims it, or get a standing retention answer from the user so deliveries can prune to N on their own.

## In plain terms

Every delivery to the Desktop portable copy and the network share keeps a backup
of the files it replaced, and nothing ever cleaned them up: 6 GB had piled up
with nobody told. Now the daily install check measures the pile and, once it
passes 1 GB, says so in every loop turn and in the morning digest, with one
command that trims it to the newest three. Deleting stays the user's call.

## Goals

- [x] the read-only audit measures the `.bak-*` pile per location
- [x] a `BACKUP PILE` line with the trim command, in the claim every turn and named in the digest
- [x] a prune-only mode, so trimming does not first add another delivery generation

## Validation criteria

- [x] Audit reports the pile and the one command, read-only, verdict unchanged - G13a-G13d of `test\win32\deliver-windows-build.ps1` (ALL PASS, 162 assertions, 2026-11-24); real run: `BACKUP PILE: 6.1 GB in 3 location(s), up to 39 delivery generation(s)`.
- [x] Quiet under the threshold (negative control) - G13e.
- [x] `deliver-audit.ps1` relays it into the claim, fresh and cached - G13f/G13g.
- [x] `-PruneOnly` refuses without a keep count, deletes nothing under `-DryRun`, keeps exactly the newest N - G13h-G13l; real `-DryRun` would free 5.6 GB.
