# T2509 - Composition step 4b: the desk, card shadows, corners and rims become the bottom chrome visual - PaneDesk's composed buffer drawn into a CompositionSurface with dirty-rect updates instead of BitBlt into the window DC

## Summary

T2468 split, part b; depends on 4a. The GDI desk blit is skipped when the visual is live. Oracle: WGC ghost capture of the desk matches today's GDI pixels (tolerance for rounding) on opaque and translucent windows, and a divider drag updates only the moved rects.

## In plain terms

The coloured desk around the terminals - with every card's shadow, rounded
corners and rim - was painted by hand into the window each time anything moved.
With the compositor switch on (`GHOZTTY_COMP_CHROME=1`), it now goes to the
system compositor instead, and only the part that changed is sent each time.
It looks exactly the same; it is the base the smooth resize and fold work
builds on. The switch is still off by default.

## Goals

- [x] The desk is the compositor layer's picture on an ordinary (opaque) window, and the window stops painting it by hand
- [x] Only what changed goes up: the rectangles a moved card reaches, the busy-light rings, the strip names
- [x] Anywhere something else is still hand-drawn over the desk (a hero tab, rearrange header bands, a see-through window) the desk stays hand-drawn, so nothing disappears under it
- [x] On screen, the compositor's desk matches the hand-drawn one pixel for pixel

## Design (2026-10-31)

`PaneDesk` keeps composing into its CPU buffer exactly as before (the T2467
pattern: upload the existing pixels first, port painters to Direct2D later). A
new hook, `PaneDesk.Sink` (the same shape as the `Names` hook), replaces the
blit when set: it is handed the whole buffer plus the rectangles that changed
- the partial compose's rects, every light ring's strips before and after, and
the laid names - or null for all of it. `chrome_comp.Host` carries the desk
visual: an `IDCompositionSurface` (BGRA, `DXGI_ALPHA_MODE_IGNORE`, since the
buffer's alpha byte is coverage for the translucent blend, not transparency),
placed at the content area's origin and clipped below the caption the way the
GDI blit was (`max(area.top, chromeHeight)`); each rectangle is one
`BeginDraw(rect)` + `UpdateSubresource` + `EndDraw`, one commit per paint. A
new size or a fresh host (device loss) uploads the whole buffer.

`Window.deskOnVisual` decides per paint. Eligible: host up, opaque, no hero
tab, no rearrange header, not the debug test fill. Otherwise the visual is
dropped, the desk memo forgotten and the area invalidated, so the very next
paint is a whole GDI blit. `WM_PRINTCLIENT` paints the desk into the caller's
DC and forgets the memo so the visual catches up. `paintDeskUnderPanes` is
skipped while live (the visual already lies under every pane), and busy-light
frames upload their strips. A failing step logs `chrome desk visual failed at
<stage>` and parks that host's desk on GDI. The drag-perf line gains
`desk_uploads_full/rect/rect_px`.

Translucent windows were scoped out to T2541: the visual composes over the
window's own pixels, so a premultiplied desk needs those cleared first.
