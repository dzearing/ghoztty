# T2601 - A terminal frame at a new size during an edge drag stalls ~0.75 ms on its first synchronous GL call (any call - a glGetError probe takes it over from the uniform upload); a glFlush at draw-begin does not hide it

## Summary

T2598 step 2 split the `synced` stage (target-ready -> synced in
`src/renderer/generic.zig`) with stamps between each upload, ReleaseSafe,
CHROME+PRESENT+NOREDIR+RESIZE_TRACE, idle box. All of the new-size excess
(~0.8 ms) sat on `frame.uniforms.sync` - a ~200-byte `glBufferSubData` - and
none on the cell uploads. A `glGetError` probe placed before it took the whole
stall over (probe 1.00-1.12 ms new vs 0.26-0.28 same; the uniform upload fell
to 0.25), so it is the frame's first synchronous GL round-trip, not the
buffer. A `glFlush` at `draw-begin` (`GHOZTTY_GL_PRIME`, four alternating
arms) did not move it.

It is not plain idle time: same-size frames after a 16+ ms gap did not stall
(n=3, thin), and new-size frames drawn under 1 ms after the previous present
did not either (0.34 ms, n=9). It shows on new-size frames after a 4+ ms gap
(n=107), the gap in which the UI thread does the window's own D3D/DComp work
for the resize step. Candidates: the GL driver's command thread parked and
woken by the first sync call, or the GL context waiting on GPU work the UI
thread's resize step queued (the interop/swap chain share the device).

Do: identify the GPU/driver on the box, try the same probe with the driver's
threaded optimization off (a per-app driver profile, for the experiment only),
and look at GPUView/ETW (`xperf -on ... DX`) across one drag step for what the
render thread waits on. Each stamp on the render trace costs ~0.25 ms of its
own (the log line), so keep stamps few.

## In plain terms

During a window-edge drag the terminal loses most of a millisecond waiting
for the graphics driver before it can start each new-size picture. This finds
what it is waiting on and whether it can be avoided.

## Goals

- [x] name what the first GL call waits on: the pane WINDOW the context was current on. A window-edge drag resizes that window, and the driver revalidates the resized drawable on the context's next synchronous call (inferred from the A/B below; the driver internals are not observable without ETW, which needs elevation)
- [x] remove the wait: already removed by T2788 (7b8df1fbc3, 2026-11-08), which put a composition pane's context on a hidden 1x1 helper that never resizes

## Validation criteria

- [x] resize trace: the new-size frame's first GL round-trip within ~0.2 ms of a same-size frame's, alternating A/B on one build (edge-drag-rate.ps1 -Trace, Debug @b7027f38d, GHOZTTY_PANE_GL_HELPER 1/0/1/0: new-size gap>=4ms sync median 0.045/0.042 ms helper on vs 0.778/0.807 off; same-size 0.10-0.14 both arms. Now asserted as F of edge-drag-rate.ps1 -Trace: PASS 0.043 vs 0.103; -NegativeControl FAIL 0.748 vs 0.100)
- [x] floor lanes, comp-present.ps1 and comp-chrome.ps1 stay green (no product code changed, test-only. Harness floor scoped run green after registering the new seam in seam-audit.registry.json. Plain edge-drag-rate is red on its pre-existing flaky C budget, filed T3850 and guard-acked)

## Outcome (2026-11-26)

Already fixed by T2788 before anyone came back to it. The stall was never
GPU work or the driver's command thread in general: it was the context being
current on the pane's own window, which the drag resizes. Same Debug build,
background test desktop, four alternating arms, row3 + viewer scenes:

| arm | new size, gap >= 4 ms (median sync) | new size, gap < 1 ms | same size |
|---|---|---|---|
| helper on #1 | 0.045 ms (n=43) | 0.165 | 0.100 |
| helper off #1 | **0.778 ms** (n=33) | 0.263 | 0.102 |
| helper on #2 | 0.042 ms (n=41) | 0.152 | 0.095 |
| helper off #2 | **0.807 ms** (n=37) | 0.255 | 0.099 |

The helper-off arm reproduces the filed ~0.75 ms exactly, the shipped arm
removes it. ETW/GPUView and a driver-profile threaded-optimization A/B were
not done: the session is not elevated, and the driver profile is the user's
global setting. Neither is needed now. A window reused from the pane pool that
already carries a pixel format (T3739) still keeps its context on itself, so
it would still pay this; that only happens to a window that once fell back to
SwapBuffers.

Deliverable: assertion F in `test/win32/edge-drag-rate.ps1 -Trace` keeps it
from coming back, with `-NegativeControl` proving it can go red.
