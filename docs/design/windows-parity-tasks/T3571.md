# T3571 - Linux L11i: a hidden or minimized GTK window stops animating and redrawing, while its activity state and notifications keep running

## Summary

Port docs/reference/background-windows.md: work that only matters to the eye runs only where someone can see it - terminal frames, titles that change often, animations and repeating timers pause for a window that is minimized, on another workspace or fully covered, while state (idle/busy/needs_input, notifications, banners) never pauses. GTK translation: drive the core occlusion call from GdkToplevel state (minimized/suspended, GDK_TOPLEVEL_STATE_SUSPENDED on Wayland) and widget mapping; Wayland reports suspension where the compositor supports it, so record what WSLg reports. win32 counterpart: occlusion.zig. Acceptance measures CPU/frames of a backgrounded busy pane.

## In plain terms

On Linux, a terminal in a background tab, or in a window that is minimized
or covered, kept redrawing for nobody: a busy program there cost as much CPU
as one on screen. Now it stops drawing until you look at it again, then shows
everything that happened at once. Its work, its activity marks and +list keep
going the whole time, and a hidden window's title still catches up within 5
seconds.

## Goals

- [x] a pane nobody can see (background tab, minimized/suspended window, hidden stacked pane) stops building frames
- [x] it catches up once when it shows
- [x] a hidden window holds a changing title; lands it on show or within 5s; +list reads it at once
- [x] state (+set-state, activity suffix) never pauses
- [x] record what WSLg's compositor reports
