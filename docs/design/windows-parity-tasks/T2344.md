# T2344 - A failed msiexec install is told by the reopened app in its own window, not by the detached applier's ownerless modal nobody sees; an automatic install that fails says so in a balloon and on the menu row

## Summary

Split from T2322 (user report 2026-10-26: 'i click install and restart. NOTHING HAPPENS'). The applier (update_install.run) raises its failure modal from a DETACHED, windowless process with no foreground right, after relaunching the app - so it opens behind the reopened terminal and on 2026-10-26 nobody saw it (T2321 bounded it to 10 minutes). Fix: the applier writes a failure marker (code, log path, from-version, manual/auto from an env var set at arm time) BEFORE relaunching and shows its own modal ONLY when the relaunch failed; the reopened app consumes the marker at startup (beside announceUpdateReopen) and shows describeFailure in a ConfirmDialog OWNED by its first window for a manual install, a balloon for an automatic one, and in both cases sets App.update_last_install_failed so the menu row reads '(last try failed)' (the flag/label landed in T2322). Rework test/win32/update-failure-visible.ps1 arms A/B/F: the dialog is now the reopened app's (Wait-Dialog on the sandbox exe's pid), and F becomes 'the applier exits at once once it has handed the failure over'.

## In plain terms

When an update failed to install, the message saying so came from a hidden
helper program, and it opened behind the terminal it had just reopened, so
nobody saw it. Now the reopened terminal says it, in a dialog attached to its
own window when you clicked Install, or in a notification when the update was
automatic. Either way the update menu item also says the last try failed.

Mac parity: the Mac build's Sparkle updater already reports a failed install in
its own in-app alert, so the Windows build now matches it and no Mac task is
needed.

## Goals

- [x] the applier hands the failure to the reopened app with a marker written before the relaunch
- [x] a clicked install that fails is told in a dialog owned by the reopened app's window
- [x] an automatic install that fails is told in a balloon, and no dialog
- [x] both set the "(last try failed)" menu flag
- [x] the applier raises its own (bounded) dialog only when the relaunch failed

- [x] Marker format, report spec and notice decision unit-tested (`zig test src\apprt\win32\update_apply.zig`: 31/31, seven new T2344 tests; win32 lane filtered on T2344 green).
- [x] A clicked install that msiexec rejects: the applier exits at once, the reopened app raises "Ghoztty could not finish updating" owned by its terminal window, the dialog stays, and the marker is consumed (update-failure-visible.ps1 A0-A13).
- [x] With no report spec (an applier driven by hand) the failure is still a click's dialog, and the 1618 collision is named in words (B1-B7).
