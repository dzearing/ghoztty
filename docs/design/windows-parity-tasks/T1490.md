# T1490 - A survivor of the clean-slate kill unwinds the script instead of printing SETUP FAIL

## In plain terms

A test run that finds a leftover copy of the app still alive now stops
instead of blaming the app - which is the point of T688 - but it stops the
ugly way: a raw PowerShell error with a stack trace, in the middle of setup.
Whoever is watching gets the right facts wrapped in the wrong shape, and it
does not look like the suite's other setup failures.

## Summary

T688 made `Stop-RepoGhoztty` (`test\win32\lib\CleanSlate.ps1`) THROW when a
path-exact process outlives the stop deadline, naming the surviving pids. That
is the correct verdict - the box is not clean, so nothing measured from there
means anything - but the delivery is an unhandled exception: the calling script
unwinds, prints a PowerShell error record, and exits with whatever the host
decides, rather than the one-line `SETUP FAIL: <reason>` shape every other
setup refusal in `test\win32\` uses.

Two places are worth converting:

- `Reset-GhozttyTestState` (same file) calls it on the pre-fixture path, so the
  throw lands before the script has printed anything at all.
- the 50 `Kill-RepoInstances` wrappers, which are one-line pass-throughs and
  could carry the report.

Filed from the T688 turn; not urgent, because the honest failure already
happens and this is about how it reads.

## Validation criteria

- [ ] A survivor that outlasts the deadline produces a single
      `SETUP FAIL: ...` line naming the surviving pids, not a PowerShell error
      record.
- [ ] The exit code is the suite's setup-failure code, not a host default.
- [ ] `test\win32\cleanslate-audit.ps1` section D asserts the shape, so the
      report cannot regress to a bare throw.
