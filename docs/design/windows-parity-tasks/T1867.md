# T1867 - The soak scripts' Stop-Tree can kill a user's own program: its family walk adopts any process whose stale parent pid matches a family member (T1840's flaw, in a kill path)

## Summary

scripts\soak-daemon.ps1 Stop-Tree (~l.320) and scripts\test-binary-soak.ps1 Stop-Tree (~l.700) kill the root FIRST and then walk a fresh snapshot by ParentProcessId alone. Windows reuses pids and never rewrites ParentProcessId, so any long-lived process whose real parent died before a family member was handed that pid (T1840: the user's Spotify) joins the family and is Stop-Process -Force'd. Fix: capture CreationDate for every family member as it joins (root's before the kill) and adopt a child only if it is younger than the member it names, the T1840 guard in scripts\floor-lane.ps1 Get-ProcessTree. Also audit go-loop-pane-probe.ps1, loop-session.ps1 and test\win32\lib\PaneIdle.ps1 walks (read-only, lower stakes). Validation: synthetic-row test on each kill walk with a negative control, like floor-lane-leak-sweep arm 15b; soak-daemon and test-binary-soak harnesses stay green.

## In plain terms

When the background test runners clean up after themselves, they kill every
program "descended" from the one they started. Windows recycles process
numbers, so a program the user started days ago could look like a descendant
and get killed too. After this, cleanup only kills programs that were
actually started after (and by) the thing being cleaned up.
