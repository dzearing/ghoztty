# T849 - the go-loop cannot reset its own context when no Ghoztty app is running, and only the 45-minute watchdog notices

## Summary

Found closing out **T478**, at go.md step 7. The turn was complete and pushed;
`/reset-context` then reported `FAILED: not in a Ghoztty pane`. It was right:

```
ghoztty +read --name=$GHOZTTY_PANE_ID  ->  No running Ghoztty instance found.
Get-Process ghoztty*   ->  only ghoztty-agent.exe (pid 22664)
pipes                  ->  \\.\pipe\ghoztty-agent-David, four ghostty-pty-*
```

The **app** was gone; the **agent** was still hosting this session's ConPTYs, so
the Claude session was alive, healthy, and detached with no UI to type into.
That is session persistence working exactly as designed — and it is also the one
state in which the loop cannot perpetuate itself, because every reset path ends
in "send keys to a pane".

No `Application Error` for `ghoztty*` in the preceding 12 hours, so the app
exited rather than crashed (a closed window, or a delivery restart that did not
come back). The watchdog was alive and ticking, which means the loop does
recover — after up to ~45 minutes of dead time, which is the safety net doing a
job the reset should not have handed it.

## In plain terms

The terminal window was closed while the assistant was still working in it. The
work itself was fine — it finished and shipped — but the way it normally starts
its next task is by typing into that window, so it had nowhere to type and had
to stop and wait for a supervisor to notice several minutes later.

## Goals

- [x] A turn that ends with no app running gets the loop moving again in
      seconds, not in up to 45 minutes — `go-loop-exec.ps1 recover`, run from
      go.md step 7 when the reset says it has nowhere to type
- [x] Whatever the recovery is, it must not surprise the user by opening windows
      they did not ask for while they are away from the machine — see the
      judgement call below: the recovery is the last-resort branch that already
      opened a window, and it fires only behind open tasks and a stalled loop

## Details

- The detection half already works and is cheap: the reset skill's probe chain
  falls through to `FAILED`, and `Get-Process`/pipe enumeration distinguishes
  "app gone, agent alive" from "not in a Ghoztty at all" in one call.
- Candidate recoveries, needing a judgement call about the second goal:
  re-launch the app and re-attach this session (the agent exists precisely so a
  session survives to be re-attached); or leave the app alone and have the turn
  signal the watchdog to act NOW rather than on its next stale-heartbeat sweep.
  The second is the smaller promise and does not touch the user's desktop.
- Whatever lands, `scripts\go-loop-watchdog.ps1` is where the recovery belongs,
  not the reset skill: the skill is shared with non-loop sessions, where "no app
  is running" genuinely does mean "ask the human".

## Validation criteria

- [x] With the app killed and the agent left running, a turn ending in
      `/reset-context` reaches a fresh session (or a running watchdog re-entry)
      within a minute, proven on the box. Verified through the decision and the
      diagnosis rather than by killing the user's terminal: H11/H12 drive the
      watchdog against a stand-in ghoztty that answers the way the CLI does with
      nothing listening, and it chooses `launch-app` with the resume shim
      instead of the `+new-window` that cannot work there; H15/H16 drive
      `go-loop-exec.ps1 recover` against both stand-ins and pin its two verdicts.
      The action it takes is the same `+new-window`/shim re-entry that sections
      I/J already prove end-to-end against a live GUI.
- [x] The existing `test\win32\go-loop-guard.ps1` stays ALL PASS, and gains an
      arm for the app-gone case — six of them (H11-H16), plus the app-up
      negative control that makes the probe's two answers differ in exactly the
      thing under test.

## The judgement call (recorded, not filed)

Goal 2 asks that the recovery not surprise a user who is away from the machine,
and launching an app on an unattended desktop is a real cost. It is taken
anyway, and this is not a decision for the user's feed: go.md 5b files a
decision only where a mac->win translation produces experiences the user could
tell apart, and this is the loop's own supervision.

The reason it is allowed: the branch being fixed ALREADY opens a window. It is
the watchdog's last resort, reached only with open tasks for this seat and a
turn that has stopped moving, and the window it opens is the loop's own. Before
this change that branch simply failed - `+new-window` is IPC, and there was
nothing to receive it. Launching the app is that same promise with its
precondition satisfied, not a new promise. The alternative considered and
rejected was "signal the watchdog to act NOW and open nothing", which recovers
in seconds only if the watchdog can then do something - and in this exact state
it cannot, for the same reason the reset could not.
