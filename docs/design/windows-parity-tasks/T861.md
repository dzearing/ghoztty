# T861 - A bare CLI set-status still journals an unattributed transition - stamp a default source (user, process, cwd) when -SourceNote is omitted so every reopen carries a receipt

## In plain terms

When a task changes state, the tracker writes a line into that task's history
saying so. If the change came from the dashboard, the line says the dashboard
did it; if it came from a command typed in a terminal, the line said nothing
about who or what made the change. So the next person reading the history had to
guess, and once that guess cost a whole session's opening minutes. Now every
change names its author, whether or not anyone said who they were.

## Summary

T564 made every status transition journal itself, and the dashboard always attributes its own writes - but a bare 'parity-tasks.ps1 set-status Tnnn -Status todo' from a shell journals 'status: a -> b' with no '(by ...)' at all. On 2026-08-15 exactly that shape reopened T443's armed watch at 12:35 and the next turn spent its opening minutes ruling out the dashboard, scripts, and the previous session before it could decide whether to honor the reopen (it did, under D27's crash-recurred condition). The D27 lesson was that a reopen must carry its own receipt; the CLI is now the only unattributed path. Fix: when -SourceNote is omitted, synthesize one from what the script can see for free - David, the parent process name, the working directory - e.g. '(by cli: David, from pwsh)'. Zero friction for the caller, and the journal line stops being a whodunit. Acceptance: extend the set-status section of test\\win32\\parity-tasks-seat.ps1 with an omitted-SourceNote case asserting the synthesized attribution appears.

**Re-verified 2026-09-18** (the `CHECK FIRST` prompt): still real.
`scripts\parity-tasks.ps1` wrote `(by ...)` only when `$SourceNote` was
non-empty, so a bare CLI flip journaled an anonymous line. None of the nine
commits that had touched the file since it was filed changed that.

**What landed.** `Get-DefaultSourceNote` synthesizes an attribution from the
user (`$env:USERNAME`), the parent process (`Win32_Process` -> `Get-Process`)
and the leaf of the working directory, and `set-status` falls back to it when
`-SourceNote` is omitted: `status: todo -> done (by cli: David, from pwsh, in
ghoztty)`. Everything it reads is free and every read is wrapped, so an
unreadable parent degrades to `from unknown` rather than failing the flip.

**The fallback is attribution, not evidence.** It is computed at journal time,
*after* the T892 un-block gate, so a bare flip out of `blocked(...)` is still
refused - "David, from pwsh" is not a claim that a park condition was checked.
An explicit `-SourceNote` still wins outright, and `-NoNote` still writes
nothing.

**Found on the way** (and filed, not fixed here): section O of the harness
probed dashboard liveness with `/api/data` on a 5s timeout, and that endpoint
now takes ~58s against the real tracker - so the section went red over server
performance rather than over anything it tests. The probe now asks `/` (a file
read), which is the question it meant to ask, and the slowness itself is
**T1660**.
