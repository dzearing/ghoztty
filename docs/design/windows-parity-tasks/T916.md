# T916 - The link-paths row walk samples one row in three, so a probe can miss every line it is aimed at

## In plain terms

A test that is supposed to click twelve different lines of a terminal pane was
only finding text on about a third of them, and could miss every one of them
outright. Its answers were real where it landed, but nothing checked that it
had landed — so a problem that only shows on some lines would slip through,
and when the test did miss, it blamed the product.

## Goals

- [x] Find out, from a measurement rather than a theory, which row each probe
      really reaches
- [x] Make the walk unable to miss the lines it is aimed at
- [x] Make "the walk walked" an assertion the script scores, not an assumption
- [x] Put T802's jitter arm back on the exact string it was written for

## Summary

Found while adding T802's double-click arms to
`test\win32\terminal-link-paths.ps1`.

`Get-Column0Selections` walks rows by computing a y from the surface's client
rect (`Get-TestWindowRect -Client`, which returns the client area in SCREEN
coordinates) and handing it to `Send-TestMouse -Y`, which is also screen. That
should be right — but an instrumented Debug build logging the position the
core resolves for each press showed the app receiving a y about **39.4x** the
screen y that was posted, at a constant ratio across samples:

```
posted screen y   237     292     348
core pos.y       9328   11492   13696     (ratio 39.36 = 100/2.54, every row)
```

x came through unscaled (`4` in, `4` at the core). A y that large is below the
pane, so `posToViewport` clamps it and every probe resolves to the bottom
row(s) — which is why an 8-row walk returns one or two unique strings, and why
the same points can answer differently across two passes: when a probe's
ctrl+c finds no selection the performable binding falls through to the shell,
`^C` prints a fresh prompt, and the screen scrolls under the next pass.

That drift is what made T802's jitter arm (section E) read as a product
failure while the instrumented build showed the core doing exactly the right
thing (`samePin` firing, selection preserved). The arm was rewritten to assert
selection GRANULARITY rather than one exact string; it should go back to
asserting the string once the walk really walks.

## What it actually was (2026-09-20)

The y-scaling theory above is wrong, and the evidence that says so is a ruler
rather than an argument. Fill the pane with `R1`..`R60`, one marker per row,
then probe every 10px down the client rect and print what each probe selects:
the mapping is strictly linear at ~26px per row at dpi=120, monotone from the
first content row to the last, the blank row answers with no selection, and
only a y past the last content row answers with the bottom prompt. No 39.4x,
no clamp. `Get-TestWindowRect -Client` + `Send-TestMouse` hits the row it is
aimed at, and the jitter double-click walks identically — so T802's `samePin`
guard has been live the whole time.

The real defect is **aliasing**. `Write-Lines` sent `echo <text>` once per
line, which leaves the screen as a repeating THREE-row block — the echoed
command, its output, a blank — so only one row in three carries the text. A
fixed-pitch walk beats against that period: twelve probes are ~1.5 rows apart
and section E's eight are ~2.1, so which phase each probe lands on depends on
where the content happened to stop, and `Select-Object -Unique` then collapses
whatever it did hit into one or two strings. Section E drew eight prompt rows
in a row, which is how a correct build came to look like a product failure.

The cross-pass drift has the same origin: a probe that lands on a blank row
selects nothing, its ctrl+c falls through to the shell as `^C`, cmd prints a
prompt, and the screen scrolls under the next probe.

The fix is two-sided. One `for /l` command now fills EVERY row, so no probe
can miss and nothing scrolls; and a new section W walks the numbered ruler and
asserts the walk reaches content rows, many of them, in order, without
jumping — so a regression to one-row sampling fails loudly instead of passing
quietly on a screen that cannot tell the difference.

## Validation criteria

- [x] The cause is named with evidence — and it is NOT the y scaling this card
      assumed. A ruler screen (`R1`..`R60`, one marker per row) probed every
      10px down the client rect gives a strictly linear mapping at ~26px per
      row with no clamp anywhere, so the idiom is correct. The defect is
      aliasing between the probe pitch and the 3-row block `echo` leaves.
- [x] A probe at row i demonstrably lands on row i — section W walks the ruler
      and asserts the answers are content rows, at least 8 distinct, monotone,
      never jumping more than 2 rows, and traversing 10+ rows
- [x] T802's section E goes back to asserting the exact URL string
- [x] `test\win32\terminal-link-paths.ps1` stays ALL PASS — 35 assertions, up
      from 23, and `-NegativeControl` still scores its single red
- [x] Any other script using the same client-rect-to-Send-TestMouse idiom is
      swept: `keybinds-t01.ps1`, `notification-click-real.ps1` and
      `split-divider.ps1` are the only other users of a fraction-of-a-rect y,
      and all three pick ONE point inside a region rather than walking a
      periodic screen, so the aliasing cannot apply to them
