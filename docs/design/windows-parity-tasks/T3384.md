# T3384 - Linux: a closed pane or a +rearrange-omitted pane can be undone (Ctrl+Shift+Z), as on Mac and Windows

## Summary

The GTK app closes a pane at once: +close and a +rearrange layout that leaves a pane out end it with its shell, and there is no undo. Mac (Rearrange Layout / close undo) and win32 (T2234, CloseUndo/LayoutUndo, undo-timeout default 5s) hide the pane and keep its shell until the timeout, and Ctrl+Shift+Z puts it back with its name. Port that: a per-window undo stack in the GTK frontend, the omitted/closed pane hidden and out of +list until undo-timeout expires, undo/redo bindings, and the shared layout_undo logic where it fits. Acceptance: a test/linux script that rearranges a pane out, checks its shell is alive and it is absent from +list, undoes, and checks it is back by name.

## In plain terms

On Linux, closing a pane by mistake - or rearranging a window with a script that leaves a pane out - used to end that pane and whatever was running in it, for good. Now, as on Mac and Windows, the pane disappears but keeps running for a few seconds, and Ctrl+Shift+Z puts it back exactly where it was, still running and still answering to its name; Ctrl+Shift+Y redoes the close.

## Goals

- [x] a closed pane is parked, not ended, for `undo-timeout`, and Ctrl+Shift+Z restores it in place, by name, same shell
- [x] a `+rearrange` that leaves panes out (or only moves them) is undone by Ctrl+Shift+Z, and redone by Ctrl+Shift+Y
- [x] the shell ends when the undo expires; `+close --force` is never undoable; an undo never crosses windows
- [x] a Linux test proves all of it headless (and a negative control proves the test can fail)
- [ ] a tab or window close is undoable too - filed as T3590
