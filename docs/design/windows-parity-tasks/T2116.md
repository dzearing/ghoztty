# T2116 - App keybinds such as Ctrl+D (split) likely do nothing while a viewer's address or find field has focus

## Summary

Found in T2087, from reading the code (not yet reproduced on the box: verify first). On Mac a menu key equivalent (Cmd+D split, Cmd+W close) fires while the viewer's address field has focus. On Windows the main loop routes a nav/find EDIT's keys only to handleEditKey/handleEditChord (viewer_accel.paneChord); any other chord goes to the EDIT, which ignores it. So Ctrl+D from the page splits since T2087, but Ctrl+D with the caret in the address bar does nothing. Fix: after handleEditChord, offer the chord to the owning ViewerPane's binding route (window_chord + bindingChord, NOT zoom, and keeping pageOwns' editing chords such as ctrl+c/v/x/a/z with the EDIT), in App.zig ~2199 and ~2282. Acceptance: viewer-panes.ps1 11d - Ctrl+D with the address field focused splits, Ctrl+A there still selects the text.

## In plain terms

With the cursor in a viewer pane's address bar (or its find box), the app's
keyboard shortcuts - Ctrl+D to split, Ctrl+W to close, and the rest - did
nothing: the text box swallowed them. On Mac they work from there. Now they
work from the text boxes too, while the box's own editing keys (select all,
copy, paste, undo, word-by-word moves and selection) still edit the text.

## Goals

- [x] App keybinds fire from the address and find fields
- [x] The fields keep their own text-editing chords
- [x] Zoom stays with the page content (Mac scopes it to content, the field is chrome)

## Validation criteria

- [x] The defect was real before the fix - negative control: with the address-field hook removed, `viewer-panes.ps1` scored `FAIL T2116 ctrl+d from the address field split the window (4 -> 4 panes)` (1 failure, 202 passed).
- [x] Ctrl+D with the address field focused splits the window - `viewer-panes.ps1` 11d `T2116 ctrl+d from the address field split the window (4 -> 5 panes)`; ALL PASS (203 assertions) via `acceptance-parallel.ps1 run`.
- [x] Ctrl+A there still selects the address - 11d reads `EM_GETSEL` after End collapsed it (control: `sel 23..23`), then `sel 0..23 of 23` after ctrl+a.
- [x] Which chords leave a field is unit-tested - `viewer_accel.fieldOffers` test in the none lane (split/close/tab chords offered; typing, shift-selection, ctrl+A/C/V/X/Y/Z, ctrl(+shift) arrows/Home/End, ctrl+Insert, alt+Backspace, zoom and the pane chords kept).

## Resolution

`viewer_accel.fieldOffers` decides which chords may leave a viewer text
field; `ViewerPane.claimFieldChord` asks the window-chord table and the app
keybind table (`bindingChord`) and posts a claim to the same
`WM_APP_VIEWER_ACCEL` delivery a page chord uses. App.zig's main loop calls it
after `handleEditChord` for both the nav and find EDITs, on WM_KEYDOWN and
WM_SYSKEYDOWN. Mechanism choice (no decision filed): ctrl+shift arrows/Home/End
stay with the field even though the Windows defaults bind ctrl+shift+arrows to
tab navigation from the page, because with a caret in a text box word/line
selection is what a Windows user expects those chords to do.
