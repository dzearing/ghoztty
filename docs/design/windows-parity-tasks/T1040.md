# T1040 - The Activity Monitor guard rows still name one file the panel was split out of, so 13 of its modules and two of its harnesses are unwatched

## Summary

Found while closing T329. scripts\guard-due.ps1 has three rows that mention the Activity Monitor (activity-monitor, activity-selection, activity-monitor-dialed) and between them they name exactly one source file: src\apprt\win32\ActivityMonitor.zig. The panel is 14 files now - activity_actions, activity_borrow, activity_cards, activity_dial, activity_input, activity_layout, activity_machines, activity_paint, activity_probe, activity_probe_conn, activity_procs, activity_rows, activity_sample, activity_view - and until T329 added activity_dial.zig to the dialed row, NONE of them were in any Covers list. So an edit to the sample worker, the card probes, the borrow rule or the painter makes no harness due, which is the state the guard table exists to make impossible. Two harnesses are also in no row at all: test\win32\activity-monitor-remote.ps1 (the BORROWED path and the carousel) and test\win32\activity-monitor-probe-fail.ps1 (the refused-dial arm), so neither has a stamp and neither can ever be reported stale. The work: map each module to the harness that actually exercises it and add the rows, following the tables own convention that a file may appear in more than one row when two harnesses check different claims about it. Verified by reading guard-due.ps1 and listing src\apprt\win32\activity_*.zig, not by grep alone.

## In plain terms

The safety net that says "you changed this part of the Activity Monitor, so re-run its test" was pointing at a file the code had moved out of. Changes to typing in the filter, killing or starting a process, and the per-machine status probes could land without anyone being told to re-test them. Now every one of those files is tied to the test that actually exercises it.

- [x] activity-monitor-probe-fail.ps1 has a row and stamps itself on a green run
