# T784 - A rebuilt tree can produce a ghoztty-agent.exe stamped with an OLDER commit than the app beside it

## Summary

zig-out holds ghoztty.exe at +9672383fb and ghoztty-agent.exe at 20260811-3bbf0eefb from the same build run (found while wiring T281's agent read-back). The agent's baked stamp is what the app's upgrade policy (agent_upgrade.zig) and +sessions --agent both reason about, so a stamp that lags the tree makes both answer for a build that is not the one on disk.

**Re-verified 2026-09-16, and the half that is a defect is narrower than the title.** A stamp OLDER than the app's commit is by design (d04ecc2bb, 2026-07-19): `versionString` in `src/build/GhosttyAgent.zig` keys on the last commit that touched the AGENT's sources, not HEAD, so a release that does not change the agent does not re-stamp it and spuriously report the running agent stale. That part is correct and stays.

What is real is the silent direction. The path list it keyed on named four leaves - `src/agent_main.zig`, `src/remote`, `src/pty.zig`, `src/CommandCore.zig` - and the agent is compiled from 925 tracked files: `src/remote/agent/*` reaches `src/os/main.zig`, `src/terminal/main.zig` and `src/apprt/win32/job_spawn.zig` by relative import, and those reach the rest. A commit to any of them changed the agent's BYTES and left its stamp alone, so `isStale(running, bundled)` (and macOS `LocalAgentManager.agentIsStale`) read two different builds as the same one: the upgrade policy stands down and the user silently keeps an old agent, and T281's delivery gate compares two copies of the same wrong answer and passes.

Fix: derive the stamp from the input set the COMPILER reports (`src`, `pkg`, `vendor`, `dist/windows`) rather than a shortlist anyone has to remember to extend, and add `scripts/agent-stamp-inputs.ps1`, which reads the agent compile's own cache manifest and fails on any tracked input no stamp path covers. A stamp that moves early costs at most an idle refresh (never a live session, since T1056 on win32 and `deferUntilIdle` on mac); a stamp that lags costs the user the fix.

## In plain terms

Ghoztty ships a small background program - the agent - that owns your terminal sessions so they survive the app closing. The app decides whether to refresh it by comparing build stamps, and the agent's stamp was built from a short list of source folders that had stopped matching what the agent is actually built from. So an agent that had genuinely changed could carry the same stamp as the old one, the app would see "same build, nothing to do", and you would keep running the old agent - including past a fix you had just installed. Now the stamp follows everything the agent is compiled from, and a check fails the build pipeline if that ever drifts apart again.
