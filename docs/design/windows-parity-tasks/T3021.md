# T3021 - PA-I07: each session's pty holder polls for shell exit 5 times a second for its whole life, and process-exit and dial waits elsewhere sleep-poll in 50 ms steps (pty_host.zig:330-341)

## Summary

PA-I07 (audit-1, T2962). src/remote/agent/pty_host.zig:328-341 exitPoller loops `child.tryWait()` then `std.Thread.sleep(200ms)`, and after exit lingers in a 500 ms sleep loop (:354). Cost (arithmetic): 5 wakeups/s per session, in the holder processes so invisible in the agent's 5.3/s; 20 idle panes is 100 wakeups/s box-wide. Also pty_holder_child.zig:839-845 waitProcessExit sleeps 50 ms per check (up to 50 ms added to every +close) and dial/dialExisting (:1176, :1190) poll the same way. Fix: WaitForSingleObject on the shell process handle (INFINITE) then a timed condition wait for the linger, ideally on the holder's main thread so the poller thread goes; WaitForSingleObject(holder_proc, 400) for the exit wait; WaitNamedPipeW for the dial. Risk low; keep the reap under PtyChild.mutex. Holder-internal, so old running holders keep polling until their session ends. Windows-only code path. Findings: docs/design/perf-audit/audit-1/I-findings.md.

## In plain terms

Every terminal pane whose session survives an app restart has a small helper
process behind it, and that helper woke up five times a second, forever, just
to ask "has the shell quit yet?". With twenty panes open that is a hundred
pointless wakeups a second, which costs battery and keeps cores from resting.
After this, the helper sleeps until the shell actually exits, and closing a
pane no longer waits up to an extra 50 ms for the helper to be noticed gone.

## Goals

- [x] the holder's exit poller blocks on the shell's process handle instead of polling every 200 ms
- [x] the post-exit linger is a timed condition wait, woken when an owner disconnects, instead of a 500 ms poll
- [x] waiting for a holder to exit on `+close` is one kernel wait instead of 50 ms steps; startup dial and redial pace on the holder's handle so a dying holder ends them at once
- [x] an acceptance check measures an idle holder's real wakeup rate

## Design notes

- The poller waits on a DUPLICATE of the shell handle it owns alone: `PtyChild.terminate` (SHUTDOWN) closes the original, and a wait on a handle another thread closes is a wait on whatever reuses the number. A failed duplicate falls back to the old 200 ms poll rather than never reaping.
- The reap itself still goes through `child.tryWait()`, so it stays under `PtyChild.mutex` as before.
- Dial retries are NOT replaced with `WaitNamedPipeW`: during holder startup the pipe does not exist yet, and `WaitNamedPipeW` returns `FILE_NOT_FOUND` immediately for a missing name, so it cannot wait for a pipe to be created. The retry instead sleeps on the holder's process handle (`WaitForSingleObject(holder, 50)`), which keeps the cadence but ends the wait the moment the holder dies. These are startup/redial-only loops, not steady-state cost.
- Holder-internal: holders already running keep their old poller until their session ends; new sessions get the new one.

## Validation criteria

- [x] an idle holder process shows under 0.5 context switches/s over 60 s (was ~5), measured per holder pid - `test\win32\pty-host.ps1 -IdleSeconds 60` C1: 2 switches across 5 threads in 60 s = 0.03/s (0.07/s on the default 30 s run)
- [x] shell exit is still reported promptly (session close acceptance green) and +close latency does not rise - pty-host.ps1 C2/C3 (a shell exiting with no owner ends its holder at 3.1 s = ~1 s shell + 2 s linger, not before), smoke A9/A10/A16/A17 (EXIT code delivered, holder finishes, terminate leaves nothing); session-shell-exit.ps1, pty-holder.ps1, holder-volume.ps1, sessions-running-cmd.ps1 ALL PASS; +close now waits once in the kernel instead of in 50 ms steps, so it can only get shorter
