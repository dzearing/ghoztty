# T1752 - Command-palette entries a user adds in their config never show up in the Windows palette, and Ghostty's built-in list shows many commands twice

## Summary

Found by T1671. Config.RepeatableCommand.init preloads Ghostty's ~98 default command-palette-entry commands (src/input/command.zig defaults), and an empty 'command-palette-entry =' RESETS to those defaults rather than clearing (cli/args.zig parseIntoField: empty value calls init), so the list a user can build is always defaults + theirs. The win32 palette (Surface.zig filterPaletteEntries) then shows only the first MAX_USER_PALETTE_ENTRIES (64) of it, so every user-added entry past the defaults is silently dropped - measured on-box: 30 entries passed via --command-palette-entry gave user.len=128 and zero matching rows. Second symptom on the same seam: the 64 defaults that DO show duplicate the win32 registry (both 'Change Window Title...' prompt_window_title and 'user:Change Window Title...' sit adjacent at rows 5/6), so the palette lists 145 rows with many commands twice. Decide the model Mac uses (Mac's palette is built from the config list) and translate: likely de-duplicate defaults that the registry already covers and lift the cap so user entries always show. Validation: none-lane test over the merge, and an arm in test\win32\palette-order.ps1 that adds an entry via config and runs it from the palette.

## In plain terms

Commands you add to the command palette in your Ghoztty config never appeared
in the Windows palette, and many built-in commands were listed twice. After
this, every command you configure shows up and runs, and each built-in
command is listed once.

## Goals

- [x] configured palette entries always show (the 64-entry read no longer drops them)
- [x] Ghostty defaults the Windows command list already offers are listed once
- [x] a default with no Windows counterpart still shows, as it does on Mac

## Design

Mac's palette IS the config list (`terminalOptions` in
TerminalCommandPalette.swift), so each command appears once. Windows shows its
own registry (`commands.zig`) plus the config list, and the config list always
starts with Ghostty's ~100 defaults (`RepeatableCommand.init`). Two changes:

- `commands.coversDefault(cmd)`: a config entry EQUAL to a Ghostty default
  (title, description, action) whose action a `.binding` registry row already
  performs is skipped. A user's own entry always shows, even for an action the
  registry has - they asked for that row by name.
- The read cap goes 64 -> 512. The cap existed because each user row composed
  its `user:<title>` history key into a per-row stack buffer; `palette_order.Item`
  now carries `user: bool` and matches the prefixed key in place (`keyIs`), so
  no buffer is needed. A list past 512 logs a warning instead of truncating
  silently.

Confirmed the Summary's reading: an empty `command-palette-entry =` is routed
by `cli/args.zig parseIntoField` to `init` (a reset to the defaults) before
`parseCLI`'s own clear branch is reached, so a user cannot empty the list and
the defaults are always there. The fix does not depend on it either way.
