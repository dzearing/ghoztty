# T2370 - The focused-pane glow's fade tick costs ~15.5 ms of a 16.4 ms frame (it repaints the whole pane desk every tick), so on the vsync frame clock it still drops ~5% of frames and holds the UI thread ~95% busy for the 250 ms fade; paint only the glow ring

## Summary

Found by T2365's harness (`test\win32\frame-clock.ps1`, 2026-10-27). With
every animation on the vsync frame clock, a do-nothing probe subscriber
lands 240/240 frames one period apart, but the focused-pane glow
(`Window.focusGlowTick`, id 0x4647) costs a mean 15.5 ms (max ~20 ms) per
tick against a 16.4 ms period. A tick that overruns the frame makes the next
vblank find the previous frame still in flight, so the glow still skips
~2.5-5% of its frames, and for the 250 ms of every fade the UI thread is
almost entirely busy painting.

Cause: `focusGlowTick` calls `repaintPaneDesk()` - a synchronous repaint of
the whole pane desk - to move a glow ring that occupies a thin band around
one or two panes (T2232 already measured ~15 ms per desk repaint).

Fix: invalidate/paint only the union of the old and new glow rings (or move
the glow onto its own layered/DComp surface, see T2360) so a tick costs well
under a millisecond.

## Validation criteria

- [ ] `test\win32\frame-clock.ps1` reports the glow's `cost mean` under 3 ms, and its `doubled` share at the probe's level (0-1%).
- [ ] The glow still renders identically (existing pane-elevation / focus-glow pixel harnesses green).
