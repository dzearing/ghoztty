# T2382 - Frame capture engine for the T2373 lab: Windows.Graphics.Capture monitor capture cropped to the window rect (so owned layered popups are in frame), free-threaded pool sized for 120 Hz, QPC timestamps, online scoring on a worker with failing frames + a 1% sample written as PNG, and a DXGI Desktop Duplication cross-check that reports composed frames the capture skipped

## Summary

Split out of T2373 (user-directed 2026-10-27: no bleeding during window/pane resize; smoothness measured). See T2373's Summary for the full design; this card is one piece of it.

## In plain terms

To prove the terminal never "bleeds" while you resize it, the lab has to
photograph every frame the screen actually shows. This piece is the camera: it
records a chosen rectangle of the screen at the display's full refresh rate
(120 times a second here), stamps each picture with the moment it was shown,
hands each one to the judge built in T2381, and keeps only the bad ones plus a
small sample. It also counts the frames it may have missed, so a "smooth" score
can never come from a camera that blinked.

## Goals

- [x] Monitor capture cropped to a rect (owned popups stay in frame), borderless, no cursor, the ~60 fps cap lifted (`test\win32\lib\FrameCapture.ps1`, `Start-FrameCapture`)
- [x] Free-threaded pool sized from the refresh rate; QPC stamps that are the frame's display slot
- [x] Online scoring on one worker (a `GfcScorer` delegate), bounded queue with counted drops, failing frames + a 1% sample written as PNG
- [x] Frame accounting: slot accounting on every run, plus a Desktop Duplication accounting run that names the composed frames the capture skipped
- [x] Acceptance `test\win32\frame-capture.ps1` (guard row `frame-capture`)

## Design notes (measured on this box, 120 Hz, 2026-10-28)

- **csc, not Add-Type.** The WinRT projection needs the `*.winmd` files as
  references and Add-Type tries to load each reference as an assembly
  (0x80131047). The engine is C# compiled by the framework's csc.exe into
  `%TEMP%\ghoztty-framecapture\gfc-<hash>.dll`, once per source change.
- **WGC caps at ~60 fps by default**: 167 frames in 3 s while duplication
  counted 345 presents. `MinUpdateInterval` (set by reflection) lifts it.
- **`SystemRelativeTime` is the refresh slot DWM targeted**, an exact multiple
  of 8.333 ms, not the present. It is kept as the frame's display time
  (`Qpc`). Two frames can share a slot; the earlier is marked `Superseded`.
- **A running capture makes DWM compose every refresh**, even on a static
  screen: duplication alone saw 0 presents in 2 s, and ~110/s once a capture
  started. So a refresh with no frame (`SlotGaps`) is a real completeness
  signal on every run.
- **Desktop Duplication beside a capture perturbs it**: DWM missed 5-16% of
  refreshes (capture alone: 0-4%) and each frame arrived ~5 ms later. So
  duplication is an opt-in ACCOUNTING run (`-Duplication`), not a passenger on
  measured runs. T2384 must measure smoothness on capture-only runs and prove
  each cell's completeness with a separate duplication run.
- **Pairing is on arrival time, order-preserving, then a rescue pass.**
  FrameArrived fires a steady ~1.2 ms before duplication's `LastPresentTime`,
  while slot stamps drift against presents by up to a refresh. Equal-stamp
  pairing matched 29 of 167; nearest-neighbour cascaded (46 false skips on
  equal counts); first-fit in order with 0.75-refresh tolerance plus a rescue
  pass (a hidden or unpaired present takes a spare capture frame within 1.5
  refreshes) reads 0 skipped run after run, and a count floor was dropped
  because a same-slot duplicate let it swallow a real skip.
- **The handler-stall positive control is T2384's**, not this card's: it
  needs DWM composing from a moving scene, because on a static screen the
  compositions stop when the capture's buffer is held (the capture is what
  causes them). Here the control removes frames from the LIVE timelines.
