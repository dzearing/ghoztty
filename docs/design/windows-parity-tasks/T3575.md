# T3575 - Linux L12b: the GTK machine chooser's account row signs in and out with Google, and says when the sign-in is kept in a private file because no keyring runs

## Summary

T3341 landed the Linux account store (Secret Service via libsecret, else a 0600 file under XDG_DATA_HOME; relay_account.location() says which) and the sign-in flow core (relay_signin.signIn/signOut) already builds and tests on Linux. What is left is the GUI affordance docs/claude/remote.md names for every platform: the chooser's account row (T3563 builds the chooser) shows the signed-in email + Sign Out, or Sign in with Google... when signed out, runs signIn on a worker thread and posts the outcome back with g_idle_add (win32: MachineChooser.signInAsync), shows the no-client-id sentence when the build cannot sign in, and - Linux-only information the Mac and Windows rows have no need for - says when relay_account.location() is .file (no keyring daemon, the WSL default) so the person knows the credential is in a private file rather than a keyring. Acceptance: a headless-harness script (test/linux/lib/headless.sh) that drives the row signed out, signed in from a seeded store (GHOSTTY_ACCOUNT_STORE), and in both store locations.

## In plain terms

On Linux the "New Remote Window" chooser could show your machines but had no
way to sign in or out: there was no button. Now its top row offers "Sign in
with Google…", shows your email with "Sign Out" once you are in, and - on WSL,
where no keyring runs - tells you your sign-in is kept in a private file only
you can read, and where.

## Goals

- [x] the row signs in with Google (browser flow on a worker) and out
- [x] the words match Windows and the Mac (one shared module)
- [x] an unconfigured build says so instead of showing a dead button
- [x] the Linux-only sentence says when the sign-in sits in the private file
- [x] a sign-in brings back relay windows a signed-out launch had to keep
