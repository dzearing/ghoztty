# T3820 - A new pane joins the OLD WSL shell instead of starting a fresh WSL bash prompt (1.56.36, user P0)

## Summary

User report 2026-11-26, on the newly installed latest release (1.56.36), WSL as the shell: "every time i open a new pane, it is REUSING THE OLD WSL PROCESS!!!!!!!!!! I NEED NEW WSL BASH PROMPTS IN NEW PANES". Every new pane must get its OWN fresh WSL bash (new process, new prompt), never the shell of another pane - open or closed.

### Window reuse stays ON
Pane-WINDOW reuse (T2597, parked HWNDs) is required by the user and is not the cause to remove. Never "fix" this with GHOZTTY_PANE_REUSE=0. A parked HWND must never carry a shell/session with it; if that is what happens, fix the hand-off inside reuse.

### Leads (measure, do not guess)
1. Timing: 1.56.36 is the first release with T3772 (901ecdb632: a split/new tab of a WSL pane starts in that pane's folder - Surface.zig rewrites `remote_command_argv` / `config.command` via applyWslFolder). Also new in the last ~day: T3755 (9989c421f, restore each pane's shell - App.zig/session_layout/restart_shell), T3754 (6b74c8f9f, shell-family folder inheritance), T3752 (Restart Pane with Shell), T3751/T3753 (shell pickers). Bisect across win-v1.56.30..36 with a debug build.
2. Session-agent attach: local panes run through ghoztty-agent (session persistence). Check whether the new pane ATTACHES to an existing agent session (another live pane's, or a closed pane's still parked under CloseUndo/undo-timeout, cf. T1684) instead of creating one - look for `attach: session=` vs a create in the log for the new pane, and whether two panes report the same session id / child pid in `+list --json`.
3. Closed-pane teardown (the user's earlier hypothesis, 2026-11-25): close a WSL pane, wait past undo-timeout, assert its wsl.exe/bash tree is gone and its agent session is ended - a lingering session must never be adopted by a new pane.
4. wsl.exe itself: confirm each pane spawns its own `wsl.exe` (distinct PIDs); `wsl.exe` sharing the distro VM is fine, sharing the bash is not.

### Interim for the user
Until fixed, the previous release (1.56.35) predates T3772; say so in the reply if bisect confirms T3772.

## In plain terms

With WSL as the shell, the user saw a newly opened pane come up on an old pane's shell instead of a fresh Linux prompt of its own. Every new pane must start its own fresh shell, and closing a pane must really stop its shell and free it. The user's own test (open, echo, close, three times over) is now an automated check against real WSL. On this machine it passes, so the defect has not been reproduced yet: we need to know exactly how the user opened the pane and what they saw.

## Findings (2026-11-26, lane b)

Not reproduced on this box, Debug build at 03cc32a18 (no pane/agent/termio change since 1.56.36's 8806b03b4 except two sidebar/dim commits), real `wsl.exe -d Ubuntu --cd ~` as the default command, session persistence on, window reuse on:
- Scratch repros first: `+split` x3 with closes, then ctrl+d / ctrl+shift+t keybind splits and tabs (with and without the parent reporting an OSC 7 folder, so T3772's `--cd <folder>` rewrite ran: the new panes started in `/tmp`). Every new pane had its own `wsl.exe` PID, its own Linux bash `$$`, its own agent session id and an empty scrollback; closed panes' `wsl.exe` and Linux bash were gone (`ps` inside the distro).
- `wsl-pane-lifecycle.ps1 -Wsl` (6 rounds x split/tab/window = 18 panes, odd rounds closed past undo-timeout, even rounds within it): **WSL LIFECYCLE: ALL PASS (367 assertions)**. The log shows panes taking parked windows.
- Static read: a new pane only ATTACHes when an override hands it a `session_id` (restore paths only); the agent's OPEN always spawns, and holder pipe ids are random - nothing on the code path lets a new pane reach another pane's shell.
- The 1.56.36 release log on this box records no pane being opened between the 15:55Z update and the report, so the report likely came from another machine or a gesture not yet covered (the + / palette shell picker `--shell=wsl:<distro>`, a keybind new window, the machine chooser).
- Memory: app private bytes climb ~130 MB over the first four rounds and then hold flat (rounds 4-7 within 1 MB); handles flat after round 2; agent +3.5 MB. High water, not a per-pane leak - filed as T3822.

Positive control: since nothing reproduces, "fails on 1.56.36" cannot be shown; `-NegativeControl` (probe P0 as if new) proves the identity assertions go red (4 failures, exactly those).
