# T1791 - Machine chooser lists sessions another viewer holds (and a just-closed pane's session) as Resume rows; Mac's actionable filter hides them

## Summary

Found while doing T1760. Mac's chooser shows only the sessions the user can
act on: `actionable()` in `macos/Sources/Features/Remote/MachineChooserView.swift`
(~line 1119) drops any session the agent reports as `attached` that no pane of
ours holds. In practice that is (a) a pane just closed, whose session stays
alive and bound to us for the 5 s undo window, and (b) a session another
viewer (another machine) holds. Mac's reasoning: a Resume row for a window the
user deliberately closed "reads as a leak and invites reviving it", and a
session held elsewhere cannot be resumed from here. The row count badge uses the
same filter, so the number agrees with the rows.

Windows' `SessionRoster.visible` (`src/apprt/win32/SessionRoster.zig`) filters
only `isConnectable` and killed rows, so both kinds still appear, wearing the
`attached` chip (which T1760 kept for exactly this reason). The machine-row
count capsule (T1745) must be checked to use the same filter as the rows.

Fix: add the `attached && !open_locally` drop to `visible` (and whatever the
count capsule counts from), then decide whether the `attached` chip still has a
case left; if not, remove it as Mac did.

## In plain terms

The new-window chooser's session list offered "Resume" on sessions this
window could not actually take over - ones another Ghoztty window was already
showing. Now, as on Mac, the list shows only sessions you can act on from
here, the machine's session count matches the list, and the grey "attached"
tag that marked those rows is gone with them.

## Goals

- [x] One shared filter decides the rows, the keyboard cursor, the count and the Restore All button
- [x] Sessions held by another viewer (or a pane just closed) are not listed
- [x] The `attached` chip is removed, as Mac did

## Validation criteria

- [x] Unit test (none lane): the visible-row filter drops an attached session no local pane holds and keeps an attached one we hold open. - `isActionable` test in `src/apprt/win32/chooser_sessions.zig`, green in `floor-lane.ps1 -Lane all`.
- [x] Closing a pane and opening the chooser within the undo window shows no Resume row for it - section 3b of `test\win32\chooser-sessions.ps1`. On Windows `+close` ends the session at once (the run printed `lingering attached: False`), so this case cannot linger here; section 3c (a second app on the same debug agent) is the discriminating proof: every session app 1 holds is hidden from app 2, and with the filter mutated off 3c goes red (2 failures).
- [x] The machine row's session count equals the number of rows listed - 3c asserts `chooser row count key=local count=N` equals the roster's `listing N` (1 vs 1).
