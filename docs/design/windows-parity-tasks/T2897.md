# T2897 - Busy-light ring and focus glow paint through GetDC on a timer, outside WM_PAINT - no paint probe can see them and every capture re-derives the right frame from the clock

## Summary

Found by T1407's survey. `syncBusyLights`/`busyLightTick` (`Window.zig` ~9440-9500,
`BUSY_LIGHT_TIMER_ID`) and `syncFocusGlow`/`focusGlowTick` -> `repaintPaneDesk`
(~9075-9125, 9520) draw through `GetDC` + `paintAlphaCorrect` with no
`InvalidateRect`, and the frame/expiry state is computed from the clock at paint
time. So pane-busy-light:132 (ring moves, 9;4 on/off, 15s expiry) and
pane-elevation ~887-928 (glow follows focus) pass on a capture that re-derives
the right frame even if the timer never ran, and a `WM_PAINT` counter would not
see these paths either.

Needs its own probe: count the timer-driven GetDC paints (a `paint_probe`
surface recorded from the tick, not from `WM_PAINT` - extend printclient-audit
section D's positive half to accept that arm), then measure both claims against
a deleted tick/sync and RUN the new assertions red.
