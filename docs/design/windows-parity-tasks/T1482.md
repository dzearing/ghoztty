# T1482 - A watchdog re-entry can type into a loop window the user has since repurposed

## In plain terms

When the automated work loop stalls, its supervisor revives it by typing a
"clear your context and start over" message into the loop's window. If you had
since started using that window for your own Claude conversation, that message
would land in your conversation and wipe it. Now the supervisor first checks
whose conversation is in the window, and if it is yours it leaves it alone and
opens a fresh window for the loop instead.

## Goals

- [x] Before typing, the watchdog identifies the Claude session in the pane
      (pid -> Claude Code's own per-process session record -> its transcript)
- [x] A pane whose last typed prompt is not the loop's is never typed into;
      the re-entry opens a window of its own instead and says why
- [x] The taken-over window is unmarked, so the next claim's duplicate sweep
      cannot close it
- [x] A session that cannot be read keeps the pre-T1482 behaviour (the
      recovery is not traded for the check)
- [x] Acceptance with negative controls in both directions

## Summary

T1478 made the watchdog fall back to the loop's LAST pane (from go-loop-history.jsonl) when the lock is gone, which is what lets a stop/resume cycle recover. It also widens an exposure that already existed for the lock's pane: if the user has taken that window over for their own Claude session, the re-entry types the reset-first go prompt into it and costs them their context. The pane id is a GUID so it cannot be recycled, but nothing checks that the session sitting there is still the LOOP's. Options: require the window to still carry the [go-loop] marker (a stop unmarks it, so that alone would defeat the recovery), or read the pane for the loop's own fingerprint before typing.

## Design (2026-11-14)

The task named two options; neither was taken as-is. The window marker cannot
be the test (a stop unmarks it, which is exactly the T1478 state), and reading
the SCREEN for a loop fingerprint fails once a long turn scrolls it away. What
Claude Code writes is decisive instead: `~/.claude/sessions/<pid>.json` names
the session that process runs NOW (a /clear changes it; `procStart` defends
against a recycled pid), and that session's transcript holds every prompt typed
into it. Every prompt the loop types names go.md (reset continuation, watchdog
nudge, resume shim), so `scripts\lib\LoopPaneSession.ps1` reads:

- **foreign** - the last typed prompt is not the loop's (the user's own
  session after a /clear, or the user typing into the parked loop session);
- **loop** - last prompt is the loop's and it ran the claim (output, or the
  claim command when the output was redirected, as lane b does), or it has
  only ever been typed loop prompts;
- **unknown** - nothing readable; the watchdog keeps its old behaviour.

Only `foreign` stops the nudge. Checked against the live box on 2026-11-14:
lane a's and lane b's sessions read `loop`, the user's own chat reads `foreign`.

A shell (no claude) in the remembered pane still gets the resume shim as
before - there is no session to ask, and an idle prompt in the loop's own pane
is the dead-loop case T1478 exists for.
