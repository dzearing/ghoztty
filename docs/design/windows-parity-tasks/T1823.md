# T1823 - An OpenWith 'How do you want to open this?' dialog appeared on the user's desktop at 00:17:52 during a loop turn and holds the foreground

## Summary

Found during T1820 (2026-10-11 01:2x). The interactive desktop's foreground
window was `C:\WINDOWS\system32\OpenWith.exe -Embedding` (pid 59836, parent
svchost, created 2026-10-11 00:17:52, empty title) - the shell's "How do you
want to open this file?" picker, which Windows shows when something
ShellExecutes a file or URL scheme with no registered handler. 00:17:52 is one
minute after T1806's tracker close (00:17) and inside the T1815 turn, so a
script run in that turn (a test lane, the crash re-run, or an acceptance
script) most likely launched an unassociated file/URI on the USER's desktop.
That is a focus pull the go.md rule forbids, and it also made T1820's K arm
fail deterministically (the foreground was held by a foreign app).

Find the caller: candidates are anything that `Start-Process <file>`s or
`ShellExecute`s a path/URI (viewer "open externally", ghoztty:// scheme tests,
dump/log openers in scripts\crash-catch.ps1 or the T1815 re-run). Make it
refuse (or route to the test desktop) under test, and add a tripwire: the
foreground watcher already samples pids on the interactive desktop - extend it
to flag any NEW top-level window owned by OpenWith.exe/explorer during a run.

## In plain terms

Twice in a day, a Windows "How do you want to open this file?" box popped up
over the user's screen while the automation loop was working, and sat there
holding the keyboard focus. It turned out not to be a test at all: the
instruction Ghoztty gives Claude for updating its status banner names a `.sh`
script, and when Claude ran that line from PowerShell instead of bash, Windows
did not know how to open a `.sh` file and asked the user. Now the instruction
says to use bash, and the loop says so out loud at the start of every turn if
one of those boxes is sitting on the screen.

## Goals

- [x] Find what opened the picker
- [x] Stop the banner instruction from inviting a PowerShell call
- [x] Make a left-behind picker visible at every turn instead of silent

## Resolution

Root cause (verified): NOT a script. Both surviving pickers (pid 26580,
2026-10-10 10:52:25.4; pid 59836, 2026-10-11 00:17:52.7) started within a
second of a PowerShell-tool call that began
`~/.config/ghoztty/hooks/ghoztty-banner.sh 2>$null; powershell ... daily-publish.ps1`
(transcripts 4af9904a, 45956b42; the daily-publish watermark `at` of the second
run is 00:17:52). PowerShell cannot execute a `.sh`, so it ShellExecutes it;
`assoc .sh` is `sh_auto_file` with no open verb, so DCOM starts
`OpenWith.exe -Embedding` on the interactive desktop. Six such PowerShell calls
in the last 40 session transcripts. The line comes from the shipped Windows
hook's `banner_help` text, which the UserPromptSubmit hook hands the model.

Fix: the Windows fork's help text now says "from the Bash tool (never from
PowerShell ...)"; hook-json section A asserts it (negative control: the same
check against the HEAD~ text finds the help block and fails). Tripwire:
`scripts\focus-pull-scan.ps1`, called by `go-loop-exec.ps1 claim`, prints
`FOCUS PULL: <n> ... picker(s)` naming pid and start time; status by design
(gate-negatives registry row), harness `test\win32\focus-pull-scan.ps1` with
`-NegativeControl` and a guard-due row. The two live pickers were left for the
user to dismiss (their screen).

Mac: no change owed - a `.sh` runs natively from every Mac shell, so the Mac
text has no equivalent hazard.
