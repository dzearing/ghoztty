# T2918 - pane-stack-strip D6: a strip dropped at a screen edge lands in the new window as a DIFFERENT terminal window (handle changed), not the dragged pane moved

## Summary


Found by T2917 (2026-11-11) once the agent-backed harnesses could run again. `test\win32\pane-stack-strip.ps1` section D6 fails twice running, alone and in parallel: the drop opens a second window covering the right half (pass) and three panes stay behind (pass), but `Get-TestChildWindows` on the new window finds a GhozttyTerminal whose HWND is not the dragged pane's (`D6: it holds the dragged pane s2, the same window (1)`). Either the drop now re-creates the terminal instead of reparenting it (a user-visible scrollback/state loss), or the assertion's identity check is stale. Log: %TEMP%\ghoztty-acceptance-parallel\20261111-051629\01-pane-stack-strip.log. Owns the pane-stack-strip guard via guard-ack.
**Resolved as a harness defect - the app was right.** Re-run with D6 naming
what actually arrived: the new window held **s3**, a pane that was already
there, not a re-created terminal. After D5 the two tucked strips (s2, s3) sit
side by side in the same colour, so `Measure-Strip`'s colour walk read them as
ONE strip 90 px wide (`s2[1051-1141]`, `s3[1096-1141]`). D6 pressed at that
"strip's" middle, x=1096, which is s3's leading edge, and the app correctly
tore s3 out. Fix: `Get-StripRow` ends each item where the next one begins, and
D6's failure message now names the arriving pane (`s3`, `unnamed <hwnd>`, or
`NEW <hwnd>`), so a real re-create would read differently from a mis-aim.

## In plain terms

A test said that dragging a minimized pane out to its own window swapped it for
a different terminal, which would mean losing what was in it. It did not: the
test had grabbed the neighbouring minimized pane by mistake, because two of
them side by side looked like one wide one. The test now aims correctly and
says which pane arrived.
