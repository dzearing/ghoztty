# T2292 - git-commit-guard leaves a half-finished rebase when its push-reject pull --rebase hits a transient index.lock: the commit is made, the guard exits 6 with 'Another git process seems to be running', the message file is deleted, and the tree sits mid-rebase with a stale CHERRY_PICK_HEAD

## Summary

Seen 2026-10-25 22:12 on lane b while lane A was committing: the next guard call then failed with 'cannot do a partial commit during a cherry-pick' and rebase --continue could not find rebase-merge/message. The guard should retry the pull on an index.lock, and on any failure mid-rebase either finish or abort it and say which, never exit with the repo mid-rebase. Recovered by hand: git commit -F + rebase --continue + push.

## In plain terms

When two work sessions share one copy of the code and both save their work at
the same moment, one of them could get stuck halfway through syncing - and the
copy then refused every later save from either session until someone untangled
it by hand. Now the sync waits for the other session to finish and completes
itself, and if it truly cannot finish it backs out cleanly and says so.

## Goals

- [x] A sync interrupted by the other session's brief file lock waits and finishes on its own
- [x] Anything the sync cannot finish (a real conflict, a lock that never goes) is backed out, or named plainly when even that is impossible
- [x] The leftover "cherry-pick in progress" marker that blocked later saves is cleared when nothing owns it
