# T2600 - Make a 'resize trace' stamp cost microseconds, not ~0.2 ms: each one does a GetWindowRect and a log line on the UI thread, so the trace inflates every resize phase it splits (T2593 measured it)

## Summary

T2593 put one-off stamps around each pane inside the region cut. Back-to-back
`resize trace` stamps with nothing between them read 0.23-0.27 ms apart: each one
calls `GetWindowRect` and writes a formatted log line (`Window.resizeTrace`,
`resizeTraceMsg`) on the UI thread, and the render-thread stamps
(`draw-begin` ... `present`) log the same way. A layout pass carries ~15 of them,
so the trace adds a few ms to the very pass whose ~6 ms budget it measures, and a
phase split finer than ~0.5 ms is mostly the trace itself.

Do: record stamps into a fixed in-memory ring (name id, QPC, optional width read
only where a line needs it) and write the ring out after the size loop ends
(`WM_EXITSIZEMOVE`) or at exit, in the same `resize trace ...` text so the film
summarizers keep working. Then re-film one baseline and say how far the phase
numbers in T2577 moved.

## Validation criteria

- [ ] back-to-back stamps read under ~10 us apart in a trace
- [ ] the trace text format is unchanged (the film summarizer reads it as before)
- [ ] one ReleaseSafe film with the cheap trace, phase medians recorded against T2593's table

## In plain terms

The timing log used to measure window-resize lag slows the resize down while it
measures it, by enough to mislead which fix looks worth making. This makes the log
nearly free.

## Goals

- [ ] stamps cost microseconds
- [ ] resize phase numbers re-measured with the cheap trace
