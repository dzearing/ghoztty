# T2600 - Make a 'resize trace' stamp cost microseconds, not ~0.2 ms: each one does a GetWindowRect and a log line on the UI thread, so the trace inflates every resize phase it splits (T2593 measured it)

## Summary

T2593 put one-off stamps around each pane inside the region cut. Back-to-back
`resize trace` stamps with nothing between them read 0.23-0.27 ms apart: each one
calls `GetWindowRect` and writes a formatted log line (`Window.resizeTrace`,
`resizeTraceMsg`) on the UI thread, and the render-thread stamps
(`draw-begin` ... `present`) log the same way. A layout pass carries ~15 of them,
so the trace adds a few ms to the very pass whose ~6 ms budget it measures, and a
phase split finer than ~0.5 ms is mostly the trace itself.

Do: record stamps into a fixed in-memory ring (name id, QPC, optional width read
only where a line needs it) and write the ring out after the size loop ends
(`WM_EXITSIZEMOVE`) or at exit, in the same `resize trace ...` text so the film
summarizers keep working. Then re-film one baseline and say how far the phase
numbers in T2577 moved.

## Result (2026-11-06)

`GHOZTTY_RESIZE_TRACE` now formats each line into a fixed in-memory ring
(`src/apprt/win32/resize_trace.zig`, a `trace_ring.Ring(16384, 224)` behind a
mutex, since renderer threads stamp too) and writes it out, byte-identical, once
the size loop has ended and no layout pass has stamped for 250 ms (a WM_TIMER armed
once per batch from the first traced message), and on WM_DESTROY. The desk's
`desk trace`/`desk build` lines ride the same ring so they keep their place among
the stamps. A header `trace ring resize lines= dropped= stamps= stamp_avg_ns=
stamp_max_ns=` precedes each flush (deliberately not a `resize trace` line).
`GHOZTTY_RESIZE_TRACE=log` keeps the old write-as-you-go behaviour.

Rig: ReleaseSafe @910a71f05 + this change, `GHOZTTY_COMP_CHROME+PRESENT+NOREDIR`,
`scripts/resize-sync-onscreen.ps1` (ghost window, never took the foreground), four
drags, 126 traced passes each. Same build, only the trace mode differs. Medians in
ms after `nccalc`:

| trace | bad (rs/rg/ls/lg) | cut phase (faces -> cut-end) | wait-end (n=5) | first present | back-to-back stamp p5 |
|---|---|---|---|---|---|
| log (pre-T2600 behaviour) | 37/58/37/53 = 185 | 1.58 | 14.96 | 5.47 | 58 us |
| ring (this change) | 33/39/28/38 = 138 | 1.57 | 10.89 | 5.06 | 0.4 us |

- The logged trace was costing bad frames, not just phase time: 185 -> 138 with
  nothing else changed. Earlier films read through it overstated the defect.
- The cut phase does not move (1.57 vs 1.58): T2593's ~1.8-2.0 there was the
  older tree, not the trace. First present moves ~0.4 ms. T2593's absolute numbers
  (first present ~12 ms) are not comparable to today's ~5 ms: the resize path has
  changed since 2026-11-01 (T2621 presenter wait and others), so compare arms
  within one build.
- The films ran on the user's desktop as a ghost window (never focused, bottom of the
  z-order; check F passed both times). T2666 is parked on the reading that go.md forbids
  this film while the user may be present, so the question went to the user as D108.
  No further films run until it is answered.
- left-grow shows `flat_background` frames in both modes (27 ring / 38 log); that is
  the existing resize defect the P0 work (T2577) is chasing, not this change.

## In plain terms

The timing log used to measure window-resize lag slows the resize down while it
measures it, by enough to mislead which fix looks worth making. This makes the log
nearly free.
