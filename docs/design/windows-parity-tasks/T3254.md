# T3254 - A late OPENED/ATTACHED reply after one pane's 10s timeout is handed to the NEXT pane's request - panes cross-wire to each other's sessions and the last one times out (split from T3252)

## Summary

connection.rpcCall correlates OPEN/ATTACH replies by reply TYPE (pending_opened/pending_attached), and protocol.Attached/Opened carry no request id or session id. When pane A's ATTACH times out (rpc_open_timeout_ns, 10s) its slot is removed; pane B (serialized behind open_rpc_mutex) registers the same by-type slot, and A's late ATTACHED is delivered to B - B adopts A's session channel, B's own reply goes to C, and the last pane waits out its own Timeout. One slow attach on a relaunch therefore produces cross-wired panes plus an extra error.Timeout, a candidate mechanism for T3252's report. Verified by reading connection.zig deliverRpcReply (~3386) and protocol.Attached (~1383). Fix shape (mechanism call, not a decision): additive request correlation - the client sends a request id in OPEN/ATTACH, a capability-gated agent echoes it, and the client drops an uncorrelated reply (and DETACHes the stray session); against an older agent, count owed late replies per type after a timeout and discard that many. Shared core: lands for both mac and win. Acceptance: unit test in connection.zig with a mock agent that answers the first ATTACH after the timeout - the second pane must get its OWN session or fail, never the first's.

## In plain terms

When several panes reconnect to the background session service at once (a relaunch
restoring a window full of panes) and one of them is slow, its answer used to be handed
to the NEXT pane. That pane then showed the wrong terminal, the one after it showed the
wrong one too, and the last pane gave up with an error. Now each answer names the request
it belongs to, so a late answer is recognised and put away instead of being handed on,
and each pane gets its own session or a clear failure.

## Goals

- [x] An OPEN/ATTACH reply that arrives after its request timed out is never adopted by the next request of the same type
- [x] Works against the agents already installed (no id echo) by discarding late replies in order, but only where the agent is known to answer every request
- [x] The stray session is DETACHed again, except when a retry of the same session is in flight or a pane already reads it
- [x] Newer agents echo a request id (`capability.reply_correlation`), additive in both skew directions

## Design (mechanism call, recorded per go.md 5b)

- **Wire**: optional `req_id` on `Open`/`Attach`, echoed on `Opened`/`OpenFailed`/`Attached`/`AttachFailed`; null is elided, so a request without one is byte-identical to before. New capability `reply_correlation` (both sides advertise; intersection). The agent echoes whatever the request carried; an unparseable request has no id to echo.
- **Client** (`src/remote/connection.zig`): a by-type slot that is given up on (timeout, cancel) while its request was sent and unanswered is recorded as *abandoned* (bounded FIFO of 16, plus an exact per-type overflow count). `deliverRpcReply` matches a reply by its echoed id; with no id it consumes the oldest abandoned request first (replies come back in request order). Without an id the abandonment is recorded only if the agent negotiated `open_failed`/`attach_failed` - an older agent may stay silent on a refused request, and counting that as owed would swallow the next pane's genuine reply (test 5 covers this).
- **Races closed in passing**: the timeout and its slot release are one critical section, so a reply that lands between the wait expiring and the release is taken by its own caller (it used to be dropped and its duped payload leaked); a reply to a cancelled request is recognised as that request's answer.
- **DETACH** is enqueued under `rpc_mutex`, so no ATTACH can register-and-send between the decision and the frame.
