# T3254 - A late OPENED/ATTACHED reply after one pane's 10s timeout is handed to the NEXT pane's request - panes cross-wire to each other's sessions and the last one times out (split from T3252)

## Summary

connection.rpcCall correlates OPEN/ATTACH replies by reply TYPE (pending_opened/pending_attached), and protocol.Attached/Opened carry no request id or session id. When pane A's ATTACH times out (rpc_open_timeout_ns, 10s) its slot is removed; pane B (serialized behind open_rpc_mutex) registers the same by-type slot, and A's late ATTACHED is delivered to B - B adopts A's session channel, B's own reply goes to C, and the last pane waits out its own Timeout. One slow attach on a relaunch therefore produces cross-wired panes plus an extra error.Timeout, a candidate mechanism for T3252's report. Verified by reading connection.zig deliverRpcReply (~3386) and protocol.Attached (~1383). Fix shape (mechanism call, not a decision): additive request correlation - the client sends a request id in OPEN/ATTACH, a capability-gated agent echoes it, and the client drops an uncorrelated reply (and DETACHes the stray session); against an older agent, count owed late replies per type after a timeout and discard that many. Shared core: lands for both mac and win. Acceptance: unit test in connection.zig with a mock agent that answers the first ATTACH after the timeout - the second pane must get its OWN session or fail, never the first's.
