# T2768 - Live run on an idle box: the overlay scrollbar's compositor fade (T2761) must advance on every refresh at UI stalls of 0, 50 and 500 ms - a scrollbar-fade-onscreen.ps1 film adapted from bell-fade-onscreen.ps1, with the stepped arm as control

## Summary

T2761 put the scrollbar fade on DirectComposition with the seams GHOZTTY_DEBUG_SCROLLBAR_FADE_STALL_MS and GHOZTTY_DEBUG_SCROLLBAR_FADE_STEPPED already in place; comp-present G1a-d proves it is declared (and red under the stepped seam). Owed: the frame-by-frame film (advance >= 0.98, max hold 1, max jump bounded) on an idle box, stepped arm freezing under the 500 ms stall, plus -NegativeControl. Trigger the fade by printing output into a pane with scrollback (the thumb lights, then fades out after 1 s idle).

## In plain terms

When output scrolls past, a thin scrollbar thumb lights up at the pane's right
edge and fades away a second after the output stops. That fade used to be
driven by the app itself, so a busy app made it stutter or freeze. It now runs
in the system compositor, and this task is the on-screen proof: the fade is
filmed frame by frame and shown to stay smooth even while the app is stuck for
half a second.

## Goals

- [x] A film script for the scrollbar fade (`scripts\scrollbar-fade-onscreen.ps1`), adapted from the bell-border film
- [x] Film the shipped fade at app stalls of 0, 50 and 500 ms
- [x] Show the old (stepped) fade freezes through the same 500 ms stall
- [x] Show the scorer can go red (negative control)

## Design notes

- The filmed event is the idle fade-OUT (lit thumb -> gone, 128 ms linear ramp, 1 s after output stops), not the fade-in: the fade-in overlaps the output, whose text changes would pollute the score.
- Each frame is split into a right-edge strip (the overlay scrollbar; the output is short numbers at the left) scored by brightness, and the text half, whose last change marks the output's end.
- The stepped control does not snap the way the bell's did: the UI-thread fade steps a fixed 32 alpha per tick, so after the stall it runs a clean, short ramp. What gives it away is LATENCY - the stall delays its first step - so `stepped.6` compares output-end -> first-faded-frame between the two arms (lag >= 0.6 x stall).
- A first print before the film lets the pane's first fade-in/out cycle run unfilmed, so the filmed fade is the steady case.
