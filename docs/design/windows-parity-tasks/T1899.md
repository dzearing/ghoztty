# T1899 - Windows panes show no in-pane progress at all: Mac draws a soft white light circling the pane border while a program is busy, and a glowing line across the top for a percentage

## Summary

main a5c0841be + the busy-border half of 3ac40dc8b. Mac's SurfaceProgressBar/SurfaceBusyBorder: OSC 9;4 indeterminate = a 1pt line with a long fading tail travelling round the pane's rounded border (2.4s per revolution, two shadow glows); a percentage = a 2px glowing capsule across the top edge; white on dark, charcoal (0.2) on light; error red, pause orange. The win32 apprt reflects OSC 9;4 only on the taskbar button (App.zig progress_report, 'the win32 apprt has no progress bar of its own'), so Claude Code working in a pane is invisible in the pane itself. Build the in-pane indicator on the elevated pane card (respecting its corner radius), keep the taskbar progress, gate on progress-style like Mac.

## In plain terms

On a Mac, a pane where Claude Code (or any program that reports progress) is
working has a soft white light running round its border, and a download or
build that reports a percentage shows a glowing line across the pane's top.
On Windows the only sign was a green bar on the taskbar button, so you could
not tell which pane was busy. Now the pane itself shows it, the same way.

## Goals

- [x] A busy pane with no percentage shows a light circling its border, once
  every 2.4 seconds, with a long fading tail, as on Mac.
- [x] A percentage shows a glowing line across the pane's top, as long as the
  share that is done; a pause shows it full and orange.
- [x] White on a dark pane, charcoal on a light one, red for an error.
- [x] It goes away when the program says it is done, or 15 seconds after the
  last report, as on Mac. The taskbar progress stays.
- [x] Costs almost nothing while it runs: only the ring of pixels is redrawn.
- [x] Holds still (no rotation) when Windows' Animation effects are off.

## Design (mechanism; recorded per go.md 5b)

- Mac's light is a layer inside the pane, clipped to the card, so its glow
  spills inward over the terminal. On Windows a pane is its own GL child
  window covering the card's interior, and the window that owns the card
  paints only its 1px rim and the desk around it. So the line runs along the
  rim, where Mac's does, and the glow spills OUTWARD onto the desk. The
  user-visible half of that is filed as a decision (see the log).
- `busy_light.zig` (pure, unit-tested): shapes, colours, Mac's comet ramp, the
  head's clock, and a cache of the ring's pixels - each pixel's distance from
  the edge and angle about the centre are fixed by the card's geometry, so a
  frame is one table lookup and three blends per ring pixel.
- `PaneDesk.zig`: keeps a ring cache per busy pane, rebases it after every
  full desk paint, and `paintLightFrame` redraws only the ring and blits only
  the four strips it lies in. `Window.zig` runs a 30fps timer only while a
  visible pane is busy (1s when Animation effects are off, for the expiry
  alone), skips frames while minimised, and repaints the full desk only when
  the set of lights changes.
- Elevated style only: the flat style has no desk for the light to sit on.

## Validation criteria

- [x] Unit tests (`busy_light.zig`, 8 tests: shapes, colours, comet ramp, head
  clock and direction, interior never painted, head movement restores pixels,
  bar length, glow stays short of the gap, strips hold the ring) - `zig test
  busy_light.zig` all 62 pass, and the none/win32 lanes.
- [x] `test\win32\pane-busy-light.ps1` ALL PASS (15): a real OSC 9;4 stream
  through the ConPTY; the ring lights the right and bottom rims in turn and
  each goes dark again (moves), the glow lifts the desk beside the lit rim

  dark after 15s. `-NegativeControl` fails as it must.
