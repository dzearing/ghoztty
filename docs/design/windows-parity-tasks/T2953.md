# T2953 - 4K fold glide: a laid tick's placement spends 5-10 ms off-CPU outside the desk blits (place ~15 ms, UI-thread CPU 7-12 ms), so 2 of 20 release drags still have one tick at 16.8-18 ms

## Summary

Found by T2952's stall probe (`stack trace stall` line, `GHOZTTY_STACK_TRACE=ring`). Soak 2 (`temp\t2952-soak2.txt`, `-analysis.txt`; 20 x 4K ReleaseFast drags of `temp\t2952-rel2`, release sandbox) had no blocked-blit episodes, but 5 laid ticks of 16.1-18.0 ms in 3 runs (2 runs over 16.7: 16.8 and 18.0 ms). Every one is `place_us` 14.5-16.3 ms with the desk blits only ~1.0-1.4 ms in total, yet the UI thread's own CPU over the tick is 6.7-15.7 ms: up to 10 ms of placement is spent off-CPU somewhere that is not a desk blit (candidates: `EndDeferWindowPos`, `SetWindowRgn`, the strip-face commit - each a window-manager call that can wait on DWM). Normal ticks run cpu/wall ~0.84.

Next: time each placement phase with thread cycles too (the probe's `Lap` shape) so the off-CPU part names its call, then decide whether it can be moved off the tick, batched or avoided.

## In plain terms

On a 4K screen, a divider drag occasionally has a frame that comes a little late (17-18 ms instead of under 16.7). This card found where that time goes: in the one Windows call that moves all the panes to their new places at once. Windows sits idle inside that call for a few milliseconds now and then, waiting on something of its own. Our own code inside the call costs almost nothing. Naming what Windows waits for needs an administrator trace, the same one T2952 is waiting on.

## Findings (2026-11-13)

Probe: `stall_probe.placeBegin`/`placeLap` time each stretch of the glide's placement pass with wall and the UI thread's cycles (phases in `src/apprt/win32/place_laps.zig`), emitted as `stack trace place worst=<phase> off_us=<n> plan=w/c defer=w/c end_defer=w/c cut_batch=w/c apply=w/c viewers=w/c faces=w/c cut=w/c clear=w/c`. Analyzers: `temp\t2953-place.ps1 -Soak <file>` (slow ticks by phase), `temp\t2953-arm.ps1 -Soak <file>` (end_defer distribution).

- **Soak 1** (`temp\t2953-soak1.txt`, `-analysis.txt`; 20 x 4K ReleaseFast, release sandbox): among slow ticks, the phase with the most off-CPU time is `end_defer` (`EndDeferWindowPos`) 91 times, far ahead of any other. Typical: `end_defer=9403/1341`, `11335/1682`, `19579/2113` (wall/cpu us). The batch's own `filled` line shows `sizes=1 size_qpc~0`, so the panes' `WM_SIZE` work is nothing. The wait is inside the window manager moving the five pane children. Baseline `end_defer` is 1.5 ms wall, 1.0 ms CPU.
- The box was loaded during soak 1 (another app holding 4-8 of 32 cores). Runs 5 and 6 (5.5-8.5 cores) hold 126 of the 132 ticks over 16.7 ms. Those are mostly CPU-bound `end_defer` (cpu ~= wall, 10-22 ms): same call, slowed by contention. With the box quieter (A/B arm A, 3.9 cores), `end_defer` off-CPU is p50 0.29 / p90 0.74 / p99 1.7 ms, and over 3 ms in 25 of 9254 ticks.
- `SWP_NOCOPYBITS` on the pane moves was already ruled out (T2485 run29: `EndDeferWindowPos` median 4.7 vs 5.3 ms, tick cost unchanged).
- **No redirection surface** (A/B 2, `temp\t2953-ab2A/B.txt`, 6 interleaved pairs, both arms with the chrome host `GHOZTTY_COMP_CHROME=1`, B adds `GHOZTTY_COMP_NOREDIR=1`): `end_defer` off-CPU p50 272 -> 164 us, p90 670 -> 341, p99 1142 -> 804, so dropping the surface roughly halves the typical wait. The tail stays (over 3 ms: 1 -> 9 of ~2200). The chrome host itself is not usable for a glide yet: its `clear` phase is 33-42 ms of CPU per tick (filed as T2954).
- A/B 1 (`temp\t2953-abA/B.txt`) set `GHOZTTY_COMP_NOREDIR` without the chrome host, so the knob did nothing. It was a default-vs-default control: `end_defer` off-CPU p99 1.66 vs 1.59 ms. Not evidence about NOREDIR.
- Conclusion: the off-CPU time is the window manager's own wait inside `EndDeferWindowPos`. It is the same family as T2952's blocked desk blit (the window manager syncing with the compositor), and the same elevated ETW capture answers both: in WPA, read the UI thread's CSwitch ReadyThread stacks across a slow `EndDeferWindowPos`.

## Validation criteria

- [x] The off-CPU part of a slow place tick is attributed to a named call (wall vs cycles per phase). `EndDeferWindowPos`: soak 1 above, 91 of the slow ticks' worst off-CPU phase, with the panes' `WM_SIZE` work measured at ~0 inside it.
- [ ] A change that removes it, measured over 20+ 4K release runs with 0 ticks over 16.7 ms from this shape, or a recorded finding that it is outside the app.
