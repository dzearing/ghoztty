# T2489 - Verify a closed pane's shell ends when its undo-timeout runs out on Windows (Mac ef57f03fd ClosedPaneRelease): prove the process exits, an undone pane is left alone, a re-close restarts the clock

## Summary

Main intake 2026-10-29 (evening, lane b): Mac `ef57f03fd` added `ClosedPaneRelease` - a closed pane's core surface (and so its shell or agent session) is freed when its `undo-timeout` passes, whoever still holds the view. Before it, the last split closed in a window kept its process alive until that window's tree next changed shape.

Windows parks a closed pane/tab in `src/apprt/win32/CloseUndo.zig` (T1825) and ends it from the `undo-timeout` timer in `App.zig`, so the Mac defect's shape (a stray reference keeping the surface alive) may not exist here. What is owed is the evidence: an acceptance that closes the last split in a window, waits past `undo-timeout`, and asserts the pane's shell process has exited; that an undone pane is not ended; and that closing it again restarts the clock.

## In plain terms

On the Mac, closing a split could leave the program that was running in it alive in the background long after the "undo close" window had passed. This checks that Windows does not have the same leak: a closed pane's shell really ends once its undo time runs out, a pane you undo keeps running, and closing it a second time starts the countdown over.

## Goals

- [x] Prove a closed split's shell ends when the undo window runs out
- [x] Prove an undone pane keeps its shell
- [x] Prove a re-close restarts the countdown

## Findings

Windows was already right: `CloseUndo.pushOwned` stamps every close with its own `now() + undo-timeout` deadline, and an undo pops the entry off the undo stack, so the first close's deadline cannot end a pane that was brought back and closed again. Nothing holds a parked pane past expiry the way Mac's stray view reference did - `onTimer` finalizes the entry itself. No code change; the owed proof is the new section 5r of `test\win32\close-undo.ps1`.

## Validation criteria

- [x] Closing the last split in a window ends its shell process within `undo-timeout` + slack - `close-undo.ps1` section 5 (u1 is the window's only split; HWND destroyed and shell exited inside 6s + slack), green 2026-10-30
- [x] A pane brought back by undo inside the window keeps its process - sections 2/3 (same shell pid after undo, after redo+undo), green 2026-10-30
- [x] A re-close after an undo ends the process one full `undo-timeout` after the re-close, not after the first close - NEW section 5r: undo at 3.5s, re-close at 3.9s; shell alive 4.1s after the re-close (past the first deadline), exited 6.3s after it; green 2026-10-30 (94 assertions). `-NegativeControl` (undo-timeout=0) scores 28 failures as it must
