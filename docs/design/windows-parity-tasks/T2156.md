# T2156 - A full harness-floor sweep (42m on a two-lane box) runs past both wrappers' time limits, so the due run reads STALL and floor-lane reads TIMEOUT over a sweep that finished

## Summary

Found in T1145 (2026-10-22, lane b): acceptance-parallel due ran harness-floor.ps1 to all 32 members and then killed it at 3600s during the confirm re-run (STALL, no stamp); floor-lane.ps1 -Lane harness then reported harness#1=TIMEOUT at member 26. harness-floor.ps1 run directly took 42m46s and stamped after a -Include re-run. go.md says a full sweep is about 24 minutes; with two loop lanes on the box it is nearly double. Either size the wrapper limits from the sweep's measured duration or let the wrappers see a sweep that is still making progress (the CPU-aware stall logic floor-lane already has) instead of a fixed clock.

## In plain terms

The morning check that sweeps every test script for harness defects used to take
over 40 minutes, longer than the time limit the two tools that run it allowed.
They then reported the sweep as hung or timed out even though it had finished,
so the morning result could not be read. It now finishes in well under half of
its time limit, so it reports a real pass or fail.

## Goals

- [x] a full sweep finishes inside both wrappers' caps with room to spare
- [x] a wedged sweep is still killed by the idle/stall check, not left to run to the cap

## Resolution: already fixed (re-verified 2026-11-24)

Fixed at the source before this turn, by two commits:

- **de63c0ca3 (T1657)**: `harness-floor.ps1` declares `# suite-timeout-sec: 3600`.
  Both wrappers honour that declaration (`Get-HarnessLaneTimeout` in
  `scripts\floor-lane.ps1`, and the `Get-ScriptTimeout` path in
  `scripts\lib\AcceptanceParallel.ps1`). The audits now run four at a time
  (`-Jobs 4`) instead of one after another.
- **8a4820a24 (T1969)**: the five heaviest members read only the scripts that
  changed, which takes another big slice off the full sweep.

Measured from `temp\harness-floor\*\summary.json` (start time to when the
summary was written, full sets of 30 or more members only):

- 2026-10-27 to 11-11 (after T1657, before T1969): 17 sweeps took over 40m,
  the longest 48.1m, all under the 60m cap.
- 2026-11-12 to 11-24 (after T1969): 202 full sweeps, median 5.6m, longest
  31.9m (2026-11-19 20:47). That is about half the cap.
- No `WALL-CLOCK CAP` or `harness#1=TIMEOUT` in any of the 967
  `%TEMP%\floor-lane-harness-*.log` files on the box.

The second half of the summary (a cap that stretches while the sweep is still
making progress) was not built. A hung sweep is already killed early by the
CPU/output idle check, separately from the cap, and with about 2x headroom a
stretchable cap would only add a way for a slow-but-alive run to go on forever.
T1661, the same finding against the lane cap alone, was closed the same way
(356000632).
