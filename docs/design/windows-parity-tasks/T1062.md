# T1062 - Eight stale per-task scratch directories are reported every turn and nothing ever resolves them

## Summary

T1054's sweeper reports what it will not delete: zig-out-t473, zig-out-t206, zig-out-t229old, zig-out-prof, zig-out-release, .dumps and two more (~3 GB), all leftovers from tasks that closed weeks ago. Reporting was the right call - they sit outside a cache, so 'entirely regenerable' is an assumption rather than a fact, and the standing rule is to ask before deleting anything outside a cache. But a report that nobody can act on becomes noise on the claim line every single turn, which is how the guard-due list learned to be ignored. The work: establish which of them anything still reads (grep the scripts and harnesses for each name), get the user's yes on the ones nothing references, remove those, and teach the sweeper to name a directory only while it is NEW - a first-seen stamp, so a leftover that has been acknowledged stops being announced. Do not delete anything before the yes.

## In plain terms

Every loop turn started with a line listing two dozen "stale" build folders
that nobody could act on, so it became noise. Now the line names a leftover
only for its first day, a separate listing says which leftovers anything still
uses, and the deletion of the unused ones waits for the user's yes (T2066).
