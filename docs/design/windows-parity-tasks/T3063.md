# T3063 - PA-C06/PA-C07: the Windows font discovery has no index, so each uncovered codepoint rescans every font file under the exclusive grid lock and each new font size rescans on the GUI thread (discovery.Windows)

## Summary

PA-C06 + PA-C07 (audit-1, T2964). src/font/discovery.zig:929-937 `discoverFallback` ignores the collection and calls `discover`, which walks %SYSTEMROOT%\Fonts and the user fonts opening each file with Face.initFile (up to 16 faces per .ttc; :959-1008, :1050-1085). PA-C06: on a codepoint miss src/font/CodepointResolver.zig:167-213 runs that scan while src/font/SharedGrid.zig:172-181 holds the grid's exclusive lock, so the renderer of every pane sharing the grid stalls; the negative cache is per (codepoint, style, presentation) and dies with the grid, so bold and regular scan separately. Cost (estimated from the file's own comment at :896-899, tens of ms per query): 50-300 ms per distinct missing codepoint; binary output with hundreds of distinct unassigned codepoints stalls for seconds. PA-C07: src/Surface.zig:3451-3462 setFontSize -> src/font/SharedGridSet.zig:122-134, :191-197 does one discover per style per configured family on the GUI thread, ~40-200 ms per zoom step when font-family is set. Fix: a one-time lazy index (path, face index, family, style, coverage via cmap) built off the GUI thread and reused across grids and sizes, invalidated on WM_FONTCHANGE; or DirectWrite IDWriteFontFallback::MapCharacters. Risk: medium (index lifetime, invalidation). Windows only. Correctness aside filed separately: `matches` (:1091-1099) ignores bold/italic. Findings: docs/design/perf-audit/audit-1/C-findings.md.
