# T2188 - acceptance-parallel's durable-state check reads the user's own in-app update as a test leak and turns a green run red

## Summary

2026-10-23 06:35: checkout-guard, test-reach-audit and harness-floor all passed, yet the run ended ACCEPTANCE RED with state-changes=4: arp ADDED Ghoztty 1.43.5 and install CHANGED ghoztty.exe/.com/agent under %LOCALAPPDATA%\Programs\Ghoztty. That was the user's in-app updater taking win-v1.43.5 during the run (the user's screenshot shows 'Update installed'), not any script. T1230's snapshot diff cannot tell a published release landing through the updater from a test writing outside its sandbox. Attribute it: when the install/ARP delta is a version that exists as a published win-v release and the installer/updater ran (MSI log, updater state file, or the ARP DisplayVersion matching a gh release), report it as 'user update, not a test' and do not fail the run.

## In plain terms

The test runner checks that a test run leaves the machine exactly as it found
it. When the user installed a Ghoztty update from inside the app while tests
were running, the runner saw the installed app change and blamed the tests,
failing a run that was actually fine. Now it recognises a real published update
landing in the user's install and reports it as "the user's update, not a test"
instead of failing - while anything else that changed still fails the run.

## Goals

- [x] the user's in-app update of a published release no longer turns a green acceptance run red
- [x] anything not explained by that update (a leaked startup entry, an unpublished build in the install, a fixture install elsewhere) still fails it
- [x] the attribution is printed, never silent

## Fix

`Resolve-PersistentStateAttribution` (test\win32\lib\PersistentState.ps1)
attributes a diff to the user's update only when ALL of: an arp entry was added
or changed to exactly `Ghoztty <x.y.z>`; its InstallLocation (read live) is the
user's `%LOCALAPPDATA%\Programs\Ghoztty`; and `win-v<x.y.z>` is a published,
non-draft release on dzearing/ghoztty (`gh release view`). Then the three
install files, that entry and any retired `Ghoztty <ver>` arp entry are
attributed; everything else stays unattributed and still fails the run. A
release that cannot be confirmed attributes nothing (fails closed).
`scripts\acceptance-parallel.ps1` runs it between the settle check and the
verdict, prints `PERSISTENT STATE USER UPDATE ...` with the attributed lines,
and records `userUpdate` in summary.json.

## Validation criteria

- [x] the 2026-10-23 shape (old entry out, published version in, exe/com swapped) is fully attributed - persistent-state.ps1 E1-E3, ALL PASS 44
- [x] a leak riding alongside the update, an unpublished version, a published version installed elsewhere, a bare exe swap and a throwaway identity all stay red - E4-E8
- [x] the runner attributes before its verdict and prints what it attributed - D6/D7; acceptance-parallel.ps1 ALL PASS 87
- [x] the default `gh` path on the real box: the live ARP entry at 1.56.22 is attributed to published win-v1.56.22, and the same entry at 9.99.99 is refused with "could not be confirmed" (hand run, 2026-11-24)
