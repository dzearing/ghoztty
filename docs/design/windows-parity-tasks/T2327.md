# T2327 - Eight 'Ghoztty' products are registered on the box (1.43.4..1.44.2 plus current), seven with no cached package: major upgrades leave orphan Apps & Features entries, and arp-version.ps1 C1 is red on them

## Summary

Found by T2320's due sweep 2026-10-26 (arp-version.ps1 C1, log %TEMP%\ghoztty-acceptance-parallel\20261026-222348\05-arp-version.log): HKCU Uninstall holds product codes {0D7919A6..}, {1D7FAED2..}, {2EB9520F..}, {4B803B2C..}, {52E26F36..}, {74097DC4..}, {9E4BD2E5..} (DisplayVersion 1.43.4-1.44.2) for which Windows Installer has no cached package, beside the live {4BABA428..}. C1's own label says 'red until T2168', but T2168 is done. Determine whether these are orphans of upgrades the RemoveExistingProducts step should have removed (a user-visible duplicate list in Apps & Features) or test/hand-cleanup debris, fix the cause, and give C1 a task-accurate label. Never msiexec /x the user's live product.

## In plain terms

Every time Ghoztty updated itself, Windows Settings > Apps kept the old version
listed beside the new one. This box shows 45 "Ghoztty" entries, and clicking
Uninstall on any but the newest fails because that version is already gone.
From the next release on, an update replaces the entry instead of adding one.
Clearing the rows already there is the follow-up, T2679.

## Goals

- [x] find out whether the rows are upgrade orphans or test debris (orphans: one per in-app update)
- [x] fix the cause in the installer so an upgrade leaves exactly one entry
- [x] prove it on a real published package, with a check that can see the defect
- [x] give arp-version C1 an accurate label, and file the sweep of existing rows (T2679)

## Root cause and fix (2026-11-03)

Read from the installed package (`C:\WINDOWS\Installer\33c164a.msi`, 1.52.10):
`RemoveExistingProducts` sits at **6604**, after `InstallFinalize` (6600).
`build-msi.sh` asked for `After="InstallValidate"`; wixl's sequencer emitted
it at the end of the table, the same After=-anchoring defect T1367 found for
the custom actions. A LATE removal installs the new product first. `C_ArpEntry`
(T2168) keeps one component GUID across releases, so when the old product is
removed the component already has the new product as a client and Windows
Installer leaves its resources in place - including the old release's
`HKCU\...\Uninstall\{old ProductCode}` values. The component registration on
this box agrees: the ArpEntry key path is registered to ONE product, the
current one, while 44 listed keys remain.

Fix: `<RemoveExistingProducts Sequence="1401"/>` (early - WiX's own
afterInstallValidate default, and what the T23 upgrade-safety comments in
build-msi.sh were already written for), plus a build-time check that fails the
MSI build unless the action sits strictly between InstallValidate and
InstallInitialize.

Found on the way: `scripts\msi-test-identity.ps1` rejected every package from
1.43.4 on (its verifier required every Registry.Key to end in the identity, and
the T2168 ARP keys are `Uninstall\[ProductCode]`), so no real-MSI harness had
ever installed a post-T2168 release. Fixed: that key is accepted by name.
