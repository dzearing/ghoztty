# T3228 - Agent drain: grow the per-wake slice from a fixed 1 KiB toward 4-16 KiB while the mailbox is not under pressure, so a 2 MB re-attach replay is not 2,048 lock cycles and render posts (T3068 follow-up)

## Summary

Split from T3068 (PA-C15, audit-1/2). `drainRing` (src/termio/Remote.zig, `slice_bytes = 1024`) pops at most 1 KiB per iteration, and every iteration is one renderer-mutex lock cycle plus `queueRender` and clock reads in `Termio.processOutputTracked`. A 2 MB re-attach replay is therefore ~2,048 lock cycles and render posts. T3068 made the priority handoff run between those cycles (so a key or the renderer is no longer starved); the cycle count itself is unchanged.

Fix: size the pop by mailbox pressure - start at 1 KiB and grow toward 4-16 KiB (capped at `max_parse_slice` or raise both together) while `mailbox.underPressure()` stays clear, dropping back to 1 KiB the moment it is not. Risk: the 1 KiB bound exists because 512 KiB of Claude Code output carries thousands of `?2026h` and queries that overflow the 64-slot mailbox (comment above `max_chunks_per_wake`); a bigger slice must not let one slice push the mailbox past half.

Mac half: the same file serves both platforms' agent path (T3071 is the Mac seat's PA-C15 card).

## Validation criteria

- [ ] GHOZTTY_PERF on a 2 MB re-attach replay: lock cycles / render posts per MB drop vs 1 KiB fixed, measured before and after
- [ ] no mailbox overflow (no `Mailbox.send` 50 ms waits/drops) replaying a Claude Code session ring
- [ ] keystroke latency during the replay no worse than T3068's
- [ ] agent lane + session-restore harnesses green
