# T1053 - A failed 'parity-tasks new' leaves a zero-byte task file behind, holding an id and tripping validate

## Summary

`scripts/parity-tasks.ps1 new` allocates the next id and opens its file before
the body is written. When the write fails, the id is spent and a zero-byte
`T<id>.md` is left in the tracker directory - no frontmatter, no title, and the
next `validate` has to decide what to make of it. This file IS the corpse: it
was created on 2026-08-21 when the drive hit 0 bytes free (T1054) and the
`Close` threw `There is not enough space on the disk`.

## In plain terms

Filing a task can half-happen. If anything goes wrong while the file is being
written, the tracker keeps the task number but ends up with an empty file where
the task should be — and the check that runs before every commit then complains
about a task nobody ever wrote. It is a small thing that shows up at the worst
moment, because the conditions that break the write (a full disk) are already
the conditions where a turn is trying to write down what went wrong.

## Details

The allocate-then-write shape is deliberate - go.md leans on `new` allocating
ids atomically so two agents filing at the same moment cannot collide - so the
fix is not to stop reserving the id, it is to make the write all-or-nothing:

1. Compose the whole file body in memory, write it to a temp file in the same
   directory, then `Move-Item` it into place. A failed write then leaves a temp
   file rather than a task-shaped hole, and the id can be released or simply
   left as a gap (gaps are harmless; corpses are not).
2. If the write does fail, say which id was burned and that nothing was filed,
   so the turn knows to re-run rather than assuming the note landed.
3. `validate` should name a zero-byte or frontmatter-less task file as exactly
   that ("T1053.md is empty - a failed `new`; delete it or write it"), rather
   than reporting it as a malformed task.

Related but distinct from T1054, which is about the disk filling up in the
first place; this is about the tracker surviving a failed write of any cause.

## Goals

- [x] `new` writes a task file atomically, so a failed write leaves no corpse
- [x] A failed `new` says the id it burned and that nothing was filed
- [x] `validate` describes an empty task file in words that name the cause
