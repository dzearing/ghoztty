# T2695 - The viewer's address bar repaints its glass per pixel on every paint (~3.4 ms ReleaseFast, ~5 ms Debug at 1100 px), so T2666's edge-drag burst - which paints the bar every step - misses edge-drag-rate -Burst's viewer shrink budget; cache the glass head region by size

## In plain terms

Dragging the edge of a window that shows a web page or document is slower
than it needs to be, because the page's address bar redraws its frosted
background one pixel at a time on every repaint. Making that redraw cheap
lets the smoother edge-drag fix (T2666) turn on without costing frame rate.

## Summary

`ViewerNavBar.paintGlass` calls `pane_elevation.glassHeadRegion` over every
pixel of the bar on each `WM_PAINT`, then `StretchDIBits`. Measured in
T2666's burst trace (`burst-paint` -> `burst-release`, which is now just
`UpdateWindow(nav.hwnd)` for the viewer): ~3.4 ms per paint in a ReleaseFast
sandbox build, ~5-6 ms in Debug, at an 1100 px window. Under
`GHOZTTY_RESIZE_BURST` the bar paints inside every edge-drag step, so the
viewer shrink step costs 20.9 ms against `edge-drag-rate.ps1 -Burst`'s
17.6 ms budget (release sandbox, 2026-11-04) and 18.4 ms vs 13.3 ms in Debug.

Fix direction: the glass head is a function of (width, height, glass rect,
palette, bg, bar colour, sheet); cache the rendered pixels and reuse them
while those are unchanged, or render only the strip a width change exposes.
Keep the pixels byte-identical to today's (the chrome pixel probes read them).

## Outcome (2026-11-04)

The premise was wrong, and that is the main finding. A new trace (T2695's
`resize trace burst-nav` / `burst-sheet` lines in `Window.releaseBurst`)
shows the bar paints INSIDE the layout pass, at ~0.54 ms Debug (0.34 ms of
it glass), and the burst-time `UpdateWindow(nav)` paints nothing (0 paints,
~24 us). `burst-paint -> burst-release` is the window's own
`RedrawWindow(UPDATENOW)`: 6.3 ms in the viewer scene vs 2.1 ms in row3
(Debug), and 3.77 ms of it is the viewer HOST's glass sheet, rendered over
the whole client (419k px) on every paint. That is filed as **T2702** and
made a dep of T2666.

What landed here:

- **The desk is 2.5x cheaper on the shipped CPU baseline.** Release builds
  target plain x86-64 (SSE2), where a vector `@round` and a float-to-unsigned
  convert are emulated lane by lane - ~60% of `Palette.atRow`.
  `desk_palette.chanLanes` now clamps, truncates with a signed convert and
  rounds up on an exact fraction >= 0.5: the same bits as `@round` (exhaustive
  sweep of every f32 in [-16, 300]: 0 mismatches; unit tests at every halfway
  point +-6 ulps and a 160k-value random sweep). Microbench, 1100x60 head
  band, ReleaseFast baseline: 494 -> 201 us; 1100x380: ~1.24 ms. In-app, the
  viewer sheet is 1.46 ms a burst step in a ReleaseFast sandbox build. Every
  glass surface that reads the desk (bars, sheets, banners) gets the speedup.
- **The bar keeps its glass** (`pane_elevation.GlassHeadCache`): a repaint
  with the size, slice and colours unchanged (hover, press, an address
  change) blits the kept pixels and renders nothing.

Debug numbers did not move (Debug's cost is per-op overhead, not the
rounding). The Debug burst step-cost rows are still red, but row3, which has
no viewer, is red too (shrink 15.9/14.8 ms), so the remaining gap is not the
bar.

## Goals

- [x] bar paint at an unchanged size does no per-pixel glass work (`GlassHeadCache`)
- [x] a width change is well under 1 ms ReleaseFast: the bar's glass at 1100x60 is ~0.2 ms on the shipped baseline (was ~0.5)
