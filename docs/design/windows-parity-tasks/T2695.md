# T2695 - The viewer's address bar repaints its glass per pixel on every paint (~3.4 ms ReleaseFast, ~5 ms Debug at 1100 px), so T2666's edge-drag burst - which paints the bar every step - misses edge-drag-rate -Burst's viewer shrink budget; cache the glass head region by size

## In plain terms

Dragging the edge of a window that shows a web page or document is slower
than it needs to be, because the page's address bar redraws its frosted
background one pixel at a time on every repaint. Making that redraw cheap
lets the smoother edge-drag fix (T2666) turn on without costing frame rate.

## Summary

`ViewerNavBar.paintGlass` calls `pane_elevation.glassHeadRegion` over every
pixel of the bar on each `WM_PAINT`, then `StretchDIBits`. Measured in
T2666's burst trace (`burst-paint` -> `burst-release`, which is now just
`UpdateWindow(nav.hwnd)` for the viewer): ~3.4 ms per paint in a ReleaseFast
sandbox build, ~5-6 ms in Debug, at an 1100 px window. Under
`GHOZTTY_RESIZE_BURST` the bar paints inside every edge-drag step, so the
viewer shrink step costs 20.9 ms against `edge-drag-rate.ps1 -Burst`'s
17.6 ms budget (release sandbox, 2026-11-04) and 18.4 ms vs 13.3 ms in Debug.

Fix direction: the glass head is a function of (width, height, glass rect,
palette, bg, bar colour, sheet); cache the rendered pixels and reuse them
while those are unchanged, or render only the strip a width change exposes.
Keep the pixels byte-identical to today's (the chrome pixel probes read them).

## Goals

- [ ] bar paint at an unchanged size does no per-pixel glass work
- [ ] a width change re-renders at most what changed, or is well under 1 ms ReleaseFast

## Validation criteria

- [ ] unit test: the cached path returns the same pixels as `glassHeadRegion` for the same inputs, and recomputes when any input changes
- [ ] `test\win32\edge-drag-rate.ps1 -Burst` (Debug) viewer rows within budget, or the remaining gap is not the bar
- [ ] the viewer chrome pixel harnesses that read the bar stay green
- [ ] floor lanes green
