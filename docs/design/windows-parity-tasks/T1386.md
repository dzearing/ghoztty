# T1386 - A win32 module's unit tests can silently not run at all, and nothing says so

## In plain terms

Some of the checks that are supposed to run before every change are not
running. They look like they are: the file has tests in it, the test command
says everything passed, and nobody is told that a whole file's worth of checks
was skipped. A bug in one of those files can therefore reach a build with the
tests that would have caught it sitting right there, never executed.

## Goals

- [x] Every win32 module that contains unit tests has them actually executed by
      a lane (T1191's sweep: B4 + D4, 340 win32 modules, 0 missing)
- [x] A module whose tests are NOT executed fails a check, rather than passing
      quietly (`test/win32/test-reach-audit.ps1`, guard row `test-reach`,
      harness-floor daily member)
- [x] The check is demonstrated to be able to fail (section C plants
      unreferenced test-bearing modules and requires both sweeps to go red)

## Summary

Found while building T575 (2026-09-05). The new pure module
`src/apprt/win32/menu_activation.zig` was imported by
`src/apprt/win32/Surface.zig` and its unit tests **did not run in either
lane** - and nothing said so. It was only caught because that turn deliberately
probed for it: a `@compileError` appended to the module produced a GREEN
`zig build test -Dapp-runtime=win32`.

The mechanism is Zig's lazy analysis. A container-level `const x =
@import("y.zig");` is only analyzed when something references it, and here the
only reference was inside `trackMenuActivation`, a function body no test calls.
So the module was never part of the test compilation, and a test build includes
tests only from the files it actually analyzes. The fix for T575 itself was one
line in `src/apprt.zig`'s test block (`_ = @import("apprt/win32/menu_activation.zig");`),
which is the convention the pure win32 modules already follow - `hero_math`,
`dim_math`, `window_chord`, `remote_pill` and about forty others are listed
there for exactly this reason.

What is missing is the thing that NOTICES. The registry is a hand-maintained
list, and the failure mode of forgetting to add to it is invisible in every
direction: the lane is green, the summary's test count moves by an amount
nobody has a baseline for, and the file reads as tested.

## Details

A first-cut scan of `src/apprt/win32/*.zig` (files containing `test "` and not
named in `src/apprt.zig`) returns ~30 names, but most of them are false
positives: `App.zig`, `Surface.zig` and the dialogs are reached eagerly through
`apprt.runtime` when `-Dapp-runtime=win32`, so their tests do run in that lane.
The dangerous set is the one this task has to identify precisely: a module whose
ONLY reference is a lazy decl in a body nothing analyzes.

Approaches worth weighing (mechanism is the implementer's call):

- **Ask the compiler rather than the source.** Something that enumerates the
  tests actually built into `ghostty-test.exe` and diffs that set against the
  `test "` declarations found in the tree is the only version that cannot be
  fooled by a reference pattern nobody predicted. `zig build test` does not
  print names, but a test runner or `--listen` mode may expose them.
- **A registry lint.** Require every `src/apprt/win32/*.zig` that declares tests
  to be either named in `src/apprt.zig`'s test block or on an explicit
  "reached eagerly by the runtime" allowlist, with the allowlist entries owing a
  reason. Cheap, static, and its weakness is the allowlist drifting into a
  place to put anything inconvenient.

Whatever is built, T1133 applies: construct the state it is supposed to catch -
an unregistered module carrying a failing test - and prove the check goes red.

*Validation:* an acceptance/audit script under `test\win32\`, plus a
demonstration that it fails on a deliberately unregistered module. Both `zig
build test` lanes, `zig build test-agent` and P1-P3 stay green.
