# T2267 - Focusing a pane whose sidebar row is scrolled out of view no longer brings the row into view (pane-sidebar-scroll section 4 red on HEAD 238292301)

## Summary

test\win32\pane-sidebar-scroll.ps1 section 4 fails deterministically on HEAD 238292301 (found during T1880, reproduced with T1880's changes reverted): after '+split --name=<id> --focus' the sidebar logs 'pane sidebar reveal surface=rail' but the next rows line still has the focused row out of view (scroll 132). Last green stamp 2026-10-21 (c4b0cbeda); bisect the commits since that touched PaneSidebar.zig / pane_sidebar_scroll.zig / the focus path (T2257's no-focus side pane is a suspect). Evidence: %TEMP%\ghoztty-t1878-fail-20261025-170844-35124.log.

## In plain terms

The sidebar test said that clicking over to a pane whose row had scrolled out
of view no longer scrolled the row back into sight. The sidebar was fine: the
test's "go to that pane" step had started opening a brand-new pane instead,
after a change made pane names work per window, as they do on Mac. The
sidebar scrolled to that new pane, as it should. The test now goes to the
pane by its name and checks that no pane was added.

## Goals

- [x] find out why section 4 went red
- [x] fix the actual cause (the harness, not the sidebar)
- [x] make the same mistake fail loudly next time

## Root cause

`+split --name=X --focus` reuses a pane only when X is a **registered name**
in that window (`IpcRegistry.holderIn`, T2250 / 40f38f2a4, the same rule as
Mac's `existingHolder`). A pane's id is not a name there, so section 4's
`+split --name=<pane id> --focus` created a 15th pane named after the id. The
sidebar revealed *that* pane (item 3, scroll 132) correctly; the restored row
(item 1) stayed scrolled away. Before T2250 the Windows check went through
`ipcLookup`, which also resolves ids, so it worked. That is why it went red
after the 2026-10-21 green run. No other harness focuses through `+split`
with a pane id (`+read --name=<id>` still resolves ids by design).
