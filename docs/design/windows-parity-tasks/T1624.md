# T1624 - The Claude ghoztty plugin comes back after the app retires it, so the banner instructions arrive twice every prompt

## In plain terms

Ghoztty used to ship its Claude integration as a separate plugin; the app now
installs that integration itself and retires the plugin on first run. But the
retirement happens once, and nothing stops the plugin from being installed
again afterwards - which is exactly what happened on this box. The result is
that both copies run: every prompt in a Claude session gets the same "keep the
banner current" instruction twice, one of them pointing at a script path that
was supposed to be gone, and the old plugin keeps re-creating that dead script.

## Summary

Observed live on 2026-09-16 in the go-loop session: the UserPromptSubmit context
carried the banner instruction TWICE, once naming
`~/.config/ghoztty/hooks/ghoztty-banner.sh` (the app-installed hook, registered
in `~/.claude/settings.json`) and once naming `~/.claude/scripts/ghoztty-banner.sh`
(the wording only the older plugin copy emits).

Evidence on the box:

- `~/.claude/plugins/installed_plugins.json` still lists
  `ghoztty@dzearing-claude-marketplace` at version `0.10.0`, installed
  `2026-08-21T14:27:37Z` with `"auto": true` - i.e. re-added by a marketplace
  sync, six days AFTER T870's migration shipped (`59388143f`, 2026-08-15).
- `~/.claude/plugins/cache/dzearing-claude-marketplace/ghoztty/0.10.0/hooks/hooks.json`
  registers its own `SessionStart`, `UserPromptSubmit` and `Stop` hooks against
  `${CLAUDE_PLUGIN_ROOT}/hooks/ghoztty-banner.sh`, and its SessionStart step
  runs `ln -sf ... ~/.claude/scripts/ghoztty-banner.sh` - which is why that
  retired path exists again (dated 2026-08-21) even though the app never writes
  it any more.

`src/apprt/win32/claude_plugin_migration.zig` (and Mac's
`ClaudePluginMigration.swift`) do the right thing when they run: uninstall the
plugin through Claude's own CLI, carry the banner state over, leave a
user-authored script alone. The gap is that `isNeeded` is asked once and the
answer is not re-checked, so a re-registration is invisible - and the marketplace
entry that causes it is still published.

Two halves to consider:

- **App side (this repo):** re-run the migration check when the integration is
  installed/refreshed rather than treating it as a one-shot, so a plugin that
  came back is retired again instead of shadowing the app's own hook. Whatever
  the mechanism, it must stay idempotent and must never touch a user-authored
  script (the existing ownership proof in `claude_plugin_migration.zig`).
- **Marketplace side (outside this repo, `D:\git\dzearing-claude-marketplace`):**
  the `ghoztty` plugin is what a sync re-adds. Retiring or emptying that entry is
  what actually stops the loop; note it here so the app-side fix is not mistaken
  for the whole story.

Both platforms are affected identically - the plugin is Claude-Code-level, not
OS-level - so whatever lands here has a Mac counterpart.

## Goals

- [ ] A plugin that reappears after migration is retired again, without a
      manual step
- [ ] A user-authored `~/.claude/scripts/ghoztty-banner.sh` is still left alone
- [ ] A Claude session gets the banner instruction exactly once

## Validation criteria

- [ ] Unit test in `claude_plugin_migration.zig`: a tempdir HOME where the
      migration has already run and the plugin is registered AGAIN reports
      `isNeeded` true and retires it a second time (the one-shot regression).
- [ ] Acceptance: `test\win32\claude-integration.ps1` (or
      `agent-integrations.ps1`, whichever owns the migration walk) covers the
      re-registration case alongside the existing first-run one.
- [ ] Observed on this box: after the fix and a marketplace sync,
      `installed_plugins.json` carries no `ghoztty@...` entry and a fresh Claude
      session's prompt context shows one banner instruction, not two.
