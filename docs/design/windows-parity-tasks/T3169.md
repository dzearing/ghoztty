# T3169 - Closing every viewer frees none of the ~67 MB the app grew when they opened, and keeps 14 GDI / 21 USER objects (perf-baseline viewer phase)

## Summary

Measured by T3033's viewer phase (scripts\perf-baseline.ps1 -Phase viewer), Debug and ReleaseFast alike, 5 runs: app private 202 MB before any viewer, 268 MB with markdown + git-status: + website viewers open (+67 MB, +40 GDI, +45 USER, +10 threads), 313 MB with a covering tab over them, and 308-320 MB 90 s after every viewer and the covering tab closed (leak +106..115 MB, GDI +14, USER +21, threads +6). The WebView2 processes all exit, so this is app-side residue: controller/composer windows, snapshot bitmaps (PA-V14), find/composer windows created up front (PA-V22), template caches. The leak figure includes the covering tab's terminal pane residue; split it by re-running with the hidden span done by minimising instead, then attribute with the cycle phase's census tools. Done when after_close.leak.private_mb is within ~15 MB of a terminal-only open/close and GDI/USER return to base.

## In plain terms

It looked as if closing viewer panes (markdown, git status, web pages) gave back none of the memory they took. Most of that memory was never the viewers'. The first time any new pane appears, the graphics driver grows its own pool and keeps it. What the viewers themselves leave behind is about 11-15 MB plus a few system objects, all from first use (the web engine's libraries and a small worker pool). Opening and closing viewers again adds nothing, so it does not build up.

- [x] attribute the viewers' share by owner (memory class, allocation, windows/handles/threads)
- [x] tell one-time warm-up from a per-open leak

## Findings (2026-11-18, +ee6e081ed, perf-baseline -Phase viewer, test desktop)

The viewer phase now opens and closes a terminal-only CONTROL tab before any viewer (the same ctrl+shift+t tab the hidden span uses), so `warm_base` already includes what one terminal tab leaves. Two repeat open/close rounds of the three viewers follow `after_close`.

| | Debug run 1 | Debug run 2 | Release |
|---|---|---|---|
| control tab leak (base -> warm_base) | +38.3 MB, +5 GDI, +11 USER | +37.8 MB, +5, +10 | +39.3 MB, +4, +10 |
| viewers open (vs warm_base) | +3.6 MB, +39 GDI, +45 USER | - | +6.5 MB, +39, +44 |
| **viewer_leak (closed vs warm_base)** | **+11.3 MB**, +9 GDI, +15 USER | **+16.2 MB**, +9, +14 | **+14.9 MB**, +9, +15 |
| repeat round 1 adds | - | +5.0 MB, 0 GDI, 0 USER, +3 threads | +4.3 MB, 0, 0, +3 |
| repeat round 2 adds | - | **0 / 0 / 0 / 0** | **0 / 0 / 0 / 0** |

- **The control tab's share** is the GL driver arena T3130 already named and decided (private_rw +24 MB, write-combined +10.5 MB). The old "+106..115 MB leak" counted it, plus the first-open growth it shares with the viewers. Total leak against the cold base is now +50-54 MB, and +39 MB of that is the terminal tab.
- **What the viewers leave** (Release regions): private_rw +8.8, write-combined +3.7, stack +1.5, heap +0.4 MB. Image +14.6 / mapped +12.7 MB are WebView2's DLLs, which stay loaded and are not private bytes. Every viewer window is destroyed: of the 42 windows opened, only one `Chrome_MessageWindow` is left. Threads: +3-5 `viewer-worker` (the pool), +1 WebView2 `MojoThread`, the environment PA-V02 keeps for the app's life. USER +14 is non-window objects, GDI +9.
- **Warm-up, not a leak.** Round 1 grows the ntdll thread pool by 3 and adds ~4-5 MB. Round 2 adds exactly zero on every count, on both builds.

## Decision: keep

The residue is first-use state that later opens reuse. Nothing grows per open, so there is nothing to release. The literal "GDI/USER return to base" bar is not met (+9 / +15 stay), but those objects belong to the WebView2 environment, and PA-V02 keeps that environment for the app's life by design. No follow-up filed: the per-context driver lever is already T3232.
