# T1670 - The throughput harness calls a still-catching-up pane dead, so a green measurement reads as a lost session

## Summary

`test\win32\pane-ingest-ab.ps1` section B4 asserts the agent-held pane is still
LIVE after the 8 MB flood, via `Test-PaneLive` — type `echo <token>` and read the
token back within its 25 s default. Measured on 2026-09-19 over T889's tree: RED,
RED, then GREEN with the same binaries, and GREEN on a pristine-HEAD build in
between. Four runs, one bit flipping, no code in the path that could explain it —
so the deadline, not the product, is what is being measured.

Why it matters beyond a flaky run: B4 is the assertion that would catch a flood
actually killing a session, and a check that cries wolf twice in four runs is one
a turn learns to re-run rather than believe. Both red runs also happened to be
the ones where section A finished FASTER (74-77 s vs 84 s), i.e. the box was
freer, which rules out the obvious "it was loaded" story and points at the pane
still draining its backlog when the token is typed.

The fix is to make the liveness wait proportional to what just happened rather
than a flat 25 s — quiesce on the pane's own output first (the flood's tail
stops arriving), THEN type the token and wait — or, failing that, to raise the
deadline for the post-flood arms with the reason recorded at the call site. Hold
the T831 rule: bounded by the wall clock, never by a count of spins.

## In plain terms

The throughput test sometimes reports that the terminal died right after a big
burst of output, when it is really just still catching up. Nothing is wrong with
the terminal; the test gives up too early. That matters because this is the exact
check that would notice a burst genuinely killing a session.

## Validation criteria

- [ ] `pane-ingest-ab.ps1` runs green ten times in a row on this box over an
      unchanged tree (the flake rate today is roughly one in two)
- [ ] The post-flood liveness wait is justified at its call site — what it waits
      FOR, not just how long
- [ ] A negative control still fails: `GHOZTTY_TEST_LIVENESS_BREAK=1` (or the
      equivalent) makes B4 go red, so the relaxed wait has not neutered it
