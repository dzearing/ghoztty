# T3587 - Linux viewer-reload.sh R8/R9 flake: a live markdown re-render sometimes loses the scroll position

## Summary

test/linux/viewer-reload.sh failed R8 (save in place) and R9 (atomic save) once at 7631fc72a in WSL: the file re-rendered (Live One / Live Two) but the probed scroll was 0 instead of 600; the next run at the same commit was ALL PASS 30/30. Either the scroll restore after a live reload races the render (a user would see the document jump to the top on save) or the test probes before the restore lands. Find which, fix it, and prove with several consecutive green runs.

## In plain terms

A document open in a viewer pane could jump back to the top when its file
was saved, so you lost your place in a long README or plan. It was a real
bug in the page itself, not just the test, and it affected Mac, Windows and
Linux alike because they share that page. Now the pane stays where you were.

## Goals

- [x] find whether the lost scroll is the product or the test
- [x] fix it at the source
- [x] a check that reproduces each cause deterministically
- [x] several consecutive green runs

## Root cause

Two bugs in the shared `src/viewer/viewer.js` restore, both real:

1. `restoreScroll` ran only inside `requestAnimationFrame`, so a restore
   scheduled by one render overwrote any scroll made before that frame.
   In a pane that is not drawing (headless Weston here; a hidden pane in
   general) the frame is far off. Diagnostic run: `scrollTo(0, 600)` read
   back 600, then **0** 300 ms later with no save in between: the first
   render's pending `scrollTo(0, 0)` landed. That is the R8 flake, and R9
   inherited R8's 0.
2. A save written in two pieces further apart than the 100 ms debounce
   (a slow writer, a loaded box) renders the short first piece; the scroll
   clamps, and the full render then captured the clamped value.

Fix: restore at once (`scrollTo` lays out first), re-apply after the frame
only if nothing scrolled since (generation + position check), remember a
clamped restore (`scrollWanted`) for the next render, and cancel a pending
restore when the error card replaces the document.
