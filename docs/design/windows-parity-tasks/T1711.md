# T1711 - The go-loop watchdog nudges a turn that is idle only because it is waiting on its own background task, discarding the wait

## Summary

2026-09-23: T1703's close-out turn started harness-floor (~14 min) with run_in_background and went idle awaiting the task notification. At 16:25:28 the watchdog logged STALLED(by=composer-idle) at turn_age=19.5m (limit 180m) because the composer held unsent 'keep going' text with the session idle, wiped the composer and submitted a nudge; the turn's wait was discarded and a new turn re-did the resume (the harness result landed afterward, in the dead session). An earlier turn died the same way at ~16:07. The composer-idle rule (T1319) cannot tell 'idle with a background task outstanding' from 'idle with nothing running'. Fix direction: treat a session with an outstanding background task (Claude Code's tasks dir for the session, or a live child process of the claude pid such as floor-lane/powershell) as working, and fall back to the turn clock only; also find out who typed 'keep going' into the composer. Evidence: %TEMP%\ghoztty-go-loop-watchdog.log 16:25:28-16:25:52; T1703 progress log (three RESUMEs).

## In plain terms

The loop's babysitter checks every five minutes whether the working session has gone quiet, and pokes it if so. But a session that has started a long test run and is simply waiting for it to finish also looks quiet — so the babysitter poked it, the session restarted from scratch, and the test result arrived to nobody. Three times on 2026-09-23. Now the babysitter checks whether the session is waiting on a job of its own, and leaves it alone until the job reports back (or three hours pass, the existing hard limit).

## Goals

- [x] Tell "idle, waiting on its own background job" apart from "idle, nothing running"
- [x] Keep the 3-hour backstop, so a job that never reports back cannot hold the loop forever
- [x] Show the count on every watchdog decision line (`bg=N`), so a held nudge can be read in the log
- [x] Find where the 'keep going' text comes from: most likely Claude Code's own greyed prompt suggestion; confirming and fixing the probe is filed as T1712

## Fix

`scripts\loop-session.ps1` gains `Get-LoopPendingBackgroundTasks` (plus its pure half `...FromLines`): it reads the session transcript for launches (`toolUseResult.backgroundTaskId` for a backgrounded Bash/PowerShell command, `isAsync` + `agentId` for a background agent) and subtracts every `<task-id>` named by a `<task-notification>`, whatever its status. It matches raw lines rather than parsing JSON, which is fast (~50 ms on a 1 MB transcript) and means a transcript that only *quotes* a launch (escaped quotes) is not counted. `Resolve-LoopStallVerdict -BackgroundPending N` returns not-stalled for N > 0 after the 180m backstop and before every other arm. The watchdog and `go-loop-health.ps1` both pass it in.

I chose this over the two directions the summary suggested. The tasks dir is keyed on the process's ROOT session id (`dc676253...`), not the current one, and holds every output file ever written, so it cannot say what is outstanding. A child-process walk cannot tell a background job from an MCP server. The transcript names both ends of each job.
