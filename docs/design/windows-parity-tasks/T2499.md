# T2499 - A closed terminal pane keeps a window-sized GPU buffer until its window is destroyed (3 MB at the default size, 8 MB at 1800x1100, also with GHOZTTY_COMP_PRESENT), and ~3 MB a window outlives the window close

## In plain terms

Every time you close a terminal split, Ghoztty keeps a chunk of graphics memory the size of the whole window (3 MB for a normal window, more for a big one) until that window closes, and some of it is never given back. A long session of splitting and closing panes keeps eating video memory.

## Summary

Found by T2473's `test\win32\window-close-memory.ps1` (A8, GPU Process Memory counters). Evidence on HEAD 9a289d01a (RTX 4090, WGL path):

- `-Shape split` (two terminals) and `-Shape full`: **+3.0 MB GPU dedicated per closed window, exactly linear**, and it survives the window's destruction. `-Shape single` and `-Shape viewer` (one terminal): flat. Not the undo parking (`-AppArgs '--undo-timeout=0'`: same 3.0 MB), not a resize (`-Shape single -Resize`: flat).
- Splitting and closing a terminal pane INSIDE one window (scratch `pane-cycle.ps1`): +3.0 MB per closed pane while the window lives, **all of it returned when that window closes**. Child window count and USER objects stay flat, so the pane HWND is reaped; GL contexts are balanced (13 created, 12 deleted + the anchor).
- The held buffer is **window-sized, not pane-sized**: in an 1800x1100 window the same cycle leaks 8.0 MB per closed pane (1800*1100*4).
- `GHOZTTY_COMP_PRESENT=1` leaks too (~4-5 MB per closed pane), so it is not WGL `SwapBuffers` into the child alone.
- Under `cdbX64` the driver allocates ~10x more and the leak scales with it (32 MB a window), which reads like a whole per-drawable allocation.

- **T2494's `test\win32\pane-close-memory.ps1` measures it at pane level** (2026-10-30, HEAD 5ba434046, 10 cycles, one window open throughout): +3.45 MB GPU per closed terminal split, +2.95 MB per split closed mid-layout (`rapid`), and **+2.95 MB per closed TAB** (ctrl+shift+t, `+close` its pane) - so a tab close leaks it too, not only a split close. Every other meter (private, handles, GDI, USER, threads, child processes) is flat in all three, and the viewer scenarios are flat on GPU. That harness is the pane-level oracle for the fix; its guard is acked here.

So something allocates a top-level-sized GPU surface per terminal pane (or per split/close relayout) and only the top-level's destruction releases it; and in the window-cycle shape ~3 MB a window is never released at all. Not yet ruled out: the pane's pixel format / DC lifetime vs the deferred HWND reap (T681), a GDI paint of the parent over a GL child, DWM redirection of the parent. Next: GPU allocation trace (WPR GPU profile) of one split+close, then bisect in-app.
