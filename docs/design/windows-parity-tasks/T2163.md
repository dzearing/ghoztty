# T2163 - Splitting one pane stops a busy pane elsewhere in the window from drawing: its renderer never presents another frame

## Summary

Found by T1160 on +95c284ad8 (ReleaseFast, test desktop, GHOZTTY_PERF=1). Window 'rep': probe pane, split right -> soak-stream (endless type), probe split down -> soak-altscr (PowerShell loop toggling ESC[?1049h/l, ~23 fps). The altscr pane logs 'perf pane=<id> fps=21-24' every second UNTIL soak-stream is split down (soak-grow) - from that moment the altscr pane logs NO perf line at all, i.e. drawFrameEnd (src/renderer/OpenGL.zig:470) is never reached again for it, while its terminal state keeps updating (+read shows fresh churn). Reproduced 4/4 (two full 30-minute soaks 20261022-103620 and 20261022-110922, two scripted repros; timeline in T1160's progress log: altscr samples 18:41:22..18:41:27, grow split 18:41:27, nothing after). Without the grow split the same pane renders the whole time. If the pixels are frozen too, a user splitting one pane sees a busy unrelated pane stop redrawing. First step: confirm on screen (PrintWindow / Get-TestWindowPixels over the altscr rect across the split); suspect the occlusion/visibility path (src/apprt/win32/occlusion.zig, PaneView/Window relayout after a split) marking a pane outside the split subtree as hidden. Repro script: the T1160 scratch repro shape (new-window, split stream, split altscr, wait 6s, split grow off stream).
