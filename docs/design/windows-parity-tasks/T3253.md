# T3253 - An agent too old to see the in-app update beside it is reported as 'replacing itself' forever - fall back to the waiting-update row instead of standing down

## Summary

Follow-up to T3251. Agents built before T3251 cannot see an in-app update (they look for a .bak rename through the frozen PEB path), yet they advertise capability.agent_handoff, so agent_upgrade.evaluate answers stale_handoff ('standing down') on every launch and the app does nothing - no menu row, no bound, no completion check. Every box running such an agent (the user's included: 20261116-1d7b2e7ba) stays on it until its last persistent window closes or a reboot. Fix: the app should only trust stale_handoff from an agent whose build can actually see the updater's sideline (a HELLO capability bump, or a stamp floor at the T3251 build), and otherwise classify as stale_handoff_draining/stale_live_deferred so the 'Background Update Ready...' row appears. Also bound it generally: if a stale_handoff check in this process sees the same running build again after N minutes, log 'handoff overdue' and show the row. Acceptance: test/win32 arm in agent-upgrade.ps1 - a handoff-capable agent that does not replace itself yields the waiting-update row within the bound and logs which path was taken. Wire-protocol change -> follow docs/claude/sessions.md (additive, capability-detected).

## In plain terms

After an in-app update, Ghoztty's background process could get stuck on its old
version, while the app kept telling itself "it's updating itself, nothing to do".
No menu row ever appeared, so there was no way to see or install the waiting
update. Now an older background process is no longer taken at its word: the
"Background Update Ready..." row shows up. And if any background process says
it is updating itself but is still the same version ten minutes later, the row
appears then too.

## Goals

- [x] The app trusts "replacing itself" only from an agent that can actually see an in-app update (new additive HELLO capability `agent_handoff_rename`)
- [x] A stand-down that is not kept within 10 minutes is logged as "handoff overdue" and shows the waiting-update row
- [x] Neither path restarts the agent or ends a session

## Design (mechanism calls, recorded per go.md 5b)

- **Capability, not a stamp floor.** A date floor on the build stamp would
  misread dev/debug stamps and any rebuilt old tree; a capability string says
  exactly what the agent can do. `agent_handoff_rename` is advertised by both
  sides (agent: Windows only, beside `agent_handoff`, and withdrawn with it by
  the T1038 kill switch), and `Connection.peerHandsOffItself` now requires both.
  Purely additive: an older app never asks, an older agent reads as legacy.
- **Overdue bound in the app**, pure in `agent_upgrade.HandoffWatch`
  (`observe(decision, running, now, bound)`): same running build seen standing
  down past the bound -> `Reason.stale_handoff_overdue` (`.none`, pending
  `when_idle`). A one-shot `msg_timer.handoff_overdue` (id 31) re-runs the check
  past the bound, because the check otherwise only runs at launch and on the last
  window closing. Bound: 10 min; `GHOZTTY_AGENT_HANDOFF_OVERDUE_MS` in debug.
- **Mac**: no change owed. The Mac agent does not advertise `agent_handoff`
  (the Mac handoff is increment 5 of the T705 split), so the stand-down arm is
  unreachable there; the new string rides with that work when it lands.
