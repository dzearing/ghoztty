# T2522 - Pace window-edge resize steps to the compositor: once the layout pass fits in a frame, each SetWindowPos must land just after a DWM compose so the pass has a whole frame before the new frame size is shown (T2516)

## Summary

T2516's film + GHOZTTY_RESIZE_TRACE (2026-10-30) shows DWM puts a resized frame on screen at the first compose after the SetWindowPos, whatever the app has painted, and WM_SIZE arrives ~1 ms after NCCALCSIZE on the window's own thread. So a pass shorter than the frame interval still shows stale content whenever the SWP lands late in the interval. Try DwmFlush (or waiting on the frame clock) in WM_WINDOWPOSCHANGING/WM_SIZING while a live resize is on and the size changes, so the step starts right after a compose; measure with resize-sync-onscreen.ps1 (async steps) at ReleaseSafe. Only worth doing after the pass fits a frame (the desk and nav tasks filed beside this). The complete fix is all content in one composition commit (T2508-T2511).

## In plain terms

The idea was to make each step of a window-edge drag start just after the
screen refreshes, so the redraw would always have a full refresh to finish in.
It was built and filmed, and it does not help: every step still shows one
out-of-step frame, and the drag gets visibly slower to follow the mouse. The
out-of-step frame comes from the web page drawing on its own schedule, which
only the "everything in one composition" work (T2510) can fix. The change was
not kept.

## Goals

- [x] build the pacing (DwmFlush in `WM_WINDOWPOSCHANGING`, only inside a size/move loop, only for a step that resizes, off for the gesture after an overrun) and film it against the same build with it off
- [x] decide from the film whether to keep it: no - see Findings

## Findings (2026-10-30, lane B)

Built as a pure rule (`resize_pace.zig`, four unit tests) plus a
`WM_WINDOWPOSCHANGING` handler with an A/B knob (`GHOZTTY_RESIZE_NO_PACE`),
filmed with `scripts\resize-sync-onscreen.ps1 -Exe zig-out-rsafe\...` (ReleaseSafe,
`GHOZTTY_RESIZE_TRACE=1`), 30 steps per drag, same build both ways:

| window | pacing | pass median | right-shrink bad/frames | left-shrink | right-grow | left-grow |
|---|---|---|---|---|---|---|
| 1400x800 | off | 13.2 ms | 30/64 | 30/64 | 61/64 | 62/66 |
| 1400x800 | on | 12.2 ms | 30/92 | 30/93 | 88/92 | 90/92 |
| 760x420 | off | 7.2 ms | 30/60 | 31/60 | 46/60 | 45/60 |
| 760x420 | on | 7.2 ms | 34/77 | 32/84 | 73/80 | 75/83 |

- **Shrink: exactly one bad frame per step either way**, at both sizes - even
  at 760x420, where the pass (7.2 ms) fits the 8.3 ms frame. So the task's
  premise ("a pass that fits a frame still shows stale content when the step
  lands late in the interval") is not what the film shows: the stale frame is
  there however much of the interval the pass gets.
- **What the bad frame is**: the WebView2 page still at its old width
  (`pageR=1356/barR=1369 right=2` on a shrink step) while the nav bar, a
  synchronous GDI child, is already at the new one. The page presents through
  WebView2's own compositor and lands a composition later than the frame and
  the GDI chrome. Pacing the step cannot move that; putting every surface in
  one composition commit (T2510, already a dep of T2516) is the fix.
- **Grow is bad on nearly every frame either way** (95%+): the page and the
  bar disagree by ~7 px for the whole step, not only its first frame. That is
  not a phase effect either; it is T2516's own subject, already covered by its
  deps.
- **Cost of pacing**: `DwmFlush` waited 6.7-17 ms (median 9.7 ms large, 13.3
  ms small), longer than a frame, so a step took ~3 compositions instead of
  ~2: the drag follows the mouse ~40% less often, for no fewer bad frames.

Not kept: the code is reverted (a pacing that only ever slows the drag is a
regression, and a dormant one is dead code). If T2510 lands and a film then
shows stale frames that ARE phase-dependent, this experiment is the starting
point: the diff is described above and takes about 50 lines.
