# T2641 - In the composition pane tree, the hero pane's picture is drawn too large after entering hero mode: a block painted at split size reads 720x148 px on screen where the painted path shows 480x115 (scripts\hero-glide-onscreen.ps1 rest-before)

## Summary

Found by T2573's film (`scripts\hero-glide-onscreen.ps1`). Two panes side by side, each painted with a 12-row x 40-cell solid block, then hero mode (F9 = toggle_hero_mode) with the left (red) pane as the hero. At rest, before any selection change:

- `off` arm (no composition knobs): red reads 120-599 x 54-168, 115 rows.
- `tree` / `stall` arms (COMP_PRESENT + COMP_CHROME + COMP_PANE_TREE): red reads 133-853 x 54-201, 148 rows - wider and taller, so the hero pane's picture is scaled up (about 1.5 x horizontally, 1.3 x vertically) rather than re-rendered at the hero size.
- Same with `GHOZTTY_HERO_DECLARE=0`, so it is not T2573's slide; the slide's landing (blue, after) matches the painted arm to the pixel.

Likely shape: on the hero-mode re-layout the pane window grows from half the row to the hero rect, and the tree visual is placed (or its swap chain presented) at the new size before the renderer has drawn a frame at it - the stretch is the old buffer filling the new rect. Check what `syncTreeVisual` / the composition swap chain does on a resize in tree mode (T2566 banner band, `gridBand`).

- [ ] The same block measured at rest after entering hero mode is the same size on the painted and tree paths
