# T3136 - Single-window mode on Windows (Mac 3f772a2f0 macos-window-mode = single): one top-level window, every new window/+new-window/restore becomes a workspace in it, switched in place from the pane sidebar's all-windows list with the gradient crossfading; parked workspaces keep running but stop drawing; CLI sees no difference

## Summary

Mac 3f772a2f0 (+9b05b54a4 parked title kept for +list, 51e6e5aba sidebar row x closes a parked workspace, 8c6987575 workspace takes first responder on show without replaying the blade stack). Config macos-window-mode separate|single, read at launch. Every workspace keeps its own controller; only the native window is shared; a parked workspace's terminals stop rendering and give back render targets; viewers stop polling; IPC/+list/+close/--focus reach parked workspaces (--focus switches); session manifest gains additive 'frontmost' so the window that was in front comes back last (honor it on Windows restore in both modes). docs/reference/window-modes.md is the spec. Windows already has tabs per window; the translation is one HWND hosting several Window controllers' content, swapped from the sidebar. Large: split into children (config + manifest frontmost; parking/stop-drawing; sidebar switch + crossfade; IPC/list/close reach) when planned.

## In plain terms

On the Mac you can choose to keep everything in ONE window: every "new window" becomes a workspace inside it, and you flip between them from the pane sidebar. Windows does not have that yet. This task is the whole feature; it is split into eight smaller pieces that land one at a time.

## Details - the Windows translation (decided 2026-11-16)

**One shared top-level HWND, adopted and surrendered by Window controllers** - the same shape as the Mac's one `NSWindow` shared by several `TerminalController`s. Considered and rejected: one hidden top-level HWND per workspace, swapped at the same frame. It needs almost no refactor, but the user would see it: the taskbar button vanishes and reappears on every switch, DWM show/hide animations play, Alt-Tab and virtual-desktop membership follow the hidden windows, and each switch fires a deactivate/activate pair. The Mac experience is one window that never blinks, so the shared HWND is the faithful port, and this is a mechanism call (no experience fork), so no decision was filed.

Why it is workable here: panes are already WS_CHILD HWNDs that move between top-level windows (`adoptPane`, `src/apprt/win32/Window.zig:7278`, used by pane drag-to-window), their overlays are owned popups that follow, and `Window.hwnd` is already optional. A parked Window has `hwnd = null` (controller->window work is skipped, as on Mac); its pane HWNDs are reparented under a hidden park host so they survive the shared window closing; inactive-tab hiding (`setTabSurfacesVisible`) and the T3035 background-viewer path are the not-drawing half.
