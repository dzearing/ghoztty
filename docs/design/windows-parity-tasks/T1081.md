# T1081 - The pre-fixture reset half of CleanSlate: converted scripts kill, but still do not clear the debug restore state

## In plain terms

A test script that wants a clean box has to do two things: close the app, and
forget the saved window layout. T351 gave every script the one shared way to do
the first. The second is still missing from about 120 of them, so a window a
previous run left behind can be restored into a run that asked for an empty box -
and the script then measures last run's window instead of building its own.

## Summary

T351 converted 130 scripts to the shared **kill** (`Stop-RepoGhoztty`), which was
the safe half: it preserves each script's existing semantics exactly and cannot
break a test that relies on the manifest surviving. What it deliberately did NOT
do is upgrade each script's PRE-FIXTURE call to the full
`Reset-GhozttyTestState`, which also drops
`%LOCALAPPDATA%\ghoztty\session-layout-debug.json` and the debug agent's
`layouts.json`.

That is the original T248 defect and it is still live: with the manifest intact,
`+new-window --target=X -e <fixture>` FOCUSES last run's pane instead of running
this run's fixture, and a `+read` or pixel oracle then measures the previous
build and passes. Observed for real building `color-contrast.ps1` (T150).

Why it needs per-script judgement rather than another sweep: a call site is safe
to upgrade only when it is the pre-fixture reset. The session-* family calls the
same helper MID-TEST to simulate an app restart, and there the manifest is the
thing under test - clearing it would break the assertion rather than isolate it.
Roughly 87 scripts call their helper exactly twice (setup + teardown, both safe);
the rest need reading.

## What to do

- For each converted script, decide whether its FIRST call is the pre-fixture
  reset (before the first launch). If it is, that call - not necessarily the
  helper - becomes `Reset-GhozttyTestState`.
- Where a script calls the helper mid-test to restart the app, leave it on
  `Stop-RepoGhoztty` and say in a comment that the manifest is deliberately kept.
- The session-* family and the agent upgrade/recovery scripts want `-AppOnly`
  with the manifest still cleared at setup, which the shared reset already does.
- Batch it: the guards the edits make due have to be re-run, and that is the real
  cost. One family per turn.

## What it turned out to be (2026-10-18)

Most of the premise had already been retired by later work. Since T351 was
filed, T1012 made every launch declare its persistence intent and T1983/T691
moved scripts onto private endpoints and lineages, so nearly every converted
script now runs in a throwaway `LOCALAPPDATA`, under a per-run agent lineage
(the manifest and `layouts.json` follow `GHOZTTY_AGENT_INSTANCE`), or with
`--session-persistence=false`. In all three cases no stale manifest is
reachable.

Inventory of the 228 `test\win32` scripts that call `Stop-RepoGhoztty`:
excluding those that already call `Reset-GhozttyTestState`, set
`$env:LOCALAPPDATA`, mint a lineage/isolation, pass persistence off, or clear the
manifest themselves left 8. Four of those never launch into the ambient state
(`acceptance-parallel`, `agent-adopt`, `gui-postmortem`, `test-desktop-spike`).
The other four were the live remainder of the T248 defect: they launch with
persistence ON in the ambient `LOCALAPPDATA` and cleared only
`sessions.json`/rings:

- `chooser-session-cpu.ps1` - `Start-Fixture` now opens with `Reset-GhozttyTestState`
- `chooser-sessions-push.ps1` - same
- `chooser-session-sort.ps1` - the setup call now resets; the run-2 relaunch stays
  a kill, commented as a RESTART whose own manifest is the point
- `history-guard-flavor.ps1` - setup and each trial's fresh-agent reset
