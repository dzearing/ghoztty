# T1380 - Send-TestControlKey accepts -Modifiers and silently drops them

## Summary

`Send-TestControlKey -Modifiers shift` takes the modifier, sets it with
`SetKeyboardState` on the harness worker thread, and posts the key - but it
never attaches that thread's input queue to the app's, so the app's own
`GetKeyState` answers for a queue in which nothing is held down. The modifier
is dropped and NOTHING SAYS SO: the keystroke lands as a bare key and whatever
the script was asserting about the chord quietly becomes an assertion about the
unmodified key.

Measured while adding T569's backwards-Tab probe: the four Shift+Tab steps land
on the BACKWARDS neighbour through `Send-TestKeys` and on the FORWARD one
through this helper. The doc comment now warns about it and names
`Send-TestKeys` as the route that works (which it does for a dialog/panel child
control, not only for a terminal surface - the difference is the attachment,
not the target). No script currently passes `-Modifiers` to this helper, so
nothing is red today; what is left is a parameter that is a trap for the next
person who reaches for it.

The fix is one of two shapes, and the choice is a mechanism call rather than
anything a user can see: either give it the same `AttachThreadInput` bracket
`SendChord` has, so `-Modifiers` means what it says, or REMOVE the parameter so
the helper cannot be asked for something it will not do. Removing is the
smaller surface and the doc comment already routes callers elsewhere; attaching
is the smaller diff for a caller who wants a chord at a control. Either way the
demonstration is the same and it already exists in reproducible form - swap
section L2b of `test/win32/activity-monitor.ps1` onto this helper and watch the
first step land on "Show all".
