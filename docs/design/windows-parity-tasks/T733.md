# T733 - A -Dtest-filter run can pass while running none of the tests it named

## In plain terms

There is a way to run just a few of our tests instead of all of them, so a
change can be checked in seconds rather than six minutes. Measured during T222,
that shortcut reported success while apparently running nothing at all — over a
build that was deliberately broken and that the full run caught immediately. A
shortcut that says "fine" when it checked nothing is worse than no shortcut,
because it is trusted.

## Summary

Measured on the box during T222, in this order, from the same tree:

1. `zig build test -Dapp-runtime=win32 -Dtest-filter="T64"` — **exit 0, zero
   output**, against the correct predicate.
2. The `VK_PACKET` exemption in `translate_policy.skipTranslate` was then
   deliberately removed (T222's negative control).
3. `zig build test -Dapp-runtime=win32 -Dtest-filter="T64"` again — **exit 0,
   zero output**, over the broken tree.
4. The same command with **no** `-Dtest-filter` — **exit 1**, naming
   `apprt.win32.translate_policy.test.T64: VK_PACKET is translated even on a
   terminal surface` and `...test.the exemption reads the low word...`.

So the filtered run did not execute the tests whose names contain `T64`, and
said nothing about it. `-Dtest-filter` is a real option (`build.zig:42`, fed to
each test step's `.filters`), and `scripts\floor-lane.ps1 -Filter <f>` is
documented in `go.md` step 3 as the way to re-run a lane narrowly — which is
exactly the path that would be trusted here.

## Details

Unknown at filing time, and the point of the task is to find out rather than
guess. Candidates worth separating:

- Zig's `--test-filter` matches the fully-qualified test name; ours contain
  `T64` as a substring, so a plain substring match should have hit. Check what
  the build actually passes to the test binary.
- `build.zig:452` has a `if (test_filters.len == 0)` branch — find out which
  step it gates and whether a filtered `test` step still runs the win32 unit
  binary at all.
- A run step reporting **cached** prints nothing and exits 0; a filtered build
  whose binary was already cached could look identical to a real green run.
  Step 3 above compiled changed source, so this alone does not explain it.

Whatever the cause, the fix has to make an empty match **loud**: a filter that
selects zero tests must not be reported the same way as a filter that selected
tests and they all passed. That is the vacuous-green shape T216, T217 and T219
are all about, and this one hides inside the tool the other three are run with.

## Validation criteria

- [x] The cause is named from evidence (what the filtered lane ran, or did not).
      `GHOZTTY_TEST_FILTER_DUMP=1` — added here, because those names exist only
      in the run's test metadata — prints every test the guarded binaries
      contain. Under `-Dtest-filter=VK_PACKET` the win32 binary contains **zero
      named tests**: only the 83 unnamed `_ = @import(…)` aggregators, which are
      compiled in whatever the filter says and all pass. That is the whole of
      the 2026-08-11 "exit 0, zero output". The reason none were selected is
      that zig 0.15.2's compile-time matching is **not** a plain substring of
      the name the runner prints: `translate_policy` selects all nine tests of
      that module, while `T64:`, `VK_PACKET`, `win32.translate_policy`,
      `translate_policy.test` and the entire printed name
      `apprt.win32.translate_policy.test.T64: VK_PACKET is translated even on a
      terminal surface` each select none.
- [x] A filter that matches zero tests reports that fact and does not exit 0
      silently. T631 landed the build-side guard; verified here on T733's OWN
      command — `zig build test -Dapp-runtime=win32 -Dtest-filter=VK_PACKET`
      now exits 1 with `-Dtest-filter matched no tests, so \`zig build test\`
      proved nothing`, where in August it exited 0 in silence. Sections A and F
      of `test\win32\test-filter-guard.ps1`. Recorded limit: the guard answers
      *did anything match*, not *did what you meant match* — the literal August
      command `-Dtest-filter=T64` is green today because
      `apprt.win32.viewer_bridge.test.T641: …` matches it. The dump is how a
      caller checks that.
- [x] Negative control: with the `VK_PACKET` arm dropped from
      `translate_policy.skipTranslate`, `-Dtest-filter=translate_policy` fails
      naming `apprt.win32.translate_policy.test.T64: VK_PACKET is translated
      even on a terminal surface` and `…test.the exemption reads the low word…`
      — so a filtered run does catch it, without the six-minute lane. The same
      broken tree under `-Dtest-filter=VK_PACKET` does NOT catch it and fails as
      matched-nothing instead, which is exactly why the guard is the deliverable
      rather than a rule to remember.
- [x] Documentation says what a filtered run does and does not prove:
      `docs\claude\testing.md` (write the filter as a module segment; the dump
      env var; what the guard makes survivable), the `.PARAMETER Filter` block
      in `scripts\floor-lane.ps1`, and the module header of
      `src\build\TestFilterGuard.zig`. `go.md` step 3 points at
      `docs\claude\testing.md` for the harness rules and is unchanged.
