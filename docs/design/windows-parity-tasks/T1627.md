# T1627 - pane-ingest-ab B4 flakes: the pane is judged dead while the app is still digesting the 400k-chunk burst

## Summary

`test\win32\pane-ingest-ab.ps1` scored `FAIL B4 the agent-held pane is still LIVE
afterwards` on 2026-09-16, and the same script over the same tree was ALL PASS on
the immediately following run. The app's own log names the state it was in: the
liveness probe's `+list` reported
`ipcperf action=list accept=18445ms`, and the renderer was at `fps=1` with
`max_gap_ms=~608`. Nothing was dead - the app was still working through the
400,000-chunk burst the arm had just fired at it, and the probe's timeout is
shorter than that digestion takes on a loaded box.

So the oracle is measuring the wrong thing at the wrong moment: B4 is there to
prove the pane SURVIVED the burst, and a pane that answers 20 seconds later
survived it. Either the probe waits for the app to go quiet first (the ingest
numbers B3 scores already say when the workload finished, not when the app
caught up), or its budget is scaled to the burst it follows.

## In plain terms

A stress test occasionally reports the terminal as dead when it is only busy
finishing the enormous amount of output the test just threw at it. Nothing is
wrong with the terminal; the test asks it a question before it can come to the
phone.

## Goals

- [ ] B4 does not go red for a pane that is merely still catching up.
- [ ] It still goes red for a pane that is genuinely dead (a negative control).

## Validation criteria

- [ ] Ten consecutive runs of `pane-ingest-ab.ps1` with no B4 failure.
- [ ] A deliberately killed pane still fails B4.
