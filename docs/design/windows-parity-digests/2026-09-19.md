### Reflection

Yesterday's theme was background jobs interfering with foreground evidence.
Today's is narrower and sharper: **we chased a stderr line for four turns
because the tool put it where the cause belongs.** Zig's build runner prints
`error: <test> failed: <text>` with whatever stderr happened to arrive, every
test in the binary shares one stream, and our own lane wrapper keeps the first
six `error:` lines — so the misattributed line is exactly what survives into
the kept output while the real error return trace, which carries no `error:`
prefix, is dropped. Five progress-log entries were written about a warning
emitted by a *passing* test.

The lesson generalises past Zig: **every place we summarise a failure is a
place we can lose the cause.** The lane wrapper's six-line window, the guard
report's one-line-per-row, the digest itself — each is a lossy projection
chosen before we knew what we would need to see. The rule worth adopting is
that a summary must be *anchored*: keep the lines that name the thing that
failed, not the lines that happen to match a pattern. T1662 does that for the
lane wrapper; the same question is worth asking of the suite-run summary and
of `guard-due`'s output.

The other thing the resume exposed: **a memo with a TTL is a bet that nothing
changes inside the window, and we keep making that bet without writing down
who loses it.** The viewer's directory memo had a comment naming exactly the
mutation that would break it — `git init` — and it broke on exactly that. A
comment that predicts a failure is not a mitigation. Where we cache, the cache
should be reachable only by the caller whose repetition justified it, which is
what the fix does.

Structurally, nothing has moved on the cutover: it is still gated on the Mac
seat (T87) and on merging `origin/main` into this branch, and `origin/main`
has not moved in four days.

## Feature ideas

### Trusting what a pane tells you

- **Say which repository this pane is filing against** — *High.* The viewer's
  feedback button, the git-status pane and the diff pane all act on "the
  repository this file is in", and today that answer is invisible until it is
  wrong. Put the repository's name in the pane's own chrome, so the pane you
  are about to send a report from says where it is going.
- **A pane that notices the folder underneath it changed** — *Medium.* Create
  a repository, switch branches, or move a checkout, and the panes watching
  that folder catch up on their own instead of at their next navigation. You
  would feel it as the terminal never being a few minutes behind reality.

### Getting out of a mistake

- **Take back the last thing I sent to a pane** — *High.* One chord after an
  accidental paste or a mis-sent command, and the terminal shows exactly what
  it delivered and offers to interrupt it. Today the only recovery is Ctrl-C
  and hope, and you never get to see what actually went down the wire.
- **A confirmation that shows the blast radius** — *Medium.* When closing a
  window would end sessions, name them — "3 panes, 2 with something running" —
  instead of asking a generic question. The answer you need is what you are
  about to lose, not whether you are sure.

### Reading a long day

- **Show me today, as a timeline** — *High.* One view across every window and
  session: what ran, how long it took, what failed, what is still going. The
  data is already being captured for the activity monitor; what is missing is
  the shape that answers "what happened while I was away".
- **Search everything I have seen, not just this pane** — *Medium.* One box
  that searches the scrollback of every open and restored session at once, and
  takes you to the pane and line that matched. Find-in-pane exists; the
  question people actually ask spans panes.

### Under the floor

- **Keep the line that names the failure, not the line that matches the
  pattern** — *Medium.* Every failure summary we print — the lane wrapper, the
  suite runner, the guard report — chooses what to keep by pattern, and today
  that cost four turns chasing a warning from a passing test. Anchoring each
  summary to the thing that actually failed would make a red run readable the
  first time. You would feel it as fixes arriving without three turns of
  detour.
