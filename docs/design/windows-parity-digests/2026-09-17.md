### Reflection

Three days running, the work has converged on one theme, and it is worth naming
because it is a design rule rather than a backlog category: **the app knows more
than it says.** The meter knew its stream was dead. The roster knows when it has
stopped being updated. The relaunch knows it restarted the shell. In each case
the code had the fact and the screen kept the old picture, because "keep showing
the last good thing" is the path of least resistance in every UI framework ever
written. A stale reading is not a smaller version of a fresh one; it is a
different claim, and presenting the two identically is the defect.

What follows from that, and is worth making standing policy: **any live
indicator needs an answer to "what does this look like when the feed stops?"
before it ships.** Today's staleness rule is the first one written as a rule
rather than as a fix — stated on silence, not on any particular cause, so it
covers the causes nobody has thought of. The other live surfaces (the Activity
Monitor's process table, the connection pill, the session roster) should each
get the same question asked of them. That is maybe three tasks and it would
close a class.

The other recurring theme is **the harness paying for its own thoroughness.**
A one-line change to `MachineChooser.zig` cost four separate GUI acceptance runs
this morning — twenty-plus minutes of wall clock — because four guard rows name
that file. The guard rows are right, and the fifteen-minute `-Lane harness`
sweep is right, but the shape is becoming "one small fix, an hour of proving
it". Worth thinking about: can the guard runner batch every due GUI harness into
one desktop session and one app launch, instead of each script standing up its
own fixture from scratch? Most of the cost is fixture, not assertion.

## Feature ideas

### Finding your way back to work

- **Name a session, not a folder** — *High.* Give a persistent session a name
  you chose ("api build", "prod tail") and have that name be what the chooser,
  the tab and `+sessions` show. Six sessions all called `C:\Users\David` is the
  single biggest reason the chooser is harder to read than it should be.
- **Go to a session by typing its name** — *High.* One chord opens a one-line
  box that fuzzy-matches every session on every machine you can reach, and Enter
  attaches to it. The chooser is a list you browse; this is the thing you use
  when you already know where you are going.
- **A chooser that opens on what you used last** — *Medium.* Preselect the
  machine and session you last attached to, so the common case is open-and-Enter
  rather than open-and-hunt.
- **Copy a link to this session** — *Medium.* Right-click a session, get a
  `ghoztty://` link that attaches to it, and paste it into your notes or a PR
  description. The scheme already exists; nothing offers you a link to a session.

### Knowing what your machines are doing

- **Say what a pane is waiting ON** — *High.* "Idle at a prompt" and "blocked on
  a password prompt" look identical everywhere in the app today. A pane that is
  waiting for YOU is the one thing you want surfaced — in the tab, in the
  chooser and in the taskbar.
- **Jump to the session eating the box** — *Medium.* The CPU meter already knows
  which session is pinning cores. Make the number a target: click it and you are
  in that session, wherever it lives.
- **Tell me when the long one finishes** — *Medium.* Any command past a
  threshold posts a Windows notification when it exits, with its exit code, and
  clicking it focuses the pane. The information exists; it just never leaves the
  window you walked away from.

### What changed while you were away

- **A re-attach that catches you up** — *Medium.* Coming back to a persistent
  session, a foldable notice at the top lists what completed while you were
  gone and how each command exited. Today a re-attach hands you a wall of
  scrollback and leaves the reading to you.
