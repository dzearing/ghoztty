## Commentary

### Yesterday

Two halves to the day, and the first one you can see. **A diff pane can now be
walked change by change**, side by side, the way the Mac one always could — so
reviewing a branch in a side pane stopped being a scroll-and-hunt exercise. The
same pane also stopped being able to **hang forever on a wedged `git`**: it now
gives up and says so instead of sitting there looking busy. **The command
palette and the find bar redraw properly when a window moves between monitors**
— before that they could come back half-painted at the new scale. And the
**machine view stopped losing your own sessions on a busy box**: the process
snapshot used to stop counting at 512 processes, which on a loaded machine meant
the sessions you were looking for fell off the end.

The second half was spent making this box's test results mean something again,
and it was worth the day. A background job that hunts a rare crash in the
machine's idle time had started **killing the builds and test binaries the main
job was running**, so lanes were going red with a bare exit code and no
explanation — twice inside twenty minutes. That is the worst possible failure
mode for a loop that decides what to work on from lane results. Two fixes later
(T1648, T1649) a red lane means red code again, and an overlapping run can no
longer reap another run's processes.

**What shipped: `win-v1.36.28`, on 2026-09-17, at commit `f0a7bfd37`.** That is
what your terminal is offering, and it carries the diff-pane navigation. It does

### Reflection

The soak-daemon incident is the interesting thing to sit with, because it is a
new failure class rather than a new bug. We have been steadily adding
*background* work to this box — an idle crash hunt, a supervisor, a watchdog,
a daily publish — and each one was designed as if it were the only thing running.
Yesterday two of them met, and the symptom was not "the background job failed",
it was "**the foreground job's evidence became untrustworthy**". A lane went red
for a reason that had nothing to do with the code under test. That is a much
more expensive kind of wrong than an outage, because it is silent and it makes
you distrust the right things.

The rule worth writing down from it: **any background job that can touch
processes must be able to name what it owns, and touch only that.** Both fixes
landed that way in the end — ownership by pid lineage rather than by image name
— but they landed after the fact, twice, for the same reason. The other
background jobs on this box (the watchdog's restarts, the delivery audit, the
publish) should each be asked the same question before something else meets
them.

Beside that, yesterday's harness-cost observation stands and is now a card:
a one-line change to a GUI file can trigger four separate acceptance runs, each
standing up its own desktop, app launch and fixture from scratch. Most of that
twenty minutes is fixture, not assertion. Batching every due GUI harness into
one desktop session is a day's work that would pay back weekly, and it is filed
rather than admired this time.

The other thing today's numbers say out loud: with the P0/P1 band empty, **the
cutover to `main` is now the only structurally large thing left**, and it is
still gated on the Mac seat (T87) and on merging the `origin/main` commits into
this branch. Nothing this seat does to the P2 tail moves that gate. It may be
time to ask what the smallest honest version of the cutover looks like.

## Feature ideas

### Reaching a machine that is not there yet

- **Wake a machine that is asleep, from the chooser** — *High.* A machine you
  have used before shows up dimmed with a "wake" action; one click sends the
  magic packet and the chooser waits for it to answer, then opens the session
  you asked for. Today a sleeping box is indistinguishable from a dead one and
  the fix is to go find it physically.
- **Tell me when a machine comes back** — *Medium.* Mark an unreachable machine
  and get a quiet notification the moment it answers again, with the session you
  were trying to reach one click away. Reconnecting today means re-opening the
  chooser every few minutes to check.

### Working with a machine that is not this one

- **Drop a file onto a remote pane and have it arrive there** — *High.* Drag a
  file from Explorer onto a remote or WSL pane and it is transferred to that
  machine's working directory, with the path pasted ready to use. The connection
  is already open; today you leave the terminal to use another tool to push a
  file down it.
- **Open a remote machine's file in a viewer pane beside it** — *High.* Click a
  path printed by a remote pane and get the rendered file in a local side pane —
  a log, a README, a diff — without copying it anywhere first. Viewer panes only
  understand local paths today, which is exactly backwards from where the
  interesting files live.

### Reading a machine at a glance

- **A machine row that says more than CPU** — *Medium.* Memory pressure, free
  disk and uptime on the machine row in the chooser, in the same small-type
  strip as the CPU meter. "Which box should I run this on" is the question the
  chooser is actually asked, and it currently answers a third of it.
- **Press a key, jump to any pane** — *Medium.* One chord labels every visible
  pane across every window with a letter; press it and you are there. Link
  hinting is already planned for what a pane *printed*; this is the same
  gesture for the panes themselves, and it is the fastest way to cross a
  four-window layout without the mouse.

### Under the floor

- **One desktop, one app launch, every due GUI check** — *Medium.* The
  acceptance harnesses each build their own desktop, launch their own app and
  tear it all down, so one small change can cost four full fixtures and twenty
  minutes. Batching every due GUI harness into a single session would turn that
  into one. You would feel it as fixes arriving faster, not as anything on
  screen.
